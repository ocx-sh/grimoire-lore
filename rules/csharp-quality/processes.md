# Wrapping an External CLI

Binds to .NET SDK 10.0.401 on Linux x64 with runtimes 8.0.31 and 10.0.12, TFMs net8.0 and net10.0, BannedApiAnalyzers 5.6.0 and
VS.Threading analyzers 18.7.23 (measured 2026-10-11). Windows rows were measured on Windows 11 build 26200 with SDK 10.0.102,
runtime 10.0.2 and console code page 437 (measured 2026-10-11). macOS, arm64 and linux-arm64 rows are `unverified: read only`.

Owns how a .NET library (**the SDK**) starts a wrapped command-line tool, feeds and drains its streams, stops it and classifies
its exit. Not owned here: CS-BIN owns acquiring, pinning and verifying the binary, and CS-TEST-01..04 owns the fake-CLI harness
that every real-child behaviour below is asserted with, so those rows cite it instead of re-running a child. Neighbours cite by
ID: `CS-ERR` the exception tree, the one exit table and `ChildExit`, `CS-ASYNC-08` the cancel-versus-timeout shape, `CS-XP-11`
the `TimeProvider` bans, `CS-OBS-26` the log-level flag, `CS-JSON` the decode seam, `CS-SEC-07` the jitter source and
`CS-BUILD-13` warnings as errors.

`ocx`, `OcxProcess`, `OcxInvocation`, `ChildExit`, `IsOcxError`, `OcxException`, `OcxCommandException`, `OcxTimeoutException`,
`OcxRetry.cs`, `ExitTable.cs`, `OcxCommandException.cs`, the `OCX_*` variables, exit 75 with
`temp_fail` and the tool's JSON member names (`exit_code`, `error.kind`, `detail`, `status`, `contract`) are example names from
the reference consumer; rename them once, together with every command below that spells them. Every verification command keeps
working on the example names. Defaults an adopter may override once: the 16 MiB output cap
(`CS-PROC-10`), the 5 s drain and reap bounds (`CS-PROC-13`, `CS-PROC-14`), kill grace 0 and no job object for cancellation
(`CS-PROC-14`, `CS-PROC-18`), the 7-key scrub deny-list (`CS-PROC-06`), the 64 KiB document head and the heuristic tool-reported flag
(`CS-PROC-21`).

## Conventions

Every `rg` command runs from the repository root. `SRC`, `TESTS`, `SLN` and `BASE` are the operand variables of the index
Conventions (`SRC` is the space-separated product source directories, written unquoted as `$SRC`), and `SCOPE` is its test-exclusion
glob array: every `*.cs` command writes `-g '*.cs' "${SCOPE[@]}"`, the exclusions after the include glob because a later `-g` wins,
and retypes no glob. Every cell and block starts with the guard `: "${SRC:?MISSING SRC}" "${SCOPE:?MISSING SCOPE}"` (add `TESTS`,
`SLN` or `BASE` where it reads one) and runs its commands in the same shell: an unset `SRC` expands to nothing, `rg ... $SRC` then
reads stdin or the working directory and passes vacuously, and a `[ -d ]` loop does not catch that. The commands then run as
`if applies; then <commands>; fi`, with `applies any` for a `[launches-process]` row. `applies` (P0) prints `MISSING repo-relative SRC`,
`MISSING scanned zero files` or, on a tree with no launch seam, `N/A: no launch seam` on stdout, and the commands do not run. The
verdict is always stdout and never a status: empty is the pass once `applies` passed, a `MISSING` line fails, `N/A:` means the row
does not apply, and `rg` exit 2 (a directory operand that does not exist) is a failure, never a pass.

Every row opens with its applicability tag. `[cli-wrapper]`, the default of this family, is a library whose purpose is wrapping one
tool, and its launch seam is a file `tools` lists. `[launches-process]` binds only `CS-PROC-01`, `-09`, `-11`, `-12` and `-14` and
applies to any child launch, a pager included. `[json-cli]` binds `CS-PROC-07` and `CS-PROC-19` to `-22` and applies when the
wrapped tool prints JSON documents the SDK decodes. A row outside its tag is silent. A row that needs an API missing on a project's
lowest TFM also binds `[greenfield]` and names its fallback; the ban file is the greenfield posture, so that fallback line is an
RS0030 error until it carries `#pragma warning disable RS0030 // <reason>` inside the one seam (`CS-CORE-01`). A row about
process-wide state also binds `[library]`, because an application owns its process. Ban lines are the CS-PROC section of
`.claude/rules/dotnet-build/checks/BannedSymbols.txt` and severity lines live in `.claude/rules/dotnet-build/checks/analyzers.globalconfig`; a
row names the symbol or the diagnostic ID and never copies the line. RS0030 reports nothing unless the ban file is an
`AdditionalFiles` item of each shipped project (`CS-PROC-01`, P18). A command with a pipe is a block under
[Pipeline Checks](#pipeline-checks), and P0 there defines the seam finder `seams`, `tools` and the probe `applies` that the blocks
and cells call, under bash 4+; the cell cites a block as P1 to P19 (a regex alternation also needs a block, because a bare `|` splits a table
cell). "Watched" means a planted defect ran red and its twin ran green on both net8.0 and net10.0 (measured 2026-10-11);
behaviours that need a real child cite `CS-TEST-04`.

Interactive-child clause for `CS-PROC-02`, `-03`, `-05`, `-09`, `-14` and `-15`: a user-facing interactive child, a pager or an editor, is not a wrapped tool.
Its seam may inherit stdout and stderr (the child owns the terminal), name an OS utility (`less`) as `FileName`, catch any start failure to
fall back to plain output, wait with `WaitForExit()` and no timeout until the user quits, and force-close with a root-only `Kill()`, provided
the `FileName` and `catch` lines and the pragma line over each banned wait or kill carry a same-line `// interactive child: <reason>` comment
(`#pragma warning disable RS0030 // interactive child: <reason>`). It still redirects stdin, builds argv with `ArgumentList` (`CS-PROC-01`) and starts no shell. P9, P11, P14 and P16 and the `FileName` cell of
`CS-PROC-03` skip what carries the comment, `tools` of P0 leaves the file out, and a wrapped tool never uses the clause. Watched on a pager fixture: without the comments P9 printed the four missing members, P13 the file, and P16 the kill and the timeout; with them `tools` listed nothing and P9, P16 and the `FileName` cell were silent, while a tool seam beside the pager was still checked (measured 2026-10-11).

Resolver contract for `CS-PROC-03`:

1. One resolver, one order: (1) the explicit option, (2) the SDK override variable, (3) the tool's re-entry pin variable if it
   defines one, (4) rooted PATH entries, absolute entries only, the cwd entry skipped on Windows, the exact name
   `ocx`/`ocx.exe` with no PATHEXT, a hit that fails the trust check skipped, (5) the tool's home: the stable symlink in its
   data root, kept unresolved, same trust check, (6) the opt-in download of `CS-BIN-06`, never implicit.
2. The data root of tier 5 comes from the `CS-XP-04` environment snapshot; never read `HOME` straight from the process
   environment, and never steer the lookup through `psi.Environment["PATH"]`.
3. Tiers 1 to 3 are caller or operator intent and are never trust-checked.
4. The POSIX trust check refuses a real target whose directory or file is group- or other-writable; Windows is `CS-PROC-25`.
5. Each skipped hit appears as `dir: reason` in the not-found launch error.
6. `CS-BIN-01` starts only the rooted result.

ACL contract for `CS-PROC-25`:

1. One `[SupportedOSPlatform("windows")] internal static class PathAcl`, with the attribute on the class and never on a method,
   called only under `OperatingSystem.IsWindows()` from the resolver (`CS-PROC-03`) and never for tiers 1 to 3.
2. Resolve junctions and symlinks first (`ResolveLinkTarget(true) ?? fsi`).
3. Read `Access` and `Owner` sections only, through `GetAccessRules(true, true, typeof(SecurityIdentifier))`, never `NTAccount`.
4. The trusted set is an allow-list of SIDs (the user, `S-1-5-18`, `S-1-5-32-544`, `S-1-3-0`, TrustedInstaller), never a
   deny-list; an untrusted owner refuses.
5. The mutating mask is exactly `WriteData`, `AppendData`, `ChangePermissions` and `TakeOwnership`.
6. Only Allow ACEs count, inherited ACEs count, and `InheritOnly` ACEs are skipped on directories only.
7. Fail closed on `UnauthorizedAccessException`, `IOException` and `InvalidOperationException` and nothing broader.

## Pinned Decisions

Pinned for this set; an adopter overrides once, in the engine, with the reason recorded.

- **The SDK owns its engine and depends on no process library.** A wrapper that builds string argv, probes the cwd, resolves
  `.cmd`, has an unbounded drain or extracts a signaller exe fails four rows here, and RS0030 cannot reach inside a dependency.
- **PATHEXT is not honoured.** .NET ignores it (code 2) and batch files bring `CS-PROC-04`.
- **A pipe held past exit returns a flag, not a timeout.** The result is complete, tree kill reaches nothing after a natural exit
  on Linux, and `DrainTimedOut` tells the caller (`CS-PROC-13`).
- **Kill wiring is catch-based**, not `ct.Register`, which races the awaiting continuation (`CS-ASYNC-08`; the `CS-PROC-14`
  grep finds a `Register` lambda that kills). `Kill(entireProcessTree: true)` throws `NotSupportedException` on a platform
  without tree kill, so a target that includes one adds it to the filtered catch of `CS-PROC-14` and falls back to a root-only kill.
- **No CRLF normalisation and no per-chunk decode**: byte pumps translate nothing.
- **`CS-ASYNC-09` stays compatible**: `WaitAsync` bounds only waits after the process exited or was killed, each such line
  carries the same-line `//` comment naming what stops the work (`CS-PROC-13`, `CS-PROC-14`), and the work timeout is the
  timeout source of `CS-PROC-15`.
- **`login`-style commands promise no credential check**: exit 0 does not mean the credential was verified, so a result type
  carries no `Verified` member.

## What Agents Get Wrong Here

Ranked by how often the idiom appears in training data and in surveyed wrappers (10 of 10 keep a string argv path and 5 of 10
call bare `Kill()`).

1. **`psi.Arguments = $"install {pkg}"`, `string.Join(" ", args)`, `Process.Start("ocx", "version")`.** `CS-PROC-01`.
2. **`ReadToEnd()` on stdout then stderr, or two sequential `await ReadToEndAsync()`**, and **`p.WaitForExit()` after
   `WaitForExitAsync` "to flush output"**. `CS-PROC-09`.
3. **`p.Kill()` on cancel**, `taskkill /T`, `GenerateConsoleCtrlEvent`, a default SIGTERM grace, a `CreateJobObject` P/Invoke for cancellation.
   `CS-PROC-14`, `CS-PROC-18`.
4. **No `StandardInputEncoding`, or `Encoding.UTF8` on stdin**, because Linux is UTF-8 and CI runs at cp65001. `CS-PROC-11`.
5. **`FileName = "ocx"`**, PATHEXT scanning, accepting `ocx.cmd`. `CS-PROC-03`, `CS-PROC-04`.
6. **`catch (OperationCanceledException) { throw new TimeoutException(); }`**, `CancelAfter` on a linked source, and
   `Task.Delay(d)` with no provider. `CS-PROC-15`, `CS-PROC-22`.
7. **`if (p.ExitCode != 0) throw` before stdout is read**, deserializing stderr, or mapping a passthrough child's code.
   `CS-PROC-19`, `CS-PROC-21`.
8. **`StandardInput.WriteLine(secret)`**, a BOM preamble, a secret in argv. `CS-PROC-08`, `CS-PROC-12`.
9. **`psi.Environment.Remove("OCX_QUIET")` exact-case, `Environment.Clear()`, `Environment.SetEnvironmentVariable`.**
   `CS-PROC-06`.
10. **A `switch` on literal exit numbers typed from memory, a table keyed on the `version` string, or retry on the transient number alone.**
    `CS-PROC-20`, `CS-PROC-22`.
11. **Stopping the read loop at the cap.** `CS-PROC-10`.
12. **`psi.ArgumentList = new List<string>{...}`.** A compile error (CS0200); use `.Add` or `.AddRange`. `CS-PROC-01`.
13. **A Windows trust check skipped, or written as a deny-list of Everyone, Users and Authenticated Users, with a `Write` or
    `Modify` mask, `GetAccessRules(true, false, ...)`, `NTAccount` names or a method-level attribute.** `CS-PROC-25`.
14. **`--json` or `--format json` after the verb, or omitted on a passthrough call.** `CS-PROC-07`.
15. **Gate false-greens**: deleting the `AdditionalFiles` item, a nested `Directory.Build.targets` that shadows the registered one, a ban ID without a parameter list believed to ban every overload
    (it bans only the parameterless one), the short flag `-L` read as "files without match" (it means `--follow`). `CS-PROC-01`.

## Failure Classes

| Class | Mechanism | Rows | Check that catches the class |
|---|---|---|---|
| A. String and shell boundary | A structured value is flattened into a string another parser re-tokenises | `CS-PROC-01`, `CS-PROC-04`, `CS-PROC-14` | RS0030 on every string-argv API, `.cmd` refusal, no shell-outs |
| B. Ambient state and untrusted search path | The child or the resolver trusts host state the SDK did not choose | `CS-PROC-03`, `CS-PROC-06`, `CS-PROC-11`, `CS-PROC-25` | One resolver and env scrub at one seam, explicit encodings, tests that plant the ambient state |
| C. Pipe capacity and EOF coupling | A reader, writer or waiter depends on a pipe another process controls | `CS-PROC-09`, `CS-PROC-10`, `CS-PROC-12`, `CS-PROC-13` | Byte pumps, bans on every EOF-waiting API, a bounded drain |
| D. Byte and text boundary | Bytes cross an encoder or decoder the SDK did not pin | `CS-PROC-11`, `CS-PROC-12` | `Utf8NoBom` on stdin (and, as a SHOULD, on both outputs), raw-byte stdin, decode once |
| E. Process lifetime | A kill, wait or handler assumes one process, or that waiting means stopping | `CS-PROC-14`, `CS-PROC-17`, `CS-PROC-18` | RS0030 on `Kill()` and the handler events, tree kill while alive, a bounded reap |
| F. Outcome classification | One number or exception type carries two meanings | `CS-PROC-15`, `CS-PROC-19` to `CS-PROC-22` | Distinct types, the tool-reported flag, one shape reader, the contract-keyed table |
| G. Gate wiring false-green | The check exists but silently does not run or does not match | `CS-PROC-01`, `CS-PROC-25` | A wired check (the evaluated `AdditionalFiles` list, P18) plus one planted red line per ban; CA1416 at error |
