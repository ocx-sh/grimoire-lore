# Declaring Dependencies and Trusting Them

Owns the coordinate: which configuration carries it, which version resolution
actually produces, and what proves the downloaded bytes came from the publisher.
It does not own where a declaration lives structurally or how a convention plugin
composes one, which is `GRADLE-STRUCT` in `structure-and-conventions.md`, nor the
compiler wiring behind an annotation processor or a toolchain, which is
`GRADLE-TOOL` in `toolchains-and-compilation.md`. Publishing a coordinate, and
`mavenLocal()` in a consuming block, are `GRADLE-PUB` in `publishing.md`.
Relocating a dependency into a shaded artifact is `GRADLE-DIST` in
`distribution.md`. Maven's nearest-wins mediation, `dependencyManagement` and the
enforcer rules are `MVN-DEP`, in the separate `maven-build` rule set, which a
Gradle-only repository never loads.

## The Dependency-Analysis Gate

One invocation covers all four rows: `./gradlew buildHealth` for the build, or
`./gradlew :<module>:projectHealth` for one module. Both come from the
`com.autonomousapps.dependency-analysis` plugin (DAGP 3.x, verified 2026-09-12),
so `GRADLE-DEP-04` is the precondition for the other three having any mechanical
check at all. **Never `./gradlew build` as evidence here.** A wrong-configuration
leak does not fail the module that declares it, only the consumer that compiles
against it later. Floor: Gradle 9.x with the `java-library` plugin.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| GRADLE-DEP-01 | Declare a dependency `api` when any of its types appears in a public superclass or interface, a public method parameter or return type (generics included), a public field, or a public annotation. Declare it `implementation` otherwise. | This is Gradle's own ABI boundary. Too narrow and the consumer's `compileJava` fails on a type it can see in your signature but cannot resolve. Too wide and every consumer inherits your entire classpath and every upgrade you make becomes their breaking change. | `./gradlew :<module>:projectHealth`. An empty wrong-configuration section is the pass. A local `./gradlew build` is not evidence about this rule in either direction. | MUST |
| GRADLE-DEP-02 | Never leave a dependency on `compileOnly` when it is reached at runtime through reflection, generated bytecode, or a `ServiceLoader`. Use `implementation` or `runtimeOnly`. | `NoClassDefFoundError` in production, and invisible to unit tests, which share the compile classpath and therefore see the class the shipped runtime will not. | `./gradlew :<module>:dependencies --configuration runtimeClasspath`. The coordinate must appear in that tree. A `compileOnly`-only coordinate absent from it is the finding. | MUST |
| GRADLE-DEP-03 | Declare annotation processors on the `annotationProcessor` configuration, paired with `compileOnly` for the annotations themselves. Never put a processor on the compile classpath. | A processor on the compile classpath runs in an order nothing pins and is silently skippable, so the generated sources vanish with no error. The typed configuration is also what keeps `-processorpath` out of `compilerArgs`, which `GRADLE-TOOL` rejects outright. | `./gradlew :<module>:projectHealth`: no `unusedAnnotationProcessors` advice, and no processor coordinate declared on `implementation`. Empty advice is the pass. | MUST |
| GRADLE-DEP-04 | Wire `com.autonomousapps.dependency-analysis` (or `com.autonomousapps.build-health`) and set at least one issue category to `severity("fail")`. Invoke `fixDependencies` only with `--upgrade`. **pinned**: which categories fail is a default an adopter overrides once, repository-wide. That at least one fails is not negotiable. | A plugin left at the default `warn` reports and blocks nothing, and it is the only mechanism that catches a wrong configuration before a consumer's build does. `--upgrade` only adds or widens (`implementation` to `api`) and never removes, whereas a bare `fixDependencies` deletes a dependency the declaring module does not use but a consumer reaches through the leaked transitive. | `grep -rn --include='*.gradle.kts' --include='*.gradle' -e 'autonomousapps' .` A hit with a `severity("fail")` in the same block is the pass. A hit with no `severity` (the default is `warn`) is the finding, as is empty output. Then `grep -rn -e 'fixDependencies' .github/`: a bare invocation on a published module is a finding. | SHOULD |

```kotlin
// wrong: the consumer sees JsonElement in the signature and cannot resolve it
implementation(libs.gson)
fun render(node: JsonElement): String

// right: a type in the public signature is api, everything else stays implementation
api(libs.gson)
```

## Greps Over Build Scripts and Catalogs

One pass over `*.gradle.kts`, `*.gradle` and `*.versions.toml`, every command
with a directory operand and `--include`. Floors: Gradle 7.4+ for the catalog
rows (`GRADLE-DEP-08`, `GRADLE-DEP-09`), Gradle 9.x for the rest, verified
2026-09-12.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| GRADLE-DEP-05 | Never use `enforcedPlatform()` in a module that is published or consumed as a library. Use `platform()`. `enforcedPlatform()` is permitted only in a leaf application, a test or smoke-test configuration, or an internal platform that is never published. | The override is transitive and beats a consumer's own explicit version. Their only remaining defence is a per-dependency `exclude`, which they have to discover first ([platforms.html](https://docs.gradle.org/current/userguide/platforms.html)). | `grep -rn --include='*.gradle' --include='*.gradle.kts' -e 'enforcedPlatform(' .` then **open each hit's module**. A hit on `api(` or `implementation(` in a module applying `maven-publish` is the finding. A hit in a test, smoke-test or internal-platform module is not. Empty output is the pass. Grep alone flags the repositories that get this right: in 32 public JVM repositories read on 2026-09-12, all 13 hits were permitted uses and none was a violation, so the read step is mandatory. | MUST |
| GRADLE-DEP-06 | Never use `strictly(...)` or the `!!` version shorthand in a published library's own `api` or `implementation` declarations. Both are correct in an application, a distribution, test or provided catalog, a build-logic platform, or a CLI module. | A strict constraint from a library is a forced version for every consumer and can make an otherwise-resolvable graph unresolvable. It is also lossy through a published POM: only the strongest surviving declaration publishes, and `reject` is dropped entirely ([dependency_versions.html](https://docs.gradle.org/current/userguide/dependency_versions.html)). | `grep -rn --include='*.gradle.kts' --include='*.gradle' --include='*.versions.toml' -e 'strictly(' -e '!!"' .` then read the owning module. A hit inside a `maven-publish`-applying module's own dependency block is the finding. Empty output is the pass. | MUST |
| GRADLE-DEP-07 | Never declare a version range, a `+` suffix, `latest.release`, `latest.integration`, or a `-SNAPSHOT` coordinate in a build that produces a release artifact. | Not reproducible, and not re-resolvable by a consumer months later. Gradle has no built-in `banDynamicVersions` equivalent, so this grep is the whole gate. | `grep -rnE --include='*.gradle.kts' --include='*.gradle' --include='*.versions.toml' -e '[0-9]\.\+' -e 'latest\.release' -e 'latest\.integration' -e '[-]SNAPSHOT' -e ':[[:space:]]*\[[0-9]' -e ':[[:space:]]*\([0-9]' .` **Empty output is the pass.** Measured 0 hits across 32 public JVM repositories on 2026-09-12, so any hit is a real outlier and not a house style. | MUST |
| GRADLE-DEP-08 | Never conclude "no version catalog" from a `**/gradle/libs.versions.toml` glob. Detect a catalog by content. | The filename is not guaranteed and the convention is not enforced. Apollo Kotlin names its catalog `gradle/libraries.toml`, and gradle/gradle wires three named catalogs programmatically from a settings file, so the tool that invented the feature is itself a false negative for a filename check. | `grep -rn --include='settings.gradle' --include='settings.gradle.kts' --include='*.settings.gradle.kts' -e 'versionCatalogs' .` or `grep -rln --include='*.gradle.kts' --include='*.gradle' -e 'alias(libs.' .` Either hit proves a catalog exists whatever the file is called. Empty output from both, and only from both, is evidence of absence. | MUST |
| GRADLE-DEP-09 | Never state that versions are pinned on the strength of a version catalog. A catalog constrains declared requests only. | Gradle's own words: overwriting a version "only affects what is imported and used when declaring dependencies. The actual resolved dependency version may differ due to conflict resolution" ([version_catalogs.html](https://docs.gradle.org/current/userguide/version_catalogs.html)). A transitive requesting something higher wins silently, with no build failure and no diff in the TOML. | Before accepting any "pinned" claim: `find . -name 'gradle.lockfile' -o -name 'buildscript-gradle.lockfile'`. Empty output means nothing is pinned, whatever the catalog says. A catalog hit is never sufficient on its own. | MUST |

## What the Settings File Declares

Read `settings.gradle.kts`, `settings.gradle`, and any precompiled
`*.settings.gradle.kts` in build logic. Floors: Gradle 6.8+ for
`GRADLE-DEP-10`, Gradle 6.2+ for `GRADLE-DEP-11`, verified 2026-09-12.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| GRADLE-DEP-10 | Declare repositories once in `dependencyResolutionManagement` and set `repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)`. | One line closes the "a subproject quietly adds its own repository" loophole, and it is the precondition that makes content filtering enforceable at all. Only 4 of 25 Gradle repositories measured on 2026-09-12 set it, including repositories that had already centralised their catalog. | `grep -rn --include='settings.gradle.kts' --include='settings.gradle' --include='*.settings.gradle.kts' -e 'FAIL_ON_PROJECT_REPOS' .` A hit is the pass and empty output is the finding. Then `grep -rn --include='build.gradle.kts' --include='build.gradle' -e '^repositories' .` outside the root build file: hits are the finding. | SHOULD |
| GRADLE-DEP-11 | Resolve every internally owned group through `exclusiveContent`, never a bare `content { includeGroup(...) }`. | Non-exclusive filtering restricts what one repository is *asked* for. It does nothing to stop another repository in the list from answering first. The 2025 Jackson prefix-swap, where an attacker-owned domain passed Central's namespace verification on its own terms and published under a lookalike group, makes this a live attack rather than a theoretical one ([aikido.dev](https://www.aikido.dev/blog/maven-central-jackson-typosquatting-malware)). | `grep -rn --include='settings.gradle.kts' --include='settings.gradle' --include='*.gradle.kts' -e 'includeGroup' -e 'exclusiveContent' .` An `includeGroup` for an internal namespace with no wrapping `exclusiveContent` is the finding. 3 of 32 public repositories used `exclusiveContent` at all on 2026-09-12, so absence is common and still wrong. | MUST *(whenever any non-public repository is declared)* |

```kotlin
// wrong: mavenCentral() is still asked for com.acme.internal and may answer first
maven(url = internalRepo) { content { includeGroup("com.acme.internal") } }

// right: nothing else may answer for that group
exclusiveContent {
    forRepository { maven(url = internalRepo) }
    filter { includeGroup("com.acme.internal") }
}
```

## The Lockfile on Disk and in Git

The gate is the file plus its git history, not the command that wrote it.
`GRADLE-DEP-12` is **pinned**: a default an adopter overrides once,
repository-wide. MUST for a repository that publishes release artifacts on a
fixed boundary, SHOULD for an application or an internal build. `GRADLE-DEP-13`
and `GRADLE-DEP-14` bind only once locking is on. Floor: Gradle 4.8+, shapes
verified against Gradle 9.x on 2026-09-12. This is a new commitment rather than a
codified convention: 0 of 32 public JVM repositories locked as of 2026-09-12, so
ground any example synthetically and never cite a repository as precedent.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| GRADLE-DEP-12 | Enable `dependencyLocking { lockAllConfigurations() }` and commit the resulting `gradle.lockfile`, plus `buildscript-gradle.lockfile` where the buildscript classpath is locked. **pinned**, see above. | Without it, the same commit resolves a different graph on a different day. Once locked, Gradle enforces each locked version as if it were declared `strictly()`, so drift becomes a build failure instead of a silent upgrade ([dependency_locking.html](https://docs.gradle.org/current/userguide/dependency_locking.html)). Locking pins resolution and says nothing about legitimacy: a malicious first resolution is locked in exactly as faithfully as a good one, which is why `GRADLE-DEP-15` is a separate control and not an alternative. | `find . -name 'gradle.lockfile'` must print at least one path, and `git ls-files --error-unmatch` on each printed path must exit 0. An untracked lockfile is the finding, not the pass. | MUST *(publishes releases)* / SHOULD *(otherwise)* |
| GRADLE-DEP-13 | Never lock a configuration that resolves a changing module or a `-SNAPSHOT` version. Dynamic versions (ranges) are lockable. Changing coordinates are not. | Gradle's docs call the combination "a misunderstanding of these features" that "can lead to unpredictable results". The build does not refuse it, it just stops meaning anything. | On any module with locking enabled: `grep -rn --include='*.gradle.kts' --include='*.gradle' -e '\-SNAPSHOT' -e 'isChanging = true' -e 'changing = true' .` A hit is a defect, not a style nit. Empty output is the pass. | MUST *(given GRADLE-DEP-12)* |
| GRADLE-DEP-14 | Run `--write-locks` only in a dedicated, gated lockfile-update job, never in the same job as a release or test build, and never infer success from the lockfile existing afterwards. | Gradle "won't write the lock state to disk if the build fails", so a `--write-locks` step chained ahead of something that fails leaves the previous lockfile in place looking entirely healthy. | `grep -rn -e 'write-locks' .github/`: a hit inside the main build or release job is the finding, and empty output is the pass. After any local `--write-locks`, read `git diff --stat -- '*.lockfile'` rather than checking that the file is present. | SHOULD |

## Verification Metadata and the Wrapper

`GRADLE-DEP-15` is **pinned**: MUST for a repository that publishes release
artifacts, CONSIDER for an application, a default an adopter overrides once.
`GRADLE-DEP-16` binds only once verification is on. Floors: Gradle 6.2+ for the
metadata rows, `gradle/actions` v3+ for the wrapper row, verified 2026-09-12. One
public repository in 32 carries a `verification-metadata.xml` at all (gradle/gradle,
with signature verification on and 258 trusted keys). Cite that as how the build
tool's own maintainers work, never as ecosystem practice.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| GRADLE-DEP-15 | Bootstrap `gradle/verification-metadata.xml` with `./gradlew --write-verification-metadata sha256,pgp`, commit it, and require a human review of **every** regeneration diff. **pinned**, see above. | The bootstrap "trusts whatever is currently in your repositories", which Gradle's own docs call a critical security limitation. The file is therefore not the control. The reviewed diff is, and a new hash for a coordinate and version that already existed is the signal it exists to surface ([dependency_verification.html](https://docs.gradle.org/current/userguide/dependency_verification.html)). | `find . -name 'verification-metadata.xml'` must print a path, and a CODEOWNERS or branch-protection entry must cover it: `grep -rn -e 'verification-metadata' .github/` A path with no ownership rule is the finding, because the command produced a file and nobody is required to read its next diff. | MUST *(publishes releases)* / CONSIDER *(otherwise)* |
| GRADLE-DEP-16 | Count only `sha256` and `sha512` entries as verification, key every trusted PGP entry by its full 40-character fingerprint, and never clear a `checksum is missing from verification metadata` failure by disabling verification or hand-editing the XML. Re-run the bootstrap instead. | Gradle: "only SHA-256 and SHA-512 are considered secure… SHA-1 has known collisions and MD5 should not be used." A signature proves "signed by this key" and never "the signatory was legitimate", so the trusted-key allowlist does all the work and a short key id invites a collision against it. The missing-checksum failure is the transitive-dependency trap, and hand-editing the entry removes the alarm rather than the cause. | `grep -rnE -e '<md5' -e '<sha1' -e 'id="[0-9A-Fa-f]{1,39}"' gradle/` Any hit is the finding: a weak hash, or a short key id that invites a collision against the allowlist. Then `grep -rcE -e '<sha256' gradle/`: a zero count is the finding, not the pass. | MUST *(given GRADLE-DEP-15)* |
| GRADLE-DEP-17 | Validate the committed `gradle-wrapper.jar` checksum in CI with `gradle/actions/wrapper-validation`, unless `gradle/actions/setup-gradle@v4` or later is already in the workflow, which validates automatically. | Free, zero configuration, no false-positive risk, and it guards the one binary a JVM repository commits. Measured 2026-09-12: 9 of 21 wrapper-bearing public repositories ship no `distributionSha256Sum` and 1 of 32 runs the standalone action, so the default state is unguarded. | `grep -rnE -e 'wrapper-validation' -e 'setup-gradle@v[4-9]' .github/` Either hit is the pass. Empty output while `gradle/wrapper/gradle-wrapper.jar` is tracked is the finding. | MUST *(any repository committing a wrapper jar)* |

## Before You Emit a Version String

No repository check catches this one. It governs the agent, not the build.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| GRADLE-DEP-18 | Never write a dependency version string that has not been observed to resolve against the real repository in this session. Resolve the candidate coordinate first. If resolution failed, or was not run, do not state the version. | Sonatype checked roughly 37,000 unique package-version pairs across Maven, npm, PyPI and NuGet and found non-existent versions recommended at rates from about 7 percent for 2026 frontier models to over 25 percent for older ones ([sonatype.com](https://www.sonatype.com/resources/research/making-ai-work-safely)). The rule quotes no rate in its text because the rate moves with every model generation. The check does not. | In a throwaway worktree with the candidate substituted: `./gradlew :<module>:dependencies --refresh-dependencies`. The coordinate must appear resolved with no `FAILED` line. The commit or pull request that bumps the version links that run or its captured log. A bump with neither is the finding. | MUST |

## What Agents Get Wrong Here

1. **Emitting a version string from training data.** The headline failure of the
   whole family: a plausible version that never existed, stated with confidence.
   `GRADLE-DEP-18` is binary and there is no partial credit.
2. **Treating a version catalog as a lockfile.** Catalogs are the newer and
   better-documented idiom, so "versions are pinned via the catalog" is the
   sentence that gets written while nothing constrains resolution at all.
   `GRADLE-DEP-09` requires a lockfile on disk before the claim is accepted.
3. **Accepting "the build passes" as evidence about `api` versus
   `implementation`.** The leak compiles locally every time and fails in the
   consumer, so the only evidence is a `projectHealth` run in the same diff.
4. **Reaching for `enforcedPlatform()` when it means `platform()`.** One word
   apart, and the stronger-sounding one silently changes the transitivity of the
   override for everyone downstream.
5. **Grepping for `enforcedPlatform(` and flagging every hit.** The inverse
   failure, and the one that wastes a reviewer's afternoon: in the measured
   corpus every hit was a permitted use. Read the owning module.
6. **Stopping after `--write-verification-metadata`.** The command produces a
   file, not a control. Nothing is verified until someone is required to review
   the next regeneration diff.
7. **Claiming locking prevents supply-chain attacks.** A category error. Locking
   prevents drift. A malicious version resolved once is locked in faithfully,
   which is why `GRADLE-DEP-15` exists as a separate row.
8. **Concluding "no version catalog" from the conventional filename.** Both
   Apollo Kotlin and gradle/gradle defeat that check, and a false negative here
   makes the agent add a second, competing dependency-declaration style.
9. **Writing `!!` or `strictly` into a library to be safe.** Carried over from
   application-shaped examples, where it is correct, into the one place where it
   forces a version on every consumer.
10. **Treating Central namespace verification or a PGP signature as "safe to
    add".** Verification proves domain or SCM control at registration time and
    never artifact contents, which is exactly the gap the Jackson typosquat
    exploited. Check the proposed group against the project's real published
    domain before accepting a lookalike prefix.
11. **Proposing a per-module `repositories { }` block** to fix a resolution
    failure. A pre-`dependencyResolutionManagement` idiom that reopens the
    loophole `GRADLE-DEP-10` closed, and it is the second thing an agent reaches
    for after a version bump.
