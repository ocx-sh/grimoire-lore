# Manifest

Binds to Swift 6.4.0 and 6.3.3 on Linux x86_64 (measured 2026-10-10), with the `swift:6.2.0` floor leg a pinned default
that was not run here (`unverified: not run`). Apple, Xcode and Windows manifest behaviour is `unverified: read only`.
Floors say which mechanism gates them: the manifest tools version, the compiler (`#if compiler`), or the toolchain.

Owns the 22 SW-PKG rows the index (`swift-package`) does not carry, rows whole with their IDs unchanged. The index
holds the MUST rows, the lock gate and the skeleton these rows refer to. CI wiring of the lock flag is SW-GATE-03,
warning control is SW-GATE-13 to SW-GATE-17, release tags and `path:` dependencies are SW-REL-17 to SW-REL-21, and the
regeneration drift check is SW-CORE-05. **The SDK** is a library that wraps the project's CLI, a pinned default.

## Dates and Defaults

A grep, awk or find check prints its violation, so empty output is the pass (ignore grep's exit status: 1 on no match, 123
behind `xargs`), and a presence check (`grep -L`) lists the violators. Run each from the package root, with `jq` installed (the `swift` images lack it) and
`set -o pipefail` on every `dump-package` pipeline. Every grep over `.` carries `--exclude-dir='.build'` (and `.claude`, `.agents`).
A grep over Swift sources is `-R`, never `-r`: `-r` skips a symlinked file or directory (RxSwift's `Sources` is a symlink farm, 1 file
seen of 412), and the matching `find` is `find -L`. **Which manifest:** `./Package.swift` cells verify the default manifest. A
`Package@swift-*.swift` that shadows it on a leg's toolchain (`floor-read` prints the tools version in effect) is checked by the
`find . -maxdepth 1 -name 'Package*.swift'` form, whose hits name their file, so a result that changes between legs on such a
package is the shadow, not flakiness. Only SW-PKG-16, SW-PKG-17, SW-PKG-20, SW-PKG-25 and SW-PKG-38 read root manifests of every name by default; the other `.`-recursive cells also read a nested `Benchmarks` or fixture manifest, which is a hit only where that package is yours to fix.

**Brownfield default, the adopter may override once:** new packages enforce these rows whole-tree. An existing
repository lints changed manifests only and adopts one feature at a time through SW-PKG-32, never lowering a rule to fit.
**Manifest side effects:** a manifest that reads the environment (`ProcessInfo`, `Context.environment`) or writes a file at evaluation (`.write()`) is a reading item, not a defect: 3 of 4 held-out manifests do (swift-markdown's graph switch on `SWIFTCI_USE_LOCAL_DEPS`, `TARGET_OS_ANDROID`, SwiftGen's Komondor hooks) with no merge-blocking failure seen (2026-10-10). List the hits with `grep -n -e 'ProcessInfo' -e 'Context.environment' -e '\.write()' Package*.swift` and leave them be.
**Underscored products (SW-PKG-24):** banned with an `exact:` plus dated-reason exception, and swift-nio's graduation of
`_NIOFileSystem` does not change it until the owner adds an exception. **Macro authoring (SW-PKG-38):** not in scope,
consuming a third-party macro package is.

## Process Rules

Gate: reading heuristics. No mechanical check separates these from a careful hand edit, and each row says why.

| ID | Rule | Rationale | Verification | Severity |

| SW-PKG-32 | Enable a new upcoming feature on an existing package with `swift package migrate --target T --to-feature NAME` from a clean tree, never by editing the list first.
