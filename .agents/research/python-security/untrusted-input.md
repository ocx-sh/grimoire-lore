# Untrusted input and supply-chain security for shipped Python

This fleet downloads archives from remote registries, unpacks them onto the
filesystem, reads manifests other people wrote, and holds registry
credentials. That is a materially different threat model from "don't use
`pickle`" — this dive establishes the actual standard for archive
extraction, deserialization, filesystem safety, and credential handling
this domain requires, and measures the fleet against it, live, everywhere
it could be checked.

## Findings

### 1. Archive extraction

**The CVE this whole area exists because of.** [CVE-2007-4559](https://nvd.nist.gov/vuln/detail/CVE-2007-4559): "Directory traversal vulnerability in the (1) extract and (2) extractall functions in the tarfile module in Python allows user-assisted remote attackers to overwrite arbitrary files via a .. (dot dot) sequence in filenames in a TAR archive" — CWE-22, and NVD's modern CVSS 3.1 re-score (CISA-ADP) is **9.8 Critical**. It sat effectively unfixed at the language level for 17 years.

**The fix, and exactly when it applies.** [`tarfile`'s extraction-filter documentation](https://docs.python.org/3/library/tarfile.html) and [PEP 706](https://peps.python.org/pep-0706/) together give the precise timeline:

- **3.12**: `filter=` parameter **added**, opt-in, to `TarFile.extract()`/`extractall()`. Calling either without it emits a `DeprecationWarning`.
- **3.12–3.13.x**: default filter strategy is still **`fully_trusted`** (no filtering at all) unless you pass `filter=` yourself.
- **3.14**: the **default flips** — "The _filter_ parameter now defaults to `'data'`, which disallows some dangerous features such as links to absolute paths or paths outside of the destination. Previously, the filter strategy was equivalent to `fully_trusted`." This is the one line worth memorizing: **on any Python older than 3.14, an unfiltered `extractall()` is exactly as dangerous as it was in 2007.**

**What each named filter does**, per the same page:
- `fully_trusted_filter` — returns the member unchanged. No protection.
- `tar_filter` — strips leading slashes, refuses absolute paths (`AbsolutePathError`), normalizes `..` via `os.path.normpath()`, refuses extraction outside the destination even after following symlinks (`OutsideDestinationError`), clears setuid/setgid/sticky bits and group/other write bits.
- `data_filter` — everything `tar_filter` does, **plus**: normalizes and refuses absolute link targets (`AbsoluteLinkError`), refuses links pointing outside the destination (`LinkOutsideDestinationError`, even on platforms without symlink support), refuses device files/pipes (`SpecialFileError`), strips ownership/most permission bits on regular files, and skips applying permissions to directories entirely.

**What `filter='data'` explicitly does *not* solve** — this is the part a rule that just says "pass `filter='data'`" would miss, quoted directly from [the "Hints for further verification" section](https://docs.python.org/3/library/tarfile.html#hints-for-further-verification): "Even with `filter='data'`, tarfile is not suited for extracting untrusted files without prior inspection. Among other issues, the pre-defined filters do not prevent denial-of-service attacks." The incomplete list the docs give: duplicate member names ("Tar files may contain multiple versions of the same file. Later ones are expected to overwrite any earlier ones... but can be abused maliciously"), files that would collide on a **case-insensitive filesystem** (macOS default, Windows), no cap on extracted-file count/total size/filename length, no defense against "live" tampering with the destination directory mid-extraction, and no resource (disk/memory/CPU) limit — "use external (e.g. OS-level) limits."

**`zipfile` has no `filter=` equivalent at all.** What replaces it, per [the zipfile docs](https://docs.python.org/3/library/zipfile.html): `extract()`/`extractall()` **do** auto-sanitize on every version — "If a member filename is an absolute path, a drive/UNC sharepoint and leading (back)slashes will be stripped... And all `\"..\"` components in a member filename will be removed" — so zipfile's baseline has actually been safer than tarfile's pre-3.14 default for path traversal specifically. What it does **not** do: validate symlink members (a Unix zip can carry a symlink via `ZipInfo.external_attr`'s high 16 bits; `extractall()` writes it as a regular file with that content, so *reading* through it later is where a symlink-escape would bite, not the extraction call itself) — the docs' own recommendation for `zipfile.Path` applies equally to a hand-rolled extractor: "resolve filenames using `os.path.abspath()` and check against the target directory with `os.path.commonpath()`."

**Decompression bombs.** `ZipInfo.file_size` is attacker-controlled and must not be trusted as a bound — it is metadata the archive itself supplies, not a verified property of the compressed bytes. The zipfile docs' own "Decompression pitfalls" section names this directly: "decompression bombs (aka [ZIP bomb](https://en.wikipedia.org/wiki/Zip_bomb)) apply to zipfile library that can cause disk volume exhaustion." The only sound defense is to cap the **stream you are decompressing**, not the file you've already written: read in fixed-size chunks and abort once a running total exceeds a limit, before the next chunk is requested from the decompressor — capping after the fact means the bomb has already gone off.

**The reference implementation available in this fleet is the best one found in this dive**, `ocx-sdk-python/src/ocx_sdk/_bootstrap.py:745-800` (verified live in §3 of the shipped-Python audit and re-confirmed here): never `.extractall()`; resolves the wanted member by **base name only** (`_only_member`, `:783-800`: "a hostile entry cannot steer the write... refused when it is absolute or walks upward"); rejects the member if it's a directory or — for zip — a symlink (`stat.S_ISLNK(entry.external_attr >> 16)`, `:775`); streams the single member out via `tarfile.extractfile`/`zipfile.open` (never a batch method); and caps the copy against `_dist.ARTIFACT_MAX_BYTES` via `_copy_capped`, which bounds the **stream**, not the finished file. This independently reconstructs almost everything `data_filter` gives you, on a `requires-python = ">=3.12"` package that cannot assume 3.14's default flip, plus the DoS-bound the docs say the filters never gave you.

### 2. Deserialization and config parsing

**`pickle`**: zero uses on untrusted data anywhere in the fleet (`grep -rnF 'pickle.load' src` → empty in every shipped `src/` tree). The only `pickle` usage found at all is `ocx-sdk-python/tests/unit/test_errors.py:301,311,323`, round-tripping the SDK's own exception objects through `pickle.dumps`/`pickle.loads` to test `OcxError.__reduce__`'s cross-process-boundary behavior (`_errors.py:80-81`) — data the test itself just created, not external input. Any use of `pickle.load(s)` on data that crossed a trust boundary is arbitrary code execution by design (`__reduce__` is exactly the mechanism a malicious pickle abuses) — there is no safe-mode flag, unlike `yaml`.

**`yaml.load` vs `safe_load`**: zero unsafe `yaml.load(` calls fleet-wide (`grep -rnF 'yaml.load(' ... | grep -vF 'safe_load'` → empty everywhere). The one YAML consumer in scope, `grimoire-lore/.claude/skills/research-lang/scripts/check-artifacts.py:131`, uses `yaml.safe_load` and falls back to a hand-rolled minimal parser if PyYAML isn't importable — never touches the unsafe `Loader`.

**`json.loads` on unbounded input.** No fleet code caps *before* parsing (`json.loads` itself has no size argument — the cap has to be on the bytes handed to it). Where the bound actually lives varies by call site, and one is worth flagging: `ocx-sdk-python/src/ocx_sdk/_results.py:131`'s `json.loads(raw)` decodes `raw`, which is stdout **captured via `subprocess.PIPE`** in `_process.py:487` with no explicit read-size limit in that module — unlike the SDK's own network-download path (`_dist.py:889-894`), which is explicitly capped mid-stream. This is a narrower risk than a network read (the `ocx` binary is provisioned and checksum-verified by the SDK's own `bootstrap.ensure()` before it's ever invoked), but the asymmetry — capped when the source is "the network," uncapped when the source is "a subprocess we spawned" — is real and worth naming. `index/bot/src/indexbot/core/validate_entry.py:596,654`'s `json.loads(raw)` sites decode catalog-entry JSON that a separate CI step (`check-jsonschema`, per the function's own docstring) already gates before this code runs — the size bound exists, just upstream of this file, not in it.

**`tomllib`.** Not used anywhere in the audited fleet (`ocx.toml`/config-file parsing happens in the Rust binary, not the Python SDK, which only *drives* `ocx` — it never reads `ocx.toml` itself). Worth stating for completeness since the fleet's domain is exactly "package-manager config files, possibly checked into someone else's repo": [`tomllib`'s own docs](https://docs.python.org/3/library/tomllib.html) carry an explicit, unambiguous warning that would apply the moment this changes: "Be cautious when parsing data from untrusted sources. A malicious TOML string may cause the decoder to consume considerable CPU and memory resources. Limiting the size of data to be parsed is recommended." `tomllib` is read-only (added in 3.11; no write support — [`tomli-w`](https://pypi.org/project/tomli-w/) or `toml-kit` for that) and enforces no recursion/size limit itself.

**XML / `defusedxml`.** Zero XML usage anywhere in the fleet — no `xml.etree`, `xml.sax`, or `xml.dom` import found. Included here because it is the single most severe DoS-by-default surface in the stdlib the moment it *is* touched: [`defusedxml`](https://pypi.org/project/defusedxml/)'s own framing — "an attacker can occupy several Gigabytes of memory within seconds" using a few hundred bytes — covers billion-laughs (nested entity expansion), quadratic blowup, XXE (both remote-URL and local-file entity expansion), automatic external DTD retrieval, and (for `xmlrpc` specifically) decompression bombs, by monkeypatching/replacing `xml.etree.ElementTree`, `xml.sax`, `xml.dom.minidom`/`pulldom`, and `xmlrpc`. Standing guidance for this fleet: if XML parsing is ever added for a manifest/feed format, it goes through `defusedxml`'s replacements, not the stdlib modules directly — never bare `xml.etree.ElementTree.parse` on untrusted bytes.

**`eval`/`exec`.** Zero calls to either builtin anywhere in the fleet. Every apparent hit is a false cognate: `Project.exec()`/`ocx.package.exec()` are this SDK's own method names (they run `ocx package exec` as a subprocess, per `_client.py:112,1444`), and `asyncio.create_subprocess_exec` is an unrelated, safe async-subprocess API.

### 3. Filesystem safety

**TOCTOU / symlink-following on write.** Handled the sound way, not the naive way, at the one place in the fleet that installs an executable: `_bootstrap.py:582` opens via `tempfile.mkstemp(dir=binary.parent, prefix=".ocx-")` — the descriptor from `mkstemp` is the file, there is no separate check-then-open window, and staging in the **destination's own directory** (not `/tmp`) is what makes the final `os.replace()` atomic (see below) rather than a cross-filesystem copy-then-delete.

**`tempfile.mktemp` vs `NamedTemporaryFile`/`mkstemp`/`mkdtemp`.** Zero calls to the unsafe, deprecated `tempfile.mktemp` (which reserves a *name*, not a file — a race window between the reservation and the caller's own `open()`) anywhere in the fleet's production code (`grep -rnF 'tempfile.mktemp(' ...` → empty). Every hit for the bare substring `mktemp` is `tmp_path_factory.mktemp(...)`, a **pytest fixture method** with an unrelated, safe implementation (it creates the directory immediately, atomically, via `tempfile.mkdtemp` under the hood) — a different API that happens to share a name.

**Predictable temp paths in a shared `/tmp`.** Not observed as a problem: every staging path found uses `tempfile.mkstemp`/`mkdtemp` (which include a random suffix and create with a private mode) or `tmp_path_factory` (pytest's own per-test isolated directory) — no fleet code builds a temp path by string-formatting a PID or timestamp into `/tmp/something`.

**Path-containment: `os.path.realpath` and why prefix comparison is wrong.** The one place a containment-shaped check exists in the fleet, `ocx/.claude/hooks/pre_commit_verification.py:90` and `pre_push_main_blocker.py:98`, uses **equality** — `os.path.realpath(git_root) == os.path.realpath(project_dir)` — which sidesteps the bug class entirely rather than needing the fix for it. The bug class itself, for the record (not currently present anywhere audited, but this fleet's domain — resolving whether an archive member or a symlink target lands inside a destination directory — is exactly where it would show up next): `str(resolved_child).startswith(str(resolved_parent))` is wrong because `/dest-evil` is a string-prefix match for `/dest` without a trailing separator, and even with one appended, a resolved symlink can produce a path that shares a textual prefix while denoting a different, sibling directory on some filesystems. The zipfile docs' own fix, quoted above, is the correct shape: `os.path.commonpath([os.path.abspath(candidate), os.path.abspath(dest)]) == os.path.abspath(dest)`, or equivalently `Path(candidate).resolve().is_relative_to(Path(dest).resolve())` (3.9+).

**Atomic write via temp-plus-`os.replace`, and what it actually guarantees.** The fleet's one production instance, `_bootstrap.py:576-593` (installing the downloaded `ocx` binary) and `:606-611` (writing its digest sidecar), is the reference:
```python
fd, name = tempfile.mkstemp(dir=binary.parent, prefix=".ocx-")
staged = Path(name)
try:
    _extract_member(archive, release.filename, binary.name, fd)
    digest = _hash_fd(fd)
    if os.name != "nt":
        os.fchmod(fd, _CACHE_MODE)
    os.close(fd)
    os.replace(staged, binary)  # atomic: same filesystem
    _write_digest(sidecar, digest)
finally:
    if not closed:
        os.close(fd)
    staged.unlink(missing_ok=True)  # no orphan on any failure before replace
```
What this guarantees: a reader of `binary` at any instant sees either the fully-old or fully-new content, never a partial write — because `os.replace()`/`os.rename()` is atomic **only within a single filesystem**, and `dir=binary.parent` is what makes that true here (staging in `/tmp` and replacing across a filesystem boundary either raises `OSError` or, on some platforms/tools, silently falls back to non-atomic copy — the fleet does not make this mistake). What it does **not** guarantee: durability across a power loss without an `fsync()` on the file and its containing directory first (POSIX rename is atomic but not synchronous) — not exercised here because the failure mode this code defends against is a concurrent reader, not a crash mid-write, and the whole operation is trivially re-run (re-download, re-verify checksum) if it's interrupted.

**File permissions on anything holding a credential.** `_bootstrap.py:411,587` (`os.chmod`/`os.fchmod(fd, _CACHE_MODE)`) harden the binary cache directory's mode, not a credential file — the Python fleet itself does not write a credential file anywhere (registry auth flows through env vars and stdin, never a file the SDK creates; see §4). The one place in the fleet that *models* correct credential-file permissions is `ocx/test/tests/test_sign.py:327,410` (`token_file.chmod(0o600)`) and `tests/fixtures/adversarial.py:281` — fixtures the pytest harness builds to test the Rust binary's own handling, matching the `0600` convention [the Rust side of this catalog already established](../rust-ecosystem/credential-storage-and-registry-auth.md) for `~/.docker/config.json`.

### 4. Credentials

**Where they live.** `ocx-sdk-python` never stores a credential on disk — `OCX_AUTH_<SLUG>_{TYPE,USER,TOKEN}` env vars and an explicit `login(password_or_token=...)` call are the two paths in (`_client.py:382-435`); neither writes a file. `index/bot` reads `GITHUB_TOKEN` from `os.environ` at exactly one composition-root chokepoint, `cli/_wiring.py:190,202,216` (`_require_env("GITHUB_TOKEN")` / `os.environ.get("GITHUB_TOKEN", "")`), and passes it down as a plain constructor argument — no other module reads the environment for it. `ocx-mirror-sdk` reads `GITHUB_TOKEN` in `github/_auth.py:13` (`os.environ.get("GITHUB_TOKEN")`) and `GITLAB_TOKEN`/`CI_JOB_TOKEN` in `gitlab/_auth.py`, same one-function-reads-the-env shape.

**Does it reach a log line, an exception message, or `repr()`?** No, verified by reading the actual redaction machinery, not by its absence from a grep:
- `ocx-sdk-python/src/ocx_sdk/_env.py` is a formalized, self-declared "contract C-009": "Every child environment this SDK hands to a process is composed here, and every secret that env carries is scrubbed through the `redact` callable... One choke point means one place to audit" (`:4-11`). `_process.py` applies `redact()` to **argv before logging** (`:396,432`), to **captured stderr before it's attached to an exception** (`_decode(err, redact)` at `:565,580`), and dynamically widens the redactor with a call's own `input=` value when one is passed (`_also_redacting`, `:239,328`) — so a credential piped to `ocx`'s stdin for one call is scrubbed from that call's own logs and errors too, not just the static env-derived set.
- `index/bot/src/indexbot/adapters/github_api.py:82`: `token: str = field(default="", repr=False)` — a dataclass field flag, not a convention someone has to remember; the module's own docstring states the invariant it enforces: "never appears in a log line, `repr()`, or exception message" (`:6-9`).

**Does it reach a subprocess argv (visible via `ps`/`/proc/<pid>/cmdline`)?** No — the one place the SDK sends a secret to a child process at all, `login()`, documents and implements stdin transport explicitly: "The token travels on stdin through `--password-stdin`, never in argv" (`_client.py:395`), and the actual call passes `input=token` (`:428`) rather than appending it to the argv list. This is the same shape the Rust side of this catalog found for `docker_credential`'s wire protocol (`{ServerURL, Username, Secret}` JSON over stdin, never argv) — independently arrived at on the Python side.

**Does it reach an environment variable inherited by a child process the fleet doesn't need to trust it with?** This is where the fleet's posture is uneven, verified two ways:
- **Strong, and confirmed for credentials specifically** (the thing this dive was asked to verify, not just note): `ocx/test/src/runner.py:60-87`'s `OcxRunner.__init__` builds `self.env` as a **fresh `dict`**, not `os.environ.copy()` — only `OCX_HOME`/`OCX_DEFAULT_REGISTRY`/`OCX_INSECURE_REGISTRIES` (test-scoped values) plus `PATH`/`HOME`/`XDG_CONFIG_HOME` and, on Windows only, `SYSTEMROOT`/`TEMP`/`TMP`/`PATHEXT` are pulled from the real environment; the class docstring states the intent directly ("tests never leak host state into ocx"). Concretely: even if the developer's or CI runner's shell has `GITHUB_TOKEN` or `OCX_AUTH_*` set, the `ocx` binary under test never sees it through this path, because those names are not in the allowlist.
- **Weaker, not-a-credential-risk-today**: the 4 `subprocess.run` sites in `ocx/.claude/hooks` (all invoking `git`) pass no `env=` at all, meaning implicit full-environment inheritance — low actual risk here because the child is `git` itself with fully-trusted, fixed argv (no credential-relevant behavior turns on an env var these hooks would leak), but it is a real inconsistency against the allowlist standard the test harness sets, and the next hook someone adds that shells out to something less trusted would inherit the same gap by default unless it's named explicitly.

**Docker credential-helper stdout.** Not applicable to the Python fleet directly — the Docker-credential-helper protocol (`~/.docker/config.json`, `credHelpers`/`credsStore`) is implemented on the Rust side ([`docker_credential`](../rust-ecosystem/credential-storage-and-registry-auth.md)), not by any Python package in scope; no Python code in this fleet shells out to a `docker-credential-*` helper or reads `~/.docker/config.json`. Flagged here only as a boundary note: if a Python tool in this fleet ever needs the same credential-helper protocol, the Rust side's finding #10 (one of the two implementations redacts a helper's failure output before it reaches the exit-code chain, the other does not) is the exact class of mistake to avoid — a failed `docker-credential-<name> get` can echo the credential it was given as part of its own error text on stderr, and that stderr must go through the same redaction chokepoint as everything else, not straight to a log line.

**Net finding: no live credential-*value*-exposure path was found in the Python fleet.** Every credential-bearing surface checked — `repr()`, log lines, exception messages, subprocess argv, and (for the one component that actually spawns children) the child's environment — routes through a chokepoint that either excludes or actively redacts the value. The one real gap found (§3/§5's `_stderr_excerpt()`) is adjacent, not the same finding: it's about **unneutralized control/escape bytes**, not about a **credential** — the redaction layer scrubs known secret *values* before that text is built, so a credential specifically would not survive to reach it in the first place.

### 5. Terminal escape injection

**CWE-150** ("Improper Neutralization of Escape, Meta, or Control Sequences"): "The product receives input from an upstream component, but it does not neutralize or incorrectly neutralizes special elements that could be interpreted as escape, meta, or control character sequences when they are sent to a downstream component." The practical form in a terminal: ANSI escape codes reflected from untrusted input can "change the color of console output... arbitrarily move the cursor, clear the screen, and make fake prompts inside the interactive CLI," and in some terminal emulators, worse. [The Rust side of this catalog found exactly this defect, live, in a shipped binary](../rust-security.md) — it is in scope here because the Python fleet has the identical shape of surface: a registry error message, a package description, a filename, all flow toward a `print()`.

**The Python answer, and it's already the incidental convention in the one place it matters most.** `index/bot/src/indexbot/core/validate_entry.py`'s `ValidationError` messages that echo back an attacker/PR-influenced field consistently interpolate it with `!r` — Python's `repr()` conversion, which **escapes control and non-printable characters** as their `\x..` literal representation rather than passing raw bytes through (`repr("\x1b[31mFAKE")` renders the four characters `\`, `x`, `1`, `b`, not the raw ESC byte). Examples: `f"package id {raw!r} does not match the expected shape"` (`:87`), `f"namespace {package_id.namespace!r} is reserved"` (`:313`), `f"{raw!r} is not a valid sha256 digest"` (`:416`). This is a free, already-idiomatic defense — no new import, no allowlist to maintain — and it is applied at every site checked **except one, found by direct inspection, not assumption**:

```python
# validate_entry.py:283-291 — tag_name is a dict key from root.tags.items(),
# and the *immediately adjacent* interpolations on the same two messages
# ARE !r-wrapped, but tag_name itself is not:
raise ValidationError(
    f"tags[{tag_name}].observed {entry.observed!r} is not a "  # entry.observed: !r ✓, tag_name: bare
    "Z-anchored UTC timestamp (YYYY-MM-DDThh:mm:ssZ)"
)
```
Practical severity is low — `tag_name` is a version-tag string whose shape is constrained by an earlier schema check per this module's own docstring (`:1-6`) — but it is a genuine, narrow inconsistency inside a single function that gets the adjacent case right, exactly the kind of thing a mechanical check (§"Normative guidance candidates" below) catches and a code reviewer skims past.

**The one place raw, unneutralized text does reach a message with a real (if narrow) path to a caller's terminal**: `ocx-sdk-python/src/ocx_sdk/_errors.py:146,243`, `OcxProcessError`/`OcxTimeoutError`'s `_summary()` embeds `self._stderr_excerpt()` — the `ocx` subprocess's own stderr, redacted for known secrets (§4) but **not** stripped of control/ANSI bytes — directly into the exception's `__str__()`. If `ocx`'s stderr ever reflects attacker-influenced content (e.g., a compromised or misbehaving mirror's error text passed through verbatim) and a caller does the natural thing — `print(exc)` or lets an uncaught exception's traceback print — that text reaches the terminal unneutralized. Where this belongs, per CWE-150's own framing and the Rust-side precedent: at the boundary where text meets an output device, not scattered through every producer — either `_stderr_excerpt()` strips or `repr()`-wraps its excerpt once, or (better, since `repr()` would make an otherwise-readable error ugly for the 99.9% non-malicious case) the SDK's actual terminal-facing consumers (a CLI built on top of it) are the ones responsible for sanitizing before printing, and that responsibility should be stated in the SDK's own docs since it currently is not.

### 6. The tooling layer

**`bandit` — run live against the fleet** (`uv run --with bandit bandit -r src`, 2026-08-23): `ocx-sdk-python/src` → 4 issues (3 Low, 1 Medium): two are `B404` ("Consider possible security implications associated with the subprocess module" — fires on the bare `import subprocess`, zero information about actual usage), and the other two are confirmed, concretely, **false positives**: `B105` (`hardcoded_password_string`) on `_client.py:130`'s `TOKEN = "unset"` — a sentinel enum value, not a password — and `B604` (`shell=True` detected) on `_results.py:324`'s `shell=_need(data, "shell", "about")` — a dataclass field named `shell` (the user's login shell, from parsed JSON) being populated, matched purely because the keyword-argument *name* is `shell=`, regardless of what function is being called or that the value isn't even a boolean. `index/bot/src` → 0 issues.

**`ruff`'s `S` (flake8-bandit) family vs. bandit itself, and vs. what ruff never ported** — verified against [ruff's own rule pages](https://docs.astral.sh/ruff/rules/#flake8-bandit-s), not recalled: `S324` (`hashlib-insecure-hash-function`) **does** cover bandit's B324; `S704` (`unsafe-markup-use`) **does** cover B703 (renumbered, not dropped). What's genuinely un-ported: **B613 (trojansource), B614 (pytorch_load), B615 (huggingface_unsafe_download)** — none has a ruff S-code. Run live: `ocx-sdk-python` (which does **not** select `S` in its own `pyproject.toml`) has 2 real findings when checked ad hoc — the same `S105` false positive bandit found, plus a new one, `S310` ("Audit URL open for permitted schemes") on `_dist.py:885`'s `urllib.request.Request(url, method="GET")`. This is very likely mitigated upstream — the same file has a dedicated `validate_url()` function (`:583-595`) that refuses any non-`https` URL before a manifest/mirror URL is used, and a custom redirect handler (`_HTTPSOnlyRedirectHandler.redirect_request`, `:544-560`) that refuses a redirect to anything but `https` too — but this dive did not trace every caller of the flagged line to 100% certainty, so it's reported as "very likely already handled, not confirmed clean." `ocx-mirror-sdk` (also no `S` selected) surfaces **2 more confirmed false positives** when checked ad hoc: `S105` on `gitlab/_auth.py:22-23`'s `_PRIVATE_TOKEN_ENV = "GITLAB_TOKEN"` / `_JOB_TOKEN_ENV = "CI_JOB_TOKEN"` — these are the **names** of environment variables to look up later, not credential values, and ruff's heuristic (like bandit's) matches on the assigned-to identifier containing "TOKEN," not on anything about the string's content. `index/bot` (the one package that **does** select `S`) passes clean under its own committed gate. Real cost, measured: **3 of the 4 distinct S105/B105 hits found across this whole fleet are false positives on env-var-name or non-secret sentinel constants** — this rule is genuinely noisy in this codebase's own idiom (constants named `*_TOKEN`/`*_TOKEN_ENV` that hold names, not values) and would need either a per-file `# noqa: S105` convention or living as advisory rather than a hard gate.

**`pip-audit` — run live** (`uv run --with pip-audit pip-audit --strict`, OSV/PyPI-advisory-backed, [PyPA-maintained, Trail of Bits + Google-supported](https://pypi.org/project/pip-audit/)): `ocx-sdk-python` → **5 known vulnerabilities, 1 package**: `gitpython` 3.1.57 (GHSA-9rj7-rf2p-w77r, GHSA-4gmw-gg2m-w46p, GHSA-hh9p-6wh2-4mfc, GHSA-wvpp-8hx9-p66j, GHSA-jm78-9fvv-mhgr; fix in 3.1.58) — traced to `uv.lock:251,466`: a **transitive dependency of `mkdocs-git-revision-date-localized-plugin`**, the docs-build toolchain only, never reachable through the shipped `ocx-sdk` artifact (which itself declares `dependencies = []`). `ocx-mirror-sdk` → **2 known vulnerabilities**: `idna` 3.11, `PYSEC-2026-215`, fix in 3.15 — this one **is** runtime-reachable, as a transitive dependency of `httpx`, which is a real declared dependency of the shipped package. `index/bot` → **0** (audited via `uv export --no-hashes --no-emit-project | pip-audit -r -`, a workaround this dive had to discover live: `pip-audit` run directly against a `uv`-managed venv errors on the project's *own* local/unpublished distribution — `ERROR: indexbot: Dependency not found on PyPI and could not be audited` — because it tries to look up every installed distribution, including the one that will never be on PyPI; `--skip-editable`/`--local` did not resolve it, only exporting to a plain requirements file did). This is itself a real, live-observed tooling cost worth naming for anyone wiring this into CI on an unpublished internal package.

**`uv audit`** — genuinely new: announced [8 June 2026](https://astral.sh/blog/uv-audit), OSV-backed, "between 4x and 10x faster on typical projects" than pip-audit, but **explicitly "in preview... considered unstable and there may be breaking changes"** as of that announcement — not yet in `uv`'s main documentation index as a settled feature. A separate, opt-in **malware check** (`UV_MALWARE_CHECK=1`) does a "lightweight OSV-based lookup for previously-resolved malware on every sync operation" (`uv add`/`uv sync`) — off by default, and also preview. Neither is currently invoked by any package in this fleet (no `UV_MALWARE_CHECK` reference found anywhere in scope).

**`zizmor` for GitHub Actions — run live** against `grimoire-lore/.github/workflows` (`uvx zizmor .github/workflows`, [zizmor's own description](https://docs.zizmor.sh/): "a static analysis tool for your CI/CD," targeting GitHub Actions/Dependabot/pre-commit configs for script injection, unpinned floating tags, excessive permissions, and secrets exposure): **13 findings (10 suppressed by default verbosity, 1 with an available unsafe auto-fix); 0 informational, 1 low, 1 medium, 1 high.** The high-severity one is exactly this dive's theme: `error[dangerous-triggers]` at `.github/workflows/validate.yml:58` — `pull_request_target` as a trigger, which zizmor's own message states plainly: "`pull_request_target` is almost always used insecurely" (it runs with the base repo's permissions/secrets against a workflow file and code that can be influenced by an untrusted PR). The medium finding, `ref-version-mismatch` at `python.yml:60`, is a distinct, real supply-chain footgun: `actions/setup-python@e9d6f990972a57673cdb72ec29e19d42ba28880f # v6.0.0` — the human-readable version comment and the pinned SHA have **drifted apart**; the SHA actually resolves to a different commit than `v6.0.0`'s tag does today, meaning a reviewer trusting the comment without re-verifying the hash is trusting the wrong thing. The low finding, `artipacked`, flags `actions/checkout` without `persist-credentials: false`.

**Dependency pinning with hashes.** Free, not opt-in: every `uv.lock` in the fleet (`ocx-sdk-python`, `index/bot`, `ocx-mirror-sdk`) carries a `hash = "sha256:..."` field on every resolved wheel/sdist by construction — confirmed directly (`grep -A3 'wheels = \[' uv.lock`) — because `uv.lock`'s format always records one, unlike `pip`'s `requirements.txt`, where `--require-hashes` is an opt-in flag someone has to remember to pass.

## Normative guidance candidates

Severity follows this repo's existing convention ([`rust-security.md`](../rust-security.md)): **MUST** = blocks merge. **SHOULD** = blocks merge absent a stated, reviewed exception. **ADVISORY** = surfaced, not gating.

| # | Rule | Rationale | Verification | Sev |
|---|---|---|---|---|
| R1 | Never call `.extractall()`/batch `.extract()` on a `tarfile`/`zipfile` object opened from anything not `fully_trusted` — stream and validate one named member at a time. | `.extractall()` is CVE-2007-4559's exact shape and, pre-3.14, is `fully_trusted` by default even with `filter=` unset. | `grep -rnF 'extractall(' src` (empty = pass) **or** `ruff check --select S202 src` (no output = pass); watched red live against a planted `tar.extractall(dest)` — printed the violation. | MUST |
| R2 | Where a batch extract is unavoidable, always pass `filter='data'` (or a callable no weaker than it) explicitly — never rely on the installed Python's default. | The default is version-dependent (`fully_trusted` before 3.14, `data` from 3.14) and this fleet's `requires-python` floors are below 3.14. | `ruff check --select S202 src`; confirmed live (fired on a planted `tar.extractall(dest)` with no `filter=`, silent on the same call with `filter="data"`). | MUST |
| R3 | Never build a destination path by joining an archive member's raw `.name`/`.filename` onto a directory (`dest / member.name`) — resolve by base name, or validate containment after the join. | A member name can contain `../` or be absolute; `filter='data'` catches this for `tarfile` alone, nothing catches it for a hand-rolled `zipfile` walk. | `check_member_name_join.py <file>` (AST; empty stdout beyond "clean:" = pass); watched red on a planted `dest / member.name`. | MUST |
| R4 | Reject a symlink/hardlink archive member whose target — after `os.path.normpath` — resolves outside the destination, even on a platform without symlink support. | `data_filter` does this for tar; nothing does it for zip except manual `external_attr` inspection, which is what this fleet's own SDK does (`_bootstrap.py:775`). | Manual: confirm every zip-extraction call site checks `stat.S_ISLNK(entry.external_attr >> 16)` before trusting an entry as a regular file. | MUST |
| R5 | Cap bytes read from an archive member or a network body **during** the read/decompress loop, not after the file is fully written. | `ZipInfo.file_size` is attacker-supplied metadata, not a verified property — capping post-hoc means the bomb already landed on disk/in memory. | Manual: confirm every streaming read loop checks a running total against a named `_MAX_*` constant inside the loop, not after it. Reference: `_dist.py:889-894`'s `_download`. | MUST |
| R6 | Never call `yaml.load()` without `Loader=SafeLoader` — use `yaml.safe_load()`. | `yaml.load` with the default loader deserializes arbitrary Python objects via YAML tags; this is pickle's danger with a YAML front door. | `grep -rnF 'yaml.load(' src \| grep -vF 'safe_load'` (empty = pass); watched red on a planted `yaml.load(text, Loader=yaml.Loader)`. | MUST |
| R7 | Never `pickle.load(s)` data that crossed a trust boundary — only ever unpickle bytes the same process/version wrote. | `pickle` deserialization is arbitrary code execution by design (`__reduce__`); there is no safe subset. | `grep -rnF 'pickle.load' src` (empty = pass, or every hit is on the process's own `dumps()` output); watched red on a planted `pickle.load(f)` reading an external path. | MUST |
| R8 | Cap the byte size of any buffer handed to `json.loads()` when its source is a network response or a subprocess's captured output, at the point that buffer is assembled — not inside `json.loads` itself (it has no such option). | An uncapped read into memory before parsing is a memory-exhaustion vector regardless of whether the eventual JSON is small; the parse succeeding proves nothing about what was read to get there. | Manual per call site: confirm the buffer feeding `json.loads` passed through a size-checked read loop or an upstream schema/CI gate. Known-clean reference: `_dist.py:889-894`. Known gap: `_process.py`'s `subprocess.PIPE` capture, feeding `_results.py:131`. | SHOULD |
| R9 | Never call `tempfile.mktemp()` — use `tempfile.mkstemp()`/`NamedTemporaryFile()`/`mkdtemp()`. | `mktemp()` reserves a name and returns it unclaimed; anything else on the system can create that path before the caller does, a classic TOCTOU race. | `grep -rnF 'tempfile.mktemp(' src` (empty = pass — note `tmp_path_factory.mktemp()` is an unrelated, safe pytest fixture, not this function); watched red on a planted `tempfile.mktemp(prefix=...)`. | MUST |
| R10 | Stage a write via `tempfile.mkstemp(dir=<same directory as the destination>)`, write and `fsync`/`chmod` as needed, then `os.replace(staged, dest)`; clean up the staged file in a `finally` if the replace never happens. | `os.replace()` is atomic only within one filesystem — staging in the destination's own directory is what makes it atomic rather than a silent cross-filesystem copy; readers never observe a partial write. | Manual per write site: confirm `dir=` on `mkstemp` matches the destination's parent, and `os.replace` (not `shutil.move`/`os.rename` alone, which is not guaranteed atomic cross-platform) is the final step. Reference: `_bootstrap.py:576-611`. | MUST |
| R11 | A path-containment check compares `os.path.commonpath([...])` or `Path.is_relative_to(...)` on **resolved** (`os.path.realpath`/`.resolve()`) paths — never a raw string `.startswith()` on a resolved path. | `/dest-evil` string-prefix-matches `/dest`; a naive check silently admits a sibling directory. | `check_naive_containment.py <file>` (AST; flags a `.startswith()` call inside a function that also resolves a path); watched red on a planted `resolved.startswith(dest)`. | MUST |
| R12 | Any field/variable holding a credential value is excluded from `repr()`/`__str__`/default logging — `field(repr=False)` on a dataclass, or an equivalent explicit override. | The default `repr()` of a dataclass prints every field; an incidental `logger.debug(self)` or `print(instance)` on a class that forgot this is a full-value leak. | `check_credential_repr.py <file>` (AST; flags a sensitively-named dataclass field lacking `repr=False`); watched red on a planted `token: str = ""` with no `repr=False`. Reference: `github_api.py:82`. | MUST |
| R13 | A credential is passed to a child process via stdin or a scoped environment variable — never as a bare subprocess argv element. | Argv is visible to every other local user via `ps`/`/proc/<pid>/cmdline`; stdin and a child-only env var are not. | `check_secret_in_argv.py <file>` (AST; flags a sensitively-named `Name` inside a `.run()`/`.Popen()` argv list — note this shape misses call-through-a-factory-variable indirection, confirmed against `_client.py` with a 0-match, inconclusive result); watched red on a planted `subprocess.run([..., password, ...])`. Reference (the stronger evidence): `_client.py:395,428`'s documented `input=token`. | MUST |
| R14 | A child process that doesn't need the parent's full environment gets an explicitly constructed, minimal `dict` — never `os.environ.copy()`, `{**os.environ, ...}`, or an implicit unset `env=` when the parent may hold secrets the child has no reason to see. | Every ambient credential in the parent's shell becomes visible to every process the child spawns in turn; an allowlist bounds the blast radius to what's actually named. | `grep -rnF '{**os.environ' src` and `grep -rnF 'env=os.environ' src` (both empty = pass — does not catch an *implicit*, unset `env=`, which needs per-call-site reading); watched red on a planted `env={**os.environ, "OCX_HOME": ...}`. Reference: `ocx/test/src/runner.py:60-87`. Known gap: `ocx/.claude/hooks`'s 4 `subprocess.run` calls to `git`, no `env=` at all. | SHOULD |
| R15 | Any string whose origin is outside the process's control (subprocess stderr, an API response field, a filename, a validated-but-attacker-influenced identifier) is `!r`-wrapped (or otherwise control-character-stripped) before it is interpolated into a message a caller may print to a terminal. | Raw ANSI/control bytes reaching a TTY are CWE-150 — cursor movement, screen-clear, faked prompts, and on some terminals worse; `repr()` is a free, already-idiomatic defense in Python. | `check_unrepred_error_interp.py <file>` (AST; flags a non-constant f-string interpolation into an `*Error(...)` call missing `!r`) — **found a real, live violation**, not just a synthetic one: `validate_entry.py:285,290`'s bare `{tag_name}` beside two `!r`-wrapped siblings in the same message. Also watched red on a planted `raise ValidationError(f"description {desc} is too long")`. | SHOULD |
| R16 | Every shipped package's lint config selects `ruff`'s `S` (flake8-bandit) family — `S105`/`S106` false positives on `*_TOKEN`/`*_TOKEN_ENV`-named non-secret constants are handled with a scoped `# noqa: S105`, not by leaving the whole family off. | An un-gated package is only as safe as whoever remembers to run `bandit` by hand; `ruff` is already the fleet's lint tool everywhere, so this is one line in an existing config, not a new dependency. | `grep -nF '"S"' pyproject.toml` per package (present = pass); **live, real result**: present in `index/bot`, absent in `ocx-sdk-python` and `ocx-mirror-sdk` — 2 of 3 shipped packages currently fail this. | SHOULD |
| R17 | A GitHub Actions workflow never combines `pull_request_target` with checking out or executing the PR's own ref/code without an explicit, documented reason the maintainers reviewed. | `pull_request_target` runs with the base repository's permissions and secrets against a trigger an external contributor can shape; it is the single most common real-world Actions-workflow compromise vector. | `uvx zizmor <workflows-dir>`, treat any `error[dangerous-triggers]` as build-breaking; **live, real finding**: `grimoire-lore/.github/workflows/validate.yml:58`, `on: pull_request_target`, zizmor severity High. | MUST |

## AI-agent angle

| Default mistake | Why it's the obvious wrong answer | Smallest mechanical check |
|---|---|---|
| `archive.extractall(dest)` | It's the one-line, first-suggested method in every tutorial; `filter=` is opt-in on the exact Python versions this fleet targets. | `grep -rnF 'extractall(' src` / `ruff check --select S202` |
| `dest / member.name` when hand-rolling extraction | Looks identical to any other "join two paths" idiom; nothing about the syntax hints the right-hand side is attacker-controlled. | `check_member_name_join.py` |
| `yaml.load(text)` | Countless tutorials, Stack Overflow answers, and older library docs use the 2-arg-optional form; `safe_load` requires knowing it exists. | `grep -rnF 'yaml.load(' \| grep -vF 'safe_load'` |
| `requests.get(url, verify=False)` to clear a TLS error | The error message itself often suggests this as "the fix"; it silently disables the one check that makes HTTPS meaningful. | `grep -rnF 'verify=False'` |
| `subprocess.run(f"cmd {user_input}", shell=True)` with an interpolated value | `shell=True` is what makes shell examples in docs look simplest; an f-string interpolation reads as normal string-building, not as command construction. | `ruff check --select S602,S604` / `grep -rn 'shell=True'` |
| `tempfile.mktemp()` | The name literally describes what's wanted ("make a temp [file] name"); `mkstemp`'s extra letter and different return shape (fd + path, not just a path) reads as more ceremony for the same job. | `grep -rnF 'tempfile.mktemp('` |
| `if resolved.startswith(dest):` for containment | Reads as obviously correct; the string-prefix edge case (`/dest-evil`) doesn't occur to someone who hasn't seen it fail. | `check_naive_containment.py` |
| `logger.info(f"fetched {response.text}")` including a header or token | "Log everything for debugging" is a reasonable-sounding default; nothing marks a response object's `.text`/`.headers` as secret-shaped at the call site. | `check_credential_repr.py` (catches the field-level version); a targeted `grep -rn 'headers\b' src \| grep -i 'log\|print'` for the call-site version |
| `except Exception: pass` wrapped around a security check specifically (a signature check, an origin check, an auth check) | Broad excepts are already this program's known failure mode (see the exemplar-patterns dive); around a check whose only job is to say "no," swallowing the exception makes the default outcome "yes." | `grep -rnE "^\s*except\s*:"` for the bare form; for the targeted form, manual review of every `except Exception` site's *disposition* (does it re-raise, fail-open with a comment, or silently continue past a check?) — this dive's earlier audit already applied that discipline and found all 6 fleet-wide sites documented and justified. |

## Contested / evolving

As of 2026-08-23:

- **`tarfile`'s default-filter flip (3.14) is recent enough that "which Python version am I actually running" still matters for this rule** — every package in scope pins `requires-python` below 3.14 (`>=3.12` or `>=3.13`), so none of them can rely on the new default; R2's explicit `filter=` requirement is not optional-for-now, it's the only thing standing between this fleet and pre-2007-fix behavior on its own stated minimum Python.
- **`uv audit` and its malware check are explicitly unstable previews** (Astral's own wording, 8 June 2026) — not yet something to gate CI on; `pip-audit` remains the load-bearing tool today, with the caveat (found live, not theoretical) that it needs a `uv export`-to-requirements-file workaround against an unpublished local package.
- **Whether `ruff`'s `S105`/`B105` (hardcoded-password heuristic) is worth keeping as a hard gate is a live, evidence-backed question this dive can answer with real numbers, not just an opinion**: 3 of the 4 hits found fleet-wide are false positives on `*_TOKEN`/`*_TOKEN_ENV`-named constants holding environment-variable *names*. Recommendation in R16 is advisory-with-scoped-suppression rather than blanket disable, but the alternative (drop S105 specifically, keep the rest of `S`) is a reasonable position this dive doesn't resolve either way.
- **Whether R14 (env allowlist) should be MUST or SHOULD for hooks specifically is genuinely unsettled** — every hook's subprocess target today is `git` with fixed argv, which is low risk regardless of inherited environment; the rule is written SHOULD (blocks merge absent a stated exception) rather than MUST because tightening it before a hook shells out to something less trusted would be solving a problem that doesn't exist yet in this fleet, and the ponytail-style cost of a full allowlist for 4 two-line `git` invocations is real.
