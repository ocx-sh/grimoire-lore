# csharp-language: the language posture for `csharp-quality/language.md`

This file is the source for the `csharp-quality/language.md` depth file (rule prefix `CS-LANG`). Era: C# 14 on .NET 10 LTS (SDK 10.0.401), `net8.0` floor at `LangVersion 14`, C# 15 / .NET 11 at RC1 (11.0.100-rc.1.26425.128) fenced and marked.

The props there are the pinned gate: `LangVersion 14`, `AnalysisLevel 10.0-all`, `EnforceCodeStyleInBuild`, TWAE, `Nullable`. `run-all.sh` re-runs every probe.

"The gate" means CS-BUILD-04/10/13/14: `LangVersion 14`, `AnalysisLevel 10.0-all`, unconditional `TreatWarningsAsErrors`, and `EnforceCodeStyleInBuild=true`. Under it a compiler or CA **warning becomes an error**. An **IDE rule stays silent until a per-rule line raises it**: `AnalysisLevel` does not raise style rules, and IDE0370 was silent with ECSB on and no line ([NUL] V3). "Watched" means the check was seen failing on a planted defect and passing on its fixed twin on the pinned toolchain.

## Verdict

1. **Nullability is one project switch plus three hard bans: no `#nullable` directive, no unexplained `!`, no bare `= null!`.**
   - `Nullable=enable` is set once in the root props (CS-BUILD-14).
   - Every per-file directive is banned, `#nullable enable` included. A forgotten file in a per-file regime is nullable-oblivious, and consumers then get a `NullReferenceException` with no diagnostic ([NUL] V1).
2. **Annotations do not replace runtime guards.** Public entry points validate their arguments with the throw helpers.
   - **Decision:** CA1062 goes back on (`warning`, so an error under TWAE) for `src/`. This reverses CS-BUILD-12's repo-wide `none`.
   - **Reason:** it is the only mechanical check for dotnet/runtime's "DO continue to validate all arguments" rule. [CL] measured it firing on exactly the two unguarded public dereferences and on nothing else.
3. **C# 14 on `net8.0` (CS-BUILD-04's recorded decision, which Microsoft calls unsupported) is safe for syntax and loud for runtime-bound features. It is silent only where binding changes.**
   - The one measured silent miscompile is `arr.Reverse();`: an in-place reversal on net8.0 and a discarded no-op on net10.0. It is banned with RS0030 ([C14] §5).
4. **C# 15 / .NET 11 is fenced by the SDK 10.0.401 pin itself.** A `NET11_0_OR_GREATER` region may not exist until some leg builds net11.0, because the compiler never sees it ([C14] §10).
   - This sets the timing for CS-PROC-23, which stays the shape rule for later.
5. **Idioms are policed by mechanism, not by taste.** Ungated: `var`, `new()` and primary constructors on internal types. Gated: anything that hides mutable state, aliases data, fails open, or blinds the analyzers.
6. **A copied generated-code marker turns the whole gate off for that file. The `.editorconfig` must override the heuristics, scoped to `obj/`.**
   - **Correction:** the idioms researcher's `[*.g.cs] generated_code = true` pair breaks every xUnit v3 / MTP test project. [CL] measured CA1018, CA1852 and CA1707 inside `Tests/obj/**/XunitAutoGeneratedEntryPoint.cs` and `SelfRegisteredExtensions.cs`.
   - `[**/obj/**.cs] generated_code = true` builds green, keeps STJ generator output exempt, and still catches a planted `// <auto-generated/>` header.

## The ruleset

Prefix `CS-LANG`. Verification runs from the repo root in bash. A grep check prints violations, so empty output passes. Cited, not re-decided:
- CS-API-04/05: records and sealing of public types.
- CS-BUILD-04: the `LangVersion 14` pin.
- CS-JSON-08, CS-API-07 and CS-API-10: the `required`, `[JsonRequired]` and open-enum policy.

### A. Nullability

**CS-LANG-01 (MUST). Set `<Nullable>enable</Nullable>` only in the root `Directory.Build.props`, and write no `#nullable` directive in any hand-written `.cs` file under `src` or `tests`.**
- Why:
  - In a per-file regime, a file without the directive is oblivious. Its members accept `null` from NRT consumers silently, and its returns throw a `NullReferenceException` at run time ([NUL] V1: 1 error red vs 3 errors green, runtime NRE).
  - `#nullable disable` hides CS8602-class flow while CA rules still fire ([IDM] H9).
  - The corpus holds 221 enable and 562 disable directives, and the disables are migration debt ([shape] §3.1).
- Check:
  - `find src tests -name '*.csproj' -print0 | xargs -0 -r -n1 dotnet msbuild -nologo -getProperty:Nullable | grep -vx enable` prints nothing.
  - `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin '^[[:space:]]*#nullable\b' src tests` prints nothing.
- Watched: **yes**. getProperty in [NUL] V1 (red: empty, green: `enable`); the grep in [CL] greps N1 (red: `A.cs:1:#nullable enable`, `T.cs:1:#nullable disable // legacy`; green: empty).

**CS-LANG-02 (MUST). Never promote or suppress nullable warnings by list: no `WarningsAsErrors` of `nullable` or `CS8xxx` (TWAE already covers them), and no `nullable`, `CS8xxx` or `CS9264` in `NoWarn`.**
- Why:
  - A hand-written list such as `CS8600;CS8602;CS8604;CS8618;CS8625` promoted 4 of the 16 nullable IDs present and left 12 as warnings.
  - The `nullable` value is a strict subset of TWAE ([NUL] V2).
  - `NoWarn` of `nullable` removes the whole family.
- Check: `grep -rnE --include='*.props' --include='*.csproj' --include='*.targets' -e '<(WarningsAsErrors|NoWarn)>[^<]*(nullable|CS8[0-9]{3}|CS9264)' .` prints nothing.
- Watched: **yes**. Behaviour in [NUL] V2. The grep in [CL] greps NW (red: the `CS8600;CS8602` list plus `NoWarn CS8618`; green: a NU190x-only `WarningsNotAsErrors`).

**CS-LANG-03 (MUST). The null-forgiving operator in `src` is allowed only in two forms:**
- (a) `= null!;` on a member that also carries `[JsonRequired]`. This is the CS-API-10 later-added wire-mandatory member.
- (b) A `!` with a same-line `// null-forgiving: <invariant>` comment.

`default!` is never allowed. Tests may pass `null!` to guard tests.
- Why:
  - A bare `public string Name { get; init; } = null!;` deserialized from `{}` yields `Name == null`, and later a `NullReferenceException`. Only `required` or `[JsonRequired]` turn the omission into a `JsonException` ([NUL] V4, also on net8.0 with STJ 10.0.0).
  - IDE0370 removes dead `!` but cannot judge deliberate ones. It also flags a member only if every `!` in it is removable ([NUL] §1.3, `f3-bang-mixed` silent).
- Check:
  - `.editorconfig`: `dotnet_diagnostic.IDE0370.severity = error` (default silent; needs ECSB and SDK ≥ 10, and is absent from 8.0.425). `grep -cE '^dotnet_diagnostic\.IDE0370\.severity[[:space:]]*=[[:space:]]*error' .editorconfig | grep -vx 1` prints nothing.
  - `grep -rnP --include='*.cs' --exclude-dir=obj --exclude-dir=bin '(?<=[\w\)\]>])!(?=[\.\)\;\,\[\]\s\}]|$)' src | grep -v -e 'null-forgiving:' -e '= null!;'` prints nothing.
  - `find src -name '*.cs' -not -path '*/obj/*' -print0 | xargs -0 -r awk 'FNR==1{prev=""} /= *null! *;/ && prev !~ /JsonRequired/ && $0 !~ /JsonRequired/ {print FILENAME":"FNR": "$0} {prev=$0}'` prints nothing.
- Watched: **yes**.
  - IDE0370: [NUL] V3, 3 × `error IDE0370` red, exit 0 green, silent without ECSB or without the line.
  - Both greps: [NUL] V9, red `Bad.cs:5 = null!;`, `:11 default!`, `:12 s!.Length`; green passes `[JsonRequired] ... = null!;`, `"Hello!"` and `a != b`.

**CS-LANG-04 (MUST). Every public `Try*` method carries a nullability attribute on its `out` parameter:**
- `[NotNullWhen(true)] out X? v` for a non-generic method.
- `[MaybeNullWhen(false)] out T v` with `v = default;` for a generic one.

Also:
- Throw helpers carry `[DoesNotReturn]`.
- Init helpers called from constructors carry `[MemberNotNull(nameof(...))]`.
- Pass-through returns carry `[return: NotNullIfNotNull(nameof(p))]`.
- A lookup that can miss never returns an unconstrained `T?`.
- Why:
  - Without the attributes every caller needs `!` ([NUL] V5: 5 × CS8602 plus CS8618 red, 0 errors green, with the same zero-`!` caller).
  - For a value type `T?` is `T`, so a miss reads as `0` ([NUL] V7: `type=Int32 value=0`).
- Check: the gate (CS8602/CS8618/CS8762/CS8763/CS8774 are errors under TWAE). The workaround an agent writes is a `!` in the SDK's own callers, which CS-LANG-03 catches.
- Watched: **yes** ([NUL] V5, V7).
- net8.0 and net10.0: the attributes ship in both shared frameworks.

**CS-LANG-05 (MUST). Public and protected members of public types validate every reference parameter they dereference, store or forward, on their first lines.**
- Use the throw helpers: `ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrEmpty`/`ThrowIfNullOrWhiteSpace`, `ArgumentOutOfRangeException.ThrowIf*`, `ObjectDisposedException.ThrowIf`.
- Never write `new ArgumentNullException(`.
- Never guard value types (CA2264), `T?` parameters that accept null, or internal or private members.
- In an `async` method the guard faults the returned Task. Document it that way, never as "throws synchronously".
- Why:
  - Oblivious, reflection and `null!` callers bypass the compiler ([NUL] V6: `NullReferenceException` unguarded vs `ArgumentNullException` guarded).
  - dotnet/runtime nullability.md: "DO continue to validate all arguments".
  - The corpus is 1,401 `ThrowIfNull` vs 2,155 `new ArgumentNullException(` ([shape] §0).
- Check:
  - `.globalconfig`: `dotnet_diagnostic.CA1062.severity = warning` (an error under TWAE). Remove CA1062 from CS-BUILD-12's `none` list.
  - CA1510, CA1511, CA1512 and CA1513 stay at the `10.0-all` warning, an error under TWAE.
  - `grep -cE '^dotnet_diagnostic\.CA1062\.severity[[:space:]]*=[[:space:]]*(warning|error)' .globalconfig | grep -vx 1` prints nothing.
  - `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin 'new ArgumentNullException\(' src` prints nothing.
- Watched: **yes**.
  - CA1062: [CL] `ca1062-red` gave 2 × `error CA1062` (exit 1) and `ca1062-green` gave exit 0, on `net8.0;net10.0`.
  - CA1510–1513 and CA2264 fire identically on net8.0 and net10.0 ([NUL] V6).
  - The severity grep: [CL] greps CA1062 (red `none`, green `warning`).
  - CA1062 also follows a call into a private helper, and stays silent when a parameter is only stored or passed to the BCL ([NUL] §1.7). Those cases are a reading check.
- Async: `ThrowIfNull` in an `async` body leaves the Task `Faulted` ([NUL] V10).

**CS-LANG-06 (MUST). Test for null with `is null` / `is not null` / `is { }`, never `== null` / `!= null`. Parenthesize `not` when it is mixed with `and`/`or`.**
- Why: `==` dispatches to a user-defined operator. With a lying overload, `real != null` printed `False` ([NUL] V7). The SDK's open-enum `readonly record struct`s are exactly where operators appear. No IDE or CA rule enforces this; IDE0041 covers only `ReferenceEquals` ([NUL] V7).
- Check: `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin -e '[=!]=[[:space:]]*null\b' src` prints nothing.
- Watched: **yes** ([NUL] V9 C5, [IDM] row 24 N1).

**CS-LANG-07 (SHOULD). Treat a `?` on a shipped public signature as contract.**
- Tightening a parameter (`string?` → `string`) or loosening a return (`string` → `string?`) is a consumer-visible change. List it in the release notes.
- Never rely on package validation for this.
- Why: package validation exited 0 for all four annotation-change directions, even in strict mode. Only PublicApiAnalyzers RS0016/RS0017 saw them ([NUL] V8, control `CP0002` exit 1).
- Check:
  - RS0016/RS0017/RS0036/RS0037 at `error` (CS-API-11).
  - `grep -rL --include='PublicAPI.*.txt' -e '#nullable enable' src` prints nothing.
  - Reading: the release reviewer reads the `PublicAPI.Unshipped.txt` diff for `?` and `!` flips.
- Watched: the detector, yes ([NUL] V8, 4 × RS0016 plus 4 × RS0017); the grep, no.

### B. C# 14 on net8.0 (LangVersion 14, Microsoft-unsupported) and net10.0

Every pure-syntax C# 14 feature compiled and ran identically on 8.0.31 and 10.0.12 ([C14] row 1). The compiler refuses the two runtime-bound ones on net8.0: `allows ref struct` is `CS9240`, and a covariant span is `CS0656 ReadOnlySpan<T>.CastUp` ([C14] rows 9-10). The rows below are the hazards that remain.

**CS-LANG-08 (MUST). Never call `.Reverse()` on an array. Write `Array.Reverse(a)` to reverse in place or `Enumerable.Reverse(a)` for a lazy copy, and ban the span overload with RS0030.**
- Status by TFM:
  - **net8.0:** at LV14, `a.Reverse();` binds `MemoryExtensions.Reverse(Span<T>)` and reverses in place (`3,2,1`). `var y = a.Reverse()` is `CS0815`.
  - **net10.0:** the same statement binds `Enumerable.Reverse(T[])` and is a discarded no-op (`1,2,3`).
- Same source, same LangVersion, no diagnostic ([C14] rows 3-4). Roslyn calls net8.0 plus C# 14 "an unsupported configuration" for this case.
- Check: add `M:System.MemoryExtensions.Reverse``1(System.Span{``0});Use Array.Reverse (in place) or Enumerable.Reverse (copy)` to `BannedSymbols.txt` (RS0030 at `error`, CS-BUILD-15). Then `grep -c 'MemoryExtensions.Reverse' BannedSymbols.txt | grep -vx 1` prints nothing.
- Watched: **yes** ([C14] row 22). Red on net8.0 was `error RS0030 ... MemoryExtensions.Reverse<T>(Span<T>)`; net10.0 was clean because it binds LINQ; the green twin was clean on both. The same binding class flips `Path.Combine` with 5 arguments to a span overload on net10.0 only (CS-XP V2).

**CS-LANG-09 (MUST). Test projects inherit the src TFM list, and every behavioural test runs on every TFM.**
- Why: binding-dependent C# 14 changes appear only as a per-TFM behaviour difference ([C14] §1). They include CS-LANG-08, `a.StartsWith(1)` (`CS1503` on net8.0, `True` on net10.0), and a `Span<T>` overload beating `IEnumerable<T>` (`ArrayTypeMismatchException` on both).
- Check: `find src tests -name '*.csproj' -print0 | xargs -0 -r -n1 dotnet msbuild -nologo -getProperty:TargetFrameworks | sort -u | wc -l` prints `1` (with CS-BUILD-01, no csproj sets TFMs).
- Watched: **yes**. The hazard in [C14] rows 2-5. The check in [CL] `net11/check.sh`: red printed `tfm-variants=2` (a `net10.0`-only project), green printed `1`.

**CS-LANG-10 (MUST). Keep spans off the public surface and out of async code:**
- No `Span<T>`/`ReadOnlySpan<T>` in public signatures.
- No public overload set mixing `IEnumerable<T>`, `T[]` and span parameters.
- `Span<T>` and `stackalloc` appear only in synchronous internal helpers, outside loops.
- Async methods take arrays, `string` or `ReadOnlyMemory<T>`.
- No `unsafe`, no `AllowUnsafeBlocks`.

- Why:
  - C# 14 prefers span overloads, which gives ambiguity and `ArrayTypeMismatchException` ([C14] row 5).
  - A Span parameter in an async method is `CS4012`; a Span local crossing an `await` is `CS4007`. Both are errors on net8.0 and net10.0 ([IDM] row 16).
  - A `stackalloc` in a loop is CA2014 (warning, so an error under TWAE).
  - The SDK path is async I/O (CS-PROC), and the corpus keeps span code in a few serializers ([shape] §3.4).
- Check:
  - `grep -nE 'Span<' src/*/PublicAPI.Shipped.txt src/*/PublicAPI.Unshipped.txt` prints nothing.
  - `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin -e 'async[^=;{]*\([^)]*\b(Span|ReadOnlySpan)<' -e '\bunsafe\b' src` prints nothing.
  - `grep -rnE --include='*.csproj' --include='*.props' 'AllowUnsafeBlocks' .` prints nothing.
- Watched: **yes**. The PublicAPI grep in [CL] greps SP; the async-span and `unsafe` greps in [IDM] row 24; CS4007, CS4012, CA2014 and CS0227 in [IDM] rows 16-17.

**CS-LANG-11 (MUST). Use the C# 14 `field` keyword safely:**
- **No identifier named `field`** (member, inherited member, local or parameter) in a type with property accessors. Rename it; never "fix" CS9258 with `@field`. The same goes for `union`, `closed` and `extension` as type or member names.
- **Initialize non-nullable `field`-backed properties.** Every one has an initializer or is `required`.
- **No `field ??=` on state that two threads can touch.** Use `Lazy<T>`/`LazyInitializer` instead.

- Status by TFM: net8.0 and net10.0 behave identically, including STJ source generation ([C14] row 1, F13).
- Why:
  - A member named `field` silently rebinds: LV13 printed `41`, LV14 printed an empty line ([C14] row 11).
  - CS9264 (not CS8618) reports the missing initializer, so a CS8618 text search misses it ([NUL] §1.9).
  - `field ??=` is the same unsynchronised read-check-write as a hand-written lazy field, and it is the dominant corpus use (8 repos; testfx has 24 sites) ([C14] §12).
- Check:
  - `CS9258` (warning, so an error), `CS9273`/`CS9272` (error) and `CS9264` (warning, so an error) under the gate. None of the three may appear in `NoWarn` or a `.globalconfig`.
  - `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin -e '\b(private|internal|public|protected)[[:space:]]+[A-Za-z0-9_<>?,]+(\[\])?[[:space:]]+field[[:space:]]*[;=]' src` prints nothing.
  - `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin -e 'field[[:space:]]*\?\?=' src` lists the `??=` sites. Each hit must sit in a type documented as single-threaded.
- Watched: **yes**. The diagnostics in [C14] rows 11-14 and [IDM] row 19; the member grep in [IDM] row 24; the `??=` grep in [CL] greps FL (red: a hit; green: empty).

**CS-LANG-12 (MUST). Public extension blocks contain methods only. Extension properties, static extension members and operators are `internal`.**
- A static `extension(BclType)` block that polyfills a BCL member missing on net8.0 is `internal`, has identical semantics, and carries a `// BCL since net<N>` comment.
- Status by TFM: blocks work on net8.0, net10.0 and netstandard2.0, with no polyfill needed.
- Why:
  - A block method stays callable from a LangVersion 13 consumer. A block *property* gives the consumer `CS9260` ([C14] row 29), and net8.0 consumers default to C# 12.
  - The real BCL member wins on newer TFMs (net8.0 printed `polyfill-used`, net10.0 `BCL-used`), so a semantic difference becomes a per-TFM bug ([C14] row 30).
- Check:
  - RS0016 at error (CS-API-11) records any public block member.
  - `grep -nE 'extension\([^)]*\)\.[A-Za-z_0-9]+\.(get|set|init)\b|^static [A-Za-z_0-9.]+\.extension\(' src/*/PublicAPI.Shipped.txt src/*/PublicAPI.Unshipped.txt` prints nothing.
  - The site-level CA1034 pragma is CS-BUILD-12's.
- Watched:
  - RS0016 on a public block property, yes ([C14] row 31).
  - The property half of the grep, yes ([CL] greps XP, using the entry text measured in row 31).
  - The `static` alternative: its PublicAPI entry text was not measured.

**CS-LANG-13 (SHOULD). Declare no user-defined compound assignment operators (`public void operator +=`) and no instance `++`/`--`.**
- Status by TFM: net8.0 and net10.0 are identical. `var alias = a; a += 10;` mutates `alias` too: 11/11, vs 11/1 with only a binary `+` ([C14] row 15).
- Why: adding one later silently changes every recompiled caller.
- Check: `grep -rnE --include='*.cs' --exclude-dir=obj --exclude-dir=bin 'void[[:space:]]+operator' src` prints nothing.

**CS-LANG-18 (MUST). A primary constructor appears only on a non-public `class` or `struct`.**

**CS-LANG-21 (MUST). ## Applied to the ocx C# SDK

**New commitments this group forces on the design:**
- **`.editorconfig` gains these lines:** IDE0370 `error`; IDE0072 and IDE0010 `warning`; `dotnet_style_prefer_collection_expression = when_types_exactly_match`; the `generated_code` false/obj pair.
- **`.globalconfig` changes:** CA1062 moves from `none` to `warning`, a change to CS-BUILD-12; MA0143 `error`.
- **`BannedSymbols.txt`** gains `MemoryExtensions.Reverse<T>(Span<T>)`.
- **Every public command method guards its reference parameters.** Examples are package references, project paths and option objects. The first line is `ArgumentNullException.ThrowIfNull`; the exception surfaces on the awaited Task.
  - `OcxClient.CreateAsync(OcxClientOptions? options = null, …)` takes a nullable options object and needs no guard (CS-API-01).
- **No `NET11_0_OR_GREATER` code ships in 0.x on SDK 10.0.401.** CS-PROC-23's `Process.Signal`/`RunAsync` branches are written when the SDK 11 GA pin lands, together with the net11.0 leg (CS-LANG-16).
- **Internal engine types may use primary constructors for read-only inputs.** Examples are the byte pump, the resolver and the env builder. `OcxClient` and every public type may not (CS-LANG-18).
- **The compat-gate memo is not a `field ??=` property.** It is the single-flight `Lazy<Task>` that CS-ASYNC prescribes (CS-LANG-11).
- **No span types appear on the public surface** (CS-LANG-10). The byte pump uses arrays and `Memory<byte>` across awaits.
- **If ocx's sdkgen gains a C# backend (CT-02), its output is a source generator or lands in `obj/`.** Committed generated models in `src/` would be analyzed under CS-LANG-24 and are ruled out by CS-LANG-23.

**What the Python SDK already models:**
- **Strict typing at the boundary.** pyright strict on `src` maps to `Nullable` plus TWAE ([py] row 45). Python's three-row presence table maps directly to these rules ([py] §results, :124):
  - Always present: `required T`.
  - `Option<T>`, always present: `required T?`.
  - `Option<T>` with skip-if-none: `T?`, not required.
  - With ocx's "absent = unset, `null` only inside opaque publisher metadata" ([ocx]:132), a first-release type never needs `= null!` (CS-LANG-03).
- **"Enums only where the runtime iterates; open sets stay `str`"** ([py]:254). This is CS-API-07's open-enum struct plus CS-LANG-22's fail-closed discard.
- **Runtime guards beyond the type checker.** `__getattr__` traps and `_need` raising with context ([py]:59, :122) are what CS-LANG-05 asks for.

**Where the Python design must NOT be copied:**
- **`with_config` via `c with {...}` on a `sealed record` ([py] row 22), and "sealed record" result types ([py] row 5).** Config and results are sealed classes (CS-API-04). Deriving is an explicit `WithOptions`. Records alias collections under `with` (CS-LANG-20).
- **`_need` returning `Any` with no scalar check ([py]:126).** Do not reach for `object` or `JsonElement` to mimic it. STJ checks scalar types for free; only opaque metadata is `JsonElement` (CS-JSON-15).
- **Hiding code from the checker with `if not TYPE_CHECKING` ([py]:59).** The C# analogue is `#nullable disable`, `!`, or a generated-code header, and all three are banned (CS-LANG-01/03/23).

**What the ocx CLI contract forces:**
- **Open enums and unknown-is-not-success** ([ocx]:69, :129-132) make the fail-closed discard (CS-LANG-22) a correctness rule, not a style rule.
- **The contract exists only on unreleased ocx main** ([ocx]:25). The SDK's first release will probably follow the net8 EOS (2026-11-10). If the owner then drops net8.0 (decision 2), CS-LANG-08 and the per-TFM binding hazards of CS-LANG-09 go away. The rules stay harmless.
