## Summary

- The dominant Swift 6 failure is not a data race but the diagnostic that has no good fix: non-isolated mutable global/static state, non-Sendable singletons, and callbacks from pre-concurrency APIs. The migration guide funnels these into a short ladder (`let` → global-actor isolation → `Sendable` → `Mutex`/actor → `nonisolated(unsafe)`), and a rule should encode that ladder, not the escape hatch.
- `@unchecked Sendable` and `nonisolated(unsafe)` emit NO diagnostic on an unguarded body (measured: an `@unchecked Sendable` class with an unprotected `[String: Int]` compiles clean in 6.3 and 6.4) and SwiftLint 0.65.1 has no rule for either. They are only catchable by grep plus a mandatory justification comment — the swift-nio reviewers demand exactly that ([apple/swift-nio#3433](https://github.com/apple/swift-nio/pull/3433)).
- A class whose only stored state is `Mutex<…>` is `Sendable` with no `@unchecked` (measured 6.4; SwiftPM reviewers reject `@unchecked` there, [swift-package-manager#10425](https://github.com/swiftlang/swift-package-manager/pull/10425)). Mutex-guarded code must make no outcalls or continuation resumes while the lock is held ([#10405](https://github.com/swiftlang/swift-package-manager/pull/10405), [#10403](https://github.com/swiftlang/swift-package-manager/pull/10403)).
- Swift 6 mode converts compile-time silence into run-time traps: a closure from a Swift 5 module, an Objective-C block, or a `DispatchGroup.notify` handler that inherits `@MainActor` isolation but runs on a background queue crashes with `_dispatch_assert_queue_fail` / "Incorrect actor executor assumption" ([swift#75453](https://github.com/swiftlang/swift/issues/75453), DTS thread 803515). Measured on Linux: exit 132 with `_dispatch_assert_queue_fail`.
- Continuations: double-resume is a fatal error (`SWIFT TASK CONTINUATION MISUSE: f() tried to resume its continuation more than once`), a leak only logs and hangs the awaiting task forever (measured: process timed out, exit 124). Swift 6.4 adds the noncopyable `Continuation` (SE-0528) that makes the first a compile error and the second a trap.
- Unstructured `Task {}` is the quiet leak/error-swallower: Swift 6.4 adds the `NoUseUnstructuredThrowingTask` warning (SE-0520; absent in 6.3, measured) and SwiftLint has `unhandled_throwing_task`; neither covers the missing cancellation path or the strong `self` capture.
- Swift 6.4 retires two cleanup antipatterns: `await` inside `defer` (SE-0493) and `withTaskCancellationShield` (SE-0504). Older advice (`Task { await cleanup() }` from a `defer`, or skipping cleanup after cancellation) is now wrong for 6.4-floor code but still right for 6.3-and-below.
- Traps are the top server-side security class: swift-nio `Int(_:)` on a 64-bit WebSocket length (CVE-2026-43678), `UInt32(truncatingIfNeeded:)` ByteBuffer overflow giving out-of-bounds write (CVE-2026-43671), Hummingbird `ClosedRange` precondition on `Range: bytes=5-2` and unbounded recursion in a form decoder (three 2026-08 advisories). A rule must name the trapping initialisers and their non-trapping forms.
- Crash exit codes on Linux x86_64 -O builds are not a contract: trap/precondition/overflow/OOB/force-unwrap = 132 (SIGILL), fatal access-conflict and unowned-dead = 134 (SIGABRT), stack overflow = 139, early-closed pipe = 141 with no message. Piped stdout loses buffered `print` output before a trap (measured). A Swift CLI must never let a trap stand in for an error exit code.
- Dictionary/Set iteration and `JSONEncoder` key order are re-randomised per process (measured, two runs differ); `.sortedKeys` is required for any file that is hashed, diffed, locked or signed. Default `JSONEncoder` `Date` encoding is a Double since 2001-01-01 (`-978307200` for the Unix epoch), a silent wire-format trap.
- String semantics bite in boring ways: `"e\u{301}x".hasPrefix("e")` is `false`, `count`/`utf8.count`/`utf16.count`/`NSString.length` of one three-glyph string are 3/29/14/14, `"a" < "B"` is `false` while `localizedCompare` says ascending, `"ß".uppercased()` is `"SS"` (all measured).
- Foundation on Linux: `URLSession` needs `import FoundationNetworking`; the error is `type 'URLSession' (aka 'AnyObject') has no member 'shared'` (measured 6.4). Static Linux SDK has no `dlopen` and uses Musl; 6.4 `--static-swift-stdlib` can miss `_FoundationICU` archives ([forum 89913](https://forums.swift.org/t/static-linking-issue-using-swift-6-4-0-on-linux/89913)).
- `unsafeFlags` in a dependency blocks consumers only when the dependency's `swift-tools-version` is below 6.2 (measured: dep at 6.0 → `contains unsafe build flags`; dep at 6.2 builds). The "disable the check" change landed 2025-07 but was gated by tools version ([PR 8951](https://github.com/swiftlang/swift-package-manager/pull/8951)).
- Macro packages remain the top SwiftPM resolution hazard: a single `from: 603.0.0` swift-syntax requirement conflicts with every sibling pinned to 602; guidance is a wide range, `#if canImport(SwiftSyntaxXYZ)`, and an opt-out product/trait for macros in foundational libraries; multiple major versions are not supported ([forum 86317](https://forums.swift.org/t/multiple-major-versions-of-a-package-in-swiftpm-opening-the-discussion/86317)).
- Swift 6.4 makes Swift Build the default SwiftPM build system (`--build-system native` is marked deprecated); parity gaps are live (per-configuration `unsafeFlags` linker settings imparted to Debug, [#10597](https://github.com/swiftlang/swift-package-manager/issues/10597)).
- Type-checker timeouts still reproduce in 6.4 and 6.3 with mixed integer/double literal arithmetic (measured: 3.6 s then `the compiler is unable to type-check this expression in reasonable time`); `-warn-long-expression-type-checking=N` and `-warn-long-function-bodies=N` localise them; a roadmap exists but is not shipped as a fix ([forum 82952](https://forums.swift.org/t/roadmap-for-improving-the-type-checker/82952)).
- Swift Testing runs tests in parallel in-process by default; any shared global, env var, cwd, port or temp path is a flake source. XCTest and Swift Testing assertions interoperate from 6.4 (ST-0021), which removes the all-or-nothing migration excuse.

## Survey

### 2.1 Migration guide "Common Compiler Errors" and Runtime Behavior

Read in full: [CommonProblems.md](https://raw.githubusercontent.com/swiftlang/swift-migration-guide/main/Guide.docc/CommonProblems.md) (860 lines), [RuntimeBehavior.md](https://raw.githubusercontent.com/swiftlang/swift-migration-guide/main/Guide.docc/RuntimeBehavior.md), grep of [DataRaceSafety.md](https://raw.githubusercontent.com/swiftlang/swift-migration-guide/main/Guide.docc/DataRaceSafety.md). Chapter headings: "Unsafe Global and Static Variables" (Sendable Types / Non-Sendable Types), "Protocol Conformance Isolation Mismatch" (Under-Specified Protocol, Adding Isolation, Asynchronous Requirements, Preconcurrency Conformance, Isolated Conforming Type, Non-Isolated, Conformance by Proxy), "Crossing Isolation Boundaries" (Implicitly-Sendable Types, Preconcurrency Import, Latent Isolation, Computed Value, Sending Argument, Sendable Conformance: Global Isolation, Actors, Manual Synchronization, Retroactive Sendable Conformance, Sendable Reference Types, Using Composition).

- Canonical diagnostic: `global variable 'x' is not concurrency-safe because it is non-isolated global shared mutable state`, with three notes: convert to `let`; restrict to the main actor; "unsafely mark … as concurrency-safe if all accesses are protected by an external synchronization mechanism" (`nonisolated(unsafe)`). The guide ladders them in that order and says `nonisolated(unsafe)` is only for variables "carefully" guarded by "a lock or dispatch queue".
- The guide states complete checking "can surface latent issues, even in Swift 5 code that doesn't use any concurrency language features directly" and that most warnings trace to a small set of root causes — the basis for a class-based fix catalogue.
- Runtime Behavior chapter: "Limiting concurrency using Task Groups" — creating thousands of child tasks eagerly allocates memory per task; the guide throttles with `maxConcurrentWorkTasks = min(lotsOfWork.count, 10)` and re-`addTask` on each completed result (`addTask` or `addTaskUnlessCancelled`).
- `@unchecked Sendable` is positioned as the "Manual Synchronization" option: the type promises thread safety and "the compiler will not perform any checking".

### 2.2 Compiler diagnostic-group documentation (swiftlang/swift userdocs)

Directory listing of `userdocs/diagnostics` (≈75 files) and full reads of: `diagnostic-groups`, `sending-risks-data-race`, `nonisolated-nonsending-by-default`, `implicit-strong-capture`, `no-use-throwing-unstructured-task`, `exclusivity-violation`, `strict-memory-safety`, `isolated-conformances`, `temporary-pointers` under [userdocs/diagnostics](https://github.com/swiftlang/swift/tree/main/userdocs/diagnostics).

- Warning-control syntax: `-Werror <group>`, `-Wwarning <group>`, `-warnings-as-errors -Wwarning DeprecatedDeclaration` (the doc's own example).
- `SendingRisksDataRace`: error text `sending 'person' risks causing data races`; "most common fix" is `nonisolated(nonsending)` on the `async` method, or enabling `NonisolatedNonsendingByDefault`.
- `NonisolatedNonsendingByDefault` (SE-0461, Swift 6.2): `-enable-upcoming-feature NonisolatedNonsendingByDefault`; migrate with `NonisolatedNonsendingByDefault:migrate`, which adds `@concurrent` to every existing nonisolated async function; `@concurrent` = "always switch off of an actor".
- `ImplicitStrongCapture`: a `[weak self]` in an inner closure while the outer escaping closure implicitly captures `self` strongly — the weak is decorative. Silence by an explicit capture-list item on the OUTER closure.
- `NoUseUnstructuredThrowingTask`: `Task { throw MyError() }` unused → warning; fix by storing, awaiting `task.value`, or `_ = Task {…}`.
- `ExclusivityViolation`, `TemporaryPointers` (inout-to-pointer and string-to-pointer conversions are valid only for the call), `StrictMemorySafety` (`-strict-memory-safety`, `@unsafe`, `unowned(unsafe)`, `unsafeBitCast`), `IsolatedConformances` (a `@MainActor P` conformance cannot satisfy a `Sendable` requirement; `acceptSendableP(myType)` errors).
- Other groups listed with warnings: `DeprecatedDeclaration`, `PreconcurrencyImport`, `AddPreconcurrencyImport`, `ExistentialType`, `SemanticCopies`, `UntypedThrows`, `UnnecessaryUnsafe`, `UnstableGlobalActorShared`, `Oslog`, `UseAnyAppleOSAvailability`, `ReturnTypeImplicitCopy`, `EmbeddedRestrictions`, `UselessAvailabilityCheck`, `VariableNeverMutated`, `UnusedImportAccess`.

### 2.3 Language Steering Group vision: approachable data-race safety

Read [visions/approachable-concurrency.md](https://raw.githubusercontent.com/swiftlang/swift-evolution/main/visions/approachable-concurrency.md) (198 lines; Swift Forums thread 76183, 183 posts, 2024-11-23). Key claims: three-phase progressive disclosure (sequential → async without data-race errors → parallelism); executables default to the main actor, libraries "default to `nonisolated` the same way they do today" and "specific libraries could still decide to default to the main actor" (UI widget libraries); a permanent per-module "dialect" is acknowledged as a readability risk; SE-0423 dynamic isolation assertions "make Swift 6 adoption painful for clients when they migrate before their dependencies"; some runtime crashes are "false positives" because the check is inserted from static isolation.

### 2.4 Swift Forums problem threads 2024-2026

Fetched through the Discourse JSON API (`https://forums.swift.org/t/<id>.json`, `/search.json`); posts read, not snippets.

- Continuation misuse: [Pitch: Continuation](https://forums.swift.org/t/pitch-continuation-safe-and-performant-async-continuations/85165) (2026-03-05, 41 posts, 45 likes on the opener) states `UnsafeContinuation` "resuming twice is undefined behavior and forgetting to resume silently leaks the awaiting task forever"; became SE-0528.
- Long synchronous work on the cooperative pool: [Is @concurrent now the standard tool…](https://forums.swift.org/t/is-concurrent-now-the-standard-tool-for-shifting-expensive-synchronous-work-off-the-main-actor/82976) (2025-10-31, 45 posts): answerers say the pool is "engineered to avoid the thread explosion issue" so non-yielding work can fill all queues ("It won't deadlock, it will just feel that way"); advice: `Task.yield()` to break up work, or wrap a `DispatchQueue` in a continuation for long opaque work.
- Crash class: [Incorrect actor executor assumption run-time error](https://forums.swift.org/t/incorrect-actor-executor-assumption-run-time-error-in-swift-6-mode/74870) (global-actor class conforming to a protocol, accessed through the existential; ktoso links swift#76507 "Opening actor existentials breaks dynamic isolation checks inserted for @preconcurrency conformances"; a later poster found that making the protocol requirement `{ get async }` avoided it). [MainActor.assumeIsolated crashes on main thread](https://forums.swift.org/t/mainactor-assumeisolated-crashes-on-main-thread/80624) (2025-06-23, `awakeFromNib` on a `NSTextView` subclass; `EXC_BREAKPOINT` from `_assertionFailure` in `MainActor.assumeIsolated`; answerers call it "a bug" — read-only, Apple runtime).
- Detached tasks: [Is Task.detached still useful?](https://forums.swift.org/t/is-task-detached-still-useful/83580) (2025-12-05): `Task.detached` drops actor isolation, priority and task-local state; alternatives are a `TaskExecutor` preference (which also affects the whole child hierarchy, per ktoso), a nonisolated wrapper function, or the pending "closure isolation control" spelling.
- Cancellation: [Task Cancellation Shields](https://forums.swift.org/t/pitch-task-cancellation-shields/83379) (2025-11-23, 113 posts → SE-0504). Johannes Weiss: today's cleanup pattern `Task.value { try await cleanup }.value` "is bad"; motivating shape is `defer { try await withTaskCancellationShield { try await withTimeout(.seconds(10)) { … } } }`.
- Isolation and defaults: [Default actor isolation and deinit](https://forums.swift.org/t/default-actor-isolation-and-deinit/84511) (2026-02-01): with `-default-isolation MainActor`, a subclass's explicit `deinit` errors `nonisolated deinitializer 'deinit' has different actor isolation from main actor-isolated overridden declaration` while the base's implicit deinit is isolated — the proposals (SE-0371, SE-0466) do not state it. [defaultIsolation MainActor and Core Data background tasks](https://forums.swift.org/t/defaultisolation-mainactor-and-core-data-background-tasks/80569) (2025-06-20): generated `NSManagedObject` subclasses become `@MainActor` under Xcode 26 default isolation (read-only; Apple tooling).

[Best way to support multiple swiftsyntax versions](https://forums.swift.org/t/best-way-to-support-multiple-swiftsyntax-versions/86961) (2026-05-28) and [Multiple Major Versions of a Package in SwiftPM](https://forums.swift.org/t/multiple-major-versions-of-a-package-in-swiftpm-opening-the-discussion/86317) (2026-04-28): "if two parts of your dependency graph require incompatible major versions… SwiftPM is unable to resolve".

### 2.6 Apple Developer Forums and WWDC25 sessions (read-only for Apple runtimes)

### 2.8 Compile-time and diagnostic differences measured 6.3 vs 6.4

Fixtures in `fixtures/failure/diag` (`swiftc -swift-version 6 -typecheck`, `SWIFT_VERSION=6.3` for the older image).

- 6.4 only: `unstructured throwing task created by 'init(name:priority:operation:)' is not used, which may accidentally ignore errors thrown inside the task [#NoUseUnstructuredThrowingTask]`. 6.3: silent.

## Recent shifts seen in this corpus

- Swift 6.4.0 (2026-09-14/15): async `defer` (SE-0493) and `withTaskCancellationShield` (SE-0504) invalidate "never `await` in cleanup / cleanup is skipped after cancel" advice; `Continuation` (SE-0528) supersedes hand-rolled once-only wrappers for new code; `NoUseUnstructuredThrowingTask` makes `Task { try … }` fire-and-forget a compiler warning (SE-0520); `~Sendable` (SE-0518); `@diagnose` source-level warning control (SE-0522); Swift Build becomes SwiftPM's default (`--build-system native` deprecated, measured); Subprocess reaches 1.0; ST-0021 lets `XCTAssert` and `#expect` coexist ([release post](https://raw.githubusercontent.com/swiftlang/swift-org-website/main/_posts/2026-09-15-swift-6.4-released.md)).
- Swift 6.3 (2026-03-24): `ImmutableWeakCaptures` / `weak let` (SE-0481), Codable error printing (SE-0489), clock epochs (SE-0473), `@c`/`@cdecl` (SE-0495), official Swift SDK for Android. The upcoming-feature list is unchanged 6.3 → 6.4 (measured).
- Swift 6.2 (2025-09-15): `defaultIsolation(MainActor.self)` (SE-0466), `nonisolated(nonsending)` default and `@concurrent` (SE-0461), isolated conformances (SE-0470), isolated deinit (SE-0371), strict memory safety (SE-0458), SwiftPM `strictMemorySafety`/`defaultIsolation` settings (tools 6.2), `unsafeFlags` check lifted for tools 6.2+ dependencies (PRs 8896/8951). Older advice "nonisolated async runs on the global executor" is now conditional on whether `NonisolatedNonsendingByDefault` is enabled; "mark everything `@MainActor`" is superseded by the module-level setting.
- Swift 6.1 (2025-03-31): `-warnings-as-errors` finer control (SE-0443), package traits (SE-0450), member import visibility (SE-0444); runtime crash in `async let` inside `do {}` (swift#81771, open).
- Xcode 16 → 26: Swift 6 mode in Xcode 16 introduced the SE-0423 dynamic isolation crashes that DTS and forum threads document; Xcode 26 turns default `MainActor` isolation on for new app projects (WWDC25 268), which changes Core Data generated models and `Bundle.module` behaviour (read-only).
- 2026 server CVEs shift the security baseline: swift-nio ≥ 2.100.0 for the `ByteBuffer` fix; Hummingbird ≥ 2.26.0; the lesson "memory-safe ≠ crash-safe on untrusted input" is now documented by vendor advisories, not folklore.
- Tooling: SwiftLint 0.65.1 and SwiftFormat 0.63.1 (per the frame) do not know the new 6.4 escape-hatch landscape; swift-format is bundled in the toolchain (`swift format`).

## Contested

- Escape hatches vs refactoring: the migration guide and WWDC25 268 say keep model classes non-`Sendable` and on the main actor ("Making a class `Sendable` usually requires … a lock"); swift-nio and swift-protobuf maintainers use `@unchecked Sendable`/`nonisolated(unsafe)` extensively but demand a written justification. Trend: hatches tolerated in infrastructure libraries with proof, discouraged in application code.
- Offloading CPU work: Apple's WWDC guidance says `@concurrent`; forum answerers (younata, Jon Shier) say long non-suspending work belongs on Dispatch/threads because the cooperative pool is deliberately width-bounded. Trend: `@concurrent` plus `Task.yield()` for moderate work; Dispatch for long opaque work, until a first-party "run on a queue" API exists.
- `Task.detached`: older advice says use it to leave the main actor; the 2025-12 thread says task-executor preference, a nonisolated wrapper, or `@concurrent` are better and detached is a side-effect-heavy tool. Trend: detached is rare (40 exemplar hits) and shrinking.
- `unsafeFlags`: SwiftPM engineers (Schaefer, Petroules, Dvorsky) argue the check was never well-defined and should go; Ecosystem Steering Group supported removal; implementation is gated to tools 6.2+. Trend: relaxing, but only for new manifests.
- Macros in foundational libraries: Point-Free and Apple engineers say prebuilt swift-syntax makes them acceptable if opt-out exists; others fear resolution/build cost, and traits do not yet prevent resolving unused dependencies. Trend: acceptable with a macro-free product and a wide swift-syntax range.
- Dynamic isolation checks: SE-0423 runtime assertions catch real races but also false positives; the vision admits some should be elided. Trend: fewer false positives over releases, but `-disable-dynamic-actor-isolation` remains an unsupported crutch.
- Where the source/hypothesis conflict: H1 (most exemplars in Swift 6 mode) was not tested in this corpus; H2 is partly contradicted — locks and `Mutex` (≈3400 hits) outnumber `@unchecked Sendable` + `nonisolated(unsafe)` (≈3350), though element-x-ios alone supplies 2006 of the latter; H7 is supported for unstructured `Task`, force-unwrap and `@unchecked Sendable`, and the lint-gap table (§2.14) shows why agents cannot be corrected by the formatter alone.
