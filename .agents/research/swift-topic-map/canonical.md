## Summary

- The Swift book is current to 6.4 (revision `2026-09-14`) but its concurrency chapter stops at the main actor/isolation basics: it has 0 mentions of `Mutex`, `nonisolated(unsafe)`, `nonsending`, `defaultIsolation`, `Span`, `InlineArray`, `@Observable`, `assumeIsolated`; `@concurrent` appears once, inside an HTML TODO comment about SE-0461.
- The Swift 6 migration guide (last commit 2026-01-02) predates the approachable-concurrency settings in practice: no `defaultIsolation`, `Mutex`, or `InlineArray` text, though it documents `swift package migrate --to-feature NonisolatedNonsendingByDefault`.
- The API Design Guidelines (page edited 2026-10-09) are Swift 3-era: grep finds no guidance on `async`, `Sendable`, `actor`, `throws`, `some`/`any`, noncopyable types, or `package`.
- `@unchecked Sendable` compiles with no diagnostic on 6.4 (fixture), so the compiler will never flag the most common escape hatch; review rules must.
- The first Swift 6 error every migration hits is `MutableGlobalVariable`; the diagnostic note fixes it in the order `let`, `@MainActor`, then `nonisolated(unsafe)` with external synchronization.
- Swift 6.2 made nonisolated async functions run on the caller's actor under `NonisolatedNonsendingByDefault` (SE-0461) and added `@concurrent`; pre-6.2 advice that nonisolated async hops to the global executor is inverted under that setting.
- The approachable-concurrency vision says libraries should not default to the main actor (executables may), confirming H8 as design intent.
- 6.4 closes the cleanup gap: async `defer` (SE-0493), `withTaskCancellationShield` (SE-0504), noncopyable `Continuation` (SE-0528), and a warning for ignored throwing `Task {}` (`NoUseUnstructuredThrowingTask`, reproduced).
- SwiftPM 6.4 makes Swift Build the default build system; the native system is labelled `(deprecated)` in `swift build --help` (verified), and bin paths, `--static-swift-stdlib` strictness and per-target test runners changed.
- Manifest API grows by tools version: 6.1 traits, 6.2 `defaultIsolation`/`treatWarning`/`enableWarning`/`strictMemorySafety`, 6.5 `bridgingHeader`; Swift Testing's default XCTest interop mode depends on toolchain and `swift-tools-version` (>=6.4 and >=6.4 gives `complete`).
- Warning control moved from module flags (SE-0443, 6.1) to diagnostic groups in manifests (6.2) to per-declaration `@diagnose(Group, as: error|warning|ignored)` (SE-0522, 6.4; compiles on 6.4.0).
- Swift Testing is documented as the migration target, with exit tests (6.2), attachments (6.2), `Test.cancel`/warning severity (6.3), repetition and XCTest interop (6.4); the migration page has no counterpart for UI or performance tests.
- Memory-safety tooling is opt-in and layered: `-strict-memory-safety` (6.2), `Span` family (6.2), `InlineArray` (6.2), and in 6.4 `UniqueBox`, `UniqueArray`, `Ref`, `Iterable`, borrow/mutate accessors; availability of the stdlib types is gated by `@available(SwiftStdlib 6.x)`.
- Cross-platform surface widened: static Linux SDK (musl), Wasm SDK on swift.org downloads, Android SDK (official since 6.3; still listed for 6.4.0 in `releases.json`), Windows (WinGet), but the Windows "guide" is a workgroup charter, not a how-to.
- `FilePath` (SE-0529, accepted with modifications) and `CommandLine` executable path (SE-0513) are heading into the standard library; until they ship, paths are swift-system `FilePath`, `URL`, or `String` and each has Windows and non-Unicode pitfalls.
- Library evolution got new tools: `@nonexhaustive` enums (SE-0487, 6.2.3), `@export(interface|implementation)` (SE-0497, 6.3), `@inline(always)` (SE-0496), `@specialized(where:)` (SE-0460, 6.3); `swift package diagnose-api-breaking-changes` is the gate.
- Several swift.org server guides are historical (XCTest-only testing guide, Docker recipes with `--static-swift-stdlib`), and the old concurrency-adoption guideline URL now redirects to the migration guide.
- Embedded Swift documentation disagrees with the release posts on whether public releases support it (user docs: "experimental... Public releases of Swift do not support Embedded Swift, yet"; 6.4 post and Wasm article ship an embedded SDK).

### 2. API Design Guidelines

Read: [swift.org/documentation/api-design-guidelines](https://www.swift.org/documentation/api-design-guidelines/) (source `documentation/api-design-guidelines/index.md`, 1069 lines, last edited 2026-10-09).

- Structure: Fundamentals (Clarity at the point of use; Clarity is more important than brevity; write a documentation comment); Naming (Promote Clear Usage, Strive for Fluent Usage, Use Terminology Well); Conventions (General, Parameters, Argument Labels); Special Instructions.
- Checklist items worth keeping: omit needless words; name by role not type; compensate for weak type information; fluent use sites; factory methods begin with `make`; name by side effects (`sort()` vs `sorted()`); Booleans read as assertions; protocol naming (`-able`, `-ible`, `-ing`); avoid abbreviations; document complexity of non-O(1) computed properties; methods over free functions; case conventions; default parameters trailing; prefer `#fileID` in production APIs; omit labels only when arguments cannot be distinguished; label tuple members; "take extra care with unconstrained polymorphism (`Any`, `AnyObject`)".
- Gaps: no text on `async` naming, `Sendable`, isolation, `throws(E)`, `some`/`any`, noncopyable parameters, `package` access, macros. The doc still reads as the Swift 3 original.

## Contested

- **Is Embedded Swift supported in public releases?** The embedded user documentation says "Embedded Swift is experimental. Public releases of Swift do not support Embedded Swift, yet" and tells readers to install `main-snapshot`; the 6.4 blog, the Wasm article and `swift sdk` give an `-embedded` SDK from a release. Trend: toward supported subset in releases (6.3/6.4 posts, `EmbeddedRestrictions` group), docs lagging.
- **`@specialize` or `@specialized`?** The 6.3 release post says `@specialize`; SE-0460 and WWDC26 use `@specialized(where:)`. Trust the proposal and compile before writing a rule.
- **Who should default to the main actor?** The approachable-concurrency vision and SwiftPM allow `defaultIsolation(MainActor.self)` per target and Xcode 26 enables it for new app projects, while the vision says libraries should not. The vision itself flags the "risk of a language dialect". Trend: executable/app targets on, libraries off.
- **Migration order.** The migration guide says begin outside-in in Swift 5 mode with `StrictConcurrency` warnings; the `swift package migrate` workflow and Xcode 26 templates push "flip the mode and fix" for new code. Trend: new code starts in 6 mode with approachable settings; old code follows the guide.
- **XCTest vs Swift Testing.** Swift Testing docs and WWDC26 267 say write new tests in Swift Testing and leave XCTests; the server guides (still XCTest-only) and any UI/perf testing have no Swift Testing path. Trend: Swift Testing for unit and integration; XCTest remains for UI and performance until documented otherwise.
- **`--static-swift-stdlib` vs the static Linux SDK.** The packaging guide recipes use the former; the SDK article treats musl static linking as the way to get a fully static executable. Swift Build now errors where the former is unsupported. Trend: SDK for fully static, `--static-swift-stdlib` for Docker/glibc.
- **Should strict memory safety become default?** The memory-safety vision poses it as an open question; 6.2-6.4 keep it opt-in. Trend: opt-in, with more safe APIs (Span, `withTemporaryAllocation`, safe `RawSpan` loads) removing reasons to use `unsafe`.
- **Stdlib vs package for paths.** SE-0529 moves `FilePath` into the stdlib ("Accepted with modifications") while swift-system remains the shipping implementation. Trend: stdlib, but not in 6.4.0.
- **Where Windows guidance lives.** The Windows workgroup (revived 2026-01-26) is charter-only on swift.org; practical guidance is in forums and the Foundation/Testing sources. Trend: more official material is likely, none yet.
