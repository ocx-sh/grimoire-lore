## Summary

- rules_rust's own `MODULE.bazel` calls `rust.toolchain(edition = "2021")` as a non-dev-dependency tag, and `_rust_impl`'s fallback (`root.tags.toolchain or rules_rust.tags.toolchain`) means a root module that `use_extension`s the `rust` extension but never calls `rust.toolchain(...)` itself still gets a fully working, silently-version-pinned toolchain — rules_rust's own default, not an error.
- That default floats on almost every release: `DEFAULT_RUST_VERSION` went 1.95.0 → 1.96.0 → 1.97.1 → 1.97.1 → 1.98.0 across tags 0.70.0 → 0.74.0 (four months), each paired with a re-dated nightly (`nightly/2026-04-16` → `nightly/2026-08-20`). Bumping the `rules_rust` `bazel_dep` version alone re-pins the compiler for any repo that never sets `versions=`.
- Both a stable *and* a nightly toolchain are registered and fetched by default (`_RUST_TOOLCHAIN_VERSIONS = [rust_common.default_version, DEFAULT_NIGHTLY_VERSION]`), even though toolchain **selection** defaults to stable via `@rules_rust//rust/toolchain/channel:channel` (`build_setting_default = "stable"`) — a plain default setup downloads a nightly toolchain that resolution will never pick unless `--@rules_rust//rust/toolchain/channel:channel=nightly` is passed.
- A `versions` entry for beta/nightly must carry an ISO date; a bare `"nightly"`/`"beta"` is a hard `fail()`: *"iso_date must be specified if version is 'beta' or 'nightly'"* (`rust/private/repository_utils.bzl:843`).
- rules_rust's source never reads `rust-toolchain.toml`: `grep -rl "rust-toolchain" .` over the whole 0.74.0 tag returns zero files. Cargo's own toolchain-pin file is completely invisible to the ruleset.
- `extra_target_triples` (the `rust.toolchain()` cross-compile default) and `SUPPORTED_PLATFORM_TRIPLES` (crate_universe's `crates_repository` default, BZL-RUST-08) are two *different* curated lists in two different files — the toolchain one carries three wasm triples and both Apple/Linux arches but zero Windows; never assume the two are the same set.
- `cargo_build_script`'s new `root_path` ([#4243](https://github.com/bazelbuild/rules_rust/pull/4243), merged 2026-08-27) is a pure 3-line pass-through into `rust_binary`'s pre-existing `root_path` attribute (added by [#4142](https://github.com/bazelbuild/rules_rust/pull/4142)), governing crate-root resolution when `srcs` is a single `TreeArtifact`. It never touches `cargo_build_script.bzl`'s `_cargo_build_script_impl` — the file that actually synthesizes `CARGO_MANIFEST_DIR`. BZL-RUST-12/13's guarantees are unaffected.
- `rust_prost_library`/`rust_prost_toolchain` live in **`rules_rust_prost`**, a *separate* BCR module pinned to 0.74.0 alongside `rules_rust` (not auto-pulled by `bazel_dep(rules_rust)` alone), and it is the only Bazel-native protobuf codegen path shipping at this version — there is no separate legacy `rust_proto_library`/`rust_grpc_library` extension to choose between. Tonic is not a separate rule; it is `tonic_plugin`/`tonic_runtime` attributes on the *same* `rust_prost_toolchain`.
- `rules_rust_prost` does register a working default toolchain (`//:default_prost_toolchain`, wired to its own vendored prost 0.13.1/tonic 0.12.1 crates), despite the docstring's blanket "no default toolchain" framing — the actual reason to author a custom one is avoiding a type-identity mismatch between the toolchain's internal tonic/prost versions and whatever version a service crate pulls through its own `crate_universe` graph.
- crate_universe's per-crate tarball fetch (`mode = "remote"`, the default) is rendered as an ordinary `http_archive(url=..., sha256=...)` call (`repo_http.j2`) — a genuine Bazel-native download `--credential_helper`/`.netrc` cover like any other. The lockfile/metadata resolution step (`cargo-bazel splice`/`query`) instead runs via `repository_ctx.execute()` wrapping a real `cargo` binary — an arbitrary subprocess Bazel's credential helper cannot see at all.
- `cargo_config` (a `.cargo/config.toml` you point at) is available on both `crates_repository` (WORKSPACE) and `crate.from_cargo`/`crate.from_specs` (bzlmod); cargo-bazel's own splicer (`cargo_config.rs`) parses `[registry]`/`[registries.NAME]`/`[source.NAME]` including `replace-with`, tested directly against an Artifactory-shaped fixture in the ruleset's own unit tests.
- The ruleset's own docs state the private-registry recipe in plain language, naming Artifactory: *"make sure you set the `CARGO_BAZEL_ISOLATED=false` … If not, crates_universe will not be able to pull from your private registry."* This is the sanctioned mechanism, not an inferred one, and it directly grounds BZL-RUST-02's escape hatch.
- `crates_vendor`'s (not `crates_repository`'s) private-registry/SSH credential forwarding was outright broken by a literal typo (`grep ^CARGO_REGISTER`, which never matches a real `CARGO_REGISTRY*`/`CARGO_REGISTRIES_*` variable) until [#3964](https://github.com/bazelbuild/rules_rust/pull/3964), merged 2026-04-16, replaced the narrow allowlist with `env -u OUTPUT_BASE` — full ambient-environment passthrough minus one variable. Confirmed still present, unchanged, at the 0.74.0 tag.
- There is no stardoc-`diff_test`-equivalent staleness gate for `rust_doc` anywhere in the ruleset (zero `diff_test` hits in the whole 0.74.0 tree). The stardoc analogy does not transfer cleanly: `rust_doc`'s normal output is a build artifact (a zip meant for hosting), not a checked-in file diffed against source, and its HTML content is a pure function of the pinned Rust toolchain — never of the Bazel major, unlike stardoc's Build-API coupling.

## Answers

### Q1 — `rust.toolchain()` pinning at 0.74.0

> `rust.toolchain()` at 0.74.0: fetch `rust/extensions.bzl` and `rust/repositories.bzl` from bazelbuild/rules_rust at the 0.74.0 tag — what `versions`, `edition`, `rust_analyzer_version`, `sha256s`, `extra_target_triples`, `extra_exec_rustc_flags_triples` pin; what the default versions are at that tag and whether they float per release; how a repo with no rust-toolchain.toml and no MSRV (3 of 6 fleet repos) should choose (the ruleset's stance on nightly vs stable, `allocator_library`, the "beta"/"nightly" channel spellings); whether Cargo's rust-toolchain.toml is read at all (it is not — confirm) and the proposed drift check between rust-toolchain.toml and rust.toolchain(versions=...).

**Findings.**

*File location correction first.* At 0.74.0 there is no `rust/repositories.bzl` — the module-extension surface is `rust/extensions.bzl`, and the actual `attr.*()` declarations and defaults live one level down at [`rust/private/repositories.bzl`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/repositories.bzl) and [`rust/private/repository_utils.bzl`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/repository_utils.bzl). The commission's file name is close but not exact; cite the `private/` path.

*The `toolchain` tag class, attribute by attribute, read directly from `extensions.bzl:250-302`* (cross-checked against the rendered [`rust_bzlmod.html`](https://bazelbuild.github.io/rules_rust/rust_bzlmod.html), which matches the tag's own defaults exactly):

| Attribute | Type | Default at 0.74.0 |
|---|---|---|
| `versions` | `string_list` | `["1.98.0", "nightly/2026-08-20"]` (`_RUST_TOOLCHAIN_VERSIONS = [rust_common.default_version, DEFAULT_NIGHTLY_VERSION]`) |
| `edition` | `string` | `""` (unset — every rule must then set its own `edition`) |
| `rust_analyzer_version` | `string` | `""` (unset — falls back to `select_rust_version(versions)`, i.e. tracks the pinned rustc, [`repository_utils.bzl:135-136`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/repository_utils.bzl#L135-L136)) |
| `sha256s` | `string_dict` | `{}` (empty — see integrity fallback below) |
| `extra_target_triples` | `string_list` | `DEFAULT_EXTRA_TARGET_TRIPLES` = `["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "x86_64-apple-darwin", "x86_64-unknown-linux-gnu", "wasm32-unknown-unknown", "wasm32-wasip1", "wasm32-wasip2"]` ([`repository_utils.bzl:27-35`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/repository_utils.bzl#L27-L35)) |
| `extra_exec_rustc_flags_triples` | `string_list_dict` (keyed by triple) | `{}`; the extension `fail()`s if both this and `extra_exec_rustc_flags` are set on the same tag call (`extensions.bzl:121-122`) — already BZL-RUST-15's finding, reconfirmed at this tag |
| `allocator_library` / `global_allocator_library` | `label` | `None` (unset; no custom allocator wired unless you supply one) |

*Whether the defaults float — yes, measured across five tags:*

```
0.70.0: DEFAULT_RUST_VERSION = "1.95.0"   DEFAULT_NIGHTLY_ISO_DATE = "2026-04-16"
0.71.0: DEFAULT_RUST_VERSION = "1.96.0"   DEFAULT_NIGHTLY_ISO_DATE = "2026-05-28"
0.72.0: DEFAULT_RUST_VERSION = "1.97.1"   DEFAULT_NIGHTLY_ISO_DATE = "2026-07-16"
0.73.0: DEFAULT_RUST_VERSION = "1.97.1"   DEFAULT_NIGHTLY_ISO_DATE = "2026-07-16"
0.74.0: DEFAULT_RUST_VERSION = "1.98.0"   DEFAULT_NIGHTLY_ISO_DATE = "2026-08-20"
```

(`rust/private/common.bzl:34,36` at each tag, read directly.) Four of five releases moved the default. This is the Rust-toolchain analogue of BZL-PY-01's Python finding: **the default is hermetic, but it is not pinned, and it moves on its own schedule** — a `rules_rust` version bump alone silently re-pins the compiler for any consumer that never sets `versions=`.

*A genuinely non-obvious mechanism: how a repo with no `rust.toolchain()` call at all still builds.* rules_rust's own [`MODULE.bazel:47-49`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/MODULE.bazel#L47-L49) declares:
```python
rust = use_extension("//rust:extensions.bzl", "rust")
rust.toolchain(edition = "2021")
use_repo(rust, "rust_toolchains")
```
This is **not** marked `dev_dependency = True`, so it is visible module-graph-wide. `_rust_impl`'s toolchain-selection line reads: `toolchains = root.tags.toolchain or rules_rust.tags.toolchain` ([`extensions.bzl:116`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/extensions.bzl#L116)). If the *root* module (a consumer's own `MODULE.bazel`) never calls `rust.toolchain(...)` — but still `use_extension`s the `rust` extension and `use_repo`s it, which is required to reach `register_toolchains(...)` at all — `root.tags.toolchain` is the empty list, and the extension silently falls back to **rules_rust's own** `rust.toolchain(edition = "2021")` tag, with every other attribute at its tag-class default. A repo can therefore end up building real Rust with a fully operational toolchain while nothing in its own `MODULE.bazel` ever named a version — the version is whatever `rules_rust` 0.74.0 happens to ship, and it changes on the next `bazel_dep` bump with zero signal.

*Channel handling — the ruleset's actual stance on nightly vs stable.* `@rules_rust//rust/toolchain/channel:channel` is a `string_flag`-shaped build setting, `build_setting_default = "stable"`, `scope = "universal"` ([`rust/toolchain/channel/BUILD.bazel`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/toolchain/channel/BUILD.bazel)), with `config_setting`s for `beta`/`nightly`/`stable` gating each registered toolchain's `target_settings`. So: **stable is the default selection, unconditionally** — there is no MSRV-aware or repo-content-aware selection logic anywhere in the ruleset; it is a flat, global flag. Because the default `versions` list registers *both* a stable and a nightly toolchain, a plain default setup fetches (downloads) the nightly toolchain too, even though it is never selected without the flag flip — a real, un-warned bandwidth/disk cost with no opt-out short of setting `versions` explicitly to a single-channel list.

*Beta/nightly spelling — a hard-`fail()`, not a convention.* `check_version_valid()` enforces the date requirement in code, not merely in a doc example: `if version in ("beta", "nightly") and not iso_date: fail("{param_prefix}iso_date must be specified if version is 'beta' or 'nightly'")` ([`rust/private/repository_utils.bzl:842-843`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/repository_utils.bzl#L842-L843)). `"nightly"` or `"beta"` alone is invalid input, not a fuzzy default; it must be `"nightly/2026-08-20"`-shaped.

*`sha256s` — the integrity fallback, and its gap.* An empty `sha256s` dict does **not** mean unverified downloads for a known release: `sha256 = sha256s.get(archive_path, None) or FILE_KEY_TO_SHA.get(archive_path, None)` ([`rust/private/repository_utils.bzl:685`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/repository_utils.bzl#L685)) falls back to the ruleset's own committed `known_shas.bzl` table of official rust-lang.org-published hashes. The gap is real but narrow: a version/target combination absent from that table (a very fresh release, an unusual nightly date) resolves `sha256 = None`, and Bazel's `download`/`download_and_extract` proceed with **no integrity check at all** in that case — silent, not loud.

*Whether `rust-toolchain.toml` is read — confirmed, it is not.* `grep -rn "rust-toolchain" .` across the entire extracted 0.74.0 tarball (every `.bzl`, `.rs`, `.md`, test fixture included) returns **zero matches**. Cargo's toolchain-pin file has no code path into rules_rust whatsoever — not read, not validated, not cross-checked. Combined with the floating-default finding above, this means a repo that keeps `rust-toolchain.toml` for `cargo build`/rustup and *also* adopts Bazel has two independent, unlinked version sources by construction; nothing in either tool notices if they diverge.

*The proposed drift check.* Because nothing upstream links the two files, any consistency check is a project-authored addition, not a ruleset feature. For a repo that already carries `rust-toolchain.toml` (3 of the fleet's 6 Rust repos do not, and for those the more urgent question is BZL-RUST-01's "pin `versions=` at all," not drift), the mechanical form is: read `channel`/`[toolchain] channel` out of `rust-toolchain.toml`, read the first stable entry out of `rust.toolchain(versions=[...])` in `MODULE.bazel`, and fail CI if they disagree. This is worth stating as a SHOULD, not MUST — `rust_analyzer:setup` (BZL-RUST-20, already established) already gets rust-analyzer, the proc-macro server, and rustfmt from the Bazel toolchain with **no host Rust install**, which means `rust-toolchain.toml`'s only remaining live consumer in a Bazel-adopted repo is a bare `cargo build`/`cargo test` run outside Bazel (a contributor without Bazel, or a CI leg that intentionally exercises the Cargo path directly) — a real but narrower audience than "every developer," so the drift check is a hygiene SHOULD, not a MUST.

**Answer.** At rules_rust 0.74.0, `rust.toolchain()`'s `versions` defaults to `["1.98.0", "nightly/2026-08-20"]`, `edition` and `rust_analyzer_version` default to unset (the latter falling back to the pinned rustc version), `sha256s` defaults to empty but is backstopped by a committed known-hash table for official releases, `extra_target_triples` defaults to a curated seven-triple list distinct from crate_universe's own curated seven, and `extra_exec_rustc_flags_triples` cannot be combined with `extra_exec_rustc_flags` on one tag (enforced by `fail()`). The default `versions` float on almost every release (measured across five tags), and — critically — a root module that never calls `rust.toolchain()` at all still gets rules_rust's own default toolchain via a documented-in-code fallback, not an error. The ruleset's stance on channel is a flat default-to-stable build flag with no MSRV awareness, both channels fetched regardless of which is selected, and beta/nightly version strings without an ISO date are a hard failure. `rust-toolchain.toml` is never read by any code path in the ruleset at this or, per the empty grep, any recent version; a drift check against it is a project-authored SHOULD, most valuable for the minority of repos that still run a bare `cargo build` alongside Bazel.

### Q2 — Protobuf codegen: prost/tonic under Bazel

> Protobuf codegen: rules_rust's proto/prost and proto/protobuf extensions at 0.74.0 (`rust_prost_library`, `rust_prost_toolchain`, tonic support; the older `rust_proto_library`) — what creeptd-ng's build.rs-driven tonic-build/prost-build over 7 .proto files (crates/creeptd-proto, read-only) becomes under Bazel: `rust_prost_library` on a `proto_library` (with Bazel 9 autoload caveat, cite the aspects-vs-macros-protobuf-and-execution-groups.md dive), a `cargo_build_script` wrapping tonic-build with a declared protoc toolchain, or keep build.rs and declare protoc as a tool. State the recommended path and its cost.

**Findings.**

*There is no separate legacy `rust_proto_library` shipping at 0.74.0.* `extensions/` under the 0.74.0 tag contains exactly `bindgen, mdbook, prost, pyo3, wasm_bindgen` — no `proto`/`protobuf` directory. `grep -rl "rust_proto_library\|rust_grpc_library" .` over the whole tag hits only `examples/proto/README.md` and `examples/proto/proto_bindings/BUILD.bazel`, and those are the current example's own comment linking to `https://bazelbuild.github.io/rules_rust/rust_proto.html#rust_proto_library` — a stale link (the live page is `rust_prost.html#rust_prost_library`; the same "own docs cite the wrong/dead thing" pattern the consolidation already logged for `bazel sync`, Verdict 3). There is exactly one Bazel-native proto path in this ruleset today: `rust_prost_library`.

*It ships in a separate BCR module.* `extensions/prost/MODULE.bazel` declares `module(name = "rules_rust_prost", version = "0.74.0")` with its own `bazel_dep(name = "rules_rust", version = "0.74.0")`, `bazel_dep(name = "rules_proto", version = "7.1.0")`, `bazel_dep(name = "protobuf", version = "28.3", repo_name = "com_google_protobuf")`. `bazel_dep(name = "rules_rust", version = "0.74.0")` alone does **not** pull this in — a consumer needs a separate `bazel_dep(name = "rules_rust_prost", version = "0.74.0")`.

*`rust_prost_library`'s shape confirms the one-`proto_library`-plus-aspect model* (already established for C++/Python by the sibling `aspects-vs-macros-protobuf-and-execution-groups.md` dive, [§2](../bazel-followups/aspects-vs-macros-protobuf-and-execution-groups.md#2-protobuf-modelling-under-bzlmod-on-bazel-9)): its sole proto-facing attribute is `"proto": attr.label(providers = [ProtoInfo], aspects = [rust_prost_aspect], mandatory = True)` ([`extensions/prost/private/prost.bzl:429`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/extensions/prost/private/prost.bzl#L429)). You point it at one `proto_library`; the aspect walks that target's `deps`. On Bazel 9 with `--incompatible_autoload_externally` empty, the underlying `proto_library` call needs its own explicit `load("@protobuf//bazel:proto_library.bzl", "proto_library")` — the exact caveat the sibling dive already nailed down with primary sources; this dive adds nothing new there beyond confirming `rust_prost_library` sits on top of that same `proto_library`, unaffected by which loading mechanism produced it.

*Tonic is not a second rule — it is toolchain attributes on the same rule.* `rust_prost_toolchain` takes `prost_plugin`, `prost_runtime`, `prost_types`, `proto_compiler`, `tonic_plugin`, `tonic_runtime` all on one declaration ([`extensions/prost/defs.bzl:99-119`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/extensions/prost/defs.bzl#L99-L119); `extensions/prost/private/BUILD.bazel:75-87` for the shipped default instance). The actual gRPC codegen is done by a `protoc` plugin crate, **`protoc-gen-tonic`** — a from-scratch reimplementation of `tonic-build`'s codegen as a `protoc` plugin, not `tonic-build` itself (`tonic-build` is a build.rs-time library; it has no role in this path at all).

*A default toolchain does exist, contrary to the docstring's blanket claim.* `defs.bzl`'s own prose says "the prost and tonic rules do not specify a default toolchain," but `extensions/prost/BUILD.bazel` registers `toolchain(name = "default_prost_toolchain", toolchain = "//private:default_prost_toolchain_impl", ...)`, and `extensions/prost/MODULE.bazel` itself calls `register_toolchains("//:default_prost_toolchain")` — a normal (non-dev) registration, so it is visible to any consumer's toolchain resolution once `rules_rust_prost` is a `bazel_dep`. That default is wired to the module's own internally vendored crates (`rrprd__prost-0.13.1`, `rrprd__tonic-0.12.1`, etc., under `//private/3rdparty/crates`). It genuinely works end to end for a toy example. The real reason the docs steer you toward a custom toolchain is not "there is none" but **avoiding a type-identity mismatch**: generated code references `tonic::Request<T>`/`prost::Message` from whichever `tonic`/`prost` crate the *toolchain's* `tonic_runtime`/`prost_runtime` point at; if a service crate's own `crate_universe`-resolved `tonic`/`prost` is a different version, the two are different Rust types from Cargo's perspective and the build fails to compile with a confusing "expected `tonic::Request`, found `tonic::Request`" — exactly the failure mode "mismatched dependency issues" in the docs is naming, just not spelled out mechanically.

*How creeptd-proto's 7 files map onto this.* Reading the fleet source directly (`creeptd-ng/crates/creeptd-proto/build.rs`, `Cargo.toml`, read-only per the commission): the crate compiles `health.proto`, `ids.proto`, `identity.proto`, `lobby.proto`, `game.proto`, and two leaderboard files (`match_result.proto` + `leaderboard.proto`, compiled together) — seven files across five logical steps, using `tonic_build::configure().build_server(true).build_client(true).extern_path(".creeptd.common.v1", "crate::common")…compile_protos(...)`, with a vendored `protoc` from the `protoc-bin-vendored` crate (no system dependency) and a workspace-relative `proto_root` at `CARGO_MANIFEST_DIR/../../proto`. Under `rust_prost_library`, this becomes: one `proto_library` per package (mirroring the existing `health`, `common`(ids), `identity`, `lobby`, `game`, `leaderboard` boundaries — six `proto_library` targets for seven files, matching the crate's own five-step, six-package grouping), each with `deps = [":common_proto"]` wherever it imports `creeptd.common.v1` (Bazel's native `proto_library` `deps=` graph does this import resolution structurally — there is no `extern_path`-shaped workaround needed for cross-package Bazel-native `proto_library` imports; whether `rust_prost_aspect` also needs `rust_prost_transform`'s `prost_opts`/`tonic_opts` to reproduce the crate's *module layout* choice, i.e. whether generated Rust code nests `pkg::common::v1` or flattens to `crate::common` the way the current `extern_path` call does, is **not verified end to end** by this dive — see Not settled), then one `rust_prost_library(proto = ":<pkg>_proto")` per package, and one authored `rust_prost_toolchain` naming this workspace's own `crate_universe`-resolved `prost`/`tonic` versions (never the module's internal default) plus `proto_compiler` pointed at whatever protoc toolchain the repo already resolves (per the sibling dive's prebuilt-protoc guidance).

**Recommended path and its cost.** `rust_prost_library` on `proto_library` is the recommended path — it is the only Bazel-native, currently-maintained one; `build.rs` + `tonic-build` is what you are migrating away from, not a fallback to keep, and a `cargo_build_script`-wraps-`tonic-build` hybrid buys nothing `rust_prost_library` doesn't already do more natively while still paying the `cargo_build_script` `use_cc_toolchain`/hermeticity costs BZL-RUST-14 already names. The concrete cost: (1) a second BCR module (`rules_rust_prost`) to add and keep in lockstep with `rules_rust`'s own version; (2) authoring one `rust_prost_toolchain` naming this repo's own crate_universe-resolved `prost`/`tonic`/`protoc-gen-prost`/`protoc-gen-tonic` versions — a one-time, non-trivial toolchain-wiring exercise, not a flag flip; (3) converting seven `.proto` files' single build.rs orchestration into one `proto_library` graph with explicit `deps=` per cross-package import (mechanical, but a real diff); (4) an explicit `load()` on every `proto_library` on Bazel 9 (already covered by the sibling dive); (5) unverified whether `rust_prost_transform`'s `prost_opts`/`tonic_opts` fully reproduces the crate's current `extern_path`-flattened module layout without a deeper spike.

**Answer.** At rules_rust 0.74.0, protobuf codegen for Rust has exactly one live Bazel-native path, `rust_prost_library` + `rust_prost_toolchain`, shipped from a separate BCR module `rules_rust_prost` pinned to the same version; there is no `rust_proto_library` to choose between (any reference to one is either historical or a stale doc link). Tonic/gRPC support is native to the same toolchain rule via `tonic_plugin`/`tonic_runtime`, backed by the `protoc-gen-tonic` protoc plugin rather than the `tonic-build` crate creeptd-proto's build.rs currently uses. A working default toolchain does ship and does register automatically, but production use should still author a custom one to avoid a prost/tonic type-identity mismatch against the consuming crate's own dependency graph — the real cost of adoption is that toolchain-authoring step plus reshaping one build.rs into a `proto_library` graph, not a missing capability.

### Q3 — `cargo_build_script`'s `root_path` (#4243)

> `cargo_build_script` `root_path` (PR #4243, merged 2026-08-27; on the public macro wrapper): what it changes about CARGO_MANIFEST_DIR / the sandbox root visible to build.rs, and whether it weakens BZL-RUST-12's guarantee about build scripts not seeing the source tree.

**Findings.**

[#4243](https://github.com/bazelbuild/rules_rust/pull/4243), *"Support `root_path` attribute in `cargo_build_script`"*, merged 2026-08-27 (one day before the 0.74.0 tag), states its own scope in its own description: *"Following [#4142](https://github.com/bazelbuild/rules_rust/pull/4142) which added `root_path` to Rust compilation rules, this change adds it to the `cargo_build_script` macro."* Read via `gh api repos/bazelbuild/rules_rust/pulls/4243/files`, the change touches exactly one file, three additions:

```diff
--- a/cargo/private/cargo_build_script_wrapper.bzl
+++ b/cargo/private/cargo_build_script_wrapper.bzl
@@ def cargo_build_script(
         crate_root = None,
+        root_path = None,
@@ Args:
         crate_root (label): ...
+        root_path (str, optional): The path to the crate root within a directory artifact passed in `srcs`.
@@ rust_binary(
         crate_root = crate_root,
+        root_path = root_path,
```

`root_path` on `cargo_build_script` does exactly one thing: it is forwarded, unchanged, into the internal `rust_binary(name = name + "_", ..., root_path = root_path, ...)` call that **compiles** the build-script binary itself (`cargo/private/cargo_build_script_wrapper.bzl:200-213`). Tracing `root_path` through `rust/private/rust.bzl`, it exists solely to resolve `crate_root` when `srcs` is a single directory (`TreeArtifact`) rather than an explicit file list: `_validate_root_path()` fails the build unless `root_path` is used exactly when `crate_root` is unset and `srcs` is a single-element directory artifact (`rust/private/rust.bzl:212-231`), and the resolved value flows into `rustc`'s `--crate-name`-adjacent path computation via `_get_crate_root_path()` (`rust/private/rustc.bzl:3100-3113`). This is entirely a **compile-time** concern.

`CARGO_MANIFEST_DIR` — the thing BZL-RUST-12 is actually about — is computed in a completely different file, never touched by this PR: `cargo/private/cargo_build_script.bzl`'s `_cargo_build_script_impl` builds a synthetic runfiles directory via `_create_runfiles_dir()` (an `ctx.actions.declare_directory` populated from the compiled script's own runfiles plus the `cargo_build_script_runfiles` target's `data`) and sets `manifest_dir = "{runfiles_dir.path}/{workspace_name}/{package}"`, then `env["CARGO_MANIFEST_DIR"] = manifest_dir` ([`cargo/private/cargo_build_script.bzl:433-464`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/cargo/private/cargo_build_script.bzl#L433-L464)). This is the **execution-time** path — what the compiled build.rs binary actually sees when it runs — and `root_path` never appears anywhere in this file. `gh api`'s file list for #4243 confirms the diff never touches `cargo_build_script.bzl` at all: only `cargo_build_script_wrapper.bzl` (3 lines) plus a new test fixture (`test/root_path/*`).

**Answer.** `root_path` on `cargo_build_script` is a mechanical pass-through of a pre-existing, unrelated `rust_binary` attribute (crate-root resolution inside a directory-typed `srcs`) into the wrapper macro that compiles the build-script binary — it changes nothing about what CARGO_MANIFEST_DIR resolves to, nothing about the sandbox/runfiles root the compiled script sees at execution time, and it does not touch the file (`cargo_build_script.bzl`) that computes either. BZL-RUST-12's guarantee — that `CARGO_MANIFEST_DIR` under `cargo_build_script` is a synthesized, runfiles-backed path that structurally never contains `.git/` — is unaffected by this PR at every version from 0.74.0 onward; no revision to BZL-RUST-12 or -13 is needed.

### Q4 — `rust_doc`/`rust_doc_test` and doc freshness

> `rust_doc` / `rust_doc_test` at 0.74.0: is there a "generated docs are stale" gate analogous to stardoc's `diff_test`, and does `rust_doc` output depend on the Bazel major the way stardoc output does (rules_ocx's goldens match one version only)? Propose the row or state none is warranted.

**Findings.**

*No `diff_test`-equivalent exists anywhere in the ruleset.* `grep -rn "diff_test" --include='*.bzl' .` over the full 0.74.0 tag returns zero hits, in `rustdoc`-adjacent files or anywhere else. Whatever staleness-detection convention a team might want has to be authored from scratch; nothing in `rules_rust` provides or expects one.

*`rust_doc`'s output shape does not resemble stardoc's checked-in-markdown pattern in the first place.* Per its own docs, `rust_doc` produces a **zip archive**: *"Running `bazel build //hello_lib:hello_lib_doc` will build a zip file containing the documentation for the `hello_lib` library crate generated by `rustdoc`"* ([`docs/src/rust_doc.md`](https://bazelbuild.github.io/rules_rust/rust_doc.html), cross-checked against the tagged `rust/rust_doc.bzl` source). The intended consumption pattern the sibling `rustdoc.md` page states is "Output is a directory tree suitable for hosting on a static site" — a build artifact meant to be published, not a file committed to the repo and diffed against source the way `rules_ocx` diffs stardoc-generated markdown against `.bzl` docstrings. The entire "stale checked-in doc" failure mode stardoc golden-tests guard against only arises if a team deliberately commits rendered rustdoc HTML — an unusual, project-specific choice, not the ruleset's own workflow.

*The actual compile action confirms no Bazel-major coupling.* `rustdoc_compile_action()` ([`rust/private/rustdoc.bzl:72-90`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/rust/private/rustdoc.bzl#L72-L90)) builds its `CrateInfo`/`Args` purely from the toolchain's `rustc`/`rustdoc` binaries and the target's own `CrateInfo` — there is no Build-API-shaped input anywhere in the construction. `rustdoc`'s HTML (search index, page layout, embedded metadata) is a pure function of the pinned Rust toolchain version, entirely independent of which Bazel major produced the invocation — the opposite of stardoc, whose *own* output format is coupled to Bazel's Build API and is exactly why `rules_ocx`'s stardoc goldens match only one Bazel version (frame Decision 2). The premise "does `rust_doc` output depend on the Bazel major the way stardoc's does" has a clean, sourced **no**.

**Proposed row: none.** No primary source treats `rust_doc` staleness as a problem the ruleset solves or expects a downstream check for, and the failure mode this dive was asked to find an analogue for (goldens tied to one Bazel version) does not exist for rustdoc's toolchain-driven output. Consistent with the house standard of not inventing a verification that would never change a diff (the same bar `bazel-rust.md`'s Verdict 7 already applied to the Cargo-as-IDE-source-of-truth question), this ships as **no new row**. The one CONSIDER-worthy variant — a team that *does* commit rendered rustdoc HTML to its repo — is a project-specific pattern outside this family's scope to standardize.

**Answer.** No stardoc-`diff_test`-equivalent staleness gate exists for `rust_doc`/`rust_doc_test` in rules_rust 0.74.0, and the analogy to `rules_ocx`'s stardoc-goldens problem does not transfer: `rust_doc`'s output is normally a build artifact for hosting, not a checked-in file compared against source, and its content depends only on the pinned Rust toolchain, never on the Bazel major. No new BZL-RUST row is warranted; propose CONSIDER only for the narrow, project-specific case of a team choosing to commit rendered rustdoc output.

### Q5 — crate_universe against a private registry

> Private registries: crate_universe against a private registry — `.cargo/config.toml` handling (`CARGO_HOME`, `CARGO_BAZEL_ISOLATED=false`), credential flow (cargo's credential providers, netrc), whether Bazel's `--credential_helper` reaches `cargo-bazel` (it runs inside a repository rule, so answer from how `repository_ctx.download` vs `ctx.execute`'d cargo differ), and the documented pattern in rules_rust's docs or issues.

**Findings.**

*Two structurally different network paths exist inside crate_universe, with two different credential universes.*

1. **Lockfile/metadata resolution** (`cargo-bazel splice`/`query`, run once per repin) executes via `repository_ctx.execute()` wrapping a real `cargo` binary: `new_cargo_bazel_fn()`'s inner `_execute()` calls `repository_ctx.execute(args = [cargo_bazel_path] + args + ["--cargo", cargo_path, "--rustc", rustc_path], environment = {"CARGO": ..., "RUSTC": ...} | cargo_environ(...) | env)` ([`crate_universe/private/common_utils.bzl:70-112`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/private/common_utils.bzl#L70-L112)). This is an ordinary subprocess invocation, not a Bazel download of any kind — Bazel's `--credential_helper` mechanism, which hooks Bazel's own downloader, is structurally invisible to it. Credentials for this phase come entirely from Cargo's own resolution: whatever `CARGO_HOME` the subprocess sees (its `.cargo/config.toml` registries, `.cargo/credentials.toml` tokens, or a configured credential provider), plus any `CARGO_REGISTRIES_<NAME>_TOKEN`-shaped environment variables Cargo itself reads.
2. **Per-crate tarball fetch** (`mode = "remote"`, the default `crates_repository`/`crate.from_cargo` shape) is rendered into the generated `@crate_index//` repository as a plain `maybe(http_archive, name = ..., urls = ["{{ attrs.url }}"], sha256 = "{{ attrs.sha256 }}", ...)` ([`crate_universe/src/rendering/templates/partials/module/repo_http.j2`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/src/rendering/templates/partials/module/repo_http.j2)) — an ordinary Bazel-native download indistinguishable, mechanically, from any other `http_archive`. This path **is** covered by Bazel's own downloader stack, including `--credential_helper` and `.netrc`, for whatever host the crate's resolved URL points at. Notably, crate_universe itself exposes **no** `auth`/`auth_patterns`/`netrc` attribute of its own on `crates_repository`/`crate.from_cargo` (unlike the `rust` toolchain extension's `repository_set` tag, which explicitly has all three) — a private registry's tarball host must be authenticated through Bazel's global credential-helper/netrc configuration, not through a crate_universe-specific knob.

*`.cargo/config.toml` handling — `cargo_config`, confirmed on both surfaces.* Both `crates_repository` (`"cargo_config": attr.label(doc = "A Cargo configuration file")`, [`crate_universe/private/crates_repository.bzl:266-268`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/private/crates_repository.bzl#L266-L268)) and bzlmod's `crate.from_cargo` (`"cargo_config": CRATES_VENDOR_ATTRS["cargo_config"]`, [`crate_universe/extensions.bzl:1229`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/extensions.bzl#L1229)) accept it. When `isolated = True` (the default) and `cargo_config` is set, `get_rust_tools()` symlinks the supplied file into the synthetic, per-repository `CARGO_HOME` at `.cargo_home/config.toml` before any cargo subcommand runs ([`crate_universe/private/common_utils.bzl:125-129`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/private/common_utils.bzl#L125-L129)) — this is how a private-registry `[registries.NAME]`/`[source]` block reaches cargo-bazel's exec'd `cargo` while everything else about the host's real `~/.cargo` stays excluded. cargo-bazel's own splicer parses this file directly and understands Cargo's full registry-redirection semantics: `[registry]` (default registry name + token), `[registries.NAME]` (index URL + token), and `[source.NAME]` (`replace-with`, custom `registry` URL) — read verbatim from [`crate_universe/src/splicing/cargo_config.rs:11-90`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/src/splicing/cargo_config.rs#L11-L90), and its own unit tests use a literal Artifactory-shaped fixture (`registry = "https://artmirror.mycompany/artifactory/cargo-mirror.git"`, a named `art-crates-remote` source) to prove `get_registry_index_url_by_name()` resolves it correctly (`cargo_config.rs:220-267`). This is not an inferred capability — it is the exact private-registry shape, tested directly in the ruleset's own repository.

*`CARGO_HOME` / `CARGO_BAZEL_ISOLATED=false` — documented in the ruleset's own prose, not just inferred from code.* `crate_universe/extensions.bzl:69-73` carries a section titled *"Note if using Private Crate Registries"*, verbatim: *"If you are using from_cargo and are pulling dependencies from a private crate registry such as Artifactory, make sure you set the `CARGO_BAZEL_ISOLATED=false bazel build //...` environmental. If not `crates_universe` will not be able to pull from your private registry."* This doc text was added by [#3278](https://github.com/bazelbuild/rules_rust/pull/3278) ("Add note about private crate registries," merged 2025-02-20), itself a follow-up to the `isolated` attribute's introduction. Mechanically: `cargo_environ()` only forces `CARGO_HOME` to the synthetic isolated path when `CARGO_BAZEL_ISOLATED` is unset (defaulting isolated=True) or explicitly truthy; setting it to `false` (case-insensitively `"false"`/others) drops that override entirely, letting the exec'd `cargo` inherit the invoking job's ambient `CARGO_HOME` — with whatever registry credentials, credential-provider configuration, or `.netrc`-driven auth that host environment already has set up ([`crate_universe/private/common_utils.bzl:161-183`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/crate_universe/private/common_utils.bzl#L161-L183)). This confirms BZL-RUST-02's escape hatch is the ruleset's own sanctioned recipe, word for word, not an inferred workaround.

*`crates_vendor`'s credential/SSH forwarding was separately broken by a typo, now fixed.* [#3964](https://github.com/bazelbuild/rules_rust/pull/3964), *"Pass all environment variables to vendoring,"* opened 2026-04-14 by a practitioner reporting: *"I have been struggling for a long time with getting private registries and git repositories to work with vendoring. CARGO_REGISTR* is currently broken due to a typo. Private git repositories don't work because the ssh auth socket is not forwarded."* The bug: the `crates_vendor` shell-wrapper wired a narrow allowlist that tried to forward registry tokens via `env | grep ^CARGO_REGISTER` — a string that never matches any real Cargo variable name (`CARGO_REGISTRY_TOKEN`, `CARGO_REGISTRIES_<NAME>_TOKEN`). Merged 2026-04-16, the fix deletes the allowlist entirely and switches the wrapper's final invocation to `exec env -u OUTPUT_BASE "${_BIN}" ...` — full ambient-environment passthrough, minus exactly one variable (`gh api repos/bazelbuild/rules_rust/pulls/3964/files`, confirmed by direct diff). `grep -n "env -u OUTPUT_BASE" crate_universe/private/crates_vendor.bzl` on the 0.74.0 tag confirms the fix is present, unchanged, at this pin. This is a distinct code path from `crates_repository`'s `repository_ctx.execute()`-based splicing (no shell wrapper, no allowlist, no typo ever existed there) — the bug and its fix are specific to `crates_vendor`'s `bazel run … -- --repin` mechanism.

*Sparse-registry protocol support is old and hardened, not a recent addition.* [#2325](https://github.com/bazelbuild/rules_rust/pull/2325) (merged 2023-12-13) fixed cargo-bazel's splicer misdetecting a `sparse+https://` registry URL as a git-index registry because `cargo_lock::Lockfile` strips the `sparse+` prefix before cargo-bazel sees it — filed against exactly the same private-Artifactory shape. This confirms sparse-index registries (the modern protocol crates.io itself uses, and the one most self-hosted private registries speak) have long-standing, specifically-tested support, independent of the git-index legacy protocol.

**Answer.** crate_universe against a private registry splits cleanly into two credential worlds. Metadata/lockfile resolution runs as a plain `repository_ctx.execute()`-wrapped `cargo` subprocess, so it is entirely governed by Cargo's own credential machinery (`.cargo/config.toml` registries — settable per-repository via the `cargo_config` attribute even while `isolated = True` — plus `CARGO_HOME`, credential providers, and env vars Cargo itself reads); Bazel's `--credential_helper` cannot reach this phase because it is not a Bazel download. The actual per-crate tarball fetch, by contrast, is rendered as an ordinary `http_archive` in the generated repo and genuinely is covered by Bazel's downloader stack (`--credential_helper`, `.netrc`), though crate_universe exposes no `auth`/`netrc` attribute of its own for it. The documented, ruleset-sanctioned recipe for a private registry (named example: Artifactory) is `CARGO_BAZEL_ISOLATED=false`, added to the docs by #3278 and confirmed mechanically in `common_utils.bzl`; a separate, now-fixed bug (#3964, merged 2026-04-16) affected only `crates_vendor`'s SSH/registry-token forwarding via a literal typo, unrelated to `crates_repository`'s path.

## AI-agent angle

1. **Assumes a repo's Rust version is "whatever `rust.toolchain()` defaults to" is a safe, neutral choice.** It is not neutral — it floats on almost every `rules_rust` release, and a repo with no `rust.toolchain()` call at all (but a working `use_extension`/`use_repo`) still silently builds against rules_rust's own default, with zero signal that no version was ever actually chosen. *Check:* does `MODULE.bazel`'s `rust.toolchain(...)` call carry an explicit `versions=`? Absence is the finding, not evidence of "using the sensible default."
2. **Cites the toolchain's `extra_target_triples` default and crate_universe's `SUPPORTED_PLATFORM_TRIPLES` default interchangeably**, because both are described as "the curated default seven triples" in adjacent prose. They are two different lists in two different files with different member sets (one has three wasm triples and no Windows; the other has neither). *Check:* which file/attribute is actually being cited before reusing a "the default covers X" claim from one for the other.
3. **Reads `root_path`'s addition to `cargo_build_script` and assumes it is about the build-script *execution* sandbox** (because "cargo_build_script" and "CARGO_MANIFEST_DIR" are adjacent concepts in most mental models of this ruleset). It is a compile-time crate-root attribute with zero code-path overlap with `CARGO_MANIFEST_DIR`. *Check:* does the PR/diff touch `cargo_build_script.bzl` (execution) or only `cargo_build_script_wrapper.bzl`/`rust.bzl` (compilation)? Only the former could plausibly affect BZL-RUST-12.
4. **Recommends `rust_proto_library` for Rust protobuf**, because that name is dense in general Bazel-protobuf training data (it is the real, current name in several *other* language ecosystems' proto rules, and was rules_rust's own name years ago). At 0.74.0 the only shipping rule is `rust_prost_library`, from a separate `rules_rust_prost` module. *Check:* does the guidance name `rules_rust_prost` as a separate `bazel_dep`, or does it assume `rules_rust` alone is sufficient?
5. **Treats "the toolchain has no default" (from `rust_prost_toolchain`'s own docstring) as literally true** and either skips toolchain setup as unnecessary or invents a from-scratch one, missing that a working default toolchain is auto-registered and the real decision point is *whether to override it* to avoid a version mismatch, not whether one exists at all. *Check:* did the guidance explain *why* a custom toolchain matters (type-identity mismatch against the service crate's own tonic/prost) or just assert "you must define one"?
6. **Assumes `CARGO_BAZEL_ISOLATED=false` is an unusual, dangerous escape hatch invented for this specific migration**, when it is the ruleset's own named, documented recipe for private registries. *Check:* is the private-registry job's `CARGO_BAZEL_ISOLATED=false` usage scoped to that one job (BZL-RUST-02) and cited against the ruleset's own doc section, rather than treated as a novel workaround needing separate justification?
7. **Assumes Bazel's `--credential_helper` is either "the" mechanism for all crate_universe network access or "irrelevant" to all of it.** Neither is true — it covers the generated `http_archive` tarball fetches and is entirely invisible to the exec'd-`cargo` metadata/splice phase. *Check:* which of the two phases is the actual failure point before reaching for `--credential_helper` as the fix.

## Contested / evolving

- Whether `rust_prost_transform`'s `prost_opts`/`tonic_opts` (mapping to prost-build's/tonic-build's own builder flags, e.g. an `extern_path`-equivalent) is sufficient to reproduce creeptd-proto's current flattened-module-tree design (`crate::common` rather than nested `pkg::common::v1`) without a deeper migration spike — this dive confirmed the mechanism exists (`extensions/prost/private/prost_transform.bzl`) but did not run it end to end against real multi-package `.proto` sources.
- Whether `rules_rust_prost`'s shipped default toolchain (`prost` 0.13.1 / `tonic` 0.12.1) will keep tracking `rules_rust`'s own release cadence closely enough that "just override it" stays a one-time cost rather than a recurring version-matching chore — no source states a maintenance commitment either way.
- Whether the `crates_vendor` full-environment-passthrough fix (#3964, `env -u OUTPUT_BASE`) will itself be tightened later (an allowlist done correctly, rather than a full-env fallback) — the PR reads as a pragmatic unblock, not a stated permanent design; no linked follow-up issue exists as of this era.

## Not settled

- Whether `rust_prost_aspect`'s cross-`proto_library`-`deps` resolution actually produces compiling Rust code for a real multi-package graph shaped like creeptd-ng's (`identity`/`lobby`/`game` all importing `common`) without any `rust_prost_transform` intervention — this needs a real spike (a scratch Bazel workspace with `rules_rust_prost` and a handful of the actual `.proto` files), not another source read. Out of scope for this dive per its own tool-use limits (no scratch Bazel execution was budgeted for this question).
- Whether `known_shas.bzl`'s coverage lags fresh Rust releases meaningfully in practice (i.e., how often a freshly-released stable/nightly falls outside the committed hash table and silently loses integrity verification) — this dive confirmed the fallback's existence and logic but did not measure the table's actual currency against `static.rust-lang.org`'s release cadence.
- Whether Bazel's `repository_ctx.execute()` environment semantics (which ambient variables pass through unlisted, versus which require `--repo_env`) are consistent enough across CI systems that a documented `CARGO_REGISTRIES_<NAME>_TOKEN` recipe for `crates_repository` (as opposed to the now-fixed `crates_vendor` path) can be stated as a single, portable instruction — this dive traced the code path but did not test it against a real private-registry CI job.
