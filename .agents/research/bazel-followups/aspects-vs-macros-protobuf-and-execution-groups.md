## Summary

- An aspect adds zero labels to `bazel query //...`; a BUILD-file macro that instantiates *N* rule calls adds exactly *N* new targets per wrapped target — this is definitional (a macro is "a function called from the BUILD file that can instantiate rules" and every rule instantiation is a target), not a measured claim.
- Decision rule for cross-cutting concerns (lint, format, docs-check, codegen-check): **write an aspect** if the output is a report/side-effect attached to existing targets; **write a macro** only if the check must be independently addressable as its own label — invocable alone (`bazel test //foo:lint_test`) or consumed by `deps=` from another rule.
- `rules_lint`'s own stated reason for choosing aspects: "you don't need to add lint wrapper macros, and lint doesn't appear in `bazel query` output" — this is the primary citable source for the whole decision, and it is normative-by-example (a widely-used ruleset's own design rationale), not merely argued.
- Go's `nogo` takes a third path neither aspect nor macro: it runs inside the existing `GoCompilePkg` compile action itself, so it adds zero targets *and* is not a separate `--aspects` invocation — worth naming as a third option when the language's own compile action can absorb the check.
- On Bazel 9 with `--incompatible_autoload_externally` defaulting to the empty string, a bare `proto_library(...)` call with no `load()` fails to resolve (`native.proto_library` does not exist) — official, dated confirmation: "all language-specific rules will now need to be loaded from their respective modules" (Bazel 9.0.0 release notes).
- The BCR module name is **`protobuf`**, not `com_google_protobuf` — but `protobuf`'s own `MODULE.bazel` sets `repo_name = "com_google_protobuf"`, so both `bazel_dep(name = "protobuf")` (Bzlmod graph) and `@com_google_protobuf` (apparent repo name, and the name Bazel's own autoload redirect map hardcodes) are correct, in different contexts.
- Bazel 9's official release notes state the exact floor and the exact flag: "Bazel 9 enforces a minimum dependency on `protobuf` version 33.4 ... Users can set the `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc` flag" — but that flag path is **stale for anything newer than 33.4**: protobuf 34.0 moved the flag to `//bazel/flags:prefer_prebuilt_protoc` (keeping the old path as an `alias`) and flipped its default from `False` to `True` in the same release.
- protobuf's own `bazel_compatibility` field (`>=8.0.0`) first appears at BCR version 35.0, not 33.4 — no published protobuf version declares a 9.0 floor in its own `MODULE.bazel`; the "9.0 floor" is Bazel's own enforced minimum on the *protobuf module version*, a different mechanism from `bazel_compatibility`.
- The one-`proto_library`-plus-per-language-wrapper model is real and independently confirmed in four rulesets' own source: `cc_proto_library.bzl` and `proto_library.bzl` both forward to native or Starlark depending on `hasattr(native, ...)`; protobuf's own `py_proto_library` is implemented as an aspect (`_py_proto_aspect_impl`) over a `deps=` proto_library; `rules_rust`'s `rust_prost_library` takes a single mandatory `proto` attribute of type `attr.label(providers=[ProtoInfo], aspects=[rust_prost_aspect])`; rules_js's new (experimental) JS/TS path drops the wrapper rule entirely — you list the `proto_library` straight in a `js_library`'s `deps`.
- `ts_proto_library` in `rules_ts` (BCR module `aspect_rules_ts`) is **deprecated** as of the pinned 3.10.1: its own docstring says "This API has been replaced by rules_js" and points at `rules_js`'s `js/proto.bzl`, currently marked **EXPERIMENTAL**. Any guidance naming `ts_proto_library` as current for TypeScript is citing a dead API.
- No source — normative or measured — recommends duplicating a `proto_library` per consuming language; the pattern across every ruleset checked is the opposite (one `proto_library`, N language-specific wrapper/aspect attachments), so the row ships SHOULD, not MUST (house standard caps a cross-ecosystem-convergence-but-no-explicit-prohibition claim below MUST).
- Execution groups exist for one genuine reason: a single target whose actions must run on two different execution platforms (the docs' own example: compile on a Linux remote worker, link locally on macOS). Declaring one is cheap syntactically (`exec_group(exec_compatible_with=..., toolchains=...)` in a dict) but each declared group adds its own toolchain-resolution pass at analysis time — no source quantifies this cost, so any threshold rule is CONSIDER.
- Bazel 9 added exactly one new implicit execution group fleet-wide: every Starlark test rule now carries an implicit `test` exec group requiring `@bazel_tools//tools/test:default_test_toolchain_type`, gated by `--@bazel_tools//tools/test:incompatible_use_default_test_toolchain` (default enabled in 9.1.0; absent from the 8.7.0 snapshot). The legacy path is explicitly marked for future removal. This is `BZL-TEST` territory already flagged as an open research item there — no new BZL-ARCH row needed, only a cross-reference.
- `rules_python#2445` (open since 2024-11-26, still open and "more pervasive than originally understood" per the maintainer's 2025-09-17 follow-up) is the concrete, primary-sourced instance of the exec-group-scoping failure mode: two `py_test` targets sharing one `.py` source file, one setting a bare `exec_properties` key and one not, produce a genuine action-identity conflict because the bare key is applied to *every* exec group including the shared `py_precompile` one. The maintainer's own documented workaround is exactly the reviewer check the commission asked for: **scope the key to its exec group** (`py_precompile.foo`, not `foo`) whenever the key is meant to affect one action, not the whole target.
- Every version-specific claim above is anchored to a tagged snapshot or an official, dated release note — no rolling `bazel.build` prose page or ruleset `main` branch is cited as the sole source for any MUST-worthy claim.

## Answers

### 1. Aspects vs BUILD-file macros for a cross-cutting concern (M-G-13)

> Aspects versus BUILD-file macros for a cross-cutting concern (lint, format, docs, codegen checks): what a BUILD-file wrapper macro adds to `bazel query //...` output (extra targets per wrapped target — count for a 3-rule macro), to analysis time, and to `bazel test //...`; what an aspect adds instead (output groups, `--aspects` flag, `--output_groups`, no new targets); when a macro is still right (needs a new target: a test that must run in `bazel test //...`). Produce the decision rule and its query-based verification.

**Findings.**

A macro, symbolic or legacy, is Bazel's own definition: "A macro is a function called from the `BUILD` file that can instantiate rules" [bazel.build/extending/macros](https://bazel.build/extending/macros). Every rule instantiation is a target. So the target-count arithmetic is definitional, not measured: a macro that internally calls three rule constructors (say, a `lint_test`, a `format_test`, and a `docs_check` rule, wrapping one `py_library`) adds **exactly 3 new labels** per wrapped target to whatever `bazel query //...` (or any pattern covering that package) returns, because `//...` is the "everything under this root" pattern and rule instantiation is exactly what a target *is*. For symbolic macros specifically, those new targets are also required to be name-prefixed (`name_` by convention) — [bazel.build/extending/macros](https://bazel.build/extending/macros): "The names of any targets or submacros created by a symbolic macro must either match the macro's `name` parameter or must be prefixed by `name` followed by `_`". If any of the 3 new targets is a `_test` rule, it is now also in the closure of `bazel test //...` and runs — and is billed — on every invocation of that command, whether or not anyone asked for the lint result that run.

An aspect, in contrast, attaches to an *existing* target without creating a new label. Its mechanism: "An aspect has an implementation and a list of all attributes it propagates along ... This aspect can be applied to a target X, yielding an aspect application node A(X)" [bazel.build/extending/aspects](https://bazel.build/extending/aspects) — propagation follows a shadow graph over the attributes named (typically `deps`), and `OutputGroupInfo` from the same page is explicitly the one provider type Bazel allows both a rule and an aspect applied to it to return simultaneously, "so long as the rule and aspect specify different output groups." Requesting the aspect's output is `--aspects=<bzl-file-label>%<aspect_name>` — the doc's own example: `bazel build //MyExample:example --aspects print.bzl%print_aspect` [bazel.build/extending/aspects](https://bazel.build/extending/aspects) — and the produced output group is fetched with `--output_groups`: `bazel build //pkg:mytarget --output_groups=debug_files` [bazel.build/extending/rules § Output Groups](https://bazel.build/extending/rules). Neither call adds a label; `bazel query //...` is identical before and after the aspect is registered, because the aspect is not a target, it is a computation attached at analysis time to the target graph that already exists.

`rules_lint` states this exact tradeoff as its own design rationale, in its own words: "you don't need to add lint wrapper macros, and lint doesn't appear in `bazel query` output" [aspect-build/rules_lint README](https://raw.githubusercontent.com/aspect-build/rules_lint/main/README.md). The invocation form it documents is `common:lint --aspects=//tools/lint:linters.bzl%linter1[,...]` in a `.bazelrc`, wired to `bazel build --config=lint //...` [aspect.build/blog/lint](https://aspect.build/blog/lint). The 1.0 "Bazel Linting Now Generally Available" post frames the whole feature as the ability to lint "existing `*_library` targets" — no wrapper needed at all.

A third option exists that the commission's framing (aspect-vs-macro) does not name: fold the check into the *existing* compile action rather than attaching a second one. Go's `nogo` does exactly this — it is neither an aspect nor a macro. Per its own docs, "The `nogo` rule will generate a program that executes all the supplied analyzers at build-time. The generated `nogo` program will run alongside the compiler when building any Go target," running "as part of the `GoCompilePkg` action" [bazelbuild/rules_go go/nogo.rst](https://github.com/bazel-contrib/rules_go/blob/master/go/nogo.rst). No new target, no `--aspects` flag, no separate action — the check is inlined into the compile step itself and can be disabled per-invocation with `--norun_validations`. This is the cheapest of the three when the language toolchain's own compile action is the thing being extended (available to a rule author, not to a downstream *consumer* of an existing ruleset — a consumer writing a lint check over someone else's `py_library` cannot reach inside `PyInfo`'s compile action the way `rules_go` reaches inside its own).

**Decision rule.** Use an aspect (or, if you author the underlying rule, fold the check into the existing compile action) whenever the check's output is a report or a pass/fail signal attached to a target that already exists — lint, format-check, docs-freshness, most codegen-consistency checks. Use a macro only when the check must be independently addressable: a target other code needs to `deps=` on, or a test result that must show up as its own row in `bazel test //...`'s output (CI systems that gate on named test targets, not on an aspect's output group, need this). The two are not mutually exclusive with generation: a Gazelle-generated `_test` target is a macro-shaped choice made once by the generator, not per-check.

**Verification.** Before/after target-count diff for the macro path: `diff <(bazel query //path/to/pkg:* 2>/dev/null) <(bazel query //path/to/pkg:* 2>/dev/null)` run before and after adding the wrapper macro to one `BUILD` file — the diff's line count is the exact target-count cost, and it is never zero for a macro that instantiates ≥1 rule. For the aspect path, the same query run before and after registering the aspect via `.bazelrc`'s `--aspects` line must be **empty** — any non-empty diff means what was added was a macro wearing an aspect's name. **Empty diff after enabling an aspect = pass (no query pollution); any diff = the "aspect" is secretly adding targets and the claim is false.**

**Answer.** As of `rules_lint`'s current (2026-era) design and Bazel's own aspects/macros documentation, a macro that instantiates *N* rules adds exactly *N* new labels to `bazel query //...` per wrapped target — for a 3-rule macro, +3 targets, and if any are test rules they also join `bazel test //...`'s closure and consume executor time on every run. An aspect adds none: it is requested with `--aspects=<label>%<name>` and its result is pulled with `--output_groups=<name>`, with zero effect on query output, established both by Bazel's own aspects/rules documentation and by `rules_lint`'s own stated design rationale for choosing this mechanism over macros. The decision rule is: aspect for attached-report checks, macro (or a rule the generator emits) only when the check needs its own addressable label.

### 2. Protobuf modelling under Bzlmod on Bazel 9 (M-G-12)

> With `--incompatible_autoload_externally` empty by default, what happens to a bare `proto_library`, and what is the correct `load()` from `@protobuf` (or `@com_google_protobuf` — verify the module name on the BCR and the 9.0 floor of protobuf >= 33.4 with `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc`. The one-`proto_library`-plus-per-language-wrappers model: how `py_proto_library`, `rust_prost`/`rust_proto`, `ts_proto_library` (aspect_rules_ts) and `cc_proto_library` attach; is there any measured reason to duplicate per language. Fetch the protobuf repo's `bazel/` docs.

**Findings.**

*Autoload and the bare `proto_library`.* `--incompatible_autoload_externally` is a hardcoded redirect table: "Bazel maintains a hardcoded list of all symbols that may be autoloaded" [BuildLanguageOptions.java, Bazel 9.2.0](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/packages/semantics/BuildLanguageOptions.java#L105-L142). The redirect map itself, read directly from source, contains `.put("proto_library", ruleRedirect("@com_google_protobuf//bazel:proto_library.bzl"))` [AutoloadSymbols.java, Bazel 9.2.0, line ~835](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/packages/AutoloadSymbols.java) — but the flag's *default value* is the empty string, per Bazel's own 9.0.0 release notes, in plain English: "The flag `--incompatible_autoload_externally` now defaults to the empty string ... meaning that all language-specific rules will now need to be loaded from their respective modules (`rules_cc`, `rules_java`, etc). This marks the conclusion of the Starlarkification effort" [bazelbuild/bazel release 9.0.0](https://github.com/bazelbuild/bazel/releases/tag/9.0.0). An empty default means the redirect table exists but nothing in it fires automatically — `native.proto_library` does not exist on a stock Bazel 9 invocation, so a bare `proto_library(name=..., srcs=...)` call with no `load()` fails name resolution (`name 'proto_library' is not defined`), the same failure mode as any other undefined Starlark symbol. This is independently confirmed by protobuf's own wrapper macro, which is written specifically to handle both worlds: `if not hasattr(native, "proto_library"): _proto_library(**kwattrs) else: native.proto_library(**kwattrs)` [protobuf `bazel/proto_library.bzl`, tag v33.4](https://github.com/protocolbuffers/protobuf/blob/v33.4/bazel/proto_library.bzl) — the existence of this branch is itself proof that `native.proto_library` can and does disappear.

*The correct `load()`, and the module-name/repo-name split.* `load("@protobuf//bazel:proto_library.bzl", "proto_library")` is correct under Bzlmod. The BCR module is named **`protobuf`** — confirmed directly from its own `MODULE.bazel`: `module(name = "protobuf", version = "33.4", ..., repo_name = "com_google_protobuf")` [bazel-central-registry, modules/protobuf/33.4/MODULE.bazel](https://github.com/bazelbuild/bazel-central-registry/blob/main/modules/protobuf/33.4/MODULE.bazel) — but that same declaration sets `repo_name = "com_google_protobuf"`, meaning the module's *apparent repository name* inside any consuming module's namespace is `@com_google_protobuf`, not `@protobuf`, unless the consumer explicitly re-maps it. Both forms are therefore "correct," in different roles: `bazel_dep(name = "protobuf", version = "...")` is how you declare the dependency in `MODULE.bazel`; `@com_google_protobuf//...` (or `@protobuf//...` if you don't rely on the default `repo_name`) is how you `load()` from it, and Bazel's own hardcoded autoload table uses `@com_google_protobuf` throughout because that is the name protobuf's own module declares. The commission's `@protobuf//bazel/toolchains:...` framing is a legal label too (nothing stops a consumer relying on the bare module name as its own repo mapping instead of the `repo_name` override) — either spelling resolves to the same repository, and an artifact should not present one as *the* only correct form.

*The 33.4 floor, precisely.* Bazel's own 9.0.0 release notes state the exact number and the exact flag it was originally shipped under: "Bazel 9 enforces a minimum dependency on `protobuf` version 33.4, which includes support for a prebuilt protobuf compiler. Users can set the `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc` flag to avoid having to build `protoc`" [bazelbuild/bazel release 9.0.0](https://github.com/bazelbuild/bazel/releases/tag/9.0.0). This is a Bazel-side enforced minimum on the *protobuf module version resolved into the graph* — a different mechanism from protobuf's own `bazel_compatibility` field, which is a Bzlmod compatibility floor protobuf declares about *itself*. Read directly from the BCR, `bazel_compatibility = [">=8.0.0"]` first appears at protobuf **35.0** (absent at 33.4 and 34.x) and protobuf's `main` branch, at `37.0-dev`, still declares only `>=8.0.0`, never `>=9.0.0` [bazel-central-registry, modules/protobuf/{33.4,34.0,34.1,35.0,35.1,36.0,36.1}/MODULE.bazel, read directly]. No published protobuf version, as of this era, declares a 9.0-specific floor in its own manifest — the "9.0 floor" in the commission's framing is Bazel's enforced minimum-version check on the module graph, not protobuf's self-declared compatibility range; conflating the two would misattribute the mechanism in shipped guidance.

*`prefer_prebuilt_protoc` moved, and its default flipped, one release after the Bazel-9 floor.* Reading the flag directly from protobuf's own source at the exact pinned version: at **v33.4**, `//bazel/toolchains:prefer_prebuilt_protoc` is a real `bool_flag`, `build_setting_default = False`, with the comment "TODO: this should be True after the feature is vetted with some adoption" [protobuf `bazel/toolchains/BUILD`, tag v33.4](https://github.com/protocolbuffers/protobuf/blob/v33.4/bazel/toolchains/BUILD#L46-L51). At **v34.0**, the flag moved to a new package: `//bazel/toolchains:prefer_prebuilt_protoc` is now an `alias(actual = "//bazel/flags:prefer_prebuilt_protoc")` — the old label still resolves, but the canonical location is `//bazel/flags:prefer_prebuilt_protoc` [protobuf `bazel/toolchains/BUILD`, tag v34.0]. By **v36.1** (the newest tagged BCR release at this era), that flag's own definition has flipped: `build_setting_default = True`, with a comment pointing at [protocolbuffers/protobuf#25561](https://github.com/protocolbuffers/protobuf/issues/25561) [protobuf `bazel/flags/BUILD`, tag v36.1]. Protobuf's own announcement corroborates the timeline directly: "protobuf 33.4 offers an option to skip re-compiling Protobuf tools and runtimes and use a pre-built protoc binary, available to Bazel 7 and later. ... In the breaking v34 release, protobuf will change the default of `--@protobuf//bazel/flags:prefer_prebuilt_protoc` to true" [protobuf.dev/news/2026-01-16](https://protobuf.dev/news/2026-01-16/) — that same announcement also names the *other* required flag for the modern prebuilt-protoc path, `--incompatible_enable_proto_toolchain_resolution`, and states it "becomes default starting with Bazel 9," which Bazel's own release notes confirm as one of the incompatible flags flipped at 9.0.0 ([bazelbuild/bazel#28182](https://github.com/bazelbuild/bazel/pull/28182)). **Net effect for anything pinned to protobuf newer than 33.4 (which, per the BCR's version list, is almost every real install today — 34.0 through 36.1 are all published): the flag path in the commission's own framing is the pre-34.0 spelling, opt-in with a default of `False`; the current spelling is `//bazel/flags:prefer_prebuilt_protoc`, and its default is `True`.**

*The one-`proto_library`-plus-wrappers model, verified per language.*

- **C++**: `cc_proto_library.bzl` is the same forwarding-macro pattern as `proto_library.bzl` — `if not hasattr(native, "cc_proto_library"): _cc_proto_library(**kwattrs) else: native.cc_proto_library(**kwattrs)` [protobuf `bazel/cc_proto_library.bzl`, v33.4](https://github.com/protocolbuffers/protobuf/blob/v33.4/bazel/cc_proto_library.bzl). Correct load: `load("@protobuf//bazel:cc_proto_library.bzl", "cc_proto_library")`.
- **Python**: protobuf ships its *own* `py_proto_library`, implemented as an aspect over the `proto_library`'s deps — not a `rules_python` rule. Its own docstring: "The implementation of the `py_proto_library` rule and its aspect," with the working function named `_py_proto_aspect_impl`, which "Generates and compiles Python code for a proto_library" [protobuf `bazel/py_proto_library.bzl`, v33.4](https://github.com/protocolbuffers/protobuf/blob/v33.4/bazel/py_proto_library.bzl#L1-L38). Correct load: `load("@protobuf//bazel:py_proto_library.bzl", "py_proto_library")`.
- **Rust**: `rules_rust` ships `rust_prost_library`, whose sole proto-facing attribute is exactly what the model predicts — `"proto": attr.label(doc = "A proto_library target for which to generate Rust gencode.", providers = [ProtoInfo], aspects = [rust_prost_aspect], mandatory = True)` [bazelbuild/rules_rust `extensions/prost/private/prost.bzl`, tag 0.74.0, line 429](https://github.com/bazelbuild/rules_rust/blob/0.74.0/extensions/prost/private/prost.bzl#L429-L444). Correct load: `load("@rules_rust//proto/prost:defs.bzl", "rust_prost_library")`. At this pinned version, `rules_rust`'s `extensions/` directory contains exactly `bindgen, mdbook, prost, pyo3, wasm_bindgen` [confirmed by directory listing at tag 0.74.0] — there is **no** separate legacy `rust_proto_library`/`rust_grpc_library` extension shipping alongside it; `rust_prost_library` is the only Bazel-side protobuf path in current `rules_rust`, so "rust_prost / rust_proto" in the commission's framing names one live rule, not a choice between two.
- **TypeScript/JavaScript — the one genuinely moving target.** `ts_proto_library`, shipped in `rules_ts` (BCR module `aspect_rules_ts`, matching the frame's "rules_ts 3.10.1"), is **deprecated at the pinned version**. Its own docstring, read directly from source: "**This API has been replaced** by rules_js: https://github.com/aspect-build/rules_js/blob/main/js/proto.bzl. See updated documentation at https://docs.aspect.build/bazel/javascript/aspect_rules_js/js_proto" [aspect-build/rules_ts `ts/proto.bzl`, tag v3.10.1](https://github.com/aspect-build/rules_ts/blob/v3.10.1/ts/proto.bzl#L1-L20). The replacement, in `rules_js`'s own `js/proto.bzl`, is marked **EXPERIMENTAL** — "This API is subject to breaking changes outside our usual semver policy. In a future release of rules_js this should become stable" — and drops the wrapper-rule idea entirely: "Just write `proto_library` targets as usual, or have Gazelle generate them. Then reference them anywhere a `js_library` could appear," with a `js_proto_toolchain` (not a `js_proto_library`) doing the codegen work behind the scenes, triggered by the plain `deps = [":your_proto_library"]` on an ordinary `js_library` [aspect-build/rules_js `js/proto.bzl`, `main`](https://github.com/aspect-build/rules_js/blob/main/js/proto.bzl). This is the strongest form of the one-`proto_library` model of all four languages — no wrapper rule at all, just a `deps=` reference the toolchain machinery reads — but it ships as EXPERIMENTAL, so any shipped guidance must name that status rather than presenting it as stable.

No source found — normative, measured, or even strongly argued — recommends duplicating a `.proto` file's `proto_library` per consuming language. Every one of the four rulesets checked converges on the opposite: exactly one `proto_library`, N language-specific attachments (a forwarding macro for C++, protobuf's own aspect for Python, an `attr.label(aspects=[...])` for Rust, a plain `deps=` reference for the experimental JS path).

**Answer.** On Bazel 9.2.0 with the default (empty) `--incompatible_autoload_externally`, a bare, unloaded `proto_library` call fails outright — `native.proto_library` does not exist, confirmed both by Bazel's own 9.0.0 release notes and by protobuf's own defensive `hasattr()` branch in its wrapper macros. The correct, Bzlmod-native load is `load("@protobuf//bazel:proto_library.bzl", "proto_library")` (BCR module name `protobuf`, apparent repo name `com_google_protobuf` per protobuf's own `repo_name=` override — both spellings resolve). Bazel 9 enforces a minimum protobuf module version of 33.4, per its own 9.0.0 release notes, but that floor is a graph-resolution minimum, not the version's own declared `bazel_compatibility` (which is `>=8.0.0`, first appearing at 35.0). The `prefer_prebuilt_protoc` flag exists at 33.4 (default `False`, path `//bazel/toolchains:...`) but moved to `//bazel/flags:prefer_prebuilt_protoc` and flipped to default `True` at 34.0 — any guidance should cite the current path with the old one noted as a still-working alias. The one-`proto_library`-plus-per-language-wrapper model is confirmed in production source for C++, Python and Rust, and is the explicit design of JS/TS's new (experimental) replacement for the now-deprecated `ts_proto_library`; no source recommends duplicating the `proto_library` per language.

### 3. Execution groups (M-G-11)

> When does a target genuinely need actions on two execution platforms (`exec_group`, `exec_properties` per group, the implicit test exec group Bazel 9 added), what the boilerplate costs, and how a reviewer checks that `exec_properties` keys are scoped to their group (rules_python #2445's workaround is one instance). Propose CONSIDER rows only unless a normative source makes one MUST.

**Findings.**

*The genuine need.* Bazel's own definition: "Each execution group has its own toolchain dependencies and performs its own toolchain resolution" [bazel.build/extending/exec-groups](https://bazel.build/extending/exec-groups). The doc's own motivating example is exactly the cross-platform case the commission names: a target compiles on one platform and links on another — e.g. compiling on a Linux remote worker while linking locally on macOS — expressed by giving the `link` exec group its own `exec_compatible_with` distinct from the target's default execution platform. Outside genuine multi-platform action graphs (cross-compilation toolchains, a build step that must run on a specific OS a downstream link step does not need), a single target has no reason to declare more than the implicit default exec group.

*The boilerplate.* Declaring one is a dict entry, not a new file or a new rule: `exec_groups = {"link": exec_group(exec_compatible_with = ["@platforms//os:linux"], toolchains = ["//foo:toolchain_type"])}` on the rule definition [bazel.build/extending/exec-groups]. Overriding a property for one group from a target uses a hyphenated/dotted key, e.g. `exec_properties = {"link.mem": "16g"}` layered over a target-level default of `{"mem": "12g"}` — the syntax cost is genuinely small. The cost that is *not* small and that no source quantifies is the analysis-time one implied by the group's own definition: an extra declared exec group is an extra, independent toolchain-resolution pass. No primary source publishes a number for this, which is exactly why this family ships as CONSIDER per the commission's own instruction.

*The implicit Bazel-9 test exec group.* This is already established, primary-sourced, inside this program's own `BZL-TEST` consolidation and should not be re-derived here — only cross-referenced. Diffing the pinned 8.7.0 and 9.1.0 test-encyclopedia snapshots byte-for-byte, "the only substantive addition is a new 'Execution platform' section — an implicit `test` exec group on `@bazel_tools//tools/test:default_test_toolchain_type`, with the legacy path already marked for removal" [`.agents/research/bazel-testing.md:32-37`](../bazel-testing.md), sourced from the dive itself: "every test rule now has an implicit `test` exec group defaulting to a mandatory toolchain requirement on `@bazel_tools//tools/test:default_test_toolchain_type`, gated by `--@bazel_tools//tools/test:incompatible_use_default_test_toolchain` (default enabled) — the legacy `legacy_test_toolchain` path ... is explicitly flagged as due for removal" [`.agents/research/bazel-testing/test-contract-sizing-and-flakiness.md:238-240`](../bazel-testing/test-contract-sizing-and-flakiness.md). This answers the commission's sub-question directly and needs no further primary research; the open item the `BZL-TEST` consolidation already names for a future round is what breaks when the legacy path is actually removed, which this dive did not test either.

*The reviewer check for `exec_properties` scoping — `rules_python#2445` in full.* This issue is the concrete instance the commission asked to use, read directly from GitHub, primary and current: two `py_test` targets share one `.py` source file; one sets `exec_properties = {"foo": "bar"}`, the other uses the rule's defaults; both produce the identically-named precompiled output (`__pycache__/foo.cpython-311.pyc`) because the generated filename is keyed on the *source file*, not the target — and Bazel refuses the build with an action-conflict error, because the two actions differ only in `exec_properties` and are otherwise indistinguishable to the action cache [bazelbuild/rules_python#2445](https://github.com/bazelbuild/rules_python/issues/2445), filed 2024-11-26, **status: open**, confirmed via `gh api` (`"state":"open"`, 2 comments, most recent 2025-09-17). The maintainer's own diagnosis, quoted directly: "the exec_props were being set to affect specific actions and affecting *every* action was unnecessary. ... I updated a few hundred targets to have them use the exec-group for exec properties instead of using general keys, e.g. using the key `cpp_link.mem` instead of simply `mem`." The precompile-specific instance: "The basic thing we have to do is ensure that the `py_precompile` exec group is always getting the same exec properties. Ideally, both targets are set to 'use the defaults for the py_precompile exec group' ... However, having both set the same `py_precompile.XXX` keys/values is also acceptable. The important thing is both targets have the same values for the `py_precompile` exec group." The maintainer also states plainly why the *rule* can't fix this on its own: exec properties set on a target take precedence over anything the rule sets internally (working as intended — that precedence is the whole point of a target-level override), there is no way to "reset" a key to "unset" once given, and the accepted key/value space is unbounded, so the rule cannot supply a safe universal default. The 2025-09-17 follow-up widens the blast radius: the same failure shows up whenever "the same test gets run for different ML accelerator backends" via `args=`/`tags=` variants of one `.py` file, and the maintainer's only proposed (not yet implemented) fix is a loading-phase split of `srcs` into a separate, `exec_properties`-free precompile target. **No fix has landed as of this era.**

This is directly generalizable into the reviewer check the commission asked for: whenever two targets in the same package can produce the same derived output from the same source file (the fingerprint is a shared `srcs` entry feeding an implicit, rule-generated action), any `exec_properties` difference between them must be either absent from both or scoped with the owning exec group's name as a dotted prefix — never a bare key that silently spans every exec group on the target, including one both targets share implicitly.

**Answer.** An `exec_group` earns its place only when a target's own actions genuinely need two different execution platforms — Bazel's own docs name cross-compilation (compile remote, link local) as the canonical case; nothing in the current era's sources argues for exec groups as a general-purpose organizing tool below that bar. The boilerplate is syntactically minimal (a dict literal) but each group is its own toolchain-resolution unit at analysis time, a cost no source quantifies. Bazel 9 added exactly one fleet-relevant implicit exec group — the `test` group behind `--@bazel_tools//tools/test:incompatible_use_default_test_toolchain` — already covered by this program's `BZL-TEST` family. The reviewer check for `exec_properties` scoping is concretely demonstrated, not merely argued, by `rules_python#2445`: a bare (unscoped) `exec_properties` key differing across two targets that share a derived output is the failure signature, and the fix is a dotted, group-scoped key (`<exec_group>.<key>`) — a live, still-open (as of 2026-09-05) upstream defect, so any shipped rule states it as a documented workaround for a known-unfixed class of conflict, not as a solved problem.

## AI-agent angle

1. **Reaches for a BUILD-file macro to add a lint/format check "because that's what a `_test` target is for."** A model trained on years of macro-heavy examples defaults to macros for anything test-shaped, without weighing the query-pollution and `bazel test //...` cost. *Check:* NEW-2's before/after query diff — a nonzero diff for a check whose output is only ever consumed as a report is the finding.
2. **Writes a bare `proto_library(...)` with no `load()`**, because that was correct for years under WORKSPACE and under Bazel's pre-9 default autoload. *Check:* on the target Bazel major, does the file `load()` the rule from `@protobuf` (or `@com_google_protobuf`), or does it rely on `native`/no-load at all? The latter is a Bazel-9 breakage waiting to happen even if it still works on 8.x.
3. **Cites `ts_proto_library` for TypeScript protobuf support.** It is the single most likely stale-API citation in this family: current training data is dense with it, and its own upstream docstring already disowns it. *Check:* does the guidance name `rules_js`'s `js/proto.bzl` (and flag it EXPERIMENTAL), or does it point at `ts_proto_library`?
4. **Recommends `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc`** as the current flag without naming a protobuf version — right for exactly one version (33.4) and stale for every version after it. *Check:* does the guidance name the protobuf version alongside the flag path?
5. **Treats `exec_properties = {"foo": "bar"}` as safe on a `py_test`/`cc_test`** without checking whether a sibling target shares the same `srcs` file. This is the exact, currently-open `rules_python#2445` failure. *Check:* does a reviewer comment ask "does any other target in this package share this `srcs` file with a different `exec_properties`?" before approving an unscoped key.
6. **Assumes `nogo`-style compiler-integrated checks generalize to any language.** Only viable when you author the compile action itself (a ruleset maintainer), not when consuming someone else's rule as a downstream user — a model should not propose "just put it in the compile action" to someone who only has BUILD-file-level access to a third-party ruleset.

## Contested / evolving

- Whether `js_proto_toolchain`'s no-wrapper-rule pattern (plain `deps=` on `js_library`) is the eventual stable JS/TS shape or a transitional EXPERIMENTAL design that gets a proper `js_proto_library` rule later — the docstring explicitly says "In a future release of rules_js this should become stable," with no committed target shape.
- Whether `protobuf`'s v34 default flip on `prefer_prebuilt_protoc` (to `True`) is itself stable across the whole BCR-published range, or whether a later regression walks it back the way `--repo_contents_cache` was walked back between 8.3.0 and 8.4.0 (a pattern this program has already seen once, per `bazel-frame.md`'s wave-2 correction 3) — no source states a stability guarantee beyond "breaking v34 release."
- Whether `rules_python#2445`'s maintainer-floated fix (loading-phase split of `srcs` into a separate, `exec_properties`-free precompile target) will land, and on what timeline — the 2025-09-17 comment is still describing it as an idea, not a PR.

## Not settled

- What does `bazel query 'kind(rule, //...)' | wc -l`'s delta actually look like on a *real, adopted* codebase before/after wiring an aspect-based lint into CI (vs. this dive's definitional argument)? No fleet repository runs `rules_lint` today, so NEW-2's verification is untested against a live target graph.
- Does protobuf's `//bazel/flags:prefer_prebuilt_protoc` default-`True` change interact badly with `rules_ocx`'s CC-toolchain posture (zero `cc_*` targets today, but the family's own cpp guide is written for future adopters) — would a prebuilt-protoc default silently swap in a precompiled binary a hermeticity-focused reviewer would want surfaced? Nothing in this dive tested a real build.
- Whether any ruleset besides `rules_go`'s `nogo` folds a lint/analysis check into the compile action itself rather than using an aspect — this dive found exactly one instance and did not survey Rust's `clippy`-via-`rules_rust` or Python's analogous mechanisms for the same pattern.
