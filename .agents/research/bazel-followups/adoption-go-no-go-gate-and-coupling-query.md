## Summary

- The 383-project study (arXiv:2405.00796, Zheng/Adams/Hassan) is real and its number checks out verbatim: **"31.23% of Bazel projects adopt a CI service but do not use Bazel in the CI service"** — the denominator is Bazel projects *with a CI service configured*, not all 383. A sibling number in the same abstract, **27.76%**, is projects that do invoke Bazel in CI but lean on Shell/Make/Docker wrappers to do it.
- The ~11% year-two abandonment figure traces to a named, dated talk — Shane McIntosh (Waterloo), *"The Classics Never Go Out of Style: An Empirical Study of Downgrades from Bazel,"* BazelCon 2024 — not a located peer-reviewed paper. Its own reported base rate matters as much as the abandonment rate: only **1.5% of ~35,000 GitHub projects surveyed ever adopted Bazel** in the first place.
- RabbitMQ's PR #13514 (merged 2025-03-14) removed Bazel calling it "a great tool" that "provided a much needed capability of caching and build optimisation" — an explicit non-defect departure, in favor of Make/erlang.mk.
- No source — not the 383-project study, not RabbitMQ, not Aspect's or EngFlow's own blogs — gives a single numeric go/no-go threshold (repo count, language count, target count) for "should this repo adopt Bazel." Aspect's closest data point is qualitative: a "large Aspect customer" at 2M SLOC / 500 engineers still runs whole-repo shared-green, and Aspect frames the predictive-tooling need as arising only near Google's 2015 scale (2B SLOC, 50k engineers) — 100-1000x larger.
- Target-count threshold for target selection over whole-repo green: **no source states one.** Canva's own graph is >10^5 nodes with ~3,000 P90 CI jobs before they built a custom `bazel-diff`-based selector; Tinder's bazel-diff README says only "tested with projects containing tens of thousands of targets"; target-determinator's README gives no scale claim at all. Frame decision 3 ("selection becomes the default above the target count the wave-3 CI dive names") has no wave-3 number to inherit yet — the CI dive is still in flight.
- M-K-15 (partial JS Bazelification cache benefit) stays contested: pow.rs's "0 to 100%" cliff is confirmed **argued, not measured** — a hypothetical dependency-chain example, no numbers, no cited project. No measured counter-account exists either; the "staged migration" counterweight the dive mentions is a different mechanism (Tweag's Cargo-stays-authoritative pattern) applied to Rust, not evidence about JS cache economics.
- `bazel mod graph --extension_info`, `bazel mod show_repo`, and `bazel mod explain` all verified present on both the 8.7.0 and 9.1.0 (9.2.0 has no archived versioned doc snapshot) command pages, with identical descriptions — the coupling query is stable across the fleet's pinned major and the Active LTS.
- Applied to the fleet: **the coupling is invisible today because none of the three repos are Bzlmod modules yet.** `git_override` cannot make `rust-oci-client`/`docker_credential` visible in `bazel mod graph` until those forked submodules themselves gain a `MODULE.bazel` — BZL-ARCH-28 already states this precondition ("requires the vendored fork to itself declare a MODULE.bazel") and it is the actual blocker, not a missing query.
- The narrower-fix-first ladder (M-G-23) has fleet-shape-specific cheaper fixes (cargo build cache/nextest for Rust, uv's own resolver+cache for Python, pnpm's content-addressable store plus Nx/Turborepo for TS) but **no source in the corpus states a measured point at which any of them stops being enough** — every "when it breaks" account in the corpus (Uber, Canva) is a story about scale nobody in this fleet is at, never a stated threshold.
- Comparison-post consensus (aviator.co/sourcegraph.com/daily.dev cluster, already in `bazel-topic-map`) is unusually blunt for a JS-only shape: Nx/Turborepo is "capped below Bazel's ceiling but sufficient for most JS/TS-only teams" — i.e., per that consensus a JS-only repo like `setup-ocx` or `kate-middlechild` is not expected to outgrow it at all, not "outgrows it above N packages."
- Consequence for `bazel-adopt`: the opening gate cannot be a numeric threshold table — every input the map wanted (repo count, language count, target count, CI-minutes) has zero sourced cutoffs. It has to be a checklist of measured yes/no questions (does CI already run Bazel where adopted; is the dominant pain build time or something else; was a narrower fix tried) with named sources for *why* the question matters, not a number gate.

## Answers

### Q1 — Build the runnable go/no-go gate {#q1}

**Question (commission Q1):** Fetch the 383-project study the map cites, verify the number and its method; the ~11 percent year-two abandonment source; Aspect's and EngFlow's "should you adopt Bazel" writing; the RabbitMQ removal PR and its stated reasons; two or three "we adopted Bazel and stayed" accounts with team size and language count. State the measurable inputs and the thresholds each source supports, or say none exists.

**Findings.**

*The 383-project study, verified.* [arXiv:2405.00796](https://arxiv.org/abs/2405.00796), "Does Using Bazel Help Speed Up Continuous Integration Builds?" (Zheng, Adams, Hassan; submitted 2024-05-01). Method, quoted from the abstract: "we collected 383 Bazel projects from GitHub, then studied their parallel and incremental build usage of Bazel in 4 popular CI services... We conducted 3,500 experiments on 383 Bazel projects and analyzed the build logs of a subset of 70 buildable projects... Additionally, we performed 102,232 experiments on the 70 buildable projects' last 100 commits." The exact sentence: **"31.23% of Bazel projects adopt a CI service but do not use Bazel in the CI service, while for those who do use Bazel in CI, 27.76% of them use other tools to facilitate Bazel's execution."** The denominator for 31.23% is Bazel projects *that adopted a CI service*, a strict subset of the 383 — the map's own phrasing ("31.23 percent of Bazel projects with CI configured never invoke Bazel there," [bazel-topic-map.md:120](../bazel-topic-map.md)) is accurate; a naive reading against "all 383 projects" would be wrong. Two performance numbers ride along in the same abstract and are worth carrying: parallel-build median speedups of 2.00x/3.84x/7.36x/12.80x at 2/4/8/16 threads (vs. sequential), and incremental-build median speedups of 4.22x/4.71x (tool-independent vs. tool-specific CI cache, vs. clean build) — both scoped to "long-build duration projects" only, not the full 383.

*The ~11% abandonment figure.* Traced to a specific, dated talk: **Shane McIntosh (University of Waterloo), "The Classics Never Go Out of Style: An Empirical Study of Downgrades from Bazel," BazelCon 2024**, Monday 2024-10-14, Hahn Auditorium ([BazelCon 2024 schedule](https://bazelcon2024.sched.com/)). No paper link is published on the schedule page, and a search for a companion paper from Waterloo's REBELs group (`rebels.cs.uwaterloo.ca`) 404'd — treat this as a **conference talk, not (yet, or ever) a peer-reviewed publication**. The independent recap ([BazelCon 2024 recap, Julio Merino/Blog System 5](https://blogsystem5.substack.com/p/bazelcon-2024-recap)) gives the fuller number the map's citation drops: *"The REBELs research group at the University of Waterloo conducted a study over 35,000 significant GitHub projects... from the 1.5% of projects that adopted Bazel, 11% of those abandoned the migration at roughly the 2-year mark."* Two numbers, not one: **1.5% adoption rate** among 35,000 surveyed projects, and **11% of that 1.5% churn out around year two**, citing "technical challenges, team coordination and onboarding issues, and community trends" (naming Kubernetes' departure as a community-trend example) as the three reason-buckets, with no further breakdown reported in the recap.

*Aspect's and EngFlow's "should you adopt Bazel" writing — the negative result.* Neither vendor has a piece that states adoption criteria as thresholds. [Aspect: "Estimating Bazel's Adoption"](https://aspect.build/blog/estimating-bazel-adoption) (2022-09-12) is a market-sizing exercise (public-user-list × private-consulting-list capture-recapture, giving ~602/~3,750 companies) with **zero mention of team size, language count, or repo scale as adoption criteria** — its own framing is that Bazel is crossing Geoffrey Moore's "Chasm" between early adopters and early majority, a maturity claim, not a fit claim. [Aspect: "Principles of a Bazel Migration"](https://aspect.build/blog/principles) (2022-02-22) is entirely about *how* to migrate once decided, with no *whether* criteria. EngFlow's blog index (`blog.engflow.com`) has no adoption-decision post at all; its closest content is customer case studies of migrations already underway (e.g. Iterable, sbt→Bazel). The single quantified scale reference from either vendor is inside Aspect's CI-strategy post, not an adoption post: [Aspect, "Monorepo Shared Green"](https://aspect.build/blog/monorepo-shared-green) states a "large Aspect customer" runs at **"2 million SLOC and 500 engineers"** on whole-repo shared-green with no predictive tooling, and frames the case for predictive/target-selection tooling as arising only near **Google's circa-2015 scale (2 billion SLOC, 50,000 engineers)** — "100-1000 times smaller in SLOC × engineers" than that is, in Aspect's own words, still fine without it. That is a scale claim about *target selection*, not about *whether to adopt Bazel at all* (see Q2).

*RabbitMQ's departure, verified primary.* [PR #13514](https://github.com/rabbitmq/rabbitmq-server/pull/13514), merged 2025-03-14, titled "Remove Bazel files." Stated reason, quoted verbatim: **"Bazel was a great tool for our team, it provided a much needed capability of caching and build optimisation. However, in recent times, we decided to focus on Make and erlang.mk."** This is explicitly a non-defect departure — no bug, no outage, no correctness complaint — consolidation toward the language-native toolchain (erlang.mk) instead of a polyglot build system, for a project that is effectively single-language (Erlang/C).

*"Adopted and stayed" accounts, with team size and language count.*

| Account | Team size | Language mix | Outcome as of the source |
|---|---|---|---|
| [Uber — Go monorepo](https://www.uber.com/en-NO/blog/go-monorepo-bazel/) | "under 10 to nearly 900" monthly active engineers | Primarily Go, with Bazel + Gazelle generating BUILD files; 70,000+ files, 1,000+ external modules | Sustained; still named as active infra in 2024-2025 BazelCon recaps. Named ongoing pain even post-adoption: IDE support and target-affected detection stayed home-grown problems. |
| [Canva — CI rebuild](https://www.canva.dev/blog/engineering/faster-ci-builds-at-canva/) | Not stated as a headcount in this post | Multi-language (BE, ML, frontend web) — >10^5-node build graph | Sustained and expanded: 80min→<30min builds, ~3,000 P90 CI jobs, ~$1.8M/year claimed savings (Apr 2022 → Sep 2023 before/after). Non-hermetic blockers (shared `localstack` containers, a11y suites) had to be fixed *before* any target-selection strategy could be trusted — the precondition, not the tool choice, is Canva's own load-bearing detail. |
| [Snowflake — two years in](https://blogsystem5.substack.com/p/bazel-at-snowflake-two-years-in) | Not stated | Not stated | "Completed our migration to Bazel for the largest part of our codebase" (2025-03-13) with forward-looking framing, no stated reconsideration — but this account gives no measurable team-size or language-count input at all, so it corroborates persistence without adding a threshold. |

**Answer.** The measurable inputs the map wanted (repo count, language count, target count, CI-minutes share of the dominant pain, generator maturity per language) each have **zero sourced numeric thresholds** anywhere in this corpus, as of 2026-09-05. What is sourced and measured: (1) adoption that never reaches CI is real and common (31.23% of Bazel-CI-configured projects, arXiv:2405.00796, verified); (2) year-two abandonment is real but the base rate is tiny (1.5% of 35,000 projects ever adopt; 11% of *those* churn — BazelCon 2024 talk, not a paper); (3) departure is not always failure (RabbitMQ, dated, explicit non-defect reason); (4) staying is correlated with multi-language, high-headcount monorepos (Uber, Canva) but no source states the floor below which staying stops working. `bazel-adopt`'s gate cannot be threshold-shaped; it has to be the yes/no checklist the frame's decision table already gestures at — "does CI actually run Bazel" (a direct M-F-04-shaped check against the 31.23% finding), "is the dominant pain build time" (Aspect's SLOC×engineers framing, qualitative only), "was a narrower fix tried" (Q5) — each backed by a named source, none backed by a number.

### Q2 — The target-count threshold for target selection {#q2}

**Question (commission Q2):** What do Tinder, Canva, Aspect, Uber and the target-determinator README give as the scale at which whole-repo builds stopped fitting a CI budget? Produce the number/range with source, or state none exists.

**Findings.** No source in this set states a target-count (or repo-scale) threshold at which whole-repo green stops fitting a CI budget. What each gives instead:

- **Canva**, the fullest quantified case: build graph **>10^5 nodes**, **~3,000 jobs at P90** per `check-merge` build, 80-minute average PR-to-merge time before the fix ([canva.dev](https://www.canva.dev/blog/engineering/faster-ci-builds-at-canva/), verified primary). This is a *description of the state they were in when they built a selector*, not a stated "above this many targets you need one" rule — and Canva's own sequencing point (fix non-hermetic tests first) means the trigger for building a selector was correctness-readiness, not a target count crossed.
- **Tinder's bazel-diff** README states scale only as a design-validation claim: **"tested with projects containing tens of thousands of targets"** ([raw.githubusercontent.com/Tinder/bazel-diff/master/README.md](https://raw.githubusercontent.com/Tinder/bazel-diff/master/README.md), verified primary) — evidence the tool *works* at that scale, not a claim that whole-repo green *fails* below it. Tinder's own BazelCon 2025 talk ("Precision CI at Scale: Target-Aware Workflows with Bazel Diff") reportedly claims a 93% CI time reduction per the secondary BazelCon 2025 recap ([blogsystem5.substack.com/p/bazelcon-2025-recap](https://blogsystem5.substack.com/p/bazelcon-2025-recap)) — no primary Tinder blog post with a target count was locatable in this pass to corroborate the percentage with a scale number.
- **Aspect** explicitly declines to give one and argues the opposite direction: predictive tooling only earns its complexity near Google's 2015 scale (2B SLOC / 50k engineers); a customer at 2M SLOC / 500 engineers (roughly 1000x smaller) runs whole-repo shared-green successfully ([aspect.build/blog/monorepo-shared-green](https://aspect.build/blog/monorepo-shared-green), verified primary). Aspect frames both `bazel-diff` ("very incorrect") and `target-determinator` ("very slow") as the reason to prefer no selection at all below Google-adjacent scale — this is an argued position, not a measured threshold.
- **Uber's** Go monorepo post gives scale (70,000+ files, ~900 monthly active engineers, ~10,000 commits/month, 1,000+ external modules) but **states no target-count trigger** for when whole-repo checks became infeasible; it names `SubmitQueue` (parallel checking) as the fix for commit-volume queueing, a CI-throughput problem, not explicitly a target-selection-versus-whole-repo decision ([uber.com/en-NO/blog/go-monorepo-bazel](https://www.uber.com/en-NO/blog/go-monorepo-bazel/), verified primary).
- **target-determinator's** README ([raw.githubusercontent.com/bazel-contrib/target-determinator/main/README.md](https://raw.githubusercontent.com/bazel-contrib/target-determinator/main/README.md), verified primary) gives **no scale claim at all** — only correctness caveats (clean-checkout enforcement, environment-variable cache staleness) and a Bazel-version-support statement ("4.0.0 up to and including the latest LTS release").

**Answer.** No number or range exists across Tinder, Canva, Aspect, Uber, or target-determinator's own documentation for "the target count above which whole-repo green stops fitting a CI budget." The two closest proxies — Canva's ~10^5 nodes/~3,000 jobs (a description of when they *acted*, not a threshold) and Aspect's ~1000x-below-Google framing (an argued ceiling for *not* needing selection) — point in opposite directions and neither is a target-count number. Frame decision 3's premise ("selection becomes the default above the target count the wave-3 CI dive names") currently has nothing to inherit; the CI-and-target-selection consolidation is still in flight as of this pass, and even once landed it will need to draw on this same evidence gap — there may be no number for it to name either. `bazel-adopt` should present target selection as gated on the **determinism precondition** (Canva's own sequencing) plus **team appetite for a self-maintained hashing/query pipeline** (both open-source tools ship documented correctness caveats), not on a target count.

### Q3 — Partial Bazelification cache benefit (M-K-15) {#q3}

**Question (commission Q3):** Is there a measured account of cache benefit at partial coverage, or only the argued "0 to 100" cliff?

**Findings.** Only the argued cliff, and it is thinner than "argued" alone suggests. [pow.rs, "Bazel is incompatible with JavaScript"](https://pow.rs/blog/bazel-is-incompatible-with-javascript/), verified directly: the passage is a **hypothetical**, not a measured account — "Imagine you had a dependency chain of Internal Package A → Internal Package B → Internal Package C in a monorepo... it requires you to fully Bazelify all three modules before you can see the results of one," concluding "Requiring 100% implementation to evaluate should be a deal breaker on its own." No project is named, no percentage or timing number accompanies the claim — it is an architectural inference from "Bazel doesn't know about any builds outside its special sandbox," not a report from a real migration. The bazel-typescript dive's own framing confirms this: M-K-15 is listed as "Contested in both directions... argued evidence on both sides" and its Contested/evolving section calls the counterweight "the broader corpus's staged-migration accounts for **other languages**" ([bazel-typescript/rules-js-architecture-and-dependency-resolution.md:240](../bazel-typescript/rules-js-architecture-and-dependency-resolution.md)) — meaning even the pro-partial-adoption side of the argument is not a JS-specific measured account; it is Tweag's Rust dual-build-system pattern (Cargo stays authoritative, `CARGO_BAZEL_REPIN=1` re-syncs into Bazel incrementally) generalized by analogy, a different mechanism (source-of-truth staging during a migration) from the question actually asked (does partial *coverage* produce partial *cache hits*).

**Answer.** As of 2026-09-05, no measured JS-monorepo account of cache benefit at partial Bazel coverage exists on either side of the question in this corpus. The "0 to 100% cliff" is a plausible, architecturally-grounded inference (Bazel's sandbox genuinely cannot see outside itself, so an upstream un-Bazelified step is an untracked, uncached input to anything downstream) but it is CONSIDER-only evidence by the house standard: one argued source, no measurement, no named project. M-K-15 correctly stays out of the ruleset rather than shipping a preference as a finding.

### Q4 — The coupling query under Bzlmod (M-G-21) {#q4}

**Question (commission Q4):** Which `bazel mod`/`bazel query` invocation makes a vendored-tree lineage visible? Verify each subcommand exists in the 8.7.0 and 9.2.0 CLI reference. Apply to the fleet's ocx → grimoire → ocx-mirror lineage and state what the migration would have to declare.

**Findings.** Verified directly against Bazel's own versioned docs (not the unversioned prose page, per the frame's correction #10 about pages drifting ahead of or behind numbered releases):

| Subcommand | Present on `versions/8.7.0/external/mod-command` | Present on `versions/9.1.0/external/mod-command` | Description (identical both versions) |
|---|---|---|---|
| `bazel mod graph` | Yes | Yes | "Displays the full dependency graph of the project, starting from the root module." |
| `bazel mod graph --extension_info` | Yes | Yes | "Include information about the module extension usages as part of the output graph." |
| `bazel mod show_repo` | Yes | Yes | "Displays the definition of the specified repos." |
| `bazel mod explain` | Yes | Yes | "Shows all the places where the specified modules appear in the dependency graph, along with the modules that directly depend on them." |

[bazel.build/versions/8.7.0/external/mod-command](https://bazel.build/versions/8.7.0/external/mod-command) and [bazel.build/versions/9.1.0/external/mod-command](https://bazel.build/versions/9.1.0/external/mod-command) both fetched and read directly. A versioned snapshot for **9.2.0 itself does not exist** on bazel.build (`versions/9.2.0/external/mod-command` returns 404) — Bazel's doc-versioning snapshots per LTS release, not per patch, so 9.1.0 is the closest archived text and the frame's own era note (9.2.0 Active LTS) inherits it. No behavior-relevant diff was found between the two versions' command descriptions.

**Applying this to the fleet's lineage** ([bazel-audit/fleet-bazel-readiness.md](../bazel-audit/fleet-bazel-readiness.md), Smells §2 and Contradictions #4, verified): `ocx` and `grimoire` each vendor the **same two git submodules** (`docker_credential`, `rust-oci-client`, forked at `ocx-sh/*`) via `.gitmodules` + a Cargo path dependency; `ocx-mirror` vendors **all of `ocx`** as a nested submodule and path-deps two directories deeper into `ocx`'s own submodules (`ocx-mirror/Cargo.toml:34-35,120-121`). None of the three are Bzlmod modules today — this is plain git + Cargo, and `bazel mod graph`/`explain`/`show_repo` have **nothing to query yet**, because there is no `MODULE.bazel` anywhere in the lineage.

The precondition is already named, correctly, in `BZL-ARCH-28`: *"[`git_override`] requires the vendored fork to itself declare a `MODULE.bazel` — which a vendored fork generally does not"* ([bazel-architecture-monorepo.md:188](../bazel-architecture-monorepo.md)). Concretely, for this lineage to become visible in `bazel mod graph --extension_info`:

1. `ocx-sh/rust-oci-client` and `ocx-sh/docker_credential` (the fork remotes, not just the submodule paths) would each need a `MODULE.bazel` added — turning them from vendored Cargo crates into real Bazel modules.
2. `ocx` and `grimoire` would each declare `bazel_dep(name = "rust_oci_client", ...)` / `bazel_dep(name = "docker_credential", ...)` plus a matching `git_override(module_name = ..., remote = "https://github.com/ocx-sh/...", commit = ...)` pointing at the *same* fork and commit — at which point `bazel mod explain rust_oci_client` would show both `ocx` and `grimoire` as direct users of one shared node, replacing today's silent duplication.
3. `ocx-mirror` faces the harder call: today it vendors `ocx` *whole* as a nested submodule and Cargo-path-deps through it. To surface in the module graph rather than staying an opaque nested checkout, `ocx-mirror` would need to declare a real `bazel_dep(name = "ocx")` (with its own `git_override`) instead of re-vendoring — only then would `bazel mod graph` draw the edge `ocx-mirror → ocx → {rust_oci_client, docker_credential}` as one lineage, which is exactly the "three fleet repos read as independent and are one dependency lineage two submodules deep" fact the map already states qualitatively (M-G-21).

**Answer.** All three subcommands are confirmed present and behaviorally identical on 8.7.0 and 9.1.0 (no 9.2.0-specific snapshot exists). The query itself is not the blocker for this fleet: `bazel mod graph --extension_info`, `bazel mod explain <repo>`, and `bazel mod show_repo <repo>` would all make the lineage visible the moment it exists as Bzlmod modules — but none of `ocx`, `grimoire`, `ocx-mirror`, `rust-oci-client`, or `docker_credential` are Bzlmod modules today, so the rule cannot say "run this query" as a diagnostic on the fleet as it stands; it has to say "adding a `MODULE.bazel` to the forked submodules is the prerequisite the coupling query depends on," which is a restatement and sharpening of BZL-ARCH-28's own caveat, not a new mechanism.

### Q5 — The narrower-fix-first ladder (M-G-23) {#q5}

**Question (commission Q5):** For each fleet shape, what is the cheaper fix a team tries before Bazel, and what evidence says when it stops being enough?

**Findings**, per fleet shape (reading commission, no commands run):

| Fleet shape | Cheaper fix tried first | Evidence it stops being enough |
|---|---|---|
| Rust workspaces (`ocx`, `grimoire`, `ocx-mirror`, `creeptd-ng`, `bob`) | `cargo build`'s own incremental compilation + workspace-level dependency dedup; `sccache` for a distributed/shared compiler cache; `cargo nextest` for parallel test execution | **No source in this corpus states a measured point at which these stop being enough.** Rust RFC 2136 and multiple 2023-2025 blog posts (Tweag, mmapped.blog) treat "does a Rust workspace need Bazel at all" as an explicitly open, contested question, not a settled progression ([architecture-and-monorepo-practice.md:55](../bazel-topic-map/architecture-and-monorepo-practice.md)). The one concrete Rust-adjacent pain named in the corpus (`crate_universe` ignoring path dependencies, forcing hand-written BUILD wiring for internal workspace crates — Tweag) is a *cost of adopting* Bazel, not evidence that Cargo-native caching had already failed. |
| Python projects (7 fleet repos, all uv-locked, none cross-project) | `uv`'s own resolver speed and its cache directory; no cross-project import graph exists to break | The comparison-post cluster in this corpus is unusually direct here: **Pants, not Bazel, is repeatedly named as "the right starting point for Python-heavy monorepos that find Bazel's BUILD-file overhead too steep"** ([architecture-and-monorepo-practice.md:51](../bazel-topic-map/architecture-and-monorepo-practice.md)) — i.e. even the next rung up from a fast per-project resolver is argued to be Pants before Bazel, for exactly this shape. Nothing in the fleet audit shows any Python project outgrowing `uv` today (`fleet-bazel-readiness.md`: "every one locks through `uv.lock`," no cross-project relative imports found). |
| TypeScript/JS packages (npm ×6, bun ×2, one pnpm-declared-but-npm-actual mismatch in `creeptd-ng/web`) | pnpm's content-addressable store / `npm ci` caching; Nx or Turborepo for task-level (not target-level) build caching layered over the existing per-package tools | The 2026 comparison-post consensus is the sharpest evidence here, and it argues the ladder mostly **never needs to climb further** for this shape: "Nx/Turborepo are lightweight task-runners layering caching over existing per-language tools, capped below Bazel's ceiling but **sufficient for most JS/TS-only teams**" ([architecture-and-monorepo-practice.md:52](../bazel-topic-map/architecture-and-monorepo-practice.md), source #20 cluster: aviator.co, sourcegraph.com, daily.dev). No account in the corpus shows a JS-only fleet repo (which every fleet TS package is — none cross-couples to Rust or Python) outgrowing Turborepo/Nx into needing Bazel; the corpus's own framing treats that migration direction as the wrong one for a JS-only shape, not an eventual necessity. |
| General/cross-cutting (any repo relying on CI-level task caching, e.g. GitHub Actions `actions/cache`, or a Bazel-aware merge queue) | Plain CI cache steps; Trunk.io-style dependency-graph-aware merge queues (cited as exploiting *Bazel's own* declared graph once present, not a pre-Bazel substitute) | Not directly evidenced as a "narrower fix" *before* Bazel in this corpus — Trunk.io's merge-queue material assumes Bazel's graph already exists ([architecture-and-monorepo-practice.md:129](../bazel-topic-map/architecture-and-monorepo-practice.md)). No fleet repo has hit a documented failure of plain CI caching. |

**Reverse evidence worth naming explicitly:** the corpus's clearest "narrower fix" story runs the *other* direction — RabbitMQ tried Bazel and moved back to the narrower Make/erlang.mk, not the reverse. This is worth stating in `bazel-adopt` as a caution: the corpus has more documented instances of teams reverting to a simpler system after Bazel than of teams naming the exact moment a simpler system stopped working and Bazel was the fix.

**Answer.** For every fleet shape, a cheaper fix exists and is plausibly already in use or trivially available (cargo/sccache/nextest for Rust, uv for Python, pnpm+Nx/Turborepo for TS), but **no source anywhere in this corpus states a measured trigger point at which any of these stops being enough** for a repo of this fleet's size. The strongest sourced claim runs in the opposite direction for two of three shapes: Python-heavy monorepos are steered toward Pants before Bazel, and JS-only monorepos are argued to be *permanently* well-served by Turborepo/Nx rather than expected to outgrow it. Only the Rust shape is left genuinely open (RFC 2136, contested), and even there no threshold is sourced. M-G-23's own question ("is a narrower fix considered first") is answerable today only as a **checklist item** ("name the narrower fix and why it was rejected"), never as a measured comparison, because the comparison data does not exist.

## AI-agent angle

An agent asked "should repo X adopt Bazel" will confidently synthesize a plausible-sounding numeric threshold (a target count, a team-size cutoff) because that is the shape adoption advice usually takes in training data — this research found none exists in the sourced corpus for this question, at any scale. The smallest mechanical check: before an agent states a number as a go/no-go criterion in `bazel-adopt` output, require it to name the exact source and quote the number verbatim; if it cannot produce a quote, the number must be dropped and replaced with the checklist form. A second, narrower trap: an agent reasoning about the fleet's `ocx`/`grimoire`/`ocx-mirror` coupling will reach for `bazel mod graph` as if it already applies — it verifiably does not, because none of the three are Bzlmod modules. The check: `find <repo> -maxdepth 1 -iname 'MODULE.bazel*'` before recommending any `bazel mod` invocation against a fleet repo; empty means the query is aspirational, not runnable, today.

## Contested / evolving

- Whether M-K-15's "0 to 100% cliff" is real for JS specifically remains open in both directions, but the evidential weight is asymmetric: the cliff argument is a single hypothetical with no measurement; its counterweight is an analogy from a different language's different migration pattern. Treat as leaning toward "unmeasured, not truly contested" rather than a balanced two-sided dispute.
- Aspect's Google-2015-scale framing for when target selection becomes necessary is itself argued (Aspect is a commercial party with an interest in the "you probably don't need predictive tooling" position being wrong for smaller customers who might buy Aspect Workflows) — it is the best available number but should be cited as Aspect's own claim, not neutral evidence.
