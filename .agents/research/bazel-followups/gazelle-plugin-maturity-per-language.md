## Summary

- Aspect's JS/TS Gazelle plugin is real, BCR-published, and usable with a plain `MODULE.bazel` dependency and zero Aspect CLI or paid Workflows — `aspect_gazelle_prebuilt` ships a drop-in Gazelle binary with the `js` language compiled in.
- That plugin never emits a `transpiler=` attribute on generated `ts_project` targets. rules_ts has required one explicitly since 2.0 (hard `fail()` otherwise). The plugin's own e2e smoke test papers over this with the repo-wide `--@aspect_rules_ts//ts:default_to_tsc_transpiler` flag — the exact escape hatch BZL-JS-13 already flags as a defect when left as a permanent state.
- The plugin's npm-import resolution reads `pnpm-lock.yaml` with a parser that dispatches on `lockfileVersion` major 5, 6, or 9 only. pnpm 12's multi-document lockfile format breaks it — open bug [aspect-gazelle#461](https://github.com/aspect-build/aspect-gazelle/issues/461) (2026-09-01) with a fix in flight ([#460](https://github.com/aspect-build/aspect-gazelle/pull/460), still open).
- The plugin's headline convenience distribution, `aspect_gazelle_prebuilt`, is still pre-1.0 (`0.0.25`) even though the `js` language module itself reached BCR version `1.2.1` — the maturity label a consumer should quote is the module they actually depend on, not the most-mature sibling.
- rules_python's Gazelle extension is genuinely first-party (`rules_python/gazelle/`) with three generation modes (`file`/`package`/`project`, default `package`), import validation on by default (`python_validate_import_statements = true`, which is a **loud** generation-time error, not a silent one), and does not generate a pytest entrypoint shim — a hand- or Gazelle-generated `py_test` on a pytest-style file is a permanently green target running zero tests unless paired with a wrapper like `pytest-bazel`.
- gazelle_rust (`Calsign/gazelle_rust`) is single-maintainer, BCR-published, and still on its only tag, `v0.1.0` (2026-05-05), despite the repo existing since 2022 and main-branch commits continuing through 2026-08-24. Its default generation mode is one target per source file — finer-grained than either Go's or Python's package-level default — with a `generate_from_cargo` mode as the package-level alternative.
- gazelle_rust cannot: generate protobuf-derived Rust code; delete a target when its source file is removed; use `mod` declarations to infer structure; infer platform-conditional (`select()`-shaped) dependencies (requires a hand-written `#[gazelle::ignore]` attribute plus a `# keep` BUILD comment); route a `resolve` override into `proc_macro_deps`; or parse crate_universe's bzlmod direct-dependency lockfile — it falls back to a raw `Cargo.lock`, which double-counts transitive dependencies (open bug [#15](https://github.com/Calsign/gazelle_rust/issues/15)).
- bazel-gazelle core (Go + protobuf) is the actual maturity baseline: `v0.54.0` (2026-09-03), ~monthly releases, 1,415 stars, a decade-plus of history. Its built-in `proto` language ships five generation modes (`default`/`package`/`legacy`/`disable`/`disable_global`).
- A distinct protobuf-adjacent tool, `bufbuild/rules_buf`'s `buf` Gazelle language (`v0.5.4`, pre-1.0), does **not** generate `proto_library` — it generates `buf_lint_test`, `buf_breaking_test`, and a `buf_dependencies` repo rule. It is a lint/breaking-change add-on, not a competitor to bazel-gazelle's own `proto` language.
- No language's own installation docs wire the `gazelle_test`/`sh_test` freshness gate by default — verified by reading rules_python 2.3.3's install doc, gazelle_rust's own example, aspect-gazelle's `aspect_gazelle()` macro source, and even bazel-gazelle's own root `BUILD.bazel`. All four wire only the plain `gazelle()`/`sh_binary` target. `gazelle_test` is always a manual, opt-in wiring step, and it is the *same* macro (`@gazelle//:def.bzl`) regardless of which language plugin sits behind it.
- Aspect's `aspect_gazelle(with_check = True)` convenience macro produces a `<name>.check` target that is an `sh_binary` (`bazel run`), not an `sh_test` — it calls upstream's plain `gazelle()` macro internally, never `gazelle_test`. A `bazel test //:gazelle_test`-shaped CI gate for JS/TS does not exist out of the box; an adopter must hand-wire it against the Aspect binary.
- "BUILD files are generated, never hand-written" is not cleanly achievable today for any fleet shape that includes JS/TS (shapes C, E) without accepting a named, documented exception for the transpiler gap. It is achievable for Rust with review discipline (BZL-ARCH-13) and named escape hatches for platform-conditional deps. For Python it is achievable only above roughly 30-50 hand-maintained targets (BZL-PY-30, CONSIDER) — below that, hand-writing is the correct default regardless of plugin maturity.

## Answers

### Q1 — Aspect's JS/TS Gazelle plugin {#q1}

> Is it usable as a plain gazelle language plugin outside the Aspect CLI and the paid Workflows offering as of 2026-09-05; what does it generate for a `ts_project` with the mandatory transpiler choice; how does it resolve npm imports?

**Findings.**

The plugin lives in [`aspect-build/aspect-gazelle`](https://github.com/aspect-build/aspect-gazelle) ("Aspect Gazelle languages, enhancements, utils"), created 2024-09-12, pushed 2026-08-27, 13 stars, 43 open issues, Apache-2.0. Two BCR-published modules matter:

- `aspect_gazelle_js` (the `js` language implementation) — BCR versions up to **1.2.1**, tagged `js-v1.2.1` (2026-08-27).
- `aspect_gazelle_prebuilt` (a prebuilt Gazelle binary with every Aspect-endorsed language already compiled in) — BCR versions up to **0.0.25** (2026-08-25), `bazel_compatibility = [">=7.6.0"]`.

Both are confirmed live in the real registry: `curl https://bcr.bazel.build/modules/aspect_gazelle_js/metadata.json` and the `aspect_gazelle_prebuilt` equivalent both return version lists, not 404s.

**Usable outside the Aspect CLI: yes, unambiguously.** The repo's own README states the setup as a `MODULE.bazel` dependency plus a native macro, no CLI required:

```starlark
bazel_dep(name = "aspect_gazelle_prebuilt", version = "...")
```
```starlark
load("@aspect_gazelle_prebuilt//:def.bzl", "aspect_gazelle")
aspect_gazelle(name = "gazelle", languages = ["js", "python", ...], with_check = True)
```
— [aspect-gazelle README](https://raw.githubusercontent.com/aspect-build/aspect-gazelle/js-v1.2.1/README.md). The one-line disclaimer near the top ("This repository uses the Aspect CLI for CI and local development") describes how the *aspect-gazelle project itself* is developed, not a runtime requirement for consumers — nothing in the `aspect_gazelle()` macro, the `js` language's Go source, or the BCR listing invokes the CLI or a Workflows account. The prebuilt module's explicit selling point is avoiding a Go/Rust/LLVM toolchain at build time, which a CLI wrapper would not change.

The one real constraint on "plain plugin" framing: **the runner's language set is fixed.** Per the README, "further Gazelle languages (written with the Go SDK) cannot be added without changes to the runner" — the built-in set is `buf`, `cc`, `go`, `js`, `kotlin`, `orion`, `proto`, `python`, `starlark`, `visibility_extension`. This same list is baked into `runner/def.bzl`'s `_VALID_LANGUAGES` and mirrors `runner/runner.go`'s `AddLanguage()` switch statement. A consumer who wants a custom Go-SDK language alongside `js` cannot compose it into `aspect_gazelle()` — that path requires building your own `gazelle_binary` from source against `@aspect_gazelle_js//:js` directly (documented, but loses the prebuilt's toolchain-avoidance benefit).

**What it generates for a `ts_project`, and the transpiler gap.** Per [language/js/README.md](https://raw.githubusercontent.com/aspect-build/aspect-gazelle/js-v1.2.1/language/js/README.md), generated targets include `ts_project`/`js_library` for sources and tests, `ts_config` for `tsconfig.json`, `npm_package`/`js_library` for pnpm-workspace packages, and `npm_link_all_packages`. Reading the plugin's own `Kinds()` map directly (`language/js/kinds.go`, `js-v1.2.1`) shows the full `MergeableAttrs`/`NonEmptyAttrs` set for `TsProjectKind`: `srcs`, `assets`, `isolated_typecheck`, `tsconfig`, and every reflected-tsconfig attribute (`allow_js`, `composite`, `declaration`, `declaration_map`, `emit_declaration_only`, `source_map`, `incremental`, `ts_build_info_file`, `resolve_json_module`, `preserve_jsx`, `out_dir`, `root_dir`). **`transpiler` is not in that list, is not mentioned anywhere in `generate.go` (1,810 lines, grepped for `transpil`), and returns zero hits from a repo-wide code search** (`gh api search/code -f 'q=transpiler repo:aspect-build/aspect-gazelle'` → 1 hit, a `.bazelrc` comment, not generation code). The generated `ts_project` calls load straight from `@aspect_rules_ts//ts:defs.bzl` (`ApparentLoads()` in `kinds.go`) — the native macro, not a wrapper that could inject a default.

Since [rules_ts requires an explicit `transpiler=` since 2.0](https://github.com/aspect-build/rules_ts/releases/tag/v2.0.0) (a hard `fail("Required Transpiler Selection")` per `bazel-typescript/rules-ts-typecheck-and-transpiler.md:66-79`, and confirmed here independently by the absence of the attribute in the plugin's own kind spec), **every `ts_project` this plugin generates fails to load under rules_ts ≥2.0 unless something else supplies a transpiler.** The plugin's own repository proves this is a real, unresolved gap rather than a theoretical one: its `language/js/e2e/smoke/.bazelrc` carries

```
# Transpile ts_project targets with tsc (rules_ts requires an explicit choice).
common --@aspect_rules_ts//ts:default_to_tsc_transpiler
```

— the exact repo-wide default flag BZL-JS-13 already names as "a legitimate escape hatch... and a defect as a permanent state." The plugin's own e2e test treats it as permanent, not transitional. **No open issue on the tracker mentions "transpiler" at all** (`gh api search/issues -f 'q=transpiler repo:aspect-build/aspect-gazelle'` → 0 results) — this gap is not even tracked, let alone scheduled.

**How it resolves npm imports.** The `js` language implements Gazelle's `resolve.Resolver` interface (`language/js/resolve.go`, 768 lines): for each `ts_project`/`js_library`/`ts_proto_library`/`ts_config` rule it emits `resolve.ImportSpec`s from the parsed source files (an oxc-based Rust parser linked in via cgo, per `language/js/README.md`'s Build setup section). Package-name resolution for npm imports goes through `language/js/node/package.go` and `language/js/pnpm/parser.go`, which parses `pnpm-lock.yaml` to map a package name to the workspace/npm target `npm_link_all_packages` generates (`//:node_modules/<pkg>`). Reading `parser.go` directly: it reads only the file's first `lockfileVersion:` line via a regex, then dispatches:

```go
if version.Major() == 5 { return parsePnpmLockDependenciesV5(...) }
else if version.Major() == 6 { return parsePnpmLockDependenciesV6(...) }
else if version.Major() == 9 { return parsePnpmLockDependenciesV9(...) }
return nil, fmt.Errorf("unsupported version: %v", versionStr)
```

**pnpm 12 changed the lockfile to a multi-document YAML** (separated by `---`); a minimal repro exists at [david-wasser/pnpm-12-aspect-gazelle-bug-repro](https://github.com/david-wasser/pnpm-12-aspect-gazelle-bug-repro) (created 2026-08-31: "aspect-gazelle's js language cannot read a pnpm 12 multi-document pnpm-lock.yaml") and is tracked as an open bug, [aspect-gazelle#461](https://github.com/aspect-build/aspect-gazelle/issues/461) ("[Bug]: Gazelle cannot parse `pnpm` 12 lockfile"), with two open fix PRs in flight as of this read: [#460](https://github.com/aspect-build/aspect-gazelle/pull/460) ("read multi-document pnpm lockfiles") and [#459](https://github.com/aspect-build/aspect-gazelle/pull/459) ("read project dependencies from combined lockfiles"). **As of 2026-09-05, `js-v1.2.1` cannot resolve npm imports against a pnpm-12-locked workspace.**

**Answer.** Aspect's JS/TS Gazelle plugin is a real, standalone, BCR-published Gazelle language usable with a plain `MODULE.bazel` dependency and no Aspect CLI or Workflows subscription, as of `js-v1.2.1`/`aspect_gazelle_prebuilt 0.0.25` (2026-09-05). It generates `ts_project` targets with no `transpiler=` attribute at all — a load-time `fail()` under rules_ts ≥2.0 unless the adopter accepts the repo-wide `default_to_tsc_transpiler` default (the plugin's own e2e test does exactly this) or hand-patches every generated target. Its npm-import resolution walks `pnpm-lock.yaml` but only understands lockfile major versions 5, 6, and 9; pnpm 12's multi-document format is an open, unfixed bug as of this date.

### Q2 — rules_python's first-party Gazelle extension {#q2}

> 2.3.3: `python_generation_mode` file/package/project, import validation defaults, manifest workflow, what it does with pytest files.

**Findings.** Grounding: `bazel-python/python-tests-and-build-generation.md` (dive), `bazel-python.md` Group H (consolidation), both re-verified here against [`rules_python/gazelle/docs/directives.md`](https://raw.githubusercontent.com/bazel-contrib/rules_python/main/gazelle/docs/directives.md) and [`gazelle/docs/installation_and_usage.md`](https://raw.githubusercontent.com/bazel-contrib/rules_python/refs/tags/2.3.3/gazelle/docs/installation_and_usage.md) at the pinned `2.3.3` tag.

- **`# gazelle:python_generation_mode file|package|project`** — per-file, per-package (**default**), or whole-subtree generation. `file` is the finest grain (one target per source file, matching gazelle_rust's default rather than Go's package default); `project` collapses an entire subtree into one target group.
- **Import validation defaults to `true`** (`python_validate_import_statements`), and an unresolvable import is a **loud** `bazel run //:gazelle` failure printing three concrete remediations (add to `requirements.txt`, add a `resolve` directive, or `# gazelle:ignore`) — not a silent skip. This directly overturns the frame's inherited map row M-J-13 ("silently fails to resolve"), confirmed independently here by reading the plugin's own error string quoted in [rules_python#709](https://github.com/bazel-contrib/rules_python/issues/709).
- **Manifest workflow (`gazelle_python.yaml`):** three `bazel_dep`s (`gazelle`, `rules_python`, `rules_python_gazelle_plugin`), a `modules_mapping`/`gazelle_python_manifest` pair, and a `gazelle_binary`+`gazelle` pair in the root `BUILD.bazel` — [installation_and_usage.md](https://raw.githubusercontent.com/bazel-contrib/rules_python/refs/tags/2.3.3/gazelle/docs/installation_and_usage.md). The manifest file itself must exist before the first `.update` run (`touch gazelle_python.yaml` — this is **not** auto-created; still open as [rules_python#1156](https://github.com/bazel-contrib/rules_python/issues/1156)) and drift against `requirements.txt`/`uv.lock` is caught only by `bazel test //:gazelle_python_manifest.test` — a target distinct from the BUILD-freshness `gazelle_test` (see Q7).
- **pytest files:** the plugin does **not** generate a pytest entrypoint shim. Native `py_test` runs `unittest` discovery inside `srcs`; pointed at a `def test_`-shaped pytest file with no `TestCase`, the target is "silently pass[ing] without running any tests" per a maintainer quoted directly on the open feature request (`bazel-python/python-tests-and-build-generation.md:70-76`). The supported pairing is a wrapper — [pytest-bazel](https://github.com/aignas/pytest-bazel) 0.1.6 is the currently-maintained one — wired as the `py_test`'s entrypoint. What the plugin *does* handle automatically: sibling `conftest.py` wiring since rules_python 0.14.0, and **ancestor** `conftest.py` wiring since 1.9.0 (2026-02-21, [PR #3498](https://github.com/bazel-contrib/rules_python/pull/3498)) — a hand-maintained BUILD file gets neither.
- **Version floor for correctness, not just for existence:** `rules_python_gazelle_plugin` 2.3.0 (2026-08-07) is a **BREAKING** release requiring `rules_python ≥1.5.0`, fixing a stdlib-misclassification bug where Python 3.13/3.14 targets fell back to the 3.11 stdlib list (`telnetlib` wrongly stdlib, `compression.zstd` wrongly third-party) — silent wrong `deps`, no error. As of 2026-09-05 both `rules_python` and the plugin are pinned at **2.3.3**, past the fix.

**Answer.** rules_python's Gazelle extension is genuinely first-party, ships three generation-granularity modes with `package` as the default, validates imports loudly by default (a generation-time error with remediations, not a silent drop), requires a manually-created empty manifest file before first use, and generates no pytest wrapper — a `py_test` on a pytest-style file is a permanently-green, zero-test target unless paired with a wrapper like pytest-bazel. All of this holds at `rules_python`/plugin **2.3.3** (2026-09-04/08-07).

### Q3 — gazelle_rust {#q3}

> Calsign/gazelle_rust: maintenance state, crate_universe integration, what it cannot generate.

**Maintenance state.** [`Calsign/gazelle_rust`](https://github.com/Calsign/gazelle_rust) — "Gazelle language plugin for Rust", created 2022-09-03, single maintainer (William Smith, `Calsign`), 51 stars, Apache-licensed. **Exactly one tagged release, `v0.1.0` (2026-05-05)** — nearly four years after creation — confirmed both via `gh api repos/Calsign/gazelle_rust/releases` and the BCR (`bcr.bazel.build/modules/gazelle_rust/metadata.json` lists only `"0.1.0"`). The repo is **not stale**: main-branch commits continue through 2026-08-24 ("Handle discovery of test-only modules correctly"), and the commit history shows an active feature/fix cadence ("Unbreak after 0.71.0 release of rules_rust", "update readme now that gazelle_rust is in the BCR") — but the *published, pinnable* artifact has never moved past `0.1.0`, meaning semver makes zero stability promise. Only 2 open GitHub issues, but the maintainer runs a public backlog issue ([#16](https://github.com/Calsign/gazelle_rust/issues/16), opened 2025-11-27) listing a much longer set of known gaps not filed as individual issues — a real single-point-of-failure risk pattern (one person's private TODO list stands in for a public issue tracker).

**Requires `rules_rust ≥0.40.0`** (fleet pins 0.74.0, cleared) and `bazel_compatibility = [">=7.0.0"]` per its own `MODULE.bazel` (`v0.1.0` tag) — compatible with both Bazel 8 and 9.

**Generation mode.** By default gazelle_rust generates **one target per source file** — finer-grained than Go's package default and matching rules_python's `file` mode as the *default* rather than an opt-in. A directive switches to a Cargo-structure-aligned mode: `# gazelle:rust_mode generate_from_cargo` generates `BUILD.bazel` files next to existing `Cargo.toml` files instead, with `# gazelle:rust_default_edition` controlling the edition attribute on generated targets. There is no "whole subtree" project-level mode; **it does not support sources in subdirectories** — targets always land in the BUILD file adjacent to their sources, so a Rust module tree that spans directories without a `Cargo.toml`-per-directory shape is not generated the way a human might structure it.

**crate_universe integration.** Both a raw `Cargo.lock` (`# gazelle:rust_cargo_lockfile`) and a bzlmod-produced custom lockfile (`# gazelle:rust_lockfile`, e.g. `cargo-bazel-lock.json`) are supported, mutually exclusively, alongside a required `# gazelle:rust_crates_prefix` (e.g. `@crates//:`) telling it where crate_universe labels live. **The raw-`Cargo.lock` path has an open, confirmed bug**: [gazelle_rust#15](https://github.com/Calsign/gazelle_rust/issues/15) ("Transitive dependencies are considered when using `Cargo.lock`") — the maintainer's own issue text: parsing `Cargo.lock` "include[s] all packages, including transitive dependencies," which (a) makes unused-dependency reporting incorrectly flag every transitive crate as unused, and (b) can make gazelle add a `deps` entry for a crate that is a transitive-only dependency with **no corresponding top-level target**, breaking the build. Direct-dependency parsing from crate_universe's own bzlmod lockfile (the fix the maintainer names as the preferred long-term direction) is an open feature request, not yet implemented.

**What it cannot generate (from the README plus the maintainer's own tracking issue, both primary):**
- No Rust-protobuf rule generation ("Support rust protobuf rules" — open item on #16).
- No target deletion when a source file is deleted (listed as a TODO, "maybe only with `gazelle fix`" — meaning it does not do this even under `fix` today).
- No `mod`-declaration awareness to inform default target structure (open item, linked to [#13](https://github.com/Calsign/gazelle_rust/issues/13) and [PR #25](https://github.com/Calsign/gazelle_rust/pull/25)).
- No inference of **platform-conditional dependencies** (a `select()`-shaped `deps` list, e.g. a wasm-only import): the README states this outright ("too complex... for now you must handle this manually") and documents the workaround — a `#[gazelle::ignore]` attribute macro on the `use` item plus a `# keep` comment in the BUILD file's `deps`.
- `resolve` directive overrides are never routed into `proc_macro_deps` — a standing gap referenced from a 2023 comment thread and still open.
- A **global crate-name namespace**: if two crates in the project (or crate universe) share a name, generation raises a hard error ("more than one crate with that name was found") unless resolved per-directory via the standard gazelle `resolve` directive.

**Answer.** gazelle_rust is single-maintainer, BCR-published, still at its only tagged release `0.1.0` (2026-05-05) despite continuing main-branch activity through 2026-08-24. It integrates with crate_universe via either lockfile shape but has an open correctness bug specific to the raw-`Cargo.lock` path (transitive-dependency over-inclusion). It cannot generate protobuf-derived code, delete stale targets, infer `mod`-based structure, infer platform-conditional dependencies, route `resolve` overrides into `proc_macro_deps`, or resolve a global crate-name collision automatically.

### Q4 — bazel-gazelle core (Go) and the protobuf plugin {#q4}

**bazel-gazelle core, the maturity baseline.** [`bazel-contrib/bazel-gazelle`](https://github.com/bazel-contrib/bazel-gazelle) — "Gazelle is a Bazel build file generator... It natively supports Go and protobuf" — latest release **`v0.54.0`** (2026-09-03), preceded by `v0.53.0` (2026-08-19), `v0.52.2/.1/.0` (July), `v0.51.3/.1` (June): a roughly-monthly cadence. 1,415 stars, 460 open issues (proportionate to a decade-plus, widely-depended-on project — not a red flag at this scale the way it would be for a single-maintainer 0.1.0 plugin). This is the maturity floor every other plugin in this program is measured against.

**Go's own generation mode:** package-level by default, with `# gazelle:go_generate_proto true|false` toggling proto interplay per directory ([language/go/reference.md](https://raw.githubusercontent.com/bazel-contrib/bazel-gazelle/v0.54.0/language/go/reference.md)).

**Protobuf: the baseline is bazel-gazelle's own built-in `proto` language, not a third-party plugin.** [`language/proto/reference.md`](https://raw.githubusercontent.com/bazel-contrib/bazel-gazelle/v0.54.0/language/proto/reference.md) documents five modes via `# gazelle:proto`:

| Mode | Behavior |
|---|---|
| `default` | Generates `proto_library`, `go_proto_library`, `go_library` — one of each per directory. **The default.** |
| `package` | (special-cased for `# gazelle:proto_import_prefix`, effective only in this mode) |
| `legacy` | `filegroup` only; `go_proto_library` hand-written. Auto-selected if `go_proto_library.bzl` is already loaded, to avoid disrupting existing projects. |
| `disable` | `.proto` files ignored. Auto-selected inside a `vendor/` directory. |
| `disable_global` | Like `disable`, but also disables Well-Known-Types/Google-APIs special-casing — "useful for avoiding build-time dependencies on protoc." |

This is first-party, mature, and has existed since early in the project's life — no separate maturity concern beyond the core baseline above.

**A distinct protobuf-adjacent tool exists and must not be conflated with proto generation:** [`bufbuild/rules_buf`](https://github.com/bufbuild/rules_buf) ships its own Gazelle language, `buf` (registered in Aspect's runner's `_VALID_LANGUAGES` list too, confirming cross-ecosystem reuse) — latest release **`v0.5.4`** (2026-04-30), still pre-1.0, 62 stars, 14 open issues. Reading its Go source directly (`gazelle/buf/kinds.go`, `gazelle/buf/buf.go`, `v0.5.4` tag) shows it generates exactly three things: `buf_lint_test`, `buf_breaking_test`, and a `buf_dependencies` repo rule. **It does not generate `proto_library`** — that remains bazel-gazelle core's job. `rules_buf`'s `buf` extension is an additive lint/breaking-change layer that assumes `proto_library` targets already exist (from the `proto` language above), not a competing or replacement proto generator.

**Answer.** bazel-gazelle core (Go + built-in protobuf) is the maturity baseline at `v0.54.0` (2026-09-03): mature, first-party, roughly-monthly releases, five documented proto generation modes. The separate `bufbuild/rules_buf` "buf" Gazelle language (`v0.5.4`, pre-1.0) is a lint/breaking-change add-on layered on top of, not a substitute for, bazel-gazelle's own `proto_library` generation.

### Q6 — Per fleet shape: generated, never hand-written? {#q6}

Using the map's shapes (`bazel-frame.md` § "The codebases that will adopt the output"; none of these shapes has adopted Bazel yet, so every answer here is Shape-F framing per BZL-ARCH's own convention):

- **Shape B — Rust CLI + Python harness (`ocx`, `grimoire`, `ocx-mirror`, `bob`, `rust-oci-client`).** Rust: achievable *with review discipline*, not as a blanket guarantee — gazelle_rust (0.1.0) generates the bulk correctly, but platform-conditional deps and any crate-name collision require hand-authored `#[gazelle::ignore]`/`resolve` escape hatches that gazelle then respects on every regeneration (BZL-ARCH-13's "review every regenerated diff by hand" applies directly). Python: achievable only once past roughly 30-50 hand-maintained targets (BZL-PY-30, CONSIDER); the fleet's two harnesses are pytest-root-shaped, not per-file, so migrating them as one or two `pytest_test` targets each keeps them **below** that threshold — hand-writing, not Gazelle, is the right default for Python here today. **Fallback granularity where not generated: coarse, package-per-directory, hand-maintained** (BZL-ARCH-11's coarse branch).
- **Shape C — Rust + TypeScript monorepo (`creeptd-ng`).** Rust: same as Shape B. TypeScript: **not achievable without a named exception.** The transpiler gap (Q1) means every generated `ts_project` either needs the discouraged repo-wide `default_to_tsc_transpiler` default (contradicting BZL-JS-13's SHOULD) or a hand-patched `transpiler=` line reintroducing a hand-written element into every generated target. This fleet's own three-JS-package-manager drift (`typescript-packaging`'s row) and the open pnpm-12 lockfile bug compound the problem if/when the workspace migrates to pnpm 12. **Fallback: coarse, hand-maintained `ts_project`/`js_library` per directory until the transpiler gap is closed upstream, or a documented, reviewed exception (the repo-wide flag) is adopted as a stated trade-off, not a silent default.**
- **Shape D — Python library or automation.** Same reasoning as Python in Shape B: every fleet repo in this shape is small (single-package library scale), well below the ~30-50 target threshold. **"Generated, never hand-written" is premature here; hand-write `py_library`/`py_test` and revisit only if the repo crosses the threshold** (BZL-PY-30).
- **Shape E — TypeScript package, extension, or Action.** Same transpiler-gap blocker as Shape C's TS half, with an additional wrinkle: two fleet packages in this shape are bun-locked with no `npm_translate_lock` ingestion path at all (wave-2 finding, `bazel-typescript.md`), so Aspect's plugin — which only parses `pnpm-lock.yaml` — cannot even reach those two packages' imports regardless of the transpiler question. **Fallback: coarse, hand-maintained BUILD per directory; Gazelle is viable only for the pnpm-locked packages, and even there only with the transpiler exception named and reviewed.**

**Answer.** "BUILD files are generated, never hand-written" is not a fleet-wide-achievable mandate today. It holds, with review discipline and named escape hatches, for Rust wherever a repo is large enough to justify gazelle_rust's fixed setup cost. It does not hold for TypeScript in any shape without accepting and documenting the transpiler workaround as a stated exception, not a silent default. For Python it holds only above roughly 30-50 targets — every fleet Python repo sits below that line today, so hand-writing is the correct default there regardless of plugin maturity.

### Q7 — The gazelle_test-based freshness check, per language {#q7}

BZL-ARCH-12 pins `gazelle_test` (from `@gazelle//:def.bzl`, `mode` defaulting to `"diff"`) as the correct, hermetic, Bazel-native "no diff" check, in place of a bare `gazelle -mode=diff` shell invocation. Reading the macro's source directly (`def.bzl`, `v0.54.0`) shows it is built from a genuinely distinct rule pair — `gazelle()` emits an `sh_binary` (a `bazel run` target), `gazelle_test()` emits an `sh_test` (a real `bazel test //:name` target) via its own `_gazelle_test_runner` rule with `mode` locked to `"diff"`. This mechanism is identical across every language — it lives in one file, `@gazelle//:def.bzl`, regardless of which language plugin the underlying `gazelle_binary` embeds.

**The finding that refines BZL-ARCH-12: none of the four ecosystems examined wires `gazelle_test` by default, verified by reading each one's own canonical example directly:**

| Source checked | What it wires | `gazelle_test` present? |
|---|---|---|
| bazel-gazelle's own root `BUILD.bazel` (`v0.54.0`) | `gazelle(...)` × 2 | No |
| rules_python's own [installation_and_usage.md](https://raw.githubusercontent.com/bazel-contrib/rules_python/refs/tags/2.3.3/gazelle/docs/installation_and_usage.md) (`2.3.3`) | `gazelle_binary` + `gazelle(...)` | No |
| gazelle_rust's own [example/BUILD.bazel](https://raw.githubusercontent.com/Calsign/gazelle_rust/main/example/BUILD.bazel) (`main`) | `gazelle(...)` | No |
| aspect-gazelle's `aspect_gazelle()` macro (`runner/def.bzl`, `main`) — the public surface behind `with_check=True` | `aspect_gazelle_runner` → upstream `gazelle()` (twice: `mode="fix"` for the main target, `mode="diff"` for `<name>.check`) | **No — confirmed by source read: `runner/rules.bzl` imports only `gazelle` from `@gazelle//:def.bzl`, never `gazelle_test`; a repo-wide code search for `gazelle_test` across the whole `aspect-build/aspect-gazelle` repo returns exactly one hit, an unrelated internal dev target at `runner/bin/gazelle/BUILD.bazel`** |

**Per-language freshness verification to name in the shipped rule:**

- **Go and Protobuf (baseline):** `bazel test //:gazelle_test`, hand-wired against `@gazelle//:def.bzl`'s `gazelle_test` macro pointed at a `gazelle_binary` with the `go`/`proto` languages. Not present by default; must be added.
- **Python:** the same `bazel test //:gazelle_test` for BUILD-file freshness, **plus** a second, distinct gate for manifest freshness: `bazel test //:gazelle_python_manifest.test` (BZL-PY-26). Two separate targets, two separate failure modes — conflating them is a finding.
- **Rust (gazelle_rust):** `bazel test //:gazelle_test`, hand-wired against `@gazelle_rust//:gazelle_bin` (or a custom `gazelle_binary` with `@gazelle_rust//rust_language`) — the plugin's own example never does this, so the adopter must add it themselves, using literally the same macro as the Go baseline.
- **JS/TS (Aspect):** **`aspect_gazelle(with_check=True)`'s `<name>.check` target is not a `bazel test` target — it is an `sh_binary`.** A genuine `bazel test //:gazelle_test`-shaped gate for JS/TS requires bypassing the `aspect_gazelle()` convenience macro and wiring `gazelle_test` directly against the `aspect_gazelle_prebuilt` binary (or a from-source `gazelle_binary` embedding `@aspect_gazelle_js//:js`). Until that is done, `bazel run //:gazelle.check; echo $?` in a CI script is the only freshness check Aspect's own tooling hands you, and it is excluded from `bazel test //...` and from any CI aggregation that only counts test results.

**Answer.** The `gazelle_test` mechanism BZL-ARCH-12 names is portable and correct across every language plugin examined — it is the same macro regardless of which language's `gazelle_binary` it wraps. But it is *never* supplied by the plugin's own documentation or convenience macros; every one of the four ecosystems checked (including bazel-gazelle's own repo) ships only the `gazelle()`/`sh_binary` half by default. For JS/TS specifically, Aspect's `with_check=True` convenience flag is a false friend: it looks like the freshness gate BZL-ARCH-12 asks for, but it produces a `bazel run` target, not a `bazel test` target, and the shipped rule must say so explicitly rather than let an agent assume `with_check=True` closes the loop.

## AI-agent angle

- **Assuming "Gazelle supports JS/TS" implies a working `ts_project`.** An agent that runs Aspect's Gazelle and sees BUILD files appear will report success; the actual failure surfaces later as a `fail("Required Transpiler Selection")` at load time, or — worse — passes silently if the repo already carries the repo-wide `default_to_tsc_transpiler` flag from an earlier, unrelated migration step. Mechanical check: after any `bazel run //:gazelle` that touches `.ts` sources, run `bazel query 'kind(ts_project, //...)'` and confirm every result resolves at `bazel build`, not just `bazel query`.
- **Treating `with_check=True` as "the CI gate is now wired."** An agent asked to "add the freshness check" for a JS/TS repo using Aspect's plugin will plausibly stop at `with_check=True` and report the job done. It produces a `bazel run` target, not a `bazel test` target — `bazel test //...` will not catch drift. Mechanical check: `bazel query 'kind("sh_test", //:gazelle*)'` — empty output on a repo that believes it has a Gazelle freshness gate is the finding.
- **Citing "0.1.0" as a snapshot fact rather than a live check.** Both `gazelle_rust` and `aspect_gazelle_prebuilt`'s version numbers can change between this read and when an agent acts. Mechanical check: `curl https://bcr.bazel.build/modules/<name>/metadata.json` before asserting a maturity claim tied to a specific version — a hallucinated version number is a common failure mode here because pre-1.0, single-tag projects are exactly the ones training data is thinnest on.
- **Assuming every Gazelle language plugin defaults to the same granularity.** An agent porting a rule of thumb from Go (package-default) to Rust will get the opposite of gazelle_rust's actual default (one target per file). Mechanical check: does the generated rule text name the plugin's actual default mode, sourced from that plugin's own directive docs, rather than assuming parity across languages?
- **Reading a raw `Cargo.lock` grep as proof crate_universe is correctly wired.** `# gazelle:rust_cargo_lockfile` looking present is not evidence of correctness — it is evidence of the mode with the open transitive-dependency bug. Mechanical check: does the generated guidance distinguish `rust_cargo_lockfile` from `rust_lockfile` and prefer the latter, rather than treating "a lockfile directive exists" as sufficient?

## Contested / evolving

- **Whether Aspect will fix the transpiler gap by adding a directive, or by continuing to lean on the repo-wide default flag.** No open issue tracks it as of 2026-09-05 — silence, not a stated non-goal. A future release could add a `# gazelle:js_transpiler` directive at any time; until then, treat the gap as permanent.
- **gazelle_rust's roadmap is a private list, not a public commitment.** Issue #16 is explicitly framed by the maintainer as "non-exhaustive, and I may change it" — items like Rust-protobuf support or dead-target removal could land or could sit indefinitely. Any rule built on "this will be fixed" is CONSIDER at best.
- **The pnpm-12 lockfile bug's resolution shape.** Two competing open PRs (#459, #460) exist for the same underlying issue as of this read — which lands, or whether they merge into one change, is unresolved.

## Not settled

- **Whether Aspect's `js` language plugin correctly resolves imports across an `npm_link_all_packages` boundary when a workspace mixes pnpm and npm** (the exact shape of `creeptd-ng`'s own drift, per `bazel-architecture-monorepo.md`'s fleet evidence) — no dive in this program has run the plugin against a mixed-package-manager fixture. Would settle with a minimal repro mirroring `creeptd-ng`'s actual `pnpm-workspace.yaml`/`package-lock.json` split.
- **Whether gazelle_rust's `resolve`-to-`proc_macro_deps` gap has a documented workaround beyond hand-editing.** The one reference found is a 2023 GitHub comment thread, not the README or the tracking issue — a fuller primary source (a maintainer response on the actual open issue, if one exists) was not located in this pass.
- **Kotlin's Gazelle maturity** (named "still under development" by BZL-ARCH's own dive) was not re-verified here; out of this commission's scope but adjacent to the same `aspect-gazelle` repo and worth a joint refresh next time either is revisited.
