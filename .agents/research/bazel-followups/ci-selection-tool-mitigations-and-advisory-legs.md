## Summary

- **New, measured fact — `--useCquery` closes the repository-rule miss class too, not only `select()`.** A scratch experiment on Bazel 8.7.0 with a `use_repo_rule`-generated external repo shows `--useCquery` alone (no `--fineGrainedHashExternalRepos`) correctly flags a dependent target as impacted when the repo rule's input file changes — because it switches the underlying query from `//...:all-targets` (definition enumeration) to `deps(//...:all-targets)` (a transitive closure that walks real dependency edges into external repos regardless of an allow-list). No source in the existing corpus tests this; it is measured here for the first time.
- **`--fineGrainedHashExternalRepos` also closes it, by a different mechanism** — it unions `@<repo>//...:all-targets` into the query pattern, exposing per-target hashes inside the named repo. Both flags independently fixed the same scratch repro; **default mode (neither flag) missed it completely** — the dependent target's hash was byte-identical before/after, confirming BZL-CI-21's core claim exactly as measured.
- **`--includeTargetType` closes no miss class.** It is a JSON output-schema flag only (`{target: sha256}` → `{target: "type#sha256"}`), unrelated to correctness — BZL-CI-21/26 should not cite it as a mitigation.
- **`--excludeExternalTargets` closes a different, narrower miss class than #134**: it stops `//external:*` synthetic labels (bzlmod-managed) from being handed to `bazel build`/`test`, where they fail (bazel-diff#326) — a usability crash, not a staleness miss. Auto-detected true on Bzlmod, per the tool's own current `--help`.
- **A previously-unflagged mechanism update: PR #322 (bazel-diff, fixing #255) added `bazel mod show_repo`-based diffing of MODULE.bazel-declared repo definitions on Bazel 8.6.0+/9.0.1+**, so a `bazel_dep` version bump is now caught in *default* mode without any flag. This does **not** cover #134's actual miss (content read at *execution* time behind an unchanged label) — confirmed by the scratch experiment, where the external repo's hash was identical before/after in default mode despite the dependent target's real output changing.
- **target-determinator's README does not compare itself to bazel-diff**; the comparison lives in the bazel-diff#134 thread itself, where target-determinator's own maintainer states it was built "particularly to solve" the repository-rule-execution miss class, and confirms the exact #134 repro is caught by their tool.
- **`-before-query-error-behavior` defaults to `ignore-and-build-all`** (not fatal) — a silent-safe-fallback default that matters for the M-F-02 comparison table: a query failure on the "before" revision does not stop the pipeline, it treats everything as potentially affected.
- **target-determinator's cache-key composition, confirmed against the current `--help` text**: home/system `.bazelrc`, environment variables, and host hardware/OS are explicitly *not* in the results-cache key; CLI options that affect `cquery` output (e.g. `-bazel-opts`, `-bazel-startup-opts`) *are*. This matches BZL-CI-22 exactly, no drift found.
- **A red `continue-on-error`/`soft_fail` leg produces essentially zero automated action, confirmed from three independent primary sources.** GitHub's own spec: a job with `continue-on-error: true` reports the *workflow run* as passed even when the job failed — a required check cannot see the failure as a distinct state. Bazel's own `bazelci.py` explicitly *excludes* `soft_fail`-flagged steps from the one automated consumer that exists (`try_update_last_green_commit`'s failure scan) — the only consumption is exclusion. BCR presubmit has no soft-fail concept at all; its nearest analog is a human-typed, audited `@bazel-io skip_check <name>` comment, the opposite shape (explicit, one-time, attributed) from a standing green-passing advisory leg.
- **Bazel's own CI code admits the gap in-repo, first-hand.** `create_check_docs_step()` in `bazelci.py` soft-fails the docs check with the comment "Docs should not fail the post-submit pipeline. TODO: come up with a better detection mechanism." — the Bazel team's own acknowledgment that today's soft-fail has no detection/consumption story.
- **BZL-CI-08 needs a "routed to a named owner" clause.** Recommendation: extend the SHOULD-with-stated-choice text so the required comment must *also* name who or what consumes a red run (an owner, an on-call rotation, a scheduled digest) — "state the choice" alone is not enough per the above evidence.
- **Tinder's and Aspect's numbers reconfirmed against their primary pages with zero drift.** Buildkite's own Tinder webinar page: "1.5 million line codebase with 300+ targets", "40-60 minute CI builds", "93% time savings in P100", "54% improvement over Bazel-diff alone" — matches the frame/consolidation verbatim. Aspect's `monorepo-shared-green` post (Alex Eagle, 2022-08-08): "A large Aspect customer has 2 million SLOC and 500 engineers. They are still on shared green" — matches verbatim; also independently reconfirms "very incorrect" is Aspect's own characterization of bazel-diff, citing #134 directly.
- **Canva's number needs a correction.** The consolidation's Verdict 12 and BZL-CI-03's rationale read "67,145 a11y jobs → 1". The primary page's actual sentence: "A11y tests executed 67145 jobs for 13947 commits. By executing 1 job per commit instead of 1 per page, we could reduce the number of jobs by **5x**." This is a **pre-migration rough estimate of an opportunity**, not a measured before/after pair, and the real multiplier is ~5x (67145/13947 ≈ 4.8), not 67,145-to-1.
- **Lint reach past `.bazelignore` is already settled — cite, don't redo.** [`buildifier-gate-reach-and-generated-starlark.md`](../bazel-measurements/buildifier-gate-reach-and-generated-starlark.md) measured directly on `rules_ocx` at Bazel 8.7.0: `//:buildifier.check`'s `find . -type f` runner has no concept of `.bazelignore` and lints `examples/`/`e2e/` with the **same exit code (123)** as in-graph trees — BZL-CI-12's "measure it" is answered for this fleet's shape; the rule's generic "measure, don't assume" text should stay for other linter/runner shapes, per that file's own scope note.

### Q1 — bazel-diff flag miss-classes, and a scratch experiment

**Question (as commissioned):** *Read the README, the `--useCquery`, `--fineGrainedHashExternalRepos`, `--includeTargetType`, `--excludeExternalTargets` docs and issue #134 plus any issue on repository-rule / module-extension changes being missed. Which miss class does each flag close? Then RUN a scratch experiment on 8.7.0: a workspace with one module extension or repository_rule whose implementation reads a file (or a MODULE.bazel bazel_dep version change), a target depending on the generated repo; compute bazel-diff hashes before and after changing only the repo-rule input / the dependency version, with and without `--fineGrainedHashExternalRepos` and `--useCquery`. Does the dependent target show as changed?*

**Findings**

Current `bazel-diff generate-hashes --help` (v46.1.0, 2026-08-28, both the JVM and the "Experimental Rust candidate" binary — confirmed byte-identical flag surface between the two), fetched via `gh api repos/Tinder/bazel-diff/contents/README.md` (curl to `raw.githubusercontent.com` truncates large files in this sandbox to ~1.7KB with no error signal; `gh api`'s contents endpoint does not):

| Flag | Exact scope (from `--help`/README) | Miss class it closes |
|---|---|---|
| `--useCquery` | "yield more accurate build graph at the cost of slower query execution... only works with Bazel 6.2.0 or above" [(README:generate-hashes)](https://github.com/Tinder/bazel-diff/blob/master/README.md) | Documented: `select()`/configurable-attribute over-approximation ([bazel-diff#170](https://github.com/Tinder/bazel-diff/issues/170), fixed by [#178](https://github.com/Tinder/bazel-diff/pull/178)). **Newly measured here:** also closes the repository-rule/module-extension execution miss of #134, because the default cquery expression is `deps(//...:all-targets)` — a transitive-closure query, not a definition enumeration. |
| `--fineGrainedHashExternalRepos` | "By default, external repos are treated as an opaque blob. If an external repo is specified here, bazel-diff instead computes the hash for individual targets" [(README)](https://github.com/Tinder/bazel-diff/blob/master/README.md) | The named #134 miss, directly — but only for repos on the (must-stay-exhaustive) allow-list. |
| `--includeTargetType` | "Whether include target type in the generated JSON... `{"<target>": "<sha256>"}` → `{"<target>": "<type>#<sha256>"}`" | **None.** Output-schema convenience only; unrelated to any miss class. |
| `--excludeExternalTargets` | Two distinct behaviors per subcommand: on `generate-hashes`, skip querying `//external:all-targets`, auto-true when Bzlmod detected; on `get-impacted-targets`, drop `//external:*` labels from the *output* because "these synthetic labels... are not buildable in bzlmod-only mode... and will fail downstream `bazel build`. See https://github.com/Tinder/bazel-diff/issues/326" [(README, get-impacted-targets)](https://github.com/Tinder/bazel-diff/blob/master/README.md) | A usability/crash miss (unbuildable synthetic label), not #134's staleness miss. |

**Issue #134** ([Tinder/bazel-diff#134](https://github.com/Tinder/bazel-diff/issues/134)) — re-fetched via `gh api repos/Tinder/bazel-diff/issues/134`. Alex Eagle's own diagnosis, verbatim: *"bazel-diff is relying on the **definition** of a repository rule to understand the dependency graph, rather than the result of **executing** the repository rule."* Maintainer's close (`tinder-maxwellelliott`): *"This is expect[ed] behavior. If you want to include these transitive targets I would look into the `-s=<seedFilepaths>` option."* — note the maintainer's own suggested mitigation is `--seed-filepaths` (marks everything affected on any change to named files), a third, blunter tool from the one already in the corpus.

**A second, more targeted fix exists and is new to this corpus:** [PR #322](https://github.com/Tinder/bazel-diff/pull/322) ("Detect impacted targets when MODULE.bazel changes via `mod show_repo`", fixing [#255](https://github.com/Tinder/bazel-diff/issues/255)): *"When running against Bazel 8.6.0+ or 9.0.1+, bazel-diff now queries bzlmod-managed external repo definitions using... `bazel mod show_repo`... Synthetic `//external:<apparent_name>` targets are created from these protos... This fixes the issue where MODULE.bazel changes (e.g. adding a new `bazel_dep` or changing a version) would not produce correct fine-grained diffs."* This is a **different** miss class than #134: it fixes a declared-value change (a version string visible in the module's own resolved definition), not an execution-time content read. The scratch experiment below empirically separates the two.

**Scratch experiment (Bazel 8.7.0, `bazel-diff-rust-linux-amd64` v46.1.0 — a statically-linked native binary from the same release; no `java`/JDK is present on this host, so the JVM-default `bazel-diff_deploy.jar` could not be run; the Rust build is documented as "Experimental" but ships the identical flag surface, confirmed against `--help`).**

Setup: `MODULE.bazel` declares `gen_repo = use_repo_rule("//:repo_rule/defs.bzl", "gen_repo")` then instantiates `gen_repo(name = "genrepo", input_file = "//input:data.txt")`. The rule's implementation `rctx.read()`s the input file and writes a `genrule` into the generated repo's `BUILD.bazel`. `//:consumer` is a `genrule` with `srcs = ["@genrepo//:out"]`. Changing `input/data.txt`'s *content* (the label itself never changes) is exactly #134's shape: a static definition unaffected, an execution result affected.

| Mode | `//external:genrepo` (opaque node) hash | Dependent target hash | `//:consumer` flagged impacted? |
|---|---|---|---|
| default (no flags) | **identical** before/after | **identical** before/after | **No** — only `//input:data.txt` itself is reported |
| `--fineGrainedHashExternalRepos=@genrepo` | n/a (bypassed; `@genrepo//:out` hashed directly) | changed | **Yes** — `//:consumer`, `@genrepo//:out` both listed |
| `--useCquery=true` | present, unchanged (inert) | `@@+_repo_rules+genrepo//:out` hash **changed** | **Yes** — `@@//:consumer`, `@@+_repo_rules+genrepo//:out` both listed |
| both flags together | — | changed | **Yes** — same set as cquery-only |

Idempotency check: re-running `--useCquery=true` with no source change reproduced byte-identical hashes (ruled out flakiness/spurious diffs). Verbose trace (`-v`) confirms the mechanism directly: `--useCquery` issues `[Info] Executing Query: deps(//...:all-targets)` via `cquery --transitions=lite --output streamed_proto`, versus plain mode's `'//external:all-targets' + '//...:all-targets'` — the `deps()` wrapper is what walks the real `srcs = ["@genrepo//:out"]` edge into the external repo, independent of any allow-list. Two flag-syntax gotchas hit during the run, worth naming for anyone reproducing: `--fineGrainedHashExternalRepos` must be given the label form with a leading `@` (`@genrepo`, not the bare apparent name or the canonical `+_repo_rules+genrepo` — both produced `ERROR: invalid package name '...//' package names may not end with '/'`, a query built as `<value>//...:all-targets` without inserting the `@`); the Rust CLI's boolean flags need `=true` (`--useCquery true` as two tokens is swallowed as the positional `OUTPUT_PATH` argument by clap).

Scratch artifacts (disposable, `bazelisk shutdown` run against the isolated `--output_user_root`): `/tmp/claude-1000/-home-mherwig-dev-grimoire-lore/946b693c-7b64-4917-9d73-8efea67c92ab/scratchpad/followup/bazel-diff-repo-rule-experiment/`.

**Answer.** Each flag closes a distinct, nameable miss: `--fineGrainedHashExternalRepos` closes #134 directly for allow-listed repos; `--useCquery` closes both the documented `select()` over-approximation *and*, newly measured here, #134's repository-rule/module-extension execution miss — for any external target reachable via a real dependency edge from an in-repo target, because it swaps the query for a transitive `deps()` cquery, not because of anything allow-list-shaped. `--includeTargetType` closes nothing; `--excludeExternalTargets` closes an unrelated unbuildable-label crash (#326). A newer, third mechanism (`mod show_repo` diffing, PR #322/#255, live on Bazel 8.6.0+/9.0.1+) now also closes a *different* miss — a declared `bazel_dep` version change — in **default** mode with no flag, but does not touch execution-time content reads, confirmed by this experiment's default-mode row showing zero change to the opaque node's hash. At Bazel 8.7.0 / bazel-diff v46.1.0 (2026-08-28), the corpus's characterization of default mode as "blind" to #134's exact shape is still exactly correct; but two independent flags fix it, and the previously-untested claim that `--useCquery` doesn't touch this miss class is now shown false.

### Q2 — target-determinator vs bazel-diff

**Question (as commissioned):** *README, its handling of MODULE.bazel and repository changes, `--before-query-error-behavior`, its "changes in the toolchain / .bazelrc / startup flags" handling, and how it compares to bazel-diff on the same miss classes. Table: miss class | bazel-diff (flags) | target-determinator | whole-repo green.*

**Findings**

Full README fetched via `gh api repos/bazel-contrib/target-determinator/contents/README.md` (8,939 bytes; the earlier `curl` to `raw.githubusercontent.com` again silently truncated to 1,751 bytes — same sandbox behavior as Q1, worth flagging once for future dives: **use `gh api .../contents/<path> | base64 -d`, not raw-host `curl`, for any GitHub file over ~2KB in this environment**).

- **MODULE.bazel / repository-rule handling**: the README's flag reference does not describe the internal mechanism (it is closed-source relative to its own docs — the comparison lives in the issue tracker, not the README). What it does state, from the tool's maintainer directly in [bazel-diff#134](https://github.com/Tinder/bazel-diff/issues/134) (`illicitonion`, target-determinator co-maintainer): *"this style of issue was one of our motivations for putting together... target-determinator - we put in quite a bit of care to follow deps through repository rules to all affecting files. I manually tested out the supplied repro, and that implementation detected the change properly."* This is the primary, first-hand comparison point the question asks for: target-determinator was purpose-built against exactly this miss class, and its maintainer confirms (informally, not as a published benchmark) that it catches the #134 repro bazel-diff's default mode misses.
- **`--before-query-error-behavior`**: `"How to behave if the 'before' revision query fails. Accepted values: fatal,ignore-and-build-all (default \"ignore-and-build-all\")"` [(README flag reference)](https://github.com/bazel-contrib/target-determinator/blob/main/README.md). Default is the **safe-fallback** direction — a query failure does not halt the pipeline, it marks everything as potentially affected (build-all), which is the conservative choice but means a broken "before" query silently degrades to "no selection happened" rather than erroring loudly.
- **Toolchain / `.bazelrc` / startup-flag handling**: from the `-cache-dir` flag doc, verbatim: *"Cache directory to avoid existing re-computations. Note: home- and system- bazelrc files, environment variables, and host hardware/OS are not included in the results cache key. Use --nocache_results if necessary."* CLI options passed via `-bazel-opts`/`-bazel-startup-opts` **are** part of the cache key (they're explicit invocation parameters, not ambient environment). The tool documents the resulting risk directly for environment variables: *"If an environment variable affected Bazel's query output... the cached result reflects the old environment, while the 'after' result reflects the new one"* — a spurious-diff risk, not a missed-diff risk (it errs toward over-reporting, the opposite direction from bazel-diff's #134 miss). This matches BZL-CI-22 verbatim with no drift found.
- **`-filter-incompatible-targets`**: `"Whether to filter out incompatible targets from the candidate set of affected targets. (default true)"` — matches BZL-CI-25's characterization exactly.
- **Bazel version floor**: `"Target Determinator currently supports Bazel 4.0.0 up to and including the latest LTS release."` — matches the consolidation's stated floor with no drift.
- **Direct comparison to bazel-diff in the README itself**: none found. The README is self-contained and does not name bazel-diff anywhere in its flag reference or design sections that were fetched; the comparison exists only in the shared issue thread and in Aspect's blog (which calls target-determinator "very slow", citing its own [issue #3](https://github.com/bazel-contrib/target-determinator/issues/3) — a claim from a competing vendor's blog, not the tool's own docs, so treat with the same argued-source caution the corpus already applies to "very incorrect").

**Miss-class table**

| Miss class | bazel-diff (flags) | target-determinator | Whole-repo green |
|---|---|---|---|
| Repository-rule/module-extension execution reads unchanged label, changed content (#134) | Default: **miss**. `--fineGrainedHashExternalRepos=@<repo>` (allow-listed) or `--useCquery` (measured here, Q1): **catches** | Purpose-built for this ([maintainer's own words](https://github.com/Tinder/bazel-diff/issues/134#issuecomment-1141118217) in #134); **catches** by design, no flag | Catches trivially — nothing is skipped |
| `select()`/configurable-attribute over-approximation | Default query mode: over-approximates (many false positives, not false negatives). `--useCquery`: resolves it | cquery-based throughout; not a distinct failure mode for it | Catches trivially |
| `bazel_dep` version bump, declared in MODULE.bazel | Default (Bazel 8.6.0+/9.0.1+, via PR #322/#255's `mod show_repo` diffing): **catches**, no flag needed | Catches (cquery walks the resolved graph) | Catches trivially |
| Stale results-cache across a `.bazelrc`/env/host change | N/A — bazel-diff has no persistent results cache in the CLI path used here (the `serve` mode has a separate cache-key story, out of scope) | **Named risk**: none of the three enter the cache key; `--nocache_results` is the documented escape hatch (BZL-CI-22) | N/A — no cache to go stale |
| Query failure on the "before" revision | Not documented as a distinct mode | `-before-query-error-behavior=ignore-and-build-all` (default): silently degrades to build-all, the safe direction | N/A |
| Non-hermetic target reading undeclared workspace state (e.g. a repo-wide linter) | `--alwaysAffectedTags` (opt-in, per-tag) | Not found in the fetched README as a named flag | Catches trivially |

**Answer.** target-determinator does not publish a self-comparison to bazel-diff; the comparison that exists is a first-hand claim from its own maintainer inside the bazel-diff issue thread, not a benchmark. Confirmed at current versions (bazel-diff v46.1.0 2026-08-28, target-determinator v0.34.0 2026-06-19): the two tools converge on catching #134's class (bazel-diff needs a flag or the newer `mod show_repo` path for the narrower version-bump case; target-determinator claims to catch it by design), and target-determinator's distinct risk is a stale results cache across an environment change it cannot see, mitigated by `--nocache_results`, while bazel-diff's distinct risk is exactly the flag-dependent miss classes in the table above. `-before-query-error-behavior`'s default is the corpus's first documented instance of a selection tool choosing "degrade to build-all" over "fail loud" on its own internal error — worth naming in BZL-CI-25's reading heuristic alongside the two flags already there.

### Q3 — does a red advisory leg produce action?

**Question (as commissioned):** *Find any measured or first-hand account of whether a red continue-on-error CI leg produces action... Decide whether BZL-CI-08's advisory option needs a "routed to a named owner" clause, and propose the row text.*

**Findings**

**GitHub's own spec** (`content/actions/reference/workflows-and-actions/workflow-syntax.md`, fetched via `gh api repos/github/docs/contents/...`, current as of this fetch):

> `jobs.<job_id>.steps[*].continue-on-error`: "Prevents a job from failing when a step fails. Set to `true` to allow a job to pass when this step fails."
> `jobs.<job_id>.continue-on-error`: "Prevents a workflow run from failing when a job fails. Set to `true` to allow a workflow run to pass when this job fails."

Read literally: the job/workflow-run **conclusion is "success"** when the flagged step/job fails — not a distinct "neutral" or "warning" status a branch-protection rule could special-case. A required check watching that job sees a pass. This is the direct answer to "does a red leg produce action" at the platform-mechanism level: **no distinct state exists for branch protection to act on.**

**Bazel's own CI (`bazelbuild/continuous-integration`, `buildkite/bazelci.py`, fetched in full via `gh api`)**. Two exhibits:

1. `try_update_last_green_commit()`'s failure scan, verbatim: `# Find any failing steps other than Buildifier and steps with soft_fail enabled then "try update last green".` followed by `not job.get("soft_failed")` in the `has_failed()` predicate ([bazelci.py:4249-4256](https://github.com/bazelbuild/continuous-integration/blob/master/buildkite/bazelci.py)). This is the **only** automated consumer of build-step results found in the file (`grep -i "slack\|notify\|digest\|dashboard"` across the whole file returns nothing tied to `soft_fail`), and its treatment of a soft-failed step is to **exclude it** from the check — i.e. a red soft-fail leg is invisible to the one piece of automation that reads job outcomes at all.
2. `create_check_docs_step()`, the current, live example: `enable_soft_fail=os.getenv("BUILDKITE_PIPELINE_SLUG")=="bazel-bazel"`, with the adjacent comment *"Docs should not fail the post-submit pipeline. TODO: come up with a better detection mechanism."* ([bazelci.py:3552-3554](https://github.com/bazelbuild/continuous-integration/blob/master/buildkite/bazelci.py)) — the Bazel team's own, first-hand, in-repo admission that today's soft-fail on this leg has no detection/consumption story.

**BCR presubmit** (`bazel-central-registry/docs/README.md`, fetched in full via `gh api`): has **no soft-fail concept at all**. The closest analog is a human-typed, audited skip: *"Comment `@bazel-io skip_check unstable_url` to skip this optional check"* / *"comment `@bazel-io skip_check compatibility_level`... The bot records each skip by applying the corresponding label to the PR."* This is structurally the opposite of a standing advisory CI leg: it is one-time, explicit, attributed to a person, and leaves an audit trail — not a channel that silently accumulates red runs nobody looks at.

**Practitioner account — Alex Eagle, "Keeping main green in a monorepo"** ([aspect.build/blog/keeping-main-green](https://aspect.build/blog/keeping-main-green), 2024-06-21), the same author already cited in this family for the bazel-diff "very incorrect" characterization. On unowned red CI generally: *"'hey is anyone looking at the red CI?'"* is named as the recurring failure mode, with *"there is often no clear ownership"* as the diagnosis, and the post's own fix is an assigned on-call rotation (*"Someone is quite literally on-call for reverting broken commits from `main`"*) — the same shape of fix this dive is proposing for advisory legs. Not a soft-fail-specific measurement, but a first-hand, named-author account of the identical failure mode (a red signal nobody is assigned to look at) directly transferable to an advisory leg, which is a strictly weaker signal (not even blocking, so has less pull on anyone's attention than an unowned red required check already gets).

No source found (measured or first-hand) reports the opposite — a red advisory/soft-fail leg reliably producing action without an assigned consumer.

**Answer.** Across four independent primary sources — GitHub's own status-conclusion semantics, Bazel's own CI source code (both its one automated consumer and its own un-fixed TODO), BCR's presubmit docs (which solve the same problem with an attributed one-time skip instead of a standing leg), and a named practitioner's first-hand account of the identical "who's watching this" gap — the corpus now has convergent evidence that **an advisory leg with no named consumer produces no action.** BZL-CI-08's advisory option needs the ownership clause. Proposed row text for the SHOULD-with-stated-choice clause:

> "...an Active-LTS-as-advisory choice is acceptable **only with a comment stating the choice and naming who or what consumes a red run** — an owner, an on-call rotation, or a scheduled digest destination. A stated choice with no named consumer is measured to be equivalent to no leg at all: GitHub's own `continue-on-error` reports the job/workflow as passed with no distinct state for anything to act on, and Bazel's own CI excludes `soft_fail` steps from its one automated result-consumer outright."

Verification clause to add: "...EMPTY **plus no comment naming both the choice and a consumer** = finding."

### Q4 — cross-checking the three threshold sources

**Question (as commissioned):** *Cross-check the three named threshold sources for decision 3 (Tinder ~300 targets / 40-60 min, Canva, Aspect's 2M SLOC anchor) against their primary pages once more and state the threshold row text the reviser should carry, with the exact citations.*

**Findings**

**Tinder — [Buildkite's own webinar page](https://buildkite.com/resources/webinars/how-tinder-built-and-open-sourced-bazel-diff-to-transform-their-ci-cd-at-scale/)** (re-fetched directly): *"1.5 million line codebase with 300+ targets"*, *"40-60 minute CI builds"*, *"93% time savings in P100 scenarios"*, *"54% improvement over Bazel-diff alone"* (comparing bazel-diff+Buildkite-dynamic-pipelines against bazel-diff standalone), speakers Maxwell Elliott and Connor Wybranowski. **Zero drift** from the frame's Correction 9 / wave-3b Correction 1 text — every number matches verbatim.

**Aspect — [`monorepo-shared-green`](https://aspect.build/blog/monorepo-shared-green)** (Alex Eagle, 2022-08-08, re-fetched directly): *"A large Aspect customer has 2 million SLOC and 500 engineers. Also independently reconfirms the corpus's own Verdict 3 correction: "very incorrect" is this post's own characterization of bazel-diff, citing #134 directly — not a bazel-diff README concession. **Zero drift.**

**Canva — [`Faster CI builds at Canva`](https://www.canva.dev/blog/engineering/faster-ci-builds-at-canva/)** (Marco Lacava & Arpit Sharma, 2024-07-30, re-fetched as raw HTML — the page is a client-rendered app whose text is inline in the initial HTML payload, confirmed by direct string search, so no truncation risk here). By executing 1 job per commit instead of 1 per page, we could reduce the number of jobs by 5x."* — **this contradicts the consolidation.** BZL-CI-03's rationale ("Canva shipped three hermeticity fixes first, collapsing a 67,145-job-per-commit a11y suite to 1") and Verdict 12 ("67,145 a11y jobs → 1") both misstate this as a 67,145-to-1 collapse; the primary source's actual figure is an aggregate 67,145 jobs across 13,947 commits (≈4.8 jobs/commit average) projected to fall to 1 job/commit — a **~5x** reduction, stated as an estimate justifying the hermeticity work, not a measured result of it.

**Answer.** Two of the three sources reconfirm with zero drift and need no change: the Tinder threshold (~300 targets / 40-60 min whole-repo wall-clock, 1.5M lines) and the Aspect anchor (2M SLOC / 500 engineers still viable on shared-green, arguing against a universal target-count trigger) both carry forward unchanged, with the citations above. The Canva figure needs correction wherever it is used as evidence: replace "67,145 → 1" with "an aggregate 67,145 jobs across 13,947 commits, projected (not measured) to fall ~5x to one job per commit" and mark it a pre-migration estimate, not a first-party *measured* result — this changes Verdict 12's "first-party measured numbers" framing for this specific figure (the 680K-minutes/month and cost figures on the same page carry the identical "rough estimates" framing and should get the same caveat if cited elsewhere). The threshold row text BZL-CI-01 should carry is unchanged by this dive: **~40 minutes median whole-repo CI wall-clock as the lead signal, ~300 rule targets as the tripwire, sourced to the Buildkite/Tinder webinar page above, with Aspect's 2M-SLOC/500-engineer shared-green anchor cited as the reason no universal target-count ceiling exists in the corpus.**

## AI-agent angle

An agent reading bazel-diff's flag docs in isolation will reach for `--fineGrainedHashExternalRepos` for *any* "external repo changed but wasn't flagged" complaint and stop there, because that flag's description names the miss class explicitly while `--useCquery`'s description ("more accurate build graph") reads as a generic quality knob. The smallest mechanical check that catches this: before recommending a fine-grained allow-list, run `bazel-diff -v generate-hashes ...` (or grep bazel-diff's own verbose log) and read the literal `Executing Query:` line — if it already reads `deps(//...:all-targets)` (i.e. `--useCquery` is set), the repository-rule miss class this dive found may already be closed, and adding an allow-list is redundant maintenance surface, not a fix. Separately, an agent citing Canva's a11y numbers should be made to re-fetch the sentence itself before repeating "67,145 → 1" — this dive is the second time in this program a specific number from that exact family of sources (Tinder's 93%, now Canva's job count) needed a primary-page re-read to catch a magnitude/framing error; the mechanical habit worth encoding is: **any number crossing from a blog into a rule's rationale gets the surrounding sentence quoted verbatim in the citation, not paraphrased**, so drift is visible on the next re-read without re-fetching.

## Contested / evolving

- Whether `--useCquery` closing the repository-rule miss class (measured here on one small repro) generalizes to real fleets with deep `pip`/`npm`/Maven dependency graphs is not established — the mechanism (transitive `deps()` walking a real edge) should generalize, but query cost and correctness at tens-of-thousands-of-targets scale (where cquery's per-revision cost is the stated reason target-determinator exists) is untested here.
- Whether GitHub's Actions UI shows any distinct visual signal (an orange/warning icon in the run summary) for a `continue-on-error` failure, short of the check-run conclusion itself, was not confirmed from primary docs in this dive (the workflow-syntax page gives the conclusion semantics but not a UI screenshot/description) — immaterial to the branch-protection question this dive answers, but a reader wanting the exact dashboard behavior should treat that detail as unconfirmed.

## Not settled

- **Cross-tool benchmark of `--useCquery` vs `--fineGrainedHashExternalRepos` at scale.** This dive's scratch repro is a single small target; a follow-up on a synthetic repo with hundreds of targets and a real `pip`/`rules_jvm_external`-shaped extension would settle whether cquery-mode's per-invocation cost is acceptable as a *default* mitigation for the repo-rule miss class, rather than an allow-list.
- **Whether the `mod show_repo` default-mode fix (PR #322) has any of its own gaps** (e.g. does it handle a module extension whose *tag* changes rather than the `bazel_dep` version itself?) — not tested here; the PR body's own scope is "MODULE.bazel changes... adding a new bazel_dep or changing a version," which may not cover every module-extension-introduced dependency shape.
- **Whether an assigned owner/on-call for an advisory CI leg is actually acted on** (as opposed to a required check's red state) — no source found measures this directly; the recommendation in Q3 generalizes from the identical failure mode observed for *unowned required* red CI, one inferential step removed from advisory legs specifically.
