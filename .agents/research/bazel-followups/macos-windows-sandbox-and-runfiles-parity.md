## Summary

- **darwin-sandbox genuinely blocks the network when `--sandbox_default_allow_network=false`.** Its `sandbox-exec` profile writer emits `(deny network*)` unless network is allowed, then carves out localhost — this is a real, working mechanism, not "roughly the same" hand-waving ([DarwinSandboxedSpawnRunner.java:283-287](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/DarwinSandboxedSpawnRunner.java#L283-L287)).
- **The localhost carve-out is not parity with Linux.** macOS has no network namespace, so "localhost" inside the darwin-sandbox is the *same* loopback interface the host uses — a sandboxed process can be blocked from binding a port another process already owns outside the sandbox, unlike on Linux. This is an open, unfixed bug: [bazelbuild/bazel#11325](https://github.com/bazelbuild/bazel/issues/11325).
- **darwin-sandbox silently falls back to `processwrapper-sandbox` only when nested** — i.e. when Bazel itself is already running inside another `sandbox-exec` jail. Outside that case (ordinary macOS CI runners), darwin-sandbox is the strategy actually used and it does enforce the flag.
- **A Windows sandbox strategy exists in Bazel's source (`windows-sandbox`, BuildXL-based) but is vaporware for practical purposes**: off by default (`--experimental_use_windows_sandbox` defaults `false`), needs an external `BazelSandbox.exe` binary Bazel does not ship, and is never mentioned on `bazel.build/docs/sandboxing`. "Windows has no sandbox" is correct in practice, not in the source tree.
- **`--enable_runfiles` defaults to `"auto"` (off on Windows, on elsewhere) identically on Bazel 8.7.0 and 9.2.0** — byte-identical option definition, no version split ([CoreOptions.java](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/analysis/config/CoreOptions.java)).
- **Windows runfiles trees are not one mechanism.** Directory-level entries become NTFS **junctions** unconditionally (no privilege needed); file-level entries become real **symlinks** only when `--windows_enable_symlinks` is set (needs Dev Mode or admin), otherwise they silently **copy** ([WindowsFileSystem.java:94-105](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/windows/WindowsFileSystem.java#L94-L105)).
- **rules_js 3.4.1's exact documented failure — empty coverage plus `code coverage requires a runfiles tree` — is the only ruleset-confirmed instance of M-E-13**, verbatim-matched in its 3.4.1 troubleshooting doc.
- **rules_rust 0.74.0 does not merely omit Windows from its coverage doc — it disclaims Windows support fleet-wide**: *"We do not have sufficient maintainer expertise to support Windows. Most things probably work, but we have had to disable many tests in CI"* ([index.md](https://github.com/bazelbuild/rules_rust/blob/0.74.0/docs/src/index.md)). Treat `rust_test` coverage-on-Windows as unverified-by-upstream, not merely untested by this corpus.
- **rules_python already solved the M-E-13 problem for itself, ahead of the flag.** Since 1.9.0 (2026-02-21), `py_binary`/`py_test` force `--enable_runfiles=true` via a rule-level transition on Windows regardless of the global default — a repo can override it back off, but out of the box a Windows `py_test` gets a runfiles tree without anyone setting `--enable_runfiles` in `.bazelrc`. The 1.9.0 changelog also warns this override will "soon become **required**."
- **The rules_python changelog also confirms the two other version facts the commission asked about**: 1.5.0 (2025-06-11) force-sets `--bootstrap_impl=system_python` on Windows; 2.0.0 (2026-04-09) makes venv-based binaries the default everywhere Bazel 8+ runs, and switches Windows from zip-and-extract to a symlink-based runfiles tree by default.
- **BZL-HERM-27's cited evidence (`bazelbuild/bazel#11482`) doesn't actually support its own claim.** The issue's own root-cause discussion is a DLL basename collision, not a `SymlinkAction`-falls-back-to-copy defect; the real, better-sourced justification is a maintainer comment on a different (unlinked) 2020 thread: Bazel "did many improvements" on long paths but "the MSVC compiler still doesn't support long path," hence the short-`--output_user_root` mitigation. The rule's *conclusion* survives; its citation should be replaced.
- **Bazel's own documented short-path recipe is `startup --output_user_root=C:/tmp`**, not an arbitrary short string — worth stating exactly, since an agent inventing its own path (e.g. `C:\b`) loses nothing functionally but drifts from the one recipe Bazel actually publishes.
- **`--incompatible_strict_action_env`'s "static PATH" is OS-shaped, not one fixed string.** Non-Windows gets the literal `/bin:/usr/bin:/usr/local/bin`; Windows gets the MSYS root (parsed from the resolved `bash.exe`) plus `C:\Windows;C:\Windows\System32;...\WindowsPowerShell\v1.0` — computed identically on 8.7.0 and 9.2.0. A generated explanation of the flag that states one fixed string for both OSes is wrong for whichever OS it didn't name.
- **rules_ocx's Windows CI leg needs no `BAZEL_SH` because GitHub's own `windows-latest` image happens to preinstall MSYS2 at exactly the path Bazel's fallback hardcodes** (`C:\msys64`, matching `SHELL_EXECUTABLE.get(OS.WINDOWS) == "c:/msys64/usr/bin/bash.exe"`) — a coincidence of the runner image, not a Bazel guarantee, and not portable to a self-hosted Windows runner.
- **rules_ocx sets zero of `--sandbox_default_allow_network`, `strict_action_env`, or `--output_user_root` anywhere** — its Windows and macOS legs are exactly as exposed as BZL-HERM-02/-27 already say a fleet with no such flags is.

## Answers

<a id="q1"></a>
### Q1 — darwin-sandbox network

> Read bazel.build/docs/sandboxing, the Bazel source for DarwinSandboxedSpawnRunner (sandbox-exec profile generation: what it denies — network? file writes outside the sandbox? reads of the host?), and the issues on `--sandbox_default_allow_network` on macOS. Does the darwin sandbox actually block network when the flag is false, or does macOS silently fall into the processwrapper class for this control? Which Bazel version, and what `--experimental_sandbox_*` flags apply on macOS only.

**Findings**

`bazel.build/docs/sandboxing` documents darwin-sandbox only in prose: it "uses Apple's `sandbox-exec` tool to achieve roughly the same as the Linux sandbox," and separately that "you cannot run `sandbox-exec` inside a process that's already being sandboxed" — when that happens Bazel falls back to `processwrapper-sandbox` ([bazel.build/docs/sandboxing](https://bazel.build/docs/sandboxing)). The page never enumerates what "roughly the same" excludes, which is exactly the gap the sibling hermeticity dive flagged as unconfirmed (`sandbox-environment-and-toolchain-leakage.md:401`).

Reading the actual profile generator, `DarwinSandboxedSpawnRunner.writeConfig` (unchanged in shape across 8.7.0 and 9.2.0 — verified both tags), settles it directly. It emits an Apple sandbox-exec profile:

```
(version 1)
(debug deny)
(allow default)
(allow process-exec (with no-sandbox) (literal "/bin/ps"))

; only emitted when network is NOT allowed for this spawn:
(deny network*)
(allow network-inbound (local ip "localhost:*"))
(allow network* (remote ip "localhost:*"))
(allow network* (remote unix-socket))

(deny file-write*)
(allow file-write*
    (subpath "<each writable dir>"))

; only emitted if inaccessiblePaths is non-empty (rare — sandbox_block_path):
(deny file-read*
    (subpath "<each blocked path>"))
```
([DarwinSandboxedSpawnRunner.java:279-308](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/DarwinSandboxedSpawnRunner.java#L279-L308))

Three load-bearing facts fall out of this:

1. **`(allow default)` is the first rule.** Apple sandbox profiles are last-rule-wins, so darwin-sandbox starts from "everything is allowed" and layers specific denials on top — the *opposite* posture from linux-sandbox's mount-based default-deny. Reads of the host filesystem are **not** denied by default; only `file-write*` and (conditionally) `network*` are. The "roughly the same as Linux" phrasing is doing real work here: darwin-sandbox isolates writes and (optionally) network, not reads. Host-read isolation on macOS relies on the same "original sin" read-only-mount idiom being absent — there is no equivalent to linux-sandbox's whole-filesystem remount.
2. **Network denial is real and driven directly by the flag.** `allowNetwork` is computed per-spawn as `helpers.shouldAllowNetwork(...) || Spawns.requiresNetwork(spawn, getSandboxOptions().defaultSandboxAllowNetwork)` ([DarwinSandboxedSpawnRunner.java:235-237](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/DarwinSandboxedSpawnRunner.java#L235-L237)), and `Spawns.requiresNetwork` falls through to `defaultSandboxDisallowNetwork` (i.e. the *inverse* of `--sandbox_default_allow_network`) unless the action is tagged `block-network` or `requires-network` ([Spawns.java:79-88](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/actions/Spawns.java#L79-L88)). `--sandbox_default_allow_network` itself defaults `true` on both majors, unchanged since it was promoted from `--experimental_sandbox_default_allow_network` ([SandboxOptions.java:291-300](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/SandboxOptions.java#L291-L300)) — so **the default-allow finding is identical on macOS to Linux**; setting the flag false genuinely flips darwin-sandbox to deny.
3. **Fallback to processwrapper-sandbox is conditional, not silent-by-default.** `DarwinSandboxedSpawnRunner.isSupported()` returns `false` (routing to `processwrapper-sandbox`) only when `OS.getCurrent() != OS.DARWIN`, no `process-wrapper` binary is found, or `computeIsSupported()`'s probe invocation of `sandbox-exec -p "(version 1)(allow default)" /usr/bin/true` fails ([DarwinSandboxedSpawnRunner.java:62-85](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/DarwinSandboxedSpawnRunner.java#L62-L85)) — which happens when Bazel is already nested inside another sandbox, per the docs page above. An ordinary macOS runner (GitHub-hosted `macos-latest` included — it is not itself sandbox-exec-jailed) is not in that state, so darwin-sandbox is what actually runs, and it does enforce the flag. The commission's binary framing ("does it block, or does macOS silently use processwrapper") has a third answer: it blocks, *except* in the specific nested-sandbox case, which is rare and detectable (the build fails outright if `sandbox-exec` cannot be invoked at all, it does not quietly downgrade mid-build).

The network story is not fully parity with Linux, though — and this is the part neither `bazel.build/docs/sandboxing` nor either wave-2 dive had. The localhost carve-out (`(allow network-inbound (local ip "localhost:*"))` etc.) exists because an earlier, broken version of this exact profile let *all* network through by accident — [bazelbuild/bazel#10068](https://github.com/bazelbuild/bazel/issues/10068) (filed and fixed in 2019) shows a `curl -I http://www.google.com` succeeding under a `block-network`-tagged genrule, root-caused to an overly permissive sandbox-exec grammar (`(allow network* (local ip "localhost:*"))` — no `tcp`/`udp` qualifier — plus an unrestricted `(allow network* (remote unix-socket))`), fixed by tightening to the asymmetric inbound/outbound shape shown above. That fix landed; the *shape* it fixed is exactly what ships in 8.7.0/9.2.0 today, confirming the mechanism works as intended for outright network denial. What remains genuinely unparallel is [bazelbuild/bazel#11325](https://github.com/bazelbuild/bazel/issues/11325) (still **open**): because macOS has no network-namespace equivalent, "localhost" inside darwin-sandbox is literally the host's loopback interface — a sandboxed process cannot bind a port some other, unsandboxed process already has open, whereas on Linux the sandboxed network namespace's loopback is independent and binding never conflicts. A test suite that starts its own local server and expects Linux-style isolation from anything else on the host can flake or fail on macOS for reasons that have nothing to do with `--sandbox_default_allow_network`.

On `--experimental_sandbox_*` flags scoped to macOS: **there are none as of 8.7.0/9.2.0.** Grepping the full `SandboxOptions.java` option list (29 `@Option` declarations) turns up `--experimental_use_hermetic_linux_sandbox` and `--incompatible_sandbox_hermetic_tmp`, both explicitly Linux-only by name and doc text; `--experimental_use_windows_sandbox`/`--experimental_windows_sandbox_path`, Windows-only (Q2); `--experimental_enable_docker_sandbox` and its `--experimental_docker_*` siblings, cross-platform via Docker; and `--sandbox_default_allow_network`, `--sandbox_fake_hostname`, `--sandbox_fake_username`, `--sandbox_tmpfs_path`, `--sandbox_writable_path`, `--sandbox_add_mount_pair`, `--sandbox_block_path`, `--sandbox_debug`, `--reuse_sandbox_directories` — all shared across linux-sandbox and darwin-sandbox with no OS-gated variant. The macOS-only surface area lives outside `SandboxOptions.java` entirely, inside `DarwinSandboxedSpawnRunner` itself: `DARWIN_USER_TEMP_DIR`/`DARWIN_USER_CACHE_DIR` client-env passthrough, and hardcoded always-writable paths (`~/Library/Caches`, `~/Library/Logs`, `~/Library/Developer` — the last one there specifically "because certain Xcode tools expect to be able to write to this path") ([DarwinSandboxedSpawnRunner.java:153-181](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/DarwinSandboxedSpawnRunner.java#L153-L181)).

**Answer.** As of Bazel 8.7.0 and 9.2.0 (source identical across both), darwin-sandbox does actually block the network via a working `sandbox-exec` profile when `--sandbox_default_allow_network=false` — this is a real, direct mechanism, not an illusion or a silent no-op, and BZL-HERM-02's MUST severity for macOS is fully justified. The "roughly the same as Linux" gap that neither the frame nor the wave-2 dive could close is real but narrower than "does it work at all": darwin-sandbox does not isolate file *reads* by default the way linux-sandbox's whole-filesystem remount does (both start from `(allow default)`/read-only-elsewhere respectively, but darwin's default is "allow", not "deny"), and its localhost network carve-out shares the host's actual loopback interface rather than a private one, an open parity gap tracked by #11325. The only condition under which darwin-sandbox silently does not run at all is nesting inside another `sandbox-exec` process, in which case Bazel falls back to `processwrapper-sandbox` (and the fallback is loud — it changes which strategy attaches to the build, not a silent downgrade of enforcement within darwin-sandbox itself). No macOS-only `--experimental_sandbox_*` flag exists in `SandboxOptions.java` today; macOS-specific behavior is hardcoded, not flag-gated.

### Q2 — Windows: sandbox, runfiles, coverage

> No sandbox at all — confirm from source and docs which spawn strategies exist on Windows. Runfiles manifests vs trees (`--enable_runfiles` default per Bazel version on Windows, `--windows_enable_symlinks`, developer mode), junctions vs symlinks, MAX_PATH and `--output_user_root`, what rules_js, rules_python and rules_rust each document for Windows runfiles and coverage. Does `bazel coverage` on Windows report empty coverage without `--enable_runfiles` for `rust_test` and `py_test` as rules_js documents for JS?

**Spawn strategies available on Windows.** `bazel.build/docs/sandboxing` documents exactly four strategies (`linux-sandbox`, `darwin-sandbox`, `processwrapper-sandbox`, `local`/standalone, plus `worker`) and never mentions Windows once. `SandboxModule.java`'s strategy-registration logic gates `linux-sandbox` and `darwin-sandbox` on `OS.getCurrent()`, so neither is even considered on Windows. `processwrapper-sandbox` is the one the docs call "should work on any POSIX system out of the box" — but the module's own code, not the prose, is what actually decides Windows: `SandboxModule.java` also wires up a **fourth, undocumented strategy, `windows-sandbox`**, gated behind `WindowsSandboxUtil.isAvailable(binary)` where `binary` defaults to `experimental_windows_sandbox_path = "BazelSandbox.exe"` ([SandboxOptions.java:200-219](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/SandboxOptions.java#L200-L219), [SandboxModule.java:280-381](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/SandboxModule.java#L280-L381)). `WindowsSandboxedSpawnRunner`'s own class doc says it is a "Spawn runner that uses BuildXL Sandbox APIs to execute a local subprocess" ([WindowsSandboxedSpawnRunner.java:31-32](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/sandbox/WindowsSandboxedSpawnRunner.java#L31-L32)) — Microsoft's BuildXL project, not anything Bazel ships. `--experimental_use_windows_sandbox` defaults `false` (a `TriState`, not `auto`), and `BazelSandbox.exe` is not distributed with Bazel or Bazelisk; nothing on `bazel.build` documents how to obtain or build it. **Net effect: in practice Windows gets `processwrapper-sandbox` (weak — "no undeclared-input read" only, no network or write isolation beyond what the process itself respects) or `local` (no isolation at all); `windows-sandbox` exists in the source tree but is unreachable without a binary nobody ships and undocumented anywhere public.** "Windows has no sandbox" is the correct practical statement; "Bazel has no Windows sandbox code" is not.

**`--enable_runfiles` default.** Fetched `CoreOptions.java` at both 8.7.0 and 9.2.0 — byte-identical option block: `defaultValue = "auto"`, help text *"Enable runfiles symlink tree; By default, it's off on Windows, on on other platforms."* ([CoreOptions.java:846-852 @8.7.0](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/analysis/config/CoreOptions.java#L846-L852), [:955-961 @9.2.0](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/analysis/config/CoreOptions.java#L955-L961)). No version split — confirming the existing consolidation's claim exactly.

**`--windows_enable_symlinks` and Developer Mode.** A `startup` option, `defaultValue = "false"` ("Only for documentation; value is set by the client" — the real default lives client-side), help text: *"If true, real symbolic links will be created on Windows instead of file copying. Requires Windows developer mode to be enabled and Windows 10 version 1703 or greater."* ([BlazeServerStartupOptions.java:477-486](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/runtime/BlazeServerStartupOptions.java#L477-L486)). `bazel.build/configure/windows` restates this and adds the alternative: symlinks also work if Bazel runs as Administrator, and warns *"Creating symlinks on Windows is an expensive operation… only enable this feature when you need it."*

**Junctions vs symlinks — the actual decision tree.** `WindowsFileSystem.createSymbolicLink` ([WindowsFileSystem.java:79-106](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/windows/WindowsFileSystem.java#L79-L106)):

```java
if (!createSymbolicLinks && existingFile) {
  Files.copy(target.toPath(), link.toPath());                         // no symlink support, target is a file → COPY
} else if (createSymbolicLinks
    && (existingFile || (!existingDirectory && type != SymlinkTargetType.DIRECTORY))) {
  WindowsFileOperations.createSymlink(link.toString(), target.toString()); // symlinks on, target is a file → real SYMLINK
} else {
  WindowsFileOperations.createJunction(link.toString(), target.toString()); // target is/will be a DIRECTORY → JUNCTION, always
}
```

The class comment spells out why directories get special treatment: *"Directory junctions can be created without any user privileges"* while *"directory symlinks can only be created by Administrators"* and *"normal [file] symlinks… only Administrators may create"* ([WindowsFileSystem.java:257-270](https://github.com/bazelbuild/bazel/blob/8.7.0/src/main/java/com/google/devtools/build/lib/windows/WindowsFileSystem.java#L257-L270); Dev Mode is the non-admin escape hatch the public docs describe, layered on top of this). So a runfiles tree on Windows is a **three-way mixture**, not a binary manifest-vs-tree choice: directory-shaped runfiles entries (an external repo's whole tree, a sub-binary's `.runfiles`) become junctions regardless of `--windows_enable_symlinks`; file-shaped entries become real symlinks only with that flag (plus Dev Mode/admin) and silently degrade to full-content copies otherwise. A tool that walks the runfiles tree checking `is_symlink()` per Python/Node semantics can get inconsistent answers depending on whether it hit a junction (which many POSIX-emulation layers report as a directory, not a symlink) or a copy.

**MAX_PATH and `--output_user_root`.** `bazel.build/configure/windows` states plainly: *"Some tools have the Maximum Path Length Limitation on Windows, including the MSVC compiler,"* and gives the exact recipe: `startup --output_user_root=C:/tmp`. A 2020 maintainer comment on a related (misfiled) issue is the clearer primary statement of *why* this remains a mitigation rather than a fix: *"Bazel actually did many improvements on that. It can handle long paths in most of places. But because the MSVC compiler still doesn't support long path, we recommend to use a short output directory"* ([bazelbuild/bazel#11482, comment](https://github.com/bazelbuild/bazel/issues/11482#issuecomment-634781862)). Note for citation hygiene: **BZL-HERM-27's existing evidence (`#11482`'s issue body) is not actually about this.** The reporter's own theory — "`SymlinkAction` can not create a symlink whose name is too long, [so] it has to copy the file" — is not what the issue was really about; the maintainer redirected the whole thread to a DLL-basename-collision bug and closed it as such, never confirming or fixing a symlink-length-triggers-copy defect. The rule's *conclusion* (set a short `--output_user_root` on Windows) is correct and independently sourced from the docs page above; the citation should point there, not at #11482.

For rules_python specifically, the CHANGELOG (not the coverage doc) settles the question the commission actually asked. Three dated entries, all present by 2.3.3:

- **1.5.0** (2025-06-11): *"On Windows, `--bootstrap_impl=system_python` is forced. This allows setting `--bootstrap_impl=script` in bazelrc for mixed-platform environments."*
- **2.0.0** (2026-04-09), Breaking: *"`--windows_enable_symlinks` is required… venv-based binaries are created by default (`--bootstrap_impl=system_python`) on supported platforms (Linux/Mac with Bazel 8+, or Windows)… Windows no longer defaults to creating a zip file and extracting it; a symlink-based runfiles tree is created, as on unix-like platforms."*
- **1.9.0** (2026-02-21): *"(binaries/tests) (Windows) `--enable_runfiles=true` is the default for `py_binary/py_test`. Prior behavior can be restored by adding `@rules_python//command_line_option:enable_runfiles=false`… to the `config_settings` attribute. NOTE: `enable_runfiles=true` will soon become **required** for Windows."*
([CHANGELOG.md](https://github.com/bazel-contrib/rules_python/blob/2.3.3/CHANGELOG.md) — entries at their respective version headers.)

That last entry means py_test/py_binary rule definitions carry their own Starlark transition forcing `enable_runfiles` on for Windows, layered on top of (and overriding) Bazel's own `auto` core default — independent of whatever `.bazelrc`/CI sets globally.

**Answer.** Windows ships one experimental, unreachable-by-default sandbox strategy (`windows-sandbox`, needs an external BuildXL binary) plus the universally-weak `processwrapper-sandbox`/`local` — no meaningfully sandboxed execution exists on Windows in practice, confirmed by both docs silence and source. `--enable_runfiles` is `auto` (off on Windows) unchanged across 8.7.0 and 9.2.0. Runfiles trees on Windows are not a single manifest-vs-symlink switch: directories always get junctions (no privilege needed), files get real symlinks only with `--windows_enable_symlinks` + Dev Mode/admin, otherwise silent copies. The MAX_PATH mitigation is a documented, MSVC-driven operator workaround (`--output_user_root=C:/tmp`), not a lifted limit — the commonly-cited issue for it (#11482) is mis-cited and should be replaced with the docs page. rules_js 3.4.1 is the one ruleset that documents the exact "empty coverage, PASSing test, `requires a runfiles tree` error" failure the commission describes; rules_python does not document it because it already forces runfiles on for py_binary/py_test on Windows as of 1.9.0 (well inside the 2.3.3 pin), so the JS-style failure should not reproduce for `py_test` out of the box; rules_rust 0.74.0 neither documents nor (by its own admission) reliably tests Windows at all, so `rust_test` coverage-on-Windows is an open, upstream-unverified question, not a settled "works" or "fails."

### Q3 — the fleet's Windows CI leg

> rules_ocx runs 3 of 9 test shards on windows-latest and sets startup `--windows_enable_symlinks` and `common:windows --enable_runfiles`. What else does a Windows CI leg need for hermeticity parity (`strict_action_env` on 8.x, PATH handling, `BAZEL_SH`, the MSYS dependency) and what can never be made hermetic there.

**Findings, against the actual fleet files** (`/home/mherwig/dev/rules_ocx/.bazelrc`, `.github/workflows/ci.yml`, read-only):

```
common --enable_platform_specific_config
startup --windows_enable_symlinks
common:windows --enable_runfiles
build --incompatible_disallow_empty_glob
test --test_output=errors
try-import %workspace%/.bazelrc.user
```

No `--sandbox_default_allow_network`, no `--incompatible_strict_action_env`, no `--output_user_root`, no `BAZEL_SH`, and no MSYS2 install step anywhere in `.bazelrc` or `ci.yml`; the matrix runs `os: [ubuntu-latest, macos-latest, windows-latest] × bazel: ["8.7.0","9.x","rolling"]` (9 shards, 3 on Windows).

- **`strict_action_env` on 8.x**: still defaults `false` on the whole 8.x line (per the hermeticity consolidation's own primary-source read of `BazelRuleClassProvider.java`, corroborated here — its per-OS branch is unchanged between the tags I pulled). Nothing in `rules_ocx` sets it, so the 8.7.0 and `9.x`/`rolling` Windows legs run under genuinely different environment-inheritance policies with no flag announcing the split — the exact BZL-HERM-01 finding, and it applies to the Windows legs too, not just Linux/macOS.
- **PATH handling is not "the same fixed string as Linux."** Even *with* `strict_action_env=true`, Windows does not get the POSIX `/bin:/usr/bin:/usr/local/bin` constant — `pathOrDefault(os, path, sh)` branches on `os != OS.WINDOWS` for that string; for Windows it instead computes the MSYS root from the resolved `bash.exe` path plus `C:\Windows;C:\Windows\System32;C:\Windows\System32\WindowsPowerShell\v1.0`, appending the caller's own `path` argument only when non-null ([BazelRuleClassProvider.java:347-390 @9.2.0](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/bazel/rules/BazelRuleClassProvider.java#L347-L390), identical logic present at 8.7.0). In the *non-strict* (today's actual, on both 8.7.0 and current `9.x`/`rolling` since `rules_ocx` never sets the flag) default path for Windows specifically, the code reads `System.getenv("PATH")` — the Bazel **server process's** own launch-time PATH — rather than treating PATH as inherited per-action the way the non-Windows non-strict branch does (`env.put("PATH", null)`, a sentinel meaning "read live at execution time") ([BazelRuleClassProvider.java:144-176 @9.2.0](https://github.com/bazelbuild/bazel/blob/9.2.0/src/main/java/com/google/devtools/build/lib/bazel/rules/BazelRuleClassProvider.java#L144-L176)). This is a real, sourced OS asymmetry worth naming in any generated explanation of the flag, separate from the version split BZL-HERM-01 already covers.
- **`BAZEL_SH` / MSYS dependency**: Bazel needs Bash for `genrule`, `sh_binary`/`sh_test`, and any Starlark rule using `ctx.actions.run_shell()`/`ctx.resolve_command()` — confirmed from `bazel.build`'s own Windows install page, which also documents the fallback: if Bazel can't find Bash, set `BAZEL_SH` to `<MSYS2 install>\usr\bin\bash.exe`, "for example… `C:\msys64\usr\bin\bash.exe`" ([site/en/install/windows.md](https://github.com/bazelbuild/bazel/blob/8.7.0/site/en/install/windows.md#L120-L159)). `rules_ocx` sets no `BAZEL_SH` and installs no MSYS2 — it works today only because `BazelRuleClassProvider.SHELL_EXECUTABLE.get(OS.WINDOWS)` hardcodes exactly `c:/msys64/usr/bin/bash.exe` as Bazel's own default probe path, **and** GitHub's `windows-latest` (Windows Server 2022) runner image preinstalls MSYS2 at precisely `C:\msys64` — confirmed from GitHub's own runner-image manifest: *"MSYS2 … Location: C:\msys64 … MSYS2 is pre-installed on image but not added to PATH"* ([runner-images, Windows2022-Readme.md](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md)). This is a coincidence of two independently-maintained defaults lining up, not a contract between them — a self-hosted Windows runner, a different CI vendor, or a future GitHub image that relocates or drops MSYS2 would silently break Bash-dependent targets with no warning until the day it happens.
- **What a Windows leg still needs, beyond what's already set**: (a) a short `--output_user_root` per BZL-HERM-27 — genuinely absent today (`grep -rn output_user_root .bazelrc* .github/workflows/*.yml` in `rules_ocx` is empty); (b) an explicit `common --incompatible_strict_action_env=true` decision — the open question the consolidation already surfaced for the fleet generally, but with the Windows-specific consequence that flipping it changes *which* PATH-construction branch every Windows action takes, not just whether LD_LIBRARY_PATH leaks (irrelevant on Windows) or the PATH value is fixed; (c) either a pinned `BAZEL_SH`/MSYS2 install step, or an explicit acceptance that the Windows leg's Bash resolution rides on the GitHub image's current MSYS2 placement.

**What can never be made hermetic on Windows, structurally**: there is no sandboxed execution strategy with real isolation available (Q2) — `processwrapper-sandbox`/`local` enforce nothing beyond "don't read an undeclared input," so `--sandbox_default_allow_network=false` is a complete no-op on Windows (there is no network namespace for any Windows strategy to revoke — this is the same "no signal" case BZL-HERM-02's own verification text already calls out for `processwrapper-sandbox` generally, and it is the *only* strategy Windows has by default). File-write isolation outside the exec root is likewise not enforced by anything on Windows. Bash-dependent rules add a second, permanent host dependency (MSYS2/Git-Bash's exact location and version) with no Bazel-side pinning mechanism — `BAZEL_SH` names a path, not a hash, so two Windows machines with different MSYS2 point releases installed at the documented location are not proven identical the way two Linux sandboxed builds can be.

## AI-agent angle

1. **Treating "roughly the same as the Linux sandbox" as full parity, or as no isolation at all — both wrong.** *Check*: an agent explaining darwin-sandbox should name the write-isolation and (conditional) network-denial it does provide, and the host-read isolation and localhost-namespace parity it does not; neither extreme survives reading `DarwinSandboxedSpawnRunner.java`.
2. **Stating "Windows has no sandbox in Bazel" as a source-level fact rather than a practical one.** *Check*: `grep -rn experimental_use_windows_sandbox` against any claim that no Windows sandbox code exists — the flag and class are real, just unreachable without an unshipped binary.
3. **Grepping `.bazelrc`/CI for `--enable_runfiles` as sufficient proof of Windows coverage health for every language.** *Check*: for a Windows leg that only runs `py_test`, first read the pinned `rules_python` version — `≥1.9.0` already forces the flag at the rule level, so an EMPTY grep is not automatically a FINDING there the way it is for a JS-only or Rust-only leg.
4. **Citing an issue number without reading whether its own resolution matches the claim being sourced to it.** *Check*: `#11482` is the textbook trap — its title and reporter's theory match a common claim about `SymlinkAction` path-length fallback, but the thread's actual root cause and fix are unrelated (a DLL basename collision). Read the closing comments, not just the opening body.
5. **Assuming Windows runfiles trees are either "real symlinks" or "a flat manifest," with nothing in between.** *Check*: `WindowsFileSystem.createSymbolicLink`'s three-way branch — an agent diagnosing "this Windows test can't find its data dependency" should first determine whether the missing entry is a directory (junction, should always work) or a file (symlink-or-copy, gated on the flag).

## Contested / evolving

- Whether `bazel.build/docs/sandboxing` will ever state darwin-sandbox/linux-sandbox network parity explicitly — as of both tags read here, it still doesn't, and the phrasing has been static for years judging by the age of the issues cited.
- rules_rust's Windows position is a maintainer capacity statement ("we lack the expertise"), not a technical ceiling — it could improve with new contributors; today's "most things probably work" is explicitly not a tested guarantee, coverage included.
- rules_python's own 1.9.0 changelog flags that the `enable_runfiles=false` override for Windows "will soon become **required**" (i.e., possibly removed) — no version number given for when; a repo relying on the override to opt back into manifest-only Windows `py_test` runs should watch for this.
- Whether GitHub's `windows-latest` image will keep MSYS2 at `C:\msys64` indefinitely is an operational assumption, not a contract; `actions/runner-images` publishes per-image-version manifests and the location is documented per-release, not guaranteed stable across releases.

## Not settled

- **No macOS or Windows runner was exercised for this commission** — everything above is sourced from Bazel's tagged source, official docs, ruleset docs/changelogs, and GitHub issue threads, never from running `bazel build`/`bazel coverage` on either OS. The sibling Linux measurement's protocol (`bazel-measurements/sandbox-strategy-network-and-hermetic-sandbox-on-this-host.md`) is directly portable to a macOS or Windows runner and would turn every "confirmed by source" claim above into "confirmed by source and measurement." Concretely: re-run its Q3 (network) protocol on a macOS runner with darwin-sandbox, and re-run `bazel coverage` for a trivial `py_test` and `rust_test` on a Windows runner with and without `--enable_runfiles` to get the exact log text rules_js already documents (or discover it differs).
- **The mount set `--experimental_use_hermetic_linux_sandbox` needs for a typical build is Linux-specific and still open** per the sibling measurement's own "Not settled" — orthogonal to this commission but worth resolving before generalizing any hermetic-sandbox guidance across OSes.
- **No evidence was found of any real-world adoption of `windows-sandbox`/BuildXL.** It may be effectively dead code; nobody who filed a public issue or wrote a blog post referencing `--experimental_use_windows_sandbox` surfaced in this research.
