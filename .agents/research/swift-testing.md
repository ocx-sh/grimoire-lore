# Swift testing: consolidated ruleset (SW-TEST)

Dated 2026-10-10, Swift 6.4.0 era (prior line 6.3.3). Two sub-artifacts fed this file: [test-style](swift-testing/test-style.md) (20 rules, 21 verification runs, 23 grep rows) and, in the revision, [isolation-and-seams](swift-testing/isolation-and-seams.md) (7 rule candidates, 10 verification groups, 25 sources). The first consolidation re-ran test-style's greps, settled its conflicts with 15 runs (C1-C15) and numbered rules 01-17 by the check that catches them. The revision folds in the follow-up round that file commissioned, settles the new conflicts with 10 more runs (C16-C25) and appends rules 18-24: IDs are append-only, no number moved or was reused. An audit pass of that revision corrected five stale cross-set references and took in two sibling hand-offs ([swift-gates](swift-gates.md) C19 on TSan, [swift-api](swift-api.md) K4 on the SDK coverage tier); see the Revision log. Linux only (swift:6.4 and swift:6.3 images); every Apple, Windows, Wasm and Android claim is "unverified: read only".

## Verdict

1. **Framework by test kind.** New unit, integration, async, crash and CLI end-to-end tests are Swift Testing, for every code kind (library, SDK, CLI, server, app, test code). XCTest stays only for XCUITest, Apple `measure {}` performance tests (the map's decision) and files that already exist. The rule is diff-scoped: the corpus is 48.6% Swift Testing by function and the split follows repository age, not vendor (SW-TEST-01).
2. **Interop is a CI decision.** On a 6.4 toolchain, a manifest below tools 6.4 gets `limited`: an `XCTAssert` inside `@Test` is a warning and the gate block's `swift test -Xswiftc -warnings-as-errors` still exits 0 (C1). Libraries and the SDK (tools 6.2 under owner Q1) pin `SWIFT_TESTING_XCTEST_INTEROP_MODE=complete`; CLIs and servers at tools 6.4 get `complete` by default (SW-TEST-10).
3. **Parallel by default means state per test, and no test touches process-global state.** Shared mutable state is a defect; `.serialized` is not the fix unless it sits on the one suite that owns the resource and nothing else reads it (two serialized suites raced 50/50 on 6.4, 49/50 on 6.3). `setenv`, `chdir` and `umask` in a test are process-global writes the compiler accepts silently: planted pairs went red 48/50, 32/50 and 30/30, and on glibc 2.39 a `setenv`/`getenv` race killed the test process with SIGSEGV. The fix is to pass the value; a temp path or port another test can name is the same defect. `--no-parallel` is a triage step, never the answer (SW-TEST-04, -05, -14, -18, -19).
4. **Sleeps are not synchronisation.** One grep, applied to the lines a diff adds, because even Apple repos carry 638 sleep lines. Wait for the event: `await`, `confirmation()` plus a continuation, an `AsyncStream`, or an injected `Clock` (SW-TEST-03, -12).
5. **Trap contracts are exit tests**, written against `precondition`, never `assert`; `.failure` for traps, `.exitCode(n)` for defined exits; guarded by platform (SW-TEST-07, -11).
6. **CLI and SDK process tests run the built executable out of process** and assert stdout, stderr and status as three facts, with swift-subprocess or temp files, never `Pipe` read after `waitUntilExit()` (SW-TEST-15). Do not copy swift-argument-parser's own harness. The SDK's unit and coverage run starts no process: the spawn is a substitutable seam owned by one module, replayed from byte-exact recorded cases located through `Bundle.module`; the live adapter has its own suite (SW-TEST-20, -21).
7. **Coverage** is computed from `Sources/` lines of the JSON that `--show-codecov-path` names, never from `totals`. Floor: 100% lines for the SDK on Linux legs (owner Q4), plus 100% regions over the core prefix as the default pending Q-T7 (a lines gate stayed green when a recorded case was deleted); a committed ratchet for everything else. Swift has no line- or region-level coverage exclusion (a documented gap below), so code that cannot be covered lives in its own file excluded by path. Code reachable only through a trapping child counts as uncovered (C6), so the SDK validates by throwing (SW-TEST-16, -22). Both 100 floors are targets until real code meets them: the one real-code measurement (swift-api's reference SDK, per its R11, not re-run here) was 283/283 lines and 179/182 regions, and that package tests the SDK against a fake CLI out of process instead of a replay seam (Q-T8).
8. **Sanitizers**: an ASan leg may gate; a TSan leg gates only on the report kind (SW-GATE-27's `tsan-check.sh` fails on `WARNING: ThreadSanitizer: data race` and never on `Swift access race`), because TSan reports correct `Synchronization.Mutex` code as `Swift access race` and no suppression was safe. Watched on 6.4 and 6.3 (C25). The earlier "TSan is advisory" is superseded (SW-TEST-17).
9. **Test targets and fakes.** A test target of a module that enables `NonisolatedNonsendingByDefault` enables it by name (measured for `@MainActor` tests only). SDK contract tests use a plain `import`, because `@testable import` hid a missing public `init`; white-box suites keep `@testable`. Fakes are hand-written values behind the seam; a mock macro is not added for a type that is one closure (SW-TEST-23, -24).

### Documented gaps

Established by the revision as gaps, not answers; each is a fact to design around, not an open question.

- **No coverage exclusion.** Four comment markers, `#sourceLocation`, `@_transparent` and `@_semantics` left every count unchanged on 6.3 and 6.4 (lines 1/12); `#if` build switches hide the code from the thing under test. [llvm-project#33625](https://github.com/llvm/llvm-project/issues/33625) is open since 2017 and an inline-marker PR was closed unmerged on 2026-06-13. Only file-level (jq prefix, `--ignore-filename-regex`) and function-name allowlists exist. Re-check at each LLVM bump (SW-TEST-22).
- **No cross-suite serialization on a shipped toolchain.** `.serialized(for:)` is `@_spi(Experimental)` and does not compile from a shipped toolchain even with the SPI import (exit 1 on 6.3 and 6.4); the maintainer's pitch (2026-04-17) is unmerged; the built-in `.taskLocal(_:withValue:)` trait is Swift 6.5 only. Until then isolate by passing the value or a hand-written scoping trait. Re-check at 6.5 (SW-TEST-08, -18).
- **The measured seam covers exit status and streams only.** Seven recorded cases cover 25/25 core lines and 19/19 core regions, but the replay closure ignores the argv it receives (read from `Replay.swift`; no plant), so a change to the flags the SDK sends passes all of them. SW-IO-26's timeout race, cancellation and kill ladder sit in the excluded spawn module here; `ocx-sdk-python` unit-tests its ladder through `popen_factory`, `clock` and `kill_grace` under its 100% gate, and no Swift equivalent was measured here (SW-TEST-20). The api/sdk-shape round answered it differently rather than closing it: its reference SDK drops the replacing runner and tests the timeout race, cancellation and kill ladder against a fake CLI out of process, because three of its planted reds (`red-a`, `red-b`, `red-c`) fail only against real children ([swift-api](swift-api.md) SW-API-13, K4, R8; not re-run here). Which design the SDK takes is Q-T8.
- **100% regions has one real-code measurement, and it missed.** The fixture has 19 core regions and passes; swift-api's reference SDK (a swift-subprocess runner, 467 source lines) is 283/283 lines and 179/182 regions (`Discovery.swift` 27/29, `ProcessRunner.swift` 50/51; the three regions were not investigated; [swift-api](swift-api.md) R11, not re-run here), so a regions gate at 100 is red there. Generic specializations, `defer` and `catch` arms remain the suspects (Q-T7).
- **The TSan filter has a blind spot.** SW-GATE-27's filter gates on `data race` reports. A real race that TSan reports only as `Swift access race` passes it; no planted race was in that class (C25 and SW-GATE-27's plants each also printed `data race`), and why a correct `Mutex` produces only the `Swift access race` kind is not established (SW-TEST-17).
- **The crash is a glibc fact, not a Swift guarantee.** `setenv` racing `getenv` crashed only on glibc 2.39 (54/60 and 40/40); glibc 2.43 survived 100/100, and a C reproducer did not crash on either image, so the attribution to glibc commit `7a61e7f557a9` is "consistent with". musl, macOS and Windows are unmeasured. A green run on a newer libc proves nothing.
- **No Swift exemplar** has a replay-fixture layout, a spawn seam, a coverage minimum or a line exclusion; SW-TEST-20 to -22 rest on the plants and the Python original.
- **Non-Linux resource and environment behaviour** (`Bundle.module` with `.copy` on Windows and Apple, `setenv` semantics off Linux) is unverified: read only.

### Where sources disagreed, and the decision

- **Nuke is not "a mixed tree" (map brief) vs measured.** `Nuke@d5548dd61395`: 0 files import XCTest, 153 import Testing, 2,506 `@Test` (C4). Decision: Nuke is the Testing-only counter-example, not a mixed-tree exemplar.
- **XCTest keeps `measure {}` (map conflict 3) vs Nuke's hand-written `ContinuousClock` helper** (`Nuke@d5548dd61395:Tests/NukePerformanceTests/Measure.swift:16-27`). Decision: the map binds. No rule here replaces `measure {}`; the helper is an owner question (Open questions, Q-T4).
- **Three sleep greps disagree.** The map's `sleep(` flags a test clock's own `func sleep(until:)`; the dive's `\.sleep(` misses a bare `sleep(1)`; the gates dive's E08 (`Task\.sleep`, `Thread\.sleep`) misses `usleep`, `clock.sleep` and bare `sleep`. Decision: one combined grep, 7/7 variants caught and the clock twin clean (C3). SW-TEST owns the `Tests/` side; swift-gates C15 has since replaced E08 with this grep (and excludes `func usleep(`/`func nanosleep(` declarations as well).
- **Gate-block step 3 vs interop.** `swift test -Xswiftc -warnings-as-errors` is green under `limited` with two warnings (C1); with `complete` it is red (C2). Decision: on 6.4+ legs the step carries the env prefix (SW-TEST-10); swift-gates C17 has since edited its verbatim block (SW-GATE-01 step 3) to carry it.
- **The XCTest-in-Testing grep over-reports.** Name prefix `XCTAssert` flags 156 of 2,112 Testing-importing test files; the exact API-name regex flags 108, dropping commented-out code and local helpers such as `XCTAssertMatch` (C11, measured over the corpus). Decision: the exact-name regex; hits in files that also `import XCTest` are legitimate inside `XCTestCase` classes, so review at function level.
- **Pipe-drain has two owners.** The dive's rule 13 duplicates SW-IO-P12 ([subprocess-contract](swift-io/subprocess-contract.md)). Decision: P12 owns the production and legacy-`Process` rule; SW-TEST-15 keeps only the harness obligations plus the `Pipe()` grep.
- **Sanitizers have three owners.** The dive's rule 15 and SW-CONC-27 ([isolation-and-sendable](swift-concurrency/isolation-and-sendable.md); the first consolidation cited it as SW-CONC-16, which is now a different rule) reproduce the same TSan facts independently (seccomp, `Mutex` false positive), and SW-GATE-27 adds the CI script. Decision: SW-TEST-17 owns the ASan recipe and the TSan facts, SW-GATE-27 owns the TSan job script, SW-CONC-27 keeps the count assertion. "Advisory TSan stands because the program prefers `Mutex`" is withdrawn: see the next entry.
- **Revision (hand-off): "TSan is advisory" (SW-TEST-17 as first consolidated, SW-CONC-27) vs SW-GATE-27 (a TSan job that gates on `data race` only).** swift-gates C19 found no usable suppression but a usable filter and handed the change to SW-TEST-17. Re-run on test-style's own fixtures (C25): the filter script exits 1 on the racy `@unchecked Sendable` counter (prints `WARNING: ThreadSanitizer: data race`) and 0 on the `Mutex`, actor and `NSLock` twins, on 6.4 and 6.3. Decision: SW-TEST-17 is amended in place and its TSan severity rises from CONSIDER to SHOULD; the blind spot is a documented gap; Q-T2 is retired.
- **Census counts.** The dive counts coverage in 3 repos and `.serialized` 464 times (docs included); the gates audit counts 6 repos collecting coverage, 0 enforcing a minimum, and `.serialized` 22 on `@Test` plus 87 on `@Suite` ([gates](swift-audit/exemplar-quality-gates.md) Axes 2 and 4). Decision: the audit numbers, per the map's counting discipline (conflict 21).
- **Coverage floor.** Rust `TEST-24` bans fixed floors for a ratchet ([testing](../../rules/rust-quality/testing.md)); owner Q4 sets 100% for the SDK, as `ocx-sdk-python` does (`fail_under = 100`, Linux legs only; [config-inventory](swift-audit/config-inventory.md) §4). Decision: both, by code kind (SW-TEST-16).
- **Exit-test condition.** The dive says `.failure`; the CLI dive uses `.exitCode(n)` ([exit-codes-and-streams](swift-cli/exit-codes-and-streams.md), where it is numbered SW-CLI-17; the consolidated rule is SW-CLI-14 in [swift-cli](swift-cli.md), and SW-CLI-17 there is configuration precedence). Decision: `.failure` for traps (the signal differs per architecture), `.exitCode(n)` for a defined `exit(n)`.
- **swift-subprocess pin.** The dive ran 1.0.0; the map names 1.0.1 current. The harness recipe passes unchanged on 1.0.1 (C5). Decision: the harness uses the product's own pin, never a second one.
- **Revision: "a process-wide resource goes to one suite" (SW-TEST-04, first consolidation) vs the isolation round.** The sentence overclaimed: two `@Suite(.serialized)` suites racing each other were 50/50 red (49/50 on 6.3), and a single owner suite is safe only while no other suite or library code reads the same state. Decision: SW-TEST-04 and -05 are rewritten in place; env, cwd and umask are not protected but not touched (SW-TEST-18), paths and ports are made unique (SW-TEST-19), and the one-suite shape is the residual for a resource that can be neither injected nor made unique.
- **Revision: exit-test exemption, file-level (dive) vs line-level.** The dive's alternative form exempts every file containing `processExitsWith`; on a file with a top-level `setenv` plus an exit test it printed nothing (C16). Decision: the gate is the plain grep minus lines carrying `// exit-test child`; the file-level form is dropped.
- **Revision: production reads the environment once (SW-TEST-18 as proposed) vs SW-IO-24/-25.** The spawn module merges `ProcessInfo.processInfo.environment` with overrides at spawn time, so "once, at the composition root" is not literally true of the SDK. Decision: the production half is a reading heuristic (SHOULD) naming both places; only the `Tests/` half is a MUST.
- **Revision: SW-IO-26 `ProcessRunner` (a struct with a `run` method in the spawn module) vs SW-TEST-20's substitutable seam (a closure-holding struct or protocol, defined where the core can see it).** The two are not the same type, and SW-IO-26's `run` also takes `workingDirectory` and `timeout` that the measured two-parameter seam omits. Decision: SW-TEST-20 states the invariant (one module imports `Subprocess`/`Process`; the core takes the runner by injection) and is shape-neutral; the type is for api/sdk-shape (Open questions).
- **Revision: Q4 says 100% line coverage; the dive makes 100% regions a MUST.** Decision: the regions gate is computed and enforced from day one, with its 100 floor a default pending Q-T7 (an extension of Q4, not Q4 itself).
- **Revision: the dive's `--skip` and the `.spawns` tag.** The fixture declares `.tags(.spawns)` but skips the suite by name (`--skip LiveSpawn`); `swift test --help` offers only `--filter` and `--skip` regexes (C22). Decision: the rule names the suite-name regex; a tag filters nothing.
- **Revision: corpus counts.** `setenv` calls in tests: 9 repos (first consolidation), 7 (dive), 8 re-measured (C23; containerization's hit is a method named `setenv`, swift-build calls `POSIX.setenv`). `Mock*` files: 174 in 9 repos (dive) against 128 in 12 (C23; regexes and file sets differ). `@testable import`: 54% of 3,891 test files (dive) against 45% of 5,160 Tests-path files (C23). Decision: cite the range, "about half"; no rule depends on the exact figure.
- **Revision (cross-set): SW-API-13 and K4 ([swift-api](swift-api.md)) vs SW-TEST-20 and SW-TEST-22.** swift-api's reference SDK keeps no replacing runner: seams are stored values (`captureLimit`, `killGrace`, an injectable `sleep`) and pure `static` functions, the tests run a fake CLI found through `Bundle.module` out of process, and the lines gate is 100 over all of `Sources/` including the real spawn path (283/283, R11). Its K4 chose that form for the SDK and kept SW-TEST-20 for a CLI core without a spawn module. Both designs agree on one-module ownership of the spawn (SW-TEST-20's first sentence, SW-API-09) and on `Bundle.module` fixture lookup. They differ on how the SDK reaches its coverage: a replay seam with the adapter excluded by path (SW-TEST-20/22) against a real child with nothing excluded (SW-API-13). The exclusion in SW-TEST-22 was forced by the Foundation `Process` vehicle (25/27 lines, error arms that cannot be forced), not shown necessary for the swift-subprocess runner. Decision, provisional until the owner or the set reconciliation says otherwise (Q-T8): the shape owner wins for the SDK; SW-TEST-20/21/22 stay as written and bind a CLI core and any SDK that keeps a replacing runner; a replay unit tier (SW-TEST-21) may coexist with SW-API-13's process tier. No SW-TEST rule text changed for this; each of 20 and 22 carries a scope note.
- **Revision (audit): stale cross-set references.** The first consolidation cited SW-CONC-16 for TSan (it is SW-CONC-27; 16 is the `MainActor.run` tell) and SW-CLI-17 for exit-status tests (it is SW-CLI-14; 17 is configuration precedence). Both were corrected in place; no SW-TEST ID or meaning changed.

## The ruleset

Conventions. Severity is MUST, SHOULD or CONSIDER. "Watched" names the run in which the check went red on a violation and green on a twin: `V#`/`G#` are test-style's [Verification runs](swift-testing/test-style.md#verification-runs); `IS-V#` are the V1-V10 groups of [isolation-and-seams](swift-testing/isolation-and-seams.md#verification-runs) (its grep rows are cited as IS-V6, IS-V8, IS-V9); `C#` are this file's runs below. "From" is the test-style dive's rule number; rules 18-24 are the isolation dive's own numbers. Greps print the violation, so empty output is a pass; a pipeline ending in `xargs -r` exits 123 when empty; `grep` over a missing `Tests/` operand exits 2 (an error, not a pass). A gate that must be mechanical (18, 19) accepts a hit only on a line ending in a stated marker comment, the SW-GATE-10 convention of an adjacent reason: whole tree in a new repository, added lines in an adopted one (the SW-TEST-03 diff wrapper).

### SW-TEST

Index (24 rules, 14 MUST): grep or diff over test sources, 01-05 and 18-19; compile or run the suite, 10-14; out-of-process harness, 15; spawn seam and recorded fixtures, 20-21; CI leg, 16-17 and 22; smaller grep- or report-checked rules, 06-09 and 23-24 (listed last). The IDs are stable; the order below follows the catching check.

#### Caught by a grep over test sources or the diff

**SW-TEST-01. A diff adds no test file that imports XCTest; new tests are Swift Testing.** Exceptions: XCUITest and Apple-only `measure {}` performance directories, listed in the pathspec. Existing XCTest files are neither rewritten nor forbidden to grow.
- Why: XCTest has no exit tests, `confirmation()` or parameterization, and agents default to `XCTestCase` from pre-2024 training.
- Check: `git diff --name-only --diff-filter=A origin/main...HEAD -- 'Tests/*.swift' ':(exclude)Tests/*UITests/*' ':(exclude)Tests/*PerfTests/*' ':(exclude)Tests/*PerformanceTests/*' | xargs -r grep -l -e 'import XCTest'` (output = violating files). Inventory: `grep -rln -e 'import XCTest' --include='*.swift' Tests/`.
- Watched: yes. G7d and C10: red prints `Tests/NewTests/NewTests.swift`; green (Testing file plus UI and perf XCTest files added) is empty. With only the UI exclusion the perf directory is flagged, hence the extra pathspecs.
- Severity MUST. Floor: Swift 6.0 (Testing ships in the toolchain); the 6.4 `swift package init` emits it. From 01.

**SW-TEST-02. No XCTest API runs under Swift Testing; port it.** `XCTAssert*` becomes `#expect`; `XCTUnwrap` becomes `try #require`; `XCTFail` becomes `Issue.record`; `XCTSkip` becomes an `.enabled(if:)` trait or `try Test.cancel(...)`; `XCTestExpectation`, `XCTWaiter`, `wait(for:)` become `confirmation()` or a plain `await`; `setUp`/`tearDown` become `init`/`deinit` of a suite type (struct for per-test state, `final class` when `deinit` is needed; async cleanup uses a scoping trait, not run here).
- Why: under tools/toolchain `none` an `XCTAssertEqual(1, 2)` in a `@Test` passes silently (exit 0); under `limited` it is a warning; `throw XCTSkip` is a failure; `XCTestExpectation` is documented unsafe. A leftover `func setUp()` in a Testing suite is never called.
- Check (two greps, output = review items):
  `grep -rl -e 'import Testing' Tests/ | xargs -r grep -nE '\b(XCTAssert(Equal|NotEqual|True|False|Nil|NotNil|Identical|NotIdentical|GreaterThan|GreaterThanOrEqual|LessThan|LessThanOrEqual|ThrowsError|NoThrow)?|XCTFail|XCTUnwrap|XCTSkip[A-Za-z]*|XCTExpectFailure|XCTestExpectation|XCTWaiter)\b|wait\(for:|fulfillment\(of:'`
  `grep -rl -e 'import Testing' Tests/ | xargs -r grep -n -e 'func setUp' -e 'func tearDown'`
  Limits: in a file that imports both frameworks a hit inside an `XCTestCase` class is legitimate (68 such files in 12 repos); a helper file that imports only XCTest is invisible to the grep and is caught at run time by SW-TEST-10.
- Watched: yes. G2/G6 on the dive's plants; C11 (refined regex: `interop-st-t64` 2 lines, `interop-skip` 3 lines, twin 123, a local `XCTAssertMatch` shim unflagged); C12 (`func setUp` grep red, twin 123, and `swift test` exit 1 because `setUp` never ran).
- Severity MUST. Floor: Swift 6.0; interop outcomes per SW-TEST-10. From 02, 17, 18.

**SW-TEST-03. A sleep is never how a test waits.** Not `Task.sleep`, `clock.sleep`, `Thread.sleep`, `usleep`, `nanosleep` or a bare `sleep(n)` on lines a diff adds or changes. Wait for the event (SW-TEST-12). A sleep that deliberately simulates slow work inside a fake carries a comment saying so. A timeout is `.timeLimit` (SW-TEST-13), not a racing sleep.
- Why: a sleep-guarded async test is green idle and red under load; every sleep also slows the suite.
- Check, whole tree (inventory) then diff-scoped (the gate):
  `grep -rnE --include='*.swift' '(^|[^[:alnum:]_])(usleep|nanosleep|sleep)\(' Tests/ | grep -v -E 'func +sleep\('`
  `git diff -U0 origin/main...HEAD -- 'Tests/*.swift' | grep -E '^\+' | grep -vE '^\+\+\+' | grep -E '(^\+|[^[:alnum:]_])(usleep|nanosleep|sleep)\(' | grep -v -E 'func +sleep\('`
  Behavioural: build, then `taskset -c 0 swift test --skip-build`.
- Watched: yes. V6 (pinned red exit 1 three times, `confirmation()` twin exit 0 three times, both toolchains); C3 (7/7 variants flagged, clock twin clean); C14 (diff-scoped red prints the added `sleep(1)`, green with a touched legacy sleep prints nothing).
- Severity MUST on added lines; the whole-tree grep is an inventory, the corpus having 638 sleep lines in 235 files. Floor: any Swift. From 07.

**SW-TEST-04. Tests share no mutable state.** No `static var`, global `var` or `nonisolated(unsafe)` that two `@Test`s touch. State belongs to the test: stored properties of a `@Suite struct` (a fresh instance per `@Test`, `mutating` test functions) or arguments. Process-global state (environment, working directory, umask) is not shared state to protect but state not to touch (SW-TEST-18); a temp path or port is made unique per test (SW-TEST-19); only a resource that can be neither injected nor made unique (an external singleton) goes to one suite, SW-TEST-05.
- Why: tests of different suites run concurrently in one process; two tests bumping a shared counter failed on 6.3 and 6.4.
- Check: `grep -rn -e 'static var' -e 'nonisolated(unsafe)' --include='*.swift' Tests/` (each hit is a review item; a `static var` used as `arguments:` data is fine). Behavioural: `swift test --no-parallel` green while `swift test` is red means test-to-test interference.
- Watched: yes. G3, V1, V4: `shared-red` exit 1 on both toolchains, `--no-parallel` exit 0 three times, `shared-instance` exit 0.
- Severity MUST. Floor: Swift 6.0. From 04. (Revised 2026-10-10: the one-suite sentence is narrowed and `setenv`, `chdir`, `umask`, fixed temp paths and ports, planted in the revision, are owned by SW-TEST-18 and -19.)

**SW-TEST-05. `.serialized` goes on the one `@Suite` that owns every test touching a shared resource, or on a parameterized `@Test`; never alone on a plain `@Test`, never as cross-suite protection.** The single-suite owner is safe only while no other suite and no library code reads or writes the same state: `.serialized` orders tests inside its own suite and nothing else. It is the residual tool for a resource that can be neither injected nor made unique (SW-TEST-18, -19).
- Why: the trait orders tests inside its own suite or test only (ST-0003: on a non-parameterized test it "does not have any effect"); two `@Suite(.serialized)` suites still race each other: one suite writing `setenv` and one reading were 50/50 red on 6.4 and 49/50 on 6.3.
- Check: `grep -rnE --include='*.swift' '@Test\(.*\.serialized' Tests/ | grep -v -E 'arguments:|serialized\(for'` (output = no-op shapes, multi-trait forms included). The cross-suite shape has no grep, because the shared resource is not syntactic: every `@Suite(.serialized)` touching the same file, variable or port must be one suite, and that suite must be the only reader (reading heuristic).
- Watched: yes for the grep (C13: `shared-serialized-pertest` 2 lines, `shared-serialized` and `shared-serialized-split` 0 lines, multi-trait plant flagged and parameterized plant not); V2/V3 prove both bad shapes red (exit 1, 6.3 and 6.4); IS-V1 `env-serialized-red` (cross-suite reader and writer: 50/50 and 49/50 red).
- Severity MUST. Floor: Swift 6.0 (ST-0003). From 05.

**SW-TEST-18. For the Swift SDK mirroring `ocx-sdk-python`: the SDK keeps unit, spawn and contract tiers. The unit tier replays recorded cases through the seam (SW-TEST-20, -21) with no process and carries the lines-and-regions gate on the core (SW-TEST-22); the spawn tier is the `LiveSpawn` suite (SW-TEST-15); the contract tier runs the real `ocx`, env-gated (SW-TEST-06). If Q-T8 goes to swift-api's form (SW-API-13), the spawn tier becomes a fake CLI run out of process, it carries the lines gate over all of `Sources/`, and the replay unit tier shrinks to mapping logic. It maps `.signaled(n)` to 128+n (owner Q6) and covers it with a recorded case and a live test; tests retry with an injected clock (SW-TEST-12); its tests never mutate the environment (SW-TEST-18). For Swift CLIs in the ocx/grimoire mould: every exit code has a real-invocation test with separate streams, Windows legs are not allowed to pass vacuously, the coverage ratchet applies and tests inject configuration instead of setting it. For OCI tooling in the `apple/containerization` mould: split slow integration targets from unit targets and exclude them from coverage runs (`container@f70ecbb926d9:Makefile:387`, `--skip TestCLI --skip IntegrationTests`), and put registry references in tests behind `// literal ok:` or a port-0 local registry.

## AI-agent failure modes

Ranked by how often each bites: corpus prevalence first, then the dive's AI-angle table. Items 1-15 are unchanged; 16-23 were appended by the revision, ordered by the isolation dive's likelihood.

1. **New tests written as `final class FooTests: XCTestCase`.** Habit from pre-2024 training; still compiles. Check: SW-TEST-01 diff grep.
2. **Sleep, then assert.** Green on a laptop, red under load; 638 lines in 235 test files, including Apple repos. Check: SW-TEST-03 grep; `taskset -c 0 swift test --skip-build`.
3. **An old XCTest helper (`XCTAssertEqual`) called from an `@Test`.** Silent pass on toolchains below 6.4, a warning under `limited`, and a green gate block (C1). Check: SW-TEST-02 grep; SW-TEST-10 command.
4. **Shared `static var` state, or `@Test(.serialized)` and two `@Suite(.serialized)` suites as the "fix".** Reads like a fix, changes nothing. Check: SW-TEST-04 and -05 greps; `swift test --no-parallel` against plain `swift test`.
5. **`confirmation { c in service.start { c() } }` without awaiting.** Fails deterministically with an unhelpful message. Check: the run (exit 1, "confirmed 0 times").
6. **Copying `swift-argument-parser`'s `Pipe` + `waitUntilExit()` + read harness, merging streams, or returning early on Windows.** Deadlocks above 64 KiB and hides stream and exit bugs. Check: SW-TEST-15 run against a buggy CLI; `Pipe()` grep.
7. **Wrong flags for Swift Testing**: `--num-workers 1` or `--parallel` for control, `--repeat-until` on a 6.3 toolchain. Check: only `--no-parallel` works (V4); 6.3 exits 64.
8. **Invented exit-test API (`#expect(exitsWith:)`, `.crash`, no `await`), `assert` as the contract, asserting the trap message.** Check: `swift build --build-tests`; `swift test -c release`.
9. **Exit-test file with no platform guard.** Check: SW-TEST-07 grep (non-Linux effect unverified).
10. **Reading `.data[0].totals` as the coverage figure, or hard-coding `.build/debug/codecov/...`.** Check: SW-TEST-16 gate; always `--show-codecov-path`.
11. **TSan red on `Mutex` code read as a real race (or the leg dropped), TSan green read as proof, ASan red on a fresh package disabled.** Check: SW-TEST-17 filter (the report kind decides) and log check; `--disable-xctest`.
12. **Setting the interop variable on a 6.3 toolchain and trusting the green.** Check: `swift --version` assertion in the same job.
13. **`@Test(arguments: [1,2,3], ["a","b","c"])` expecting pairs.** Check: the `with N test cases` line; `zip`.
14. **`@unchecked Sendable` test doubles with unprotected state, "verified" by a passing run.** Check: deterministic count assertion; SW-TEST-17 TSan leg.
15. **`throw XCTSkip` or `XCTestExpectation` in an `@Test`.** Check: SW-TEST-02 grep; the first is a plain failure on 6.4.
16. **`setenv("X", "y", 1); defer { unsetenv("X") }` in a `@Test`**, copying XCTest `setUp`/`tearDown` or pytest `monkeypatch` habits. Compiles silently, flakes 48/50 and can crash a 6.3 image. Check: SW-TEST-18 gate (also its Windows spellings); `--maximum-repetitions 50 --repeat-until fail`.
17. **Hallucinated isolation API**: `.serialized(for: \Env.self)`, `.serialized(for: *)` from the forum pitch, `.taskLocal(_:withValue:)` or `Trait.environment(...)` as if shipped. Compile error on 6.4 (`cannot call value of non-function type 'ParallelizationTrait'`). Check: `swift build --build-tests`; SW-TEST-08 grep. A trailing `//` comment on a `@TaskLocal static var` line also breaks the macro.
18. **A fixed temp path or port**: `/tmp/test.json`, `temporaryDirectory.appendingPathComponent("test.json")`, `127.0.0.1:8080`; or an assertion on `Dictionary` order. Check: SW-TEST-19 grep; `SWIFT_DETERMINISTIC_HASHING=1` to reproduce.
19. **Spawning the real CLI inside SDK core code** (`Process()` with `/usr/bin/env ocx`) and testing it only on machines that have the CLI. Check: SW-TEST-20 grep; the unit run on a machine without `ocx`.
20. **Locating fixtures with `#filePath`, `#file` or `"Tests/Fixtures/x.json"`, declaring `.process("Fixtures")`, or listing the directory to feed `arguments:`** (a deleted fixture silently drops a case). Check: SW-TEST-21 greps and inventory test.
21. **A lines-only coverage gate, or `// LCOV_EXCL_LINE` expecting it to work.** Check: SW-TEST-22 loop and marker grep.
22. **Pasting a pre-NNBD `nonisolated async` helper into an NNBD target, leaving the template's `ApproachableConcurrency` on the test target, `@testable import` everywhere, or reaching for Mockable for a CLI runner.** Check: SW-TEST-23 jq; SW-TEST-24 greps.
23. **Treating a green run on a newer glibc as proof the `setenv` race is harmless.** Check: SW-TEST-18 gate; a cross-run on the `swift:6.3` image.
