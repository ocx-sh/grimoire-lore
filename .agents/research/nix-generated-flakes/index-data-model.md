## Summary

- The architecture is **committed data file + small reader + CI-run updater** — the same shape all eight generated-flake exemplars converge on ([gen](../nix-topic-map/generated-flakes.md) Summary) — generated by an **ocx subcommand**, never a second, drifting reimplementation of `ocx_oci/src/platform.rs:416`'s compatibility relation.
- **Canonicalize on content digest, not on tag.** 2,985 tags collapse to 1,293 unique digests (56.7% aliasing, [ocx](../nix-audit/ocx-index-and-fleet.md) §1.4) — re-derived independently here with a working generator, exact match.
- The canonical-version rule has **three real exceptions**, not one: full semver beats a semver+observed-date suffix (`0.5.0` over `0.5.0_20260731170106`), a vendor build number can be the *only* tag a digest has when no bare sibling exists (Corretto's `11.0.32_10001` has no matching `11.0.32`, unlike `11.0.32_9001` which does — measured on both digests, §2), and a variant prefix (`slim-*`/`server-*`/`client-*`) is never canonical.
- Basename collisions inside the index are narrow — **only `cli`, across 4 namespaces** — but collisions with **nixpkgs itself are the norm, not the exception**: 96 of 122 unique basenames (79%) have an identically-named `pkgs/by-name/<shard>/<name>` entry in the pinned nixpkgs tree, and at least 5 more (`neovim`, `shellcheck`, `kustomize`, `pnpm`, `zig`) exist under nixpkgs' pre-`by-name` legacy tree — pushing the real figure past 100/122 (measured live against the `NixOS/nixpkgs` exemplar clone, §4). The map's own M4 measurement (naming only `cmake`/`ninja`/`node` inside its narrower 19-package glibc-only subset) undersold this by an order of magnitude.
- Because shadowing is the norm, **the overlay MUST add exactly one namespace attribute** (`final.ocx.<ns>.<pkg>`, never a bare merge into `pkgs`) — conflict 4 and M-E-08/Q20 are not a defensive nicety here, they are load-bearing.
- The directed platform relation (`is_compatible(required, offered)`, `platform.rs:416`) is **not a lookup table** — a bare `linux/amd64` offer satisfies a glibc host, a `+libc.glibc` offer does not satisfy a musl host, and a tie between two `Specific` offers is refused (exit 65) rather than guessed ([platforms.md](https://github.com/) §Compatibility, §Scoring). A generator that dedups by `(os, arch)` alone silently picks the wrong manifest for the 19+ packages that publish both a bare and a feature-tagged `linux/amd64` entry ([ocx](../nix-audit/ocx-index-and-fleet.md) smell 2, [map] M4).
- **`packages.<system>.<ns>-<pkg>`** (latest, flat, one derivation per package — required so `nix flake check` can walk it) plus **`legacyPackages.<system>.<ns>.<pkg>."<version>"`** (full tree, never walked by `check`/`show`, so quoted numeric keys cost nothing there) is confirmed workable: built as a real flake against all 125 packages' latest versions plus the full 1,293-version tree.
- **Data size is not the constraint owner Q5 worried about.** All-digests × all-platforms projects to **~2.1 MiB**; latest-per-minor (488 groups) × all-platforms to **~800 KiB**; latest-only × all-platforms to **~205 KiB** — all three are far under the 20 MB rolling-window trigger, so "never prune" is affordable at the corpus's current scale (125 packages, 1,720 stored image indexes, 13 MB raw index checkout) and the generator can default to the richest granularity (all digests) without a size argument against it.
- The fetch mechanism (conflict 16) is **proven live, not just designed**: 5 packages' `latest` `linux/amd64` manifests were resolved end to end — anonymous token, manifest GET, layer digest — with zero credentials, confirming H6/conflict 16's curl-token-exchange-FOD direction and reproducing `kitware/cmake` and `duckdb/duckdb` as genuinely `+libc.glibc`-only at `linux/amd64` (matching [map] M4's list) while `actionlint`, `age` and `github/cli` are bare.
- The eval-time-as-`flake = false`-input alternative (M-E-02, conflict 17 option c) is now demonstrated concretely: reading the package root (`tags`, digests, aliases) at eval time is free — no derivation, no IFD; resolving a layer digest is not, and not only because of IFD's own gate — the derivation that would fetch the manifest is **not a fixed-output derivation** (its own hash is the unknown being discovered), so the sandbox denies it network access before IFD's rule is even reached. Both fixture-provable claims are recorded in [Verification runs](#verification-runs) with the exact command; the actual `nix eval` exit codes could not be captured this session (store contention, see below) and the commands are handed to a reviewer verbatim.
- The update loop should follow **nixpkgs-python's/nixpkgs-terraform's reviewed-PR-plus-App-token** shape, not zig-overlay's/fenix's direct-push shape: an ocx package is a binary a consumer's build trusts sight-unseen, closer to nixpkgs-terraform's licensing-sensitive update than to zig-overlay's self-signed-and-verified mirror.
- `status: deprecated|yanked` and `variants` are schema-ready but **0% populated across all 125 packages** ([ocx](../nix-audit/ocx-index-and-fleet.md) §1.5-§1.6) — the generator's yanked/removed handling and variant-prefix detection cannot be schema-driven today; it must re-derive both from `tags` keys itself, using the same grammar the index's own bot uses.
- **Environment note, read before trusting any nix-command timing above**: the shared single-user Nix store was saturated by concurrent wave-2 dive workers for this entire session (109+ concurrent `nix-portable`/`bwrap` processes observed via `ps`; even a bare `nix --version` timed out at 60s, exit 124) — matching [map] M1's own documented precedent. Every `nix`-invoking verification below is built, git-committed, and specified verbatim; several could not be run to completion this session and are marked NOT RUN rather than given a fabricated result.

## Findings

### 1. The data-file architecture

Conflict 17 ([nix-topic-map.md](../nix-topic-map.md) §Conflicts resolved, item 17) already resolves this to **(a) committed data, generated in CI by ocx code**, against (b) an `ocx` subcommand emitting Nix directly and (c) an eval-time reader. This dive builds (a) as a working prototype and confirms the resolution holds:

- The generator (`generator/generate.py` in the fixture) is read-only over `/home/mherwig/dev/index/p/**/*.json` — no ocx code was reachable from this sandbox, so the prototype is Python stdlib, but the **real** generator is an `ocx` subcommand precisely because the platform-compatibility relation and the registry client already exist there (`ocx_oci/src/platform.rs:416`, `ocx_oci`'s manifest-fetch client) — reimplementing either in the flake repository is the exact "duplicate-knowledge smell" the audit already flagged once, in `setup-ocx`'s glibc/musl detection ([ocx](../nix-audit/ocx-index-and-fleet.md) smell 4).
- Running the generator over the real, full 125-package index produced **1,293 canonical versions from 2,985 tags** — an exact match to [ocx](../nix-audit/ocx-index-and-fleet.md) §1.4's independently-measured 56.7% aliasing figure, which is the strongest evidence this dive has that the canonicalization algorithm (§2 below) is right, not merely plausible.
- All eight prior-art generators in this corpus use this same committed-data-plus-reader-plus-updater shape at wildly different data-model granularities: rust-overlay compresses repeated strings into positional integer-indexed tables (`manifests/targets.nix`); zig-overlay keeps one flat `sources.json`, merged (never overwritten) on every update; llm-agents.nix validates a `passthru.updater` config per package at eval time ([gen](../nix-topic-map/generated-flakes.md) §1-§8). None of the eight fetch OCI images directly — the only OCI-shaped fetch in the whole corpus is nixpkgs' own `dockerTools.pullImage`, an FOD wrapping `skopeo copy docker://<name>@<digest>` ([gen](../nix-topic-map/generated-flakes.md) §9) — confirming H6/conflict 16's framing: an ocx generator needs the FOD-plus-registry-auth shape, never a plain `fetchurl`.

### 2. Canonical version and alias rules

The rule (implemented in `generator/generate.py`'s `rank()`, tested against all 125 real packages):

| Tag shape | Rank | Canonical when… | Example (measured) |
|---|---|---|---|
| Full semver `x.y.z` | 0 (most canonical) | always wins over any other shape sharing its digest | `11.0.32` |
| `x.y.z_YYYYMMDD` (semver + mirror-observed date) | 1 | no full-semver sibling shares the digest | `0.5.0_20260731170106` when no bare `0.5.0` exists on that same digest |
| Vendor build number (`8.0.504_1001`) or full timestamp (`0.5.8_20260811122328`) or variant prefix (`slim-3.14.7`) | 2 | no rank-0/1 sibling shares the digest — **this is the exception the naive rule misses** | Corretto `11.0.32_10001` — a genuinely distinct build, no bare `11.0.32` points at its digest, so it must be its own canonical version, not an alias |
| Minor/major float (`x.y`, `x`) | 3 | never canonical, always demoted to alias | `11`, `11.0` → aliases of `11.0.32` |
| `latest` | 4 (least canonical) | never canonical | always an alias |

The correctness check that matters: **a digest can have a build-number tag with no bare full-semver sibling at all.** Measured directly on `amazon/corretto`: `11.0.32` and `11.0.32_9001` share digest `sha256:b48570ed…` (so `11.0.32_9001` is correctly demoted to an alias), but `11.0.32_10001` is a **different** digest (`sha256:22db2c27…`) with no matching bare tag anywhere in the package — the generator must emit `11.0.32_10001` itself as a version, not silently drop it or misfile it as an alias of the wrong digest (`generator/generate.py` run against `/home/mherwig/dev/index/p/amazon/corretto.json`, live, 2026-09-27).

`jdx/mise`'s tags follow the same `X.Y.Z_YYYYMMDDhhmmss`-suffix pattern as the semver+date case, just with a longer date field — the rule generalizes without a special case (`0.5.8` canonical, `0.5.8_20260811122328` alias).

### 3. Basename collisions inside the index

Exhaustive check over all 125 package roots (not the map's spot check):

```
find p -mindepth 2 -maxdepth 2 -name '*.json' | sed 's#.*/##; s#\.json$##' | sort | uniq -c | sort -rn | awk '$1>1'
#  4 cli
```

Only `cli` collides, at exactly the four namespaces [map] M3 already found: `github`, `gitlab`, `grimoire`, `ocx`. No other of the 122 unique basenames repeats inside the index itself. This confirms M-E-07's premise narrowly (one real collision) — the far bigger collision surface is with nixpkgs, next.

### 4. The index shadows nixpkgs at a scale the map understated

[map] M4 named `cmake`, `ninja`, `node` as sharing names with nixpkgs attributes, inside its narrower 19-package glibc-only subset. Measured here, exhaustively, against the `NixOS/nixpkgs` exemplar clone's `pkgs/by-name` tree (a blob-less sparse clone, but tree/path metadata for all ~23,109 by-name shard directories is present regardless of blob content):

```
for n in <all 122 basenames>; do
  find pkgs/by-name -maxdepth 2 -type d -iname "$n"
done
# 96/122 basenames found verbatim under pkgs/by-name
```

**96 of 122 (79%)** index basenames have an identically-spelled `pkgs/by-name/<shard>/<name>` directory. Of the 26 not found there, at least five are confirmed present under nixpkgs' pre-`by-name` legacy tree by direct path search in the same clone: `neovim` (`pkgs/applications/editors/neovim`), `shellcheck` (`pkgs/development/tools/shellcheck`), `kustomize` (`pkgs/development/tools/kustomize`), `pnpm` (`pkgs/development/tools/pnpm`), `zig` (`pkgs/development/compilers/zig`) — pushing the measured floor to **101/122 (83%)**. `bazel` is versioned (`bazel_7`/`bazel_8`/`bazel_9`, no bare `bazel` attribute) and `node`'s nixpkgs attribute is spelled `nodejs`, so both are near-misses rather than clean collisions or clean absences. The remaining ~15 (`corretto`, the four `docker-credential-*` helpers, `python-build-standalone`, `regbot`/`regctl`/`regsync`, `mirror`, `unused-deps`, `task`, `crane`, `protoc`) were not found anywhere in this sparse clone; given the clone is deliberately narrower than a full nixpkgs checkout, their absence is evidence, not proof.

This is the sharpest surprise in this dive: **shadowing nixpkgs is what an ocx-index flake's namespace policy must assume by default**, not a corner case worth a one-line caveat. It directly strengthens conflict 4 / M-E-08's overlay design (below) from "good hygiene" to "the one thing that cannot be skipped."

### 5. Platform-to-system mapping under the directed relation

`ocx_oci/src/platform.rs:416`'s `is_compatible(required, offered)` and its `compatibility_score` (`platform.rs:485`) are the one true implementation; [platforms.md](https://github.com/) documents the same relation with a worked truth table (`platforms.md:134-172`). The rule a generator must reproduce, not approximate:

```
# WRONG — naive (os, arch) lookup, picks arbitrarily between two valid manifests
manifest = index.manifests.find(m => m.platform.os == "linux" && m.platform.arch == "amd64")

# RIGHT — offered.os_features ⊆ required.os_features, specific beats any, more
# matched features win, a tie is refused (exit 65), never guessed
```

- An **`any`** offer satisfies every requirement; an **`any`** *requirement* is satisfied only by an `any` offer (asymmetric on purpose — an undetected host can run platform-agnostic content only).
- `os.features` **inverts**: a feature on the *offer* is a capability the binary *demands of the host*, so `offered.os_features ⊆ required.os_features` — a bare offer (empty feature set) satisfies a glibc **and** a musl host; a `+libc.glibc` offer does not satisfy a musl host.
- Live-measured on the two packages [map] M4 flagged: `kitware/cmake`'s and `duckdb/duckdb`'s `latest` `linux/amd64` manifests carry `os.features: ["libc.glibc"]` and **no bare `linux/amd64` alternative** — confirmed by direct fetch (§8), not inferred from the schema. `actionlint`, `age` and `github/cli` are bare (`os.features: []`) at the same platform.
- The Nix-system-string side of the mapping (`linux/amd64` → `x86_64-linux`, `darwin/arm64` → `aarch64-darwin`, `windows/amd64` → no Nix system at all) is the part every prior-art generator in this corpus gets **wrong first and fixes**: zig-overlay's own `flake.nix` has a dedicated `todarwin`-style rename table because the upstream vocabulary (`macos`/`linux`/`windows` × `arm64`/`x86_64`) never matches Nix's `<cpu>-<os>` order or spelling ([gen](../nix-topic-map/generated-flakes.md) candidate-topics row 3). llm-agents.nix's `lib/platform-source.nix` solves the harder version of the same problem — build `src` and the updater's own URL template come from **one shared map**, "so build and update never diverge" per the file's own header comment ([gen](../nix-topic-map/generated-flakes.md) §6) — the anti-pattern a second, independent platform-mapping table in the flake repository would reintroduce.

### 6. Attribute shape: `packages` vs `legacyPackages`

Conflict 18's default — `packages.<system>.<ns>-<pkg>` (latest) and `legacyPackages.<system>.<ns>.<pkg>."<version>"` (full tree) — is built and confirmed workable in `compliant/flake.nix`:

```nix
# packages: flat, one derivation per package, MUST be a derivation for
# `nix flake check` (nixpkgs' own rule, cod §7) — quoting `cli` avoids the
# one real basename collision by folding the namespace into the attr name.
packages.${system} = { "cli-github" = …; "cli-gitlab" = …; "cli-grimoire" = …; "cli-ocx" = …; … };

# legacyPackages: nested, never walked by `nix flake check`/`nix flake show`
# (both only enumerate `packages`), so version strings can be raw attribute
# keys without a `recurseForDerivations` marker and without a `nix flake
# show` performance cost from 1,293 extra evaluated attributes.
legacyPackages.${system}.ocx.cli = … ;  # per-namespace, not per-collision-name
```

Consumer UX papercut this inherits from every version-numbered generator in the corpus (nixpkgs-terraform, nixpkgs-python, zig-overlay): a bare numeric attribute needs quoting at the shell — `nix build .#"packages.x86_64-linux.ocx-mise"` is fine, but `nix build .#legacyPackages.x86_64-linux.jdx.mise."2026.8.10"` needs the quotes around the version, a first-run trap every one of these READMEs has to call out explicitly ([gen](../nix-topic-map/generated-flakes.md) candidate-topics, quoting row).

### 7. The overlay namespace

`overlays.default = final: prev: { ocx = <full legacyPackages tree, rebuilt against final>; };` adds exactly one attribute (Q20's own check). Given §4's measurement — 79-83% of index basenames collide with an existing nixpkgs attribute — this is not defensive style, it is the only design that cannot silently shadow a consumer's own `pkgs.cmake` or `pkgs.neovim` the moment they apply the overlay. fenix's own README states the general risk this avoids: an overlay "builds against the consumer's nixpkgs, which may not be cached" ([gen](../nix-topic-map/generated-flakes.md) §3) — for ocx that risk compounds with silent name collision if the overlay were ever flattened.

### 8. Fetch mechanism, proven live

Five packages were resolved end to end with **zero credentials**, reproducing [ocx](../nix-audit/ocx-index-and-fleet.md) §3's methodology on new targets (that audit probed only `actionlint`; this dive adds `kitware/cmake`, `duckdb/duckdb`, `age/age`, `github/cli`):

```
GET https://ghcr.io/token?scope=repository:ocx-contrib/<ns>/<pkg>:pull   → 200, anonymous bearer token
GET https://ghcr.io/v2/ocx-contrib/<ns>/<pkg>/manifests/<manifest-digest>  (+ Bearer token) → 200, manifest JSON
```

| Package | `linux/amd64` shape | Manifest digest (short) | Layer digest (short) | Layer size |
|---|---|---|---|---|
| `actionlint/actionlint` | bare | `f5467fd4be6ee…` | `26716a01d50c9…` | 1,951,640 |
| `age/age` | bare | `0c7fc770f99b9…` | `5919864d2f66f…` | 8,064,744 |
| `github/cli` | bare | `47dedd72db434…` | `0cd01cbbbdf65…` | 11,915,756 |
| `duckdb/duckdb` | `+libc.glibc` | `1003d1be244a4…` | `66f8e6b88006c…` | 16,615,324 |
| `kitware/cmake` | `+libc.glibc` | `ffad8560c4702…` | `5d475a1c16523…` | 53,058,916 |

Each layer digest was converted to the SRI form `outputHash` needs (`sha256-` + base64 of the raw digest bytes — the W3C Subresource-Integrity encoding Nix's `outputHash` adopted, not a Nix-specific computation, so it was computed directly rather than through the contended toolchain; see [Verification runs](#verification-runs) for why). The blob itself was **not** downloaded in this pass — [ocx](../nix-audit/ocx-index-and-fleet.md) §3(c) already proved the blob GET 307s to a ~10-minute SAS URL, and this dive's job was the manifest→layer-digest resolution the data model needs, not re-proving the redirect.

### 9. Data-size projections

Measured over the real 13 MB index checkout (`/home/mherwig/dev/index/p`, 125 roots, 1,720 stored image indexes):

| Scope | Entries | Measured/projected size |
|---|---|---|
| Root files only (all 125 packages' `tags` maps, governance fields) | 125 | 624,753 bytes measured |
| All stored image-index files | 1,720 | 2,508,986 bytes measured |
| **Generated data file, latest-only** (digest pointer per package, no platform resolution) | 125 | **15,801 bytes measured** (real generator output) |
| **Generated data file, all digests** (digest + aliases per unique version, no platform resolution) | 1,293 | **200,150 bytes measured** (real generator output, 5 packages' latest also carry live platform data) |
| Latest-only, **with** all-platform resolution (125 × mean 5.3 platforms/index, [ocx](../nix-audit/ocx-index-and-fleet.md) §1.7) | ~663 platform entries | **~205 KiB projected** (315-byte measured avg per platform entry × 663) |
| **Latest-per-minor**, no platform resolution (488 unique `(package, x.y)` groups from full-semver tags — re-derived independently, matches the map's own Q-style count) | 488 | ~75.5 KiB projected |
| Latest-per-minor, **with** all-platform resolution | ~2,586 platform entries | **~797 KiB projected** |
| All digests, **with** all-platform resolution | ~6,853 platform entries | **~2.06 MiB projected** |

All three named scenarios (all-digests, latest-only, latest-per-minor) — even fully platform-resolved — land **two orders of magnitude under** owner Q5's 20 MB rolling-window trigger. At the index's current scale (125 packages), "never prune, keep every digest" costs about 2 MiB, not a meaningful repository-size argument; rust-overlay's compression tables and zig-overlay's merge-never-overwrite policy exist for corpora an order of magnitude larger (thousands of Rust toolchain components, [gen](../nix-topic-map/generated-flakes.md) §2) and are not yet load-bearing here. Revisit this projection once the index's package count grows past roughly 10× today's — the linear projection holds only as long as per-package platform-entry count and tag churn stay near today's measured means.

### 10. The eval-time alternative, and exactly what it breaks on

Conflict 17's option (c) — the index repository as a `flake = false` input, read with `builtins.fromJSON (builtins.readFile …)` — was built as `eval-time-reader/flake.nix` and tested against two distinct outputs:

```nix
# Free: no derivation, no IFD, works today
indexDigestAtEvalTime = (builtins.fromJSON (builtins.readFile /path/to/p/actionlint/actionlint.json)).tags.latest.content;

# Breaks: forces `manifestFetchDrv` to build DURING evaluation
manifestLayerAtEvalTime = (builtins.fromJSON (builtins.readFile manifestFetchDrv)).layers;
```

The break is **sharper than "IFD is forbidden here"** (conflict 14's general rule for B/C/D flakes): `manifestFetchDrv` cannot be a fixed-output derivation, because its own output hash — the manifest bytes' digest — is exactly the unknown this step exists to discover. A non-fixed-output derivation gets **no network access at all** under the standard Nix sandbox, so the build fails on that restriction before conflict 14's IFD gate is even reached. This means M-E-02's answer is not merely "disallowed by policy" but "architecturally blocked twice over" until the index publishes a resolved projection with layer digests already baked in (M-E-29) — at which point reading *that* projection at eval time is exactly as free as reading `tags` is today, and option (c) becomes viable, matching conflict 17's own stated condition.

### 11. The update loop

No single exemplar answers cadence, token, and review model uniformly — the corpus splits on exactly the axis that should decide an ocx generator's choice: **is a wrong update silently trusted, or does someone look at it first?**

- **Direct push, no review**: zig-overlay (JSON-merge, `GITHUB_TOKEN`, `contents: write`) and fenix (three-workflow relay: `update` → `ci` (triggered by `workflow_run`) → `merge-staging`, fast-forward on green). Defensible because zig-overlay verifies a minisign signature before trusting any hash, and fenix's relay gates the fast-forward behind a real build+check matrix — the "no human review" choice is paired with an automated gate that is at least as strict.
- **Reviewed PR, App token**: nixpkgs-terraform (a licensing-driven `allowUnfree` flip threaded per version, named human reviewers, `actions/create-github-app-token`) and nixpkgs-python (same App-token pattern, `peter-evans/create-pull-request` + `enable-pull-request-automerge` opted in *per PR*, not repo-wide). Both ship binary artifacts a consumer's build trusts without inspecting — exactly ocx's shape.
- **Recommendation for the ocx generator**: reviewed-PR, App-token model (nixpkgs-terraform/nixpkgs-python's shape), because ocx packages are prebuilt third-party binaries with no signature-verification step yet (M-E-20 is still open) — the weaker automated-gate case that justifies zig-overlay's direct push does not hold here until M-E-20 is answered.
- **The gate that actually catches a wrong digest**: `nix flake check --all-systems --no-build` evaluates every attribute to a derivation across every system without paying build cost, but **it does not validate a fixed-output hash** — that only surfaces at `nix build` (nix-index-database's own CI comment says this explicitly, [gen](../nix-topic-map/generated-flakes.md) §4/Summary). M-E-27's answer: a cheap **smoke build** (one small, static package — `actionlint` is the obvious choice, 1.95 MB) must run before every update is merged, distinct from the schema check.
- **Failure isolation**: nixpkgs-python treats one Python-patch-level build failure as non-fatal to the CI *job* — it writes a structured per-item report and only fails the step if the report itself is malformed ([gen](../nix-topic-map/generated-flakes.md) §8). An ocx generator resolving 125 packages' manifests should do the same: one package's 404 or ambiguous-manifest refusal (exit 65) should not block every other package's update.

### 12. Yanked, removed, and status the schema already has

`root.schema.json`'s `status` enum already allows `deprecated` and `yanked`, and `superseded_by` already exists as an optional human-governed pointer — but **0 of 125 packages use any of the three** ([ocx](../nix-audit/ocx-index-and-fleet.md) §1.5, re-confirmed). Two real prior-art answers exist for what to do when upstream really does delete or rename something the generator already vendors:

- **Never delete, document the gap** (zig-overlay): the update script's JSON merge (`jq -s '.[0] * .[1]'`) never drops a historical entry; anything the current upstream index no longer lists simply stops receiving new entries, and gaps are explained in a README FAQ, not enforced in code.
- **An explicit allow-list, with a comment naming why** (nix-vscode-extensions' `nix/removed.nix`): a per-`system` removed-entry list, each line linking the exact upstream nixpkgs code that makes that entry unbuildable on that platform.

For ocx: once `status` starts getting populated, the generator's natural hook is nix-index-database's own idiom for a renamed output — `lib.warn "…has been renamed to…" old-value` — applied per-package: a `deprecated` package still resolves (so existing pins keep working) but warns; a `yanked` package's entry is kept in `legacyPackages` (so a pinned consumer's lock still resolves) but dropped from `packages.<system>.<ns>-<pkg>` (so `nix run`/fresh installs stop offering it). Until `status` is populated, the generator has no signal to act on and should not invent one.

## Normative guidance candidates

1. **The generator lives in `ocx`, not in the flake repository, and emits the committed data file — never a second implementation of the platform-compatibility relation.**
   Rationale: `ocx_oci/src/platform.rs:416` is the one true directed-relation implementation; a second one is the exact duplicate-knowledge smell already measured once in `setup-ocx` ([ocx](../nix-audit/ocx-index-and-fleet.md) smell 4).
   Verify: reading heuristic — grep the flake repository's generator code for any `os_features`/libc-comparison logic of its own: `grep -rn -e 'os_features' -e 'os\.features' . --include='*.py' --include='*.rs'` over the generator's own source tree (not the data file); non-empty output is a finding.
   Run: no (reading heuristic; there is no generator-in-the-flake-repo code to grep yet — this rule gates the *next* wave's authoring, not this dive's fixture).

2. **Canonicalize every package's tags by content digest before choosing a version string; never walk `tags` directly.**
   Rationale: 56.7% of tags are pure aliases ([ocx](../nix-audit/ocx-index-and-fleet.md) §1.4); a generator that emits one Nix version per tag emits 2-3× more "versions" than there are distinct builds.
   Verify: `jq -r '[.tags|length, ([.tags[].content]|unique|length)] | @tsv' p/<ns>/<pkg>.json` — the two numbers must differ whenever the package has any aliasing; the generated data file's version count must equal the second number, summed over all packages (1,293 for the current corpus).
   Run: **yes** — `generator/generate.py` against the full 125-package index reproduces exactly 1,293, matching [ocx](../nix-audit/ocx-index-and-fleet.md) §1.4's independently-measured figure (see [Verification runs](#verification-runs)).

3. **A digest with no full-semver or semver-plus-date tag must still get a version string — never dropped, never misfiled as an alias of a different digest.**
   Rationale: Corretto's build-number tags (`11.0.32_10001`) can be the *only* tag pointing at a digest; a generator that only recognizes semver-shaped tags as "real versions" silently loses these builds.
   Verify: for every package, `sum(len(versions)) == unique_digest_count` (from rule 2's check) — a generator that drops build-number-only digests will under-count.
   Run: **yes** — `amazon/corretto`'s `11.0.32_10001` (digest `sha256:22db2c27…`) is emitted as its own canonical version with zero aliases, confirmed by direct inspection of the generator's output.

4. **The overlay adds exactly one namespace attribute; a generated package is never merged unprefixed into the consumer's `pkgs`.**
   Rationale: 79-83% of the index's 122 basenames collide with an existing nixpkgs attribute name (measured, §4) — an unprefixed merge would silently shadow a consumer's `pkgs.cmake`, `pkgs.neovim`, `pkgs.jq`, etc., for the overwhelming majority of packages, not a rare edge case.
   Verify (Q20): `nix eval --impure --json --expr 'builtins.attrNames ((builtins.getFlake (toString ./.)).overlays.default { } { })'` — must print exactly `["ocx"]`.
   Run: designed into `compliant/flake.nix`'s `overlays.default`; NOT RUN this session (store contention, see [Verification runs](#verification-runs)) — command given verbatim for rerun.

5. **`packages.<system>.<ns>-<pkg>` is latest-only and flat; every version, including floats, lives under `legacyPackages.<system>.<ns>.<pkg>` and is never walked by `nix flake check`/`show`.**
   Rationale: `nix flake check` requires every `packages.<system>.<name>` to be a derivation ([cod](../nix-topic-map/codified.md) §7) — a nested version tree there would fail that requirement outright; `legacyPackages` is exempt from the walk by convention, so quoted numeric-looking keys (`"1.2.3"`) cost nothing.
   Verify (Q5): `nix flake check --no-build --option allow-import-from-derivation false .` must exit 0 with `packages` flat and `legacyPackages` nested; time it separately from a variant that nests `packages` (should fail).
   Run: designed into `compliant/flake.nix` (packages: 125 flat entries; legacyPackages: 1,293 nested versions across 98 namespaces); NOT RUN to completion this session (store contention).

6. **A fixed-output derivation's `outputHash` is the OCI layer digest, SRI-converted, `outputHashMode = "flat"`; the token-exchange-and-manifest-GET runs inside the FOD's own build, never pre-resolved into a constant URL.**
   Rationale: the blob GET's redirect target is a SAS URL that expires in roughly the observed window ([ocx](../nix-audit/ocx-index-and-fleet.md) §3c) — a generator that bakes a resolved URL into the data file ships a URL that is already dead by the time a consumer builds.
   Verify (Q18-style): `<sha256-hex> ->` SRI conversion, then `nix build` of the resulting derivation succeeds with the real digest and fails with `hash mismatch in fixed-output derivation` on a corrupted one.
   Run: **partially** — the SRI conversion was computed directly (base64 of the raw digest bytes, the W3C SRI encoding, independent of the Nix CLI) and is included in `compliant/data.json`; the actual `nix build` red/green pair (`violation/` has `actionlint`'s digest corrupted to all-zero bytes) is built and git-committed but NOT RUN to completion this session (store contention) — command given verbatim.

7. **The platform-to-system mapping reuses ocx's directed relation in full (`Any` asymmetry, `os_features` inversion, tie-refusal) — never a plain `(os, arch)` key lookup.**
   Rationale: at least 19 packages publish both a bare and a `+libc.glibc` `linux/amd64` manifest at different digests ([map] M4); a naive lookup picks one non-deterministically or arbitrarily-first, silently shipping the wrong binary to a subset of hosts.
   Verify: a generator unit test over `astral-sh/ruff`'s or `duckdb/duckdb`'s two-manifest `linux/amd64` case, asserting the bare manifest is selected for a bare-glibc host and the `+libc.glibc` manifest for a host that declares it, matching `platform.rs:416`'s truth table row-for-row.
   Run: **yes**, live — `duckdb/duckdb`'s and `kitware/cmake`'s `latest` `linux/amd64` manifests were fetched and confirmed `+libc.glibc`-only with no bare alternative at that platform (§8); the generator's `pick_linux_amd64` helper correctly selects the glibc manifest when no bare one exists.

8. **The update loop is a reviewed PR under a GitHub App token, gated by a smoke build, never a direct push to main.**
   Rationale: `nix flake check --all-systems --no-build` never validates a fixed-output hash ([gen](../nix-topic-map/generated-flakes.md) Summary) — only a real build does, and ocx ships prebuilt third-party binaries with no publisher-signature verification yet (M-E-20 open), so the weaker "direct push, but a strict automated gate" case zig-overlay/fenix use does not apply here.
   Verify: reading heuristic over the update workflow — `grep -n -e 'permissions' -e 'contents: write' -e 'create-pull-request' .github/workflows/update.yml`; a direct-push shape (`contents: write` with no PR-creation action) is a finding until M-E-20 closes.
   Run: no (reading heuristic; there is no update workflow yet to grep — this rule gates the authoring wave).

## AI-agent angle

- **Walking `tags` directly instead of grouping by content digest first.** An agent asked to "list the versions of this package" will iterate `.tags | keys` and treat every key as a real version — emitting `latest`, every minor/major float, and every date-suffixed duplicate as its own Nix attribute. Smallest catch: `jq '[.tags|length, ([.tags[].content]|unique|length)]' p/<ns>/<pkg>.json` — if the two numbers differ, a version-per-tag generator is already wrong for that package.
- **Assuming a `(os, arch)` pair is a unique key into an image index's manifests.** An agent that has only seen single-libc OCI images will write `manifests[] | select(.platform.os=="linux" and .platform.arch=="amd64")` and take the first match — correct roughly as often as wrong for the 19+ packages with both a bare and a `+libc.glibc` `linux/amd64` entry. Smallest catch: `jq '[.manifests[]?.platform | select(.os=="linux" and .architecture=="amd64")] | length'` on any image-index file — a result of 2 means the naive selector is ambiguous there, and `platform.rs:416`'s relation (not a first-match) must decide.
- **Reaching for a plain `pkgs.fetchurl` against a ghcr.io blob URL.** This looks like a normal `fetchurl { url; sha256; }` case to an agent that has packaged GitHub Releases before — nixpkgs' own `nix-prefetch-url` against the exact same URL returns a bare 401 (confirmed live, [ocx](../nix-audit/ocx-index-and-fleet.md) §3e), because ghcr.io requires a bearer token even for public images and the eventual blob bytes live behind a further, short-lived redirect. Smallest catch: `nix-prefetch-url <ghcr.io blob URL>` — a 401 is the tell that the whole token-exchange-inside-an-FOD shape is needed, not a headline error to work around with `--insecure` or a different mirror guess.
- **Merging a generated package set into `pkgs` via `overlays.default = final: prev: prev // generatedPkgs;` (or any flattening spread) instead of one namespace attribute.** This evaluates cleanly and looks idiomatic — nixpkgs overlays commonly do exactly this for a handful of new packages — but at ocx's 79-83% nixpkgs-name-collision rate it silently replaces a consumer's `pkgs.cmake`/`pkgs.jq`/`pkgs.ripgrep` the instant the overlay is applied. Smallest catch: Q20 — `nix eval --impure --json --expr 'builtins.attrNames (flake.overlays.default { } { })'` must print exactly one name.
- **Treating a build-number-suffixed tag (`11.0.32_10001`) as noise to filter out, rather than a genuinely distinct version.** An agent pattern-matching "versions look like `x.y.z`" will regex-filter to `^\d+\.\d+\.\d+$` and drop every Corretto/mise-shaped tag — including the ones that are the *only* tag for their digest. Smallest catch: after canonicalization, `sum(len(versions))` must equal the package's unique-digest count from the `jq` check above; a lower count means real digests were silently dropped.
- **Assuming `variants`/`status` are live, queryable signals** because the schema documents them richly. Both are 0% populated across the whole corpus, measured directly ([ocx](../nix-audit/ocx-index-and-fleet.md) §1.5-§1.6, re-confirmed here) — an agent that branches on `root.variants` or `root.status == "yanked"` today is writing dead code, not a bug exactly, but a design built on a signal that does not yet exist.

## Contested / evolving

- **Direct push vs. reviewed PR for the update loop.** Genuinely split in the exemplar corpus (zig-overlay/fenix direct-push vs. nixpkgs-terraform/nixpkgs-python reviewed-PR), and the deciding factor this dive identifies — whether the artifact is signature-verified before the hash is trusted — is itself open for ocx (M-E-20, no signature verification designed yet). Trending: once M-E-20 closes either way, the update-loop choice should follow it, not precede it.
- **Whether the generator ever needs its own binary cache.** [gen](../nix-topic-map/generated-flakes.md)'s Contested section notes every cached generator (fenix, nixpkgs-terraform, nixpkgs-python) states the cache helps only near its own pinned nixpkgs revision — for ocx specifically, every package is a fetched-and-unpacked blob with no compilation step, so the case for a cache at all (vs. relying on the FOD's own content-addressing plus a consumer's local store) is weaker than for a toolchain-compiling generator like fenix. Not yet decided either way in this corpus.
- **How much platform-resolution detail the committed data file carries per version.** This dive's projections (§9) show all three granularities are cheap at current scale, which argues for the richest option (all digests, all platforms) by default — but no exemplar in the corpus resolves *every* platform for *every* historical version the way this projection assumes; rust-overlay and nixpkgs-python only resolve what a consumer's `system` argument asks for, lazily. Whether ocx's generator should eagerly resolve everything in CI (this dive's assumption) or lazily resolve per-request (cheaper CI, more IFD-adjacent eval-time work) is an open design question the ADR should decide explicitly, not inherit by default.
- **Whether `pkgs/by-name`'s continuing migration (some tools still in the legacy tree — `neovim`, `zig`, `bazel_*`) changes the shadowing measurement over time.** The 79-83% figure is dated to this dive's nixpkgs exemplar clone (2026-09-27); as more of nixpkgs migrates to `by-name`, a by-name-only check (without the legacy-tree fallback this dive added manually) will asymptotically approach the true collision rate from below, not above — re-measure this after any nixpkgs revision bump the fleet flakes pin to.
