All dates 2026-10-10. Measurements are Swift 6.4.0 and 6.3.3, Linux x86_64, glibc 2.43, ArgumentParser 1.8.x (`swift-argument-parser@efd239f0055b`; the follow-up resolved 1.8.2), swift-service-lifecycle 2.12.1, swift-log 1.16.1 and swift-configuration 1.2.2, reached through `swift-tools/run.sh`. ## Verdict

Two dives fed this group: [ces] (entry point, exit table, streams, signals) and [svc] (the root hook, log bootstrap, configuration, `ServiceGroup`, aggregate errors, the remaining Rust CLI rows). The position below is both, reconciled against the audits, the fleet's Rust contract (`rules/rust-quality/cli-contract.md`), the live `ocx` and `grim` sources, and fresh re-runs. The conflicts this reconciliation settled, several of them corrections to [ces] or [svc], are listed under "Conflicts resolved" at the start of the next section; every change to a rule that existed before the 2026-10-10 revision is in the "Revision log". A verification pass the same day (FXC) built the pieces the first fold-in had only amended, planted the checks that had never been planted, and found three recorded checks that stayed green on a likely violation one sentence that overclaimed (a closed stdout never reaching EBADF) and one exemplar citation that was wrong (`ConfigCommand.swift` does gate on stdin); each is fixed in place and listed in the log.

1. **Shape.** A Swift CLI is an `@main` root `AsyncParsableCommand` (ArgumentParser 1.8.0 or later, which needs Swift 6) whose every process status comes from one `UInt8`-backed `Status` enum (SW-CLI-01, -02). The root owns parse, run, render, classify, flush and one terminator, `Stdio.terminate` (SW-CLI-03, -23); `await Self.main(nil)` is no longer the hook. This binds CLI executables and the executable target of a server. A library or the SDK never calls `exit`, `signal`, `fatalError` or `LoggingSystem.bootstrap`.
2. **The table.** Pin the core that `ocx`, `grim` and `ocx-sdk-python` already share: 0, 1, 64, 65, 69, 74, 75, 77, 78, 79, 80, 81. A binary allocates 82 upward for itself. Follow the live `ocx` enum, not the lore Rust file ("83-99 unassigned"). Never assign 2-63 or 100-255: 128+n means "killed by signal n" (measured 130, 132, 137, 141, 143; 134 and 139 from the failure scout). A refused prompt is 64, an unparsable configuration value is 78, a mixed-status batch and any `ServiceGroupError` are 1.
3. **SIGPIPE: exit 0, not 141.** Fleet CLIs ignore SIGPIPE in their first statement and exit 0 on EPIPE (SW-CLI-08); libraries never call `signal`. This follows the fleet contract (Rust CLI-05) against the platform norm. The Swift runtime leaves SIGPIPE at the kernel default (`SigIgn 0`, measured), so `cli big | head -1` dies with 141 and no message (re-run: no hook 141, any hook 0). The flush check must exempt EPIPE, or the same command exits 74 (SW-CLI-09, -23; measured).
4. **`print` alone is not a safe output path.** stdout is block-buffered off a TTY, `print` to `/dev/full` exits 0, and a trap loses unflushed lines. A successful run ends with `fflush(stdout) == 0 && ferror(stdout) == 0` or exits 74, and the check sits in the root hook, because `--help`, `--version` and `--generate-completion-script` leave through `exit(withError:)` and never reach code placed after `await Self.main(nil)` (SW-CLI-09, -23; measured, `--help >/dev/full` exits 0 under the simple hook, 74 under the full one). The C globals are named in one `Stdio.swift` behind `@preconcurrency import Glibc` (SW-CLI-07); output goes through one funnel that records the first errno (SW-CLI-24). The legacy `FileHandle.write(_:)` is banned (SW-CLI-04).
5. **An uncaught throw is a crash.** A throw escaping top-level code or a bare `main() async throws` exits 132 with an 88-line backtrace, not 1 (SW-CLI-02). Only a catching entry point yields a `Status`.
6. **Streams, colour, prompts and progress.** Results (or the JSON payload alone) go to stdout; everything else goes to stderr, reported once per channel (SW-CLI-05). Under `--format json` a failure adds one envelope on stdout (SW-CLI-29). `NO_COLOR` means present and non-empty; 6 of 7 corpus read sites get that wrong (SW-CLI-06). Prompts need a stdin TTY and no truthy `CI`, else exit 64 naming `--yes` (SW-CLI-31); progress draws on stderr only on a TTY, with `CI` unset and text format (SW-CLI-30). Error text that quotes argv is sanitized, because ArgumentParser echoes raw ESC and BEL (SW-CLI-25).
7. **Signals.** A finite command that handles Ctrl-C uses `signal(SIGINT, SIG_IGN)` plus a `DispatchSource` feeding an `AsyncStream`; it cleans up, flushes, then `signal(sig, SIG_DFL); kill(getpid(), sig)`, so the shell sees 130 or 143; `raise()` from the cooperative pool is silently dropped (SW-CLI-10, -11, -22). A server uses `ServiceGroup` and must list `gracefulShutdownSignals: [.sigterm, .sigint]`, because the 2.x defaults are `[]` and the 2020 blog says otherwise (SW-CLI-20); it bounds the escalation (SW-CLI-21) and exits 0 after a graceful stop (SW-CLI-22).
8. **Verification host.** Linux only. Contract tests that assert 64 or flush-on-exit stay off Windows and WASI until a leg on that platform has run them (SW-CLI-12).
9. **Logging, configuration, batches.** `LoggingSystem.bootstrap` runs once, in the executable, naming stderr, after the level is resolved and before any logger exists (SW-CLI-15, -16). Configuration resolves in one function, flag > env > project file > user file > system file > default, with the participating `@Option` optional and undefaulted, proven by a 2^n table test (SW-CLI-17); files are located through one spec-exact XDG helper (SW-CLI-18). A batch collects results, prints `K of N failed` and exits with the shared status or 1 (SW-CLI-26). The global flags live in one `GlobalOptions` (SW-CLI-28).
10. **Boundaries.** Child-status mapping (`.signaled(n)` to 128+n, owner Q6) belongs to SW-IO and SW-API. Trap policy (`fatalError`, `precondition`) belongs to SW-ERR. Cleanup under cancellation (async `defer`, the cancellation shield, its deadline) belongs to SW-CONC (`swift-concurrency/backpressure-and-cleanup.md`, rules 32 to 34 there, measured with the second-press escape of SW-CLI-11 and the signal-source isolation trap).
11. **Documented gaps** (the research established them; no rule here closes them):
    - Windows and WASI: `UnixSignals` compiles to an empty stream, so `gracefulShutdownSignals` is a silent no-op there and a bridge to `triggerGracefulShutdown()` is unresearched; ArgumentParser's Windows `_exit` flush and its 160 usage code stay read only. The hook's usage remap and its `#if !os(WASI)` guard compile and run on Linux 6.4.0 and 6.3.3, where the remap is a no-op: the 160-to-64 branch itself has never executed.
    - WASI: `Self.exitCode(for:)` returns `ExitCode(1)` for a usage failure and for a plain failure, so the 64 pin of SW-CLI-12 cannot be reached through the public API on WASI (reading).
    - No corpus exemplar implements a five-tier precedence, an error envelope, a `K of N` line, a flush check at the root, or a TTY-and-`CI` gate on progress and prompts; rules 17, 23, 26, 29, 30 and 31 rest on fixtures, not on prior art.
    - Foundation's XDG mapping covers cache and data only; config and state need the helper. Windows and macOS locations are unverified.
    - swift-configuration 1.2.2 treats an empty environment variable as set and then fails the parse (measured; no option for it).
    - A closed stdout (`>&-`) reaches EINVAL in an async root (the runtime's epoll descriptor takes fd 1) and EBADF in a plain synchronous `ParsableCommand` root (measured, FXC `fxs ok >&-`: `Bad file descriptor`, 74 on 6.4.0 and 6.3.3). Both exit 74 under the hook. Rust's std treats EBADF on stdout as success, so for a synchronous root the 74 is a choice that differs from Rust, not a difference by construction (D7). An earlier version of this line said a Swift process never reaches EBADF; that overclaimed.
    - Flush failure against an earlier non-success status: measured. `fx fail --format json >/dev/full` exits 74 under the hook as written (the lost envelope replaces 65) and 65 under a variant that only upgrades a success (FXC `-DKEEPSTATUS`); `fx fail >/dev/full` in text mode prints nothing to stdout and keeps 65 either way. SW-CLI-23 keeps "74 wins" (a retry wrapper keyed on 75 must not retry into a full disk); no source decides it (D10).
    - The orchestrator grace periods (Kubernetes 30 s, Docker 10 s) are documentation, not measured; the harness window was 3 s.
    - Rust CLI-03, -04 and -08 are MUST in the fleet file; their Swift ports are SHOULD (owner decision D9).

## The ruleset

Severity follows the house tiers: MUST = Block, SHOULD = Warn, CONSIDER = Suggest. "Watched" says what went red on a planted violation and green on its twin: **[ces row x]** is a row of [ces] "Verification runs"; **[svc VR-n]** is a group of [svc] "Verification runs"; **[re-run]** means a consolidation repeated it (the first on 2026-10-10, the revision the same day). Greps are run from the repo root, and **empty output is a pass** unless the line says otherwise. [svc] names its grep checks V15a to V25a; the map to rule IDs is V15 = SW-CLI-15, V16 = -17, V17 = -20, V19 = -23, V20 = -26, V21 = -28, V23 = -30, V24 = -31, V25 = -32. ### Conflicts resolved

Each item is a place where [ces], [svc], an audit, the map, or the fleet's sources disagree, with the decision. The first ten were settled by the first consolidation; the rest by the 2026-10-10 revision, the last six (marked "verification pass") by the same-day pass that built and planted what the revision had only amended and re-read the exemplar citations it had taken from [svc].

- **Table drift, three ways.** The lore Rust file says 83-99 are unassigned. `ocx-sdk-python@80136dde4162:src/ocx_sdk/_errors.py:28-51` assigns 83-86. `ocx@5de9d777eb7d:crates/ocx_exit/src/exit_code.rs:44-62` assigns 82-87 (87 is `RegistryDeleteUnsupported`; [ces] stops at 86). `grimoire@4650ad830375:src/cli/exit_code.rs:49-55` stops at 81 (`OfflineBlocked`, where `ocx` says `PolicyBlocked`). Decision: the shared core above is pinned; 82+ is per-binary; the live `ocx` source wins over the lore file. The drift is reported to the Rust set, not patched here.
- **`fflush` after `print` on `/dev/full`.** [cfg] §5.2 saw `fflush` return 0; [ces] saw -1, then 0. The two observations are consistent. The [cfg] fixture prints a 1 MiB payload (`streams/main.swift`), so the buffer drains inside `print` and the error flag is already set when `fflush` runs. The [ces] probe `p1.swift` prints 7 bytes, so `fflush` holds the data and fails once (-1, `errno` 28). `ferror(stdout)` is the sticky witness in both, which is why SW-CLI-09 demands both calls. The payload-size explanation is reasoned from the two fixtures' sources, not run: `p2.swift`, the long-output probe, has no recorded output. The same mechanism is why errno must be recorded at the failing write (SW-CLI-24).
- **`@preconcurrency` ordering.** [ces] Summary and SW-CLI-07 rationale say "a later plain `import Foundation` re-breaks it". The probes say the opposite. Re-run on 6.4.0: `@preconcurrency import Glibc` then `import Foundation` compiles (`t3`, exit 0); `import Foundation` then `@preconcurrency import Glibc` fails (`t4`, exit 1). The preconcurrency import must come first. The rule text uses the measured order. With `import FoundationEssentials` the order stops mattering (see the FoundationEssentials item below).
- **Blanket-catch EPIPE twin.** [ces] cites `b-filehandle = 0` as proof that `write(contentsOf:)` turns EPIPE into exit 0. The fixture (`Cli.swift:71-80`) is `catch { throw Status.success.exitCode }`, which also maps ENOSPC to success. It proves nothing about discrimination. The verified green path stays stdio plus `ferror` plus `errno == EPIPE` (`b-green`); the throwing-write route needs an explicit EPIPE match, which the verification pass then ran (FXC `fh`: the blanket catch exits 0 on `>/dev/full`, the discriminating one 74, both 0 on `| head -1`; SW-CLI-04).
- **"15:1 print to stderr" ratio.** [ces] SW-CLI-11 calls it "diagnostics printed to stdout at 15:1". [pkg] counted all `print(` calls (741) against explicit stderr writes (48) in 18 CLI repos, and says ArgumentParser carries the diagnostics. Most of those prints are results. The evidence for SW-CLI-05 is the verified sites in the Applied section, not the ratio.
- **NO_COLOR coverage.** The domain scout says no exemplar reads it; [ces] says six sites in four repos. Re-measured: 7 read sites in 5 repos (adds `container@f70ecbb926d9:Sources/ContainerBuild/Builder+Start.swift:70`, presence-only forwarding). Only `swift-testing` is spec-correct. The recorded grep catches 5 of the 6 deviating sites and misses `tuist@2f6ac74754bf:cli/Sources/TuistEnvironment/Environment.swift:219` (truthy-only).
- **Exit-test adoption.** [ces] says only swift-testing and its dependents use `processExitsWith`. [gates] counts 238 uses in 9 repos (nio 41, vapor, SwiftPM and others); a raw grep finds 314 text hits in 10 repos. The audit number stands (counting discipline, [map] conflict 21). The substance of [ces] holds: none of those asserts a CLI exit status, and `container`, `containerization`, `swiftly` and ArgumentParser use 0.
- **`fatalError` in the process-end grep.** [ces] C2 bans `exit`, `_exit` and `fatalError` together, but [pkg] counts 596 `fatalError(` in 18 CLI-shaped repos (mostly tool internals). Decision: `exit` and `_exit` outside the entry point are the MUST; `fatalError` as the way to report an operational failure is the same defect (exit 132), but programmer-error traps are SW-ERR's, so the `fatalError` grep is a tell.
- **SwiftLint `custom_rules` as the delivery vehicle.** [map] conflict 1 names it the optional vehicle for grep bans. [ces] row n shows the research SwiftLint 0.65.1 skips `custom_rules` ("requires SourceKit and SourceKit access is prohibited"). No SwiftLint verification is claimed; the greps below are the checks. The sibling `swift-gates.md` (SW-GATE-11, -26) later showed that the SourceKit-enabled image runs `custom_rules` and that the static binary only skips them; it ships them as an advisory second reader and the grep script as the gate. This file's greps were not ported: the file-absence pipelines (`grep -rl X | xargs -r grep -L Y`) have no single-file regex form.
- **Usage code.** [map] conflict 20 says "keep 64 and document the Windows divergence"; [ces] says pin 64 with `classify`. Decision: pin and document (SHOULD, Windows unverified). Reading the source also shows the [ces] `classify` snippet misfires on WASI (SW-CLI-12).
- **The flush-check placement and the EPIPE exemption (revision; corrects SW-CLI-08 and SW-CLI-09).** The first consolidation said the flush check goes "after `await Self.main(nil)` returns in the root `main()`" and recorded that the placement "was not run". [svc] ran it. `exit(withError:)` terminates inside `main(_:)` for `--help`, `--version`, `--generate-completion-script` and every error, so the code after the call runs on the success path only: `--help >/dev/full` exits 0 under that hook and 74 under a hook that owns parse, run and catch (re-run). A plain `fflush == 0 && ferror == 0` check without an EPIPE exemption also turns `fx big | head -1` into 74, against SW-CLI-08's 0 (the `-DSTRICTEPIPE` build, re-run: 74; the exempting build: 0). Decision: SW-CLI-23 is the hook; SW-CLI-08 and SW-CLI-09 keep their mechanism and their Placement and Rule text is corrected in place.
- **`CleanExit` is not the test (revision).** The first draft of [svc]'s full hook used `error is CleanExit`; `--help` then landed on stderr with exit 0. The error `asyncParseAsRoot` throws for help is an internal type, and `Self.exitCode(for: error) == .success` is the public test. SW-CLI-23 states the latter and bans the former.
- **Usage remap versus the hook (revision; SW-CLI-12 against SW-CLI-23).** The [svc] hook maps `Self.exitCode(for: error)` through `Status.checked(code.rawValue)`, which sends any value outside the table to `.failure`. On Windows a usage failure is `ERROR_BAD_ARGUMENTS` (160), so the hook as written would exit 1 there, not 64 (reading result: `Platform.swift:155-163` and the `checked` source in FXB `c-fx/Sources/fx/Status.swift`; not run off Linux). Decision: the hook applies the SW-CLI-12 remap before `checked` (`#if !os(WASI)`), and SW-CLI-12 names the hook as the one entry point. The first fold-in had not built the combined snippet; the verification pass did (FXC `fx/Root.swift`, async root, and `fxs/Root.swift`, plain `ParsableCommand` root): both compile with the remap and the guard on 6.4.0 and 6.3.3 and keep the whole matrix. The remap is a no-op on Linux (`validationFailure` is already 64), so the Windows branch is still unexecuted.
- **A thrown domain error through the hook (revision).** `Self.exitCode(for:)` returns 1 for any error that is not an `ExitCode` or an ArgumentParser error (`throw Boom()` exits 1, [ces] row d). A hook that consults only `exitCode(for:)` therefore drops a classified `FxError` to 1. The [svc] fixture avoids it by printing and throwing `Status.exitCode` from the command. Decision: SW-CLI-23 classifies a domain error with the SW-CLI-14 exhaustive `switch` before it consults `exitCode(for:)`. Built and watched in the verification pass (FXC): a thrown `FxError.badData` exits 65, `.unreachable` 69, `.config` 78 through the hook (6.4.0 and 6.3.3), against exit 1 with the same message in the `-DNODOMAIN` build that skips the classification (red), and a plain `ParsableCommand` root behaves the same.
- **Where `exit` may appear (revision; SW-CLI-03 against SW-CLI-23).** SW-CLI-03 allowed `exit` in "the entry-point file". [svc] found that inside a `ParsableCommand` type a bare `exit(...)` resolves to the instance method (`use of 'exit' refers to instance method rather than global function 'exit' in module 'SwiftGlibc'`), so the one terminator sits in `Stdio.swift` (`Stdio.terminate`). The rule text now names that file and keeps the entry-point file for a hand-written entry point that does not use SW-CLI-23.
- **Graceful exit 0 against the re-raise rule (revision; SW-CLI-22 against SW-CLI-10).** A service whose `ServiceGroup.run()` returns after a graceful stop exits 0 (every exemplar does); a finite command ended by a signal re-raises (130 or 143). SW-CLI-10 governs handlers that end the process themselves, so it is scoped to say so; SW-CLI-22 states both outcomes. Whether a bounded job hosted in a `ServiceGroup` should also exit 143 is argued, not sourced (Contested, D8).
- **Tier dependency, SW-CLI-23 (MUST) on SW-CLI-24 (SHOULD) (revision).** The hook needs the errno of the first failed write to tell EPIPE from ENOSPC, and only the funnel records it. SW-CLI-08 (MUST) already requires reading errno at the failing write for unbounded output. Decision: SW-CLI-24 keeps SHOULD as a rule about all stdout writes, SW-CLI-23 and SW-CLI-08 are the MUST that depends on it for any command whose output can exceed one stdio buffer. Why a bare `print` cannot serve: after the buffer drains inside `print`, `ferror` is set, a later `fflush` returns 0 and `errno` is stale (reasoned from the `/dev/full` observations above; not run with EPIPE).
- **Envelope shape (revision).** The lore Rust file's CLI-04 describes `{"error": {"code", "exit", "message", "reason"?, "retryable"?, "forceable"?}}` (`rules/rust-quality/cli-contract.md:112`); the live `ocx` ships `schema_version`, `command`, `exit_code`, `error.kind/detail/message/context` (`ocx@5de9d777eb7d:crates/ocx_cli/src/error_envelope.rs:1-25,38-65`). Decision: SW-CLI-29 follows `ocx`; the drift joins D2 and is reported to the Rust set.
- **Tier drift against the Rust file (revision).** Rust CLI-03 (sanitized rendering), CLI-04 (envelope) and CLI-08 (progress) are MUST; [svc] ported them as SHOULD (SW-CLI-25, -29, -30) with no stated reason beyond "no Swift exemplar satisfies any". Decision: the SHOULD tiers stand until the owner says otherwise (D9); CLI-09 (prompts) and CLI-10 (global flags) keep their MUST (SW-CLI-31, SW-CLI-28 for fleet-family CLIs).
- **Stale `ServiceLifecycle` documentation (revision).** The 2020 swift.org post says handlers for INT and TERM are installed by default; that is the 1.x API. The 2.x `ServiceGroup` defaults to none (`ServiceGroupConfiguration.swift:140,143`, re-read; behaviour re-run: default SIGTERM exits 143). The 2.12.1 DocC article writes `.shutdownGracefully`, which does not compile (`.gracefullyShutdownGroup` is the member). The source and the run win over both documents.
- **Closed stdout (revision; corrected by the verification pass).** Rust's std treats EBADF on stdout as success (the fleet's Rust file is silent on it). In an async root, `>&-` yields EINVAL, not EBADF: the runtime opens an epoll descriptor that takes fd 1 (`readlink /proc/self/fd/1` is `anon_inode:[eventpoll]`), and the hook exits 74 (re-run: `ok-closed` and `help-closed` 74; no hook 0 with the output dropped). The first fold-in generalised this to "a Swift process never sees EBADF"; FXC disproved it: a plain synchronous `ParsableCommand` root has no runtime descriptor, `fxs ok >&-` writes into a closed fd 1 and gets EBADF (`Bad file descriptor`), exit 74 under the hook (6.4.0 and 6.3.3). Decision: 74 for both, SHOULD-level, contested (D7); for a synchronous root the choice is deliberate, where the first fold-in called it forced.
- **FoundationEssentials (revision; corrects the rationale of SW-CLI-07).** With `import FoundationEssentials` the import order no longer matters (`@preconcurrency import Glibc` before or after it compiles, exit 0), because it does not re-export Glibc; the same property means it alone cannot see `ferror` (`cannot find 'ferror' in scope`). `JSONSerialization` is not in it; `JSONDecoder`, `JSONEncoder`, `FileManager`, `ProcessInfo` and `URL` are. SW-CLI-07 is unchanged for the explicit Glibc import.
- **A recorded check that missed a spelling (revision; SW-CLI-17).** [svc]'s grep for a defaulted `@Option` (`var [a-zA-Z_]+: *[A-Za-z]+ *= *[^ ]`) needs a type annotation, so `@Option var timeout = 30` (inferred type, the likelier agent spelling) is green on a violation (re-measured on a one-line input: 0 hits). The pattern is replaced by one that makes the annotation optional (SW-CLI-17); red on the planted trees and on `cfgcli-bad`, green on the twin (re-run).
- **Handled SIGTERM (revision).** SW-CLI-11 said the handled-SIGTERM variant "was not planted". [svc] planted it (`long --mode reraise`: SIGTERM runs the cleanup and exits 143, SIGINT 130, two SIGTERMs 0.1 s apart exit 143 before `cleanup-done`; re-run). The cleanup-under-cancellation half (async `defer`, shield, deadline) is SW-CONC's and was measured there.
- **Numbering (revision).** [svc] issued SW-CLI-15 to -32 and left -27 unused "so the table keeps the order of the fixture's V-ids"; it says the consolidator may renumber. Decision: the numbers are kept, so that [svc]'s cross-references (for example SW-CLI-16 to SW-CLI-28) stay valid; SW-CLI-27 is not issued and is never reused. The [svc] V-ids are not the rule numbers (map above). A second collision: [ces] numbers 15 to 20 (its own list) are not the consolidated IDs 15 to 20, which were issued by this revision; `swift-testing.md` and the map's contradiction 16 cite "SW-CLI-17" in the [ces] sense, which means SW-CLI-14 here (see the crosswalk).
- **Three recorded checks that stayed green on a likely violation (verification pass; SW-CLI-23, -31, -20).** Planted in `FXC/greps/` (`bash checks.sh bad` then `good`). (1) SW-CLI-23's grep listed files that call `Self.main(nil)` without `fullMessage(for`; the likeliest agent output, a bare `@main struct App: AsyncParsableCommand` with no `main()` override, never mentions `Self.main(nil)`, so the grep printed nothing on it (`X23-current`: EMPTY on bad). Replaced by a grep over every `@main` file lacking `fullMessage(for` (`X23-wide`: red on the bare root, empty on the hooked root). (2) SW-CLI-31's grep accepted any `isatty(`, so SwiftPM's shape (read stdin after testing the output stream: `outputStream.isTTY`, `swift-package-manager@5546f44a3b52:Sources/CoreCommands/SwiftCommandObservabilityHandler.swift:144-153`, and `Sources/Commands/PackageCommands/PluginCommand.swift:294`) or a planted `isatty(1)` gate printed nothing (`X31-current` listed only the ungated file) and the stdin helper `Stdio.isTTY(0)` was a false positive. ## AI-agent failure modes

Ranked by judgment from [ces]'s and [svc]'s agent-angle tables and the corpus counts; no agent-output experiment was run, so the order is argued, not measured. Items 1 to 12 are from the first consolidation; 13 to 22 are the revision's; 23 to 25 are the verification pass's.

1. **`exit(1)` or `Foundation.exit` after printing an error.** It skips `defer`, may drop buffered stdout, and `Darwin.exit` does not build on Linux. Check: the SW-CLI-03 grep.
2. **`throw ExitCode(n)` with a computed integer or a small custom code (2, 3, 4, 200).** It wraps modulo 256 and collides with crash and shell codes. Check: the SW-CLI-01 greps and the exit test of SW-CLI-14.
3. **`print("Error: ...")` for diagnostics.** The line lands on stdout, in the pipe. Check: the SW-CLI-05 grep, then `cli <failing-command> 2>/dev/null` must print nothing.
4. **`FileHandle.standardError.write(Data(...))`, the training-data default.** It traps 132 on EPIPE under SIG_IGN and dies 141 otherwise. Check: the SW-CLI-04 grep.
5. **`print` as the only output path, with no flush check.** `>/dev/full` and a closed pipe exit 0. Check: `cli <command> >/dev/full; echo $?`.
6. **Top-level `try await` in `main.swift`, or `@main` with `static func main() async throws` and no catch.** Exit 132 with a backtrace, not 1. Check: the SW-CLI-02 grep and a forced-throw run.
7. **Swift 6 rejects `fflush(stdout)`, and the agent "fixes" it with `nonisolated(unsafe) let out = stdout` or drops the target to `.v5`.** The alias still fails to compile; the downgrade is an escape hatch. Check: build in language mode 6 and the SW-CLI-07 grep; only the `@preconcurrency` first-import form works.
8. **No SIGPIPE handling, or `signal(SIGPIPE, SIG_IGN)` placed in a library, or followed by `Process()` children.** Check: the SW-CLI-08 pipe test; the heuristic grep for `SIGPIPE` and `Process()` in one target.
9. **Two-stage Ctrl-C with `raise(SIGINT)` or `exit(128 + sig)` in a handler.** `raise` from a pool thread does nothing. Check: the SW-CLI-10 grep and the twice-`kill -INT` run.
10. **`environment["NO_COLOR"] != nil` or `== "1"`.** Check: the SW-CLI-06 grep and matrix.
11. **`signal(SIGINT) { _ in ... }` capturing state.** A `@convention(c)` handler cannot capture; agents reach for `nonisolated(unsafe)` globals. Check: prefer `DispatchSource`; `grep -rn -e 'signal(SIG' --include='*.swift' Sources` for review.
12. **Asserting 64 in a cross-platform CI test.** Windows gives 160 and WASI 1. Check: contract tests gated to platforms where they ran (SW-CLI-12).
13. **`await Self.main(nil)` as the whole hook, a flush check after it, and `if error is CleanExit` to detect help.** It compiles; `--help`, `--version` and completions leave through `exit(withError:)` and skip the check; `CleanExit` is false for `--help`; a check without the EPIPE exemption turns `| head -1` into 74. Check: the SW-CLI-23 grep and `--help >/dev/full`.
14. **`ServiceGroup(services: [...], logger: logger)` with no signals, trusting the 2020 blog ("handlers for INT and TERM by default").** That is the 1.x API; 2.x defaults to `[]` and SIGTERM ends the process at 143 with no cleanup. Check: the SW-CLI-20 grep; send SIGTERM and read the exit code.
15. **`gracefulShutdownSignals: [.sigterm]` only, then Ctrl-C kills at 130; or `successTerminationBehavior: .shutdownGracefully` copied from the DocC article.** The member is `.gracefullyShutdownGroup`; the compiler says so. Check: send SIGINT in the check; build.
16. **`LoggingSystem.bootstrap` in a library, a test helper or every subcommand's `run()`; `StreamLogHandler.standardOutput` or trusting the doc comment (default = STDOUT); `static let logger = Logger(label:)` read before the bootstrap, then `logger.logLevel = .debug` on one instance.** The second bootstrap traps at run time; the early logger keeps `.info`. Check: the SW-CLI-15 greps, `fx ... --twice`, the SW-CLI-16 behaviour run.
17. **`@Option var timeout: Int = 30` (or `= 30` with an inferred type), then `flag ?? env ?? file`.** The default makes the flag non-nil, so the env var never wins. Check: the SW-CLI-17 grep and the subset test.
18. **`ProcessInfo.processInfo.environment["X"]` scattered, `NSHomeDirectory() + "/.config"` and `~/.config` literals.** No resolver, no XDG rules. Check: the SW-CLI-18 grep.
19. **`withThrowingTaskGroup` plus `try await group.waitForAll()` believed to cancel siblings or to report every failure.** `waitForAll()` waits for all and rethrows the first; `for try await` cancels the rest. Check: the SW-CLI-26 grep and run.
20. **`readLine()` prompt with no TTY gate and the prompt text on stdout; `print("\r...")` progress on stdout; a hand-written completion script.** All work at a terminal and fail in a pipeline. Check: the SW-CLI-31, -30 and -32 greps.
21. **`signal(SIGTERM) { _ in exit(0) }`.** A `@convention(c)` handler, not async-signal-safe, loses cleanup. Check: the SW-CLI-10 grep plus the signal run.
22. **`import FoundationEssentials` and `JSONSerialization`; `Task.detached` for the signal loop expecting `Logger.current` to follow.** The first does not compile (`cannot find 'JSONSerialization' in scope`); task-locals are not inherited by detached tasks (`Logger.swift:1519-1529`, reading). Check: the compiler; reading.
23. **A root hook that maps every thrown error through `Self.exitCode(for:)` alone, or no hook at all (a bare `@main struct App: AsyncParsableCommand`).** A thrown domain error is neither an `ExitCode` nor an ArgumentParser error, so it exits 1 whatever the table says (measured: `boom` 1 against 65 with the classification); the bare root skips the flush check, the SIGPIPE ignore and the sanitizer. Check: the `@main` form of the SW-CLI-23 grep, then `fx <command that throws a domain error>; echo $?` must print its status.
24. **A prompt gated on the output stream (`isatty(1)`, `outputStream.isTTY`), as SwiftPM does, or on nothing but `--yes`.** `echo y | cli rm x` reads the pipe and acts on it. Check: the stdin-specific form of the SW-CLI-31 grep, then the piped run must exit 64.
25. **`gracefulShutdownSignals: []` written out, or `[.sigterm]` alone copied from the README.** `[.sigterm]` alone leaves Ctrl-C at 130 and `[]` leaves SIGTERM at 143 as well, both without cleanup (measured); the empty list also passes a grep that only looks for the argument label. Check: both SW-CLI-20 greps, then send SIGINT and SIGTERM.

## Open questions

Owner decisions, each with the default the program applies until told otherwise:

- **D1. Exit-table scope.** Pin the shared core (0, 1, 64, 65, 69, 74, 75, 77-81) and leave 82+ per binary. Default: yes. The alternative, copying `ocx`'s 82-87 into every Swift CLI, hard-codes conditions most binaries do not have.
- **D2. Upstream drift.** Report to the Rust set that `rules/rust-quality/cli-contract.md` ("83-99 unassigned") is stale against `ocx` (83-87), the Python SDK (83-86) and `grim` (stops at 81), and that its CLI-04 envelope (`code/exit/retryable/forceable`) is not the shape `ocx` ships (`schema_version/command/exit_code/error{kind,detail,message,context}`). Default: report, do not patch from this program; SW-CLI-29 follows `ocx`.
- **D3. SIGPIPE stance.** All fleet-mould Swift CLIs ignore SIGPIPE and exit 0. Default: yes, following Rust CLI-05; scripts that rely on 141 get 0.
- **D4. Global flags.** `--format json` and `--color auto|always|never` mandatory in every fleet-family Swift CLI. Default: yes for CLIs the SDK or scripts drive, SHOULD elsewhere (SW-CLI-28 applies this).
- **D5. Windows exit path** (owner Q7). Default: unverified. SW-CLI-09 and SW-CLI-12 stay "read only", and `ServiceGroup` signals on Windows and WASI stay a documented gap, until a Windows run exists.
- **D6. Signal-killed children** (owner Q6). Default: 128+n, owned by SW-IO and SW-API; this file only fixes that 128-255 is never a `Status` case.
- **D7. Closed stdout.** A closed fd 1 (`>&-`) is exit 74 here. In an async root the Swift runtime reuses fd 1 and the errno is EINVAL; in a plain synchronous root the errno is EBADF, which Rust's std treats as success. Default: 74 for both (SHOULD). The alternatives: exempting EBADF (Rust parity, reachable only in a synchronous root) or EINVAL on fd 1 (fragile, async roots).
- **D8. Exit status after a graceful stop.** A service exits 0 and an interrupted finite command re-raises (143 or 130). A bounded job hosted in a `ServiceGroup` may prefer 143 everywhere (Rust EXIT-11 reads that way). Default: 0 for a service, re-raise for a command; no source decides it, and 143 shows as an error in some orchestrator UIs.
- **D9. Tiers of the ported Rust rows.** Rust CLI-03 (sanitized rendering), CLI-04 (envelope) and CLI-08 (progress) are MUST in the fleet file; SW-CLI-25, -29 and -30 are SHOULD. Default: SHOULD until a fleet-family Swift CLI exists; lift to MUST for those on the owner's word.
- **D10. A failed flush against an earlier non-success status** (new, verification pass). Measured: with `--format json`, `fx fail >/dev/full` exits 74 under the hook as written and 65 under a variant that only upgrades a success. Default: 74 wins, because the machine-readable result was lost and a retry wrapper keyed on 75 must not retry into a full disk. The alternative (keep the command's own status, write the flush failure to stderr) is a one-line change in SW-CLI-23. No source decides it.
