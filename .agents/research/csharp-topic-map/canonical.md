## Summary

- The open netstandard2.0 question has two defensible canonical answers that disagree. Microsoft library guidance says start with `net8.0`+ and only CONSIDER `netstandard2.0` for breadth ([cross-platform-targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)); the Azure SDK guideline says build every library for .NET Standard 2.0 ([Azure .NET intro](https://azure.github.io/azure-sdk/dotnet_introduction.html)). The ecosystem splits the same way (exemplar evidence below).
- netstandard2.0 is not free: measured with SDK 10.0.401, its default `LangVersion` is 7.3 against 12.0 for `net8.0` and 14.0 for `net10.0` (fixture command in Findings A). Even with `LangVersion` 14, `record`/`init`/`required`/`Index`/`ReadOnlySpan` fail to compile without polyfills. The decision cascades into every C# language rule an agent will follow.
- Support clock: .NET 8 LTS and .NET 9 STS both end support on 2026-11-10, a month after this research date; .NET 10 LTS runs to 2028-11-14 ([support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)). A "floor" of `net8.0` is a floor that is about to be unsupported.
- No new .NET Standard versions will ship after 2.1; .NET Standard is "not deprecated" but only justified for sharing with .NET Framework ([net-standard](https://learn.microsoft.com/en-us/dotnet/standard/net-standard)).
- Public API evolution has a precise, citable rulebook: the "API changes that affect compatibility" page lists allowed/disallowed/judgment changes (parameter rename disallowed, adding interface members judgment, adding abstract member to unsealed type disallowed, sync-to-async disallowed) ([library-change-rules](https://learn.microsoft.com/en-us/dotnet/core/compatibility/library-change-rules)). Package validation can enforce it in CI ([package-validation](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview)).
- Subprocess control is where the Learn docs are thin and the traps are many: sync read of both redirected streams deadlocks, `Kill` is asynchronous and `WaitForExit` ignores descendants, `ArgumentList` is the only safe quoting path, and default encodings differ between .NET Framework and .NET (Core) ([StandardOutput](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.standardoutput?view=net-10.0), [Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0), [Process](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process), [ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist?view=net-10.0)).
- `[.NET 11 RC1]` adds a large Process surface: `RunAndCaptureText[Async]`, `ReadAllLinesAsync` with stdout/stderr tagging, `StartAndForget`, `KillOnParentExit` (Windows only), `StartSuspended`, `Process.Signal`, `WaitForExitStatusAsync` returning `ProcessExitStatus` (`ExitCode`, `Canceled`, `Signal`) ([.NET 11 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries), [ProcessExitStatus](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processexitstatus?view=net-11.0)). An SDK targeting net8/net10 cannot call them; a seam is needed.
- .NET 10 removed the runtime's default SIGTERM/SIGHUP handlers; `ProcessExit` and `AssemblyLoadContext.Unloading` no longer fire on SIGTERM ([breaking change](https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/10.0/sigterm-signal-handler)). Cancellation and cleanup that relied on process-exit hooks silently stop working.
- TAP rules that bite libraries: throw only for usage errors, otherwise fault the returned task; add a `CancellationToken` only when the operation is actually cancelable; ValueTask only when measured ([TAP](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/task-based-asynchronous-pattern-tap)). Library code uses `ConfigureAwait(false)` ([ConfigureAwait FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)).
- System.Text.Json: default is reflection; under `PublishTrimmed` reflection serialization is auto-disabled, so a library that relies on it breaks only in trimmed/AOT apps ([source-generation](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)). Unmapped JSON members are skipped by default; `Disallow` is opt-in since .NET 8 ([missing-members](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/missing-members)); .NET 10 adds `AllowDuplicateProperties` and `JsonSerializerOptions.Strict` ([.NET 10 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/libraries)).
- Trim/AOT analysis requires `net6.0`+ (trim) and `net8.0`+ (AOT) targets; for a multi-targeted library the properties are conditioned with `IsTargetFrameworkCompatible`, and a separate trimming test app with `TrimmerRootAssembly` is recommended because library builds lack dependency implementations ([trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming), [Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)).
- RIDs: since .NET 8 only portable (non-distro, non-version) RIDs are considered; "don't parse RIDs", "don't build RIDs programmatically unless absolutely necessary" ([RID catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog)). Directly relevant to "bootstrap ocx anywhere" (win/linux/linux-musl/osx x x64/arm64).
- Paths and strings are the quiet cross-platform failure class: drive-relative `C:foo`, per-process current directory, `\\?\` normalization skipping, .NET 8 stopped mapping `\` to `/` on Unix ([file-path-formats](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats)); ordinal as the safe default, invariant culture to persist, the Turkish-I security example ([best-practices-strings](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings)).
- Packaging checklist is long and mostly mechanical: SPDX license expression, 64x64 HTTPS icon, SourceLink, snupkg vs embedded PDB (embedding adds about 30 percent to package size), deterministic builds, prerelease suffix, major-only `AssemblyVersion` ([nuget](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget), [versioning](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning), [sourcelink](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink)).
- Publishing security moved on: NuGet Trusted Publishing (OIDC, one-hour single-use API keys) replaces long-lived keys ([trusted-publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing)); the older library-guidance page still says "enable 2FA" ([publish](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/publish-nuget-package)).
- Azure SDK guideline IDs (about 120 DO/DON'T items) are the best checklist-shaped source for client/options/mocking/paging/LRO/exception/diagnostics design, and several map one-to-one onto a CLI-wrapping SDK (immutable client, `Options` suffix, protected ctor and virtual members for mocking, no abstractions unless returned and consumed, thread-safe, version-resilient JSON) ([Azure intro](https://azure.github.io/azure-sdk/dotnet_introduction.html), [Azure implementation](https://azure.github.io/azure-sdk/dotnet_implementation.html)).
- Testing platform moved: Microsoft.Testing.Platform (MTP) is the VSTest alternative, supported by MSTest, NUnit, xUnit v3 and TUnit; `[.NET 11 RC1]` SDK templates default xUnit v3 to MTP ([MTP intro](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-intro), [.NET 11 overview](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/overview)).
- C# 14 is stable (extension members, `field`, null-conditional assignment, implicit span conversions, partial constructors/events, unbound `nameof`); C# 15 `[.NET 11 RC1]` (union types, `closed` hierarchies, collection-expression `with(...)`, extension indexers, labeled break/continue, memory-safety changes) must be flagged and kept out of default guidance ([C# 14](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-14), [C# 15](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-15)). Union case-type changes are themselves a binary and source break ([change rules](https://learn.microsoft.com/en-us/dotnet/core/compatibility/library-change-rules)).
- Fetch gaps (honest list in section I): two Learn URLs returned 404, the Framework Design Guidelines child pages are thin reprints from the 2008 2nd edition, and the corpus says nothing about downloading/verifying a binary, atomic installs, or time.

## Findings

### A. Targeting and language level

- **Two goals, not one.** Learn separates "modern APIs and patterns" from "breadth targeting"; if all consumers run modern .NET, no older TFM is needed ([cross-platform-targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)).
- **Guidance as written (page updated 2026-05-07).** DO start with `net8.0` or later; CONSIDER `netstandard2.0` for .NET Framework or maximum compatibility (supported by .NET Framework 4.6.1+); AVOID `netstandard1.x`; DO NOT include a netstandard target for platform-specific app models; CONSIDER adding `net462` alongside `netstandard2.0` because of .NET Framework 4.6.2-4.7.1 problems fixed in 4.7.2; AVOID changing the assembly name per TFM; CONSIDER multi-targeting even with identical source when there are dependencies (avoids binding redirects) ([same page](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)). One bullet on that page reads "DO NOT publish for `netstandard2.0` if your project or dependencies multi-target", which sits oddly next to the multi-target advice and needs reading in context before it is turned into a rule.
- **.NET Standard page.** No new versions after 2.1; netstandard2.0 is "the recommended way to support multiple platforms with one target" for reach including .NET Framework; "most widely used libraries multi-target for both .NET Standard 2.0 and .NET 5+"; recommends skipping 2.1 and going to `net10.0`; Unity appears in the 2.0 and 2.1 support tables; a warning is emitted for netstandard1.x from .NET 9 ([net-standard](https://learn.microsoft.com/en-us/dotnet/standard/net-standard)). Unity support for netstandard2.1 starts at 2021.2 on the same page.
- **Azure SDK position.** DO build all libraries for .NET Standard 2.0, SHOULD build for the current LTS, DO define the same APIs for all TFMs, SHOULD reference polyfill packages only for netstandard2.0/legacy targets (IDs `dotnet-build-net-standard`, `dotnet-build-net-current-lts`, `dotnet-build-multi-targeting-api`, `dotnet-trim-polyfills`) ([Azure intro](https://azure.github.io/azure-sdk/dotnet_introduction.html)). Extracted via page summary; re-verify the exact wording before quoting.
- **Language version follows the TFM.** Learn: the default language version aligns with the project TFM, "using a C# language version newer than the version associated with your target TFM isn't supported", and `LangVersion=latest` is explicitly discouraged ([configure-language-version](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/configure-language-version)). Measured: `cd /home/mherwig/.cache/research-lang/dotnet-tools/fixtures/canonical-scout && ../../run.sh dotnet msbuild Probe.csproj -p:TargetFramework=<tfm> -getProperty:LangVersion` with SDK 10.0.401 gives netstandard2.0 = 7.3, net8.0 = 12.0, net10.0 = 14.0.
- **Polyfill cost, measured.** `LangVersion` 14 + `<Nullable>enable` on `netstandard2.0` compiling a positional `record`, `required`+`init` properties, a `field` accessor, `System.Index` and `ReadOnlySpan<char>`: `../../run.sh dotnet build -nologo -v q | grep error` gave CS0518 (`IsExternalInit`), CS0656 (`RequiredMemberAttribute`, `CompilerFeatureRequiredAttribute`) and CS0234 (`Index`, `ReadOnlySpan<>`); the `field` accessor itself produced no error. Learn's own coding conventions recommend `required` properties, records, collection expressions and file-scoped namespaces ([coding-conventions](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/coding-style/coding-conventions)), so "which conventions are available" depends on the TFM decision.
- **Support clock.** .NET 10 LTS: released 2025-11-11, EOS 2028-11-14. .NET 9 STS and .NET 8 LTS: EOS 2026-11-10. .NET 11: RC1 2026-09-08, GA at .NET Conf 10-13 November 2026, STS inferred, not stated ([support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)). Latest patches listed there: 10.0.12, 9.0.20, 8.0.31 (the research toolchain has SDK 8.0.425 and 10.0.401).
- **Exemplar split** (command: `git -C <dir> grep -n -E "<TargetFrameworks?>" -- '*.csproj' '*.props'`): CliWrap `netstandard2.0;netstandard2.1;net6.0;net7.0;net10.0` (Tyrrrz__CliWrap@7dbc252fa773:CliWrap/CliWrap.csproj:3); simple-exec `net8.0;net9.0;net10.0` (adamralph__simple-exec@f80913246993:Directory.Build.props:13); pulumi-dotnet Automation `net6.0` only (pulumi__pulumi-dotnet@2a0dca84f09b:sdk/Pulumi.Automation/Pulumi.Automation.csproj:4); anthropic-sdk-csharp `net8.0;net9.0;netstandard2.0` (anthropics__anthropic-sdk-csharp@ae16e5933f39:src/Directory.Build.props:28); stripe-dotnet `net8.0;net9.0;net10.0;netstandard2.0;net462` (stripe__stripe-dotnet@dbdca6ba5efc:src/Stripe.net/Stripe.net.csproj:14); octokit.net `netstandard2.0` (octokit__octokit.net@7fa5b0fe4a18:Octokit/Octokit.csproj:9). The one CLI-wrapping peer from a vendor (pulumi) chose modern-only; the process helper libraries split.
- **Platform reach is a different axis from TFM.** Compiling for `net8.0` or netstandard "doesn't guarantee that the library will run successfully on all platforms"; platform-specific APIs throw `PlatformNotSupportedException`; the CA1416 analyzer is on by default only for `net5.0`+ and can be enabled elsewhere ([cross-platform-targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting), [platform-compat-analyzer](https://learn.microsoft.com/en-us/dotnet/standard/analyzers/platform-compat-analyzer)).

### B. Public API design and evolution

- **Framework Design Guidelines (FDG).** The Learn copy is the 2008 2nd edition reprint ("some of the information may be out-of-date"); the book was revised as a 3rd edition ([FDG index](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/)). 3rd edition chapters: Introduction; Framework Design Fundamentals; Naming Guidelines; Type Design Guidelines; Member Design; Designing for Extensibility; Exceptions; Usage Guidelines; Common Design Patterns; it adds async with `Task`/`ValueTask` and `Memory<T>`/`Span<T>` and was published 2020-06-18, updated to C# 8 ([InformIT](https://www.informit.com/store/framework-design-guidelines-conventions-idioms-and-patterns-9780135896464)). Child pages fetched on Learn: naming of classes/structs/interfaces (suffix rules: `Attribute`, `EventArgs`, `Exception`, `Collection`, `Stream`; no `Enum`/`Flags` suffix; `T` prefix on descriptive type parameters) ([names](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/names-of-classes-structs-and-interfaces)); exceptions and usage guidelines pages are one-paragraph stubs pointing to children that were not fetched ([exceptions](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/exceptions), [usage](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/usage-guidelines)).
- **Azure SDK .NET guidelines: the checklist-shaped canon.** Sections: Service Client (constructors, options, service versions, mocking, subclients, methods, parameters, paging, LRO, conditional requests), Supporting Types (models, enums, Azure Core types, primitives), Exceptions, Authentication, Namespaces, Mocking, Packaging, Versioning, Target Frameworks, Dependencies, Native Code, Documentation Comments, Repository (README, samples), Package Publishing, "Commonly Overlooked .NET API Design Guidelines" ([Azure intro](https://azure.github.io/azure-sdk/dotnet_introduction.html)). Directly transferable IDs for an ocx wrapper: `dotnet-client-immutable`, `dotnet-client-constructor-minimal`, `dotnet-http-pipeline-options` (Options suffix), `dotnet-options-no-default-constructor`, `dotnet-service-methods-sync-and-async`, `dotnet-service-methods-cancellation`, `dotnet-service-methods-virtual`, `dotnet-service-methods-thread-safety`, `dotnet-params-complex-methods` (options-parameter pattern), `dotnet-enums-exception` (readonly struct for extensible values), `dotnet-mocking-constructor` (protected parameterless ctor), `dotnet-mocking-extensions` (instance methods not extension methods, for mockability), `dotnet-problems-abstractions` (no abstractions unless the SDK both returns and consumes them), `dotnet-problems-interfaces` (abstract classes over interfaces), `dotnet-problems-too-many-types`, `dotnet-problems-generic-words`, `dotnet-problems-empty-types`, `dotnet-docs-document-everything`, `dotnet-versioning-no-api-breaking`, `dotnet-versioning-no-binary-breaking`, `dotnet-versioning-new-package`. Azure-specific parts (HttpPipeline, `Response<T>`, `Pageable<T>`, `Operation<T>`, `WaitUntil`, Azure.Core) do not transfer.
- **Azure implementation chapter.** Serialization: DO use System.Text.Json, SHOULD use `Utf8JsonWriter` to write and `JsonDocument` to read, DO make serialization version resilient by deserializing optional properties into nullable model properties; enumeration-like readonly structs with `IEquatable<T>` on the string value and `EditorBrowsable(Never)` on `Equals(object)`/`GetHashCode`; distributed tracing via a diagnostic-scope wrapper rather than raw `ActivitySource`; one internal sealed EventSource per library whose name/GUID/event IDs "are public API"; parameter validation through a shared `Argument` helper rather than a bespoke class ([Azure implementation](https://azure.github.io/azure-sdk/dotnet_implementation.html)).
- **Library guidance on breaking changes.** Low/mid-level libraries suffer most; the three kinds are source, behavioral and binary breaks; behavioral breaks (including "a bug fix if users relied on the bug") are the most common; hide new behavior behind opt-in settings; CONSIDER abstract base classes over interfaces; CONSIDER `[Obsolete]` with migration text and keep obsolete members indefinitely in low-level libraries; DO NOT change the assembly name or strong-name key; CONSIDER shipping a major rewrite as a new package ([breaking-changes](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/breaking-changes)).
- **The change-rules table is the rulebook** (page updated 2026-04-14). Examples that routinely bite: renaming a parameter is DISALLOWED (named arguments, `dynamic`); adding or removing `params`, changing a `params` collection type (C# 13 `params ReadOnlySpan<T>`), changing a default value, adding an overload that rebinds existing calls, adding `virtual` to a member, sealing a type, changing sync to async, changing an enum underlying type, adding a field to an all-public-field struct are DISALLOWED; adding an interface member is "judgment" and is a source break for `ref struct` implementers in C# 13+; adding or removing a union case type is a binary and source break; converting an extension method to the C# 14 `extension` block is allowed; throwing a new exception type is disallowed unless more derived; changing message text is allowed; adding `OverloadResolutionPriorityAttribute` to an existing overload is judgment ([library-change-rules](https://learn.microsoft.com/en-us/dotnet/core/compatibility/library-change-rules)).
- **Tooling for the rulebook.** `EnablePackageValidation` runs after `Pack` with three validators: baseline-version (against a previously released stable package), compatible-runtime, and compatible-framework (code compiled against one TFM runs against the others in a multi-targeting package) ([package-validation](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview)).
- **Compiler-level source breaks to know.** C# 14 `field` keyword can collide with an existing symbol named `field` (`@field` / `this.field`) ([C# 14](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-14)); .NET 10 lists "C# 14 overload resolution with span parameters" as a behavioral change and `System.Linq.AsyncEnumerable` entering the core libraries as source-incompatible ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)).

### C. Packaging, versioning, signing, publishing

- **NuGet metadata.** Core properties: `PackageId`, `PackageVersion`, `Title`, `Description`, `Authors`, `PackageTags`, `PackageIcon`, `PackageProjectUrl`, `PackageLicenseExpression` (SPDX; only OSI/FSF approved can use an identifier). A project without a license defaults to exclusive copyright. DO use an HTTPS icon; DO use a 64x64 transparent icon; CONSIDER an ID prefix that meets NuGet prefix reservation; CONSIDER SourceLink; a stable package cannot depend on a prerelease package; the nupkg cannot be deleted or re-uploaded at the same version (unlist and bump) ([nuget](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget), [publish](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/publish-nuget-package)).
- **Symbols.** snupkg for on-demand debugging without bloating restore; embedding PDBs (`AllowedOutputExtensionsInPackageBuildOutputFolder`) costs about 30 percent package size; nuget.org symbol server needs portable PDBs ([nuget](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget)). SourceLink: CONSIDER publishing symbols and CONSIDER deterministic builds; verify with NuGet Package Explorer or nuget.info ([sourcelink](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink)).
- **Versions (four of them).** NuGet package version (SemVer 2.0.0, prerelease suffix for non-stable), `AssemblyVersion` (CONSIDER major only; DO NOT freeze it), file version (`Major.Minor.Build.Revision`, CI build number as revision), informational version (AVOID setting it yourself; SourceLink appends the commit hash) ([versioning](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning)).
- **Strong naming.** No benefit on .NET Core/5+; strict-load downside exists only on .NET Framework; viral on .NET Framework (a strong-named assembly can only reference strong-named ones); CONSIDER strong-naming if the library targets .NET Framework or netstandard; if multi-targeting both worlds, sign all TFMs; DO NOT add, remove or change the key; DO NOT publish signed and unsigned variants; public-signing as fallback; CS8002 can be suppressed for modern-only libraries ([strong-naming](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/strong-naming), page dated 2026-03-23).
- **Dependencies.** Diamond dependencies are the failure mode; minimize packages; DO NOT omit a minimum version, AVOID exact pins, AVOID upper bounds (NuGet picks lowest applicable version); shared-source packages (`PrivateAssets="All"`, internal types only, never published to nuget.org) ([dependencies](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/dependencies)). Azure adds: align runtime library versions with the current LTS, polyfills only for netstandard2.0, no native dependencies ([Azure intro](https://azure.github.io/azure-sdk/dotnet_introduction.html)). .NET 10 SDK changes that touch this: `PackageReference` without a version is now an error, `dotnet restore` audits transitive packages, NU1510 for pruned references, `dotnet new sln` defaults to SLNX ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)).
- **Publishing security.** Library-guidance era: Microsoft account, 2FA, email notification ([publish](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/publish-nuget-package), content dated 2018, updated 2025-07). Current mechanism: Trusted Publishing, GitHub Actions or GitLab OIDC token exchanged at nuget.org for a one-hour, single-use API key; policy fields owner/repo/workflow file/optional environment; private repos start with a 7-day temporary policy ([trusted-publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing)). NuGet package signing and Authenticode are the "publisher identity" mechanisms per library guidance ([strong-naming](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/strong-naming)). Note `dotnet nuget sign` SHA-1 fingerprints are deprecated in .NET 10 ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)).

### D. Subprocess control

- **Class remarks** ([Process](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process)): implements `IDisposable`; "leaking handles is more virulent than leaking memory"; property groups are cached until `Refresh()`; untrusted input is a security risk (OWASP "validate all inputs" link); on .NET Framework the default stream encoding is the console code page, on .NET Core a limited subset is available and `Encoding.UTF8` is the fallback unless `CodePagesEncodingProvider` is registered before any Process call.
- **Deadlock rules** ([StandardOutput](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.standardoutput?view=net-10.0)): read the redirected stream before `WaitForExit`; reading stdout then stderr synchronously deadlocks when stderr fills; use async reads on at least one stream; you cannot mix sync and async reads on the same stream (but can across the two streams); `UseShellExecute=false` and `RedirectStandardOutput=true` are prerequisites.
- **Arguments.** `ArgumentList` escapes and builds one string internally; `Arguments` and `ArgumentList` are mutually exclusive; the docs advise `ArgumentList` "if you aren't sure how to properly escape" ([ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist?view=net-10.0)). Argument lists collapse to a single command-line string on Windows, so program-specific parsing rules (for example `cmd.exe /c`) remain the caller's problem (the page's own `cmd.exe /c dir` example).
- **Kill.** `Kill` "executes asynchronously": follow with `WaitForExit` or check `HasExited`; with `Kill(entireProcessTree: true)` `WaitForExit`/`HasExited` report completion when the root exits "even if all descendants have not yet exited"; processes the caller cannot inspect are "silently skipped"; may throw `AggregateException` if not all descendants terminate; `InvalidOperationException` if the caller is itself in the descendant tree; iOS/tvOS unsupported ([Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0)).
- **Signals.** `[.NET 10]` the runtime no longer installs default SIGTERM (Unix) or CTRL_SHUTDOWN/CTRL_CLOSE (Windows) handlers; `ProcessExit` and `AssemblyLoadContext.Unloading` are not raised on termination; use `PosixSignalRegistration` or the generic host's console lifetime ([sigterm breaking change](https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/10.0/sigterm-signal-handler)). `[.NET 10]` also: `dotnet` CLI commands log non-command data to stderr and `dotnet watch` logs to stderr, relevant when an SDK shells out to `dotnet` tooling ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)).
- **`[.NET 11 RC1]` Process expansion** ([.NET 11 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries)): `Process.Run/RunAsync`, `RunAndCaptureText[Async]` (returns `ProcessTextOutput` with `StandardOutput` and `ExitStatus`), `ReadAllText/ReadAllBytes/ReadAllLines[Async]` (`ProcessOutputLine` distinguishes stdout from stderr), `StartAndForget`, `ProcessStartInfo.StartDetached`, `KillOnParentExit` (Windows only), `InheritedHandles`, `Standard{Input,Output,Error}Handle`, `StartSuspended` (Windows and macOS), `Process.Signal(PosixSignal)`, `Process.TryGetProcessById`, `SafeProcessHandle.Start/Kill/Signal/WaitForExit[Async]/Resume/Open/TryOpen`, `WaitForExitStatus[Async]`/`TryWaitForExitStatus` returning `ProcessExitStatus(int exitCode, bool canceled, PosixSignal? signal)` ([ProcessExitStatus](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processexitstatus?view=net-11.0); the API pages list `net-11.0` as the only applicable moniker, [WaitForExitStatusAsync](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.waitforexitstatusasync?view=net-11.0)). .NET 10 libraries added "Launch Windows processes in new process group" ([.NET 10 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/libraries)).

### E. Async, cancellation, disposal

- **TAP** ([TAP](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/task-based-asynchronous-pattern-tap), updated 2026-04-30): `Async` suffix on awaitable-returning methods; match the sync counterpart's parameters; avoid `out`/`ref`; usage errors may throw synchronously but all other errors must be placed on the returned task even if completion is synchronous; returned tasks must be hot; `async` does not mean another thread; prefer `Task`/`Task<T>`, `ValueTask` only when measured; add the async overload next to the sync one without removing the sync API; a cancellation overload only when the operation can be canceled; cancellation requested before the call should return a canceled task; a task ends `Canceled` only if the operation ended because of the request; progress via `IProgress<T>` that accepts null and reports synchronously.
- **Cancellation model** ([cancellation](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads)): cooperative; `CancellationTokenSource` is `IDisposable`; tokens are single-use after cancel; one token per cancelable operation; `Register` callbacks must be fast (`Cancel` runs them synchronously) and disposing a registration while holding a lock the callback waits on can deadlock; linked sources must be disposed; library code should treat an `OperationCanceledException(externalToken)` from user delegates as cooperative cancellation, not failure.
- **ConfigureAwait** ([FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)): libraries use `ConfigureAwait(false)`, apps do not; `ConfigureAwait(true)` is a no-op; applying it to the first await only is unreliable; it does not affect `GetResult()`; `AsyncLocal` still flows. The FAQ fetched here does not cover `ConfigureAwaitOptions` (.NET 8), which would need a separate source.
- **Dispose** ([implementing-dispose](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/implementing-dispose)): `Dispose` must be idempotent and callable repeatedly without throwing; sealed classes skip `Dispose(bool)`; finalizers only for direct unmanaged resources, otherwise wrap in `SafeHandle`; own what you create, do not dispose what you do not own; the Learn example uses `Interlocked.CompareExchange` for thread-safe disposal. The FDG "Dispose Pattern" page is linked from the usage-guidelines stub ([usage](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/usage-guidelines)) but was not fetched; `IAsyncDisposable` guidance was not in the fetched page.
- **Background services** `[.NET 10]`: `BackgroundService` now runs all of `ExecuteAsync` as a Task (behavioral change) ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)); `[.NET 11 RC1]` Runtime Async changes stack traces and overhead for `await` ([.NET 11 overview](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/overview)).

### F. JSON, trimming, Native AOT

- **STJ basics** ([overview](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/overview)): built into the shared framework for .NET Core 3.0+, NuGet package supports netstandard2.0, .NET Framework 4.6.2+ and .NET 8+; `JsonSerializerOptions` instances are thread-safe once locked; no `[Serializable]`/`ISerializable` support; a threat-model document exists.
- **Source generation** ([source-generation](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation), updated 2026-03-30): `partial` class deriving `JsonSerializerContext` + `[JsonSerializable]`; members typed `object` need explicit runtime types; two modes (metadata, serialization-optimization) with fast-path not supported for async serialization; setting `JsonSerializerIsReflectionEnabledByDefault=false` makes reflection use throw `InvalidOperationException`, and under `PublishTrimmed` reflection is auto-disabled; options through `[JsonSourceGenerationOptions]` apply only when you use the context's `Default`/type-info (a custom `JsonSerializerOptions` passed to the context constructor overrides them); the non-generic `JsonStringEnumConverter` is not supported under Native AOT, use `JsonStringEnumConverter<TEnum>`; resolver-chain order is significant.
- **Format evolution** ([missing-members](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/missing-members), [.NET 10 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/libraries)): default skips unmapped members; `JsonUnmappedMemberHandling.Disallow` opt-in since .NET 8; `[.NET 10]` `AllowDuplicateProperties=false` (also on `JsonDocumentOptions`) and `JsonSerializerOptions.Strict`; `PipeReader` deserialization; `ReferenceHandler` in `JsonSourceGenerationOptions`. `[.NET 10]` STJ now checks for property name conflicts (behavioral change) ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)). `[.NET 11 RC1]` adds union serialization, JSON Lines output, expanded polymorphism and source generation ([.NET 11 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries)). Azure: deserialize optional properties into nullable members for version resilience ([Azure implementation](https://azure.github.io/azure-sdk/dotnet_implementation.html)).
- **Trimming and AOT for libraries** ([trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming), [Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)): `IsAotCompatible=true` defaults `IsTrimmable`, `EnableTrimAnalyzer`, `EnableSingleFileAnalyzer`, `EnableAotAnalyzer` to true; target `net6.0`+ for trim warnings and `net8.0`+ for AOT warnings; condition properties with `IsTargetFrameworkCompatible` in a multi-target project; `VerifyReferenceAotCompatibility` / `VerifyReferenceTrimCompatibility` are opt-in (IL3058 / IL2125; `IsAotCompatible` assembly metadata exists only from .NET 10); create a test app with `PublishTrimmed` + `TrimmerRootAssembly`; "introducing trim analysis warnings is a breaking change"; avoid reflection in static constructors and annotating virtual/interface methods; `UnconditionalSuppressMessage` and `DynamicDependency` are last resorts. Native AOT limits: no `Assembly.LoadFile`, no `Reflection.Emit`, `Linq.Expressions` interpreted; supported targets on .NET 9+: Windows x64/Arm64/x86, Linux x64/Arm64/Arm, macOS x64/Arm64.

### G. Cross-platform behaviour

- **RIDs** ([rid-catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog)): portable RIDs only since .NET 8; common set `win-x64/x86/arm64`, `linux-x64`, `linux-musl-x64`, `linux-musl-arm64`, `linux-arm`, `linux-arm64`, `linux-bionic-arm64`, `linux-loongarch64`, `osx` (universal), `osx-x64`, `osx-arm64`; `RuntimeInformation.RuntimeIdentifier` returns the platform the runtime was built for; read `/etc/os-release` for distro detail; do not parse RIDs; computed RIDs must match the catalog exactly, including case; RID-specific NuGet assets use `runtimes/<rid>/` and warning NETSDK1206 flags assets that will be ignored.
- **Paths** ([file-path-formats](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats)): `C:foo` (drive-relative) vs `C:\foo` bug class; `Path.IsPathFullyQualified`; relative paths are dangerous because the current directory is process-wide; `Path.GetFullPath(path, basePath)` exists from .NET Core 2.1; `\\?\` skips normalization (long paths are handled implicitly in .NET Core+, no MAX_PATH check); trailing spaces/periods are trimmed during normalization; Windows is case-insensitive and case-preserving; since .NET 8 on Unix `\` is no longer converted to `/`; legacy device names (`CON`, `COM1`) behave differently before Windows 11.
- **Strings and culture** ([best-practices-strings](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings), updated 2026-06-26): use `Ordinal`/`OrdinalIgnoreCase` as the safe default; call overloads with an explicit `StringComparison`; use invariant culture to persist non-string data and current culture only for display; avoid `InvariantCulture` string operations in most cases; some overloads default to ordinal (char search) and others to culture-sensitive (string search); the Turkish-I example turns a security check (`IsFileURI("file:")`) on or off by culture; embedded nulls are ignored by culture-sensitive compare; invariant globalization mode makes everything ordinal. The dedicated "globalization invariant mode" Learn URL I tried returned 404, so ICU/NLS dependency details on Alpine and minimal containers are an unfetched gap. `[.NET 10]` ICU version override env var was renamed (`DOTNET_ICU_VERSION_OVERRIDE`) ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)); .NET 10 adds numeric ordering for string comparison ([.NET 10 libraries](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/libraries)).
- **Platform compatibility** ([platform-compat-analyzer](https://learn.microsoft.com/en-us/dotnet/standard/analyzers/platform-compat-analyzer)): unattributed APIs are assumed to work everywhere; `SupportedOSPlatform`/`UnsupportedOSPlatform` with versions; guard with `OperatingSystem.IsX()` or `RuntimeInformation.IsOSPlatform` (works from netstandard); custom guards via `SupportedOSPlatformGuard`; child annotations can narrow but not widen; analyzer reads TFM platform from the generated assembly attribute, so `GenerateAssemblyInfo=false` produces false warnings. Library guidance adds the capability-API pattern (`IsSupported` plus `PlatformNotSupportedException`) ([cross-platform-targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)).
- **Other `[.NET 10]` platform items worth a rule**: OpenSSL 1.1.1+ required on Unix and OpenSSL primitives unsupported on macOS; `DriveInfo.DriveFormat` returns Linux fs types; "Default .NET images use Ubuntu"; single-file apps no longer search the executable directory for native libraries ([breaking changes .NET 10](https://learn.microsoft.com/en-us/dotnet/core/compatibility/10.0)). `[.NET 11 RC1]` raises minimum hardware instruction-set requirements for x86/x64 and Arm64 ([.NET 11 overview](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/overview)).
