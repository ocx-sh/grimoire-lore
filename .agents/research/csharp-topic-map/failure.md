## Summary

- The process-spawning layer is where C# wrappers fail most. Of the 26 closed `bug` issues on CliWrap, the dominant themes are pipe deadlocks/buffering, process lifecycle races, and argument escaping (list fetched at [S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)).
- `Process.WaitForExit()` also waits for EOF on redirected stdout/stderr, so a grandchild that inherited the pipe makes it hang forever. dotnet/runtime closed this as expected behaviour, not a bug ([#29232](https://github.com/dotnet/runtime/issues/29232), dup [#120452](https://github.com/dotnet/runtime/issues/120452)). The SDK must define "done" itself.
- `dotnet build-server` style daemons are a live instance of that trap: MedallionShell's `Command.Result` hung until `dotnet build-server shutdown` ran ([MedallionShell #104](https://github.com/madelson/MedallionShell/issues/104)). Any `ocx` subcommand that spawns a background helper would reproduce it.
- `Process.Kill(entireProcessTree: true)` returns "exited" when the root exits even if descendants live, silently skips processes it cannot inspect, and throws `AggregateException` on partial failure ([Process.Kill docs](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0)).
- A CliWrap 3.7.0 regression orphaned `cmd.exe`+`notepad.exe` on cancellation because the net8.0 target was dropped ([CliWrap #270](https://github.com/Tyrrrz/CliWrap/issues/270)). Kill-tree behaviour depends on the target framework you ship, which feeds the netstandard2.0 question.
- Argument quoting is lossy by design: CliWrap joins args into one string even on Unix and does not escape backslashes ([CliWrap #298](https://github.com/Tyrrrz/CliWrap/issues/298)). `ProcessStartInfo.ArgumentList` is the .NET-native alternative; CliWrap's `Command.Execution.cs:408` still assigns a single `Arguments` string.
- Encoding is not under the caller's control: `StandardOutputEncoding` "does not guarantee the process will use the specified encoding"; the child must cooperate ([CliWrap #196](https://github.com/Tyrrrz/CliWrap/issues/196)). Chunked merging can also split multibyte UTF-8 ([CliWrap issue list, #81](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)).
- A CliWrap deadlock was caused by a one-shot EOF signal in an internal stream that violated the `Stream` contract; it only triggered when output was an exact multiple of 1,024 bytes with a multibyte char ([CliWrap #346](https://github.com/Tyrrrz/CliWrap/issues/346)). Wrapping a process library imports its bug surface.
- SIGCHLD ownership is global: a PAM module reset .NET's handler and left `WaitForExitAsync` hung with 2,147 zombies ([runtime #114847](https://github.com/dotnet/runtime/issues/114847)). Root cause was the reporter's finding, not a maintainer analysis.
- Sync-over-async is the standard thread-pool-starvation cause; .NET 6 sped up pool growth but did not remove the problem ([starvation doc](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-threadpool-starvation)). Library authors still need a ConfigureAwait policy ([ConfigureAwait FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)).
- Culture bugs are silent: `IsFileURI("file:")` flips on Turkish culture; ICU vs NLS changes `IndexOf("\0")` results; invariant-globalization mode disables linguistic comparison ([string best practices](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings), [ICU doc](https://learn.microsoft.com/en-us/dotnet/core/extensions/globalization-icu)).
- `Path.Combine` discards earlier segments when a later one is rooted; `Path.Join` is the safe alternative; drive-relative `C:foo` is "a common source of bugs"; `.NET Core+` handles long paths without `\\?\` ([Path.Combine](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.combine), [path formats](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats)).
- System.Text.Json is case-sensitive, throws on comments/trailing commas, ignores unmapped members by default and rejects quoted numbers unless told otherwise ([migration doc](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/migrate-from-newtonsoft), [missing members](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/missing-members)). For a wire contract with `ocx`, "strict or tolerant" is a decision, not a default.
- Reflection-based STJ breaks under Native AOT in ways that CoreCLR debugging hides; `JsonSerializerIsReflectionEnabledByDefault=false` makes it fail loudly, and the non-generic `JsonStringEnumConverter` is not AOT-supported ([source-gen doc](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)).
- Binary vs source vs behaviour breaks are separate categories; adding an abstract interface member, renaming a parameter, changing a default value, adding `[Flags]`, and adding `sealed` to a type with accessible constructors are all disallowed ([breaking-change-rules](https://raw.githubusercontent.com/dotnet/runtime/main/docs/coding-guidelines/breaking-change-rules.md)).
- Microsoft's current library guidance: start with `net8.0`+, "consider" `netstandard2.0` only for .NET Framework / broad reach, and do not publish `netstandard2.0` if dependencies multi-target ([cross-platform targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)). Azure SDK still ships netstandard2.0 and `net462;net472` (`Azure__azure-sdk-for-net@32c48fc3d524:sdk/core/Azure.Core/src/Azure.Core.csproj:11`).
- **[.NET 11 RC1]** the Process API is being overhauled to fix exactly these failures (deadlock-free capture, `InheritedHandles`, `KillOnParentExit`, `ProcessExitStatus` with signal). The SDK floor is .NET 8, so this is a "do not depend on it, design so it can be adopted" topic ([devblog](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)).
- Exemplar reality check: the one wrapper-SDK exemplar (pulumi-dotnet) pins CliWrap `3.3.2` (`pulumi__pulumi-dotnet@2a0dca84f09b:sdk/Pulumi.Automation/Pulumi.Automation.csproj:44`) and uses `PipeTarget.Merge`, the construct that had two deadlock bugs ([#212](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug), [#346](https://github.com/Tyrrrz/CliWrap/issues/346)). Dependency choice and pinning are first-class design questions.

## Findings

### 1. Subprocess control (the centre of gravity)

**Pipes, EOF, and "done".** `WaitForExit()` waits for process exit and for EOF on redirected, asynchronously read streams. A maintainer states the code does this on both Unix and Windows, and that removing the wait broke tests expecting `OutputDataReceived` before `WaitForExit` returns; the issue was closed "completed" in March 2023 with the position that a grandchild holding output open is expected, and the child must redirect output when it spawns it ([runtime #29232](https://github.com/dotnet/runtime/issues/29232)). The October 2025 duplicate repeated the explanation: ".NET can't solve this", with a workaround of looping `WaitForExit(timeout)` and then draining with a short second call ([runtime #120452](https://github.com/dotnet/runtime/issues/120452)). The .NET 11 post confirms the mechanism: children inherit all inheritable handles by default, so "a sibling or grandchild can keep a pipe open and stall EOF" **[.NET 11 RC1]** ([devblog](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)).

**Concrete wrapper-library instance.** MedallionShell `Command.Result` blocked indefinitely under xunit and NUnit but not in a console app; the sync-context theory did not hold (no missing `ConfigureAwait`), and the stuck tasks were waiting on stdout until `dotnet build-server shutdown` ended the hang; closed "not planned" and re-filed on dotnet/sdk ([MedallionShell #104](https://github.com/madelson/MedallionShell/issues/104)).

**Stdout/stderr deadlock mechanics.** The .NET 11 post names the classic cause: reading the two redirected streams one after another blocks when the child fills the other pipe's buffer; `BeginOutputReadLine`/`BeginErrorReadLine` tie up two thread-pool threads per process on Windows (fixed in .NET 11 by named-pipe async reads) **[.NET 11 RC1]** ([devblog](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)). MedallionShell has an open issue titled "Redirecting stdout/stderr blocks a thread pool thread for each call" (#94 in its issue list, [S14](https://github.com/madelson/MedallionShell/issues?q=is%3Aissue)).

**Library-level pipe bugs.** CliWrap #346: `PipeTarget.Merge` hangs when a sub-target reads past end-of-stream because the internal `SimplexStream` signals EOF once; the `Stream` contract requires repeated reads at EOF to return 0 ([#346](https://github.com/Tyrrrz/CliWrap/issues/346)). Related list entries: #212 (Merge deadlocks if one target throws with large output), #185 (`ToDelegate` blocks in `StreamReader`), #81 (Merge malforms variable-length encodings), #75 (chunk splitting), #74 (stdin that never resolves) ([S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)). Local evidence of how a mature wrapper structures it: stdin/stdout/stderr pumped as three background tasks, with comments that "output and error streams may legally outlive the process" and a deliberate `CancellationToken.None` on `WaitForExitAsync` so no detached process is left (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/Command.Execution.cs:170-215`).

**Kill and cancellation.** Documented contract: `Kill()` is asynchronous (follow with `WaitForExit`); `WaitForExit`/`HasExited` do not reflect descendants; with `entireProcessTree: true` the call returns done after the root exits, "processes where the call lacks permissions to view details are silently skipped", and `AggregateException` is thrown if not all descendants die ([Process.Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0)). CliWrap wraps this as `TryKill(entireProcessTree = true)` that swallows every exception (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/Utils/Extensions/ProcessExtensions.cs:44-54`) and registers two separate tokens: graceful (`TryInterrupt`, SIGINT; `Command.Execution.cs:186`) and forceful (`TryKill`; `Command.Execution.cs:181`). Regression: #270 shows a cancellation that stopped killing the tree after a target-framework change (reporter: "Processes orphaned in v3.7.0 instead of being killed"; maintainer attributed it to the net8.0 bump, fixed by re-adding the `net8.0` target) ([#270](https://github.com/Tyrrrz/CliWrap/issues/270)). #37 "CancellationToken not always being honored" is also in the bug list ([S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)).

**Argument quoting.** CliWrap #298: backslash in an argument (a systemd unit name) was altered because CliWrap joins arguments into one string even on Unix and its escaper handles only spaces and quotes; a trailing backslash merged with the next argument; the workaround was manual quoting with `escape: false`, and the maintainer said shell-specific escaping is out of scope ([#298](https://github.com/Tyrrrz/CliWrap/issues/298)). MedallionShell #107 "Parameter with spaces and quotes fails to execute" and #95 "In .NET5+ projects one could use ProcessStartInfo.Arguments" belong to the same class ([S14](https://github.com/madelson/MedallionShell/issues?q=is%3Aissue)). Runtime-level rules are not primary-verified here; see section 9.

**SIGCHLD and zombies.** runtime #114847: on .NET 8.0.14 / Rocky Linux 8.1, `WaitForExitAsync` hung for some children and zombies reached 2,147; the reporter attributed it to a PAM authentication module resetting .NET's SIGCHLD handler during a transaction, with parallel authentications saving another thread's empty handler as "default"; the reporter's workaround was a lock around PAM calls. No maintainer analysis on the page ([#114847](https://github.com/dotnet/runtime/issues/114847)). Relevance: any SDK that is loaded into a host that also does native interop inherits this risk.

**Process lifecycle races.** CliWrap #278, #93, #73 ("Cannot process request because the process has exited", "No process is associated with this object"), #139 ("Wrong process ID if target executable doesn't exist"), #31 (ObjectDisposedException on a semaphore) show start/exit/dispose races are a repeating class ([S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)).

**Working directory and relative paths.** MedallionShell #116/#118 (WorkingDirectory and relative paths unsupported), #115 (requires elevation) ([S14](https://github.com/madelson/MedallionShell/issues?q=is%3Aissue)).

**.NET 11 direction [.NET 11 RC1].** New APIs named in the official post: `Process.RunAndCaptureText[Async]`, `Process.Run[Async]`, `Process.ReadAllText/Bytes/Lines`, `ProcessStartInfo.InheritedHandles`, `StandardInput/Output/ErrorHandle`, `KillOnParentExit`, `StartDetached`, `Process.StartAndForget`, a lightweight `SafeProcessHandle` surface, and `ProcessExitStatus` reporting exit code, terminating signal on Unix, and cancel/timeout ([devblog](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)). **Discrepancy:** the blog says `KillOnParentExit` works on Windows, Linux and Android, while the .NET 11 libraries what's-new page says "Windows only" ([what's new](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries), line 88 of the fetched page). Treat platform support as unsettled until GA.

### 2. Async, cancellation, thread pool

- Sync-over-async (`Task.Result`, `.Wait()`, `.GetAwaiter().GetResult()`) is "the most common cause of ThreadPool starvation"; signals are thread count climbing 1-2 per second with CPU well below 100%. .NET 6 improved pool heuristics for blocking Task APIs but starvation still occurs; the `WaitHandleWait` event (.NET 9+) diagnoses it ([starvation doc](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/debug-threadpool-starvation)).
- ConfigureAwait FAQ: use `ConfigureAwait(false)` in general-purpose library code; applying it to the first await only is insufficient; ASP.NET Core has no SynchronizationContext but custom contexts/TaskSchedulers can still appear; blocking is the trigger for the UI-thread deadlock ([FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)). The FAQ is from 2019 and does not cover `ConfigureAwaitOptions` (.NET 8); that gap is unfilled by this scout.
- Local rule evidence (Meziantou.Analyzer, 239 rule docs: `git -C meziantou__Meziantou.Analyzer ls-files docs/Rules | wc -l`): MA0004 use `ConfigureAwait`, MA0032 pass a `CancellationToken` even when none is in scope, MA0040 forward the token, MA0045 no blocking calls, MA0147 avoid `async void` delegates (`meziantou__Meziantou.Analyzer@161b7e948ad3:docs/Rules/MA0004.md:1`, `MA0032.md:1`, `MA0040.md:1`, `MA0045.md:1`, `MA0147.md:1`).
- Azure SDK guidance: optional `CancellationToken cancellationToken` as the last parameter, both sync and async variants for every service method ([Azure .NET guidelines](https://azure.github.io/azure-sdk/dotnet_introduction.html)). That sync+async duplication is exactly what causes sync-over-async shortcuts; it is a design decision for a CLI wrapper.

### 3. Encodings, culture, time

- Child encoding: setting `StandardOutputEncoding` is not honoured by every child; CliWrap #196 found it had no effect on .NET console apps, workaround was passing `Encoding.UTF8` to the pipe target and `chcp` for batch files ([#196](https://github.com/Tyrrrz/CliWrap/issues/196)). CliWrap's own default decoding is `Encoding.Default` in many overloads (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/Command.PipeOperators.cs:28`), which is UTF-8 on .NET Core but a code page on .NET Framework; this is the netstandard2.0 trap, noted but not verified by running (see section 9).
- Culture: use ordinal for non-linguistic data, invariant culture to persist non-string data, culture-sensitive only for display; the Turkish-I example shows a security-relevant bug (`IsFileURI("file:")` returns false under tr-TR); results differ between .NET versions and OSes because .NET uses ICU, not NLS; invariant-globalization mode forces ordinal behaviour ([string best practices](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings)). ICU doc: on Linux a missing ICU makes the process terminate with "Failed to load system ICU" unless invariant mode is set; `IndexOf("\0")` returns 0 under ICU linguistic search; `TimeZoneInfo` IANA/Windows ID conversion fails in NLS/invariant mode ([ICU doc](https://learn.microsoft.com/en-us/dotnet/core/extensions/globalization-icu)).
- Local rule evidence: MA0011 IFormatProvider missing, MA0074/MA0075/MA0076 implicit culture-sensitive methods and ToString, MA0132 implicit conversion to `DateTimeOffset` (`meziantou__Meziantou.Analyzer@161b7e948ad3:docs/Rules/MA0011.md:1`, `MA0074.md:1`, `MA0075.md:1`, `MA0076.md:1`, `MA0132.md:1`). CliWrap's `ArgumentsBuilder` pins `CultureInfo.InvariantCulture` (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/Builders/ArgumentsBuilder.cs:15`).
- Time: `DateTimeOffset` is the recommended default; `DateTime.Kind == Unspecified` is ambiguous even on the same machine; when saving or sharing `DateTime`, use UTC with `Kind.Utc`; `DateOnly`/`TimeOnly` are not on .NET Framework ([date/time doc](https://learn.microsoft.com/en-us/dotnet/standard/datetime/choosing-between-datetime)).

### 4. Paths across operating systems

- `Path.Combine`: if a later argument is rooted, earlier parts are ignored; it assumes the first argument is absolute; use `Path.Join`/`TryJoin` for user-supplied segments (not on .NET Framework); on Unix a backslash is not treated as a separator ([Path.Combine](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.combine)).
- Windows path formats: `C:foo` (drive-relative) vs `C:\foo` is "a common source of bugs"; the current directory is per-process so "relative paths are dangerous in multithreaded applications"; `Path.GetFullPath(path, basePath)` (.NET Core 2.1+) avoids it; trailing spaces/dots are trimmed in normalisation; `\\?\` skips normalisation; .NET Core and .NET 5+ do not apply the MAX_PATH check; since .NET 8 backslashes on Unix are no longer converted to separators ([path formats](https://learn.microsoft.com/en-us/dotnet/standard/io/file-path-formats)).
- The same page states Windows paths are case-insensitive; Unix case sensitivity and symlink behaviour are not covered by a fetched primary source (section 9).

### 5. System.Text.Json

- Defaults that bite: case-sensitive matching (Newtonsoft was insensitive), exceptions on comments and trailing commas, quoted numbers rejected, `NaN`/`Infinity` literals need `AllowNamedFloatingPointLiterals`; ASP.NET Core flips several of these via web defaults, so a library behaves differently inside and outside ASP.NET Core ([migration doc](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/migrate-from-newtonsoft); lines 82-92, 128-150, 233, 861 of the fetched page).
- Missing/extra members: unmapped members are ignored by default; since .NET 8 `JsonUnmappedMemberHandling.Disallow` throws ([missing members](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/missing-members)).
- Polymorphism (.NET 7+): derived types must be opted in; deserialising a base type does not materialise the derived type without a discriminator; `$type` must be first unless `AllowOutOfOrderMetadataProperties` (with an over-buffering warning); undeclared derived types throw `NotSupportedException`; fast-path source generation does not support polymorphism ([polymorphism](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/polymorphism)). **[.NET 11 RC1]** C# 15 `closed` hierarchies can drive polymorphism inference (`InferClosedTypePolymorphism`), and open generic derived types are accepted (same page).
- Source generation / AOT: reflection fallback breaks under Native AOT unpredictably and is invisible when debugging on CoreCLR; `JsonSerializerIsReflectionEnabledByDefault=false` converts that into an `InvalidOperationException`; with `PublishTrimmed` reflection is auto-disabled; members typed `object` need explicit runtime types; non-generic `JsonStringEnumConverter` is unsupported in Native AOT; serialization-mode fast path is unavailable for async serialization ([source generation](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)).

### 6. Library evolution, target frameworks, NuGet

- Three breaking-change classes (source, behaviour, binary) are not equally harmful; low-level libraries are the most exposed; "even a bug fix can qualify" as behaviour break; guidance includes prefer abstract base classes over interfaces, keep `[Obsolete]` members indefinitely in low/mid-level libraries, never change assembly name or strong-name key ([library breaking changes](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/breaking-changes)).
- Runtime rule table: adding an abstract interface method disallowed; adding a default-implemented interface method allowed; changing a default value, renaming a parameter (including case), reordering parameters, adding `[Flags]`, changing enum values disallowed; adding `sealed` allowed only when no accessible constructors ([breaking-change-rules](https://raw.githubusercontent.com/dotnet/runtime/main/docs/coding-guidelines/breaking-change-rules.md)).
- Tooling: `EnablePackageValidation` runs baseline-version, compatible-runtime and compatible-framework validators after `Pack` ([package validation](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview)).
- Target frameworks (open question for the owner): Microsoft says start with `net8.0` or later, "consider" `netstandard2.0` for .NET Framework / broad compatibility, do not ship `netstandard2.0` if the project multi-targets, multi-target when dependencies exist to avoid binding-redirect problems, and keep the assembly name identical across TFMs ([cross-platform targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)). Trimming/AOT analysis needs `net6.0`+, and a `netstandard2.0`/`net472` target gets no trimming benefit; multi-target to include a modern TFM ([trimming prep](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming)). Exemplars split: CliWrap ships `netstandard2.0;netstandard2.1;net6.0;net7.0;net10.0` (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/CliWrap.csproj:3`), Azure.Core adds `net462;net472` (`Azure__azure-sdk-for-net@32c48fc3d524:sdk/core/Azure.Core/src/Azure.Core.csproj:11`), pulumi Automation is `net6.0` only (`pulumi__pulumi-dotnet@2a0dca84f09b:sdk/Pulumi.Automation/Pulumi.Automation.csproj:4`). The owner's "all platforms" requirement is about OS and CPU, which `net8.0+` already covers; netstandard2.0 adds only .NET Framework / Unity and the polyfill and kill-tree-behaviour costs seen in #270.
- NuGet resolution: lowest applicable version, "direct dependency wins" may silently downgrade (warning NU1605), cousin dependencies pick the lowest satisfying version, exact-version pins can make a graph unresolvable (the consumer must add a direct reference), floating versions need lock files for repeatability, and a prerelease anywhere in the graph admits prereleases ([dependency resolution](https://learn.microsoft.com/en-us/nuget/concepts/dependency-resolution)).
- Azure SDK design rules a CLI-wrapper can borrow: `Client` suffix, `ClientOptions` with service-version enum first, protected parameterless constructor and virtual members for mocking, model factory for test doubles, never expose dependency types publicly, keep the public API identical across TFMs ([Azure guidelines](https://azure.github.io/azure-sdk/dotnet_introduction.html)).
- Packaging hygiene: Source Link, symbol packages and deterministic builds are "consider" items ([SourceLink guidance](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink)). CliWrap #96 "Symbols package does not get uploaded to NuGet.org" is a real incident ([S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)). Package signing was not covered by a fetched source (section 9).
- Trim/AOT for libraries: `IsTrimmable`/`IsAotCompatible`, a trimming test app with `TrimmerRootAssembly`, `RequiresUnreferencedCode`/`DynamicallyAccessedMembers`; "introducing trim analysis warnings is a breaking change when the library is used with `PublishTrimmed`"; avoid annotating virtual/interface methods ([trimming prep](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming)).

### 7. HttpClient, resources, tests

- HttpClient: resolves DNS only when a connection is created; use a long-lived client with `PooledConnectionLifetime` or `IHttpClientFactory`; per-request clients exhaust ports; disposing a client only disposes the pool if it owns the handler; the factory shares `CookieContainer` across pooled handlers ([HttpClient guidelines](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines)). Relevance: "bootstrap ocx anywhere" implies downloading a binary; pulumi's `LocalPulumiCommand` does this (`DownloadToTmpFileAsync`, `pulumi__pulumi-dotnet@2a0dca84f09b:sdk/Pulumi.Automation/Commands/LocalPulumiCommand.cs:208`) and shells out to install scripts (`InstallWindowsAsync` line 150, `InstallPosixAsync` line 188).
- Disposal and concurrency: CliWrap #79 (`Console.OpenStandardInput()` not released after use as pipe source), #31 (disposed semaphore) ([S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug)). CliWrap models registrations as `await using` via a `ToAsyncDisposable` extension (`Command.Execution.cs:181-189`).
- Memory: MedallionShell #105 (OOM when consuming a stream with a timeout), #93 (suspected leak, closed) ([S14](https://github.com/madelson/MedallionShell/issues?q=is%3Aissue)). Streaming vs buffering is a design axis.
- Tests: MedallionShell #110 transient CI failure of a buffering test, #117 `TestWriteAfterExit` fails on .NET 8, #104 hang only under test runners ([S14](https://github.com/madelson/MedallionShell/issues?q=is%3Aissue)).

### 8. Exemplar-repo evidence

- CliWrap bug list: 26 closed `bug` issues (page header of [S13](https://github.com/Tyrrrz/CliWrap/issues?q=is%3Aissue+label%3Abug); fetched via WebFetch, one page of 25 plus one). Counted by me by theme from titles: pipe/buffering/deadlock 7 (#346, #212, #185, #81, #79, #75, #74), lifecycle 5 (#278, #93, #73, #139, #31), escaping 2 (#298, #72), encoding 1 (#261; #81 is counted under pipes), cancellation 1 (#37), kill-tree 1 (#270), packaging/TFM 2 (#96, #271), concurrency 1 (#336), other 5 (#279, #97, #61, #17, #15); 25 titles seen. Categorisation is mine from titles, not maintainer labels.
- CliWrap has no CHANGELOG on disk (`git -C Tyrrrz__CliWrap ls-files | grep -i -E "changelog|release|history"` returned only `.github/release.yml`), so release-note theme counts were not possible; MedallionShell has none either. `adamralph__simple-exec` has `CHANGELOG.md` and `.github/workflows/release.yml` but was not mined.
