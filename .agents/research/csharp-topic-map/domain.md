## Summary

- No exemplar is a close twin of the ocx SDK. The closest are Pulumi Automation (wraps a CLI, but weak: stderr regexes, runtime-download without a digest, `net6.0` only), Cake/Nuke tool wrappers (strong on tool resolution and argument/secret handling, weak on versions), and CliWrap (the process engine most others sit on). The Python SDK is already ahead of all of them on bootstrap hardening, exit-code mapping and compat gating; the C# SDK should port its invariants, not copy any C# wrapper.
- **The netstandard2.0 question is a real fork, not a default.** Microsoft's guidance is "start with net8.0 or later" and only "consider" netstandard2.0 for .NET Framework reach ([cross-platform targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)). In the corpus, `ProcessStartInfo.ArgumentList` (the only escape-free argv API) is documented for netstandard-2.1 but not netstandard-2.0 ([ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist)), so a netstandard2.0 target forces a hand-written Windows argument escaper (CliWrap copies .NET's `PasteArguments`: `Tyrrrz__CliWrap@7dbc252fa773:CliWrap/Builders/ArgumentsBuilder.cs:135-138`).
- The support floor moves under the project: .NET 8 **and** .NET 9 both end support on 2026-11-10; .NET 10 LTS runs to 2028-11-14 ([support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)). The owner's ".NET 8 is the floor" is one month from EOL on the research date.
- Three viable ways to put the `ocx` executable on a user's machine: (1) per-RID content packages (Aspire's `Aspire.Hosting.Orchestration.<rid>`), (2) NuGet `runtimes/<rid>/native` (designed for P/Invoke libraries, flattens subfolders), (3) runtime download with sha256 pinning (the Python SDK). Pulumi downloads `install.sh` with no digest check (`pulumi__pulumi-dotnet@2a0dca84f09b:sdk/Pulumi.Automation/Commands/LocalPulumiCommand.cs:188-244`). Nobody in the corpus verifies a digest on a runtime download.
- RID handling is a quiet trap: portable RIDs only since .NET 8, `linux-musl-x64` is its own RID, `osx` and `win-arm64` exist, and "don't parse RIDs" is official advice ([RID catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog)). The ocx dist manifest speaks cargo-dist triples, so a RID-to-triple map is owned code.
- Version skew has one good model (Python SDK: tested window + MIN_SUPPORTED + latest-canary job, `ocx-sdk-python@80136dde4162:.claude/artifacts/sdk-design.md:68-100`) and one weak one (Pulumi: min version constant, opt-out env var, per-feature `>3.205.0` branch at `LocalPulumiCommand.cs:48-78,299`).
- Process control is where a C# SDK gets cross-platform wrong. Windows has no process groups or SIGTERM; graceful interrupt needs a helper exe (CliWrap embeds `CliWrap.Signaler.exe` and extracts it to `%TEMP%` on every interrupt: `Native/WindowsSignaler.cs:60-64`; MedallionShell does the same: `Signals/WindowsProcessSignaler.cs:14-19`).
- **.NET 11 (RC1) changes the process story**: `ProcessStartInfo.KillOnParentExit`, `StartDetached`, `InheritedHandles`, stdio handle redirection, `Process.Run*` / `RunAndCaptureText*` / `ReadAllLinesAsync` ([What's new](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries), [devblog](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)). Cake already uses them behind `#if NET11_0_OR_GREATER` (`cake-build__cake@08885933e936:src/Cake.Core/IO/ProcessRunner.cs:180,217-250`). Docs conflict on platforms (Learn: "Windows only"; devblog and Cake: Windows, Linux, Android). All of this is RC1, not GA.
- Environment hygiene is a shared pattern: GitVersion strips `GIT_DIR` and friends and sets `GIT_TERMINAL_PROMPT=0`, `LC_ALL=C` (`GitTools__GitVersion@5057cdbcc177:src/GitVersion.Git.Managed/CommandLine/GitCliExecutor.cs:45-56`); Pulumi sets `PULUMI_SKIP_UPDATE_CHECK` and `--non-interactive` (`LocalPulumiCommand.cs:93`, `PulumiArgs`); the Python SDK neutralises ambient `OCX_PROJECT/OCX_GLOBAL/OCX_QUIET` and always sets `OCX_NO_CONSENT` (`.claude/rules/architecture.md`, "State & concurrency").
- Secrets: Nuke redacts by exact string replacement (`nuke-build__nuke@27e8077b8ab0:source/Nuke.Tooling/ToolTasks.Run.cs:20-21`), Cake renders a "safe" argv (`ProcessRunner.cs:148`, `ProcessArgumentBuilder.cs:119`). Neither handles stderr echo or exception messages as thoroughly as the Python SDK's single choke point.
- Errors: Pulumi classifies by stderr regex (`Commands/Exceptions/CommandException.cs:23-33`); ocx publishes a BSD-sysexits exit-code taxonomy marked `#[non_exhaustive]` (`ocx@5de9d777eb7d:crates/ocx_exit/src/exit_code.rs:11-37`), which five codes (83-87) have extended recently. A C# enum must survive unknown codes.
- JSON: Cake and Testcontainers use System.Text.Json source generation for CLI/daemon JSON (`cake ...GitVersionJsonContext.cs:11-17`, `testcontainers ...Builders/SourceGenerationContext.cs`; GitVersion and BenchmarkDotNet also ship `JsonSerializerContext` types); Cake's context needs a custom converter because the CLI emits numbers where strings are declared. ocx already publishes its `--format json` contract as JSON Schema 2020-12 with an absent-vs-null marker (`ocx_schema/src/reports.rs:9,14`), so handwritten vs generated models is a live design decision.
- Test strategy exemplar is CliWrap: a dummy executable (`CliWrap.Tests.Dummy/Commands/`: Echo, Exit, Sleep, Environment, GenerateBinary...) driven by the real engine. The Python SDK adds a pinned-binary contract tier and a canary. Windows cross-checking is a local step in this fleet, not a CI wait.
- DI/Options/ILogger: Microsoft's library guidance exists (Add{Service}, options on `IOptions`, `ILoggerFactory`/`NullLogger` defaults, source-generated logging). For a thin CLI wrapper the defensible minimum is plain options records plus an optional `ILogger`, with DI in a separate package; none of the six wrapper csproj files checked (CliWrap, simple-exec, Pulumi.Automation, Nuke.Tooling, MedallionShell, Cake.Core; `grep -l "Microsoft.Extensions.DependencyInjection\|Microsoft.Extensions.Logging"` returned nothing) reference `Microsoft.Extensions.DependencyInjection` or `Logging`.
- Corpus numbers: of 32 repos with TFMs in non-test csproj files, 27 include a netstandard2.0 project (204 of 537 projects). Inflated by Roslyn analyzers that must be netstandard2.0; among process/CLI libraries the split is CliWrap yes, MedallionShell yes, Nuke.Tooling yes, Testcontainers yes, Pulumi.Automation no (net6.0 only), Cake no.
- AI-agent config prior art exists in the corpus: Aspire ships 24 `.agents/skills/*/SKILL.md` and 12 `.github/instructions/*.instructions.md`; Azure SDK ships `.github/skills/` and `copilot-instructions.md`. Worth a dedicated read by the style/agents scout.
- Boring biters with direct evidence: `Encoding.Default` as the pipe default (`CliWrap/PipeTarget.cs:236`) is UTF-8 on .NET 10 (measured below) but not on .NET Framework; missing executable surfaces as `Win32Exception` with `NativeErrorCode=2`; Windows `.cmd` shims exist in ocx (`ocx_shim/src/main.rs:735`) and PowerShell keeps a legacy argument-passing mode for exactly such files.

## Findings

### A. The wrapper landscape

| Library | Role | Process engine | Arg model | TFMs | Notable |
|---|---|---|---|---|---|
| CliWrap | general process lib | own, `Process` + byte pipes | string `Arguments` + own escaper | `netstandard2.0;netstandard2.1;net6.0;net7.0;net10.0` (`CliWrap.csproj:3`) | graceful + forceful tokens; embedded signaler exe |
| MedallionShell | general process lib | own | string, Windows/Mono syntaxes | `netstandard1.3;netstandard2.0;net45;net46;net471` (`MedallionShell.csproj:4`) | oldest design; signal helper exe |
| simple-exec | script-style runner | own | `ArgumentList` | `net8.0;net9.0;net10.0` (`Directory.Build.props:13`) | ReproducibleBuilds, SBOM, MinVer, PublicApiAnalyzers (`src/Directory.Build.props:5-28`) |
| Pulumi.Automation | CLI-wrapping SDK | CliWrap | list of strings, escaped by CliWrap | `net6.0` only (`Pulumi.Automation.csproj:4`) | install.sh bootstrap, version gate, event log |
| Nuke.Tooling | tool wrappers | own | typed option objects | `net10.0;netstandard2.0` (`Nuke.Tooling.csproj:4`) | `<TOOL>_EXE` override, secrets, JSON-spec code generator |
| Cake.Core Tool<T> | tool wrappers | `Process` | `ProcessArgumentBuilder` with safe render | `net10.0` (`Cake.csproj:3`), `net11.0` conditional (`Cake.csproj:33`) | tool locator/installer seams; .NET 11 opt-ins |
| Testcontainers | Docker driver | HTTP API, not CLI | n/a | `net8.0;net9.0;net10.0;netstandard2.0;netstandard2.1` (`Testcontainers.csproj:3`) | endpoint provider chain |
| GitVersion | git consumer | LibGit2Sharp + managed reader + `git` CLI | `ArgumentList` | not read | env scrubbing (`GitCliExecutor.cs`) |
| PowerShell | native-command host | `Process` | `ArgumentList` | n/a | `NativeArgumentPassing` modes |

Sources for each row are the files named in the cells under `~/.cache/research-lang/exemplars/csharp/`; shas: CliWrap `7dbc252fa773`, MedallionShell `e45f1f6ffd4c`, simple-exec `f80913246993`, pulumi-dotnet `2a0dca84f09b`, nuke `27e8077b8ab0`, cake `08885933e936`, testcontainers `04cbb73fcc58`, GitVersion `5057cdbcc177`, PowerShell `5d871eb5e02c`.

Cross-language prior art: Terraform's `tfexec` takes the binary path from the caller (`NewTerraform(workingDir, execPath)`) and keeps installation in a separate module, `hc-install`, which explicitly is "not a package manager" and verifies signatures/checksums ([terraform-exec](https://github.com/hashicorp/terraform-exec), [hc-install](https://raw.githubusercontent.com/hashicorp/hc-install/main/README.md)). tfexec states best-effort compatibility "with latest minor versions from 0.12 and later" and "does not imply coverage of all features". That is the same split the Python SDK makes (`discover()` vs `ensure()`), and the opposite of Pulumi, which fuses install into the command class. Docker.DotNet is the contrast case: it talks to the daemon's HTTP API, with its MINOR version tracking the Docker Remote API version ([README](https://raw.githubusercontent.com/dotnet/Docker.DotNet/master/README.md)); Testcontainers does likewise with a provider chain for `DOCKER_HOST`, unix socket, rootless socket, npipe and Docker Desktop (`testcontainers-dotnet@04cbb73fcc58:src/Testcontainers/Builders/{Unix,Npipe,RootlessUnix,DockerDesktop}EndpointAuthenticationProvider.cs`, `Configurations/EnvironmentConfiguration.cs:17`). Wrapping the CLI is a deliberate choice that ocx has already made; the question left open is only what to do about the things a wrapper gets for free from a protocol client (stable wire format, versioned API).

### B. Getting the binary onto the machine

- **Per-RID content packages (Aspire).** `eng/dcppack/` builds one package per RID, `Aspire.Hosting.Orchestration.<rid>` (linux-arm64, linux-musl-x64, linux-x64, osx-arm64, osx-x64, win-arm64, win-x64), each repacking an upstream Go binary into `tools/`, with `SuppressDependenciesWhenPacking` and `IncludeBuildOutput=false`, plus a `UnixFilePermissions.xml` shipped in `data/` for Unix RIDs and a `.targets` that computes `DcpCliPath` (`dotnet__aspire@af646baee1e8:eng/dcppack/Common.projitems:6-14,37-43`, `Aspire.Hosting.Orchestration.targets`, `Aspire.Hosting.Orchestration.linux-arm64.csproj`; read with `git show HEAD:<path>` because the clone is sparse). The host resolves the path from configuration, then env (`ASPIRE_DCP_PATH`), then the package (`src/Aspire.Hosting/Dcp/DcpOptions.cs:248-260`).
- **`runtimes/<rid>/native` (NuGet convention).** Documented for P/Invoke native libraries: NuGet picks the single best-matching RID folder and copies only that folder; the SDK flattens subdirectories under `native/`; `contentFiles/` is "not recommended" because it has no per-RID selection; .NET Framework projects need custom props/targets and the docs recommend splitting into three packages ([Native files in .NET packages](https://learn.microsoft.com/en-us/nuget/create-packages/native-files-in-net-packages)). That page never discusses shipping an executable that is later spawned, so the convention may copy the file but guarantees nothing about the executable bit or location in a framework-dependent app. Treat as open.
- **Runtime download.** Pulumi: `Install()` picks `install.sh` or a PowerShell script, writes it to a temp file, `chmod u+x` via a spawned `chmod` ("TODO: In .net7 there is File.SetUnixFileMode"), runs it with `--no-edit-path --install-root --version` and deletes it (`LocalPulumiCommand.cs:112-244`); the download is `new HttpClient()` per call with no digest (`:210`). The Python SDK is the standard to match: manifest rows with `sha256`, fail-closed on non-canonical hosts, field regex validation, size caps, never `extractall`, `mkstemp` in the final directory then rename, root refused if symlinked or group-writable (`ocx-sdk-python@80136dde4162:src/ocx_sdk/_bootstrap.py:1-60`, `sdk-design.md:163-224`). `dotnet-install` is the MS analogue: documented for CI, "doesn't need to persist"; the script itself is GPG-signed, `--dry-run` prints a deterministic URL, and the page describes only a size-equality check on the archive ([dotnet-install](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-install-script)). `@actions/tool-cache` downloads, extracts per platform, caches by name+version+arch, and its README does not mention checksums ([tool-cache](https://raw.githubusercontent.com/actions/toolkit/main/packages/tool-cache/README.md)).
- **Discovery before provisioning.** Nuke resolves in order: explicit option, then `<TOOL>_EXE` env variable (asserted to exist), then attribute-defined resolver (PATH via `where.exe`/`which`, NuGet, npm) (`Nuke.Tooling/ToolTasks.ToolPath.cs:19-60`, `ToolPathResolver.cs:21-60`). The Python SDK has the same ladder with `OCX_BINARY_PIN`-style opaque pins and a typed `OcxNotFoundError`. Cake adds an installer seam (`IToolInstaller`, `IToolLocator`, `IToolResolutionStrategy` in `Cake.Core/Tooling/`).
- **Platform mapping is owned code.** RID facts: portable RIDs only since .NET 8; `linux-musl-x64`, `linux-musl-arm64`, `osx`, `osx-arm64`, `win-arm64` are first-class; "don't try to parse RIDs"; `RuntimeInformation.RuntimeIdentifier` "returns the platform for which the runtime was built" ([RID catalog](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog)). The ocx manifest uses cargo-dist triples with a musl-first Linux rule and a Rosetta-to-native-arm64 redirect (`sdk-design.md:163-224`). Measured here: `RuntimeIdentifier=linux-x64 ProcessArch=X64` on this WSL host (`/home/mherwig/.cache/research-lang/dotnet-tools/fixtures/domain-scout/Program.cs`, run with `run.sh dotnet run -c Release`).
- **Release plumbing for the SDK itself**: nuget.org Trusted Publishing issues one-hour, single-use API keys via GitHub/GitLab OIDC, no stored secret ([Trusted Publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing)); the policy only becomes permanent after the first successful publish supplies repo and owner IDs. Relevant because the lore repo publishes on merge.

### C. CLI version skew

- Python SDK (the reference): `TESTED_OCX_VERSION` and `MIN_SUPPORTED` constants (`src/ocx_sdk/_types.py:33-34`), lazy first-call `version()` probe, raise below MIN, DEBUG-log (not warn) above tested, a latest-ocx canary job, and a durable-anchor checklist re-verified per bump (exit-code taxonomy, plain `version` output, schema URLs, wire ABI). Rationale in the design doc: ocx's own policy is that "even interfaces break pre-1.0", and exit-code semantics, JSON envelopes and lock formats moved within v0.5.0 to v0.5.8 (`sdk-design.md:68-100`).
- Pulumi: `_minimumVersion = 3.1.0`, raised to the SDK's own version if higher; opt-out via `PULUMI_AUTOMATION_API_SKIP_VERSION_CHECK`; major mismatch throws `InvalidOperationException`; behaviour switches by CLI version at call sites (gRPC event stream for `> 3.205.0`, file-based otherwise) (`LocalPulumiCommand.cs:48-78,247-267,299`). The version enters through a third-party `Semver` package (`PulumiCommand.cs:8`, `LocalPulumiCommand.cs:15`).
- Docker.DotNet and tfexec both encode compatibility in the package's own SemVer or a stated window rather than runtime gating (links above).
- Open edge: which SemVer parser (BCL has `Version`, not SemVer; ocx versions carry prerelease and build metadata), and whether to fail closed when the probe itself fails.

### D. Process control

- **Argument passing.** `ArgumentList` "escapes the provided arguments" and cannot be combined with `Arguments`; the Learn page warns that untrusted data in a `ProcessStartInfo` is a security risk ([ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist)). CliWrap, built for netstandard2.0, uses the string property (`Command.Execution.cs:408`). PowerShell has three modes (`Legacy`, `Standard`, `Windows`), defaulting to `Windows` on Windows and `Standard` elsewhere, because native programs on Windows parse their own command line ([about_Preference_Variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_preference_variables), `PowerShell__PowerShell@5d871eb5e02c:src/System.Management.Automation/engine/NativeCommandProcessor.cs:1590-1591`). Pulumi inserts its flags before a `--` separator (`PulumiArgs`), and the Python SDK refuses leading-dash positionals and emits `--` before child argv groups (`architecture.md`, "Argv safety").
- **Launching Windows shims.** ocx has an `ocx.cmd` launcher alongside `ocx.exe` (`ocx@5de9d777eb7d:crates/ocx_shim/src/main.rs:735`). Whether .NET escapes correctly for `.cmd`/`.bat` targets was not established here (a search for .NET specifics returned only Rust and Zig reports of the cmd.exe issue; not fetched, not cited as a source). Needs a fixture on Windows.
- **Pumping streams.** CliWrap models stdin/stdout/stderr as `PipeSource`/`PipeTarget` over bytes, with text decoding as a choice at the pipe (`ExecuteBufferedAsync(Encoding, Encoding, ...)` in `Buffered/BufferedCommandExtensions.cs:25-26`). GitVersion's executor uses `OutputDataReceived`/`ErrorDataReceived` plus two `ManualResetEventSlim` to wait for stream closure (`GitCliExecutor.cs:69-90`). .NET 11 adds `Process.ReadAllLinesAsync` returning `ProcessOutputLine` values that distinguish stdout and stderr and `Process.RunAndCaptureText[Async]`, described as deadlock-free (RC1; [devblog](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)).
- **Cancellation.** CliWrap exposes two tokens: forceful (kill) and graceful (interrupt) (`Command.Execution.cs:160-186`); the design came from issue #47, where a single kill token was too blunt and Ctrl+C on Windows hits every process sharing the console ([issue 47](https://github.com/Tyrrrz/CliWrap/issues/47)). Microsoft's model: cooperative tokens, linked sources, dispose the source, treat `OperationCanceledException(externalToken)` as cancellation not failure ([Cancellation in managed threads](https://learn.microsoft.com/en-us/dotnet/standard/threading/cancellation-in-managed-threads)). simple-exec kills on cancellation with an option to leave the tree alone (`src/SimpleExec/Internal/ProcessExtensions.cs:29,69,108-115`). The Python SDK's kill ladder is group SIGTERM, grace, then SIGKILL, with the Windows branch documented as "TerminateProcess only, no graceful phase" and orphans of a SIGKILLed parent a stated non-goal (`sdk-design.md:617-636`, `_process.py:714-800`).
- **Kill tree and orphans.** `Process.Kill(true)` is what CliWrap uses for the tree (`ProcessExtensions.cs:44-48`). The unsolved case is a parent that dies abruptly. Windows Job Objects solve it but need P/Invoke; .NET 11's `KillOnParentExit` is the managed answer, and Cake gates it behind `NET11_0_OR_GREATER`, throwing `PlatformNotSupportedException` outside Windows/Linux/Android and rejecting `KillOnParentExit` + `StartDetached` together (`ProcessRunner.cs:217-250`).
- **Environment.** GitVersion removes repo-targeting variables and sets `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C` to keep parsed output locale-independent (`GitCliExecutor.cs:45-56`). Cake injects `CAKE_VERSION` (`ProcessRunner.cs:170`). The Python SDK centralises spawn-env assembly and redaction in one function (`architecture.md`, "Layering").
- **Secrets.** Nuke: `secrets.Aggregate(text, (s, v) => s.Replace(v, "[REDACTED]"))` applied to tool output (`ToolTasks.Run.cs:20-21`), secrets declared per option via an `ArgumentAttribute.Secret` flag (`ToolOptions.Secrets.cs`). Cake: `RenderSafe()` for logged argv.
- **Start failures.** CliWrap wraps `Win32Exception` with a message naming file path, working directory and credentials, and throws `InvalidOperationException` when `Start()` returns false (`Command.Execution.cs:300-340`). Measured on .NET 10 Linux: starting `/nonexistent/ocx` throws `Win32Exception` with `NativeErrorCode=2`.

### E. Typed results, JSON, event streaming

- **Source-generated JSON.** Microsoft's guidance: derive from `JsonSerializerContext`, mark types with `[JsonSerializable]`, pass the context or `JsonTypeInfo<T>`; options can be set at compile time via `[JsonSourceGenerationOptions]` since .NET 8; with `PublishTrimmed`, reflection-based serialization is disabled automatically; non-generic `JsonStringEnumConverter` is not supported under Native AOT, use `JsonStringEnumConverter<TEnum>` ([source generation](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)). In the corpus: Cake's `GitVersionJsonContext` adds a number-or-string converter because "CLI number/string values deserialize to string properties" (`GitVersionJsonContext.cs:11-17`); Testcontainers uses a one-type context (`Builders/SourceGenerationContext.cs`); Pulumi.Automation still uses reflection-based STJ with a family of hand-written converters (`Serialization/Json/*.cs`, `LocalSerializer.cs:14-20`); Stripe still depends on Newtonsoft (`Stripe.net.csproj:48`).
- **Contract source.** ocx publishes `https://ocx.sh/schemas/reports/v1.json` (JSON Schema draft 2020-12), generated from the CLI's own report types, with a custom `x-ocx-absent-when-none` marker distinguishing an omitted field from a nullable one (`ocx@5de9d777eb7d:crates/ocx_schema/src/reports.rs:9,14,35-38`). The ocx repo's own research note concludes that off-the-shelf generators for zero-dependency SDKs vary by language (`ocx/.agents/research/research_zero_dep_sdk_codegen.md`, dated 2026-09-25; C# not covered there). The Python SDK went handwritten `from_dict`, unknown keys ignored, "carry, don't parse" identifiers (`architecture.md`, "Positioning", "API conventions").
- **Generated wrappers.** Nuke generates its typed tool wrappers from per-tool JSON specs (`Nuke.Tooling.Generator/{schema.json,CodeGenerator.cs,Generators/,Writers/}`). Whether ocx's command surface is better generated or handwritten (Python chose handwritten, one method per command) is open.
- **Streaming events.** Pulumi has two transports behind `IEventWatcher`: a file the CLI appends to, tailed by polling with `FileShare.ReadWrite` and `Task.Delay` (`Events/EventLogWatcher.cs:83-99`), and a gRPC watcher for new CLIs. CliWrap offers pull-based (`IAsyncEnumerable<CommandEvent>`) and push-based event streams (`Readme.md`, "Pull-based event stream" / "Push-based event stream"). .NET 11 adds `ReadAllLinesAsync` (RC1). Whether ocx emits NDJSON on stdout is not established from the files read; the Python SDK treats stdout as one JSON document and carries a partial-failure report in `OcxProcessError.stdout` (`architecture.md`, "Security").
- **Raw vs typed.** The Python SDK pins `--format json --color never` on typed methods only and leaves presentation to the caller on raw `invoke`/`spawn`.

### F. Errors and exit codes

- ocx exit codes follow `sysexits.h` (64+), with `TempFail = 75` documented as the only code where "automated retry [is] safe", `AuthError = 80`, `NotFound = 79`, new codes 83 to 87 for transparency-log, referrers, key-backend, forge-capability and registry-delete conditions, and the enum is `#[non_exhaustive]` (`ocx@5de9d777eb7d:crates/ocx_exit/src/exit_code.rs:11-37`). The Python SDK maps code to exception subclass and "never classifies by stderr text" (`architecture.md`, "API conventions"), keeps `retryable` fixed True for 75, and does not retry checksum mismatches.
- Pulumi does the opposite: `_notFoundRegexPattern = "no stack named.*found"` and substring checks for lock conflicts (`CommandException.cs:23-33`); success is `ExitCode == 0`, otherwise `CommandException.CreateFromResult`.
- CliWrap's `CommandExecutionException` carries the command and exit code; `CommandResultValidation` defaults to throwing on non-zero (`Exceptions/CommandExecutionException.cs`, `CommandResultValidation.cs`); simple-exec has `ExitCodeException` and `ExitCodeReadException` (`src/SimpleExec/`).
- C# specifics not yet researched: unsigned/negative exit codes on Windows (e.g. NTSTATUS values) vs `128+signal` on Unix; exception `Data`/`ToString()` redaction; exception serialization expectations (not researched).

### G. What a .NET developer expects: DI, options, logging

- Microsoft's options-pattern guidance for libraries: `Add{Service}` extension on `IServiceCollection`, in your own namespace (not `Microsoft.Extensions.DependencyInjection`), with overloads for parameterless, `IConfiguration` section, section path with `ValidateOnStart`, `Action<TOptions>` and an options instance; use `BindConfiguration` over manual `Bind` to keep `IOptionsMonitor` working ([options for library authors](https://learn.microsoft.com/en-us/dotnet/core/extensions/options-library-authors)).
- Logging guidance: accept `ILoggerFactory` for public entry points so internal classes can get their own category without an API change; prefer `[LoggerMessage]` source generation; never interpolate into log messages; default to `NullLogger` rather than nullable ([logging guidance](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/library-guidance)).
- In the corpus: Aspire's `DcpOptions` is a validated options class resolved from configuration (`DcpOptions.cs:180-260`); GitVersion's executor takes `ILogger<GitCliExecutor>`; Pulumi, CliWrap, Nuke, simple-exec expose static or fluent APIs with callbacks (`onStandardOutput`) and no DI. The wrapper libraries that people actually reuse (CliWrap, simple-exec) are DI-free. This supports "plain options record + optional logger, DI as a thin add-on package" and flags eager `AddOcx` plumbing in the core package as over-engineering for a CLI wrapper whose handles the Python SDK already keeps frozen and cache-free.
- Telemetry is not covered by the Learn pages fetched (the instrumentation page 404'd at the guessed URL). Treat `ActivitySource`/`Meter` for process spawns as unverified.

### H. Target frameworks, packaging, compatibility

- **TFM policy.** See Summary. Also: Microsoft says to "CONSIDER adding a target for net462 when you're also targeting netstandard2.0" and to AVOID multi-targeting next to netstandard when the source is identical and there are no dependencies (extra TFMs "increase the nupkg size for no benefit") ([cross-platform targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)). CliWrap's multi-target consequences are visible in its props: nullable annotations only (`annotations`) on frameworks without BCL nullability, trim/AOT analyzers off for frameworks older than net10, `IsTrimmable` from net6, `IsAotCompatible` from net7 (`CliWrap/CliWrap.csproj:5-11`, `Directory.Build.props:14-22`), plus `PolyShim`, `System.Memory`, `Microsoft.Bcl.AsyncInterfaces` and `System.Management` package references for the older targets (`CliWrap.csproj:26-40`). Microsoft's page names "a .NET game in Unity" as a motivation for breadth targeting but does not say which netstandard version Unity consumes (not verified here).
- **Language level.** CliWrap's internal extensions use C# 14 extension blocks (`ProcessExtensions.cs:13`, `extension(Process process)`) while still targeting netstandard2.0, which means newer language syntax with a PolyShim for missing types; Nuke sets `LangVersion=preview` (`source/Directory.Build.props:4`).
- **Versioning and API evolution.** Library-guidance rules: NuGet version = SemVer; assembly version tracks major only; do not change the assembly name or strong-name key; prefer abstract classes to interfaces for evolving contracts; `[Obsolete]` with migration text and keep it "indefinitely" in low-level libraries; hide behaviour changes behind opt-in settings ([versioning](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning), [breaking changes](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/breaking-changes)). Tooling: `EnablePackageValidation` runs baseline, compatible-runtime and compatible-framework validators after Pack ([package validation](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview)); Pulumi and simple-exec use `PublicApiAnalyzers` (`Pulumi.Automation/PublicAPI.Shipped.txt`, 58 KB; `simple-exec/src/Directory.Build.props:16-17` silences RS0016/RS0037, i.e. the unshipped file is not enforced there).
- **Dependencies.** Minimise; lowest-applicable-version resolution means no upper bounds and no exact pins; avoid unneeded packages that cause diamond conflicts ([dependencies](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/dependencies)). CliWrap "internalizes" its helper (`PowerKit Internalize="true"`) and uses `Binternal` to hide types: a shared-source pattern the same page endorses.
- **Packaging mechanics.** SDK-style pack; metadata set (id, version, authors, license expression, icon, project URL); SourceLink for repo/commit metadata; symbols as `.snupkg` unless the 30% size growth of embedding is acceptable ([NuGet and libraries](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget)). Real configurations: simple-exec uses `DotNet.ReproducibleBuilds`, `Microsoft.Sbom.Targets` (`GenerateSBOM` in Release), `MinVer` and `PublicApiAnalyzers` (`src/Directory.Build.props:5-28`); Nuke sets `EmbedUntrackedSources` and `Microsoft.SourceLink.GitHub` (`source/Directory.Build.props:10,38`).
- **Pinning the toolchain.** CliWrap pins `global.json` to `10.0.100` with `rollForward: latestFeature`. This machine's measured fact (given in the brief): with no `global.json`, `dotnet` picks the newest installed SDK including a prerelease, so an unpinned repo built on a machine with 11.0 RC1 silently uses it.

### I. Testing against a fake CLI

- CliWrap's test project drives a purpose-built dummy executable with named commands (`CliWrap.Tests.Dummy/Commands/{EchoCommand,EchoStdInCommand,EnvironmentCommand,ExitCommand,GenerateBinaryCommand,GenerateTextCommand,LengthStdInCommand,SleepCommand,WorkingDirectoryCommand}.cs`), covering exit codes, stdin, env, working directory, binary output and slow children without needing a real tool. Pulumi's `ParseAndValidatePulumiVersion` is `internal static` for direct unit tests (`LocalPulumiCommand.cs:247`). The Python SDK has three tiers: unit (100% coverage), contract tests against a pinned real `ocx`, and acceptance against a compose stack, plus doc-snippet tests (`sdk-design.md:757-834`).
- The fleet rule from the user's global config is that Windows behaviour is reproduced locally (cross-compile, stage on `C:`, run via `cmd.exe`) rather than waited on in CI; a C# SDK's Windows-only branches (kill, signals, `.cmd`) need that loop.

### J. Boring topics that bite

- **Encoding.** CliWrap's string pipes default to `Encoding.Default` (`PipeTarget.cs:236`). Measured on .NET 10 / Linux, with and without `LANG=C LC_ALL=C`: `Encoding.Default=utf-8`, `Console.OutputEncoding=utf-8`, child stdout read as `utf-8` and `café` decodes to length 4 (fixture `.../fixtures/domain-scout/`; command `run.sh dotnet run -c Release`). On .NET Framework `Encoding.Default` is the ANSI code page, so a netstandard2.0 build run there would differ. PowerShell takes the output encoding from a user variable or `Console.OutputEncoding` (`NativeCommandProcessor.cs:1649-1659,1722-1727`). The Python SDK decodes UTF-8 with `replace` and normalises `\r\n` to `\n` (`_process.py:703-710`).
- **Culture and time.** CliWrap's argument builder has overloads taking `IFormattable` plus a `CultureInfo` (`ArgumentsBuilder.cs:60`), an admission that default formatting is culture-sensitive. GitVersion forces `LC_ALL=C` for parsing. No fixture here yet for `InvariantGlobalization` or `TimeProvider`.
- **Paths.** Nuke walks `PATH` itself when `which`/`where` is absent and appends `.exe` on Windows (`ToolPathResolver.cs:30-45`); the Python SDK refuses symlinked cache roots and realpaths the exe at construction. Pulumi prefixes `PATH` with the CLI's directory (`PulumiEnvironment`, `LocalPulumiCommand.cs:386`) so bundled plugins win: a case where environment composition changes behaviour.
- **Resource cleanup.** CliWrap disposes registrations with `await using` and links tokens, so a failure in the stdin/stdout pump cancels the child (`Command.Execution.cs:169-243`). simple-exec's `Exited` handler guards a canceled TCS and swallows `ObjectDisposedException` (`ProcessExtensions.cs:54-71,138,156`). Pulumi deletes the downloaded script in `finally` (`LocalPulumiCommand.cs:184,204`).
- **Idempotency and retry.** Only exit 75 is declared safe to retry; checksum failures never retry (Python SDK). Testcontainers has a hand-written `RetryStrategy` with `WithMaxAttempts`/`WithInterval` (`Clients/RetryStrategy.cs:10-50`), while Polly is in the corpus as the mainstream choice (`App-vNext__Polly@e4476096da5b`).
- **Concurrency.** Python SDK: handles frozen and cache-free; one benign-race memo (the version probe); `$OCX_HOME` store locking is ocx's domain (`sdk-design.md:716-736`). C# translation (a `Lazy<Task<>>` or `SemaphoreSlim` around the probe and bootstrap) is unexamined.
- **Ordering determinism.** Env block assembly, JSON output order and test snapshots: no direct evidence gathered; carried as a candidate.
- **Binary compatibility.** See H; the corpus evidence is the `PublicAPI.*.txt` files in Pulumi, GitVersion (`GitVersion.Git.Managed/PublicAPI.Shipped.txt`) and simple-exec.

### K. Gaps and conflicts in the evidence

- `KillOnParentExit` platform support: Learn What's-new (RC1) says "(Windows only)"; the May 2026 devblog and Cake's code say Windows, Linux and Android. Resolve against the .NET 11 GA docs (November 2026) before any rule cites it.
- The `dotnet/core` 11.0 release-notes landing page does not mention Process APIs; the library-preview pages it links were not read.
- No exemplar shows runtime download with digest verification in C#. The Python SDK is the only model; the C# equivalent (`HttpClient` lifetime, `System.Formats.Tar`, `ZipArchive` entry-name checks, `File.SetUnixFileMode`, atomic move) needs a fixture.
- ocx's event-stream surface (if any) and the exact `ocx.cmd` argument-forwarding behaviour were not examined.
- `ToolTask` (Microsoft.Build.Utilities) and the `Docker.DotNet`-vs-CLI trade-off beyond the README were not read in depth; GitHub Actions toolkit "equivalents in .NET" were not found as a distinct artifact.
