## Summary

- The netstandard2.0 question is genuinely contested. Microsoft's current library guidance says DO start with `net8.0`+ and only CONSIDER `netstandard2.0` for .NET Framework reach ([cross-platform targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting), updated 2026-05-07); the 2020 .NET Standard post expected widely used libraries to ship both ([future of .NET Standard](https://devblogs.microsoft.com/dotnet/the-future-of-net-standard/)).
- The exemplar fleet splits: CliWrap ships `netstandard2.0;netstandard2.1;net6.0;net7.0;net10.0` (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/CliWrap.csproj:3`), simple-exec ships `net8.0;net9.0;net10.0` only (`adamralph__simple-exec@f80913246993:Directory.Build.props:13`).
- netstandard2.0 is not free for a subprocess SDK. `ProcessStartInfo.ArgumentList` is documented only for netcore-2.1+ and netstandard-2.1 monikers, and `Process.Kill(bool entireProcessTree)` only for netcore-3.0+/net5+ ([ArgumentList](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist), [Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill)). A netstandard2.0 target means hand-quoting and hand-written tree kill.
- Era flag: .NET 8 and .NET 9 reach end of support on 2026-11-10, one month after this research date ([end-of-support post](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/)). The "8.0 floor" is a policy question, not a given.
- `System.Diagnostics.Process` is the dominant source of subtle bugs, and every practitioner agrees on the mechanism: sequential stdout/stderr reads deadlock, `Dispose` does not kill, and `Kill` is asynchronous and not tree-aware by default ([.NET 11 Process post](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/), [Process.Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill)).
- Era flag, .NET 11 (RC1, GA Nov 2026): `Process.Run`, `RunAndCaptureText`, `KillOnParentExit`, `StartDetached`, `InheritedHandles` do not exist on .NET 10. A library targeting 8/10 needs `#if NET11_0_OR_GREATER` or its own implementation ([Andrew Lock](https://andrewlock.net/exploring-the-dotnet-11-preview-5-improvments-to-process-apis/), [startdebugging](https://startdebugging.net/de/2026/09/process-run-vs-process-start-in-dotnet-11/)).
- Cancellation semantics disagree across the same ecosystem: CliWrap kills and throws `OperationCanceledException` ([README](https://github.com/Tyrrrz/CliWrap)); .NET 11 `Process.Run` reportedly returns `Canceled = true` without throwing (secondary source, RC1); StackExchange.Redis says cancelling stops observing but the command may still be sent ([AsyncTimeouts](https://seredis.dev/AsyncTimeouts)). An SDK must pick and document one contract.
- `ConfigureAwait(false)` is still the live disagreement: Toub says library yes, app no, and that CA2007 "basically shouldn't be turned on" for apps ([FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)); Cleary in 2012 called relying on it for deadlock avoidance "at best a hack" ([post](https://blog.stephencleary.com/2012/07/dont-block-on-async-code.html)); Fowler's guide leaves its ConfigureAwait section "TBD" ([AsyncGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/master/AsyncGuidance.md)). CliWrap uses it 48 times in `CliWrap/*.cs` (`git -C Tyrrrz__CliWrap grep -c "ConfigureAwait(false)" HEAD -- 'CliWrap/*.cs'`, summed).
- Library compatibility has three layers and they are different jobs: source, binary, behaviour ([breaking changes](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/breaking-changes)). Package Validation (`EnablePackageValidation`) automates the binary layer ([overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview)); Meziantou argues a generated C# API snapshot is easier to review than `PublicApiAnalyzers` text ([post](https://www.meziantou.net/generate-and-review-the-public-api-of-a-dotnet-library.htm)).
- Extensibility is argued two ways: Microsoft prefers abstract classes over interfaces for evolvability; Noda Time seals almost everything and injects clocks instead of exposing hooks ([NodaTime design](https://nodatime.org/userguide/design)).
- `InvariantCulture` is not invariant for comparisons; results vary with ICU/NLS version. Use ordinal comparison and ban the symbols ([Meziantou, 2025-05-05](https://www.meziantou.net/stringcomparison-invariantculture-is-not-always-invariant.htm)). Alpine/Docker images run invariant-globalization mode and `RegionInfo(LCID)` breaks ([Andrew Lock, 2019](https://andrewlock.net/dotnet-core-docker-and-cultures-solving-culture-issues-porting-a-net-core-app-from-windows-to-linux/)).
- Path handling is an under-covered bite: .NET accepts names Win32 rejects, `Path.GetInvalidFileNameChars()` does not list `CON/PRN/AUX/NUL/COMx/LPTx`, and deterministic builds rewrite source paths to `/_/` ([reserved filenames](https://www.meziantou.net/reserved-filenames-on-windows-con-prn-aux-nul.htm), [reproducible builds and paths](https://www.meziantou.net/reproducible-builds-and-snapshot-testing-handling-file-paths-in-dotnet.htm)).
- Trimming/AOT is a contract, not a feature: introducing a trim warning in a dependency update "is a breaking change when the library is used with `PublishTrimmed`", and `IsTrimmable` needs a `net6.0`+ TFM ([prepare libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming)).
- STJ source generation: reflection is auto-disabled under `PublishTrimmed`; `JsonStringEnumConverter<T>` is the AOT-safe enum converter; contexts combine via `TypeInfoResolverChain` ([source generation](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)).
- Era flag, C# 15 / .NET 11 preview 7: `union` and `closed` types do not round-trip through STJ by default and the author expects some support may slip to .NET 12 ([Andrew Lock, 2026-09-01](https://andrewlock.net/exploring-the-dotnet-11-preview-7-the-pain-of-serializing-unions-and-closed-class-hierarchies-with-system-text-json/)). Do not design a wire format around them.
- Publishing is moving to keyless: nuget.org Trusted Publishing issues 1-hour single-use API keys from a GitHub/GitLab OIDC token ([docs](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing)). Package assets (analyzers, build targets) execute on consumer machines; Meziantou argues for `IncludeAssets`/`PrivateAssets` ([post, 2026-08-24](https://www.meziantou.net/limit-what-nuget-packages-can-do-in-your-project.htm)).
- Time is injectable since .NET 8 via `TimeProvider`; `Microsoft.Bcl.TimeProvider` back-ports it to netstandard2.0, and it also covers BCL timing such as `Task.Delay`, which a hand-rolled `IClock` does not ([Andrew Lock, 2023-10-31](https://andrewlock.net/exploring-the-dotnet-8-preview-avoiding-flaky-tests-with-timeprovider-and-itimer)).
- Coverage gap: Marc Gravell has no personal-blog material that I could fetch; his positions reach this scout only through the StackExchange.Redis docs (thread theft, async timeouts). Nick Craver's corpus is ops/web-scale architecture and yielded nothing library-specific. Gerald Versluis was skipped per brief.

## Findings

### 1. Target frameworks and support horizon

**Microsoft's current stance (2026).** `DO start with a net8.0 target or later for new libraries`; `CONSIDER a netstandard2.0 target if you need broad compatibility or .NET Framework support`; `AVOID netstandard1.x`; and `DO NOT include a .NET Standard target if the library relies on a platform-specific app model` ([cross-platform targeting](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/cross-platform-targeting)). The page also splits two goals, "modern APIs and patterns" (AOT, trimming) versus "breadth targeting", and says they "don't always require the same approach". Internal tension on that page: one bullet says `DO NOT publish for netstandard2.0 if your project or dependencies multi-target`, while its own example packs `net8.0;netstandard2.0` and says NuGet "falls back to the `netstandard2.0` assembly". Treat the bullet as unreliable; a scout for the decision topic should read the page's git history or the dotnet/docs issue.

**The 2020 position.** For reusable NuGet libraries, "most code can skip netstandard2.1 and go straight to net5.0 if .NET Framework support isn't needed", and widely used libraries "will likely multi-target both netstandard2.0 and net5.0" ([future of .NET Standard](https://devblogs.microsoft.com/dotnet/the-future-of-net-standard/), 2020-09-15). The page is era-specific (net5.0 as the modern target); its principle (reach versus feature set) still stands.

**Skeet's practice.** In a 2026 fork he keeps `netstandard2.0` as the "bait" target, moves `net45` to `net48` and `netcoreapp2.1` to `net10`, and drops mobile targets because "I don't like the idea of trying to maintain code that I can't test" ([Forking an open source project](https://codeblog.jonskeet.uk/2026/07/11/forking-an-open-source-project/)). That is an argued rule: do not ship a TFM you cannot test.

**Unity is the concrete netstandard2.0/2.1 consumer.** Unity's default profile is .NET Standard 2.1; the .NET Framework profile is 4.8 plus Unity additions; managed plug-ins compiled for ".NET Core (any version)" are not supported under either profile ([Unity manual](https://docs.unity3d.com/6000.1/Documentation/Manual/dotnet-profile-support.html)). So `netstandard2.0` (or `2.1`) is the only route to Unity and .NET Framework; a `net8.0`-only package is invisible to both.

**Exemplar split (measured).** Commands: `git -C <dir> grep -nE "<TargetFrameworks?>" HEAD -- '*.csproj'` (and `*.props`).

| Repo | Library TFMs |
|---|---|
| `Tyrrrz__CliWrap@7dbc252fa773` | `netstandard2.0;netstandard2.1;net6.0;net7.0;net10.0` (`CliWrap/CliWrap.csproj:3`) |
| `adamralph__simple-exec@f80913246993` | `net8.0;net9.0;net10.0` (`Directory.Build.props:13`) |

**Support horizon (date-bound).** `.NET 8 (LTS) ends support 2026-11-10; .NET 9 (STS, 24 months) the same day; .NET 10 (LTS) runs through November 2028` ([end-of-support post](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/)). The post does not address libraries/NuGet. The practical implication for a new SDK: a `net8.0` floor is already out of support at its first release, but a library floor is about consumers, not the library author's own runtime.

### 2. Subprocess control (the centre of an ocx wrapper)

**The mechanics everyone agrees on.**
- Sequential `ReadToEnd()` on stdout then stderr can deadlock when the child fills the other pipe; async reads or event handlers avoid it, and the author finds event-handlers "more code than I'd like to write" ([Andrew Lock on .NET 11 Process APIs](https://andrewlock.net/exploring-the-dotnet-11-preview-5-improvments-to-process-apis/), 2026-07-07).
- `WaitForExitAsync` is not the async twin of `WaitForExit`: it returns on exit without waiting for redirected-output events, so `OutputDataReceived` lines can be missing; Meziantou's workaround is `await WaitForExitAsync(); WaitForExit();` ([post](https://www.meziantou.net/process-waitforexitasync-doesn-t-behave-like-process-waitforexit.htm), 2020-11-16, .NET 5 era; fix status unverified on .NET 8/10).
- `Kill` is asynchronous; with `Kill(entireProcessTree: true)`, `WaitForExit`/`HasExited` report completion after the root exits "even if all descendants have not yet exited"; processes the caller cannot inspect are "silently skipped"; it can throw `AggregateException` if not all descendants die ([Process.Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill)).
- `ProcessStartInfo.ArgumentList` escapes each element; `Arguments` and `ArgumentList` are mutually exclusive; both carry an untrusted-data security warning ([docs](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.processstartinfo.argumentlist)). Monikers listed: netcore-2.1, netstandard-2.1, net5+; netstandard-2.0 is absent from the fetched page.
- The .NET 11 official post lists the pitfalls it fixes: sequential-read deadlock, handle inheritance by sibling/grandchild processes keeping pipe write ends open (so EOF never arrives), `Dispose` does not kill, `BeginOutputReadLine` pinned two thread-pool threads per process on Windows (issue #81896), and orphaned children ([Process API improvements in .NET 11](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/), 2026-05-13).

**CliWrap's design position** ([README](https://github.com/Tyrrrz/CliWrap)): non-zero exit throws by default (`CommandResultValidation.None` to disable) and the exception carries stderr; forceful cancellation kills and the task completes only after the process has exited; a second token requests graceful interrupt (Ctrl+C equivalent) that the child may ignore; `ExecuteBufferedAsync` assumes `Encoding.Default` unless told otherwise; `WithEnvironmentVariables` layers over the inherited set and `null` removes a variable; stdout and stderr may use different encodings; "buffering may be impractical for binary or large output". Measured in the exemplar: `process.TryKill()` registered on the cancellation token (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap/Command.Execution.cs:181`).

**Correction on attribution.** The "Stop using the Process class for CLI interactions in .NET" video that CliWrap's README lists is by Nick Chapsas, not Tyrrrz, and the README gives only its title. I found no Tyrrrz blog post of the "Process in .NET is broken" kind; the "dozen different deadlocking situations" quote exists only in a search snippet of an event summary and is not used here.

**.NET 11 additions (era flag, RC1; none exist on .NET 10 or 8).**
- `Process.Run[Async]`, `RunAndCaptureText[Async]`, `ReadAllText/Lines/Bytes[Async]`, `ProcessExitStatus { ExitCode, Canceled, Signal }`, timeouts that kill the child ([Andrew Lock](https://andrewlock.net/exploring-the-dotnet-11-preview-5-improvments-to-process-apis/), [official post](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)).
- `KillOnParentExit`: Windows job object (Preview 4), Linux/Android `PR_SET_PDEATHSIG` (Preview 5), other Unix "under consideration"; `StartDetached`; `InheritedHandles` (default `null` keeps old behaviour "due to backwards compatibility reasons") ([official post](https://devblogs.microsoft.com/dotnet/process-api-improvements-in-dotnet-11/)).
- Secondary source (German-language blog, tested on RC1 on macOS, not corroborated by Microsoft text I fetched): `Process.Run` timeout kills only the direct child, a grandchild survived; `RunAsync` does not throw on cancel (returns `Canceled = true`); `Run` throws `InvalidOperationException` on any `RedirectStandard*` flag ([startdebugging](https://startdebugging.net/de/2026/09/process-run-vs-process-start-in-dotnet-11/)). Re-verify against the shipped GA before relying on it. The official post's own wording is that `Run`/`RunAndCaptureText` "will also try to kill the process"; it describes no tree-kill API.
- Whether any of this is back-ported is not stated; the post's call to action points only at .NET 11 Preview 4.

**Orphan prevention before .NET 11.** Meziantou's Windows job-object recipe: `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, job handle non-inheritable, no breakaway; the post is Windows-only and offers `Meziantou.Framework.Win32.Jobs` ([post, 2022-11-21](https://www.meziantou.net/killing-all-child-processes-when-the-parent-exits-job-object.htm)). The Linux/macOS equivalent is not covered by any fetched practitioner source.

**Analyzer detail.** .NET 10 adds CA2024 which flags `StreamReader.EndOfStream` in async methods because it can block on I/O ([Toub, Performance Improvements in .NET 10](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-10/); only characters 0-100000 and 300000-400000 of the page were read).

### 3. Async, cancellation, disposal

**ConfigureAwait.** Toub (2019-12-11, .NET Core 3.x era): app code do not; library code do; partial application "guarantees it won't be queued back to the original context" only for incomplete awaits; `ConfigureAwait(true)` "does nothing meaningful"; "Nothing's changed" on .NET Core; the `Task.Run`/`SetSynchronizationContext(null)` workarounds are "very far from ideal"; CA2007 "basically shouldn't be turned on" for apps ([FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)). The FAQ does not discuss `ConfigureAwaitOptions` (added after it was written); a source for that is still needed. Cleary 2013: "If you can use ConfigureAwait at some point within a method, then I recommend you use it for every await in that method after that point" ([MSDN, 2013-03](https://learn.microsoft.com/en-us/archive/msdn-magazine/2013/march/async-await-best-practices-in-asynchronous-programming)), which is subtly different from Toub's reading. Cleary 2012: the root fix is to avoid blocking at all ([post](https://blog.stephencleary.com/2012/07/dont-block-on-async-code.html)).

**Continuations and thread theft.** Fowler: "Always use `TaskCreationOptions.RunContinuationsAsynchronously`" with `TaskCompletionSource` ([AsyncGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/master/AsyncGuidance.md)). StackExchange.Redis documents the failure mode: continuations run on the reader loop, the symptom is timeouts with `rs: CompletePendingMessage`; mitigation is the flag plus a `preventthreadtheft` option for misbehaving `SynchronizationContext`s such as `LegacyAspNetSynchronizationContext`; the docs add that .NET Core/5+ install no server `SynchronizationContext` ([ThreadTheft](https://seredis.dev/ThreadTheft)).

**Cancellation.**
- Fowler: pass tokens to everything that takes one; dispose timeout `CancellationTokenSource`s (undisposed ones "put pressure on the timer queue"); prefer `Task.WaitAsync` on .NET 6+ to cancel uncancellable operations ([AsyncGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/master/AsyncGuidance.md)).
- StackExchange.Redis recommends the framework `WaitAsync` family over client-specific timeouts for async calls and warns the command "may still be buffered and issued to the server" after cancel ([AsyncTimeouts](https://seredis.dev/AsyncTimeouts)). Relevant to an ocx wrapper: a cancelled `install` may already have mutated the store.
- Toub: an `OperationCanceledException` produces a cancelled (not faulted) task; pre-`await` exceptions land on the task too ([How async/await really works](https://devblogs.microsoft.com/dotnet/how-async-await-really-works/), 2023-03-16).

**Async-void and delegates.** Cleary 2013: async void only for event handlers; async lambdas should convert to `Func<Task>`, not `Action`. Fowler: offer both sync and `Func<Task>` callback overloads ([AsyncGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/master/AsyncGuidance.md)).

**Disposal.** Cleary (2013-03-07, pre-`IAsyncDisposable`): `Dispose` cannot be async; options are "cancellation as dispose" (a benign race) versus a `Complete`/`Completion` pair ([Async OOP 6](https://blog.stephencleary.com/2013/03/async-oop-6-disposal.html)). Fowler: buffered writers' `Dispose` can block synchronously, so `FlushAsync` or `DisposeAsync` first. The .NET 11 post confirms `Process.Dispose` does not kill the child.

**Construction and caching.** Fowler: constructors are synchronous, use a static async factory; cache the `Task`, not the result, and wrap in an `AsyncLazy` so the factory runs once ([AsyncGuidance](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios/blob/master/AsyncGuidance.md)). Cleary: `SemaphoreSlim.WaitAsync` for async mutual exclusion because `await` cannot sit inside `lock`.

**State.** Fowler on `AsyncLocal<T>`: avoid; never store disposables or non-thread-safe objects. Toub: `ExecutionContext` flows ambient data, and builder `Start` restores the prior context after the first synchronous `MoveNext`.

### 4. Public API design and binary compatibility

**Three break kinds** ([breaking changes](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/breaking-changes), guidance last updated 2023): source (new overload ambiguity, renamed parameter breaks named-arg callers), behaviour ("even a bug fix can qualify"), binary (`MissingMethodException`; changing assembly name or strong-name key changes identity). Rules: DO minimise breaks in low-level libraries; CONSIDER abstract base classes over interfaces ("adding anything to an interface will cause existing types that implement it to fail"); CONSIDER `[Obsolete]` with migration text and keeping obsolete members indefinitely in low/middle-level libraries; CONSIDER leaving new behaviour opt-in behind a setting; CONSIDER shipping a major rewrite as a new package.

**Counter-position.** Noda Time: "Almost all types are sealed, and there actually aren't very many interfaces", follows Bloch's "design for inheritance or prohibit it", limits hooks "to reduce the opportunities for coupling", uses explicit culture/time zone/clock with "we don't like defaults", and injects clocks for tests ([NodaTime design](https://nodatime.org/userguide/design)). The two positions agree on the goal (evolvability) and disagree on the lever.

**Tracking the surface.** `EnablePackageValidation` checks the baseline version, compatible runtime, and compatible framework across a multi-targeted package ([overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview)). Meziantou compares three review styles: `PublicApiAnalyzers` text (not C# syntax, multi-target files hard to review), no tooling (guesswork), and a generated compilable C# snapshot with `#if` blocks per TFM and a CI `--verify-no-change` gate ([post, 2026](https://www.meziantou.net/generate-and-review-the-public-api-of-a-dotnet-library.htm)).

**Versions.** Four version numbers with different consumers; DO NOT have a fixed `AssemblyVersion`; CONSIDER major-only `AssemblyVersion` in sync with NuGet major; AVOID setting `InformationalVersion` yourself, let SourceLink do it ([versioning](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning), page updated 2025-12-04). Dependencies: no minimum-less references, AVOID exact or upper-bound ranges, review for unneeded dependencies ([dependencies](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/dependencies)).

**Records in public APIs.** Skeet: record-generated equality uses `EqualityComparer<T>.Default`, so collection members compare by reference; no per-property comparer; prefers explicit ordinal comparison helpers in public APIs ([Records and Collections](https://codeblog.jonskeet.uk/2025/03/27/records-and-collections/), 2025-03-27). Directly relevant to "typed handle" return types that carry lists.

**Deprecation/rename.** NuGet's package deprecation notice can point users to a successor without republishing (comment by Cleary on Skeet's post, [source](https://codeblog.jonskeet.uk/2026/07/11/forking-an-open-source-project/)); Skeet's own rename plan accepts that users "won't get prompted by Visual Studio, Renovate etc."

### 5. NuGet packaging, signing, provenance

- Trusted Publishing: OIDC token exchanged for a temporary key; 1-hour validity; one token yields one key; GitHub Actions and GitLab; policies on private GitHub repos start as 7-day temporary to bind immutable repo/owner IDs and prevent resurrection attacks ([nuget.org docs](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing), page updated 2026-09-01). Andrew Lock wrote a walkthrough (found in search results, not fetched).
- Source Link: CONSIDER Source Link, symbols, and deterministic builds; verify `Repository` metadata and `.pdb` presence with Package Explorer ([SourceLink guidance](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink), page dated 2019, updated 2025-07-31).
- Package assets execute: analyzers and MSBuild props/targets run at restore/build on dev and CI machines; limit with `IncludeAssets`/`ExcludeAssets`, `PrivateAssets="all"`, lock files and source mapping ([Meziantou, 2026-08-24](https://www.meziantou.net/limit-what-nuget-packages-can-do-in-your-project.htm)).
- Lead not verified: search snippets say Microsoft is rotating its NuGet author-signing certificate from 2026-09-23 and that a `trustedSigners` pin to the old one can fail with NU3034; the two sources named different fingerprints. The Microsoft post itself was not fetched. Relevant only if a consumer pins signers.
- No practitioner source fetched covers signing a first-party package with your own certificate versus relying on nuget.org repository signing. Gap.

### 6. JSON, AOT, trimming

- STJ source-gen basics for a library: derive a `partial` `JsonSerializerContext`, use `[JsonSerializable]`, call overloads taking `JsonTypeInfo<T>` or the context; `object`-typed members need the runtime types declared; fast-path (`Serialization` mode) is not supported for async serialization; reflection is auto-disabled under `PublishTrimmed`; use `JsonStringEnumConverter<T>` (the non-generic one is unsupported on Native AOT); chain contexts with `TypeInfoResolverChain`, order significant ([docs](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation), page updated 2026-03-30).
- Library trimming contract: set `IsTrimmable` or `IsAotCompatible`; test with a trimmed app using `TrimmerRootAssembly`; target at least `net6.0` (netstandard2.0/net472 targets get no trim analysis, so multi-target a modern TFM); "avoid reflection when possible"; do not annotate virtual/interface methods; reflection in static constructors poisons every member; `UnconditionalSuppressMessage` is valid only when the reflected targets are visible to the analyzer ([prepare libraries for trimming](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/prepare-libraries-for-trimming), updated 2026-01-08).
- Era flag, .NET 11 / C# 15 (preview 7, may slip to .NET 12): `closed` classes and `union` types; `InferClosedTypePolymorphism` failed for internal derived types under a public base and for two-level hierarchies; union deserialization is ambiguous when several cases map to the same JSON token type; "I really don't like the fact that unions don't round-trip by default" ([Andrew Lock](https://andrewlock.net/exploring-the-dotnet-11-preview-7-the-pain-of-serializing-unions-and-closed-class-hierarchies-with-system-text-json/)). On .NET 10 the stable route remains `[JsonDerivedType]` plus a discriminator.
- Not found in any fetched practitioner source: on-disk and wire-format versioning guidance (tolerating unknown properties, additive-only evolution, `JsonExtensionData`, `UnmappedMemberHandling`). It is an obvious gap and goes into the candidate list as a question.

### 7. Boring things that bite: paths, culture, time, encodings

- **Windows reserved names.** `CON, PRN, AUX, NUL, COM0-COM9, LPT0-LPT9`, case-insensitive, extension does not help (`NUL.txt`); `Path.GetInvalidFileNameChars()` does not include them; `\\?\` disables most legacy path parsing but "does not bypass security checks"; files with such names can exist (created via WSL) ([Meziantou, 2026](https://www.meziantou.net/reserved-filenames-on-windows-con-prn-aux-nul.htm)). Relevant to any SDK that derives file names from package identifiers.
- **Deterministic builds rewrite paths.** The compiler emits `/_/src/file.cs`; libraries that locate files from `[CallerFilePath]` (snapshot testing) must map the placeholder back through `SourceRoot` items at runtime ([Meziantou, 2026](https://www.meziantou.net/reproducible-builds-and-snapshot-testing-handling-file-paths-in-dotnet.htm)). The post does not discuss `DeterministicSourcePaths`/`PathMap` by name.
- **Culture.** `StringComparison.InvariantCulture` is "incorrect in most situations and should be replaced with Ordinal"; formatting/parsing with `CultureInfo.InvariantCulture` is fine; ban the symbols with `BannedApiAnalyzers`; pin ICU with app-local ICU; invariant-globalization mode is "not equivalent to using Ordinal" ([Meziantou, 2025-05-05](https://www.meziantou.net/stringcomparison-invariantculture-is-not-always-invariant.htm)). Invariant mode config: `InvariantGlobalization` / `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT`, `PredefinedCulturesOnly` ([globalization config](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/globalization)). Alpine images lack ICU; unit tests passed in SDK images that have ICU and the app crashed in the runtime image; fix with `RegionInfo(culture.Name)` or install `icu-libs` ([Andrew Lock, 2019-12-10](https://andrewlock.net/dotnet-core-docker-and-cultures-solving-culture-issues-porting-a-net-core-app-from-windows-to-linux/), .NET Core 2.x era, mechanism still current).
- **Time.** `TimeProvider` (.NET 8) over hand-rolled `IClock` because it also virtualises BCL timing; prefer `ITimer` from the provider over `Task.Delay(…, timeProvider)` because the latter has a race with the test advancing time; `Microsoft.Bcl.TimeProvider` back-ports to netstandard2.0 ([Andrew Lock, 2023-10-31](https://andrewlock.net/exploring-the-dotnet-8-preview-avoiding-flaky-tests-with-timeprovider-and-itimer)). Noda Time's counter: never default to "now" or the system zone.
- **Encodings.** CliWrap defaults to `Encoding.Default` for buffered text; .NET 11 `ReadAllText` honours `ProcessStartInfo.StandardOutputEncoding`; `ReadAllBytes` exists "so you can handle the encoding yourself". No fetched practitioner source argues for a specific policy (UTF-8 without BOM, `NO_COLOR`, `LC_ALL`) when wrapping a Rust CLI. Gap.
- **Ordering and determinism.** Skeet argues for explicit ordinal comparison helpers and reference-versus-value comparers in public APIs. Nothing fetched covers dictionary iteration order, merged stdout/stderr interleave, or sorted output as a contract. Thin.

### 8. Testing

- Meziantou (2026-10, .NET 10 SDK 10.0.400, Apple M5 Pro): startup for one test 146-204 ms on the platform executable; per-test marginal cost MSTest 15 µs, TUnit 42 µs, xUnit v3 56 µs, NUnit 85 µs; "the runner matters more than the framework" and switching `dotnet test` to the Microsoft.Testing.Platform executable is "a bigger win"; Native AOT test publish: MSTest about 84 minutes versus 43 s xUnit and 23 s TUnit, attributed to `ILLink.RoslynAnalyzer`, fixed in .NET 11 but not backported; "for most projects, none of this decides anything" ([benchmark](https://www.meziantou.net/benchmarking-dotnet-test-frameworks-xunit-v3-nunit-mstest-and-tunit.htm)).
- Exemplar: CliWrap tests spawn a purpose-built dummy executable (`Tyrrrz__CliWrap@7dbc252fa773:CliWrap.Tests.Dummy/CliWrap.Tests.Dummy.csproj`, and `CliWrap.Signaler` targeting `net35` at `CliWrap.Signaler/CliWrap.Signaler.csproj:4`, a tiny helper for sending interrupt signals on Windows). I did not read these projects' contents; flagged as lead.
- Test hygiene from the practitioners: unit tests that never run in the runtime image's globalization mode hide culture bugs (Lock, 2019); `FakeTimeProvider.Advance` for time.
