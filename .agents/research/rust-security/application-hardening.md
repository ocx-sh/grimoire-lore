## Summary

- The `zip` crate's own `extract()` sanitizes names via `enclosed_name()`, but versions 1.3.0–2.2.x still let an early symlink entry redirect later entries outside the target dir (CVE-2025-29787) — pin `zip >= 2.3.0` and never trust "sanitized" as a substitute for testing.
- The `tar` crate has shipped two distinct symlink-driven escapes in the last five years: directory creation outside root (RUSTSEC-2021-0080, fixed 0.4.36) and `fs::metadata`-follows-symlinks chmod-outside-root (RUSTSEC-2026-0067, fixed 0.4.45) — both were default-safe-looking APIs (`Archive::unpack`, `Entry::unpack_in`).
- Neither `zip` nor `tar` bounds decompressed size, entry count, or compression ratio by default — a tool that extracts untrusted archives must enforce its own entry-count cap, per-entry size cap, and total-size cap while streaming, not after the fact.
- `cap-std` (Bytecode Alliance) gives capability-scoped filesystem access (`Dir::open_file` relative to a directory handle, not an ambient path) and on Linux 5.6+ uses `openat2` with `RESOLVE_BENEATH`-equivalent semantics — this is the correct primitive for "extract into this directory and nowhere else," stronger than post-hoc `canonicalize()` checks which are inherently TOCTOU-able.
- `std::fs::canonicalize` + string-prefix check is a race: the filesystem can change between the check and the actual open. Prefer `*at` syscalls (openat, cap-std, rustix) that resolve one path component below a fixed directory fd.
- Always create download/extraction temp files with the `tempfile` crate (random names, private permissions, O_EXCL-style atomic creation), never `format!("{}.tmp", name)` in a shared directory — predictable names are a classic symlink-race / TOCTOU vector.
- `std::process::Command` never invokes a shell — `arg()`/`args()` pass literal strings, so classic `; rm -rf` shell injection does not apply — but on Windows, `cmd.exe` and `.bat`/`.cmd` targets use non-standard argument decoding and remain injectable; this was CVE-2024-24576 ("BatBadBut", CVSS 10.0) and the first fix (Rust 1.77.2) was itself incomplete until Rust 1.81.0 (CVE-2024-43402, trailing-whitespace/period bypass).
- Argument injection (not shell injection) is still live: any argument beginning with `-` passed to a CLI you spawn (git, tar, curl-like tools) can be reinterpreted as a flag — always terminate your argument list construction with `--` before untrusted positional args, or validate the leading character.
- `secrecy` + `zeroize` stop three real things — Debug/Display leaks, use-after-drop of stale sensitive bytes, and accidental copy-out — and stop nothing else: no `mlock`, no swap/hibernation protection, no defense against a process-memory dump or a debugger attached to the running process. Say this explicitly when justifying (or skipping) their use.
- `rustls` is now the community-recommended default TLS backend; `native-tls`/OpenSSL bindings are the fallback for platform cert-store integration, and `rustup` itself started deprecating `native-tls` in 2025 — a new tool should default to `rustls-tls` in its HTTP client's Cargo features.
- Never disable certificate verification (`danger_accept_invalid_certs`, custom `ServerCertVerifier` that always accepts) even "temporarily for testing" — this is the single highest-severity TLS misconfiguration and is trivially grep-able.
- `reqwest`'s default redirect policy already caps at 10 hops; a downloader still needs an explicit request timeout (`reqwest` sets none by default) and an explicit response-size cap enforced while streaming the body, not after `bytes()` has buffered an unbounded blob into memory.
- OCI registry token auth (`WWW-Authenticate: Bearer realm=... service=... scope=...`) allows the token server to silently narrow requested scope without erroring — a client must check the token it actually got covers what it asked for, not assume the request succeeded because the HTTP call didn't 401.
- Digest verification per the OCI spec must (a) check content length before hashing, (b) hash while streaming rather than buffering the whole blob, and (c) treat "verified" as meaning the exact bytes that were hashed are the exact bytes later executed — a separate download-then-verify-then-open-by-path step reintroduces TOCTOU if the path can be swapped between verify and open.
- `overflow-checks` is `true` in dev/test but `false` in release by default — an OCI blob-size or offset computation that overflows silently wraps in the shipped binary unless `[profile.release] overflow-checks = true` is set explicitly; this is a one-line Cargo.toml fix with real precedent (a `ring` overflow panic was itself a remotely triggerable DoS once checks were on).
- `#[serde(deny_unknown_fields)]` is a UX/typo-catching feature, not a security boundary — it does not bound recursion depth or payload size; deeply nested untrusted JSON/YAML/TOML can still exhaust the stack via recursive descent before any field-name check runs.
- Case-insensitive/normalization-insensitive filesystems (Windows, default macOS) let an archive contain two entries whose names differ only in case; the second write silently collides with or symlink-hijacks the first — extraction logic must normalize and reject collisions per-target-filesystem-case, not assume the archive's declared names are all distinct.
- Long path handling on Windows: `MAX_PATH` (260 chars) truncation/rejection is a real extraction failure mode for deeply nested archives; use extended-length paths (`\\?\` prefix) or the `dunce`/`cap-std` handling rather than silently failing mid-extraction with partial state on disk.
- Prefer `tokio::process::Command::kill_on_drop(true)` plus `tokio::time::timeout` around `child.wait()` for any subprocess you spawn and don't fully trust to terminate — Tokio's default is that a dropped `Child` handle leaves the process running.
- `env_clear()` on Unix does not mean "child gets no PATH" — if you don't explicitly set `PATH` after clearing, `execvp` falls back to a default search path (`/bin:/usr/bin`), which can silently resolve to a different binary than intended.

## Findings

### 1. Untrusted archive extraction

**Zip: symlink-based path escape past "sanitized" names.**
The `zip` crate documents that `ZipArchive::extract()` sanitizes paths via `ZipFile::enclosed_name()`, and that "symbolic links are only created and followed if the target is within the destination directory (checked conservatively using `std::fs::canonicalize`)" ([docs.rs/zip](https://docs.rs/zip/latest/zip/read/struct.ZipArchive.html)). Despite this documented intent, versions 1.3.0 through 2.2.x had a real bypass: an attacker places a symlink entry early in the archive pointing outward (e.g. into a parent directory), then extracts later file entries *through* that symlink — the per-entry sanitization checked each name in isolation but not the fully resolved path after the symlink had already been materialized on disk. Fixed in 2.3.0, tracked as [CVE-2025-29787 / GHSA-94vh-gphv-8pm8](https://github.com/advisories/GHSA-94vh-gphv-8pm8).

```rust
// WRONG (pre-2.3.0 zip, or any hand-rolled loop that trusts each name in isolation):
for i in 0..archive.len() {
    let mut file = archive.by_index(i)?;
    let outpath = dest.join(file.enclosed_name().unwrap()); // per-entry check only
    // ... extract, following symlinks created by a PRIOR entry in this same archive
}

// RIGHT: pin zip >= 2.3.0 and additionally defer symlink creation to last,
// or extract into a directory obtained via cap-std so escapes are OS-enforced:
let dir = cap_std::fs::Dir::open_ambient_dir(dest, cap_std::ambient_authority())?;
// every subsequent open/create is resolved relative to `dir`'s fd; `..` and
// absolute paths and symlink escapes are rejected by the OS resolver, not by
// a canonicalize()-then-compare that can race.
```

**Tar: two separate symlink-driven CVEs in the safe-looking default API.**
`tar::Archive::unpack()` (and the lower-level `Entry::unpack_in`) are the crate's documented "just extract it" entry points, and both have shipped real escapes:
- RUSTSEC-2021-0080 (fixed 0.4.36): a symlink entry followed by path components through it caused directory creation outside the destination — "the function errors when it's trying to create a file, but the folders are already created at this point" ([rustsec.org](https://rustsec.org/advisories/RUSTSEC-2021-0080.html)).
- RUSTSEC-2026-0067 (fixed 0.4.45): `unpack_dir` uses `fs::metadata()` — which follows symlinks — to decide whether an existing path is a directory it can `chmod`. A symlink entry followed by a same-named directory entry makes the crate `chmod` through the symlink to an arbitrary target outside the extraction root ([rustsec.org](https://rustsec.org/advisories/RUSTSEC-2026-0067.html)).

Related async ecosystem: `astral-tokio-tar` (CVE-2025-59825) had its `allow_external_symlinks` guard (default `true`) bypassable via a *pair* of symlinks that individually resolved inside the destination but combined to point outside it ([GHSA-3wgq-wrwc-vqmv](https://github.com/advisories/GHSA-3wgq-wrwc-vqmv)), and the "TARmageddon" async-tar issue is a further extraction-escape variant in the async ecosystem ([linuxsecurity.com writeup](https://linuxsecurity.com/news/security-vulnerabilities/linux-tar-async-tar-vulnerability-tarmageddon)). The pattern across all of these: single-entry validation is not sufficient when earlier entries can change how later entries resolve — the escape is *compositional*.

**Practical rule derived from the above**: pin exact minimum versions (`tar >= 0.4.45`, `zip >= 2.3.0`), and treat "this crate sanitizes paths" as necessary but not sufficient — extract into a `cap-std`-scoped directory (or an equivalent `openat`-relative walk) so that even a future undiscovered crate bug cannot escape the target, and reject (don't silently skip) any entry that is itself a symlink, hardlink, device file, or has the setuid/setgid bit set unless your tool has an explicit, documented reason to preserve them. `tar`'s `Entry::header().entry_type()` exposes `Symlink`, `Link` (hardlink), `Char`/`Block` (device), and permission bits are available via `header().mode()` — check `mode & 0o6000` for setuid/setgid before applying.

**Decompression bombs.** Neither `zip` nor `flate2`/`tar` impose a default limit on decompressed size, entry count, or compression ratio; the classic `42.zip` example achieves 4.5 petabytes from 42KB by nesting archives past DEFLATE's ~1032:1 single-layer ratio ([Wikipedia, Zip bomb](https://en.wikipedia.org/wiki/Zip_bomb)). A tool that extracts untrusted archives must enforce, while streaming (not after buffering):
- a maximum entry count (reject archives with absurd file counts before iterating each one),
- a maximum per-entry decompressed size, read incrementally via `io::copy` with a bounded/limited reader (e.g. wrap the entry reader in a byte-counting `Read` adapter that errors past a threshold) rather than `read_to_end`,
- a maximum cumulative decompressed size across the whole archive,
- and optionally a compression-ratio ceiling (declared uncompressed size vs. compressed size in the archive header) as an early reject, understanding that the *declared* size in zip/tar headers is attacker-controlled and must be treated as a hint, not ground truth — the real limit must be enforced against bytes actually written, not the header's claim.

**Windows/cross-platform extraction hazards.**
- *Long paths*: Windows' legacy `MAX_PATH` (260 chars) truncates or rejects long paths unless the path uses the `\\?\` extended-length prefix or the process has opted into long-path support; a deeply nested archive can fail extraction mid-way, leaving partial state. Handle via extended-length path prefixing or a crate like `dunce`/`cap-std`'s Windows backend rather than surfacing a raw OS error after partial writes.
- *Case-insensitive / normalization-insensitive collisions*: Windows NTFS and default macOS APFS are case-insensitive; an archive with entries `FOO/bar` and `foo/bar` (or Unicode-normalization variants of the same name) collide on extraction even though the archive treats them as distinct. Research into `tar`/`cp`/`rsync` cross-filesystem collisions found these silently cause data loss or, worse, let a later entry write through a symlink left by an earlier "directory" entry that got collapsed into a colliding name ([USENIX FAST'23, "Unsafe at Any Copy"](https://www.usenix.org/system/files/fast23-basu.pdf); background survey found in search covering `node-tar`'s equivalent CVE for the same class of bug). Extraction logic targeting Windows/macOS must track already-written names case-insensitively (and NFC-normalized) and reject or explicitly report collisions rather than silently overwriting.

### 2. Filesystem safety: TOCTOU, atomic writes, temp files, permissions

**Canonicalize-then-check is a race, not a guarantee.** `std::fs::canonicalize()` resolves symlinks and `..` at the moment it's called; nothing stops the filesystem changing between that call and the subsequent open/write. The correct primitive is resolving the final path component in one directory-relative operation. `cap-std` is the maintained, Bytecode-Alliance-backed answer: it "reimplements Rust's standard library APis... using capabilities" — access requires an existing `Dir` handle, and traversal attempts using `..`, absolute paths, or symlinks pointing outside the directory return a permission error rather than escaping, because on Linux 5.6+ it uses a single `openat2` syscall with `RESOLVE_BENEATH`-style semantics (treating absolute paths as errors, unlike `RESOLVE_IN_ROOT`), and falls back to sequential per-component opens plus `RESOLVE_NO_SYMLINKS`/`RESOLVE_NO_XDEV`-equivalent emulation on platforms without `openat2` ([cap-std README](https://github.com/bytecodealliance/cap-std/blob/main/README.md); [rustix::fs docs for the underlying `openat2` bindings](https://docs.rs/rustix/latest/rustix/fs/)).

```rust
// WRONG: check-then-open race, and does not stop a symlink swapped in
// between the canonicalize() call and the fs::write() call.
let resolved = target.canonicalize()?;
if !resolved.starts_with(&extract_root) { bail!("escape"); }
std::fs::write(&resolved, data)?; // TOCTOU window here

// RIGHT: every operation is relative to a capability handle; the OS
// resolver enforces containment on each syscall, no separate check step.
let root = cap_std::fs::Dir::open_ambient_dir(&extract_root, cap_std::ambient_authority())?;
root.write(relative_entry_name, data)?; // cannot escape `root` regardless of `..`/symlinks
```

**Atomic write-then-rename, with fsync.** The standard durable-write pattern for lockfiles/caches is: write to a temp file in the *same directory* as the final target (so the rename is on the same filesystem and thus atomic), `fsync` the temp file's contents before renaming (otherwise a crash after rename but before the underlying data hits disk can leave a zero-length or truncated "final" file on some filesystems/journaling modes), rename over the target (POSIX `rename()` is atomic; on Windows use `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING` — `std::fs::rename` maps to this), and optionally fsync the containing directory afterward if you need the rename itself to survive a crash (directory-entry durability is a separate guarantee from file-content durability on Linux).

**Temp files: use `tempfile`, never predictable names.** Predictable temp names in a shared directory (e.g. `format!("{}/download.tmp", cache_dir)`) are a symlink-race target: an attacker who can predict or observe the name creates a symlink at that path pointing at a sensitive file before your process opens it, or races to read partial contents. The `tempfile` crate creates files with atomic collision-free creation, 6 random characters of entropy by default (reseeded from system randomness after repeated collisions when the `getrandom` feature is enabled), and files that are "private by default on all operating systems," while directories inherit the process umask and are world-readable unless umask restricts them ([docs.rs/tempfile](https://docs.rs/tempfile/latest/tempfile/)). Use `NamedTempFile` + `.persist(final_path)` for the download-then-atomic-place pattern; `.persist()` performs the same-directory rename described above.

**Permissions: set explicitly, don't rely on umask alone for secrets.** Credential files, private keys, and lockfiles containing tokens should be created with `0600` (owner read/write only) and directories holding them with `0700`, set explicitly via `std::os::unix::fs::PermissionsExt::set_mode` or at creation via `OpenOptions::mode(0o600)` (through `std::os::unix::fs::OpenOptionsExt`) rather than trusting the ambient umask, because umask is process/environment state the tool doesn't control and can legitimately be `0022` or looser on a misconfigured host. On Windows there is no umask/mode-bit equivalent; the correct mechanism is ACLs (`std::os::windows` doesn't expose these directly — use the `windows-acl` or platform APIs, or rely on the fact that per-user temp/profile directories are already ACL'd to the owning user, which is the model `tempfile` leans on).

**Symlink-following policy.** Decide and document, per operation: does opening a config/lockfile path follow a symlink placed by another user in a shared directory? Default to *not* following symlinks for anything security-sensitive (credential files, lockfiles you're about to overwrite) — open with `O_NOFOLLOW` semantics (`rustix::fs::OFlags::NOFOLLOW`, or check `symlink_metadata()` before opening) rather than the plain `std::fs::File::open`, which follows symlinks unconditionally.

### 3. Subprocess execution

**No shell, by default — this closes classic injection but not all of it.** `std::process::Command::new(program).arg(a).arg(b)` never invokes `/bin/sh` or `cmd.exe` — arguments are passed literally, and "shell syntax like quotes, escaped characters, word splitting, glob patterns, variable substitution... have no effect" per the standard library docs ([doc.rust-lang.org/std/process/struct.Command.html](https://doc.rust-lang.org/std/process/struct.Command.html)). This means `Command::new("ls").arg(user_input).spawn()` is safe from `; rm -rf /`-style shell injection on both Unix and (for well-behaved executables) Windows.

**Windows exception: BatBadBut (CVE-2024-24576) and its incomplete fix (CVE-2024-43402).** `cmd.exe` and `.bat`/`.cmd` files decode their command line non-standardly, and the Rust standard library's original escaping for these targets could be defeated by malicious arguments — CVSS 10.0, discovered by RyotaK/Flatt Security, fixed for the common case in Rust 1.77.2. The fix was itself incomplete: Windows strips trailing whitespace (0x20) and trailing periods (0x2E) from file names before matching extensions, so a program named e.g. `run.bat` with trailing dots/spaces could still bypass the `.bat`/`.cmd` detection and reach the vulnerable code path; this was assigned CVE-2024-43402 and fully fixed in Rust 1.81.0 ([blog.rust-lang.org CVE-2024-43402 advisory](https://blog.rust-lang.org/2024/09/04/cve-2024-43402/)). **Practical takeaway for this codebase: pin the Rust toolchain to >= 1.81.0** (check `rust-toolchain.toml` / CI `rustc --version`), and never invoke `.bat`/`.cmd` files directly with untrusted arguments even on a patched toolchain if avoidable — prefer invoking the underlying `.exe` if the tool ships one.

**Argument injection remains live regardless of shell/no-shell.** A subprocess you `exec` (git, tar, an extracted tool binary) parses its own argv, and an argument beginning with `-` can be reinterpreted as a flag rather than a positional value — this is the mechanism behind real CVEs in other ecosystems (bundler's CVE-2021-43809 via a `git` URL starting with `-u./payload`, treated as `--upload-pack`; npm's CVE-2022-25900 in `git-clone`). Mitigation: insert a literal `--` argument before the first untrusted positional argument wherever the invoked program supports the GNU convention (most do), or validate that user-controlled values passed as positional arguments do not begin with `-` before passing them.

```rust
// WRONG: an artifact name or ref beginning with "-" can be reinterpreted as a flag.
Command::new("tar").arg("-xf").arg(archive_path).arg(user_supplied_member_name).status()?;

// RIGHT: terminate options explicitly.
Command::new("tar").arg("-xf").arg(archive_path).arg("--").arg(user_supplied_member_name).status()?;
```

**PATH resolution and PATH poisoning.** `Command::new("tool")` (a bare name, no path separator) resolves via `PATH` search — if your process's `PATH` includes a directory an attacker can write to (a common CI/build-tool misconfiguration, e.g. a world-writable `./bin` prepended to `PATH`), a malicious `tool` binary can be resolved and executed instead of the intended one. For any subprocess whose identity matters for security (a downloaded/verified binary you are about to execute), invoke it by absolute, canonicalized path — never by bare name — so `PATH` search is not in the trust chain at all.

**Environment sanitization.** `env_clear()` removes all inherited environment variables from the child, but on Unix, if `PATH` is not then explicitly re-set, `execvp` falls back to a compiled-in default search path (typically `/bin:/usr/bin`) rather than failing closed — this can silently resolve a bare program name to an unexpected binary on a host with unusual `/bin` contents ([doc.rust-lang.org Command docs](https://doc.rust-lang.org/std/process/struct.Command.html)). If you `env_clear()`, always also explicitly `.env("PATH", known_good_value)`. For secrets in particular: never pass them via `arg()` (visible in `/proc/<pid>/cmdline` and `ps` output to any user on the host) or via inherited environment variables that the child might log or that appear in crash dumps — prefer stdin, a file descriptor, or a short-lived file with `0600` permissions passed by path.

**Working-directory races and `current_dir`.** If the program path passed to `Command::new` is relative, whether it resolves relative to the parent's or the child's working directory is platform-specific and considered unstable behavior by the standard library docs; always pass an absolute (ideally `canonicalize()`d) path to `Command::new` when also setting `current_dir()`.

**Timeouts and kill-on-drop.** `std::process::Command`/`Child` has no built-in timeout. Under `tokio::process`, dropping a `Child` handle does **not** kill the process by default — it keeps running detached from your handle unless `Command::kill_on_drop(true)` is set ([tokio-rs source/tests for this behavior](https://github.com/tokio-rs/tokio/blob/master/tokio/tests/process_kill_on_drop.rs)). For any subprocess invocation with an untrusted or potentially-hanging target (an extracted tool being run for the first time), wrap the wait in `tokio::time::timeout(duration, child.wait())` and explicitly `child.kill()` on timeout — timeout elapsing alone does not terminate the child.

### 4. Secrets

**What `secrecy` + `zeroize` actually buy you, precisely.** `secrecy::SecretBox`/`Secret<T>` wraps sensitive data so that (a) `Debug`/`Display` don't leak it — the crate's whole design point is "limit accidental exposure" via requiring an explicit `ExposeSecret`/`ExposeSecretMut` trait call to read the value, making every read auditable/greppable, and (b) `Drop` zeroizes the backing memory via the `zeroize` crate, closing the "use-after-free reads stale sensitive bytes from reused heap/stack memory" class of bug. The crate's own documentation is explicit about the boundary: it "favors a simple, `no_std`-friendly, safe implementation and does not provide more advanced memory protection mechanisms e.g. ones based on `mlock(2)`/`mprotect(2)`" ([docs.rs/secrecy](https://docs.rs/secrecy/latest/secrecy/)). Concretely this means: it does **not** stop the secret being swapped to disk, does **not** stop a process-memory dump or an attached debugger from reading it while live, and does **not** stop a hibernation image capturing it. `zeroize`'s own docs frame `mlock`-class protection as "interesting and useful, but often overkill (e.g. defending against RAM scraping or attackers with swap access)" ([appsec.guide memory-zeroization notes](https://appsec.guide/docs/languages/rust/memory-zeroization/), corroborated by `zeroize`/`secrecy` docs.rs). **Threat model that justifies zeroize here**: a long-running process holding a registry credential in memory, where the realistic attacker is "another local process or a later heap-reuse bug reads leftover bytes," not "an attacker with root or ptrace access" — against the latter, no userspace-only crate helps, and `mlock` only helps with the *swap* sub-case, not ptrace.

**Storage.** Prefer the OS credential store (`keyring` crate wrapping Keychain/Secret Service/Windows Credential Manager) over a plain file when available, since it inherits OS-level access control beyond file permissions. Where a file is the only option (headless CI, containers), mirror Docker's own `~/.docker/config.json` convention: JSON file, `0600`, in a directory that is itself not world-traversable in a meaningful way, and never checked into any cache that might be tarred up and shipped elsewhere.

**Avoid secrets in logs/errors/argv/env.** Concretely: never `format!("{:?}", token)` into a log line (use a wrapper whose `Debug` is redacted by construction — this is exactly what `secrecy` gives you for free); never interpolate a token into a `Command::arg()` (visible via `/proc/<pid>/cmdline`, `ps aux`); scrub `Authorization` headers before logging HTTP requests/responses (many HTTP client tracing integrations log headers by default — audit this explicitly); and make sure error types that wrap upstream HTTP errors don't `Display` the full request including auth headers.

### 5. Network / TLS / SSRF

**rustls is the current default recommendation.** The Rust ecosystem has been consolidating on `rustls` (pure-Rust, no OpenSSL dependency, no C toolchain requirement, no CVE class shared with OpenSSL) over `native-tls`; concretely, `rustup` began emitting a deprecation warning for the `native-tls` backend starting with rustup 1.28.2 (May 2025), stating the project wants to "standardize on an HTTP + TLS stack with more components in Rust, which should increase security, potentially improve performance, and simplify maintenance" ([blog.rust-lang.org rustup 1.28.2 announcement](https://blog.rust-lang.org/2025/05/05/Rustup-1.28.2/)). For `reqwest`, enable the `rustls-tls` feature and disable default features that pull in `native-tls`/OpenSSL, unless there's a specific requirement to trust the OS certificate store (e.g. corporate MITM proxies with an installed enterprise root CA) — in which case `rustls-tls-native-roots` bridges the OS store into rustls without depending on OpenSSL.

**Never disable certificate verification.** `reqwest::ClientBuilder::danger_accept_invalid_certs(true)` (the name itself is the warning) or a custom `rustls::client::danger::ServerCertVerifier` that unconditionally accepts must never ship, including "temporarily for local testing" — these flags have a habit of surviving into production behind a feature flag nobody audits. Grep for `danger_accept_invalid_certs`, `accept_invalid_hostnames`, and any `impl ServerCertVerifier` in CI.

**Timeouts and redirect/response-size limits.** `reqwest::Client`'s default redirect policy already follows up to 10 hops before erroring ([docs.rs reqwest::redirect](https://docs.rs/reqwest/latest/reqwest/redirect/index.html)) — reasonable, but a downloader pulling from a registry should still consider capping this lower and validating each hop's target isn't a private/loopback address if SSRF is in scope (see below). `reqwest` sets **no request timeout by default** — this must be set explicitly via `ClientBuilder::timeout()` (whole-request) and/or `connect_timeout()`; an unset timeout means a slow/stalled upstream can hang the tool indefinitely. Response size must be bounded while streaming (`response.bytes_stream()` + a running byte counter that aborts past a threshold) rather than via `response.bytes().await`, which buffers the entire body into memory first regardless of any later size check — a multi-gigabyte or infinite response can OOM the process before your code gets a chance to reject it.

**SSRF, for a tool that fetches URLs it did not fully choose (redirects, registry-returned blob URLs).** If any part of the target URL is influenced by external input (a registry's redirect response, a manifest-declared blob location), validate the resolved IP is not loopback/link-local/private-range before connecting, and re-validate on every redirect hop (not just the initial URL) — DNS rebinding means the hostname can resolve to a public IP at validation time and a private IP at connection time if these aren't the same connection. Practically: pin the resolved address for the lifetime of a single request rather than re-resolving DNS between check and connect.

### 6. Content trust: digest and signature verification

**Digest verification per the OCI spec.** The OCI image-spec's descriptor guidance is explicit and worth following to the letter: "Retrieved content SHOULD be verified against this digest when consumed via untrusted sources," and — importantly for avoiding a hash-collision-adjacent footgun — "Before calculating the digest, the size of the content SHOULD be verified to reduce hash collision space," with a further caution that "heavy processing before calculating a hash SHOULD be avoided" ([opencontainers/image-spec descriptor.md](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)). Concretely: check `Content-Length` (or the manifest-declared size) against the descriptor's declared size *before* starting to hash, hash incrementally as bytes are streamed off the wire (wrap the response body reader in a hashing adapter, e.g. computing SHA-256 via `sha2::Sha256` fed through a `Write`/`AsyncWrite` forwarding wrapper) rather than buffering then hashing, and reject on the first byte where the running digest cannot match (or, if streaming precludes early rejection, discard the entire buffer/temp file on final mismatch — never let a partially-verified file become the one that gets opened).

**"Verify before execute" as an operational, not just logical, sequence.** The dangerous gap is not "did we compute the hash correctly" but "is the file we hashed provably the same file we later open/execute." If verification writes to path A and execution opens path A again by name, anything that can replace path A between those two steps (another process, a symlink swapped in, a second concurrent invocation of your own tool racing itself) defeats the verification. The robust pattern: verify against an open file descriptor / handle, and continue using *that same handle* (or a hardlink taken while still holding it) for extraction/execution rather than re-opening by path — this is the filesystem-level analogue of the OCI/registry TOCTOU concern, and the same `cap-std`/`openat`-relative discipline from §2 applies. At minimum, verify-then-use must happen inside a directory the tool exclusively controls (private temp dir, `0700`), not a shared cache path another process/user could also write to mid-sequence.

**Signature verification (cosign/sigstore).** The `sigstore` crate (`sigstore::cosign::Client`, built via `ClientBuilder`) provides the verification half of cosign's model in Rust — checking a cosign signature layer against an OCI artifact, including keyless verification through Fulcio (Web-PKI-based short-lived cert issuance) and Rekor transparency-log inclusion proofs ([docs.rs/sigstore cosign module](https://docs.rs/sigstore/latest/sigstore/cosign/index.html)). As of the crate's own documentation this ecosystem is explicitly marked experimental / API-unstable, so pin an exact version and treat upgrades as requiring re-review, not routine bumps. If sigstore verification is adopted, it is additive to (not a replacement for) digest verification — signature verification proves *who* produced the artifact; digest verification proves the bytes you have are the bytes that were signed/pulled.

### 7. Input validation and parsing

**`#[serde(deny_unknown_fields)]` is a correctness/UX tool, not a DoS bound.** It causes deserialization to fail if the input contains fields the target struct doesn't define — useful for catching config typos early — but it does not bound recursion depth, collection size, or string length, and (per open serde issues) interacts awkwardly with `#[serde(flatten)]` and untagged enums, sometimes rejecting legitimately-shaped input ([serde-rs/serde issue discussion on deny_unknown_fields + flatten](https://github.com/serde-rs/serde/issues/1600)). Use it for config/lockfile schemas where the field set is meant to be closed, but pair it with explicit size/depth limits for anything read from the network — deeply nested untrusted JSON/YAML/TOML can exhaust the call stack via ordinary recursive-descent deserialization *before* any unknown-field check ever runs; this exact class of bug was fixed as a stack-overflow DoS in `serde-json-wasm` by adding a recursion-depth check (RUSTSEC/CVE-2024-58264 class). Concretely: prefer parsers/config formats with a configurable recursion limit, or pre-check nesting depth / total byte size before handing untrusted bytes to `serde_json`/`serde_yaml`/`toml`, and set the input size ceiling at the transport layer (§5's streaming response-size cap) so a deserializer never sees an unbounded buffer in the first place.

**`overflow-checks` in release builds is off by default — and this matters here.** Cargo's default `overflow-checks` is `true` for `dev`/`test` profiles and **`false`** for `release`/`bench` ([doc.rust-lang.org cargo profiles reference](https://doc.rust-lang.org/cargo/reference/profiles.html#overflow-checks)) — meaning the exact build a user runs silently wraps on overflow while `cargo test` would have panicked and caught the same bug in CI. For a tool doing arithmetic on attacker-influenced values (archive entry sizes, offsets, declared content-lengths, cumulative byte counters against a size-limit check), a wraparound can turn a size check that should reject an oversized value into one that accepts it (classic "negative/huge value wraps to something under the threshold" bug class). Concrete precedent for real-world impact once checks are enabled: `ring`'s `aead::quic::HeaderProtectionKey::new_mask()` could panic under `overflow-checks = true` on an attacker-crafted QUIC packet, i.e. the check itself becomes a DoS surface if triggered on unvalidated input in a hot path (search corroboration: ANSSI guidance flags this dev/release behavior difference explicitly as a pitfall to be aware of). Recommendation: set `overflow-checks = true` in `[profile.release]` for this codebase given it parses attacker-controlled sizes, and additionally use `checked_add`/`checked_mul`/`saturating_*` explicitly at every point where an untrusted length or offset is combined with another value, so the failure mode is a clean rejection rather than either a silent wrap (checks off) or an unhandled panic (checks on, no explicit handling) — `clippy::arithmetic_side_effects` is the lint that flags exactly this pattern (any `+`, `-`, `*`, `<<` that can overflow, or `/`, `%` that can panic on zero) and pushes toward the explicit `checked_`/`wrapping_`/`saturating_` alternatives ([rust-lang.github.io/rust-clippy lint index](https://rust-lang.github.io/rust-clippy/master/index.html)).

## Normative guidance candidates

1. **Pin `tar >= 0.4.45` and `zip >= 2.3.0` (or later) explicitly in Cargo.toml, not just "latest compatible."** Rationale: both crates shipped real symlink-driven extraction escapes below these versions (RUSTSEC-2021-0080, RUSTSEC-2026-0067, CVE-2025-29787). Verify: `cargo tree -i tar -i zip` shows resolved versions ≥ the floor; `cargo audit` / `cargo deny check advisories` in CI fails the build on any RUSTSEC hit for these crates.
2. **Never extract an untrusted archive by writing to paths derived from `canonicalize()`-then-compare; extract into a `cap-std::fs::Dir` (or equivalent `openat`-relative walk) instead.** Rationale: canonicalize-then-check is TOCTOU-able; capability-scoped directory handles are enforced per-syscall by the OS resolver. Verify: grep extraction code for `canonicalize` used as a security check (vs. purely cosmetic path display); confirm the extraction routine takes a `Dir`/fd, not a `PathBuf`, as its containment boundary.
3. **Reject archive entries that are symlinks, hardlinks, device files, or carry setuid/setgid bits unless the tool has an explicit documented need to preserve them.** Rationale: this is the exact entry-type class every cited CVE in this file abused. Verify: code-reading heuristic — extraction loop must match on `EntryType`/`ZipFileType` (or zip's file-attribute bits) and explicitly branch/reject non-regular, non-directory entries rather than falling through to a generic write.
4. **Enforce a max entry count, max per-entry decompressed size, and max total decompressed size while streaming extraction, before any bytes are trusted.** Rationale: neither `tar` nor `zip` bounds decompression by default; declared sizes in archive headers are attacker-controlled and must not be trusted as the enforcement mechanism. Verify: code reads use a byte-counting reader wrapper (not `read_to_end`/`extract()` unmodified) with a hard error path when a threshold is exceeded; a test fixture with a deliberately oversized/nested archive should fail fast.
5. **Set `[profile.release] overflow-checks = true` in the workspace Cargo.toml.** Rationale: release default is `false`; this codebase computes offsets/sizes from attacker-controlled archive and HTTP inputs where silent wraparound is a security-relevant miscalculation, not just a correctness nit. Verify: `grep -A2 '\[profile.release\]' Cargo.toml` shows the setting; `cargo build --release` + a targeted overflow test panics as expected.
6. **Any argument passed to a spawned subprocess that originates from untrusted/external data must either be preceded by a literal `--` in the argument list, or validated not to start with `-`.** Rationale: `Command` never invokes a shell, but the *invoked program's own* argv parser can reinterpret a leading-dash value as a flag (argument injection, distinct from shell injection). Verify: grep `Command::new` call sites for untrusted values passed via `.arg()`/`.args()` without a preceding `.arg("--")`.
7. **Invoke any subprocess whose identity is security-relevant (a downloaded/verified binary, a tool the user asked to run) by absolute canonicalized path, never by bare name via `PATH` search.** Rationale: PATH poisoning — an attacker-writable directory earlier in `PATH` silently substitutes the executed binary. Verify: grep `Command::new(` call sites for bare program names (no `/` or `\`) where the target came from a download/verification step rather than being a well-known system utility.
8. **Pin the Rust toolchain to `>= 1.81.0` and never invoke `.bat`/`.cmd` targets directly on Windows with untrusted arguments, even on a patched toolchain.** Rationale: CVE-2024-24576's first fix (1.77.2) was incomplete until CVE-2024-43402's fix (1.81.0, trailing-whitespace/period bypass). Verify: `rust-toolchain.toml` / CI `rustc --version` ≥ 1.81.0; grep for `Command::new` targets ending in `.bat`/`.cmd` or resolving to `cmd.exe`.
9. **Use `tokio::process::Command::kill_on_drop(true)` plus `tokio::time::timeout(...)` around `child.wait()` for every subprocess spawn of an extracted/untrusted binary.** Rationale: a dropped `Child` handle leaves the process running by default under Tokio; an unbounded wait lets a hung/malicious subprocess block the tool indefinitely. Verify: grep `tokio::process::Command::new` call sites for a paired `.kill_on_drop(true)` and a `timeout(...)` wrapping the wait/output call.
10. **Never call `.env("PATH", ...)` implicitly by omission after `env_clear()`; always set `PATH` explicitly when clearing the environment for a subprocess.** Rationale: `execvp` silently falls back to a default search path on Unix, not "no PATH," which can resolve to an unexpected binary. Verify: grep `env_clear()` call sites; each must have an adjacent explicit `.env("PATH", ...)`.
11. **Create all download/extraction temp files via the `tempfile` crate (`NamedTempFile`/`Builder`), never via a hand-built predictable path in a shared directory.** Rationale: predictable temp names in a shared/world-writable directory are a symlink-race and TOCTOU vector. Verify: grep for `format!(...".tmp"` or similar ad hoc temp-path construction; confirm `tempfile::` is used instead.
12. **Set credential/lockfile permissions explicitly to `0600` (files) / `0700` (directories) at creation time via `OpenOptionsExt::mode`/`set_permissions`, not via ambient umask.** Rationale: umask is uncontrolled environment/process state and can legitimately be looser than intended on a misconfigured host. Verify: grep credential-file creation paths for an explicit `.mode(0o600)` or post-creation `set_permissions` call.
13. **Never construct an HTTP client with certificate verification disabled (`danger_accept_invalid_certs`, an always-accept `ServerCertVerifier`).** Rationale: this is the single highest-severity TLS misconfiguration and is not appropriate even for local testing paths that could ship. Verify: `grep -rn "danger_accept_invalid\|accept_invalid_hostnames\|impl.*ServerCertVerifier" src/` returns nothing outside of test-only, non-shipped code.
14. **Set an explicit request timeout on every HTTP client used for network fetches.** Rationale: `reqwest` enforces no timeout by default; an unbounded request can hang the tool indefinitely on a stalled/malicious upstream. Verify: every `reqwest::Client`/`ClientBuilder` construction site includes `.timeout(...)` and/or `.connect_timeout(...)`.
15. **Bound response body size while streaming (`bytes_stream()` + running counter), never via `response.bytes()`/`.text()` on a source you don't fully trust the size of.** Rationale: `.bytes()` buffers the entire body before any size check can run, allowing memory exhaustion from an oversized or unbounded response. Verify: grep for `.bytes().await`/`.text().await` on HTTP responses from registry/network sources; each such call site should instead stream with an enforced cap.
16. **Hash downloaded content incrementally while streaming and compare against the expected digest before the bytes are used for anything (extraction, execution, caching as "verified").** Rationale: buffer-then-hash defers rejection past the point where damage (memory use, or worse, partial extraction) has already happened; verify-then-reopen-by-path reintroduces TOCTOU. Verify: code-reading heuristic — the hashing writer/reader must wrap the same stream that is written to the eventual cache/extraction target, and the target must not be treated as trusted (moved out of a quarantine temp path) until the digest comparison has succeeded.
17. **Treat an OCI bearer-token response as narrower than requested until proven otherwise — check the token's actual granted scope, don't assume a 200 response means the full requested scope was granted.** Rationale: the token spec explicitly allows the server to intersect requested scope with actual permissions without erroring. Verify: code-reading heuristic — token-acquisition code inspects the returned token's scope/claims (where decodable) or otherwise fails closed on the specific operation (push/pull) it needed, rather than assuming success from HTTP status alone.
18. **Do not rely on `#[serde(deny_unknown_fields)]` as a size/DoS guard; enforce input size and nesting-depth limits (or a size cap upstream in the HTTP layer) separately for any untrusted JSON/YAML/TOML.** Rationale: `deny_unknown_fields` only rejects unexpected field names after parsing has already recursed; it does not bound stack depth or payload size. Verify: grep deserialization call sites on network-sourced input for an upstream size cap (see rule 15) and, where the format allows configuration, an explicit recursion-depth limit.

## AI-agent angle

- **Hallucinated "safe by default" extraction APIs.** An LLM trained on general Rust knowledge will confidently write `archive.extract(dest)?` (zip) or `archive.unpack(dest)?` (tar) as if that alone is the complete security story, because that is genuinely what most tutorials show. It is *necessary* but was *not sufficient* even in-version, historically (§1). Mechanical check: any extraction call site that is not additionally paired with a version floor pin (rule 1) and either an entry-type allowlist (rule 3) or a `cap-std`-scoped directory (rule 2) should be flagged in review.
- **Command-line "shell-safe" false confidence.** Agents often reason "I used `Command::arg()`, not a shell string, so this is injection-safe" and stop there — true for shell injection, false for argument injection (rule 6) and false for Windows `.bat`/`.cmd` targets pre-1.81.0 (rule 8). Mechanical check: grep every `Command::new`/`.arg` call site touching untrusted data for a `--` separator or leading-dash validation; grep for `.bat`/`.cmd` targets.
- **Assuming `zeroize`/`secrecy` = "handled" for secrets, full stop.** Agents commonly add `Secret<String>` and consider the secret-handling task complete, without noticing the crate's own documented boundary (no `mlock`, no swap protection) — then either over-claim the security property in a comment/doc, or fail to also address the argv/env/log leak vectors that `secrecy` does *not* cover (§4). Mechanical check: reviewer greps for `ExposeSecret`/`expose_secret()` call sites and manually verifies the exposed value doesn't then flow into `Command::arg()`, `format!`, or a log macro.
- **Missing `overflow-checks` in release, or "fixing" overflow with `as` casts.** A common LLM pattern when told "handle large numbers safely" is to insert `as u64`/`as usize` truncating casts, which silently changes the bug from a debug-build panic to a release-build silent-wrong-value in exactly the same way `overflow-checks = false` does — it looks like a fix but preserves the vulnerability. Mechanical check: `cargo clippy -- -W clippy::arithmetic_side_effects -W clippy::cast_possible_truncation` on the touched module; reviewer greps diff for new `as` casts adjacent to size/offset arithmetic.
- **Reaching for `native-tls`/`openssl` out of habit from older tutorials.** Training data skews toward `native-tls` examples predating the 2025 rustls consolidation (§5); an agent may add `reqwest = { features = ["native-tls"] }` without being aware of the ecosystem shift. Mechanical check: `cargo tree -i openssl-sys -i native-tls` should return nothing in a fresh dependency add; CI can hard-fail on either appearing.
- **Treating `deny_unknown_fields` as "input validated."** Agents asked to "harden the config parser against untrusted input" frequently add only `#[serde(deny_unknown_fields)]` and consider the task done, missing that it does nothing for recursion/size DoS (§7). Mechanical check: reviewer confirms a size cap exists upstream of the deserializer call, independent of what serde attributes are present on the target struct.
- **Confusing `std::fs::canonicalize` with a security boundary.** Agents frequently produce exactly the "WRONG" pattern shown in §2 (canonicalize, then `starts_with` check) because it reads as correct and is the top explanation for "prevent path traversal in Rust" in generic training material, without surfacing the TOCTOU caveat. Mechanical check: grep for `canonicalize()` followed within a few lines by `starts_with`/`contains` as the sole containment check, with no `cap-std`/`openat`-relative operation backing it.

## Contested / evolving

- **rustls vs. native-tls is trending decisively toward rustls (as of mid-2025), but is not yet a unanimous "always" rule.** `native-tls` retains a real argument where integration with an OS-managed certificate store (enterprise MITM proxies, custom internal CAs already trusted at the OS level) is a hard requirement; `rustls-tls-native-roots` narrows but doesn't fully close this gap. Current direction: default to rustls, special-case native-tls only with a stated reason.
- **Whether `overflow-checks = true` belongs in release builds is genuinely debated in the wider Rust community** — the performance cost is generally small but nonzero, and enabling it can turn a previously "wrong but running" code path into a hard panic in production if the code wasn't written with `checked_`/`saturating_` discipline in the first place (the `ring`/QUIC precedent cited in §7 illustrates this cuts both ways: checks-on can itself become the DoS trigger if the resulting panic is reachable on attacker input in a service context). For a CLI tool (crashes rather than takes down a shared service), the tradeoff favors enabling it; for a long-running daemon, some teams prefer explicit `checked_`/`saturating_` arithmetic at trust boundaries instead of a blanket flag, treating the flag as a development-time safety net rather than a production guarantee.
- **`cap-std` adoption is still comparatively niche outside the Bytecode Alliance/WASM ecosystem** — it is the technically strongest answer to path-traversal-proof extraction, but pulling it into a codebase whose ambient-authority filesystem code is otherwise plain `std::fs` is a real architectural change, not a drop-in. Current direction: growing awareness following repeated tar/zip CVEs, but most Rust CLI tools as of 2026 still rely on canonicalize-and-check plus careful entry-type filtering rather than full capability-based sandboxing — treat `cap-std` as the target state to migrate toward for new extraction code, not necessarily a blocking requirement for every existing call site on day one.
- **Sigstore/cosign verification for Rust tools is early and the crate ecosystem says so itself** (`sigstore-rs`, `sigstore-verification` both flagged experimental/API-unstable in their own docs). Whether an OCI-consuming Rust CLI should require sigstore verification by default, or treat it as an opt-in trust-on-first-use enhancement layered on top of mandatory digest verification, is unsettled in the ecosystem — digest verification is the non-negotiable baseline; signature verification is trending toward "increasingly expected for security-sensitive tools" but is not yet as universally mechanical to implement correctly in Rust as it is in Go (where `cosign`/`sigstore-go` are more mature).
