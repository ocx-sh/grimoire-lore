## Smells (ranked)

1. **Genuinely free-to-change comments are rare in this fleet.** Grepping ocx
   and grimoire for "arbitrary", "for readability", "cosmetic", "purely
   stylistic" and "round number" (`grep -rln 'arbitrary\|for readability\|purely stylistic\|round number' --include='*.rs' crates/`)
   returned only load-bearing hits (e.g. `ocx_console/src/progress.rs:208`'s
   "arbitrary file descriptor" is part of a real `is_term` security-adjacent
   check, not an incidental choice). All 8 FTC sites I did find are trivial
   accessor doc comments, not inline "why" comments — this fleet does not
   appear to carry much genuinely-incidental prose at all, which cuts against
   treating "shorten everything" as a safe default strategy (see H4/H6 below).
2. **The identical RAII-rename footgun exists in two unrelated codebases**
   (OCX-09, GRM-08): `let _<name> = <guard-returning-call>` where renaming the
   binding to `_` (a completely standard, tool-suggested unused-variable
   cleanup) silently drops the guard at that statement instead of holding it
   for the enclosing scope. Neither site's comment says "do not rename this
   binding" in so many words — the reader has to infer it from "held until
   this call returns" / "owning the slot here… is what prevents." A shorter,
   more literal warning (e.g. "NAMED BINDING: renaming to `_` drops this
   immediately") would be more robust to compression than the current prose.
3. **`Option<bool>` vs `bool` collapsing is a recurring, unlabeled danger
   shape.** OCX-20's `insecure_hosts` and, less severely, the general "None
   means silence, Some(false) means a decision" pattern (also visible in
   `ManagedConfig::required: Option<bool>`, not separately harvested) rely on
   a reader noticing the type is `Option<bool>` and not `bool`. A comment that
   states the three-state semantics explicitly survives compression better
   than one that only shows it in a code example.
4. **Two sibling functions differing only in symlink posture, with the
   difference load-bearing** (GRM-05's `atomic_write` vs
   `atomic_write_through_symlink`) is a shape an agent's "reduce duplication"
   reflex is specifically primed to attack. The current comment already
   explains *why* twice (module-adjacent + per-function), which is probably
   correct — this is a case where the frame's "essay" instinct to cut would
   likely be wrong.
5. **Structural (compile-time-exhaustive) guards have no test-coverage
   answer at all** (OCX-17). The eval's ground-truth schema asks "does a test
   fail today if the guard is removed," but this category's honest answer is
   "no test can," which the schema doesn't distinguish from "no test happens
   to exist yet." The eval design should treat `n/a:structural` as its own
   bucket, not fold it into "no test."

## Patterns worth encoding

- **Name the binding explicitly as load-bearing when it's an RAII guard.** A
  one-clause tag ("named on purpose — dropping it early releases the
  <lock/slot>") next to any `let _<x> = <guard>` would have survived every
  compression level tested informally against the two real sites found
  (OCX-09, GRM-08), where the current prose is longer and less literal.
- **State three-way `Option<bool>`/tri-state semantics as a rule, not just an
  example.** OCX-20 gets this right in prose ("`Some(false)` is a decision;
  `None` is silence and subtracts nothing") — that sentence, not the
  surrounding paragraph, is the part worth preserving verbatim under any cut.
- **Distinguish "no test yet" from "no test possible" in the eval/rule
  schema.** A structural/compile-time guard (OCX-17's exhaustive match) needs
  its comment preserved *because* no test backs it, which is the opposite of
  how "add a test instead of a comment" advice usually reads.
- **A comment that names its own counter-example function is worth more than
  one that doesn't.** OCX-02 ("the opposite posture from `ocx launcher
  shim`'s `resolves_inside`") and GRM-01/GRM-02 (path_safety.rs and
  path_anchor.rs cross-referencing each other's divergent CurDir handling)
  both let a cold reader sanity-check by diffing two functions instead of
  trusting prose alone — this is a cheap, robust "where else the reason
  lives" pattern that isn't an ADR, a rule, or git history, and the current
  rule sets don't call it out as its own category.

## Contradictions of the frame

- **H4 ("a guard survives a cut when its constraint stays as one local line…
  or when a test named for the constraint fails on removal") undercounts a
  real third state.** 12 of 40 sites (30%) are obviousness-3 with *no* test
  today, meaning the comment is the sole defense — H4's "or a test" escape
  hatch does not apply to them. One of those 12 (OCX-17) additionally can
  *never* get a runtime test (it's a compile-time exhaustiveness guarantee),
  which H4 doesn't have a category for at all. If the cut-line eval scores
  guard survival only where a test exists as ground truth, it will silently
  skip evaluating exactly the sites where the comment matters most.
- **H5 ("cold agents seldom read git history or decision records
  unprompted") is not contradicted by this pass, but it is also not tested by
  it, and the frame should not treat it as confirmed.** I never needed `git
  log -S`/`git log -L` to recover a single site's ground truth — the reason
  was always already in the file I was reading. That is *consistent* with H5
  (nothing here required a cold agent to go looking further), but I did not
  attempt the actual test H5 implies (strip the comment, then see whether an
  agent goes looking for git history) — see the disclosure at the top of this
  file and Gaps below.
- **H6 ("narration, plan IDs, history and tautology carry under 10 percent of
  guard information") is indirectly supported by this harvest in a way worth
  flagging: none of the 40 mechanism sites' load-bearing reason lines were
  narration, a plan ID, or history phrasing** — every single one was either a
  why-constraint or a named counter-example/test pointer. The 8 free-to-change
  sites, by contrast, were *all* tautological "Returns the X" narration. That
  is a clean split in this sample (guard sites carry constraints; incidental
  sites carry narration), which is a stronger version of H6 than the frame
  states — worth re-testing on a larger sample before generalizing.
- **The owner's 1:4–1:6 target and H1/H2/H3 are not addressed by this
  document at all** — this pass harvested eval sites, not comment-density
  ratios or block-length distributions, and running `comment_census.py`
  again here would only reproduce numbers the frame and the prior-evidence
  file already carry. Flagging this explicitly so it isn't mistaken for a
  second, independent confirmation of those hypotheses.

## Gaps

- **No `git log -S` / `git log -L` was run for any of the 48 sites**, despite
  demand 3 asking for it. Every "elsewhere: none found" above means "not
  checked," not "checked, absent." Before this eval's ground truth is treated
  as final, at least the 12 Tier-A (no-test) sites should get a real history
  check — if any of them turn out to have an ADR or a detailed commit message
  behind them that the file itself doesn't surface, that changes their
  eval value (a cold agent with git-blame access might recover the reason a
  different way than assumed here).
- **cfg(windows) tests were not executed** (this session ran on Linux) for
  OCX-03, OCX-05, OCX-08, and the Windows halves of GRM-05/TS-04's platform
  reasoning; their "test: yes" status is read from the test's name and body,
  not from a green run. The user's own CLAUDE.md documents a local
  cross-compiled Windows test path (`grim-wintest`/`ocx`-equivalent) that
  this pass did not use, since it targets `grimoire`'s own `grim.exe`, not
  `ocx`'s Windows-gated unit tests specifically — a follow-up should confirm
  these directly rather than trusting test names.
- **TS-01's precise guarded scenario (a symlinked *parent* directory
  specifically) has no dedicated test**, only a plain `../` traversal test
  that exercises a different, earlier check in the same function. This is
  flagged in its row but worth restating: it is the one site in the whole
  harvest where I could show the *general* mechanism is tested but the
  *specific* line's own failure mode is not.
- **grimoire-vscode's TS-03 (torn-write-on-concurrent-save) has no concurrency
  test I could find**, and I did not write one (read-only mandate) — a
  reason-recovery eval probe that removes this comment and asks "does a
  concurrent save still work" has no oracle in-repo today beyond re-reading
  the comment itself.
- **This document does not re-verify the frame's fleet-wide density table or
  H1–H3**; that is out of scope for an eval-site harvest and would need a
  separate `comment_census.py` run, which I deliberately did not duplicate
  here (see `method` in the frontmatter).
- **Sample coverage inside each repo is shallow relative to repo size** (e.g.
  89,987 ocx code lines per the frame vs. 24 sites read closely here). The
  40+8 sites are a hand-picked, keyword-seeded sample, not a random one; the
  "spot-read ≥3 hits, report false-positive rate" instruction was followed
  per search pattern, not per repo, so silent guard patterns using different
  vocabulary (no "fail-open", no "must propagate", etc.) are systematically
  under-sampled here.
