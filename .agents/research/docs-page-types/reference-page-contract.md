## Summary

- A reference page has a fixed section set — title+description, syntax/declaration, parameters, return value, behavioral remarks, example, requirements, see-also — not a free-form essay; Microsoft's table names eight, ocx's own agent file independently reinvented four of them uncredited ([Microsoft](https://learn.microsoft.com/en-us/style-guide/developer-content/reference-documentation)).
- Reference structure must mirror the actual code/API structure — one section per real command, endpoint, or type, in the code's own grouping — never an author's preferred regrouping ([Diataxis](https://diataxis.fr/reference/)).
- Reference prose is neutral description only: no instruction, no opinion, no narrative frame, no "let's" — link out to a how-to or explanation instead of writing one inline ([Diataxis](https://diataxis.fr/reference/)).
- Auto-generated reference needs a human review pass before publishing, specifically to strip internal-only detail developers leave in doc-comments — stated as an explicit warning, not a nice-to-have ([Microsoft](https://learn.microsoft.com/en-us/style-guide/developer-content/reference-documentation)).
- The fleet already has a live counterexample of an unreviewed generated stub: `ocx-mirror-sdk/docs/api/text.md` is one line, a bare mkdocstrings directive with zero surrounding prose (verified by direct read).
- Single-page-per-resource and one-page-per-item are both real, deliberate architectures in 2026 — but a direct fetch of `docs.stripe.com/api/charges/create` shows Stripe itself has moved to standalone per-endpoint pages, contradicting the "one long personalized page" reputation the same corpus's own exemplar-sites scout recorded on the same day. Treat that as settled: converge toward per-item.
- Rust's `std` reference is one page per item with permalinks, generated by rustdoc directly from doc-comments — the other real-world instance of the per-item default, and evidence it scales to a whole standard library ([doc.rust-lang.org/std](https://doc.rust-lang.org/std/index.html)).
- GitLab's style guide gives the one numeric, mechanically-checkable split trigger found anywhere in the corpus: "avoid heading levels greater than H5 … move the topics to a new page instead" ([GitLab](https://docs.gitlab.com/development/documentation/styleguide/)).
- The fleet's own worst instance of not splitting: `ocx/website/src/docs/reference/command-line.md` is 30 top-level commands and 34,298 prose words in one file — longer than the entire docs surface of 12 of 23 measured repos.
- ocx already runs a structural (non-executing) drift gate for that one file: `test/tests/test_doc_command_reference.py` (479 lines) asserts a stable `{#anchor}`, a `**Usage**` block, and an `**Options**` block per live command, and a separate tombstone check for removed ones.
- grimoire runs the equivalent gate for a table instead of a page tree: `src/install/client_target.rs::docs_matrix_row_set_matches_all_and_cells_track_kind_support` reads `docs/src/clients.md` at test time and fails the build if the row set or any cell drifts from `ClientTarget::ALL` and each vendor's `kind_support`.
- Both drift gates are non-executing structural tests, not the acceptance-tested-command mechanism — they check shape (anchors, blocks, table cells), not behavior, and that is the right generalizable shape for an enumerative reference page.
- A naive link checker manufactures false positives against generated reference: `ocx-sdk-python`'s mkdocstrings anchors don't exist until `mkdocs build` runs, producing 65 "dead" links from one repo alone before that's special-cased.
- No canonical source states a total-word-count split trigger for reference pages; the only numeric trigger found is heading-depth (GitLab, H5). Treat a word-count cap as a fleet-specific argued heuristic, not a citable rule.
- "Purpose sentence + flags table (Name/Short/Description/Default) + behavioral notes + error conditions" already exists, unnamed, in `ocx/.claude/agents/worker-doc-writer.md` — the shipped contract should generalize this pattern rather than re-derive one from scratch.
- Neutral tone has no off-the-shelf lint; the only checkable proxy found is a targeted grep (banned narrative openers, first-person, imperative mood outside a fenced Usage block) run only on pages that declare `type: reference` — worthless without that declaration existing first.

## Findings

### 1. The fixed-section contract

Microsoft's developer-content style guide gives the canonical fixed-section table for a reference article, and states explicitly that "not all sections appear in all reference articles" — the table is a menu, not a mandatory checklist for every kind of element:

| Section | Contains |
|---|---|
| Title and description | Element name + a concise sentence describing it, ideally without repeating the name |
| Declaration/syntax | The code signature; multiple languages get multiple syntax blocks |
| Parameters | Name, type, required/optional, input/output, with real detail — "Don't just repeat the words in the parameter name or the data type" |
| Return value | The value and its type; for a boolean, the condition it signals |
| Remarks | Anything not obvious from syntax/parameters/return — comparisons, gotchas |
| Example | A runnable code sample |
| Requirements / Applies to | Language or platform requirements |
| See also | Links to related elements and usage guides |

Plus, named separately for elements that raise: **Exceptions/error codes** — "list them and describe the conditions under which they occur" ([Microsoft](https://learn.microsoft.com/en-us/style-guide/developer-content/reference-documentation)).

idratherbewriting.com's REST API course converges on a narrower, five-section version purpose-built for HTTP endpoints: **resource description, endpoints and methods, parameters, request example, response example and schema** — "API reference documentation usually includes five key sections for each resource" ([Learning API Doc — Documenting API endpoints](https://idratherbewriting.com/learnapidoc/docendpoints.html)).

The fleet already has its own version of this, uncredited, doing double duty as three sub-contracts by data shape rather than one generic template:

> "Command reference: purpose sentence + flags table (Name | Short | Description | Default) + behavioral notes + error conditions. Environment variables: name + purpose + valid values (explicit list) + default + example. Metadata fields: name + type + description + constraints + example. ... No tutorials, no narrative — facts only." — [`ocx/.claude/agents/worker-doc-writer.md`](../../../../ocx/.claude/agents/worker-doc-writer.md)

`ocx/website/src/docs/reference/command-line.md`'s `lock` command is a real, in-the-wild instance that satisfies Microsoft's table almost section-for-section: a title+description paragraph, a `:::tip` remark comparing it to a sibling command, a `**Usage**` code block (declaration/syntax), an `**Options**` table (parameters), an `**Exit codes**` table (exceptions/error codes), and a `**JSON output**` schema table (return value) — five of Microsoft's eight sections present, in the order Microsoft lists them, arrived at independently.

**Bad** — the entire content of a "reference" page with none of this:

```markdown
# Text

::: ocx_mirror_sdk.text.extract_urls
```
— [`ocx-mirror-sdk/docs/api/text.md`](../../../../ocx-mirror-sdk/docs/api/text.md), verified by direct read: one heading, one mkdocstrings directive, zero prose, zero examples.

**Good**, same repo family, same "reference" intent — a real section from `command-line.md`:

```markdown
### `lock` {#lock}

Resolves every tool tag in the nearest `ocx.toml` to per-platform leaf
digests and writes the result to `ocx.lock` next to it. ...

**Usage**
​```shell
ocx lock [OPTIONS]
​```

**Options**

| Flag | Short | Description | Default |
|------|-------|-------------|---------|
| `--pull` | — | ... | on |
...

**Exit codes**

| Code | Meaning |
|------|---------|
| 0 | `ocx.lock` written (or preserved if content was unchanged). |
...
```
— [`ocx/website/src/docs/reference/command-line.md:432-500`](../../../../ocx/website/src/docs/reference/command-line.md).

### 2. Reference must mirror the code, not an author's grouping

Diataxis states the structural rule directly, under "Respect the structure of the machinery": "the structure of the documentation should mirror the structure of the product" so a reader can navigate the two side by side ([diataxis.fr/reference](https://diataxis.fr/reference/)). Microsoft's implied version is the fixed-table-per-element convention itself — one article (or section) per programming element, following the code's own taxonomy of element kinds (class, method, property, event), not a topic-based regrouping.

The two independent fleet mechanisms both enforce exactly this, mechanically:

- ocx's `test_doc_command_reference.py` walks `NEW_COMMAND_ANCHORS`, a literal list of `(anchor, command)` pairs kept in sync by hand with the CLI's real command set, and fails if a live command's section is missing its `**Usage**`/`**Options**` blocks, or if a removed command still carries one (`TOMBSTONE_ANCHORS`, checked for a `> **REMOVED**` or `> **Moved to**` marker instead) — [`ocx/test/tests/test_doc_command_reference.py:45-72`](../../../../ocx/test/tests/test_doc_command_reference.py).
- grimoire's `client_target.rs` reads `docs/src/clients.md`'s first markdown table at **test runtime** (`std::fs::read_to_string`, not compile time), parses `(client, kind)` cells, and asserts the row set equals `ClientTarget::ALL` exactly and every cell (`✓`/`◐`/`✗`) matches the corresponding `Vendor::kind_support` — [`grimoire/src/install/client_target.rs:742-775`](../../../../grimoire/src/install/client_target.rs).

Both gates prove the same property — the reference's enumeration (of commands, of clients) is identical to the code's enumeration — by comparing against a literal, hand-maintained or code-derived list, not by re-deriving structure from prose.

### 3. Neutral tone, and how to check it

Diataxis's "Describe and only describe" names the target register directly: reference demands "austere and uncompromising… neutrality, objectivity, factuality," prioritizing "accuracy, precision, completeness and clarity" over instruction or explanation — "You will certainly not expect to find for example recipes or marketing claims mixed up with this information." Where instruction is needed, reference should "link to how-to guides, explanation and introductory tutorials," not absorb their content ([diataxis.fr/reference](https://diataxis.fr/reference/)).

GitLab's voice rules give the closest thing to a grep-ready version of the same idea, aimed at prose generally but directly applicable to a reference page's remarks: never write about the page itself ("This page shows…" is banned outright), never "allow/enable" framing, never "easily/simply" ([GitLab style guide](https://docs.gitlab.com/development/documentation/styleguide/)).

No canonical source in this survey ships a lint rule scoped specifically to "reference-page neutrality" — it is a reading judgment everywhere it's stated. The checkable proxy is narrower than the ideal: grep a `type: reference`-tagged page's prose (excluding fenced code and tables) for first-person pronouns ("we," "I"), narrative openers ("let's," "now that we've"), and imperative-mood sentence starts outside a `**Usage**` block ("run," "add," "set" as the first word of a sentence). This only works once page-type declaration exists (owned by the sibling `page-type-set-and-declaration` topic) — reference-neutrality has no target to fire on before that.

**Bad** (narrative frame inside a nominally "reference" page):

> "Now that we've covered installation, let's look at how `ocx lock` works. You'll want to run this whenever your `ocx.toml` changes."

**Good** (same fact, descriptive):

> "`ocx lock` resolves every tool tag in the nearest `ocx.toml` to per-platform leaf digests and writes the result to `ocx.lock`."
— actual opening sentence of [`command-line.md`'s `lock` section](../../../../ocx/website/src/docs/reference/command-line.md).

### 4. Single page vs one page per item

The brief's comparison assumed Stripe's API reference is "one long page per resource, personalized per account." A direct fetch (2026-09-05) shows that description is stale for the current site:

- `docs.stripe.com/api` is itself now a navigation hub, not a reference body — it opens with "Read this page in your terminal" (a Stripe-CLI `stripe docs` invocation) and CLI/skills onboarding before any endpoint content ([docs.stripe.com/api](https://docs.stripe.com/api)).
- `docs.stripe.com/api/charges` — the resource-level page — is an **index**: it lists six endpoints (`Create a charge`, `Update a charge`, `Retrieve a charge`, `List all charges`, `Capture a charge`, `Search charges`), each linking to its own `.md`-suffixed URL, plus an `## Events` section; it carries no inline parameter or response detail itself ([docs.stripe.com/api/charges](https://docs.stripe.com/api/charges)).
- `docs.stripe.com/api/charges/create` is a fully standalone page: its own `## Request`, `## Response`, `## Returns`, and `## Parameters` sections, scoped to exactly that one endpoint, with its own permalink ([docs.stripe.com/api/charges/create](https://docs.stripe.com/api/charges/create)).

So by this era, Stripe's reference is genuinely per-endpoint, structurally the same shape as Rust's `std` (one page per item, its own permalink) rather than the opposite of it. Rust's `std` remains the clean machine-generated instance: every type, function, macro, and primitive gets its own page and URL (`vec/struct.Vec.html`, `option/enum.Option.html`, `macro.format.html`), generated by rustdoc directly from source doc-comments, with a "Source" link back to the defining code and a collapsible summary view rather than a single scrolling document ([doc.rust-lang.org/std](https://doc.rust-lang.org/std/index.html)).

Neither real-world instance found in this survey is still "one giant page." The corpus's stated conflict (single-page-per-resource vs. one-page-per-item) resolves toward per-item as the converged 2026 default — see [Contested / evolving](#contested--evolving).

### 5. The page-splitting threshold

The one numeric, source-backed trigger found anywhere in this survey is GitLab's heading-depth cap, quoted directly: "Avoid heading levels greater than `H5` (`#####`). If you need more than five heading levels, move the topics to a new page instead," further noting "Heading levels greater than `H4` do not display in the right sidebar navigation" — an independent, mechanical reason (the right-rail TOC silently drops anything past H4) for the same cap ([GitLab style guide](https://docs.gitlab.com/development/documentation/styleguide/)). GitLab's companion links-per-page guidance — "try not to use more than 15 links to other pages" — is a second soft signal that a page has grown past a single coherent unit, though it targets link density generally, not reference pages specifically.

No source in this survey states a reference-page word-count or item-count split trigger directly. The fleet supplies the empirical case for needing one: `command-line.md` documents 30 top-level commands (`add`, `clean`, `deps`, `deselect`, `env` ×2, `exec`, `which`, `direnv`, `index`, `about`, `status`, `inspect`, `init`, `install`, `login`, `logout`, `lock`, `update`, `pull`, `remove`, `select`, `shell`, `self`, `uninstall`, `version`, `ci`, `package`, `patch`, `config`, plus 17 top-level flag sections) at **34,298 prose words in one file** — an average of over 1,100 words per command, and alone longer than the entire docs surface of 12 of the 23 repos measured in this program's grounding wave. It stays under GitLab's H5 cap throughout (its deepest heading is H4, for `add`'s "Binding names" subsection), so the one sourced numeric trigger would not itself have caught this file — the failure mode here is unbounded page length under a fixed heading depth, not heading-depth violation.

Decision for this deliverable: the split trigger is **heading depth**, checked mechanically (no `#####` inside a page whose type is `reference`; GitLab's own reasoning), *plus* a fleet-specific word-count backstop stated honestly as a heuristic, not a citation: a single reference file documenting more than roughly 15–20 enumerable items (commands, endpoints, resource types) should split one file per item, mirroring the code's own item boundaries (finding 2) rather than staying single-file past that count. `command-line.md`'s 30 items is the concrete number this heuristic is calibrated against — it is twice the proposed ceiling.

### 6. Auto-generated reference needs a review layer

Microsoft's guide states the requirement in one sentence, directly after its section table: "If you automatically generate reference documentation and comments from the source code, review the quality and appropriateness of the comments. Developers might leave out details that are important to customers. Remove any implementation or internal details that aren't suitable for documentation." ([Microsoft](https://learn.microsoft.com/en-us/style-guide/developer-content/reference-documentation)). This is the one place in the corpus where autogeneration and hand-authoring guidance visibly disagree on emphasis: hand-authoring guides assume a human writes every word; this is the sole explicit acknowledgment that generated reference needs an editorial pass, not just a build step.

The fleet has both a documented near-miss and an outright failure of this:

- `ocx-sdk-python/docs/reference/api.md` is the near-miss: it opens with "Auto-generated from docstrings via [mkdocstrings](https://mkdocstrings.github.io/python/)," then adds a hand-written **Conventions** section (what counts as public API, docstring style, `Raises:` semantics, links out to a command↔method map) before the generation directive — 109 words of real editorial framing around the generated body (verified by direct read of `ocx-sdk-python/docs/reference/api.md`).
- `ocx-mirror-sdk/docs/api/text.md` is the outright failure: one heading, one directive, nothing else (finding 1). `ocx-mirror-sdk/docs/api/http.md` sits between the two — a four-line intro sentence, then three bare directives with no per-method framing (verified by direct read).

The checkable form of "review pass happened" is a proxy, not a direct test: a script flagging any file under a `type: reference` + generated-directive marker (`::: <module.path>`) whose surrounding hand-written prose is under some minimum word count (`ocx-sdk-python`'s 109-word Conventions section is the found positive baseline; `ocx-mirror-sdk`'s 0-word case is the found negative). It cannot verify the *content* of the review, only that one was attempted.

### 7. Generated anchors break naive link checkers

A link checker that walks the file tree statically cannot see anchors mkdocstrings manufactures at `mkdocs build` time from docstrings. Measured directly: every one of `ocx-sdk-python`'s 65 flagged-dead internal links targets `docs/reference/api.md#ocx_sdk.<Class>.<method>` — anchors that exist only after a build, invisible to a static-file scan; net real dead-link rate fleetwide drops from a nominal 3.8% to ≈1.9% once this is special-cased. This is a link-checker configuration finding, not a reference-page-authoring rule, but it is a direct consequence of choosing generated per-item reference (finding 4/6): the more a reference page is machine-generated, the more its link checker needs a build-time-anchor exemption, or it will manufacture false positives at scale from that one page (docs-shape.md §5, verified against `ocx-sdk-python/docs/reference/api.md` and `command-map.md` directly).

### 8. The fleet already builds the drift gate twice

Two independent implementations of the same shape — a non-executing structural test that reads the reference artifact at test/build time and fails if it drifts from a hand-maintained or code-derived list — already exist in this fleet, and they are the fleet's only two documentation rules with a runnable check behind them at all (of ~92 fleet-wide docs-prose rules):

| | ocx | grimoire |
|---|---|---|
| Reference artifact | `website/src/docs/reference/command-line.md` | `docs/src/clients.md` |
| Test file | `test/tests/test_doc_command_reference.py` (479 lines) | `src/install/client_target.rs` (test module, ~26 `#[test]` fns) |
| What it asserts | Every live command has a `{#anchor}`, a `**Usage**` block, an `**Options**` block; every removed command has a tombstone marker instead | The table's row set equals `ClientTarget::ALL` exactly; every `✓`/`◐`/`✗` cell matches the corresponding `Vendor::kind_support` |
| Read at | pytest collection (file-content check, no subprocess) | Rust test runtime (`std::fs::read_to_string`, not compile time) |
| Scope | Explicitly out of scope for ocx's separate acceptance-tested-command drift gate (`ADR "Locked Tenets" §5`) — this is a second, narrower, complementary gate | The fleet's only docs-table build-time parity test |

The portable shape to ship, generalized from both: **a reference page (or table) that enumerates real code entities gets a structural test asserting (a) the enumerated set matches the code's actual set exactly, and (b) each entry's required sub-sections are present** — not an executable-example test (that mechanism is a different, already-covered pattern — see `tested-examples-mechanism.md` §3, cited by pointer per this program's coverage rules) and not a prose-quality check.

## Normative guidance candidates

1. **A hand-authored reference page must contain, in order: a one-sentence title+description, a syntax/declaration block, a parameters/options table, behavioral remarks, error/exit conditions, and at least one example.** Return value and see-also are present when the element has one. — *Rationale*: this is the fixed set two independent canonical sources (Microsoft's table, the fleet's own uncredited `worker-doc-writer.md` contract) converge on; omitting one silently produces the fleet's own stub pattern (finding 1). — *Verify*: a schema script per reference page that greps for the section markers (`**Usage**`, `**Options**`/parameter table header, an exit-code or error-condition heading) and fails on any missing marker for a page tagged `type: reference` with a runnable/callable surface. — **codified** (Microsoft; independently reinvented once in the fleet).

2. **A reference page's item enumeration must equal the code's real item set exactly, checked by a build- or test-time comparison, not eyeballed.** — *Rationale*: this is the only rule in the fleet's ~92 docs-prose rules with a working, non-coarse check behind it (grimoire's `client_target.rs`, ocx's `test_doc_command_reference.py`); a reference page that silently drops or invents an entity is the single most damaging reference defect and the cheapest to catch mechanically. — *Verify*: a test that reads the reference file/table at run time, derives the code's real entity list (a `--help`/CLI introspection, an enum's `::ALL`, or a parsed OpenAPI operation list), and asserts set equality plus per-entity required-block presence — generalizing `client_target.rs`'s and `test_doc_command_reference.py`'s shape. — **codified** (two independent fleet implementations; zero canonical-guide citation of the mechanism itself, though Diataxis and Microsoft both state the underlying "must mirror the code" requirement).

3. **Reference prose stays purely descriptive: no first-person, no narrative opener, no imperative-mood sentence start outside a fenced Usage/example block.** — *Rationale*: Diataxis names this as reference's defining register; a page that slides into instruction or narrative is the type-mixing failure this whole group exists to catch. — *Verify*: grep a `type: reference`-declared page's prose (code fences and tables excluded) against a banned-opener list ("let's", "now that", "you'll want to") and a first-person-pronoun list ("we", "I", "our"); flag any sentence outside a fenced block whose first word is a bare imperative verb from a small named set (run, add, set, use, try). — **argued** (no off-the-shelf lint targets this specifically; the grep is this program's own construction from Diataxis's stated register).

4. **Reference pages default to one page per enumerable item once the item count exceeds ~15–20, or once any item's section would need heading depth past H4.** — *Rationale*: GitLab's H5 cap is the only sourced numeric split trigger found, and the fleet's own 30-command, 34,298-word single-file page is the empirical case for a count-based backstop the heading-depth rule alone would not have caught. — *Verify*: a heading-level lint on files under a `reference/` path or `type: reference` front matter (no `#####`); a companion script counting top-level item headings per file and warning past 15, failing past 20. — **normative** for the heading-depth half (GitLab states it as a rule); **argued** for the count backstop (this program's own threshold, calibrated against one measured fleet instance, not a cited external number).

5. **When a reference page is single-file (below the split threshold), a small stable item count is the condition, not an author's stylistic preference.** — *Rationale*: both real per-2026 instances found (post-redesign Stripe, Rust's `std`) are per-item; single-page reference at fleet scale (`command-line.md`) is the counterexample the split threshold exists to prevent, not a validated alternative pattern to keep choosing. — *Verify*: same script as candidate 4 — a page passing the item-count/heading-depth check is implicitly "small enough to justify staying single-file"; there is no separate lint for "did the author choose correctly," only the threshold. — **argued** (a design default drawn from two real-world instances converging the same way, not a canonical rule stated as such anywhere).

6. **Auto-generated reference content requires a minimum band of surrounding hand-written prose before it may ship** (what counts as public, conventions, cross-links to the human-authored guide) — a bare generation directive with no framing is a stub, not a finished page. — *Rationale*: Microsoft names the failure mode directly (developers leave internal detail in doc-comments); the fleet has both the near-miss (`ocx-sdk-python/docs/reference/api.md`, 109 words of framing) and the failure (`ocx-mirror-sdk/docs/api/text.md`, 0 words) as calibration points. — *Verify*: a script flagging any file containing a generation directive (`::: <module.path>`, `mkdocstrings` fence, or equivalent) whose word count outside that directive falls under a stated floor (the fleet's own near-miss, 109 words, is a defensible floor). — **codified** (Microsoft states the requirement; the word-count proxy is this program's own operationalization, since Microsoft states no number).

7. **A link checker running against reference content must special-case build-time-generated anchors (mkdocstrings and equivalents) or explicitly run post-build**, never against source files alone. — *Rationale*: measured directly — one repo's mkdocstrings anchors alone produce 65 false "dead" links out of the fleet's 135 total flagged, before the exemption; ship the check un-exempted and it either blocks real merges on phantom failures or gets ignored/disabled by the next agent that hits it. — *Verify*: the link-checker config (lychee `.lycheeignore`/`--exclude`, or run-order: checker executes after `mkdocs build`, against the built site, not the markdown source) explicitly lists or structurally avoids build-time-anchor patterns. — **measured** (docs-shape.md §5, verified independently against `ocx-sdk-python/docs/reference/api.md` and `command-map.md`).

8. **Reference structure is derived from the code's own taxonomy of entities (command list, endpoint list, type list), never regrouped by an author's preferred topic clustering.** — *Rationale*: stated independently by Diataxis ("mirror the structure of the product") and implied by Microsoft's fixed per-element-kind table; violated silently as code drifts if nothing enforces it, which candidate 2's mechanism exists to catch. — *Verify*: same structural-parity test as candidate 2; additionally, a reviewer heuristic — does every top-level reference heading correspond to one real, currently-shippable code entity, with no heading that groups two or more entities under one label? — **normative** (Diataxis and Microsoft both state the principle directly).

## AI-agent angle

- **Reaches for one giant file instead of splitting.** An agent asked to "document the CLI" defaults to appending every new command to the existing reference file — the path of least resistance — reproducing `command-line.md`'s 34,298-word failure mode one command at a time. *Check*: the heading-depth/item-count script from candidate 4, run on every PR touching a `reference/` path, not just periodically.
- **Invents parameters, flags, or fields that don't exist in the actual code.** A reference page is the type most exposed to hallucination because it enumerates exact facts (flag names, defaults, exit codes) an LLM will confidently interpolate if it drafts from memory instead of the source. *Check*: candidate 2's structural-parity test — comparing the doc's enumerated set against a real code-derived list catches an invented entry the same way it catches a missing one.
- **Ships the raw autogeneration directive with no review framing**, because the directive itself looks complete to a model that has no signal a "review pass" is a separate, required step — `ocx-mirror-sdk/docs/api/text.md` is exactly this failure, in production, right now. *Check*: candidate 6's word-count floor around every generation directive.
- **Slides into narrative or instructional tone mid-page**, because most training data blends how-to and reference content under one "docs" umbrella and the model has no signal it switched types — folds a `## Common patterns` or `## Getting started with X` section into what should be pure enumeration. *Check*: candidate 3's grep, plus the type-mixing signature from the sibling `page-type-set-and-declaration` topic (a "we'll build X" opening plus a later conditional imperative in the same file).
- **Folds error conditions into vague prose** ("this may fail if the input is invalid") instead of an exhaustive table, because a table requires enumerating every case and prose lets the model gesture at "an error" without doing that work. *Check*: a grep for an `## Error`/`## Exit codes`/`**Errors**` table-header marker on any reference page whose described operation is callable (has a Usage/Request block) — flag prose-only failure mentions with no adjacent table.
- **Uses inconsistent section order or omits sections between sibling entries in the same file** — command 3 gets an Exit-codes table, command 12 doesn't, because a long single-session authoring pass drifts. *Check*: candidate 1's per-section-marker schema script, run across every top-level entry in a file, not just once per file.
- **Uses an ellipsis (`...`) to omit example content** instead of a real comment (`# ... additional fields omitted`) — a common generative tic when producing a "representative" example. *Check*: grep fenced code blocks in reference pages for a bare `...` or `# ...` with no surrounding word explaining what was cut.

## Contested / evolving

- **Single-page-per-resource vs. one-page-per-item, named as an open conflict in this program's topic map.** Resolved here, not left open: a direct September 2026 fetch shows Stripe's API reference is no longer the "one long page" instance the corpus assumed — `docs.stripe.com/api/charges/create` is a standalone page with its own Request/Response/Parameters, and the resource-level page (`/api/charges`) is now an index of links to per-endpoint pages, not inline content. Rust's `std` was already per-item. Both real 2026 instances now converge on per-item; treat "one giant page" as the failure mode this rule's split threshold (candidate 4) exists to prevent, not a live, still-contested alternative. Trending: toward per-item, driven partly by the same forces pushing markdown-twin/agent-fetchable pages — a per-item page is a smaller, independently-fetchable unit for both a human deep link and an agent's raw-markdown fetch.
- **Whether a word-count split trigger for reference pages is citable at all.** It is not — checked directly against GitLab (the one source with any numeric page-structure rule), Microsoft, and Diataxis; none states one. This deliverable ships a word/item-count backstop labelled **argued**, calibrated against one measured fleet instance, alongside the one **normative** trigger that does exist (GitLab's H5 heading-depth cap). This is not a case of practice disagreeing — it's a case of practice being silent, and the gap has to be filled honestly rather than presented as settled.
- **Whether "review the generated reference" can ever be a real lint versus a permanently manual step.** Microsoft's own wording ("review the quality and appropriateness") is a human-judgment instruction with no operational check attached anywhere in this survey. The word-count-floor proxy shipped here (candidate 6) is this program's own construction, not a citation, and it only catches the *absence* of a review attempt (zero surrounding prose), never whether a review that happened was any good. This gap is not trending toward resolution as of this era — no tool in this survey's corpus scores documentation-comment quality automatically.
