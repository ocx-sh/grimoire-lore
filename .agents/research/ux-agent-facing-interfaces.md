# Agent-facing interfaces

This artifact answers one question: when the caller is an agent, what must a tool, CLI or MCP server provide? An agent picks its next action from the output alone. It has no memory of the tool, it brings habits learned from other CLIs, and it follows prose literally. So the interface has to answer three questions in fields, not prose:

- Did it work?
- If not, which class of failure is it?
- Will an unchanged retry help, and if not, what should change?

Rule IDs are `UX-AGENT-01` to `UX-AGENT-26`. `UX-AGENT-08` is retired. Measurements were taken on 2026-11-27 with ocx 0.6.8 and grim 0.16.0. Every count traces to a command in a sub-artifact, to a command run for the revision (listed under "Revision measurements"), or to a `file:line` re-read for this consolidation. `file:line` paths are relative to `/home/mherwig/dev/ocx-sh/ocx/crates/` (ocx), `/home/mherwig/dev/grimoire-rs/grimoire/` (grim) and `/home/mherwig/dev/grimoire-rs/vscode/` (extension). Catalog paths (`skills/…`) are relative to this repository's root.

## Verdict

1. **Machine output is one flag, and it works in any position.** The canonical selector is `--format json`, because catalog rule CLI-10 already pins `--format` as a family-wide global flag. `--json` is accepted as an alias, because agents write it by habit from gh, npm and [clig.dev](https://clig.dev/). A flag that works only before the subcommand is a defect: `ocx about --json` exits 64, and it is the likeliest first call an agent makes. The 7-CLI position table in machine-output-contracts §1 is the evidence: no two of ocx, grim, gh, docker, npm, cargo and uv agree on flag position.
2. **Every JSON document, success or failure, carries an integer `schema_version`.** This overrules grim's unversioned additive-only policy (`docs/src/content/docs/json-interface.md:13`). Adding the field is itself additive under that policy. Without it, a consumer cannot tell a changed shape from a bad call. For error documents of a binary under Rust CLI-04, the field waits on the CLI-04 revision (owner decision 4).
3. **Every exit in machine mode prints exactly one JSON document on stdout, usage errors included.** grim prints nothing on stdout for exit 64, which is exactly when an agent mistyped and most needs the machine path. ocx already does this (measured, revision measurement R1).
4. **Errors use a required field set, not a third envelope.** The catalog already pins two envelope spellings:
   - Rust CLI-04 pins grim's shape, `{"error":{"code","exit",…}}`.
   - Swift SW-CLI-29 pins ocx's shape, `{"schema_version","command","exit_code","error":{"kind",…}}`.

   The correctable-errors dive proposed a third shape in the style of RFC 9457. This consolidation rejects it. It requires instead a field set that either spelling can carry:
   - a class from a closed vocabulary
   - the exit code
   - `retryable` as a boolean (always present once CLI-04 is revised; see 5)
   - `retry_after_seconds` when the upstream sent one
   - `message`
   - `hint`
5. **`retryable` is authoritative. The exit code is a fallback only for builds that do not send the field.** This settles a disagreement inside the fleet. The grim producer keys retryability on a reason and omits the field unless it is true (`src/error.rs:256-257`, `src/main.rs:328`). The VS Code extension retries on exit 75 even when it reads an explicit `false` (`src/grim.ts:685-686`). Two halves of one product disagree on what "retry" means. "Always present" is SHOULD until Rust CLI-04 changes `retryable?` from optional to required (owner decision 4). A producer that always sends the field already conforms to CLI-04 today, because an optional field may always be present.
6. **"Retryable" means an unchanged rerun can succeed. The same cause maps to the same class in every binary of the family.** This is SHOULD, not MUST, until the owner reconciles the catalog's exit-69 wording (owner decision 3).
   - Retryable: a transport failure that may clear (connection refused or reset, timeout), lock contention, 408, 429, and 5xx except 501. The HTTP part is catalog GO-NET-11's pinned retry set.
   - Not retryable, because input or config must change first: a TLS-to-plain-HTTP mismatch, a DNS name that does not exist, a refused certificate, 501, and every other 4xx.

   Today ocx and grim are wrong in opposite directions. grim sends 429 and 503 to exit 69. ocx sends the TLS mismatch to exit 75.
7. **An MCP server reports every failure the model can act on as an `isError: true` result, argument failures included.** JSON-RPC errors are only for an unknown tool, a request that fails the `CallToolRequest` schema, and a genuine server fault. This overrules E8 in the correctable-errors dive, which put inputSchema violations on the protocol channel. The reason is in the spec text, fetched for this revision (quoted under C1). The same lists and the same open `arguments` type are in revision 2025-11-25, so the verdict holds for clients on either revision (followup-q3). The [MCP tools spec, revision 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) defines "Malformed requests" as "requests that fail to satisfy CallToolRequest schema". In that revision's [schema](https://modelcontextprotocol.io/specification/2026-07-28/schema), `CallToolRequestParams.arguments` is typed `{ [key: string]: unknown }`, so a missing or wrong-typed argument still satisfies the `CallToolRequest` schema. The spec instead lists "Input validation errors" as tool execution errors. Clients SHOULD pass tool execution errors to the model and MAY drop protocol errors. grim's `tool_error` maps every operational failure to `-32603` (`src/mcp/server.rs:198-199`). That is the largest single defect measured. Source reads of three non-Claude clients (followup-q0, 2026-11-27) show that Codex CLI, Copilot in VS Code and Gemini CLI all pass both channels to the model. So the case for `isError` is not that clients drop protocol errors. It is that clients rewrite them: Copilot appends "Please check your input and try again." to every thrown error, server faults included.
8. **Tool descriptions are judged on content, not length.** A description should state its purpose, when to use it, a pointer to the sibling tool where tools overlap, what it returns and its limits. Nothing breaks when an item is missing, so the rule is SHOULD (UX-AGENT-19). It has no minimum sentence count. This overrules the "at least 3 to 4 sentences" floor in the [Claude API docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) (undated page, fetched 2026-11-27). The evidence is an independent preprint, [arXiv 2602.14878](https://arxiv.org/abs/2602.14878). Its abstract, which is the v3 abstract (v3 dated 2026-05-31) and was re-read on 2026-11-27, reports 97.1% of tools with a smell, 56% with an unclear purpose, a median +5.85 points from augmentation, +67.46% execution steps, and regression in 16.67% of cases. The per-component failure rates (usage guidance 89.3%, limitations 89.8%) and the finding that compact descriptions were statistically equivalent come from the [v1 full text](https://arxiv.org/html/2602.14878v1) (2026-02-16). The v3 full text was not read. The 2,048-character cap is a compatibility margin for Claude Code installs older than v2.1.296. It is not a current platform limit.
9. **A gated-off tool stays absent from `tools/list`, and the gate is named in a tool that is always registered.** This overrules E12 in the correctable-errors dive, which asked for a "disabled" result instead. Absence is what the spec describes, and it keeps the attack surface small. grim already does this: `grim_status`'s description states the write gate, pinned by a test at `src/mcp/server.rs:266`.
10. **A hint never leads with a destructive or policy-relaxing remedy, and a conflict is its own class.** grim's `rerun with --force to move it` on a tag conflict (`src/oci/release.rs:96`, exit 65 `data`) turns a refusal into an overwrite for any agent that follows hints literally.
11. **The caller side is part of the contract, at SHOULD.** An agent that calls a tool should:
    - keep stdout and stderr apart
    - branch on class, exit code and `retryable`, never on message text
    - retry at most 3 times
    - read `truncated` before it concludes anything

    UX-AGENT-25 binds this. It stays SHOULD until a transcript or skill audit measures how often callers get it wrong.

### Documented gaps

- **No source shows that a fixed error-text prefix changes agent behaviour.** UX-AGENT-16's prefix is a convention for consistency, held at SHOULD. One source read supports "the text must say it failed": Copilot in VS Code writes `isError` only into UI `details` and gives the model no failure marker ([mcpLanguageModelToolContribution.ts#L280](https://github.com/microsoft/vscode/blob/f39e18fe98e794bccc2de9ed95e898b4406b6301/src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts#L280), commit 2026-11-27, followup-q0). That is code, not a measurement of model behaviour (Open question 6).
- **Size and truncation numbers come from four clients, read in two ways, and none was run.** Claude Code is vendor documentation. Codex CLI, Copilot in VS Code and Gemini CLI are source reads at the commits named in followup-q0. Not determined, each needing what this program may not use:
  - Cursor, entirely. Its client is closed source and its [MCP docs](https://cursor.com/docs/mcp) (undated, fetched 2026-11-27) describe only the UI ("The tool call is marked as failed"). Settling it needs a logged-in Cursor install with a probe server.
  - Copilot's absolute cap. It is 50% of `modelMaxPromptTokens`, so it depends on the model, and how `TokenLimit` in `@vscode/prompt-tsx` cuts (head, tail or middle) was not read.
  - Whether Gemini CLI's `isError` wrapper reaches its 40,000-character cut (`tool-executor.ts:541`) was not traced.
  - No client was run against a live probe server, so a build that differs from the cloned commit may behave differently.
- **The MCP spec never says in words that an `inputSchema` violation is a tool execution error.** UX-AGENT-15's argument clause rests on a reading of three texts, measured identical in revisions 2025-11-25 and 2026-07-28 (followup-q3). No client was observed handling a `-32602` for a bad argument.
- **No provider rejection of a top-level combinator has been reproduced.** OpenAI documents "the root level object of a schema must be an object, and not use `anyOf`" for Structured Outputs, but no page states it for strict function parameters, and the openai Python SDK 2.0.0 accepts a root `anyOf` client-side (followup-q4). A live API call needs an OpenAI API key that this program may not use. UX-AGENT-20's combinator clause stays SHOULD until an API key owner runs the one-call recipe in followup-q4.
- **No caller-side corpus has been measured.** UX-AGENT-25's greps are locators without a false-positive rate.

## The ruleset

Severity: MUST means it breaks callers or violates a normative source. SHOULD means a measured gap against a cited source. CONSIDER means the evidence is mixed. Where one clause of a rule carries a lower severity than the rest, the rule names that clause and its severity. Placeholders: `<cli>` is the binary, `<sub>` is a subcommand, and `tools.json` is the `tools` array of a `tools/list` result (capture recipe: block R3).

These rules do not restate rules the catalog already pins:

- CLI-01 and CLI-02: stdout carries only the result, and only the payload under `--format json`.
- EXIT-01 to EXIT-11: the exit-code table and its append-only rule.
- CLI-07: colour.
- GO-NET-11: which HTTP statuses an HTTP client retries internally.
- `ai-config-authoring` `references/descriptions.md`: description craft for skills.
- UX-ACT-16: what a repeated mutating command returns.

## What an agent must ask a human

- Whether to break a published JSON schema (bump `schema_version`), and how long the deprecation window is. MCP's own minimum of twelve months applies to the spec, not to your tool ([MCP changelog, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- Renaming or removing a published tool name, JSON field or error slug (UX-AGENT-24). Propose the alias. Do not just do it.
- Overwriting or moving a published tag or artifact after a `conflict` (`--force`).
- Entering, rotating or choosing a credential after an auth error, or switching registry or account.
- Dropping `--offline`, `--frozen` or `--locked`, or any other policy flag, after exit 81.
- Enabling write tools (`--allow-writes`) on an MCP server. grim's help calls this "a trust decision of whoever wires the server into a harness, never of the model calling the tools".
- Turning on plain-HTTP registry access (`insecure = true`, `OCX_INSECURE_REGISTRIES`) in a shared or committed config.
- Which operations belong in the default-registered tool set, and whether a write tool exists at all.
- Adding a registry, host or path override parameter to a tool. grim omits one on purpose (SSRF, CWE-918).
- Raising `_meta["anthropic/maxResultSizeChars"]` or `MAX_MCP_OUTPUT_TOKENS`, or picking a default row limit that hides data from existing scripts.
- How much internal detail an error may disclose (hosts, tenant ids, versions).
- A description sentence that makes a legal, security or pricing claim ("no data leaves your machine"), or that promises behaviour the code does not yet guarantee.
- Retrying a mutating call after a timeout when idempotency is not documented.

## Open questions

**Subareas that deserve another round, as questions** (labels are stable; Q2, on non-Claude clients, was answered in part by followup-q0, and what it left open is under Documented gaps):

- **Q1.** When a tool retries internally (grim's MCP path turned a 429 into `deadline has elapsed`) and the agent also retries, how large should the tool's own retry budget be, and must the tool report that it already retried (`attempts`)? Read the grim retry layer and measure it against the 429 stub.
- **Q3.** Does a fixed-task regression tripwire catch description regressions? For grim this is 5 tasks, plus 2 for the describe/fetch pair, each run 3 times. What does one run cost? The dive computed that a significance claim would need about 900 tasks per arm, so a tripwire is the only affordable form.
- **Q4.** MCP 2026-07-28 adds `InputRequiredResult` (elicitation through multi-round-trip requests). When should a tool ask for input instead of failing with `isError: true`, and how does that interact with "ask a human" (UX-ACT)?
- **Q5.** Is an agent's first-call success on an unfamiliar CLI driven more by `--help` structure (examples, a stated flag position) than by error hints? This overlaps with UX-CLI, which should own the measurement.
- **Q6.** Does a class-and-verdict prefix on MCP error text (UX-AGENT-16) change what a model does next, compared with the same text without it? A small paired probe on the R4 conditions would settle whether the prefix earns a MUST.
- **Q7.** How often do catalog skills and recorded transcripts mix streams, parse messages or retry without a cap (UX-AGENT-25)? Run the locator greps over the catalog skills and a sample of transcripts, and hand-check the hits for a false-positive rate.

**Owner decisions:**

1. Converge ocx and grim on one envelope spelling, or keep both and add the missing fields? Recommendation: keep both spellings and add `schema_version`, an always-present `retryable`, `hint` and the missing classes, because the extension already parses grim's shape.
2. Should `conflict` get its own exit code (the next free one is 83, under append-only EXIT-06), or stay on 65 with a distinct class slug?
3. Reconcile the catalog's connection-failure mapping. The Rust table says 69 means "unreachable, non-retryable", the Go table says 69 is "not retryable", and Swift says a connect failure is 75. This artifact recommends refused or reset means 75, and DNS or TLS failures mean 69 (C8). UX-AGENT-10 stays SHOULD until this is decided.

5. Should grim add `--json` as an alias of `--format json` (UX-AGENT-02)?
6. Is a release-time tool-selection eval wanted, and at what budget?
