## Summary

- `context.Context` is the first parameter of every function on a call path that can block, cancel, time out, or carry request-scoped data, named `ctx`; the sole normative exceptions are `main`/`init` (`context.Background()`), a `testing.TB` (`t.Context()`), an HTTP handler (`req.Context()`), and a gRPC/streaming method whose stream exposes its own `Context()`.
- A callee that has `ctx` on its call path and instead calls `context.Background()`/`context.TODO()` breaks the chain one level down; `contextcheck` (kkHAIKE) catches this at real production call sites, not just in theory — verified true positive at `cli/cli@9b031151a825:internal/codespaces/rpc/invoker.go:77,91`.
- `context.Context` must not be a struct field; pass it to every method that needs it. The one normative exception is retrofitting context support into a pre-existing interface you do not control (the `net/http.Request` precedent: an internal field plus a `WithContext`/`NewRequestWithContext` constructor, never a field applications read or write directly).
- `containedctx` (sivchari) flags any `context.Context` struct field with no exceptions of its own — a repository that takes the `net/http.Request` retrofit route still trips it and needs a documented `//nolint:containedctx` at that one declaration, not a blanket disable.
- Every `cancel` returned by `WithCancel`/`WithTimeout`/`WithDeadline`/`WithCancelCause`/`WithTimeoutCause`/`WithDeadlineCause` must be called on every path out of the function that created it, normally by `defer cancel()` on the next line — `go vet`'s `lostcancel` analyzer catches both the "never called" and the "not called on this return path" shapes, confirmed on a planted early-return fixture.
- `lostcancel` and the `contextcheck`/`containedctx`/`noctx`/`fatcontext` linters run only under `go vet` or `golangci-lint`, never under `go test`'s built-in 11-analyzer vet subset — a repository whose gate is `go test ./...` alone never sees any of them.
- `context.WithTimeout`/`WithDeadline` lose the *reason* for the deadline: `context.Cause(ctx)` after expiry is always exactly `context.DeadlineExceeded`, with no linter or vet check flagging the loss — confirmed on a planted fixture where the golangci-lint 2.14.0 gate (`govet`, `staticcheck`, `contextcheck`, `containedctx`, `noctx`, `fatcontext`) fired 0 issues on the cause-losing `WithTimeout` code.
- Use `context.WithTimeoutCause`/`WithDeadlineCause` (Go 1.21) whenever the expiring timeout is one of several possible causes reaching the same call site (a CLI's own `--timeout` flag vs. a caller's ambient deadline vs. a server-imposed one) — `context.Cause(ctx)` then reports the *right* one instead of the generic sentinel.
- `signal.NotifyContext` (`os/signal`, 1.16) has cancelled with a `context.CancelCauseFunc` and a signal-naming cause **since Go 1.26** — a CLI on `go 1.26`+ gets "why did we exit" almost for free via `context.Cause(ctx)`; a CLI still declaring `go 1.25` or lower does not have this and must synthesize its own cause.
- `context.WithoutCancel` (1.21) detaches a derived context from its parent's cancellation while keeping its values — the correct tool for work that must outlive the request that started it (a background cleanup, an async audit log write); it must never be reached for by a function that also wants the parent's deadline, since it strips that too.
- `context.AfterFunc` (1.21) runs a function in its own goroutine when `ctx` is done, without a `select`/`Done()` channel loop; its `stop` return must be called once the caller no longer needs the callback, or the goroutine that would run it stays registered.
- `context.WithValue` keys must be an unexported, comparable type the calling package defines (`type ctxKey struct{}` or a named type over `int`), never a bare `string` or other built-in — `staticcheck` `SA1029` fires on a literal string key, confirmed on a planted fixture, and is enabled by default whenever `staticcheck` runs (no extra config).
- `context.Value` is for request-scoped data that crosses an API boundary the caller does not own (a trace ID, a deadline-setting middleware's derived value) — never as a substitute for an explicit parameter a function's own signature should carry.
- Reassigning `ctx = context.WithValue(ctx, k, v)` to the same variable inside a loop chains a new context node onto the previous one every iteration, turning a short-lived value lookup into an O(n) linked list walk; `fatcontext` (Crocmagnon) catches this, confirmed on a planted fixture, and the fix is a loop-scoped `ctx := ...` (or building each derived context outside the reassignment chain).
- `os/exec.Command` and `net/http.NewRequest`/`Get`/`Post`/`Head` (and their `*http.Client` method equivalents) must be the `*Context`-taking variant (`exec.CommandContext`, `http.NewRequestWithContext`) — `noctx` (sonatard) fires on both **and does cover `os/exec` at golangci-lint 2.14.0**, confirmed on a planted fixture and live at 21 real call sites across the three measured exemplars (map row M-G-08 resolved: yes).
- `staticcheck` `SA1012` ("do not pass a nil Context ... pass context.TODO if you are unsure") fires when `nil` is passed directly to a parameter typed `context.Context`, confirmed on a planted fixture; it did **not** fire when the `nil` was passed through an intermediate `func(context.Context) error` value in the same test — treat `SA1012` as catching the direct-literal shape only, not every nil-context path.
- `contextcheck` false-positives on the deliberate "functional-option overrides the context" idiom (`google/go-containerregistry@0c8bedb78437:pkg/v1/remote/catalog.go:75`, where an `Option` can replace the parameter `ctx` with `o.context`) — a reviewer reads the flag, confirms the override is intentional and documented, and suppresses it locally rather than treating every hit as a defect.

## Findings

### 1. Where context comes from and how far it must flow (M-C-15)

The `context` package doc is unambiguous about placement and flow: *"The Context should be the first parameter, typically named ctx"* in every function signature that needs one ([pkg.go.dev/context](https://pkg.go.dev/context)). The Go blog's original context post frames this as an org-wide convention, not a suggestion: *"Go programmers pass a Context parameter as the first argument to every function on the call path between incoming and outgoing requests"* ([go.dev/blog/context](https://go.dev/blog/context)). Google's style guide names the same four exceptions the summary lists — HTTP handlers via `req.Context()`, streaming RPC via the stream's own `Context()`, test functions via `(testing.TB).Context()`, and entrypoints (`main`, `init`) via `context.Background()` ([google.github.io/styleguide/go/decisions#contexts](https://google.github.io/styleguide/go/decisions.html)).

"Flowing through" means every blocking call downstream receives the *same* (or a `WithXxx`-derived) context, not a fresh one. The exemplar corpus measured this breaking down at scale: 964 `context.Background()` calls and 275 `context.TODO()` calls outside `package main`, over 2,662,258 LOC across the repos where these are non-zero — a corpus-wide rate of 3.621 `Background()` and 1.033 `TODO()` per 10k LOC ([exemplar-runtime-posture.md §2](../go-audit/exemplar-runtime-posture.md)). Not every one of these is a defect — an entrypoint deep in a `cmd/` tree, a background daemon loop with no natural parent request, or a genuinely disconnected subsystem can legitimately start fresh — but each one is a candidate the reviewer must classify, and `contextcheck` is the tool that finds the subset where a `ctx` was *already on the call path* and got discarded.

A verified true positive: `cli/cli@9b031151a825:internal/codespaces/rpc/invoker.go:77` defines `func connect(ctx context.Context, fwd portforwarder.PortForwarder) (Invoker, error)` and, inside the body at `invoker.go:91`, creates its background-task-cancelling context as `connectctx, cancel := context.WithCancel(context.Background())` instead of `context.WithCancel(ctx)` — the caller's cancellation can never reach the goroutines this spawns (the port-forward and gRPC-dial goroutines keyed off a context descended from `connectctx`, not `ctx`). `golangci-lint` with `contextcheck` enabled flags exactly this line: `Non-inherited new context, use function like 'context.WithXXX' instead`.

### 2. Storing context in a struct field (M-C-16)

The dedicated Go blog post on the subject states the rule and its scope directly: *"Contexts should not be stored inside a struct type, but instead passed to each function that needs it"* ([go.dev/blog/context-and-structs](https://go.dev/blog/context-and-structs)). The reasoning is about caller control: passing `ctx` as an argument lets each call set its own deadline and cancellation and lets a reader see exactly which invocation a context governs; a stored field hides that scope and invites reuse of a stale or overly-broad context across unrelated calls.

The one normative exception is *retrofitting* context support into an API surface that predates `context.Context` (introduced Go 1.7) or that must satisfy an interface outside your control. The blog's own worked example is `net/http.Request`: it holds an internal `ctx` field, but the exported surface is `req.Context()` (read) and `req.WithContext(ctx)`/`http.NewRequestWithContext` (derive a new `*Request`), never direct field access — and the post's suggested alternative, tried first, is a plain method-doubling shim:

```go
// Uses context.Background() internally — legacy signature kept.
func (c *Client) Call() error {
    return c.CallContext(context.Background())
}

// The real, context-aware entrypoint.
func (c *Client) CallContext(ctx context.Context) error {
    // ...
}
```

Google's style guide draws the same line even more narrowly: *"Do not add a context member to a struct type. Instead, add a context parameter to each method on the type that needs to pass it along,"* with the sole exception being *"matching interfaces outside of Google's control — extremely rare situations requiring prior discussion"* ([google.github.io/styleguide/go/decisions#contexts](https://google.github.io/styleguide/go/decisions.html)).

Measured: 219 `context.Context` struct fields across the interface-and-shape sample, 249 by the runtime-posture audit's broader scan, present in 15/34 repos ([exemplar-code-shape.md §6](../go-audit/exemplar-code-shape.md), [exemplar-runtime-posture.md §2](../go-audit/exemplar-runtime-posture.md)). A spot-read of 6/6 hits in `etcd-io/etcd` found all genuine — not the retrofit exception, just the anti-pattern shipped anyway:

```go
// etcd-io/etcd@7583cc6e7e27:client/v3/concurrency/session.go:120
type Session struct {
    client *v3.Client
    opts   *sessionOptions
    id     v3.LeaseID
    cancel context.CancelFunc
    donec  <-chan struct{}
}
```

(the `donec`/`cancel` pair is the session's own lifecycle context, stored because the session's *entire purpose* is to outlive any one call — see the WithoutCancel discussion in §4 for why this specific shape is closer to legitimate than the median hit). The finding for a reviewer is narrower than "any ctx field": is this struct a request/operation object whose exported surface already hides the field behind accessor methods (the retrofit exception, documented), or is it a plain data struct that a method could take `ctx` on directly (the anti-pattern, `etcd`'s own `client/v3/concurrency/session.go` reads as the latter — `Session` has ordinary methods like `Close()` that could accept a `ctx context.Context` parameter instead of reaching into `s.ctx`).

### 3. Cancel discipline (M-C-17)

The `lostcancel` analyzer (part of `go vet`'s default set) states its own scope precisely: *"The cancellation function returned by context.WithCancel, WithTimeout, WithDeadline and variants such as WithCancelCause must be called, or the new context will remain live until its parent context is cancelled"* ([pkg.go.dev/golang.org/x/tools/.../lostcancel](https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/lostcancel)). It runs both the "never called on any path" check and a control-flow-sensitive "not called on *this* path" check — confirmed directly (§Verification runs, fixture c).

Measured: 268 `WithCancel`/`WithTimeout`/`WithDeadline` call sites where a `defer <cancelvar>(...)` does not appear within the next 12 lines ([exemplar-runtime-posture.md §2](../go-audit/exemplar-runtime-posture.md)). This is a triage list, not a defect count: the audit's own spot-read found `etcd-io/etcd@7583cc6e7e27:server/proxy/grpcproxy/watch_broadcast.go:46` storing `cancel` in a struct field (`wb.cancel = cancel`) for explicit later invocation — legitimate lifecycle management, not a leak, and outside `lostcancel`'s detection surface entirely (the analyzer only tracks whether `cancel` is *called* somewhere reachable, not whether every path reaches that call promptly). The rule for a reviewer: `defer cancel()` on the line immediately after the `WithXxx` call is the default and needs no justification; a stored `cancel` needs a one-line comment naming who calls it and when, because nothing mechanical verifies that promise.

The Go 1.13 errors blog and the context docs converge on the reason cancellation must reach every path: a `cancel` never called (on any exit) leaks the context's internal goroutine and any timer it holds until the *parent* is cancelled — which, for a context derived from `context.Background()`, is never.

### 4. Cancellation cause (M-C-18)

The plain `WithCancel`/`WithTimeout`/`WithDeadline` family cancels with exactly one of two sentinels: `context.Canceled` or `context.DeadlineExceeded`. `context.Cause(ctx)` ([pkg.go.dev/context#Cause](https://pkg.go.dev/context), added Go 1.20) *"returns a non-nil error explaining why c was canceled — the first cancellation of c or one of its parents sets the cause"* — but for the plain family, that cause is always one of the same two sentinels; there is no richer information to return. `WithCancelCause` (1.20), `WithTimeoutCause`, and `WithDeadlineCause` (1.21) let the caller attach a real error instead: *"Calling cancel with a non-nil error (the 'cause') records that error in ctx; it can then be retrieved using Cause(ctx)"* ([pkg.go.dev/context](https://pkg.go.dev/context)).

Confirmed on a planted fixture (§Verification runs, fixture d): `context.Cause(ctx)` after a plain `WithTimeout` expiry is indistinguishable from `context.Cause(ctx)` after any other `WithTimeout` expiry anywhere in the program — both are exactly `context.DeadlineExceeded` — and **no analyzer in the golangci-lint 2.14.0 set used here (`govet`, `staticcheck`, `contextcheck`, `containedctx`, `noctx`, `fatcontext`) flags this loss**; it is a reading-heuristic-only finding ("does this deadline's cause matter to the caller, and if so is it `WithTimeoutCause`").

Measured adoption of the whole cause-carrying family (`WithoutCancel` + `AfterFunc` + `WithCancelCause` + `Cause`) is 82 combined hits corpus-wide, concentrated in `tailscale/tailscale` (23 of 82) and `golang/tools` (26 of 82); 25/34 repos show zero across all four ([exemplar-runtime-posture.md §2](../go-audit/exemplar-runtime-posture.md)) — this is minority practice today, not yet the default, even though it is normatively better. A concrete real adoption: `caddyserver/caddy@54937914234b:listeners.go:567` — `ctx, cancel := context.WithCancelCause(context.Background())`.

**When a cause is required, not merely nice:** a CLI's exit path on a signal, and an SDK's timeout error. For the CLI case, `signal.NotifyContext` (`os/signal`, added 1.16) changed its own cancellation mechanism in **Go 1.26**: *"NotifyContext now cancels the returned context with context.CancelCauseFunc and an error indicating which signal was received"* ([go.dev/doc/go1.26](https://go.dev/doc/go1.26)) — this is a breaking behavioral change to an existing function's cancellation shape, not a new function; a CLI whose `go` line is 1.26+ gets a signal-naming `context.Cause(ctx)` without writing any cause-plumbing of its own, but a CLI still on `go 1.25` or lower does not have this and must roll its own (e.g. `signal.Notify` into a channel plus a manual `WithCancelCause`). For the SDK case, an ambient `WithTimeout` deadline and a caller-set `--timeout` deadline both collapse to the same `context.DeadlineExceeded` unless the SDK uses `WithTimeoutCause` at the point it applies its *own* timeout, so its error path can say "the SDK's own 30s budget expired" rather than "a deadline expired, somewhere."

**`WithoutCancel` and `AfterFunc`:** `WithoutCancel` (1.21) *"returns a derived context that points to the parent context and is not canceled when parent is canceled"* — it also does not inherit the parent's deadline or values-derived-from-cancellation, only the value chain. The correct use is background work that must survive the request that triggered it: an audit log write, a cleanup, a metric flush. `tailscale/tailscale@6b3a45f14ef6:control/controlhttp/controlhttpserver/controlhttpserver.go:164` uses it exactly this way, detaching a long-lived websocket connection's context from the request handler's own: `context.WithoutCancel(ctx)`. It must never be reached for merely to "make an error about cancellation go away" — that is a correctness bug hiding behind a real API. `AfterFunc` (1.21) *"arranges to call f in its own goroutine after ctx is canceled"* — it replaces a `select { case <-ctx.Done(): ... }` goroutine-and-channel pattern with a single registration whose `stop` return must be called once the callback is no longer wanted, per the doc's own resource-management note. `tailscale/tailscale@6b3a45f14ef6:tstest/natlab/vnet/vnet.go:443,469,480` uses it to force a connection deadline the instant a shutdown context fires: `context.AfterFunc(n.s.shutdownCtx, func() { tc.SetDeadline(time.Now()) })`.

### 5. context.Value policy (M-C-19)

`context.WithValue`'s own doc gives the policy directly: *"Use context Values only for request-scoped data that transits processes and APIs, not for passing optional parameters to functions"* and warns that key types should avoid built-ins *"to prevent package collisions"* ([pkg.go.dev/context](https://pkg.go.dev/context)). `staticcheck`'s `SA1029` states the mechanical form of that second half: *"The provided key must be comparable and should not be of type string or any other built-in type to avoid collisions between packages using context"* — confirmed firing by default whenever `staticcheck` is enabled (no extra flag), on a planted fixture (§Verification runs, fixture e).

Even the practice's own defenders are unresolved on the *first* half. Merovius's critique of `context.Value` frames the core problem precisely: it is *"often criticized for not being explicit enough about the dependencies a function has"* because the compiler cannot verify a required value exists before a call — his own proposed fix (generic type-parameterized context wrappers) he calls *"pretty infectious"* across a codebase and is explicitly unsure the type-safety gain is worth the machinery ([blog.merovius.de/posts/2020-07-20-parametric-context](https://blog.merovius.de/posts/2020-07-20-parametric-context/)). No linter enforces the "request-scoped, not a disguised parameter" half of the policy — it is a reading heuristic: if removing a `context.Value` lookup and adding an explicit parameter would change every caller's signature in an obviously-correct way, the value should have been a parameter.

## Normative guidance candidates

1. **A function on a call path that can block, time out, be cancelled, or needs request-scoped data takes `context.Context` as its first parameter, named `ctx`.** *Rationale:* this is the mechanism the whole cancellation and deadline system depends on; a parameter one layer down that lacks it cannot receive a caller's cancellation. *Verify:* `contextcheck` under golangci-lint (`enable: [contextcheck]`), which flags a callee that discards an available `ctx` for a fresh `context.Background()`/`TODO()`. *Run:* **yes** — fixture `a-restart/`, red on `bad/`, green on `good/`.

2. **A callee never restarts the chain with `context.Background()`/`context.TODO()` when a `ctx` is already available on the call path.** *Rationale:* this is the exact production defect class in finding 1 — the caller's cancellation and deadline silently stop propagating one function down. *Verify:* `contextcheck` (same config as rule 1) plus the reading heuristic "does this function's parameter list already have a `ctx` that a `context.Background()`/`TODO()` call three lines later ignores." *Run:* **yes**, and additionally reproduced live: `contextcheck` fired a true positive at `cli/cli@9b031151a825:internal/codespaces/rpc/invoker.go:91` in the unmodified exemplar.

3. **`context.Context` is never a struct field, except when retrofitting context support onto an interface you do not own — and that exception is documented at the declaration with a `//nolint:containedctx` naming the interface.** *Rationale:* a stored context hides its own scope and invites reuse across unrelated calls; the retrofit exception exists because you cannot add a parameter to a method signature an external interface fixes. *Verify:* `containedctx` under golangci-lint (`enable: [containedctx]`) flags every hit including the documented exception, so the check is "every hit either has no nearby suppress-comment (finding) or has one naming the owned interface (accepted)." *Run:* **yes** — fixture `b-structfield/`, red on `bad/`, green on `good/`.

4. **Every `cancel` returned by `WithCancel`/`WithTimeout`/`WithDeadline`/`*Cause` variants is called on every exit path from the function that created it — by an immediate `defer cancel()` unless the function documents who else calls it and when.** *Rationale:* an uncalled `cancel` leaks the derived context's internal goroutine and timer until the parent is cancelled, which for a `Background()`-rooted context is never. *Verify:* `go vet`'s `lostcancel` analyzer (`go vet ./...` or `golangci-lint` with `enable: [govet]`), which is control-flow-sensitive and catches partial coverage, not just "never called." *Run:* **yes** — fixture `c-cancelskip/`, red on `bad/` (2 issues: never-called-on-this-path plus the general lostcancel finding), green on `good/`.

5. **A `WithTimeout`/`WithDeadline` whose expiry cause matters to the caller (a CLI's own `--timeout` flag, an SDK's internal retry budget, any site with more than one possible timeout source reaching the same code) uses `WithTimeoutCause`/`WithDeadlineCause` instead, so `context.Cause(ctx)` reports which deadline actually fired.** *Rationale:* the plain family collapses every timeout everywhere in the program to the single sentinel `context.DeadlineExceeded`; nothing distinguishes "the SDK's own budget" from "the caller's ambient deadline" without this. *Verify:* no analyzer catches the omission — reading heuristic only: at a `WithTimeout`/`WithDeadline` call site, ask "if this fires, does the caller need to know it was *this* deadline and not some other." *Run:* **no, reading heuristic only** — confirmed by running the full check set (`govet`, `staticcheck`, `contextcheck`, `containedctx`, `noctx`, `fatcontext`) against the cause-losing fixture and observing 0 issues (fixture `d-timeoutcause/bad/`).

6. **A Go CLI whose `go` line is 1.26 or higher relies on `signal.NotifyContext`'s built-in cancellation cause for its signal-driven exit path; a CLI on `go 1.25` or lower synthesizes its own cause via `signal.Notify` + `context.WithCancelCause`.** *Rationale:* `NotifyContext` began cancelling with `context.CancelCauseFunc` and a signal-naming error in Go 1.26 ([go.dev/doc/go1.26](https://go.dev/doc/go1.26)) — below that floor the feature does not exist and a CLI that assumes it will silently get the generic `context.Canceled` instead. *Verify:* reading heuristic gated on the module's `go` line — `grep -n '^go ' go.mod` to read the floor, then check whether the signal-handling code path reads `context.Cause(ctx)` (expects it) or only `ctx.Err()` (does not depend on it). *Run:* **no, reading heuristic only** — the release-note wording is normative and version-gated; there is no fixture-appropriate way to "watch this go red" since it is a version-detection check, not a code-pattern check.

7. **`os/exec.Command` and `net/http.NewRequest`/`Get`/`Post`/`Head`/`PostForm` (and the `*http.Client` method equivalents) are never used; their `Context`-taking variants (`exec.CommandContext`, `http.NewRequestWithContext`) are.** *Rationale:* the non-context variants cannot be cancelled or given a deadline once started — a hung subprocess or a stalled HTTP call then blocks its caller with no way out. *Verify:* `noctx` under golangci-lint (`enable: [noctx]`) — **confirmed to cover `os/exec.Command` at golangci-lint 2.14.0** (resolves map row M-G-08: yes), plus a grep fallback for a repo not running golangci-lint: `grep -rn -e 'exec\.Command(' -e 'http\.NewRequest(' -e 'http\.Get(' -e 'http\.Post(' -e 'http\.Head(' --include='*.go' . | xargs -r echo` (empty output = pass; exclude `_test.go` files first if test helper calls are accepted, per the noctx README's own scope). *Run:* **yes** — fixture `g-exectx/`, red on `bad/` (2 issues), green on `good/`; additionally reproduced live at 21 real call sites (`os/exec.Command`: 6; `net/http.NewRequest`/`.Get`/`Post`: 15) across `etcd-io/etcd@7583cc6e7e27`, `cli/cli@9b031151a825`, `google/go-containerregistry@0c8bedb78437` (see §Exemplar evidence).

8. **`context.WithValue` keys are an unexported type the calling package defines, never a `string` or other built-in.** *Rationale:* a string key can collide with an identical string used as a key by an unrelated package sharing the same context chain, silently overwriting or misreading a value. *Verify:* `staticcheck` `SA1029`, enabled by default whenever `staticcheck` runs (`golangci-lint` `enable: [staticcheck]`, or standalone `staticcheck ./...`) — no extra config needed. *Run:* **yes** — fixture `e-stringkey/`, red on `bad/`, green on `good/`.

9. **`context.Value` carries only request-scoped data that crosses an API or process boundary the caller does not own (a trace ID, a deadline hint from a middleware); it never substitutes for a parameter a function's own signature should carry.** *Rationale:* the package doc's own boundary ("not for passing optional parameters to functions") plus Merovius's observation that the compiler cannot verify a `context.Value` dependency exists before the call, unlike a parameter. *Verify:* no linter enforces this half of the policy — reading heuristic: "would adding this as an explicit parameter change every caller's signature in an obviously-correct way? If yes, it should be a parameter, not a Value." *Run:* **no, reading heuristic only.**

10. **`context.WithValue` (or any `WithXxx`) is never reassigned to the same loop variable across iterations (`ctx = context.WithValue(ctx, ...)` inside a `for`); each iteration derives its own locally-scoped context from the loop's original parent.** *Rationale:* reassignment chains a new context node onto the previous one every pass, turning what should be a constant-depth value lookup into an O(n) linked-list walk that grows for the life of the loop. *Verify:* `fatcontext` under golangci-lint (`enable: [fatcontext]`). *Run:* **yes** — fixture `f-valueloop/`, red on `bad/`, green on `good/`.

11. **A `nil` literal is never passed where a parameter is typed `context.Context`; `context.TODO()` stands in when no context is available yet.** *Rationale:* every context-consuming stdlib and idiomatic API assumes a non-nil context and will panic or misbehave on `nil`; `context.TODO()` documents "not yet wired up" without that risk. *Verify:* `staticcheck` `SA1012`, enabled by default whenever `staticcheck` runs — **but confirmed to catch only the direct-literal shape** (`Do(nil)` where `Do(ctx context.Context)`), not `nil` passed through an intermediate `func(context.Context) error` value (fixture h/v1, revised to the direct shape in fixture h/v2 to get a true positive — see §Verification runs for both). *Run:* **yes, on the direct-literal shape** — fixture `h-nilctx/`, red on `bad/`, green on `good/`.

## AI-agent angle

- **Restarting with `context.Background()` "to be safe" inside a helper.** An LLM asked to write a small helper function often defaults to `context.Background()` when it isn't immediately obvious what context is in scope, rather than adding a `ctx context.Context` parameter and threading it from the caller — this is the exact shape `contextcheck` exists to catch. Smallest check: `contextcheck` enabled in the repo's `golangci-lint` config; on a repo without golangci-lint, `grep -rn -e 'context\.Background()' -e 'context\.TODO()' --include='*.go' . | xargs -r echo` (empty = nothing to review) as a first-pass triage, since the real analyzer needs the wired build.
- **Storing `ctx` in a struct because "the object needs to make several calls."** A generated client or service type frequently gets a `ctx context.Context` field added by an LLM trying to avoid threading `ctx` through every method — this compiles, looks idiomatic to someone who has only seen it done elsewhere in the wild (it *is* common, per the 219–249 measured hits), and is still the anti-pattern both the Go blog and Google's style guide name directly. Smallest check: `containedctx` under golangci-lint, or `grep -rn -E '^\s+ctx\s+context\.Context\s*$' --include='*.go' .` on a repo without it (empty output = pass, though this misses fields not exactly on their own line).
- **Reaching for `context.Value` instead of adding a parameter.** Models trained on a mix of pre-context and post-context idioms, and on frameworks (some web frameworks, some testing helpers) that lean on `context.Value` for dependency injection, tend to reach for it as a generic "smuggle data downstream" mechanism rather than reserving it for cross-boundary, request-scoped data. Smallest check: no analyzer catches the misuse of *intent*; the mechanical half (string keys) is `SA1029`, which at least catches the most common surface symptom.
- **Hallucinating or misremembering the cause API's shape.** A model may write `ctx, cancel := context.WithTimeout(ctx, d, cause)` (mixing up `WithTimeout`'s two-value return with `WithTimeoutCause`'s three-argument, still two-value signature) or call `cancel(cause)` on a plain `CancelFunc` (which takes no arguments — only `CancelCauseFunc`, returned by the `*Cause` constructors, takes one). Smallest check: `go build ./...` catches every one of these immediately — they are compile errors, not runtime bugs, so the mechanical gate is simply "did it build."
- **Writing `os.Exit`/manual `signal.Notify` cancellation logic that assumes `NotifyContext`'s 1.26 cause exists on an older `go` line.** A model unaware of the 1.26 behavior change may write `context.Cause(ctx)`-dependent signal-handling code against a module whose `go` line is 1.25 or lower, where `NotifyContext` still cancels with the plain `context.Canceled` sentinel and no meaningful cause. Smallest check: read the module's own `go` line (`grep -n '^go ' go.mod`) before trusting `context.Cause(ctx)` on a `NotifyContext`-derived context; below 1.26, `ctx.Err()` is all that's guaranteed.
- **Using `exec.Command`/`http.NewRequest` in new code because that's what most training data shows.** Both non-context variants vastly predate their context-aware siblings and dominate the training distribution; a model writing new subprocess or HTTP client code defaults to the older call unless explicitly prompted otherwise. Smallest check: `noctx` under golangci-lint — confirmed to cover both `os/exec.Command` and the `net/http` family at 2.14.0 (this dive's fixture and live-corpus verification, §Verification runs / §Exemplar evidence).

## Contested / evolving

- **Whether `context.Value` needs a type-safe wrapper.** Merovius's own 2020 proposal for generic-parameterized context wrappers is presented by its author as unresolved — *"pretty infectious," not clearly worth the complexity* ([blog.merovius.de/posts/2020-07-20-parametric-context](https://blog.merovius.de/posts/2020-07-20-parametric-context/)) — and no such wrapper has become a de-facto stdlib or ecosystem standard as of 2026-09-26; the corpus shows no adoption of any such pattern. Trend: unresolved, leaning toward "still just `context.Value` with an unexported key type" as the practical default.
- **Cause-carrying cancellation's adoption curve.** `WithCancelCause`/`Cause` (1.20) and `WithTimeoutCause`/`WithDeadlineCause`/`WithoutCancel`/`AfterFunc` (1.21) are all several years old as of 1.27.1 but sit at 82 combined hits across the entire 35-repo, 2.66M-LOC corpus, with 25/34 repos at zero. Trend: growing (concentrated in the two most Go-version-current repos, `tailscale/tailscale` and `golang/tools`) but not yet a default anyone should assume is already in place when reading unfamiliar Go code.
- **`signal.NotifyContext`'s 1.26 cause change is recent enough that most existing code predates it.** As of 2026-09-26 (Go 1.27.1, released ~August 2026, with 1.26 as the prior release), essentially the entire exemplar corpus was written before this behavior existed, so the plain-`signal.Notify` vs. `NotifyContext` split measured (17 vs. 71, [exemplar-runtime-posture.md §2](../go-audit/exemplar-runtime-posture.md)) predates the feature this dive is recommending it for; expect that ratio to shift only in code written after this dive's date.
- **`contextcheck`'s precision on the functional-options-override-context idiom.** This dive found one confirmed false positive (`google/go-containerregistry@0c8bedb78437:pkg/v1/remote/catalog.go:75`) in a 3-repo, ~276k-LOC sweep that also found 6 true/plausible positives (5 `contextcheck`, one `containedctx`) — not enough samples to state a corpus-wide false-positive rate with confidence; a larger sweep (the full 35-repo corpus) would sharpen this if the effort is spent later.
