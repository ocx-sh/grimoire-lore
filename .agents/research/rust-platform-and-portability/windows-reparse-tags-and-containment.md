## Summary

1. Rust's `std::fs` classifies a reparse point as a symlink using the **name-surrogate bit** (`tag & 0x2000_0000`) of the reparse tag, not a hardcoded list of tags — verified in `library/std/src/sys/fs/windows.rs`. This means directory **junctions/mount points report `is_symlink() == true`** in Rust, contrary to common assumption.
2. Computed against Microsoft's own tag values (§A), `IO_REPARSE_TAG_APPEXECLINK` (UWP execution alias) is **not** a name-surrogate and so is **not** classified as a symlink by Rust — it reads as a plain file/directory.
3. `IO_REPARSE_TAG_LX_SYMLINK` (WSL symlink) **is** a name-surrogate, so `is_symlink()` is `true`, but Rust's `readlink()` only decodes `IO_REPARSE_TAG_SYMLINK` and `IO_REPARSE_TAG_MOUNT_POINT` payloads — reading an LX_SYMLINK's target via `std::fs::read_link` fails with "Unsupported reparse point type" even though the file correctly reports as a symlink. Fails safe, but is a real, cite-worthy gap between "is a symlink" and "can read where it points."
4. `IO_REPARSE_TAG_CLOUD*` (OneDrive Files On-Demand) and `IO_REPARSE_TAG_PROJFS` (VFS for Git) are **not** name-surrogates — placeholders read as ordinary files/directories to `std::fs`, not as symlinks. `IO_REPARSE_TAG_ONEDRIVE` (the pre-2018 tag) is documented by Microsoft as "Not used."
5. `GetFinalPathNameByHandleW` with the default `VOLUME_NAME_DOS` flag **always** returns a `\\?\`-prefixed path — this is documented Microsoft behaviour, not an edge case. Naively stripping the four-character prefix is unsafe: a `\\?\UNC\server\share\...` path needs rewriting to `\\server\share\...`, not truncation.
6. `dunce::canonicalize` is `std::fs::canonicalize` (which fully resolves symlinks/junctions via the OS) followed by a **string-level** rewrite that drops the `\\?\` prefix only when the result is unambiguously re-expressible in legacy form; it keeps the verbatim form for `\\?\UNC\...` shares and other cases it can't simplify. It does **not** change what gets resolved — do not treat it as a security boundary or as evidence a path stayed inside a root.
7. Windows has **no direct analogue of Linux's `openat2`/`RESOLVE_BENEATH`**. `FILE_FLAG_OPEN_REPARSE_POINT` on `CreateFile` opens the reparse point itself instead of following it, but there is no single flag that walks a multi-component relative path while refusing to cross a reparse point or an absolute component partway through.
8. `cap-std`'s Windows backend (`cap-primitives/src/windows/fs/open_impl.rs` → `manually::open`) proves the point above by construction: it does **manual, component-by-component path resolution**, holding an open directory handle per ancestor and re-walking through every symlink target — the same "manually" fallback path cap-std uses on Unix platforms that lack `openat2`. This is source-verified, not a guess.
9. cap-std's Windows symlink/reparse-point detection is **entirely delegated to `std::fs::Metadata::file_type().is_symlink()`** (`cap-primitives/src/windows/fs/file_type_ext.rs`) — so it inherits both the robustness (any current/future Microsoft name-surrogate tag is caught automatically) and the gap (APPEXECLINK-style non-surrogate reparse points are invisible to it as "symlinks", though they also cannot redirect path resolution, so this is consistent with the OS's own behaviour).
10. cap-std's Windows `open_impl` also has an **explicit reserved-device-name blocklist** (CON, PRN, AUX, NUL, COM0–9, LPT0–9, plus the superscript ¹²³ variants) checked before every open — proving this is a real, independently-implemented defence, not folklore.
11. `CreateHardLinkW` cannot target a directory, requires source and destination on the **same volume** (own comment: "all hard links to a file must be on the same volume"), and is capped at **1023 hard links per file** (`ERROR_TOO_MANY_LINKS`-class failure beyond that) per Microsoft's own documentation. Not supported on ReFS.
12. Creating a real NTFS symbolic link (`CreateSymbolicLinkW`) requires either **`SeCreateSymbolicLinkPrivilege`** (elevated/admin) or the `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` (0x2) flag **and** Developer Mode enabled on the machine — both are prerequisites documented directly by Microsoft, and both are conditions ordinary CI runners typically don't satisfy unless explicitly configured.
13. Directory **junctions require no privilege and no Developer Mode** to create (they're implemented as a plain reparse point set via `FSCTL_SET_REPARSE_POINT` by any process with write access to the containing directory) — this is the reparse type every unprivileged Windows CI job *can* exercise, and therefore the one every containment test suite must cover unconditionally.
14. Real, Windows-relevant CVEs exist in the exact two crate families named in scope: `tar` (Rust) has at least three symlink/hardlink-related advisories — CVE-2018-20990 (arbitrary file overwrite via re-used hardlink/symlink names), CVE-2021-38511 (symlink-directory escape creates directories outside the extraction root before the file-create fails), and CVE-2026-33056 (`unpack_dir` used `fs::metadata` — which follows symlinks — instead of `fs::symlink_metadata`, letting a symlink-then-directory pair `chmod` an arbitrary outside directory). The `zip` crate has CVE-2025-29787 (a zip-slip variant: a symlink written earlier in the archive is not re-validated when a later entry is extracted through it).
15. Alternate Data Streams are addressed via a colon in the filename (`file.txt:streamname:$DATA`); Microsoft's own naming rules forbid the colon character generically but **explicitly exempt ADS syntax** from that ban — an extractor that only forbids `:` in a "reasonable" way may still let an entry write to `victim.txt:evil:$DATA` inside an otherwise-safe directory.
16. Reserved device names (CON, PRN, AUX, NUL, COM1–9, LPT1–9) are reserved **with any extension appended** (`NUL.txt` and `NUL.tar.gz` both mean `NUL`) and Windows additionally reserves the ISO-8859-1 superscript-digit forms (COM¹, COM², COM³, LPT¹, LPT², LPT³) as valid digits in every directory — both facts are stated directly by Microsoft's own naming documentation.
17. Trailing dots and trailing spaces on a file/directory name are stripped/rejected by the Win32 layer (not by NTFS itself) — Microsoft: "Do not end a file or directory name with a space or a period," while a *leading* period is fine. An extractor validating names against the archive's literal bytes, then handing them to a Win32 API that silently trims the trailing dot/space, can end up writing to a *different* path than the one it validated.
18. `FSCTL_GET_REPARSE_POINT` requires no elevated privilege to query — any handle with read-attribute access can retrieve the reparse tag and payload; it returns `STATUS_NOT_A_REPARSE_POINT` if called on a non-reparse file. This makes tag-based detection cheap and always available, unlike symlink *creation*.

## Findings

### A. The reparse-point taxonomy

1. Reparse tags are 32-bit values with a documented bit layout: bit 31 = **M** (Microsoft-owned), bit 30 = **R** (reserved, must be 0 for non-Microsoft tags), bit 29 = **N** (name-surrogate: "the file or directory represents another named entity in the system"), bit 28 = **D** (directory bit, mutually exclusive with N). Source: [Reparse Point Tags — Win32 apps](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags) and, with the exact bit numbering, [\[MS-FSCC\]: Reparse Tags](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/c8e77b37-3909-4fe6-a4ea-2b9d423b1ee4).

2. Microsoft macros exist to test the tag: `IsReparseTagMicrosoft` and `IsReparseTagNameSurrogate` (documented on the same reparse-point-tags page). `IsReparseTagNameSurrogate` is exactly the `tag & 0x2000_0000 != 0` test that Rust's std reimplements (§B.1).

3. Exact hex values (from [\[MS-FSCC\]: Reparse Tags](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/c8e77b37-3909-4fe6-a4ea-2b9d423b1ee4), the canonical wire-protocol enumeration) and whether each is a name-surrogate — **the surrogate/not-surrogate column below is computed by this researcher** from the tag's top nibble against the N-bit position; Microsoft does not publish a single "which tags are name surrogates" table, only the bit definition plus each tag's numeric value:

   | Tag | Value | Name-surrogate (N-bit) | What it does |
   |---|---|---|---|
   | `IO_REPARSE_TAG_MOUNT_POINT` | `0xA0000003` | **Yes** | Directory junction / drive mount point |
   | `IO_REPARSE_TAG_SYMLINK` | `0xA000000C` | **Yes** | NTFS symbolic link (file or directory) |
   | `IO_REPARSE_TAG_APPEXECLINK` | `0x8000001B` | **No** | UWP app-execution alias — "encodes information that allows the application to be launched by CreateProcess"; format undocumented ("server-side interpretation only, not meaningful over the wire") |
   | `IO_REPARSE_TAG_LX_SYMLINK` | `0xA000001D` | **Yes** | WSL Unix symlink |
   | `IO_REPARSE_TAG_AF_UNIX` | `0x80000023` | No | WSL Unix-domain socket, no defined structure |
   | `IO_REPARSE_TAG_LX_FIFO`/`LX_CHR`/`LX_BLK` | `0x80000024`/`25`/`26` | No | WSL FIFO / char-special / block-special |
   | `IO_REPARSE_TAG_WCI` | `0x80000018` | No | Windows Container Isolation filter |
   | `IO_REPARSE_TAG_WCI_1` | `0x90001018` | No | Windows Container Isolation filter |
   | `IO_REPARSE_TAG_WCI_LINK` / `WCI_LINK_1` | `0xA0000027` / `0xA0001027` | **Yes** | Windows Container Isolation filter link |
   | `IO_REPARSE_TAG_WCI_TOMBSTONE` | `0xA000001F` | **Yes** | Windows Container Isolation filter |
   | `IO_REPARSE_TAG_GLOBAL_REPARSE` | `0xA0000019` | **Yes** | NPFS named-pipe symlink from a server silo into the host silo |
   | `IO_REPARSE_TAG_CLOUD` and `CLOUD_1`…`CLOUD_F` | `0x9000001A`, `0x9000101A`…`0x9000F01A` | No | Cloud Files filter (OneDrive Files On-Demand placeholders) |
   | `IO_REPARSE_TAG_ONEDRIVE` | `0x80000021` | No — and Microsoft marks it **"Not used"** | Legacy, superseded by the `CLOUD*` family |
   | `IO_REPARSE_TAG_PROJFS` | `0x9000001C` | No | Projected File System (VFS for Git) |
   | `IO_REPARSE_TAG_PROJFS_TOMBSTONE` | `0xA0000022` | **Yes** | Projected File System tombstone |
   | `IO_REPARSE_TAG_WIM` | `0x80000008` | No | WIM Mount filter |
   | `IO_REPARSE_TAG_DEDUP` | `0x80000013` | No | Data Deduplication filter |
   | `IO_REPARSE_TAG_NFS` | `0x80000014` | No | NFS component |

4. **Privilege/mode to create, per type:**
   - Junctions/mount points: no privilege, no Developer Mode — set via `FSCTL_SET_REPARSE_POINT` by any process that can write to the parent directory. Confirmed indirectly by [Hard Links and Junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions), which lists no privilege requirement, and directly by cap-std's own manual `FSCTL_SET_REPARSE_POINT` call for creating a mount point (`cap-primitives/src/windows/fs/create_file_at_w.rs`/symlink code path).
   - NTFS symlinks: `SeCreateSymbolicLinkPrivilege` (elevated) **or** `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` (0x2) with Developer Mode enabled — [CreateSymbolicLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createsymboliclinkw): *"Specify this flag to allow creation of symbolic links when the process is not elevated. Developer Mode must first be enabled on the machine before this option will function."*
   - APPEXECLINK, LX_SYMLINK, WCI/cloud/projfs tags: created only by their owning subsystem (App Installer/UWP deployment, WSL's `lxutil` driver, the container isolation filter, the cloud-files/projfs filter driver respectively) — not something an ordinary process (or archive extractor) can create directly through a documented Win32 API, and Microsoft explicitly labels their payload format "server-side interpretation only, not meaningful over the wire," i.e. **the documentation is deliberately silent on the internal structure**. Do not assume a structure for these; treat any reparse point you don't recognize as opaque and refuse to follow it.

### B. Detecting a reparse point correctly

1. **`std::fs`'s classification, verified against source.** `library/std/src/sys/fs/windows.rs` (`main` branch) defines:
   ```rust
   impl FileType {
       fn new(attributes: u32, reparse_tag: u32) -> FileType {
           let is_directory = attributes & c::FILE_ATTRIBUTE_DIRECTORY != 0;
           let is_symlink = {
               let is_reparse_point = attributes & c::FILE_ATTRIBUTE_REPARSE_POINT != 0;
               let is_reparse_tag_name_surrogate = reparse_tag & 0x20000000 != 0;
               is_reparse_point && is_reparse_tag_name_surrogate
           };
           FileType { is_directory, is_symlink }
       }
   }
   ```
   This is the exact `IsReparseTagNameSurrogate` test from §A applied by std itself — **not** a hardcoded `match` over `IO_REPARSE_TAG_SYMLINK | IO_REPARSE_TAG_MOUNT_POINT`. Source: `library/std/src/sys/fs/windows.rs` in [rust-lang/rust](https://github.com/rust-lang/rust) (path moved from the pre-2024 `library/std/src/sys/pal/windows/fs.rs` layout; fetched from the `main` branch during this research).

2. **`std::fs::read_link` is narrower than `is_symlink`.** The same file's `readlink()` only parses `IO_REPARSE_TAG_SYMLINK` (`SYMBOLIC_LINK_REPARSE_BUFFER`) and `IO_REPARSE_TAG_MOUNT_POINT` (`MOUNT_POINT_REPARSE_BUFFER`) payloads; every other tag falls through to:
   ```rust
   _ => {
       return Err(io::const_error!(
           io::ErrorKind::Uncategorized,
           "Unsupported reparse point type",
       ));
   }
   ```
   Consequence: for `IO_REPARSE_TAG_LX_SYMLINK` (a name-surrogate per §A), `symlink_metadata(...).file_type().is_symlink()` returns `true`, but `std::fs::read_link(...)` errors out. Code that branches on `is_symlink()` and then unconditionally calls `read_link()` to validate the target will hit this error path on a WSL-created symlink sitting inside a Windows-visible tree (e.g. under `\\wsl$\...` or a mixed filesystem) — it must be handled, not treated as "this can't happen."

3. **Getting the raw tag without following the point.** `FSCTL_GET_REPARSE_POINT` via `DeviceIoControl` on a handle opened with `FILE_FLAG_OPEN_REPARSE_POINT` returns a `REPARSE_DATA_BUFFER` (or `REPARSE_GUID_DATA_BUFFER`) whose first field is the tag. Requires no special privilege; fails with `STATUS_NOT_A_REPARSE_POINT` if the target isn't one. Source: [FSCTL_GET_REPARSE_POINT](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/fsctl-get-reparse-point). `GetFileInformationByHandleEx` with `FileAttributeTagInfo` is the higher-level equivalent used by cap-std and std internally to fetch `(FileAttributes, ReparseTag)` in one call without a full reparse-buffer read — visible at multiple call sites in `library/std/src/sys/fs/windows.rs` (e.g. the `attr_tag.ReparseTag` reads guarded by `FILE_ATTRIBUTE_REPARSE_POINT`).

4. **`FindFirstFile`/`WIN32_FIND_DATA`** also carries the tag in `dwReserved0` when `FILE_ATTRIBUTE_REPARSE_POINT` is set — the cheapest way to get tag + attributes for every entry in a directory listing in one syscall, per [Reparse Point Tags](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags): *"To retrieve the reparse point tag, use the FindFirstFile function. If the dwFileAttributes member includes the FILE_ATTRIBUTE_REPARSE_POINT attribute, then the dwReserved0 member specifies the reparse point [tag]."*

5. **Directory-vs-file ambiguity after a symlink is confirmed.** Rust's own doc comment on `fill_dir_buff` states the operational consequence plainly: *"On Windows a file is either a directory or a non-directory. A symlink directory is simply an empty directory with some 'reparse' metadata attached. So if you open a link (not its target) and iterate the directory, you will always iterate an empty directory regardless of the target."* This matters for a containment walk: iterating a directory handle opened with `FILE_FLAG_OPEN_REPARSE_POINT` over a symlink-directory never leaks the target's children — the OS itself won't traverse through it — but code that opens *without* that flag will silently follow the link and enumerate the target instead.

### C. Canonicalisation: GetFinalPathNameByHandleW and dunce

1. `GetFinalPathNameByHandleW`'s `dwFlags` combine a name-normalization axis (`FILE_NAME_NORMALIZED` = 0x0 default, or `FILE_NAME_OPENED` = 0x8) with a volume-format axis (`VOLUME_NAME_DOS` = 0x0 default, `VOLUME_NAME_GUID` = 0x1, `VOLUME_NAME_NT` = 0x2, `VOLUME_NAME_NONE` = 0x4). Source: [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew).

2. **The `\\?\` prefix is not an edge case — it's the documented default.** Verbatim from the API doc: *"When using VOLUME_NAME_DOS, the string that is returned by this function uses the '\\?\' syntax."* `VOLUME_NAME_NT` instead returns an NT device path (`\Device\HarddiskVolume1\...`) that "can not be used directly by Windows programs, as it resembles a relative path" — also stated directly in the Remarks.

3. The doc's own example of what "final path" means: *"for a symbolic link named 'C:\tmp\mydir' that points to 'D:\yourdir', the final path would be 'D:\yourdir'."* The resolution itself happens when the file was opened (the filesystem processes the reparse point at `CreateFile` time unless you passed `FILE_FLAG_OPEN_REPARSE_POINT`); `GetFinalPathNameByHandleW` reports the path of whatever the handle already refers to — it does not perform its own independent reparse-point walk. Open with `FILE_FLAG_OPEN_REPARSE_POINT` and the "final path" it reports is the link's own location, not the target's.

4. **8.3 short names**: not addressed by `GetFinalPathNameByHandleW`'s docs directly, but [Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file) is explicit that "not all file systems follow the tilde substitution convention, and systems can be configured to disable 8.3 alias generation" — so an extractor cannot assume `GetShortPathName`/short-name expansion is available or stable, and a containment check that compares a raw string path against a root without going through a handle-based resolution can be defeated by a caller supplying the short-name alias of a path outside the root (when 8.3 generation is enabled, which is not guaranteed but also not something a hardening check can rule out without querying).

5. **`dunce::canonicalize`.** Per the crate's own description on [lib.rs](https://lib.rs/crates/dunce) and [docs.rs](https://docs.rs/dunce/latest/dunce/): *"Normalize Windows paths to the most compatible format, avoiding UNC where possible."* Its documented behaviour is to call the real `std::fs::canonicalize` (so symlink/junction resolution is still fully performed by the OS) and then rewrite the **already-resolved** result: strip the `\\?\` verbatim prefix only when the remaining path is unambiguous in legacy form, and keep `\\?\UNC\...`-style paths as-is when they can't be. **Where dunce is not a safe substitute:** it is a display/compatibility convenience over an already-canonical path, not an independent containment or resolution mechanism — swapping it in for `std::fs::canonicalize` does not change *what* gets resolved, only how the resolved string is spelled, and it must never be used as the sole gate that decides whether a path is "inside" a root (do the containment comparison on the `std::fs::canonicalize` output, or on open file handles, before any dunce-style cosmetic rewrite).

### D. Opening without following, and the missing RESOLVE_BENEATH

1. `FILE_FLAG_OPEN_REPARSE_POINT` passed to `CreateFile` opens the reparse point itself rather than its target — documented at [Reparse Points and File Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations): *"Applications that use the CreateFile function should specify the FILE_FLAG_OPEN_REPARSE_POINT flag when opening the file if it is a reparse point."* The same page notes `OpenFileById` "will either open the file or the reparse point, depending on the use of the FILE_FLAG_OPEN_REPARSE_POINT flag" — the flag is the one universal lever across the relevant open APIs.

2. **There is no Windows equivalent of `openat2(..., RESOLVE_BENEATH)`.** No Microsoft Learn page documents a flag or function that walks a multi-segment relative path while refusing, atomically, to resolve any reparse point or any absolute/rooted component it encounters partway through. `FILE_FLAG_OPEN_REPARSE_POINT` only controls the *final* component of whatever path you hand to `CreateFile`; intermediate components in a multi-segment path are still resolved (and reparse-followed) by the filesystem before the final component is reached. This is a documentation-silence finding, not folklore: it was checked directly against the relevant primary pages and none describes such a primitive.

3. **cap-std's answer confirms point 2 by how it's built.** `cap-primitives/src/windows/fs/open_unchecked.rs` implements `open_at` by manually decomposing the path into `Component`s and only calling the OS's `CreateFileAtW`/`CreateFileW` **one component at a time**, with its own home-rolled `..`/`.` handling ("`PathCchCanonicalizeEx` and friends don't seem to work with relative paths... we manually canonicalize `..` and `.`"). The outer `cap-primitives/src/fs/manually/open.rs` module (shared with non-`openat2` Unix targets) then wraps that with symlink-count-limited manual resolution, holding an open handle to every ancestor directory in a `dirs: Vec<MaybeOwnedFile>` stack so that a `..` component pops back to the actual handle already held rather than re-resolving a path string (defeating a rename-race between check and use of an ancestor). A component of kind `PrefixOrRootDir` (an absolute path or drive prefix appearing mid-walk) is rejected outright with `errors::escape_attempt()`. This is the closest thing to `RESOLVE_BENEATH` for Windows and it is implemented entirely in userspace, component by component — not a single kernel-provided flag.

### E. cap-std on Windows

1. Confirmed from source (§D.3, §B's parallel in cap-std): cap-std's Windows symlink/reparse detection for the manual walk is not its own tag inspection — `cap-primitives/src/windows/fs/file_type_ext.rs`'s `ImplFileTypeExt::from_std` calls straight through to `std::os::windows::fs::FileTypeExt::is_symlink_file()`/`is_symlink_dir()`/`std::fs::FileType::is_symlink()`. It therefore inherits exactly the name-surrogate-bit behaviour of §B.1 (junctions look like symlinks to cap-std too, which is the conservative, safe direction) and the read_link gap of §B.2 for tags std can't decode.

2. cap-std's own doc for `Dir::from_std_file` states a Windows-specific TOCTOU mitigation not present on Unix: *"To prevent race conditions on Windows, the file must be opened without FILE_SHARE_DELETE."* ([docs.rs cap-std Dir](https://docs.rs/cap-std/latest/cap_std/fs/struct.Dir.html)) — evidence that cap-std's own maintainers consider the Windows guarantee to need extra, platform-specific hardening beyond what the Unix implementation requires; there is no single "Windows capability guarantee" statement published separately from the API docs (no `WINDOWS_SECURITY.md` or equivalent exists in the repository as of this research — checked directly, 404).

3. `cap-primitives/src/windows/fs/open_impl.rs` (§summary point 10) independently blocks the full reserved-device-name set — `CON, PRN, AUX, NUL, COM0-9, LPT0-9`, plus the superscript ¹²³ variants — by checking the file's *prefix* (the part before the first `.`) against an uppercased blocklist before ever calling `manually::open`. This exists as a defence *in addition to* whatever the OS itself does, which is worth noting: cap-std's authors did not trust `CreateFile`'s own reserved-name handling alone.

### F. Archive extraction hazards and real CVEs

1. **Reserved device names**: forbidden with any extension — Microsoft: *"Also avoid these names followed immediately by an extension; for example, NUL.txt and NUL.tar.gz are both equivalent to NUL."* And the ISO-8859-1 superscript digits ¹²³ are recognized as valid COM#/LPT# digits, reserved in **every** directory (not just the root). Source: [Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

2. **Trailing dots/spaces**: *"Do not end a file or directory name with a space or a period... it is acceptable to specify a period as the first character of a name."* This is a Win32-layer behaviour (strip/reject), and Microsoft doesn't claim NTFS itself can't store such names — meaning an extractor that opens files through the `\\?\` verbatim-prefix namespace (which "turns off automatic expansion of the path string" per the same page) can actually create a name a plain `CreateFile("victim.")` call would silently normalize to `victim`, producing two different files a naive after-the-fact "does this path collide" check would miss.

3. **Alternate Data Streams**: colon syntax `file:stream:$DATA` documented in [File Streams](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams). The general naming rules forbid `:` as a reserved character, but ADS is a documented, sanctioned exception — *"characters whose integer representations are in the range from 1 through 31, except for alternate data streams where these characters are allowed."* An entry name containing a colon is not automatically invalid on Windows; it may target a stream of an existing file rather than create a new one.

4. **Case-insensitive collision**: *"Do not assume case sensitivity... NTFS supports POSIX semantics for case sensitivity but this is not the default behavior."* ([Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)) — two archive entries differing only by case are the same NTFS path by default; last-write-wins silently overwrites the first unless the extractor explicitly checks for case-insensitive collisions itself (the OS will not report a conflict).

5. **Real CVEs, `tar` crate (Rust):**
   - **CVE-2018-20990 / [GHSA-2367-c296-3mp2](https://github.com/advisories/GHSA-2367-c296-3mp2)** — `tar-rs < 0.4.16`: "Tarballs with hard links or symlinks... can be used to overwrite any file on the filesystem" by first creating a link entry pointing at a target path, then a second entry with the same in-archive name that gets written through the link.
   - **CVE-2021-38511 / [GHSA-62jx-8vmh-4mcw](https://github.com/advisories/GHSA-62jx-8vmh-4mcw)** — `tar-rs < 0.4.36`: unpacking a tarball containing a symlink can create directories outside the intended extraction root before the eventual file-create fails, leaving the escaped directories behind.
   - **CVE-2026-33056 / [GHSA-j4xf-2g29-59ph](https://github.com/advisories/GHSA-j4xf-2g29-59ph)** — `tar-rs ≤ 0.4.44`: `unpack_dir` used `fs::metadata()` (follows symlinks) instead of `fs::symlink_metadata()` to check an existing path; a symlink-then-directory entry pair lets the subsequent `chmod` apply to whatever the symlink points at outside the extraction root. Fixed in 0.4.45 by switching to `symlink_metadata`. This is the single most on-point CVE for this report's subarea: it is exactly a "the code called the wrong metadata function and followed a reparse point it should have detected and refused" bug.
   - Also present: [GHSA-3pv8-6f4r-ffg2](https://github.com/advisories/GHSA-3pv8-6f4r-ffg2) (PAX header desync letting one entry's content smuggle a second, differently-interpreted entry) — not reparse-specific but relevant to "don't trust the archive's own bookkeeping of what an entry is."

6. **Real CVE, `zip` crate (Rust):** **CVE-2025-29787 / [GHSA-94vh-gphv-8pm8](https://github.com/advisories/GHSA-94vh-gphv-8pm8)** — `zip 1.3.0` through `< 2.3.0`: *"symbolic links earlier in the archive are allowed to be used for later files in the archive without validation of the final canonicalized path."* The crate's own `extract()` docs claimed the result "can't resolve to a path outside the current directory," which the advisory calls out as false once a symlink from an earlier entry is in play — a documented API guarantee that silently didn't hold. Affects `zip::read::ZipArchive::extract` and `zip::unstable::stream::ZipStreamReader::extract`. The advisory text does not single out Windows path syntax (backslash, drive letters, UNC) as a distinct vector — the vulnerability is symlink re-use, platform-independent in mechanism though its *containment* consequence differs by platform per §D–E.

7. **The generic pattern across all of the above** is the same one this report's containment algorithm (§ below) must close: an entry is checked against its own declared name, then written by *following whatever a prior entry in the same archive already placed on disk* (a symlink or hardlink), and the check-time path is not the write-time path. This is TOCTOU inside a single extraction, not a multi-process race — and it is exactly the case a Windows containment guard must re-verify at *every* path segment, every time, including segments the archive itself created moments earlier.

### G. Hardlinks on Windows

1. `CreateHardLinkW`: *"This function is only supported on the NTFS file system, and only for files, not directories."* Source and existing file "must be on the same volume" and neither parameter "can specify the name of a directory." Not supported on ReFS (explicit table entry: `Resilient File System (ReFS) | No`). Source: [CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw).

2. **1023 hard links per file, hard cap**: *"The maximum number of hard links that can be created with this function is 1023 per file. If more than 1023 links are created for a file, an error results."* — directly documented, exact number.

3. **Hardlink to a symlink hardlinks the symlink, not the target**: *"Symbolic link behavior—If the path points to a symbolic link, the function creates a hard link to the symbolic link."* — relevant for containment because an entry that looks like an ordinary file creation via hardlink, where the *existing* file it links from is itself a symlink, produces a second directory entry that is *also* effectively a symlink (same reparse point, new name) — a containment check keyed only on "is the new name a symlink by attribute" at creation time won't see this coming from the hardlink source side; it must check the *source* of every hardlink the same way it checks any other file.

4. **What a hardlink does to atomic replace**: because "any changes made to a hard-linked file are instantly visible to applications that access it through the links that reference it," but "directory entry size and attribute information... are visibly updated only at the link through which the change was made," an atomic-rename-based publish (rename staged file over final name) is unaffected in its atomicity, but if the *staged* path itself has an extra hardlink pointing elsewhere (created by a malicious or buggy prior step), the rename swaps only the one directory entry — the other hardlinked name keeps pointing at what is now stale content, which is the expected hardlink semantic but is easy to reason about incorrectly if the writer assumes "one file, one path."

## Normative guidance candidates

1. **Classify reparse points by the name-surrogate bit (`tag & 0x2000_0000`), not by matching known tag values.** Rationale: this is exactly what `std::fs` and (transitively) `cap-std` already do, so it fails safe for any current or future Microsoft-owned redirect-capable tag the containment code has never heard of. VERIFICATION: unit test that constructs (or mocks) `FileType::new(FILE_ATTRIBUTE_REPARSE_POINT, tag)` for each tag in the §A table and asserts `is_symlink()` matches the computed column.

2. **Never call `read_link()`/`readlink`-equivalent unconditionally after `is_symlink()` returns true; handle the "Unsupported reparse point type" error explicitly and refuse-to-follow rather than panic or silently continue.** Rationale: LX_SYMLINK and any other name-surrogate tag std can't decode will hit exactly this path (§B.2). VERIFICATION: on a WSL-accessible Windows host (or `winx`/manual `FSCTL_SET_REPARSE_POINT` fixture built with `IO_REPARSE_TAG_LX_SYMLINK`), confirm `symlink_metadata().file_type().is_symlink() == true` and `read_link()` returns an `Err`, and that the extractor's own error path is exercised, not a panic.

3. **Detect every reparse point (name-surrogate or not) via `FILE_ATTRIBUTE_REPARSE_POINT` on `symlink_metadata`/`FindFirstFile` before deciding what to do with an archive entry destination; never open a path for write without first checking whether any existing entry at that path (or any ancestor) is a reparse point.** Rationale: a non-surrogate reparse point (cloud placeholder, projfs virtual file) can still carry unusual read/write semantics (offline/sparse triggers, provider round-trips) that make "just write through it" unsafe even though it isn't a redirect. VERIFICATION: fixture with an `IO_REPARSE_TAG_PROJFS`-tagged path (requires a running Projected File System provider, or a scriptable one such as a minimal `ProjFS` test provider) confirming the extractor detects `FILE_ATTRIBUTE_REPARSE_POINT` and takes the deny/skip path rather than writing.

4. **Perform containment resolution component-by-component against open directory handles (cap-std's `manually::open` pattern), never against a string path checked once and then reused.** Rationale: Windows has no `openat2`/`RESOLVE_BENEATH`; a single upfront canonicalize-then-string-compare is a TOCTOU gap because any component can be replaced by a reparse point between the check and the eventual write (§D, and every CVE in §F.5–F.6 is a variant of exactly this). VERIFICATION: fixture that (a) creates a target directory `root/sub`, (b) extracts an archive entry into `sub`, (c) *before* the next entry in the same extraction is processed, replaces `sub` with a junction pointing outside `root`, (d) asserts the extractor's next write is refused, not silently redirected. Only requires an unprivileged junction (§A.4) — runnable in ordinary CI.

5. **Reject archive entries whose extracted name, compared case-insensitively, collides with an already-materialized name in the same destination directory** — do not rely on the filesystem to report the collision. Rationale: NTFS is case-insensitive by default (§F.4); the second entry silently overwrites the first with no OS-level error. VERIFICATION: fixture archive containing both `Foo.txt` and `foo.txt` entries; assert the extractor errors or applies a defined last-wins policy explicitly, rather than depending on incidental filesystem behaviour.

6. **Reject archive entries whose name-prefix (component before the first `.`), case-insensitively, is one of `CON, PRN, AUX, NUL, COM0–9, LPT0–9` or their superscript ¹²³ variants, in every directory level, not just the extraction root.** Rationale: directly documented Microsoft reservation, applies per-directory not just at the root (§F.1); cap-std independently re-implements exactly this check rather than trusting `CreateFile` (§E.3) — a strong signal this needs an explicit application-level check, not just OS reliance. VERIFICATION: port cap-std's own blocklist test (or write an equivalent) exercising every name in the list with at least one extension appended (`NUL.txt`) and confirm rejection.

7. **Reject (or explicitly, intentionally allow with a documented policy) any archive entry name containing a colon (`:`), since it may address an Alternate Data Stream of an existing file rather than create a new one.** Rationale: `:` is a sanctioned-but-dangerous exception to the reserved-character rule (§F.3); an entry named `readme.txt:secret:$DATA` doesn't fail generic character validation the way other reserved characters do. VERIFICATION: fixture entry named with an embedded colon, targeting a stream of a file already extracted earlier in the same archive; assert it is rejected before any `CreateFile` call is attempted.

8. **Do the containment root comparison against the output of `std::fs::canonicalize` (or handle-based resolution), never against a `dunce`-processed path, and never against a raw string that might still carry the `\\?\` prefix, an 8.3 short name, or a trailing dot/space the Win32 layer will later strip.** Rationale: `dunce` only re-spells an already-resolved path for display/compatibility (§C.5); comparing pre-canonicalization strings misses short-name aliasing and trailing-dot/space normalization (§C.4, §F.2). VERIFICATION: fixture where the containment root is passed to the checker via its 8.3 short-name alias (requires 8.3 generation enabled — not guaranteed present, see Contested/evolving) and via a name with a trailing dot; assert both compare equal to the canonical form.

9. **When creating a hardlink from an archive `hardlink` entry, apply every containment/reparse check to the link's *source* path, not only to the new name being created.** Rationale: `CreateHardLinkW` documents that hardlinking to a path that is itself a symlink creates a hardlink to the symlink (§G.3); an extractor that validates only the new name and blindly trusts a source path already on disk (because "it must have passed containment when it was created") is wrong if that source was itself modified out from under it between entries (§F.7's TOCTOU pattern generalized). VERIFICATION: fixture where entry N creates a symlink at `root/link` pointing outside `root`, and entry N+1 is a hardlink entry naming `root/link` as its source; assert the extractor refuses rather than creating a second reparse-carrying name.

10. **Treat "requires Developer Mode or elevation to create" as a CI-coverage boundary, and say so in the test suite, rather than silently skipping symlink-creation tests.** Rationale: real NTFS symlinks need `SeCreateSymbolicLinkPrivilege` or Developer Mode (§A.4); a CI runner without either will have every `std::os::windows::fs::symlink_*` call fail, and a test that swallows that failure (rather than asserting on it explicitly, or gating on a detected capability) silently stops testing the exact code path this whole report is about. VERIFICATION: a startup probe in the test harness that attempts a throwaway symlink creation, records whether it succeeded, and either runs the symlink-specific fixtures or explicitly reports them as skipped-with-reason — never a bare `#[ignore]` with no rationale.

## AI-agent angle

- An AI agent extracting an untrusted archive on Windows on a user's behalf is the exact threat model of every CVE in §F.5–F.6: it must not assume "checked the entry name once at the top" is sufficient, because every one of those CVEs is a variant of "checked once, then a later entry exploited what an earlier entry had already placed on disk."
- An agent that shells out to `tar`/`zip`/PowerShell `Expand-Archive` rather than a vetted crate inherits whatever bugs that tool has on Windows, with no visibility into which CVEs from §F it has patched; pin and audit the actual extraction dependency version, don't assume "it's just tar."
- Because Developer Mode/elevation gates real symlink *creation* but not junction creation or reparse-point *detection*, an agent's own test/verification pass for "does my extractor resist a malicious symlink" can be satisfied on an unprivileged CI runner using junctions as the stand-in reparse type (§A.4, §Normative-4) — the agent should not conclude "can't test this without admin" and skip the check entirely; only the NTFS-symlink-specific variant needs elevation/Developer Mode, and that gap should be reported explicitly (Normative 10), not silently absorbed.
- When an agent's own containment code calls `std::fs::symlink_metadata` or `Metadata::file_type().is_symlink()` on Windows to gate a write, it is relying on the name-surrogate-bit heuristic of §B.1 whether it knows it or not — worth stating explicitly in the agent's own code comments, so a future maintainer (human or AI) doesn't assume it's tag-enumerating and "helpfully" narrow it to `match tag { SYMLINK | MOUNT_POINT => ... }`, which would silently stop catching WCI_LINK/GLOBAL_REPARSE/PROJFS_TOMBSTONE-style future tags.

## Contested / evolving

- **Whether 8.3 short names are present at all is not knowable from documentation alone.** Microsoft states short-name generation "can be configured to disable... even if they normally support it," and explicitly warns "do not make the assumption that the 8.3 alias already exists on-disk." A containment check cannot assume short names are either present or absent; it can only ask (`GetShortPathName`) and handle both answers. This report does **not** assert a default state, because Microsoft's own docs decline to.
- **The exact byte-level payload format of APPEXECLINK, the LX_* family, WCI/WCI_LINK, and the CLOUD family is undocumented by Microsoft** ("server-side interpretation only, not meaningful over the wire" is the recurring phrase in the MS-FSCC table). Any code that parses these payloads is reverse-engineered against observed behaviour on a specific Windows build, not against a stable contract — folklore, not a documented guarantee, and it can change across Windows versions without notice. This report deliberately does not include such a parse.
- **Whether cap-std's manual-walk containment on Windows is airtight against every reparse tag** is not something this research can certify from documentation or source reading alone — it depends on `std::fs::Metadata::file_type().is_symlink()` continuing to catch every future name-surrogate tag (reasonable, since it's bit-based) *and* on no Windows filesystem filter driver being able to redirect resolution through a **non**-surrogate tag in a way `FILE_ATTRIBUTE_REPARSE_POINT` detection still wouldn't catch (Normative 3 assumes detection-not-classification is the safe fallback; this is this researcher's inference from the documented bit semantics, not a Microsoft-stated guarantee, and should be flagged as such wherever it's relied on).
- **RUSTSEC/GHSA coverage for Windows-specific archive-extraction bugs is thin** — the advisories found (§F.5–F.6) describe platform-independent mechanisms (symlink re-use, hardlink re-use) whose *containment* consequence is worse on Windows (reparse-point ambiguity, no RESOLVE_BENEATH) but none of the advisory texts call out Windows explicitly. Absence of a Windows-labeled CVE is not evidence the Windows-specific failure mode (§D, §Normative-4) has been separately found-and-fixed upstream; it may simply be untested there, per this whole report's premise.
