## Summary

- The exemplar-deps audit's "5 repos with no CI sync" (headline) and "4"
  (body) are both wrong: reading the actual CI content, only **3** of the 11
  dual repos genuinely never build+test the Bazel side in any tracked CI
  path — `jbeder__yaml-cpp`, `madler__zlib`, and `nlohmann__json` (the last
  never named by the audit at all).
- `abseil__abseil-cpp` and `google__googletest` build and test **both**
  descriptions on every platform, but through `ci/*.sh` scripts referencing
  `KOKORO_*` env vars (Google's internal CI), not through any
  `.github/workflows/*.yml` file — a repo with zero GitHub Actions workflow
  files is not evidence of no CI, and no evidence of no sync.
- `google__re2` and `google__benchmark` build+test both descriptions through
  two ordinary, equally-triggered GitHub Actions workflows each — the audit
  wrongly counted both as "no sync" (re2) or was internally split on
  benchmark (headline included it, body dropped it; the body was right).
- `protocolbuffers__protobuf` builds and tests both in **one** workflow file
  (`test_cpp.yml`) with bazel and cmake jobs side by side — the strongest
  sync case in the corpus.
- `grpc__grpc`'s root `CMakeLists.txt` carries a generated-file header naming
  `templates/CMakeLists.txt.template` and `tools/buildgen/generate_projects.sh`
  as its source; the reverse (Bazel `BUILD` files generated from CMake) does
  not exist — grpc's own `extract_metadata_from_bazel_xml.py` states its
  purpose as avoiding "two sources of truth" by treating **Bazel BUILD as the
  source and CMake as the derived copy**.
- `protocolbuffers__protobuf` goes one step further: `cmake/dependencies.cmake`
  is a generated file whose header says "Auto-generated by
  `@//cmake:make_dependencies`... based on our Bazel config", produced by a
  `genrule` in `cmake/BUILD.bazel` that parses `//:MODULE.bazel`; a paired
  `staleness_test` target exists but carries `tags = ["manual"]`, so it does
  not run under a plain `bazel test //...` and was not found wired into any
  tracked GitHub Actions workflow.
- The two clean, measured version-drift examples the map's "chase the
  surprise" asked for: `jbeder__yaml-cpp` vendors `googletest-1.16.0` as a
  checked-in source tree for its CMake tests while `MODULE.bazel` pins
  `bazel_dep(googletest, 1.17.0.bcr.2, dev_dependency)`; `google__benchmark`'s
  CMake fallback `ExternalProject_Add` pins `GIT_TAG "v1.15.2"` for
  googletest while `MODULE.bazel` pins `bazel_dep(googletest, 1.14.0,
  dev_dependency)` — CMake newer than Bazel this time, the opposite direction
  from yaml-cpp. Neither is a major-version split; the corpus has none at the
  2026-09-26 SHAs.
- `google__re2`'s CMake side calls `find_package(absl REQUIRED)` and
  `find_package(GTest REQUIRED)` with **no version argument at all** against
  `MODULE.bazel`'s pinned `abseil-cpp 20250814.1` / `googletest
  1.17.0.bcr.2` — genuinely "not knowable statically"; re2's own CI installs
  both via `vcpkg update`, so the real version is whatever the vcpkg registry
  baseline resolves to at CI run time, a third, independent version source.
- Target-name mapping is inconsistent across the corpus and an agent cannot
  guess it: `absl::strings` ↔ `@abseil-cpp//absl/strings:strings` (matches on
  leaf but not on repo-vs-namespace spelling), `protobuf::libprotobuf` ↔
  `@protobuf//:protobuf` (leaf name itself differs: `libprotobuf` vs
  `protobuf`), `GTest::gtest` ↔ `@googletest//:gtest` (case differs:
  `GTest` vs `googletest`), `ZLIB::ZLIB` ↔ `@zlib//:z` (leaf name differs
  entirely: `ZLIB` vs `z`), `benchmark::benchmark` ↔
  `@google_benchmark//:benchmark` (module/repo name differs: `benchmark` vs
  `google_benchmark`), `nlohmann_json::nlohmann_json` ↔
  `@nlohmann_json//:json` (leaf differs: `nlohmann_json` vs `json`).
  `yaml-cpp::yaml-cpp` ↔ `@yaml-cpp//:yaml-cpp` and `re2::re2` ↔
  `@re2//:re2` are the only two exact matches found.
- Conan 2.32.0's `BazelDeps` (`conan/tools/google/bazeldeps.py`) **does**
  produce a working Bzlmod-native path: a generated `conan_deps.MODULE.bazel`
  file that a consumer's own `MODULE.bazel` pulls in with Bazel's native
  `include("//conan:conan_deps.MODULE.bazel")` directive — not a
  `local_path_override`, not a hand-written module extension, and not
  WORKSPACE-only as the topic map's conflict 19 suspected from the docs page
  alone.
- Bazel's own `include()` restricts itself to "only the root module and
  modules subject to a non-registry override" (`bazel.build/rules/lib/globals/module`) —
  BazelDeps' Bzlmod path works for an application/workspace consuming Conan
  packages directly, not for a library published to the Bazel Central
  Registry that wants to re-export Conan-resolved dependencies transitively.
- Bazel 9 removed the autoloaded `cc_library`/`cc_import` symbols BazelDeps'
  generated `BUILD.bazel` files need, so Conan ships a second, `rules_cc`-aware
  variant (`BUILD.rules_cc.bazel`, `conan_deps_module_extension_rules_cc.bzl`)
  whose generated include snippet itself declares
  `bazel_dep(name = "rules_cc", version = "0.2.17")` — this is the same
  explicit-`load()`/autoload-removal fact `BZL-LARK` owns on the Bazel side;
  cite it there, never restate the mechanism here.
  WORKSPACE support (`dependencies.bzl`, `native.new_local_repository`) is
  labeled in the generator's own source comment as "Bazel 6.x... it'll
  likely be dropped soon."
- The Bazel-9-aware `BazelDeps` behavior traces to Conan PR
  [#20042](https://github.com/conan-io/conan/pull/20042) ("[Bazel] Add
  support for 9.x LTS version"), merged 2026-06-16 and shipped in Conan
  **2.30.0** (2026-06-29); confirmed unchanged through 2.32.0 (2026-08-31,
  current as of 2026-09-26).
- `BazelToolchain` only ever emits a `.bazelrc`-style `conan_bzl.rc` with a
  `build:conan-config` config group; it never touches WORKSPACE or
  MODULE.bazel and needs no Bzlmod-specific handling — it composes with
  either Bazel generation model unchanged.
- vcpkg has no Bazel-export generator of any kind. The only two `bazel` hits
  in the vcpkg exemplar are `vcpkg_find_acquire_program(BAZEL)` (vcpkg
  acquiring the `bazel` binary to build a *port whose own upstream build is
  Bazel* — the opposite direction) and a community port
  `vcpkg-tool-bazel`, last released 2022 and unrelated to exporting vcpkg
  packages into a Bazel build. vcpkg-tool itself has zero Bazel references.

## Findings

### 1. The audit's "no sync" count was wrong in both directions

`cmake-audit/exemplar-deps-and-dual-build.md`'s headline named five repos
with no CI sync mechanism (benchmark, googletest, re2, yaml-cpp, zlib); its
own §8 named four, dropping benchmark; both counted CI files that merely
*mention* `bazel` (re2 6 files, benchmark 3, yaml-cpp 2, googletest 1) as
"incidental" without opening them (topic map conflict 20). Reading every
`.github/workflows/*.yml` that mentions `bazel` or `cmake`, plus — because
two of the audit's five candidates turned out to have **zero** GitHub Actions
workflow files at all — every `ci/*.sh`/`ci/*.bat` script in each of the 11
repos, the true count of repos with **no** dual-build verification anywhere
in the tracked tree is **3**: `jbeder__yaml-cpp`, `madler__zlib`, and
`nlohmann__json` (a repo the audit never named).

Two repos the audit called "no sync" (`google__googletest`,
`abseil__abseil-cpp`) build and test both descriptions through
Google-internal CI that never surfaces as a `.github/workflows` file — an
agent that checks only that directory will reach the audit's wrong
conclusion for the same reason the audit did.

### 3. grpc generates CMakeLists.txt from Bazel, never the reverse

`grpc__grpc@0f8d72ed71:CMakeLists.txt:1-6` opens: "This file has been
automatically generated from a template file. Please look at the templates
directory instead. This file can be regenerated from the template by running
`tools/buildgen/generate_projects.sh`" and names
`templates/CMakeLists.txt.template` as the source. The metadata that
template consumes is itself extracted **from Bazel**:
`grpc__grpc@0f8d72ed71:tools/buildgen/extract_metadata_from_bazel_xml.py:16-22`
states its purpose in its own docstring: "To avoid having two sources of
truth for the build metadata... this script analyzes the contents of bazel
BUILD files and generates a YAML file (currently called
`build_autogenerated.yaml`)." `build_autogenerated.yaml` is a tracked file
(`git -C grpc__grpc ls-tree -r --name-only HEAD | grep build_autogenerated.yaml`
→ one hit) that then feeds the CMakeLists.txt template.

No `templates/BUILD.template` or equivalent exists (`git -C grpc__grpc
ls-tree -r --name-only HEAD | grep -iE 'templates.*build\.template'` → empty,
2026-09-26), and grpc's root `BUILD.bazel` is a zero-line file — grpc's real
Bazel target graph lives in per-package `BUILD` files that are hand-written,
never templated. **Direction is one-way: Bazel BUILD → generated
CMakeLists.txt, never CMake → generated BUILD.**

### 4. protobuf generates its CMake dependency versions from MODULE.bazel

`protocolbuffers__protobuf@c64743979d:cmake/dependencies.cmake:1-7` carries
the header "Auto-generated by `@//cmake:make_dependencies` ... This file
contains lists of external dependencies based on our Bazel config... Changes
to this file will be overwritten based on Bazel definitions," followed by
`set(<name>-version "<version>")` lines including
`set(abseil-cpp-version "20250512.1")`, `set(googletest-version "1.17.0")`,
`set(re2-version "2024-07-02")` — each matching, up to BCR-suffix stripping,
the corresponding `bazel_dep` in `protocolbuffers__protobuf@c64743979d:MODULE.bazel`
(`abseil-cpp` 20250512.1, `googletest` 1.17.0.bcr.2, `re2`
2024-07-02.bcr.1). The generation mechanism is a `genrule` in
`protocolbuffers__protobuf@c64743979d:cmake/BUILD.bazel:9-16`:

```
genrule(
    name = "generate_dependencies",
    srcs = ["//:MODULE.bazel"],
    outs = ["generated-in/dependencies.cmake"],
    cmd = "$(location :dependencies_generator) $(location //:MODULE.bazel) $@",
    tools = [":dependencies_generator"],
)
```

paired with a `staleness_test` target (`test_dependencies_staleness`,
`protocolbuffers__protobuf@c64743979d:cmake/BUILD.bazel:18-25`) that diffs
the generated output against the committed `dependencies.cmake`. That target
carries `tags = ["manual"]`, which excludes it from a plain `bazel test
//...` invocation; `grep -rn 'test_dependencies_staleness\|generate_dependencies'`
over every tracked `.github/workflows/*.yml` file in this repo returns no
hit, so this measurement cannot confirm the staleness check runs in CI it
can see — only that the generation mechanism and the check both exist and
are wired to the same source of truth. `cmake/gtest.cmake` and
`cmake/abseil-cpp.cmake` both consume the generated `<name>-version`
variables as the `GIT_TAG` for a `FetchContent_Declare` fallback when
`find_package` fails (`protocolbuffers__protobuf@c64743979d:cmake/abseil-cpp.cmake:18-24`).
This is the strongest measured answer in the corpus to "how do the two
dependency graphs stay in step": **generate the CMake side's pins from the
Bazel side's `MODULE.bazel`, then test staleness** — even though the test's
CI wiring is unconfirmed.

### 5. Exported target names: the mapping and its mismatches

Measured with `git show HEAD:<path> | grep -n '^cc_library('` for the Bazel
side and `grep -n 'NAMESPACE\|ALIAS'` over the CMake install/export code for
the CMake side, one repo at a time.

| library | Bazel module name (`MODULE.bazel`) | Bazel label | CMake namespaced target | leaf-name match? |
|---|---|---|---|---|
| Abseil strings | `abseil-cpp` | `@abseil-cpp//absl/strings:strings` | `absl::strings` | yes (only the module/namespace spelling differs) |

| GoogleTest | `googletest` | `@googletest//:gtest` | `GTest::gtest` | **no** — case differs, `googletest` (repo) vs `GTest` (namespace) |
| zlib | `zlib` | `@zlib//:z` | `ZLIB::ZLIB` | **no** — `z` vs `ZLIB` |
| Google Benchmark | `google_benchmark` | `@google_benchmark//:benchmark` | `benchmark::benchmark` | leaf matches; module/repo name (`benchmark` vs `google_benchmark`) does not |

### 6. Per-pair dependency drift table

`bazel_dep` entries read from `git show HEAD:MODULE.bazel` per repo, one
`bazel_dep(name = ...)` line at a time; the CMake side read from the same
repo's root `CMakeLists.txt`, its `cmake/*.cmake` includes, `.gitmodules`,
and (for a vendored tree) the checked-in directory name.

| pair | `MODULE.bazel` pin | CMake-side acquisition | comparable? | verdict |
|---|---|---|---|---|
| `jbeder__yaml-cpp` ↔ googletest | `bazel_dep(name = "googletest", version = "1.17.0.bcr.2", dev_dependency = True)` | vendored source tree at `test/googletest-1.16.0/` (checked in, not fetched) | yes, both are concrete versions | **DIFFERENT** — 1.17.0 (Bazel) vs 1.16.0 (CMake) |
| `google__benchmark` ↔ googletest | `bazel_dep(name = "googletest", version = "1.14.0", dev_dependency = True, repo_name = "com_google_googletest")` | `ExternalProject_Add(googletest GIT_TAG "v1.15.2" ...)` fallback in `cmake/GoogleTest.cmake.in`, used only if `GOOGLETEST_PATH` (default `./googletest`, no CMake-side vendor) is absent and downloading is allowed | yes | **DIFFERENT** — 1.14.0 (Bazel) vs 1.15.2 (CMake), CMake newer this time |
| `protocolbuffers__protobuf` ↔ abseil-cpp, googletest, re2, zlib | `bazel_dep` pins `abseil-cpp 20250512.1`, `googletest 1.17.0.bcr.2` (dev), `re2 2024-07-02.bcr.1`, `zlib 1.3.1.bcr.5` | `cmake/dependencies.cmake` (generated from `MODULE.bazel`, §4) sets the matching `<name>-version` used as `FetchContent`/`ExternalProject` `GIT_TAG` fallback | yes | **SAME BY CONSTRUCTION** — generated, not independently drifted |
| `grpc__grpc` ↔ abseil-cpp, googletest, protobuf, re2, zlib, c-ares, boringssl | `bazel_dep` pins e.g. `abseil-cpp 20260526.0`, `googletest 1.17.0`, `protobuf 35.1`, `zlib 1.3.1.bcr.5` | `gRPC_<NAME>_PROVIDER` cache var defaults to `"module"` (a `.gitmodules` submodule at an opaque pinned commit, e.g. `third_party/abseil-cpp` at `5650e9cf76d3`) with a `"package"` (`find_package`) fallback | **not knowable statically** — the submodule commit is not a release tag without resolving it against the upstream repo's history | **NOT KNOWABLE STATICALLY** |
| `google__re2` ↔ abseil-cpp, googletest | `bazel_dep(name = "abseil-cpp", version = "20250814.1")`, `bazel_dep(name = "googletest", version = "1.17.0.bcr.2", dev_dependency = True)` | `find_package(absl REQUIRED)` / `find_package(GTest REQUIRED)` with **no version argument**; CI installs both via `vcpkg update` (`.github/workflows/ci-cmake.yml`), so the actual resolved version is whatever vcpkg's registry baseline is at CI run time | no — three independent version sources (Bazel pin, vcpkg baseline, "whatever's on the system" for a local build) | **NOT KNOWABLE STATICALLY, and CI itself never states a version** |

`gflags__gflags`, `catchorg__Catch2`, `madler__zlib`, `nlohmann__json` have no
`bazel_dep` beyond `rules_cc`/`platforms`/`bazel_skylib`/`rules_license`
shared with any other corpus repo in this set, so no drift row applies to
them.

### 7. Conan's BazelDeps under Bzlmod: measured at 2.32.0

The topic map's conflict 19 flagged that Conan's docs page for Bazel shows
only `WORKSPACE`/`dependencies.bzl` wiring while the 2.30.0 changelog claims
Bazel 9 support, and Bazel 9 removed WORKSPACE. Fetching the actual generator
source resolves this: `conan/tools/google/bazeldeps.py` at conan-io/conan tag
**2.32.0** implements three parallel output sets in `_BazelPathsGenerator.items()`:

- **Bazel 6.x** (WORKSPACE): `dependencies.bzl` + `native.new_local_repository`,
  loaded via `load("@//conan:dependencies.bzl", "load_conan_dependencies")` in
  the project's own `WORKSPACE` file. The class docstring for this path reads
  "it'll likely be dropped soon."
- **Bazel 7.1–8.x** (MODULE.bazel via a user-registered extension):
  `conan_deps_module_extension.bzl` defines a `module_extension`; the
  consumer writes `load_conan_dependencies = use_extension(...)` and
  `use_repo(...)` itself.
- **Bazel 9.x** (MODULE.bazel via `include()`): `conan_deps.MODULE.bazel`
  (file name required to end `.MODULE.bazel` per Bazel's own `include()`
  contract) is generated with the whole `use_extension`/`use_repo` wiring
  **already written**, plus its own `bazel_dep(name = "rules_cc", version =
  "0.2.17")` because Bazel 9 no longer autoloads `cc_library`/`cc_import`.
  The consumer's `MODULE.bazel` needs exactly one line:
  `include("//conan:conan_deps.MODULE.bazel")`.

This is a real, working Bzlmod-native path, not a documentation gap papering
over a WORKSPACE-only reality — the topic map's suspicion was reasonable
from the docs page alone (which the fetch of
`docs.conan.io/2/integrations/bazel.html` confirms says only "must be loaded
by your WORKSPACE file" with no MODULE.bazel example) but the reference page
for `BazelDeps` (`conan-io/docs` `develop2` branch,
`reference/tools/google/bazeldeps.rst`) and the source itself both describe
the `include()` path in full. **The docs are split across two pages; an
agent that reads only the integrations landing page will conclude,
incorrectly, that Bazel 9 is unsupported.**

Constraint measured against Bazel's own reference
(`bazel.build/rules/lib/globals/module`, `include()`): "Only the root module
and modules subject to a non-registry override may use `include()`." A
project consuming Conan-resolved dependencies as the Bazel **root module**
(an application or top-level workspace) can use this path unmodified today.
A library that itself wants to be a Bazel Central Registry module and
re-export Conan-resolved transitive dependencies cannot use `include()` —
that use case has no BazelDeps-native answer at 2.32.0.

The Bazel 9 support traces to conan-io/conan PR
[#20042](https://api.github.com/repos/conan-io/conan/pulls/20042)
("[Bazel] Add support for 9.x LTS version. ... Feature: Add support for
Bazel 9.x to BazelDeps. Feature: Adapt `bazel_7_lib`/`bazel_7_exe` templates
to support Bazel 9.x (`conan new` command)"), merged 2026-06-16, released in
Conan **2.30.0** (2026-06-29). Re-fetching the 2.32.0 source
(`conan/tools/google/bazeldeps.py`) on 2026-09-26 shows the same code
unchanged, matching the era-recheck's finding that Conan itself has had no
release since 2.32.0.

### 8. BazelToolchain is orthogonal to WORKSPACE/MODULE.bazel

`conan-io/docs` `develop2`'s `reference/tools/google/bazeltoolchain.rst`
describes `BazelToolchain` as generating exactly one file, `conan_bzl.rc`,
containing a `build:conan-config` `.bazelrc` config group (compiler and
linker flags derived from the Conan profile). It is invoked at the command
line as `bazel --bazelrc=<path>/conan_bzl.rc build --config=conan-config
<target>` and never mentions WORKSPACE, MODULE.bazel, or Bzlmod anywhere in
the reference page. Because `.bazelrc` config groups are a flag-injection
mechanism independent of the external-dependency model, `BazelToolchain`
needs no Bzlmod-specific variant and composes with either `BazelDeps` output
path (§7) unchanged.

### 9. vcpkg has no Bazel integration

`microsoft__vcpkg@c4ee5a52d7` and `microsoft__vcpkg-tool@51bf87ca6e`
(re-fetched 2026-09-26) contain exactly two `bazel`-matching paths in the
former and zero in the latter:
`microsoft__vcpkg@c4ee5a52d7:scripts/cmake/vcpkg_find_acquire_program(BAZEL).cmake`
(a helper that lets a **vcpkg port whose own upstream build system is
Bazel** acquire the `bazel` binary to build itself — the reverse direction
from exporting vcpkg packages to Bazel) and
`microsoft__vcpkg@c4ee5a52d7:versions/v-/vcpkg-tool-bazel.json` (a
community-maintained port named `vcpkg-tool-bazel`; per
`vcpkg.link/ports/vcpkg-tool-bazel` its latest version, 5.2.0, dates to
October 2022, unrelated to vcpkg's own generator surface and stale for four
years as of 2026-09-26). No `vcpkg export --format=bazel` or equivalent
exists in vcpkg-tool's source. **A team with a vcpkg manifest and a Bazel
build has no vendor-provided bridge; the only paths are hand-written BUILD
files pointing at the vcpkg installed tree (`new_local_repository`) or
switching the Bazel side to `rules_foreign_cc`/BCR for that dependency.**

## Normative guidance candidates

1. **Rule.** Before reporting a dual CMake+Bazel repo as having "no sync
   mechanism," check for CI evidence outside `.github/workflows/`: a
   `ci/*.sh`/`ci/*.bat` directory referencing `KOKORO_*` env vars, or a
   `tools/internal_ci/**/*.cfg` (or equivalent internal-CI config directory)
   naming both a CMake and a Bazel invocation.
   *Rationale.* Two of the corpus's 11 dual repos (`abseil-cpp`,
   `googletest`) build and test both descriptions exclusively through
   Google-internal CI invisible to a `.github/workflows`-only check (§1, §2).
   *Verify.* `git -C <repo> ls-tree -r --name-only HEAD | grep -E '^\.github/workflows/'`
   returning empty is not evidence of no CI; follow with
   `git -C <repo> ls-tree -r --name-only HEAD | grep -E '^ci/|^tools/internal_ci/'`
   and read any hit for both `bazel` and `cmake` mentions before concluding
   "no sync."
2. **Rule.** Two GitHub Actions workflow files that separately build+test a
   Bazel and a CMake description under matching `on:` triggers is a real,
   checkable sync mechanism (SHOULD, not MUST) for a dual-build repository;
   one that only builds (no test step) on either side is a weaker, partial
   sync and should be named as such, never rounded up to "tested."
   *Rationale.* `google__re2` and `google__benchmark` both run separate
   workflows with identical triggers that build **and** test each side
   (§2); `catchorg__Catch2` and `gflags__gflags` build both but test only
   the CMake side (§2) — collapsing these two categories together is how
   the audit under- and over-counted.
   *Verify.* For each workflow file matching `bazel` or `cmake` in name or
   content, grep its job steps for `bazel test` / `ctest` / `cmake --build .
   --target test`; a build-only job (no test invocation found) downgrades
   the row from FULL to PARTIAL sync. Empty output on the test-step grep
   for one side is the finding.
3. **Rule.** When a dual-build repo's `CMakeLists.txt` (or any generated
   build file) carries a "this file is auto-generated" header, read the
   named generator before writing anything about that repo's dependency or
   build-description sync — the direction of generation (Bazel→CMake, never
   the reverse in this corpus) determines which side is authoritative for
   drift purposes.
   *Rationale.* `grpc`'s `CMakeLists.txt` and `protobuf`'s
   `cmake/dependencies.cmake` are both generated from Bazel-side sources
   (§3, §4); treating either as independently authored invites a false
   "drift" finding when the real state is "generated, and therefore
   synchronized by construction."
   *Verify.* `rg -n -e 'auto.generated' -e 'automatically generated' -e 'DO NOT EDIT' CMakeLists.txt cmake/*.cmake` —
   a hit means read the named source/generator before comparing versions
   against `MODULE.bazel`; empty means treat the CMake side as independently
   authored and eligible for real drift.
4. **Rule.** A per-pair dependency-drift check compares `bazel_dep` version
   strings in `MODULE.bazel` against the CMake side's `FetchContent_Declare`/
   `ExternalProject_Add` `GIT_TAG`, a `find_package(<Pkg> <version>)` version
   argument, or (if neither pins a version) reports "not knowable
   statically" rather than silently passing.
   *Rationale.* `re2`'s CMake side calls `find_package(absl REQUIRED)` with
   no version at all against `MODULE.bazel`'s `abseil-cpp 20250814.1` (§6);
   a check that only diffs two version *strings* would report a false
   "empty diff = no drift" here because there is no second string to diff.
   *Verify.* `rg -n 'bazel_dep\(name = "PKG"' MODULE.bazel` for the pinned
   version, then `rg -n -e 'FetchContent_Declare\(\s*PKG' -e 'find_package\(\s*PKG' -g CMakeLists.txt -g '*.cmake' .`
   (substitute the real package name for `PKG`); if the CMake-side match
   carries no `GIT_TAG`/version token, the row is NOT KNOWABLE STATICALLY,
   never PASS.
5. **Rule.** A CMake-side dependency acquired as a git submodule
   (`.gitmodules` entry with mode `160000` in `git ls-tree`) is never
   comparable to a `bazel_dep` version string without resolving the
   submodule's pinned commit to an upstream tag first; report the
   comparison as blocked, not as a silent pass.
   *Rationale.* `grpc`'s `gRPC_ABSL_PROVIDER=module` default resolves to a
   submodule commit (`5650e9cf76d3...`) that carries no version string of
   its own in the parent repo's tree (§6); most agent tooling that diffs
   version *strings* will find nothing to compare and wrongly report "no
   drift detected" rather than "unresolvable."
   *Verify.* `git -C <repo> ls-tree HEAD -- <submodule-path>` — a `160000
   commit <sha>` entry with no adjacent version file is the tell; resolving
   it requires `git -C <submodule-checkout> describe --tags <sha>` against a
   full (non-shallow) clone of the submodule's own history, which the
   corpus's blob-less depth-1 clone cannot do for a nested submodule without
   a separate fetch.
6. **Rule.** State a Bazel target label and its CMake-exported counterpart
   together, never derive one from the other by pattern (lowercase the
   namespace, singularize, etc.) — verify each pair against both build
   descriptions before publishing a mapping table entry.
   *Rationale.* 6 of the 8 measured pairs in this corpus fail a naive
   pattern match (`ZLIB::ZLIB` vs `@zlib//:z`; `protobuf::libprotobuf` vs
   `@protobuf//:protobuf`; `GTest::gtest` vs `@googletest//:gtest`; §5); an
   LLM guessing from the CMake name alone will produce a Bazel label that
   does not exist.
   *Verify.* For the CMake side: `rg -n 'NAMESPACE|add_library\(.*ALIAS' CMakeLists.txt src/CMakeLists.txt`.
   For the Bazel side: `rg -n '^cc_library\(' --include=BUILD.bazel --include=BUILD .`
   immediately followed by the `name = "..."` line, plus the `module(name =
   ...)` line in `MODULE.bazel` for the repository component of the label.
   Never publish a mapping without both greps' output in hand.
7. **Rule.** For a project consuming Conan packages under Bzlmod (Bazel
   ≥7.2, including Bazel 9), wire `BazelDeps`' output with
   `include("//<generators-folder>:conan_deps.MODULE.bazel")` in the
   project's own root `MODULE.bazel` — never a hand-written
   `local_path_override`, and never assume WORKSPACE is required — but only
   when the consuming module is the Bazel **root module** or is under a
   non-registry override; a BCR-published library cannot use this path.
   *Rationale.* This is the actual, measured 2.32.0 mechanism (§7); an
   agent trained on Conan's WORKSPACE-era docs or on the Bazel integration
   landing page alone (which never mentions MODULE.bazel) will either
   recommend a nonexistent manual wiring step or declare Bazel 9 support
   absent.
   *Verify.* `rg -n 'BazelDeps' conanfile.py conanfile.txt` confirms the
   generator is active; then `find . -name 'conan_deps.MODULE.bazel'`
   locates the generated include target, and `rg -n 'include\("//.*conan_deps.MODULE.bazel"\)' MODULE.bazel`
   confirms the consumer wired it. Empty on the last grep with the file
   present is the finding (generated but never included).
8. **Rule.** Never claim vcpkg has any Bazel-facing generator (no
   `vcpkg export --format=bazel`, no maintained `rules_vcpkg`); the only
   sanctioned bridges from a vcpkg manifest into a Bazel build are
   hand-written `new_local_repository`/`http_archive` rules over the vcpkg
   installed tree, or switching that dependency's Bazel-side acquisition to
   `rules_foreign_cc` or a BCR module instead.
   *Rationale.* The only two `bazel`-matching paths in the vcpkg exemplar
   run in the opposite direction or are a four-year-stale community port
   (§9); an LLM asked "how do I use my vcpkg manifest from Bazel" has no
   correct vendor-provided answer to reach for and must say so.
   *Verify.* `rg -rn 'bazel' --include='*.cmake' --include='*.py' <vcpkg-checkout>/scripts` —
   any hit found should name `vcpkg_find_acquire_program(BAZEL)` or nothing
   else; a hit naming any other mechanism is new and must be re-verified
   against vcpkg-tool's current source before being cited.

## AI-agent angle

1. **Concluding "no CI sync" from an empty `.github/workflows/` listing.**
   An LLM that treats GitHub Actions as the only CI surface will
   misdiagnose `abseil-cpp` and `googletest` exactly as the wave-1 audit
   did — both build and test both descriptions, just through
   Kokoro-triggered `ci/*.sh` scripts (§1, §2). The mechanical check: before
   reporting "no CI," also list `ci/` and `tools/internal_ci/` and grep
   their contents for `bazel` and `cmake`, not just `.github/workflows/`.
2. **Guessing a Bazel label from a CMake namespaced target by lowercasing or
   pattern-matching.** `ZLIB::ZLIB` does not become `@zlib//:ZLIB` or
   `@zlib//:zlib`; the real label is `@zlib//:z` (§5). The mechanical check:
   grep both `BUILD.bazel`'s `name = "..."` and the CMake `install(EXPORT ...
   NAMESPACE ...)`/`add_library(... ALIAS ...)` lines before publishing any
   mapping row; never publish one derived from only one side.
3. **Citing Conan's Bazel integration as "WORKSPACE only, no Bazel 9
   support" from the docs landing page alone.** The landing page
   (`docs.conan.io/2/integrations/bazel.html`) genuinely reads that way; the
   `include()`-based MODULE.bazel path only appears on the `BazelDeps`
   reference page and in source (§7). The mechanical check: for any Conan
   generator claim, read the generator's own reference page under
   `reference/tools/<module>/` and, where a Bzlmod-version question is at
   stake, the generator's source in `conan/tools/`, not the integrations
   overview page alone.
4. **Recommending `local_path_override` or a hand-rolled `use_extension`
   block to wire Conan-generated Bazel deps into MODULE.bazel.** That was
   necessary advice for Bazel 7.1–8.x (the manual `use_extension`/`use_repo`
   path is real and still generated, §7) but Bazel 9-targeting projects get
   a ready-made `conan_deps.MODULE.bazel` and need only one `include(...)`
   line — recommending the older, verbose wiring on a Bazel 9 project is
   the 2024-era answer surviving into a 2026 question.
5. **Treating a generated `CMakeLists.txt` or `dependencies.cmake` as an
   independently-authored file eligible for a version-drift finding.** An
   agent that diffs `protobuf`'s `cmake/dependencies.cmake` googletest
   pin against `MODULE.bazel` and reports "drift" when they match has
   missed that the file is generated *from* `MODULE.bazel` by construction
   (§4, §3) — the correct finding, if any, is about whether the generator
   was re-run (a staleness question), never about the pinned version
   itself.
6. **Assuming any dual-build repo's Bazel and CMake dependency versions are
   comparable strings.** `re2`'s CMake side has no version argument to
   compare at all (§6) — an agent that reports "same" or "different" here
   without first confirming a version string exists on the CMake side has
   fabricated a comparison.
7. **Inventing a vcpkg-to-Bazel generator or `rules_vcpkg` package that does
   not exist.** No such official mechanism exists at 2026-09-26 (§9); the
   mechanical check is the negative-evidence grep in normative candidate 8 —
   an agent should be able to state "there is no such tool" rather than
   hallucinate one, because a training-data-plausible name (`rules_vcpkg`,
   `vcpkg_bazel_deps`) is easy to invent and easy to state confidently.

## Contested / evolving

- **Whether `grpc`'s distrib CMake tests (`test/distrib/cpp/run_distrib_test_cmake*`)
  are still exercised in CI at all is not fully settled by this dive.**
  `tools/internal_ci/linux/pull_request/grpc_cmake_aarch_cross_linux.cfg`
  proves the *mechanism* is wired into at least one Kokoro job as of the
  2026-09-26 SHA, but this dive cannot read Kokoro's own scheduling
  configuration (it is not part of the tracked git tree) to confirm the job
  actually runs on every PR rather than on a schedule or manually. Treat
  "grpc's CMake distrib tests run in CI" as SHOULD-confidence, not
  MUST-confidence, until a Kokoro-side artifact is read.
- **`protobuf`'s `test_dependencies_staleness` target's CI wiring is an open
  question, not a settled negative.** `tags = ["manual"]` means it is
  excluded from `bazel test //...`, and no tracked GitHub Actions workflow
  invokes it by name (§4) — but protobuf, like grpc and abseil, may run
  additional checks through Google-internal CI this dive cannot see. State
  the mechanism as confirmed and its CI enforcement as unconfirmed, not
  absent.
- **Whether CI building both descriptions should be MUST or SHOULD for a
  dual-build project is genuinely a judgment call this dive resolves as
  SHOULD, not MUST.** Three of 11 repos in active, healthy use
  (`yaml-cpp`, `zlib`, `nlohmann/json`) ship no Bazel-side CI at all and
  show no evidence of drift-driven breakage as a result — Bazel support in
  these three reads as "we accept community `BUILD.bazel`/`MODULE.bazel`
  files but do not maintain them under test," a legitimate and stated
  posture, not an oversight. A MUST rule would flag three actively
  maintained, non-broken projects.
- **The `include()`-based BazelDeps path is new enough (Bazel 9-targeting
  code shipped in Conan 2.30.0, 2026-06-29) that no exemplar in the corpus
  uses it** — this dive's evidence for §7 is Conan's own source and
  documentation, not a real consumer. Whether real projects adopt
  `include("//conan:conan_deps.MODULE.bazel")` over the manual
  `use_extension` path, or run into friction from the root-module
  restriction, is unmeasured as of 2026-09-26.
