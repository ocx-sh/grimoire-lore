## Summary

1. ocx runs **two independent XZ decoders in production**, not one: `lzma_rust2::XzReader` (pure Rust) on the sync local-archive path (`compression::read_file`, used by `Archive::extract` for local `.tar.xz` files), and `async_compression::tokio::bufread::XzDecoder` — backed by the C `liblzma` library via the `liblzma` crate — on the async OCI-registry-pull path (`oci/client.rs::pull_layer_with_caps`). Both are reachable from production code today; this is real duplication, not dead code.
2. The C decoder is reachable specifically because `async-compression`'s `xz` feature (via its `compression-codecs` split) depends on `liblzma`, which depends on `liblzma-sys`, which vendors and statically links C `xz` 5.8.x — this is the only C parser among the five *decompressors* ocx uses on untrusted bytes.
3. ocx's own `Cargo.toml` comment already records a specific, verified rationale for keeping `liblzma`: CVE-2025-31115 (CVSS v4 8.7, heap-use-after-free / null-deref in `lzma_stream_decoder_mt`) is confirmed by NVD to affect **only** the multithreaded XZ decoder; ocx's pull path uses the single-threaded `XzDecoder`, so the vulnerable function is never called. This claim checks out against the primary CVE record.
4. A newer, lower-severity xz advisory exists that the multithreaded-only rationale does **not** cover: `GHSA-x872-m794-cxhv`, a buffer overflow in `lzma_index_append()` (Low, published 2026-03-31) — index parsing runs on every XZ stream regardless of thread count, so this is a live watch-item against the current liblzma pin, not something the existing comment addresses.
5. `liblzma`'s `static` feature is not cosmetic: without it, `liblzma-sys`'s build script pkg-config-probes for a host `liblzma` and links dynamically when found, which on the macOS CI runner bakes an absolute Homebrew path into the Mach-O — the binary then fails to start on a stock Mac. `static` is required on all 8 shipped target triples (`aarch64`/`x86_64` × `apple-darwin`/`linux-gnu`/`linux-musl`/`pc-windows-msvc`), and is unconditionally necessary for the two musl targets, which have no system `liblzma` to link against at all.
6. Eliminating `liblzma` is architecturally possible without losing XZ support: `SyncIoBridge` already sits in the pipeline to hand tar a sync `Read`; today it wraps the *decoder* (async), so decoding happens on the C-backed async side. Moving `SyncIoBridge` one layer earlier — to wrap the pre-decompression `ProgressReader`/`HashingAsyncReader` chain instead — turns the byte stream sync *before* decompression, letting the existing pure-Rust `lzma_rust2::XzReader` (already used for the local path) decode both paths. The same restructuring lets `flate2`'s sync `GzDecoder` and `zstd`'s sync `Decoder` replace `async-compression`'s gzip/zstd decoders too, removing `async-compression` from the decode path entirely.
7. Of ocx's five *decompressors*, only two are C FFI today: `liblzma` (xz, via `async-compression`) and `zstd` (via `zstd-sys`, both the direct `zstd` crate use and `async-compression`'s zstd feature) — not just the xz one. `flate2` (gzip) defaults to the pure-Rust `miniz_oxide` backend, `zip`'s `deflate` feature (as configured, `default-features = false, features = ["deflate"]`) is pure Rust, and `tar` is pure Rust.
8. Unlike xz, zstd has no mature drop-in pure-Rust production decoder in ocx's dependency graph — `ruzstd` exists but isn't evaluated or used — so the zstd C dependency is comparably harder to remove than the xz one; the two C decoders are not equally addressable.
9. The OCI image-spec defines exactly three layer media types: `tar`, `tar+gzip`, `tar+zstd` — **xz is not a standard OCI layer media type.** ocx's `application/vnd.oci.image.layer.v1.tar+xz` is a custom, non-standard extension; a registry or client that only implements the spec's three types cannot produce or consume it. This makes the xz decoder's registry-side value narrower than gzip/zstd's: it exists for ocx-to-ocx interop, not general OCI interop.
10. ocx's registry pull path explicitly rejects uncompressed layers (`CompressionAlgorithm::None` → `InvalidManifest` error) — so all three negotiated media types (gzip, xz, zstd) are live, and `zip` is **not** one of them (`media_type_from_filename` returns `None` for `.zip`; confirmed by an explicit `pull_local.rs` comment and test that a bare `.zip` is refused).
11. `zip` is therefore reachable only via local, non-registry paths (`Archive::create`/`extract` when the file extension is `.zip` — used for producing distributable package archives, exercised in `package/bundle.rs` and `package_manager/tasks/pull_local.rs`) — it sits downstream of a user pointing ocx at a local file, not on the live registry-blob path, and is comparatively closer to dead weight on the threat model this topic targets.
12. `zip` has a real, recent, high-severity CVE directly on-point for this topic: **CVE-2025-29787 / RUSTSEC-2025-0168 / GHSA-94vh-gphv-8pm8** (CVSS 7.3), a symlink-based zip-slip variant in `zip::read::ZipArchive::extract` and `zip::unstable::stream::ZipStreamReader::extract`, affecting versions ≥1.3.0 and <2.3.0. ocx is on `zip = "8.6"` (well past the patched 2.3.0) **and** never calls either vulnerable convenience method — `archive/zip.rs::extract` is a hand-rolled loop using `enclosed_name()` plus an explicit `crate::symlink::validate_target` check reused from the tar path. This is exactly the defense the CVE shows the built-in method lacked; ocx's zip extraction is not vulnerable to it, on two independent grounds (version and API surface).
13. `tar` (the crate) has its own recent CVE, unrelated to zip: **CVE-2026-33056 / RUSTSEC-2026-0067** (Medium, 5.1), a symlink-then-directory chmod confusion via `fs::metadata()` following symlinks in `unpack`/`unpack_in`, fixed in 0.4.45. ocx and grimoire both pin `tar = "0.4.46"` — already patched.
14. Path-escape / zip-slip protection is present on both extractors in ocx, under different names: tar uses `crate::utility::fs::path::escapes_root` (checked against the raw entry path before any file is created) plus `crate::symlink::validate_target` for symlink entries; zip uses `entry.enclosed_name()` (rejects null enclosure) plus the same `crate::symlink::validate_target` for its symlink entries. Both guards are exercised by dedicated regression tests (`test_extract_rejects_path_traversal_tar`, `test_extract_rejects_escaping_symlink_tar`, `test_extract_rejects_escaping_symlink_zip`).
15. Decompressed-size capping is enforced at different layers for different decoders, and not uniformly "at the API level": the OCI pull path (gzip/xz/zstd via `async-compression`) is capped by a *wrapping* `std::io::Read::take(cap_with_probe)` applied to the `SyncIoBridge` around the decoder — none of `flate2`, `zstd`, or `async-compression`'s decoders expose a native output-size-limit constructor argument, so the cap is enforced entirely by the wrapper, not the decoder API. The local sync path (`compression::read_file`, used for `.tar.xz`/`.tar.gz`/`.tar.zst`/`.zip` outside the registry pipeline) has **no equivalent cap at all** — it is a plain `Box<dyn Read>` with no `.take()` wrapper and no analogue of grimoire's `CappedSink`.
16. `zip::ZipArchive::by_index` in `archive/zip.rs::extract` also has no decompressed-size cap: `std::io::copy(&mut entry, &mut outfile)` runs uncapped per entry, and the sum of entries is uncapped across the whole archive. Whether a local, non-registry `.zip` input counts as "untrusted" is exactly the scope question this topic flags — the OCI-registry answer is that zip is off that path entirely, but any CLI surface that accepts an attacker-supplied `.zip` path inherits this gap.
17. `deny.toml`'s current `[bans]` section (`bans` axis) is minimal — `multiple-versions = "warn"` only, with **no `deny` entries at all**. cargo-deny's own docs give the exact idiom for "duplicate implementations of the same job": `multiple-versions = 'allow'` plus explicit `deny = [{ crate = "<the-loser>", use-instead = "<the-winner>" }]` entries, which is a direct, low-effort fit for banning `liblzma` in favor of `lzma-rust2` once (or if) the async pull path stops depending on it.
18. grimoire, in contrast, declares only `tar = "0.4"` for archive/compression — no gzip/xz/zstd/zip crate is a direct dependency there, so grimoire's compression handling (if any, on its OCI blob path) is either absent, uncompressed-only, or delegated entirely to a transitive dependency (e.g. the OCI client fork) outside this crate's declared surface; that is a gap worth flagging back to whoever owns grimoire's registry client, not something this file can resolve from ocx's tree alone.
19. `lzma-rust2` is an actively maintained fork (Nils Hasenbanck, 5 contributors, Apache-2.0) of a discontinued original `lzma-rust`, with a large download base (~3.3M/month, 565 dependent crates) and a release as recent as 2026-08-05 — it is not a niche or abandoned crate, which weakens any objection to standardizing on it over `liblzma`.
20. `liblzma`'s crate-level maintenance is fine on its own terms (active releases through 2026-08-09, dual Apache-2.0/MIT, static/wasm/parallel feature flags) — the concern here is never "is the Rust binding maintained," it is "does depending on it put a C parser, and the C project's advisory surface, into a cross-compiled security-sensitive binary that already has a pure-Rust decoder for the identical format."

## Findings

### 1. The xz duplication is real and both paths are live

`ocx/Cargo.toml` declares both `lzma-rust2 = "0.16.3"` and `liblzma = { version = "0.4", default-features = false, features = ["static"] }`. Source-level grep confirms both are exercised, on two structurally different pipelines:

- **Sync/local path** — `crates/ocx_lib/src/compression.rs::read_file` (line 310) constructs `lzma_rust2::XzReader::new(buffered, false)` for any `.tar.xz`/`.xz` file opened through `Archive::extract`/`Archive::extract_with_options` (`crates/ocx_lib/src/archive.rs:117-118`). This is exercised by ocx's own package-bundle round-trip tests (`crates/ocx_lib/src/package/bundle.rs`) and by the local-file install path (`crates/ocx_lib/src/package_manager/tasks/pull_local.rs:512`).
- **Async/registry path** — `crates/ocx_lib/src/oci/client.rs:917-941` constructs `async_compression::tokio::bufread::XzDecoder::new(...)` inside `pull_layer_with_caps`, driven off the live `oci::Descriptor.media_type` dispatch (`compression::CompressionAlgorithm::from_media_type`, `crates/ocx_lib/src/compression.rs:30-37`) for any layer whose media type is `application/vnd.oci.image.layer.v1.tar+xz`.

`lzma_rust2` is also used for **encoding** on both paths (`XzWriter`/`XzWriterMt` in `compression.rs`, `client.rs:3892-3894`) — encoding is single-sourced already; only decoding is duplicated.

### 2. Why the C decoder is on the async path at all

ocx's own `Cargo.toml` comment (lines 122-139) is unusually explicit and independently verifiable:

> "New transitive dep `liblzma` via `compression-codecs`: CVE-2025-31115 affects `lzma_stream_decoder_mt` (multithreaded path only); OCX uses `XzDecoder` (single-threaded), so the vulnerable code path is never reached."

`async-compression`'s docs confirm xz support now flows through a split `compression-codecs` crate rather than a direct C binding declared in `async-compression` itself ([docs.rs/async-compression](https://docs.rs/async-compression/latest/async_compression/)), and NVD confirms CVE-2025-31115 is scoped to `lzma_stream_decoder_mt` specifically, CVSS v4 8.7, XZ Utils 5.3.3alpha–5.8.0, fixed in 5.8.1 ([NVD CVE-2025-31115](https://nvd.nist.gov/vuln/detail/CVE-2025-31115)). ocx's `async-compression = "0.4.42"` pin is stated to bundle XZ ≥5.8.1. The repo's rationale is accurate as written.

What it does not cover: the xz project's own GitHub advisories list a second, more recent issue — a buffer overflow in `lzma_index_append()` (`GHSA-x872-m794-cxhv`, Low, 2026-03-31) ([xz security advisories](https://github.com/tukaani-project/xz/security/advisories)). Index parsing is not gated by thread count, so the existing "single-threaded only" argument does not automatically clear this one; it needs its own check against the bundled version.

### 3. `liblzma`'s `static` feature is a cross-compilation necessity, not a preference

The same Cargo.toml block explains: without `static`, `liblzma-sys`'s build script pkg-config-probes a host `liblzma` and links dynamically when found — on the macOS CI runner that bakes an absolute Homebrew path (`/opt/homebrew/...`) into the produced Mach-O, and the resulting `ocx` binary fails to start on a stock Mac without that exact path present. `dist-workspace.toml:13` lists the 8 shipped triples: `aarch64-apple-darwin`, `aarch64-unknown-linux-gnu`, `aarch64-unknown-linux-musl`, `aarch64-pc-windows-msvc`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`, `x86_64-pc-windows-msvc`. The two musl targets in particular have no system `liblzma` at all to dynamically link against, so `static` is not optional there — it is the only way `liblzma-sys` builds successfully. This is the cross-compilation cost the topic brief anticipated: a C decoder in a prebuilt cross-compiled binary is a build-matrix liability independent of its CVE history.

### 4. Removing the C decoder is architecturally straightforward, not just theoretically possible

The pipeline comment at `oci/client.rs:836-846` documents the current unwind order: `SyncIoBridge<Decoder<BufReader<ProgressReader<HashingAsyncReader<_>>>>>`. `SyncIoBridge` wraps the *decoder*, meaning decompression happens on the async (C-backed) side before the bytes ever become a sync `Read`. Nothing structurally requires that ordering: `HashingAsyncReader` and `ProgressReader` both operate on the *compressed* bytes already (explicitly, per the code's own comment: "digest computed over compressed wire bytes," "progress reflects download throughput, not decoded size" — `client.rs:787-791`), so `SyncIoBridge` could instead wrap `ProgressReader<HashingAsyncReader<_>>` directly, yielding a sync `Read` of *compressed* bytes one layer earlier. Feeding that into `lzma_rust2::XzReader` (already proven correct on the local path), `flate2::read::GzDecoder`, or `zstd::stream::read::Decoder` (both already used in `compression::read_file`) would decode entirely on the pure-Rust/sync side, and `async-compression` — along with its transitive `liblzma` dependency — would no longer be needed for decoding at all. This is a real refactor opportunity, not yet implemented; it is the basis for normative guidance candidate NG-1 below.

### 5. Not all C decoders are equally removable: zstd has no drop-in pure-Rust replacement in play

Of the five decompressors, two are C FFI: `liblzma` (xz) and `zstd`/`zstd-sys` (zstd) — confirmed by the `zstd` crate's own description, "a rust binding for the zstd compression library," MIT-licensed bindings around a vendored C library ([lib.rs/crates/zstd](https://lib.rs/crates/zstd)). `flate2` defaults to the pure-Rust `miniz_oxide` backend when no feature override is given ([lib.rs/crates/flate2](https://lib.rs/crates/flate2)), and ocx's `flate2 = "1.1.9"` declaration takes no feature override, so gzip is pure Rust as configured. `zip`'s `deflate` feature (as ocx configures it: `default-features = false, features = ["deflate"]`) is likewise the crate's pure-Rust deflate path, distinct from the C-backed `deflate-flate2-zlib`/`deflate-flate2-zlib-ng` variants ([lib.rs/crates/zip](https://lib.rs/crates/zip)). A pure-Rust zstd decoder (`ruzstd`) exists in the ecosystem but is unevaluated and unused here, and its production maturity relative to `zstd-sys` is not established by any source consulted. The xz duplication is therefore the addressable one; the zstd C dependency is comparably justified because there is no evidened equal-maturity pure-Rust substitute in ocx's graph today.

### 6. Media-type reachability: xz is a non-standard OCI extension; zip and "no compression" are both unreachable from the registry

The OCI image-spec's `media-types.md` defines exactly three layer types: `application/vnd.oci.image.layer.v1.tar`, `...tar+gzip`, `...tar+zstd` (plus deprecated non-distributable variants of the same three) — no xz variant exists in the spec ([OCI image-spec media-types.md](https://raw.githubusercontent.com/opencontainers/image-spec/main/media-types.md)). ocx's `MEDIA_TYPE_TAR_XZ = "application/vnd.oci.image.layer.v1.tar+xz"` (`crates/ocx_lib/src/media_type.rs:17`) is therefore a private extension: only an ocx-produced manifest referencing it is guaranteed to interoperate, since a spec-conformant registry client that only knows the three standard types cannot consume it. `pull_layer_with_caps` (`client.rs:747-749`) rejects any media type that doesn't map through `CompressionAlgorithm::from_media_type` — gzip, xz, and zstd are the only three that do — and it explicitly rejects `CompressionAlgorithm::None` (uncompressed layers) with `InvalidManifest` (`client.rs:976-981`). `.zip` is excluded even earlier: `media_type_from_filename` returns `None` for a `.zip` path, and `pull_local.rs` carries an explicit comment/test confirming a bare `.zip` local-package reference is refused (`pull_local.rs:1000-1020`). Net: gzip, xz, and zstd are all live on the registry path; `zip` and uncompressed tar are both dead weight there — `zip`'s only reachability is the local `Archive::create`/`extract` surface.

### 7. `zip` extraction posture: not vulnerable to the on-point 2025 CVE, and why

`RUSTSEC-2025-0168` / `CVE-2025-29787` / `GHSA-94vh-gphv-8pm8` (CVSS 7.3, High) affects `zip::read::ZipArchive::extract` and `zip::unstable::stream::ZipStreamReader::extract` in versions ≥1.3.0, <2.3.0: a symlink written earlier in the archive can be used, unvalidated, as a path component for a later entry, because the advisory notes the crate's own `enclosed_name()`-based sanitization "proved insufficient" against symlink-based redirection — the fix landed in 2.3.0 ([RUSTSEC-2025-0168](https://rustsec.org/advisories/RUSTSEC-2025-0168.html), [GHSA-94vh-gphv-8pm8](https://github.com/zip-rs/zip2/security/advisories/GHSA-94vh-gphv-8pm8)). ocx is doubly clear of this: it pins `zip = "8.6"` (patched since 2.3.0), and — more importantly — `archive/zip.rs::extract` never calls either vulnerable convenience method. It hand-rolls the walk: `entry.enclosed_name()` per entry, and for symlink entries specifically, reads the link target and passes it through `crate::symlink::validate_target(output, &output_path, target)` — the same root-boundary check the tar extractor uses — before calling `crate::symlink::create`. This is precisely the defense-in-depth the CVE shows the built-in method lacked.

### 8. `tar` extraction posture: patched against its own 2026 CVE, path-escape guard is named and tested

`RUSTSEC-2026-0067` / `CVE-2026-33056` (Medium, 5.1) affects `tar::Archive::unpack`/`unpack_in` before 0.4.45: `fs::metadata()` follows symlinks when checking whether an existing path is a directory, so a symlink-then-directory-of-the-same-name pair can redirect a `chmod` outside the extraction root ([RUSTSEC-2026-0067](https://rustsec.org/advisories/RUSTSEC-2026-0067.html)). ocx and grimoire both declare `tar = "0.4.46"` — already patched. ocx's own tar entry-path guard is independent of that CVE: `extract_from_archive` in `crates/ocx_lib/src/archive/tar.rs` rejects any entry whose stripped path `is_absolute()` or trips `crate::utility::fs::path::escapes_root` (`tar.rs:206-208`) before any directory or file is created, and symlink entries go through the same `crate::symlink::validate_target` used by the zip path. Both are exercised by dedicated tests (`test_extract_rejects_path_traversal_tar`, `test_extract_rejects_escaping_symlink_tar`, `archive.rs:498-522, 546-569`).

### 9. Output-size capping is per-pipeline, not per-decoder-API, and one path has none

None of `flate2`, `zstd`, or `async-compression`'s tokio decoders expose a constructor-level maximum-output-bytes argument — capping is enforced entirely by a wrapping wrapper reader. On the OCI pull path, that wrapper is `std::io::Read::take(cap_with_probe)` applied to the `SyncIoBridge` around whichever decoder is selected (`client.rs:924, 946, 964` — identical pattern for xz, gzip, and zstd), with `cap_with_probe = decompressed_cap + 1` used to distinguish "exactly at the cap" from "exceeded it" (`client.rs:873`). This wrapper is decoder-agnostic: it works identically whether the underlying decoder is `liblzma`, `flate2`, or `zstd-sys`, because it caps the *decoded byte count*, not anything decoder-internal. The local sync path (`compression::read_file`, `compression.rs:294-341`) has no such wrapper at all — it returns a bare `Box<dyn Read + Send>` for `.xz`/`.gz`/`.zst` files, with no `.take()` and no grimoire-style `CappedSink` analogue. `archive/zip.rs::extract`'s per-entry `std::io::copy(&mut entry, &mut outfile)` (`zip.rs:257-260`) is likewise uncapped, both per-entry and in aggregate across the archive.

### 10. `deny.toml`'s `[bans]` axis is essentially unused and is the right lever for this topic

ocx's `deny.toml` (repo root) currently sets `[bans] multiple-versions = "warn"` and nothing else — no `deny`, `skip`, or `skip-tree` entries exist. cargo-deny's own bans docs give the exact idiom for banning a crate in favor of another that does the same job: set `multiple-versions = 'allow'` (or leave as-is) and add `deny = [{ crate = "<name>", use-instead = "<replacement>" }]` entries, optionally scoped by version range ([cargo-deny bans/cfg.md](https://raw.githubusercontent.com/EmbarkStudios/cargo-deny/main/docs/src/checks/bans/cfg.md)). This maps directly onto the "one decoder per format" deliverable: once (or if) the async pull path stops needing `liblzma` (finding 4), a `deny` entry citing `use-instead = "lzma-rust2"` turns the decision into something `cargo deny check bans` enforces automatically rather than a comment that can silently rot.

### 11. `lzma-rust2` and `liblzma` are both actively maintained; this is not a "drop the unmaintained one" decision

`lzma-rust2` is a maintained fork (by Nils Hasenbanck, 5 contributors) of a discontinued original `lzma-rust`, Apache-2.0, ~3.3M downloads/month across 565 dependent crates, latest release 2026-08-05 ([lib.rs/crates/lzma-rust2](https://lib.rs/crates/lzma-rust2)). `liblzma` is also active (latest 0.4.8, 2026-08-09), dual Apache-2.0/MIT, maintained by the Portable-Network-Archive Developers group, with `static`/`wasm`/`parallel` feature flags and a progressively-updated vendored XZ version (5.4→5.6→5.8 across its 0.2.x→0.4.x line) ([lib.rs/crates/liblzma](https://lib.rs/crates/liblzma)). The case for consolidating on `lzma-rust2` is architectural (one fewer C parser touching untrusted input, simpler cross-compilation, matches the topic's framing that a C decoder in a cross-compiled binary is itself a cost) — not a maintenance-quality argument in either direction.

### 12. grimoire's compression surface is undeclared relative to ocx's

grimoire's `Cargo.toml` declares only `tar = "0.4"` among archive/compression crates — no `flate2`, `zstd`, `zip`, `async-compression`, or lzma crate appears as a direct dependency (`grep -n "flate2\|zstd\|lzma\|zip\s*=\|tar\s*=\|async-compression" grimoire/Cargo.toml` → one match, `tar = "0.4"`). grimoire does have a `CappedSink` (`src/oci/access/registry_client.rs`), confirming it caps *something* on its blob path, but with no declared compression crate, either grimoire's registry layers are uncompressed, or decompression is delegated to a transitive dependency outside this file's visibility. This is noted for completeness per the topic brief's cross-reference to grimoire's `CappedSink`; it is not resolved here.

## Normative guidance candidates

1. **NG-1. Move `SyncIoBridge` to wrap the pre-decompression reader chain, not the decoder, on the OCI pull path.** Rationale: this is the concrete refactor that lets ocx decode xz/gzip/zstd registry layers with the same pure-Rust decoders already used on the local path, eliminating `async-compression`'s C `liblzma` dependency from the cross-compiled binary entirely (finding 4, 5). VERIFICATION: `cargo tree -p ocx_lib -e normal | grep -i liblzma` returns nothing after the refactor, and `cargo build --target x86_64-unknown-linux-musl` (or the equivalent `dist` job) no longer needs the `liblzma`/`static` feature edge in `Cargo.toml`.
2. **NG-2. Once NG-1 lands, ban `liblzma`/`liblzma-sys`/`xz2` in `deny.toml`'s `[bans].deny`, citing `use-instead = "lzma-rust2"`.** Rationale: makes "one xz decoder" a CI-enforced fact instead of a comment that can rot the next time a dependency bump reintroduces the transitive edge (finding 10). VERIFICATION: `cargo deny check bans` fails if any crate in the graph re-adds `liblzma`/`liblzma-sys`/`xz2` as a direct or transitive dependency.
3. **NG-3. Until NG-1 lands, do not treat the CVE-2025-31115 rationale as evergreen — re-check it against every new xz/liblzma advisory, not just multithreaded-decoder ones.** Rationale: `GHSA-x872-m794-cxhv` (index-parsing overflow) is not covered by the "single-threaded only" argument, because index parsing runs regardless of thread count (finding 2, 4). VERIFICATION: on every `liblzma`/`liblzma-sys` version bump, `cargo deny check advisories` output is read in full, not filtered to only advisories mentioning "multithread."
4. **NG-4. Never call `zip::ZipArchive::extract` or `zip::unstable::stream::ZipStreamReader::extract` directly; keep the hand-rolled `enclosed_name()` + `symlink::validate_target` loop.** Rationale: this is the exact API surface CVE-2025-29787 broke even with `enclosed_name()` sanitization present, and ocx's current implementation already avoids it (finding 7) — this rule exists to keep it that way through future edits. VERIFICATION: `grep -rn "ZipArchive::extract\|ZipStreamReader::extract" crates/` returns nothing outside test fixtures that assert the vulnerable pattern is absent.
5. **NG-5. Wrap `compression::read_file`'s local-path decoders (xz/gzip/zstd) in a decompressed-size `.take()` cap, mirroring the OCI pull path's `cap_with_probe` pattern.** Rationale: finding 9 shows this path has zero output-size enforcement today, unlike the registry path — any caller that feeds it an attacker-influenced local file (e.g. a locally-built or downloaded-then-extracted package archive) has no CWE-400 protection. VERIFICATION: a test analogous to `decompressed_cap_hit_yields_cap_exceeded_not_digest_mismatch` (`oci/client.rs:3211`) exists for `Archive::extract` on a crafted `.tar.xz`/`.tar.gz`/`.tar.zst` bomb.
6. **NG-6. Wrap `archive/zip.rs::extract`'s per-entry `std::io::copy` in a matching decompressed-size cap, both per-entry and cumulative across the archive.** Rationale: finding 16 — this is the one decoder among the five with literally no size bound at any layer today. VERIFICATION: a crafted zip with a high-ratio deflate bomb entry is rejected before writing more than the cap to disk, exercised by a new test alongside the existing `test_extract_rejects_path_traversal_tar`-style regression suite.
7. **NG-7. Do not add a gzip/zip/zstd "zlib"/"zlib-ng"/C-backend feature to `flate2` or `zip` without a stated reason.** Rationale: both are currently pure Rust as configured (finding 5); silently picking up a C backend feature flag (e.g. via a transitive default-features union) would reintroduce the exact C-decoder-on-untrusted-input problem this topic exists to police, for formats that don't need it. VERIFICATION: `cargo tree -e features -p flate2` / `-p zip` shows no `zlib`/`libz-sys`/`miniz-sys` edge.
8. **NG-8. Document the OCI-spec-vs-ocx-extension status of the xz media type at the point it's declared, not just in a design doc.** Rationale: finding 6 — `application/vnd.oci.image.layer.v1.tar+xz` looks like a standard OCI type but isn't; a future contributor (or agent) reading `media_type.rs` cold has no signal that xz interop stops at the ocx-to-ocx boundary. VERIFICATION: `MEDIA_TYPE_TAR_XZ`'s doc comment states explicitly that it is non-standard relative to the OCI image-spec's three defined layer types.

## AI-agent angle

An LLM asked to "add a compression format" or "fix a decompression bug" in this codebase will, by default: (a) reach for whichever of `flate2`/`zstd`/`async-compression`/`lzma-rust2`/`liblzma` it recognizes fastest, without checking that two of them already solve the same problem on different pipelines — the duplication in finding 1 is exactly the kind of thing that's invisible from a single-file diff and only shows up on a full-repo grep across `compression.rs` and `oci/client.rs`; (b) assume a decoder crate's constructor takes a size limit, because that's the mental model from higher-level HTTP/JSON libraries, when in fact none of the five here do — the cap is always an external wrapping `.take()`, and an agent asked to "cap this decoder" is likely to go hunting for a nonexistent builder option instead of wrapping the reader; (c) call `zip::ZipArchive::extract()` because it's the crate's documented one-liner, reintroducing the exact CVE-2025-29787 surface ocx currently avoids by hand-rolling the loop — the convenience method is the *wrong* answer here and looks like the *obviously right* one; (d) assume `application/vnd.oci.image.layer.v1.tar+xz` is spec-standard because it follows the same naming pattern as the two real OCI types sitting next to it in the same file. The smallest mechanical check for all four: before touching anything under `archive/` or `oci/client.rs`'s decoder dispatch, run `grep -rn "XzReader\|XzDecoder\|GzDecoder\|GzipDecoder\|zstd::stream\|ZstdDecoder\|ZipArchive" crates/*/src` and read every hit's caller before deciding a new call site is needed — the answer "there's already a decoder for this format here" is far more often correct than "add a new one."

## Contested / evolving

- **Whether `liblzma` should be removed is a proposal here, not a landed decision.** Findings 1 and 4 establish that it's duplicative and that removal is architecturally clean, but no PR or ADR in the repo currently commits to that refactor — the Cargo.toml comment defends *keeping* `liblzma` (on CVE-2025-31115 grounds), not removing it. NG-1/NG-2 are this file's recommendation, not a description of settled ocx policy. Direction: the repo's own comment already treats the C dependency as something to justify rather than something taken for granted, which is a precondition for eventually removing it.
- **Whether a non-registry local `.zip`/`.tar.xz` input counts as "untrusted" for capping purposes (NG-5, NG-6) is a scope judgment call, not a settled fact.** The registry path is unambiguously untrusted (a remote registry blob); the local path is reached via CLI flags pointing at a filesystem path the invoking user chose. Whether that user-chosen path is itself attacker-influenced (e.g., a downloaded file, a CI artifact) depends on how ocx's CLI surfaces are used in practice, which this file doesn't have visibility into. Direction: the topic brief's framing ("every one of these is an untrusted-input parser") argues for capping regardless of the answer, on cost-of-being-wrong grounds — a cap costs a `.take()` wrapper; an uncapped local decompression bomb costs disk/memory exhaustion in a CLI a user might run against a package they didn't author.
- **zstd's C dependency (`zstd-sys`) is the one this file does *not* recommend removing, unlike liblzma — and that asymmetry could be re-litigated.** `ruzstd` exists as a pure-Rust zstd decoder but its production maturity relative to `zstd-sys` was not established by any source consulted here; if a future investigation finds `ruzstd` is in fact production-ready, the "zstd is comparably harder to remove" claim in findings 5/8 should be revisited rather than taken as permanent.
