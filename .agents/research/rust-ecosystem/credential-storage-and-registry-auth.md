## Summary

1. Both tools already read credentials through **`~/.docker/config.json`** via the `docker_credential` crate (a vendored, patched fork in `external/docker_credential/` in both repos) — this is the *primary* tier today, not a proposal.
2. `grim` has a **write** path (`grim login`/`grim logout`, `src/auth/store.rs`) that `ocx` does not yet ship in the audited tree — `ocx`'s `crates/ocx_lib/src/auth/store.rs` exists per the ADR design but the read chain (`auth.rs`) is what's wired to `ocx pull`/`ocx install`.
3. `ocx`'s read chain resolution order is **env vars first, Docker credentials second, anonymous third** (`OCX_AUTH_<SLUG>_{TYPE,USER,TOKEN}` → `docker_credential::get_credential` → `RegistryAuth::Anonymous`) — env outranks the credential store, confirmed in `crates/ocx_lib/src/auth.rs::get_impl`.
4. `grim`'s credential-store precedence for **writes** is `credHelpers[registry]` → `credsStore` → plaintext `auths[registry]` (gated behind `--allow-insecure-store`, default `false`) — `src/auth/store.rs` doc comment and `StoreOptions::allow_plaintext_put`.
5. When `grim` does fall through to the plaintext tier, the file is created **mode `0600`** from first byte (`ensure_config_file`) and re-tightened to `0600` after every write (`restrict_permissions`) — verified by an inline unit test (`plaintext_put_creates_file_mode_0600`).
6. Grimoire's `Credential` struct wraps `password` and `identity_token` in `secrecy::SecretString` for its *entire* struct lifetime; the plaintext basic-auth string is additionally wrapped in `secrecy::zeroize::Zeroizing` at the point it's base64-encoded, specifically to zero the heap-allocated `"{user}:{pass}"` intermediate that `secrecy` itself does not own (`src/auth/credential.rs`, `src/oci/access/registry_client.rs:233`).
7. Secrecy protection **ends at the OCI-client boundary**: `oci_client::secrets::RegistryAuth` (both repos depend on the same vendored `oci-client` fork) stores `Basic(String, String)` / `Bearer(String)` as plain `String`, not `SecretString` — it is *not* zeroized on drop. It is, however, hand-redacted in `Debug` (`external/rust-oci-client/src/secrets.rs`), so a stray `{:?}` does not leak it, but a heap dump or swap after use would.
8. `ocx`'s `Auth` type caches this same non-zeroizing `RegistryAuth` in an `Arc<RwLock<HashMap<String, oci::native::Auth>>>` for the life of the process (`crates/ocx_lib/src/auth.rs::Auth::cache`) — credentials outlive their use, unprotected, once they cross into the OCI-client type.
9. Grimoire found and fixed a real CWE-532 leak surface: the fork's `CredentialRetrievalError::HelperFailure { stdout, stderr, .. }` `Display` impl prints the helper's raw stdout/stderr verbatim, which can contain credential JSON on a misbehaving helper — grimoire's `map_helper_err` intercepts and redacts this specific variant before it can reach the `{err:#}` chain (`src/oci/access/registry_client.rs:264-278`).
10. `ocx`'s equivalent path does **not** apply the same redaction: `AuthError::Helper(#[source] docker_credential::CredentialRetrievalError)` passes the fork's `HelperFailure` through untouched, and `ocx`'s `main.rs` logs `log::error!("{err:#}")` which walks the full source chain — this is a live, unmitigated leak surface in `ocx` today (confirmed by reading `crates/ocx_lib/src/auth/error.rs` and `crates/ocx_cli/src/main.rs:24` side by side).
11. **There is no `keyring` dependency in either repo**, and OCX already produced its own ADR rejecting it for v1 (`.claude/artifacts/adr_ocx_login_credential_store.md`, Option C) — the research here updates that ADR's own "revisit" trigger, which has since fired.
12. The `keyring` crate has undergone a real architectural split as of 2026: the historical `keyring` crate (now v4.1.6, released 2026-08-01) is a thin legacy-compat wrapper; the actual API lives in **`keyring-core`** (v1.0.0, released 2026-04-21), with each OS backend now a separate crate (`apple-native-keyring-store`, `windows-native-keyring-store`, `zbus-secret-service-keyring-store`, `dbus-secret-service-keyring-store`, `linux-keyutils-keyring-store`) — this is the "keyring-core reaches production" trigger the OCX ADR flagged as a future re-evaluation condition, and it fired within the same year.
13. `keyring`'s default Linux backend is `zbus-secret-service-keyring-store` (async D-Bus Secret Service) — this requires a running D-Bus session bus and is exactly what fails on a headless CI runner or a bare container.
14. Failure on a missing D-Bus session is a typed `Result`, not a panic: store construction returns `Result<Arc<Self>, keyring_core::Error>`, and the crate's non-exhaustive `Error` enum has a dedicated `NoStorageAccess(PlatformError)` variant plus `PlatformFailure(PlatformError)` for exactly this case — a caller can catch it and fall through a tier.
15. `linux-keyutils-keyring-store` is the CI-friendly alternative: it uses the in-kernel `keyctl` facility, needs no D-Bus daemon, and its own README explicitly recommends itself "on a headless linux box, or one that doesn't come with gnome-keyring." Its own README equally explicitly warns it is **in-memory only, does not persist across reboots**, and the user-persistent keyring's default expiry is "a few days" — so it is not a substitute for the docker-config-on-disk tier for anything that must survive a container's lifetime, only a same-session cache.
16. `docker_credential` (both the upstream `keirlawson/docker_credential` and both repos' fork) delegates entirely to whatever `docker-credential-*` helper is already on `PATH` and configured in `~/.docker/config.json` — meaning a user's existing `docker login ghcr.io` (or `gh auth login` piping into a helper) is inherited for free, and nothing new is stored by grim/ocx unless the plaintext fallback tier is explicitly opted into.
17. `docker_credential` does **not** cover: OIDC/device-code flows, GitHub Actions' `GITHUB_TOKEN`/OIDC-to-registry-token exchange, or any registry auth that isn't expressible in the Docker credential-helper wire protocol (`{ServerURL, Username, Secret}` JSON over stdin/stdout) — those are exactly what the env-var tier (`OCX_AUTH_*`, CI `GH_TOKEN`) exists to cover.
18. `secrecy`'s own documentation states its limits plainly: it wipes what it owns on drop and blocks accidental `Debug`/serialization, but it explicitly does **not** protect intermediate heap allocations created during a clone, a `String` conversion, or deserialization that happens outside the wrapper — which is precisely the gap grimoire's `dup_credential` and the plaintext-tier `Zeroizing` wrapper are compensating for by hand.
19. Neither repo's `Cargo.lock` contains `keyring`, `keyring-core`, or any OS-keychain backend crate — confirmed by direct grep; the "no keyring dependency" premise of this research is accurate as of the audited tree.
20. A tiered storage scheme — credential helper (existing Docker/Podman helper) → OS keychain (`keyring-core` + `zbus-secret-service-keyring-store`/`apple-native-keyring-store`/`windows-native-keyring-store`) → env var (`OCX_AUTH_*`/CI token) → refuse (or opt-in plaintext) — covers every environment in the fleet's matrix (dev laptop with Docker Desktop, dev laptop with no Docker, headless CI, container with no D-Bus) without ever requiring a plaintext file unless the operator explicitly opts in.

## Findings

### 1. The credential lifecycle as it exists today, traced end to end

**Entry points.**
- Interactive: `grim login` prompts via `src/auth/prompt.rs`, which reads a username on stdin (echoed) and a password via `rpassword::read_password()` (masked), refusing a non-TTY stdin with `io::ErrorKind::Unsupported`. The prompt text goes to **stderr**, keeping stdout clean for `--format json`.
- Programmatic/CI: `OCX_AUTH_<REGISTRY_SLUG>_{TYPE,USER,TOKEN}` env vars, resolved in `ocx`'s `crates/ocx_lib/src/auth.rs::get_env_auth`. `TYPE` is one of `anonymous`/`basic`/`token`/`bearer`; when `TYPE` is unset, the code still infers `Basic` from a `USER`+`TOKEN` pair or `Bearer` from `TOKEN` alone.
- Docker credential helper: both repos' OCI clients call `docker_credential::get_credential(canonical_registry)`, which reads `~/.docker/config.json`, resolves `credHelpers[registry]` → `credsStore` → the plaintext `auths[registry]` entry, and if a helper is configured, shells out to the `docker-credential-<name>` binary with the `get` verb and the registry URL on stdin.
- No CI-OIDC path exists in-tree for registry auth (only for the unrelated `catalog/forge.rs` GitHub/GitLab announce-token flow, which is a separate concern from registry pull/push credentials).

**Where it lives at rest.** Only `~/.docker/config.json` (or `$DOCKER_CONFIG/config.json`) — grim's `DockerCredentialStore` is the only writer, and only when `allow_plaintext_put` is set (default `false`; opt-in flag documented as `--allow-insecure-store`). No other on-disk location is written by either tool. Local read: `/home/mherwig/dev/grimoire/src/auth/store.rs`.

**File mode.** `ensure_config_file` creates a fresh file at mode `0o600` before the first secret write (Unix `OpenOptionsExt::mode`); every write additionally calls `restrict_permissions`, which re-applies `0o600` after `atomic_write` (which otherwise leaves ordinary state files at `0o644`). Pinned by the inline test `plaintext_put_creates_file_mode_0600`. Non-Unix (`restrict_permissions` under `#[cfg(not(unix))]`) is a no-op — Windows relies on the user-profile ACL instead, which is the platform norm but is not independently enforced by the tool.

**Plaintext-in-config-file, confirmed and scoped.** When it happens (only under the explicit opt-in), the entry is `base64(username:password)` under `auths[registry].auth`, or the raw `identitytoken` string under `auths[registry].identitytoken` — both are base64/plaintext-equivalent, not encryption, matching the Docker config schema exactly (`put_blocking` in `store.rs`). This is the documented lowest-priority, explicitly-gated tier — never the default outcome of `grim login`.

**secrecy coverage.** `Credential { username: String, password: SecretString, identity_token: SecretString }` (`src/auth/credential.rs`) wraps every secret field for the struct's whole life; `Debug` is derived (not hand-rolled) and is safe only because `SecretString`'s own `Debug` impl redacts — confirmed by the inline test `debug_redacts_secret_fields`. The wrapping holds through construction, store `put`/`get`, and the `dup_credential` clone needed to move a `&Credential` into a `spawn_blocking` closure — the doc comment on `dup_credential` names the one deliberate, minimal exposure window (a heap `String` during the move, immediately re-wrapped) as accepted risk, not an oversight.

**Where secrecy coverage ends.** The moment a `Credential` becomes an `oci_client::secrets::RegistryAuth` (`to_docker_credential` in grim; the `Ok(DockerCredential::UsernamePassword(user, pass)) => RegistryAuth::Basic(user, pass)` arm in `oci/access/registry_client.rs`), the value becomes a plain `String` inside a third-party type this codebase does not own. `RegistryAuth`'s `Debug` is hand-redacted (`external/rust-oci-client/src/secrets.rs`) but it derives `Clone` and has no `Drop` impl — no zeroization. `ocx`'s `Auth::cache` (`Arc<RwLock<HashMap<String, RegistryAuth>>>`) then holds this un-zeroized value for the process's whole life once any registry has been authenticated to once.

### 2. `keyring` / `keyring-core` as the OS-keychain tier

The crate the ecosystem calls "`keyring`" split during 2026. `keyring` (crates.io, currently v4.1.6, released 2026-08-01 — [Cargo.toml](https://github.com/open-source-cooperative/keyring-rs/blob/main/Cargo.toml)) is now a thin, legacy-API-compatible wrapper whose default (`v1`) feature pulls in exactly three backend crates: `apple-native-keyring-store/keychain`, `windows-native-keyring-store`, and `zbus-secret-service-keyring-store`. The actual cross-platform API and the `Error` type moved into **`keyring-core`** (v1.0.0, released 2026-04-21 — [release list](https://github.com/open-source-cooperative/keyring-core/releases)), and every OS backend is now its own crate that a consumer opts into individually ([keyring-rs README](https://github.com/open-source-cooperative/keyring-rs/blob/main/README.md)):

| Platform | Backend crate | Underlying mechanism |
|---|---|---|
| macOS | `apple-native-keyring-store` | Keychain |
| Windows | `windows-native-keyring-store` | Credential Manager |
| Linux (default) | `zbus-secret-service-keyring-store` (async) / `dbus-secret-service-keyring-store` (sync, `crypto-rust`/`crypto-openssl` feature required) | D-Bus Secret Service |
| Linux (CI/headless) | `linux-keyutils-keyring-store` | kernel `keyctl` facility |

**Headless-Linux behaviour, established from source, not docs prose.** `dbus-secret-service-keyring-store::Store::new()` returns `Result<Arc<Self>>`, not a bare value or a panic ([`src/store.rs`](https://github.com/open-source-cooperative/dbus-secret-service-keyring-store/blob/main/src/store.rs)). `keyring-core`'s `Error` enum is `#[non_exhaustive]` and carries `PlatformFailure(PlatformError)` and `NoStorageAccess(PlatformError)` variants specifically for "the underlying secure storage... could not be accessed," with the platform detail attached ([`src/error.rs`](https://github.com/open-source-cooperative/keyring-core/blob/main/src/error.rs)). A D-Bus-less container therefore surfaces a typed, catchable error at store-construction or first-use time — it degrades, it does not panic.

**The CI-safe fallback is a different backend, with a real caveat.** `linux-keyutils-keyring-store`'s own README explicitly pitches itself for "a headless linux box, or one that doesn't come with gnome-keyring," because `keyctl` is a kernel facility present unconditionally on Linux ([README](https://github.com/open-source-cooperative/linux-keyutils-keyring-store/blob/main/README.md)). But the same README is equally explicit that the store is **in-memory, does not survive a reboot, and the user's persistent keyring's default expiry is on the order of days** — the README's own sample code assumes `get_password` can and will fail and plans a re-prompt/re-load fallback. For grim/ocx, this makes `keyutils` suitable only as a same-session cache inside one CI job, never as the credential's durable home — the durable home for CI remains the env-var tier.

**This closes an open question in OCX's own ADR.** `/home/mherwig/dev/ocx/.claude/artifacts/adr_ocx_login_credential_store.md` rejected `keyring-core` for v1 specifically because, at authoring time (2026-05-14), it was "not for production" and named "`keyring-core` v1.0 reaches broader adoption" as a condition to re-evaluate. `keyring-core` v1.0.0 shipped 2026-04-21 — before the ADR was even written — and the wrapper crate's own README now states the split is complete and stable. The re-evaluation trigger has fired.

### 3. `docker_credential`: what it does and does not cover

Both repos vendor a patched fork of [`keirlawson/docker_credential`](https://github.com/keirlawson/docker_credential) ("A Rust library for reading a user's Docker credentials from config") at `external/docker_credential/`, pinned via `[patch.crates-io]`, per the ADR's Option A. Upstream is read-only (`get_credential`); the fork adds `store_credential`/`erase_credential`/`list_credentials` by extracting a shared `run_helper` subprocess primitive, matching the wire protocol documented by [`docker/docker-credential-helpers`](https://github.com/docker/docker-credential-helpers) (`{ServerURL, Username, Secret}` JSON via stdin/stdout, one of `get`/`store`/`erase`/`list` as argv).

Delegating to the user's existing helper is the right primary path: it means `grim`/`ocx` never need to ask the user to log in again if `docker login ghcr.io` (or `gh auth login`, or a `docker-credential-ecr-login`-style CI helper) already put a credential in the platform's real keychain via a helper binary — nothing new is stored, and grim/ocx inherit whatever security posture the user already chose.

What it does not cover: any auth flow that isn't shaped like the Docker helper protocol. Concretely — OIDC device-code flows, GitHub Actions' ambient OIDC token exchanged for a short-lived registry token, and any registry-specific bearer-token minting flow. These are out of scope for `docker_credential` by design; they are exactly what the env-var tier is for.

### 4. Leak surfaces — greps and what each catches

| Surface | Grep | What it catches |
|---|---|---|
| `#[derive(Debug)]` on a type holding a raw credential `String` (not `SecretString`) | `rg -B3 'password\s*:\s*String\|token\s*:\s*String\|secret\s*:\s*String' --type rust \| rg -B1 'derive.*Debug'` | Any struct that would print a secret verbatim via `{:?}`; `Credential` in both repos passes because its `String` fields are `username`/non-secret only |
| Credentials in `tracing`/`log` fields | `rg -n 'tracing::(info\|debug\|warn\|error)!\(.*(password\|token\|secret\|credential)' --type rust` and same for `log::` | Structured-log fields that interpolate a secret by name; both repos currently pass (calls log the *registry*, not the credential) |
| Credentials reaching the exit-code `{err:#}` chain | `rg -n 'HelperFailure' --type rust` then manually check each hit's `Display`/`#[source]` wiring for a redaction step before `main.rs`'s error-printing call | This is the exact check that found finding #10 above: grim redacts (`map_helper_err`), ocx does not |
| Plain-`String` secret Display leaking through `#[error("{0}")]`/`#[from]` | `rg -A2 '#\[error\("\{0\}"\)\]' --type rust` cross-checked against ERR-03/ERR-17 in `rules/rust-quality/errors.md` | A wrapped error whose `Display` prints the inner value directly, bypassing any redaction the inner type has |
| Tokens on argv (visible via `/proc/<pid>/cmdline`, `ps`) | `rg -n 'Command::new\|process::Command' --type rust -A5 \| rg -i 'password\|token\|secret'` | The credential-helper protocol already avoids this (stdin-only per the ADR's block-tier requirement #3); the grep confirms no other subprocess call passes a secret as an arg |
| Tokens in a spawned subprocess's *environment* | `rg -n '\.env\(' --type rust -B3 \| rg -i 'password\|token\|secret'` | A child process (e.g. a credential helper, or a shelled-out git/gh call) inheriting a secret via `Command::env` rather than stdin; visible to anything that can read `/proc/<pid>/environ` on the same host |
| Non-`SecretString` field holding a credential | `rg -n 'RegistryAuth::Basic\|RegistryAuth::Bearer' --type rust` | Every call site is a documented crossing of the secrecy boundary (finding #7); each should be reviewed, not banned outright, since it's inherent to the vendored `oci-client` dependency |

## Normative guidance candidates

1. **No credential is ever written to a config file except through the gated, explicit plaintext-fallback tier (`--allow-insecure-store`), and never as anything but base64-wrapped `auths[registry].auth`/`identitytoken` inside `~/.docker/config.json`.** Rationale: matches Docker/oras interop and keeps the default path helper-or-refuse. VERIFICATION: `rg -n 'allow_plaintext_put\|allow-insecure-store' src/` shows the flag defaults false and gates every write to `config.json`'s `auths` map; no other `fs::write`/`atomic_write` call in the auth module writes outside that gate.
2. **Every struct field that ever holds a raw credential value is `secrecy::SecretString` (or `SecretBox<[u8]>`), never `String`, for as long as the codebase owns the type.** Rationale: `Debug`-redaction and drop-zeroization by construction beat remembering it per call site (mirrors existing rule ERR-17). VERIFICATION: `rg -n 'password\s*:\s*String\|token\s*:\s*String\|secret\s*:\s*String' --type rust` in `auth/`, `oci/` modules returns nothing outside vendored third-party types.
3. **Any crossing into a third-party type that does not use `secrecy` (e.g. `oci_client::secrets::RegistryAuth`) is a named, commented boundary, and the value's lifetime past that boundary is minimized — not cached in a long-lived map.** Rationale: the vendored `oci-client` fork's `RegistryAuth` is plain `String` with no `Drop`; caching it (as `ocx::Auth::cache` does today) extends the un-zeroized exposure window for the process's entire life. VERIFICATION: `rg -n 'RegistryAuth\b' --type rust` — check every long-lived container (`HashMap`, `Arc<RwLock<_>>`, `static`) that stores one; each needs a TTL/eviction or a documented rationale for why indefinite caching is acceptable.
4. **Every `Display` impl reachable from the top-level `{err:#}` print must be audited for raw subprocess output before it ships — a credential helper's stdout/stderr is not safe to print verbatim.** Rationale: this is CWE-532, and it is not hypothetical — grim found and fixed exactly this in its own fork's `HelperFailure` variant; ocx has not. VERIFICATION: `rg -n 'HelperFailure' --type rust` in `ocx`'s `auth/error.rs` and `oci.rs` — confirm a redaction wrapper analogous to grim's `map_helper_err` exists before `AuthError::Helper` is constructed from a `HelperFailure`.
5. **Adopt a four-tier credential resolution, in this precedence, for any new "does this registry have a credential" code path: (1) existing `docker-credential-*` helper via `docker_credential`, (2) OS keychain via `keyring-core` + the platform-appropriate backend crate (`apple-native-keyring-store` / `windows-native-keyring-store` / `zbus-secret-service-keyring-store`, with `linux-keyutils-keyring-store` as the same-tier CI/headless variant), (3) `OCX_AUTH_<REGISTRY>_*` / equivalent env vars, (4) refuse (or the explicit plaintext opt-in).** Rationale: covers the full environment matrix — dev machine with Docker Desktop, dev machine with no Docker but a real desktop keychain, a container/CI runner with no D-Bus session — without ever defaulting to plaintext. VERIFICATION: a table-driven test that stubs each tier's absence in turn (no helper on PATH, no D-Bus socket, no env var set) and asserts the resolver falls through to the next tier rather than erroring or panicking.
6. **`grim login`'s OS-keychain tier, if added, must call `keyring_core::Error::NoStorageAccess`/`PlatformFailure` a benign, silent fall-through — never surface it as a hard failure — matching the existing "infallible-by-design" posture of `RegistryClient::auth_for` (`grim`) and `get_or_fallback` (`ocx`).** Rationale: a broken/missing keychain must not block an otherwise-anonymous-eligible pull, same logic already applied to a broken Docker credential helper. VERIFICATION: unit test constructing the keychain tier against a mock/absent backend, asserting the caller falls through rather than propagating the error.
7. **Never introduce a subprocess call (credential helper or otherwise) that passes a secret via argv; stdin only.** Rationale: argv is visible to any co-resident process via `/proc/<pid>/cmdline` or `ps -ef`; this is already an explicit block-tier requirement in the OCX ADR (#3) and is already how the fork's `run_helper` is built. VERIFICATION: `rg -n 'Command::new\|process::Command' --type rust -A6 \| rg -i 'password\|token\|secret'` returns nothing.
8. **`Cargo.lock` in both repos should gain `keyring-core` + the appropriate per-platform backend crates only when the OS-keychain tier actually lands as code — do not add the dependency speculatively.** Rationale: YAGNI; the ADR's own "Option C — rejected, revisit" reasoning is sound engineering discipline and should be preserved even as the revisit condition fires — land the tier as a scoped follow-up, not a drive-by dependency add. VERIFICATION: `rg -n 'keyring' Cargo.toml Cargo.lock` stays empty until an ADR or PR explicitly adds the tier.

## AI-agent angle

An LLM asked to "add OS-keychain support" to grim/ocx will, by default, reach for the old, familiar `keyring = "2"` or `keyring = "3"` API shape it has seen most in training data (single crate, feature-flag-selected backend, synchronous `Entry::new(service, user).get_password()`) — that API no longer matches what's on crates.io. The smallest mechanical check: after generating any `Cargo.toml` diff that adds `keyring`, run `cargo tree -p keyring-core -e features` (or `-p keyring` if the legacy wrapper crate name was used) and confirm `keyring-core` v1.x plus an explicit per-platform *-keyring-store crate appear, not a monolithic v2/v3 `keyring` with baked-in features. A model will also default to treating a keychain lookup failure as fatal (`?` straight through) rather than as the benign fall-through both repos already apply to a missing/broken Docker credential helper — the check is `rg -n 'NoStorageAccess\|PlatformFailure' src/` returning a match inside a `match`/`Ok(None)` arm, never inside a bare `?`. Finally, a model asked to "fix the secret leak in the error chain" is likely to patch only the call site it was pointed at and miss that the same `docker_credential::CredentialRetrievalError::HelperFailure` type is `#[source]`-wrapped from at least two independent call sites across the two repos (grim's `registry_client.rs` and ocx's `auth/error.rs`) — the mechanical check is `rg -n 'HelperFailure' --type rust` across the whole workspace, not just the file in the bug report, before declaring the fix complete.

## Contested / evolving

- **`keyring-core` production readiness is a live, recent shift, not settled folklore.** As of the OCX ADR's authoring (2026-05-14), `keyring-core` was assessed as "likely production-ready" but deferred anyway out of caution; `keyring-core` v1.0.0 had, in fact, already shipped three weeks earlier (2026-04-21), and the historical `keyring` crate has since been fully repositioned as a legacy-compat sample wrapper (v4.1.6, 2026-08-01 — days before this research). Direction: the split is complete and the new shape (`keyring-core` + separate backend crates) is the one to design against going forward; do not add the old-style monolithic `keyring` crate to a new integration.
- **Whether the D-Bus Secret Service or the kernel `keyutils` backend should be the *default* Linux tier for a CLI tool that runs in both desktop and headless/CI contexts is not settled by the ecosystem** — `keyring`'s own default feature picks the D-Bus backend (desktop-oriented default), while its own `linux-keyutils-keyring-store` sibling crate's README argues headless/CI should prefer keyutils. For grim/ocx, this argues for detecting the environment (TTY + `DBUS_SESSION_BUS_ADDRESS` present) rather than hard-coding one Linux backend, or for skipping the OS-keychain tier entirely in a non-interactive/CI-detected run and going straight to the env-var tier.
- **Whether `ocx` should adopt grim's env-vars-second-not-first precedence, or grim should adopt ocx's env-first precedence, is an open cross-repo inconsistency this research surfaced but does not resolve** — `ocx` currently checks env before the Docker credential store (`get_impl` in `auth.rs`); grim's read path (`registry_client.rs::auth_for`) does not consult env vars at all in the audited code, only the Docker credential chain. A durable rule needs one canonical precedence across both tools.
