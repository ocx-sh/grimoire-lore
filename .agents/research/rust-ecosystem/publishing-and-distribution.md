## Summary

1. crates.io caps a published `.crate` file at **10MB**; large binaries, fixtures, or vendored assets must never enter the publish set (`exclude`/`include` in `Cargo.toml`).
2. **Yanking is not deletion.** A yanked version stays resolvable for lockfiles that already reference it; only new dependency resolution is blocked. crates.io does not offer version deletion — publish is permanent by design.
3. Crate ownership is either an individual **user** (full rights: publish, yank, add/remove owners) or a **GitHub team** (`github:org:team`; can publish/yank but cannot manage owners) — team-owned crates are the only way to avoid a single-human bus factor on crates.io.
4. **Trusted Publishing (OIDC)** is now crates.io's recommended CI publish path: no long-lived `CARGO_REGISTRY_TOKEN` secret, short-lived tokens minted per-run via `id-token: write` and `rust-lang/crates-io-auth-action@v1`, scoped to named GitHub repos. As of the source read, GitHub Actions is the only supported provider; GitLab CI and others are declared future work. The first release of a crate must still be published with a classic token before Trusted Publishing can take over.
5. Cargo has two registry index protocols: legacy **git** (clone the whole index) and **sparse** (`sparse+https://...`, fetch only the metadata files touched) — sparse is what makes large/frequent dependency resolution fast and is the default transport for crates.io today.
6. Workspace publishing has no single blessed tool in `cargo` itself — `cargo publish --workspace` publishes each member in **dependency order**, but nothing bumps versions, updates `path`-and-`version` cross-deps, writes changelogs, or tags — that's the job of a release tool.
7. The two live contenders for that job are **release-plz** (PR-based: opens/updates a "release PR" from Conventional Commits + git-cliff, compares local package state against the live registry, merges → tags → publishes → cuts GitHub/Gitea/GitLab releases) and **cargo-release** (a `cargo` subcommand invoked locally/in CI that validates repo state, bumps versions, tags, pushes, and calls `cargo publish`). **cargo-workspaces** (Lerna-inspired, shared or independent workspace versioning) is a third, older, lower-adoption option.
8. Rust semver breakage is **wider than most languages'**: adding a public struct field when none was private, tightening a generic bound, adding a non-defaulted trait item, capturing more generics in return-position-impl-Trait, and even some `repr()` attribute changes are all major-version breaks per the official Cargo Book semver reference — none of these look like "breaking changes" to a casual diff review.
9. **cargo-semver-checks** is the closest thing to an automated semver gate: it diffs rustdoc JSON against a baseline (defaulting to the last crates.io release) and flags a large but explicitly incomplete lint set — it says outright it does *not yet* catch every breaking change (e.g. many type/generic/lifetime cases), so it is a floor, not a guarantee.
10. `[patch]` is for overriding what a dependency resolves to (bug fixes, forks); **source replacement** (`[source.*] replace-with`) is for wholesale mirroring/vendoring and requires the replacement to contain *exactly* the same code as the original — mixing up the two purposes is the most common private-registry misconfiguration.
11. `cargo vendor` + directory-source replacement is the standard offline/air-gapped-build story; its `.cargo-checksum.json` is explicitly **not a security mechanism**, only a "did this get hand-edited" check.
12. docs.rs builds are controlled entirely by `[package.metadata.docs.rs]` in the crate's own `Cargo.toml` (`features`, `all-features`, `rustc-args`, `rustdoc-args`, `targets`/`default-target`) — there is no separate docs.rs config file, so a docs.rs build failure is reproducible locally by replaying those same flags with `cargo doc`.
13. `#[doc(cfg(...))]` / `#[doc(auto_cfg)]` (rustdoc, stabilizing feature, tracked under [rust-lang/rust#45040](https://github.com/rust-lang/rust/issues/45040)) is what produces the "Available on … only" badges on docs.rs pages; `cfg(docsrs)` is the companion cfg flag docs.rs sets during its build so crates can conditionally show extra platform-gated items without breaking normal builds.
14. **cargo-binstall** resolves binaries by: checking the crate's linked GitHub repo Releases for a matching asset name, falling back to the third-party **quickinstall** artifact host, then falling back to `cargo install` (source build) if nothing is found. It downloads crate metadata from crates.io over HTTPS and checks archive checksums; it verifies GitHub-published `sha256:` digests when present, and supports opt-in cryptographic signature verification (`--only-signed`) — but does **not** require or default to signatures, so a project that wants verified binstall installs must explicitly sign releases and document `--only-signed`.
15. **cargo-dist** (project renamed to **dist**, config file now `dist-workspace.toml`) is the closest thing to a Rust-native release pipeline generator: it produces GitHub Actions release workflows, per-platform archives, shell/PowerShell/MSI installers, and can push to npm/Homebrew — i.e. it generates most of what OCX/Grimoire currently hand-roll for prebuilt-binary releases.
16. `self_update` is the dominant "have my own CLI update itself" crate: it supports GitHub/GitLab/Gitea/Gitee/S3/manifest backends, verifies SHA-256/512 checksums (auto-checks GitHub's published digest when the asset carries one), and has an *optional* `signatures` feature (via `zipsign`) — again, signature verification on self-update is opt-in, not a given, so a tool that installs/updates other tools (like ocx/grim) inherits an explicit obligation to turn that on rather than assume it.
17. Homebrew distributes Rust CLIs as **bottles** (prebuilt binaries) via a **tap** repo (`homebrew-<name>`) with Ruby formulae; taps are the low-friction path before (if ever) attempting inclusion in homebrew-core.
18. Vendoring, `git` dependencies, and `[patch]`/`replace-with` all interact with **MSRV and lockfile reproducibility** in ways that are easy to get subtly wrong — a `git` dependency has no registry-enforced immutability guarantee beyond the pinned `rev`, and a floating `branch`/`tag` reference is a supply-chain and reproducibility hazard by itself.
19. Rust→Python (PyO3) binding distribution has its own dedicated, extremely dominant tool: **maturin** (formerly `pyo3-pack`) builds and publishes PyO3/cffi/uniffi-bound crates as PyPI wheels; it is used by orjson, Polars, Pydantic-core, Ruff — directly relevant to Grimoire's existing Python-binding crate if that crate is ever meant to reach PyPI.
20. Because OCX/Grimoire ships as **prebuilt binaries with nothing on crates.io today**, the crates.io-specific mechanics (trusted publishing, yanking, ownership teams, rate limits) are *decision-in-waiting* material, not active operational surface — the immediately relevant half of this corpus is binary distribution (cargo-dist/binstall/self_update/Homebrew) and workspace-internal versioning, not registry publishing.

## Findings

### 1. crates.io mechanics

- Crate size: **10MB hard limit** on the packaged `.crate` file — read verbatim from the Cargo Book publishing reference. [Cargo Book: Publishing on crates.io](https://doc.rust-lang.org/cargo/reference/publishing.html)
- Ownership model: individual users get full rights (publish/yank/owner management); GitHub teams (`github:org:team` syntax, added via `cargo owner --add github:org:team`) get publish/yank rights but explicitly **cannot** add or remove owners — team ownership needs an already-added human owner to manage the owner list. [Cargo Book: Publishing on crates.io](https://doc.rust-lang.org/cargo/reference/publishing.html)
- API tokens now require `read:org` scope specifically to resolve team membership for team-owner operations; this is a newer requirement layered onto the original no-scope tokens. [Cargo Book: Publishing on crates.io](https://doc.rust-lang.org/cargo/reference/publishing.html)
- Yanking (`cargo yank --version X.Y.Z`, reversible with `--undo`) is **permanent like a publish** — it does not remove code from the index, it only prevents *new* dependency resolutions from selecting that version; anything with it already in `Cargo.lock` keeps building. crates.io provides no path to delete an accidentally-published secret this way. [Cargo Book: Publishing on crates.io](https://doc.rust-lang.org/cargo/reference/publishing.html)
- Registry Web API (used by `cargo publish`/`yank`/`unyank`/owners/search) authenticates via a bearer `Authorization: <token>` header, obtained via `cargo login` and stored by Cargo; a bad/missing token yields HTTP 403. The Cargo Book's Web API reference does **not** itself enumerate fine-grained token scopes (publish-new vs publish-update vs yank vs owners) — that granularity lives in crates.io's own account UI/docs, not the protocol spec. [Cargo Book: Registry Web API](https://doc.rust-lang.org/cargo/reference/registry-web-api.html#tokens)
- **Trusted Publishing**: crates.io supports OIDC-based short-lived token issuance from CI, removing the need to hold a `CARGO_REGISTRY_TOKEN` secret in the repo. GitHub Actions is the currently supported provider (`id-token: write` permission + `rust-lang/crates-io-auth-action@v1`); GitLab CI and other providers are called out as future work. A crate must have its **first version published with a classic API token** before Trusted Publishing can be enabled for it — it's a graduation step, not a from-scratch bootstrap. [crates.io dev blog: 2025-07 update](https://blog.rust-lang.org/2025/07/11/crates-io-development-update-2025-07/) (fetched — content on trusted publishing confirmed, exact publish date of the OIDC feature itself not independently re-verified beyond this post)
- Sparse vs git index protocol: sparse (`sparse+https://…`) fetches only per-crate metadata files over plain HTTP instead of cloning a monolithic git repo; crates.io supports both, selectable via `[registries.crates-io] protocol = "sparse"|"git"` in `.cargo/config.toml`. [Cargo Book: Registries](https://doc.rust-lang.org/cargo/reference/registries.html)
- Alternative/private registries are configured under `[registries]` in `.cargo/config.toml` (index URL + optional token via `CARGO_REGISTRIES_<NAME>_TOKEN` or `cargo login --registry=<name>`); crates.io **refuses to accept published crates that depend on crates from other registries** — you cannot mix a crates.io publish with a dependency pinned to a private registry. A crate can restrict *where* it may be published via `publish = ["my-registry"]` or disable publishing entirely with `publish = false`. [Cargo Book: Registries](https://doc.rust-lang.org/cargo/reference/registries.html)

### 2. Workspace publishing and release automation

- `workspace.package` lets member crates inherit shared keys (`version.workspace = true`, etc.) including a `publish` key, giving lockstep-version workspaces a single source of truth for the version string — but the Cargo Book's workspace reference itself stops at manifest inheritance; it does not describe the actual publish-ordering or version-bump *process*. [Cargo Book: Workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html)
- **release-plz**: PR-based release automation. It computes what changed by diffing local packages against what's actually **live on the registry** (not against git tags, which it calls out as the key difference from release-please-style tools), opens/keeps-updated a release PR (changelog via git-cliff, version bumps from Conventional Commits), and on merge creates the git tag(s), publishes to the registry, and cuts GitHub/Gitea/GitLab releases. Ships both as a GitHub Action and a standalone CLI (for GitLab/Gitea or non-GitHub CI). 1.5k GitHub stars, 184 forks, 2,352 commits at time of read — actively developed. [release-plz README](https://github.com/release-plz/release-plz)
- **cargo-release**: a `cargo` subcommand (not a bot/PR flow) that validates repo state (branch, remote-sync, clean tree), bumps versions, updates dependents, tags, pushes, and drives `cargo publish`; supports workspace-wide operation via `--workspace`/`--exclude`/`--package` and has a "share commits" concept for coordinated multi-crate bumps. 1.6k stars, 137 forks, at v1.1.5 at time of read. Lists release-plz as a related/alternative tool without detailed comparison. [cargo-release README](https://github.com/crate-ci/cargo-release)
- **cargo-workspaces**: older (Lerna-inspired) tool, explicitly built for workspace projects like `clap`. Supports both shared (default) and independent per-crate versioning (configured under `[package.metadata.workspaces]`), auto-detects changed crates since the last tag, prompts for semver bump keyword, updates intra-workspace deps, and does the git commit/tag/push. Lower adoption than the other two (599 stars, 57 forks) and no explicit maintenance-status or successor note found in the README. [cargo-workspaces README](https://github.com/pksunkara/cargo-workspaces)
- **cargo-smart-release** exists as a fourth, lower-profile entrant (author: Sebastian Thiel / `gitoxide` project) but was out of scope to fetch directly this pass; treat as a legacy/niche option pending confirmation, not a default recommendation.
- Bottom line on lockstep vs independent: lockstep (single version across the whole workspace) is simplest to reason about and is what `workspace.package.version` inheritance directly optimizes for; independent per-crate versioning is what cargo-workspaces/cargo-release/release-plz all support but costs you a changelog-per-crate and cross-crate version-compat matrix — worth paying only when crates in the workspace have genuinely different release cadences or genuinely-different consumers.

### 3. Semver in practice

- The Cargo Book's own SemVer Compatibility reference lists breaking changes far beyond "removed a public function": adding a public struct field when the struct currently has *no* private field (breaks struct-literal construction sites), adding new enum variants without `#[non_exhaustive]`, adding any non-defaulted trait item (breaks every implementor), *any* change to a trait item's signature, tightening a generic bound, capturing more generic parameters in return-position-impl-Trait, and multiple `repr()` transitions (adding `packed`/`align`, removing `C`/`align`/`transparent`/`<int>`, reordering public `repr(C)` fields). [Cargo Book: SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)
- There's a documented **"possibly-breaking"** middle tier the reference calls out explicitly: adding a defaulted trait item, adding any inherent item, introducing a new function type parameter, bumping MSRV, changing platform/environment requirements, and removing an optional dependency — these *can* break downstream code (ambiguity, ecosystem MSRV pinning, feature-gated code) without being guaranteed to. [Cargo Book: SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)
- MSRV bump: the reference itself lists it only as "possibly-breaking," and confirms this is a matter of *project convention*, not something Cargo/crates.io enforces as a semver-relevant field — cargo-semver-checks likewise explicitly does not treat MSRV bumps as major. [cargo-semver-checks README](https://github.com/obi1kenobi/cargo-semver-checks)
- **cargo-semver-checks** (`cargo install cargo-semver-checks --locked`, then `cargo semver-checks`) diffs rustdoc JSON output between the current tree and a baseline (default: last crates.io release) and lints for known-breaking patterns. 1.7k stars, 136 forks at time of read; ships an official GitHub Action for CI gating. It is explicit that it does **not** catch everything yet — type-change, generic/lifetime, and some feature-conditional breaks are named gaps — and it depends on the unstable rustdoc JSON format, so it needs updates in lockstep with new Rust releases; nightly support is "best-effort" only. [cargo-semver-checks README](https://github.com/obi1kenobi/cargo-semver-checks)
- `cargo-public-api` (Enselic) is the complementary "print/diff the public API surface as text" tool — useful for human-reviewed API diffs in a PR, distinct from cargo-semver-checks' automated lint-and-fail approach; not independently re-fetched this pass, listed here from established ecosystem knowledge and flagged as such in the Inventory table.

### 4. Alternative registries, vendoring, patch/replace

- `[patch]` (e.g. `[patch.crates-io] some-crate = { path = "…" }`) is for **overriding dependency resolution** — the correct tool for pulling in a forked/patched dependency. Source replacement (`[source.crates-io] replace-with = "…"`) is explicitly documented as the **wrong** tool for that job; it exists for mirroring/vendoring where the replacement *must* contain byte-identical content to the original source. [Cargo Book: Source Replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)
- Four source-replacement kinds exist: registry sources (git/sparse/https index URL, same shape as crates.io), local-registry sources (managed by the separate `cargo-local-registry` crate — full `.crate` files plus an index), directory sources (managed by the built-in `cargo vendor` subcommand — unpacked source trees, one `.cargo-checksum.json` per crate), and git sources (pin by `branch`/`tag`/`rev`; explicitly **not the same mechanism** as a git-backed registry index). [Cargo Book: Source Replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)
- `.cargo-checksum.json` in a `cargo vendor` tree is stated outright to be **not a security mechanism** — it only detects accidental local edits to vendored sources, not tampering or provenance. [Cargo Book: Source Replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)
- When source replacement is active, commands that talk to the registry directly need an explicit `--registry` flag to disambiguate — a documented operational gotcha. [Cargo Book: Source Replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)
- **Kellnr** is a self-hosted private cargo registry (Rust-native alternative to pointing Artifactory/Cloudsmith/Shipyard at a generic-registry endpoint); content fetch failed this pass (malformed response), so its comparison against Artifactory/Cloudsmith/Shipyard is carried from established ecosystem knowledge, not independently re-verified — flagged in the Inventory table as needing a follow-up read before being cited as normative.

### 5. Binary distribution

- **cargo-dist**, renamed **dist**, config file `dist-workspace.toml`: generates GitHub Actions release workflows, per-target archives, shell/PowerShell/MSI installers, machine-readable release manifests, and can publish to npm and Homebrew. Actively maintained (3,457 commits, 2.1k stars, 148 forks at time of read); the rename itself ("dist (formerly known as `cargo-dist`)") is a live signal the project is mid-rebrand, which matters for anyone writing install docs or CI badges that reference the old name. [dist (cargo-dist) README](https://github.com/axodotdev/cargo-dist)
- **cargo-binstall** resolution order: (1) crate's linked GitHub repo Releases, matching filename conventions or an explicit `[package.metadata.binstall]` block in `Cargo.toml`; (2) the third-party **quickinstall** artifact host as fallback; (3) `cargo install` (source build) as last resort. Downloads crate metadata from crates.io over HTTPS, verifies TLS 1.2+ for artifact downloads, checks tar/archive checksums, and auto-verifies a GitHub-published `sha256:` digest when the chosen asset has one; supports optional cryptographic signature verification via `--only-signed`, but this is opt-in — the README states the ecosystem's signature adoption is still limited. 2.8k stars, 110 forks at time of read. [cargo-binstall README](https://github.com/cargo-bins/cargo-binstall)
- Producing `[package.metadata.binstall]` metadata (or `dist`-generated release assets, which binstall also understands) is the concrete lever a project has to make `cargo binstall <tool>` "just work" instead of falling through to quickinstall or a full source build.
- **Homebrew**: distribute via a **tap** (`homebrew-<name>` repo on GitHub, `Formula/*.rb` files); users run `brew tap user/name && brew install name`. Homebrew's own bottle mechanism (prebuilt binary poured into the Cellar) is the fast path and is what a Rust CLI wants — building from source via `cargo build` inside a formula works but is slow and adds a Rust-toolchain build dependency for the installing machine. Formulae need a valid homepage, DFSG-compatible license, and a test block. [Homebrew Formula Cookbook](https://docs.brew.sh/Formula-Cookbook)
- **rustup's own install script** is the reference convention for "curl | sh" installers in this ecosystem: `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh` — the `--proto '=https'` and `--tlsv1.2` pins are explicit anti-downgrade hardening baked into the documented one-liner itself, worth mirroring in any install script this project ships. [rustup installation docs](https://rust-lang.github.io/rustup/installation/index.html)
- Scoop, WinGet, AUR, Nix, apt/rpm, and Docker images were not independently re-fetched this pass; they remain valid distribution channels from established ecosystem knowledge and are listed in the Inventory table with that caveat rather than a fetched citation.
- **npm and PyPI as delivery channels for Rust binaries**: this is a real, common pattern — npm packages that ship a `postinstall` script fetching a platform-specific Rust binary (the pattern `dist`/cargo-dist itself supports generating), and PyPI wheels built by **maturin** for PyO3-bound crates. Maturin (formerly `pyo3-pack`) is the dominant tool for the latter: builds and publishes PyO3/cffi/uniffi-bound crates and standalone Rust binaries as Python wheels, supports Python 3.8+, Windows/Linux/macOS/FreeBSD, PyPy/GraalPy, and is used by orjson, Polars, Pydantic-core, and Ruff. 5.8k stars, 428 forks at time of read. Directly relevant if Grimoire's Python-binding crate is meant to reach PyPI. [maturin README](https://github.com/PyO3/maturin)
- Zig-cc / `cargo-zigbuild` and musl static builds for portable cross-compiled Linux binaries were not independently re-fetched this pass; carried from established knowledge, listed in Inventory, not cited to a fetched source.

### 6. Self-update

- **self_update** (`jaemk/self_update`) is the dominant crate for "let my own binary replace itself." Backends: GitHub, GitLab, Gitea, Gitee, S3-compatible storage, and manifest-based hosting. Verification: automatically checks a GitHub-published `sha256:` digest against the downloaded asset when the asset carries one; supports manual `verify_checksum()` for SHA-256/SHA-512; has an *optional* `signatures` feature (via `zipsign`) for `.zip`/`.tar.gz` artifact signature verification. It reached 1.0 with a documented breaking-change migration guide from 0.x, i.e. it is past its earliest unstable phase. 955 stars, 94 forks at time of read. [self_update README](https://github.com/jaemk/self_update)
- The load-bearing fact for a tool that installs/updates *other* tools (ocx, grim): checksum verification is largely automatic when publishing conventionally to GitHub Releases, but **cryptographic signature verification is opt-in on both the publish side and the consume side** — nobody gets it by accident. A package manager over an OCI registry should treat this as a design decision to make deliberately (content-addressable digests from the registry itself may already give a stronger guarantee than an ad hoc self-update crate would, which is worth stating explicitly rather than bolting on self_update out of habit).

### 7. docs.rs

- All docs.rs build configuration lives in the crate's own `Cargo.toml` under `[package.metadata.docs.rs]` — there is no separate docs.rs config file to write. Keys: `features` (list, default `[]`), `all-features` (bool, default false), `no-default-features` (bool), `default-target` (defaults to `x86_64-unknown-linux-gnu`), `targets` (list; if both `targets` and `default-target` are unset, docs.rs builds **all Tier-1 targets** and uses `x86_64-unknown-linux-gnu` as the default landing page), `additional-targets`, `rustc-args` (→ `RUSTFLAGS`), `rustdoc-args` (→ `RUSTDOCFLAGS`), `cargo-args`. [docs.rs metadata reference](https://docs.rs/about/metadata)
- Because the whole build is just `cargo doc` with those flags replayed, reproducing a docs.rs failure locally is mechanical: read the crate's own `[package.metadata.docs.rs]` block and run the equivalent `cargo doc` invocation with the same feature/target/flag combination — no docs.rs-specific tooling required.
- `#[doc(cfg(...))]` and the newer `#[doc(auto_cfg)]` (rustdoc; tracked at [rust-lang/rust#45040](https://github.com/rust-lang/rust/issues/45040)) are what produce docs.rs's "Available on … only" badges for feature/platform-gated items; `auto_cfg` derives the badge automatically from the real `#[cfg(...)]` attribute (with `hide(...)`/`show(...)` controls), while manual `#[doc(cfg(...))]` lets you show a badge independent of the actual compile-time condition. `cfg(docsrs)` itself is the flag docs.rs's build sets so a crate can conditionally compile extra "documentation only" surface (e.g. compile every platform-specific module for docs purposes even though only one would compile on the actual host). [rustdoc unstable features: doc(cfg)](https://doc.rust-lang.org/rustdoc/unstable-features.html#doccfg-recording-what-platforms-or-features-are-required-for-code-to-be-present)

### 8. The consumer side (what cargo does that a package manager can imitate)

- Cargo's dependency source model cleanly separates three concerns worth imitating in any similar OCI-backed tool: **resolution** (index metadata lookup — sparse HTTP fetch of small per-package files, not a full index clone), **caching** (downloaded packages live in a shared, content-keyed local cache independent of any one project), and **verification** (checksum-checked archive content, with the lockfile pinning exact resolved versions so a second `cargo build` on the same lockfile does not re-resolve). The sparse-index design in particular is the concrete precedent for "don't clone a whole index/catalog when you only need to answer questions about a handful of packages," which is directly applicable to how an OCI-registry-backed CLI should query available packages/versions rather than pulling a full catalog manifest on every run. [Cargo Book: Registries](https://doc.rust-lang.org/cargo/reference/registries.html)
- The `[patch]`/source-replacement split (override resolution vs replace the whole source wholesale) is a second reusable design lesson: a package manager needs two distinct, non-overlapping escape hatches — "resolve this one dependency differently" and "point at a different, content-identical mirror of everything" — conflating them is what produces the private-registry misconfiguration bugs Cargo explicitly warns against. [Cargo Book: Source Replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)

## Normative guidance candidates

1. **If/when this project publishes to crates.io, use Trusted Publishing (OIDC) for the CI publish step, not a long-lived `CARGO_REGISTRY_TOKEN` secret.** Rationale: eliminates a standing high-privilege secret from the CI environment, the exact class of credential a supply-chain compromise targets. VERIFICATION: repo's publish workflow YAML contains `id-token: write` and `rust-lang/crates-io-auth-action@v1` (or successor), and no `CARGO_REGISTRY_TOKEN` secret reference remains in that workflow.
2. **Never point `cargo yank` at a version and consider the incident closed if the concern was a leaked secret or malicious code** — yank does not remove content from the index. Rationale: yanked crate content is still fetchable by anyone who already resolved it, and by direct download. VERIFICATION: any incident runbook for "bad version published" names crates.io support/registry-admin escalation as the actual remediation path, not `cargo yank` alone.
3. **Own every published crate through a GitHub team, never a single personal account**, once anything is published to crates.io. Rationale: single-owner crates are a documented crates.io failure mode (owner leaves, account compromised, unreachable) with no institutional recovery path. VERIFICATION: `cargo owner --list <crate>` (or crates.io UI) shows a `github:org:team` entry, and at least one human owner remains able to manage that team's membership.
4. **Gate every PR that touches a public API with `cargo-semver-checks` in CI, scoped per-crate to the ones actually intended to be publishable/stable.** Rationale: Rust's semver-breaking surface (trait items, generic bounds, `repr` details) is wider and less obvious than most languages'; a human diff review reliably misses it. VERIFICATION: CI workflow runs `cargo semver-checks` (or the equivalent Action) and fails the build on a detected breaking change without a matching major-version bump.
5. **Never use `[source] replace-with` to pull in a bugfix or fork of one dependency — use `[patch]`.** Rationale: source replacement requires content-identical mirrors; using it to inject a divergent fork silently breaks that invariant and produces confusing, hard-to-diagnose resolution failures for anyone else touching the workspace. VERIFICATION: `git grep -n "replace-with"` in `.cargo/config.toml` shows only genuine mirror/vendor configs, and any dependency override lives under `[patch.*]` in `Cargo.toml` instead.
6. **Pin git dependencies (if any are ever used) by `rev`, never bare `branch` or `tag`.** Rationale: `branch`/`tag` are mutable pointers — a force-push or tag move changes what a "locked" build resolves to without any change in this repo's own files. VERIFICATION: `git grep -n 'git = ' -- '*.toml'` shows every git dependency entry paired with an explicit `rev = "<full sha>"`.
7. **If this project ever ships a self-update path (ocx/grim updating themselves), verify a cryptographic signature on the downloaded artifact before replacing the running binary, not just a checksum.** Rationale: a checksum published alongside the artifact on the same channel an attacker who compromised that channel controls proves nothing; a signature from a key held separately from the release pipeline does. VERIFICATION: the self-update code path calls a signature-verification routine (e.g. `zipsign`-style) against a public key baked into the binary at build time, and fails closed (refuses to update) on any verification error.
8. **When configuring `cargo-binstall` support, treat `--only-signed` as the target state, not the default a user must discover.** Rationale: binstall's own maintainers note signature adoption across the ecosystem is still the exception; a tool that cares about install-time integrity should not rely on that being someone else's problem. VERIFICATION: `[package.metadata.binstall]` (or the release pipeline generating binstall-compatible assets) is paired with published signatures for those assets, and install docs recommend `--only-signed`.
9. **Reproduce a docs.rs build failure locally by replaying the crate's own `[package.metadata.docs.rs]` flags through `cargo doc`, never by guessing at a different flag set.** Rationale: docs.rs runs nothing but that metadata block plus `cargo doc`; any other combination of flags is testing a build docs.rs doesn't actually run. VERIFICATION: the local repro command's `--features`/`--target`/`RUSTDOCFLAGS` match the crate's `[package.metadata.docs.rs]` table exactly.
10. **Before choosing a workspace-release tool, decide lockstep vs independent versioning explicitly and write it down — don't let the tool choice make the decision by default.** Rationale: release-plz, cargo-release, and cargo-workspaces all support both modes, but each requires configuration (`workspace.package.version` inheritance for lockstep; `[package.metadata.workspaces]`-style independent config otherwise) — picking a tool first and discovering its default behavior later has already produced real workspace version drift in other projects. VERIFICATION: a short ADR or README note states the chosen versioning policy for this workspace (given ocx is 4 crates / grimoire is 1 crate today) and the release tool's config matches it.

## AI-agent angle

- **Agents routinely treat `cargo yank` as "delete this from the world."** It is not — it's a soft block on new resolutions only. An agent asked to "remove a leaked secret from a published crate" that stops at `cargo yank` has not fixed the problem. Smallest mechanical check: grep the agent's own remediation steps/commit for the word "yank" used as a terminal action on a security-incident task; if present without an accompanying rotation/escalation step, flag it.
- **Agents underestimate Rust's semver-breaking surface** — they'll happily bump a patch version for "just added a struct field" or "just tightened a bound," both of which are majors per the Cargo Book reference. Smallest mechanical check: run `cargo semver-checks` (if the crate has a published baseline) before accepting any version-bump PR the agent proposes as non-major; a nonzero exit contradicts a patch/minor bump claim.
- **Agents conflate `[patch]` and `[source] replace-with`** because both "redirect a dependency" in casual description. Smallest mechanical check: grep `.cargo/config.toml` and `Cargo.toml` diffs an agent produces — any new `[source.*] replace-with` entry paired with a dependency-version change (rather than a pure mirror setup) is very likely a misuse that should have been `[patch]`.
- **Agents propose `curl | sh` install scripts without the TLS/protocol pinning rustup itself uses**, or without checksum verification, because the naive version "works." Smallest mechanical check: grep any generated install script for `--proto '=https'`-equivalent enforcement and a checksum/signature verification step before the binary is executed or moved into place; absence of both is a finding, not a style nit.
- **Agents assume a fetched GitHub-Releases checksum is a security control.** It's integrity-only and attacker-controlled if the release pipeline itself is compromised — self_update's own docs draw this line (checksum auto-verified, signature opt-in) but an agent skimming "verifies the download" will conflate the two. Smallest mechanical check: any self-update/install code review should explicitly ask "what entity controls the value being compared against, and is it independent of the artifact's own delivery channel?" before accepting "it verifies checksums" as sufficient.
- **Agents reach for cargo-workspaces or cargo-smart-release out of habit/training-data recency bias** rather than checking which of the three workspace-release tools is still actively maintained *right now*. Smallest mechanical check: before an agent proposes adopting a release-automation tool, have it fetch that tool's own repo and report the latest commit date / open PR count — don't accept a recommendation sourced purely from training-data familiarity.

## Contested / evolving

- **Trusted Publishing rollout is still GitHub-only.** crates.io's own material names GitLab CI and other OIDC providers as future work, not shipped — any guidance that assumes OIDC publishing is universally available across CI providers is currently wrong and should be revisited as the feature expands. [crates.io dev blog: 2025-07 update](https://blog.rust-lang.org/2025/07/11/crates-io-development-update-2025-07/)
- **cargo-dist's rename to "dist"** is mid-flight — documentation, install one-liners, and community references still say "cargo-dist" in many places even as the canonical name and config file (`dist-workspace.toml`) have moved. Expect stale tutorials/blog posts for a while; treat the GitHub repo's current README as the source of truth over older blog posts. [dist (cargo-dist) README](https://github.com/axodotdev/cargo-dist)
- **cargo-semver-checks explicitly does not claim completeness** — it is an actively-improving lint set built on unstable rustdoc JSON, meaning both its coverage and its Rust-version compatibility are moving targets, not a settled baseline to treat as a permanent, complete gate. [cargo-semver-checks README](https://github.com/obi1kenobi/cargo-semver-checks)
- **Workspace release tooling has no consensus winner.** release-plz (PR-based, Conventional-Commits-driven) and cargo-release (imperative CLI) both have comparable adoption signals (1.5k vs 1.6k stars at time of read) and neither project's own docs stake a clear "use us instead of them" claim beyond listing each other as related tools — this is a live, unresolved choice in the ecosystem, not a solved question with one right answer.
- **Binary-distribution signature verification remains largely opt-in ecosystem-wide** (cargo-binstall's `--only-signed`, self_update's optional `signatures` feature) rather than a growing default — whether this shifts toward "signed by default" as supply-chain tooling (sigstore, cosign) becomes more standard in Rust CI is an open trajectory, not yet a resolved direction.
