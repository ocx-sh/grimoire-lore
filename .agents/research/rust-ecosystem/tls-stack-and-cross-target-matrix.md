## Summary

1. **The task's stated ground truth is half wrong: correct it before writing the rule.** `grep -rn "install_default\|CryptoProvider" ocx/ grimoire/` (excluding `.cache`/`target`/vendored `registry/src`) finds two calls to `.install_default()` in both trees' vendored `external/rust-oci-client` fork — but they call `jsonwebtoken::crypto::aws_lc::DEFAULT_PROVIDER.install_default()`, jsonwebtoken 10.4.0's own `CryptoProvider` type (JWT signing/verification), not `rustls::crypto::CryptoProvider`. Both call sites are `#[cfg(test)]`-only, in `test_helpers`. **No call to `rustls::crypto::{ring,aws_lc_rs}::default_provider().install_default()` exists anywhere in either tree's own source.**
2. `cargo tree -e features -i rustls` in `ocx/` proves the `rustls` crate itself resolves with exactly one crypto-provider feature turned on: `aws-lc-rs` (reached via `reqwest`'s `__rustls-aws-lc-rs` feature, which `features = ["rustls"]` on reqwest 0.13 selects). The `ring` package that also appears in `Cargo.lock` is **not** in the resolved build graph at all — `cargo tree -i ring --target all` prints "nothing to print." It's an unreachable optional dependency of `quinn-proto`/`rustls-webpki`, not an active second provider.
3. Because rustls compiles with exactly one provider feature, `CryptoProvider::get_default_or_install_from_crate_features()` — the internal function whose ambiguity panic ("Could not automatically determine the process-level CryptoProvider... make sure exactly one of the 'aws-lc-rs' and 'ring' features is enabled") is the panic named in this task — cannot fire in these binaries today: the ambiguous-features precondition doesn't hold.
4. Reading reqwest 0.13.4's own `ClientConfig` construction (`src/async_impl/client.rs:719`) shows it never calls that ambiguity-panicking function at all: it does `CryptoProvider::get_default().unwrap_or_else(default_rustls_crypto_provider)`, and `default_rustls_crypto_provider()` only panics when reqwest is built with `rustls-no-provider` *and* the `aws-lc-rs` provider feature is absent — neither is true here. **The panic the task asks about is unreachable via reqwest's own code path in this feature configuration**, full stop, independent of whether any `install_default()` is ever called.
5. The startup rule is therefore not "call `install_default()` once" — it's "keep the feature graph unambiguous." The rule that actually needs enforcing is: `rustls` must never resolve with both `aws-lc-rs` and `ring` cargo features simultaneously. ocx's own `Cargo.toml` comment already names this hazard (`adr_index_indirection.md` F) and the `reqwest = { features = ["rustls"] }` pin on both `reqwest` and `oci-client` is the mechanism that keeps it unambiguous via Cargo feature unification.
6. `grimoire/src/tls.rs` and `ocx/crates/ocx_lib/src/utility/tls.rs` independently document and test the real footgun in this stack: **not** the CryptoProvider panic, but `rustls-platform-verifier`'s `Verifier::new()` erroring on a host with an empty system trust store (bare container, minimal CI image), which `oci-client`'s `Client::new` fallback re-triggers as a process-crashing `.expect()` panic through `reqwest::Client::default()`.
7. Both trees ship `webpki-root-certs` and feed it through the **merge** path — `tls_certs_merge` (grimoire) / repeated `add_root_certificate` (ocx) — never `tls_certs_only`. Verified against reqwest 0.13.4 source: `tls_certs_only` defaults to `false` and neither call sets it, so both trees keep `rustls_platform_verifier::Verifier::new_with_extra_roots`, which layers the embedded Mozilla roots **on top of**, not instead of, the OS trust store and `SSL_CERT_FILE`/`SSL_CERT_DIR`.
8. Consequence for a corporate MITM proxy: nothing breaks. A corporate root injected via the OS store or `SSL_CERT_FILE` is honored because the platform verifier is still consulted; the embedded Mozilla roots only add coverage for hosts where the OS store is empty or missing. This is a deliberate, tested, documented stance in both trees, not an accident (`grimoire/src/tls.rs:67-97` has regression tests asserting the embedded set is non-empty specifically to keep this branch selected).
9. `aws-lc-rs` needs only a C/C++ compiler for non-FIPS builds on platforms with pre-generated bindings (all four families here are pre-generated except Windows, which needs `bindgen`) — no CMake, Go, or NASM unless the FIPS variant is selected. Neither tree uses the FIPS feature.
10. `aarch64-unknown-linux-musl` cross-compiled via `cargo-zigbuild` is a supported, CI-exercised combination for `aws-lc-rs` (`aws/aws-lc-rs` PR #1103 added zig-compiler CI coverage); a real footgun existed (`-Wp,-U` breaking `zig cc`, issue #993) and was fixed upstream, not a currently-open blocker.
11. `aarch64-pc-windows-msvc` cross-compiled had a real, now-closed linkage bug (`aws/aws-lc-rs#453`, closed 2024-07-17): unresolved externals (`__imp_ftell`, `__imp_strdup`) traced to a MinGW header polluting the include path and a CRT-linkage (`/MT` vs `/MD`) mismatch — not something inherent to the architecture. Because `xwin` supplies a genuine MSVC sysroot (no MinGW headers in the include path), and ocx's own `Cargo.toml` documents `cargo xwin build --target aarch64-pc-windows-msvc` as a working command in this exact tree, this combination is sound today.
12. ocx's real per-triple matrix, read from `.github/workflows/deploy-dev.yml` and `.github/actions/build-rust/action.yml`: Linux (both musl triples) via `cargo-zigbuild` + Zig on `ubuntu-22.04`; macOS (both darwin triples) via native `cargo build` on `macos-latest`; Windows-MSVC (both triples) via `cargo xwin build` inside the `messense/cargo-xwin` container, **pinned by image digest, not tag** ("has no stable versioned tag"). ocx additionally cross-builds a `*-pc-windows-gnullvm` shim via `cargo-zigbuild@0.22.3` pinned in `build-windows-shims.yml`, referencing `adr_shim_hermetic_zigbuild.md`.
13. `cross` (cross-rs/cross) is structurally incapable of covering this matrix regardless of its release cadence: its `docker/` directory has Dockerfiles only for `i686`/`x86_64-pc-windows-gnu` — no `-msvc`, no `-gnullvm`, and **no `apple-darwin` image at all** (Apple SDK redistribution terms block a public Docker image). Two of the eight triples (`aarch64`/`x86_64-apple-darwin`) and the MSVC ABI it needs are permanently out of reach for `cross`.
14. `cross`'s crates.io staleness (no release since v0.2.5, 2023-02-04) does not reflect its actual maintenance: the GitHub repo shows a push on 2026-07-31 and 8.3k stars, and its own README now tells users to `cargo install cross --git https://github.com/cross-rs/cross` rather than use the stale crates.io release. It's alive — it's just structurally the wrong tool for a matrix that includes Darwin and MSVC. Neither ocx nor grimoire CI invokes it anywhere.
15. `cargo-zigbuild` (v0.23.0, released 2026-06-18) and `xwin`/`cargo-xwin` (v0.10.0 / v0.23.1, both released within the last two days of this research as of 2026-08-14) are both under active, current development — the opposite maintenance profile from `cross`.
16. rustls 0.24 has not shipped as of 2026-08-14 (latest release: 0.23.43, 2026-07-29); its own tracking issue (`rustls/rustls#2400`) lists no headline item changing the default-provider-selection or CryptoProvider-ambiguity-panic model — the provider-install contract documented for 0.23 is the one to build a startup rule against, and there's no imminent breaking change to plan around.

## Findings

### 1. The CryptoProvider install site: verified absence, and why it doesn't matter here

`grep -rn "install_default\|CryptoProvider" ocx/ grimoire/` (with `.cache`, `target`, and vendored `registry/src` excluded) turns up exactly two source locations, present identically in both trees' vendored `external/rust-oci-client/src/lib.rs`:

```rust
pub(crate) fn jsonwebtoken_install_default_crypto_provider() {
    let _ = jsonwebtoken::crypto::aws_lc::DEFAULT_PROVIDER.install_default();
}
```

called from `#[cfg(test)]` blocks in `token_cache.rs` and `client.rs`. This is [jsonwebtoken 10.4.0's own `CryptoProvider`](https://github.com/Keats/jsonwebtoken) type — a JWT signing/verification abstraction that mirrors rustls's naming — **not** `rustls::crypto::CryptoProvider`. Confusing the two is easy (identical type name, identical `install_default()` method signature, identical panic-avoidance framing) and is exactly the trap flagged in [AI-agent angle](#ai-agent-angle) below. No call to `rustls::crypto::ring::default_provider().install_default()` or `rustls::crypto::aws_lc_rs::default_provider().install_default()` exists in either tree's own source.

The reason this is safe rests on two independent facts, both verified directly against this exact codebase and dependency graph rather than assumed from rustls's general documentation:

- `cargo tree -e features -i rustls` (run inside `ocx/`) shows `rustls` resolving with exactly one crypto-provider feature: `aws-lc-rs`, reached through `reqwest feature "__rustls-aws-lc-rs"` ← `reqwest feature "rustls"` ← the `reqwest = { features = ["rustls"] }` pin in `ocx/Cargo.toml`. The `ring` v0.17.14 package that shows up in `Cargo.lock` is an unreached optional dependency of `quinn-proto`/`rustls-webpki` — `cargo tree -i ring --target all` prints "nothing to print," confirming it's inert. rustls's own ambiguity panic — [`CryptoProvider::get_default_or_install_from_crate_features()`](https://docs.rs/rustls/latest/rustls/crypto/struct.CryptoProvider.html), whose `.expect()` message reads *"Could not automatically determine the process-level CryptoProvider from Rustls crate features. Call CryptoProvider::install_default() before this point to select a provider manually, or make sure exactly one of the 'aws-lc-rs' and 'ring' features is enabled."* — requires both features active to fire; that precondition doesn't hold.
- Even setting the feature graph aside, reqwest 0.13.4 never calls that ambiguity-checking function. Its `ClientConfig` construction (vendored at `reqwest-0.13.4/src/async_impl/client.rs:719`, matching upstream [reqwest v0.13.4](https://github.com/seanmonstar/reqwest/blob/v0.13.4/src/async_impl/client.rs)) does:
  ```rust
  let provider = rustls::crypto::CryptoProvider::get_default()
      .map(|arc| arc.clone())
      .unwrap_or_else(default_rustls_crypto_provider);
  ```
  and `default_rustls_crypto_provider()` (same file, ~line 2482) only panics under `#[cfg(not(feature = "__rustls-aws-lc-rs"))]` — i.e. only if you opted into reqwest's `rustls-no-provider` escape hatch and didn't compile in `aws-lc-rs`. Neither tree does. Absent that feature combination, `default_rustls_crypto_provider()` unconditionally returns `Arc::new(rustls::crypto::aws_lc_rs::default_provider())` — a **local** provider instance for that one client, not a process-wide install. So even a hypothetical process that never calls `install_default()` anywhere gets a working TLS client from reqwest; it just rebuilds the provider per-`ClientConfig` instead of reusing one process-wide instance (a minor perf/consistency cost, not a correctness or panic risk).

The only place the ambiguity panic *could* reach these binaries is a future dependency that (a) calls `rustls::ClientConfig::builder()` (the zero-arg form, which does hit `get_default_or_install_from_crate_features()`) and (b) is pulled in without going through `reqwest`'s/`oci-client`'s feature-pinned path, breaking the "exactly one provider feature" invariant `cargo tree` currently confirms.

### 2. The real panic in this stack is the empty-trust-store one, and it's already handled

`grimoire/src/tls.rs` documents the actual failure chain end to end in its module doc comment: with no explicit roots, `reqwest`'s rustls backend delegates to `rustls-platform-verifier`, whose `Verifier::new()` loads roots *only* from the system store and hard-errors when that store is empty (a distroless/minimal-CI image without `ca-certificates`, or an `SSL_CERT_FILE` pointing at an empty bundle). `oci-client`'s `Client::new` catches that error and falls back to `reqwest::Client::default()`, whose internal `.expect()` re-triggers the identical failure as a process-crashing panic. Both trees close this specific hole by seeding `webpki-root-certs::TLS_SERVER_ROOT_CERTS` as **extra** roots (never `tls_certs_only`, confirmed against reqwest 0.13.4 source: `tls_certs_only` field defaults to `false`, and `add_root_certificate`/`tls_certs_merge` never set it), which flips execution onto `Verifier::new_with_extra_roots` — a path that never errors on an empty system store and still merges the platform store when present. `grimoire/src/tls.rs:67-97` carries two regression tests: one asserting the embedded root set stays non-empty (else this exact panic branch reopens), one locking the DER→`reqwest::Certificate` projection against a silent parse-drop. This IS the test that catches the panic condition this task asked for — it just isn't a CryptoProvider test, because the reachable panic in this stack isn't the CryptoProvider one.

### 3. Bundled roots vs. system trust: deliberate merge, not replace

[`webpki-root-certs`'s own docs](https://docs.rs/webpki-root-certs/latest/webpki_root_certs/) recommend `rustls-platform-verifier` for end-user deployments over relying on the bundled Mozilla set alone — precisely the combination both trees use (bundled roots as a *floor*, platform verifier as the primary path). Because the merge semantics are confirmed (`tls_certs_only` never set), a corporate MITM proxy's injected root — whether installed in the OS store or supplied via `SSL_CERT_FILE`/`SSL_CERT_DIR` — is still consulted by `rustls-platform-verifier` and works exactly as it would with system-only trust. The bundled roots only add coverage on hosts where the OS store is missing or empty (minimal containers). This is the deliberate, documented, tested stance the task asked to confirm.

### 4. `aws-lc-rs` build requirements per triple

Per [aws-lc-rs's platform support page](https://aws.github.io/aws-lc-rs/platform_support.html): non-FIPS builds need only a C/C++ compiler on any platform Rust and AWS-LC both support — "Bindgen is never required, CMake is never required, and Go is never required" — *because* pre-generated bindings ship for supported platforms. The one caveat: pre-generated bindings don't cover Windows, so Windows targets need `bindgen` regardless of FIPS. Neither ocx nor grimoire enables the FIPS feature, so CMake/Go aren't in the build requirement at all.

- **`aarch64-unknown-linux-musl`**: covered by pre-generated bindings; only needs a C compiler. `cargo-zigbuild` supplies that compiler (`zig cc`) when cross-compiling from an `x86_64-unknown-linux-gnu` runner. This combination has upstream CI coverage: [aws-lc-rs PR #1103, "Add zig compiler support and CI coverage"](https://github.com/aws/aws-lc-rs/pull/1103). A real regression existed and was fixed: [issue #993, `"-Wp,-U" breaks cross-builds using zig cc`](https://github.com/aws/aws-lc-rs/issues/993) — historical, not currently open.
- **`aarch64-pc-windows-msvc`**: needs `bindgen` (no pre-generated Windows bindings) plus a genuine MSVC sysroot. [`aws-lc-rs#453`](https://github.com/aws/aws-lc-rs/issues/453) (closed 2024-07-17) documents a real linkage failure cross-compiling this exact triple from a Windows CI runner — unresolved externals (`__imp_ftell`, `__imp_strdup`, `__imp__setmode`) traced by maintainers to a MinGW header (`_mingw_mac.h`, defining `__imp_*` macros) leaking into the include path, compounded by a CRT-linkage (`/MT`/`/MD`) mismatch in the CMake config. `xwin` sidesteps the root cause structurally: it stages a real Microsoft SDK/MSVC toolchain (via `xwin` itself, which the eight-triple matrix already depends on for `x86_64-pc-windows-msvc`) with no MinGW headers anywhere on the include path. ocx's own `Cargo.toml` documents `cargo xwin build -p ocx_shim --profile shim --target aarch64-pc-windows-msvc` as a real, currently-used build command in this tree — first-party confirmation the combination works today, independent of the historical bug report.
- No triple in this matrix needs `ring` as a fallback: `aws-lc-rs` is the sole active provider feature (finding 2), and its build needs are met by the toolchains the matrix already provisions (`zig cc` for musl/aarch64-linux, native Xcode toolchain for darwin, `xwin`'s MSVC sysroot for windows-msvc).

## Normative guidance candidates

1. **Never let `rustls` resolve with both the `aws-lc-rs` and `ring` cargo features active at once.** *Rationale*: this is the actual precondition for the "no process-level CryptoProvider" panic (`get_default_or_install_from_crate_features()`); reqwest's own client-construction code never triggers it, so the panic can only reach these binaries through a future dependency that both bypasses reqwest's provider handling and breaks feature unification. **Verification**: `cargo tree -e features -i rustls` (run from each workspace root) — `aws-lc-rs` must be the *only* provider-feature line in the output; add this as a CI check (`cargo tree -e features -i rustls | grep -c '"ring"'` must be `0`) rather than trusting `Cargo.lock` presence, since `ring` can appear in the lockfile as an unreached optional dependency (verified true today via `cargo tree -i ring --target all` → "nothing to print") without being active.
2. **Do not add an explicit `rustls::crypto::*::default_provider().install_default()` call anywhere in production code.** *Rationale*: it's unnecessary (reqwest already falls back to a local `aws-lc-rs` provider per `ClientConfig` when none is installed) and, per rustls's own contract, can only be called once per process — adding it creates a footgun for any future test harness or embedding scenario that also wants to install a provider (e.g., a mock TLS backend), which would then panic on the second call. **Verification**: `grep -rn "install_default" --include='*.rs' -- ':!*/tests/*' -- ':!external/*'` (excluding the vendored fork's test-only jsonwebtoken call) returns nothing.
3. **Never call bare `rustls::ClientConfig::builder()`; always use `builder_with_provider(provider)` when constructing rustls configs directly** (as opposed to going through reqwest, which already does this correctly). *Rationale*: the zero-arg form is the one function (`get_default_or_install_from_crate_features`) that can panic on feature ambiguity or missing features; the explicit form can't, because the provider is supplied by the caller. **Verification**: `grep -rn "ClientConfig::builder()" --include='*.rs'` in any first-party crate should return zero matches; any hit is a candidate for this rule.
4. **Keep `webpki-root-certs` roots merged (`tls_certs_merge` / repeated `add_root_certificate`), never switch to `tls_certs_only`.** *Rationale*: `tls_certs_only` disables the platform verifier and the corporate-proxy/`SSL_CERT_FILE` override path entirely — a silent behavior change for any user behind a MITM-inspecting proxy. **Verification**: `grep -rn "tls_certs_only" --include='*.rs'` across both trees should return zero call sites (only the reqwest source itself defines the method).
5. **Regression-test that the embedded root set is non-empty**, mirroring `grimoire/src/tls.rs::oci_extra_roots_is_non_empty`. *Rationale*: an empty embedded set silently reopens the `Verifier::new()` empty-store panic on any host without a system trust store — the actual reachable panic in this stack, verified by reading the fallback chain in reqwest → oci-client → rustls-platform-verifier. **Verification**: the test exists and is green in CI; `cargo test oci_extra_roots_is_non_empty` (grimoire) / equivalent for ocx's `seed_embedded_roots`.
6. **Pin toolchain container images used for cross-compiling by digest when the upstream image has no stable version tag** (as ocx already does for `messense/cargo-xwin`); pin CLI tools with real releases (`cargo-zigbuild`) by exact version. *Rationale*: an unpinned `:latest` Windows cross-toolchain image is a silent supply-chain and reproducibility risk on every release build. **Verification**: `grep -n "image:" .github/workflows/*.yml` — every cross-toolchain image reference must include `@sha256:` or an exact version, never a bare `:latest`/`:main`.
7. **Do not add `cross` (cross-rs/cross) to this project's toolchain.** *Rationale*: it cannot build 2 of the 8 required triples (`apple-darwin`, no image exists, Apple SDK licensing) and doesn't cover the MSVC ABI either (its Windows images are `-gnu` only) — `zigbuild` + `xwin` already cover the full matrix and `cross` adds a second, redundant Docker-based toolchain with no coverage gap it fills. **Verification**: `grep -rln "cross" .github/workflows/ taskfiles/ 2>/dev/null | xargs grep -l "cross-rs\|cargo cross\b"` — should be empty; if someone adds it, this rule is the thing to point them at.
8. **When bumping `cargo-zigbuild`'s pinned version, re-check `aws-lc-rs`'s zig-cc compatibility notes first** (issue #993-class regressions have happened before). *Rationale*: `aws-lc-rs` has C/assembly build steps that are sensitive to the exact flags `zig cc` passes; a `cargo-zigbuild` bump can silently break the musl/aarch64-linux legs even though nothing in this project's own code changed. **Verification**: after any `cargo-zigbuild` version bump, run `cargo zigbuild --target aarch64-unknown-linux-musl --release` locally/in CI before merging, don't just trust the version-pin diff.

## AI-agent angle

An autonomous coding agent asked to "fix the TLS panic" or "add rustls setup" in this codebase is very likely to:

- **Confuse `jsonwebtoken::crypto::CryptoProvider` with `rustls::crypto::CryptoProvider`.** Both types are named `CryptoProvider`, both have an `install_default()` method with an identical one-shot-per-process contract, and both appear together in the same vendored file (`external/rust-oci-client/src/lib.rs`). An agent grepping for "CryptoProvider" and finding an existing `install_default()` call will plausibly assume the TLS provider is already installed process-wide and skip investigating the actual reqwest fallback behavior — or, worse, "fix" a perceived gap by adding a *second*, real `rustls::crypto::aws_lc_rs::default_provider().install_default()` call in production code, which does nothing useful today and becomes a live footgun (panics on a second call) the moment any test harness or future embedding also wants to install a provider. **Smallest mechanical check**: before touching anything under "CryptoProvider", `grep -n "use.*CryptoProvider\|::crypto::" <file>` and confirm which crate's `crypto` module is in scope — `jsonwebtoken::crypto::` vs `rustls::crypto::` — before writing about "the" CryptoProvider.
- **Assume the presence of `ring` in `Cargo.lock` means two providers are active** and "fix" it by adding `default-features = false` tweaks or an explicit provider-disambiguation call that isn't needed. **Smallest mechanical check**: `cargo tree -e features -i rustls`, not `grep ring Cargo.lock` — the lockfile lists resolvable packages across the whole feature space, not what's actually active for the default build.
- **Reach for `cross` by habit** (it's the best-known name for "Rust cross-compilation") when asked to add a new target or fix a cross-build, without checking whether it can even build the target in question. **Smallest mechanical check**: before invoking or recommending `cross` for any target in `{aarch64,x86_64}-apple-darwin` or any `*-pc-windows-msvc`/`*-pc-windows-gnullvm` target, check `docker/` in the `cross-rs/cross` repo (or just recall: no darwin image exists, Windows images are `-gnu` only) — this project already solved cross-compilation with `zigbuild`+`xwin`, and `cross` is not a drop-in alternative for either.
- **Treat "bundled roots" and "system trust" as mutually exclusive**, and "fix" a corporate-proxy complaint by ripping out `webpki-root-certs` (assuming it's what's overriding the corporate cert) or by switching to `tls_certs_only` (assuming that's needed to make embedded roots "take effect"). Both trees' actual behavior is additive merge, not replacement — verified against reqwest source, not assumed. **Smallest mechanical check**: `grep -n "tls_certs_only\|tls_certs_merge\|add_root_certificate" src/tls.rs` and confirm which method is used before touching root-cert handling; only `tls_certs_only` disables system trust.

## Contested / evolving

- **rustls 0.24 is in active pre-release development** (tracking issue [`rustls/rustls#2400`](https://github.com/rustls/rustls/issues/2400), open, last updated 2026-07-29) but as of this research (2026-08-14) has not shipped and its tracked scope doesn't include a provider-selection contract change. Direction: stable, not urgent to plan around — but re-check this issue before any future rustls major bump.
- **`aws-lc-rs` vs `ring` as the ecosystem default remains a live debate elsewhere** (e.g. the Rustup project's own migration discussion referenced inside [`aws-lc-rs#453`](https://github.com/aws/aws-lc-rs/issues/453): "we ... are trying to replace the `ring` backend with `aws-lc-rs` ... as a part of Rustup's plan to ship the `rustls` backend by default"). This project has already made the same choice (aws-lc-rs, confirmed via `cargo tree`) but the broader ecosystem hasn't fully converged — expect continued churn in downstream crates' default feature choices for a while yet.
- **`cargo-zigbuild`'s pinned version (0.22.3) trails current upstream (0.23.0, released 2026-06-18) for the Windows-gnullvm shim build**, while the Linux-triple builds in `deploy-dev.yml` install `cargo-zigbuild` unpinned (via `taiki-e/install-action` with no version specified, so it floats to latest). This is an inconsistency between the two zigbuild usages in the same repo — worth a deliberate reconciliation pass, not treated as settled.
