## Summary

- Buildifier's linter has ~84 distinct warning categories (`WARNINGS.md` lists 90 anchors, several collapsed onto one entry — the 18 `native-cc-*` names and 14 `native-java-*` names each share one writeup); **only one, `unsorted-dict-items`, is off by default** — confirmed in `warn/warn.go`'s `nonDefaultWarnings` map, which contains exactly that single key.
- `rules_ocx`'s own `buildifier.check` target (`BUILD.bazel`) sets neither `warnings = "all"` nor an explicit list — it inherits buildifier's default set, meaning it already gets ~83 of 84 checks for free, but nobody in the repo has verified that, and `unsorted-dict-items` is silently off.
- `rules_ocx`'s check target uses `lint_mode = "warn"` with `mode = "diff"` — this **prints** lint findings but does not fail the Bazel action on a lint violation the way `lint_mode = "fix"` on `//:buildifier.fix` would; only formatting drift fails `mode = "diff"`. CI's `task lint` step needs to be read for whether it separately greps buildifier's warning output for non-zero findings.
- Roughly 40 of the ~84 warnings carry a named `--incompatible_*` Bazel flag (e.g. `attr-cfg` → `--incompatible_disallow_data_transition`, `ctx-actions` → `--incompatible_new_actions_api`); the rest (naming, docstrings, `positional-args`, `bzl-visibility`, `overly-nested-depset`) are pure style with no flag and no future removal — buildifier is their only enforcement mechanism.
- The 18-name `native-cc-*` family and the ~14-name `native-java-*` family all resolve to one flag, `--incompatible_autoload_externally`, which is the single biggest current migration surface: it went from "list of removed rules" in Bazel 8 to **`--incompatible_autoload_externally=` (empty) by default in Bazel 9** ([issue #23043](https://github.com/bazelbuild/bazel/issues/23043), closed 2026-02-05), meaning every native rule call needs an explicit `load()` under Bazel 9 that worked silently under 8.
- `load-on-top`, `out-of-order-load`, and `same-origin-load` are marked "Obsolete... implemented in the formatter" and "Not supported by the latest version of Buildifier" — these three are no longer separately toggleable lint categories; the formatter (`buildifier` with no `-lint` flag at all) already applies their fixes unconditionally except in `WORKSPACE` files.
- `attr-package-metadata` is also flagged "Not supported by the latest version of Buildifier" in the current `WARNINGS.md` — it is documented but effectively inert; a rule that tells someone to `# buildifier: disable=attr-package-metadata` is citing a dead category.
- The BUILD style guide and `.bzl` style guide together assert roughly 45 concrete do/do-not rules; only about half map to a buildifier warning (glob wildcard, load order, docstrings, naming, positional args). The other half — package-scoped `default_visibility`, minimizing exported `.bzl` symbols, "prefer DAMP over DRY," no dependency-list variables — have **no mechanical check at all**, which is exactly the gap a lore rule should flag as "grep for this yourself."
- The BCR's `incompatible_flags.yml` — the actual file BCR presubmit uses via Bazelisk's `--migrate` — currently tracks only **6 active flags** (`--incompatible_config_setting_private_default_visibility`, `--incompatible_disable_starlark_host_transitions`, `--incompatible_disable_native_repo_rules`, `--incompatible_autoload_externally=`, `--incompatible_disable_autoloads_in_main_repo`, `--incompatible_strict_action_env`), with a seventh (`--noincompatible_enable_deprecated_label_apis`) commented out pending an unresolved bug. This is a far smaller, far more authoritative list than the general `--incompatible-change`-labeled issue backlog (30+ open, dozens closed).
- The prose page `bazel.build/release/backward-compatibility` **names no flags at all** — it describes only the *process* (file a GitHub issue, ship behind a flag) and defers to the GitHub issue tracker and `bazel.build/llms.txt`. A rule that needs "the current flag list" should point at BCR's `incompatible_flags.yml`, not this page.
- Flags that flipped in the **last 18 months**, confirmed via `gh api` issue-close dates: `--incompatible_use_new_cgroup_implementation` (closed 2026-08-05, targets Bazel 9, changes `--experimental_sandbox_limits` from no-op to effective), `--incompatible_stop_exporting_language_modules` (closed 2026-06-22), `--incompatible_disable_non_executable_java_binary` (closed 2026-05-11), `--incompatible_check_testonly_for_output_files` (closed 2026-03-06), `--incompatible_autoload_externally=` (closed 2026-02-05), `--incompatible_strict_action_env` (closed 2025-11-24), `--incompatible_disable_native_repo_rules` (closed 2025-09-17).
- BCR acceptance is procedural, not automatic: every module version needs a `presubmit.yml`, the registry is **add-only** (a broken version gets a new `X.Y.Z.bcr.N` release, never an edit), `compatibility_level` bumps are presubmit-checked against the previous version, and a **test module or anonymous-module build check is "highly recommended"** but not hard-required.
- BCR names its own naming-collision review policy in prose, not code: overly generic names (`package-utils`) get rejected in favor of `mycompany-package-utils`; official-sounding prefixes (`rules_`, `toolchains_`) on a non-canonical module are explicitly called out as confusing.
- `rules_lint` (Aspect) formalizes linting as a Bazel **aspect** producing an `exit_code` output group and human-readable `rules_lint_human` output group, invoked either via `bazel build --config=lint --output_groups=rules_lint_human //...` or via the paid Aspect Workflows GitHub App (`aspect lint //...`); it supports 40+ linters (ESLint, Ruff, Clippy, ShellCheck, buildifier itself, buf lint, Stylelint) — meaning a fleet repo adopting Bazel gets one *mechanism* to replace today's ad hoc `ocx exec -- <linter>` pattern, one language at a time.
- Two competing patterns exist for provisioning dev tools inside a Bazel repo: `bazel-contrib/rules_multitool` (declarative per-tool binaries) and `buildbuddy-io/bazel_env.bzl` (a `direnv`-backed virtual PATH). `rules_ocx` uses neither — it dogfoods its own OCX-provisioned toolchain — which is a genuine, undocumented three-way choice a "Bazel-friendly architecture" rule must name rather than assume away.
- Aspect's own `.bazelrc` recommendations (`--nolegacy_external_runfiles`, `--sandbox_default_allow_network=false`, `--experimental_remote_merkle_tree_cache`, `--remote_local_fallback`) are **none of them present** in `rules_ocx`'s checked-in `.bazelrc`, which currently sets only `--enable_platform_specific_config`, `--incompatible_disallow_empty_glob`, `--windows_enable_symlinks`/`--enable_runfiles`, and `--test_output=errors`.
- Content-defined chunking for remote caching (`--experimental_remote_cache_chunking`) needs **Bazel 8.7 or 9.1+** per BuildBuddy's own docs — `rules_ocx` pins exactly 8.7.0, meaning the fleet's one Bazel repo is right at the version floor for a flag it does not currently set.
- Bzlmod migration guidance (`bazel.build/external/migration`) flags `bind` as unsupported under Bzlmod, requires `register_toolchains`/`register_execution_platforms` to live only in `MODULE.bazel` (not a module extension), and states the now-confirmed deadline: WORKSPACE support disabled by default in Bazel 8, code fully removed in Bazel 9.
- `rules_ocx`'s own CI comment (`ci.yml`) documents a live Bazel-9 regression already worked around in the fleet: **stardoc's generated `docs/*.md` gains an extra `repo_mapping` attribute row under Bazel 9+**, so the docs-freshness golden-diff test only runs on the pinned 8.7.0 leg — a concrete, dated (as of this CI file) instance of "recent shift invalidates older doc-generation assumptions."

**Buildifier flags that matter** (from `buildifier/config/config.go`, fetched verbatim): `-lint={off,warn,fix}` (default `off` — a bare `buildifier` call with no `-lint` flag runs **no lint at all**, only formatting); `-warnings=<comma-list>|all` (empty means [`warn.DefaultWarnings`](https://raw.githubusercontent.com/bazelbuild/buildtools/master/warn/warn.go) = all-but-`unsorted-dict-items`); `-mode={check,diff,fix}` (default `fix`); `-type={build,bzl,workspace,module,repo,vendor,default,auto}`; `-tables`/`-add_tables` (replace/merge the naming and load-location tables); `-config=path.json` for a `.buildifier.json`. `rules_ocx`'s two targets: `buildifier.fix` (`lint_mode="fix"`, `mode="fix"`) and `buildifier.check` (`lint_mode="warn"`, `mode="diff"`) — confirmed by reading `BUILD.bazel` directly; neither sets `-warnings`, so both get the ~83-warning default set, but `buildifier.check`'s `warn` lint-mode only *prints* findings rather than failing the build the way `fix` mode's diff-detection does for formatting.

### 2. Bazel BUILD style guide — [bazel.build/build/style-guide](https://bazel.build/build/style-guide)

~30 concrete rules. Highlights not already covered by a buildifier warning: package-scoped `default_visibility` must never be `//visibility:public` (no mechanical check — grep for the string); dependencies should be direct-only, never transitive, and never hidden behind a shared list variable ("DAMP over DRY" is the stated rationale — no check, it's a code-review judgment call); list comprehensions are banned at BUILD top level (no dedicated warning, though `no-effect` catches some misuse); recursive globs (`**/*.java`) are banned outright, distinct from buildifier's narrower `constant-glob` check.

### 3. .bzl style guide — [bazel.build/rules/bzl-style](https://bazel.build/rules/bzl-style)

~25 concrete rules layered on top of the buildifier-enforced ones. The load-bearing ones with no mechanical check: "use rules whenever possible instead of macros"; macro-generated implementation-detail targets need `visibility = ["//visibility:private"]` and a `manual` tag to escape wildcard expansion; positional args block future migration from legacy macros to **symbolic macros** (a Bazel 8 feature) — this ties `positional-args` directly to a version-specific migration path, not just style; attribute names should stay consistent with the corresponding rule's existing attribute names across a ruleset family.

### 4. Aspect's bazelrc presets and flag guidance

[`bazel-contrib/bazelrc-presets`](https://raw.githubusercontent.com/bazel-contrib/bazelrc-presets/main/README.md) generates a version-matched `.bazelrc` snippet meant to be vendored and code-reviewed (explicitly *not* semver-safe, because a preset bump can change build behavior silently if auto-pulled). Separately, [Aspect's ".bazelrc flags you should enable"](https://aspect.build/blog/bazelrc-flags) names specific always-on flags: `--nolegacy_external_runfiles` (sandbox perf, some rules break under it), `--host_jvm_args=-DBAZEL_TRACK_SOURCE_DIRECTORIES=1` (directory-as-`srcs` invalidation), `--experimental_remote_merkle_tree_cache`/`--experimental_remote_merkle_tree_cache_size`, `--remote_local_fallback`, `--sandbox_default_allow_network=false` (catches non-hermetic network-dependent actions/tests), `--incompatible_allow_tags_propagation`. None of these are set in `rules_ocx`'s `.bazelrc` (confirmed by direct read).

### 5. BuildBuddy and EngFlow remote-cache flag guidance

Via search (not a raw fetch — flagged secondary in the sources table): BuildBuddy recommends `--experimental_remote_cache_chunking` for content-defined chunking, **gated to Bazel 8.7 or 9.1+** — `rules_ocx` pins exactly 8.7.0, i.e. it sits at the version floor for this flag today. `--remote_download_minimal` is recommended from Bazel 7.0+ to reduce BwoB transfer; `--disk_cache` plus `--experimental_disk_cache_gc_max_age` (below the remote TTL) round out the local-fallback story.

### 6. The `--incompatible_*` flag catalogue — three complementary sources

- **BCR's own tested set** — [`incompatible_flags.yml`](https://raw.githubusercontent.com/bazelbuild/bazel-central-registry/main/incompatible_flags.yml), fetched verbatim: 6 active flags (listed in Summary), each tagged with the Bazel major-version tracks it's tested against (`6.x`/`7.x`/`8.x`/`last_green`/`rolling`), plus one commented-out flag (`--noincompatible_enable_deprecated_label_apis`) pending [issue #23144](https://github.com/bazelbuild/bazel/issues/23144).
- **The general issue backlog** — `gh api search/issues` against `repo:bazelbuild/bazel label:incompatible-change`: 28 open issues (newest: [`#30642` `--incompatible_bazel_external_directory`](https://github.com/bazelbuild/bazel/issues/30642), [`#28082`/`#28081` removing `ctx.objc_fragment`/`ctx.apple_fragment`](https://github.com/bazelbuild/bazel/issues/28082)), and 30+ closed issues with close dates back through 2022 — the ones closed in the **last 18 months** are the Recent Shifts list above.
- **The prose page** — [`bazel.build/release/backward-compatibility`](https://bazel.build/release/backward-compatibility) itself names zero flags; it states policy only ("It is recommended to use `--incompatible_*` flags for breaking changes," "a GitHub issue explains the change... and aims to provide a migration recipe") and defers elsewhere.

Individual issue bodies read for migration detail: [`#23043`](https://github.com/bazelbuild/bazel/issues/23043) (`--incompatible_autoload_externally`, closed 2026-02-05 — full migration table: Bazel 8 needs `protobuf>=28.3`, `rules_java>=8.5.1`, `rules_cc>=0.0.17`; Bazel 9 sets the flag to empty by default, requiring explicit `load()`s); [`#28244`](https://github.com/bazelbuild/bazel/issues/28244) (`--incompatible_use_new_cgroup_implementation`, closed 2026-08-05, targets Bazel 9, makes `--experimental_sandbox_limits`/`--experimental_sandbox_enforce_resources_regexp` take effect where they were previously no-ops).

### 7. Bazel Central Registry policies — [`docs/bcr-policies.md`](https://raw.githubusercontent.com/bazelbuild/bazel-central-registry/main/docs/bcr-policies.md) and [`docs/README.md`](https://raw.githubusercontent.com/bazelbuild/bazel-central-registry/main/docs/README.md)

Both fetched verbatim. Concrete, quotable rules: "Add-only: existing module versions must not be modified to ensure reproducible builds"; "Every module version must have a presubmit.yml file"; "BCR modules can only depend on modules already in the BCR"; naming review is manual and prose-only ("a module named `package-utils` would be too generic... `mycompany-package-utils` would work instead"); `compatibility_level` bump vs the previous version is presubmit-validated (`@bazel-io skip_check compatibility_level` to override deliberately); a "test module" or "anonymous module test" build check is **"highly recommended"**, not mandatory; a yanked version blocks resolution unless the user passes `--allow_yanked_versions` or sets `BZLMOD_ALLOW_YANKED_VERSIONS`; maintainer response SLA is stated as "most PRs may be addressed in 3 business days."

### 8. Bzlmod migration guide — [bazel.build/external/migration](https://bazel.build/external/migration)

Names the concrete incompatibilities: `bind` is "deprecated and not supported in Bzlmod" (replace with `alias` or direct external-repo references); `register_toolchains`/`register_execution_platforms` "are only available in the MODULE.bazel file" — a module extension cannot call `native.register_toolchains`; `local_path_override` requires the target to already be a Bazel module (unlike the more flexible legacy `local_repository`); confirms the deadline already known from the frame — WORKSPACE disabled by default in Bazel 8, fully removed in Bazel 9.

### 9. Bazel 8 and 9 release announcements

[Bazel 8.0 LTS](https://blog.bazel.build/2024/12/09/bazel-8-release.html) (2024-12-09): WORKSPACE/WORKSPACE.bzlmod no longer auto-read by default; symbolic macros ship with typed attributes, macro-aware visibility, and rule finalizers; Android/C++/Java/Protobuf/Python/Shell rules "Starlarkified" into separate modules, migration required "by 2025... before Bazel 9 releases"; `--incompatible_autoload_externally` introduced as the transition mechanism. [Bazel 9 LTS](https://blog.bazel.build/2026/01/20/bazel-9.html) (2026-01-20): WORKSPACE code fully removed ("`--enable_bzlmod` and `--enable_workspace` are now no-ops"); built-in C++ rules removed into `rules_cc`; `--incompatible_autoload_externally` empty by default; `bazel sync` command removed entirely.

### 10. rules_lint's aspect pattern — [aspect-build/rules_lint](https://github.com/aspect-build/rules_lint)

Runs linters as Bazel **aspects** attached to existing `*_library`/`*_binary` targets with no BUILD-file changes required. Produces two output groups per the aspect contract: a CI-facing `exit_code`-style group and a human-readable `rules_lint_human` group; direct invocation is `bazel build --config=lint --output_groups=rules_lint_human //...`, or via the paid Aspect Workflows GitHub App as `aspect lint //...` with inline PR review comments. Claims 40+ supported linters/formatters spanning JS (ESLint), Python (Ruff), Rust (Clippy), Shell (ShellCheck), Starlark (buildifier itself), Protobuf (buf lint), CSS (Stylelint), and formatters (Prettier, gofmt, rustfmt, ktfmt). This is the pattern a fleet repo adopting Bazel would use to fold today's per-language `ocx exec -- <linter>` invocations into one Bazel-native mechanism.

### 11. Dev-tool provisioning patterns: rules_multitool vs bazel_env.bzl vs OCX

Two named community patterns exist for "how does a Bazel repo give developers the same tool versions the build uses": `bazel-contrib/rules_multitool` (declarative per-platform tool binaries as a Bazel dependency) and [`buildbuddy-io/bazel_env.bzl`](https://raw.githubusercontent.com/buildbuddy-io/bazel_env.bzl/main/README.md) (creates a stable-path virtual PATH, wired through `direnv`, so "all developers... share the same tool versions as used in the Bazel build for IDEs and local usage" — read verbatim). `rules_ocx` is a **third pattern**: it is itself a module extension that provisions tools through the OCX package manager, and dogfoods that mechanism for its own dev toolchain (confirmed via `MODULE.bazel`'s "Dogfooding" comment). None of the three is objectively superior in any source read; this is a genuine open choice a "Bazel-friendly architecture" topic must name.

### 12. rules_ocx's own configuration, read directly

`BUILD.bazel`: two `buildifier()` targets as detailed in Survey §1. `MODULE.bazel`: `buildifier_prebuilt` pinned at `8.2.0.2` as a `dev_dependency`; `rules_shell` and `stardoc` also `dev_dependency`. `.bazelrc`: four active lines beyond the try-import of the gitignored `.bazelrc.user` — `--enable_platform_specific_config`, `--windows_enable_symlinks` (startup) / `--enable_runfiles` (windows-only), `--incompatible_disallow_empty_glob`, `--test_output=errors`. `.github/workflows/ci.yml`: a `lint` job running `ocx exec -- task lint` (which wraps `bazel run //:buildifier.check`, `actionlint`, license-header, link, and dist-snapshot checks per `taskfile.yml`), and a `test` job matrixed over `{ubuntu, macos, windows} × {8.7.0, 9.x, rolling}` where the `rolling` leg is `continue-on-error: true` ("forward-compat early-warning only — never blocks," per the file's own comment) — and a code comment documenting a live Bazel-9 stardoc regression (`repo_mapping` attribute row appears in generated docs under Bazel 9+, so the golden-diff docs-freshness check only runs on the pinned 8.7.0 leg). `AGENTS.md`/`.claude/rules/starlark.md`: module extension impl is asserted `reproducible = True`; every `repository_ctx.getenv`/`watch()` call is inventoried by convention, not by an automated grep; every public symbol requires a docstring, stricter than buildifier's own 5-statement-function threshold.

## Recent shifts seen in this corpus

- **`--incompatible_autoload_externally` went from "list of removed native rules" (Bazel 8, closed backport) to empty-by-default (Bazel 9.0, closed 2026-02-05, [#23043](https://github.com/bazelbuild/bazel/issues/23043))** — this single flag is why every `native-cc-*`/`native-java-*`/`native-proto*`/`native-py`/`native-sh-*` buildifier warning suddenly matters for real, not just as style.
- **`--incompatible_use_new_cgroup_implementation` closed 2026-08-05** (three weeks before this research date), targeting Bazel 9 — makes `--experimental_sandbox_limits` and `--experimental_sandbox_enforce_resources_regexp` take effect where they were previously silent no-ops. Any repo already passing those flags "for future-proofing" gets a behavior change the moment it moves to 9.
- **WORKSPACE is now fully gone, not just disabled** — Bazel 8 (2024-12-09) disabled auto-reading it; Bazel 9 (2026-01-20) deleted the supporting code entirely, and `--enable_bzlmod`/`--enable_workspace` became no-ops. Any older guidance that says "WORKSPACE still works if you pass a flag" is now wrong under 9.
- **`--experimental_remote_cache_chunking` requires Bazel 8.7 or 9.1+** (BuildBuddy) — a flag that did not exist as a usable option until very recently at the fleet's exact pinned version.
- **Content-defined-chunking and cgroup-v2 changes both land inside 2026**, meaning training-data-era advice about remote cache transfer sizing or sandbox resource limits from before mid-2026 should be treated as stale for this fleet's pinned version.
- **rules_lint's aspect + output-group pattern is the current recommended mechanism for Bazel-native linting** as of this corpus, superseding older ad hoc "wrap the linter in a genrule" patterns that predate the aspect ecosystem's stabilization.
- **A live, dated regression already hit the fleet**: stardoc's generated docs gained an extra `repo_mapping` attribute row under Bazel 9+, breaking a golden-diff docs-freshness test that only the pinned 8.7.0 CI leg still passes (rules_ocx `ci.yml` comment) — concrete evidence that "generate docs once, diff forever" needs a stated Bazel-version owner.

## Contested

- **How strict should default `-warnings` be?** Buildifier's own maintainers ship 83 of 84 warnings on by default and call the remaining one (`unsorted-dict-items`) too noisy for general use — but several large adopters (implied by the "used inside google3" comment on `DefaultWarnings` in `warn.go`) still treat that default as the floor, not the ceiling, and add `-warnings=all` deliberately when they want the sorted-dict check too. No source in this corpus states a universal answer; `rules_ocx` currently takes the unexamined default.
- **`lint_mode="warn"` vs `"fix"` in CI.** Aspect's `buildifier_prebuilt` rule offers both; `rules_ocx` uses `"warn"` for its check target specifically so CI can report without auto-mutating trees mid-PR, but this trades away hard enforcement of the ~40 flag-backed and ~20 style-only warnings unless something downstream inspects the warn output for non-zero findings. No source resolves whether report-only linting is "enough" in a fleet where the same CI also runs a separate `mode=diff` formatting check.
- **rules_multitool vs bazel_env.bzl vs a custom package-manager extension (rules_ocx's own approach) for dev-tool provisioning.** All three are live, maintained patterns; none of the sources read here compares them head to head, and `rules_ocx` is itself evidence that "roll your own module extension" is a viable fourth option nobody in the official corpus documents as a named pattern. This is trending toward more entrants, not consolidation — worth flagging as unsettled rather than picking a side.
- **How much to trust `bazel.build/release/backward-compatibility` as a starting point.** The page itself defers to GitHub issues and `bazel.build/llms.txt` rather than listing flags, which reads as the Bazel team deliberately keeping the flag list in code (`incompatible_flags.yml`, issue labels) rather than prose that goes stale. A rule built against the prose page would already be out of date; one built against the YAML file tracks BCR's own presubmit reality.
