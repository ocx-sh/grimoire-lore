## Summary

- Symbolic macros are the default macro flavor as of Bazel 8 ("Symbolic macros are available by default in Bazel 8"); legacy macros are the fallback, not the recommendation.
- WORKSPACE was disabled by default in Bazel 8 and the migration guide states it "will be removed in Bazel 9" — Bzlmod is the only supported dependency system going forward.
- `compatibility_level` is now a documented anti-pattern: "You should stop using `compatibility_level`" and, "starting with Bazel 8.6.0 and 9.1.0, both `compatibility_level` and `max_compatibility_level` are no-ops."
- As read on 2026-09-05, Bazel's own support matrix lists **Bazel 9 as "Active"** (latest 9.2.0) and **Bazel 8 as "Maintenance"** (latest 8.8.0) — the fleet's `rules_ocx` pin at 8.7.0 sits one LTS major behind Active and is not the newest patch even within 8.
- Transitions carry an explicitly documented scaling failure mode: a per-target 1-input transition composed down a binary dependency tree "makes the build graph exponentially larger than the target graph," and the page's own mitigation section is a stub: "TODO: Add strategies for measurement and mitigation of these issues."
- Repository rules are only re-fetched when their attributes, their Starlark implementation, a declared/`getenv()`-read environment variable, or a `watch`ed path changes — anything else (network fetch results, arbitrary file reads) is invisible to Bazel's re-fetch trigger unless explicitly declared.
- Module extensions can mark themselves `reproducible = True` to be excluded from the lockfile and skipped from re-evaluation — cache/CI determinism for Bzlmod hinges on this flag being used honestly.
- The BUILD encyclopedia's `genrule` "General Advice" is a direct determinism checklist: no timestamps in output, stable ordering for sets/maps, relative paths only, no absolute paths, silent on success, and no directories/symlinks (Bazel doesn't track their structure for caching).
- `--incompatible_*` flags are the sanctioned breaking-change mechanism; the corpus states flatly "Never run production builds with `--experimental_*` or `--incompatible_*` flags."
- Test size (`small`/`medium`/`large`/`enormous`) maps to fixed RAM (20/100/300/800 MB), CPU (1 core each), and default timeout (1/5/15/60 min) — `timeout` can override the size-derived default independently.
- `flaky = True` re-runs a test up to three times and reports pass on any success, but the docs call this "generally discouraged."
- `shard_count` is capped at 50 and silently does nothing unless the test runner implements the sharding protocol.
- Sandbox-control tags (`no-sandbox`, `no-cache`, `no-remote-cache`, `no-remote-exec`, `no-remote`, `no-remote-cache-upload`, `local`, `requires-network`, `block-network`, `requires-fakeroot`) are read from both test/genrule `tags` and Starlark action `execution_requirements` — the same string means different things at different action types.
- `manual` on a target's `tags` removes it from wildcard (`...`, `:all`) and `test_suite` expansion for `build`/`test`/`coverage`, but not from `query` — a common source of "why didn't this run in CI" confusion.
- `--remote_download_minimal` (Build without the Bytes) is the documented fix for network-bound remote-execution builds, traded off against losing local copies of intermediate artifacts.
- `aquery` output order is explicitly unspecified: "In general, do not depend on the order of output."
- The BCR requires a `presubmit.yml` per module version, validates `compatibility_level` stability against the previous version, and escalates to required maintainer review when a module has no maintainer or when `presubmit.yml` changes "beyond just platform names or bazel versions."
- BCR module naming policy actively discourages `rules_`/`toolchains_`-prefixed names for anything that isn't the well-known canonical ruleset, to avoid confusing users about what's official.
- The MODULE.bazel.lock has a documented, narrow safe-merge path (`registryFileHashes`, `selectedYankedVersions` only); every other conflict must be resolved by resetting the lockfile and running `bazel mod deps`, never by hand-editing.
- BCR "attestations" (source.json/MODULE.bazel/archive provenance verified via slsa-verifier) exist and are read by presubmit if present, but are explicitly marked "still experimental" and optional as of this corpus.

## Survey

1. **[Documentation index (llms.txt)](https://bazel.build/llms.txt)** — bazel.build publishes a machine-readable full index of its docs, versioned per release (HEAD: 318 pages; 9.1, 9.0, 8.7: 119 pages each). This confirms the doc tree structure used for the rest of this survey and gives an exact page inventory per Bazel version — useful for detecting when a page moves or is added between the fleet's pinned 8.7.0 and the currently active 9.x.

2. **[Concepts: build-ref, labels, build-files, dependencies, visibility, platforms](https://bazel.build/concepts/build-ref)** — defines the repository/workspace/package/target vocabulary the rest of the docs assume. `visibility.md` covers `//visibility:public|private`, package groups, and (per the extending/toolchains note below) that visibility interacts with `select()` default-visibility flags. `platforms.md` is titled "Migrating to Platforms" in the 8.7.0 snapshot, signaling the platform system is still framed as a migration target even at that version.

3. **[Extending: Macros](https://bazel.build/extending/macros)** — "Symbolic macros are available by default in Bazel 8. Where this document mentions `macros`, it's referring to **symbolic macros**." `inherit_attrs` lets a macro inherit a rule's or another macro's public attributes (or the special string `"common"`), with `None` used to explicitly drop an inherited attribute — quoted example: `"defines": None,  # do not inherit native.cc_library's defines attribute`. Inherited non-mandatory attributes always default to `None` regardless of the original rule's default, so macro implementations must handle the `None` case explicitly.

4. **[Extending: Configurations (transitions)](https://bazel.build/extending/config)** — "Important: Transitions have memory and performance impact." The worked "badly-behaved builds" case study shows a per-edge transition producing `2^n` configured targets for a tree of depth `n`, concluding "This makes the build graph exponentially larger than the target graph, with corresponding memory and performance consequences," immediately followed by "TODO: Add strategies for measurement and mitigation of these issues" — the canonical docs admit they don't yet answer how to detect this.

5. **[Extending: Rules](https://bazel.build/extending/rules)** — action purity contract: "Actions must list all of their inputs... Actions must create all of their outputs... Actions are comparable to pure functions: They should depend only on the provided inputs, and avoid accessing computer information, username, clock, network, or I/O devices." Naming contract: "Test rules must have names that end in `_test`... Non-test rules must not have this suffix." Deprecated-features section flags predeclared-output executables and legacy struct-based providers ("*This style is deprecated and should not be used in new code*") and lists specific runfiles APIs to avoid: `ctx.runfiles(collect_data=...)`, `collect_default`, and `DefaultInfo.data_runfiles` in favor of `DefaultInfo.default_runfiles`.

6. **[Extending: Toolchains](https://bazel.build/extending/toolchains)** and **[Aspects](https://bazel.build/extending/aspects)** — toolchains decouple rule logic from platform-based tool selection via implicit private attributes and `toolchain_type`; aspects augment the dependency graph for cross-cutting concerns (IDE integration, codegen) without modifying the rules that produce the graph.

7. **[Extending: Execution groups / Automatic Execution Groups](https://bazel.build/extending/exec-groups)** — `--incompatible_auto_exec_groups` is the flag gating AEGs; the doc shows both the "set to true" (enable) and "set to false" (fully disable) forms, meaning it's still a live toggle rather than settled default behavior as documented here.

8. **[Extending: Optimizing Performance (depsets)](https://bazel.build/rules/performance)** — "the most common performance pitfall is to traverse or copy data that is accumulated from dependencies... these operations can easily take O(N^2) time or space." Concrete illustration: with plain lists, a diamond dependency graph re-lists a shared leaf value once per path; depsets dedupe by construction. Guidance: "avoid any flattening of depsets except for debugging."

9. **[External dependencies overview, Bazel modules, Module extensions](https://bazel.build/external/overview)** — Bzlmod's `MODULE.bazel`/`bazel_dep`/module-extension model, contrasted against WORKSPACE. `external/extension.md`: an extension can declare `reproducible = True` metadata so "Bazel [can] skip this extension when writing to the lockfile" and can even survive server restarts without persisting facts, provided its output is provably deterministic from its declared inputs.

10. **[Bazel Lockfile](https://bazel.build/external/lockfile)** — the lockfile "promotes reproducible builds" and enables "fast incremental resolutions" by skipping re-evaluation of unchanged extensions. Merge guidance is explicit and narrow: only `registryFileHashes` and `selectedYankedVersions` conflicts are safe to resolve by keeping both sides; "Other types of merge conflicts should not be resolved manually" — the prescribed recovery is `git reset MODULE.bazel.lock && git checkout MODULE.bazel.lock`, fix `MODULE.bazel`, then `bazel mod deps`. A custom `jq`-based git merge driver is documented as the automatic-resolution path.

11. **[Vendor Mode](https://bazel.build/external/vendor)** — `--vendor_dir` supports fully offline/hermetic builds by materializing external repos on disk; the vendor directory is recommended to be gitignored, not checked in.

12. **[Bzlmod Migration Guide](https://bazel.build/external/migration)** — "The WORKSPACE file is already disabled in Bazel 8 (late 2024) and will be removed in Bazel 9 (late 2025)." Confirms the frame's hypothesis as fact, though the stated dates are already behind the corpus's own "now" (this doc's text predates the September 2026 vantage point). Migration advice includes starting from a generated `WORKSPACE.bzlmod` and avoiding loading transitive dependencies via macros during the transition.

13. **[Repository Rules](https://bazel.build/external/repo)** — precise re-fetch trigger list: attribute changes, implementation Starlark changes, a changed `getenv()`/`environ`-declared env var (overridable via `--repo_env`), or a changed `watch`ed path (including paths implicitly watched by `read()`, `execute()`, `extract()`, `watch_tree()`, `path.readdir()`). The `configure` flag controls re-fetch on `bazel fetch --force --configure`; the `local` flag additionally re-fetches on every Bazel server restart. Anything a rule's implementation reads without declaring it through these channels is a hermeticity hole invisible to Bazel's caching.

14. **[Bazel registries, Frequently asked questions](https://bazel.build/external/registry)** — `compatibility_level`'s FAQ entry: "You should stop using `compatibility_level`... starting with Bazel 8.6.0 and 9.1.0, both `compatibility_level` and `max_compatibility_level` are no-ops," with the legacy documentation (increment on breaking change, but "incrementing... too frequently can be very disruptive") retained only for pre-8.6/9.1 compatibility.

15. **[Remote Caching](https://bazel.build/remote/caching)**, **[Persistent Workers](https://bazel.build/remote/persistent)**, **[Dynamic Execution](https://bazel.build/remote/dynamic)** — caching requires reproducible actions to pay off; persistent workers need `requires-worker-protocol` in the execution platform if not the default protocol; the previously-recommended `--experimental_spawn_scheduler` flag is now itself marked deprecated in favor of the modern dynamic-execution flag surface.

16. **[Advanced performance: breaking down build performance](https://bazel.build/advanced/performance/build-performance-breakdown)** — ties JSON trace profiles and `NetworkMetrics.SystemNetworkStats` (via `--experimental_collect_system_network_usage`, "new in Bazel 6.0") to diagnosing network-bound remote-execution builds, and names the fix: "consider turning on Build without the Bytes by passing `--remote_download_minimal`... This will speed up your builds by avoiding the download of unnecessary intermediate artifacts." A local disk cache (`--disk_cache`) is offered as an alternative bandwidth mitigation.

17. **[Write bazelrc configuration files](https://bazel.build/run/bazelrc)** — `.bazelrc` precedence and `--config`; version-gated flag syntax (`<` for flags removed in newer versions); naming convention advice for personal-rc `--config` names to start with `_` to avoid collisions with shared configs.

18. **[Configurable Build Attributes (select)](https://bazel.build/configure/attributes)** — canonical `select()` + `config_setting` example keyed on `values = {"cpu": ..., "compilation_mode": ...}`; explicit deprecation: "First of all, do not use `bind()`. It is deprecated in favor of `alias()`." Repo rules are called out as having no specific configuration and not being evaluated under `select()`.

19. **[Query Language, Query guide, cquery, aquery](https://bazel.build/query/language)** — `aquery` output order is unspecified ("do not depend on the order of output"); `query`'s dependency graph "may contain cycles that do not exist in the configured target graph" it operates over; `--universe_scope` and file-vs-BUILD/`.bzl` distinctions govern what `query` even sees (plain source files like `foo.cc` are ignored by the graph).

20. **[BUILD Style Guide](https://bazel.build/build/style-guide)**, **[.bzl style guide](https://bazel.build/rules/bzl-style)** — BUILD-file guidance: eponymous targets (matching the containing directory name) should exist "if there is such a target"; readability is explicitly prioritized over DRY ("readability is more important than avoiding repetition" in BUILD files, a different bar than `.bzl` files). `.bzl` style: "Important: Do not create a variable or macro just to avoid some amount of repetition"; document with docstrings per buildifier's `function-docstring` warning; an 80-column guideline that is explicitly "not required" and should not be strictly enforced.

21. **[Reference: test-encyclopedia, common-definitions (test size/timeout/flaky/shard_count/tags)](https://bazel.build/reference/test-encyclopedia)** — hermeticity is a hard requirement in spirit though not always enforced: "Tests should be hermetic... If tests are not properly hermetic then they do not give historically reproducible results." A long list of environment invariants a test must not assume: no absolute-path assumptions, no writable `/home`, atimes not guaranteed enabled, runfiles tree must not change mid-execution, must not remove/chmod test infra directories, must avoid `..` path components in runfiles. Size/timeout/RAM/CPU table (`common-definitions.md`): small=20MB/1min, medium=100MB/5min, large=300MB/15min, enormous=800MB/60min, all 1 CPU core assumed. `flaky`: reruns up to 3x, "use of this attribute is generally discouraged." `shard_count`: integer ≤ 50, requires runtime protocol support or "will most likely run every test in every shard, which is not what you want." Tags taxonomy (`no-sandbox`, `no-cache`, `no-remote-cache`, `no-remote-exec`, `no-remote`, `no-remote-cache-upload`, `local`, `requires-network`, `block-network`, `requires-fakeroot`, `exclusive`, `exclusive-if-local`, `manual`, `external`) each with distinct cache/sandbox/remote semantics.

22. **[Reference: build encyclopedia general (genrule, filegroup, alias, config_setting, test_suite)](https://bazel.build/reference/be/general)** — `genrule`'s "General Advice" is the corpus's most direct determinism checklist (see Summary). `test_suite` performs "test_suite expansion" transitively at `bazel test` time and is commonly filtered with negative tags (`tags = ["-flaky"]`). `licenses`/`output_licenses` common attributes are marked "part of a deprecated licensing API that Bazel no longer uses. Don't use this."

23. **[Release Model, Backward Compatibility](https://bazel.build/release)** — support matrix as read 2026-09-05: Bazel 10 Rolling, **Bazel 9 Active** (9.2.0, EOL Dec 2028), **Bazel 8 Maintenance** (8.8.0, EOL Dec 2027), Bazel 7 Maintenance (7.7.1, EOL Dec 2026), Bazel 6/5/4 Deprecated. Backward-compat policy: "Never run production builds with `--experimental_*` or `--incompatible_*` flags"; incompatible flags "are recommended to be back-ported to the latest LTS release without enabling the flag by default."

24. **[The Starlark Language Specification](https://github.com/bazelbuild/starlark/blob/master/spec.md)** — the language Bazel's rules/macros/extensions are written in: untyped, dynamically typed, Python-derived syntax, no floats by default in core Starlark (Bazel enables `float` as an extension), deterministic execution and immutability-after-freeze are core design invariants the spec calls out as distinguishing Starlark from Python (no arbitrary I/O, no unbounded recursion by default, frozen values once a module finishes loading).

25. **[BCR: bcr-policies.md — contribution and maintainer policy](https://github.com/bazelbuild/bazel-central-registry/blob/main/docs/bcr-policies.md)** — "Add-only: existing module versions must not be modified to ensure reproducible builds." Naming guidance actively discourages generic or falsely-official-sounding names: "Official-sounding prefixes such as `rules_` or `toolchains_` in particular could lead new users away from the more well-maintained options." Visibility discipline is called out explicitly: "PR authors sometimes forget `//visibility:public`... Encourage PR authors to keep the set of publicly visible targets small."

26. **[BCR: contributing.md, README.md — presubmit and validation](https://github.com/bazelbuild/bazel-central-registry/blob/main/docs/contributing.md)** — every module version needs a `presubmit.yml`; presubmit validates that the checked-in `MODULE.bazel` matches the extracted+patched source tree, that `compatibility_level` matches the previous version (skippable via a labeled PR comment), and requires maintainer review when a module has no maintainers or its `presubmit.yml` changes beyond trivial platform/Bazel-version edits. "Anonymous module test": presubmit builds `@module//:target` from a synthetic root module depending only on `bazel_dep(name=..., version=...)`, which is the actual BCR-compatibility gate a module must pass.

27. **[BCR: attestations.md](https://github.com/bazelbuild/bazel-central-registry/blob/main/docs/attestations.md)** — experimental, optional supply-chain provenance: an `attestations.json` alongside `source.json`/`MODULE.bazel` referencing `.intoto.jsonl` files verified by `slsa-verifier`; roadmap explicitly says future work includes "Eventually enforcing attestations for all new module versions."

## Recent shifts seen in this corpus

- **`compatibility_level` became a no-op on Bazel 8.6.0 / 9.1.0** — the FAQ now opens with "You should stop using `compatibility_level`," inverting years of prior guidance to bump it on every breaking change. Anything written before this point (including much second-hand blog advice) is now stale. [external/faq](https://bazel.build/external/faq)
- **LTS support matrix moved on**: as of this read, Bazel 9 is "Active" (9.2.0) and Bazel 8 is already "Maintenance" (8.8.0) — the fleet's 8.7.0 pin is behind both the newest 8.x patch and the newest LTS major. [release/index](https://bazel.build/release)
- **WORKSPACE is gone in Bazel 9**, confirming (not just hypothesizing) the frame's assumption; any lingering `WORKSPACE`/`WORKSPACE.bazel` file or `bind()` reference is now dead weight rather than "legacy but working." [external/migration](https://bazel.build/external/migration)
- **`--experimental_spawn_scheduler` is deprecated**, superseded by the current dynamic-execution flag set — anything referencing it in an `.bazelrc` predates the current mechanism. [remote/dynamic](https://bazel.build/remote/dynamic)
- **Skymeld (merged analysis/execution phases) has been the Bazel 7.0+ default since December 2023** (per web search, not this corpus) — older than this survey's 18–24 month recency window, so it's now baseline behavior, not a "recent" change; any tuning advice assuming separate analysis/execution phases (pre-7.0) is stale.
- **BCR attestations exist but are still experimental/optional** as of this read, with an explicit roadmap toward eventual enforcement — a topic to revisit rather than treat as settled.

## Contested

- **How strictly to enforce `--experimental_*`/`--incompatible_*` avoidance in production vs. deliberately testing against `rolling`.** The backward-compatibility page says "never" run production builds on these flags, but the release model's own rolling track exists specifically so early adopters exercise incoming incompatible behavior before it becomes default — the fleet's own CI matrix (8.7.0/9.x/rolling) is a live instance of this tension. Trend: the corpus treats "rolling" as a distinct, sanctioned pre-adoption lane, not an exception to the "never" rule — the rule is about *production* builds specifically.
- **Bzlmod migration timing rhetoric vs. reality.** `external/migration.md`'s own text ("removed in Bazel 9 (late 2025)") is already a year stale relative to this survey's September 2026 vantage point, even though the underlying claim (WORKSPACE gone in 9) held up. Bazel's docs carry visible publication-lag artifacts; treat embedded dates as approximate, not authoritative.
- **80-column style guidance in `.bzl` files.** The style guide states a soft 80-column guideline that "should not be enforced strictly," while separately pointing at buildifier's own automated warnings (docstrings, others) as things that ARE enforced — the line between "guideline, don't gate on it" and "warning, buildifier will flag it" isn't always obvious from the prose alone; buildifier's own warning taxonomy (a sibling scout's corpus) is the actual arbiter.
- **Whether `compatibility_level`'s legacy guidance is fully dead or just soft-deprecated.** The FAQ retains a full "legacy documentation" section on when/how to bump it, for pre-8.6.0/9.1.0 compatibility — trending toward removal but not yet removed from the page.
