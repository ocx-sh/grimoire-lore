## Summary

- Google's own justification for Bazel-shaped architecture is fine-grained targets: "fine-grained modules scale better than coarse-grained modules" because they narrow the affected-test set and enable distributed builds (SWE at Google, ch18).
- Pants coined "1:1:1" (one directory : one package : one BUILD target); Bazel's own docs never use that phrase but converge on the same rule: "every directory that contains buildable files should be a package" and a BUILD file referencing a subdirectory's files is a sign a BUILD file is missing there (Bazel best-practices).
- Fine-grained targets are only sustainable with BUILD-file generation — Google amortizes the maintenance cost by "investing in tooling to automatically manage BUILD files" (SWE at Google); in the open ecosystem that tooling is Gazelle, natively covering Go and protobuf with community plugins for Python, JS/TS (Aspect, BenchSci), and Rust (gazelle_rust).
- Default-public visibility is a named anti-pattern: "avoid setting default_visibility to public... the risk of inadvertently creating public targets increases as the codebase grows" (Bazel visibility docs); package_group is the reusable-allowlist mechanism for enforcing boundaries at scale.
- Bazel's artifact-based model (vs task-based) is the architectural reason parallelism and incrementality work at all: "because tasks can do anything, there's no way in general to check whether they've already been done," but Bazel "knows that each target will only produce a [library]... so it's safe to run these steps in parallel" (SWE at Google ch18).
- Platforms/toolchains (constraint_setting, constraint_value, platform, target_compatible_with) are the intended way to model multi-platform builds; select() on raw flags is treated as the legacy path being migrated away from, and migrating existing select()/config_setting to the platform API is called out as the hardest part of a platforms migration.
- layering_check is Bazel's mechanical enforcement of "no transitive header leakage" for C++: it requires `--features=layering_check`, works only with clang on Unix/macOS, and enforces "only include headers from direct dependencies" via `-fmodules-strict-decluse`/`-Wprivate-header` and generated `.cppmap` files.
- Symbolic macros (default in Bazel 8) are now the recommended encapsulation layer over legacy macros: they get typed attributes, restricted target visibility ("visible within the macro itself, but not necessarily to the macro's caller"), and an enforced naming schema that prevents name collisions.
- write_source_files + diff_test (Aspect bazel-lib) is the canonical "generated file checked into source control stays honest" pattern: a diff_test fails with instructions like "run: bazel run //:write_all" when the checked-in copy drifts from the generated one — rules_ocx's own `docs/BUILD.bazel` stardoc pipeline is a worked instance of exactly this pattern.
- proto_library is deliberately language-neutral; each language gets its own wrapper (`cc_proto_library`, `java_proto_library`, `py_proto_library`, …) consuming the same `proto_library`, which is the mechanism that lets one schema serve a polyglot repo without per-language duplication.
- Aspects are the chosen extension point for repo-wide cross-cutting concerns that must not touch BUILD files: rules_lint runs 17+ linters as aspects, needs "no changes to BUILD files," doesn't show up in `bazel query`, and — because lint actions are normal Bazel actions — gets RBE and remote-cache reuse for free.
- Test architecture is standardized around two enums: `size` (small/medium/large/enormous) implying a `timeout` (short=60s, moderate=300s, long=900s, eternal=3600s), independently overridable — this is the mechanical lever for CI wall-clock budgeting.
- Target determination in CI has two open-source tools with opposite failure modes: bazel-diff (hash-based, fast, but "an incorrect solution can result in a system you can't trust" since it can silently miss non-hermetic dependencies) versus target-determinator (cquery-based, slower, defaults to refusing an unclean checkout).
- Bazel-enabled merge queues (Trunk.io and similar) exploit the declared dependency graph to build "dynamic parallel queues," making the affected-target model a first-class CI architecture decision, not just a speed optimization.
- Dual-build-system migration (Cargo + Bazel) has a named pattern: keep Cargo files as "source of truth regarding external dependencies and project structure" so IDEs keep working off Cargo, and re-sync into Bazel with `CARGO_BAZEL_REPIN=1 bazel sync --only=crate_index`; the named pain point is that `crate_universe` ignores path dependencies, forcing manual BUILD wiring for internal workspace crates (Tweag).
- glob() has a package-boundary trap: a recursive `**/*.cc` glob silently stops at any subdirectory that is itself a package (has a BUILD/BUILD.bazel file), and results depend on which packages currently exist — an incrementality and correctness hazard the docs flag explicitly.
- Buck2's architectural pitch against Bazel is "remote execution first" (not bolted on later), a single unphased dependency graph instead of Bazel's target-graph/action-graph split, and full language-agnosticism of the core binary — a genuine architecture-level contrast, not just a speed claim.
- The market's 2026 framing for "when NOT to adopt Bazel" converges on team/language-mix size: small, single-language, JS-only, or already-simple codebases pay Bazel's operational surface area before it pays back; Pants is repeatedly positioned as the lower-ceremony entry point for Python-heavy monorepos.
- IDE/LSP strategy for Bazel is bifurcating in 2026: starpls (rust-analyzer-based Starlark LSP) and bazel-lsp are both "under active development" with "no recommendation... between" them, while JetBrains is moving IntelliJ's Java/Kotlin intelligence to LSP so it can serve VS Code/Cursor over Bazel projects (announced August 2026).
- Hermetic dev tooling (`bazel_env.bzl`) exists to solve "works on my machine" by making Bazel-managed toolchains available on PATH via `bazel run` + direnv, with a `print-path` subcommand for CI — the dev-tooling half of "Bazel-friendly architecture" that has nothing to do with the build graph itself.
- Execution groups (`exec_group`/`exec_groups`) let a single target declare multiple execution platforms for different actions (e.g., compile remotely on Linux, link locally on macOS) and replace unreliable mnemonic-based resource targeting — an architecture lever for hybrid local/remote multi-platform builds.
- Rust RFC 2136 and multiple 2023-2025 blog posts (Tweag, mmapped.blog) treat "does this Rust workspace actually need Bazel" as an open, contested question rather than a foregone conclusion, unlike the framing for large polyglot repos.

## Survey

### 1. Bazel docs: packages, BUILD files, targets
[bazel.build/concepts/build-files](https://bazel.build/concepts/build-files) — BUILD files are a restricted Starlark dialect (no function defs, no `for`/`if` statements, only list comprehensions and `if` expressions) specifically so builds stay hermetic and reproducible. Targets fall into `*_binary`, `*_test`, `*_library` categories. Docs explicitly ask authors to "comment liberally to document the role of each build target... and the role of the package itself."

### 2. Bazel docs: visibility
[bazel.build/concepts/visibility](https://bazel.build/concepts/visibility) — Three visibility mechanisms: target visibility, transitive (load) visibility, and load visibility. Syntax: `//visibility:public`, `//visibility:private`, `//foo/bar:__pkg__`, `//foo/bar:__subpackages__`, or a `package_group` reference. Explicit warning: "Avoid setting default_visibility to public. It may be convenient for prototyping or in small codebases, but the risk of inadvertently creating public targets increases as the codebase grows."

### 3. Bazel docs: platforms and constraints
[bazel.build/extending/platforms](https://bazel.build/extending/platforms) — A platform is "a collection of constraints that specifies a complete machine," built from `constraint_setting`/`constraint_value` pairs. Three platform roles: host, execution, target. Hard rule: "platforms may only have one constraint_value for a given constraint_setting." `target_compatible_with` is offered as the alternative to broad `select()` usage for marking a target incompatible with a platform, auto-skipping it under pattern-based builds.

### 4. Bazel docs: external dependencies / Bzlmod
[bazel.build/external/overview](https://bazel.build/external/overview) — Bzlmod (`MODULE.bazel`, `bazel_dep`) is the current dependency system, replacing WORKSPACE. Design principle: "only direct dependencies are visible, ensuring correctness and predictability" — Minimal Version Selection resolves the rest, avoiding manual diamond-dependency resolution.

### 5. Bazel Best Practices (official)
[bazel.build/configure/best-practices](https://bazel.build/configure/best-practices) — "Use fine-grained dependencies to allow parallelism and incrementality." "Everything should be built from source whenever possible." Versioning rule: "avoid including the version in the target name (for example, `//guava`, not `//guava-20.0`)." Package-per-directory rule: "every directory that contains buildable files should be a package. If a BUILD file refers to files in subdirectories... it's a sign that a BUILD file should be added to that subdirectory," else risk "circular dependencies... inadvertently created."

### 6. "Software Engineering at Google," ch. 18 (Build Systems and Build Philosophy)
[abseil.io/resources/swe-book/html/ch18.html](https://abseil.io/resources/swe-book/html/ch18.html) — Central argument for fine-grained modules: "a typical production binary at Google will likely depend on tens of thousands of targets," and "finer-grained targets mean that the build system can be much smarter about running only a limited subset of tests." The cost is BUILD-file maintenance, mitigated by "investing in tooling to automatically manage BUILD files." Second argument: artifact-based (Bazel) vs task-based (Make/Ant) build systems — task systems can't safely parallelize because "there's no way in general for the system to know" whether tasks share resources; artifact systems know each target's declared output type and "run these steps in parallel," and can report "up to date" in under a second on a no-op rebuild.

### 7. bazel-diff (Tinder)
[github.com/Tinder/bazel-diff](https://github.com/Tinder/bazel-diff) — SHA256-hashes the entire Bazel graph (`generate-hashes`) at two revisions, diffs them (`get-impacted-targets`), and can `explain` why a target was flagged; also has `serve`/`warmup`/`fingerprint` subcommands for cached, service-mode use. Explicit self-caveat: "an incorrect solution can result in a system you can't trust, because tests could be broken at a commit where you didn't select to run them" — i.e., it can silently miss targets affected through non-hermetic or undeclared dependencies.

### 8. target-determinator (bazel-contrib)
[github.com/bazel-contrib/target-determinator](https://github.com/bazel-contrib/target-determinator) — cquery-based alternative to bazel-diff; caches cquery results per commit to skip recomputation on a hit. Defaults to refusing to run on an unclean checkout (override: `--enforce-clean=allow-ignored`). Caching caveat: a cached "before" result computed "under the environment variables that were in effect at that time" can produce spurious diffs if env vars change between runs. Supports "Bazel 4.0.0 up to and including the latest LTS release," tested regularly only against the latest LTS.

### 9. rules_lint (Aspect / bazel-contrib)
[github.com/aspect-build/rules_lint](https://github.com/aspect-build/rules_lint) — Aspect-based linting: "no changes needed to BUILD files... lint doesn't appear in `bazel query` output." Covers Python, Go, Rust, TypeScript, Java, C/C++, Shell, Kotlin, Scala with common tools (Prettier, gofmt, rustfmt, clang-format, ESLint, ShellCheck, Clippy, Pylint, Checkstyle). Because lint actions are ordinary Bazel actions, "they support Remote Execution and the outputs are stored in the Remote Cache." Aspect's own framing: [Announcing Linting for Bazel](https://aspect.build/blog/lint).

### 10. write_source_files / diff_test (Aspect bazel-lib)
Cited via [Aspect docs](https://docs.aspect.build/rulesets/aspect_bazel_lib/docs/write_source_files/) and corroborating mirrors — a dict of source-tree paths to generated-content labels; auto-generates a `diff_test` per entry that fails if the checked-in file is stale or missing, naming a fix command such as "run: bazel run //:write_all" (or a target-specific `suggested_update_target`). `rules_ocx`'s own `docs/BUILD.bazel` (read locally, not published) reimplements the identical shape by hand with `stardoc` + `diff_test` + a generated `update.sh`, proving the pattern generalizes beyond the one library that names it.

### 11. Symbolic macros / macros / rules (Bazel docs)
[bazel.build/extending/macros](https://bazel.build/extending/macros) — Symbolic macros are "available by default in Bazel 8" and are now the default encapsulation choice: typed attributes, target visibility scoped so targets are "visible within the macro itself, but not necessarily to the macro's caller," and an enforced naming schema (targets must derive from the macro's own name or use `_`/`.`/`-` prefixes) that prevents collisions. Legacy macros remain only for cases symbolic macros can't yet handle (e.g. calling `glob()`, non-`attr`-typed parameters).

### 12. layering_check and C/C++ strict deps
[bazel.build/reference/be/c-cpp](https://bazel.build/versions/7.0.0/reference/be/c-cpp) plus corroborating search results — `layering_check` must be requested via `--features=layering_check` (or the package `features` attribute) and is implemented "only with clang on Unix and macOS," using `-fmodules-strict-decluse`/`-Wprivate-header` against generated `.cppmap` module files. It only checks direct `#include`s: transitive headers may still be *read* by the compiler through the closure, but a `.cc` file must not `#include` a header unless its owning library is a direct `dep`. `implementation_deps` on `cc_library` separates private compile-only deps from the public link-time surface. rules_ocx's own `.bazelrc.user` (not published) is noted in the frame as disabling `layering_check` for a host-specific toolchain — a concrete counter-example of the discipline this section documents.

### 13. proto_library / cross-language protobuf model
[bazel.build/reference/be/protocol-buffer](https://bazel.build/reference/be/protocol-buffer) — `proto_library` produces a language-neutral `FileDescriptorSet`; `cc_proto_library`, `java_proto_library`, `java_lite_proto_library`, `py_proto_library` each wrap one `proto_library` and must point their `deps` at `proto_library` targets, not at each other. Naming convention: `foo.proto` → target `foo_proto`; the wrapper is named `foo_[language]_proto`. This is the concrete mechanism behind "protobuf as the cross-language API layer."

### 14. Test size/timeout/tags model
[bazel.build/reference/test-encyclopedia](https://bazel.build/reference/test-encyclopedia) — `size` (small/medium/large/enormous) implies a default `timeout` (short/moderate/long/eternal); explicit seconds: short=60, moderate=300, long=900, eternal=3600. "All combinations of size and timeout labels are legal" — a test can declare `size = "enormous"` with `timeout = "short"`. Recommended minimums before stepping down a timeout: moderate ≥30s, long ≥300s, eternal ≥900s actually elapsed.

### 15. Execution groups
[bazel.build/extending/exec-groups](https://bazel.build/extending/exec-groups) — `exec_groups` on a `rule()` declares named execution-platform requirements (`exec_compatible_with`, `toolchains`); actions opt into a group with `ctx.actions.run(exec_group = "...")`. Named use case: "compiling iOS apps on remote Linux workers while linking/code signing locally on macOS." Built-in groups `test` and `cpp_link` exist on native rules. Solves the problem that mnemonic-based action targeting for resource allocation is unreliable.

### 16. glob() package-boundary trap
Corroborated across [bazel.build/reference/be/functions](https://bazel.build/reference/be/functions) and multiple bazelbuild/bazel issues (#4194, #13950) — "glob does not match files in subpackages... the glob expression `**/*.cc` in package x does not include `x/y/z.cc` if `x/y` exists as a package." The match set silently depends on which BUILD/BUILD.bazel files currently exist, which is an incrementality and correctness hazard, not merely a style nit — adding a BUILD file to a subdirectory can silently shrink an existing glob's matches elsewhere.

### 17. bazel_env.bzl (BuildBuddy)
[github.com/buildbuddy-io/bazel_env.bzl](https://github.com/buildbuddy-io/bazel_env.bzl) — "The `bazel_env` rule creates a 'virtual environment' for Bazel-managed tools and toolchains by making them available under stable, platform-independent paths as well as on PATH." Uses `bazel run` to provision, direnv to inject into the shell, and a `print-path` subcommand for CI use — the reference implementation of "hermetic dev tools" invoked from outside `bazel build`/`bazel test`.

### 18. rules_multitool (bazel-contrib, formerly theoremlp)
[Bazel Central Registry: rules_multitool](https://registry.bazel.build/modules/rules_multitool) and [GitHub](https://github.com/theoremlp/rules_multitool) — declarative, lockfile-driven (`multitool.lock.json`) management of OS/CPU-specific external tool binaries, resolved per-platform through ordinary Bazel toolchain resolution; accessed as `@multitool//tools/tool-name`. Complements `bazel_env.bzl` as a way to pin exact tool binaries rather than relying on `$PATH`.

### 19. Buck2's architecture pitch (Meta)
[buck2.build/docs/about/why](https://buck2.build/docs/about/why/) — Contrasts itself with Bazel on four architecture axes: "remote execution first — local execution is considered a special case"; a single unphased dependency graph ("not phased — there are no target graph/action graph phases") versus Bazel's split; "dynamic dependencies" letting a rule inspect a built file's contents before declaring downstream deps (useful for import-following languages); and full language-agnosticism of the core binary ("all the rules external to the binary"). Also claims "transitive-sets," wired directly into the dependency graph, shrink graph size versus Bazel's `depset`.

### 20. Cross-tool architecture comparison landscape
[Sourcegraph: Best Monorepo Build Tools (2026)](https://sourcegraph.com/blog/monorepo-build-tools) (fetch blocked by 403; cited via search snippet) and multiple 2025-2026 blog posts (Incredibuild's Bazel-in-the-real-world post, daily.dev's Turborepo/Nx/Bazel comparison, Earthly's "When to use Bazel?") converge: Bazel has "the broadest language support by a significant margin," Buck2 targets "very large polyglot codebases" needing maximum RE-first performance, and Pants is "the right starting point for Python-heavy monorepos that find Bazel's BUILD-file overhead too steep." The "when NOT to adopt" framing repeats across sources: small, single-language, or JS-only codebases pay Bazel's "large operational surface area" before it pays back; the more honest fix for some teams is targeted (a slow linker step, expensive tests, CI queue time) rather than a build-system swap.

### 21. Dual build system during Rust migration (Tweag)
[tweag.io: Building a Rust workspace with Bazel](https://www.tweag.io/blog/2023-07-27-building-rust-workspace-with-bazel/) — Recommends keeping Cargo files "as a source of truth regarding external dependencies and project structure" so IDEs keep configuring off Cargo; re-sync into Bazel via `CARGO_BAZEL_REPIN=1 bazel sync --only=crate_index` after `cargo add`. Explicit pain point: "`crate_universe` ignores path dependencies," so internal workspace-crate dependencies must be hand-declared in BUILD files — a manual synchronization burden the post says the community is working to automate. Rust RFC 2136 ([rust-lang.github.io/rfcs/2136-build-systems.html](https://rust-lang.github.io/rfcs/2136-build-systems.html)) documents that "does a Rust workspace need Bazel at all" remains a live, contested design question upstream, not settled practice.

### 22. Gazelle and language-plugin maturity
[github.com/bazel-contrib/bazel-gazelle](https://github.com/bazel-contrib/bazel-gazelle) — "Gazelle is a Bazel build file generator... It natively supports Go and protobuf, and it may be extended to support new languages." Community plugins exist for Python (via rules_python's extension generating `py_library`/`py_binary`/`py_test`), JS/TS (Aspect's plugin; BenchSci's `rules_nodejs_gazelle` covering `ts_project`, `js_library`, `jest_test`, web bundlers like Webpack/Next.js), and Rust (`gazelle_rust`). Maintainer base is split across bazel-contrib, Aspect, EngFlow, and VirtusLab — plugin maturity is uneven by language, and at least the Kotlin plugin is explicitly still "under development."

### 23. IDE/LSP strategy for Bazel monorepos
Search-corroborated: [starpls](https://github.com/withered-magic/starpls) is "an implementation based on rust-analyzer" providing a Starlark LSP; the [vscode-bazel](https://github.com/bazel-contrib/vscode-bazel) extension supports launching either starpls or bazel-lsp, with the project stating "no recommendation is currently made between starpls and bazel-lsp… both are under active development." Separately, [JetBrains' August 2026 announcement](https://blog.jetbrains.com/idea/2026/08/intellij-idea-goes-lsp/) that IntelliJ's Java/Kotlin intelligence is moving to LSP is framed explicitly as enabling that intelligence "in VS Code, Cursor, and Agentic Flows" for Bazel projects — a 2026-dated shift away from a single IDE plugin toward LSP-shared tooling.

### 24. CODEOWNERS, trunk-based development, Bazel-aware merge queues
Search-corroborated across [Trunk.io's Bazel merge-queue docs](https://docs.trunk.io/merge-queue/concepts-and-optimizations/parallel-queues/bazel) and general CI practice write-ups — "merge queues can leverage your Bazel build graph to create parallel merge lanes" because "Bazel already knows the structure of your code and can automatically generate a dependency graph." CODEOWNERS-per-package is presented as the standard way to route review load ("designating /frontend/ for the frontend team"), and "tools with strong affected-change detection make trunk-based development much more practical" — tying the CI-architecture topics directly back to target determination (survey items 7-8).

## Recent shifts seen in this corpus

- **Symbolic macros became the default in Bazel 8** (rules_ocx pins 8.7.0, so this applies now): legacy macros are now the fallback for cases needing `glob()` or untyped attributes, not the default choice. Anything written before Bazel 8 that uses a legacy macro purely for encapsulation is dated advice. Source: [Macros](https://bazel.build/extending/macros).
- **JetBrains moving IntelliJ's Java/Kotlin intelligence to LSP** (announced August 2026) — a genuinely new 2026-dated shift toward LSP-shared IDE tooling for Bazel projects across VS Code/Cursor, displacing the older single-plugin-per-IDE model as the only option. Source: [JetBrains blog, August 2026](https://blog.jetbrains.com/idea/2026/08/intellij-idea-goes-lsp/).
- **rules_lint reaching "generally available"** status (Aspect, 2024-2025 era per the blog's own framing) established aspects-as-linting as mainstream practice, not an experimental pattern — older advice that treats linting as a wrapper-macro-per-target concern is superseded.
- **Gazelle's plugin ecosystem broadening beyond Go/proto** (Aspect's JS/TS plugin, BenchSci's `rules_nodejs_gazelle`, `gazelle_rust`) means "Gazelle only really works for Go" is dated; plugin maturity is now uneven-but-present per language rather than absent for non-Go languages.
- **Buck2 becoming a real, externally-adopted open-source option** ("now open source with real external adoption" per search-corroborated framing) changes the comparison set from "Bazel vs. an internal Meta tool" to a genuine architecture-level choice teams evaluate.

## Contested

- **Bazel-diff vs. target-determinator for CI target selection**: no consensus winner. bazel-diff is faster and hash-based but self-documents a trust gap around non-hermetic dependencies; target-determinator is more rigorous (cquery-based) but self-documents an environment-variable caching caveat and requires clean checkouts. The trend favors whichever tool a team's CI infra vendor (e.g., EngFlow, BuildBuddy) has already integrated, rather than either tool "winning" on merits alone.
- **starpls vs. bazel-lsp for Starlark language support**: the projects themselves state no recommendation exists between them; both are actively developed. No visible trend toward consolidation as of this survey.
- **Whether Rust workspaces need Bazel at all**: Rust RFC 2136 keeps this an open question upstream; Tweag and mmapped.blog both write from a "here's how, if you must" posture rather than a settled "yes, always" recommendation — contrasted with the far more confident "yes" for large polyglot repos generally.
- **Pants vs. Bazel for Python-heavy monorepos**: the 2026 comparison-blog consensus (Sourcegraph, others) is trending toward "Pants for lower ceremony, Bazel for polyglot breadth and RE/RBE," but this is comparison-blog consensus, not primary-source Bazel or Pants documentation taking a position — treat as directionally likely, not settled.
- **1:1:1 naming**: Pants' own "1:1:1" phrase versus Bazel's docs never using that term but converging on the identical rule — a terminology gap, not a substantive disagreement, but worth flagging so a rule doesn't cite "1:1:1" as if it were Bazel's own vocabulary.
