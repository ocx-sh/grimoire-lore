## Summary

- Bzlmod migration pain is dominated by three mechanical facts: `load()` is banned inside `MODULE.bazel`, module extensions cannot call `native.register_toolchains()`/`native.bind()`, and canonical repo names change format (`@@`, `_main`) — each breaks a distinct class of WORKSPACE-era code and each has a documented workaround.
- `MODULE.bazel.lock`'s `moduleFileHash` field changes on almost any dependency edit, which produces near-constant git merge conflicts in a monorepo with many concurrent committers; the two competing mitigations (a git merge driver vs. `.gitignore` during migration) are both in active use and neither is clearly dominant as of 2026.
- Build without the Bytes (BwoB, default since Bazel 7, October 2023) turns the remote cache into load-bearing infrastructure: once an intermediate output exists only as a CAS digest, its eviction produces "Failed to fetch blobs because they do not exist remotely" — mitigated by `--experimental_remote_cache_lease_extension` and `--experimental_remote_cache_eviction_retries`, not eliminated.
- Untrusted PR builds writing to a shared remote cache is a live cache-poisoning vector (a fork build can plant a backdoored compiler binary that a trusted build later executes); the documented fix is a read-only token plus `--noremote_upload_local_results` for PR/fork CI lanes — this is exactly the shape `rules_ocx`'s own `.bazelrc.user` split already implements.
- Symbolic macros (Bazel 8+) are the biggest source of new porting friction: strict target-naming (must start with the macro's `name`), frozen kwargs (mutating them throws "trying to mutate a frozen dict value"), all-attributes-configurable-by-default (so `select()`-wrapped values can't be read or `.append()`-ed inside the macro body), and inherited attributes defaulting to `None` instead of the wrapped rule's real default.
- The promised performance win of symbolic macros — lazy evaluation so unrequested targets never get macro-expanded — is not yet shipped as of the corpus's most recent primary source (Tweag, 2025-11-20); today all macros still evaluate at BUILD-file load time regardless of macro kind.
- Bazel 9 removes WORKSPACE entirely and disables autoloading of native rules by default, so `.bzl` files that relied on implicit `native.*` symbols must add explicit `load()` statements — a mechanical, greppable migration.
- `genrule` hermeticity breaks on PATH pass-through: any change to the user's `PATH` environment variable forces action re-execution, and genrule's Bash dependency is a standing recommendation to prefer a purpose-built rule (bazel-skylib or similar) instead.
- Checked-in generated files silently go stale without a `diff_test`/`write_source_files` pattern; the fix relies on `bazel run`'s exposure of `BUILD_WORKSPACE_DIRECTORY`, which `bazel build`/`bazel test` deliberately do not expose.
- `layering_check` silently stops enforcing anything once compilation runs unsandboxed, because Clang can then load transitive module maps Bazel never declared as inputs — the documented adoption path is per-package opt-in, not repo-wide flip.
- Symlinked sandbox construction scales linearly with input count and is reported as the dominant cost for actions with thousands of inputs (up to ~300K files cited); Windows additionally hits path-length limits that force `SymlinkAction` to fall back to copying files.
- `crate_universe`'s `cargo-bazel-lock.json` and Cargo's own `Cargo.lock` are two different lockfiles that can drift; repinning today means a full `cargo update`-style regeneration rather than a scoped update, and `rust-analyzer` gets confused by env vars/targets that exist only inside Bazel's `cargo_build_script` model.
- `rules_python`'s `uv` integration runs `uv pip compile` as a faster `pip-compile` replacement feeding `pip.parse()` — it does not consume a real `uv.lock`; maintainers point users wanting a fully independent hermetic-`uv` interpreter story at `aspect_rules_py` instead.
- `rules_js` forces pnpm specifically (not npm/yarn) because pnpm's virtual store and linker semantics are the only ones Bazel actions can reproduce; migration off `rules_nodejs` routinely surfaces previously-hidden phantom dependencies that npm/yarn hoisting was silently tolerating.
- Configuration transitions can multiply action counts by building the same target once per distinct configuration reached, and Bazel treats those as separate actions in `aquery` even when their output artifacts share the same `execPath` — a documented, demonstrable graph-explosion pattern, not a rare edge case.
- The disk cache and repository cache both grow unbounded with no built-in garbage collection in older Bazel — the oldest, highest-reaction closed issue in this corpus (103 reactions) is exactly this ask, and repository-cache GC was still an open feature request as of the most recent search.
- "Bazel is slow" resolves, per official guidance, into a small number of causes: a rule implementation flattening depsets, recursive globs or complex macros inflating loading time, and JVM heap pressure evicting the analysis cache — each has a distinct diagnostic (`--experimental_generate_json_trace_profile`, `--host_jvm_args=-Xmx`).
- The comparison-post consensus as of 2026 is a bifurcation, not a single winner: Bazel/Buck2/Pants are "polyglot heavyweights" worth their setup cost only at large-org scale, while Nx/Turborepo are lightweight task-runners that cap out below Bazel's fine-grained-dependency ceiling but suit most JS/TS teams fine.
- Departures are real but not universal: RabbitMQ removed its Bazel files (March 2025) in favor of Make/erlang.mk; Kubernetes and Nomulus moved off Bazel historically; AOSP's Bazel migration was explicitly cancelled for "business priorities," not a technical failure, per Google's own statement — while Snowflake (two years in) and Uber (Go monorepo, ~900 monthly active engineers) both report successful, sustained adoption at scale.
- The IDE story is mid-transition: Google is deprecating its own IntelliJ Bazel plugin and handing it to JetBrains, whose independently-developed plugin reached General Availability in the 2025.2 release (July 2025) with new Python/Scala support and Bazel 8 compatibility.

## Survey

### 1. Bzlmod migration mechanics — EngFlow's multi-part series and the official migration guide

EngFlow's ["Migrating to Bazel Modules (a.k.a. Bzlmod) — The Easy Parts"](https://blog.engflow.com/2024/06/27/migrating-to-bazel-modules-aka-bzlmod---the-easy-parts/) (2024-06-27) is the single richest pain-point source in this corpus. It documents, with exact error text: `load()` statements are outright forbidden inside `MODULE.bazel` ("load statements may not be used in MODULE.bazel files"), forcing a separate module-extension `.bzl` file; `http_archive()` and a `load()` of a macro from that same archive cannot happen in the same extension because Bzlmod forbids intra-extension repo dependencies; module extensions cannot call `native.register_toolchains()` or `native.bind()`, breaking any WORKSPACE-era toolchain-registration macro; canonical repo names change format entirely (stable `_main` replaces the workspace name; the mangled form is `module_repo_canonical_name~extension_name~repo_name`, explicitly documented as "not an API you should depend on"); mixing a WORKSPACE-sourced and a Bzlmod-sourced version of the same repo in one build silently conflicts unless resolved with `multiple_version_override()`; and rules not yet Bzlmod-ready (the post names `rules_scala` and the deprecated `rules_nodejs`) require hand-written module extensions. It also documents the `rules_python` breaking change directly: pre-0.37.0, `python_register_toolchains()` explicitly disabled its own WORKSPACE registration path once `--enable_bzlmod` was on, forcing migration to the `python.override()` tag with `minor_mapping` (0.36.0+). The companion posts in the same series — [Module Extensions](https://blog.engflow.com/2025/01/16/migrating-to-bazel-modules-aka-bzlmod---module-extensions/), [Toolchainization](https://blog.engflow.com/2025/05/14/migrating-to-bazel-modules-aka-bzlmod---toolchainization/), [Repo Names and Runfiles](https://blog.engflow.com/2024/08/09/migrating-to-bazel-modules-aka-bzlmod---repo-names-and-runfiles/), and [Fixing and Patching Breakages](https://blog.engflow.com/2025/03/25/migrating-to-bazel-modules-aka-bzlmod---fixing-and-patching-breakages/) — extend the same theme into 2025, indicating the migration is still an active, multi-quarter body of practice rather than a solved problem. The official [Bzlmod Migration Guide](https://bazel.build/external/migration) confirms the recommended incremental strategy (enable `--enable_bzlmod=true` with WORKSPACE still present, migrate one dependency at a time) over a "big bang" rewrite.

### 2. Lockfile churn: MODULE.bazel.lock merge conflicts

Three GitHub issues converge on the same complaint from different angles: [#20272](https://github.com/bazelbuild/bazel/issues/20272) ("MODULE.bazel.lock file 'reads through' already-locked package manager"), [#20369](https://github.com/bazelbuild/bazel/issues/20369) ("moduleFileHash in MODULE.bazel.lock causes frequent Git merge conflicts" — the value changes on essentially any dependency edit anywhere in the module graph, which the issue calls unscalable for a monorepo with many concurrent committers), and [rules_python#2434](https://github.com/bazelbuild/rules_python/issues/2434) ("Avoid merge conflicts in MODULE.bazel.lock"). A fourth, [#19154](https://github.com/bazelbuild/bazel/issues/19154), documents a cross-platform variant: the generated lockfile changes depending on which platform ran `bazel` when `requirements_darwin`/`requirements_windows` parameters are in play. The practical fallout named across these threads: teams facing the conflict "will likely just delete-and-recreate the lockfile," which silently discards the pinning of every other module in the file — a correctness regression disguised as a convenience fix. Bazel's own docs recommend an automated git merge driver; the alternative in active use is `.gitignore`-ing the lockfile until the team is comfortable with Bzlmod, which the EngFlow series independently recommends as a migration-phase workaround.

### 3. Build without the Bytes and remote-cache eviction

[Blog: BwoB in Bazel 7](https://blog.bazel.build/2023/10/06/bwob-in-bazel-7.html) (official, 2023-10-06) establishes BwoB as default in Bazel 7. Once default, the remote cache becomes load-bearing: intermediate outputs may exist only as CAS digests, and a finite-storage cache can evict them mid-build. The resulting failure mode, "Failed to fetch blobs because they do not exist remotely," recurs across independent trackers: [cockroachdb/cockroach#130203](https://github.com/cockroachdb/cockroach/issues/130203) is a real-world hit of it; [bazelbuild/bazel#21777](https://github.com/bazelbuild/bazel/issues/21777) ("Cache eviction hangs action evaluation with remote execution"), [#22220](https://github.com/bazelbuild/bazel/issues/22220) ("Constant 'remote cache eviction error' message"), [#22822](https://github.com/bazelbuild/bazel/issues/22822) ("Intermittent issue while trying to fetch remote blob"), and [#18696](https://github.com/bazelbuild/bazel/issues/18696) ("`--experimental_remote_cache_eviction_retries` doesn't evict all metadata causing build failure" — i.e., even the fix flag has a documented gap) collectively show this is a recurring, not one-off, class of failure. The mitigations Bazel shipped are two flags: `--experimental_remote_cache_lease_extension` (periodically refresh leases on blobs Bazel still references, reducing LRU-eviction odds) and `--experimental_remote_cache_eviction_retries` (detect the specific error, reset local state, and retry). Neither is a structural fix — both are still `--experimental_*` as of this survey.

### 4. Cache poisoning from untrusted builds

[bazelbuild/bazel#4276](https://github.com/bazelbuild/bazel/issues/4276) ("Saving the remote cache from cache poisoning?") and a [bazel-discuss thread on public HTTP cache security](https://groups.google.com/g/bazel-discuss/c/0005BAB_mlI) describe the same threat model found via web search: an untrusted build (a fork PR) that can write to a shared cache can plant a malicious artifact — the canonical example given is a backdoored compiler binary — that a later trusted build downloads and executes instead of building from source. The documented mitigation is a two-tier token model: untrusted PR/fork lanes get a read-only cache token and `build --noremote_upload_local_results` so they can read shared cache entries but never populate them; only trusted (post-merge, main-branch) builds get write credentials. This is precisely the split the frame documents for `rules_ocx` itself (`--remote_upload_local_results=false` on PRs, write-authorized on `main` pushes) — meaning the fleet's one Bazel repo is already implementing the corpus's recommended fix, which is worth stating as validation rather than a gap.

### 5. Symbolic macro migration gotchas (Bazel 8/9)

[Tweag: "Migrating to Bazel symbolic macros"](https://www.tweag.io/blog/2025-11-20-migrating-bazel-symbolic-macros/) (2025-11-20, the single most recent primary-adjacent source in this survey) is a hands-on gotcha list, not a rationale essay. Concrete traps documented: target names created inside a symbolic macro must equal the macro's `name` or start with it followed by `_`, `.`, or `-` (a macro named `tool` creating a target literally called `genruletool` fails; `tool_genrule` is required); symbolic macros cannot directly read source files unless passed in as arguments or exported public by the parent package (no more implicit inlining); no positional arguments are accepted — everything must be a declared, keyword `attrs` entry; attributes inherited from a wrapped rule silently default to `None` rather than that rule's real default, breaking code that assumed e.g. an empty list; all macro arguments arrive frozen, so `kwargs["env"]["some"] = "more"` throws "trying to mutate a frozen dict value" where a legacy macro would have silently allowed it; and — the sharpest one — attributes are configurable (`select()`-wrapped) by default, so reading or `.append()`-ing into `kwargs["deps"]` inside the macro body fails with "'select' value has no field or method 'append'" because resolution happens at analysis time, after macro evaluation. The documented workaround is forcing early resolution via an `alias` target with a non-configurable `attr.label()`. Official docs at [bazel.build/extending/macros](https://bazel.build/extending/macros) confirm the underlying performance rationale (avoiding "performance blowup" from unconditional macro evaluation) but also confirm lazy evaluation is still "currently being considered for a future Bazel release" — the win is not yet real.

### 6. C++ toolchain, layering_check, and sandboxing costs

[bazelbuild/bazel#21592](https://github.com/bazelbuild/bazel/issues/21592) ("`layering_check` doesn't work without sandboxing") documents the precise mechanism: Bazel stages only the direct dependencies' Clang module maps as declared inputs, but an unsandboxed compile can still load transitive module maps off disk, producing a false negative where the check silently stops catching missing-dependency-declaration bugs. The documented rollout pattern (from the same search cluster) is per-package opt-out-then-remove, not a repo-wide flip. [#12767](https://github.com/bazelbuild/bazel/issues/12767) ("Provide a way to create a toolchain from an autodetected one") captures the well-known second-order pain: autodetected toolchains are great for a cold start, then become tedious the moment anyone needs to tweak one setting. On sandboxing cost, [#16711](https://github.com/bazelbuild/bazel/issues/16711) ("Symlinked sandbox is slow") states the mechanism plainly: sandbox construction via symlinks scales linearly with input count, is reported costly for actions with up to ~300K files, and macOS/iOS compilation under Bazel's sandbox is cited as up to 2.5x slower than Xcode for the same work. [#11482](https://github.com/bazelbuild/bazel/issues/11482) ("Remove maximum path length limitation on Windows") documents the Windows-specific variant: `SymlinkAction` cannot create an overlong-name symlink and falls back to a full copy instead, and the standing advice is to raise the OS path-length limit rather than expect Bazel to route around it.

### 7. Genrule hermeticity and the checked-in-generated-file pattern

Multiple sources converge on genrule as a hermeticity trap: PATH is passed through to genrule's Bash environment, so any PATH change forces action re-execution regardless of whether the command's actual behavior changed, and the general guidance (surfaced via [bazel.build/rules/windows](https://bazel.build/rules/windows) and the general-rules search cluster) is to prefer a purpose-built rule (bazel-skylib or similar) over a raw genrule shell script, or to override individual tool paths with `POSIX_<COMMAND_NAME>` environment variables. Separately, [Aspect: "Bazel can write to the source folder!"](https://aspect.build/blog/bazel-can-write-to-the-source-folder) explains the checked-in-generated-file antipattern precisely: without a verification step, a developer can be "working against an out-of-date file in the source folder" and not know it until CI fails. The fix pattern chains four primitives — `write_file` (bazel-skylib) generates an update script, `sh_binary` wraps it as a `bazel run`-able target, and `diff_test` (bazel-skylib) or Aspect's own `write_source_files` rule fails the build with a message like "Please run: bazel run //:update" when the source and generated versions diverge. The mechanism this relies on is that `bazel run` uniquely exposes `BUILD_WORKSPACE_DIRECTORY` as an environment variable, letting the action mutate the source tree — something `bazel build`/`bazel test` deliberately forbid.

### 8. Configuration transitions and action-count explosion

[GitHub: lucidsoftware/bazel-build-graph-explosion](https://github.com/lucidsoftware/bazel-build-graph-explosion) is a small demonstration repo built specifically to show that, without an outgoing transition resetting configuration back to default at a dependency boundary, a target reached through multiple configuration paths gets built once per distinct configuration rather than once total — the shared-output-across-configurations case Bazel does not infer automatically. [bazelbuild/bazel#14236](https://github.com/bazelbuild/bazel/issues/14236) ("Avoid action conflicts due to different configuration hashes") is the corresponding upstream tracker: Bazel errors out when the same action (identical action hash) gets created under two different configuration hashes, which is the direct symptom of transition-induced duplication. `aquery`'s own documented behavior compounds the diagnostic difficulty: because it operates on the pre-execution action graph, two shared actions whose output artifacts have the exact same `execPath` still render as separate entries — meaning `aquery` output alone cannot cheaply answer "did my transition just double my action count," a query someone has to compose deliberately (diffing distinct configuration hashes per target).

### 9. crate_universe / rules_rust lockfile and rust-analyzer friction

The `crate_universe` docs ([bzlmod variant](https://bazelbuild.github.io/rules_rust/crate_universe_bzlmod.html)) describe `cargo-bazel-lock.json` as the generated, Bazel-native lockfile distinct from Cargo's own `Cargo.lock`, with `all_crate_deps()` and friends reading from the former. [rules_rust#1522](https://github.com/bazelbuild/rules_rust/issues/1522) ("Don't update Cargo.lock when re-pinning") is the direct friction report: re-pinning today (e.g., after changing the pinned Rust version) has no scoped-update path — it forces a broad `cargo update`-shaped regeneration touching many unrelated dependency versions at once. [rules_rust discussion #2879](https://github.com/bazelbuild/rules_rust/discussions/2879) ("Problems with cargo-bazel and cargo when using rules_rust crates_universe (bzlmod)") is the community's ongoing catalogue of the two-lockfile drift problem. Separately, the corpus (via the Tweag "Building a Rust workspace with Bazel" cluster) documents that `rust-analyzer` loses fidelity once `cargo_build_script`-defined environment variables or Bazel-only targets are load-bearing for a crate to compile — `rust-analyzer` reasons from `Cargo.toml`/`cargo check`, not from the Bazel graph, so anything visible only to Bazel is invisible to it.

### 10. rules_nodejs → rules_js and the forced pnpm requirement

The [Aspect migration guide](https://docs.aspect.build/guides/rules_js_migration/) and [rules_js docs/pnpm.md](https://github.com/aspect-build/rules_js/blob/main/docs/pnpm.md) both document the same design constraint: `rules_js` requires pnpm specifically — not npm, not yarn — because pnpm's "virtual store" of packages maps directly onto Bazel's external-repository model, and pnpm's linker (the step that materializes `node_modules`) has semantics reproducible as discrete Bazel actions, which npm's and yarn's linkers do not. The direct migration cost named: engineers must be retrained to run `pnpm` instead of npm/yarn for any dependency change, and `rules_js` does not support pnpm's "phantom hoisting" — meaning packages that depended on an undeclared transitive dependency (silently tolerated under npm/yarn hoisting) now fail to resolve and must be declared explicitly. This is the exact "previously-hidden bug becomes a build break on migration" pattern named generically in the frame's hypothesis list.

### 11. rules_python: uv is a resolver speedup, not a hermetic-lockfile story (yet)

Search-derived evidence (rules_python discussion and community commentary) converges on one specific, checkable claim: `rules_python`'s `uv` integration runs `uv pip compile` as a build action — a faster drop-in for `pip-compile` — whose output (a generated `requirements.txt`) still feeds `pip.parse()` → `whl_library` repository rules at loading time. It does not consume a `uv.lock` file at all. Teams wanting a fully independent, hermetic-interpreter `uv` story are pointed at `aspect_rules_py`'s `uv.declare_hub()` extension instead, which generates and consumes an actual `uv.lock`. This directly tests (and partially contradicts) the frame's implicit assumption that "rules_python has uv support" settles the Python/Bazel hermetic-interpreter question — as of this survey it only partially does, and the gap is maintainer-acknowledged, not merely undocumented.

### 12. Disk cache, repository cache, and action-graph introspection: old asks, still open

A cluster of high-reaction but old GitHub issues shows a consistent multi-year gap between what operators want and what ships: [#5139](https://github.com/bazelbuild/bazel/issues/5139) ("Implement automatic garbage collection for the disk cache," 103 reactions, closed) is the highest-reaction issue found in the entire `team-Remote-Exec` label; [#22516](https://github.com/bazelbuild/bazel/issues/22516) ("Implement garbage collection for the repository cache") shows the same ask recurring for a *different* cache years later, and is still open; [#4891](https://github.com/bazelbuild/bazel/issues/4891) ("Bazel's action graph is very hard to introspect and debug") and [#3582](https://github.com/bazelbuild/bazel/issues/3582) ("Option to calculate the number of actions in execution phase") show the same "we can't see what the build is actually doing" complaint from two angles. [#7093](https://github.com/bazelbuild/bazel/issues/7093) ("`.bazelignore` should support wildcard prefix," 68 reactions) and [#11935](https://github.com/bazelbuild/bazel/issues/11935) ("`glob` in WORKSPACE files") round out the ExternalDeps cluster — small ergonomic gaps that accumulate into real day-to-day friction at scale.

### 13. Company retrospectives: Snowflake, Uber, and the "too pure" critique

[Snowflake, two years in](https://blogsystem5.substack.com/p/bazel-at-snowflake-two-years-in) reports OOM as the dominant early pain — Bazel's defaults assumed workstation-class hardware, and IntelliJ itself froze under constrained container-VM memory — fixed by tuning memory-bound flags and eventually moving to cloud workstations; separately, their Buildbarn remote-execution cluster suffered an extended, hard-to-diagnose performance regression that was eventually root-caused to slow local storage on the RE workers, only found via a custom-built cluster visualization tool. [Uber's Go monorepo](https://www.uber.com/en-NO/blog/go-monorepo-bazel/) (launched 2018, now 70,000+ files, ~10,000 commits/month, ~900 monthly active engineers, 1,000+ external modules) documents Gazelle-generation limits at scale — it could only append `go_repository` rules to WORKSPACE, never prune ones for removed modules — and a missing target-hash primitive analogous to Buck's `targets --show-target-hash`, which Uber had to build itself for CI parallelization; they upstreamed the fixes (Gazelle PRs #480, #493, #514, #603, #649; Bazel PR #10856, landed 3.1+, letting target lists be read from a file instead of the CLI). [clientserver.dev: "Bazel is too pure for this world"](https://www.clientserver.dev/p/bazel-is-too-pure-for-this-world) is the sharpest critical synthesis: Bazel demands full input/output specification and reproducibility while "the world has drifted away from Bazel's happy place" toward convention-over-configuration tooling; it names Nomulus's move to Gradle and Kubernetes's move to Make as concrete departures, and calls out Bash-based genrules as the specific reason Windows support lags (forcing WSL in practice).

### 14. Departures, cancellations, and comparison posts

[RabbitMQ's PR removing Bazel](https://github.com/rabbitmq/rabbitmq-server/pull/13514) (March 2025) is a primary, dated data point: Bazel is described in the PR as "a great tool" that provided real caching and build-optimization value, but the project chose to consolidate on Make/erlang.mk instead — a departure not motivated by a Bazel defect. The [bazel-discuss AOSP cancellation thread](https://groups.google.com/g/bazel-discuss/c/PYFb6FtoPFE) similarly records Google's own statement that Android's Bazel migration was halted "due to a review of Android business priorities, not due to shortcomings of Bazel or Android itself" — with a commenter's unconfirmed speculation about funding as the only dissenting voice. On the comparison-post side, 2026-era pieces (aviator.co, sourcegraph.com, hermetiq.com, daily.dev — secondary but consistent) converge on the same framing: Bazel/Buck2/Pants are "polyglot heavyweights" whose hermetic, fine-grained model is worth its setup cost mainly at large-org scale, while Nx/Turborepo are lightweight task-runners layering caching over existing per-language tools, capped below Bazel's ceiling but sufficient for most JS/TS-only teams; Pants is explicitly positioned as "the right starting point for Python-heavy monorepos that find Bazel's BUILD-file overhead too steep."

### 15. Ecosystem state as of BazelCon 2025 and the JetBrains IDE handoff

[BazelCon 2025 recap](https://blogsystem5.substack.com/p/bazelcon-2025-recap) (secondary but detailed conference notes) is the most current single digest of ecosystem direction: Bazel 9 removes WORKSPACE support entirely and disables autoloading of native rules by default (users must now explicitly `@load` everything they use); Starlark is gaining type annotations (syntax in Bazel 9, type-checking planned for Bazel 10); "Starlarkification" of built-in rules is nearly complete except a few C++ integration points; a new `PROJECT.scl` file format is emerging as the canonical place to map targets to flags at the project level; Cloudflare now hosts BCR mirrors (available in Bazel 8.4+); and Google's Skycache (serialized analysis-graph caching) demoed a 46-second-to-13-second cold-build improvement. Named performance deltas: NestedSets memory optimization ("up to 20%"), Merkle-tree handling ("reduce wall time by up to 30%"), and path stripping now "more mature," cited at "up to an 84% reduction in build time" for the rule sets that have adopted it. Separately, the [JetBrains Bazel plugin GA announcement](https://blog.jetbrains.com/idea/2025/07/bazel-ga-release/) (July 2025) confirms Google is deprecating its own IntelliJ Bazel plugin and handing ownership to JetBrains, whose plugin reached General Availability with new official Python and Scala support and Bazel 8 compatibility.

## Recent shifts seen in this corpus

- **Bazel 9 (2025-2026 release cycle): WORKSPACE removed entirely, native-rule autoloading disabled by default.** Invalidates any older guidance ("just add a `WORKSPACE` file", "native rules are always in scope") written before this cycle. Source: [BazelCon 2025 recap](https://blogsystem5.substack.com/p/bazelcon-2025-recap).
- **Bazel 7 (2023-10-06): Build without the Bytes became the default.** Older advice that treats the remote cache as a pure optimization, not load-bearing infrastructure, is stale from this date forward. Source: [BwoB in Bazel 7](https://blog.bazel.build/2023/10/06/bwob-in-bazel-7.html).
- **Bazel 8+ (2024-2025): symbolic macros exist and are the recommended macro style, but lazy evaluation — their headline performance promise — is still unshipped as of 2025-11-20.** Guidance that says "switch to symbolic macros for a performance win" is currently overclaiming; the honest claim as of this survey is "switch for correctness/typing, the performance win is pending." Source: [Tweag, 2025-11-20](https://www.tweag.io/blog/2025-11-20-migrating-bazel-symbolic-macros/).
- **rules_python 0.36.0-0.37.0 (2024-era): Bzlmod-mode toolchain registration API changed** from WORKSPACE's `tool_versions` parameter to the `python.override()` tag with `minor_mapping`. Guidance written against pre-0.36 rules_python WORKSPACE APIs under Bzlmod is stale. Source: [EngFlow](https://blog.engflow.com/2024/06/27/migrating-to-bazel-modules-aka-bzlmod---the-easy-parts/).
- **JetBrains Bazel plugin GA, 2025-07.** Google's IntelliJ Bazel plugin is now legacy; any IDE guidance pointing at the Google-owned plugin as the current option is stale from mid-2025. Source: [JetBrains GA blog](https://blog.jetbrains.com/idea/2025/07/bazel-ga-release/).
- **BCR mirror via Cloudflare, Bazel 8.4+.** Registry-availability guidance ("BCR is a single point of failure") needs updating for repos on 8.4+. Source: [BazelCon 2025 recap](https://blogsystem5.substack.com/p/bazelcon-2025-recap).
- **RabbitMQ's departure from Bazel, 2025-03,** is a dated, primary counter-example to "companies keep adopting Bazel and never leave" — worth citing precisely rather than as vague folklore. Source: [RabbitMQ PR #13514](https://github.com/rabbitmq/rabbitmq-server/pull/13514).

## Contested

- **Is Bazel worth its setup cost outside the largest orgs?** "Bazel is too pure for this world" and the departure examples (RabbitMQ, Kubernetes historically, Nomulus historically) argue no for small-to-mid teams; Snowflake's two-year retrospective and Uber's sustained Go-monorepo investment argue yes at sufficient scale. The 2026 comparison-post cluster is converging on a bifurcated answer (heavyweight-for-scale vs. lightweight-for-most) rather than either extreme — this looks like the settling consensus, not an open fight.
- **Should `MODULE.bazel.lock` be checked into version control?** Official docs recommend a git merge driver; the EngFlow migration series and multiple GitHub issue threads document teams `.gitignore`-ing it instead, at least during migration. No source in this corpus claims the merge-driver approach has actually eliminated the pain at scale — leaning toward "still unresolved" rather than "trending toward an answer."
- **Does `rules_python`'s `uv` support count as "real" uv/hermetic-interpreter support?** Maintainer commentary points users elsewhere (`aspect_rules_py`) for the full story, while rules_python's own docs present the `uv pip compile` speedup as if it were the uv story. This is a live scoping disagreement inside the ecosystem, not just an external critique — a rule citing "rules_python has uv support" without qualification would be taking one side of a still-contested claim.
- **Was AOSP's Bazel cancellation a technical or an organizational verdict?** Google's own statement says organizational/business-priorities; a bazel-discuss commenter speculates funding-related, which is a variant of the same non-technical explanation, not a rebuttal. No source in this corpus argues it was technical — worth treating as settled toward "non-technical," with the caveat that Google did not publish a technical post-mortem to fully rule it out.
- **Is `--noremote_upload_local_results` on untrusted lanes sufficient cache-poisoning protection, or does it need to be paired with read-side restrictions too?** The corpus's sources consistently recommend it as the primary control but do not claim it is complete; whether additional controls (separate cache instances per trust tier, content verification) are necessary in practice is not resolved in any source read here.
