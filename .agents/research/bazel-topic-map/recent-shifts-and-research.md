## Summary

- WORKSPACE went disabled-by-default in Bazel 8.0 (2024-12-09) and its code was **fully removed** in Bazel 9.0 (2026-01-20, issue [#26131](https://github.com/bazelbuild/bazel/issues/26131)); `--enable_bzlmod` and `--enable_workspace` are now no-ops. Any advice that says "use WORKSPACE" or "toggle `--enable_workspace`" is dead on the pinned 8.7.0 and dead-dead on 9.x/rolling.
- The Starlarkification effort that moved `android_*`/C++/`java_*`/`proto_library`/`py_*`/`sh_*` out of Bazel's core **concluded in Bazel 9.0**: `--incompatible_autoload_externally` now defaults to the empty string, so nothing autoloads any more — every one of those rules must be `load()`ed from `rules_android`/`rules_cc`/`rules_java`/`protobuf`/`rules_python`/`rules_shell`. `rules_ocx` and any C++ probe in the fleet must load `cc_binary` etc. from `@rules_cc`, not assume it's native.
- Symbolic macros (Bazel 8.0) are the intended replacement for legacy `.bzl` macros: typed arguments, automatic `select()` promotion, macro-aware visibility that hides internal targets, and (new in 9.0) enforced Starlark computation step limits. Legacy macros still work but keep none of these guarantees.
- `MODULE.bazel.lock` has its own version number (10, as fetched from the current docs) independent of the Bazel version; a version bump can make an old lockfile unreadable by a newer Bazel and vice versa, and `bazel mod deps --lockfile_mode=update` is the fix, not hand-editing the file.
- A module extension can opt out of lockfile tracking entirely by returning `repository_ctx.repo_metadata(reproducible=True)` / declaring `reproducible=True`; such repos are also the only ones eligible for the new Bazel 9.0 `--repo_contents_cache` and `--experimental_remote_repo_contents_cache`.
- Canonical repository names changed shape twice in this window: `~` became `+` (flipped by default in 8.0) and, in 9.0, repos created via `use_repo_rule` got new, more-stable canonical names — anything hardcoding a canonical repo name in a flag (`--override_repository`) or string can silently break across an upgrade.
- Bazel's own release-notes appendix is the ground truth for flag churn: 9.0.0 alone lists 8 flags removed outright and 8 more turned into permanent no-ops, on top of ~19 `--incompatible_*` flags flipped by default.
- `.bazelversion` accepts more than a pinned semver: `rolling` tracks the latest rolling release, `last_green` tracks the last commit that passed Bazel's own CI — neither is meant for a repo's default pin, both are fine for a canary/nightly job.
- Bazel's release lifecycle (per [bazel.build/release](https://bazel.build/release)) currently shows Bazel 9 in **Active**, Bazel 8 and 7 in **Maintenance**, and Bazel 6 already **Deprecated** — `rules_ocx`'s CI matrix (8.7.0, 9.x, rolling) is testing one Maintenance and one Active major plus the bleeding edge, and has no coverage on a Deprecated major.
- Ruleset majors moved independently of Bazel majors and faster than the frame's guess: `rules_js` is at **3.4.1** (not 2.x) as of 2026-09-04, having dropped Bazel 6, WORKSPACE, and pnpm <9 support entirely in 3.0; `rules_python` is at **2.3.3** and made Windows use venvs by default and enabled the Bazel downloader by default for PyPI fetches in 2.0; `rules_rust` is at **0.74.0**.
- Bazel 9.0 raises a hard floor: it requires `protobuf` ≥ 33.4 and offers `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc` to skip building `protoc` from source — irrelevant to the fleet today (zero `.proto` files) but relevant to `rules_ocx`'s own consumers.
- "Build Systems à la Carte" (Mokhov/Mitchell/Peyton Jones, ICFP'18 / JFP'20) frames every build system as a (persistent build store, task scheduler, rebuilder) triple; Bazel is a *suspending scheduler* over a *verifying-trace, constructive* rebuilder — a useful frame for explaining **why** a given `.bzl` change does or doesn't invalidate the cache, not just documenting that it does.
- Buck2's public design argument (Meta, 2023) is that a build-system core with **zero language-specific knowledge**, plus a single incremental target+action graph (no separate analysis/execution phases), is what let them claim 2x build-time improvement over Buck1 — directly relevant to how `rules_ocx`'s own extensions should stay generic rather than special-casing OCX package shapes.
- *Software Engineering at Google* ch. 18 argues artifact-based build systems (Bazel's category) beat task-based ones (Make, npm scripts, raw `cargo build` orchestration) specifically because restricting what a build step is allowed to do is what buys parallelism, caching, and hermeticity — this is the closest thing to a formal argument for "why adopt Bazel at all" that the corpus offers, and it's argued, not measured, in the book itself.
- Ch. 23 gives real numbers: Google's TAP runs "more than four billion individual test cases per day" across "over 50,000 unique changes," using the dependency graph to pick a minimal test set — the direct ancestor of target-determination tooling (`bazel-diff`, target-determinator) that a monorepo CI topic should point to.
- Meta's Predictive Test Selection (ICSE-SEIP 2019, arXiv:1810.05286) is a **measured** result: a learned test-selection model cut testing infrastructure cost by 2x while still reporting >95% of individual test failures and >99.9% of faulty changes — a concrete, cited number for why "run everything on every PR" is not the CI end-state a Bazel monorepo should target.
- An empirical study of 383 real Bazel GitHub projects (arXiv:2405.00796) found **31.23%** of projects with CI configured don't actually invoke Bazel inside that CI — a measured antipattern (adopt Bazel locally, never wire it into CI) that a `bazel-adopt` procedure should explicitly guard against.
- Two dependency-error-detection papers (VeriBuild/EChecker family, ISSTA'20 and arXiv:2404.13295) both target Make/C++, not Bazel — Bazel's sandboxed, hermetic actions are explicitly cited as the mitigation the field is chasing for other build systems, which is evidence *for* Bazel's core design claim rather than a Bazel-specific finding.
- Skyframe's own documented invariant — "if all input data of all functions is recorded, Bazel can invalidate only the exact set of nodes that need to be invalidated" — is the one-sentence reason every hermeticity rule in this program eventually reduces to "did you read something without declaring it as a dependency."
- Nothing found in this corpus discusses remote-execution/caching **economics** (cost-per-cache-hit, cache-size-vs-cost curves) as a Bazel-specific, cited, numeric study — this is a real gap, not an oversight; see Contested.

## Survey

### 1. Bazel 7.0.0 release (2023-12-11)

Full [release notes](https://github.com/bazelbuild/bazel/releases/tag/7.0.0) and its accompanying [Bazel 7.0 LTS blog post](https://blog.bazel.build/2023/12/11/bazel-7-release.html). Bzlmod ("Bazel's new way to manage 3rd party dependencies") is enabled by default (`--enable_bzlmod`). WORKSPACE still works in 7.x; the notes state the plan explicitly: "With Bazel 8, we plan to disable WORKSPACE by default (can still be enabled) and with Bazel 9 we plan to remove the legacy WORKSPACE based dependency system." Skymeld ("Bazel now starts executing actions while it is still analyzing other top-level targets") ships enabled by default, claiming "up to 15%" wall-time reduction on multi-target builds; it can be reverted with `--noexperimental_merged_skyframe_analysis_execution`. Build without the Bytes (BwoB) is default-on: `--remote_download_outputs` now defaults to `toplevel`, "speeding up builds by up to 40%" with remote caching/execution. Platform-based toolchain resolution is default for Android and C++.

### 2. Bazel 8.0.0 release / "Bazel 8.0 LTS" (2024-12-09)

Full [release notes](https://github.com/bazelbuild/bazel/releases/tag/8.0.0) and [blog post](https://blog.bazel.build/2024/12/09/bazel-8-release.html). Two headline changes:

- **WORKSPACE disabled by default.** "The WORKSPACE and WORKSPACE.bzlmod files are no longer read by Bazel, by default. To bring back this behavior, use `--enable_workspace`." (`--enable_workspace` flipped by [#23023](https://github.com/bazelbuild/bazel/issues/23023).)
- **Symbolic macros introduced.** Typed, `select()`-aware, mutation-resistant macro arguments; macro-aware visibility hiding a macro's internal targets from its caller; legacy macros that call `native.existing_rules()` "can often be replaced by finalizer macros." Lazy evaluation is explicitly flagged "not implemented yet" at this release.
- **Starlarkification.** `android_*` → `rules_android`, C++ toolchain symbols → `rules_cc` (rules themselves "moved in a future release" — i.e., not yet in 8.0), `java_*`/`JavaInfo` → `rules_java`, `*_proto_library`/`ProtoInfo` → `protobuf`, `py_*`/`PyInfo` → `rules_python`, `sh_*` → `rules_shell`. `--incompatible_autoload_externally` is introduced, defaulting to auto-loading these from their new homes so `load()` statements aren't yet mandatory (that comes in 9.0).

Other flipped-by-default flags in this release, verbatim from the appendix: `--incompatible_disallow_empty_glob` (true, [#8195](https://github.com/bazelbuild/bazel/pull/8195) — an empty `glob()` result is now an error, not silently empty), `--incompatible_struct_has_no_methods` (true — legacy `struct`-as-provider methods gone), `--incompatible_use_plus_in_repo_names` (true — canonical repo names use `+` not `~`), `--incompatible_no_implicit_watch_label` (true — a `repository_ctx.watch` call is required, an attribute alone no longer implicitly watches a label), `--legacy_external_runfiles` (false), `--legacy_important_outputs` (false), `--zip_undeclared_test_outputs` (false — undeclared test outputs now a directory, not a zip), `--incompatible_macos_set_install_name` (true), `--incompatible_disallow_ctx_resolve_tools` (true). Labels in all error/log/BEP output are now double-`@`-prefixed (canonical repo names). Java's default language level moved to 11 (via rules_java 8.1.0, was 8). New `cc_static_library` rule (experimental, `--experimental_cc_static_library`). New Skyfocus memory-reduction feature (`--experimental_enable_skyfocus`). New compact execution-log format (`--execution_log_compact_file`). Disk-cache GC flags added (`--experimental_disk_cache_gc_max_size`, `--experimental_disk_cache_gc_max_age`, `--experimental_disk_cache_gc_idle_delay`).

### 3. Bazel 9.0.0 / "Bazel 9 LTS" (2026-01-20)

Full [release notes](https://github.com/bazelbuild/bazel/releases/tag/9.0.0) and [blog post](https://blog.bazel.build/2026/01/20/bazel-9.html). This is the release the frame's pinned/CI-matrix majors (8.7.0 + 9.x + rolling) straddle.

- **WORKSPACE is gone.** "Bzlmod is now always enabled, and all `WORKSPACE` logic has been removed from Bazel" ([#26131](https://github.com/bazelbuild/bazel/issues/26131)). `--enable_bzlmod` and `--enable_workspace` are now no-ops. `bazel sync` is removed; use `bazel fetch --all`.
- **Starlarkification "concludes."** `--incompatible_autoload_externally` now defaults to the **empty string** ([#23043](https://github.com/bazelbuild/bazel/issues/23043)) — nothing autoloads. All C++ rules (`cc_binary`, `cc_import`, `cc_library`, `cc_shared_library`, `cc_static_library`, `cc_test`, `cc_toolchain`, `cc_toolchain_alias`, `objc_import`, `objc_library`, `fdo_prefetch_hints`, `fdo_profile`, `memprof_profile`, `propeller_optimize`) are removed from Bazel core outright and must load from `@rules_cc`. The flag itself "will be removed in Bazel 10.0" per the blog summary — i.e., even the escape hatch is temporary.
- **Protobuf becomes a hard module dependency.** Minimum `protobuf` version 33.4, with `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc` to avoid building `protoc` from source.
- **New repo-fetch caching layer.** `--repo_contents_cache` (new, local, keyed off `--repository_cache`'s `contents` dir) and `--experimental_remote_repo_contents_cache` (new, lets a *reproducible* repo rule's fetched contents live in a shared HTTP/gRPC remote cache, "including via `repository_ctx.watch` or `.getenv`"). Both require the repo rule to declare `repository_ctx.repo_metadata(reproducible=True)`.
- **Canonical repo names for `use_repo_rule`-created repos changed** to be "more stable," which may require updating `--override_repository` usages — though that flag "now also supports apparent repo names" as the mitigation.
- **`single_version_override` pinning below a `bazel_dep` requirement is now a hard error**, not silently ignored — a deliberate anti-footgun change (was previously an easy way to accidentally freeze a stale dependency).
- Struct providers: `--incompatible_disallow_struct_provider_syntax` is now a no-op (permanently disallowed). `range()`, string `split()`/`rsplit()`, list `index()`/`pop()` no longer accept `None`.
- Python: `--python_top` can no longer set runtimes; `--incompatible_use_python_toolchains=false` "no longer works." Points users to `rules-python.readthedocs.io/en/latest/toolchains.html`.
- Test exec groups decoupled from the default exec group's toolchain/constraint requirements — anything that relied on a rule's `toolchains=`/`exec_compatible_with=` reaching test actions needs an explicit test exec group now.
- Housekeeping: `--watchfs` (startup flag) removed, `--verbose_explanations` a no-op, macOS's default output base moved to `$HOME/Library/Caches/bazel` (respecting `XDG_CACHE_HOME`) from `/private/var/tmp`, periodic GC added for the action cache (`--experimental_action_cache_gc_max_age` etc.) and stale install bases (`--experimental_install_base_gc_max_age`). Full appendix: 8 flags removed, 8 more turned into permanent no-ops, ~19 `--incompatible_*` flags flipped in this release alone.
- Windows: junction-vs-symlink handling in `ctx.actions.symlink` made type-aware; graceful fallback (no crash) on filesystems without junction support (`virtiofs`, VirtualBox shares).

### 4. Bzlmod design and lockfile mechanics

["What's new with Bzlmod?"](https://blog.bazel.build/2023/07/24/whats-new-with-bzlmod.html) (2023-07-24) and the current [lockfile docs](https://bazel.build/external/lockfile). The lockfile has its own version number, independent of the Bazel version — the fetched docs show version **10** as of this survey. `--lockfile_mode` has four values: `update` (default — use cached data, skip re-fetch/re-evaluation where safe), `refresh` (like update, but re-checks anything the extension marked mutable), `error` (fail on anything missing, never write), `off` (ignore the lockfile entirely). Each module extension's cached entry is keyed by `bzlTransitiveDigest` (hash of the extension's implementation) and `usagesDigest` (hash of how it's invoked across the graph), alongside the `generatedRepoSpecs` it produced — this is *how* Bazel decides whether to re-run an extension. An extension that returns `reproducible=True` "promises that they will always create the same repositories when given the same inputs" and is excluded from the lockfile entirely. `update` mode also **prunes** stale entries — extensions no longer used anywhere in the graph disappear from `moduleExtensions` on the next `update`-mode run.

### 5. `bazel mod` subcommands

Current [`mod` command docs](https://bazel.build/external/mod-command), cross-checked against the raw source at [`site/en/external/mod-command.md`](https://raw.githubusercontent.com/bazelbuild/bazel/master/site/en/external/mod-command.md). Documented subcommands: `graph` (full dependency graph from root, `--from` to start elsewhere), `deps <module>...` (resolved direct deps), `all_paths`/`path` (paths between modules), `explain` (why/where a module appears), `show_repo` (repo definition; 9.0 added `--all_repos` and `--all_visible_repos`), `show_extension`. Two more subcommands exist and are exercised in the wild but are *not* in that doc page: `bazel mod tidy` ("automatically updates `use_repo` calls in the `MODULE.bazel` file for extensions that use `module_ctx.extension_metadata`") and `bazel mod dump_repo_mapping <canonical-repo>...` (NDJSON repo-mapping dump, the primitive IDEs/Starlark LSPs use to resolve labels) — confirmed via live GitHub issues ([#28601](https://github.com/bazelbuild/bazel/issues/28601)) rather than the docs page itself, a documentation gap worth flagging to a rule author, not just a fact to state.

### 6. Vendor mode and offline builds

[Vendor Mode docs](https://bazel.build/external/vendor). `bazel vendor --vendor_dir={dir}` fetches all external repos (including registry files, under `<vendor_dir>/_registries`) into a local directory; `bazel build --vendor_dir={dir}` then prioritizes that directory over the network. The docs' own caveat: changing targets, external deps, build config, *or the Bazel version* can all require re-vendoring — vendoring is not a permanent offline snapshot, it's a cache that goes stale on more triggers than people expect. Open GitHub issues ([#22302](https://github.com/bazelbuild/bazel/issues/22302), [#29222](https://github.com/bazelbuild/bazel/issues/29222)) show vendor mode still missing content needed for a fully network-free `bzlmod` build and not capturing `bazel mod tidy`-added deps as of the versions filed against — treat "vendor mode gives you offline builds" as aspirational, not proven, in the current corpus.

### 7. Skyframe

[Skyframe reference](https://bazel.build/reference/skyframe) (mirrored verbatim in the [GitHub source](https://github.com/bazelbuild/bazel/blob/master/site/en/reference/skyframe.md)). Three properties, quoted: **hermeticity** ("if functions only request input data by way of depending on other nodes, Bazel can guarantee that if the input state is the same, the same data is returned"), **incrementality** ("if all the input data of all functions is recorded, Bazel can invalidate only the exact set of nodes that need to be invalidated when the input data changes"), **parallelism** (functions that don't depend on each other run in parallel with a guaranteed-equivalent-to-sequential result). This is the formal basis for every "you read something without declaring it" hermeticity bug in the corpus.

### 8. Release lifecycle and versioning policy

[bazel.build/release](https://bazel.build/release), the original [LTS announcement](https://blog.bazel.build/2020/11/10/long-term-support-release.html), and the [rolling-releases post](https://blog.bazel.build/2021/06/15/bazel-rolling-releases.html). LTS majors cut "roughly every 12 months," minor releases on the Active track "once every 2 months," patches on-demand. A new LTS immediately enters **Active**; the previous one drops to **Maintenance** for **2 years** before **Deprecated**. Rolling releases are cut "around every two weeks" from the same HEAD as Google's internal Blaze release and preview the next LTS; no patches are ever backported to a rolling release. As fetched, current staging: Bazel 9 Active, Bazel 8 and 7 Maintenance, Bazel 6 and earlier Deprecated — consistent with the GitHub releases timeline pulled directly (7.7.1 on 2025-11-12, 8.8.0 on 2026-08-31, 9.2.0 on 2026-07-13, 9.0.0 on 2026-01-20).

### 14. "Build Systems à la Carte" (Mokhov, Mitchell, Peyton Jones)

[ACM DL entry](https://dl.acm.org/doi/10.1145/3236774) (ICFP'18 → *JFP* 2020), [PDF](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems.pdf). **Argued**, formal/executable framework, not an empirical study. Core move: every build system is characterized by two independent choices — an ordering strategy for tasks (the *scheduler*: topological, restarting, or suspending) and a decision of whether a task needs rebuilding (the *rebuilder*: dirty-bit, verifying-trace, constructive-trace, or deep-constructive-trace). The paper explicitly reconstructs Make, Shake, Excel, **Bazel**, Buck, CloudBuild, and Nix inside this taxonomy in Haskell. This is the frame's requested grounding for "where Bazel sits": a suspending-scheduler, verifying-trace system (it recomputes a task only when a dependency's *content* — not just presence — changed, and it can suspend a task mid-build to satisfy a newly-discovered dependency, which is exactly what Skyframe's SkyFunction re-entrancy does).

### 15. Buck2 design (Meta engineering blog)

["Build faster with Buck2: Our open source build system"](https://engineering.fb.com/2023/04/06/open-source/buck2-open-source-large-scale-build-system/) (2023-04-06). **Argued + one measured number.** Central design claim, quoted structure: "the core build system has no knowledge of any language-specific rules" — every language (C++, Rust, Python, OCaml, in the shipped "prelude") is Starlark on top of a core that knows nothing about any of them, versus Buck1's Java-embedded rules and Bazel's C++/Java rules living inside the binary (true as of pre-9.0 Bazel; less true after 9.0's Starlarkification-complete). Second structural claim: Buck2 keeps target-graph and action-graph as "a single incremental dependency graph" instead of Bazel's separate analysis/execution phases (which Skymeld exists specifically to blur, but doesn't unify). The one cited number: "Buck2 completed builds 2x as fast as Buck1" in Meta's internal comparison — a vendor-measured, not third-party-measured, number.

### 16. Pants v2 design

["Introducing Pants v2"](https://www.pantsbuild.org/blog/2020/10/27/introducing-pants-v2) (2020-10-27). **Argued.** Pants v2's engine is Rust for the incremental-graph core, driving Python `async` coroutine "rules" as the user-facing extension mechanism; the design goal stated is that "fine-grained invalidation, concurrency, hermeticity, caching, and remote execution happen naturally, without rule authors needing to think about it" — i.e., push the hard incrementality problem into the engine, keep rule code declarative. Useful contrast to Bazel/Starlark's more macro-and-attribute-shaped extension surface.

### 17. Software Engineering at Google, ch. 18 (Build Systems and Build Philosophy)

[abseil.io/resources/swe-book/html/ch18.html](https://abseil.io/resources/swe-book/html/ch18.html). **Argued**, with scale claims stated as fact rather than cited to a study. Central argument: artifact-based build systems (Bazel's category — you declare *what* to build and the system derives *how*) beat task-based ones (Make, Ant, Gradle-as-scripted, and by extension a hand-rolled `cargo build`/`pnpm run build` graph) precisely because they *remove* flexibility from what a build step may do, and that removed flexibility is what buys parallel and cached execution. Other named principles: the "1:1:1 rule" (one package : one BUILD file : one directory), no cyclic dependencies enforced by the tool, the "One-Version Rule" for external dependencies. Scale claims as stated: "more than two billion lines of code" in one monorepo, "millions of builds executing millions of test cases... every day."

### 18. Software Engineering at Google, ch. 23 (Continuous Integration)

[abseil.io/resources/swe-book/html/ch23.html](https://abseil.io/resources/swe-book/html/ch23.html). **Measured**, Google's own numbers. TAP (their CI/test-selection layer): "over 50,000 unique changes daily," "more than four billion individual test cases per day," "more than one change per second," average presubmit wait "approximately eleven minutes." Mechanism: TAP "uses Google's dependency graph to run minimal necessary tests" — this is target determination at Google's scale, the direct ancestor of `bazel-diff`/target-determinator tooling a Bazel-adopting monorepo would reach for. Flaky tests are named as corrosive to trust in CI independent of whether the underlying code is actually broken; the chapter's mitigation menu is retries plus "hermetic testing," not a novel flaky-detection algorithm.

### 19. Predictive Test Selection (Meta/Facebook, ICSE-SEIP 2019)

[arXiv:1810.05286](https://arxiv.org/abs/1810.05286), [Meta's own writeup](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/). **Measured.** A model learned from historical test-outcome data picks a subset of tests per change; in production it "reduces the total infrastructure cost of testing code changes by a factor of two" while still surfacing ">95% of individual test failures" and ">99.9% of faulty changes," and it explicitly accounts for test flakiness in its training signal rather than treating flaky results as noise to discard.

### 20. Taming Google-Scale Continuous Testing (Google, ICSE-SEIP 2017)

[research.google/pubs/pub45861](https://research.google/pubs/pub45861/). **Measured**, older (2017, outside the frame's 24-month window but explicitly named in the brief as foundational). Findings, as summarized from the paper: very few tests ever fail overall; the ones that do fail tend to be "closer" (dependency-distance) to the changed code; certain frequently-modified files and certain tools/users correlate with more breakages; code touched by more than 3 developers recently breaks more often. This is the empirical basis for "test what's near the change first," which is what target-determination tooling operationalizes.

### 21. Detecting Build Dependency Errors — Make/C++ (2020, 2024)

["Escaping Dependency Hell: Finding Build Dependency Errors"](https://qingkaishi.github.io/public_pdfs/ISSTA20-VeriBuild.pdf) (ISSTA'20) and its 2024 successor, ["Detecting Build Dependency Errors in Incremental Builds"](https://arxiv.org/abs/2404.13295) (EChecker). **Measured**, both target Make-based C/C++ builds, not Bazel. VeriBuild: ~100 open-source C/C++ projects, finds both missing and redundant declared dependencies via a unified dependency graph built from compiler/linker traces. EChecker (2024): infers dependency changes incrementally from preprocessor directives and Makefile diffs instead of doing a clean-build trace every time — measured **85.14× faster on average** (median 16.30×) than the prior state of the art, evaluated across 12 projects / 240 commits, with an F1 improvement of 0.18 over the baseline. Neither paper studies Bazel; both implicitly validate Bazel's design choice (sandboxed actions that fail loudly on an undeclared read) as the structural fix for the exact class of bug they're detecting after the fact elsewhere.

### 22. Does Bazel actually speed up CI? (empirical study, 2024)

[arXiv:2405.00796](https://arxiv.org/abs/2405.00796), "Does Using Bazel Help Speed Up Continuous Integration Builds?" **Measured.** 383 real Bazel projects from GitHub, 4 CI services, 3,500 tests plus 102,232 experiments across the last 100 commits of 70 buildable projects, benchmarked against Maven. Adoption-gap finding: **31.23%** of Bazel projects that *have* a CI service configured don't invoke Bazel inside that CI at all, and **27.76%** of the ones that do lean on extra tooling to make it work. Performance finding (on long-build projects only): parallel-build median speedups of 2.00×/3.84×/7.36×/12.80× at 2/4/8/16 threads; incremental-build median speedups of 4.22× (tool-independent cache) and 4.71× (tool-specific cache).

## Recent shifts seen in this corpus

- **WORKSPACE**: introduced-as-legacy in 7.0 (2023-12-11, still default-on), disabled by default in 8.0 (2024-12-09, `--enable_workspace=false`), all code removed in 9.0 (2026-01-20). Old advice "add a `WORKSPACE` entry" is dead on anything at 8.7.0+ without `--enable_workspace`, and unfixably dead on 9.x/rolling.
- **Autoload of native rules**: `--incompatible_autoload_externally` introduced in 8.0 (2024-12-09) defaulting to *autoload on* (so old code kept working); flipped to default *off* (empty string) in 9.0 (2026-01-20), meaning every `android_*`/`cc_*`/`java_*`/`proto_library`/`py_*`/`sh_*` reference now needs an explicit `load()` from its external repo. Old advice "these rules are just available" is dead on 9.x.
- **Symbolic macros**: introduced in 8.0 (2024-12-09) as the recommended macro pattern; 9.0 (2026-01-20) added `inherit_attrs` and, more importantly, started *enforcing* Starlark computation step limits inside them (previously exempt) — a symbolic macro that was silently unbounded-cost on 8.x can now hit a hard limit on 9.x.
- **Canonical repo names**: `~`→`+` flipped by default in 8.0 (2024-12-09); `use_repo_rule`-created repos got new, more stable names in 9.0 (2026-01-20). Anything hardcoding the old shape in a script, flag, or string comparison breaks across either boundary.
- **Ruleset majors moved independently and faster than expected**: rules_js jumped 1.x→2.x (2024) →3.x (2026, dropping Bazel 6/WORKSPACE/pnpm<9); rules_python jumped 0.x→1.x (2024) →2.x (2026, Windows-venvs-by-default, Bazel-downloader-by-default). Advice pinned to "rules_js 2.x" or "rules_python 1.x" as current is already one major behind as of 2026-09-05.
- **Repo-fetch caching**: `--repo_contents_cache` and `--experimental_remote_repo_contents_cache` are both new in 9.0 (2026-01-20) — no prior-version equivalent existed; a repository rule written before 9.0 needs to actively declare `reproducible=True` to benefit, it doesn't happen automatically.
- **Protobuf**: moved from "special-cased inside Bazel" toward "just a module with a version floor" — 9.0 (2026-01-20) requires protobuf ≥ 33.4 and adds `--@protobuf//bazel/toolchains:prefer_prebuilt_protoc` to skip building `protoc`.

## Contested

- **Whether Buck2's zero-language-core design is actually a meaningful contrast to *current* Bazel, or a stale one.** Buck2's 2023 pitch leans hard on "our core knows nothing about languages, Bazel's does" — true when written, but Bazel 9.0's Starlarkification-complete milestone (native `cc_*`/`java_*`/etc. rules physically removed from the binary) closes most of that gap from the other direction. The comparison is trending toward "both are Starlark-over-a-generic-core now," which weakens the frame's hypothesis #5 (recent Buck2/Pants talks carry currently-unique insight) for this specific claim, though Buck2's single-graph (no separate analysis/execution phase) design remains a real, unclosed difference from Bazel-plus-Skymeld.
- **Whether vendor mode delivers real offline-build guarantees.** The docs assert it does; open GitHub issues (`#22302`, `#29222`) from users show gaps (registry content not fully captured, `bazel mod tidy`-added deps missed). Trending: still an open problem as of this survey, not yet resolved even inside 9.0's release notes.
- **Whether `bazel mod tidy` belongs in "core, documented mod subcommands."** It functions and is referenced by name in multiple places, but is absent from the canonical `mod-command.md` doc page fetched directly from source. Trending: likely a documentation lag rather than a deliberate omission, but a rule that tells an agent to "check `bazel mod` docs for available subcommands" will miss it as currently written.
- **Remote-execution/caching economics as a research topic.** The frame asks for this explicitly ("remote execution scheduling and caching economics"); this wave found no Bazel-specific, numerically-grounded, cited paper or post on cache-hit-rate-vs-cost tradeoffs — only generic caching-systems papers unrelated to build systems, and vendor blog posts (Incredibuild) with no methodology disclosed. This is a real gap in the literature as surveyed, not a coverage miss by this scout; a later research wave chasing this specific question should expect thin primary sources and may need to fall back to BazelCon/Build Meetup talk recordings instead of papers.
