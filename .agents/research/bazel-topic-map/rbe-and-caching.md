## Summary

- An action's cache key (REAPI `Action`) hashes the `Command` digest (arguments, sorted env vars), the `input_root_digest` (a Merkle tree of file/dir/symlink digests), an optional `Platform`, and an optional `salt` — timestamps are not part of it except through what a rule chooses to feed in (`stable-status.txt`/`volatile-status.txt`).
- Bazel deliberately excludes the *volatile* build-status file from cache invalidation even when its content changes, specifically so `--stamp` doesn't defeat caching — but any rule that also depends on the *stable* status file for something that actually varies (timestamps, non-deterministic version strings) still poisons the cache.
- `--incompatible_strict_action_env` now defaults to **true**: Bazel pins `PATH` and drops `LD_LIBRARY_PATH` inheritance by default; this used to be opt-in.
- Build without the Bytes (BwoB) defaults changed in Bazel 7 (Dec 2023): `--remote_download_outputs` now defaults to `toplevel`, not `all`; CI runners that never need artifacts should still go further and set `minimal`.
- Cache-eviction handling is a named failure mode with its own exit code: Bazel 7 introduced exit code **39** for "lost inputs" (`--incompatible_remote_use_new_exit_code_for_lost_inputs`), paired with `--experimental_remote_cache_eviction_retries` (default **5**).
- Credential helpers (`--credential_helper`) graduated from experimental to stable in Bazel 7.0, replacing bare `--remote_header` bearer tokens — the pattern rules_ocx's `.bazelrc.user` still uses (a cache write credential embedded directly, per the frame).
- `--remote_cache_compression` defaults to **false**; even enabled, it only compresses blobs at or above `--experimental_remote_cache_compression_threshold` (default **100 bytes**).
- The flag the original brief named, `--experimental_remote_merkle_tree_cache`, does not exist in the current CLI reference — the live flag is `--experimental_remote_discard_merkle_trees` (default **true**, inverted semantics: it *discards* in-memory Merkle trees to save memory).
- Dynamic execution structurally cannot run against a cache-only remote backend: the docs state plainly that "it is not currently possible to use a cache-only remote system, as a cache miss would be considered a failed action" — this rules dynamic execution out for any fleet repo (rules_ocx included) that has a remote cache but no executor.
- REAPI's `SymlinkAbsolutePathStrategy` has two legal server behaviors — `DISALLOWED` (reject absolute symlink targets) or `ALLOWED` (permit them, "possibly resulting in non-hermetic builds") — a server operator's choice here, not Bazel's.
- REAPI `Command.arguments[0]` resolution changed in spec v2.3: v2.2 and earlier forbade PATH lookups and required paths relative to the input root; v2.3+ allows PATH-style resolution — servers/clients can't assume either behavior without checking capabilities.
- Bazel 9 (Jan 2026) fully removes WORKSPACE; Bzlmod is the only dependency system. Any doc describing WORKSPACE-era RBE setup (Bazel's own `remote/ci.md`, which still tells readers to add an `rbe_autoconfig` target via the `bazel-toolchains` WORKSPACE repo) is now historical-only.
- Bazel 9 adds a **local** repo contents cache (`--repo_contents_cache`, stable) and an **experimental remote** one (`--experimental_remote_repo_contents_cache`) — the remote variant requires a repository rule to declare `repository_ctx.repo_metadata(reproducible = True)` and explicitly excludes any repo rule using `repository_ctx.watch`/`.getenv` at runtime.
- EngFlow's own taxonomy counts *six* distinct caches inside a single Bazel invocation (in-memory Skyframe, repository cache, output-tree/action cache, remote action-cache+CAS, disk cache, remote-execution cache) — most cache-hit confusion comes from conflating two of these.
- The repository cache (`--repository_cache`) only helps repo rules that call `repository_ctx.download()` under the hood (e.g. `http_archive`); rules like `go_repository` or `container_pull` that shell out on their own bypass it entirely, and neither the repository cache nor the disk cache has automated garbage collection by default (unlike `--disk_cache`'s newer `--experimental_disk_cache_gc_max_size`/`_max_age`, available since Bazel 7.4).
- `bazel-remote` (the shape rules_ocx's HTTP cache uses) speaks both HTTP/1.1 and gRPC, keys CAS entries by lowercase SHA-256 and Action-Cache entries by an arbitrary 64-hex-char key, and only promises cache-directory *format* stability across major versions — a minor-version bump is not guaranteed safe to read old data with.
- Buildbarn deliberately splits `bb_worker` (fetches inputs, orchestrates) from `bb_runner` (spawns the actual process) into separate processes/privilege domains specifically to allow privilege separation and to work around a Go runtime race that prevents multi-threaded processes from writing-then-executing binaries reliably.
- `bazel-buildfarm` and target-diffing tools (`bazel-diff`, `target-determinator`) are explicitly cross-build-system: buildfarm markets REAPI compatibility with Buck2 and Pants, not just Bazel.
- `target-determinator`'s own README admits its results cache key excludes home-/system-level `.bazelrc`, environment variables, and host hardware/OS — exactly the kind of per-machine drift rules_ocx's non-hermetic `.bazelrc.user` (zig `CC`, `layering_check` disabled) would introduce, meaning a naive target-determinator adoption could report "unaffected" for targets that actually differ across machines.
- `bazel-diff`'s own README concedes it "is incorrect and will sometimes miss affected targets" — a documented false-negative risk in exchange for speed, versus target-determinator's documented slowness.
- Test sharding is opt-in cooperation from the test runner: Bazel fails the test if the runner doesn't touch `TEST_SHARD_STATUS_FILE`, so a shard-unaware custom runner fails loudly rather than silently running everything N times.

## Survey

### 1. Remote Execution API v2 — the protocol itself
[`remote_execution.proto`](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto) (2,516 lines, fetched in full).

- `Action` (line 608) carries `command_digest`, `input_root_digest`, an optional `timeout` (itself part of the digest — "two `Action`s with different timeouts are different, even if they are otherwise identical"), `do_not_cache`, an operator `salt` ("allows disowning an entire set of ActionResults that might have been poisoned by buggy software or tool failures"), and an optional `platform`.
- `Command` (line 683) requires `environment_variables` to be "lexicographically sorted by name" (byte-wise UTF-8) "in order to ensure that equivalent Commands always hash to the same value" — an unsorted env list is a self-inflicted cache-key instability. `arguments[0]` resolution changed in **v2.3**: older (v2.2 and earlier) implementations forbid PATH lookups and resolve relative paths against the input root; v2.3+ permits PATH-style resolution if the `PATH` env var is present.
- `Platform` (line 868): properties are implicitly part of the action digest, so "even tiny changes in the names or values (like changing case) may result in different action cache entries." New in v2.2: platform properties should be set on both `Action` and `Command`; servers should prefer the `Action`-level ones.
- `Directory` (line 982): children (files, dirs, symlinks) "must each be sorted in lexicographical order by path" — same footgun class as `Command`'s env-var ordering requirement.
- `SymlinkNode` (line 1060): target can be relative or absolute (`/`-prefixed); `..` components are legal but "canonicalization is still recommended... to reduce potential cache misses."
- `Digest` (line 1111): hash + size together, "even if the `hash` field is correctly specified but `size_bytes` is not, the server MUST reject the request."
- `DigestFunction.Value` enum (line 2094) lists SHA256 (implied default), SHA1, MD5, VSO, SHA384, SHA512, MURMUR3 (non-cryptographic), **SHA256TREE** (a newer chunk-based tree hash for large blobs, SIMD-friendly), and **BLAKE3** — a server/client pair must agree on one via `CacheCapabilities.digest_functions`.
- `SymlinkAbsolutePathStrategy` (line 2243): `DISALLOWED` (server rejects absolute-target symlinks) vs `ALLOWED` ("possibly resulting in non-hermetic builds") — an explicit server policy choice, not a Bazel client flag.
- `Compressor.Value` (near 2261) enumerates IDENTITY/ZSTD/DEFLATE/BROTLI as advertised compression formats via `CacheCapabilities`.
- The `Execution` service's `Execute`/`WaitExecution` RPCs document that a server "does not need to guarantee... at most one execution," MAY run an action multiple times in parallel, and that cancellation (`CANCELLED` status) is only possible "if the server implements the Operations API `CancelOperation` method."

### 2. [Bazel remote caching](https://bazel.build/remote/caching)
Documents `--remote_cache`, `--remote_upload_local_results` (read-only-cache pattern for untrusted builds), `--disk_cache` (with `--experimental_disk_cache_gc_max_size`/`_max_age`/`_idle_delay`, the last "starting with Bazel 7.4, defaulting to 5 minutes"), and `--experimental_guard_against_concurrent_changes` (mitigates uploading invalid results when an input file changes mid-build). States plainly: "Bazel currently does not track tools outside a workspace" — i.e. a host compiler/toolchain difference is invisible to the cache key unless it's hermetically packaged as an input.

### 3. [Remote Execution Overview](https://bazel.build/remote/rbe) and [Adapting Bazel Rules for Remote Execution](https://bazel.build/remote/rules)
The overview page is thin and defers to `/remote/rules` for the actual constraints. That page lists the mandatory shape for RE-compatible rules: invoke tools "in a predictable, preconfigured manner" rather than via host `PATH`/`JAVA_HOME`; declare every dependency explicitly in the tool invocation (build tools that "retain state... and access dependencies that have not been explicitly included" fail in isolated remote workers); ship or pre-install platform-appropriate tool binaries rather than host-compiled ones; and keep WORKSPACE/repository rules from building host-only binaries, installing host-specific pip packages, symlinking to local tools, or mutating the host platform.

### 4. [Debugging Remote Cache Hits for Remote Execution](https://bazel.build/remote/cache-remote)
Names the exact troubleshooting loop: build with `--execution_log_compact_file=/tmp/exec.log` (compact format recommended — "produces much smaller files with very little runtime overhead"), then diff two logs with `//src/tools/execlog:parser --log_path=... --log_path=... --output_path=... --output_path=...` to see which actions received different action keys across two runs. `--noremote_accept_cached` forces a cache-miss re-run for isolation testing; `--build_event_text_file` recovers the canonical command line for comparison.

### 5. [Execution log parser tool](https://github.com/bazelbuild/bazel/blob/master/src/tools/execlog/README.md)
Three formats: `binary`, `json`, `compact`; a separate `//src/tools/execlog:converter` tool converts between them. `--restrict_to_runner="linux-sandbox"` filters the parsed output to one execution strategy.

### 6. Build without the Bytes (BwoB): [Bazel-7 blog post](https://blog.bazel.build/2023/10/06/bwob-in-bazel-7.html) + current [command-line reference](https://bazel.build/reference/command-line-reference)
`--remote_download_outputs` (`minimal`|`toplevel`|`all`) **defaults to `toplevel`** as of Bazel 7 (previously `all`). `--remote_download_minimal`/`--remote_download_toplevel`/`--remote_download_all` are aliases for the three values. `--remote_download_regex` (a Java regex, repeatable) forces specific paths to download regardless of the mode — useful for IDE-consumed files like `compile_commands.json` under an otherwise-minimal CI profile. Cache eviction during a build now fails with a distinct **exit code 39** (`--incompatible_remote_use_new_exit_code_for_lost_inputs`), retryable via `--experimental_remote_cache_eviction_retries` (default **5**, confirmed in cli-ref) or preventable by tuning `--experimental_remote_cache_ttl` (default **3h**) and `--experimental_remote_cache_lease_extension` (default **false**; periodically calls `FindMissingBlobs` to keep referenced blobs alive).

### 7. [Dynamic execution](https://bazel.build/remote/dynamic)
Runs local and remote branches of the same action in parallel and takes whichever finishes first. Explicit hard requirement: "it is not currently possible to use a cache-only remote system, as a cache miss would be considered a failed action" — a full RE backend (not just a cache) is mandatory. `--dynamic_local_strategy`/`--dynamic_remote_strategy` configure per-branch strategies (e.g. `worker,sandboxed` for local). If either branch fails, "the entire action fails — this is intentional, to catch local/remote discrepancies." The `standalone` local strategy takes the output lock on start, which can block the remote branch from ever "winning" the race.

### 8. [Sandboxing](https://bazel.build/docs/sandboxing)
Three strategies: `linux-sandbox` (namespaces, read-only filesystem outside the sandbox dir, PID-namespace process cleanup), `darwin-sandbox` (`sandbox-exec`), `processwrapper-sandbox` (portable, POSIX-only, builds a directory of symlinks and moves outputs back afterward — the fallback where OS sandboxing isn't available, e.g. Windows). `--sandbox_debug` preserves the sandbox dir for inspection but should not be left on (disk pressure). The doc frames sandboxing as validating what RBE will also see: "mimics the behavior of remote execution."

### 9. [Finding non-hermetic behavior in WORKSPACE rules](https://bazel.build/remote/workspace)
Methodology: `bazel clean --expunge`, then rerun with `--experimental_workspace_rules_log_file=[PATH]`, then parse with the (source-built) workspacelog parser, filtering with `--exclude_rule` for noise. Flags `repository_ctx.execute` (arbitrary host commands), `.download`/`.download_and_extract` without a checksum, `.file`/`.template` (host-dependent inputs), `.os` (host-specific queries), `.symlink` (absolute/host-conditional links), and `.which` (assumes consistent worker `PATH`) as the specific non-hermetic operations to hunt for.

### 10. [Configuring Bazel CI to test rules for remote execution](https://bazel.build/remote/ci) — **stale**
Still describes adding an `rbe_ubuntu1604` config block, a `bazel-toolchains` **WORKSPACE** dependency, and an `rbe_autoconfig` target — none of which exist in a Bzlmod-only (Bazel 9) world. This page has not been updated for the Bzlmod era and should be treated as historical-only.

### 11. [Vendor mode](https://bazel.build/external/vendor)
`--vendor_dir` (a path, relative-to-workspace or absolute) enables vendor mode; `bazel vendor --vendor_dir=... [--repo=@x | //target | (nothing, i.e. everything)]` populates it via a `bazel build --nobuild` analysis pass (so build flags affect what gets vendored). `VENDOR.bazel`'s `ignore()` excludes a repo from vendoring entirely; `pin()` freezes a repo's vendored contents "as if there is an `--override_repository` flag," meaning a pinned repo silently stops picking up upstream/registry updates on subsequent `bazel vendor` runs until unpinned. Registry metadata for offline module resolution lives under `<vendor_dir>/_registries`.

### 12. [Build Event Protocol](https://bazel.build/remote/bep) + BES flags (command-line reference)
`--bes_backend=[SCHEME://]HOST[:PORT]` (default: BES uploads disabled; scheme defaults to `grpcs`). `--bes_results_url` prints a viewer URL suffixed with the invocation ID. `--bes_lifecycle_events` (default **true**). BES shares TLS/auth flags with remote cache/execution (`--google_credentials`, `--tls_certificate`, etc.) — rotating one can silently break the other. `--remote_build_event_upload` (`all`|`minimal`, **default `minimal`**): under `minimal`, most local outputs referenced by BEP are *not* re-uploaded to the remote cache except test logs and timing profiles — a BES viewer's links to other artifacts can 404 against the cache.

### 13. Bazel release notes and blog posts: [7.0](https://www.buildbuddy.io/blog/whats-new-in-bazel-7-0/), [8.0 LTS](https://blog.bazel.build/2024/12/09/bazel-8-release.html), [9.0 LTS](https://blog.bazel.build/2026/01/20/bazel-9.html)
Bazel 7.0: credential helpers stabilized (`--experimental_credential_helper` → `--credential_helper`, plus `_cache_duration`/`_timeout` variants); `no-remote-exec` execution requirement folded into the action salt; `output_symlinks` added to `ActionResult`; HTTP 429 now auto-retried; remote-cache unavailability now auto-falls-back to local execution. Bazel 8.0 LTS: mostly ruleset modularization (`--incompatible_autoload_externally` goes empty-by-default, forcing explicit loads of Android/C++/Java/Proto/Shell rules — will be removed entirely in Bazel 10); nothing remote-specific in the announcement itself. Bazel 9.0 LTS: **WORKSPACE support fully removed** ("the code supporting WORKSPACE has been completely removed... Bzlmod is now the only way"); adds a local `--repo_contents_cache` (stable) and an experimental `--experimental_remote_repo_contents_cache`; Bazel "no longer limits the size of gRPC messages received from the remote executor or cache."

### 14. [GitHub discussion #27509](https://github.com/bazelbuild/bazel/discussions/27509) — remote repo-contents cache
The experimental remote repo-contents cache (Bazel 9) requires enabling `--experimental_remote_repo_contents_cache` plus any `--remote_cache`/`--remote_executor` (HTTP or gRPC both work), and a repository rule must return `repository_ctx.repo_metadata(reproducible = True)` to be eligible. Hard limitation: "only repo rules without any dependencies added at runtime (e.g. via `repository_ctx.watch` or `.getenv`) are supported" — directly gates whether rules_ocx's own module extension (or any repo rule) could ever use it.

### 15. [`repository_ctx.repo_metadata`/`--repo_contents_cache` reference](https://bazel.build/rules/lib/repo/cache) (via command-line reference)
`--repo_contents_cache` (a path) defaults to `{--repository_cache}/contents`; empty string disables it. Confirmed default and disable syntax directly from the current CLI reference.

### 16. Command-line reference — exact current defaults ([bazel.build/reference/command-line-reference](https://bazel.build/reference/command-line-reference), fetched and parsed in full)
Quoting exact defaults as currently published: `--remote_timeout` default **"60s"**; `--remote_retries` default **"5"**; `--remote_cache_compression` default **"false"** (zstd, only above `--experimental_remote_cache_compression_threshold` default **"100"** bytes); `--incompatible_strict_action_env` default **"true"**; `--remote_upload_local_results` default **"true"**; `--remote_accept_cached` default **"true"**; `--remote_verify_downloads` default **"true"**; `--incompatible_remote_local_fallback_for_remote_cache` default **"false"**; `--experimental_remote_discard_merkle_trees` default **"true"** (the flag that has replaced the brief's expected "`--experimental_remote_merkle_tree_cache`," which does not exist); `--remote_build_event_upload` default **"minimal"**; `--jobs` default **"auto"**, legal range 1–5000, "values above 2500 may cause memory issues"; `--remote_executor`/`--remote_cache` both default to scheme `grpcs` if unspecified; `--distdir` searches additional local archive dirs "before accessing the network."

### 17. Test execution: [Test encyclopedia](https://bazel.build/reference/test-encyclopedia)
`TEST_TMPDIR` is the only directory (with `TEST_UNDECLARED_OUTPUTS_DIR`) a test may write to; tests "must not attempt to remove, chmod, or alter" these dirs; `HOME` is recommended set to `$TEST_TMPDIR`. Sharding: `--test_sharding_strategy` + `shard_count` drive `TEST_TOTAL_SHARDS`/`TEST_SHARD_INDEX` (0-based); the runner must touch `TEST_SHARD_STATUS_FILE`'s mtime or "Bazel will fail the test" (not silently run the full suite per shard).

### 18. Stamping and volatile-status non-determinism: [GH #14341](https://github.com/bazelbuild/bazel/issues/14341), [GH #6786](https://github.com/bazelbuild/bazel/issues/6786), [HN thread](https://news.ycombinator.com/item?id=21390096)
Bazel maintains `stable-status.txt` and `volatile-status.txt` in `bazel-out`; the volatile file is deliberately excluded from action-key invalidation ("Bazel pretends that the volatile file never changes") specifically so `--stamp` doesn't defeat caching wholesale — but the *stable* file is not exempt, so a stable-status value that isn't actually stable (a rules_docker regression cited in the HN thread) reintroduces non-determinism. The HN thread's specific claim: "Bazel does not really hash any of the system stuff like system headers," i.e. host-toolchain drift outside declared inputs is invisible to the cache key by design.

### 19. [`buchgr/bazel-remote`](https://github.com/buchgr/bazel-remote) — the shape rules_ocx's cache uses
HTTP/1.1 + gRPC server implementing REAPI; CAS entries keyed by lowercase SHA-256, Action-Cache entries by an arbitrary 64-hex-char key; LRU eviction against a configured max size; optional S3/GCS/experimental-Azure backends. Explicit compatibility promise: "cache directory format changes are only allowed in major version upgrades" — a minor bump is not guaranteed to preserve on-disk data.

### 20. Buildbarn: [`bb-storage`](https://github.com/buildbarn/bb-storage), [`bb-remote-execution`](https://github.com/buildbarn/bb-remote-execution)
`bb-storage` alone is cache-only (forwards execution elsewhere); pluggable backends including a self-cleaning on-disk hash-table store (no GC needed). `bb-remote-execution` decomposes RE into `bb_scheduler` (queues actions), `bb_worker` (fetches inputs, orchestrates), and `bb_runner` (actually spawns the process) as **separate processes** specifically for privilege separation (worker can hardlink-cache input files without a build action overwriting them) and to dodge a Go runtime race ("a race condition that effectively prevents multi-threaded processes from writing executables to disk and spawning them"). Supports a pluggable runner protocol, e.g. swapping in QEMU user-mode emulation.

### 21. [`bazelbuild/bazel-buildfarm`](https://github.com/bazelbuild/bazel-buildfarm)
REAPI-compatible cache+execution system explicitly "compatible with the build systems Bazel, buck2, pants, and more." Uses Redis for scheduling state.

### 22. [`TraceMachina/nativelink`](https://github.com/TraceMachina/nativelink)
Rust-based RE/cache server ("enter the shipstorm"); README is thin on protocol/hermeticity specifics compared to Buildbarn/Buildfarm — worth a dedicated deeper read in a later research pass rather than treated as fully surveyed here.

### 23. BuildBuddy: [Remote Caching and Remote Execution Explained](https://www.buildbuddy.io/blog/bazels-remote-caching-and-remote-execution-explained/), [Bazel Remote Cache Debugging](https://www.buildbuddy.io/blog/bazel-remote-cache-debugging/), [What's New in Bazel 7.0](https://www.buildbuddy.io/blog/whats-new-in-bazel-7-0/)
Protocol support: cache over "HTTP(S), gRPC(S), or UNIX sockets," executor over "gRPC(S) or UNIX sockets." Debugging methodology via their "cache requests card": sort by size descending to find oversized uploads; search `bes-upload` to find files uploaded outside any action (timing profiles etc. that can block completion); sort by start time ascending — "the earliest action is most likely the root cause of the change from the previous build," i.e. trace cascading cache misses back to their origin action.

### 24. EngFlow: [The Many Caches of Bazel](https://blog.engflow.com/2024/05/13/the-many-caches-of-bazel/), [Bazel Invocation Analyzer](https://github.com/EngFlow/bazel_invocation_analyzer)
Names six caches: in-memory Skyframe cache (glob/action-graph results, gone on daemon restart), repository cache (`bazel info repository_cache`, no auto-pruning), output-tree/local action cache (`bazel-out/` + `$(bazel info output_base)/action_cache/`), remote cache (action-cache + CAS pair), local disk cache (`--disk_cache`, same shape as remote cache but on local disk), and remote execution (an extension of remote caching). The Invocation Analyzer is a datum-supplier → suggestion-provider pipeline that consumes a Bazel profile and emits speed suggestions; usable as a CLI or via analyzer.engflow.com.

### 25. [sluongng — Bazel Caching Explained, pt. 3: Repository Cache](https://sluongng.hashnode.dev/bazel-caching-explained-pt-3-repository-cache)
Repository cache is SHA-256-content-addressed, survives `bazel clean --expunge`, lives outside `output_base`/`install_base` so it's shared across workspaces. Two named footguns: (1) Bazel trusts a matching SHA-256 without re-validating source — pasting the wrong SHA-256 for a different archive version silently serves stale/wrong content from cache; (2) coverage is incomplete — only repo rules that call `rctx.download()` under the hood benefit (`http_archive` etc.); rules that shell out on their own (`go_repository`, `container_pull`) bypass the repository cache entirely.

### 26. [`Tinder/bazel-diff`](https://github.com/Tinder/bazel-diff) and [`bazel-contrib/target-determinator`](https://github.com/bazel-contrib/target-determinator)
`bazel-diff` computes exact affected-target sets between two git revisions using Java protobuf `parseDelimitedFrom` against Bazel's `streamed_proto` query output specifically to avoid the argv-length ceiling (cites [bazelbuild/bazel#8609](https://github.com/bazelbuild/bazel/issues/8609), the "Argument list too long" failure mode); its own README concedes it "is incorrect and will sometimes miss affected targets." `target-determinator` takes the opposite tradeoff — more correct, described elsewhere as "slow" enough to "hurt the time between pushing a hotfix and being able to release it" — and its own `--cache-dir` documentation explicitly warns: "home- and system- bazelrc files, environment variables, and host hardware/OS are not included in the results cache key. Use `--nocache_results` if necessary."

## Recent shifts seen in this corpus

- **Bazel 7.0 (Dec 2023), baseline for everything in this file**: BwoB default flips `all`→`toplevel`; credential helpers stabilize (`--experimental_credential_helper`→`--credential_helper`); exit code **39** introduced for cache-evicted "lost inputs"; `--experimental_remote_cache_eviction_retries`, `--experimental_remote_cache_ttl`, `--experimental_remote_cache_lease_extension` all new; Skymeld becomes default. Older guidance assuming `--remote_download_all` behavior, `--experimental_credential_helper`, or no-eviction-handling is invalidated.
- **Bazel 7.4**: `--experimental_disk_cache_gc_max_size`/`_max_age`/`_idle_delay` land, giving `--disk_cache` its first automated garbage collection (previously unbounded growth, per EngFlow's own "Many Caches" complaint).
- **Bazel 8.0 LTS (Dec 2024)**: `--incompatible_autoload_externally` goes empty-by-default — native rules (cc, java, proto, shell, android) must now be explicitly loaded from external modules; this indirectly affects any RBE toolchain/container setup that relied on autoloaded native rules being implicitly available. Vendor mode (`--vendor_dir`) matures as the Bzlmod-era offline mechanism.
- **Bazel 9.0 LTS (Jan 2026, inside the 18–24 month window)**: WORKSPACE support is **fully removed** — Bazel's own `remote/ci` doc, which still instructs readers to add a `bazel-toolchains` WORKSPACE dependency and an `rbe_autoconfig` target, is now flatly wrong for any Bazel-9 build. New local `--repo_contents_cache` (stable) and experimental `--experimental_remote_repo_contents_cache` (requires `reproducible=True`, excludes `.watch`/`.getenv`-dependent repo rules) ship — a brand-new gate that didn't exist 18 months ago and that couples directly to module-extension purity.
- **Flag rename/removal**: `--experimental_remote_merkle_tree_cache` (the name this research brief was given) does not exist in the current CLI reference at all — the live, related flag is `--experimental_remote_discard_merkle_trees` (default **true**, inverted intent: it discards rather than caches). Anyone writing a rule from memory or an old blog post around the brief's original flag name would cite a flag that no longer exists.
- **`--incompatible_strict_action_env` flip**: confirmed default **true** in the current reference — this used to be an explicit opt-in hardening step and is now the baseline; guidance written before this flip ("turn on strict_action_env for hermetic RBE") is now redundant, and guidance that never mentions it may be describing pre-flip behavior.

## Contested

- **BwoB aggressiveness**: Bazel's own default (`toplevel`) is a compromise; vendor guidance (BuildBuddy) still pushes CI-only runners toward `minimal` for maximum speed. No primary source argues `all` is still correct for anything except IDE/tooling integration or debugging — trending toward `minimal` for pure build/test CI and `toplevel`+`--remote_download_regex` for anything that also needs specific artifacts.
- **Dynamic execution's real applicability**: presented prominently in Bazel's own docs and EngFlow material as a performance lever, but its own spec-level requirement ("cache miss = failed action" under a cache-only remote) rules it out for a large fraction of real fleets — including the one Bazel repo in this program's own fleet, which has a cache but no executor. The gap between how often it's discussed and how often it's actually usable looks structural, not transitional.
- **`bazel-diff` vs `target-determinator`**: a live, acknowledged-by-both-projects correctness/speed tradeoff (bazel-diff admits false negatives; target-determinator is described elsewhere as too slow for hotfix latency). No clear winner is emerging in the ecosystem; both remain actively maintained, suggesting the tradeoff is inherent rather than one project catching up to the other.
- **Credential handling maturity vs. adoption**: the credential-helper spec has been stable since Bazel 7.0 and is the community-recommended pattern (EngFlow has its own blog post walking through setup), but real deployments — including the one this program is scoped around — still use bare static tokens in a gitignored `.bazelrc.user`. The spec side is settled; the adoption side is lagging.
- **Skymeld's remote-execution story**: widely repeated (BuildBuddy, EngFlow, Bazel's own 7.0 announcement materials) as "interleaves analysis and execution, up to 15% wall-time improvement," but this wave could not locate a primary bazel.build doc page describing the RE-specific mechanics in detail — the claim rests on blog-level sourcing rather than a spec or reference doc.
