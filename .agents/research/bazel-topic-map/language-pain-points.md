## Summary

- The single most-repeated JS/TS failure is a runtime `require`/`import` of a package never declared as a dependency; rules_js's own troubleshooting doc calls this "the most common error rules_js users encounter" and roots it in pnpm's strict (non-hoisting) `node_modules` layout, not in Bazel itself.
- rules_js re-uses `@pnpm/lifecycle` to run npm lifecycle hooks (`preinstall`/`install`/`postinstall`) as cacheable Bazel actions — a deliberate design choice, not a gap, as of the current docs.
- Practitioners report Bazel's per-sandbox `node_modules` reconstruction as expensive (disk and pre-build time) and occasionally buggy on symlink reconstruction, per a 2024-era first-person account (pow.rs).
- rules_js 2.0 (15 Aug 2024) fixed a real 1.x cost: linking a `js_library` directly into a consumer, instead of forcing an intermediate `npm_package` copy step that triggered premature TypeScript type-checking.
- Jest/Vitest module-resolution failures under `bazel test` are a long-running, still-open class of issue in rules_nodejs/rules_js — the fix is almost always a missing `data` dependency or a missing `public_hoist_packages` entry for plugin-pattern tools (eslint, prettier).
- rules_python's `pip.parse`/`uv` integration runs `uv pip compile` as a faster drop-in for `pip-compile`; as of the sources read, it does **not** consume an existing `uv.lock` — a maintainer-acknowledged gap, not a "coming soon."
- rules_python's `--bootstrap_impl=script` (added 1.5.0, 2025-06-11) is forced on Windows and changes `sys.path` ordering and `PYTHONSAFEPATH` inheritance versus the older `system_python` bootstrap — a version-gated behavior change, not a universal default.
- Precompiling (`--precompile`, `pyc_collection`) shipped in rules_python 0.33.0 (2024-06-12) but had a real regression — per-binary opt-in "doesn't function correctly" — tracked and open as of the corpus read.
- crate_universe's repin workflow (`CARGO_BAZEL_REPIN=1 bazel sync --only=crate_index`) is the one command every Rust-on-Bazel source repeats; CI drift is caught by re-running it and diffing `Cargo.Bazel.lock` (or the bzlmod lockfile), never by trusting a stale checked-in file.
- Proc-macro crates must build for the **host**, not the target, during cross-compilation — a design gap tracked in rules_rust since issue #205 and still not fully resolved by a monolithic `rust_toolchain` that bundles clippy/cargo/rustc/stdlib/rustfmt as one unit.
- `cargo_build_script` is where Rust-under-Bazel hermeticity actually breaks: network access, `pkg-config` host lookups, and `OUT_DIR` env leakage are the concrete failure modes, fixed with `crate.annotation(build_script_env = {...})`.
- Two independent 2023-2024 practitioner writeups (Tweag, mmapped.blog) converge on the same end-state: keep `Cargo.toml` as the dependency source of truth via `all_crate_deps()`/`aliases()`, run CI exclusively on Bazel, and keep Cargo only for IDE/quick-check convenience — not a temporary migration state but a stable dual-tool equilibrium.
- rust-analyzer support generated from Bazel (`gen_rust_project`) is reported to work in small prototypes but "choke" on a real codebase — a scale problem, not a correctness one, per mmapped.blog.
- Bazel's default, autodetected C/C++ toolchain is non-hermetic by construction; Pigweed's own account (SEED 0113, `rules_cc` 0.0.10) names four concrete problems — non-hermetic behavior, gcc/binutils default instead of clang/llvm, CI-vs-local mismatches, and flags only settable via `.bazelrc` — as the reason they built a modular toolchain API that was later upstreamed.
- `layering_check` works by generating Clang module maps (`.cppmap`) from `hdrs`/`srcs`/`deps` and compiling with `-fmodules-strict-decluse` and `-Wprivate-header`; its biggest adoption blocker is that most systems don't ship Clang module maps for the C/C++ standard library, requiring Bazel's own `generate_system_module_map.sh` workaround.
- `rules_foreign_cc` wrapping of CMake/Autotools projects is explicitly flagged by its own issue tracker as slow on Windows (`configure_make`, issue #720) and "a nightmare" for deep dependency trees, because every input/output must be declared explicitly where the foreign build system infers it.
- C++20 modules have **no native Bazel support** as of the 2025 sources read; interim rulesets (e.g. `rules_ll`) exist, and an upstream PR (#19940) is in progress but unmerged.
- Google's own BazelCon 2024 statement was a stated intent to "remove the concept of a default C++ toolchain" entirely, in favor of always-explicit hermetic toolchain registration — a roadmap item every C++-under-Bazel guide should treat as coming, not hypothetical.
- Bazel action non-determinism has a short, recurring cause list across all four languages: embedded timestamps, PIDs/UIDs, hash-table iteration order leaking into output file ordering, and hidden system-toolchain file dependencies (e.g. `crtbegin.o`) — independent of which language rule is running.
- Target-determination tooling for CI is split between two real tradeoffs: `bazel-diff` (Tinder) is fast but "incorrect" — it can miss affected targets — while `target-determinator` is more correct but too slow for a hotfix-to-release path.
- Vertexwahn's 2024 opinion piece on C++/Bazel blockers ranks IDE integration (esp. Visual Studio) and missing C++20 module support above the learning curve itself — a signal that tooling maturity, not conceptual difficulty, is what C++ teams cite first.

## Survey

### TypeScript / JavaScript

1. **rules_js troubleshooting guide** — the project's own catalogue of failure modes: "module not found" errors from an undeclared runtime `require`, split into three remedies depending on whether the missing package is first-party-fixable, a genuine upstream bug (cross-referenced against Yarn's shared [extensions database](https://github.com/yarnpkg/berry/blob/master/packages/yarnpkg-extensions/sources/index.ts)), or a "plugin pattern" tool (eslint, prettier) that needs `public_hoist_packages` in `npm_translate_lock`. Also documents ugly Bazel-sandbox stack traces and a Slack-sourced `Error.prepareStackTrace` fix. [rules_js/docs/troubleshooting.md](https://github.com/aspect-build/rules_js/blob/main/docs/troubleshooting.md)
2. **rules_ts troubleshooting guide** — names the exact overlapping-`srcs` failure mode: two `ts_project` targets sharing a `.ts` file produce conflicting `.js` outputs when built together, and a build-order-dependent result when built separately; the diagnosis path is `bazel aquery //path/to:my_ts_project` to see what tsc actually received. [rules_ts/docs/troubleshooting.md](https://github.com/aspect-build/rules_ts/blob/main/docs/troubleshooting.md)
3. **rules_js pnpm docs** — documents that lifecycle hooks (`preinstall`, `install`, `postinstall`, `prepare`) are executed via `@pnpm/lifecycle` as Bazel actions, cacheable and remote-cacheable, with per-package selective execution (e.g. only `prepare` for one package, only `postinstall` for another) — this is architecture, not a workaround. [rules_js/docs/pnpm.md](https://github.com/aspect-build/rules_js/blob/main/docs/pnpm.md)
4. **Aspect: "Upgrade to rules_js 2.0"** (15 Aug 2024) — the 1.x pain it fixes: `js_library` targets required an intermediate `npm_package` copy for monorepo linking, which both copied files unnecessarily and triggered TypeScript type-checking too early; 2.0 allows direct `js_library` linking. Also: `js_image_layer` now emits 5 layers so app code alone sits in the top layer (faster `docker push`), and `npm_translate_lock` itself runs faster from reduced depset sizes. [Aspect blog: rules_js 2.0](https://aspect.build/blog/rulesjs-2)
5. **"Bazel is incompatible with JavaScript"** (pow.rs) — a first-person practitioner account: Bazel duplicates `node_modules` per-sandbox (reported ~4× disk overhead), has multi-year-old bugs in symlink reconstruction that "incorrectly reconstruct node_modules" and break Node's resolution, and its "cannot add files to `src/`" sandbox rule is incompatible with Next.js/Astro/SvelteKit codegen and with running a formatter against source. Cites Vercel's 2021 internal evaluation ("too many breaking changes / hacks required") as the reason Vercel built Turborepo instead. Concludes incremental adoption doesn't pay off until most of the dependency chain is Bazelified. [pow.rs: Bazel is incompatible with JavaScript](https://pow.rs/blog/bazel-is-incompatible-with-javascript/)
6. **rules_nodejs / rules_js Jest & Vitest module-resolution issues** — a cluster of long-running GitHub issues ([#1418](https://github.com/bazel-contrib/rules_nodejs/issues/1418) "Jest modules resolution", [#3136](https://github.com/bazel-contrib/rules_nodejs/issues/3136) resolving imports in a React/TS project, [#2325](https://github.com/bazel-contrib/rules_nodejs/issues/2325) tests failing under `bazel test` but passing under `bazel run`) that converge on the same root cause: the sandboxed runfiles tree's symlinked `node_modules` doesn't match what the test runner's module resolver expects unless every runtime dependency is declared as `data`.
7. **Next.js "standalone" output under Bazel** — [bazelbuild/examples#382](https://github.com/bazelbuild/examples/issues/382) requests an example because `output: "standalone"` fails with "Failed to resolve relative path standalone/node_modules" — Next's own bundler assumptions about a real (non-symlinked) `node_modules` collide with Bazel's runfiles model.

### Python

8. **rules_python CHANGELOG** — the authoritative, dated record of every behavior change cited below: precompiling added in [0.33.0 (2024-06-12)](https://github.com/bazel-contrib/rules_python/blob/main/CHANGELOG.md); `PYTHONSAFEPATH` made to inherit from the calling environment (requires `--bootstrap_impl=script`) in [0.35.0 (2024-08-15)](https://github.com/bazel-contrib/rules_python/blob/main/CHANGELOG.md); `--bootstrap_impl=system_python` forced on Windows in [1.5.0 (2025-06-11)](https://github.com/bazel-contrib/rules_python/blob/main/CHANGELOG.md); venv-based binaries made the default (`system_python` bootstrap) in [2.0.0 (2026-04-09)](https://github.com/bazel-contrib/rules_python/blob/main/CHANGELOG.md); the `uv pip compile` sandbox execution bug fixed in [2.1.0 (2026-06-17)](https://github.com/bazel-contrib/rules_python/blob/main/CHANGELOG.md); as of that same changelog, `pip.parse(uv_lock=...)` still does not expose uv workspace/root members, and there is **no `uv.lock` consumption path** — a maintainer-acknowledged scope boundary, not a bug.
9. **`pip_parse` failing under a hermetic interpreter** — [rules_python#1463](https://github.com/bazel-contrib/rules_python/issues/1463): `pip.parse` defaults to Bazel's hermetic host-platform Python, and mismatches with that interpreter (rather than the developer's system Python) are the reported failure; the documented escape hatch is `pip.parse.python_interpreter` / `pip.parse.python_interpreter_target`.
10. **Aspect: "Python toolchains in rules_python"** — vendor explainer of how the hermetic toolchain is selected and customized per-platform; used here to corroborate the interpreter-selection mechanics behind issue #1463. [blog.aspect.build/python-toolchains](https://blog.aspect.build/python-toolchains)
11. **pytest-bazel** — the practitioner-built wrapper that exists specifically because Bazel requires explicit test targets while pytest expects auto-discovery; supports pytest 7 and 8, `pytest-shard`-based sharding, and `bazel test --test_filter`, and is designed to slot under `py_console_script_binary` in place of the older `rules_python_pytest` macro. [pytest-bazel docs](https://pytest-bazel.readthedocs.io/latest/)
12. **"Experimentations on Bazel: Python (3), linter & pytest"** (dev.to, davidb31) — a hands-on account of wiring pytest and a linter into `rules_python`, read as corroboration that the pytest-under-Bazel integration path is nontrivial enough to blog about even for a small project. [dev.to/davidb31](https://dev.to/davidb31/experimentations-on-bazel-python-3-linter-pytest-49oh)
13. **rules_python Gazelle plugin docs** — generates `py_library`/`py_binary`/`py_test` targets by walking up the filesystem from each Python file looking for `gazelle_python.yaml`; that manifest file must exist (even empty) or generation silently fails to resolve third-party import names. [rules_python Gazelle plugin](https://rules-python.readthedocs.io/en/1.4.2/gazelle.html)
14. **Precompile per-binary opt-in regression** — [rules_python#2212](https://github.com/bazel-contrib/rules_python/issues/2212): the `pyc_collection` attribute's per-binary opt-in "doesn't function correctly," despite precompiling itself having shipped two years earlier in 0.33.0 — a live example of a "built-in since version X" feature still having open correctness gaps in the same era this research covers.

### Rust

15. **"Scaling Rust builds with Bazel"** (mmapped.blog) — argues the Cargo-side problems Bazel is chosen to fix: Cargo can't express multi-step build orchestration (build a sandboxed wasm binary, post-process, then test it), its mtime-based incremental cache is unreliable across branch switches, and `build.rs`'s "rerun-if-changed" mechanism can't track transitive resource dependencies, forcing over-broad rebuilds. On the Bazel side: sandboxing "makes it much safer to cache," but the author reports no Bazel equivalent of `cargo check`, that rust-analyzer support "worked perfectly in the prototype but choked on our code base," and no `cargo-expand`/`cargo publish` equivalents — yet concludes the migration was worth it, keeping Cargo files only for IDE/dev convenience while CI runs exclusively on Bazel. [mmapped.blog/posts/17-scaling-rust-builds-with-bazel](https://mmapped.blog/posts/17-scaling-rust-builds-with-bazel)
16. **Tweag: "Building a Rust workspace with Bazel"** (27 Jul 2023) — concrete crate_universe mechanics: repin with `CARGO_BAZEL_REPIN=1 bazel sync --only=crate_index`; use `all_crate_deps()`/`aliases()` so Cargo metadata stays the single dependency source of truth (Cargo files, not BUILD files, are authoritative); `crate_universe` **ignores path dependencies**, requiring hand-written internal target references (e.g. `"//crates/grep"`); `cargo_build_script` handles `build.rs`, but system library lookups via `pkg-config` break hermeticity and are patched with `crate.annotation(build_script_env = {"PCRE2_SYS_STATIC": "1"})`; integration tests need explicit `data` and `crate_root` to find test fixtures. [tweag.io/blog/2023-07-27](https://www.tweag.io/blog/2023-07-27-building-rust-workspace-with-bazel/)
17. **"Using Bazel to build a new Rust project"** (blog.fahhem.com, Sep 2024) — a from-scratch walkthrough on rules_rust 0.51.0 / Rust 1.81.0: an empty `Cargo.toml` "won't work as-is" for `crates_repository()`, which needs `Cargo.toml` + `Cargo.lock` + `Cargo.bazel-lock.json` all populated before the first `CARGO_BAZEL_REPIN=true bazel sync --only=crate_index`; and — surprisingly — `rules_rust` "currently requires a C++ toolchain" even for a pure-Rust build, worked around with `apt install g++`. [blog.fahhem.com/2024/09](https://blog.fahhem.com/2024/09/bazel-build-new-rust-project/)
18. **rules_rust rust-analyzer integration** — official docs: a one-shot installer configures rust-analyzer, the proc-macro server, and rustfmt to all come from the Bazel toolchain (not system Rust); the `--clippy` toggle is per-developer, stored in `user_config.json`, so it doesn't leak into the checked-in config. [rules_rust: rust_analyzer](https://bazelbuild.github.io/rules_rust/rust_analyzer.html)
19. **Proc-macro host/target confusion** — [rules_rust#205](https://github.com/bazelbuild/rules_rust/issues/205): proc-macro crates need to run on the *host* (they execute at compile time) but were being built for the *target* platform, breaking cross-compilation entirely when the target has no std. Root architecture problem named in [discussion #815](https://github.com/bazelbuild/rules_rust/discussions/815): a single monolithic `ToolchainInfo` bundles rustc, cargo, clippy, rustfmt and the stdlib together, which prevents Bazel from resolving host vs. target components independently — recent work adds `extra_exec_rustc_flags_triples` as a partial mitigation.
20. **Clippy aspect flakiness** — [rules_rust#2510](https://github.com/bazelbuild/rules_rust/issues/2510): the clippy aspect "sometimes fails when run on an unsandboxed test" with `rustc_output_diagnostics` enabled — cited as evidence that clippy-as-aspect (`bazel build --aspects=@rules_rust//rust:defs.bzl%rust_clippy_aspect --output_groups=clippy_checks //hello_lib:all`) is not yet fully sandbox-stable.
21. **crate_universe vs. Cargo friction** — [rules_rust#2879](https://github.com/bazelbuild/rules_rust/discussions/2879): open discussion of mismatches between what `cargo-bazel` resolves and what plain `cargo` resolves for the same `Cargo.lock`, i.e. the "single source of truth" claim in source #16 above still has edge cases in practice as of this discussion.

### C++

22. **Pigweed blog #6: "Shaping a better future for Bazel C/C++ toolchains"** (11 Dec 2024) — names four concrete problems with Bazel's autodetected default toolchain: it is "not hermetic" and its generated behavior is "very unintuitive to inspect and debug"; it silently prefers gcc/binutils over clang/llvm; CI and local builds diverge despite identical inputs; and every flag must be set via the command line or `.bazelrc`, with no structured API. Traces the fix from Armando Montanez's 2023 `pw_cc_toolchain` rule, through Nathaniel Brough's `modular_cc_toolchains` concept (SEED 0113), to Matt Stark's type-safe upstreaming into `rules_cc` 0.0.10. [pigweed.dev/blog/06-better-cpp-toolchains](https://pigweed.dev/blog/06-better-cpp-toolchains.html)
23. **MaskRay: "Layering check with Clang"** — mechanics: Bazel converts `hdrs`→textual headers, `srcs`→private textual headers, `deps`→module "use" declarations into generated `.cppmap` files, then compiles with `-fmodules-strict-decluse` (catches an included header from a module you don't `deps`-declare) and `-Wprivate-header` (catches including another target's private header). Names the real adoption blocker: most systems ship no Clang module maps for the C/C++ standard library, so Bazel supplies its own via `tools/cpp/generate_system_module_map.sh`; recommends running Include-What-You-Use first since the checker can't find transitive-only violations on its own. [maskray.me/blog/2022-09-25](https://maskray.me/blog/2022-09-25-layering-check-with-clang)
24. **Vertexwahn: "What blocks C++ developers from using Bazel (in 2024)?"** — an informal, self-described "gut feeling" ranking (not a survey) that still orders concrete blockers: missing IDE integration (particularly Visual Studio) ranks above missing C++20 modules support, which ranks above missing turnkey support for common libraries (OpenCV named specifically), `rules_cc` quirks, fear Google abandons Bazel, and the learning curve itself — learning curve is explicitly *not* the top blocker in this account. [medium.com/@Vertexwahn](https://medium.com/@Vertexwahn/what-blocks-c-developers-from-using-bazel-in-2024-4774fbc4d356)
25. **hedron_compile_commands (bazel-compile-commands-extractor)** — generates `compile_commands.json` via `aquery` (asking Bazel directly for the exact commands it would run) rather than doing a full build, enabling clangd/clang-tidy autocomplete and navigation across editors; defaults to covering every buildable target if none is named. [hedronvision/bazel-compile-commands-extractor](https://github.com/hedronvision/bazel-compile-commands-extractor)
26. **rules_foreign_cc pain points** — [#1221](https://github.com/bazel-contrib/rules_foreign_cc/issues/1221) tracks that `layering_check` cannot simply be turned on for foreign-build (CMake/Autotools) targets; [#720](https://github.com/bazelbuild/rules_foreign_cc/issues/720) reports specifically slow `configure_make` builds on Windows; community guidance elsewhere in the tracker states plainly that deep third-party dependency trees are "a nightmare to compile in bazel" because every input a foreign build system would auto-discover must instead be hand-declared.
27. **C++20 modules status** — as of the 2025 sources found, there is no native Bazel support; [bazelbuild/bazel#19940](https://github.com/bazelbuild/bazel/pull/19940) is an open, unmerged PR, discussed in [#19939](https://github.com/bazelbuild/bazel/discussions/19939); interim third-party rulesets (e.g. `rules_ll`) fill the gap for teams that need modules now.
28. **Cross-compilation and Windows quirks** — [bazelbuild/bazel#19208](https://github.com/bazelbuild/bazel/issues/19208): Linux→Windows C++ cross-compilation must handle MSVC's native path style (`C:/VS/VC/Tools/...`) correctly through the platforms/toolchain-resolution machinery, and reports exist of `--platforms` resolving to the wrong architecture (x64 output on an ARM64 Windows host) when constraints are incomplete; the general migration note is that a Starlark transition setting legacy flags (`--cpu`, `--crosstool_top`) is invisible to rules that read `--platforms`, so migrating to platforms requires migrating the transitions too.
29. **ASAN/TSAN/MSAN config pattern** — the community-standard `.bazelrc` shape pairs `--copt -fsanitize=address` (or tsan/msan) with `--copt -fno-omit-frame-pointer`, `--copt -O1`, `--linkopt -fsanitize=address`, and `--strip=never`, invoked as `--config=asan`; Bazel's own fuzzing blog post demonstrates the same pattern for libFuzzer (`--config=asan-libfuzzer`).

### Cross-cutting

30. **jmmv.dev: "Bazel and action (non-)determinism"** (Jul 2025) — a concrete taxonomy independent of any one language: embedded timestamps (`date >$@`-style tools), PIDs/UIDs/GIDs baked into output, unsorted hash-table iteration leaking into emitted lists, network access during a build, hidden system-toolchain file deps (`/usr/lib/gcc/.../crtbegin.o`), local/remote execution divergence, foreign-build-system nesting (i.e. `rules_foreign_cc`), and reads from `/dev/random`. Mitigations: `--nosandbox_default_allow_network` off by default, hermetic toolchains, `--action_env`/`--host_action_env`/`--strict_action_env` for environment sanitation, `--execution_log_json_file` for CI-vs-local diffing, and pushing genuinely non-deterministic actions to remote execution. [jmmv.dev/2025/07/bazel-action-determinism](https://jmmv.dev/2025/07/bazel-action-determinism.html)
31. **BazelCon 2024 recap** (Julio Merino / blogsystem5) — Bazel 8 ships first-class symbolic macros with "finalizer" attributes; `WORKSPACE` is disabled by default in 8 and gone in 9; execution logs reported "100x smaller… with only 3% runtime overhead"; Google stated an intent to "remove the concept of a default C++ toolchain" outright; AirBnB reported roughly 2× slower builds without remote persistent workers; Canva reported ~500k action dedups/day. No language-specific (Rust/Python/JS) sessions are mentioned in the recap itself. [blogsystem5.substack.com/p/bazelcon-2024-recap](https://blogsystem5.substack.com/p/bazelcon-2024-recap)
32. **bazel-diff** (Tinder) — computes the affected-target set between two git revisions from content hashes, offered as a long-running HTTP service to avoid recomputing per-CI-run; documented correctness caveat found elsewhere in the corpus: it can under-report (miss affected targets), the opposite failure mode from `target-determinator`, which is more correct but slower. [github.com/Tinder/bazel-diff](https://github.com/Tinder/bazel-diff)
33. **target-determinator** — the more-correct, slower alternative to bazel-diff for the same CI target-selection problem; named directly as the tradeoff partner in community discussion. [bazel-contrib/target-determinator](https://github.com/bazel-contrib/target-determinator)

## Recent shifts seen in this corpus

- **rules_js 2.0** (15 Aug 2024): direct `js_library`→consumer linking replaces the 1.x `npm_package`-copy requirement; `js_image_layer` now splits into 5 layers. Guidance written against rules_js 1.x that assumes an `npm_package` hop is stale. [Aspect blog](https://aspect.build/blog/rulesjs-2)
- **rules_python precompiling**: added 0.33.0 (2024-06-12); per-binary opt-in (`pyc_collection`) still had an open correctness bug as of [#2212](https://github.com/bazel-contrib/rules_python/issues/2212) — treat "precompiling shipped" and "precompiling opt-in works per-target" as two separate claims.
- **rules_python bootstrap**: `PYTHONSAFEPATH` inheritance added 0.35.0 (2024-08-15, requires `--bootstrap_impl=script`); Windows forced onto `system_python` bootstrap in 1.5.0 (2025-06-11); venv-based (`system_python`) binaries made the *default* bootstrap in 2.0.0 (2026-04-09). Any guidance written before 2.0.0 that assumes `script` bootstrap is default is now wrong.
- **rules_python × uv**: as of 2.1.0 (2026-06-17) `uv pip compile` runs correctly in the sandbox, but `pip.parse(uv_lock=...)` still doesn't expose uv workspace/root members and there is no `uv.lock`-consuming path — the "uv support" story is narrower than the phrase suggests, and was narrower still before 2.1.0.
- **Bazel 8** (per BazelCon 2024 recap and the frame): symbolic macros are first-class; `WORKSPACE` is off by default in 8 and removed in 9 — any per-language toolchain-registration example still showing `WORKSPACE` snippets needs a Bzlmod equivalent dated after this shift.
- **C++ toolchain API**: Pigweed's modular toolchain work (SEED 0113) landed upstream in `rules_cc` 0.0.10 (dated Pigweed blog entry, 11 Dec 2024) — pre-0.0.10 "write your own `pw_cc_toolchain`-style toolchain" advice is now supersedable by the upstream API.
- **rules_rust cross-compilation**: `extra_exec_rustc_flags_triples` is a recent (undated in the sources read, but post-#205) partial fix for host/target proc-macro separation — the underlying monolithic-toolchain architecture problem (discussion #815) is not yet resolved.

## Contested

- **Is incremental/partial Bazel adoption for a JS monorepo worth it?** pow.rs argues caching doesn't pay off until most of the dependency chain is Bazelified (a real "0 to 100%" cliff); Aspect's own migration guides (and Tweag's/mmapped.blog's Rust equivalents) describe successful staged migrations. Trend: vendor-authored guides describe staged success; independent practitioner accounts describe an all-or-nothing cliff — worth flagging as unresolved rather than picking a side.
- **Is `rules_rust`'s "keep Cargo as source of truth via `all_crate_deps()`" pattern stable or transitional?** Tweag (2023) and mmapped.blog (undated but recent) both land on it as a stable end-state; rules_rust's own discussion #2879 shows unresolved edge cases where `cargo-bazel`'s resolution and plain `cargo`'s resolution disagree for the same lockfile — trending toward "stable in practice, not airtight."
- **bazel-diff vs. target-determinator**: community consensus (per the search corpus) frames this as a hard correctness/speed tradeoff, not a solved problem — no single source claims either is strictly better; trend is toward running the fast-but-approximate tool for most CI and the slow-but-correct tool as a periodic or pre-release gate.
- **How hard is C++-on-Bazel, really?** Vertexwahn's informal ranking puts IDE integration and missing C++20 modules above the learning curve; Pigweed's and jmmv.dev's accounts instead emphasize hermeticity/determinism mechanics as the hard part. Both are single-author, non-statistical opinions — treat "what's hardest" as genuinely unsettled in this corpus, not resolved.
