## Summary

- The Nix reference manual (2.35) documents `nix flake` as still **experimental**: every `nix3-flake*` page carries a live warning that "this program is experimental and its interface is subject to change," measured 2026-09-27 against [nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake).
- RFC [0049 "Flakes"](https://github.com/NixOS/rfcs/pull/49) was never accepted — `gh api repos/NixOS/rfcs/pulls/49` reports `state=closed`, `merged=False` — while the implementation shipped anyway; there is no formally ratified flake spec, only the manual's description of current behavior.
- `nix flake check` has an exact, enumerable evaluation contract per output attribute (derivations for `checks.<system>.<name>`, `devShells.<system>.default/<name>`, `packages.<system>.default/<name>`, `nixosConfigurations.<name>.config.system.build.toplevel`; app-definitions for `apps.*`; template-definitions for `templates.*`; overlays for `overlays.*`; NixOS modules for `nixosModules.*`; bundlers for `bundlers.*`) and silently renames-with-warning seven pre-flake-convention attribute names (`defaultPackage.<system>` → `packages.<system>.default`, `devShell.<system>` → `devShells.<system>.default`, `overlay` → `overlays.default`, `nixosModule` → `nixosModules.default`, and three more).
- `flake.lock` is JSON schema **version 7** with `root`, `nodes.<label>.{inputs, original, locked, flake}`; `locked`/`original` are omitted only for the root node, and `narHash` (not `rev`) is what makes a locked input binary-cache-substitutable.
- A flake's own `self`-attributes (`inputs.self.submodules = true;`, `inputs.self.lfs = true;`) let a flake declare that Git submodules or Git LFS content must be fetched when it is used as an input, without the consumer specifying `?submodules=1` — a feature the NixOS wiki dates to Nix **2.27**.
- "A local directory within a flake is always copied into the Nix store completely unless it is a Git repository" (nix.dev), and when it is a Git repository, only files added to the index are visible at all — this is a silent-drop, not an error, and is the textbook cause of "my new file isn't in the build."
- `nixConfig` in `flake.nix` may only auto-apply five settings without `accept-flake-config=true` (default `false`): `bash-prompt`, `bash-prompt-prefix`, `bash-prompt-suffix`, `flake-registry`, `commit-lock-file-summary` — anything else (substituters, trusted keys) is a prompt, not silent trust.
- `allow-import-from-derivation` **defaults to `true`** in Nix 2.35 (measured via `nix config show` against the pinned toolchain) — the common assumption that IFD is opt-in/disabled by default is wrong for a stock install; `pure-eval` (which forbids IFD unconditionally) defaults to `false`.
- `access-tokens` in `nix.conf` is a plain-text, space-separated `host=token` string with no `flake.nix`-side equivalent; a token must never appear inside a committed flake, only in local/CI `nix.conf` or `NIX_CONFIG`.
- Nixpkgs' `pkgs/by-name` convention (RFC [0140](https://github.com/NixOS/rfcs/pull/140), merged) replaced ad hoc placement in `all-packages.nix` for new packages; RFC [0166](https://github.com/NixOS/rfcs/pull/166) (merged) made `nixfmt` (not the older `nixpkgs-fmt`) the canonical Nix formatter, and RFC [0136](https://github.com/NixOS/rfcs/pull/136) (merged, 2022) is the actual accepted plan to stabilize the new CLI and flakes incrementally — distinct from, and not a substitute for, RFC 0049.
- `lib.fileset` (Nixpkgs' current recommendation for source filtering) never copies a traced path into the store just by pretty-printing it; only `toSource` does, and its set-algebra functions (`difference`, `unions`, `intersection`, `fileFilter`, `gitTracked`, `maybeMissing`) are the mechanism nix.dev now teaches in place of `builtins.path`/`cleanSourceWith` filter callbacks.
- The Nixpkgs manual enumerates the `stdenv` build phases in a fixed order (unpack → patch → configure → build → check → install → fixup → installCheck → distribution) and documents `meta.license`, `meta.mainProgram`, `meta.platforms`, `meta.badPlatforms`, `passthru.tests` and `passthru.updateScript` as the attributes that downstream tooling (`nix run`, `nix flake check`, `nix-update`) actually consumes.
- A **builtin fetcher** (`builtins.fetchTree`) runs at evaluation time and is cached outside the store's build graph; a **Nixpkgs fetcher** (`fetchurl`, `fetchFromGitHub`, …) is a fixed-output derivation that runs at build time and can be substituted from a binary cache — conflating the two is why "it re-downloaded on every eval" bug reports happen.
- The NixOS module system's option types include newer additions beyond the classic `types.str`/`types.bool`/`types.enum`: `types.externalPath` and `types.pathWith { inStore; absolute; }` exist specifically to validate that a path (e.g. a secret) is *not* store-coerced, and `types.raw`/`types.optionType`/`types.optionDeclaration` are explicitly flagged in the manual as metaprogramming escape hatches to avoid by default.
- flake-parts' core module (`flake-parts.lib.mkFlake`) mirrors the flake schema 1:1 through `perSystem.*` (packages, apps, checks, devShells, formatter, legacyPackages) plus top-level `flake.*`, `systems`, `debug`, `perInput` and `transposition` options — it deliberately does *not* try to be an opinionated framework beyond that mirror.
- nix.dev's own "Flakes" concept page — not a blog, the official docs — states flakes are "an experimental extension format with outstanding issues," recommends non-flake `npins`-based dependency management as a first-class alternative, and documents that Determinate Systems and Lix have each unilaterally forked flakes' stability/feature story in different directions.
- Since NixOS **26.05**, a `system.nix` entrypoint lets one or more NixOS configurations be loaded without a flake at all, positioned by nix.dev as an alternative on equal footing with flakes for that use case.
- `DeterminateSystems/flake-checker` (measured v0.2.15 via the pinned toolchain) enforces exactly three lock-file health checks by default (`--check-outdated`, `--check-owner`, `--check-supported`) against a small enumerated list of "supported" Nixpkgs branches, plus an optional CEL `--condition` expression for custom policy.
- Determinate Nix (Determinate Systems' downstream distribution) declares flakes "stable" unilaterally and adds features absent from upstream CppNix 2.35 — lazy trees, parallel evaluation, WebAssembly-in-Nix, a native Linux builder for macOS — while Lix "consolidated" its own de-facto flake feature set; a flake tested only on one implementation is not proven to behave identically on the others.

## Survey

1. **Nix reference manual — language, purity and IFD.** [Nix language overview](https://nix.dev/manual/nix/2.35/language/index) frames the language as domain-specific, declarative, pure, functional, lazy and dynamically typed, and links out to [string context](https://nix.dev/manual/nix/2.35/language/string-context) and [types](https://nix.dev/manual/nix/2.35/language/types). [Import From Derivation](https://nix.dev/manual/nix/2.35/language/import-from-derivation) documents IFD as importing the *contents* of a derivation's build output back into the evaluator, which is why it can force a build during evaluation. The [experimental features](https://nix.dev/manual/nix/2.35/development/experimental-features) page lists the full current set for Nix 2.35: `auto-allocate-uids`, `blake3-hashes`, `ca-derivations`, `cgroups`, `configurable-impure-env`, `daemon-trust-override`, `dynamic-derivations`, `external-builders`, `fetch-closure`, `fetch-tree`, **`flakes`**, `git-hashing`, `impure-derivations`, `local-overlay-store`, `mounted-ssh-store`, **`nix-command`**, `parse-toml-timestamps`, `pipe-operators`, `read-only-local-store`, `recursive-nix`, `verified-fetches` — `flakes` itself just says "See the manual entry for `nix flake`" and points to the [flakes tracking issue](https://github.com/NixOS/nix/milestone/27), i.e. the manual does not claim flakes are feature-complete.

2. **Nix reference manual — the `nix flake` command family.** [`nix flake`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake) is the single page that defines the flake reference syntax (attrset vs URL-like vs path-like), the full list of flake reference `type`s (`indirect`, `path`, `git`, `mercurial`, `tarball`, `file`, `github`, `gitlab`, `sourcehut`), the flake format (`description`, `inputs`, `outputs`, `nixConfig`), input attributes (`follows`, `flake = false`, transitive input override), self-attributes (`submodules`, `lfs`), and the full `flake.lock` schema (`version: 7`, `root`, `nodes`, each node's `inputs`/`original`/`locked`/`flake`). [`nix flake check`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-check) enumerates every output attribute Nix type-checks and every renamed-with-warning legacy attribute, plus `--all-systems` and `--no-build`. [`nix flake update`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-update) updates all inputs by default (or named ones as positional args) and rewrites the whole lock file, versus [`nix flake lock`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-lock) which only ever adds *missing* entries and never touches an existing pin. [`nix flake show`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-show), [`nix flake archive`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-archive), [`nix flake init`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-init) (templates), and [`nix registry`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-registry) round out the family. All of these pages, measured 2026-09-27, still carry the "experimental" banner.

3. **Nix reference manual — settings reference.** [`command-ref/conf-file`](https://nix.dev/manual/nix/2.35/command-ref/conf-file) defines, among 2190 lines of settings: `accept-flake-config` (default `false`) — "whether to accept Nix configuration settings from a flake without prompting"; `access-tokens` — space-separated `host=token`, GitHub OAuth-token or GitLab `type:tokenstring` format, matched by host (optionally with a path prefix like `github.com/org=token`); `allow-import-from-derivation` (**default `true`**) — "By default, Nix allows Import from Derivation... With this option set to `false`, Nix throws an error"; `pure-eval` (**default `false`**) — restricts file/network access to hash-addressed content and disables `builtins.currentSystem`, `builtins.currentTime`, `builtins.nixPath`, `builtins.storePath`; `flake-registry` (default `https://channels.nixos.org/flake-registry.json`, empty disables it); `commit-lock-file-summary`. Measured live against the pinned toolchain (`nix config show`): `experimental-features = fetch-tree flakes nix-command`, `allow-import-from-derivation = true`, `pure-eval = true` (set explicitly by that toolchain's own flake, diverging from the manual's stated default of `false`), `accept-flake-config = false`, `flake-registry = https://channels.nixos.org/flake-registry.json`.

4. **Nix reference manual — protocols and glossary.** [Tarball fetcher protocol](https://nix.dev/manual/nix/2.35/protocols/tarball-fetcher) documents `Link: <flakeref>; rel="immutable"` response headers and explicit Gitea (≥1.22.1) / Forgejo (≥7.0.4 / 8.0.0) support via `https://<domain>/<owner>/<repo>/archive/<ref-or-rev>.tar.gz` URLs, usable as `flake = false` inputs. [Glossary](https://nix.dev/manual/nix/2.35/glossary) defines **fixed-output derivation (FOD)** as "a store derivation where a cryptographic hash of the output is determined in advance using the `outputHash` attribute, and where the builder executable has access to the network" — the mechanism every Nixpkgs fetcher (as opposed to a builtin fetcher) relies on, and the reason a FOD hash mismatch is a build-time, not eval-time, error.

5. **nix.dev — Best practices.** [guides/best-practices](https://nix.dev/guides/best-practices) is short and prescriptive: quote bare URLs (RFC 45 deprecated unquoted URL syntax); avoid `rec { ... }` in favor of `let ... in` (the canonical infinite-recursion footgun is `let a = 1; in rec { a = a; }`); do not use `with (import <nixpkgs> {});` at file top-level (breaks static analysis, ambiguous scoping — cites [nix/issues/490](https://github.com/NixOS/nix/issues/490)) and replace `buildInputs = with pkgs; [ curl jq ];` with `builtins.attrValues { inherit (pkgs) curl jq; }`; never rely on `<nixpkgs>`/`$NIX_PATH` lookup paths outside minimal examples, since they make output depend on external channel state; use `pkgs.lib.recursiveUpdate` instead of `//` when merging nested attrsets (`//` is shallow and silently drops nested keys); use `builtins.path { path = ./.; name = "myproject"; }` instead of bare `src = ./.;` to decouple the store path's symbolic name from the working-directory name.

6. **nix.dev — FAQ and Troubleshooting.** [guides/faq](https://nix.dev/guides/faq) names `nixfmt` (not `nixpkgs-fmt`) as "the official formatter for Nix language code... used to format all code in Nixpkgs," and documents the non-flake path for FHS-incompatible binaries: prefer a Nixpkgs-packaged version, else `autoPatchelfHook`, else `buildFHSEnv`, else `nix-ld` (`programs.nix-ld.enable`, does **not** work for 32-bit executables on x86_64), else `steam-run`. [guides/troubleshooting](https://nix.dev/guides/troubleshooting) covers binary-cache-down (`--option substitute false`), stale negative-cache answers (`--narinfo-cache-negative-ttl`), a corrupt Nix database (`sqlite3 ... "pragma integrity_check"`), and cross-version Nix-store-schema mismatches.

7. **nix.dev tutorials — Working with local files (`lib.fileset`).** [tutorials/working-with-local-files](https://nix.dev/tutorials/working-with-local-files) is an 839-line, code-verified walkthrough: `fs.trace` pretty-prints a file set without copying anything to the store, but plain path coercion (`"${./.}"`, or the common `src = ./.;`) copies the **entire** directory on evaluation; `fs.toSource { root; fileset; }` is the only thing that actually adds files to the store; `fs.difference`, `fs.unions`, `fs.intersection`, `fs.fileFilter (file: file.hasExt "nix")`, `fs.maybeMissing` (for a path that may not exist, e.g. a stale `./result` symlink) and `fs.gitTracked` compose to select exactly the files a build depends on. It states explicitly, as a **Warning**, that "When using the flakes and nix-command experimental features, a local directory within a Flake is always copied into the Nix store completely unless it is a Git repository," and as a **Note** that plain `nix build` "by default only allows access to files tracked by Git."

8. **nix.dev tutorials — Packaging, callPackage, cross-compilation, module system.** [tutorials/packaging-existing-software](https://nix.dev/tutorials/packaging-existing-software) (953 lines) and [tutorials/callpackage](https://nix.dev/tutorials/callpackage) (489 lines) teach `stdenv.mkDerivation`, phase overriding, and the `callPackage`/`overrideAttrs`/`override` layering by example. [tutorials/cross-compilation](https://nix.dev/tutorials/cross-compilation) (483 lines) and the Nixpkgs manual's [Cross Compilation](https://nixos.org/manual/nixpkgs/unstable/#chap-cross) chapter (`pkgsCross.<target>`, `stdenv.hostPlatform`/`buildPlatform`, the "Cross packaging cookbook", "Darwin Cross-Compilation") cover the host/build/target platform split. [tutorials/module-system/deep-dive](https://nix.dev/tutorials/module-system/deep-dive) (1711 lines) is nix.dev's own long-form treatment of the module system that the NixOS manual's writing-modules chapter assumes.

9. **nix.dev tutorials — NixOS VM integration testing and reproducibility.** [tutorials/nixos/integration-testing-using-virtual-machines](https://nix.dev/tutorials/nixos/integration-testing-using-virtual-machines) (506 lines) covers the NixOS test-driver pattern. [tutorials/first-steps/towards-reproducibility-pinning-nixpkgs](https://nix.dev/tutorials/first-steps/towards-reproducibility-pinning-nixpkgs) and its reference companion [reference/pinning-nixpkgs](https://nix.dev/reference/pinning-nixpkgs) lay out the pinning options (channels, `fetchTarball` with a hash, `niv`/`npins`, flake inputs) that predate and coexist with flakes.

10. **nix.dev — concepts/flakes (the official position statement).** [concepts/flakes](https://nix.dev/concepts/flakes) (466 lines, author-credited, editor-reviewed) is nix.dev's most direct discussion of flakes' status, structured as pros/cons/alternatives per concern. It states flakes are "an experimental extension format with outstanding issues" whose "functionality can generally be achieved without them," and under History: RFC 49 was closed/withdrawn "on merge," "raising questions about proper process"; the design was criticized for solving "too many problems at once"; Nixpkgs itself does not use flakes in its internal tooling; Determinate Systems "unilaterally declar[ed] the feature stable" while Lix "consolidated the featureset to a de-facto 'v1'" — different implementations diverging rather than one spec converging. It documents concretely that flakes: cache builds via an eval cache; only see git-tracked files; always run in pure/hermetic mode (`builtins.currentSystem`/`getEnv` unavailable); copy the whole flake directory to the store per build (cited as slower for huge repos like Nixpkgs, [nix/issues/3121](https://github.com/NixOS/nix/issues/3121)); and that since **NixOS 26.05** a `system.nix` entrypoint can load NixOS configuration without a flake. It names `flake-parts`' "dendritic pattern" (spreading all Nix code across flake-parts modules) as one alternative style, and `flake-compat` as the bridge for non-flake consumers.

11. **nix.dev recipes — dependency management, devshells, direnv.** [guides/recipes/dependency-management](https://nix.dev/guides/recipes/dependency-management) documents `npins` (successor to the now-migration-only `niv`) as the recommended non-flake pinning tool, including wiring it into a `system.nix`-based NixOS configuration (`nix.channel.enable = false;`, `nix.nixPath`, `nix.registry`). [guides/recipes/sharing-dependencies](https://nix.dev/guides/recipes/sharing-dependencies) and [guides/recipes/direnv](https://nix.dev/guides/recipes/direnv) cover devShell composition and `nix-direnv`'s automatic-environment activation. [guides/recipes/continuous-integration-github-actions](https://nix.dev/guides/recipes/continuous-integration-github-actions) and [guides/recipes/add-binary-cache](https://nix.dev/guides/recipes/add-binary-cache) cover CI installers and substituter configuration.

12. **Nixpkgs manual — stdenv, meta, fetchers, config.** The single-page [Nixpkgs Reference Manual](https://nixos.org/manual/nixpkgs/unstable/) (measured 26.11pre1026231.65179426c83b) documents the **Standard environment** phase order verbatim: unpack → patch → configure → build → check → install → fixup → installCheck → distribution, each with its own hooks. **Meta-attributes** documents `license`, `mainProgram`, `platforms`, `badPlatforms`, `hydraPlatforms`, `passthru.tests` and `passthru.updateScript` (the attribute `nix-update` reads to automate version bumps). **Fetchers**: `fetchurl` "returns a fixed-output derivation," requires a hash (`sha256`/`hash`/SRI), and a hash mismatch produces `error: hash mismatch in fixed-output derivation '...'`; the manual explicitly distinguishes a "built-in fetcher" (downloads/caches at evaluation time, producing a store path directly) from a "Nixpkgs fetcher" (a fixed-output derivation, downloaded at build time, substitutable from a cache). **Config**: `config.allowUnfree`, `permittedInsecurePackages`, `allowUnfreePredicate` gate unfree/insecure packages (## Installing unfree packages / ## Installing insecure packages). **Overlays vs overriding**: `<pkg>.override`, `<pkg>.overrideAttrs`, `<pkg>.overrideDerivation` (single-package changes) are documented as distinct from `overlays` (package-set-wide composition) and `lib.makeOverridable`.

13. **Nixpkgs manual — language builders and by-name.** `buildGoModule` ("Building Go modules with `buildGoModule`") and `buildRustPackage` ("`buildRustPackage`: Compiling Rust applications with Cargo") each document their own vendor/lock hash attribute and an `overrideAttrs`-based escape hatch (e.g. overriding `goModules`); `buildRustCrate` is documented as the from-source alternative to Cargo-driven builds. Multiple call sites reference `pkgs/by-name/<xx>/<name>/package.nix` as *the* place a new package now lives, matching RFC 0140.

14. **NixOS manual — writing modules and option types.** [nixos.org/manual/nixos/unstable](https://nixos.org/manual/nixos/unstable/) → "Writing NixOS Modules" demonstrates `mkOption`, `mkIf`, and layering `options`/`config`. Its "Option types" section documents **basic types** including `types.bool`, `types.path`, `types.pathInStore`, and two newer, narrower types worth calling out: `types.externalPath` ("a path that is not contained in the Nix store... Typical use cases are: secrets, password or any other external file" — with an explicit warning that it only checks the path isn't *currently* in the store, not that it can't be copied there later) and `types.pathWith { inStore; absolute; }` (parametric: `pathWith { inStore = false; absolute = true; }` is "Useful for password files that shouldn't be leaked into the store"). "Extensible Option Types" documents the `enum`-placeholder pattern for options a module wants third parties to extend (e.g. `services.xserver.displayManager.enable`-style additions from separate modules). `types.raw` is flagged as skipping merging/nested evaluation entirely (only top-level `mkForce`/`mkIf` still apply); `types.optionType` and `types.optionDeclaration` are flagged with an explicit Warning as "a form of metaprogramming that makes modules harder to reason about" and something to prefer avoiding.

15. **NixOS wiki — Flakes.** [wiki.nixos.org/wiki/Flakes](https://wiki.nixos.org/wiki/Flakes) (843 lines, last edited 2026-09-10) is the community-maintained schema reference: the exact output schema (`checks`, `packages`, `apps` with `type = "app"; program`, `formatter`, `legacyPackages`, `overlays`, `nixosModules`, `nixosConfigurations`, `devShells`, `hydraJobs`, `templates`), a worked `nixConfig` example for `extra-substituters`/`extra-trusted-public-keys` with an explicit note that these live under `nix.settings`, not `nix`, when translated into NixOS config; a warning that flake contents are copied to the world-readable store so secrets must never go in a flake; the git-submodules self-attribute dated to **Nix 2.27**; and a "Development tricks" section covering `nix develop --redirect` for live dependency iteration and the `git add --intent-to-add` + `git update-index --skip-worktree` trick for keeping a personal, uncommitted file visible to a flake without committing it.

16. **flake.parts.** The [flake.parts](https://flake.parts/) landing page states its scope precisely: "provides the options that represent standard flake attributes... itself has the goal to be a minimal mirror of the Nix flake schema... it is not a monorepo... but rather a single module that other repositories can build upon." The [core module options reference](https://flake.parts/options/flake-parts) enumerates the actual option surface: top-level `debug`, `flake` (mirroring `flake.packages`, `flake.apps.<system>.<name>.{meta,program,type}`, `flake.checks`, `flake.devShells`, `flake.formatter`, `flake.legacyPackages`, `flake.nixosConfigurations`, `flake.nixosModules`, `flake.overlays`), `perInput`, `perSystem` (with its own `packages`, `apps.<name>.{meta,program,type}`, `checks`, `debug`, `devShells`, `formatter`, `legacyPackages`), `processedFlake`, `systems`, and `transposition`/`transposition.<name>.adHoc`.

17. **zero-to-nix (Determinate Systems) and Determinate/FlakeHub/Lix product docs.** [zero-to-nix.com/concepts/flakes](https://zero-to-nix.com/concepts/flakes/) states plainly: "Flakes are experimental in upstream Nix but stable in Determinate Nix... there is currently no concrete timeline for declaring them stable" upstream, versus Determinate Nix where flakes are "considered stable" (cites the [Determinate Nix 3.0 blog post](https://determinate.systems/blog/determinate-nix-30)). It documents the same flake-reference/inputs/lock-file/registry/outputs/templates schema as the manual, in more example-driven form. [docs.determinate.systems](https://docs.determinate.systems/) enumerates Determinate Nix's differentiated features (Determinate Nixd, native Linux builder for macOS, **lazy trees**, parallel evaluation, WebAssembly support, provenance) and FlakeHub's (FlakeBOM, FlakeAudit, semver, private flakes, resolved store paths, FlakeHub Cache, mirroring, yanked releases). [lix.systems](https://lix.systems/) positions Lix as "a community variant of the Nix... system," fully compatible with existing Nix expressions/Nixpkgs, explicitly avoiding "corporate-controlled infrastructure, like Microsoft's GitHub," and intending to support "language versioning features" so the language can evolve without breaking existing configs — a different governance and stability philosophy from both upstream CppNix and Determinate Nix.

18. **DeterminateSystems/flake-checker.** The tool's own [README](https://github.com/DeterminateSystems/flake-checker) (measured v0.2.15 via the pinned toolchain) documents exactly three default checks against a root-level Nixpkgs input — `--check-outdated` / `NIX_FLAKE_CHECKER_CHECK_OUTDATED` (< 30 days old by default), `--check-owner` / `NIX_FLAKE_CHECKER_CHECK_OWNER` (must be the `NixOS` GitHub org, i.e. not a fork), `--check-supported` / `NIX_FLAKE_CHECKER_CHECK_SUPPORTED` (ref must be in an enumerated supported-branches list: `nixos-25.11`, `nixos-25.11-small`, `nixos-26.05`, `nixos-26.05-small`, `nixos-unstable`, `nixos-unstable-small`, `nixpkgs-25.11-darwin`, `nixpkgs-26.05-darwin`, `nixpkgs-unstable`) — plus a CEL `--condition` flag (variables `gitRef`, `numDaysOld`, `owner`, `supportedRefs`, `refStatuses`) for custom policy, with the README's own recommended baseline: `supportedRefs.contains(gitRef) && numDaysOld < 30 && owner == 'NixOS'`.

## Recent shifts seen in this corpus

- **`lib.fileset` is now the taught default for source filtering** (nix.dev tutorial, current as of this corpus's fetch date 2026-09-27), superseding `builtins.path`/`lib.sources.cleanSourceWith` filter-callback idioms that older guides and most existing flakes still use. Any rule written from pre-2023 material will teach the older, error-prone pattern.
- **`inputs.self.submodules`/`inputs.self.lfs` self-attributes** (dated by the NixOS wiki to **Nix 2.27**) are a materially newer flake-schema feature; guidance written against Nix ≤2.26 will recommend workarounds (manual `?submodules=1` URL params) that are now unnecessary.
- **`pkgs/by-name` (RFC 0140, merged)** and **`nixfmt` as the RFC-0166-canonical formatter (merged)** are both accepted-and-merged changes that postdate a large fraction of existing community flakes and blog posts; anything citing `all-packages.nix` placement or `nixpkgs-fmt` as current is stale by these RFCs' own merge status.
- **NixOS 26.05's `system.nix` entrypoint** is a 2026-era alternative to flake-based NixOS configuration, explicitly positioned by nix.dev as equal-footing, not a lesser option — this reframes "should this become a flake" as a live design question rather than a foregone conclusion, which matters directly for how prescriptive a `nix-quality` rule should be.
- **`allow-import-from-derivation` defaulting to `true`** in the current manual is worth flagging as a correction to a common assumption; whether this default has changed across recent Nix versions was not independently verified in this corpus (no older-manual diff was fetched) and should be treated as a **measured-current-state**, not a confirmed **recent change**.
- **Determinate Nix's unilateral "flakes are stable" declaration** (Determinate Nix 3.0) and **Lix's separately consolidated "de-facto v1" flake feature set** are both post-2024 developments the frame's H9 hypothesis anticipated; this corpus confirms H9 directly from all three parties' own current documentation rather than by inference.
- **FlakeHub's product surface** (FlakeBOM, FlakeAudit, resolved store paths, yanked releases) is presented in this corpus's snapshot of Determinate's docs as a going concern as of "Last updated on September 25, 2026" — i.e. two days before this research date, confirming the product docs reflect the current era rather than a stale cache.

## Contested

- **Whether flakes should be used at all for a new project.** nix.dev's own concepts page states flakes are experimental with outstanding issues and that "its functionality can generally be achieved without them," pointing to `npins` + plain Nix as a first-class alternative. Determinate Systems' docs, in contrast, present flakes (via Determinate Nix) as the default, stable, recommended path from the very first quick-start step. This is not a stylistic disagreement between blogs; it is two different parties' *official documentation* disagreeing about flakes' status. Trend: Determinate Systems and FlakeHub's commercial investment is pushing adoption forward regardless of upstream's formal position; nix.dev has not softened its "experimental" framing as of this corpus's fetch date.
- **What "stable flakes" even means across implementations.** Determinate Nix declares flakes stable and adds features (lazy trees, parallel eval) with no upstream equivalent; Lix "consolidated" its own feature set independently; upstream CppNix has neither stabilized nor frozen the schema. A flake author following only the upstream manual cannot assume behavior parity with either fork, and this corpus found no cross-implementation compatibility test suite referenced by any of the three parties' own docs.
- **Whether `follows` reliably prevents duplicate-nixpkgs problems.** The manual documents `follows` mechanically (this corpus, source 2) but takes no position on whether declaring it everywhere is sufficient; nix.dev's concepts/flakes page notes as a documented *con* that "if your flake is used as a library, you need to add follows statements for all recursive inputs" — i.e. the mechanism is opt-in per edge, not transitively safe by default, and the manual does not warn about this as prominently as the wiki/concepts pages do.
- **How prescriptive a fleet rule should be about `flake-utils` vs `flake-parts` vs hand-rolled `perSystem`.** None of the canonical sources in this corpus take an explicit "use X" position; flake.parts' own docs describe itself only as "a minimal mirror of the flake schema," not as the endorsed successor to flake-utils. This is a judgment call the dive wave should make with practitioner-corpus evidence, not canonical-corpus evidence.
