## Summary

- statix ships 20 lints in source but only **17 are active** in the installed 2.35.2-era binary — `unquoted_splice` (W09) exists in source with `code = 9` but is absent from `statix list`'s output, meaning it is source-present but disabled by default.
- Lint codes are not contiguous: W13, W15, W16, W21, W22 correspond to no file in `lib/src/lints/` at all — reserved/removed codes, not gaps in the survey.
- deadnix has no numbered rule catalogue at all: it is one check ("unused binding") with five behavior-changing flags (`--no-lambda-arg`, `--no-lambda-pattern-names`, `--no-underscore`, `--warn-used-underscore`, `--hidden`) rather than a rule list.
- nixf (the diagnostic library inside nixd) defines **41 distinct diagnostics** across four severities (`Error`, `Warning`, `Fatal`, `Hint`) in one machine-readable source file, `libnixf/src/Basic/diagnostic.py` — a strict superset of what statix/deadnix catch, including parser-level diagnostics neither AST-linter reaches.
- nixpkgs-vet (RFC 140) enforces file-structure rules on `pkgs/by-name` (2-letter lowercased shard, ASCII name charset, no symlinks/path-escapes) plus three **ratchet checks** — once a package is on `strictDeps = true` or `__structuredAttrs = true` or lives under `pkgs/by-name`, it can never regress; new top-level `callPackage` derivations are forced into all three going forward.
- nixpkgs-hammering has exactly **24 checks**, one per file under `explanations/`, split between pure-Nix overlay checks (evaluable) and Rust checks (parse/build-log/network-capable) — it is nitpick-tier, not a hard gate.
- nixfmt is a single Haskell tool with one style, defined in a 1547-line `standard.md`; the package/attribute name **`nixfmt-rfc-style` was folded back into plain `nixfmt` in nixfmt 1.3.0 (2026-05-26)** — any flake or doc still writing `pkgs.nixfmt-rfc-style` is citing dead nomenclature.
- Verified live against Nix 2.35.2 on a planted fixture: `nix flake check` treats a non-derivation value under `packages.<system>.default` as a **hard error** ("... is not a derivation"), but an unrecognized top-level output name is only a **soft warning** (`warning: unknown flake output 'foo'`) — the check never fails on a genuinely novel output name.
- `nix flake check`'s built-in schema (from the Nix 2.35.2 manual/`--help`) requires derivations for `checks`/`devShells`/`packages`/`nixosConfigurations.*.config.system.build.toplevel`, app-shape for `apps`, template-shape for `templates`, and rewrites seven old singular names (`devShell` → `devShells.<system>.default`, `overlay` → `overlays.default`, etc.) with a warning, not a failure.
- flake-checker's three built-in checks (outdated ref, non-`NixOS` owner, unsupported branch) are each independently toggleable via flag or env var, and a fourth mechanism — a CEL `--condition` expression over `gitRef`/`numDaysOld`/`owner`/`supportedRefs`/`refStatuses` — lets a consumer write an arbitrary custom policy on top.
- treefmt-nix ships **128** `programs/*.nix` formatter definitions; the Nix-relevant ones are `nixfmt`, `alejandra`, `statix`, `deadnix`, `nixf-diagnose`, and legacy `nixpkgs-fmt`.
- git-hooks.nix exposes **9** Nix-specific pre-commit hooks: `alejandra`, `deadnix`, `flake-checker`, `nixf-diagnose`, `nixfmt`, `nixfmt-classic`, `nixfmt-rfc-style`, `nixpkgs-fmt`, `statix` — three of those nine (`nixfmt`/`nixfmt-classic`/`nixfmt-rfc-style`) are the same underlying binary under three historical option names.
- nixpkgs itself runs, per PR, at minimum: `treefmt` (format check), `parse` (multi-Nix-version parse), `nixpkgs-vet`, commit-message lint (`lint-commits.ts`), `manual-file-edits`, `owners` (codeowners-validator), an `eval` matrix (`ci/eval/outpaths.nix`) and a `build` matrix that is **narrower on `aarch64-darwin`** (only `shell`, not `manual-nixpkgs`/`manual-nixos`/`lib-tests`/`tarball`) than on `x86_64-linux`/`aarch64-linux` — codified proof that Darwin coverage in CI is thinner by design, not oversight.
- nixpkgs' own commit-message convention (`pkg-name: old -> new`) is not merely style: it is what CI's per-attribute build-scoping keys off; an off-convention message loses automatic build targeting.
- IFD (Import From Derivation) is explicitly banned in nixpkgs CONTRIBUTING.md for performance reasons (Hydra evaluates the whole tree), with "commit generated files instead" as the sanctioned workaround — this is a constraint on nixpkgs itself, not automatically on a downstream flake, and that distinction matters for an ocx-generated flake that reads a JSON index at eval time (ordinary `builtins.fromJSON`, not IFD, as long as the JSON is a plain file, not a derivation output).
- `overrideAttrs`/`overridePythonAttrs` are banned for *new* in-tree nixpkgs uses (five concrete maintainability reasons given), explicitly framed as fine for out-of-tree/downstream code — the opposite policy from what an agent trained mostly on nixpkgs-internal examples might infer.
- `lib.warn` (nixpkgs' `lib.warn`) is documented as wrapping `builtins.warn`, which is **Nix ≥ 2.23 only**; on older Nix, `lib.warn` emulates it with `builtins.trace`, including honoring `NIX_ABORT_ON_WARN` but not the `nix.conf`-level setting.
- The house deprecation toolkit for NixOS module options is four functions with distinct blast radii: `mkRenamedOptionModule` (warns, keeps behavior), `mkRemovedOptionModule` (fails at eval unless message says otherwise), `mkAliasOptionModule` (silent, no warning), `mkChangedOptionModule` (arbitrary rewrite function) — plus `lib.derivations.warnOnInstantiate` for renaming a *package* attribute, not an option.
- RFC 42's "settings-style options" pattern (`pkgs.formats.<fmt> {}` + `freeformType` + a handful of typed, validated options layered on top) is the documented, current alternative to a stringly `extraConfig` option — directly relevant to how an ocx-generated NixOS/home-manager module (if ever produced) should expose per-package configuration.
- Implementation divergence is now measurable and non-hypothetical: upstream Nix 2.35 already ships lazier source-hashing; Determinate Nix 3.5.2 ships a separate, more aggressive "lazy trees" mechanism (claimed 3×+ wall-time, 20×+ disk-usage wins) that is **not** in CppNix or Lix; and Lix's own flake-stabilisation proposal explicitly targets the `input.follows` mechanism for removal ("the follows mechanism is horrible... let's just not do that"), meaning a documented core piece of flake-consumer UX may not survive across implementations.

### 1. statix — the AST lint catalogue

[oppiliappan/statix](https://github.com/oppiliappan/statix), readme at [`readme.md`](https://raw.githubusercontent.com/oppiliappan/statix/master/readme.md) (note lowercase filename; `README.md` 404s). ### 2. deadnix — dead-code detector

[astro/deadnix](https://github.com/astro/deadnix), [README](https://raw.githubusercontent.com/astro/deadnix/main/README.md); version cross-checked live: `deadnix --version` inside the toolchain reports co-installed with `nix (Nix) 2.35.2`.

deadnix has no numbered rule catalogue — it is a single check ("dead code": unused variable bindings) tunable by five flags:

- `-l`/`--no-lambda-arg` — don't check lambda parameter arguments.
- `-L`/`--no-lambda-pattern-names` — don't check lambda attrset pattern names ("don't break nixpkgs `callPackage`" — the tool's own comment, acknowledging that `callPackage`'s introspection of a function's formal-argument *names* means an apparently-unused pattern name is often load-bearing).
- `-_`/`--no-underscore` — skip bindings starting with `_` (lambda args starting with `_` are never checked regardless).
- `-W`/`--warn-used-underscore` — inverse: warn if an underscore-prefixed binding *is* referenced.
- `-h`/`--hidden` — recurse into hidden dirs/files.
- `-e`/`--edit` — auto-remove and rewrite in place.
- `-f`/`--fail` — exit 1 if anything found (needed for CI gating; default exit is 0).
- `-o json` output format for machine consumption.

This is the tool whose default behavior an agent must know *not* to blindly gate on: without `-L`, deadnix will flag an unused `callPackage`-style formal argument that nixpkgs' own convention (list every expected dependency as a formal, even if only used conditionally) treats as intentional documentation, not dead code.

### 3. nixf / nixd — the diagnostic engine

[nix-community/nixd](https://github.com/nix-community/nixd), diagnostic source of truth: [`libnixf/src/Basic/diagnostic.py`](https://raw.githubusercontent.com/nix-community/nixd/main/libnixf/src/Basic/diagnostic.py) — a Python file that code-generates the C++ `DiagnosticEnum.h` and `Diagnostic.cpp`. Fetched 2026-09-27.

This is the most complete static-analysis catalogue of the three (statix/deadnix/nixf), because nixf parses with error recovery and produces parser-level diagnostics neither of the AST linters reach. Each entry has `sname` (kebab-case short name), `cname` (C++ identifier), `severity` (`Error`|`Warning`|`Fatal`|`Hint`), and `message`. 41 entries total, grouped by prefix:

- **Lexer** (`lex-*`): `lex-unterminated-bcomment` (Error), `lex-float-no-exp` (Fatal), `lex-float-leading-zero` (Warning — "is nixf extension", i.e. this is a nixf-only lenient re-lex, not standard Nix).
- **Parser** (`parse-*`): `parse-expected`, `parse-int-too-big`, `parse-redundant-paren` (Warning — nixf's own version of statix's W08), `parse-attrpath-extra-dot`, `parse-select-extra-dot`, `parse-unexpected-between`, `parse-unexpected`, `parse-missing-sep-formals`, `parse-lambda-arg-extra-at`, `parse-operator-noassoc`, `parse-kw-or-isnot-binary-op` — all Error except the redundant-paren case.
- **Semantic construct** diagnostics not prefixed `sema-`: `let-dynamic` (Error — dynamic attrs illegal in legacy `let{}`), `empty-inherit` (Warning), `or-identifier` (Warning — `or` used as a bare identifier, legal but confusing since `or` is also a keyword), `deprecated-url-literal` (Warning), `deprecated-let` / `deprecated-let-missing-body` (legacy `let {}` syntax, matching statix W05), `path-trailing-slash`, `merge-diff-rec` (Warning — merging a `rec` and non-`rec` attrset, a common `//`-operator surprise).
- **Semantic** (`sema-*`): `sema-duplicated-attrname` (nixf's version of statix W20, but caught at parse/sema time rather than AST-lint time), `sema-dynamic-inherit`, `sema-empty-formal`, `sema-formal-missing-comma`, `sema-formal-extra-ellipsis`, `sema-misplaced-ellipsis`, `sema-dup-formal`, `sema-dup-formal-arg`, `sema-undefined-variable` (Error-severity, static-time — distinct from Nix's own **lazy runtime** `error: undefined variable` reported only when the corresponding thunk is forced), `sema-unused-def-let` / `sema-unused-def-lambda-noarg-formal` / `sema-unused-def-lambda-witharg-formal` / `sema-unused-def-lambda-witharg-arg` (four distinct "unused binding" diagnostics that split deadnix's single check by binding kind), `sema-extra-rec`, `sema-extra-with`, `sema-primop-unknown` / `sema-primop-removed-prefix` / `sema-primop-needs-prefix` / `sema-primop-overridden`, `sema-constant-overridden`.

Because nixd (the LSP built on nixf) is what an agent's editor integration surfaces in real time, this list — not statix's — is closer to what a coding agent actually sees turn-by-turn while writing Nix; statix/deadnix are batch/CI-time tools an agent must be told to *also* run.

### 4. nixpkgs-vet — the `pkgs/by-name` validator (RFC 140)

[NixOS/nixpkgs-vet](https://github.com/NixOS/nixpkgs-vet), [README](https://raw.githubusercontent.com/NixOS/nixpkgs-vet/main/README.md) and the local exemplar [`pkgs/by-name/README.md`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/pkgs/by-name/README.md). Implements [RFC 140](https://github.com/NixOS/rfcs/pull/140).

Exact "Validity checks" section (verbatim structure from the README):

- **File structure checks**: `pkgs/by-name` must only contain `${shard}/${name}` package directories; `name` must be unique when lowercased; `name` charset is ASCII `a-z A-Z 0-9 - _`; `name` must not start with a digit or `-`; `shard` is defined *exactly* as `toLower (substring 0 2 name)`; each package directory must contain `package.nix` (other files allowed).
- **Nix parser checks**: a package directory must not reference files outside itself via symlink or Nix path expression (`../`).
- **Nix evaluation checks** (evaluated with `system = x86_64-linux`): `pkgs.${name}` must be defined and `pkgs.lib.isDerivation pkgs.${name}` must be `true`.
- **Ratchet checks** (the ["ratchet" pattern](https://qntm.org/ratchet): existing violations grandfathered, new ones forbidden, using a base-vs-head comparison via `<BASE_NIXPKGS>`): (1) a new top-level package via `callPackage` must be defined with a `pkgs/by-name` directory, and once migrated it cannot move back out; (2) a new top-level package must evaluate with `strictDeps = true`, and once true it cannot regress to `false`; (3) a new top-level package must evaluate with `__structuredAttrs = true`, same one-way rule.

Practical consequence for a generator: these ratchets are *directional*, not just "on/off" — an ocx-generated package set that starts life under `pkgs/by-name`-shaped conventions and with `strictDeps`/`__structuredAttrs` set is choosing a floor it (or nixpkgs, if ever upstreamed) can never lower again, which argues for deciding this on day one rather than defaulting to legacy attributes and "fixing it later."

### 5. nixpkgs-hammering — packaging nitpicks

[jtojnar/nixpkgs-hammering](https://github.com/jtojnar/nixpkgs-hammering), [README](https://raw.githubusercontent.com/jtojnar/nixpkgs-hammering/main/README.md), rule text under [`explanations/`](https://github.com/jtojnar/nixpkgs-hammering/tree/main/explanations).

Two check mechanisms: (1) pure-Nix overlays that replace `stdenv.mkDerivation` and similar, attaching a report attribute the tool evaluates (fast, in-process); (2) Rust checks invoked with attribute paths + file paths + build logs, capable of AST parsing, build-log inspection, or network access (slower, more powerful). Exactly **24 checks**, one `explanations/*.md` file each: `attribute-ordering`, `attribute-typo`, `build-tools-in-build-inputs`, `duplicate-check-inputs`, `environment-variables-go-to-env`, `explicit-phases`, `fixup-phase`, `license-missing`, `maintainers-missing`, `meson-cmake`, `missing-patch-comment`, `missing-phase-hooks`, `name-and-version`, `no-flags-array`, `no-flags-spaces`, `no-python-tests`, `no-uri-literals`, `patch-phase`, `python-explicit-check-phase`, `python-imports-check-typo`, `python-include-tests`, `python-inconsistent-interpreters`, `stale-substitute`, `unclear-gpl`, `unnecessary-parallel-building`.

Sampled verbatim (2026-09-27 fetch):

- `environment-variables-go-to-env`: "Environment variables should go inside `env` attribute instead of being passed directly to `stdenv.mkDerivation`... `mkDerivation` will only allow values that can be safely stringified in the `env` attribute (i.e. no lists)" — directly tied to `__structuredAttrs`'s stricter typing.
- `no-flags-array`: explains that `buildFlagsArray`-as-a-Nix-list silently space-joins and re-splits through Bash with **no quoting semantics preserved** — "Bash also does not really interpret the values of variables passed to derivations... they will be passed to the Bash `buildFlagsArray` variable literally" — a foot-gun that looks like it works for a single flag and breaks the moment a second flag or a flag containing a space is added.
- `unclear-gpl`: the unqualified `lib.licenses.gpl2`/`gpl3`/`lgpl2`/`lgpl21`/`lgpl3` attributes are deprecated in favor of explicit `...Plus`/`...Only` variants, "in line with the [GNU recommendations](https://gnu.org/licenses/identify-licenses-clearly.html)".
- `duplicate-check-inputs`: for Python packages, everything in `propagatedBuildInputs` is already available during `checkPhase`, so duplicating it into `checkInputs` is pure redundancy.

This is nitpick-tier (never a hard CI gate in nixpkgs itself — it is a standalone `nix run` a reviewer opts into), unlike nixpkgs-vet.

### 6. nixfmt — the standard formatter (RFC 166)

[NixOS/nixfmt](https://github.com/NixOS/nixfmt), user docs [`README.md`](https://raw.githubusercontent.com/NixOS/nixfmt/master/README.md), the actual formatting rules in [`standard.md`](https://raw.githubusercontent.com/NixOS/nixfmt/master/standard.md) (1547 lines), history in [`CHANGELOG.md`](https://raw.githubusercontent.com/NixOS/nixfmt/master/CHANGELOG.md), and [RFC 166](https://raw.githubusercontent.com/NixOS/rfcs/master/rfcs/0166-nix-formatting.md) (the RFC that created the "one official formatter" process).

Key facts, version-anchored:

- Current version **1.5.0 (2026-09-10)**: added chained presence-check parsing (`a ? b ? c`), a `--follow-symlinks` option; fixed an exponential-parse-time bug on nested set-parameter defaults.
- **1.4.0 (2026-07-07)**: added `/*nixfmt:disable*/` / `/*nixfmt:enable*/` comment directives to exclude a code region from formatting — the escape hatch for hand-tuned tables/matrices that the formatter would otherwise mangle.
- **1.3.0 (2026-05-26)**: "**Replaced references to `nixfmt-rfc-style` with `nixfmt`**" — the package/binary that used to be named `nixfmt-rfc-style` (to distinguish it from the older, now-obsolete "classic" nixfmt during RFC 166's transition period) is now simply `nixfmt`. Also: pipe-operator (`|>`) chains now format across multiple lines; stdin formatting without an explicit `-` argument is deprecated.
- `nixfmt` deliberately processes **one file at a time** — project-wide formatting is explicitly deferred to a wrapper (`treefmt`, `nix fmt`), not nixfmt itself.
- Editor integration is documented for neovim+nixd, neovim+nil, and none-ls, all invoking the same `nixfmt` binary as the LSP's formatting command.

`standard.md` itself (not fully quoted here given length) is the authoritative source for width/indent/blank-line/comment-placement rules; `nixfmt --help`'s settings (`width`, `indent`) are exposed identically through git-hooks.nix's `nixfmt` hook options (§10).

### 7. `nix flake check` — built-in flake validation (verified, Nix 2.35.2)

Primary text: `nix flake check --help` inside the pinned toolchain (Nix 2.35.2), which is the same content published at the [Nix 2.35 manual](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake-check). **Verified live** against two planted fixture flakes under `/home/mherwig/.cache/research-lang/nix-tools/fixtures/nix-topic-map-check/`.

Exact schema (from the command's own `--help`, Nix 2.35.2):

- Must be **derivations**: `checks.<system>.<name>`, `devShells.<system>.default`, `devShells.<system>.<name>`, `nixosConfigurations.<name>.config.system.build.toplevel`, `packages.<system>.default`, `packages.<system>.<name>`.
- Must be **app definitions**: `apps.<system>.default`, `apps.<system>.<name>`.
- Must be **template definitions**: `templates.default`, `templates.<name>`.
- Must be **Nixpkgs overlays**: `overlays.default`, `overlays.<name>`.
- Must be **NixOS modules**: `nixosModules.default`, `nixosModules.<name>`.
- Must be **bundlers**: `bundlers.default`, `bundlers.<name>`.
- `hydraJobs` is evaluated the way Hydra's `hydra-eval-jobs` would (arbitrarily-nested attrset of derivations); `legacyPackages.<system>` is evaluated the way `nix-env --query --available` would.
- **Old singular names are rewritten with a warning, not a failure**: `defaultPackage.<system>` → `packages.<system>.default`, `defaultApps.<system>` → `apps.<system>.default`, `defaultTemplate` → `templates.default`, `defaultBundler.<system>` → `bundlers.<system>.default`, `overlay` → `overlays.default`, `devShell.<system>` → `devShells.<system>.default`, `nixosModule` → `nixosModules.default`.
- Flags: `--all-systems` (check every system, not just the current one), `--no-build` (evaluate but don't build check derivations), `--out-link`/`-o` (symlink prefix; none by default), `--print-out-paths`.

**Fixture-verified behavior** (both fixtures under `fixtures/nix-topic-map-check/flake.nix`, `nix flake check --no-build --no-write-lock-file`, Nix 2.35.2):

1. `packages.x86_64-linux.default = "not-a-derivation";` → **hard error**: `error: flake attribute 'packages.x86_64-linux.default' is not a derivation`, with a full trace pointing at the exact `flake.nix` line/column. This stops the whole check.
2. Fixed to a real derivation (`pkgs.hello`) plus an added unrecognized top-level attribute `somethingUnknownTopLevel = 42;` → the derivation check passes, and the unknown attribute produces exactly: `warning: unknown flake output 'somethingUnknownTopLevel'`, followed by `all checks passed!`. **An unrecognized top-level output name never fails `nix flake check`** — it is always a warning, regardless of the name.

This confirms and sharpens the frame's H3 hypothesis: exemplar flakes exposing non-derivations under `packages` *would* be caught (hard failure) if `nix flake check` were actually run on them; but a flake can carry any number of nonstandard extra top-level attributes forever with only a cosmetic warning, so "passes `nix flake check`" is a much weaker signal about schema hygiene than about actual derivation-shape correctness.

### 8. flake-checker — flake.lock health

[DeterminateSystems/flake-checker](https://github.com/DeterminateSystems/flake-checker), [README](https://raw.githubusercontent.com/DeterminateSystems/flake-checker/main/README.md).

Operates only on a flake's **root-level Nixpkgs inputs** in `flake.lock`. Three independently-toggleable checks (flag / env var / default):

| Check | Flag | Env var | Default |
|---|---|---|---|
| Outdated | `--check-outdated` | `NIX_FLAKE_CHECKER_CHECK_OUTDATED` | `true` |
| Wrong owner | `--check-owner` | `NIX_FLAKE_CHECKER_CHECK_OWNER` | `true` |
| Unsupported branch | `--check-supported` | `NIX_FLAKE_CHECKER_CHECK_SUPPORTED` | `true` |

Supported-branches list (as documented 2026-09-27): `nixos-25.11`, `nixos-25.11-small`, `nixos-26.05`, `nixos-26.05-small`, `nixos-unstable`, `nixos-unstable-small`, `nixpkgs-25.11-darwin`, `nixpkgs-26.05-darwin`, `nixpkgs-unstable`. Default "outdated" threshold is implicitly the "30-days-old" recommendation given in the README's example policy (`numDaysOld < 30`), though the flag itself is a boolean, not a configurable number — the *number* is only adjustable via the CEL condition mechanism below.

A fourth, more expressive mechanism layers on top: `--condition '<CEL expression>'` (Common Expression Language), with these variables available: `gitRef`, `numDaysOld`, `owner`, `supportedRefs` (list), `refStatuses` (map of branch name → `"rolling"|"beta"|"stable"|"deprecated"|"unmaintained"`). The README's own recommended baseline: `supportedRefs.contains(gitRef) && numDaysOld < 30 && owner == 'NixOS'`. Ships as a reusable GitHub Action (`DeterminateSystems/flake-checker-action`) that **always exits 0** in CI and reports via a Markdown job-summary instead of failing the build — a deliberate "advisory, not gating" design choice. Also telemetry-collecting by default (`--no-telemetry`/`FLAKE_CHECKER_NO_TELEMETRY=true` to disable) and ships a reusable Rust crate, `parse-flake-lock`, for third-party `flake.lock` tooling.

### 11. nixpkgs CONTRIBUTING.md & pkgs/README.md — normative rules

Local exemplar clone, [`CONTRIBUTING.md`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/CONTRIBUTING.md) and [`pkgs/README.md`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/pkgs/README.md), rev `9cab9ed832c3e8665d945418b954d518af1c629e`, 2026-09-27 (canonical: [github.com/NixOS/nixpkgs](https://github.com/NixOS/nixpkgs)).

Commit conventions: one commit per logical unit; no trailing period on the summary line; `maintainers: add <handle>` gets its own commit, ordered before the package/module change it enables; and critically, **`(pkg-name): (from -> to | init at version | ...)` is not just style — it queues nixpkgs' CI to automatically build exactly that attribute** (table given: `vim: 1.0.0 -> 2.0.0` builds `vim`; `python3Packages.{numpy,scipy}: fix build` builds both named attributes). A `WIP:`-prefixed or `[WIP]` PR title suppresses automatic builds.

Versioning: `version` must start with a digit (`nix-env`'s name-parser requirement); for an unreleased/rolling upstream commit, the convention is `<latest-preceding-version>-unstable-YYYY-MM-DD`, or `0-unstable-YYYY-MM-DD` if there is no sensible preceding version at all.

Meta requirements (`must`/`should` per RFC-2119-style keywords, explicitly scoped to just the emphasized words in that section): `meta.description` must be short, capitalized, not start with an article or the package name, no trailing punctuation, factual not subjective; `meta.license` must be set and match upstream (defaulting to `lib.licenses.unfree` if no upstream license is stated); `meta.sourceProvenance` **must** be set if the package is not built from source (e.g. repackaging a `.deb`/`.rpm`/`.whl` → `lib.sourceTypes.binaryNativeCode`); `meta.mainProgram` must be set when there is exactly one applicable executable, and explicitly must **not** be inferred from `pname` (a hardcoded string is required); `meta.maintainers` must be set for new packages.

Fetching hierarchy, worst-to-best (verbatim example progression in the README): `fetchgit` with a `git://` URL (worst — unproxyable) → `fetchgit` with `https://` (better, still a full-history clone) → `fetchFromGitHub` with a full-length `rev` (best — a snapshot archive fetch, and the doc explicitly warns that **short commit hashes are ambiguous across forks and GitHub 404s them**, having previously bitten nixpkgs in production).

IFD is explicitly banned in nixpkgs "for performance reasons" (Hydra evaluates the entire package set; sequential builds during evaluation would make evaluation impractically slow); the sanctioned workaround is to commit a generated intermediate file and read *that* instead of evaluating a derivation during evaluation.

`overrideAttrs`/`overridePythonAttrs`: explicitly **fine for out-of-tree/downstream code** ("these functions are useful for out-of-tree code"), but banned for *new* in-tree nixpkgs uses, for five stated reasons (duplicated overrides across packages going unnoticed; overrides hiding from the maintainer of the overridden package; overrides never being reviewed by that maintainer; overridden packages being forgotten and lingering; larger, duplicated dependency closures).

Patches: prefer `fetchpatch2` for upstream/externally-hosted patches (with a caveat — if the patch text itself contains short/abbreviated commit hashes, e.g. `index 0c97fcc35..f533e464a`, use `fetchpatch` instead, since `fetchpatch2` cannot expand those); vendor a `.patch` file in-tree only when the patch is nixpkgs-specific, unfetchable, or likely to rot.

Package removal: not deleted outright — replaced with `attr = throw "reason"; # added YYYY-MM-DD` in `pkgs/top-level/aliases.nix`, so users with the old attribute get an informative error rather than a silent break.

### 12. nixpkgs CI — the check matrix

Local exemplar: [`ci/README.md`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/ci/README.md), [`.github/workflows/check.yml`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/.github/workflows/check.yml), [`.github/workflows/lint.yml`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/.github/workflows/lint.yml), [`.github/workflows/build.yml`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/.github/workflows/build.yml), [`.github/workflows/eval.yml`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/.github/workflows/eval.yml), [`.github/workflows/test.yml`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/.github/workflows/test.yml) (all at rev `9cab9ed8`).

Per-PR job list, by workflow file: **`check.yml`** — `commits` (calls `commits.ts`, gates on branch classification: stable-targeting PRs need cherry-pick-style validation), `manual-file-edits` (discourages hand-editing generated files), `reminders` (bot-posted process reminders), a `github-script` self-test, and `owners` (builds and runs `codeowners-validator` with `CHECKS="duppatterns,files,syntax"` plus experimental `avoid-shadowing`). **`lint.yml`** — `treefmt` (runs `fmt.check`, and on failure prints the exact fix commands: `nix-shell --run treefmt` / `nix develop --command treefmt` / `nix fmt`), `parse` (parses all `.nix` files across multiple Nix versions with `--keep-going`), `nixpkgs-vet` (§4, run base-vs-head), `commits` (commit-message convention, `lint-commits.ts`, only runs when a `pull_request` context exists — not in the merge queue, since merge-queue commit messages can't change). **`build.yml`** — a 3-row matrix: `x86_64-linux` builds `[shell, manual-nixos, lib-tests, tarball]`; `aarch64-linux` builds `[shell, manual-nixos, manual-nixpkgs]`; **`aarch64-darwin` builds only `[shell]`** — i.e. nixpkgs' own CI does not build its manuals, lib tests, or tarball on Darwin at all. **`eval.yml`** — an evaluation matrix parameterized by `systems` and (optionally) `testVersions`, driving `ci/eval/outpaths.nix`/`diff.nix` to diff evaluated output paths between base and head. **`test.yml`** — the entry workflow, which classifies the trigger (PR vs. push vs. merge queue) and fans out to the others.

Branch classification (from `ci/README.md`): four tiers — **Channel** (`nixos-`/`nixpkgs-` prefix, PRs disallowed, only fast-forwarded from `master`/`release-*`), **Primary development** (`master`, `release-*`, PRs required), **Secondary development** (`staging-*`, `haskell-updates`), **Work-in-progress** (`backport-`/`revert-`/`wip-` prefixes, short-lived, force-push allowed). The **merge bot** (`ci/github-script/bot.js`+`merge.js`) lets any nixpkgs maintainer merge a PR that only touches `pkgs/by-name/*` files by commenting `@NixOS/nixpkgs-merge-bot merge`, subject to stated constraints (approved-or-backported-or-committer-opened-or-r-ryantm-opened, no outstanding "changes requested," merger must maintain every touched package) — direct evidence that **`pkgs/by-name` placement has a concrete governance payoff** (self-service merge rights) beyond the nixpkgs-vet ratchet checks themselves.

### 13. RFC 0042 — settings-style module options

[NixOS/rfcs #42](https://raw.githubusercontent.com/NixOS/rfcs/master/rfcs/0042-config-option.md), "Add a `settings`-like configuration style to Nixpkgs modules."

Two parts: **Part 1** standardizes *structural* `settings` options (typed via `pkgs.formats.<fmt> {}` — e.g. `pkgs.formats.json {}` — plus a `freeformType` submodule that both validates a handful of explicitly-declared, documented options *and* accepts arbitrary extra keys of the right shape) in place of a single stringly `extraConfig` option that bypasses all type-checking. **Part 2** (not fully surveyed here — see §TOC) concerns balancing overall NixOS module *option count* against pushing more into `settings`. The RFC explicitly excludes config formats that can't be mapped to Nix values at all (bash scripts, arbitrary Python, etc.) from Part 1's applicability. The worked example given (a `services.foo` module) shows the now-standard idiom: `mkDefault` for values a user should be able to override cheaply (`log_level`), no default at all for values requiring `mkForce` to change safely (`data_path`, because a systemd `StateDirectory` assumption is baked in), and referencing `cfg.settings.user` downstream (e.g. in `users.users.<name>`) safely because a `mkDefault` on that key guarantees it's always defined.

### 14. nixpkgs `lib` deprecation mechanisms

Local exemplar: [`lib/trivial.nix`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/lib/trivial.nix), [`lib/modules.nix`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/lib/modules.nix), [`lib/derivations.nix`](file:///home/mherwig/.cache/research-lang/exemplars/nix/NixOS__nixpkgs/lib/derivations.nix), rev `9cab9ed8`.

- `lib.warn :: String -> a -> a` (`lib/trivial.nix`): documented as wrapping [`builtins.warn`](https://nix.dev/manual/nix/latest/language/builtins.html#builtins-warn), which is **Nix ≥ 2.23 only**. On older Nix, `lib.warn` emulates the 2.23 behavior with `builtins.trace`, "including the `NIX_ABORT_ON_WARN` behavior, but not the `nix.conf` setting or command line option" — an explicit, documented partial-compatibility gap the library authors accepted. `lib.warnIf cond msg` / `lib.warnIfNot cond msg` are the conditional variants; `lib.showWarnings` folds a list of warning strings over a value.
- `lib.nixpkgsVersion = warn "lib.nixpkgsVersion is a deprecated alias of lib.version." version;` (`lib/trivial.nix:547`) — a live, in-tree example of the pattern applied to a value, not just a module option.
- Module-option deprecation (`lib/modules.nix`): `mkRenamedOptionModule oldPath newPath` — warns (via `lib.warn`), keeps the option's old name working by wiring it to the new one; `mkRenamedOptionModuleWith` — a parameterized variant with version-tracking metadata; a private variant exists that renames **without** a warning ("Like `mkRenamedOptionModule`, but doesn't show a warning" — used internally for renames not expected to be user-visible-yet). `mkRemovedOptionModule oldPath replacementInstructions` — makes using the old option a hard eval-time failure with a custom message (nixpkgs' own example: `mkRemovedOptionModule [ "boot" "loader" "grub" "bootDevice" ] "<replacement instructions...>"`). `mkAliasOptionModule` — a **silent** alias (no warning at all) — and its `...MD` variant is itself deprecated (`lib.warn "mkAliasOptionModuleMD is deprecated and will..."`). `mkChangedOptionModule oldPath newPath (config: <arbitrary transform>)` — the most general form, for a rename that also needs a value transformation (e.g. a boolean becoming an enum).
- Package-level (not option-level) deprecation lives in `lib/derivations.nix`: `lib.derivations.warnOnInstantiate :: String -> Derivation -> Derivation` wraps every attribute of a derivation (except `meta`/`name`/`type`/`outputName`, and recursively through `overrideAttrs`) in a `lib.warn`, so that merely *referencing* the renamed attribute (not just building it) triggers the warning — nixpkgs' own worked example: `myPackage = warnOnInstantiate "myPackage has been renamed to my-package" my-package;`.

This four-function-plus-one taxonomy (rename-with-warning / remove-with-error / alias-silently / change-with-transform / warn-on-package-reference) is the complete "house style" for deprecation windows in nixpkgs and is directly transferable to how an ocx-generated flake should handle a renamed or removed upstream package between two generated versions.

### 15. Implementation divergence: CppNix, Lix, Determinate Nix

Primary sources: [Nix 2.35 release notes](https://nix.dev/manual/nix/2.35/release-notes/rl-2.35) (nix.dev, dated to the 2026-06-22 release); [Determinate Nix's lazy-trees docs](https://docs.determinate.systems/determinate-nix/lazy-trees/) (docs.determinate.systems, page dated 2026-09-25); [Lix's flake-stabilisation-proposal wiki page](https://wiki.lix.systems/books/development/page/flake-stabilisation-proposal) (wiki.lix.systems, undated, living document); secondary/community: [goldstein.lol, "The Great Nix Flake Check"](https://goldstein.lol/posts/great-nix-flake-check/).

Upstream **Nix 2.35** (2026-06-22) already made source-copying to the store lazier at the primitive level — "sources are copied to the store more lazily" via hash-before-copy — and `builtins.getFlake` now accepts a plain path (not just a flake reference string), enabling `builtins.getFlake ./subflake`; `builtins.fetchTarball` similarly stopped eagerly copying.

**Determinate Nix 3.5.2** (per its own docs, current/default as of 2026-09-25) ships a materially different and more aggressive mechanism called **"lazy trees"**: a virtual filesystem that "scopes file copying to what the specific expression demands — and nothing more," claimed to produce "reductions in wall time of 3x or more and reductions in disk usage of 20x or more" for large repos like nixpkgs. This is **stable and on-by-default in Determinate Nix only** — not in CppNix, not in Lix.

**Lix**, per its own contributor wiki, is separately planning a stricter, versioned flake schema (`flake.lix` for the "version range" manifest, `flake.lick` replacing `flake.lock` with SemVer-style versioning instead of the current monotonic integer) and — most consequentially for consumer UX — its proposal text says outright that the **`follows` mechanism** ("the follows mechanism is horrible... let's just not do that") may not survive into Lix's stabilized flake schema, with input parameters becoming explicit arguments instead of embedded-in-URL query parameters.

The community survey at goldstein.lol (undated but referencing 2026-era tooling) measured flake-lock **resolution** success rates across implementations on the same corpus: CppNix's native resolver ~70% full success, Lix ~68%, the third-party `unflake` tool 57-59% — attributed by the author to flakes having "no specification" and being "barely documented," meaning implementations diverge on genuinely undocumented edge cases, not just on deliberately-different features.

Net effect for a published flake: at least three independent axes of implementation divergence exist simultaneously today (store/evaluation laziness, flake-schema/lock-file format, and `follows`/input-resolution semantics), and only one of the three (`follows`) is close to nixpkgs' own documented consumer-facing surface — the other two are internals a flake author can be affected by without ever intentionally opting in.

## Recent shifts seen in this corpus

- **nixfmt 1.3.0 (2026-05-26)**: the `nixfmt-rfc-style` package/attribute name was folded back into plain `nixfmt`. Any material written before mid-2026 that says "use `pkgs.nixfmt-rfc-style`" is citing a name that no longer exists as the primary attribute (git-hooks.nix still exposes `nixfmt-rfc-style` as a distinct, separately-configurable legacy hook option — so the *name* survives there, but as an alias, not the source of truth).
- **nixfmt 1.4.0 (2026-07-07)**: introduced the `/*nixfmt:disable*/`/`/*nixfmt:enable*/` region-exclusion directive — the first sanctioned escape hatch from the formatter, previously nonexistent.
- **nixfmt 1.5.0 (2026-09-10)**: fixed an exponential-parse-time bug on nested set-parameter defaults — a correctness bug in the formatter itself, present until 11 days before this survey's date.
- **Nix 2.35 (2026-06-22)**: `builtins.getFlake` gained direct path support (`builtins.getFlake ./subflake`); source-to-store copying became lazier at the hashing level; `nix flake check` gained `--print-out-paths`. This invalidates any older advice implying `getFlake` only accepts flake-reference strings.
- **Determinate Nix 3.5.2 (dated to Feb 2026 per community sources, stable/default by 2026-09-25)**: "lazy trees" — a Determinate-only virtual-filesystem mechanism, not present in CppNix 2.35 or in Lix, and explicitly *not planned* to be adopted upstream verbatim by Lix ("a functionally equivalent replacement is planned" instead). Any performance claim ("flakes are fast because sources are lazy") needs an implementation qualifier after this date.
- **nixpkgs-vet ratchets** (ongoing, RFC 140-era, still active as of the 2026-09-27 exemplar): `strictDeps = true` and `__structuredAttrs = true` are enforced one-way for any *new* top-level package — meaning the "old" idiom of leaving both unset/false is closing off for new code even though it remains legal for pre-existing packages.
- **Lix flake-stabilisation proposal** (undated, living document, contributor-wiki not an accepted RFC): explicit intent to replace `flake.lock` with a `flake.lick`/`flake.lix` pair and to reconsider (possibly drop) `follows` — not yet shipped, but a documented direction that invalidates "follows works the same everywhere" as a forward-looking assumption.
- **statix repository migration** (as of the 2026-09-27 README fetch): the canonical repo has moved to a Tangled forge, and the nixpkgs `statix` package now builds from a Molybdenum Software fork rather than `oppiliappan/statix` directly — a maintenance-status shift that should make a rule cite the *tool's behavior* (verified against the installed binary) rather than pin a single GitHub URL as ground truth.

## Contested

- **Whether `follows` is good flake design at all.** Current, universal practice (every exemplar multi-input flake) treats `inputs.X.follows = "nixpkgs"` as the correct fix for duplicate-nixpkgs-instance bloat. Lix's own contributors call the mechanism itself "horrible" and are planning to route around it entirely in a stabilized schema. Trend: unresolved — CppNix and Determinate Nix show no sign of following Lix here, so this is more likely to become a **three-way implementation divergence** than a industry-wide correction.
- **`nixfmt` vs. `alejandra`.** RFC 166 designated `nixfmt` the official/standard formatter, and nixpkgs' own CI enforces it exclusively. `alejandra` predates that RFC and remains a maintained, independent alternative (still present in treefmt-nix's formatter roster). Trend: settled in nixpkgs' own domain (nixfmt only), unsettled in the wider ecosystem — a rule for *generated, non-nixpkgs* flakes cannot assume `alejandra` usage is a mistake, only that it diverges from the RFC-166 standard.
- **Whether "passes `nix flake check`" is a meaningful correctness bar.** The built-in checker enforces real, hard-error-level derivation-shape correctness (verified live in §7) but only ever *warns* on unrecognized top-level attributes and does not validate `formatter`'s shape at all. Community sentiment (goldstein.lol) trends toward "flakes need a real specification," implying the *current* built-in checker is viewed as necessary but not sufficient by at least part of the ecosystem.
- **Store-copy laziness as a single behavior vs. three different mechanisms.** Marketing language ("flakes are lazy now") elides that upstream Nix 2.35's hash-before-copy, Determinate Nix's lazy trees, and Lix's own (different, not-yet-shipped) plan are three distinct engineering efforts with different scopes and guarantees. No consensus yet on a shared implementation or shared terminology across the three projects.
- **`overrideAttrs`'s status.** Explicitly discouraged for new in-tree nixpkgs code (five stated reasons) but explicitly endorsed for downstream/out-of-tree code in the same document. An agent that only sees nixpkgs source risks importing the in-tree prohibition into contexts (like a generated, non-nixpkgs flake) where the opposite guidance applies — not a disagreement between sources, but a single source whose scope is easy to over-generalize.
