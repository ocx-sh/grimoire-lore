## Summary

- Every generated-flake exemplar vendors a **committed data file** (`sources.json`, `versions.json`, `manifests/*.nix`, `data/*.json`) plus a **small reader** plus a **scheduled CI updater** — this is a stable, load-bearing pattern across all eight repos, confirming H5.
- None of the eight generators fetch OCI images directly; the one OCI-shaped fetch in this corpus is nixpkgs' own `dockerTools.pullImage`, which wraps `skopeo copy docker://<imageName>@<imageDigest>` in a fixed-output derivation — that is the closest template for an ocx blob fetcher, not any of the index generators themselves.
- `nix-update --flake` requires **inline** `version`/`hash` attributes in `package.nix`; a generator that stores version/hash data in a separate committed JSON file (the exemplar norm) cannot use `nix-update` directly and must write its own updater or a declarative config it interprets itself.
- llm-agents.nix's `passthru.updater` (kind: `github-source` | `npm` | `bun-github` | `platform` | `manifest` | `manifest-checksums`, each with its own required-fields schema validated at eval time) is the most direct existing template for "one declarative shape drives N packages' updates" — closer to the ocx shape than any of the other seven repos.
- Upstream deletion/rename is handled two different ways in this corpus: zig-overlay never deletes historical `sources.json` entries (its update script does a JSON merge, never a full overwrite) and instead documents gaps in a FAQ; nix-vscode-extensions maintains an explicit `removed.nix` allow-list plus an `extensionsProblematic` override list for entries that no longer round-trip cleanly through nixpkgs' own builder.
- `nixpkgs-python`'s README explicitly tells consumers **not** to override its `nixpkgs` input, because its Cachix cache is tied to one pinned revision — this directly contradicts a blanket "always add `inputs.nixpkgs.follows`" rule (tests H2: `follows` is not universally correct for a binary-artifact-shipping flake).
- Prebuilt-binary packaging in this corpus needs three different fixups depending on platform: Linux ELF needs `autoPatchelfHook` (interpreter + rpath) or an equivalent in-repo hook; macOS Homebrew-bottle-sourced binaries need `install_name_tool` rpath rewriting **and** `codesign -f -s -` re-signing before they'll run; a source-built package needs neither.
- llm-agents.nix explicitly forbids `autoPatchelfHook` project-wide in favor of an in-repo `formatelf` hook — a minority position among prebuilt-binary packagers, not the nixpkgs-wide default, so it is a project choice to flag rather than copy uncritically.
- `meta.sourceProvenance = [ lib.sourceTypes.binaryNativeCode ]` is purely informational metadata in nixpkgs — it gates nothing structurally by itself and must be paired with an explicit `license`/`allowUnfreePredicate` decision if the binary is not redistributable-by-default.
- FlakeHub's `latest` resolution is **highest-semver-wins**, not most-recent-publish-wins: a documented July 2026 case (imTHAI/nix-packages, package `mist`) shows that once ANY real tag ≥ 0.2.0 exists, every subsequent 0.1.N "rolling" release becomes permanently invisible to unpinned consumers — this is a sharp, dated trap for exactly the "rolling releases are simpler" assumption in H4.
- Three of eight generators (fenix, nixpkgs-terraform, nixpkgs-python) run their scheduled updater under a **GitHub App token** (`actions/create-github-app-token`) rather than the default `GITHUB_TOKEN`, specifically so the resulting commit/PR can trigger further workflows and carry write permissions the default token withholds.
- `nix flake check --all-systems --no-build` is the standard CI gate for a large generated flake (nix-index-database explicitly comments why: it evaluates every attribute to a derivation across every system without paying build cost) — but it does **not** catch a wrong fixed-output hash; that only surfaces at `nix build` time.
- Version-range aliasing (nixpkgs-terraform's `"1.5"` → latest `1.5.x`; nixpkgs-python's `"3.11"` → latest patch) is a recurring consumer-UX feature none of niv/npins/nvfetcher provide out of the box — a generator that wants it must build the alias resolution itself.
- rust-overlay caps its own historical depth ("nightly/beta not earlier than `{current_year-1}-01-01`... earlier versions via old snapshot tags") specifically to control repository size growth — an explicit rebuttal to "never prune, keep every version forever."
- Three separate ast-grep lint rules in llm-agents.nix (`prefer-tag-over-rev`, `no-unpinned-rev`, `no-legacy-sha256`) encode fetcher-pinning mistakes as CI-enforced, not just documented, conventions — a pattern an ocx generator's own CI could copy directly.
- `nixConfig.extra-substituters`/`extra-trusted-public-keys` **is** shipped in `flake.nix` by three of eight generators (nixpkgs-terraform, nixpkgs-python, fenix's Cachix use) as ordinary, documented practice, not universally treated as the "trap" H8 frames it as — contested, see below.
- devbox/nixhub.io and lazamar's catalog solve a different problem than any of these eight generators: they index **nixpkgs' own Hydra build history** to map package+version → nixpkgs commit; they carry no relevance to ocx, which owns its index and its own binaries outside nixpkgs entirely (covered-elsewhere for the ocx use case, contra a naive reading of H's brief).
- No exemplar in this corpus authenticates against ghcr.io from a fetcher directly with a bearer token fetched at eval time; the only ghcr.io-adjacent pattern present (`dockerTools.pullImage`) delegates all registry auth to `skopeo`, which negotiates the anonymous bearer-token flow itself — an ocx-index generator inherits that same delegation-to-skopeo option, or must implement Docker Registry v2 token auth itself in a build script if it wants a plain `fetchurl`.
- Every generator with a binary cache (fenix/Cachix, nixpkgs-terraform/Cachix, nixpkgs-python/Cachix) states the cache only helps if the consumer's `nixpkgs` pin is close enough to the one the cache was built against; none of the eight claims cache hits are guaranteed across nixpkgs revisions.

## Survey

### 1. zig-overlay

[mitchellh/zig-overlay](https://github.com/mitchellh/zig-overlay) mirrors Zig's official prebuilt compiler releases: `README.md` lists the outputs `packages.<version>` (tagged release), `packages.master` (latest nightly), `packages.master-<date>`, `packages.brew.<version>` (macOS-only Homebrew-bottle build), `overlays.default`, and `templates.compiler-dev`.

The `update` script (`nix-shell -p coreutils curl jq minisign`) fetches `ziglang.org/download/index.json`, then re-fetches the **versioned** `zig-<version>-index.json` plus its `.minisig` and verifies it against a hardcoded public key (`RWSGOq2NVecA2UPNdBUZykf1CCb147pkmdtYxgb3Ti+JO/wCYvhbAb/U`) with `minisign -V -P <key> -x ... -m ...` before trusting any hash; for release-only entries not covered by the signed index, it downloads and verifies **every individual tarball's** `.minisig` before computing `sha256sum` itself. The final `sources.json` merge is `jq -s '.[0] * .[1]'` of old and new — a merge, never an overwrite, so historical nightlies are retained indefinitely.

`default.nix`'s `mkBinaryInstall` builds a plain `stdenv.mkDerivation` around `pkgs.fetchurl { inherit urls sha256; }`, trying community `mirrors.json` URLs before falling back to the canonical `ziglang.org` URL, and reuses `import "${nixpkgs}/pkgs/development/compilers/zig/passthru.nix"` so its `passthru` matches nixpkgs' own zig package shape. `mkBrewInstall` (macOS only) fetches Homebrew bottles with `curlOptsList = ["-H" "Authorization: Bearer QQ=="]` (Homebrew's public anonymous-bottle auth convention), then does `install_name_tool -id/-change/-add_rpath` to rewrite every `@@HOMEBREW_PREFIX@@`/`/opt/homebrew` reference to `@rpath`, and finally `codesign -f -s -` (ad-hoc self-sign) on the patched binary and every bundled `.dylib`, with an explicit `grep` guard that fails the build if any Homebrew reference survives.

`.github/workflows/update.yml` runs `cron: '0 */12 * * *'`, `cachix/install-nix-action@v31`, then `git add mirrors.json sources.json`, exits 0 on no diff, else commits and pushes to `main` directly with `GITHUB_TOKEN`-level permissions (`permissions: contents: write`).

### 2. rust-overlay

[oxalica/rust-overlay](https://github.com/oxalica/rust-overlay) reads `static.rust-lang.org/dist` `channel-rust-{stable,beta,nightly}.toml` manifests (Rust's own release-channel TOML format) via `scripts/fetch.py`. Its README states the design goal explicitly: *"Hashes of toolchain components are pre-fetched in tree, so the evaluation is pure and no need to have network access. These hashes are auto-updated daily using GitHub Actions."* It states its retention policy in the README: *"Current oldest supported stable version is 1.29.0... Current oldest supported nightly version is 2025-01-01. To prevent significant repository size bloating, our current strategy is keep only nightly and beta versions not earlier than `{current_year - 1}-01-01`. Earlier versions may be accessed via old snapshot tags."*

`scripts/fetch.py` compresses the manifest data into three side tables (`manifests/targets.nix`, `manifests/renames.nix`, `manifests/profiles.nix`) that dedupe repeated target/profile/rename strings across thousands of toolchain entries into small integer-indexed lookup tables — a deliberate data-model choice to keep the generated `.nix` diff small as the corpus grows (`manifests/targets.nix` "compress_target", "compress_renames", "compress_profiles" functions in [scripts/fetch.py](https://github.com/oxalica/rust-overlay/blob/master/scripts/fetch.py)).

`.github/workflows/sync-channels.yaml` runs 3 crons/day (`'0 2 * * *'` nightly, `'0 14-20 * * THU'` stable, hourly during the Thursday stable-release window — the comment explains *"there are some stable users eagerly want to use the latest stable and cannot afford a lengthy 24hrs delay"*), runs `nix-instantiate --parse` on every changed `.nix` file as a fast syntax gate before committing, and runs a `hello-world` example build+`make run` smoke test before pushing. `update-stable.yaml` only fast-forwards a separate `stable` branch when the diff versus `origin/master` touches files *other than* `manifests/(nightly|beta)`, `docs/`, `README.md` — i.e., it explicitly excludes noisy nightly/beta churn from the stable-branch history.

### 3. fenix

[nix-community/fenix](https://github.com/nix-community/fenix) mirrors Rust toolchains from the same `static.rust-lang.org/dist` manifests, targeting `minimal`/`default`/`complete`/`latest` profiles plus `rust-analyzer`. Its `update` script (Python, stdlib `tomllib` + `urllib`) walks backward day-by-day through `channel-rust-nightly.toml` snapshots until every target/profile/component it needs resolves, explicitly skipping `rustc-docs`/`rustc-codegen-cranelift-preview` gaps rather than blocking the whole nightly on one missing component.

Its CI shape is a three-workflow relay: `update.yml` (`cron: "0 6 * * *"`, checks out a `staging` branch, runs `./update && nix flake update`, force-commits) → `ci.yml` (triggered by `workflow_run: [update]`, matrix over `macos-latest`/`ubuntu-latest` × `["", "--override-input nixpkgs github:nixos/nixpkgs/nixpkgs-unstable"]`, runs `nix flake check` then builds `.#{stable,beta,minimal,default,complete}.toolchain,rust-analyzer{,-vscode-extension}}` and `.#latest.toolchain`) → `merge-staging.yml` (triggered by `workflow_run: [ci]`, `if: conclusion == 'success'`, fast-forwards `staging` into `main`). A fourth, `monthly.yml`, force-resets a `monthly` branch to `main` once a month and separately pushes to FlakeHub with `DeterminateSystems/flakehub-push@v7` `rolling: true`. README notes a real cache-invalidation footgun: *"the nixpkgs from your system will be used when fenix is being used as an overlay, which may not be cached if you are using a stable/older version of nixpkgs"* and gives a workaround importing `fenix.inputs.nixpkgs.legacyPackages` explicitly.

### 4. nix-index-database

[nix-community/nix-index-database](https://github.com/nix-community/nix-index-database) is not a package-version generator but an artifact-of-a-build generator: it publishes a weekly [`nix-index`](https://github.com/nix-community/nix-index) file-database as a **GitHub Release** binary blob, not a Nix store path with a build recipe. Its README states a hard version floor: *"Nix 2.18 or newer: In our packages we make use of `unsafeDiscardReferences` to skip the nix store checks. On older nix version these packages might fail."* It ships two variants side by side, `nix-index-with-db` (full) and `nix-index-with-small-db` (`--filter-prefix '/bin/'`-only), so consumers can trade completeness for download size — a template for an ocx flake wanting a "small" vs "full" package set split.

`.github/workflows/update.yml` is a five-job pipeline: `update-lock` (`nix flake update --commit-lock-file`, pushed straight to `main`) → `create-release` (a **draft** GitHub release, dated `%Y-%m-%d-%H%M%S`) → `index` (matrix over `x86_64-linux`/`aarch64-linux`/`aarch64-darwin`, runs `nix run github:nix-community/nix-index#nix-index`, then hashes the produced file with `nix store prefetch-file "file://$PWD/index-${{ matrix.system }}" --json | jq -r .hash`, and uploads both index files to the still-draft release) → `update-generated` (writes `generated.nix` — literally a heredoc `cat > generated.nix <<EOF ... EOF` embedding the release URL template and per-system hashes, comment `# this file is autogenerated by .github/workflows/update.yml` — then runs `nix flake show --all-systems` and `nix flake check -L --all-systems --no-build` as a smoke test before committing) → `finalize-release` (flips the GitHub release from draft to published via `github.rest.repos.updateRelease`). `flake.nix` also demonstrates the deprecation idiom for a renamed output: `hmModules.nix-index = lib.warn "nix-index-database: flake output \`hmModules\` has been renamed to \`homeModules\`" ./home-manager-module.nix;` — old name kept, wrapped in `lib.warn`, pointing at the new one.

### 5. nix-vscode-extensions

[nix-community/nix-vscode-extensions](https://github.com/nix-community/nix-vscode-extensions) crawls the VS Code Marketplace and Open VSX daily. Its README states an explicit ToS constraint most generators in this corpus don't have to worry about: *"We have a permission from MS to use a crawler on their API (see the [discussion](https://github.com/NixOS/nixpkgs/issues/208456)). Don't abuse this flake!"* — and separately documents a **nixpkgs 26.11 platform-support regression** it inherited: *"[`x86_64-darwin` was dropped in `nixpkgs` 26.11](https://github.com/NixOS/nixpkgs/blob/c1fe1675b8c7d1dfa4a9752fc36e2657d67d46be/doc/release-notes/rl-2611.section.md#backward-incompatibilities-sec-nixpkgs-release-2611-incompatibilities)."*

`nix/mkExtension.nix` reuses nixpkgs' own `pkgs.vscode-utils.buildVscodeMarketplaceExtension`/`buildVscodeExtension` via a custom `makeOverridable` wrapper, and imports nixpkgs' extension `default.nix` directly by store path (`pathNixpkgs + "/pkgs/applications/editors/vscode/extensions/default.nix"`) so upstream fixes are inherited rather than duplicated — but maintains two explicit override lists for entries that don't round-trip: `extensionsProblematic` (extensions whose nixpkgs expression closes over arguments before the point a caller can override them) and, in `nix/removed.nix`, a per-`system` removed-extension list (e.g. `aarch64-darwin.["yzane.markdown-pdf"]`) with inline comments linking the exact upstream nixpkgs lines that make it unbuildable on that platform. `nix/semver.nix` implements SemVer 2.0.0 precedence comparison from scratch in Nix (`builtins.match` against the official SemVer regex, adapted for Nix's regex dialect — no `?:`, no `\d`) purely to compare extension versions, because `lib.compareVersions` doesn't parse SemVer prerelease/build-metadata precedence.

`.github/workflows/ci.yaml` pins `nix_version: "2.31.2"` via `nixbuild/nix-quick-install-action@v34`, uses `nix-community/cache-nix-action` with a `primary-key` hashed over `*.{nix,lock}` plus the marketplace data-cache JSON so cache keys invalidate exactly when the crawled data changes, and separately runs `nix run ./nix-dev#saveFromGC.ci.jobs.<job>` before any GC-triggering step specifically to keep the attributes-under-test alive through the run.

### 6. llm-agents.nix

[numtide/llm-agents.nix](https://github.com/numtide/llm-agents.nix) packages ~250 AI coding-tool binaries and its own docs (`AGENTS.md`) state the update policy directly: *"Prefer `nix-update` over custom update scripts... For this to work, `package.nix` must have version/hash attributes inline (not loaded from JSON)... When `nix-update` cannot handle the package, prefer a declarative `passthru.updater` config... Only fall back to a custom `update.py` script when no declarative kind fits."*

`lib/mk-updater.nix` validates that config against a `requiredByKind` map at eval time (kinds: `github-source` needs `purl`+`depHashKey`; `npm` needs `purl`; `bun-github` needs `purl`; `platform` needs `versionSource`+`urlTemplate`+`platforms`; `manifest` needs `manifestUrl`+`platformMap`; `manifest-checksums` needs `versionSource`+`manifestUrl`+`checksumPath`+`platforms`) and `throw`s a specific missing-field error rather than failing later at update time. `lib/mk-update-script.nix` turns a validated config into a `writeShellApplication` that runs `python3 -m updater.run --pkg-dir packages/<name> --config <json>`, with `PYTHONPATH`/`SSL_CERT_FILE` set so the updater carries its own tools instead of depending on CI environment state. `lib/platform-source.nix` is the `platform`-kind implementation: it reads a per-package `hashesFile` JSON (`{version, hashes.<system>}`), maps Nix system strings to upstream URL template variables (`{ os = "linux"; cpu = "x86_64"; }` or a bare platform string shorthand), and returns both the build `src` **and** a matching `updater` fragment built from the *same* `urlTemplate`+`platforms` map — a deliberate anti-drift measure ("build and updater never diverge", per the file's own header comment) that answers directly to the boring-but-biting failure mode of a generator's build path and update path silently disagreeing about the source of truth.

`.github/ci/update.py` sandboxes the updater with `bwrap` on Linux (`--ro-bind / /`, fresh tmpfs `/tmp` and `HOME`, `--bind /nix /nix`, `--bind <pkg-dir> <pkg-dir>`, `--die-with-parent`), with an `UPDATE_SANDBOX=0` escape hatch and a documented Ubuntu-24.04-runner workaround (`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`) for AppArmor blocking unprivileged user namespaces. `has_declarative_updater()` probes for a package's updater via `nix eval .#packages.x86_64-linux.<name>.updater --apply "_: true"` rather than a file-existence check, so the flake's own evaluation is the source of truth for "does this package know how to update itself."

Three of the repo's ast-grep rules encode fetcher-pinning discipline as CI-enforced checks rather than only documented conventions: [`prefer-tag-over-rev.yml`](https://github.com/numtide/llm-agents.nix/blob/main/rules/prefer-tag-over-rev.yml) (*"A bare `rev` fetches the ambiguous `archive/<rev>.tar.gz` URL, which breaks when a repo has both a branch and a tag of that name"*), [`no-unpinned-rev.yml`](https://github.com/numtide/llm-agents.nix/blob/main/rules/no-unpinned-rev.yml) (bans `rev`/`ref` literal `main|master|HEAD|trunk|develop`), and [`no-legacy-sha256.yml`](https://github.com/numtide/llm-agents.nix/blob/main/rules/no-legacy-sha256.yml) (bans bare `sha256`/`cargoSha256`/`vendorSha256` attrs in favor of SRI `hash = "sha256-..."`). A fourth, [`use-formatelf.yml`](https://github.com/numtide/llm-agents.nix/blob/main/rules/use-formatelf.yml), *bans* `autoPatchelfHook` project-wide in favor of an in-repo `formatelf` hook ("a drop-in replacement"). `lib/check-package.nix` is a per-package `runCommand` check enforcing an "FHS-like top level only" output-layout invariant (`bin|sbin|lib|lib64|libexec|share|include|etc|opt|Applications|nix-support` — anything else at `$out/*` fails the check, citing nixpkgs issue #9364 about `buildEnv` profile collisions). `AGENTS.md` also states a hard metadata requirement: `changelog` is **required** ("our updater uses it to generate release notes") and gives `meta.sourceProvenance = with lib.sourceTypes; [ fromSource ];` as the expected shape even for a repo whose packages are overwhelmingly prebuilt binaries elsewhere — i.e., `fromSource` there marks the *packaging expression*, not the upstream binary's build provenance.

### 7. nixpkgs-terraform

[stackbuilders/nixpkgs-terraform](https://github.com/stackbuilders/nixpkgs-terraform) exposes every Terraform release as `packages.${system}."X.Y.Z"` plus a cycle alias `"X.Y"` pointing at the latest patch, from a committed `versions.json` (`{ hash, vendorHash }` per version, both SRI). Its README documents a licensing-driven consumer-UX flip: *"Starting with version `4.0.0`, this project enables `allowUnfree` by default in order to build Terraform versions with a [BSL license]"* — the underlying package's relicense (MPL → Business Source License) forced the flake to change its own default rather than a Nix-side technical decision. `lib/default.nix` implements this precisely: `pkgs.lib.warnIf (compareVersions version "1.6.0" >= 0) "allowUnfree is enabled to build version ${version}" pkgs.mkTerraform {...}` — the unfree gate and the user-facing warning are both keyed off the *package version being built*, not a repo-wide flag, and three different nixpkgs pins (current, `nixpkgs-24_05`, `nixpkgs-23_05`) are selected by version range because older Terraform needs an older nixpkgs' `mkTerraform`. It also patches Terraform's provider-path lookup per major-version band (`patches/provider-path-{0_15,1_9,1_14}.patch`), and its README explicitly documents a cache-hit caveat: *"Only the most recent versions for each release cycle are pushed to the binary cache; if you are having trouble hitting the cache, try upgrading to the most recent patch version."*

`.github/workflows/update.yml` runs a Go CLI (`cli/cli update`) under `devenv shell`, authenticated as a **GitHub App** (`actions/create-github-app-token@v3`) rather than the default token, and opens a PR via `peter-evans/create-pull-request@v8` with named human reviewers rather than pushing to `main` directly or auto-merging — the update loop here always goes through review. A separate `release.yml` (triggered by `workflow_run: [Build]` succeeding) runs `semantic-release` under the same App token to cut the actual release/tag. A `notify` job posts a Slack webhook only `if: failure()`.

### 8. nixpkgs-python

[cachix/nixpkgs-python](https://github.com/cachix/nixpkgs-python) exposes every CPython (and some ActiveState-patched 2.7.x) release as `packages.${system}."X.Y.Z"` with a `"X.Y"` latest-patch alias, sourced from a committed `versions.json` (`{hash (base64 sha256), url}`) built by `scripts/update.py` against `endoflife.date/api/python.json` plus `api.github.com/repos/ActiveState/cpython/releases`, with an explicit skip-list for versions whose distutils/openssl patches are known not to apply (`"2.7.0".."2.7.5"`, `"3.3.0"`, `"3.9.0"`). Its README states the single sharpest "don't do what H2 assumes" line in this whole corpus: *"Do not override the `nixpkgs` input when using this flake. The cached builds are tied to the pinned nixpkgs revision; overriding it will result in cache misses and local rebuilds."*

Its non-flake entry point is the canonical `flake-compat` idiom: `default.nix` reads `flake.lock`'s `nodes.flake-compat.locked.{rev,narHash}`, does `fetchTarball {url = ".../archive/${rev}.tar.gz"; sha256 = narHash;}`, and returns `.defaultNix` — this lets a pre-flakes `nix-shell`/`nix-build` consumer use the same expressions with zero duplication.

`.github/workflows/build.yml` runs on a matrix of **self-hosted** runners (`[self-hosted, linux, X64]`, `[self-hosted, macOS, ARM64]`, `[self-hosted, linux, ARM64]`) plus one GitHub-hosted `macos-15-intel`, and treats individual Python-build failures as non-fatal to the CI *job* (captures a JSON build-results report, writes a Markdown summary to `$GITHUB_STEP_SUMMARY`, and only fails the step if the JSON itself is malformed — "Script completed successfully. Individual build failures are tracked in the summary" is an explicit design choice to distinguish "our tooling broke" from "one Python 2.6 patch bitrotted"). `update.yml` again uses a GitHub App token and `peter-evans/create-pull-request@v8`, then immediately calls `peter-evans/enable-pull-request-automerge@v3` on the freshly created PR — auto-merge is opted into per-PR, not repo-wide.

### 9. nixpkgs itself

[NixOS/nixpkgs](https://github.com/NixOS/nixpkgs) `pkgs/build-support/docker/default.nix` defines `pullImage` as a `lib.fetchers.withNormalizedHash` wrapper around a `runCommand` fixed-output derivation: `sourceURL = "docker://${imageName}@${imageDigest}"`, `nativeBuildInputs = [ skopeo ]`, `impureEnvVars = lib.fetchers.proxyImpureEnvVars`, `outputHashMode = "flat"`, and the build script is literally `skopeo --insecure-policy --tmpdir=$TMPDIR --override-os ${os} --override-arch ${arch} copy --src-tls-verify=${tlsVerify} "$sourceURL" "docker-archive://$out:$destNameTag"`. All registry authentication (including ghcr.io's anonymous bearer-token exchange for public images) is delegated entirely to `skopeo`; the Nix side supplies only the digest and the resulting hash. `lib/fetchers.nix` documents *why* `proxyImpureEnvVars` (`http_proxy`, `https_proxy`, `ftp_proxy`, `all_proxy`, `no_proxy` and uppercase variants) is safe to read impurely inside an FOD: *"a fixed-output derivation like fetchurl is allowed to do so since its result is by definition pure."*

[`doc/hooks/autopatchelf.section.md`](https://github.com/NixOS/nixpkgs/blob/master/doc/hooks/autopatchelf.section.md) documents `autoPatchelfHook`'s exact knobs: `runtimeDependencies` (unconditionally added to every executable's rpath — for `dlopen`'d libraries autoPatchelf can't see statically), `dontAutoPatchelf` (skip entirely), `autoPatchelfIgnoreMissingDeps` (a list of sonames to ignore, or `[ "*" ]` for all), and a `--no-recurse` flag. [`doc/stdenv/meta.chapter.md`](https://github.com/NixOS/nixpkgs/blob/master/doc/stdenv/meta.chapter.md#sec-meta-sourceProvenance) is explicit that `meta.sourceProvenance` is **presence-only, not absence-guaranteed** metadata: *"The presence of a particular sourceType... indicates that the package contains some components falling into that category, though the absence of that sourceType does not guarantee the absence of that category... A package with no `meta.sourceProvenance` set implies it has no known sourceTypes other than `fromSource`."* and *"The meaning of the `meta.sourceProvenance` attribute does not depend on the value of the `meta.license` attribute"* — i.e. it is orthogonal to, not a substitute for, the unfree/license gate.

`maintainers/scripts/update.nix` is the entry point r-ryantm and manual invocations both use (`nix-shell maintainers/scripts/update.nix --argstr package <name>`), and its own header comment points at `https://nixos.org/manual/nixpkgs/unstable/#var-passthru-updateScript` as the canonical spec for what `passthru.updateScript` must be (a program, run with no arguments, that edits the package's own source file in place).

### 10. Version-pinning tools

[niv](https://github.com/nmattia/niv) (the oldest of these, predates flakes-first workflows) pins arbitrary sources — GitHub/GitLab repos, arbitrary tarballs/URLs, local paths — into a committed `nix/sources.json` plus a small `nix/sources.nix` reader, with a `niv update`/`niv add`/`niv drop` CLI; it is explicitly the design ancestor both `npins` and the zig-overlay/rust-overlay/nixpkgs-terraform/nixpkgs-python `sources.json`/`versions.json` pattern trace back to. [npins](https://github.com/andir/npins) positions itself as niv's successor: *"Track git branches; Track git release tags (must roughly follow SemVer; GitHub/GitLab releases are intentionally ignored); For git repositories hosted on GitHub or GitLab, `fetchTarball` is used instead of `fetchGit`; Track Nix channels... Track PyPi packages."* — notably it deliberately ignores GitHub/GitLab "Releases" as a version source, tracking tags directly instead. [nvfetcher](https://github.com/berberman/nvfetcher) is a different point in the design space: a Haskell/Shake-based tool driven by a TOML config (`src.github`, `fetch.github`, and a `cargo_lock` key that also computes `outputHash`es for a Rust package's vendored git dependencies) that emits `_sources/generated.nix`, explicitly layering on top of [nvchecker](https://github.com/lilydjwg/nvchecker) for the "is there a new version" detection step rather than reimplementing per-forge version discovery itself.

[nurl](https://github.com/nix-community/nurl) is narrower and more mechanical: given a repo URL and a ref, it emits the correct fetcher call (`fetchFromGitHub`, `fetchFromGitLab`, `fetchFromBitbucket`, `fetchCrate`, `builtins.fetchGit`, etc.) with `owner`/`repo`/`tag`/`hash` filled in — its README frames [nix-init](https://github.com/nix-community/nix-init) (which builds on nurl) as the tool for generating whole packages, positioning nurl itself as the fetcher-call primitive underneath a bigger generator, not a generator itself.

[nix-update](https://github.com/Mic92/nix-update) is the tool most of this corpus's *own* documentation (llm-agents.nix's `AGENTS.md`) tells contributors to prefer over a bespoke script, but its feature table is explicit about the shape it needs: version/hash detection across BitBucket/Codeberg/crates.io/Gitea/GitHub/GitLab/npm/PyPi/RubyGems/Sourcehut/Savannah, and per-ecosystem hash flags it knows how to update in place — `cargoHash`/`cargoSha256`/`cargoLock` (Rust), `vendorHash`/`vendorSha256` (Go), `npmDepsHash` (npm), `pnpmDeps` (pnpm), `vendorHash` (PHP Composer), `mvnHash` (Maven), `mixFodDeps` (Elixir), `yarnOfflineCache`/`offlineCache` (Yarn/Yarn Berry), `zigDeps`, `nugetDeps` (.NET) — plus `--flake` to update flake outputs and `--use-update-script` to run an existing `passthru.updateScript` instead. Because all of this operates by editing attributes it finds **inline in a `.nix` file**, it structurally cannot be pointed at "the version lives in a separate committed JSON the flake reads at eval time" — the architecture every one of the eight generator exemplars actually uses.

### 11. OCI tooling

[nix-ld](https://github.com/nix-community/nix-ld) solves the opposite direction of the ocx problem (running an *unpatched* dynamic binary that expects `/lib64/ld-linux-x86-64.so.2` to exist, by providing a real dynamic loader NixOS otherwise lacks at that path) and its README frames its own scope directly against the alternatives an ocx flake generator would otherwise reach for: *"Use binary executable downloaded with third-party package managers... without having to patch them on every update... While there are other solutions such as `buildFHSUserEnv`... these sandboxes have their own weaknesses: setuid binaries cannot be executed inside a fhsuserenv; inside a `buildFHSUserEnv` you can not use other sandbox tools like bwrap or `nix build`; `buildFHSUserEnv` requires a subshell which does not work well with direnv."* This is the tool ocx's own FAQ already points NixOS users at for libc-detection problems (per the frame); it is a *consumer-side* runtime fix, not something an ocx-generated flake would itself package.

[nix2container](https://github.com/nlewo/nix2container) and [nix-snapshotter](https://github.com/pdtpartners/nix-snapshotter) both target the "build and push a container image without nixpkgs' heavier `dockerTools.buildImage`" niche — nix2container's README states its goal as *"an efficient container development workflow with images built by Nix: it doesn't write tarballs to the Nix store and allows to skip already pushed layers"*; nix-snapshotter integrates with containerd's snapshotter API so images can be pulled by *reference to a Nix store path* without a registry round-trip at all (*"Provides CRI Image Service to allow Kubernetes to 'pull images' from a Nix store, allowing you to run containers without a Docker Registry"*). Neither tool is a generator or a fetcher into Nix — both assume you already have Nix-built content and want to get it *into* an OCI-consuming system, the reverse direction from ocx's "pull a prebuilt binary blob published as an OCI artifact into Nix." They are relevant to ocx only as the wrong tool for this specific job (worth naming explicitly so a future author doesn't reach for them by category-matching on "OCI + Nix").

### 12. External catalogs

[Devbox/Nixhub.io](https://www.jetify.com/blog/introducing-nixhub) and Devbox's own explainer of [how it built the search](https://www.jetify.com/blog/how-nixhub-searches-nixpkgs) describe an index built by *"pars[ing] build outputs from Hydra... to index the available packages and versions in Nixpkgs' Git history... map[ping] package names + version numbers to commits in the Nixpkgs repo, and stor[ing] this index as a prefix tree."* This is architecturally the opposite of what ocx needs: it retrofits a version→commit map onto **nixpkgs's own history**, useful only when your packages already live in nixpkgs and you want an old version of one. ocx's index has no nixpkgs presence at all, so this pattern — and by extension Flox's catalog and lazamar's nix-package-versions, which work the same way — is prior art for "how do I get an old nixpkgs-packaged tool," not for "how do I turn my own external index into new Nix packages"; it is covered-elsewhere / not-applicable for the ocx generation goal, despite surface-level topical overlap.

[FlakeHub's semver documentation](https://docs.determinate.systems/flakehub/concepts/semver/) distinguishes **tagged** releases (author-chosen SemVer-conformant git tags) from **rolling** releases (auto-versioned `0.1.<commit-count>`, intended for the "constant commit stream, no release cadence" case), and states resolution semantics for the operators it supports: `=` (exact), `*` (any, "always uses the highest published version"), `1.*` (any `1.x.y`), `1.2.*` (any `1.2.z`) — no `~` operator. A documented case in [imTHAI/nix-packages](https://github.com/imTHAI/nix-packages) (package `mist`, July 2026) shows the sharp edge this creates: because "latest" resolution is highest-semver-wins rather than most-recent-publish-wins, a rolling release published *after* a real `v0.3.0` tag is permanently invisible to any consumer that doesn't pin an exact version — the fix was switching to real, monotonically increasing semver tags.

The [NixOS wiki's Nixpkgs/Automatic_Updates page](https://wiki.nixos.org/wiki/Nixpkgs/Automatic_Updates) and [nix-community/nixpkgs-update's own docs](https://nix-community.github.io/nixpkgs-update/) describe the **r-ryantm** bot: it draws version signal from Repology, the GitHub Releases API, and a package's own `passthru.updateScript` (in that rough order of ease), opens a PR tagging the package's maintainers on success, and honors an explicit opt-out comment (`# nixpkgs-update: no auto update`) plus a `passthru.skipBulkUpdate = true;` escape hatch for Python-monorepo-style bulk updates. Because this bot only operates *inside* nixpkgs, an ocx-index flake living outside nixpkgs gets none of this update-discovery machinery for free and must replicate whatever subset it needs (version discovery, PR-with-review vs. direct-push, maintainer notification) itself — exactly the ground the eight generator exemplars above already cover.

## Recent shifts seen in this corpus

- **FlakeHub rolling-vs-tagged semver visibility bug, documented July 2026** (package `mist`, [imTHAI/nix-packages](https://github.com/imTHAI/nix-packages)): once any real semver tag ≥ 0.2.0 exists, every subsequent `0.1.<commit-count>` rolling release is permanently invisible to unpinned `latest` consumers. Invalidates a blanket "rolling releases are simpler, just use them" recommendation for anything meant to be discoverable via unpinned FlakeHub resolution.
- **nixpkgs 26.11 dropped `x86_64-darwin` support**, per nix-vscode-extensions' own README citing the [26.11 release notes' backward-incompatibilities section](https://github.com/NixOS/nixpkgs/blob/c1fe1675b8c7d1dfa4a9752fc36e2657d67d46be/doc/release-notes/rl-2611.section.md#backward-incompatibilities-sec-nixpkgs-release-2611-incompatibilities) — any generator targeting "all Darwin systems" written against pre-26.11 advice now over-promises a system nixpkgs itself no longer builds for.
- **Terraform's BSL relicense forced nixpkgs-terraform to flip its default `allowUnfree`** starting at its own v4.0.0 (dated to the underlying Terraform ≥1.6.0/1.9.0 version bands, threaded per-version rather than repo-wide) — evidence that a generator's unfree/license posture is not a one-time decision but something that can change under a package that was previously free.
- **rust-overlay tightened its own retention window** to "nightly/beta not earlier than `{current_year-1}-01-01`," explicitly to control repository size — invalidates "never delete, keep every historical entry forever" as a universal generated-flake policy at zig-overlay's scale once a repo has been running for several years.
- CI installer actions across the corpus are uniformly pinned to `cachix/install-nix-action@v31` or `nixbuild/nix-quick-install-action@v34` with explicit `nix_version` pins (e.g., `"2.31.2"`) — none of the eight generators rely on an unpinned "latest Nix" install action, consistent with H9's premise that implementation-version drift across CI runs is a real, actively-guarded-against risk.
- `flake-checker` (0.2.15, confirmed via `nix-tools/run.sh flake-checker --help` against the pinned toolchain) exposes `--check-outdated`/`--check-owner`/`--check-supported` specifically to catch a flake's own `nixpkgs` input drifting — a fairly recent (post-2024, Determinate-Systems-originated) practice of linting a flake's *own* lock hygiene as a first-class CI gate, not something any of the eight exemplars' CI configs actually run yet (measured: none of their workflow files invoke `flake-checker`).

## Contested

- **`nixConfig.extra-substituters`/`extra-trusted-public-keys` in `flake.nix` (H8's "trap")**: three of eight generators (nixpkgs-terraform, nixpkgs-python, and fenix's Cachix usage) ship this as ordinary, documented practice, not something they warn users away from. The counter-argument (it's silently ignored for a consumer without `--accept-flake-config`, and accepting untrusted flake config is itself a supply-chain trust decision) is real but not treated in this corpus as disqualifying — trending toward "ship it, document the `--accept-flake-config` requirement plainly," not "avoid it."
- **`autoPatchelfHook` vs. a custom in-repo hook**: llm-agents.nix bans `autoPatchelfHook` project-wide via an ast-grep rule in favor of its own `formatelf`. This is a minority position — nixpkgs itself and the overwhelming majority of prebuilt-binary packages in this corpus (and in nixpkgs at large) use `autoPatchelfHook` uncontested. Worth naming as "one shop's specific reason," not a consensus best practice to copy by default.
- **`inputs.nixpkgs.follows` as a universal rule (H2)**: nixpkgs-python's README explicitly instructs consumers *not* to override its `nixpkgs` input, because its Cachix cache is tied to one pinned revision. This directly contradicts treating `follows` as always-correct hygiene; the corpus is trending toward "follow for a library-shaped flake that composes with the consumer's own nixpkgs; pin-and-warn-against-following for a binary-cache-backed flake whose whole value proposition is a fixed, cache-hit-guaranteed revision."
- **How much history to retain**: zig-overlay never prunes (`sources.json` merges only, no full rewrite); rust-overlay prunes on a rolling one-year window with an escape hatch (old snapshot tags). Both are defensible; the deciding factor in this corpus appears to be absolute entry count (rust-overlay's manifest-per-toolchain-component blowup vs zig-overlay's much smaller per-release footprint), not a universal answer.
