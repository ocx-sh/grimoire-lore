# Gradle: the plugin as a product

## Verdict

1. **A Gradle plugin is a published product with a load-time compatibility contract, not a build script that happens to be reusable.** The contract is four things an agent gets wrong by default: no internal APIs, no assumed plugin order, no `afterEvaluate`, and a declared consumer-Gradle floor that is actually exercised. Everything else in this file hangs off those.
2. **The DSL you write the plugin in sets the floor for everyone who consumes it.** Built on Gradle 9.x, a Kotlin-DSL plugin runs only on consumer Gradle ≥ 8.11; a Groovy-DSL one on ≥ 7.0 ([contract §6](jvm-gradle-plugin-dev/plugin-contract-and-validation.md)). This is a one-way door for the **OCX Gradle plugin** and must be decided before the first line, not after (Q2).
3. **`validatePlugins` is a gate you run, not a gate you get.** `java-gradle-plugin` only *warns* at `jar` time. CI runs `./gradlew validatePlugins` as its own step, and anything applying `com.gradle.plugin-publish` also sets `enableStricterValidation = true` — **we make this a MUST against 1/32 corpus adoption** (Conflict D), because the stricter mode is the only thing that checks the types the plugin *exports*, and a missing annotation there is a silent up-to-date/config-cache bug in every consumer's build, not in ours.
4. **The minimum defensible TestKit matrix is two legs, not three.** Declared floor + current stable are MUST; `release-candidate` is a SHOULD that belongs on a scheduled job. Dive 2 argued three MUST legs; the corpus's sharpest plugin-as-product exemplar (detekt) runs two, and an RC break on a pull request is Gradle's regression, not the contributor's. Conflict B below.
5. **Configuration-cache compatibility is a separate leg from the version matrix, and since `com.gradle.plugin-publish` 2.1.0 (March 2026) it is also a public claim.** `compatibility { features { configurationCache = true } }` is a statement to the Portal; shipping it without a functional-test leg that passes `--configuration-cache` is shipping a false claim. Shadow itself ships that mismatch today (violation row below).
6. **`ValueSource` reads; `BuildService` holds. Never the reverse** — a `BuildServiceProvider` cannot drive a `ValueSource`'s parameters at configuration time, and that is documented, not incidental. This settles the cell `config-inventory` Axis 4 left open for the **OCX Gradle plugin**: `ocx --format json env` runs inside a `ValueSource.obtain()` with injected `ExecOperations`; the parsed map lives in a `BuildService`.
7. **`rules_ocx`'s "no `module_ctx.os`, no getenv — repository rules only" invariant transfers exactly.** A Settings plugin must not read the environment or shell out inside `Plugin<Settings>.apply()`; the `ValueSource` is Gradle's designated impure boundary, and it is the *only* mechanism exempt from automatic configuration-cache-input detection.
8. **Shading a plugin is opt-in, not automatic, and never implies relocation.** The topic map's conflict 1 says `com.gradle.plugin-publish` "auto-applies `com.gradleup.shadow` since 1.0.0"; the primary docs and Shadow's own build say it auto-*publishes the shadow jar as the main artifact* **if you apply Shadow yourself**. We correct the map (Conflict A below). Shadow ships un-shaded and un-relocated because Gradle isolates each `plugins { id(…) }` plugin in its own classloader.
9. **Consumer kinds this file binds:** every rule binds a **Gradle plugin** (convention plugin or published plugin). The Portal rows (metadata, `--validate-only`, plugin id) bind **published plugins only** — routing on `com.gradle.plugin-publish`, never on `validatePlugins`. The **OCX SDK** is a *library*: nothing here binds it except through its own `build-logic` convention plugins, which are subject to GRADLE-PLUG-01/03/04/05 and nothing else.
10. **Confirmed as a depth file, not a skill** (map conflict 6). Every rule below fires while editing a `*.gradle.kts` file that `gradle-build` already globs. Nothing here needs a procedure slot.

### Conflicts resolved

**A. Does `com.gradle.plugin-publish` auto-apply Shadow?** The topic map's conflict 1 says it "auto-applies `com.gradleup.shadow` since 1.0.0," and uses that to call shading "the sanctioned path" for plugins. [testkit dive §8](jvm-gradle-plugin-dev/testkit-matrix-and-portal.md) read the primary doc and Shadow's own build and found the weaker mechanism: plugin-publish auto-*publishes the shadow jar as the main artifact* **if the module applies Shadow itself**. Decisive evidence: `GradleUp__shadow@541b3be475:build.gradle.kts` applies `com.gradle.plugin-publish` and neither shades nor relocates itself. **Resolved toward the dive** (primary doc + measurement beats a paraphrase): shading a plugin is opt-in and supported, not automatic and not required — GRADLE-PLUG-21 is a SHOULD, not a MUST.

**B. How many TestKit legs are mandatory?** [testkit dive candidate 1](jvm-gradle-plugin-dev/testkit-matrix-and-portal.md) says three MUST legs (floor, current, `release-candidate`); the same dive's Finding 4 argues TestKit's per-test process cost is the reason to keep the matrix to three or four legs at all, and the corpus's sharpest plugin-as-product exemplar runs **two** (`detekt__detekt@45672efb8b`, floor + current) while the RC leg exists only in `gradle__actions@a27deee331`, which is a GitHub Action rather than a plugin. **Resolved by splitting the severity**: GRADLE-PLUG-12 MUST (floor + current), GRADLE-PLUG-13 SHOULD and scheduled-only — an RC break is an upstream regression, and a red PR for it teaches contributors to ignore the matrix.

**C. Where does the `ocx --format json env` read sit?** [config-inventory Axis 4](jvm-audit/config-inventory.md) left the seat open, naming `ValueSource`, `BuildService` and `Provider` as candidates. [contract dive §8](jvm-gradle-plugin-dev/plugin-contract-and-validation.md) closes it on a documented impossibility rather than a preference: "A `BuildServiceProvider` cannot drive a `ValueSource` at configuration time." **Resolved one way only** — ValueSource reads, BuildService holds the parsed result (GRADLE-PLUG-08). The rejected third option, recomputing `ocx env` in every task, multiplies process spawns and reopens the ambient-env hole GRADLE-PLUG-07 closes.

**D. Is `enableStricterValidation` a MUST at 1/32 adoption?** [testkit dive candidate 7](jvm-gradle-plugin-dev/testkit-matrix-and-portal.md) says MUST for published modules; [gates audit:197](jvm-audit/exemplar-quality-gates.md) measures adoption at exactly one repo. **Resolved toward the dive, with the scope narrowed to modules applying `com.gradle.plugin-publish`**: the mechanism decides it, not the count — stricter mode is the only check that inspects the types the plugin *exports*, so its failures land in consumers' builds rather than ours. Flagged as a new commitment, and as Q3 for the owner.

**E. Is `validatePlugins` a routing signal?** A naive reading (and any rule keyed on the task name) says yes. [pub audit:182,420](jvm-audit/exemplar-publishing-ci-bazel.md) measured 10/32 files across 7 repos running it, 7 of those repos with zero Portal signal at all. **Resolved: route on `com.gradle.plugin-publish`** (GRADLE-PLUG-20). This is what keeps the Portal rows off the OCX SDK's own `build-logic` modules.

**F. Which `gradlePlugin { plugins { } }` id idiom is canonical?** Map conflict 5 / M-F-07 leaves it split; [shape audit §2](jvm-audit/exemplar-build-shape.md) measures the map-key form dominant in repos whose *product* is the plugin (shadow, detekt) and the explicit `id = "…"` form dominant in spring-boot and mixed in gradle/gradle. **Resolved: neither is wrong.** Write the map-key form in new code; an idiom-only rewrite of existing code is churn and is listed as failure mode 11 rather than as a rule.

## The ruleset

### GRADLE-PLUG — writing, testing and publishing a Gradle plugin

Twenty-one rules, grouped by the check that catches them.

#### Caught by `./gradlew validatePlugins`

| ID | Rule | Rationale | Verification | Severity | Floor |
|---|---|---|---|---|---|
| GRADLE-PLUG-01 | Run `./gradlew validatePlugins` as its own CI step; never rely on the `jar`-time warning to be noticed. | `java-gradle-plugin` emits warnings, not failures, during `jar` — a plugin can ship with every task property unannotated and a green build. | A CI step invoking `validatePlugins` whose exit code gates the job: `grep -rn 'validatePlugins' .github/workflows/`. Empty output on a repo that ships a `gradlePlugin {}` block is the violation. | MUST | Gradle 7.0 |
| GRADLE-PLUG-02 | In every module that applies `com.gradle.plugin-publish`, set `validatePlugins { enableStricterValidation = true }`. | The default run checks only the plugin's own task types; stricter mode also checks the types the plugin *exports*, where a missing `@Input`/`@OutputFile` becomes a silent correctness bug in every consumer's build. | `grep -rln 'com.gradle.plugin-publish' --include=build.gradle.kts .` then `grep -n 'enableStricterValidation' ` in each hit; a hit in the first list absent from the second is the violation. | MUST | Gradle 7.0 |

#### Caught by a grep over the plugin's own source

| ID | Rule | Rationale | Verification | Severity | Floor |
|---|---|---|---|---|---|
| GRADLE-PLUG-03 | Never import a Gradle type from a package with an `internal` path segment, or a type suffixed `Internal`/`Impl`. Copy the code or extend a public type instead. | Gradle reserves the right to break these "during any new Gradle release, even during minor releases" — a minor Gradle bump becomes a `NoSuchMethodError` in every consumer. | `grep -rn 'import org\.gradle\.[A-Za-z.]*\.internal\.' --include='*.kt' --include='*.java' src/` plus a scan for referenced `org.gradle.*` types ending `Internal`/`Impl`. Empty output is the pass. | MUST | any |
| GRADLE-PLUG-04 | Never assume another plugin is already applied. Apply it explicitly with `pluginManager.apply("id")` (hard dependency) or react with `pluginManager.withPlugin("id") {}` (optional integration). | Application order across convention plugins, subprojects and included builds is deterministic but not reasonable-about; the failure appears when someone reorders a `plugins {}` block. | `grep -rn 'extensions\.getByType\|plugins\.hasPlugin' src/` — every hit must sit inside a `withPlugin {}` block or follow an explicit `pluginManager.apply(...)` in the same `apply()`. | MUST | any |
| GRADLE-PLUG-05 | Never call `afterEvaluate {}` in plugin code. The one carve-out is fail-fast validation of *your own* extension's final state. Use `convention()` for defaults, a lazy `Property`/`Provider` for deferred values, and `pluginManager.withPlugin()` for cross-plugin coordination. | Registration order between callbacks is fragile, task configuration avoidance is defeated, and captured project state does not serialize into the configuration cache. A plugin that uses it forces every consumer into it. | `grep -rn 'afterEvaluate' src/`; every hit must be justified in review as own-state validation. See also GRADLE-CACHE (M-D-04) for the same rule applied to build scripts. | MUST | any |
| GRADLE-PLUG-06 | Do not use `Project.getProperties()` or `Project.container(Class, …)` in new plugin code; use `findProperty()`/`ProviderFactory.gradleProperty(…)` and `ObjectFactory.domainObjectContainer(…)`. | Both are on Gradle's deprecated list scheduled for removal in Gradle 10; `project.container()` is the reflex for backing a `NamedDomainObjectContainer` DSL block. | `grep -rn '\.getProperties()\|project\.container(' src/`. Empty output is the pass. | CONSIDER | Gradle 9.x deprecation; removal in 10.0.0 |

#### Caught by running the plugin's functional tests with `--configuration-cache`

| ID | Rule | Rationale | Verification | Severity | Floor |
|---|---|---|---|---|---|
| GRADLE-PLUG-07 | A plugin must never call `System.getenv()` (unqualified enumeration), `ProcessBuilder`, `Runtime.exec` or `ExecOperations.exec` directly at configuration time. Route the read through `providers.exec()` (simple output capture) or a custom `ValueSource` (parsing, injected services, combined reads). | These are either opaque to configuration-cache-input tracking or turn every environment variable into a cache-invalidating input. `ValueSource` is the one documented exemption: only `obtain()`'s return value is tracked. | `./gradlew help --configuration-cache --configuration-cache-problems=warn` and read the report for unexpected build-configuration inputs; plus `grep -rn 'System\.getenv()\|ProcessBuilder(\|Runtime\.getRuntime()\.exec' src/` — hits are legal only inside a `ValueSource.obtain()` body. | MUST | Gradle 8.0 |
| GRADLE-PLUG-08 | Read an external CLI once in a `ValueSource` with injected `ExecOperations`; hold the parsed result for the rest of the build in a `BuildService` whose parameter is the already-obtained value. Never let a `BuildService` drive a `ValueSource`. | Documented and unsupported in the reverse direction: "A `BuildServiceProvider` cannot drive a `ValueSource` at configuration time." Only `BuildService` *parameters* are cached; instances are recreated, so the service must hold derived values, not a process handle. | Code review of the dependency direction: `ValueSource.obtain()` must reference no `BuildService`-derived `Provider`; `BuildServiceParameters` may hold the obtained JSON or parsed map. | MUST | Gradle 8.0 |
| GRADLE-PLUG-09 | A task that spawns an external tool must build the child process's environment explicitly from declared, annotated task inputs and pass it to `ExecOperations.exec { environment(map) }`. Never let the process inherit the daemon's ambient environment. | Mirrors `rules_ocx`'s explicit-only environment invariant (`AGENTS.md:211-249`, the site/translucent/explicit/pinned classification); building the map from `MapProperty` inputs keeps the classification cache-correct and build-scan-visible. | `grep -n '@TaskAction' -A 30 <task source>` — every `execOperations.exec {}`/`javaexec {}` in the block must carry an `environment(...)` call, and `System.getenv(` may appear only in the translucent-class fallback. | MUST | Gradle 8.0 |
| GRADLE-PLUG-10 | Run a dedicated functional-test leg with `--configuration-cache`, separate from the version matrix, and only declare `compatibility { features { configurationCache = true } }` once that leg passes. | Version compatibility and configuration-cache compatibility are orthogonal failure modes (M-F-04). Since plugin-publish 2.1.0 the declaration is a public Portal claim, so an undertested declaration is a false claim, not just a gap. | `grep -rn -- '--configuration-cache' <plugin-module> .github/workflows/` returns a leg distinct from the matrix legs; cross-check that the `compatibility` block's value matches whether that leg is green. | MUST | plugin-publish 2.1.0 (March 2026) for the declaration half |

#### Caught by the TestKit matrix

| ID | Rule | Rationale | Verification | Severity | Floor |
|---|---|---|---|---|---|
| GRADLE-PLUG-11 | Declare a consumer-Gradle floor consistent with the DSL the plugin is written in, and test it: a Kotlin-DSL plugin built on Gradle 9.x requires consumer Gradle ≥ 8.11, a Groovy-DSL one ≥ 7.0, and the plugin's KGP dependency must be ≥ 2.0.0. | Gradle 8.11 is the first release embedding Kotlin metadata version 2; below it the plugin fails to *load* with a metadata-version error, not a "your Gradle is too old" message. | A functional test calling `GradleRunner.withGradleVersion("<declared floor>")`; `grep -n 'kotlin' gradle/libs.versions.toml` for the KGP version. A README-only floor with no test is the violation. | MUST | Gradle 9.0.0 |
| GRADLE-PLUG-12 | The TestKit matrix must have at least two legs: the declared floor and the current stable Gradle. | A suite that runs only against the Gradle that built it cannot detect a floor regression — the floor claim is then untested by construction. | `grep -rn 'withGradleVersion' <plugin-module>/src/` shows ≥ 2 distinct targets, or an equivalent second source set/task pinned to the floor (detekt's `…MinSupportedGradle` shape). | MUST | Gradle 7.0 |
| GRADLE-PLUG-13 | Add a `release-candidate` leg on a scheduled or nightly job, not on the pull-request job. | RC breakage is an upstream regression, not the contributor's; red PRs on an RC train people to ignore the matrix. But finding out at Gradle GA is too late for a published plugin. | `grep -rn 'release-candidate' .github/workflows/` lands in a workflow with a `schedule:` (or `workflow_dispatch:`) trigger, not `pull_request:`. | SHOULD | Gradle 7.0 |
| GRADLE-PLUG-14 | If the plugin declares `compileOnly` on another plugin's API, its functional tests must not use `GradleRunner.withPluginClasspath()`. Publish to a local Maven repository and declare it in the test project's `pluginManagement { repositories { } }`. | The recommended dependency shape defeats the recommended TestKit shortcut; the symptom is a `ClassNotFoundException` pointing at the *other* plugin's class, so the debugging trail leads away from the real cause. | `grep -rn 'compileOnly(' <module>/build.gradle.kts` paired with `grep -rn 'withPluginClasspath' <module>/src/*[Ff]unctional*/` — co-occurrence is the violation. | MUST | Gradle 7.0 |
| GRADLE-PLUG-15 | A functional test may assert only on `BuildResult`, task outcomes and files on disk — never on statics, thread-locals or other in-process state of the plugin under test. | TestKit runs the build in a separate process via the Tooling API with its own classpath, classloaders and dedicated daemons; an in-process assertion tests the test JVM, not the plugin. | Reading heuristic: `grep -rn 'import <plugin base package>' <module>/src/*[Ff]unctional*/` — a functional test importing the plugin's own implementation classes is suspect. | SHOULD | Gradle 7.0 |
| GRADLE-PLUG-16 | Pin `org.gradle.testkit.dir` (or call `withTestKitDir(...)`) to a project-relative, `clean`-swept path on any CI that reuses runners. | TestKit's per-test working directories are deliberately *not* deleted, so a self-hosted or long-lived runner accumulates them indefinitely. | `grep -rn 'testkit.dir\|withTestKitDir' <plugin-module>`; absence is a finding only on reused runners, not on ephemeral GitHub-hosted ones. | CONSIDER | Gradle 7.0 |

#### Caught by `./gradlew publishPlugins --validate-only` and the Portal

| ID | Rule | Rationale | Verification | Severity | Floor |
|---|---|---|---|---|---|
| GRADLE-PLUG-17 | A Portal-published `gradlePlugin {}` block must set top-level `website` and `vcsUrl`, and per plugin `id`, `implementationClass`, `displayName`, `description`, `tags`, plus `compatibility { features { configurationCache = … } }`. | This is the literal submission requirement; omitting `tags` is accepted but measurably hurts discovery, and omitting `compatibility` is deprecated since 2.1.0 with a stated (undated) intent to reject outright. | `./gradlew publishPlugins --validate-only` (exit 0 is the pass); per `create(...)`/`register(...)` entry confirm all seven fields non-empty. | MUST | `com.gradle.plugin-publish` 2.1.0 for the `compatibility` half; 1.0.0 for the rest |
| GRADLE-PLUG-18 | Run `publishPlugins --validate-only` on every pull request; run bare `publishPlugins` only in a job gated on a tag or release trigger, reading `GRADLE_PUBLISH_KEY`/`GRADLE_PUBLISH_SECRET` from the environment. | `--validate-only` catches metadata and packaging defects before the Portal's manual review queue (days, for a new id) does, at zero cost and with no credential exposure. | `grep -rn 'publishPlugins' .github/workflows/` — every unqualified occurrence must sit under a tag/release/environment-gated job; `grep -rn 'gradle.publish.key\|gradle.publish.secret' .` must return nothing in tracked files. | MUST | plugin-publish 2.0.0 (needs Gradle 7.4+ to build) |
| GRADLE-PLUG-19 | Choose the reverse-DNS plugin id before the first `publishPlugins` run: lowercase, at least one `.`, top-level namespace one you actually control (`io.github.<user>` for an individual). It is permanent. | Ids cannot be renamed or reassigned post-publish without Gradle's dispute process — a one-way door that agents cheerfully invent a plausible value for. | Reading heuristic, once, before first publish: confirm the `gradlePlugin { plugins { … } }` id against a Plugin Portal search for that exact string and against the module's `group` coordinate. No automated check catches "already taken by someone else." | MUST | any |
| GRADLE-PLUG-20 | Do not conclude that a module publishes a Gradle plugin from the presence of `validatePlugins`; the signal is `com.gradle.plugin-publish` in that module's `plugins {}` block. | `java-gradle-plugin` registers `validatePlugins` for any internal convention-plugin module: 10/32 corpus files hit it across 7 repos, 7 of which have zero Portal signal anywhere. | The routing grep is `grep -rln 'com.gradle.plugin-publish' --include='build.gradle*' .`; `grep -rln 'validatePlugins'` over-counts. | SHOULD | any |
| GRADLE-PLUG-21 | Shading a plugin's own dependencies is opt-in via `com.gradleup.shadow` (never the dead `com.github.johnrengelman.shadow` id) and does not imply relocation. Add `relocate(...)` only for a dependency at genuine risk of colliding in a *shared, non-isolated* classloader, and name that collision in a comment. | `plugins { id(…) }` gives each plugin its own classloader, so the sharp relocation case (a component loaded into `javac`'s own classloader, as `error-prone` is) does not generalise. Blanket relocation bloats the jar and mangles stack traces. | `grep -rn 'johnrengelman' --include='build.gradle*' .` must be empty; every `relocate(` in a plugin module must carry an adjacent comment naming the collision. | SHOULD | Shadow 8.3.0 for the id; Shadow 9.5.0+ needs Gradle 9.2 / Java 17 |

**MUST count: 15.**

**Deliberately not repeated here** (they belong to `GRADLE-CACHE`, and two rules on one glob would double-load): `Task.getProject()` at execution time (M-D-01), the `System.getenv()` enumeration mechanic in ordinary build scripts (M-D-02), configuration-time file/process/`Configuration` reads outside plugin code (M-D-03), `@Classpath`/`@CompileClasspath`/`@PathSensitive` selection (M-D-06/07), `@CacheableTask` vs `outputs.cacheIf` (M-D-09). The one genuinely shared row is GRADLE-PLUG-21's negative half: an SDK jar is never shaded (map conflict 1, zero counterexamples in 32 repos).

## AI-agent failure modes

Ranked by how often it bites.

1. **Reaching for `afterEvaluate {}` as the way to "wait until configuration is done."** The single most-cited plugin-authoring mistake (M-D-04), and the idiom every pre-2024 tutorial teaches. Check: `grep -rn 'afterEvaluate' src/` — any hit not justified as own-state validation is a rewrite target.
2. **Generating `GradleRunner.create().withPluginClasspath()` as the default functional-test scaffold.** Tutorial-shaped and silently wrong the moment the plugin has a `compileOnly` dependency on another plugin's API. Check: `grep -rn 'compileOnly(' <module>/build.gradle.kts` paired with `grep -rn 'withPluginClasspath' <module>/src/` — co-occurrence is the trigger.
3. **Treating `System.getenv()` as free because "it's just reading an env var,"** or hedging with `providers.environmentVariable("X").getOrElse(System.getenv("X") ?: …)` — which looks defensive and reintroduces the untracked read. Check: `./gradlew help --configuration-cache --configuration-cache-problems=warn` and count environment-variable inputs; plus grep for `System.getenv` co-occurring with `providers.environmentVariable` in one file.
4. **Writing `com.github.johnrengelman.shadow`.** The maintainer transfer was 2023 and the old id is dead past Shadow 8.3.0, but it dominates training data. Check: `grep -rn 'johnrengelman' --include='build.gradle*' .` must be empty.
5. **Calling `project.exec {}` or `Runtime.exec()` inside a `@TaskAction`** because it worked at the top level of a build script. `Project` is unusable at execution time at all. Check: `grep -n '@TaskAction' -A 20 <file>` and confirm no `project.` reference in the block.
6. **Casting to an `*Internal`/`*Impl` type "to get the one method that isn't public yet."** Common in real flagship plugin source, therefore well-represented in training data, and never flagged. Check: the GRADLE-PLUG-03 import grep; a compile-classpath scan beats a source grep where internal types are re-exported transitively.
7. **Omitting `compatibility { features { … } }`, or inventing a feature name.** plugin-publish 2.1.0 is March 2026 — newer than most training data. As of 2026-09-12 `configurationCache` is the *only* declarable feature; Isolated Projects is not one yet. Check: every name inside the block must be `configurationCache`; re-read `gradle/gradle-plugin-compatibility-plugin`'s README before accepting a new one.
8. **Calling "tested against the Gradle that built it" a TestKit matrix.** Produces a green CI over an unexercised floor. Check: GRADLE-PLUG-12's grep — ≥ 2 distinct `withGradleVersion` targets or an equivalent floor-pinned source set.
9. **Inventing a plugin id that is plausible but not owned, or missing the required `.`.** Check: a one-time Portal search for the literal string before first publish; nothing automated catches "taken by someone else."
10. **Wiring bare `publishPlugins` into a generic CI job**, including one reachable from a fork's pull request. Check: every unqualified `publishPlugins` in workflow YAML must be under a tag/release/approval-gated job.
11. **"Rewriting" one `gradlePlugin { plugins { } }` id idiom into the other.** Both `create("dev.ocx.gradle") { }` (map key *is* the id) and an explicit `id = "…"` property compile identically; the corpus is split with no winner across 13 plugin-shipping repos (M-F-07). Check: an id-idiom change with no other change in the diff is churn — reject it.

## Open questions

**Owner decisions.**

- **Q1 — Does the OCX Gradle plugin publish to the Plugin Portal at all**, or only to an internal/Maven repository? GRADLE-PLUG-17/18/19 apply only to a Portal publish, and the plugin id is permanent from the first `publishPlugins`. Answer before the first commit.
- **Q2 — Kotlin DSL or Java/Groovy for the plugin's implementation?** A Kotlin-DSL plugin built on Gradle 9.x is unusable below consumer Gradle 8.11; a Groovy-DSL one reaches 7.0. If any OCX adopter is on Gradle 8.0-8.10, the DSL choice is made for us.
- **Q3 — Is GRADLE-PLUG-02 (`enableStricterValidation`) really a MUST at 1/32 corpus adoption?** We say yes; the owner may prefer SHOULD. Nothing else in the ruleset depends on the answer.

**Subareas deserving another research round.**

1. **Settings-plugin tool provisioning.** Neither dive could corroborate the provisioning half against any exemplar — `config-inventory` Axis 4 leaves the cell explicitly "Open." *Question:* what is the right Gradle seat for `@ocx_tool`-style pinned-binary download with sha256 enforcement and a version-floor gate — a custom `JavaToolchainResolver`, a `BuildService`-backed download-and-verify, or an `ArtifactTransform` — and how does each behave under the configuration cache and on a cold CI runner?
2. **Isolated Projects compatibility for a Settings plugin.** M-F-04's second half is unanswered: IP reached incubating only in Gradle 9.7.0, it is not yet a declarable Compatibility-Plugin feature, and a Settings plugin registering one shared `BuildService` across every project is exactly the IP-hostile shape. *Question:* can a Settings plugin that provisions tools for all projects be Isolated-Projects-compatible on Gradle 9.7 at all, and what is the diagnostic that proves it?
3. **A plugin's own API-surface nullability (M-F-11).** Untouched by both dives. *Question:* does a plugin whose public API is consumed from a Kotlin DSL build script need JSpecify annotations, given that Kotlin treats JSpecify as `strict` (errors) and JSR-305 as `warn` — i.e. does keeping JSR-305 on a plugin API break consumer build scripts under Kotlin 2.2/K2, or only warn?
