## Verdict

1. **One text never passes four platforms. Every variant runs its own counter, and the validator is a script, not a reading.** The validator dive counted 33 test strings with five counters. A naive length disagreed with the Bluesky count on 14 strings, with the X count on 18 and with the Mastodon count on 19 ([mb-variant-validator.md](channel-microblog/mb-variant-validator.md), section 2). The four rules are: X weighted characters, Bluesky graphemes plus a byte cap, Mastodon grapheme clusters with URLs fixed at 23, and Threads characters with emoji counted as UTF-8 bytes.
2. **The release link goes in post 1 on all four platforms. This is a SHOULD (CH-MB-07). Writing it as a full `https://` URL is a separate MUST (CH-MB-22).** Both dives graded the reach evidence C or D and proposed SHOULD, and no mechanic found makes a reply link go unseen. X keeps one best-scoring post per conversation in a feed response (`DedupConversationFilter`, [xai-org/x-algorithm](https://github.com/xai-org/x-algorithm), HEAD `52d4598`, 2026-11-25). That shows a thread's posts compete for one slot, but the kept post may be the reply. On Mastodon a self-reply reaches every follower's Home: "Your replies will only appear on your followers' Home feeds if they follow both you and the person you are replying to" ([posting docs](https://raw.githubusercontent.com/mastodon/documentation/main/content/en/user/posting.md), last changed in `204b38c`, 2026-07-08, fetched 2026-11-27), and in a self-reply both parties are the poster. One bridge has dropped replies. Bridgy Fed delivers self-replies by design and only delays them, one activity per 5 s per user ([fed.brid.gy/docs](https://fed.brid.gy/docs), undated, fetched 2026-11-27; `protocol.py` at `96187d6`, 2026-11-25). But its maintainer reported on 2025-08-16 that replies "sometimes wouldn't get bridged to Bluesky" when the post they depended on "hadn't finished bridging yet", and called the fix "hopefully" done ([snarfed.org](https://snarfed.org/2025-08-16_55391), 2025-08-16, a statement by the bridge operator). A self-reply sent seconds after post 1 is that case. **Documented gap:** whether the fix holds in 2026-11 needs a live Mastodon account bridged to Bluesky, which this program may not create or use ([followup-q1.md](channel-microblog/followup-q1.md)). No fetched Buffer or Publer page says a thread sub-post is dropped (vendor help pages, undated, fetched 2026-11-27; absence of a statement is not proof), and 4 of 5 inspected posting GitHub Actions have no reply input, so a reply is usually a separate API call. What remains is still a SHOULD: post 1 carries the claim (CH-MB-08), and a reply is a second publish step that can fail on its own, which CH-MB-24 handles. The scheme rule rests on a measurement: Mastodon does not link a bare domain, so `ocx.sh/docs` is a link on X and Bluesky and plain text on Mastodon (validator dive, section 2).
3. **Conflict resolved: the link target is the owned per-version anchor when that page passes the card gate, and the GitHub Release page when it does not.** The validator dive said "the release notes page" without naming one. Measured on 2026-11-27: `grimoire.rs/changelog.html#v0-17` passes (absolute `og:image` of 105,570 bytes, an outcome-worded `og:description`). `ocx.sh/docs/changelog/` fails: it has no `og:image`, and its `og:description` is the generic "the simple package manager". The GitHub Release page carries an `og:image` of 1200 x 600 and an `og:title`, but no `og:description`. An agent falls back by rule, and it reports the failing page as a site defect. It does not ship a card with no image.
4. **Default to one self-contained post. A thread needs at least two distinct items and has at most 3 posts.** No source on any platform shows a thread effect (grade D). On Bluesky, thread roots scored higher in 5 of 6 accounts, but accounts choose threads for bigger announcements, so that does not measure an effect ([mb-link-and-thread-defaults.md](channel-microblog/mb-link-and-thread-defaults.md), section 2.2). The cap of 3 and the two-items test are project defaults, not platform facts.
5. **Cards are platform-specific work.** X and Mastodon build the card on the server from the first URL. Bluesky does not: an API post with only a text URL shows a bare link, so the client must write `app.bsky.embed.external` and upload the thumb itself ([bsky-docs posts.md](https://raw.githubusercontent.com/bluesky-social/bsky-docs/main/docs/advanced-guides/posts.md), fetched 2026-11-27). On Threads, a release post is text-only with `link_attachment`, because `link_attachment` works only with `media_type=TEXT` and the docs contradict themselves on cards for media posts ([Threads posts docs](https://developers.facebook.com/documentation/threads/posts); link limit dated 2025-12-22).
6. **Conflict resolved: one alt text of at most 1,000 characters serves all four platforms.** The dives listed four limits: X 1,000, Threads 1,000, Bluesky 2,000 (an app limit with no lexicon cap), and Mastodon set per instance (10,000 since 4.6.0, 2026-06-17; the docs sample still shows 1,500). The lowest limit passes on every platform, and one string removes the need to track four. Any detail longer than that goes on the linked page.
7. **Conflict resolved: schema beats prose, and the shared registry beats a copy kept in the skill.** The Bluesky docs say images are capped at 1,000,000 bytes, while their own sample code and the `app.bsky.embed.images` lexicon say 2,000,000. The lexicon wins, and both dives agree. The link dive also proposed a `facts.md` inside the skill. The agent-boundary consolidation decided on one registry per platform, not one per skill ([core-facts-and-channel-inventory.md](channel-agent-boundary/core-facts-and-channel-inventory.md), summary). The microblog validator reads that registry and keeps no copy, so a limit exists in one row only.
8. **Conflict resolved: the refresh cadence is set by how each source is published, not by a flat 90 days.** The link dive proposed 90 days for every fact. The registry dive measured limits changing about once per 25 page-months on docs pages and set 180 days for limits and 90 for policy. Microblog limits moved faster than that rate. In 2026 the Bluesky lexicon raised the image cap to 2 MB and the video cap to 300 MB, and Mastodon raised the alt-text limit twice. Three of the four limit sources are machine-readable (lexicon JSON, `twitter-text` `config/v3.json`, the Mastodon instance API), so a script diffs them on a schedule or reads them live. See [Decay](#decay).
9. **Never state that X, Bluesky or Threads penalises or does not penalise links.** The X executive line reversed between 2024-11-24 ("put the link in the reply", [Business Insider Japan](https://www.businessinsider.jp/post-297498)) and 2026-07-29 ("We haven't for over a year", [PPC Land](https://ppc.land/x-drops-year-old-link-penalty-musk-tells-zuckerberg-on-platform/)). Buffer's vendor data (2025-10-14, 18.8M posts, no window stated) and Nieman Lab (2026-04-08, 18 news accounts) point the other way. None of these sources tests the state after July 2026.
10. **A microblog skill of its own, `microblog-variants`, holds the validator. `launch-plan` names it for the release-day step and carries no platform numbers.** Both dives agree. Counting, cards and proofs change on platform schedules and a script can check them. Launch sequencing is a judgement.
11. **Dropped or handed off:** the X spend cap and idempotency key for URL posts (X charges $0.20 per post with a URL, [X changelog](https://docs.x.com/changelog) 2026-04-16) go to the agent-boundary topic (M-CO-1). Bot and automated-account labels belong to [core-platform-labels.md](channel-agent-boundary/core-platform-labels.md). `og:image` size and site metadata belong to marketing. A link-placement experiment is an owner decision. The Bluesky video caption limits go in the registry and get no rule.

## The ruleset

Every count below was produced by the dives' scripts (`count.js`, `facets.js` with `twitter-text` 3.1.0 and `@atproto/api` 0.32.7 on Node 26.13.1, validator dive section 2) or re-measured on 2026-11-27 with the `curl` shown. "Re-check" names the command that shows whether a platform fact still holds.

## Agent failure modes

Grouped by the mechanism behind each failure. The order is a judgement from the dives' AI-agent tables, not a measured frequency.

**A. One counter for four platforms (most frequent).**
1. Counts with `len()` or `.length`, or treats 280 and 300 as "about the same limit". Caught by CH-MB-01 (the `🇩🇪🇺🇸` vector).
2. Applies "a URL counts 23" to Bluesky and passes a URL-heavy post that is over the limit. Caught by CH-MB-03 (the 119-character URL vector).
3. Writes a bare `ocx.sh/docs`, which links on X and Bluesky but is plain text on Mastodon. Caught by CH-MB-22.
4. Treats 500 as the Mastodon limit everywhere and leaves CW text out of the count. Caught by CH-MB-05.

**B. Platform folklore from training data.**
5. Moves the link to the first reply, because 2024 advice and vendor posts say so. Caught by CH-MB-07.
6. Writes a numbered thread of 8 to 10 posts for a patch release. Caught by CH-MB-09.
7. States "X penalises links by N%", quoting Buffer's 0% or PPC Land's 94%. Caught by CH-MB-15.
8. Copies the 1,000,000-byte image limit from the Bluesky docs prose, or believes Threads has no alt-text field or no link cap. Caught by CH-MB-14 and CH-MB-06.

**C. Thinks the server does work that the client must do.**
9. Posts a text URL to Bluesky and expects a card. Caught by CH-MB-11 (`getPosts` embed check).
10. Builds facets from `indexOf`. Caught by CH-MB-04.
11. Attaches a screenshot and a link on Threads and expects a card. Caught by CH-MB-12.

**D. Alt text as a formality.**
12. Leaves alt text empty, or writes a file name or "Screenshot of terminal". Re-measured at 308 of 542 Bluesky brand-account images with no alt text, 255 of them from two of eleven accounts ([followup-q2.md](channel-microblog/followup-q2.md)). Caught by CH-MB-13, and by the recursive weekly audit in CH-MB-20 for images inside a quote post.
13. Writes alt text that describes the terminal's look instead of quoting the command and its output. Caught by CH-MB-23 (substring check against the recorded run; reading for a hand-made screenshot).

**E. One-sided proofs.**
14. Adds `fediverse:creator` but not the attribution domain, or puts `rel="me"` in a JavaScript-rendered or iframe block. Caught by CH-MB-17 and CH-MB-18 with raw-HTML `curl`.
15. Calls a domain handle a "blue check". Caught by CH-MB-19.

**F. Copying text across accounts.**
16. Sends one body to both org accounts on X. Caught by CH-MB-16.

**G. Card target not checked.**
17. Links a page with no `og:image` (every ocx.sh page today) and ships a card with no image. Caught by CH-MB-10.

**H. Thread steps treated as one atomic publish.**
18. Sends post 2 before post 1 returned its id, or deletes and re-posts post 1 when the reply call fails. Caught by CH-MB-24 (failing-reply fixture).

## What an agent must ask a human

- Whether to open an account on a platform, which handle or domain to claim, and which Mastodon instance holds the canonical identity and the attribution domain.
- Whether to run a link-placement experiment that departs from CH-MB-07, and how much lower reach is acceptable during it.
- Whether to opt the project accounts into Bridgy Fed.
- Whether to pay for X Premium or verification, or to request a Bluesky blue check. If the X account has Premium, whether a post may exceed 280 (CH-MB-02).
- Whether a release deserves a thread beyond the mechanical two-items test in CH-MB-09.
- Whether ocx and Grimoire share one set of accounts or keep two. This decides how often CH-MB-16 applies.
- Any claim in alt text about product behaviour that the screenshot does not show.
