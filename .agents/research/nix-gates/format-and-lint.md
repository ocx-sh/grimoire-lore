## Summary

- The formatter of record is **nixfmt** (`pkgs.nixfmt`, RFC 166), but the flake `formatter` output must be **`pkgs.nixfmt-tree`** (a zero-setup `treefmt` wrapper), never bare `pkgs.nixfmt` — nixfmt formats one file at a time by design and has no directory-recursion mode of its own ([nixfmt README](#8-treefmt-nix-and-git-hooksnix-how-the-gate-gets-wired-locally)).
- nixfmt's own README (2026-09-27 fetch) tells adopters to write `formatter.${system} = nixpkgs.legacyPackages.${system}.nixfmt-tree;` verbatim — this is not this dive's invention, it is upstream's stated recommendation.
- The CI check command is `treefmt --ci` (exit 0 = formatted, non-zero = would reformat), run from a checkout with `nixfmt-tree` on `PATH` (`nix develop` / `mkShell { packages = [ pkgs.nixfmt-tree ]; }`) — no flake evaluation of the check derivation is required for the format gate itself.
- `pkgs.nixfmt-rfc-style` is a **deprecated alias**, not a removed attribute, as of nixpkgs 25.11 and still today (26.11pre): it evaluates without warning or throw, it just isn't the name to write in new code — a grep finding (Q10), never an eval failure.
- statix ships 17 active lints (2 more, W13/15/16/21/22, are reserved code gaps; W09 is source-present but disabled). Of these, only a handful are safe MUST-backing defect detectors; most are style.
- Hand-classifying statix's two highest-volume codes on real exemplars found a genuine, previously-undocumented false-positive class: **W20 "repeated keys" fires on multiple dotted-attrpath assignments sharing a prefix inside one attrset** (`boot.initrd.x = …; boot.consoleLogLevel = …;`), which Nix's grammar explicitly permits and correctly deep-merges — this is not the same hazard as a literal `{ a = 1; a = 2; }` and W20 does not distinguish the two (`nix-community/disko@725ea35e410a:lib/tests.nix:147-154`).
- statix's W10 "empty pattern in function argument" fires on flake-parts' own idiomatic `{ ... }:` module-argument shape and is pure style noise in module-system code, not a defect (`hercules-ci/flake-parts@31729ca8cbdb:dev/tests/nix-unit.nix:559`).
- statix's W04 "assignment instead of inherit-from" classified as 100% real, zero false positives, across every sampled instance in disko and flake-parts — the mechanical rewrite (`x = ns.x;` → `inherit (ns) x;`) is correct every time it fires.
- deadnix's "Unused lambda pattern" category is the single largest false-positive source (908/1,914 corpus-wide per the baseline audit) and the same pattern reproduces exactly in flake-parts' own module functions (`mkPerSystemOption ({ config, extendModules, pkgs, ... }: …)`), which is a *module-argument* convention, not nixpkgs `callPackage` — `--no-lambda-pattern-names` suppresses both classes identically, because deadnix does not distinguish "callPackage formal" from "any attrset lambda pattern name."
- deadnix's "Unused lambda argument" and "Unused let binding" categories, by contrast, classified as real dead code in every sampled instance (flake-parts' `vendor/flake-compat/default.nix`, `lib/memoize/memoize.nix`) — these two categories are safe to gate on unconditionally.
- Findings-per-1,000-lines on the six named repos range from 0 (numtide/treefmt, sxyazi/yazi — both statix and deadnix clean) to 21.3 deadnix / 17.4 statix (DeterminateSystems/nix-installer, a 4-file, 1,035-line repo where density is high because the denominator is small, not because the code is worse).
- **deadnix gates (MUST) as `deadnix --fail --no-lambda-pattern-names`**, excluding generated data and vendored third-party trees; **statix advises (SHOULD only for W12, W17/W19)**, with W08/W03/W04/W20/W10 disabled by default in `statix.toml` for a new flake, because they are style-tier or carry a measured false-positive class.
- nixf's 41-diagnostic catalogue (`libnixf/src/Basic/diagnostic.py`, confirmed live: `sema-duplicated-attrname` is `Error` severity, `merge-diff-rec` and `sema-extra-with`/`sema-extra-rec` are `Warning`) is a strict superset of statix/deadnix and is what an agent's own editor (nixd) surfaces turn-by-turn — but `nixf-diagnose` as a standalone batch CLI is a git-hooks.nix/treefmt-nix hook option today, not yet a documented `nix flake check` participant, so it joins the gate as an optional git-hooks.nix hook, not a MUST.
- **cachix/git-hooks.nix, fetched live from `master` on 2026-09-27, exposes exactly 7 Nix-relevant hooks** — `alejandra`, `deadnix`, `flake-checker`, `nixf-diagnose`, `nixfmt`, `nixpkgs-fmt`, `statix` — not the 9 an earlier wave-1 audit found against a pinned exemplar SHA; `nixfmt-classic` and `nixfmt-rfc-style` are no longer distinct hook options on current master (see Contested/evolving §1). Both counts are correct for their own snapshot; cite the fetch date.
- The exclusion set a gate needs is not one glob: it is a directory-shaped exclude (`test_data/`, `tests/fixtures/`, a `vendor/` tree, a committed generated-data directory) passed to `treefmt`'s `settings.formatter.<name>.excludes` (or deadnix's own `--exclude`/`exclude` hook option) — a single `*.generated.nix` extension convention is not what the corpus actually uses, so the rule teaches the mechanism, not a fixed glob string.
- Three formatter-output fixtures were planted (`pkgs.nixfmt` bare, `pkgs.nixfmt-tree`, a treefmt-nix wrapper) and one misformatted/well-formatted twin, but the pinned Nix toolchain (`~/.cache/research-lang/nix-tools/run.sh`) was under sustained multi-worker store contention for the whole of this dive's window (every `nix`-family invocation, including a bare `nix --version`, timed out at 60–300 s across five separate attempts spanning over two hours) — no command through that toolchain returned in time to execute the planted-fixture format/lint runs myself; see [Verification runs](#verification-runs) for the exact commands, timestamps and exit codes, and the fallback evidence path this dive used instead (reading the already-executed raw JSON another wave-1 worker left under `fixtures/tool-runs/`, plus jq/grep run directly on the host, which needed no Nix toolchain).

## Findings

### 1. nixfmt is the formatter of record (RFC 166)

[RFC 166](https://raw.githubusercontent.com/NixOS/rfcs/master/rfcs/0166-nix-formatting.md) (merged) established a "Nix formatter team" and an "official Nix formatter," and states plainly: "Require that any default formatting in the Nix CLI must use the official Nix formatter" (line 22) and "In case the Nix CLI ever gets support for running a default Nix formatter, the official Nix formatter must be used" (lines 161-162). The RFC deliberately under-specifies style rules ("the formatting rules are intentionally under-specified, leaving room for the formatter implementation," line 71), delegating the actual rules to a living document.

That living document is [`standard.md`](https://raw.githubusercontent.com/NixOS/nixfmt/master/standard.md) (1,547 lines) in the `NixOS/nixfmt` repository — not the RFC text itself. Sampled normative rules (2026-09-27 fetch): two-space indentation is mandatory (line 435: "Two spaces must be used for each indentation level"); indentation must not skip levels going deeper but may drop arbitrarily many levels at once (line 486); the kind of quote (`"` vs `''`) is preserved from the input, never normalized (line 583); `/* */` single-line comments are converted to `#` comments (line 652); `/** */` doc comments follow [RFC 145](https://github.com/NixOS/rfcs/pull/145) and must keep their attachment to the same expression (lines 648-649).

Current version, from [`CHANGELOG.md`](https://raw.githubusercontent.com/NixOS/nixfmt/master/CHANGELOG.md) (fetched 2026-09-27): **1.5.0 (2026-09-10)** added chained presence-check parsing and `--follow-symlinks`; **1.4.0 (2026-07-07)** added the `nixfmt:disable`/`nixfmt:enable` directive pair (§10 below); **1.3.0 (2026-05-26)** "Replaced references to `nixfmt-rfc-style` with `nixfmt`" — the point at which the tool's own documentation stopped using the placeholder name, matching [conflict 5](../nix-topic-map.md)'s adjudication that the tool-docs rename (1.3.0) and the nixpkgs-attribute rename (25.11) are two different, both-true events.

### 2. What a bare `nix fmt` actually does — and why `pkgs.nixfmt` alone is not enough

`nix fmt` is `nix formatter run`: it "calls the formatter specified in the flake" and forwards any trailing arguments to it ([nix.dev nix3-fmt manual, Nix 2.35](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-fmt), fetched 2026-09-27). The manual documents the `PRJ_ROOT` environment variable (set to the directory containing the closest parent `flake.nix`) but is explicit that it does not itself define what the formatter must do with that root — the *contract* for what a whole-tree run looks like is entirely up to the `formatter` derivation.

nixfmt itself "can only process one file at a time" (its own README, top of the Installation section, 2026-09-27 fetch) — it has no built-in directory walk. So `formatter.${system} = pkgs.nixfmt;` alone, invoked as a bare `nix fmt` with no file arguments, has nothing to iterate: whatever files (if any) `nix fmt` forwards, nixfmt formats those and only those; it does not discover the tree. This is exactly what M-F-02 asked, and it resolves [conflict 5](../nix-topic-map.md)'s open half ("which formatter *output* … makes a bare `nix fmt` format the tree"):

- **`pkgs.nixfmt-tree`** is the answer. Its own README section, "In a project → `nixfmt-tree`" (fetched 2026-09-27), states: "`nixfmt-tree` provides an instance of `treefmt`, pre-configured to use nixfmt … Then run `treefmt` from within your shell to format all nix files in your project," and the "`nix fmt` (experimental)" subsection gives the exact flake snippet this dive planted verbatim in `fmt-nixfmt-tree/flake.nix`:
  ```nix
  formatter.x86_64-linux = nixpkgs.legacyPackages.x86_64-linux.nixfmt-tree;
  ```
- Reading `nixfmt-tree`'s own `package.nix` (fetched live from `nixpkgs/pkgs/by-name/ni/nixfmt-tree/package.nix`, master, 2026-09-27) confirms the mechanism: it is `treefmt.withConfig { settings.formatter.nixfmt = { command = "nixfmt"; includes = [ "*.nix" ]; }; runtimeInputs = [ nixfmtPackage ]; }`, with `meta.mainProgram = "treefmt"` — so `nix fmt` (which runs the `formatter` derivation's `mainProgram`) is actually invoking `treefmt`, not `nixfmt` directly, and it is `treefmt`'s own file-discovery that walks the tree. The package's own test (`passthru.tests.simple`, same file) is itself a planted-fixture pattern worth citing: it commits an unformatted `dir/b.nix`, runs `treefmt dir`, and asserts the file is now formatted while a sibling outside `dir` is untouched — the exact "check mode changes only what it should" property this dive was asked to plant.
- A hand-rolled `treefmt-nix` wrapper (`treefmt-nix.lib.evalModule pkgs { programs.nixfmt.enable = true; }`, exposing `.config.build.wrapper` as `formatter` and `.config.build.check self` as a `checks.<system>` entry) is the more configurable alternative when a project also wants other per-language formatters in the same `treefmt.toml`-equivalent — `treefmt-nix`'s README (fetched 2026-09-27) documents exactly this shape and that `settings.formatter.<name>.excludes` is the exclusion mechanism (§9).
- **The CI check command, either way, is `treefmt --ci`** — the `nixfmt-tree` package doc string states this explicitly ("To check formatting in CI, run … `treefmt --ci`") — never `nixfmt --check` alone at the repository root (that only checks whatever files are passed on the command line, and nixfmt has no recursive mode to give it a directory).

### 3. The dead-name set: `nixfmt-rfc-style`, `nixfmt-classic`, `nixpkgs-fmt`

Confirmed against nixpkgs' own release notes ([`doc/release-notes/rl-2511.section.md`](https://raw.githubusercontent.com/NixOS/nixpkgs/master/doc/release-notes/rl-2511.section.md), fetched 2026-09-27, line 11, verbatim): "The official Nix formatter `nixfmt` is now stable and available as `pkgs.nixfmt`, deprecating the temporary `pkgs.nixfmt-rfc-style` attribute. The classic `nixfmt` will stay available for some more time as `pkgs.nixfmt-classic`." Three consequences, each version-anchored:

- `pkgs.nixfmt-rfc-style` — **deprecated alias**, still evaluates (it is not `throw`n), as of 25.11 and still at 26.11pre; a grep finding (Q10), not an eval failure. No nixpkgs source in this dive's reach shows a removal date; treat "still an alias today" as current until a later release note says otherwise.
- `pkgs.nixfmt-classic` — the **pre-RFC-166** tool, kept "for some more time," explicitly not the default; citing it in new code means "I want the old style," which is almost never the intent when an agent writes it (agents trained on pre-2025 material reach for `nixfmt-rfc-style` thinking it is the *new* stable name, the opposite of its actual, now-legacy, status).
- `pkgs.nixpkgs-fmt` (the unrelated nix-community project) — **archived**, last commit 2024-07-24 (confirmed via the GitHub API by an earlier wave-1 worker, [shifts.md §11](../nix-topic-map/shifts.md)); it is not part of the nixfmt-naming migration at all, it is a different, dead tool. Any occurrence is a straightforward migration target, no ambiguity.

### 5. deadnix: one check, five flags, and the callPackage exemption

[`astro/deadnix` README](https://raw.githubusercontent.com/astro/deadnix/main/README.md) (fetched 2026-09-27) is explicit that deadnix has no rule catalogue: it is one check ("dead code: unused variable bindings") with five flags that change *what counts*: `-l`/`--no-lambda-arg`, `-L`/`--no-lambda-pattern-names` ("don't break nixpkgs `callPackage`" — the tool's own phrase), `-_`/`--no-underscore`, `-W`/`--warn-used-underscore`, `-h`/`--hidden`; plus `-f`/`--fail` (exit 1 on any finding — off by default) and `--exclude <paths>`. As of 1.1.0 it also supports an inline `# deadnix: skip` pragma to exempt the following binding.

The five-flag design maps onto exactly three output categories, confirmed against the raw JSON message text: `Unused lambda pattern: <name>` (an attrset-pattern formal, e.g. `{ foo, ... }:` — what `-L` suppresses), `Unused lambda argument: <name>` (a plain, non-destructured argument — what `-l` suppresses), and `Unused let binding: <name>` (neither flag touches this). Because deadnix's own JSON already tags each finding by exactly this category, this dive could compute "deadnix with `-L`" from the already-collected default-mode JSON by simple subtraction (drop every `Unused lambda pattern` row) without re-invoking the binary — see the caveat in [Verification runs](#verification-runs) about why the binary itself could not be re-run this session.

Sample-level classification (files read directly, `~/.cache/research-lang/exemplars/nix/`, all read-only):

- **W20 false positive**, `nix-community/disko@725ea35e410a:lib/tests.nix:147,150,153,154`: `boot.initrd.preDeviceCommands = …; boot.initrd.secrets = …; boot.consoleLogLevel = …; boot.loader.systemd-boot.enable = …;` inside one `config = { … };` attrset. statix reports "The key `boot` is first assigned here … repeated here" four times. This is the NixOS-module idiom of assigning several dotted sub-paths of the same top-level attribute within one attrset literal — Nix's grammar defines this as a legal, order-independent merge of the nested paths (unlike a `//` between two whole attrsets, which replaces wholesale), so nothing is silently dropped. statix's AST-level key tracker cannot see past the first path segment and flags the shared prefix as if it were a literal duplicate key.
- **W10 false positive**, `hercules-ci/flake-parts@31729ca8cbdb:dev/tests/nix-unit.nix:559,577`: `perSystem = { ... }: { … };` — flake-parts' own convention for a `perSystem` module function that doesn't need any of its standard arguments (`pkgs`, `config`, `self'`, `inputs'`, `system`). This is the same "keep the standard signature even when unused" pattern nixpkgs uses for `callPackage` formals, just at the module-argument layer instead — statix's W10 has no equivalent exemption to deadnix's `-L`.
- **W04, zero false positives**, sampled across `nix-community/disko@725ea35e410a:lib/types/{disk,zpool}.nix`: every instance was a literal `x = ns.x;` that `inherit (ns) x;` rewrites correctly and losslessly.
- **deadnix "Unused lambda pattern", false-positive class confirmed**, `hercules-ci/flake-parts@31729ca8cbdb:extras/easyOverlay.nix:11`: `perSystem = mkPerSystemOption ({ config, extendModules, pkgs, ... }: { … });` — `config` is flagged unused, but it is a standard flake-parts module argument kept for signature consistency with every other `perSystem` module in the same codebase, the exact shape `--no-lambda-pattern-names` was built to exempt (the flag's own description says "callPackage," but its mechanism — don't check attrset *pattern* names — catches this module-argument case too, since deadnix does not know *which* convention a pattern name belongs to).
- **deadnix "Unused lambda argument"/"Unused let binding", zero false positives**, `hercules-ci/flake-parts@31729ca8cbdb:vendor/flake-compat/default.nix` (`Unused lambda argument: n`, `inputName`) and `lib/memoize/memoize.nix` (`Unused lambda argument: k`, `v`) — both are genuinely dead, non-destructured arguments in vendored or internal helper code, not exempt by any documented convention. (`vendor/flake-compat` is itself a reason to exclude vendored trees from the gate entirely, §9 — it is third-party code a project does not own and should not be asked to fix.)

### 7. nixf / nixd: 41 static diagnostics, and whether nixf-diagnose joins the gate

[`libnixf/src/Basic/diagnostic.py`](https://raw.githubusercontent.com/nix-community/nixd/main/libnixf/src/Basic/diagnostic.py) (fetched 2026-09-27) confirms 41 diagnostics across four severities. Spot-checked entries relevant to this dive's rows: `sema-duplicated-attrname` is `severity: "Error"` (lines 151-153) — nixf catches M-C-13's repeated-key case at parse/sema time as a hard error, not a warning, which is a materially stronger signal than statix's W20 (§4/§6 above show W20 has a real false-positive class; nixf's own severity choice for the *literal*-duplicate case is `Error`, while `merge-diff-rec` — merging a `rec` and non-`rec` attrset via `//`, this dive's planted `rec-merge.nix` fixture — is only `Warning` (lines 145-147), correctly reflecting that the `//`-merge case is a real but non-fatal surprise, not a parse-time contradiction). `sema-extra-with` and `sema-extra-rec` are both `Warning` (lines 229-237) — nixf's static equivalents of statix's `with`/`rec` guidance, catchable before evaluation.

Whether `nixf-diagnose` (the batch CLI over this catalogue) is packaged in nixpkgs 26.11 and should join `nix flake check`: this dive found strong indirect evidence but could not confirm with a live `nix eval` because of store contention (see Verification runs). `cachix/git-hooks.nix`'s own `nix/tools.nix` (exemplar clone, `cachix__git-hooks.nix@<pinned-sha>`) requires `nixf-diagnose` as a **plain, non-defaulted formal argument** (`, nixf-diagnose` with no `? placeholder …` fallback, unlike `nixfmt-classic ? placeholder "nixfmt-classic"` a few lines above it) — meaning git-hooks.nix's own `callPackage` assumes the target nixpkgs unconditionally provides `pkgs.nixf-diagnose`, with no defensive fallback the way it has for the (potentially-removed) classic-nixfmt alias. ### 8. treefmt-nix and git-hooks.nix: how the gate gets wired locally

[`numtide/treefmt-nix` README](https://raw.githubusercontent.com/numtide/treefmt-nix/main/README.md) (fetched 2026-09-27) documents `settings.formatter.<name>.excludes = [ "glob" ]` as the per-formatter exclusion mechanism (its own worked example: `settings.formatter.terraform.excludes = [ "hello.tf" ];`) and that a `programs.<name>.enable = true;` module option exists per formatter (`nixfmt`, `alejandra`, `statix`, `deadnix`, `nixf-diagnose` among the 128 `programs/*.nix` files) — this is the mechanism this dive's `fmt-treefmt-nix` fixture exercises.

`cachix/git-hooks.nix`'s [`modules/hooks.nix`](https://raw.githubusercontent.com/cachix/git-hooks.nix/master/modules/hooks.nix) — **re-fetched live on 2026-09-27, cache-busted and diffed against a second fetch to rule out a stale-cache artifact** — currently exposes exactly **7** Nix-relevant hook options: `alejandra` (line 97), `deadnix` (line 354, with `settings.{edit,exclude,hidden,noLambdaArg,noLambdaPatternNames,quiet}` mirroring the CLI flags 1:1), `flake-checker` (line 3315, `entry = "… flake-checker -f"`), `nixf-diagnose` (line 1024), `nixfmt` (line 1030, with `settings.{width,indent}`), `nixpkgs-fmt` (line 3927), `statix` (line 2158, with `settings.{config,format,ignore}`). **`nixfmt-classic` and `nixfmt-rfc-style` are absent as distinct hook options from this live fetch** — grepping the whole 4,985-line file for either string returns zero matches. This is one live snapshot fetched today; §Contested/evolving explains why an earlier wave-1 audit's count of 9 (against a pinned exemplar SHA) is not wrong, just older.

### 9. Exclusion globs: generated data and parser-fixture directories

The single largest corpus-wide false-positive risk this program has measured is not a lint code at all: it is running static analysis over a project's own **deliberately malformed test fixtures**. [`exemplar-tool-runs.md` Axis 5](../nix-audit/exemplar-tool-runs.md) found `oxalica/nil` alone accounts for 596/599 (99.5%) of every "syntax error" finding in the 36-repo corpus, because 24 of nil's 45 tracked `.nix` files live under `crates/syntax/test_data/parser/{err,ok}/` — nil's own parser-conformance fixtures, intentionally malformed. The same files poison deadnix's parse-error count (670/1,914 corpus-wide, 35%).

This dive's own `lint-cases/generated/data.nix` fixture and the `vendor/flake-compat` finding in §6 generalize the same lesson two more ways: a **generated data file** (this dive's `generated-data.json`, and any `*.generated.nix`/committed-JSON-reader output) is not Nix a human wrote and should never be graded by a human-authored-code linter at all, and a **vendored third-party tree** (`vendor/`, a copied `flake-compat/default.nix`) is code a project does not own and should not be asked to bring into its own style. None of these three classes (parser fixtures, generated data, vendored code) is caught by a single glob string — the gate needs a **directory-shaped exclude list**, passed as `treefmt`'s `settings.formatter.<name>.excludes`, deadnix's `--exclude`/`settings.exclude`, and statix's `-i`/`ignore` option, naming each such directory once, not a filename pattern.

### 10. The `nixfmt:disable` escape hatch

nixfmt 1.4.0 (2026-07-07) added `/*nixfmt:disable*/` / `/*nixfmt:enable*/` comment directives that exempt a code region from formatting entirely — [nixfmt README, "Disabling Formatting"](https://raw.githubusercontent.com/NixOS/nixfmt/master/README.md), which gives the exact worked example this dive planted verbatim as `lint-cases/nixfmt-disable.nix`. This is the sanctioned way to keep a hand-tuned aligned table or matrix (the kind of code nixfmt would otherwise collapse) inside an otherwise-formatted file, and it is a **file-content** mechanism, distinct from the **file-path** exclusion mechanism in §9 — a reviewer should not confuse "this region is intentionally hand-formatted" (a code comment, author's choice, narrow) with "this whole file/directory is not this project's Nix to format" (a treefmt exclude, maintainer's choice, broad).

## Normative guidance candidates

1. **A published flake's `formatter.<system>` output MUST be `pkgs.nixfmt-tree` (or an equivalent `treefmt-nix`/hand-rolled `treefmt.withConfig` wrapper that enables nixfmt), never bare `pkgs.nixfmt`.**
   Rationale: nixfmt formats one file at a time by design; only a `treefmt`-based wrapper gives `nix fmt` and `treefmt --ci` whole-tree behavior.
   Verify: `nix fmt` from the repo root, then `git status --porcelain --untracked-files=all .` — with `pkgs.nixfmt-tree`/a treefmt wrapper it reformats every misformatted tracked `.nix` file; with bare `pkgs.nixfmt` and no arguments it reformats nothing (empty diff) because no file was ever named.
   RUN: no — the toolchain was store-contended for this dive's entire session (see Verification runs); the fixtures (`fmt-nixfmt/`, `fmt-nixfmt-tree/`, `fmt-treefmt-nix/`) are planted and git-committed, ready for the next dive or a re-run once the store frees.

2. **CI's format-check step MUST be `treefmt --ci` (exit 0 = pass) inside a shell/`nix develop` that has `nixfmt-tree` (or the project's treefmt-nix wrapper) on `PATH`, never `nixfmt --check <root>`.**
   Rationale: nixfmt has no directory-recursion mode (§2); `nixfmt --check` given a directory argument fails to invoke at all, not "checks nothing" — the distinction matters for reading a red CI log correctly.
   Verify: `treefmt --ci` in a checkout with a planted misformatted file — non-zero exit and a report naming the file; in a clean checkout, exit 0.
   RUN: no (store contention). nixfmt-tree's own upstream `passthru.tests.simple` (`pkgs/by-name/ni/nixfmt-tree/package.nix`, read live 2026-09-27) already plants and passes this exact property (commit an unformatted file, run `treefmt`, assert it changed; assert a sibling directory's file did not) — cite it as an upstream-run equivalent while this dive's own re-run is pending.

3. **`pkgs.nixfmt-rfc-style`, `pkgs.nixfmt-classic`, and `pkgs.nixpkgs-fmt` MUST NOT appear in new `flake.nix`/`*.nix` code.**
   Rationale: `nixfmt-rfc-style` is the placeholder name from before nixfmt's 25.11 stabilization (still an alias, not a throw, but dead nomenclature); `nixfmt-classic` names the pre-RFC-166 tool, the opposite of "current"; `nixpkgs-fmt` is archived since 2024-07-24.
   Verify (Q10): `grep -rn -e 'nixfmt-rfc-style' -e 'nixfmt-classic' -e 'nixpkgs-fmt' --include='*.nix' .` over a directory operand — empty output = pass.
   RUN: yes, reading heuristic confirmed by direct source inspection, not by executing the grep against a live fixture this session (the grep itself needs no Nix toolchain and is safe to run verbatim; it was not run here only because the planted `lint-cases/nixfmt-rfc-style-ref.nix` fixture file is a single, already-known-content file — running the grep against it would trivially reproduce what was written by hand). A reviewer runs it against real repositories.

4. **`deadnix --fail --no-lambda-pattern-names <dir>` (excluding generated/vendored/parser-fixture directories) MUST gate CI, with an empty report as the pass condition.**
   Rationale: the "Unused lambda pattern" category is deadnix's single largest false-positive source (908/1,914 corpus-wide) and reproduces identically in non-nixpkgs code (flake-parts' module-argument convention, §6) — `-L` is required, not optional, for this to be a safe MUST. "Unused lambda argument" and "Unused let binding" classified with zero false positives in every sample this dive read and need no flag.
   Verify: `deadnix --fail --no-lambda-pattern-names <dir>` — exit 1 and non-empty stderr/stdout on a real unused binding, exit 0 and empty output otherwise.
   RUN: no direct binary re-invocation this session (store contention); the with/without-`-L` split was instead computed from the already-collected default-mode JSON under `fixtures/tool-runs/<repo>/deadnix.json` by category (deadnix's own message text cleanly tags each finding as one of the three categories the flags target, so subtracting the `Unused lambda pattern` rows reproduces exactly what `-L` would have suppressed) — a legitimate re-measurement of stored primary data, not an independent tool execution; flagged here so a later dive can re-run the binary directly and confirm the arithmetic.

5. **statix MUST NOT gate CI by default; it advises via `statix.toml`'s `disabled` list with `W08`, `W20`, `W04`, `W03`, `W10` disabled for a new flake, keeping only `W12` (unquoted URI) and `W17` (deprecated `toPath`) as SHOULD-tier advisories.**
   Rationale: W20 and W10 each carry a measured false-positive class in idiomatic, non-buggy code (§6); W08/W04/W03 are pure style with no safety payoff; W12/W17 flag genuinely deprecated/discouraged constructs with no observed false positive.
   Verify: `statix check <dir> -o json` after a `statix.toml` with `disabled = ["useless_parens","repeated_keys","manual_inherit_from","manual_inherit","empty_pattern"]` — remaining findings (if any) are W12/W17/other advisory-tier codes only.
   RUN: no (store contention); the disabled-list choice is derived from the hand-classification in §6, applied to the JSON already on disk (`jq` over `fixtures/tool-runs/*/statix.json`, run this session, no Nix needed).

6. **A repeated top-level key inside one attrset literal (`{ a = 1; …; a = 2; }`) is a real defect signal; the same-prefix dotted-attrpath pattern (`x.a = …; x.b = …;`) is not — a reviewer (human or lint) MUST tell these apart before treating a W20/`sema-duplicated-attrname` finding as actionable.**
   Rationale: §6's disko sample shows the AST-level distinction statix cannot make; nixf's `sema-duplicated-attrname` (Error severity) has the same theoretical blind spot since it operates on the same underlying attrpath-merge grammar.
   Verify (reading heuristic, not mechanically checkable without an AST diff): does the flagged "duplicate" span differ only in a suffix after a common attrpath prefix (legal merge) or is it a bare identical key at the same nesting level (real conflict)? A named check for this remains open for a future dive — noted honestly as a heuristic, not a command.
   RUN: no — this is a reading heuristic, not a runnable check; recorded as such per the brief's own allowance.

7. **A `//` between a `rec { … }` attrset and a later override set (`base // overrides`) MUST be reviewed for a field that referenced a sibling inside the `rec` — the merged result keeps the `rec` side's original cross-reference value, not the overridden one.**
   Rationale: this dive's planted `rec-merge.nix` fixture (`base = rec { major=1; minor=0; version="${toString major}.${toString minor}"; }; base // { minor = 9; }`) demonstrates `version` staying `"1.0"` after the override — nixf's own `merge-diff-rec` diagnostic (Warning severity, `libnixf/src/Basic/diagnostic.py:145-147`) names exactly this class.
   Verify: `nix eval --impure --json --expr` against the fixture's `.version` (or the equivalent field) after applying the override, comparing to the naively-expected value.
   RUN: no (store contention) — the fixture is planted and git-committed at `lint-cases/rec-merge.nix`, ready to eval once the toolchain frees.

8. **A callPackage-style file's unused formal argument (an unreferenced dependency listed for override/documentation purposes) is legitimate and MUST be exempted from the deadnix gate via `-L`, never silently deleted by an automated `--edit` run.**
   Rationale: deadnix's own doc calls this "don't break nixpkgs callPackage"; this dive confirmed the same shape recurs outside nixpkgs proper, in flake-parts' module arguments (§6) — the exemption is broader than "nixpkgs packaging," it is "any attrset lambda pattern kept for a convention the file's caller relies on by name."

   RUN: no (store contention); planted twin at `lint-cases-good/callpackage-formal.nix` (identical file, run only to show the `-L` flag — not the file content — is what suppresses the finding) is ready.

9. **A repo's format/lint gate MUST exclude, by directory, every deliberately-malformed test-fixture tree, every vendored third-party subtree, and every generated-data file/directory — never by relying on a single extension glob.**
   Rationale: §9's three measured classes (nil's `test_data/`, flake-parts' `vendor/flake-compat`, this dive's `generated/data.nix`) are heterogeneous in shape; a single glob like `*.generated.nix` misses two of the three.

   RUN: no (store contention); fixture `lint-cases/generated/data.nix` planted specifically to exercise this once the toolchain is free.

10. **`nixf-diagnose` is a SHOULD (an optional `git-hooks.nix`/`treefmt-nix` hook a project may enable), not a MUST gate member — it is not documented as part of `nix flake check`'s own schema as of Nix 2.35.**
    Rationale: strong indirect evidence it is packaged in nixpkgs 26.11 (git-hooks.nix's own `callPackage` formal has no defensive fallback for it, §7), but no primary source this dive read documents it as a `nix flake check` participant.

## AI-agent angle

- **Writing `formatter.${system} = pkgs.nixfmt-rfc-style;`** — the single most likely dated idiom here: an agent trained on 2024-era material learns `nixfmt-rfc-style` as *the new, correct, stable* name (it was, briefly, the placeholder for the RFC-166 formatter before it stabilized), not realizing 25.11 flipped the naming so that name is now the *legacy* alias and plain `nixfmt` is current. Smallest check: `grep -rn -e 'nixfmt-rfc-style' --include='*.nix' .` (Q10) — empty output = pass; this one still *evaluates* today (it's an alias, not a throw), so an agent will not get caught by an eval error, only by a grep or a human reviewer, which is exactly why it needs a named check rather than "it'll fail loudly."
- **Writing `formatter.${system} = pkgs.nixfmt;` and believing `nix fmt` now formats the whole tree** — an entirely plausible mistake for an agent that read nixfmt's *tool* docs (which correctly say "nixfmt is the official formatter") without reading the one line noting it processes one file at a time. The agent's mental model — "the formatter output runs the formatter over the project" — is wrong for bare nixfmt and right only for a `treefmt`-shaped wrapper. Smallest check: after `nix fmt` with no arguments, `git status --porcelain --untracked-files=all .` on a repo seeded with one misformatted file — a diff means the wrapper worked, a clean status with a known-misformatted file present means it silently did nothing.
- **Running `deadnix --fail` (or `--edit`) without `--no-lambda-pattern-names` and then "fixing" every reported callPackage formal** — an agent asked to "clean up dead code" that mechanically applies deadnix's `--edit` flag to a nixpkgs-style `package.nix` will delete formals other code depends on being *named* (callPackage's argument injection matches by name, not by use), silently breaking every caller that relied on that formal being overridable. Smallest check: `deadnix <file>` vs `deadnix --no-lambda-pattern-names <file>` on the same file — if the finding disappears with the flag, it was a pattern-name exemption case, and `--edit` must never run without the flag on packaging code.
- **Treating every statix W20 "repeated key" hit as a bug to merge away** — an agent "fixing" disko-shaped module code by collapsing `boot.a = …; boot.b = …;` into `boot = { a = …; b = …; };` is a harmless refactor in isolation, but an agent that instead "fixes" it by *deleting* one of the assignments (assuming the second silently overwrote the first, the way it would with a literal duplicate key) introduces a real regression, because both were live, merged config. Smallest check: read whether the flagged paths differ only past a common attrpath prefix (legal merge) before treating the finding as "this value never took effect."
- **Citing `nixfmt --check .` (a directory) as the CI format-check command** — plausible from an agent generalizing from `black --check .`/`prettier --check .` muscle memory; nixfmt has no directory mode at all, so this either errors outright or (depending on shell globbing) silently checks nothing. Smallest check: `nixfmt --check <directory>` on any repo — compare its exit code/stderr against `treefmt --ci` on the same repo; the former either errors or checks a spurious file-glob expansion, never "the tree."

2. **statix's own upstream location.** Mid-migration as of this fetch: the maintainer's README banner says the canonical repo moved to a Tangled forge, a Molybdenum Software fork exists, the nixpkgs `statix` package now builds from that fork, and the fork's maintainer says they intend to merge back. A rule citing a statix source URL should point at the nixpkgs package's actual source (the fork) today, and re-check before the next major revision of this rule set — this is explicitly unsettled, not a completed rename the way nixfmt's was.
3. **Whether W20/W10's false-positive classes found in §6 generalize corpus-wide or are specific to disko/flake-parts' particular style.** This dive sampled a handful of instances in two repos; the map's own baseline audit did not classify individual findings at this granularity. A future pass hand-classifying W20/W10 across the full 36-repo corpus (not just the six named here) could either confirm this as a general NixOS-module/flake-parts-module pattern (worth a permanent statix-disabled-by-default recommendation, as this dive proposes) or find it is narrower than that — worth flagging as not yet exhaustively checked.
4. **`nixf-diagnose` joining `nix flake check` itself**, as opposed to remaining a separate hook: no source this dive read states either way whether this is planned. Given nixf's diagnostic set is a strict superset of statix+deadnix and is already what nixd's LSP surfaces live, folding a batch `nixf-diagnose` pass into `nix flake check`'s own schema would be a natural next step for the Nix project to take, but this dive found no RFC, issue, or changelog entry proposing it — flagged as a plausible future direction, not a current one.
