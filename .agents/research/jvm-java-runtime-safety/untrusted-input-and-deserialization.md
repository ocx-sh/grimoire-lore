## Summary

- Nine shapes cover this family, not an OWASP survey: native deserialization, Jackson polymorphic typing, XXE (×7 parser types), JNDI lookup, ZipSlip, path traversal, command concatenation, `java.util.Random` misuse, and the SonarJava Blocker/Critical intersection as a backstop gate.
- `ObjectInputStream.readObject()` on untrusted bytes is RCE-shaped by design; the fix is an `ObjectInputFilter` allow-list (JDK 9+, `ObjectInputFilter.Config.createFilter`), not a deny-list ([OWASP Deserialization](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html), [CERT SER12-J](https://cmu-sei.github.io/secure-coding-standards/sei-cert-oracle-coding-standard-for-java/rules/serialization-ser/ser12-j/)).
- "A `PolymorphicTypeValidator` is configured" is not the check — **"the validator is on a version ≥ 2.18.8 / ≥ 2.21.4 / ≥ 3.1.4"** is, because CVE-2026-54512 and CVE-2026-54513 both bypass a correctly-configured PTV by hiding the denied class inside a generic parameter or an array component the validator never inspects ([GHSA-j3rv-43j4-c7qm](https://github.com/advisories/GHSA-j3rv-43j4-c7qm)).
- CVE-2026-54512 and -54513 are two *different* bypass mechanisms sharing one advisory: `-54512` smuggles the class as a generic parameter (`ArrayList<Evil>`), `-54513` smuggles it as an array component (`Evil[]` via `allowIfSubTypeIsArray()`) — a PTV upgrade fixes both, but a hand-rolled validator patch for one does not close the other.
- Hardening `DocumentBuilderFactory` hardens nothing else: `SAXParserFactory`, `XMLInputFactory` (StAX), `TransformerFactory`, `SchemaFactory`, `javax.xml.validation.Validator`, JAXB's `Unmarshaller`, and XPath evaluators over an unhardened source each need their own disable-DTD / disable-external-entities call ([OWASP XXE Prevention](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html)).
- There is no dedicated CERT rule numbered for JNDI; the operative primary sources are Error Prone's `BanJNDI` check (bans ~40 JDK lookup APIs by name) and the Log4Shell root-cause advisory ([VU#930724](https://www.kb.cert.org/vuls/id/930724)) — CERT's closest named rule is `IDS54-J` (LDAP injection), a narrower case of the same JNDI-Reference-object attack.
- ZipSlip has no fix in the JDK itself: `java.util.zip` and `java.util.jar` ship no path-containment check, so every extractor must resolve `destDir.toPath().resolve(entry.getName()).normalize()` and verify it still starts with `destDir` before writing ([Snyk zip-slip-vulnerability](https://github.com/snyk/zip-slip-vulnerability), `CVE-2018-1002200`-class).
- `ProcessBuilder(String... command)` (array form) is the only correct shape when any argument can be attacker-influenced; `Runtime.exec(String)` or building a shell string and handing it to `bash -c` is the vulnerable shape regardless of escaping attempted, per Oracle's own `INJECT-4` guideline ("do not place any untrusted data on the command line" without base64/temp-file/stdin indirection).
- `java.util.Random`, `Math.random()`, `ThreadLocalRandom`, and even `SplittableRandom` are all forbidden wherever unpredictability is a security property (tokens, password reset codes, session IDs); only `java.security.SecureRandom` (or `UUID.randomUUID()`, itself backed by `SecureRandom`) qualifies ([OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)).
- **Core SpotBugs has no XXE detector, no command-injection detector, and no path-traversal detector at all** — those live only in `find-sec-bugs`'s `XXE_*`, `COMMAND_INJECTION`, and `PATH_TRAVERSAL_IN`/`PATH_TRAVERSAL_OUT` rules ([find-sec-bugs bug list](https://find-sec-bugs.github.io/bugs.htm)). Core SpotBugs *does* independently carry `DMI_RANDOM_USED_ONLY_ONCE` for the `Random` misuse shape.
- Measured 2026-09-12: `find-sec-bugs` is **0/32** across the exemplar corpus, and all three exemplars that run SpotBugs (kafka, assertj, spotless) run it without the plugin (jvm-quality-gates.md, `JAVA-LINT-10`). A rule in this family that assumes "SpotBugs is wired, so XXE/path-traversal/command-injection are covered" is wrong about every measured adopter.
- Oracle's own Secure Coding Guidelines page has already been edited for JDK 24: every one of its 20 Access Control guidelines (`9-1`..`9-20` / `ACCESS-1`..`ACCESS-20`) now opens with "NOTE: The security manager has been permanently disabled since Java 24, so this guideline is only applicable to earlier releases" ([oracle.com/seccodeguide](https://www.oracle.com/java/technologies/javase/seccodeguide.html)) — the page may be cited, but only through its own historical-scope annotation, never as live guidance.
- Serialization Filtering (`ObjectInputFilter`) is Oracle's own named remedy in the same document (`8-6`/`SERIAL-6`), enhanced in JDK 17 with context-specific filters — cite that guideline instead of section 9 for anything deserialization-shaped.
- The OCX SDK's JSON-from-subprocess boundary is **inside** the deserialization-shape boundary and **outside** the path/command-construction boundary — see decision (c) below; they are not one boundary.
- `Runtime.exec`/`ProcessBuilder` built from concatenated attacker-influenced strings is P0 specifically because it sits on the OCX SDK's own CLI-subprocess boundary in the other direction: the SDK is the caller constructing the command, so JAVA-SEC-07 binds it as a producer, independent of decision (c)'s consumer-side framing.
- The SonarJava Blocker/Critical `BUG`/`VULNERABILITY` intersection (46 of 501 rules) is a ready-made "never ship" backstop gate, but it is a SonarQube-specific artifact — cite it only where the build already runs SonarQube; it duplicates nothing above, it catches what the individual rules miss.
- None of the nine shapes above appear as source-code evidence anywhere in the exemplar corpus's checked-out files (the corpus is dependency libraries and build tooling, not applications with an attacker-facing surface) — the one partial exception is `gradle/gradle`'s own build-logic reading a locally-generated cache file via unfiltered `ObjectInputStream` (see Exemplar evidence), which is a low-risk instance of the exact unguarded shape this family flags.
- All measured `ProcessBuilder` call sites in the corpus (5, across apollo-kotlin, detekt) use the array/varargs constructor, never a concatenated shell string — the correct shape is already the corpus norm for build-time process spawning, even where nothing enforces it.

## Findings

### 1. Three decisions the map asked for

**(a) The MUST list lives in the depth file, with exactly one line duplicated bounded into the index — and that line already exists.** The map's "Conflicts resolved" #2 fixed the mechanism for shared MUST rows: "the MUST line only, never the depth," and it names **secure deserialization** as one of the ~6 rows already selected for that treatment. This dive does not reopen that call; it only supplies the depth. Concretely: `rules/java-quality.md` (the always-loaded index) carries one line —
> Never deserialize untrusted data with native Java serialization, and never enable Jackson default typing, without a current, allow-list-based validator. → `security-and-untrusted-input.md`

— and every other shape in this file (XXE, JNDI, ZipSlip, path traversal, command construction, `Random`) stays in the depth file only. The reasoning: the index budget is ~114-229 lines across the catalog ([config-inventory.md](../jvm-audit/config-inventory.md) Axis 1.1); deserialization is the one shape whose failure mode (RCE via a gadget chain reachable from a network-facing endpoint) is categorically worse than the other eight (file corruption, information disclosure, or a local build hazard), so it is the one line worth the always-loaded budget. The other eight are exactly as important *when the routing line fires* ("parsing, deserialising, extracting, executing, or resolving a path from data you did not write" — the `JAVA-SEC` routing description already in the map, line 991) — they just don't need to be loaded on every turn regardless of task.

**(b) Oracle's Secure Coding Guidelines section 9 may be cited, but only through its own annotation, never as standalone guidance.** [JEP 486](https://openjdk.org/jeps/486) permanently disabled the Security Manager in JDK 24: enabling it at startup now aborts the JVM with an explicit error, and `System.setSecurityManager()` throws `UnsupportedOperationException`. Fetching `oracle.com/java/technologies/javase/seccodeguide.html` directly on 2026-09-12 shows Oracle has already edited the page for this: **every one of the 20 Access Control guidelines** (`9-1` `ACCESS-1` through `9-20` `ACCESS-18`/`19`/`20`, with `EXTEND-2`/`EXTEND-3`/`OBJECT-2` also redirected into section 9) opens with a verbatim note: *"NOTE: The security manager has been permanently disabled since Java 24, so this guideline is only applicable to earlier releases."* This resolves the decision cleanly: **cite section 9 only when quoting its own historical-scope disclaimer**, never as an instruction to add permission checks or `doPrivileged` blocks to new code — a rule that told an agent to "check ACCESS-4" without that context would be actively wrong for any JDK-24+ target, which every consumer here is (Gradle 9's daemon floor is Java 17, but the OCX SDK/plugin's own CI runs current JDKs). The rest of the same Oracle document — sections 0 (Fundamentals), 1 (DoS), 2 (Confidential info), 3 (Injection/Inclusion, including `INJECT-4` command-line and `INJECT-5` XML DTD), 5 (Input Validation), and 8 (Serialization, including `SERIAL-6` Filter untrusted serial data) — carries no such caveat and is fully current; cite those sections freely.

**(c) The OCX SDK's JSON-from-subprocess payload is inside the deserialization-shape boundary, and outside the command/path-shape boundary — it is not one boundary.** Given (per the process-and-cli-boundary dive) that the SDK maps a 16-member exit-code enum and never parses stderr text, the remaining question is the JSON on stdout. Two different shapes apply to two different halves of this family:
  - **Inside** for `JAVA-SEC-02` (Jackson polymorphic typing): the JSON payload's *bytes* originate from the `ocx` CLI, but the CLI itself is a thin client over a networked OCX service — resource listings, org/project metadata, and error payloads it prints can carry attacker- or tenant-influenced strings (a resource name, a description field) that reached the CLI from that service, not from the SDK's own process. If the SDK's DTOs are ever deserialized polymorphically (a `@JsonTypeInfo` base type, or a plugin/extension response shape), that JSON is exactly as untrusted as JSON received directly over HTTP — the subprocess is a pipe, not a trust boundary, for data it did not originate. The mitigation is the same as any other Jackson consumer: fixed, closed DTOs wherever possible; if polymorphism is unavoidable, a current `PolymorphicTypeValidator` (≥2.18.8/2.21.4/3.1.4) with an explicit allow-list, never global default typing.
  - **Outside** for `JAVA-SEC-04`/`05`/`07`/`08` (JNDI, ZipSlip, command construction, path traversal): here the SDK is the *producer*, not the consumer, of the untrusted-shaped operation — it is the one invoking `ProcessBuilder` to launch `ocx`, so the relevant rule is `JAVA-SEC-07` binding the SDK's own subprocess-invocation code (array-args, no shell), not a rule about data arriving *from* the subprocess. There is no archive extraction, no JNDI lookup, and no path built from the subprocess's output in the described boundary, so those shapes do not apply to the JSON-parsing surface at all.
  - **Net effect on the SDK's rules**: `JAVA-SEC-02` is a MUST for the SDK's JSON-handling code; `JAVA-SEC-07` is a MUST for the SDK's process-launching code; they are two different call sites in the same library, not one blanket "the subprocess boundary is/isn't trusted" verdict.

### 2. Native deserialization without an ObjectInputFilter

`ObjectInputStream.readObject()` on a byte stream you did not fully control the origin of is the `ysoserial` gadget-chain shape: the stream's `writeObject`/`readObject` control flow reconstructs an object graph before any application code sees it, so `readObject`, `readResolve`, `readExternal`, and finalizers on classes already on the classpath can execute as a side effect of *reconstruction alone* ([OWASP Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html)). CERT's rule is unambiguous: [`SER12-J`. Prevent deserialization of untrusted data](https://cmu-sei.github.io/secure-coding-standards/sei-cert-oracle-coding-standard-for-java/rules/serialization-ser/ser12-j/) — "deserializing untrusted data... is an inherently dangerous activity because the content of the incoming data stream determines the objects that are created." The fix, in order of preference:

1. **Don't** — use JSON/Protobuf/a hand-rolled record format instead of `Serializable` for anything crossing a trust boundary.
2. **`ObjectInputFilter`** (JDK 9+, `java.io.ObjectInputFilter`) — an allow-list filter set via `ObjectInputStream.setObjectInputFilter(filter)` or globally via `jdk.serialFilter`/`-Djdk.serialFilter=...`. Oracle's own guideline names this the current remedy: [Guideline 8-6, "Filter untrusted serial data"](https://www.oracle.com/java/technologies/javase/seccodeguide.html) — "Serialization Filtering is a feature introduced in JDK 9 to improve both security and robustness... JDK 17 enhanced this feature by implementing context-specific filters."
3. A hand-written `resolveClass()` override that throws `InvalidClassException` for anything off an explicit allow-list, if the target JDK predates 9 (should not apply to any consumer here — floor is 17).

The reviewer-facing shape: `grep -rn 'extends ObjectInputStream\|new ObjectInputStream(' --include=*.java` and confirm every hit either (a) reads a stream this process itself wrote (self-round-trip, low risk but still worth a comment saying so) or (b) has an adjacent `setObjectInputFilter` call. **Error Prone's `BanSerializableRead`** (severity `ERROR`, [errorprone.info/bugpattern/BanSerializableRead](https://errorprone.info/bugpattern/BanSerializableRead)) is the automatable version of this same check: "Deserializing user input via the `Serializable` API is extremely dangerous." It is a MUST-severity check in Error Prone's suite, but only fires where Error Prone is wired at all — see finding 10 for how often that is true in the corpus (13/32, jvm-quality-gates.md).

### 3. Jackson polymorphic deserialization and the 2026 PTV bypass

Two failure modes, escalating:

**Global default typing** — `ObjectMapper.enableDefaultTyping()` (or its 2.10+ successor `activateDefaultTyping(PolymorphicTypeValidator, ...)` called with a permissive validator) makes *every* field typed `Object` or a non-final type eligible for polymorphic resolution from a `@class` (or similar) property in the JSON. If any gadget-capable class (a class whose no-arg constructor, setter, or `readResolve`-equivalent has an exploitable side effect) is reachable on the classpath, the attacker picks it by name. Jackson's own [CVE-criteria wiki page](https://github.com/FasterXML/jackson/wiki/Jackson-Polymorphic-Deserialization-CVE-Criteria) documents the project's own retreat from this shape: through 2.9.x Jackson shipped a deny-list of ~90 known-gadget classes; from **2.10** onward the safe path is "Safe Default Typing," an allow-list `PolymorphicTypeValidator` (`PTV`), with the old unsafe methods deprecated for removal in Jackson 3.0. **After 2021-12-31, Jackson does not accept new CVEs against default-typing gadgets at all** — the project's position is that this is a configuration error, not a library defect, once a PTV is available.

**A too-broad `@JsonTypeInfo` base type** is the same shape without calling it "default typing": `@JsonTypeInfo(use = Id.CLASS)` (or `Id.MINIMAL_CLASS`) on a base type as generic as `Object`, `Serializable`, or any interface with many unrelated implementors on the classpath reopens the identical attack surface, because the type-id string in the JSON is still attacker-controlled and still resolves to an arbitrary class unless a validator narrows it.

**Why "a validator is present" stopped being the check in 2026.** [GHSA-j3rv-43j4-c7qm](https://github.com/advisories/GHSA-j3rv-43j4-c7qm) (CVE-2026-54512 / CVE-2026-54513, fixed 2026-06-04) is two bypasses of a *correctly configured, allow-list* `PolymorphicTypeValidator`:

| CVE | Mechanism | Example shape |
|---|---|---|
| CVE-2026-54512 | `DatabindContext._resolveAndValidateGeneric()` checks only the substring of the type-id before the first `<` against the PTV; the nested generic parameter is parsed and instantiated **without** being re-validated. | Allow-list contains `java.util.ArrayList`; payload type-id is `java.util.ArrayList<com.evil.EvilGadget>` — `EvilGadget` is never checked. |
| CVE-2026-54513 | `BasicPolymorphicTypeValidator.Builder.allowIfSubTypeIsArray()` approves a value purely because `clazz.isArray()` is `true`; the array's *component* type — the thing actually instantiated once per element — is never checked. | Allow-list contains an array-of-anything rule; payload type-id is `com.evil.EvilGadget[]`. |

Both affect `jackson-databind` (and the Jackson 3.x `tools.jackson.core` coordinates) `≥2.10.0 <2.18.8`, `≥2.19.0 <2.21.4`, and `≥3.0.0 <3.1.4`; both are fixed in `2.18.8`, `2.21.4`, `3.1.4`. CVSS 3.1 is 8.1 (High) for both, unauthenticated and network-reachable wherever the vulnerable JSON reaches an `ObjectMapper` configured this way. The organizational lesson the advisory makes explicit: teams that had already done the right thing — migrated off default typing onto an explicit `PolymorphicTypeValidator` per Jackson's own 2020 guidance — were still exposed, because the validator's own implementation had the gap. **The rule is therefore version-gated, not configuration-gated**: `com.fasterxml.jackson.core:jackson-databind` must resolve to `≥2.18.8` (2.18.x line), `≥2.21.4` (2.21.x line), or `≥3.1.4` (3.x line) wherever any `@JsonTypeInfo`/default-typing polymorphism exists in the dependency graph — a version-catalog pin one minor below any of those floors is silently vulnerable even with a hand-written validator.

### 4. XXE is a per-factory problem, not a per-application one

Every XML entry point in the JDK and common libraries builds its own parser instance with its own default feature set, and hardening one does nothing for the others ([OWASP XXE Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html)):

| Factory / API | Hardening call |
|---|---|
| `DocumentBuilderFactory` | `setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)` (simplest: disables DTDs outright) or, if DTDs are required, disable `external-general-entities` / `external-parameter-entities` / `load-external-dtd` individually plus `setExpandEntityReferences(false)` |
| `SAXParserFactory` | Identical feature strings via `setFeature(...)` — **not** inherited from `DocumentBuilderFactory` hardening |
| `XMLInputFactory` (StAX) | `setProperty(XMLInputFactory.SUPPORT_DTD, false)`, or `IS_SUPPORTING_EXTERNAL_ENTITIES = false` if DTDs are needed |
| `TransformerFactory` | `setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "")` and `setAttribute(XMLConstants.ACCESS_EXTERNAL_STYLESHEET, "")` |
| `SchemaFactory` | `setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "")` and `setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "")` |
| `javax.xml.validation.Validator` | Same two `ACCESS_EXTERNAL_*` properties as `SchemaFactory` |
| JAXB `Unmarshaller` | Not hardened directly — parse through a hardened `XMLInputFactory`/`XMLStreamReader` or `SAXSource` first, then hand that to `unmarshal(Source)` |
| XPath over an untrusted `Document`/`InputSource` | Only as safe as the `DocumentBuilderFactory` used to build the source document — XPath itself has no entity-resolution knob |

Oracle's own guideline states the underlying reason in one line: [`3-5`/`INJECT-5`, "Restrict XML inclusion"](https://www.oracle.com/java/technologies/javase/seccodeguide.html) — "XML Document Type Definitions (DTDs) allow URLs to be defined as system entities... XML External Entity (XXE) attacks insert local files into XML data... Similar attacks may be made using XInclude, the XSLT document function, and the XSLT import and include elements" — XXE is one of at least three related entity-inclusion vectors (DTD, XInclude, XSLT `document()`), and hardening only the DTD path leaves the other two live if XInclude or XSLT transformation is also in use. **The check a reviewer runs**: for every `*Factory.newInstance()` / `new SAXBuilder()` / `new SAXReader()` call, confirm an adjacent hardening block naming that specific factory type — a hardened `DocumentBuilderFactory` two files away does not satisfy a `SAXParserFactory` finding.

### 5. JNDI lookup on untrusted input

There is no CERT rule numbered specifically for JNDI (the closest, [`IDS54-J`, "Prevent LDAP injection"](https://wiki.sei.cmu.edu/confluence/display/java/IDS54-J.+Prevent+LDAP+injection), covers the LDAP-directory-query half of the same API family, not the lookup-name half). The operative shape is Log4Shell's root cause, documented at [CERT VU#930724](https://www.kb.cert.org/vuls/id/930724): if the name passed to `Context.lookup(name)` (or any of ~40 related APIs across `javax.naming`, JDO, JMX, and SQL rowsets) is attacker-influenced, and that name resolves to an `rmi://`, `ldap://`, or `corba://` URL, a malicious server can return a `javax.naming.Reference` object whose `classFactory`/`classFactoryLocation` the JNDI client will fetch and instantiate — remote class loading, independent of any Java-serialization vulnerability. Error Prone's [`BanJNDI`](https://errorprone.info/bugpattern/BanJNDI) check (severity `ERROR`) is the concrete, automatable form of this rule: it bans the JDK's JNDI-lookup surface outright, on the reasoning that "using JNDI may deserialize user input via the `Serializable` API which is extremely dangerous." The reviewer-facing check without Error Prone: `grep -rn '\.lookup(\|InitialContext(' --include=*.java` and confirm every hit's `name` argument is a compile-time constant or comes from a closed, non-attacker-reachable configuration source — never a request parameter, an environment-derived string relayed from a caller, or a value round-tripped through user-supplied config.

### 6. ZipSlip: the JDK ships no safe extraction API

`java.util.zip.ZipInputStream`/`ZipFile` and `java.util.jar.JarInputStream` all return each entry's name as a raw, attacker-controlled string with no validation — `ZipEntry.getName()` can be `../../../../etc/cron.d/evil`, and nothing in the JDK stops `new File(destDir, entry.getName())` from resolving outside `destDir`. [Snyk's disclosure](https://github.com/snyk/zip-slip-vulnerability) names the exact vulnerable idiom, copy-pasted across the Java ecosystem for a decade:

```java
// VULNERABLE — no path containment check
Enumeration<ZipEntry> entries = zip.getEntries();
while (entries.hasMoreElements()) {
    ZipEntry e = entries.nextElement();
    File f = new File(destinationDir, e.getName());   // e.getName() may be "../../evil.sh"
    InputStream input = zip.getInputStream(e);
    IOUtils.copy(input, write(f));
}
```

```java
// FIXED — resolve, normalize, and verify containment before any write
Path destRoot = destinationDir.toPath().normalize();
Path target = destRoot.resolve(e.getName()).normalize();
if (!target.startsWith(destRoot)) {
    throw new IOException("Zip entry escapes target directory: " + e.getName());
}
```

The vulnerability affects every archive format built on the same directory-entry model — `tar`, `jar`, `war`, `cpio`, `apk`, `rar`, `7z` — so a fix written for `ZipInputStream` does not automatically cover a `TarArchiveInputStream` extractor elsewhere in the same codebase; each extraction loop needs its own containment check. There is genuinely no better JDK-native answer as of 2026 — `java.nio.file.Files` gained no "safe extract" method, and third-party archive libraries (Commons Compress, etc.) also leave the containment check to the caller.

### 7. Path traversal outside archive extraction

The general case (a caller-supplied filename, not necessarily from an archive) is CERT [`FIO16-J`, "Canonicalize path names before validating them"](https://wiki.sei.cmu.edu/confluence/display/java/FIO16-J.+Canonicalize+path+names+before+validating+them): "the textual representation of a path name may yield little or no information regarding the directory or file to which it refers" — a naive `String.contains("..")` check is defeated by symlinks, encoded separators, or platform-specific equivalence (`~`, UNC paths, NTFS alternate data streams). The correct order is *resolve, then validate* — `Path.toRealPath()` (follows symlinks) or `.normalize()` (does not) before any containment check against a base directory, mirroring the ZipSlip fix above exactly. This is the same shape as ZipSlip generalized past archive extraction: any time a path is built from `Path.of(base, untrustedSegment)`, the resolve-and-`startsWith` check applies.

### 8. Command construction by concatenation

`Runtime.exec(String command)` splits on whitespace using a platform-dependent, poorly-specified tokenizer — Oracle's own guideline states this plainly: [`3-4`/`INJECT-4`, "Avoid any untrusted data on the command line"](https://www.oracle.com/java/technologies/javase/seccodeguide.html) — "Behavior is platform-specific, poorly documented, and frequently surprising. Malicious data may... cause a single argument to be interpreted as an option... or as two separate arguments." The guidance is not "escape the string better" — it is to never place untrusted data on the command line at all, passing it instead as an encoded argument (Base64), a temp file, or over stdin. Where an argument is unavoidable, the array/varargs form of `ProcessBuilder` (`new ProcessBuilder(cmd, arg1, arg2)`, never `new ProcessBuilder("sh", "-c", cmd + " " + arg)`) is the only form that does not re-introduce a shell-parsing layer, because each array element is passed to the OS `exec` family as one already-delimited argument — string concatenation into a single command element hands a shell the chance to reinterpret `;`, `|`, `` ` ``, or `$()`.

### 9. java.util.Random where unpredictability is required

`java.util.Random`, `Math.random()`/`StrictMath.random()`, `ThreadLocalRandom`, and `SplittableRandom` are all Linear-Congruential or splittable PRNGs with no cryptographic hardness guarantee — an attacker who observes a handful of outputs can reconstruct internal state and predict all future and (for LCGs) prior outputs. [OWASP's Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) is explicit that all four "must not" be used for encryption keys, session identifiers, password-reset tokens, or CSRF tokens — only `java.security.SecureRandom` (seeded from an OS entropy source) or `UUID.randomUUID()` (itself `SecureRandom`-backed since JDK 7) qualify. The corpus-measured detector for this shape ([SpotBugs core, `DMI_RANDOM_USED_ONLY_ONCE`](https://github.com/spotbugs/spotbugs/blob/master/spotbugs/etc/messages.xml)) actually catches a narrower bug — a fresh `Random` instantiated per call rather than reused — not the security property directly; the security-relevant check (`Random` used at all in a security-sensitive context) is SonarJava's `S2245` or a manual read of every `new Random()`/`ThreadLocalRandom.current()` call site adjacent to a token/key/nonce variable name.

### 10. What core SpotBugs covers and what needs find-sec-bugs

Teams reach for "we run SpotBugs" as if it covers this family; measured against [find-sec-bugs's own rule catalogue](https://find-sec-bugs.github.io/bugs.htm) it mostly does not:

| Shape | Core SpotBugs | find-sec-bugs only |
|---|---|---|
| Native deserialization | — | `OBJECT_DESERIALIZATION`, `JACKSON_UNSAFE_DESERIALIZATION`, `DESERIALIZATION_GADGET` |
| XXE (all 7+ factory types) | **none** | `XXE_DOCUMENT`, `XXE_SAXPARSER`, `XXE_XMLSTREAMREADER`, `XXE_XPATH`, `XXE_DTD_TRANSFORM_FACTORY`, `XXE_XSLT_TRANSFORM_FACTORY`, `XXE_SCHEMA_FACTORY`, `XXE_VALIDATOR` |
| JNDI / LDAP | — | `LDAP_ENTRY_POISONING` |
| ZipSlip / path traversal | — | `PATH_TRAVERSAL_IN`, `PATH_TRAVERSAL_OUT` |
| Command construction | — | `COMMAND_INJECTION` |
| `java.util.Random` misuse | **`DMI_RANDOM_USED_ONLY_ONCE`** (core) | `PREDICTABLE_RANDOM` (broader — any use in a security context) |

Core SpotBugs's own `SECURITY` category is real but deliberately thin — it is one of ten categories and does not attempt injection/SSRF/weak-crypto coverage at all; that entire surface (144 vulnerability types, 800+ API signatures per the plugin's own count) lives in `find-sec-bugs`. This matches and does not duplicate `JAVA-LINT-10`'s conclusion (jvm-quality-gates.md): *"SpotBugs earns a place in the gate only when `find-sec-bugs` is wired alongside it, and only on modules that parse, deserialise or execute untrusted input."* This dive adds the row-by-row detail behind that one-line verdict — which specific shapes in this family are and are not visible to a bare SpotBugs run — because `JAVA-LINT-10`'s own measurement is stark: **`find-sec-bugs` is 0/32** across the corpus, and all three exemplars gating on SpotBugs (`apache__kafka`, `assertj__assertj`, `diffplug__spotless`) run it without the plugin. A rule that assumes "SpotBugs is in the gate, so XXE/path-traversal/JNDI/command-injection are covered" is wrong about every measured adopter that runs SpotBugs at all.

## Normative guidance candidates

1. **JAVA-SEC-01 — Never call `ObjectInputStream.readObject()`/`readUnshared()` on a stream whose bytes cross a trust boundary without an `ObjectInputFilter` allow-list attached.** *Rationale:* deserialization is class construction under attacker control before any application check runs; there is no safe deny-list. *Verify:* `grep -rn 'new ObjectInputStream(' --include=*.java`; every hit needs an adjacent `setObjectInputFilter(...)` call or a comment establishing the stream is self-written/self-read. Automated: Error Prone `BanSerializableRead` at `ERROR` (only fires where Error Prone is wired — see `JAVA-LINT-01`).
2. **JAVA-SEC-02 — Any Jackson dependency admitting polymorphic typing (`@JsonTypeInfo` with a non-final base, or any form of default typing) must resolve to `jackson-databind ≥2.18.8`/`≥2.21.4`/`≥3.1.4`, and must configure an explicit `PolymorphicTypeValidator` allow-list — never `enableDefaultTyping()`.** *Rationale:* CVE-2026-54512/54513 bypass a correctly-configured but outdated validator by hiding the class in a generic parameter or array component the old validator code never inspected; "a validator exists" is not sufficient, "the validator's implementation is patched" is. *Verify:* `grep -rn 'enableDefaultTyping\|activateDefaultTyping\|@JsonTypeInfo' --include=*.java --include=*.kt`, then cross-check the resolved `jackson-databind` version in the dependency lock/report against the three floors above — a version catalog entry one patch below any floor is the finding, independent of whether a `PolymorphicTypeValidator` is present.
3. **JAVA-SEC-03 — Every XML parser factory (`DocumentBuilderFactory`, `SAXParserFactory`, `XMLInputFactory`, `TransformerFactory`, `SchemaFactory`, `Validator`, JAXB, and any XPath source) must independently disable DTDs/external entities; hardening one factory type is not evidence for another.** *Rationale:* each factory maintains its own default feature set; XXE_* findings and CVEs are consistently per-factory, not per-application. *Verify:* for every `*Factory.newInstance()` call site, an adjacent `setFeature`/`setAttribute`/`setProperty` block naming that exact factory's disallow-doctype or `ACCESS_EXTERNAL_*` feature. Automated: `find-sec-bugs`'s eight `XXE_*` rules — **not available in core SpotBugs at all**.
4. **JAVA-SEC-04 — Never pass an attacker-influenced string as the name argument to `Context.lookup()` or any of the ~40 related JNDI/JDO/JMX/SQL-rowset lookup APIs.** *Rationale:* a malicious `rmi://`/`ldap://`/`corba://` name can return a `Reference` object whose factory class the JNDI client will remote-load and instantiate (Log4Shell's root cause, not limited to Log4j). *Verify:* `grep -rn '\.lookup(\|new InitialContext(' --include=*.java` — flag any hit whose argument traces to a request parameter, environment variable relayed from an untrusted caller, or user-editable config. Automated: Error Prone `BanJNDI` at `ERROR`.
5. **JAVA-SEC-05 — Every archive-extraction loop must resolve each entry's path against the destination root and reject any entry whose resolved path escapes it, before opening a write stream.** *Rationale:* `ZipEntry.getName()`/equivalent APIs across `zip`/`jar`/`tar`/`war`/`apk`/`7z` return unvalidated attacker-controlled strings; the JDK provides no containment check. *Verify:* every extraction loop (`ZipInputStream`, `ZipFile`, `TarArchiveInputStream`, Commons Compress equivalents) has a `Path.resolve(...).normalize()` + `startsWith(destRoot)` check (or an equivalent library call, e.g. Compress's own `zipSlipProtect` helper where present) before the corresponding `Files.copy`/`FileOutputStream`. Automated: `find-sec-bugs` `PATH_TRAVERSAL_OUT`.
6. **JAVA-SEC-06 — Canonicalize (resolve symlinks or normalize) a caller-supplied path before validating it against a base directory, never after.** *Rationale:* string-level checks (`contains("..")`) are defeated by symlinks and path-equivalence tricks; CERT `FIO16-J`. *Verify:* every `Path.of(base, untrustedSegment)`/`new File(base, untrustedSegment)` site has a resolve-then-`startsWith` check, in that order. Automated: `find-sec-bugs` `PATH_TRAVERSAL_IN`.
7. **JAVA-SEC-07 — Build subprocess commands with the array/varargs `ProcessBuilder` constructor; never concatenate attacker-influenced strings into a single command element or hand a built string to a shell (`sh -c`).** *Rationale:* Oracle's own `INJECT-4`: command-line tokenization is platform-specific and any concatenation reopens shell metacharacter reinterpretation; array elements bypass shell parsing entirely. *Verify:* `grep -rn 'Runtime.getRuntime().exec(\|ProcessBuilder(' --include=*.java --include=*.kt` — flag any single-`String` argument built via `+`/`String.format`/template interpolation, or any `"sh", "-c", ...`. Automated: `find-sec-bugs` `COMMAND_INJECTION`. This is the rule that binds the OCX SDK's own subprocess-launch code (decision (c) above) — 5/5 measured corpus call sites already use the correct array form.
8. **JAVA-SEC-08 — Never use `java.util.Random`, `Math.random()`, `ThreadLocalRandom`, or `SplittableRandom` to generate a token, key, nonce, session id, or any value where an attacker who predicts it gains something.** *Rationale:* all four are non-cryptographic PRNGs reconstructible from a handful of observed outputs. *Verify:* `grep -rn 'new Random(\|Math.random(\|ThreadLocalRandom\|SplittableRandom' --include=*.java` adjacent to a variable name containing `token`/`key`/`nonce`/`session`/`secret`/`password` is the finding; replace with `java.security.SecureRandom` or `UUID.randomUUID()`. Automated: SpotBugs core `DMI_RANDOM_USED_ONLY_ONCE` (narrower — catches only per-call instantiation, not the security-context misuse itself) plus SonarJava `S2245`.
9. **JAVA-SEC-09 — SpotBugs earns a place in the untrusted-input gate only paired with `find-sec-bugs`, scoped to modules that actually parse/deserialize/execute untrusted input.** *Rationale:* core SpotBugs has zero detectors for XXE, command injection, or path traversal, and only an indirect one (`DMI_RANDOM_USED_ONLY_ONCE`) for `Random` misuse — running SpotBugs alone and treating this family as "gated" is a false sense of coverage. *Verify:* `grep -rn 'findsecbugs' **/*.gradle* **/pom.xml **/*.toml` in any repo/module that also declares a `spotbugs {}`/`spotbugs-maven-plugin` block with a bound execution — **empty output plus a SpotBugs gate is the finding** (this is `JAVA-LINT-10`, restated here because this family is exactly the coverage gap it names; do not duplicate its text into the lint-gate file, cross-reference it instead).
10. **JAVA-SEC-10 — Do not cite Oracle's Secure Coding Guidelines section 9 (Access Control, guidelines `9-1`..`9-20`) as live guidance for any JDK-24+ target; cite it only via its own historical-scope note, or cite section 8 (`SERIAL-6`, `ObjectInputFilter`) instead for deserialization hardening.** *Rationale:* JEP 486 permanently disabled the Security Manager the entire section describes; Oracle's own page already carries the disclaimer on every guideline in the section. *Verify:* a reading heuristic — any generated rule text that says "check permissions," "use `doPrivileged`," or "restrict via `SecurityManager`" for code targeting JDK 24+ is wrong regardless of source; grep authored rules for `SecurityManager`/`doPrivileged`/`AccessController` and confirm each hit is scoped to "pre-JDK-24 code only."

## Exemplar evidence

- **`gradle__gradle@ea17004a31:build-logic/documentation/src/main/groovy/gradlebuild/docs/model/SimpleClassMetaDataRepository.java:46-48`** — `new ObjectInputStream(new BufferedInputStream(inputStream))` then `objInputStream.readObject()`, with no `ObjectInputFilter` anywhere in the file. This is the exact shape `JAVA-SEC-01` flags, present in gradle/gradle's own build-logic. Risk context lowers the severity (the file is a locally generated `repoFile` cache the same build-logic module writes via `store()`, not attacker-reachable), but the *code shape* is unguarded regardless — a genuine, if low-risk, instance of "presence without a filter" in the one exemplar this dive could measure it in.
- **`apollographql__apollo-kotlin@c145295b72:scripts/bump-kotlin-nightlies.main.kts:79`**, **`scripts/run-firebase-benchmarks.main.kts:69`**, and **`detekt__detekt@45672efb8b:scripts/compare_releases.main.kts:86,95`** — all five measured `ProcessBuilder` call sites in the corpus use the array/varargs constructor (`ProcessBuilder(*args)`, `ProcessBuilder(command)` where `command` is a `List<String>`), never a concatenated shell string. `JAVA-SEC-07`'s correct shape is already the unanimous corpus norm for build-time process spawning — good exemplar evidence, though these are internal release-automation scripts, not code parsing externally-supplied commands.
- **No corpus hits for `java.util.Random`, `SecureRandom`, `ObjectInputFilter`, `PolymorphicTypeValidator`, `@JsonTypeInfo`, any `*Factory.newInstance()` XML call, `Context.lookup(`, or any archive-extraction loop** across the checked-out `*.java`/`*.kt`/`*.kts` files. This is not evidence of good practice — it reflects the corpus shape: 32 dependency libraries and build-tooling repos, whose sparse-checkout materializes build/config files, not the full `src/main/java` tree an attacker-facing application would need for these shapes to appear. `find-sec-bugs` at 0/32 (jvm-quality-gates.md `JAVA-LINT-10`) is the only corpus-wide measurement this family has; a genuine per-shape violation count would require full-source clones of applications, which is out of scope for this corpus by the frame's own design (library/build-tool shape diversity, not application diversity).
- **`FasterXML__jackson-databind@a906e1782b`** ships the very `PolymorphicTypeValidator` class this dive discusses, but as sparse-checked-out (build files only), its `pom.xml` does not show a resolvable version newer or older than the CVE floors — the exemplar is relevant as "the library this rule is about," not as a consumer to measure against the rule.

## AI-agent angle

- **Trained-era default:** an LLM asked to "deserialize this Jackson response" reaches for `mapper.readValue(json, Object.class)` or, worse, `mapper.enableDefaultTyping()` to make a heterogeneous collection round-trip cleanly — both are the exact 2020-era anti-pattern Jackson's own CVE-criteria page retired. **Check:** grep generated code for `enableDefaultTyping`/`activateDefaultTyping` with anything but a `BasicPolymorphicTypeValidator.builder()...build()` argument; a bare `activateDefaultTyping(LaissezFaireSubTypeValidator.instance, ...)` is the same hole with a different class name.
- **"A validator is configured" read as "this is fixed":** a model that knows about the 2020 Jackson hardening (PTV allow-lists) but has a training cutoff before mid-2026 will confidently approve code with a correctly-configured `PolymorphicTypeValidator` and stop there — it has no way to know CVE-2026-54512/54513 exist. **Check:** never trust "a PTV is present" as the finding; resolve the actual `jackson-databind` version against the three floors (2.18.8/2.21.4/3.1.4) every time, mechanically, regardless of what the reviewing model "remembers" about Jackson security history.
- **XXE hardening applied once, assumed to transfer:** a model that correctly hardens a `DocumentBuilderFactory` earlier in a file will often leave a `TransformerFactory` or `XMLInputFactory` untouched later in the same file, reasoning (implicitly) that "XML parsing is now safe in this codebase." **Check:** grep for every `*Factory.newInstance()` independently; count factory-type occurrences against hardening-block occurrences — any factory type appearing more times than its matching hardening pattern is a gap.
- **`Runtime.exec(String)` from Java-tutorial-era training data:** despite being effectively deprecated in practice since Java 5's `ProcessBuilder`, `Runtime.getRuntime().exec("cmd " + arg)` is still the first idiom many models reach for when asked to "run a shell command from Java," because it appears in a huge fraction of pre-2015 StackOverflow/tutorial content. **Check:** any `Runtime.exec(` call with a single `String` argument built via concatenation is flagged regardless of what the string contains — the array-argument overload is the fix, not better escaping.
- **`new Random()` for "randomize this ID/token":** models default to `java.util.Random` or `UUID.randomUUID()` interchangeably when asked for "a random identifier," without distinguishing "needs to be unique" from "needs to be unpredictable" — the former is fine with `Random`, the latter is not. **Check:** any generated token/session-id/reset-code generator using `new Random()` or `Math.random()` rather than `SecureRandom`/`UUID.randomUUID()` is a finding, independent of whether uniqueness (not unpredictability) was the actual stated requirement — ask which property is needed before accepting either.
- **Citing Oracle's Security Manager guidelines (`ACCESS-*`) as current for a JDK-24+ target:** a model whose training corpus is full of pre-2025 "Java security" content will readily suggest `doPrivileged`, custom `SecurityManager` subclasses, or permission-file configuration for isolating untrusted code — all now not just legacy but **non-functional**: `System.setSecurityManager()` throws `UnsupportedOperationException` on JDK 24+, and enabling it at startup aborts the JVM. **Check:** any generated code or rule text referencing `SecurityManager`, `AccessController`, `doPrivileged`, or a `.policy` file for a target whose floor is JDK 24+ is dead on arrival — grep for those four tokens and reject on sight rather than reviewing for correctness.

## Contested / evolving

- **Whether plain SpotBugs (no `find-sec-bugs`) is worth running at all next to Error Prone** is explicitly still open — `JAVA-LINT-10`'s own consolidation flags it as a subarea needing another round (jvm-quality-gates.md, "SpotBugs' remaining value next to Error Prone"), and this dive does not resolve it either; it is the sibling `errors-resources-and-lifecycle` dive's question, not this family's. What this dive *can* say: for the specific shapes in `JAVA-SEC` (deserialization, XXE, JNDI, ZipSlip, path traversal, command injection), bare SpotBugs contributes nothing regardless of that open question's answer — the gap is `find-sec-bugs`-shaped, not SpotBugs-vs-Error-Prone-shaped.
- **Jackson's CVE-acceptance policy itself is unstable practice, trending toward "version floor, not configuration audit."** The project stopped accepting default-typing CVEs after 2021-12-31 on the reasoning that the vulnerability required an explicit opt-in; the 2026 PTV-bypass pair reopened exactly the case the policy was designed to close out, because this time the vulnerability was in the *safe* path's own implementation, not in an opt-in the safe path was created to replace. Trend as of 2026-09-12: treat "Jackson polymorphic deserialization" as a moving target requiring a dependency-freshness check on every release, not a one-time configuration review — the mitigation now sits in "what version is resolved," which drifts silently on every transitive-dependency bump, rather than in "what code was written," which does not.
- **Whether "the JSON payload from a subprocess I launched" is inside or outside the trust boundary is a genuinely contested framing choice**, not a settled one — this dive's decision (c) resolves it *for the OCX SDK specifically* (inside for deserialization shapes, outside for command/path shapes) by reasoning about where the bytes originate versus who invokes the process, but a different SDK whose subprocess is a fully sandboxed, offline, no-network binary with a fixed, versioned output schema would reasonably draw the boundary differently. The rule is written for a CLI that is itself a thin client to a live service; re-derive it, don't copy it, for any consumer whose subprocess has no live upstream.
