## Summary

- **Recommendation: ship the 28th depth file.** `kotlin-quality/errors-and-resources.md`, family `KT-ERR`, with five rows (`KT-ERR-01`…`KT-ERR-05`) — enough to route to, not the "two or three rows" threshold the brief says stays folded into existing files.
- `runCatching`'s single overload catches `Throwable`, not `Exception` — it swallows `OutOfMemoryError`, `StackOverflowError`, and `AssertionError` in *any* code, coroutine or not; this is JAVA-ERR-02's mistake wearing a stdlib function instead of a keyword ([kotlinlang runCatching](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/run-catching.html)).
- `runCatching` is `inline`, so its internal `try { } catch (e: Throwable) { }` never appears as a `KtCatchClause` at the call site — no detekt rule keyed on catch-clause AST (`SwallowedException`, `TooGenericExceptionCaught`, `EmptyCatchBlock`) can ever fire on it, coroutine-scoped or not ([detekt@45672efb8b:SwallowedException.kt](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-rules-exceptions/src/main/kotlin/dev/detekt/rules/exceptions/SwallowedException.kt)).
- detekt's `SuspendFunSwallowedCancellation` (the rule KT-CORO-01's sibling measurement rests on) only fires when `runCatching`/`try` wraps a **suspend call** — a non-suspend `runCatching { }` that still swallows an `Error` is outside its scope entirely, and outside `M-U-04`'s CancellationException framing too. That gap is `KT-ERR-01`.
- detekt's `SwallowedException` **whitelists `InterruptedException`** in its default `ignoredExceptionTypes` — promoting the rule (already active) does *not* catch a swallowed, non-reinterrupted `InterruptedException`; unlike Java there is no detekt equivalent to Error Prone's `InterruptedExceptionSwallowed` at all. That's `KT-ERR-02`, verified by reading heuristic only.
- `use {}` is the try-with-resources analogue for `AutoCloseable`/`Closeable`, closing on every path including cancellation of the surrounding coroutine ([kotlinlang exceptions](https://kotlinlang.org/docs/exceptions.html)) — but `kotlin.sequences.Sequence` and `kotlinx.coroutines.flow.Flow` do not implement `AutoCloseable`, so wrapping a `Stream`/`ResultSet`/file handle in either type silently decouples the handle from the wrapper's lifetime. That's `KT-ERR-03`.
- A suspending `close()` called from a `finally` block after cancellation throws immediately unless wrapped in `withContext(NonCancellable) { }` — the official kotlinx.coroutines doc's own worked example ([Kotlin/kotlinx.coroutines@f63a04bacb8b:docs/topics/coroutines-cancellation.md:437-490](https://github.com/Kotlin/kotlinx.coroutines/blob/f63a04bacb8beeafcc9d49199b1e4bb08931b7eb/docs/topics/coroutines-cancellation.md#L437-L490)); this is folded into `KT-ERR-03`, not split out.
- `throw MyException(e.message)` instead of `throw MyException(e)` — JAVA-ERR-05's mistake — is named verbatim, noncompliant/compliant pair included, in detekt's `SwallowedException` KDoc, and **that rule is active by default**, unlike Java's `UnusedException` (Error Prone `DISABLED_CHECKS`, must be promoted). Kotlin's default gate is *stronger* than Java's here. That's `KT-ERR-04`.
- `System.exit()`, `Runtime.exit()`, `Runtime.halt()` and Kotlin's `exitProcess()` outside `main` are all caught by one detekt rule, `ExitOutsideMain` — but it ships `active: false` in `default-detekt-config.yml`, the exact JAVA-ERR-08 shape (SpotBugs `DM_EXIT`, correct but off). Promote it. That's `KT-ERR-05`.
- `@Throws` placement is not a new family: it is `M-V-04` in the already-scoped `KT-INTEROP` table (`kotlin-quality/java-interop.md`) — a Kotlin function a Java caller must catch needs `@Throws` because Kotlin has no checked exceptions ([kotlinlang java-to-kotlin-interop](https://kotlinlang.org/docs/java-to-kotlin-interop.html)). Cite `M-V-04`, do not add a KT-ERR row for it.
- `kotlin.Result<T>` as a public return type is `M-V-07`/`KT-API` territory (binary-compatibility and API-surface framing), not error-handling framing — cite it. The restriction that once forbade `Result` as a return type outside the stdlib (`-Xallow-result-return-type`) was **lifted in Kotlin 1.5** (2021); the flag itself was later removed — this is historical-only guidance, not a live gate ([Kotlin/KEEP#244](https://github.com/Kotlin/KEEP/pull/244)).
- ktlint's entire rule surface (`ktlint-ruleset-standard`) is lexical/formatting — spacing, wrapping, naming, imports — with zero rule classes touching exceptions, resources, or process exit; confirmed by reading the rule-class listing in the pinned corpus clone, not by search-snippet ([pinterest/ktlint@4c933394a3](https://github.com/pinterest/ktlint/tree/4c933394a3cc7539004b7e9eeee504cba470ad57/ktlint-ruleset-standard/src/main/kotlin/io/github/ktlint/core/ruleset/standard/rules)).
- detekt's `TooGenericExceptionCaught` and `InstanceOfCheckForException` are **already active by default** (unlike Java's Error-Prone/SonarJava equivalents, which need explicit promotion) — the normative candidates below are "keep active", not "promote", for these two.
- Every new row cites, rather than restates: `M-U-04`/`SuspendFunSwallowedCancellation` for the coroutine-scoped half of cancellation-swallowing, `M-V-04` for `@Throws`, `M-V-07` for `Result`-as-return-type, and JAVA-ERR-01/02/04/05/08 for the Java shape each KT-ERR row mirrors or diverges from.
- Exemplar corpus is build-file-and-tool-source only (per `jvm-frame.md`); source-level violation counts across the 32 repos are not independently re-measured here — the same limitation `errors-resources-and-lifecycle.md` states for JAVA-ERR.

## Findings

### 1. The routing decision: five rows, not two or three

The brief's own test: "a family earns a file when it has enough rows to route to; three rows do not." Working through the six candidates named in the brief:

| Candidate | Verdict | Row |
|---|---|---|
| (a) `runCatching` swallowing `CancellationException`/`Throwable` | Splits in two: the suspend-scoped half is already `M-U-04`/`SuspendFunSwallowedCancellation` (cite, don't restate); the non-suspend `catch(Throwable)` half is uncovered | New: `KT-ERR-01` |
| — (found during the dive, not in the brief's list) InterruptedException swallowed via `runCatching`/broad catch | Uncovered — detekt's own default config exempts it | New: `KT-ERR-02` |
| (b) `use {}` and what it doesn't cover | Uncovered for `Sequence`/`Flow`/suspending `close()` | New: `KT-ERR-03` |
| (d) exception chaining (`Throwable(message, cause)`) | Same Java mistake occurs; detekt already covers it (unlike Java) | New: `KT-ERR-04` |
| (e) `System.exit`/`exitProcess` from library code | Uncovered at MUST severity — a real detekt rule exists but ships off | New: `KT-ERR-05` |
| (c) `@Throws` placement | Already `M-V-04` (`KT-INTEROP`) | No new row — cite `M-V-04` |
| (f) `Result` as public return type | Already `M-V-07` (`KT-API`) | No new row — cite `M-V-07` |

Five new rows clears the bar the brief sets. They share nothing with `KT-CORO`'s scheduler/structured-concurrency concerns or `KT-INTEROP`'s boundary-annotation concerns — they are all about what happens to a `Throwable` once it exists, or what happens to a handle once it's acquired, which is exactly `JAVA-ERR`'s scope statement on the Kotlin side of the same glob family. **Verdict: `kotlin-quality/errors-and-resources.md`, family `KT-ERR`, rows `KT-ERR-01`…`KT-ERR-05`.**

### 2. runCatching catches Throwable, not Exception

`runCatching`'s two overloads are both `inline` and both documented identically: "catching any Throwable exception that was thrown from the block function execution" ([kotlinlang stdlib: runCatching](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/run-catching.html), since Kotlin 1.3). This is JAVA-ERR-02's forbidden pattern (`catch (Throwable)`/`catch (Error)`) built into a standard-library function every Kotlin codebase reaches for, not an anti-pattern someone has to type out.

Because `runCatching` is `inline`, its `try`/`catch` block is spliced into the caller's bytecode but **never appears as source-level `KtCatchClause` PSI at the call site** — the caller's Kotlin file has a call expression with a lambda argument, not a catch clause. Confirmed by reading `SwallowedException.kt`'s visitor, which is keyed on `KtCatchClause` ([detekt@45672efb8b:detekt-rules-exceptions/.../SwallowedException.kt](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-rules-exceptions/src/main/kotlin/dev/detekt/rules/exceptions/SwallowedException.kt)) — the same is true of `TooGenericExceptionCaught` and `EmptyCatchBlock`. **No catch-clause-based detekt rule, active or promoted, can ever see a `runCatching` call.**

The one detekt rule that *does* look inside `runCatching`'s lambda is `SuspendFunSwallowedCancellation`, and it is explicitly scoped to the case where a **suspend function is called inside the lambda**: "suspend functions should not be called inside runCatching's lambda block, because runCatching catches all the Exceptions[sic — Throwables]" ([detekt@45672efb8b:detekt-rules-coroutines/.../SuspendFunSwallowedCancellation.kt](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-rules-coroutines/src/main/kotlin/dev/detekt/rules/coroutines/SuspendFunSwallowedCancellation.kt)). It is `active: false` by default (line 156 of `default-detekt-config.yml`, the same measurement `KT-CORO-01`/the map's "Surprises" table rests on) and it resolves via the Analysis API to check for a *suspend call inside the block* — a `runCatching { computeSync() }` with no suspend call inside never trips it, coroutine context or not.

So a plain, non-coroutine `runCatching { }` wrapping code that can throw `OutOfMemoryError`, `StackOverflowError`, or (in test code) an `AssertionError` from a nested `assert`/`check` is swallowed with **zero detekt coverage under any configuration** — not `SuspendFunSwallowedCancellation` (suspend-scoped), not `SwallowedException`/`TooGenericExceptionCaught` (catch-clause-scoped). This is the JAVA-ERR-02 gap the brief asked about, and it needs its own row rather than folding into `KT-CORO`'s file, because it has nothing to do with coroutines.

### 3. InterruptedException: detekt's default-config blind spot

`SwallowedException`'s default `ignoredExceptionTypes` list is `InterruptedException`, `MalformedURLException`, `NumberFormatException`, `ParseException` ([default-detekt-config.yml:224-231](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-core/src/main/resources/default-detekt-config.yml#L224-L231)) — the rule's own KDoc explains the reasoning: these are "part of Java" and treated as non-exceptional outcomes Kotlin code has to catch anyway, so the rule doesn't flag catching them.

That reasoning is correct for `NumberFormatException`/`ParseException` (control-flow signals) but wrong for `InterruptedException` — JAVA-ERR-01 exists precisely because swallowing it breaks cooperative thread cancellation for every caller up the call stack, independent of whether it's "expected." Promoting `SwallowedException` from active-by-default to stricter, or writing a custom detekt config, does **not** close this gap — the exemption is baked into the rule's semantics, not its activation state. There is no detekt module or rule ID with an `InterruptedException`-specific check (searched the full `detekt-rules-*` tree; none exists at the pinned SHA). This is a reading-heuristic-only rule, same verification posture as JAVA-ERR-11 (CONSIDER, sneaky-throw) in the Java file.

### 4. use{} and what it does not cover: Sequence, Flow, suspending close()

`kotlin.use` (`kotlin-stdlib`) is the try-with-resources analogue: "This function automatically closes the resource when the block of code completes, regardless of whether an exception is thrown, thereby eliminating the need for a finally block" ([kotlinlang exceptions](https://kotlinlang.org/docs/exceptions.html)). It is defined as an extension on `AutoCloseable`, so it reaches anything that implements that interface, including a `java.util.stream.Stream` (which does).

It does **not** reach two shapes common in Kotlin code:

- **`kotlin.sequences.Sequence<T>`** does not implement `AutoCloseable`. `Files.lines(path).use { it.asSequence().forEach(...) }` is fine (you're calling `.use` on the `Stream`), but a helper that returns the `Sequence` directly (`fun readLines(path: Path): Sequence<String> = Files.lines(path).asSequence()`) has silently detached the sequence from the stream's lifecycle — closing is now the caller's problem and nothing in the `Sequence<String>` type signature says so, the exact JAVA-ERR-04 rationale ("Stream<T>'s type signature gives no hint it holds an open file descriptor") one level worse, because `Sequence` has no `use` extension to reach for even if the caller remembers.
- **`kotlinx.coroutines.flow.Flow<T>`** does not implement `AutoCloseable` either, and the coroutines docs' own exception-handling page covers the `catch` operator's transparency contract but has no `use`-equivalent for a `Flow` that holds a resource — cleanup lives in `onCompletion { }` or a `try`/`finally` inside the `flow { }` builder ([kotlinlang exception-handling](https://kotlinlang.org/docs/exception-handling.html)).
- If that cleanup calls a **suspending** `close()`, doing it from a plain `finally` after the coroutine has been cancelled throws `CancellationException` immediately instead of running — the coroutines team's own worked example wraps the suspending shutdown in `withContext(NonCancellable) { }` for exactly this reason ("Without withContext(NonCancellable), this function doesn't complete because the coroutine is canceled") ([Kotlin/kotlinx.coroutines@f63a04bacb8b:docs/topics/coroutines-cancellation.md:437-490](https://github.com/Kotlin/kotlinx.coroutines/blob/f63a04bacb8beeafcc9d49199b1e4bb08931b7eb/docs/topics/coroutines-cancellation.md#L437-L490)). A *synchronous* `close()` in a `finally`/`use {}` needs no such wrapping — `finally` blocks run on cancellation regardless; only a suspending cleanup call is at risk.

This is JAVA-ERR-04's family with a materially different shape on the Kotlin side (the type-level gap is worse for `Sequence`, and `Flow` adds a cancellation-timing hazard Java's try-with-resources never has), so it earns its own `KT-ERR` row rather than a line inside `KT-CORO`'s file — the failure is a resource-management failure that happens to interact with cancellation, not a coroutine-correctness failure per se.

### 5. Exception chaining: already active by default, unlike Java

JAVA-ERR-05 forbids `new SomeException(e.getMessage())` — wrapping a caught exception by re-typing its message instead of passing it as `cause`, which severs the stack trace at the catch site. Kotlin's `Throwable` constructor shape (`Throwable(message: String?, cause: Throwable?)`, and every standard exception subclass forwarding to it) does not make this mistake impossible: you can still write `throw MyException(e.message)`, and detekt's `SwallowedException` names this exact shape in its own KDoc as the first noncompliant example, with `throw MyException(e)` as the fix ([detekt@45672efb8b:SwallowedException.kt](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-rules-exceptions/src/main/kotlin/dev/detekt/rules/exceptions/SwallowedException.kt)).

The asymmetry with Java is the finding worth recording: `SwallowedException` is `active: true` in `default-detekt-config.yml` ([line 224](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-core/src/main/resources/default-detekt-config.yml#L224)) — no promotion needed — whereas Java's equivalent gate, Error Prone's `UnusedException`, is in `DISABLED_CHECKS` and JAVA-ERR-03 has to spend a MUST telling agents to promote it. A Kotlin codebase running `detekt` with `buildUponDefaultConfig: true` (the config every `KT-LINT` MUST already requires) gets this check for free; a Java codebase running default Error Prone does not. `ThrowingNewInstanceOfSameException` (also active by default) covers the narrower sibling mistake of re-wrapping in the *same* exception type and rethrowing.

### 6. System.exit/exitProcess: off by default in detekt

detekt's `ExitOutsideMain` rule reports `System.exit()`, `Runtime.exit()`, `Runtime.halt()`, and Kotlin's `exitProcess()` when called outside `main`, with the KDoc rationale "makes code more difficult to test, causes unexpected behaviour on Android, and is a poor way to signal a failure in the program" ([detekt@45672efb8b:detekt-rules-potential-bugs/.../ExitOutsideMain.kt](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-rules-potential-bugs/src/main/kotlin/dev/detekt/rules/potentialbugs/ExitOutsideMain.kt)) — functionally identical to JAVA-ERR-08's rationale for SpotBugs `DM_EXIT`. It ships `active: false` in the shipped default config ([default-detekt-config.yml:404-405](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-core/src/main/resources/default-detekt-config.yml#L404-L405)) — the exact same "correct rule, off by default" shape wave 3 already documented for `SpotBugs`/`Error Prone` checks throughout `JAVA-ERR`/`JAVA-LINT`.

One rule covers all four call shapes at once (unlike Java, which needed SpotBugs `DM_EXIT` for `System.exit` specifically and had no first-party check for `Runtime.halt()`), so this is a single, clean promote — `active: true` under `ExitOutsideMain` in the project's `detekt.yml`.

### 7. @Throws is KT-INTEROP's row, not a new family

`M-V-04` in the topic map already asks exactly this question — "Does a Java caller need `@Throws` to catch an exception a Kotlin function throws?" — with the correct rationale: "Kotlin has no checked exceptions, so without it the Java caller gets a compile error." Confirmed against the primary source: "Kotlin does not have checked exceptions. So, normally the Java signatures of Kotlin functions do not declare exceptions thrown," with the exact noncompliant/compliant Java-caller pair ([kotlinlang java-to-kotlin-interop](https://kotlinlang.org/docs/java-to-kotlin-interop.html)). This is entirely a Java-interop-boundary concern — the exception is unchanged, only its *visibility to a Java caller* is at stake — so it belongs in `kotlin-quality/java-interop.md` under `M-V-04`, not `KT-ERR`. No new row.

### 8. Result as public return type is KT-API's row

`M-V-07` already frames `kotlin.Result<T>` as a public-return-type / binary-compatibility question, which is `KT-API`'s scope, not error-handling. The historical restriction is worth dating precisely: `Result` was gated behind the `-Xallow-result-return-type` compiler flag for any declaration outside the stdlib itself, and that restriction was proposed for removal in Kotlin 1.5 ("Revise Result type for Kotlin 1.5, remove restrictions") ([Kotlin/KEEP#244](https://github.com/Kotlin/KEEP/pull/244)) — the flag was later deleted entirely. As of 2026, `Result` compiles as a public return type with no flag; the live question is purely the API-design one `KT-API`/`M-V-07` already owns (JetBrains discourages it publicly while using it internally). Cite `M-V-07`, do not restate the API argument here.

### 9. ktlint carries none of this

Reading the rule-class listing under `ktlint-ruleset-standard/src/main/kotlin/io/github/ktlint/core/ruleset/standard/rules/` at the pinned SHA (`4c933394a3cc7539004b7e9eeee504cba470ad57`) shows every rule is lexical: spacing, wrapping, blank lines, naming, KDoc formatting, import ordering. No rule class name references `Exception`, `Throwable`, `Closeable`, or `Exit` anywhere in the tree — confirmed by grepping the full path listing rather than trusting the rule-count claim in ktlint's own docs site (which 404'd at the URL tried). This matches the brief's expectation and needs no further dive: ktlint is a formatter, not a correctness linter, for this surface.

## Normative guidance candidates

1. **`KT-ERR-01` (MUST) — Do not wrap code that must be allowed to propagate a JVM `Error` (`OutOfMemoryError`, `StackOverflowError`) or a test assertion in `runCatching { }`; it catches `Throwable`, not `Exception`.** *Rationale*: `runCatching`'s two overloads both catch `Throwable` ([kotlinlang runCatching](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/run-catching.html)); because it is `inline`, no catch-clause-based lint (`SwallowedException`, `TooGenericExceptionCaught`) or the coroutine-scoped `SuspendFunSwallowedCancellation` can see inside a non-suspend call to it. *Verify*: reading heuristic — grep `runCatching\s*\{` in test-source directories and any code performing bulk/recursive work where a `StackOverflowError` or `OutOfMemoryError` is plausible; there is no automatable Kotlin-side gate for this shape at the pinned detekt SHA. Cite `M-U-04`/`SuspendFunSwallowedCancellation` for the suspend-scoped sibling of this mistake — do not restate it here.
2. **`KT-ERR-02` (MUST) — A caught `InterruptedException` (directly, via `Exception`, or via `runCatching`) is always re-interrupted (`Thread.currentThread().interrupt()`) or rethrown, even though detekt's `SwallowedException` does not flag it.** *Rationale*: detekt's default `ignoredExceptionTypes` whitelists `InterruptedException` as a "nonexceptional" Java signal ([default-detekt-config.yml:224-231](https://github.com/detekt/detekt/blob/45672efb8bb780bbfefdfa57e623003334f951ca/detekt-core/src/main/resources/default-detekt-config.yml#L224-L231)), so activating or hardening that rule gives false confidence on this exact case; the JAVA-ERR-01 hazard (broken cooperative cancellation) is unchanged on the JVM regardless of source language. *Verify*: grep `catch\s*\(.*:\s*(InterruptedException|Exception)\b` bodies (and `runCatching` blocks calling anything that can throw it) for the absence of `Thread.currentThread().interrupt()` or a rethrow — no detekt rule ID exists to cite; state that absence explicitly in the shipped rule text.
3. **`KT-ERR-03` (MUST) — Use `.use { }` on any `AutoCloseable`/`Closeable`; for a `Sequence` or `Flow` built over one, keep and close the underlying handle explicitly, and wrap a suspending `close()` called during cleanup in `withContext(NonCancellable) { }`.** *Rationale*: `Sequence` and `Flow` do not implement `AutoCloseable`, so `.use` never reaches them, and a `finally`/`onCompletion` block that calls a **suspending** close after the coroutine is cancelled throws immediately unless the close runs inside a non-cancellable context — the coroutines team's own docs demonstrate the failure and fix ([Kotlin/kotlinx.coroutines@f63a04bacb8b:docs/topics/coroutines-cancellation.md:437-490](https://github.com/Kotlin/kotlinx.coroutines/blob/f63a04bacb8beeafcc9d49199b1e4bb08931b7eb/docs/topics/coroutines-cancellation.md#L437-L490)). *Verify*: reading heuristic — grep a function returning `Sequence<T>`/`Flow<T>` for a `Stream`/`ResultSet`/file-handle source with no visible close path; grep `withContext(NonCancellable)` presence around any `suspend fun close(...)`/`suspend fun shutdown(...)` call inside a `finally` or `onCompletion { }`. No detekt rule ID exists for either shape at the pinned SHA.
4. **`KT-ERR-04` (MUST) — Keep detekt's `SwallowedException` and `ThrowingNewInstanceOfSameException` active (`buildUponDefaultConfig: true`, no override to `active: false`); never wrap a caught exception as `SomeException(e.message)` instead of `SomeException(e)`.** *Rationale*: this is JAVA-ERR-05's exact mistake, but unlike Java's `UnusedException` (off by default, must be promoted per JAVA-ERR-03), detekt's `SwallowedException` already covers it at `active: true` in the shipped config — this row is "don't turn it off," not "turn it on." *Verify*: confirm the project's `detekt.yml` does not set `exceptions > SwallowedException > active: false` or `ThrowingNewInstanceOfSameException > active: false`; grep `\w+Exception\(\s*\w+\.message\s*\)` for the raw pattern as a backstop where detekt isn't wired into CI failure.

**Not a new row — cite instead:**
6. `@Throws` placement on a published API → cite `M-V-04` (`kotlin-quality/java-interop.md`, family `KT-INTEROP`); do not add a `KT-ERR` row.

## AI-agent angle

- **Reaching for `runCatching { }` as "the Kotlin try/catch"** for anything that might throw, including inside test code and around allocation-heavy work — a model trained on tutorials that only ever show `runCatching` swallowing a `NumberFormatException` or network exception has no signal that it also eats `AssertionError`/`OutOfMemoryError`. Smallest check: grep `runCatching` usage inside `src/test/**` or `src/androidTest/**` — any hit is worth a second look, since a swallowed test assertion is a false-green test.
- **Assuming `use {}` "just works" for anything Kotlin returns from a resource-opening call**, including `.asSequence()`/`Flow`-returning helpers — a model that knows `use {}` closes Java `Stream`s correctly will confidently write `fun lines(p: Path) = Files.lines(p).asSequence()` without realizing the `Sequence` it returns carries no closing contract at all. Smallest check: grep function signatures returning `Sequence<` or `Flow<` whose body opens a `Stream`, `ResultSet`, `Channel`, or file handle with no `.use`/explicit-close path visible in the same function.
- **Copying `finally { resource.close() }` from Java muscle memory into a `suspend fun`** when `close()` is itself suspending (a hand-rolled async resource wrapper) — the model has seen the pattern work a thousand times in Java and doesn't know that under coroutine cancellation the same code silently never runs. Smallest check: grep `suspend fun close(` declarations, then check every call site inside a `finally`/`onCompletion { }` for a `withContext(NonCancellable)` wrapper.
- **Treating `@Throws` as needed on every Kotlin function**, a hangover from Java's checked-exception discipline the model was trained on — it is only needed when a Java *caller* must catch the exception; over-applying it is harmless but noisy and a sign the model doesn't understand *why* the annotation exists (see `M-V-04` for the correct scoping). Smallest check: `@Throws` present on a function with no Java consumer in the module's public surface is a signal, not a failure.
- **Assuming detekt's defaults mirror Error Prone's** (mostly off, promote explicitly) — the opposite is true for this exact family: `SwallowedException`, `TooGenericExceptionCaught`, and `InstanceOfCheckForException` are active out of the box, while `SuspendFunSwallowedCancellation` and `ExitOutsideMain` are not. A model asked to "harden the detekt config" that promotes only the coroutine rules and skips `ExitOutsideMain` has the two backwards from what the corpus measurement shows. Smallest check: diff the project's `detekt.yml` against the four names above and their `active:` line numbers cited in this file.
- **Writing `new SomeException(e.message)` from Java habit** even in Kotlin, where the same string-only constructor call compiles cleanly — a model porting Java exception-wrapping code line-for-line reproduces JAVA-ERR-05 verbatim in Kotlin syntax. Smallest check: grep `\w+Exception\(\s*\w+\.message\s*\)` — same regex as JAVA-ERR-05, ported.

## Contested / evolving

- **Whether `runCatching` should exist as a "Kotlin idiom" at all for anything beyond leaf-level, single-call, non-suspending code** is genuinely split in community practice: some style guides (e.g., internal JetBrains guidance referenced in `SuspendFunSwallowedCancellation`'s own KDoc) recommend a project-local `coRunCatching` wrapper that rethrows `CancellationException` immediately; others avoid `Result`-returning helpers entirely and stick to `try`/`catch`. As of 2026-09-12 there is no first-party stdlib `coRunCatching` — projects that want the ergonomics write their own, and `KT-ERR-01`/coroutine's `M-U-04` both assume that absence.
- **`ExitOutsideMain`'s exact release history** (which detekt version introduced it, and whether `dev.detekt.*` package naming — visible throughout this SHA — is the post-1.x rename settling into a stable release) is a dated re-check the jvm-topic-map's "residue" section already lists generally for detekt's activation table; this file adds no new dated claim beyond the pinned-SHA measurement above.
- **`Sequence.use`-style extension proposals** have circulated on the Kotlin issue tracker/forums for years (giving `Sequence` an opt-in closeable variant) but nothing has shipped as of this date — the gap `KT-ERR-03` documents is the current, not historical, state.
