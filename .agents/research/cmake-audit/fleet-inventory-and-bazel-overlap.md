`find_ocx/ocx.toml` also pins `ninja = "ocx.sh/ninja-build/ninja:latest"` alongside `cmake:3.31` — the module's own toolchain is CMake + Ninja through OCX, nothing else.

`mirror-ccache/ccache/mirror.yml:30-45` documents *why* only the musl-static pair ships, a pattern worth noting alongside CMake's own glibc-only story: upstream `ccache` publishes both a `-glibc` dynamic build and a `-musl-static` fully-static one per arch (measured via `readelf -l`/`-d`: the musl-static binaries carry no `INTERP`, no `NEEDED` at all). The mirror carries only the static pair, so its platform keys are **bare** (`linux/amd64`, no `+libc.*` suffix) — "one artifact serves glibc and musl hosts alike" — the opposite tradeoff from CMake's `+libc.glibc`-tagged, dynamically-linked, no-musl-build story (§3 above). Two OCX mirrors in the same repo family made two different, each individually correct, libc decisions depending on what upstream actually ships — a CMake rule about toolchain provisioning should not assume one glibc/musl posture applies fleet-wide.

## Smells (ranked)

1. **Cross-provisioner version drift, live and unaddressed.** `find_ocx` pins ocx CLI `0.3.11` (`ocx.cmake:187`) while its stated design twin `rules_ocx` requires `≥0.6.0` (`ocx/private/versions.bzl:18`) — three minors apart, and `find_ocx/OCX-0.5-HANDOVER.md` documents a 0.5.2 adoption still in flight (working tree dirty, 10 files, `+145/-175`, confirmed by `git diff --stat`).
2. **Un-gitignored multi-gigabyte scratch trees sit directly under `/home/mherwig/dev`.** `.tmp-cmake/` (2.6G, 7,102 CMake-family files at depth 8) and `.probe-published/` (6.1G) are not inside any git repo (`/home/mherwig/dev` itself has no `.git`) yet fall inside any naive `**/CMakeLists.txt`-style glob sweep of the directory tree — 16 of this audit's 37 top-level CMake-family hits come from `.tmp-cmake` alone.
3. **Duplicate-clone sprawl inflates keyword sweeps ~3.5×, measured.** `ocx`, `ocx-evelynn`, `ocx-sion`, `ocx-soraka` are four independent checkouts of `git@github.com:ocx-sh/ocx.git` at different commits, each carrying a near-complete `.claude/artifacts/` ADR corpus. `find <each>/.claude/artifacts -name '*.md' | xargs md5sum | awk '{print $1}' | sort -u | wc -l` across all four → **418 unique file contents** out of **1,459 total files** (`find <each>/.claude/artifacts -name '*.md' | wc -l` summed) — a measured 3.49× duplication factor, not a guess — any fleet-wide audit must dedupe by git remote before reporting hit counts, or it overstates the domain's real config footprint by roughly 4×. This exact failure mode is already documented elsewhere in the lore catalog: `rules/docs-quality/checks.md:77-79` — *"VitePress config paths are named rather than globbed, because a recursive glob picked up vendored copies and inflated one repository from 6 rows to 44."* A CMake/C++ rule's own verification greps should name paths or exclude vendor/duplicate trees for the same reason, not rely on an unqualified recursive glob.
4. **`ocx-contrib/` has no `.git` of its own** even though it hosts `.claude/`/`.agents/` config directly at its root (e.g. `create-mirror`) — nothing under that path can carry a commit SHA; each `mirror-*` subdirectory is independently versioned instead (`mirror-ccache` at `6826aa7`, `mirror-ninja-build` at `0667ee3`).

## Patterns worth encoding

- **Evidence-before-policy for platform/version claims.** `mirror-kitware/cmake/mirror.yml` measures the glibc floor *per architecture* rather than assuming symmetry (`GLIBC_2.17` x86_64 vs `GLIBC_2.28` aarch64, `cmake/mirror.yml:59-63`) and states the asset-scope regex was checked to match exactly one asset at four version points, not just the newest. A CMake rule's version-specific guidance should carry the same "measured at N points across the claimed range" discipline, not a single-version spot check.
- **Declared-and-verified interface surfaces (`bin_scan: verify`).** OCX's mirror spec fails the run if a declared binary is missing *or* an undeclared one is present (`cmake/mirror.yml:141-160`) — directly analogous to CMake's own `install(EXPORT)`/Config-package correctness problem (a target's public interface silently drifting from what's actually installed); worth encoding as a verification pattern for install/export rules.
- **Classified environment-variable precedence as one table, not scattered logic.** `rules_ocx`'s `OCX_ENV_CLASSES` (site/translucent/explicit/pinned, `AGENTS.md:225-247`) is a reusable model for a CMake rule about cache-variable-vs-environment-vs-command-line precedence, a recurring CMake footgun (`CMAKE_TOOLCHAIN_FILE`, `<Pkg>_ROOT`, compiler launchers).
- **Every failure path names the fix, in a table.** `rules_ocx`'s sysexit-to-hint table (`AGENTS.md:159-176`) is the shape the artifact-set constraints already ask for ("every rule carries a verification... states which way empty output reads") — a `FATAL_ERROR` taxonomy for the shipped CMake rule (find_ocx's own `ocx.cmake` has 37 `FATAL_ERROR` sites) could use the identical table shape.
- **A frozen index as a lockfile substitute.** `find_ocx/CMakeLists.txt:15-18`: *"The committed `.ocx/` snapshot... freezes the `:3.31`/`:4` tags — CI tag resolution is hermetic. `FIND REQUIRED` locks the discovery into `OCX_INDEX`"* — a worked example of "pin a floating tag by committing its resolution," directly transferable to how a CMake+Conan/vcpkg rule should frame lockfiles/baselines.
