## Scoping mechanism

No compiler-imposed scoping exists in plain CSS. The platform's own opt-in mechanism is @scope: `@scope (.card) to (.card-body) { … }` — the ":scope root" and an optional "limit" (donut-scoping: styles apply between root and limit, not inside the limit). Ties are broken by "scoping proximity" — a new cascade step: at equal specificity, the rule whose scope root is DOM-closer to the matched element wins, independent of source order. Crucially, wrapping a selector in @scope does NOT itself add to that selector's specificity — proximity is a separate tie-break dimension, not a specificity multiplier.

## Emitted specificity

A plain `.version { … }` written inside `@scope (.card) { }` still computes to (0,1,0) — identical to the same selector outside any @scope block. @scope changes WHICH of two equal-specificity rules wins (via proximity), it does not change the specificity number itself. `:where(...)` is the platform tool for deliberately forcing a selector's specificity to (0,0,0) regardless of its contents — `:where(.foo)` is (0,0,0), not (0,1,0); use it to write "override-only" hooks that a single consumer `.class` selector can always beat.

## Cascade-layer support

Native, no compiler involved — this is the mechanism the whole doctrine is built on. Confirmed: (1) unlayered author styles ALWAYS beat any layered author style at any specificity, and this is positional — it holds even if the unlayered rule appears earlier in source than the layered one (MDN: "Styles that are not defined in a layer always override styles declared in named and anonymous layers"). (2) Layer precedence order = order of each layer's FIRST appearance, whether as a bare statement (`@layer a, b;`) or a block. (3) `!important` inverts this: important declarations in an earlier-declared layer beat important declarations in a later layer, and important-in-any-layer beats important-unlayered. CRITICAL MINIFIER FINDING: Vite's default production minifier (esbuild) has a confirmed bug (vitejs/vite#22705) where a standalone `@layer a, b, c;` ordering statement is DROPPED during minification when the corresponding blocks live in separately-imported/concatenated files, silently falling back to block-appearance (= import/concat) order — this can flip precedence with no error. Lightning CSS documents itself as never performing unsafe optimizations, but has its own separate confirmed bugs around @layer/@import interaction (parcel-bundler/lightningcss#803, and a reported `@import layer()` metadata loss in bundler/analyzeDependencies mode). No confirmed bug found for cssnano's default/advanced presets, but no authoritative confirmation of correctness either (low confidence either way). Conclusion for the rule: NEVER trust the statement form alone across a build pipeline — either make block order match declared order too (belt-and-suspenders) or grep the actual COMPILED/served CSS for a rules-outside-@layer test, per doctrine point 5.

## Consumer override entry point

There is no framework-imposed "component build" step for plain CSS — the entrypoint is whatever file a downstream consumer's own build loads last (or, once everything is layered correctly, loads at ANY point, since unlayered beats layered unconditionally regardless of source order — see layer_support). So source order at the consumer's entrypoint does NOT need to suffice, and per spec it structurally cannot be relied on for the layered/unlayered relationship — only for breaking ties among rules within the same layer bucket at equal specificity.

## Token exposure

Idiomatic form: `:root { --token-name: value; }` for untyped custom properties, or `@property --token-name { syntax: "<color>"; inherits: true; initial-value: …; }` when the token needs type-checking, a guaranteed initial value, controlled inheritance, or animatability. Consumption: `var(--token-name, fallback)`. Plain CSS has no framework-native token system or contract-file convention — "one file is the contract" is a project convention (as both grimoire-indexer's tokens.css and ocx-catalog's design-tokens rule independently chose), not something the platform enforces.

## Theme switching

Two composable primitives, easy to conflate: `prefers-color-scheme` media query reads OS/browser preference; `color-scheme` CSS property (declarative, e.g. `:root { color-scheme: light dark; }` or forced via `[data-theme="dark"] { color-scheme: dark; }`) tells the UA which schemes the page supports and drives native form-control/scrollbar rendering. `light-dark(colorA, colorB)` picks between its two arguments based on the element's COMPUTED `color-scheme` value — NOT directly on the media query. A manual toggle (JS setting `data-theme="dark"`) has zero effect on `light-dark()` unless that same attribute rule also sets `color-scheme: dark`.

## Testability

Grep the actual served/built CSS text (never re-derive from source) for two things: (1) every authored declaration block sits inside the intended `@layer name { }` wrapper — a regex/parse check that no "internal" selector appears at the top level unwrapped; (2) the layer ORDER in the compiled output (block appearance order, since the statement can be dropped — see layer_support) still matches intended precedence. This is exactly the check both grimoire-indexer and ocx-catalog already pin per doctrine point 5, and it is the only way to catch the esbuild statement-dropping bug, since source-level review looks correct even when the compiled artifact is wrong.

## Where this contradicts the core doctrine

None found — plain CSS doesn't contradict any of the five doctrine points; it's their implementation substrate. The one place it differs from the OTHER frameworks under research (not from core) is structural rather than contradictory: there is no compiler-imposed scoping mechanism inflating a selector's specificity (the concrete mechanism named in point 2), because there is no compiler. That's the null case of point 2, not a violation of it — the platform's own @scope, when used, deliberately does NOT add to specificity (only to proximity), which is consistent with, not opposed to, "only custom properties are reliably overridable."

## Traps

- Writing a literal value (hex, px, hsl()) instead of var(--token) — a value that is not a custom property is a value a consumer's override file can never reach, full stop.
- Assuming var(--x, fallback) catches a BAD value the same way it catches a MISSING one — it doesn't: a present-but-invalid value makes the declaration invalid at computed-value time (IACVT) and resets to the property's inherited/initial value, silently ignoring your fallback entirely.
- Trusting a bare `@layer a, b, c;` ordering statement to survive a production build — Vite's default esbuild minifier drops it when blocks come from separately concatenated files, silently reverting to import order (vitejs/vite#22705); verify against compiled output, not source.
- Forgetting @scope's donut hole: an element matching the scope LIMIT is excluded from the scoped styles, so a hook expected to reach a nested sub-component silently stops at that boundary.
- Trying to `transition`/`animate` a custom-property-driven value without registering it via @property — an unregistered custom property is not interpolatable, so the animation jumps instead of tweening.
- Toggling a manual `data-theme` attribute and expecting light-dark() to respond — it reads the computed `color-scheme` property, not `prefers-color-scheme` or the attribute itself; the attribute's rule must also set `color-scheme` explicitly.
- Writing a plain compound selector for an 'override-only' component hook instead of wrapping it in :where(...) — without :where(), the hook carries real specificity and can out-rank a consumer's single-class override even inside a correctly unlayered file.

### Confirmed

- Unlayered author-origin styles always beat any layered author style at any specificity, independent of source order. MDN @layer: 'Styles that are not defined in a layer always override styles declared in named and anonymous layers' and 'Even though we declare the non-layered style first, it's still applied after the layer styles.' - Layer precedence = order of each layer's first appearance (statement or block); first-declared lowest, last-declared highest. MDN @layer. Also confirmed: anonymous layers order by declaration position and rank below unlayered.
- !important inverts layer order, and an important declaration inside ANY layer beats an important declaration outside all layers. MDN @layer: 'all important declarations within CSS layers take precedence over any important declarations declared outside of a layer.' Empirically reproduced in Chrome 148 (§E1: 'Layered !important vs unlayered !important → layered wins'). Consequence worth stating in the rule: an !important inside the framework's layer locks the consumer out permanently, with no escape hatch.
- :where() always contributes (0,0,0) regardless of its arguments, unlike :is(). MDN.
- A bare selector inside `@scope (.card) { .version { … } }` computes to (0,1,0) — unchanged from the same selector outside any @scope. The researcher's answer is right; the MECHANISM they omitted is worth publishing because it is the checkable part: MDN @scope — 'both bare selectors and the & nesting selector behave as if `:where(:scope)` were prepended to the selector. Because :where() has zero specificity, bare selectors and & add zero weight.' The corollary trap: writing `:scope` EXPLICITLY does add (0,1,0) ('`:scope img` has specificity 0-1-1, while bare `img` has 0-0-1').
- Scoping proximity is a distinct cascade step, not a specificity addition: at equal specificity the DOM-closer scope root wins. MDN @scope — 'Scoping proximity overrules source order but is itself overridden by other, higher-priority criteria such as importance, layers, and specificity.' The last clause matters and the researcher didn't state it: layers outrank proximity, so @scope can never rescue a rule that lost on layer.
- @scope's donut hole: the limit element is excluded. MDN @scope — 'The scope's upper bound is inclusive and its lower bound is exclusive.'
- var()'s fallback fires only for a MISSING custom property; a present-but-invalid value makes the declaration invalid at computed-value time and resets to the inherited (if inheritable) or initial value, ignoring the fallback. Confirmed by MDN's worked example (`--text-color: 16px` used as `color` → black, not the fallback) and by the css-properties-values-api-1 spec. NOTE: the researcher's cited MDN prose sentence actually says the opposite ('Fallbacks cover the case where … the desired variable isn't defined yet OR HAS AN INVALID VALUE') — the claim is correct but the citation is a page that contradicts itself. Cite the example or the spec, not that sentence.
- light-dark() resolves against the element's COMPUTED `color-scheme` property, not `prefers-color-scheme` and not a `data-theme` attribute. The paired trap (a JS theme toggle that sets `data-theme` without also setting `color-scheme` leaves light-dark() inert) is real and well stated.

- @property's stated purposes (type-checking, guaranteed initial value, controlled inheritance, animatability) and the corollary that an UNREGISTERED custom property is not interpolatable, so transitions on it jump rather than tween. Spec-backed.

The caveat, and it is the important half: "fold this into core" is only safe AFTER the corrections above. Four of the items the researcher wants folded in are wrong or overstated (the Vite "confirmed bug", the Lightning CSS risk, the incomplete @property descriptor list, the :where()-as-component-hook category error). Folding them verbatim ships those errors into the file with the LARGEST blast radius — the framework-independent core that every consumer loads unconditionally. An annex error reaches one framework's users; a core error reaches all of them. So the annex call is correct and the folding is correct, but the folding must be gated on the corrections, not treated as a free move.

One rationale nit: the researcher justifies folding on the grounds that "an agent hits these on every stylesheet, framework or not." That is true of the IACVT trap, light-dark(), and @property. It is NOT true of the minifier finding, which is build-pipeline-specific and belongs wherever the doctrine-5 test is described, not in the platform-primitives prose.

Verdict: needs-correction. The doctrine is sound and most of the platform mechanics check out — but the two findings the researcher rated most confidently novel (the Vite "bug" and the Lightning CSS risk) are the two that are wrong, and the findings omit the single trap that both of our own repos independently found and pinned.

THE BIGGEST PROBLEM IS AN OMISSION, NOT AN ERROR. Layering does NOT fix the dark-mode token leak, and this is verified, not theoretical. From a real headless Chrome 148 run with a red control (/home/mherwig/dev/ocx-catalog/.claude/artifacts/research_css_customization_api_2026-08-24.md §E1): "Consumer unlayered `:root` vs layered `.dark`, under `html.dark` → consumer value — layering does NOT fix the dark leak." The mechanism is a direct and unpleasant consequence of doctrine point 3: because unlayered beats layered unconditionally, a consumer's one-line `:root { --accent: … }` beats BOTH the framework's layered light block AND its layered dark block, so a single accent override silently takes dark mode with it. Point 3 makes this WORSE than the unlayered baseline, and a rule that sells @layer without naming this cost is selling a broken dark mode. Both local rules document it — /home/mherwig/dev/grimoire-indexer/.claude/rules/quality-design-tokens.md: "their customCss loads last, so a `:root`-only override beats the theme's dark block and takes dark mode with it"; /home/mherwig/dev/grimoire-indexer/.claude/rules/quality-css-overrides.md: "A consumer's `:root { --grim-color-accent: … }` still leaks into dark mode. `:root` is scheme-agnostic; no cascade mechanism changes that. It stays a documentation obligation." This must be in core.

SECOND OMISSION, AND IT INVALIDATES TESTS. The researcher's `testability` section is right that you must grep compiled output, but misses the trap that makes the test itself lie: sandboxed DOM engines do not implement layers. happy-dom v20 DROPS `@layer` blocks at parse time (rule count 0); jsdom v29 parses @layer into correct CSSOM but NEVER applies layered declarations in getComputedStyle. Both produce a FALSE "unlayered wins" — the layered rule was simply inert, so the assertion passes for the wrong reason (§E1). Any doctrine-5 test written against jsdom or happy-dom is an unchecked green. The check must either grep compiled CSS text (no DOM engine involved) or run in real Chrome. This belongs in the rule verbatim; it is the highest-value single sentence in the local ground truth.

THIRD OMISSION: inline `style=""` attributes beat every author stylesheet rule, layered or not. Only `!important` reaches them — and a layered `!important` then locks the consumer out permanently. grimoire-indexer hit exactly this (Shiki writes syntax colours as inline styles) and documents it as its one allowlisted exception with a per-declaration justification comment. For a traps file this is a real, common failure: an agent tokenizes a component that emits inline styles and produces values no consumer can ever reach.

FOURTH OMISSION: `@property` with `initial-value` is the FIX for the IACVT trap the researcher raises. MDN states it plainly — with `@property --text-color { syntax: "<color>"; inherits: false; initial-value: teal }`, a bad `--text-color: 16px` resolves to teal rather than blowing up the consuming declaration. The findings name the trap in `pitfalls` and name @property in `token_exposure` and never connect them. Put the fix next to the trap.

MINOR: `revert-layer` is never mentioned; it is the primitive a consumer reaches for when they want to drop back to a lower layer rather than override a value, and it costs one line to name.

WHAT SURVIVED CLEANLY: the layer precedence model, the !important inversion, the :where() zero-specificity rule, the @scope specificity and proximity analysis (right answer, and the `:where(:scope)` mechanism I found makes it checkable), the donut-hole trap, the IACVT-vs-fallback distinction, and the light-dark()/color-scheme conflation trap. That last one is genuinely good and non-obvious — keep it.
