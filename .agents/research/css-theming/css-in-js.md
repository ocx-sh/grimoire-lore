## Scoping mechanism

Runtime libs (styled-components, Emotion) hash the component's style block to a single generated class; no attribute-selector scope hook like Astro/Vue exists. styled-components attaches TWO classes to the element — a stable `sc-xxxx` identity class (targeting/debugging only, carries no rules) plus a dynamic hashed class that DOES carry the rules (docs: "a stable CSS class for use in targeting" + "every unique interpolation result generates a new CSS class"; 200+ triggers a runtime warning). Emotion attaches one `css-xxxx` class per unique style object. Zero-runtime vanilla-extract also emits one hashed class per `style()` call, resolved at build time to a static `.css` file (prod mode: short hash only, no debug names). Panda CSS and StyleX are atomic: each individual CSS declaration (or declaration group) gets its OWN single-purpose class, so an element carries many classes, not one.

## Emitted specificity

All five emit PLAIN CLASS selectors — (0,1,0) per class, always. None use an attribute-selector scope hook, so ":where()-wrapping" doesn't apply the way it does to Astro/Vue SFC scoping; the specificity floor is already the minimum a class can have. styled-components' `&&`/`&&&` escape hatch repeats the generated class to deliberately manufacture (0,2,0)/(0,3,0) — this is the library AUTHOR's tool to beat an external stylesheet (e.g. Bootstrap), the mirror image of a consumer override. StyleX and Panda's atomic classes never combine two rules on one selector, so ties are resolved by StyleX's own deterministic last-write compile-time ordering (not CSS specificity or source order at all) — see stylexjs.com/docs/learn/thinking-in-stylex: "the order of classes in the HTML doesn't matter... the last style applied always wins," decided at compile time, not in the cascade.

## Cascade-layer support

Panda CSS: NATIVE, on by default — emits `@layer reset, base, tokens, recipes, utilities;` verbatim at the top of generated CSS (panda-css.com/docs/concepts/cascade-layers, verified 1.12.0-era docs). vanilla-extract: NATIVE via explicit `layer()`/`globalLayer()` API (`import { layer } from '@vanilla-extract/css'`; assign per-style via the `'@layer'` key) — opt-in, not automatic; a style with no `'@layer'` key ships unlayered. Emotion: MANUAL/partial — `createCache({ key, insertionPoint })` (11.11+) can point injection at a pre-declared `<style>` layer node, but nothing wraps output in `@layer` by default. styled-components: NO built-in support as of 6.5.3 — GitHub issue facebook… i.e. styled-components/styled-components#5615 ("How can I wrap all the styled-components styling with one @layer?") is open and unresolved; also tracking issue #3950. StyleX: not verified from docs fetched — do not claim either way (mark low confidence, unverified).

## Consumer override entry point

Sharply different per library — this is the core divergence for the annex. styled-components: NO single deliberate entrypoint; the docs state plainly that styled-components "injects its styles during runtime at the end of the `<head>` by default. Thus its styles win over other single classname selectors" (styled-components.com/docs/advanced) — so by default the FRAMEWORK, not the consumer, occupies the "last therefore wins" tie-break position at equal (0,1,0) specificity; a consumer only wins by loading even later (a `<link>`/`<style>` appended after mount) or via `StyleSheetManager`'s `target`/`disableCSSOMInjection` to control insertion point — and this ordering is NOT guaranteed stable under SSR streaming (chunks/styles arrive as Suspense boundaries resolve) or client rehydration. Emotion: same shape, same nondeterminism risk under streaming SSR (per emotion-js/emotion#2764, injected order differs local vs. production). vanilla-extract: the entrypoint is literally a static `.css` file the bundler emits — ordinary build/import order applies, and the `layer()` API makes order-independence achievable deliberately. Panda: already-layered output means ANY unlayered consumer CSS wins automatically, full stop — doctrine point 3 satisfied out of the box. StyleX: there is no CSS-file entrypoint for a downstream consumer at all by design — the sanctioned override path is a typed `props()`/`createTheme()` composition passed down through the React tree, not a stylesheet (stylexjs.com/docs: "All styles on an element should be caused by class names on that element itself"; overriding via external cascade is treated as the "styles at a distance" anti-pattern StyleX exists to prevent).

## Token exposure

This is the single biggest trap in the family. styled-components/Emotion's IDIOMATIC pattern — `ThemeProvider` + `props.theme.colors.primary` interpolated into a template literal or style object — bakes the resolved value into the generated declaration as a LITERAL (e.g. `color: #ff0000;`), not a `var()`. Nothing exposes it as a CSS custom property unless the author manually writes `color: var(--color-primary, ${props.theme.colors.primary})`; the community "happy path" (e.g. Josh Comeau's styled-components guide, widely cited) does not do this. So the JS theme object, not any stylesheet, is the real public surface — a downstream consumer editing only CSS has zero reach, even before any specificity question. vanilla-extract is the opposite: `createThemeContract`/`createGlobalThemeContract` declare a typed set of VARIABLE NAMES only (no values — the semantic tier), and `createTheme`/`createGlobalTheme` assign concrete values that compile to real `--hashed-name: value` custom properties scoped under a class or `:root`/selector (vanilla-extract.style/documentation/theming) — genuinely var()-based, matching doctrine's tiering natively. Panda compiles design tokens to CSS custom properties inside its `tokens` layer (`--colors-*`, `--spacing-*`) consumed via `var()` in utility/recipe output — also native. StyleX's `defineVars()` "Creates global CSS Custom Properties" but by DEFAULT generates HASHED, build-unstable variable names; only a key explicitly prefixed with `--` (e.g. `'--brand-color': ...`) produces a stable, externally-targetable custom-property name (stylexjs.com/docs/api/javascript/defineVars) — skip the prefix and the "public API" changes name on every rebuild.

## Theme switching

styled-components/Emotion: re-rendering `<ThemeProvider value={...}>` swaps the JS object driving every interpolation and forces regeneration of affected style rules — no cascade-native primitive; dark mode is typically hand-rolled with a `prefers-color-scheme` media query inside `createGlobalStyle`/`injectGlobal`, or a `data-theme` attribute the app toggles alongside the provider value. vanilla-extract: `createTheme()` returns a CLASS NAME; toggling dark mode = swapping that class on `<html>`/`<body>` (commonly via `next-themes`), which re-scopes the same custom-property names to new values — SSR-safe because it's static. Panda: config-level `conditions` (e.g. `_dark`) compile to `[data-theme="dark"]` selectors or `@media (prefers-color-scheme: dark)` blocks inside the `tokens` layer holding both value sets. StyleX: `defineVars()` values can themselves be conditional objects (media-query keyed), and/or `createTheme()` is applied via `props()` at a subtree root to swap the whole variable set for that tree — theme selection is a JS/render-tree decision, not a stylesheet swap.

## Testability

styled-components/Emotion: render the app, inject a plain external `.your-class{color:red}` `<style>` AFTER the app's `<head>` styles (simulating a consumer file) and assert the computed style via a headless browser (Playwright/`getComputedStyle`) — a text-only Jest check on class NAMES is not sufficient here because the contract that matters is injection-order-dependent, not markup-dependent; run it once with a hard mount and once after a re-render/HMR cycle to catch order flips. Also grep the rendered `<style data-styled>`/`<style data-emotion>` tag's textContent for absence of `@layer` (documents that today's output is unlayered — a known gap, not a false green). vanilla-extract: `grep -c '@layer' dist/**/*.css` to confirm the build actually wrapped the intended styles (a style with no `'@layer'` key silently ships unlayered), plus a snapshot test pinning the CONTRACT's variable names (from `createThemeContract`) since implementation hashes are gitignorable but the contract's shape is the public API. Panda: read the generated `styles.css` (or run `panda cssgen`) and assert the literal line `@layer reset, base, tokens, recipes, utilities;` is present, then grep the `tokens` layer for the expected `--colors-*`/`--spacing-*` names. StyleX: babel-compile a fixture file and assert every `defineVars()` key meant to be public uses the `--`-prefixed stable-name form — a hashed name where a stable one was intended is the regression to catch.

## Where this contradicts the core doctrine

(1) Point 2's mechanism — a scoped selector at HIGHER specificity that always loses regardless of order — does not hold for styled-components/Emotion: their single-class output ties consumer CSS at (0,1,0), and the framework's own docs state it wins that tie by DEFAULT because it injects last in <head>; the real failure mode is nondeterminism under SSR streaming/HMR, not a provable, order-independent loss. (2) Point 1's "untokenized value = defect, add a custom property" implicitly assumes CSS authorship; styled-components/Emotion's idiomatic ThemeProvider pattern bakes theme values into literals with no var() at all, so the actual public surface is a JS object, not a stylesheet — core's fix (declare a custom property) has to be paired with an explicit instruction to interpolate `var(--x, ${jsValue})`, which the ecosystem's own best-practice guides do not do. (3) Point 3 assumes the authoring framework CAN be wrapped in a layer; styled-components has no first-party mechanism to do so (open issue, unresolved) — for that library the achievable fix is lower-key (rely on default (0,1,0) + avoid `&&`) not "add @layer." (4) StyleX rejects the premise of points 1–3 outright: its documented philosophy is that external CSS cascade overrides are an anti-pattern to be designed AWAY from, with typed JS composition (`props()`/`createTheme()`) as the sanctioned override path — a rule instructing an agent to verify "the consumer's CSS can win" is simply the wrong test for StyleX code. (5) Panda CSS is the one library that already satisfies point 3 as a built-in default (ships `@layer reset, base, tokens, recipes, utilities;` automatically) — not a contradiction but worth flagging so the annex doesn't tell an agent to add a mechanism that's already there.

## Traps

- Writing `color: ${theme.color}` in a styled-components/Emotion template literal produces a LITERAL in the compiled CSS, not a custom property — the value is invisible to any downstream stylesheet even though it "looks tokenized" in the source; the fix is `color: var(--color-x, ${theme.color})`, which the idiomatic ThemeProvider pattern does not do by default.
- Assuming styled-components' single-class (0,1,0) selector loses to a consumer's (0,1,0) selector the way Astro's (0,2,0) scoped attribute always does — it doesn't: it's a tie, and styled-components' own docs say it wins that tie by default because it injects last in `<head>`; the failure mode is nondeterminism (SSR streaming, HMR, remount order) rather than a guaranteed, provable loss.
- Reaching for `&&`/`&&&` in styled-components to "fix" a losing override — that escape hatch raises the FRAMEWORK's specificity to beat outside CSS; used on a component meant to be consumer-overridable it does the opposite of the doctrine's intent and should be treated like an unexplained `!important`.
- Telling an agent to "wrap the styled-components/Emotion output in `@layer`" as if it were a supported, first-party operation — styled-components has no built-in mechanism (open issue #5615) and Emotion's is a manual `createCache({insertionPoint})` setup, not a wrapper.
- Assuming StyleX (or any atomic-CSS-in-JS lib) needs the same "make the consumer's plain CSS win" treatment — StyleX's documented design explicitly rejects external-stylesheet overrides as an anti-pattern ("styles at a distance"); the actual override surface is typed `props()`/`createTheme()` composition, and grading it against "is there an unlayered CSS entrypoint" is asking the wrong question entirely.
- Using `defineVars()` in StyleX without a `--`-prefixed key and assuming the resulting custom property is a stable public name — by default it's a build-hashed name that can change every compile.
- Assuming Panda CSS needs a manual layer fix at all — it already ships `@layer reset, base, tokens, recipes, utilities;` by default; the only real risk there is an author reaching for `!important` inside one of those layers, which (per the core doctrine's `!important`-reverses-layer-order mechanism) would lock consumers out permanently.

## Review verdict

**Refuted:** emitted_specificity: "All five emit PLAIN CLASS selectors — (0,1,0) per class, always... the specificity floor is already the minimum a class can have." and "StyleX and Panda's atomic classes never combine two rules on one selector, so ties are resolved by StyleX's own deterministic last-write compile-time ordering (not CSS specificity or source order at all)."

- Why wrong: This is the single most load-bearing error in the report and it inverts the override contract for StyleX. StyleX 0.19.0's DEFAULT configuration does not emit plain class selectors. When `useLayers` is false — which is the default in both the babel plugin and the mainstream postcss integration — StyleX pads every rule with a chain of `:not(#\#)` to manufacture specificity, one repetition per priority level. `#\#` is an escaped ID selector, and per Selectors Level 4 `:not()` takes the specificity of its most specific argument, so each `:not(#\#)` contributes (1,0,0). A colour declaration therefore ships at (2,1,0), padding at (1,1,0), and the known-in-the-wild chains run to 3 and 4 repetitions, i.e. (3,1,0)/(4,1,0). A consumer's `.thing{color:red}` at (0,1,0) can never beat that in any source order, unlayered or not — only `!important` wins. StyleX is not the library that opts out of the doctrine's concern; by default it is the WORST offender of the five, and it is the one case where doctrine point 2's "a scoped selector at higher specificity that always loses regardless of order" holds most literally. The report says the opposite, and an agent carrying that instruction would mis-diagnose every failed StyleX override.
- Correction: StyleX 0.19.0 default (`useLayers: false`): emitted selectors are `.<atomicClass>` plus N × `:not(#\#)`, specificity (N,1,0) with N = the rule's priority-group index (0 for the lowest group, commonly 1–2, up to 4 observed in the wild). Not overridable by any unlayered consumer class rule. With `useLayers: true` (babel-plugin option; `useCSSLayers: true` in @stylexjs/postcss-plugin) StyleX drops the `:not(#\#)` padding entirely and emits `@layer priority1, priority2, …;` with bare (0,1,0) classes — which satisfies doctrine point 3 natively via one config flag. That flag, not "StyleX rejects the premise", is the actionable instruction. Panda's atomic classes ARE plain (0,1,0) and are separately confirmed.

Reproduced (.../scratchpad/cssinjs/sc.cjs): `<div class="sc-bdvwhi swTDZ">` with `.swTDZ{color:red;padding:4px;}`. Confirmed verbatim from https://styled-components.com/docs/advanced: "styled-components injects its styles during runtime at the end of the `<head>` by default. The report's derived point — that the failure mode here is nondeterminism rather than a provable order-independent loss — is sound reasoning about a real (0,1,0)-vs-(0,1,0) tie.

Emotion (.../scratchpad/cssinjs/em.cjs): `.ocx-1wu0rtl{color:#ff0000;padding:4px;}`. A downstream consumer editing only CSS has zero reach to the first form. This alone earns the annex.

So any unlayered consumer rule wins against all of it, at any specificity. ### On the annex call

Agree with `annex_worth_it: true`, but reject the stated `annex_rationale` — two of its three pillars are factually wrong, and if the annex is written from that rationale it will publish incorrect instructions.

Of the three reasons given: (1) the ThemeProvider-bakes-a-literal trap is correct, reproduced, and on its own justifies the file — an agent applying only the core doctrine would look at `color: ${theme.colors.primary}` and see a tokenized value, when the compiled output is `color:#ff0000` with no `var()` anywhere and zero reach from a consumer stylesheet. (2) "it would tell an agent to wrap output in @layer for styled-components as if that were a supported first-party mechanism, when it is an open unresolved feature request" is backwards: wrapping IS achievable, per-block and globally via `StyleSheetManager stylisPlugins`, the tracking issue closed COMPLETED in 2023, and the "open" issue closed NOT_PLANNED in March 2026. Written as drafted, the annex would talk an agent OUT of the fix that works. (3) "it would apply the make-consumer-CSS-win framing to StyleX, whose documented design deliberately has no such entrypoint" inverts the most consequential fact in the family: StyleX's default output is specificity-padded with `:not(#\#)` chains at (1,1,0) and (2,1,0), so StyleX is where the core doctrine's point 2 bites hardest, and it has a one-flag fix (`useLayers`/`useCSSLayers`) the report leaves marked unverified.

The annex earns its place on a corrected set of reasons, none derivable from the core:
- Compiled output diverges from source in a way that hides the defect: the token is invisible in the CSS but looks present in the JS (styled-components, Emotion).
- Two libraries generate hashed names for things the doctrine requires to be public — StyleX `defineVars()` without a `--` prefix, and vanilla-extract `createThemeContract` (the report catches the first and misses the second).
- Per-library the layer fix is a different lever with different defaults: automatic (Panda), one config flag (StyleX, off by default), an opt-in API with a stable-vs-hashed name choice (vanilla-extract `globalLayer` vs `layer`), or a stylis middleware (styled-components, Emotion). "Ship every style block inside a single @layer" is one sentence in the core and five different operations here.
- The dark-mode selector is not guessable: Panda 1.12.0 defaults to `.dark`, not `[data-theme]`, and getting it wrong fails silently.
- The testability guidance genuinely differs: for the runtime libraries the contract is injection-order-dependent and needs a real browser, which a text grep cannot cover — that is a legitimate divergence from the core's "grep the compiled output" check and it is the one piece of the report's `divergence_from_core` that survives intact.

Scope note: five libraries in one annex is a lot for a traps file. If it must be trimmed, styled-components + Emotion (shared runtime failure mode) and StyleX (the specificity inversion) carry nearly all the non-derivable content; Panda's only real trap is the dark-mode selector plus "don't add a layer, it's already there", and vanilla-extract's is the two name-stability splits.
