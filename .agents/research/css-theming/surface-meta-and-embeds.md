## Mechanism

(1) Astro islands: Astro's `data-astro-cid-*` compile-time scoping ONLY touches elements literally written in the `.astro` template — it never reaches into a child framework component's own render output. Built fixture (React island using CSS Modules) proves the island's `<div>` carries `class="_box_13ow5_1"` (plain CSS-Modules hash) with NO `data-astro-cid-*` attribute at all, while the Astro page's own `.box` becomes `.box[data-astro-cid-lcdefpme]`. Both scoped stylesheets land in one inlined `<head><style>` block in source/import order. Custom-property inheritance (`--brand-surface` on `:root`) crosses the island boundary fine — islands render into light DOM, no Shadow DOM, so the cascade is unbroken; only the *selector* scoping mechanisms are disjoint. (2) RSC boundary: "use client" requiredness is PER-LIBRARY, not a blanket CSS-in-JS rule. styled-components 6.5.3 has no `react-server` export condition and internally detects the RSC environment (`React.createContext === undefined`) to fall back to a context-free path — a plain Server Component (no "use client" anywhere) imports `styled-components`, builds clean on Next 16.3.3/Turbopack, and SSRs a correct `<style data-styled="">.bjovqr{color:red}</style>` + `class="sc-bdvwhi bjovqr"`. Emotion (`@emotion/react` and `@emotion/styled` 11.14.x) has no such fallback: the identical scenario throws `TypeError: n.createContext is not a function` at module evaluation, and only resolves once "use client" is added — after which Emotion emits `.css-<hash>` + `<style data-emotion="css <hash>">`, matching its documented shape. (3) Nuxt/React-Router: both are Vite-based and both preserve deterministic declaration-order for global stylesheets bundled into one file — `nuxt.config.ts`'s `css: ['./a.css','./b.css']` and root.tsx's `import './order-a.css'; import './order-b.css'` both produced a single bundled CSS file with a-before-b source order, identical mechanism (import-graph-order bundling) to the react-css-modules annex's existing Next.js claim — this generalizes, it is not Next-specific. (4) Solid/Qwik scoping: solid-styled's real emitted shape is NOT `data-s-<hash>` as commonly assumed — it is a colon-namespaced BOOLEAN ATTRIBUTE `s:c-<hash>-<n>` (hash = xxhash32 of the source filename in hex, n = per-module sheet counter), consumed in CSS as an escaped attribute selector `.box[s\:c-a67badc0-0]`. This only fires under `src/**` by `unplugin-solid-styled`'s default filter (root-level files are silently skipped — no error, just unscoped). Qwik's `useStylesScoped$` scoping is a RUNTIME mechanism, not a compile-time one: the built JS bundle (`dist/build/q-*.js`) contains the RAW, unprocessed author CSS string (`.box { color: red; }`) — the scope-class rewrite only happens when Qwik's core actually renders/hydrates the component. Real SSR output: `<div class="⭐️xl09ia-0 box">` and `<style q:style="xl09ia-0" hidden>.box.⭐️xl09ia-0 { color: red; }</style>` — a literal star-emoji-prefixed class name, appended as a SECOND class (not an attribute), giving (0,2,0) specificity like Vue/Astro/Angular's attribute-scoping tier. (5) Email HTML: not build-reproduced — no email client is locally runnable. Cited from established, versioned CSS-support matrices (caniemail.com), not restated as if verified by execution here. (6) iframe embeds: not build-reproduced with a live browser (no browser engine available in this sandbox) — this is HTML Living Standard "browsing context" semantics: an `<iframe>`'s content is a fully separate `Document` in a nested browsing context, so custom properties, `@layer`, and inherited author styles never cross that boundary by any CSS mechanism; only `postMessage`/URL params can.

## Where it contradicts the core

None of the 6 items outright CONTRADICT a round-1 core non-negotiable in the sense of proving one false — but two items sharply narrow one: "Inline styles beat every author rule, layered or not" (core principle #6) is not violated by email HTML, it is INVERTED in applicability — in email, inline styles are not an override escape hatch from a token contract, they ARE the entire contract, because most clients strip `<style>`/custom properties outright, so every other core principle (layers, component hooks, `:where()`, custom-property fallback chains) is moot there. Also, core principle #14 ("the gate reads the built artifact, in a real engine") has a real exception surfaced by Qwik: reading Qwik's BUILT JS bundle for the scoped selector shows nothing scoped at all (raw author CSS only) — the gate must read live SSR/render output specifically for Qwik, not just "the build," because the scoping transform is a runtime step, not a build step. This is a case where the existing gate principle needs a one-line caveat, not a contradiction.

## Traps

- Astro: a consumer selector like `[data-astro-cid-xxx] .thing` will silently never match anything rendered by a React/Vue/Svelte/Solid island — Astro's scoping only annotates markup literally written in the .astro file.
- RSC: do not treat 'CSS-in-JS needs use client' as universal — it is false for styled-components 6.x (works server-side with no directive) and true for Emotion (hard runtime crash without it). Testing one CSS-in-JS library tells you nothing about another's RSC compatibility.
- Nuxt/React-Router global CSS order is deterministic by declaration/import order (not alphabetical, not random) — same guarantee as Next's cssChunking default, safe to rely on across these Vite-based meta-frameworks.
- solid-styled: default `unplugin-solid-styled` filter only transforms files under `src/**` — a component authored at the project root gets NO scoping and NO error, it just silently ships an untransformed `css` tagged-template call that throws at runtime ('Unexpected use of `css`') if the plugin setup is wrong, or is a no-op if merely out of the include glob.
- solid-styled emits `s:c-<hash>-<n>` (colon-namespaced attribute), NOT `data-s-<hash>` — grepping a build for `data-s-` to detect solid-styled scoping finds nothing.
- Qwik's useStylesScoped$ output is invisible in the static JS bundle — the scope class only exists in rendered/hydrated DOM output (`⭐️<hash>-<n>` appended as a second class, giving .box.⭐️hash specificity (0,2,0)). An agent 'reading the build' per core principle #14 must specifically mean reading rendered HTML for Qwik, not just the JS chunk.
- Email: carrying any of this rule's cascade-layer/custom-property doctrine into an email template actively misleads — most clients strip <style> and don't support custom properties at all; inline styles are the contract, not an escape from it.
- iframe/widget embeds: zero cascade relationship with host — no layer, no custom-property inheritance, no selector-based override channel of any kind; only postMessage or a URL param can retheme it. The strongest isolation case in the whole design, and worth naming explicitly so an agent doesn't waste time hunting for a CSS-only override path that cannot exist.

## Documentation-only

- Email client CSS stripping / custom-property non-support — no email client runnable locally; reported from caniemail.com-style documentation, not executed here.
- iframe cross-document cascade isolation — no browser engine available in this sandbox to load a host+embed pair and inspect computed styles; reported as HTML Living Standard nested-browsing-context semantics, a spec guarantee rather than a version-dependent implementation detail.
- solid-styled under SolidStart's actual SSR pipeline (only a plain Vite+CSR build was tested; SolidStart's own server-rendering wrapper around the same compiler was not scaffolded).
- Qwik's useStyles$ (unscoped/global variant) and Shadow-DOM-adjacent slot/component boundary behavior — only useStylesScoped$ was exercised.
- Astro `is:global`/`is:inline` directive interaction with an island's own styles, and a Vue/Svelte island (only React was built) — the React case is likely representative since Astro's scoping never inspects any child framework's render output regardless of which framework it is, but this was not independently confirmed for Vue/Svelte islands.
- Per-route code-split CSS-module ordering in Nuxt/React-Router (only a single root-level global bundle was tested, not chunked per-route ordering under lazy-loaded routes).
