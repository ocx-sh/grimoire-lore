## Scoping mechanism

Vue's SFC compiler (PostCSS-based) hashes each component to a `data-v-<hash>` token, appends that token as an HTML attribute to every element the component's template renders (root element gets attrs from BOTH itself and its parent — 'by design so the parent can style the child root element for layout purposes', per vuejs.org/api/sfc-css-features.html), and rewrites every selector in `<style scoped>` to append `[data-v-<hash>]` to it. `:deep(x)` compiles to `ancestor[data-v-hash] x` (drops the hash from `x` itself, not from the ancestor). `:slotted(x)` reaches slot content; default scoped rules do not. `:global(x)` emits `x` with no hash at all. `v-bind('expr')` in CSS compiles to a *hashed custom property name* (static at build time) whose *value* is set via an inline `style` attribute on the root element and updated reactively — this is a distinct, per-instance custom-property channel, not the theming token system.

## Emitted specificity

Confirmed against real compiled output at /home/mherwig/dev/ocx-catalog/.lhci-site/assets/style.DrvwuUWz.css: `.package-card[data-v-3abac49e]{...}` and `.tag-badge[data-v-3abac49e]{...}` — one class + one attribute selector = specificity (0,2,0), exactly the Astro-shape the core doctrine already names, NOT wrapped in `:where()` (Vue's compiler never does this; the specificity boost is intrinsic and unconditional). A `:deep()` rule stacks a third selector on top: `.a[data-v-hash] .b` = (0,3,0). 480 `data-v-` occurrences counted in that one build's CSS file, so this is the dominant selector shape, not an edge case.

## Cascade-layer support

Full, verified end-to-end in a real build, not just source. ocx-catalog wraps the ENTIRE body of every `<style scoped>` block (and every plain token `.css` file) in `@layer ocx { ... }`, written by hand inside the `<style>` tag — Vue's scoping transform still runs correctly on selectors nested inside the at-rule (compiled output shows `.tag-badge[data-v-3abac49e]` sitting *inside* `@layer ocx{...}`, confirmed at /home/mherwig/dev/ocx-catalog/.lhci-site/assets/style.DrvwuUWz.css). Vite/Rollup's production build (Vite's default CSS-code-splitting + minifier) preserves the `@layer` wrapper through bundling and minification — confirmed by /home/mherwig/dev/ocx-catalog/test/build/css_layer_real_build.test.ts, which runs an actual `vitepress build`, reads the linked stylesheet(s) out of the built HTML, and brace-matches the `@layer ocx{...}` span. Known drop risk documented in that same test's comments: `@layer a, b;` bare ordering statements can be removed by Vite's production minifier when block order already implies the same precedence (harmless with one flat layer, but relevant if a project ever splits into multiple named layers). VitePress's OWN default theme CSS (`vars.css` etc., from vuejs/vitepress `main`) ships with ZERO `@layer` at-rules — confirmed by fetching the raw file — so `@layer` support is something a project must apply itself; it is not inherited from VitePress or from `extends: DefaultTheme`.

## Consumer override entry point

Concrete generator confirmed at /home/mherwig/dev/ocx-catalog/src/build/config_gen.ts:272-275 (`renderThemeShim`): the scratch theme entry file is literally `import Theme from "@ocx-sh/catalog/theme"; import "<consumer-css-path>"; export default Theme;` — the consumer's CSS import statement textually follows the theme's. Because the theme's rules are inside `@layer ocx` and the consumer's file is unlayered, import order is provably irrelevant to who wins: per the CSS Cascade Layers spec (w3.org/TR/css-cascade-5/#layering), 'any declaration not assigned to an explicit layer is added to an implicit final layer' that is ordered after every named layer regardless of where in the source the unlayered rules appear — the spec's own example states unlayered rules win over layered ones 'even though the unlayered styles have a lower specificity, and come first in the source order.' So source order only matters within the SAME stratum (unlayered-vs-unlayered, or layered-vs-layered) — for a generic VitePress site that only uses `.vitepress/theme/custom.css` (no cascade layers involved at all, since the default theme itself is unlayered), the entrypoint is that custom.css file and ordinary specificity/source-order rules apply with no layer protection.

## Token exposure

Contract file(s): /home/mherwig/dev/ocx-catalog/src/theme/styles/tokens/{palette,type,shape}.css, each `@layer`-wrapped, declaring `:root{ --ocx-color-*: ...; --ocx-text-*: ...; --ocx-radius-*: ...; }` plus a `.dark{ --ocx-color-*: ... }` override block (not a media query — see theme_switching). Two-tier system in practice: primitive/semantic tokens declared in the token files (`--ocx-color-surface`, `--ocx-color-border`), PLUS a genuine component-hook tier read live in component CSS with a fallback, e.g. the built CSS shows `border: var(--ocx-border-width) solid var(--ocx-package-card-border-color, var(--ocx-color-border))` — `--ocx-package-card-border-color` is never declared anywhere in the token files, exists purely as an override point, and falls back to the semantic `--ocx-color-border` — this is doctrine tier 4's 'component hook, never declared by the theme, read with a var() fallback to the semantic tier' pattern, confirmed present verbatim. No framework-native token system exists in Vue or VitePress core; VitePress's OWN 259-variable `--vp-*` surface (theme-default/styles/vars.css) is the closest thing to a 'framework-native' set, but it is scoped to the default theme only (not core) and this repo does not import it, by deliberate choice (research doc C1: 'our 37 components use zero `.vp-*` classes').

## Theme switching

Class toggle, not a media query, in both VitePress's own default theme AND ocx-catalog's custom theme: `.dark` appended to the `<html>` element. Confirmed for VitePress via vitepress.dev/reference/site-config's `appearance` option: '(by adding the `.dark` class to the `<html>` element)', persisted to localStorage under key `vitepress-theme-appearance`, applied by an inline pre-render script to avoid flash. Interaction with token tiers is a documented DEFECT (D1) in /home/mherwig/dev/ocx-catalog/.claude/artifacts/research_design_tokens_2026-08-24.md, and independently confirmed present in VitePress's OWN `vars.css` (fetched from vuejs/vitepress `main`): `:root{--vp-c-neutral:#000}` and `.dark{--vp-c-neutral:#fff}` are BOTH single-class-equivalent selectors at specificity (0,1,0) matching the same `<html>` element, so they do not 'override' each other by specificity — whichever is LATER in source order wins in both modes. A consumer stylesheet that redeclares only `:root{--ocx-color-bg:#fff}` (intending 'my light-mode value') and loads after the theme's CSS silently wins under `html.dark` too, because it is textually later, not because `:root` beats `.dark` semantically. This is a real, reproduced trap (ocx-catalog's research doc reproduces it with happy-dom) that generic 'ship tokens as custom properties' advice does not prevent — a consumer must either redeclare BOTH `:root` and `.dark` for every color token, or scope the override to `html:not(.dark)` / `html.dark` explicitly.

## Testability

Two real, runnable checks exist in ocx-catalog and are directly portable as the annex's canonical example: (1) SOURCE-level, fast: /home/mherwig/dev/ocx-catalog/test/theme/layer_contract.test.ts regexes every `.vue`/`.css` file under `src/theme` for a `<style>` (or stylesheet) body NOT containing `@layer ocx {`, and separately flags any `!important` found INSIDE the layer that isn't next to an accessibility-lock marker comment (since `!important` reverses layer priority per the cascade-layers spec — a layered `!important` permanently beats a consumer's own `!important` with zero escape). (2) BUILD-level, authoritative: /home/mherwig/dev/ocx-catalog/test/build/css_layer_real_build.test.ts runs an ACTUAL `vitepress build`, extracts the linked stylesheet(s) from the built HTML via `<link rel=stylesheet>`, brace-matches the `@layer ocx{...}` span in the concatenated CSS, and asserts the `[data-v-...]` scoped selectors landed INSIDE it. The test's own comment is the citable warning: 'happy-dom drops `@layer` blocks at parse time and jsdom parses them but never applies layered declarations, so a cascade-layer assertion in either engine passes whether or not the mechanism works' — i.e. a unit test using jsdom/happy-dom to 'verify' cascade-layer behavior gives a false green regardless of whether layers actually work; only a real browser or a string/regex check on real build output (as done here) is honest.

## Where this contradicts the core doctrine

One real divergence, narrow and specific: core doctrine point 3 says 'ship every framework-authored style block inside a single @layer... leave the consumer's file unlayered' as if that fully solves the override problem for the whole framework surface. For VitePress specifically it does NOT, because VitePress's OWN default theme (`extends: DefaultTheme`) ships its CSS completely unlayered (confirmed: zero `@layer` in `theme-default/styles/vars.css` on vuejs/vitepress `main`). A project that dutifully layers its own new components while extending the default theme still leaves every default-theme-owned selector exactly as unreliable-to-override-by-selector as pre-cascade-layers CSS — the doctrine's fix only covers code the project itself authors, and 'extend the default theme' is the single most common path into this framework. No other doctrine point (1, 2, 4, 5) is contradicted; all four are independently confirmed true for Vue SFC/VitePress by ocx-catalog's real compiled output and tests.

## Traps

- Assuming a plain descendant selector in a parent's `<style scoped>` reaches into a child component's internals — it does not; only the child's own root element carries the parent's `data-v-hash` too, everything deeper needs `:deep()`.
- Assuming `:deep()` 'escapes' scoping/specificity concerns entirely — it still nests inside whatever `@layer` wraps the block and still carries the ancestor's `[data-v-hash]`, so the emitted rule is (0,3,0), not lower than a plain scoped rule.
- Assuming wrapping `<style scoped>` content in `@layer <name> { }` breaks Vue's scoped-CSS compiler — verified false: Vue's transform still scopes every selector nested inside the at-rule. An agent who doesn't know this may skip the layer entirely inside SFCs, or try to put `@layer` OUTSIDE the `<style>` tag (which cannot span the per-component wrapper Vue generates).
- Verifying cascade-layer behavior with jsdom or happy-dom — both silently pass whether or not `@layer` actually works (jsdom parses `@layer` but never applies layer precedence; happy-dom drops the at-rule at parse time). Only a real build + real browser (or brace-matching real build output, as ocx-catalog does) is a valid check.
- Redeclaring a color token only under `:root` to fix a 'light mode' value — because `:root` and `.dark` are equal specificity (0,1,0) matching the same `<html>` element, whichever is textually LAST wins in BOTH modes, so an incomplete override silently corrupts dark mode too. Present in both ocx-catalog's own custom theme and in VitePress's own default theme's `vars.css`.
- Assuming `extends: DefaultTheme` gives you a `@layer`-protected base to build on — VitePress's own default theme CSS ships completely unlayered; none of its `.VPButton`/`.VPNav`/etc. selectors are overridable-by-plain-selector any more reliably than pre-cascade-layers CSS, regardless of what layer discipline you apply to your OWN additions.
- Putting `!important` inside the shared `@layer` for anything other than a deliberate, unbeatable accessibility lock — cascade-layer order REVERSES for `!important` declarations, so a layered `!important` permanently outranks a consumer's own `!important`, which is the one override a consumer cannot work around at all.

**Refuted:** `:deep()` stacks a third selector: `.a[data-v-hash] .b` = (0,3,0). Pitfall #2 generalises it: "the emitted rule is (0,3,0), not lower than a plain scoped rule."

- Why wrong: True only for the `.a :deep(.b)` form the Vue docs happen to show. The compiler drops the hash from the deep part AND, when no ancestor selector is written, emits the hash as a standalone attribute selector. The tuple therefore depends entirely on what the author wrote before `:deep()`, and the bare form is common. `:deep(p)` is strictly LOWER than a plain scoped class rule — the exact inversion the brief warns about.
- Correction: Bare `:deep(.b)` → `[data-v-hash] .b` = (0,2,0), EQUAL to a plain scoped rule, not higher. `:deep(p)` → `[data-v-hash] p` = (0,1,1), LOWER than a plain scoped `.a[data-v-hash]` (0,2,0). `:deep(.b .c)` → `[data-v-hash] .b .c` = (0,3,0). Only `.a :deep(.b)` → `.a[data-v-hash] .b` = (0,3,0). State the tuple as a function of the authored form, never as a constant.
- Evidence: Reproduced with @vue/compiler-sfc 3.5.27 (installed in scratchpad, `compileStyle({scoped:true, id:'data-v-f3f3eg9'})`):

### On the annex call

Agree an annex is warranted — but the rationale as written is not the one that earns it, and one of its four legs is built on a refuted claim.

Leg (1) "@layer nests inside `<style scoped>` and still scopes" is real, non-obvious, and I reproduced it. Keep it, and extend it: it also holds inside `@media`/`@supports` nested within the layer.
Leg (2) the `:root`/`.dark` trap is real but the annex must give the corrected mechanism (layer priority, not source order) or it teaches an agent to "fix" it by reordering an import.
Leg (3) "`extends: DefaultTheme` inherits a completely unlayered base" is REFUTED as stated — vitepress 2.0.0-alpha.18 layers base.css into `@layer __vitepress_base`. The surviving, better version is sharper anyway: the default theme is *partially* layered as of v2, ~65 KB of it (vars.css, vp-doc.css, 60 scoped components) is not, and the partial layering introduces a layer-ORDER interaction with a project's own layer that the core doctrine's one-flat-layer model does not describe.
Leg (4) jsdom/happy-dom false-green is currently a self-citation (see unverifiable_claims) and the repo actually solves it with a real-Chrome script the finding missed.

What genuinely carries the annex is mostly absent from the finding — traps that only surface by running the compiler:
- `:root` and `.dark` inside `<style scoped>` compile to `[data-v-hash]:root` and `.dark[data-v-hash]`, which match NOTHING. Declaring design tokens in a scoped block is silently dead code. This directly attacks doctrine point 1 and nothing else in the finding warns about it. (Reproduced: `:root{--x:1}` → `[data-v-f3f3eg9]:root{--x:1}`; `:root,.dark{--x:1}` → `[data-v-f3f3eg9]:root,.dark[data-v-f3f3eg9]{--x:1}`.)
- `@keyframes spin` → `@keyframes spin-f3f3eg9`. Animation names are hashed, so a consumer can neither reference nor redefine them.
- `data-v-<hash>` rotates per build, so a consumer cannot even opt into the specificity war by copying the attribute.
- `:where()` neutralises the boost entirely (refuted claim #2) — a real tool the finding says does not exist.
- The `:deep()` tuple is a function of the authored form, not a constant (refuted claim #1).
- **Cascade layers cannot beat inline styles.** css-cascade-5 §6.4 sorts Element-Attached Styles ABOVE Layers: "declarations that are attached directly to an element … take precedence over declarations the same importance that are mapped via style rule." This is a genuine limit on doctrine point 3 and it bites this framework three separate ways — Shiki's inline `background-color` (why the repo's one unlayered `!important` exists), monogram.ts's 16 hex applied as inline style (research artifact D3: "overridable only with `!important`"), and Vue's own `v-bind()` in CSS, which the finding describes accurately and then never flags as an override hazard. Any framework that paints via inline style escapes the layer contract, and the only remedy is an unlayered `!important`.
- `data-slot` — the finding's token_exposure covers the hook tier but never mentions the identity tier, which the host repo treats as the actual public API ("A `data-slot` value is public API. Renaming one is a breaking change"; class names explicitly internal), and which component_hook_contract.test.ts enforces ("every published hook is actually reachable from a data-slot element"). A hook on an element a consumer cannot select is not an API. That belongs in the core doctrine, not just the annex.
- `@scope` is not a substitute (repo rule: zero specificity contribution, proximity only breaks ties among already-equal rules, leaves inherited custom properties untouched). Worth one line so an agent does not reach for it.

Verdict: annex_worth_it = true, rationale = rewrite.

Not a clean bill of health. The doctrine survives intact — all five points hold for Vue SFC/VitePress and I reproduced the load-bearing ones — but the finding is not publishable as-is: nine claims are wrong, including one specificity generalisation, one version-drifted framework fact, one fabricated compiled selector, and one causal mechanism that no longer describes the repo it cites.

Severity ranking for the rule author:
1. **`:deep()` = (0,3,0)** — a wrong tuple in the exact place the brief says a wrong tuple inverts the contract. Bare `:deep(p)` is (0,1,1), LOWER than a plain scoped rule.
2. **"VitePress default theme has ZERO @layer"** — true of 1.6.4, false of 2.0.0-alpha.18. This is the version-drift failure mode verbatim, and it is the sole support for the finding's `divergence_from_core`.
3. **The `:root`/`.dark` mechanism** — attributing it to source order in a layered theme teaches the wrong fix.
4. **"wraps the ENTIRE body of every block"** — the one deliberate exception is the most doctrinally interesting rule in the repo, and the source-level test the finding recommends as canonical cannot enforce the invariant it is described as enforcing (containment check, not coverage check). If that test ships as the annex's example, it ships with a known hole.
5. **`.tag-badge[data-v-3abac49e]`** — evidence hygiene. Actual hash `ad21926d`. Every compiled-output citation in the finding points at a gitignored, local, 3-day-old build directory.

Doctrine-level gap the whole finding misses: **cascade layers do not beat inline styles** (css-cascade-5 §6.4 sorts Element-Attached Styles above Layers). Doctrine point 3 as written promises more than the mechanism delivers for any framework that paints via inline style — and Vue's own `v-bind()` in CSS is exactly such a framework feature. The core rule needs one line naming this ceiling, and the annex needs the three concrete instances in this repo.
