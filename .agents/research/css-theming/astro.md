## Scoping mechanism

Component `<style>` blocks are scoped by appending a scope selector to every compound selector, per the `scopedStyleStrategy` config (schema default: `"attribute"`, confirmed at node_modules/astro/dist/core/config/schemas/base.js:49 and https://docs.astro.build/en/reference/configuration-reference/#scopedstylestrategy). Verified firsthand by invoking the real compiler (`@astrojs/compiler-rs`) that astro@7's `core/compile/compile.js` calls, on `.foo { color: red }`:
- `attribute` (default): HTML gets `data-astro-cid-<hash>` on every element; CSS becomes `.foo[data-astro-cid-tmciredb]{...}` — a bare attribute selector, NOT wrapped in `:where()`.
- `class`: HTML gets an added class `astro-<hash>`; CSS becomes `.foo.astro-tmciredb{...}`.
- `where`: HTML gets the same added class; CSS becomes `.foo:where(.astro-tmciredb){...}` — wrapped in `:where()`.
`:root { }` inside a scoped `<style>` block is emitted completely untouched under all three strategies — no attribute/class is appended to it (confirmed: the root element the component renders is never `<html>`, so nothing matches an added `:root[data-astro-cid-…]` anyway, and the compiler special-cases it to skip scoping). `is:global` disables scoping for that block entirely (no attribute/class added to anything in it) but the block still passes through Astro's normal CSS asset pipeline — bundled, deduped, `import`/`url()`-resolved (https://docs.astro.build/en/reference/directives-reference/). `is:inline` renders the block exactly where authored in the output HTML, completely unprocessed: not bundled, not deduped, not scoped, and its `import`/`@import`/`url()` references are NOT resolved (same doc). This is the mechanism grimoire-indexer uses to guarantee the consumer's `customCss` lands last, verbatim, and outside Astro's asset graph (src/renderer/astro/layouts/Base.astro: `<style is:inline set:html={css} />`).

## Emitted specificity

Default (`attribute`) on a single-class selector: `.foo[data-astro-cid-tmciredb]` → **(0,2,0)** — class + attribute each contribute one to the middle column; the scope hook is a bare attribute selector, NOT wrapped in `:where()`, so it is NOT specificity-0. This matches grimoire-indexer's real production build (`.version[data-astro-cid-3oqgkrws]`, quality-css-overrides.md) and my own direct compiler probe. `class` strategy: `.foo.astro-tmciredb` → also (0,2,0), numerically identical, via an added class instead of an attribute. `where` strategy: `.foo:where(.astro-tmciredb)` → **(0,1,0)**, identical to the unscoped `.foo` — `:where()` here genuinely contributes zero, confirmed by direct probe, matching MDN's `:where()` spec semantics and Astro's docs ("no specificity increase").

## Cascade-layer support

Astro does not auto-wrap component or global styles in any `@layer`; `@layer` is plain author-written CSS that Astro's compiler and Vite pipeline pass through structurally unchanged (verified: scoping is correctly applied to selectors INSIDE a `@layer grimoire { }` block by direct compiler probe, and a real production build in grimoire-indexer confirms it survives bundling+minification with zero rules leaking outside the layer — test/renderer/build.test.ts `outsideLayers()`). Astro's own generated CSS is starting to adopt layers for itself: withastro/astro#17141 wraps Astro's generated responsive-image CSS in `@layer astro.images` so it always loses to unlayered author/consumer CSS — but that is scoped to that one built-in feature, not a general auto-layering of user component styles. Known minifier gotcha (not Astro-specific, inherited from Vite): a bare ordering statement `@layer a, b;` is dropped by Vite's default esbuild-based production `cssMinify` (Astro sets `cssMinify: true` by default for builds — node_modules/astro/dist/core/build/vite-build-config.js:29) when the ordering statement and its blocks live in separately-bundled/imported CSS files (vitejs/vite#22705, open). This can silently invert cascade order in a multi-entry-point Astro site. Mitigation, already the local convention: ship exactly one layer name project-wide so no ordering statement is ever needed.

## Consumer override entry point

The idiomatic, verified-safe entrypoint for a consumer/theme override that must land last and completely unlayered is `<style is:inline set:html={consumerCss} />` (or an equivalent literal `<style is:inline>` block) placed after the component bundle in the root layout's markup. `is:inline` is the load-bearing choice, not `is:global`: `is:global` only removes scoping — the block still goes through Astro's normal CSS asset pipeline (bundled, deduplicated, its `url()`/`@import` references resolved), so neither its exact final position in the merged stylesheet nor byte-for-byte survival through minification/bundling is guaranteed. `is:inline` skips all of that, so it is both structurally unlayered (nothing rewrites it) and provably positioned exactly where authored. Source order/injection point alone is never what makes it win against a scoped component style at the default strategy — the `@layer` mechanism (core doctrine point 3) is what does that; `is:inline` only guarantees the override CSS itself reaches the page unmodified and where intended. Trade-off: because `is:inline` skips module resolution, consumer override CSS containing a relative `url(./bg.png)` or `@import` will NOT be resolved/bundled — those must be absolute URLs.

## Token exposure

No Astro-native token system exists; custom properties are declared in plain CSS, idiomatically in one dedicated `.css` file (e.g. `styles/tokens.css`) imported by the root layout — never inside a scoped component `<style>` block, per the "one contract file" discipline (this is a project-contract reason, not a technical scoping limitation: `:root` blocks are left unscoped by Astro regardless of where declared, verified above). The contract file itself is documentation-as-code: grimoire-indexer's `tokens.css` carries a contract comment enumerating all public tokens, treated as the only copy of the public API surface.

## Theme switching

No Astro-native theme/dark-mode primitive. Purely userland CSS convention — grimoire-indexer keys on `[data-theme="dark"]` as a plain attribute selector; nothing about Astro's compiler, scoping, or build pipeline changes how token tiers interact with a theme switch. The core doctrine's colour-in-both-schemes / measurement-in-one-scheme invariant applies unmodified.

## Testability

Two-tier check, both proven in a real repo (grimoire-indexer/test/renderer/{style_contract,build}.test.ts): (1) fast source-level regex/brace-match over every `.astro`/`.tsx`/`.css` file's `<style>` bodies, asserting each opens with `@layer <name> {` and nothing trails after its closing brace; (2) the check that actually pins the contract — run a real `astro build()`, read the emitted bundled CSS from disk, brace-match every `@layer <name> { … }` block and assert the remainder (everything NOT inside one) is empty (`outsideLayers(bundledCss).trim() === ""`). A minimal portable version for any Astro project: build a fixture page with one scoped component style and one deliberately-unwrapped style block, then assert the compiled CSS asset contains zero non-whitespace bytes outside `@layer` — this reddens exactly on the defect it exists to catch (an unwrapped block silently escaping the layer) and is immune to the source-grep's blind spot (it survives a build-tool or minifier change the source check can't see). Confirmed reproducible: `npx astro build` in that repo (or invoking `@astrojs/compiler-rs`'s `transform()` directly with `scopedStyleStrategy: astroConfig.scopedStyleStrategy`) is what a rule's test should exercise, not a source AST guess.

## Where this contradicts the core doctrine

No outright contradiction of the five doctrine points for Astro's DEFAULT config — Astro's default behavior is exactly the motivating case for points 2 and 3. One real qualification, not a contradiction but a scope limit an annex must state: doctrine point 2 says an unlayered author rule's scoped selector \"outranks a consumer's .version in EITHER source order\" — this is true only for the default (`attribute`) and for `class` strategy. Under `scopedStyleStrategy: 'where'` (a supported, non-default value), the scoped selector's specificity is IDENTICAL to the consumer's plain selector (0,1,0 = 0,1,0), so it ties, and source order DOES decide outcome — point 2 as literally worded is false in that configuration. @layer (point 3) remains correct and strictly stronger regardless of strategy (it wins on layer order, independent of tie-breaking), so the doctrine's PRESCRIPTION survives unchanged; only the phrase \"in either source order\" needs an Astro-specific footnote that it assumes the project hasn't opted into `where`. Everything else — layer passthrough, tiering, contract testing — is unmodified and unopposed by Astro's design.

## Traps

- Assuming placing the consumer's <link>/<style> after the component bundle makes it win: under the default `attribute` strategy a scoped `.foo[data-astro-cid-…]` is (0,2,0) and beats a plain `.foo` in EITHER source order — only @layer fixes this.
- Reaching for `is:global` as 'the' override entrypoint: it removes scoping but the block still passes through Astro's bundling/dedup/import-resolution pipeline, so its final position and unmodified survival aren't guaranteed the way `is:inline` guarantees them.
- Using `is:inline` for override CSS that contains a relative `url()` or `@import`: is:inline explicitly skips import/url resolution, so relative asset references silently fail to resolve.
- Believing `scopedStyleStrategy` can be set per-component: it's a single project-wide astro.config value: it cannot be used to fix one component's specificity in isolation, so @layer (which works regardless of the project's chosen strategy) is the only per-file-safe fix.
- Trusting a multi-file `@layer a, b;` ordering statement in a production build: Vite's default esbuild-based cssMinify drops the ordering statement when the statement and its blocks live in separately-bundled CSS files (vitejs/vite#22705), silently inverting cascade order — ship exactly one layer name to make the question moot.
- Declaring `:root { --token: … }` inside a scoped component `<style>` block on the theory that scoping will contain it: Astro leaves `:root` selectors completely unscoped in every strategy, so it leaks globally exactly like an unscoped file would — the reason to keep tokens in one file is contract discipline, not a scoping safety net.
- Assuming the doctrine's 'source order never wins' claim holds regardless of config: it is true for the default (`attribute`) and for `class`, but FALSE under `scopedStyleStrategy: 'where'` — there a scoped selector and a plain consumer selector tie at equal specificity and source order decides. An agent must check the project's configured strategy before asserting @layer is the only thing standing between a consumer and a lost override.

- Astro does not auto-wrap component or global AUTHOR styles in any layer — `grep -rno "@layer [a-z.]*" node_modules/astro/dist/` returns only the two built-in feature layers, nothing touching user `<style>` blocks.
- `is:global` disables scoping but the block STILL enters Astro's CSS asset pipeline. Note: the researcher cited the directives doc for this, and the doc does not actually say it — but my probe does. A component with `<style is:global>.g{color:red}</style>` plus a scoped block yields TWO css assets (`[".g { color: red }", ".s[data-astro-cid-…] {…}"]`) and two `import "/x/C.astro?astro&type=style&index=N&lang.css"` statements in the emitted module.
- `is:inline` renders verbatim in the template and emits no CSS asset. Reproduced: the inline block appears literally inside `$$render` as `<style>.i { color: red }</style>` (the `is:inline` attribute itself is stripped) with no corresponding `?astro&type=style` import. Docs corroborate the three consequences verbatim: "Will not be bundled into an external file." / "Will not be deduplicated—the element will appear as many times as it is rendered." / "Will not have its `import`/`@import`/`url()` references resolved relative to the `.astro` file." (https://docs.astro.build/en/reference/directives-reference/)
- `cssMinify` is true by default for Astro production builds — vite-build-config.js:29 (what it resolves TO is refuted separately).
- withastro/astro#17141 is merged (2026-06-23), title "Wrap responsive image styles in `@layer astro.images` to respect CSS cascade layers", and its body states the motivation correctly: unlayered `:where([data-astro-image=constrained]){max-width:100%}` was beating user CSS inside a `@layer` regardless of :where()'s zero specificity.
- grimoire-indexer really does use the claimed entrypoint: src/renderer/astro/layouts/Base.astro:2007 `{css && <style is:inline set:html={css} />}`, and its global block is wrapped at :382 `@layer grimoire {`.
- The build-level contract test exists as described — test/renderer/build.test.ts:897 `expect(outsideLayers(bundledCss).trim()).toBe("")` against a real `buildSite()` run (its portability is refuted separately).
- The `divergence_from_core` qualification is directionally right: under `scopedStyleStrategy:'where'` a scoped single-class selector ties a consumer's plain selector at (0,1,0) and source order decides, so doctrine point 2's "in EITHER source order" does not hold there. REFINEMENT the researcher missed: the tie only exists at equal compound count. `.foo .bar` under `where` compiles to `.foo:where(.astro-x) .bar:where(.astro-x)` = (0,2,0), which still beats a consumer's `.bar` at (0,1,0) in either order. So point 2 is false only for the exactly-matched-complexity case, not wholesale — and @layer remains the correct prescription regardless.

### Unverifiable

- "grimoire-indexer's real production build emitted `.version[data-astro-cid-3oqgkrws]`" — I did not run `astro build`; that string appears only as prose inside .claude/rules/quality-css-overrides.md, which is a claim about a past build, not an artifact. The SHAPE is independently confirmed by my compiler probe, but the specific hash and the "9.6 KB / 40% of emitted CSS" figure are unreproduced.
- "is:inline ... is both structurally unlayered and PROVABLY POSITIONED exactly where authored" relative to Astro's injected bundle `<link>`. The compiler probe proves the block stays in the template; it does not prove where Astro's `<link rel=stylesheet>` for the bundle lands relative to it in the final HTML. Since layers, not order, are supposed to decide, this is also the least load-bearing part of the entrypoint argument — the annex should not lean on it.
- Whether `compressHTML` (default true in Astro 7) leaves an `is:inline` style block byte-for-byte intact. The researcher asserts "byte-for-byte survival"; I did not test it.
- test/renderer/style_contract.test.ts — cited for the source-level check and the data-slot set; I read build.test.ts but not this file.
- The claim that `is:global` blocks are "deduped" specifically. Bundling and asset-pipeline entry are proven by my probe; dedup behaviour is inferred from the is:inline doc's contrast, not observed.

### On the annex call

Agree with `annex_worth_it: true`, but the researcher's stated rationale is roughly half wrong and the annex must be rebuilt around different content. What genuinely earns the file — none of it inferable from reading a component: (1) the three-strategy specificity table, because it is the tuple every test and every override argument is written against, and because it is config-dependent in a way an agent cannot see from the stylesheet; (2) the scoping-escape set — `:root`, `html`, `body`, `@keyframes`, `@font-face`, `:global()` leak globally out of a scoped block, and `*` and `#id` get non-obvious tuples; (3) Astro injecting `@layer astro` and `@layer astro.images` into a project that believes it ships one layer, which also breaks the naive contract test. What does NOT earn its place, and should be cut rather than published: the minifier pitfall (built on a closed-as-invalid issue, the wrong minifier, and a mechanism that does not reproduce), and most of the `is:global`-vs-`is:inline` argument (the real reason to prefer `is:inline` is that it skips the asset graph, not a positioning guarantee I could not verify — and under the layer contract position is not what wins anyway). Net: the annex is justified, but three of the five items the rationale leans on are the wrong three.

Not a clean bill of health. The compiler-level work is solid and I reproduced every emitted-selector and specificity claim exactly, from the same @astrojs/compiler-rs 0.3.1 that astro@7.1.4 imports — those tuples are safe to publish. The build-pipeline half is where it falls apart, and it fails in the direction that matters most for a published rule: it asserts a confident, cited, falsifiable mechanism (esbuild drops your @layer ordering statement, per open Vite issue) that is wrong on the minifier, wrong on the issue's status, wrong on the issue's conclusion, and does not reproduce when tested. Three separate errors stacked into one pitfall bullet, all citation-shaped.

Two things the researcher stopped one step short of, both of which change what the rule should say:

1. They probed `:root` and generalized from it. Probing eight more selectors shows `html`, `body`, `@keyframes` and `@font-face` escape identically — so the pitfall "don't declare tokens in a component block" is really "a component `<style>` block is not a container for anything root-, document- or name-scoped", which is a bigger and more useful trap.

2. They found `@layer astro.images` and concluded Astro's self-layering is narrow. A grep of astro/dist finds a second one (`@layer astro`, view transitions), and the consequence — that the "ship exactly one layer name" convention is not something a project can actually enforce, and that grimoire-indexer's `outsideLayers()` would go red on Astro's own image CSS in any project using `<Image>` — is the single most publishable finding in this whole area and it is absent.

Recommendation: keep the specificity table verbatim, delete the minifier bullet entirely, replace it with the layer-collision hazard, and expand the `:root` pitfall into the full escape set. Reproduction commands and file:line evidence for all of the above are in `refuted_claims`.
