## Overturns round 1

- **Was:** "critically — its ORDER relative to a layer a project declares itself" was flagged unverified in the brief; round-1's vue-vitepress verdict only established that vitepress 1.x ships 0 layered files and 2.0.0-alpha.18's base.css is wrapped in `@layer __vitepress_base` (4341 bytes), but never measured order against a project-declared layer. This is now measured directly: a project layer imported through the normal `theme/index.ts` `import './custom.css'` pattern automatically wins, with no ordering statement needed — good news for the rule's override contract, but it depends entirely on the project choosing a layer name that VitePress hasn't already used and never emitting an explicit `@layer a, b;` statement that could reverse it.<br>**Now:** In VitePress 2.0.0-alpha.19 (the version range ocx-catalog declares), a project's own `@layer <name>` wins over VitePress's own `@layer __vitepress_base` for a conflicting equal-selector-shape declaration, because VitePress's layer is declared FIRST in the bundled stylesheet and the project's theme-entry CSS (imported after `import DefaultTheme from 'vitepress/theme'`) is always concatenated AFTER it — and CSS cascade-layer priority is governed purely by order of first appearance of the layer name, not specificity or literal rule position.
- **Was:** Confirms round-1's own correction ("vitepress 1.6.4 default theme: 0 of 10 CSS files layered") with a real full-site production build rather than a per-file npm-pack scan, and adds the concrete consequence: a project author who wraps their override in @layer on a 1.x site, expecting @layer's normal 'organize my overrides' benefit, silently LOSES to VitePress core specifically because they opted into a layer and core didn't — the opposite of what most authors expect from "my CSS loads last".<br>**Now:** In VitePress 1.6.4, the default theme's page-reset margin rule (`body{margin:0;...}`) is NOT inside any `@layer` — it is a plain unlayered rule. A project's own `@layer project { body { margin: 4321px } }`, even though it is the physically LAST rule in the bundled stylesheet, LOSES the cascade to that unlayered rule (unlayered always outranks layered, independent of source order or specificity), so `body`'s resolved margin in a VitePress 1.x site is 0, not 4321px, despite the project's rule looking like it should win by "last rule wins" intuition.

## What belongs in the annex

- Vue's :deep() specificity tuple is NOT a constant (0,3,0) as a naive reading of the docs suggests — it is a function of the authored selector. Bare `:deep(.b)` -> `[data-v-hash] .b` = (0,2,0), equal to a plain scoped class rule; only `.a :deep(.b)` with an explicit ancestor -> `.a[data-v-hash] .b` = (0,3,0). An agent editing scoped CSS must read what precedes `:deep(`, not assume a fixed boost.
- :where(.selector) inside a Vue <style scoped> block is a genuine, compiler-supported escape hatch to (0,0,0) specificity — the compiler injects the scope hash INSIDE the :where() argument, so it inherits :where()'s zero-specificity collapse. It is not merely 'never added' as a specificity boost; it can be deliberately defeated by the author, and ocx-catalog already relies on this in production (src/theme/styles/docs-prose.css).
- :slotted() mints a DIFFERENT scope-hash suffix ('-s') than the component's plain scope attribute — `.slotted-item[data-v-<hash>-s]`, not `[data-v-<hash>]`. An agent inspecting a built stylesheet for 'the' data-v- attribute of a component will miss :slotted rules if it only pattern-matches the bare hash.
- :global() fully strips the scope hash — zero data-v- anywhere on the emitted selector — so a :global() rule in a Vue SFC has exactly the specificity it would have as ordinary unscoped CSS; nothing about being inside a component adds hidden weight.
- @layer survives a real Vite 8.2.2 / lightningcss production build for a Vue <style scoped> block verbatim, at-rule and all, with the component's own data-v- scope attribute correctly nested inside it — this was previously asserted from spec reading only; it is now confirmed from actual minified build output bytes.
- In VitePress 1.6.4, VitePress's own page-reset CSS is UNLAYERED. An author who wraps their own override in @layer on a 1.x site loses to VitePress core even though their rule is physically the last bytes in the stylesheet — 'my import comes last' does not mean 'my rule wins' once layers are involved asymmetrically.
- In VitePress 2.0.0-alpha.19, VitePress's own reset IS layered (`@layer __vitepress_base`), and because a project's theme-entry CSS is always concatenated after VitePress's own bundled CSS, a project's own freshly-named @layer automatically wins over `__vitepress_base` by plain first-appearance order — no explicit `@layer a, b;` statement required. This flips between the two shipped VitePress major-version lines and must not be stated as one universal rule.
- VitePress ships exactly 228 distinct --vp-* custom properties in both 1.6.4 and 2.0.0-alpha.19's built default-theme CSS, organized as a two-tier system: numbered primitive color-scale tokens (e.g. --vp-c-indigo-1) plus semantic tokens that alias them (--vp-c-brand-1: var(--vp-c-indigo-1)); dark mode repoints the primitive tier under html.dark, leaving the semantic alias's reference unchanged.
- ocx-catalog's theme deliberately does not extend VitePress's DefaultTheme, so none of the @layer __vitepress_base vs project-layer findings above apply to ocx-catalog's own build — but they are exactly the trap the published rule must warn OTHER consumers about if they do extend it.
- ocx-catalog's own real-build layer-contract test (test/build/css_layer_real_build.test.ts) could not be executed this round (node_modules absent, and ground rules forbid installing deps in a user's tracked repo) — its assertions are read but unverified; do not cite it as a passing check.
