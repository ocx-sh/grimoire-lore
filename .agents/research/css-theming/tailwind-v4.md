## Scoping mechanism

Tailwind itself has NO component-style scoping — utility classes are global flat class selectors generated from a content scan; there is no per-component "scope hook" at all. Any scoping seen in a Tailwind project comes from the HOST framework (Astro's data-astro-cid-*, Vue's data-v-*, CSS Modules) and is entirely outside Tailwind's control. Directly verified: in /home/mherwig/dev/kate-middlechild/packages/web/dist/_astro/index.CZveVo4H.css, Astro's scoped `<style>` blocks compile to `.hero-masthead[data-astro-cid-bbe6dxrz]{...}` and sit completely OUTSIDE and BEFORE any of Tailwind's @layer blocks (verified by locating this selector at byte offset 0 of the file, ahead of `@layer properties` at offset 3471) — i.e. the host framework's scoped CSS is unlayered by default even in a Tailwind v4 build, which Tailwind does nothing to prevent or fix.

## Emitted specificity

A generated utility = one bare class selector, specificity (0,1,0). Confirmed via the official v4 blog's own example — `.bg-blue-500\/50 { background-color: color-mix(in oklab, var(--color-blue-500) 50%, transparent); }` (https://tailwindcss.com/blog/tailwindcss-v4) — and via compiled output in kate-middlechild, e.g. `.mx-6{margin-inline:calc(var(--spacing) * 6)}`. Stacked pseudo/attribute variants on the same utility (`.hover\:bg-blue-500:hover`) raise that rule's own specificity to (0,2,0) etc. — NOT zeroed automatically. There is no Tailwind "scope hook" to wrap in :where() (see scoping_mechanism), but Tailwind's own official recipe for custom variants DOES use :where() to keep a variant condition at zero added specificity: `@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));` — this exact line is both the official docs example (tailwindcss.com/docs/dark-mode) and the literal line used in /home/mherwig/dev/kate-middlechild/packages/tokens/src/theme.css. Preflight (base-layer resets) also uses :where() for the same reason, e.g. `:where(select:is([multiple],[size])) {...}` (verified in the compiled CSS).

## Cascade-layer support

Real, native CSS cascade layers in v4 (not v3's non-standard `@layer` directive) — confirmed by the official v4 blog: "Native cascade layers — giving us more control than ever" with the exact order statement `@layer theme, base, components, utilities;` (https://tailwindcss.com/blog/tailwindcss-v4). Compiled output in kate-middlechild shows a 5th, undocumented-in-marketing-copy layer, `properties`, holding `@property` registrations guarded by an `@supports` polyfill check, positioned BEFORE `theme`. Verified exact layer positions/order in the minified bundle (byte offsets): properties(3471) → theme(4792) → base(6255) → components(9757, empty statement in this build since no `@layer components{}` content was authored) → utilities(9775). `@theme{...}` compiles to `@layer theme{:root,:host{--color-x:...}}` — verified the full token dump landed there. Layer names survive Vite/Lightning-CSS minification as literal, grep-able `@layer x{` tokens — this is exactly what makes the compiled-output test in the doctrine's point 5 mechanically trivial for Tailwind. Consequence for override precedence: because these are real cascade layers, ANY unlayered rule beats ANY layered rule at ANY specificity per spec — so a consumer's plain CSS wins over all of Tailwind's theme/base/components/utilities output without `!important` or selector games, PROVIDED the consumer's own CSS is not itself nested inside a same-named `@layer` (see override_entrypoint). Known drop risk: not observed in this repo/version, but third-party bundler/minifier mishandling of native `@layer` has been an active complaint elsewhere (e.g. https://github.com/livewire/flux/issues/783) — treat "does our toolchain preserve @layer" as a per-project thing to verify, not assume.

## Consumer override entry point

Two valid injection points, both requiring the consumer's own rule to stay UNLAYERED (no wrapping @layer of any name):
1) Redefine the semantic custom property on an unlayered selector (e.g. plain `:root{--color-accent:...}` with no @layer wrapper) — wins unconditionally over Tailwind's `theme` layer and propagates everywhere a utility consumes it via `var()`, since Tailwind's generated utilities reference tokens through `var()` rather than inlining a literal (verified: `.bg-blue-500\/50{background-color:color-mix(in oklab, var(--color-blue-500) 50%, transparent)}`).
2) Target a compiled utility class directly in unlayered consumer CSS — also wins regardless of specificity, but is fragile (requires knowing Tailwind's exact generated class names) and is not the idiomatic path.
Source order alone does NOT suffice if the consumer nests inside a Tailwind-named layer (`@layer utilities{...}` in consumer code) — same-named layers merge by first-appearance order across the whole cascade, and ordinary specificity/source-order rules apply WITHIN that merged layer, so the consumer can still lose to a more specific or later Tailwind rule.
Counter-evidence for "Tailwind auto-layers everything it touches": kate-middlechild's OWN hand-written `[data-theme=dark]{...}` token-override block (authored directly in packages/tokens/src/theme.css after `@theme{}`, with no @layer wrapper) compiles to a fully unlayered rule positioned immediately AFTER the `utilities` layer closes in the bundle (verified via brace-balance parsing: the utilities layer's closing `}` sits at byte offset 12827, and `[data-theme=dark]{` begins at 12828, i.e. zero unlayered content in between) — proving Tailwind only auto-layers content IT generates (@theme tokens, Preflight, @utility, scanned classes); a project's own plain selectors in the same import chain are emitted unlayered wherever they were written, which is exactly the mechanism a downstream consumer needs but is easy to mistake for "automatic."

## Token exposure

Idiomatic declaration is `@theme { --color-x: value; }`, not bare `:root` — docs explicitly distinguish the two: use `@theme` when the token should generate a utility-class family, use plain `:root` only for variables that should NOT (tailwindcss.com/docs/theme). `@theme` output is real custom properties on `:root, :host` inside `@layer theme` (verified compiled dump in kate-middlechild). Namespace prefix is load-bearing and maps directly to a utility family: `--color-*`→bg-*/text-*/border-*, `--font-*`→font-*, `--spacing-*`→p-*/m-*/gap-* (scaled), `--radius-*`→rounded-*, `--shadow-*`→shadow-*, `--breakpoint-*`→sm:/md:/etc. (full table at tailwindcss.com/docs/theme) — a token declared under the wrong prefix silently generates the wrong utility family or none at all. Contract file convention observed in kate-middlechild: the entire `@theme` block (all primitives + semantic aliases, light values) lives in one dedicated package file, packages/tokens/src/theme.css, imported first via `@import "@lutong/tokens/theme.css";` in packages/web/src/styles/global.css — a single source-of-truth file, not per-component inline `@theme` blocks. `@theme static` is required to keep a token in the compiled `:root` block when it's ONLY ever consumed via `var()` (inline style, JS-built class name, SVG fill) and never appears as a literal Tailwind class in Tailwind's content scan — confirmed both by docs ("By default only used CSS variables will be generated in the final CSS output... use `static` to always generate all custom properties") and by kate-middlechild's own region-accent tokens, explicitly annotated `@theme static` because they're "only referenced via CSS var / dynamic class in SVG," and confirmed present in the actual compiled `:root` output.

## Theme switching

Default `dark:` variant tracks `prefers-color-scheme` (OS-level, no markup needed). Overridden per-project via `@custom-variant dark (&:where(...));` — official recipes for both class-based (`&:where(.dark, .dark *)`) and data-attribute-based (`&:where([data-theme="dark"], [data-theme="dark"] *)`) rebinding (tailwindcss.com/docs/dark-mode). kate-middlechild uses the data-attribute recipe verbatim in packages/tokens/src/theme.css. Two SEPARATE mechanisms are wired to the same attribute and must both be kept in sync: (1) the `@custom-variant dark` binding governs which `dark:*` utility classes activate, and (2) a plain `[data-theme="dark"]{--color-bg:...; ...}` block re-declares every semantic custom property for the dark palette — this second block is NOT an `@theme` block and (per the override_entrypoint finding) compiles unlayered, positioned after Tailwind's own layers. Components never branch on theme; they read `var(--color-bg)` etc. and the attribute toggle swaps the whole token set at once. kate-middlechild's own source comment names the risk of wiring these to different conditions as "split brain" theming — a project that reconfigures only the `@custom-variant` (or only the token-override block) desyncs light/dark.

## Testability

Directly executed and confirmed working against kate-middlechild's real build output:
`grep -o '@layer [a-z]*' dist/_astro/index.*.css | sort -u` → returns `properties`, `theme`, `base`, `components`, `utilities` — pin a test asserting this list is present (regression = someone's build config dropped native layer support, e.g. an aggressive minifier).
Stronger check (used in this research to prove the [data-theme=dark] override is unlayered): a byte-offset brace-balance walk from each `@layer name{` to its matching `}`, then assert a given selector's start offset falls strictly between those bounds. Recommend the rule tell agents: any custom (non-Tailwind-generated) CSS the project intentionally wants low-priority must be found INSIDE a `@layer components{...}`/`@layer utilities{...}` span by this test; anything meant to override must be found OUTSIDE every `@layer` span — assert both, don't just assert layer names exist.

## Where this contradicts the core doctrine

No direct contradiction of the five doctrine points was found; Tailwind v4 is the most literal, native implementation of point 3 available. Two clarifications rather than contradictions: (a) Point 2's "scoped component style compiles to an attribute selector at (0,2,0)" does not describe Tailwind itself — Tailwind has no scoping mechanism at all (flat global classes, 0,1,0). Where that attribute-selector inflation shows up in a Tailwind project, it comes from the wrapping framework (Astro/Vue), and it was directly observed to ALSO be unlayered by default in a Tailwind v4 build — so the risk point 2 warns about is amplified, not contradicted: the host framework's scoped rule can beat Tailwind's utilities on BOTH higher specificity (0,2,0 > 0,1,0) AND layer status (unlayered beats layered) at once. (b) Point 3 ("ship every framework-authored style block inside a single @layer") is exactly what Tailwind's own generated output already does out of the box — but this guarantee does NOT extend to a project's own hand-authored CSS living in the same file/import chain, which stays unlayered unless deliberately wrapped. This is a real gap between what principle 3 might imply to an agent ("the framework layers its styles") and what Tailwind actually promises ("only what Tailwind itself generates is layered — your own CSS is your job"), confirmed by direct compiled-output inspection.

## Traps

- Assuming `@import "tailwindcss"` auto-layers the WHOLE file/import chain. False — only Tailwind-generated content (@theme→theme layer, Preflight→base layer, @utility/scanned classes→utilities layer) is layered; hand-written selectors in the same file compile unlayered, positioned wherever written. Verified: kate-middlechild's own `[data-theme=dark]` token-override block, written directly after `@theme{}` with no @layer wrapper, lands fully unlayered in the compiled bundle.
- Reaching for an arbitrary-value utility (`bg-[#1a2b3c]`, `text-[22px]`) instead of a token. This hardcodes a literal directly into the compiled rule, completely bypassing `@theme` — a downstream consumer's custom-property override can never reach it. This is Tailwind's own syntax for silently committing doctrine point 1's defect; the core principles alone give no warning about this specific class-name shape.
- Declaring an appearance value under bare `:root` instead of `@theme`. It becomes an ordinary CSS variable with NO generated utility-class family — components must hand-write `style={{...}}` instead of a class, and Tailwind's own class-scanner/tooling won't recognize it as a design token.
- Forgetting `@theme static` for a token that's only ever consumed via `var()` (inline style, JS-built class, SVG fill) and never appears as a literal Tailwind class in scanned source. Default behavior tree-shakes it out of the compiled `:root` block entirely — the 'public API' custom property silently stops existing in production even though the source still declares it.
- Nesting a consumer override inside `@layer utilities{...}` (or any Tailwind layer name) on the theory 'I'm in the utilities layer so I win via layer order.' Same-named layers merge by first-appearance order across the whole cascade and ordinary specificity/source-order rules apply WITHIN the merged layer — the safe override is to stay unlayered, never to join Tailwind's own layer.
- Hand-rolling a `@custom-variant` without wrapping the condition in `:where(...)`. Official recipes (dark mode, etc.) always wrap the attribute/class condition in :where() to keep it at zero added specificity; omitting it stacks specificity onto every utility using that variant, making later overrides harder for no benefit.

## Review verdict

**Refuted:** override_entrypoint #1: 'Redefine the semantic custom property on an unlayered selector ... and it propagates everywhere a utility consumes it via var(), since Tailwind's generated utilities reference tokens through var() rather than inlining a literal' — combined with token_exposure listing '--breakpoint-*' as part of the tokenized public API.

- Why wrong: Not universal. --breakpoint-* (and --container-* for @sm:* variants) are resolved at BUILD time and inlined as literals into @media prelude text. They are never emitted as custom properties, so no unlayered :root redefinition can reach them. This is load-bearing for doctrine point 1: the researcher's namespace table puts --breakpoint-* in the 'public API' tier, which tells a consumer they can retheme breakpoints from an injected stylesheet. They cannot. The value is frozen at compile time.
- Correction: Split the namespace table into two tiers. Runtime-overridable via var() indirection: --color-*, --font-*, --radius-*, --shadow-*, --spacing-*, --ease-*. Build-time-only, NOT overridable by an injected stylesheet: --breakpoint-*, --container-* (variant thresholds). Doctrine point 1's 'an untokenized appearance value is a DEFECT' still holds, but the rule must say that tokenizing a breakpoint does not make it consumer-reachable — that requires a rebuild, not a stylesheet.
- Evidence: /home/mherwig/dev/kate-middlechild/packages/web/dist/_astro/index.CZveVo4H.css: the utilities layer (span 9791-12827) emits exactly five media queries, all literal — @media(min-width:40rem){, (48rem), (64rem), (80rem), (96rem). The substring 'breakpoint' appears ZERO times in the entire 17,532-byte file (Python `'breakpoint' in s` -> False), while --color-*, --radius-*, --shadow-*, --font-* all appear as real custom properties inside @layer theme{:root,:host{...}} at 4804-6254. Docs (https://tailwindcss.com/docs/theme) list --breakpoint-* in the namespace table but are silent on its emission mechanism — the compiled output settles it.

**Refuted:** layer_support: 'because these are real cascade layers, ANY unlayered rule beats ANY layered rule at ANY specificity per spec — so a consumer's plain CSS wins over all of Tailwind's theme/base/components/utilities output without !important or selector games'.

- Why wrong: True only for NORMAL declarations. css-cascade-5 §6.4.3: 'for normal rules the declaration whose cascade layer is last wins, and for important rules the declaration whose cascade layer is first wins.' Importance dominates layer order outright, so a layered !important beats unlayered normal CSS at any specificity — the exact inversion of the stated contract. Tailwind ships this in three ways: Preflight already emits an !important inside @layer base; `@import "tailwindcss" important;` marks EVERY utility !important; and the per-class `bg-red-500!` modifier does it one utility at a time. In any project using the important flag, the researcher's override entry point fails completely and silently.
- Correction: State the contract with its precondition: unlayered author CSS beats layered author CSS for normal declarations only. Before relying on it, grep the compiled output for !important inside a @layer span, and grep the entry CSS for `@import "tailwindcss" important`. If either hits, unlayered normal CSS loses and the only remaining lever is the consumer's own !important (which then beats the layered !important only if the consumer is ALSO unlayered — no: layered-first wins among importants, so the consumer must match or exceed via their own layer position). Doctrine point 3 needs this caveat or it inverts for these projects.
- Evidence: https://www.w3.org/TR/css-cascade-5/#layering §6.4.3. Live in ground truth: index.CZveVo4H.css offset 9745 carries `[hidden]:where(:not([hidden=until-found])){display:none!important}` INSIDE @layer base (base span 6266-9756; 6266<=9745<=9756 confirmed). A consumer's unlayered `[hidden]{display:block}` loses to it today. Important flag and ! modifier confirmed at https://tailwindcss.com/docs/styling-with-utility-classes ('use the important flag when importing Tailwind to mark all utilities as !important', emitting `@layer utilities{.flex{display:flex!important}}').
