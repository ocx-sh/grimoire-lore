# Correction ledger — round 2 vs round 1

Round 1 was research. Round 2 ran the builds and the browser. This is what
changed, worst first. `inverts-the-advice` means an agent following round 1
would have done the wrong thing.

Tally: inverts-the-advice × 2, material × 6, cosmetic × 2.

### 1. core principle #4 and #5's remedy clause; shadow-dom annex (the annex already carried the correct sentence, the core principle did not) — `inverts-the-advice`

**Round 1 said:** Core principle #4/#5 (CSS-CAS-03): "`!important` inside your own layer is a permanent lock... a layered `!important` then locks the consumer out permanently — so that workaround belongs outside the layer." Exception list offers "two legitimate uses, both OUTSIDE the layer"; holds_everywhere: true.

**Measurement says:** Across a shadow boundary the remedy runs backwards. All four combinations measured in Chromium 151: outer `!important` vs inner `!important` -> INNER wins (case 6a on the ::part path, case 6d on the :host path). Outer normal vs inner `!important` -> inner wins (6c). Outer `!important` vs inner normal -> outer wins (6b). A consumer cannot out-!important a component, inside or outside a layer; the only remaining channels are adoptedStyleSheets or a custom property the component already reads. The rule must say: never author `!important` in a component's :host/::part()/::slotted() rules, and never advise a consumer to reach for `!important` across the boundary — they already win at normal importance by Context and lose to an inner `!important` unconditionally.

**Evidence:** `r2/engine-cascade/probe.mjs` (session scratch) cases 6a-6d, results in out.json; Chromium 151.0.7922.34 via playwright 1.62.1; 45/45 main cases pass, 3 red controls fail as designed.

### 2. core principle #2 ("StyleX pads every rule with `:not(#\#)` chains"); css-in-js annex — `inverts-the-advice`

**Round 1 said:** css-in-js research: "StyleX: there is no CSS-file entrypoint for a downstream consumer at all by design ... overriding via external cascade is treated as the 'styles at a distance' anti-pattern StyleX exists to prevent" and "ties are resolved by StyleX's own deterministic last-write compile-time ordering (not CSS specificity or source order at all)."

**Measurement says:** Both refuted by build. With `useCSSLayers: true` StyleX emits `@layer priority1,priority2,priority3,priority4;` plus four populated layer blocks -- ordinary layered CSS -- and a bare unlayered consumer rule beat both an atomic class and a design token in real Chromium with zero `!important`. With the plugin default (`useCSSLayers: false`) ties are resolved by manufactured CSS specificity: `.x1dcnv9r:not(#\#):not(#\#){...}` = (2,1,0), escalating to (3,1,0) on a three-property example. That is ordinary cascade mechanics, not out-of-band compile-time ordering. The design's css-in-js annex already had this right ("That flag is the actionable instruction, not 'StyleX rejects the premise'"); the underlying research did not. Correct config key is `useCSSLayers` on the postcss-plugin, which maps internally onto the babel-plugin's `useLayers`.

**Evidence:** `r2/css-in-js/stylex/dist.css` (session scratch) and dist-nolayers.css; @stylexjs/postcss-plugin 0.19.0 src/plugin.js:35 (default false), bundler.js:69 (maps to useLayers); Chromium getComputedStyle verification.

### 3. core principle #3; astro annex's "DELETE the Vite/esbuild pitfall" note (right conclusion, wrong stated reason) — `material`

**Round 1 said:** Core principle #3 / astro annex: "a bare `@layer a, b;` ordering statement is dropped by production minifiers whenever block order already implies the same precedence" + "Write layer blocks in the intended precedence order physically" / "Physical block order is the durable form."

**Measurement says:** Both the trigger and the mitigation are wrong. esbuild 0.28.2 and cssnano 9.0.1 NEVER strip the statement -- not in a matching-order fixture, not in a contradicting-order one. lightningcss 1.33.0 and Parcel 2.16.4 strip it UNCONDITIONALLY, including when it contradicts block order, and compensate by physically REORDERING the @layer blocks away from source order to re-encode the statement's priority. So source block order is not what survives for lightningcss/Parcel (the tool rewrites it), and the statement is not dropped at all for esbuild/cssnano. All five outputs plus the original rendered rgb(255,0,0) in real Chromium: no minifier in the matrix broke the contract. The advice describes a hazard that does not exist in these tools.

**Evidence:** `r2/minifiers/A_layer/{input_contradiction.css,esbuild_contradiction.css,lightningcss_contradiction.css,cssnano_contradiction.css,parcel_contradiction/dist/index.css,render_check.mjs}` (session scratch)

### 4. astro annex; the Astro row of "What Your Framework Actually Emits"; the core brace-match instruction's rationale — `material`

**Round 1 said:** astro annex: "Astro injects TWO layers of its own: `@layer astro.images` ... A contract test that matches `@layer <yourname>` specifically false-positives on Astro's own image CSS in any project using `<Image>`."

**Measurement says:** The trigger is not `<Image>` usage. A production build with `<Image layout="constrained">` under default config emits NO `@layer astro.images` at all -- `image.responsiveStyles` defaults to false (node_modules/astro/dist/core/config/schemas/defaults.js:24), and the virtual module that emits the layer (assets/vite-plugin-assets.js:172) is imported only when that flag is true. It appears only with an explicit `image: { responsiveStyles: true }` AND a layout prop. Separately `@layer astro` (view transitions) requires an actual `transition:name`/`transition:animate` directive on an element -- `<ClientRouter/>` alone emits nothing, and it lands in its own inline <style> tag outside the bundled CSS. The "brace-match ANY @layer name" instruction is still correct advice; its stated justification was not reproducible as written.

**Evidence:** `r2/astro/dist/index.html` (session scratch) across five rebuilds (astro 7.2.9, vite 8.2.2, @astrojs/compiler-rs 0.4.0)

### 5. angular annex; shadow-dom annex's isolation framing — `material`

**Round 1 said:** angular research: "ViewEncapsulation.ShadowDom attaches a real shadowRoot instead -- no attribute rewriting; scoping is browser-enforced and the specificity question is moot since page-level selectors cannot cross the boundary without ::part/::slotted."

**Measurement says:** Not isolation from Angular's own CSS. ShadowDomRenderer's constructor calls `sharedStylesHost.addHost(shadowRoot)`, copying EVERY globally-registered component style into every ShadowDom component's shadow root. Reproduced live: the component's shadowRoot contained THREE <style> elements -- its own, plus verbatim copies of a ViewEncapsulation.None component's `.none-target{color:green}` (fully live inside the shadow tree) and an Emulated component's rule. Since Angular Material ships 91/91 components as None, all of Material's CSS is re-injected into every ShadowDom component. Shadow DOM blocks outside PAGE styles; it does not block Angular's own shared styles.

**Evidence:** @angular/platform-browser 22.1.4 fesm2022/_dom_renderer-chunk.mjs; live Chromium read against dist/probe/browser at http://localhost:48213 via `r2/angular/pw/probe.mjs` (session scratch)

### 6. the new forced-colors core clause the critique asked for — `material`

**Round 1 said:** critique's proposed forced-colors clause: "the UA replaces color, background-color, border-color, outline-color and box-shadow with system colours regardless of layer, specificity, origin or !important."

**Measurement says:** Mostly right, two errors. (a) box-shadow and background-image are SUPPRESSED to `none`, not recolored -- a design assuming they convert to system colours is wrong. ### 10. shadow-dom annex (design text already correct) — `cosmetic`

- Qwik breaks core principle #13's "read the built artifact". useStylesScoped$ scoping is a RUNTIME transform: the built JS chunk (dist/build/q-D4oYNW4I.js) contains the RAW unscoped author CSS string `.box { color: red; }`, so a gate reading the build sees nothing scoped and nothing layered. Real SSR output is `<div class="star-xl09ia-0 box">` with `<style q:style="xl09ia-0" hidden>.box.<emoji>xl09ia-0 { color: red; }</style>` -- an emoji-prefixed second class, (0,2,0). - Astro's scoping does not reach islands. data-astro-cid-* annotates only markup literally written in the .astro file; a React island's own render output carries none (the island div showed a bare CSS-Modules hash and no scope attribute). A consumer selector `[data-astro-cid-xxx] .thing` silently never matches anything an island renders. Custom-property inheritance DOES cross -- islands are light DOM. .../scratchpad/r2/surface-meta-and-embeds/astro-island/dist/index.html
- Stencil `scoped: true` is a third scoping mechanism the diagnosis table has no row for -- neither attribute-scoped nor shadow-isolated. The compiler appends `sc-<tag>-h` to the host and `sc-<tag>` to descendants and compounds it onto the authored selector (`.name` -> `.name.sc-my-component`, (0,2,0)), injected as one real global <style> in <head>. A consumer's later `.name{color:green}` LOST despite later source order. The class is a guessable tag-derived string -- reachable, but with no semver contract. .../scratchpad/r2/surface-component-libs/stencil-test
- In VitePress 1.6.4, wrapping your override in a layer makes you LOSE. VitePress 1.x's own reset (`body{margin:0;...}`) is entirely UNLAYERED -- grep for @layer in the 108KB built stylesheet returns exactly one match, the project's own -- so `@layer project{body{margin:4321px}}`, physically the last bytes in the file, loses to it. In 2.0.0-alpha.19 the reset IS layered (@layer __vitepress_base) and the project layer wins by first-appearance with no ordering statement needed. This flips between shipped major lines and is the concrete instance behind core principle #3's "audit the layer landscape first" caveat. .../r2/vue-vitepress/vitepress-site/docs/.vitepress/dist/assets/style.BMp5hpPC.css and vitepress-site-alpha/.../style.CUaQ0sWL.css
- Sass nesting and native CSS nesting have DIFFERENT specificity. `.card, .card-alt#legacy { .title{...} }` compiles under Sass to two rules at (0,2,0) and (1,2,0); the spec-accurate native desugaring is `:is(.card, .card-alt#legacy) .title` -- ONE specificity of (1,2,0) applied to both branches. Migrating hand-authored nesting from Sass to native `&` changes override difficulty for elements that never touch the id-qualified branch. No existing core statement covers this. .../r2/surface-preprocessors/f4_nesting/{sass-equivalent.css,native-nest.css}
- Less variable scoping is lazy/dynamic, not lexical -- a variable used before its later redeclaration in the same block resolves to the LATER value. Editing the bottom of a Less partial silently changes a value used at the top. Strictly more dangerous than Sass's compile-time-frozen-but-lexical model. .../r2/surface-preprocessors/f6_less/scoping.css
- @use/@forward (Sass) and @import (Less) order fixes @layer first-appearance order in the built CSS. Reordering two lines in an entry file, touching no @layer line at all, silently reverses which layer wins. Core principle #3's "write blocks in the intended precedence order physically" needs a preprocessor-aware footnote. .../r2/surface-preprocessors/f3_layer_order/{entry-forward-order.css,entry-use-order.css}
- "Global" does not mean "wins a tie" in Next.js. Three (0,1,0) rules for the same class -- a root-layout global, a mid-tree consumer sheet, and a leaf component's own import -- resolved to the LEAF (green), not the root-layout global (red) or the mid-tree sheet (blue). Position, not scope, decides a tie; a consumer relying on globals.css to win will be wrong.
- A Svelte class that exists only as a runtime-computed string is DELETED with zero trace in a minified production build -- not commented out, gone -- and the build exits 0 with only a non-failing css_unused_selector log line. Worked around with a standalone local Node 24.15.0; recorded as a failure because it is a real first-command blocker.
- iframe/widget embeds have no CSS override channel at all -- a separate Document in a nested browsing context, so no custom property, no layer and no selector crosses; only postMessage or a URL param. Its absence from a table titled "What Your Framework Actually Emits" reads as "no traps here." (Spec-cited, not build-reproduced.)
- Email HTML inverts core principle #6: inline styles there are not an escape hatch from the token contract, they ARE the contract, since most clients strip <style> and support no custom properties -- so layers, hooks, :where() and fallback chains are all moot. - shadcn is not a publisher/consumer CSS surface at all -- its CLI copies component source into the consumer's repo, so there is no versioned package whose stylesheet anyone overrides from outside; the retheming surface is a git diff on code you now own, and "ship tokens as a versioned public API" has no target. - swc has no CSS minifier at all -- `swc in.css -o out.css` exits clean and writes a 0-byte file. Any pipeline that assumes the JS toolchain also minifies CSS silently ships unminified or, worse, empty CSS.

## What the gate should require

Scale the gate to the surface. Three tiers, not five unconditional commands.

ALWAYS (any repo the rule loads in): run the production build; discover the CSS artifact with `find`, never a hardcoded dir, and fail when the glob matches nothing; brace-match ANY `@layer <name>` and assert the remainder is empty — never `grep -o`, never a context grep, since production CSS is one physical line (reconfirmed: `wc -l` = 1 on both Svelte/Vite bundles); run the literal check with `var()` fallbacks stripped first; run dark-parity WITH a `light-dark()` skip, because a `light-dark()` token has exactly one declaration site and the check as specified flags every token in such a theme.

CONDITIONAL — the browser driver: required if and only if the project actually asserts a cascade-layer or cross-context relationship. The justification is no longer self-cited. happy-dom 20.12.0 has zero `@layer` support, and a bare `@layer a, b;` statement corrupts the parse of every rule after it in the same sheet, so a false pass or false failure can come from an unrelated rule. jsdom 30.0.1 parses `@layer` into correct CSSOM but never applies any layered declaration — a single uncontested layered rule computes identically to no CSS at all. So the wording is absolute in one direction and conditional in the other: NO DOM emulator may ever test a layered cascade — not "with caution", not "works for simple cases" — but a project with no layer assertion to run needs no browser at all. Skip it for a plain-CSS project with one unlayered stylesheet; for a VS Code webview ≤1.103 where the contract is deliberately NOT to layer (running the assertion asserts the opposite of the contract); and for a shadow-DOM-only component, where the consumer wins by Context rather than by layers — though if you assert Context instead, that also needs a real engine.

CONDITIONAL — which artifact: "read the built artifact" needs per-framework routing or it passes with zero coverage. Angular compiles component `styles:` into the JS bundle, not `dist/**/*.css`. Qwik's built JS chunk holds the RAW unscoped author CSS, so for Qwik the gate must read rendered HTML. Astro's `@layer astro` (view transitions) lands inline in the page HTML, not the bundled asset, so a bundled-CSS-only check misses it — and `@layer astro.images` appears only when `image.responsiveStyles: true` is set, so do not warn about that collision otherwise. Svelte publishes uncompiled `.svelte` source. Also pin Node: `@angular/cli` 22.1.6 refuses Node 24.14.0 outright, so "just run ng build" is not a runnable instruction without a version note.

DROP from the gate's rationale: "a bare `@layer a, b;` statement is dropped by minifiers, so write blocks in physical precedence order." Measured across esbuild 0.28.2, lightningcss 1.33.0, cssnano 9.0.1 and Parcel 2.16.4 with a fixture whose statement order CONTRADICTS block order — esbuild and cssnano never touch the statement; lightningcss and Parcel delete it unconditionally but physically reorder the blocks to preserve its priority; all five outputs rendered identically to the source in real Chromium. No minifier in the matrix produced a silent breakage, and physical block order is not what makes any of them safe.

KEEP AND STRENGTHEN: "has been watched go red." Two independent round-2 harnesses shipped false results before their controls caught them — a shared-page Playwright harness that silently reused the first shadow case's CSS for eight later cases, and an animatability test that transitioned a natively-animatable derived property instead of the custom property itself. Both read as clean passes. Require at least one deliberately-inverted expectation and one dead-selector control in any cascade harness, and encode each rule's identity in the observed value (e.g. rgb(1,0,0)/rgb(2,0,0)) so a "pass" cannot come from reading a UA default.
