# Engine probe — Cascade, layers and Shadow DOM — measured in a real browser. One re-runnable script (48 cases + 3 red controls), each case `page.setContent()` into a FRESH page, then `getComputedStyle` for the decisive property. Colours are encoded as rgb(1,0,0)/rgb(2,0,0)/… so an observed value names which rule won. Run: `cd /tmp/claude-1000/-home-mherwig-dev-grimoire-lore/02df8e5f-0fb1-4b65-a7c7-c9e23829614b/scratchpad/r2/engine-cascade && node probe.mjs > out.json 2> summary.txt`. Result: main 45/45 PASS, forced-colors 3/3 PASS, red controls 3/3 FAIL as designed. Full machine-readable results at out.json alongside the script.

Measured, not derived. Round 1's critic flagged this whole area as
spec-derived with no browser and no component ever run; this is the answer.

- **Engine:** Chromium 151.0.7922.34 (headless, via playwright 1.62.1 / playwright-core 1.62.1, browser build chromium-1234 from ~/.cache/ms-playwright). Node v24.14.0. Single engine only — no Firefox or WebKit was installed, so every result below is Chromium-only evidence.
- **Script:** `probes/cascade-shadow-dom.mjs` (re-runnable, committed beside this file)

## Red controls

A harness that cannot go red proves nothing. These were made to fail first:

- RED-1-wrong-expectation: case 1 (unlayered beats layered) re-run with the INVERTED expectation `B`. Harness reported FAIL with observed=A. Proves a wrong expectation is reported, not smoothed over.
- RED-2-typo-selector-never-applies: `.aTYPO { color: rgb(1,0,0) }` against `<p class=a>`, expectation `A`. Harness reported FAIL with observed=rgb(0,0,0) — proves a 'pass' cannot come from the harness reading a stale or default value and calling it a match.
- RED-3-shadow-read-of-wrong-node: outer `x-el::part(p)` rule set, but the probe reads the HOST element instead of the part, expectation `B`. Harness reported FAIL with observed=rgb(0,0,0) — proves the shadow-DOM reads are actually resolving the node they claim to.
- REAL BUG THE CONTROLS CAUGHT (not a designed control, but the strongest evidence the harness goes red): my first run reported 34/68 with eight shadow-DOM cases failing. Cause: `page.setContent()` reuses the same window, so `customElements.define('x-el', …)` only took effect for the FIRST shadow case and every later one silently inherited the first case's shadow CSS. Fixed by opening a fresh page per case; the fix is a comment in probe.mjs. Any harness that shared one page would have published wrong shadow results with a straight face.

## Overturns round 1

- REFUTED — round 1's web-components report: ':root inside a shadow root reaches nested shadow trees'. Measured (case 5m): `:root` inside a shadow root matches NOTHING, not even the root's own child. Invented behaviour; must be cut before publication.
- REFUTED — round 1's annex line that cascade layers are 'a structural no-op' inside shadow DOM. Measured: layers work fully WITHIN one shadow tree (case 7a), and the annex's own adoptedStyleSheets override channel wins precisely because an injected unlayered sheet outranks the component's layered rules (case 8a). The claim deletes the one working selector-free remedy.
- CORRECTED — round 1's parenthetical that the `:host(.foo)` vs outer `.foo` comparison 'can't' happen. Measured (cases 5i/5j): an outer type selector (0,0,1) beats both `:host` (0,1,0) and `:host(.c)` (0,2,0) on the host element. The comparison happens on every themed component and specificity loses to Context. The published :host tuples are correct in isolation but cannot be used to reason about consumer-vs-component outcomes.
- CONFIRMED, and it inverts the design's remedy — the critic was right about importance across the boundary. Inner `!important` beats outer `!important` on both the part path (6a) and the host path (6d). The design's advice to reach for `!important` on the CONSUMER side is backwards: the consumer already wins at normal importance by Context, and a component-side `!important` is unbeatable by any consumer selector. The rule must say: never author `!important` inside a component's part/slotted/host rules.
- NUANCED — round 1 called `:host-context()` 'Chromium-only' and CSSWG-removed. Measured working in Chromium 151.0.7922.34 (case 5l). Removal from the spec has not reached the shipping engine, so an agent will see it work locally and ship a portability bug. The rule should frame it as 'works where you will test it, absent where your users are', not as broken.
- GAP CLOSED — the critic's 'missing framework: forced-colors' is now measured, not asserted. Under `forced-colors: active`, author `color`, `background-color` and `border-color` are replaced even with `!important` (system values rgb(0,0,0) / rgb(255,255,255)); `forced-color-adjust: none` is the only opt-out. No layer, specificity or importance construct in the design reaches above it.
- SCOPE CAVEAT on everything above: single engine. Chromium 151 only — Firefox and WebKit were not installed, so no cross-engine claim in this probe is evidence of anything beyond Chromium. `:host-context()` (5l) and `@scope` (case 9) are the two results most likely to differ elsewhere and should be published with that caveat.

Method note worth carrying into the rule: every case reads a computed COLOUR encoded as rgb(1,0,0)/rgb(2,0,0)/rgb(3,0,0), so the observed value names the winning rule directly rather than requiring a boolean. Cases asserting non-application expect rgb(0,0,0) (UA default) so a dead selector cannot look like a pass — that is what RED-2 verifies.

Two round-1 tuples I could NOT measure and am not confirming: the absolute specificity values of `::part()` (0,0,1) and `::slotted(.foo)` (0,1,1). Every selector capable of matching a shadow-internal part must itself contain `::part()`, so that contribution is common to both sides of any competition and cancels — it is unobservable through the cascade. What IS observable, and measured, is that the prefix in front of `::part()` accumulates normally (5o) and that ties resolve by source order (5p). If the rule publishes those tuples it should cite the spec and say so, not imply they were measured. Round 1's critic already established the round-1 `::part()` specificity quote was fabricated (it is the `::slotted()` sentence); nothing here rehabilitates it.

Not probed, out of scope for this slice: `@layer` survival through a production build (bundler question, not an engine one), `:has-slotted`, `exportparts` relaying, and the flat-tree custom-property redirection for slotted content that the critic listed as pitfall 6 — that last one is cheap and measurable and worth a follow-up case if another round happens.
