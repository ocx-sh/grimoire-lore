## Scoping mechanism

ViewEncapsulation.Emulated (default) is a build-time CSS shim (`ShadowCss`), not a browser mechanism. It (a) stamps every rendered element of a component instance with an empty-value attribute unique to that component class — content elements get `_ngcontent-ng-c<N>`, the host element gets `_nghost-ng-c<N>` — and (b) appends the matching attribute selector to every compound-selector segment in that component's `styles`. Proven directly from Angular's own compiler test suite: `.one.two > three {}` → `.one.two[contenta] > three[contenta] {}` (shadow_css_spec.ts) — attribute appended per segment including across descendant combinators, always a bare (never `:where()`-wrapped) attribute selector. `:host {}` → `[a-host] {}`; `:host(.x) {}` → `.x[a-host] {}` (host_and_host_context_spec.ts). `:host-context()` is deprecated in the browser spec but Angular's compiler still fully implements it (angular.dev, quoted verbatim). ViewEncapsulation.ShadowDom attaches a real `shadowRoot` instead — no attribute rewriting; scoping is browser-enforced and the specificity question is moot since page-level selectors cannot cross the boundary without `::part`/`::slotted` (Angular exposes no first-class author hook for either). ExperimentalIsolatedShadowDom is ShadowDom plus a hard guarantee against leakage in either direction. ViewEncapsulation.None disables scoping entirely — `styles` become indistinguishable from global CSS; this is exactly what every Angular Material component uses (`encapsulation: ViewEncapsulation.None`, confirmed in src/material/button/button.ts), sidestepping the attribute-shim specificity fight altogether — see divergence.

## Emitted specificity

`.foo { color: red }` inside an Emulated-encapsulation component compiles to `.foo[_ngcontent-ng-c137] { color: red }` — specificity (0,2,0): one class + one attribute, structurally identical to the Astro `.version[data-astro-cid-3oqgkrws]` case the core doctrine already names. A bare-tag rule (`h2 {}`) becomes `h2[_ngcontent-ng-c137]` at (0,1,1). Even a component's simplest host rule, `:host {}`, compiles to a bare attribute selector `[_nghost-ng-c137]` at (0,1,0) — already enough to beat an unscoped element selector. The scope attribute is NEVER wrapped in `:where()` — confirmed directly by the compiler's own test fixtures asserting unwrapped literal output (e.g. `.foo[contenta]:not( .bar) {…}`, `[a-host]:before {}`). `::ng-deep` does not zero out this specificity risk either: `:host > ::ng-deep .x {}` compiles to `[h] > .x {}` (ng_deep_spec.ts) — the ancestor keeps its own scope attribute; only the descendant loses its `[contenta]`, so the trap persists one level up.

## Cascade-layer support

Yes, cleanly, and provably at the shim level: `@layer utilities {section {display: flex;}}` compiles to `@layer utilities {section[contenta] {display:flex;}}` (packages/compiler/test/shadow_css/at_rules_spec.ts, dedicated `@layer` test block) — ShadowCss scopes selectors normally inside `@layer`, the same finding grimoire-indexer already proved for Astro. Two Angular-specific catches the annex must carry that the core's generic advice does not: (1) `@Component({ styles: […] })` content is not emitted to a static `.css` file by default — it compiles into a string embedded in the component's JS definition (`ɵɵdefineComponent({ styles: […] })`) and is injected at runtime per component type (only global `styleUrls`/`angular.json` `styles` entries land in `dist/**/*.css`), so "grep the compiled CSS" must target the built JS bundle or the component source, not a dist stylesheet — a test aimed at the wrong file silently passes with zero coverage [medium confidence: inferred from documented Ivy renderer architecture (DomRendererFactory2 / per-type style injection, angular.dev component-styles docs), not a `ng build` I ran myself this session — verify against a real build before publishing as certain]. (2) The default build (`@angular/build`, esbuild-based since v17) minifies the global bundle with esbuild's CSS transform, which is documented upstream to preserve `@layer` block structure rather than flatten it — stated from esbuild's general documented behavior, not an artifact inspected this session; mark medium confidence and pin with a real build, same discipline both source repos already apply with their own `style_contract.test.ts`-style checks.

## Consumer override entry point

For a hand-authored Angular component library, the override entrypoint is whatever the consuming app registers as GLOBAL CSS — its `angular.json` `styles` array (concatenated into the app's root CSS bundle) or any plain `<link>`/`styleUrls` outside a component's own encapsulation. There, source order is exactly as unreliable as core doctrine says: without `@layer`, bundle order doesn't save a consumer's unscoped `.foo` (0,1,0) from losing to the library's `.foo[_ngcontent-ng-c3]` (0,2,0). With the library wrapping its `styles` in `@layer`, the fix matches core point 3 exactly — the consumer's ordinary unlayered global CSS wins outright. For Angular Material, the entrypoint is different IN KIND: Material ships `ViewEncapsulation.None`, so there is no attribute-shim fight to layer away — the only sanctioned entrypoint is the Sass `overrides` mixin API (`mat.theme-overrides()`, `mat.card-overrides()`, …), and Material's docs explicitly forbid the plain-CSS path: "Angular strongly discourages, and does not directly support, overriding component CSS outside the theming APIs described above. Component DOM structure and CSS classes are considered private implementation details that may change at any time. CSS variables used by the Angular Material components should be defined through the `overrides` API instead of defined explicitly." (angular/components `guides/theming.md`, verbatim, read in full from raw `main`.)

## Token exposure

Contract file: `guides/theming.md` in the angular/components repo, plus each component's "Styling" doc tab listing its override-mixin token names — that mixin-argument surface IS Material's public contract, not the CSS custom property names underneath it (see below). Tiers, in Material's own terms: (1) one `mat.theme()` call — typically on `html {}` — takes a palette/typography/density map and emits a full system-token set as plain (non-`@property`) CSS custom properties prefixed `--mat-sys-*` (e.g. `--mat-sys-primary-container`, `--mat-sys-on-surface`, `--mat-sys-body-large`), consumed internally via ordinary `var()` (`background: var(--mat-sys-surface)`, quoted from docs). Color tokens are declared with the native `light-dark()` CSS function keyed to `color-scheme` — a genuinely native theme mechanism, not a data-attribute or class switch. (2) System tokens are overridden at any selector scope via `mat.theme-overrides((primary-container: #84ffff))` — itself Sass sugar that emits the same `--mat-sys-*` custom properties, not a new namespace. (3) Component tokens are overridden via a per-component mixin (`mat.card-overrides()`, `mat.button-overrides()`, …) with friendly, spell-checked keys (`elevated-container-color`, `title-text-size`, `elevated-container-shape`) that resolve internally to `--mat-<component>-*`/`--mdc-*` custom properties — names the docs explicitly say NOT to write by hand, because "the `overrides` API validates that the customized tokens are correctly spelled and can be used to ensure backwards compatibility if tokens are added, moved, or renamed in future versions" (verbatim). So the durable public API is the mixin's key vocabulary; the CSS custom property underneath is treated as Material's own implementation detail, free to be renamed.

## Theme switching

Two independent axes, both from `guides/theming.md`. (a) Light/dark: color tokens use `light-dark(lightVal, darkVal)`, gated by the native `color-scheme` property (`html { color-scheme: light dark; }` defers to the OS/user-agent preference). Docs are explicit that Material "does not automatically apply different styles or themes based on user preference media queries, such as `color-scheme`, `prefers-color-scheme` or `prefers-contrast`" beyond that — a manual toggle or `prefers-contrast` support is the app's own responsibility (custom media query, or reading a saved preference and re-invoking the mixins under a class). (b) Multiple/contextual themes: calling `mat.theme()` a second time scoped to a narrower selector (Material's own "Context-specific Themes" example: a cyan palette scoped to a delete-confirmation container class) simply re-declares the `--mat-sys-*` custom properties for that subtree — ordinary CSS custom-property cascading, no attribute-shim or ViewEncapsulation involvement at all, because Material's own components carry no scope attribute to begin with (`ViewEncapsulation.None`).

(1) Layer claim, for a hand-authored Angular library: build a component with `styles: ['@layer angular-components { .foo { color: red } }']`, then grep the DISTRIBUTED JS BUNDLE (not `dist/**/*.css` — see layer_support) for every one of the library's known `.classname[_ngcontent-` occurrences and fail if any appears outside an `@layer` span — the shim-level guarantee is already pinned by Angular's own at_rules_spec.ts, so the library's own test only needs to prove every component actually opted in. ## Where this contradicts the core doctrine

Two real contradictions, one important nuance. (A) contradicts point 3 (cascade layers are THE fix): for Angular Material — the dominant component library on this framework — there is no specificity fight to layer away in the first place, because Material ships `ViewEncapsulation.None` deliberately; layering only matters for hand-authored Angular components under the default Emulated encapsulation, not for Material-based styling, and an agent must not reach for `@layer` when the actual problem is a Material override. (B) contradicts point 4's implicit 'component-hook tier is consumer-writable via a bare `var()`': Material's own docs forbid declaring its CSS custom properties directly ('should be defined through the overrides API instead of defined explicitly') — the durable public API is the Sass mixin's argument names, with the CSS custom property layer treated as a renamable implementation detail Material reserves the right to change. Nuance, not contradiction: point 1 (untokenized value = defect) still holds for an app's OWN Emulated-encapsulation components — Material is the one documented exception inside this same ecosystem, not evidence the general rule is wrong.

## Traps

- Writing a consumer override against Material's internal classes (`.mat-mdc-button-base { color: red }`) — the docs call these 'private implementation details that may change at any time'; use `mat.button-overrides()` or a documented `--mat-sys-*`/component token instead.
- Assuming an Angular library's `@layer`-wrapped component styles show up in `dist/**/*.css` — by default they don't; `styles:` metadata compiles into the JS bundle and injects per component type at runtime, so a compiled-output grep aimed at the CSS file passes with zero real coverage.
- Trying to beat a component's `.foo[_ngcontent-ng-c3]` (0,2,0) from a consumer's global stylesheet with a plain `.foo`, then escalating to `::ng-deep` when it fails — the Angular team 'strongly discourages new use' of it and offers no successor selector; the fix is `@layer`, per core point 3, not a deeper combinator.
- Assuming `::ng-deep` fully unscopes a rule — `:host > ::ng-deep .x {}` compiles to `[h] > .x {}`: the ANCESTOR keeps its own `[_nghost-*]` attribute; only the descendant selector loses its scoping, and the leak is subtree-wide from that point on, which is exactly what triggered the deprecation.
- Treating `ViewEncapsulation.None` as a generic 'no scoping, write global CSS safely' escape hatch without checking whether it's Material's deliberate, tokens-only usage of it versus a hand-authored app component, where `None` means genuine first-class collision risk with everything else on the page.
- Setting a Material CSS custom property directly (`:root { --mat-sys-primary: red }`) the way a hand-rolled component-hook tier would invite — Material's own docs explicitly ask you not to; the mixin exists precisely because the underlying variable name is not guaranteed stable, only the mixin's argument name is.
- Reaching for `mat.define-theme`/`define-light-theme`/`define-dark-theme` (M2) on Angular ≥19 — legacy API whose own docs redirect elsewhere; `mat.theme()` (M3) is the only actively maintained path as of 2026.

### Unverifiable

- Layer ORDER for a hand-authored Angular library that wraps its component styles in `@layer`. Because those blocks are `head.appendChild`-ed at runtime in component-first-render order, the layer ordering a browser computes is determined by which component happens to render first, not by authoring order. Unlayered consumer CSS still wins (that part of core point 3 is safe — unlayered beats layered regardless of order), but a library with two or more layers, or a consumer who also uses layers, gets nondeterministic precedence. I did not build an app to demonstrate it, and the findings do not address it at all. Confidence: medium that it is a real hazard; it needs a real `ng build` + browser check before it goes in a rule.
- Whether `provideCssVarNamespacing()` breaks Angular Material. Material's component styles read `var(--mat-button-filled-container-color)` and are shipped partially-compiled (`ngDeclareComponent`, 91 call sites), so the CONSUMING app's linker applies `namespaceCssVariables` to them, while `mat.theme()`'s Sass output is a global stylesheet and is not rewritten. That reads like a guaranteed mismatch, but I did not build an app with namespacing enabled to prove it. Flag it as a live question, not a finding.
- How `--global--` interacts with SSR/`platform-server` hydration and with the `@angular/build` Sass pipeline (does Sass see the `--global--` prefix, or the compiler?). Not checked.
- The findings' claim that `mat.theme()` "typically on `html {}`" is the only sanctioned entrypoint for Material. The docs do show `html`, and `mat.theme()` scoped to a narrower selector for contextual themes, but I did not verify that no other sanctioned override path exists (e.g. `mat.system-classes()`, `mat.strong-focus-indicators-theme()`, which the guide documents separately).

### On the annex call

Agree the annex is warranted — but roughly half of the researcher's stated justification does not hold up, and the strongest reason for the annex is one they never found.

Their three rationales: (1) "grep dist/**/*.css finds nothing" — real and confirmed from source, but their own replacement test is broken (it greps for `_ngcontent-ng-c\d+`, which no build artifact ever contains). (2) `::ng-deep` partial-unscoping — real, confirmed verbatim from ng_deep_spec.ts, and genuinely an Angular-only trap with a wrong-output consequence. (3) Material's mixin-not-variable contract — real, and the version inversion at v19 makes it sharper than they present it.

What actually earns the annex is the thing they missed: since Angular 22.1.0 the compiler rewrites every custom property in component styles to `--%NS%<name>` unless authored `--global--<name>`. That is a direct, framework-specific inversion of core doctrine point 1 — the tokens ARE the public API, and on Angular the token name you write is not the token name that ships. An agent applying the Astro-derived core to an Angular repo gets it silently wrong, and no other framework in the set behaves this way. Add the runtime `head.appendChild` injection order (which makes core point 2 true on Angular for a second reason, under every encapsulation mode including Material's `None`) and there is more genuinely Angular-specific trap surface than the core file can carry.

So: annex yes, but do not ship this draft. The `_ngcontent-ng-c\d+` test regex, the `--mat-(sys|mdc)-` anti-pattern regex, and the divergence-(A) claim that "there is no fight to layer away" are all wrong in ways that would actively mislead — and per the brief's own framing, a wrong test that passes with zero coverage is exactly the defect class this rule set exists to prevent.

Not sound. The selector-shape and specificity core of the findings is accurate and I reproduced all of it — but the two things a published rule would actually make an agent DO (the contract tests) are both broken, one doctrine-level divergence is argued backwards, and the single most important Angular-specific token fact is absent.
