- **Versions checked:** Next.js 16.3.3 (docs dated 2026-07-15 / 2026-08-25, checked live); css-modules spec (unversioned community spec, github.com/css-modules/css-modules, checked 2026-08-30); css-loader (webpack path, Next.js's default bundler pre-Turbopack) and Lightning CSS (Turbopack path, stable since Next.js 15.3/16) both checked for CSS Modules + @layer pass-through behavior.
- **Review verdict:** `needs-correction`
- **Annex recommended:** True — An agent holding only the core's point-2 language ('scoped styles compile to an attribute selector that outranks a consumer's plain class') would, for CSS Modules, reasonably conclude the opposite of the truth: that a consumer's plain `.button{}` simply wins by specificity and layers are therefore unnecessary here. Both halves of that inference are wrong — specificity is equal at (0,1,0), and Next.js's own docs admit the fallback tiebreaker (source order) is unstable across dev/prod and bundler mode. Three more framework-specific facts an agent would otherwise get wrong or omit entirely: (a) nothing auto-wraps CSS Modules output in a layer — it's an open, unresolved spec question, so 'we use CSS Modules' does not by itself satisfy the layering doctrine; (b) Turbopack only accepts the function form of `:global(...)`; (c) a published library's hashed class names are not a stable override surface at all, unlike Vue/Astro's per-component scope attribute, so the component-hook tier (custom properties) is the ONLY viable public surface, not an optional nicety.

## Scoping mechanism

CSS Modules scope by unique-identifier hashing, not by an attribute selector. Next.js's documented default output shape is `header_header__[hash]` (e.g. a `.blog{}` rule in `blog.module.css` compiles to `.blog_blog__aB3xZ{}`). The emitted rule is a bare single class selector — no wrapping attribute, no ID, no extra ancestor. `:global(.foo)` opts a selector out of hashing; Turbopack supports ONLY the function form `:global(...)`, not the bare block form `:global { }` that webpack/css-loader accepts — a real cross-bundler pitfall. `composes: x from './other.module.css'` concatenates another module's hashed class onto the className string at the JS call site; it does not raise any individual rule's specificity or establish precedence between them — each composed class remains its own independent (0,1,0) rule.

## Emitted specificity

(0,1,0) — exactly one class selector, identical to hand-written `.foo{}`. This is UNCHANGED from a plain class and is NOT inflated the way Vue's `[data-v-xxxx]` or Astro's `[data-astro-cid-xxx]` attribute-selector scoping inflates it to (0,2,0). There is no attribute-selector scope hook to speak of, so the ":where() wrapping" question is moot — CSS Modules never adds a second simple selector in the first place.

## Cascade-layer support

`@layer` is standard CSS and both Next.js CSS pipelines (webpack+css-loader/PostCSS, and Turbopack+Lightning CSS) pass it through untouched — you CAN write `@layer components { .foo {...} }` inside a `.module.css` file and it compiles correctly in both. BUT nothing auto-wraps CSS Modules output into a layer by default: the css-modules spec repo has an open, unresolved proposal for this (css-modules/css-modules#401, "Define how CSS modules interacts with @layer" — no resolution, no linked PR). To get every framework-authored style block into one layer across a whole component tree you must either hand-write `@layer <name> { … }` in every `.module.css` file, or add a PostCSS plugin (e.g. `postcss-assign-layer`, whose documented default targets `**/*.module.css` and wraps matches into a named layer) to Next.js's `postcss.config`. Whether Next's build-time CSS chunking/minification (`cssChunking`, see below) can split or otherwise mangle an `@layer` block during merge is not verified anywhere I found — mark that specific sub-claim low confidence and test it against real compiled output before publishing it as certain.

## Consumer override entry point

Two distinct cases: (1) Inside one Next.js app consuming its own CSS Modules, Next.js's own docs (fetched 2026-08-25, v16.3.3) state plainly: "CSS ordering can behave differently in development, always ensure to check the build (`next build`) to verify the final CSS order" — order is explicitly NOT guaranteed stable across dev vs. prod. It also depends on `experimental.cssChunking`: `true` (default, both bundlers) merges/reorders CSS by import graph, not textual import order; `'strict'` (webpack-only) preserves import order at the cost of more chunks; `false` (webpack-only) disables merging; `'graph'` (Turbopack-only) optimizes chunk grouping by a cost heuristic — none of these give a source-order guarantee an unlayered consumer file can lean on. Since specificity is already equal at (0,1,0), order is the ONLY tiebreaker absent layers — and Next.js documents that tiebreaker as unstable. (2) For a consumer of a PUBLISHED React component library built with CSS Modules: the hashed class name is not a stable public selector at all — by default the hash is derived from file path plus content and changes on the library's own rebuilds, so a consumer selector like `.Button_button__a1B2c{}` silently breaks on the next patch release. The only durable entrypoints such a consumer actually has are (a) CSS custom properties the library author deliberately exposes and reads via `var(--token, fallback)` inside its `.module.css` files, and (b) whatever JS-level `className`/`style` prop API the library chooses to expose — not the CSS cascade at all.

## Token exposure

No framework-native token-tier system exists in CSS Modules or Next.js (unlike Tailwind's `@theme`) — tiering is 100% author convention, declared as custom properties in the single unlayered global stylesheet (Next's own "Global CSS" guidance: import once, in the root layout, for "truly global CSS") and consumed with `var()` inside `.module.css` files. `next/font`'s `variable` option is the same pattern applied to fonts, confirmed from official docs: `Inter({ variable: '--font-inter' })` declares a literal CSS custom property, exposed by applying `inter.variable` as a className on whatever element you choose (commonly `<html>` or `<body>`); descendant CSS then reads `var(--font-inter)`. The plain `className` option instead applies a single non-custom-property class Next.js generates internally — that path exposes nothing overridable at all.

## Theme switching

No mechanism specific to CSS Modules or Next.js — same generic convention as any CSS codebase: flip custom-property values under a `[data-theme]`/`.dark` selector or `prefers-color-scheme` media query in the one global unlayered stylesheet. `.module.css` files only ever consume `var(...)`, never redeclare theme values. This is discoverable-by-reading-the-code territory (per the brief's "architecture that is discoverable does not belong in a trap-only rule") and needs no framework-specific annex content.

## Testability

Grep the actual `next build` output, not source: `next build && grep -rL '@layer' .next/static/css/*.css` flags any emitted stylesheet with no layer wrapper at all (fails if a file has zero `@layer` occurrences). Tighter: parse each emitted file with a real CSS parser (e.g. `postcss` in a small Node script) and assert every rule whose selector matches the project's CSS-Modules hash pattern (e.g. `/^\.[A-Za-z0-9_-]+_[A-Za-z0-9_-]+__[A-Za-z0-9]+/`) is nested inside the chosen `@layer` name's block, not at the stylesheet's top level — this is the only way to catch a minifier or `cssChunking: 'graph'`'s merge step splitting a layer block, a scenario I could not confirm does or doesn't happen (flagged low confidence above) and which a compiled-output snapshot test settles empirically. Also pin `cssChunking` explicitly in `next.config.js` rather than leaving it on the implicit default — a test asserting the config value pins the chunking strategy protects the layer-based guarantee from silently drifting if Next.js's default heuristic changes between versions.

## Where this contradicts the core doctrine

Point 2 of the five doctrine points does not hold for CSS Modules: there is no specificity inflation. CSS Modules scoping is pure identifier-hashing that emits an ordinary single class selector at (0,1,0), identical to a hand-written class — there is no attribute-selector scope hook comparable to Vue's `[data-v-xxxx]` or Astro's `[data-astro-cid-xxx]`. This changes the PREMISE of point 3 but not its CONCLUSION: because specificity is equal rather than consumer-favoring, and because Next.js documents source order itself as unstable (dev vs. prod, webpack vs. Turbopack, and dependent on the `cssChunking` setting), layers are, if anything, MORE necessary for React+CSS Modules+Next.js than for the attribute-scoped frameworks the doctrine was drawn from — there is no accidental specificity margin to fall back on if layering is skipped. A second, sharper divergence concerns point 4 (tiering) as applied to a published library: because the hashed class name is not stable across rebuilds, the component-hook tier is not merely a nice-to-have public surface for such a library — for CSS Modules it is the ONLY override surface that exists at all, since the cascade itself offers no addressable selector a consumer can safely pin to.

## Traps

- Assuming a CSS-Modules-hashed class beats a consumer's plain `.foo{}` on specificity the way Vue/Astro scoped attribute selectors do — both are (0,1,0); without layers the winner is whichever rule loads last, and Next.js's own docs admit that load order differs between dev and prod builds.
- Treating a component library's hashed class name (`.Button_button__a1B2c`) as a stable override target — the hash is derived from file path + content by default and changes on the library's own rebuilds, breaking any consumer selector pinned to it.
- Writing the bare `:global { ... }` block form inside a Turbopack project — only the function form `:global(...)` is supported under Turbopack; the block form is a webpack/css-loader-only affordance.
- Relying on `cssChunking`'s default (`true`) to preserve textual import order — it merges/reorders by import graph, not by source order; only `'strict'` (webpack-only) preserves literal import order, at the cost of more requests.
- Expecting CSS Modules or Next.js to auto-wrap authored styles in a cascade layer — nothing does this by default; it is an open, unresolved proposal in the css-modules spec repo, so omitting a hand-written `@layer` or a plugin like `postcss-assign-layer` means 'use CSS Modules' alone does NOT satisfy the layering doctrine point.
- Declaring a design token inside a `.module.css` file instead of the single global stylesheet — a module file is its own independently-hashed, independently-chunkable CSS asset, with no guarantee it loads before (or even alongside) the components that need the token.
- Relying on `composes` to raise a rule's priority — it only appends another class to the className string in JS; it never increases any individual selector's specificity or establishes cascade precedence between the composed rules.

### On the annex call

Agree the annex is warranted, but the rationale as written must be rebuilt — roughly half of what it leans on is refuted above, and shipping it as-is would publish a wrong output shape, a wrong hash-churn mechanism, and a contract test that globs an empty directory.

The annex earns its place on four facts an agent cannot derive from the core, all reproduced today against Next.js 16.3.3:

1. Doctrine point 2 is FALSE here. Specificity is (0,1,0), not inflated. An agent holding only the core's "scoped styles compile to an attribute selector that outranks a consumer's plain class" would conclude a consumer's `.button{}` wins on specificity and layers are unnecessary. This is the researcher's central call and it is correct.

2. The real trap is not "order is unstable" but "order is deterministic and against you": the root-layout global stylesheet is emitted as the FIRST `<link>`, the module chunk SECOND, so the theme file loses every (0,1,0) tie in every production build. Reproduced. This is a sharper, more actionable trap than the one the findings state, and it closes the "just reorder the imports" escape an agent would otherwise try.

3. Two opposite `:global` build errors, one per bundler, with no form that satisfies both for a fully-global selector. Pure build-breakers, undiscoverable by reading the code, and the findings name only one of the two.

4. The output path and class shape are bundler-dependent, which is exactly what any layer-contract test has to grep. Get this wrong and the test is inert.

Cut from the annex: "the hash changes on the library's own rebuilds" (false), "pin cssChunking" as protection (unavailable on the default bundler), and the theme_switching section (the researcher correctly self-identifies it as discoverable-by-reading — hold that line and delete it).

One structural note for the core file, not the annex: this framework inverts the core's premise while keeping its conclusion. If the core states point 2 as "scoped styles compile to an attribute selector at (0,2,0)", every CSS-Modules reader is being told something false before they reach the index pointer. The core should state the conclusion bundler-agnostically — "a consumer's plain selector cannot be relied on to win; only layers and custom properties are durable" — and let each annex supply the mechanism.

Not sound. Seven refutations, four of them load-bearing enough to invert or void guidance: the default emitted class shape, the hash-derivation mechanism, the contract test's output path, and the composes-precedence claim.
