# VS Code Webviews / editor-embedded surfaces (extension-hosted webview content)

Round-1 researcher artifact, vscode-webview. Adversarially reviewed; the
**Review verdict** section below overrides the body wherever they disagree.

- **Versions checked:** VS Code stable Webview API guide as current 2026-08-30 (code.visualstudio.com/api/extension-guides/webview, no version pin — API is stable since ~1.40); @vscode/webview-ui-toolkit: archived/deprecated 2025-01-06 (github.com/microsoft/vscode-webview-ui-toolkit issue #561, repo now archived); @vscode-elements/elements 2.5.1 (pinned in /home/mherwig/dev/grimoire-vscode/package.json, the maintained community successor); light-high-contrast body class added per microsoft/vscode issue #148057 (shipped, now documented behavior).
- **Review verdict:** `unsound`
- **Annex recommended:** True — An agent following only the five core points would write several concretely wrong things here: it would set --vscode-* custom properties on :root/body expecting to theme the extension (silent no-op — the host's inline style on <html> is recomputed and wins every repaint); it would wrap the extension's CSS in @layer to 'beat' a consumer file that structurally cannot exist under this CSP; it would reach for @vscode/webview-ui-toolkit, a dead package; it would guard only .vscode-light/.vscode-dark and ship a broken light-high-contrast theme; and it would write a descendant selector into a Shadow-DOM component expecting a specificity contest rather than a hard reachability wall. None of these are covered by generic 'tokens are a public API' + 'cascade layers fix specificity' advice — several actively point the agent in the wrong direction unless corrected.

## Scoping mechanism

No compile-time scoping exists for the extension's own webview CSS — it is one plain, unscoped global stylesheet per webview view (confirmed: /home/mherwig/dev/grimoire-vscode/dist/webview/{sidebar,settings,details}.css are ordinary flat selectors, e.g. `.sidebar-tabs .tab.active`, no hashed attribute or class). Scoping only appears if the webview embeds Shadow-DOM web components (e.g. @vscode-elements/elements, Lit-based): each component renders inside a native `shadow-root`, which is a hard DOM boundary, not a specificity mechanism — outer page selectors (any specificity, any @layer) cannot match elements inside it at all. Only inherited CSS custom properties and an author-exposed `::part()` cross that boundary.

## Emitted specificity

Two different things, neither a "scope-hook selector" in the framework-annex sense: (1) VS Code injects every `--vscode-*` theme token as an inline `style` attribute directly on the webview's `<html>` element, e.g. `<html style="--vscode-button-background:#0078d4; --vscode-editor-foreground:#cccccc; ...">` — inline style beats any non-`!important` author-stylesheet rule for that element/property regardless of selector specificity or @layer order (confirmed via VS Code webview devtools inspection as documented at eliostruyf.com and the extension-guides/webview page). (2) Inside a vscode-elements shadow root, internals use plain low-specificity selectors like `:host`, `.base`, `.base:after` (~(0,1,0)–(0,2,0)) — irrelevant to an outer author because the shadow boundary makes them unreachable regardless of specificity (verified against source: github.com/vscode-elements/elements src/vscode-button/vscode-button.styles.ts, `.base { background-color: var(--vscode-button-background, #0078d4); ... }`). No `:where()`-wrapped scope hook exists in this framework — there is nothing analogous to wrap.

## Cascade-layer support

Webviews render in an Electron/Chromium engine that fully supports `@layer` (modern Chromium), so it works mechanically inside the extension's own stylesheet. But it solves nothing here: `@layer` only reorders declarations from different *author stylesheets* against each other, and a VS Code webview structurally has only one author stylesheet (the extension's own) — there is no second, downstream "consumer" stylesheet to out-rank, so the core doctrine's "ship framework CSS in a layer so an unlayered consumer wins" pattern has no target to apply to. (@layer remains fine for ordinary organization of the extension's own multiple CSS files against each other — that's unrelated to the host-token problem.)

## Consumer override entry point

None exists, and the CSP forbids one structurally: the extension's `Content-Security-Policy` meta tag scopes `style-src` to `${webview.cspSource}` only (confirmed in /home/mherwig/dev/grimoire-vscode/src/views/html.ts: `style-src ${webview.cspSource}; ... script-src 'nonce-${scriptNonce}'`) — no external host, no `'unsafe-inline'`, so no third party can ever inject a competing stylesheet into the webview the way a downstream npm consumer injects one into a component library's page. The only real "entrypoint" runs the other direction: the HOST injects into the extension via the `<html>` inline `style` (theme tokens, live-recomputed on every theme change) plus `body` classes `vscode-light` / `vscode-dark` / `vscode-high-contrast` (+`vscode-high-contrast-light` alongside `vscode-high-contrast` for the light-HC theme) and `data-vscode-theme-id` / `data-vscode-theme-kind` / `data-vscode-theme-name` attributes as escape hatches for theme-specific CSS.

## Token exposure

Consume-only, no contract file to author. Read every appearance value through `var(--vscode-<theme-color-id-with-dots-as-dashes>, <hardcoded fallback>)` — e.g. `var(--vscode-editor-foreground)`, `var(--vscode-font-family)`, `var(--vscode-charts-blue, #3794ff)`, `var(--vscode-descriptionForeground)`. The vocabulary is VS Code's own Theme Color reference (code.visualstudio.com/api/references/theme-color), not something the extension declares, versions, or owns; grimoire-vscode's entire webview CSS (src/webview/**/*.css, confirmed by full-file read) uses zero un-tokened color literals outside `var(...)` fallback position. The one genuine "hook" tier an extension author DOES own is third-party embedded components' own internal knobs — e.g. vscode-elements' `--vsc-*`-namespaced properties (`--vsc-border-left-radius`, `--vsc-divider-display`, `--vsc-base-additional-right-padding`, confirmed in vscode-elements/elements source) which are NOT VS Code host tokens but library-internal structural properties settable by the extension author, distinct from the read-only `--vscode-*` color/font tier.

## Theme switching

Fully host-driven and automatic: on every VS Code theme change, the host recomputes the entire inline-style token set on `<html>`, swaps the `vscode-light`/`vscode-dark`/`vscode-high-contrast[-light]` body classes, and updates the `data-vscode-theme-*` attributes — live, no webview reload, no extension code involved. The extension does nothing to "switch"; it just keeps reading `var()`. `prefers-color-scheme` is not the mechanism (VS Code's own theme choice may or may not track the OS, but the webview never queries the media feature for this — it reads the injected classes/vars).

## Testability

Same "test the compiled artifact" discipline as the two doctrine repos, different predicate (no `@layer` to grep for): `grep -oE '#[0-9a-fA-F]{3,8}|rgba?\([^)]+\)' dist/webview/*.css | grep -v 'var(--vscode-'` — a bare hardcoded color found anywhere except inside a `var(--vscode-*, <fallback>)` fallback slot is a regression. Pair it with a CSP regression guard: `grep "style-src" src/views/html.ts` must never contain `'unsafe-inline'`. Both are one-line greps runnable in CI against the built extension, mirroring grimoire-indexer/ocx-catalog's "grep the compiled output" contract test.

## Where this contradicts the core doctrine

Every one of the five doctrine points either inverts or loses its target in this framework: (1) 'tokens are a public API you expose' is backwards — the extension is the consumer of a host-owned vocabulary (VS Code's Theme Color reference), not the publisher; it has no downstream retheming audience, and the CSP (style-src scoped to webview.cspSource, no unsafe-inline) structurally forbids one from ever existing. (2) 'scoped component styles compile to a higher-specificity selector that beats a consumer's plain class' doesn't arise for the extension's own CSS at all (it's one unscoped global stylesheet the author fully controls, no compiler-inserted scoping exists) — it only reappears, in a STRONGER form the core doctrine doesn't describe, when Shadow-DOM web components are embedded: there it isn't a specificity fight the outer author can lose, it's a hard DOM boundary the outer author can't reach at all. (3) 'the fix is cascade layers' has no entrypoint to fix — there is no second author stylesheet in a webview to out-rank, so @layer is inert against the actual override problem here (it remains ordinary useful CSS organization, nothing more). (4) primitive/semantic/component-hook tiering, authored by the shipping package, doesn't apply — the primitive+semantic tiers are entirely VS Code's, computed and injected read-only; the only tier an extension genuinely authors is a narrower one, structural knobs on embedded third-party components (e.g. vscode-elements' --vsc-* properties), not a three-tier system of its own. (5) 'grep compiled output for rules outside the layer' doesn't transfer literally (no layer to check) but its SPIRIT — pin the contract with a test against compiled artifacts — transfers directly as a grep for hardcoded color literals outside a var(--vscode-*, fallback) position, so this is the one point that survives structurally even though its concrete predicate changes completely.

## Traps

- Declaring `:root { --vscode-button-background: ... }` (or setting it on `body`) to 'theme' a component silently does nothing on next paint — VS Code's own inline `style` on `<html>` is recomputed on every theme change and outranks that rule, so the override appears to work once and then vanishes or never took effect, with no console error.
- Importing `@vscode/webview-ui-toolkit` — the package and its GitHub repo were deprecated/archived 2025-01-06; new code should target `@vscode-elements/elements` (or hand-rolled elements reading `--vscode-*` directly) instead.
- Guarding only `.vscode-light` / `.vscode-dark` for theme-specific CSS misses the light-high-contrast theme, which carries BOTH `.vscode-high-contrast` and `.vscode-high-contrast-light` — a selector list built from just the first two classes silently renders the wrong (dark-HC) styling under light-HC.
- Adding an `@layer` around the extension's own CSS 'to make it win' is a wasted no-op here — there is no second author stylesheet in a webview to out-rank (CSP's `style-src ${webview.cspSource}` forbids one existing at all), so the core doctrine's layer fix has nothing to apply to.
- Loading a Google Fonts `<link>` or any CDN stylesheet to style webview content is silently blocked by the CSP's `style-src` allowlist — no visible error unless the webview devtools console is opened; the fix is to bundle the font/CSS into the extension and serve it via `webview.asWebviewUri`, or read `--vscode-font-family` / `--vscode-editor-font-family` instead of picking a font at all.
- Writing a plain descendant selector to reach inside a Shadow-DOM component (e.g. guessing `vscode-button .base { ... }` or an unexposed `::part()` name) fails with zero specificity fight and zero console warning — the shadow root simply isn't reachable; only inherited custom properties and library-exposed `::part()` names cross the boundary.
- Hardcoding a hex color 'just for this one row' because it looks close enough to the current theme is a defect that surfaces only when the user switches to a different (or high-contrast) theme — exactly the same untokened-value trap as the doctrine's repos, just triggered by a theme switch instead of a downstream retheme.

- Evidence: microsoft/vscode pre/index.html:897-901 — `body.dataset.vscodeThemeKind = initData.activeTheme;` / `/** @deprecated data-vscode-theme-name will be removed, use data-vscode-theme-id instead */` / `body.dataset.vscodeThemeName = initData.themeLabel || '';` / `body.dataset.vscodeThemeId = initData.themeId || '';`. WebFetch of https://code.visualstudio.com/api/extension-guides/webview Theming section names only `data-vscode-theme-id`.

### Confirmed

- CSP shape in grimoire-vscode is exactly as quoted, plus more than quoted: `default-src 'none'; style-src ${webview.cspSource}; font-src ${webview.cspSource}; img-src ${webview.cspSource} data:; script-src 'nonce-${scriptNonce}';` — /home/mherwig/dev/grimoire-vscode/src/views/html.ts:27 (single line, not 'lines ~26-28'). No 'unsafe-inline', no external host.
- The extension's own webview CSS is one flat, unscoped global stylesheet per view with no compiler-inserted hash attribute or scope class — verified in /home/mherwig/dev/grimoire-vscode/dist/webview/sidebar.css:1-30 (`.monogram`, `.broken-image.codicon`, `.avatar-0`) and by `grep -c '@layer' dist/webview/*.css` → 0.
- VS Code injects theme colours as `--vscode-<id-with-dots-as-dashes>` custom properties onto the webview's `<html>` element and recomputes them live on every theme change with no reload — microsoft/vscode pre/index.html:512-529 (`document.documentElement.style` setProperty loop) and :924-940 (`hostMessaging.onMessage('styles', …)` → `applyStyles`). Mechanism precision the researcher got observationally right but described imprecisely: it is programmatic CSSOM (`style.setProperty`), which is why a `style-src` CSP without `'unsafe-inline'` does not block it.
- The light-high-contrast theme carries BOTH `vscode-high-contrast-light` and `vscode-high-contrast` on body — CONFIRMED against source, pre/index.html:492-495: `body.classList.add(initData.activeTheme); if (initData.activeTheme === 'vscode-high-contrast-light') { /* backwards compatibility */ body.classList.add('vscode-high-contrast'); }`. Note the researcher's cited evidence is partly wrong: the official docs page does NOT mention `vscode-high-contrast-light` (verified by fetch), so this must be cited to source, not to docs.
- A native shadow root is a hard reachability boundary for plain outer descendant selectors — an outer `vscode-button .base { … }` never matches, at any specificity, in any layer. Correct as stated (though the list of what crosses is incomplete: `::slotted()` and inherited properties generally also cross — `::slotted(*)` is defined in vscode-button.styles.ts:132).
- @vscode-elements/elements is pinned at exactly 2.5.1 in devDependencies, and grimoire-vscode is at extension v0.3.2 with `engines.vscode: ^1.96.0` — /home/mherwig/dev/grimoire-vscode/package.json:365, :5, :9. Component imports confirmed in src/webview/{sidebar,settings,details}/main.ts.
- vscode-elements exposes its own `--vsc-*`-namespaced structural knobs, distinct from the read-only `--vscode-*` host tier: `--vsc-border-left-radius`, `--vsc-border-right-radius`, `--vsc-border-left-width`, `--vsc-border-right-width`, `--vsc-divider-display`, `--vsc-base-additional-right-padding`, `--vsc-base-after-content` — all extracted from https://raw.githubusercontent.com/vscode-elements/elements/main/src/vscode-button/vscode-button.styles.ts. Components read host tokens directly inside the shadow root, e.g. `.base { background-color: var(--vscode-button-background, #0078d4); }` (line 21-23).
- Theme switching is entirely host-driven with no extension code — pre/index.html:924-940 shows the 'styles' message handler bumping `styleVersion` and re-running `applyStyles`, and :1069/:1116 re-apply on frame swap. `prefers-color-scheme` is indeed not the mechanism.

### Unverifiable

- Whether a strict `style-src ${webview.cspSource}` (no `'unsafe-inline'`, no hash, no nonce) actually permits VS Code's own injected inline `<style id="_defaultStyles">` element. The style element is serialized into the document string (pre/index.html:911, `newDocument.documentElement.outerHTML`) and therefore parsed under the extension's meta CSP, which on paper would block an inline style element. microsoft/vscode#261430 reports the defaults visibly applying, which suggests they do get through, but that reporter's CSP is unstated and I could not run a webview. This does not weaken the @layer refutation — codicon.css alone proves a second author stylesheet exists — but the annex should not assert either way without a live devtools check.
- Whether esbuild preserves `@layer` through the extension's bundling step. The researcher asserted '@layer works mechanically inside the extension's own stylesheet' without confirming the build. I could not run the probe (node_modules is not installed in grimoire-vscode; the cached bun esbuild binaries crashed). esbuild has documented @layer support since 0.17, and the project pins ^0.28.1, so this is likely fine — but it is asserted, not verified, in both the findings and here.
- 'No third party can ever inject a competing stylesheet into the webview.' Plausible from the CSP, but I could not enumerate every host-side injection path (workbench.colorCustomizations changes token VALUES, not CSS; extensions like Custom CSS/JS Loader target the workbench, not webview iframes). Mark low confidence rather than asserting 'structurally forbidden'.
- Completeness of the body-class list. The findings list only vscode-light/dark/high-contrast[-light]; source pre/index.html:488, 502-508 also sets `vscode-reduce-motion` and `vscode-using-screen-reader`. I confirmed those exist, but not that the annex's omission causes a specific miss — though it is the same shape of trap as the light-HC one, and `prefers-reduced-motion` does not see VS Code's own `workbench.reduceMotion` setting, so it belongs in the annex.

### On the annex call

Agree the annex is worth shipping — and disagree with almost every reason given for it. `annex_worth_it: true` survives; `annex_rationale` and `divergence_from_core` must be rewritten, because as drafted they would ship two instructions that are actively wrong and one that breaks builds. Specifically: the annex tells an agent that `@layer` is "a wasted no-op" here, when microsoft/vscode#261430 is a filed bug titled "Default Styles Override Extension Webview CSS When Using @layer" — on VS Code <= 1.103 (inside grimoire-vscode's own `^1.96.0` support floor) layering the extension's CSS makes it lose to VS Code's unlayered defaults at any specificity. And it tells an agent that setting `--vscode-*` on `body` "silently does nothing", when that is the one override that both works and survives theme changes. A rule that names a working technique as a trap is worse than no rule. The genuine, verified case for the annex is the inverse of the researcher's "the doctrine has no target here": the doctrine's exact mechanism is already implemented BY VS Code — `@layer vscode-default` since 1.104 — with the extension cast as the unlayered consumer that wins for free. That is a much sharper annex, and it yields three traps generic core doctrine cannot produce: (1) never layer your own webview CSS unless `engines.vscode >= 1.104`, and never layer it while codicon.css is unlayered and loaded first; (2) re-declare host tokens on `body`, never on `:root`; (3) `::part()` crosses the shadow boundary and wins on tree order, not specificity — so `vscode-button::part(base)` beats internal `(0,5,0)` rules with no arms race. The token-consumption, high-contrast-class, dead-toolkit, CDN-font and shadow-reachability traps are all real and should stay. The testability section must ship a grep that actually runs — the drafted one returns 98 false positives on the reference repo, and the repo it certifies as clean has two live violations in settings.css.

Not sound. The findings' structural conclusion is inverted, not merely incomplete: they claim @layer has no target in a webview and that no override entrypoint exists, when VS Code itself ships its webview defaults inside `@layer vscode-default` and two override entrypoints (body-level custom properties, `::part()`) are verifiable from source. Both errors trace to the same root cause — the researcher inspected the extension's own compiled CSS and the CSP, but never read VS Code's webview host (`src/vs/workbench/contrib/webview/browser/pre/index.html`), which is the file that decides every question in this annex. Everything about `_defaultStyles`, the `@layer` addition, the deprecated theme-name attribute, the reduce-motion/screen-reader classes, and the exact DOM node the tokens land on comes from that one file.

Highest-priority version pin the annex is missing: `@layer vscode-default` first shipped in VS Code 1.104 (commit 4791661, 2025-08-13; ancestor of tag 1.104.0, not of 1.103.0). grimoire-vscode declares `engines.vscode: ^1.96.0`, so the "wrap your CSS in a layer, it's harmless" advice would break it on eight supported minors. This is exactly the version-drift class the brief warns about.

Two claims marked `confidence: high` were not verified by any method the researcher describes: the "zero un-tokened color literals" attestation (false — two live violations at settings.css:113 and :276), and the toolkit archive date (2025-01-06 is unsupported; the announcement is 2024-07-30 and issue #561 is still OPEN). The proposed CI grep is structurally incapable of producing the result claimed for it — `grep -o` discards the context its own `grep -v` filter needs — and returns 98 false positives when run verbatim against the reference repo.

Load-bearing tuple correction: vscode-elements shadow internals top out at (0,5,0) (`:host([secondary][disabled]:hover) .base`), not the claimed (0,2,0) — `:host()` adds its argument's specificity per css-scoping-1 §3.1. `.base:after` is (0,1,1). This does not change the outer-author conclusion, but a published rule must not carry a wrong tuple.
