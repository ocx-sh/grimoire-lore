## Red controls

A harness that cannot go red proves nothing. These were made to fail first:

- Asserted forced-colors leaves an author color of rgb(1,2,3) untouched — deliberately false; harness correctly reported REFUTED (observed rgb(0,0,0))
- Asserted light-dark() always resolves to its light branch regardless of color-scheme, under an OS-dark context — deliberately false; harness correctly reported REFUTED (observed rgb(240,240,240), the dark branch)

## Overturns round 1

- Round 1 (and the critique) assumed SVG fill is auto-forced like other paint properties under forced-colors; measured: Chromium does NOT touch SVG fill/stroke at all — an SVG icon keeps its authored rgb(22,23,24) verbatim under forced-colors:active. Any rule text claiming forced-colors 'covers' SVG icons is wrong; icons need explicit handling (e.g. fill:CanvasText or forced-color-adjust) and this is a real accessibility gap to call out, not spec restatement.
- box-shadow and background-image are not merely recolored under forced-colors — they are suppressed to `none` entirely. A design that assumes shadows/gradients get 'converted to system colors' is wrong; they vanish unless forced-color-adjust:none is set (which itself has an a11y cost worth naming: it opts the whole subtree out of the user's forced palette, including text/background contrast guarantees).
- A naive lint check enforcing 'every design token must have a separately declared light-mode value and dark-mode value' will false-positive on any token authored via light-dark() — confirmed by direct inspection: exactly one declaration site holds both colors. The colour-parity principle needs to special-case light-dark()-authored tokens rather than requiring textual duplication.
- @property's practical payoff beyond documentation-level type safety is measured, not assumed: (a) invalid values fall back to initial-value rather than inheriting or being ignored — this is a real guardrail against a bad custom-property value silently cascading; (b) inherits:false is a real behavioral switch, not cosmetic — it changes whether descendants see an ancestor's override at all; (c) registration is what makes a custom property interpolable under `transition` — an unregistered custom property provably does NOT animate (discrete flip, confirmed against a corrected control after an initial contaminated test), so any token system that wants to *animate* a custom-property-driven value (not just a native property fed by one) needs @property. This settles round 1's open question of whether @property earns its place: yes, specifically for the animation and invalid-value-containment guarantees, not for narrow type-checking alone.

Methodology note on a real bug caught and fixed during this probe: the first pass of the @property animatability test transitioned the *derived* `width` property (fed by var(--w)) rather than the custom property `--w`/`--w2` itself, and got contaminated results — width interpolated smoothly for BOTH the registered and unregistered custom-property cases, because `width` is natively animatable regardless of what feeds it. This produced a false REFUTED for both the real assertion and its control (see the discarded debug_anim.js reasoning, no longer in the directory). Fixed by isolating `transition: --w 3s linear` / `transition: --w2 3s linear` to the custom property declarations themselves and reading `getComputedStyle(el).getPropertyValue('--w')` directly, confirmed against a clean time series before folding the fix into probe.js. Also caught and fixed a harness bug (not a CSS finding): the box-shadow/background-image assertions were initially recording the observed value itself as the verdict string instead of a confirmed/refuted comparison — fixed before the final run. Final run: 30 confirmed, 1 genuine refuted-against-hypothesis (SVG fill, a real finding), 2 red controls correctly refuted. Full JSON array of all 33 records (including the ones not itemized above, e.g. the two red controls) is printed at the end of out.log next to probe.js. Chromium was not headless-restricted; forcedColors and colorScheme context options both apply cleanly via Playwright's newContext(). Not tested: forced-colors behavior for `outline` vs `outline-color` shorthand differences, `forced-colors` in an actual OS High Contrast mode (only Playwright's CSS-media-feature emulation was exercised, which Chromium implements as the real forced-colors mode, not a mock — this is the standard way forced-colors is tested and matches what a real Windows High Contrast user would see), and @property inheritance through Shadow DOM boundaries (out of scope for this probe, in another engineer's slice per the task split).
