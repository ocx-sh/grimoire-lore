## Scoping mechanism

Not selector-rewriting — structural. A shadow root is a separate node tree; descendant/type/class/ID selectors simply do not match across the boundary in either direction (not "lose a specificity fight," they never enter the match set). There is no emitted scoping attribute the way Astro/Vue produce one. The ONLY selectors that can match an element on the far side of the boundary are the four designed leaks: `:host` / `:host()` (matches the shadow host, usable only inside that root's own stylesheet — has zero effect written anywhere else), `:host-context()` (matches the host based on an ANCESTOR outside the shadow tree — Chromium-only), `::slotted(<compound-selector>)` (lets a component's own stylesheet style light-DOM content projected into its `<slot>` — one compound selector, no descendant combinator, cannot reach into the slotted element's own descendants), and `::part(<ident>+)` (lets an OUTSIDE stylesheet style an element inside the shadow tree that the component explicitly marked with `part="name"`; invisible to anything beyond the immediate parent tree unless relayed with `exportparts` on every intermediate host). Plus one non-selector channel: CSS custom properties, which inherit through the shadow boundary unconditionally (open or closed mode) because inheritance operates on the flat tree and is not gated by shadow-root mode.

## Emitted specificity

No compiled attribute-selector inflation exists here (contrast Astro's `[data-astro-cid-*]`) — instead the four crossing forms carry their own, spec-fixed tuples, none auto-wrapped in `:where()` by any spec mechanism or common tooling (Lit, Stencil etc. do not do this for you): `:host {}` → (0,1,0) — a pseudo-class. `:host(.foo)` → (0,2,0) — MDN is explicit this is NOT like `:is()`/`:not()`: those take only their argument's specificity, but `:host()` adds the pseudo-class's own (0,1,0) to the argument's, so `:host(.foo)` outranks a bare `:host {}` and, if it ever matched off the host's own tree (it can't), would outrank a plain `.foo`. `::part(name) {}` → (0,0,1) — a pseudo-element; chaining a pseudo-class is allowed (`::part(tab):hover` → (0,1,1)) but structural/tree pseudo-classes (`:nth-child` etc.) cannot be appended, and `::part()` cannot be chained to another `::part()`. `::slotted(.foo) {}` → (0,0,1) pseudo-element + (0,1,0) argument = (0,1,1). Source: CSS Shadow Module Level 1, "the specificity of ::part() is that of a pseudo-element, plus the specificity of its argument" (https://drafts.csswg.org/css-shadow-1/), and MDN's `:host()` page contrasting it with `:is()`/`:not()`.

## Cascade-layer support

`@layer` can be declared inside a shadow root's own stylesheet(s) and works normally FOR ORDERING RULES WITHIN THAT ONE TREE. It does not do the cross-boundary job core doctrine assigns it. Per the CSS Cascade Level 5 cascade-sort algorithm (https://drafts.csswg.org/css-cascade-5/#cascade-sort), "cascade layers are scoped to their origin and context, so the ordering of layers in the light DOM has no impact on the order of identically-named layers in the shadow DOM (and vice versa)" — a light-DOM `@layer components { … }` and a shadow-DOM `@layer components { … }` are two unrelated layers that never compete, even same name. More importantly, the cascade-sort step for "context" (which shadow tree a competing declaration originated in) is evaluated BEFORE the layers step and before specificity: for two declarations on the same element from different shadow-tree contexts, the declaration from the OUTER context wins at normal importance, and the INNER context wins only if it is `!important`. This means the entire "ship framework styles inside @layer so the unlayered consumer wins" mechanism from core doctrine point 3 is inapplicable here — for the ::part()/::slotted() override paths, the consumer already wins by cascade-context precedence, with no layer authored by either side, and the ONLY thing that flips that win back to the component is the component using `!important` internally. Never observed a build-tool caveat about layers being dropped by a shadow-DOM bundler because there is no bundler-side transform involved — the browser's native cascade algorithm does this work directly.

## Consumer override entry point

Three channels, in order of how "ordinary" the CSS is: (1) Custom properties — a light-DOM rule like `custom-element { --brand-color: teal; }` reaches every internal `var(--brand-color, <fallback>)` reference, unconditionally, open or closed shadow root, because it rides on ordinary CSS inheritance (not on `::part`/`::slotted`). This is the ONLY entrypoint that needs zero cooperation beyond the component author having used `var()` — matching core doctrine point 1 exactly. (2) `custom-element::part(name) { color: blue; }` written in the light-DOM stylesheet, targeting an element the component tagged `part="name"` — guaranteed to win over the component's own non-`!important` internal rule for that node by the cascade-context step above; no `@layer`, no specificity fight, no source-order dependency. Requires the component to have exposed the part. (3) `element.shadowRoot.adoptedStyleSheets = [sheet, ...]` (or `.push()`ing onto it) — a JS-only path that hands the shadow root an entire constructed `CSSStyleSheet`, bypassing selector matching altogether; works only on an OPEN shadow root the caller holds a reference to (`mode: "closed"` makes `element.shadowRoot` return `null`, blocking this specific path while leaving (1) and (2) untouched, since neither is JS-mediated). Constructable stylesheets are Baseline widely available since March 2023 (MDN `Document.adoptedStyleSheets` / caniuse `mdn-api_document_adoptedstylesheets`) and can be shared by reference across many shadow roots plus the document, avoiding N re-parses of a component's base sheet.

## Token exposure

Idiomatic pattern: declare primitives at `:host` (not a bare `:root`, which inside a shadow root only reaches nested shadow trees further down, not the host's own scope) — `:host { --_surface: #1a1a1a; }` (private, underscore-prefixed by convention, never consumed outside) — then a semantic tier also at `:host`, e.g. `--card-bg: var(--_surface);`, and finally every appearance declaration in the component's actual rules reads a component-hook custom property with a semantic fallback: `background: var(--component-card-bg, var(--card-bg));`. The contract file is just the component's own stylesheet (or, for a Lit/Stencil-style component, its static `styles` tagged-template) — there is no separate "tokens.css" the way a build-tooled framework has, because the whole point is these properties are declared for CONSUMPTION via inheritance, not exported as a design-token file. No framework-native token system ships with native Web Components (that's Lit/Stencil/Shoelace territory, each with its own convention); the platform gives you only the custom-property mechanism itself.

## Theme switching

Dark mode / theme toggling is driven entirely by the custom-property channel: a `data-theme` attribute or `prefers-color-scheme` query in the LIGHT DOM re-resolves custom-property values at `:root`/`html`, and every shadow root's internal `var(--semantic-token)` references recompute automatically on the next style pass — no JS re-render, no per-component theme prop threading, and it is not blocked by `mode: "closed"` (inheritance is unconditional). The component-local piece is `:host { color-scheme: light dark; }` plus internal semantic tokens declared with `var(--component-token, var(--host-semantic-token, <hardcoded fallback>))`, mirroring core doctrine's primitive/semantic/component-hook tiering but with `:host` as the one place primitives are allowed to be declared.

## Testability

No compiled-CSS grep exists for shadow DOM the way it does for a build-step framework — there is no build step that emits a single stylesheet to scan. The equivalent pinned contract is a real-browser (Playwright/WebDriver; jsdom does not implement the shadow cascade correctly) assertion suite with three checks: (a) token wiring — set `el.style.setProperty('--brand-color','red')` from outside, then `getComputedStyle` an internal node and assert the resolved value changed, which fails the moment an internal rule hardcodes a value instead of `var()`-referencing the token; (b) untokenized-value grep over the live CSSOM — iterate `el.shadowRoot.styleSheets` (or the sheets in `adoptedStyleSheets`) via `sheet.cssRules`, and for each declaration of an appearance property (`color`, `background`, `border-color`, etc.) assert `style.getPropertyValue(prop)` matches `/^var\(--/` — this is the shadow-DOM analogue of the two source repos' "grep compiled output for rules outside the layer" test, just pointed at `CSSStyleSheet.cssRules` instead of a build artifact; (c) override-precedence regression — author both an outer `el::part(x){color:blue}` and an inner (shadow-tree) rule targeting the same node, assert the outer wins, which is the test that would catch a regression where someone added `!important` to the internal rule and silently inverted the one override guarantee the platform gives consumers for free.

## Where this contradicts the core doctrine

Point 3 (cascade layers are 'the fix'): inapplicable to the primary override paths. @layer is scoped per origin+context and never crosses the shadow boundary (light-DOM and shadow-DOM layers of the same name are unrelated, per CSS Cascade 5's cascade-sort). The actual mechanism that makes a consumer's plain CSS win here is the cascade's 'context' precedence step, which outranks layers AND specificity outright for cross-tree declarations — so the doctrine's 'ship it in a layer, consumer wins with no !important' advice is not wrong so much as solving a problem Shadow DOM doesn't have, while missing the one Shadow DOM does have (component-side !important is the actual failure mode, inverted from the core's framing where it's the CONSUMER who's tempted to reach for !important). — Point 2 (specificity inflation via a compiled scoping attribute): doesn't exist here at all. There is no emitted `.version[data-foo-cid]`-style selector; a consumer selector targeting shadow-internal markup doesn't lose a specificity fight, it fails to match anything, full stop — the failure mode is total non-selectability, not a rankable specificity loss, and the fix is categorically different (expose a part / expose a custom property) rather than 'raise your specificity or add a layer.' — Points 1 and 4 (tokens as public API; primitive/semantic/component-hook tiering) hold and are, if anything, MORE load-bearing here than in Astro/Vue: because ordinary selectors cannot cross the boundary at all, custom properties are not merely the best override path, for non-exposed internals they are the ONLY one — an untokenized value inside a shadow root is unreachable by any means short of the component author later adding a `part` attribute. Point 5 (contract needs a test) also holds but needs a different test shape: no build step emits compiled CSS to grep, so the pin has to be a live-browser CSSOM/computed-style assertion (detailed in `testability`) rather than a text grep over an output file.

## Traps

- Writing appearance values straight into a shadow-root stylesheet: unlike Astro/Vue scoped CSS, an untokenized value here is not merely hard to override, it is UNREACHABLE from outside by any selector-based mechanism — only var()-consumption gets a downstream consumer in at all.
- Reaching for @layer to let a consumer's CSS win over shadow-DOM component styles: layers never cross the shadow boundary (identically-named layers in light and shadow DOM are unrelated), so this is a structural no-op here, not just weaker than in Astro/Vue.
- Assuming a consumer needs !important or high specificity to beat an internal ::part()/::slotted()-targeted rule: per the CSS Cascade Level 5 'context' cascade step, the OUTER (consumer) declaration already wins over the INNER (component) declaration at equal importance, regardless of specificity — the actual trap is a component author adding !important internally, which is the one thing that flips this and should be treated as a defect, not a fix.
- Using :host-context() for ancestor-driven theming (e.g. `:host-context([data-theme=dark])`): Chromium-only; Firefox marked its implementation bug WONTFIX and Safari opposes the feature on principle, so this silently no-ops in two of three engines with no visible error.
- Writing `::slotted(div span)` or any selector list/combinator inside ::slotted(): the argument must be a single compound selector — this is a parse-time silent-fail trap (the whole rule is dropped), not a specificity issue.
- Assuming a top-level page can style a grandchild component's internals through nested shadow roots via ::part(): part exposure is one hop only; every intermediate custom element must re-declare `exportparts` for the name to relay upward, with no default forwarding.
- Treating :host(.foo) as equivalent to :is(.foo) for specificity purposes: :host() ADDS the pseudo-class's own (0,1,0) to its argument's specificity (unlike the forgiving :is()/:not()), so :host(.foo) is (0,2,0), not (0,1,0) — this changes which of two host rules wins in ties.
- Relying on adoptedStyleSheets injection as 'the' override path and gating a component's theming story on it: it is JS-only and silently unavailable the moment the shadow root is mode:'closed' (shadowRoot returns null), while custom properties and ::part()/::slotted() keep working regardless of mode — closed mode blocks JS access, not CSS.
- Declaring primitive tokens at a bare :root inside the shadow root instead of :host: a :root selector inside a shadow tree matches only nested shadow roots further down the tree, not the host's own light-DOM-facing scope, so host-level consumer overrides silently miss it.

## Review verdict

**Refuted:** token_exposure: "declare primitives at :host (not a bare :root, which inside a shadow root only reaches nested shadow trees further down, not the host's own scope)" — and the matching pitfall "a :root selector inside a shadow tree matches only nested shadow roots further down the tree".

- Why wrong: A selector evaluated in the context of a shadow tree can never match an element in a DIFFERENT tree — including a descendant shadow tree. CSS Shadow Module L1 §3.2.2: "A shadow host is outside of the shadow tree it hosts, and so would ordinarily be untargettable by any selectors evaluated in the context of the shadow tree (as selectors are limited to a single tree)". And Selectors 4 §13.1: ":root pseudo-class represents an element that is the root of the document. For example, in a DOM document, the :root pseudo-class matches the document element. In HTML, this will be the html element." A shadow root is a DocumentFragment, not an element, and the host is featureless ("unselectable except through :host and its related functional forms"). So `:root` inside a shadow root's stylesheet matches NOTHING AT ALL. The published sentence invents a downward-piercing behaviour that does not exist, and an agent that believes it will 'fix' a broken theme by adding a nested `:root` block and see nothing change.
- Correction: "`:root` written inside a shadow root's stylesheet matches nothing — selectors are limited to a single tree and the shadow root is not an element. Declare host-level tokens at `:host`." Drop the 'reaches nested shadow trees' clause entirely.
- Evidence: https://drafts.csswg.org/css-shadow-1/ §3.2.2 (fetched 2026-08-30, ED dated 28 April 2026) and https://drafts.csswg.org/selectors-4/#root-pseudo §13.1, both quoted verbatim above from the fetched documents.

**Refuted:** layer_support / pitfalls / divergence_from_core: "the entire 'ship framework styles inside @layer so the unlayered consumer wins' mechanism from core doctrine point 3 is inapplicable here" / "Reaching for @layer ... is a structural no-op here".

- Why wrong: Over-broad, and it contradicts the researcher's own override channel (3). Layers are scoped per origin AND context — true — but that only kills CROSS-boundary layering. Inside one shadow tree, all sheets applied to that root (the component's own `<style>`, its `static styles`, and any sheet a consumer pushes onto `shadowRoot.adoptedStyleSheets` or appends as a `<style>`) share one encapsulation context, so cascade sorting falls straight through the Context step to the Layers step, where CSS Cascade 5 says "Unlayered rules are sorted later than any layered rules within the same parent layer" — i.e. an injected UNLAYERED consumer sheet beats the component's LAYERED rules at any specificity, with no !important. That is doctrine point 3, verbatim, and it is the ONLY selector-based override path for any internal element the component did not expose as a part. Publishing 'layers are a no-op in shadow DOM' tells an agent to delete the one thing that makes injected-sheet theming work.
- Correction: "Layers never cross the shadow boundary: a light-DOM `@layer components` and a shadow-DOM `@layer components` are unrelated, and for `::part()`/`::slotted()` the consumer already wins by the Context step, so layering buys nothing there. Layers still matter INSIDE the root: wrap the component's own rules in one `@layer` so a sheet injected via `adoptedStyleSheets` (unlayered) wins at any specificity. That is the only override path for internals with no exposed part."
- Evidence: https://drafts.csswg.org/css-cascade-5/#cascade-sort (fetched 2026-08-30): sort order 1 Origin/Importance, 2 Context, 3 Element-Attached Styles, 4 Layers, 5 Specificity, 6 Order — plus "Cascade layers are scoped to their origin and context…" and, from #layering, "Unlayered rules are sorted later than any layered rules within the same parent layer (if any)."

**Refuted:** emitted_specificity: "::part(name) {} → (0,0,1) … Source: CSS Shadow Module Level 1, 'the specificity of ::part() is that of a pseudo-element, plus the specificity of its argument' (https://drafts.csswg.org/css-shadow-1/)", and claim #2 restating the same quote.

- Why wrong: The quote is fabricated for ::part(). I fetched the full ED (2026-04-28) and extracted every occurrence of 'specificity of': the spec defines specificity for exactly four things — `:host` (pseudo-class), `:host()` (pseudo-class + argument), `:host-context()` (pseudo-class + argument), and `::slotted()` (pseudo-element + argument). §5.4 (::part) contains NO specificity sentence at all; the Changes log says "Moved various ::part() details to fully styleable pseudo-element", and css-pseudo-4's definition of 'fully styleable pseudo-element' is only about which properties apply, not specificity. Worse, the borrowed '+ the specificity of its argument' clause is meaningless for ::part, whose grammar is `::part( <ident>+ )` — idents carry no specificity, so `::part(tab active)` is still (0,0,1). A reader of the rule as written will conclude multi-ident parts get more specific.
- Correction: Value (0,0,1) is CORRECT but must be derived, not quoted: Selectors 4 §15 — "count the number of type selectors and pseudo-elements in the selector (= C)". State: "`::part(x)` is (0,0,1); the ident list contributes nothing, so `::part(a b c)` is also (0,0,1). Cite Selectors 4 §15, not css-shadow-1."
- Evidence: https://drafts.csswg.org/css-shadow-1/ §5.4 full text dumped this session (no specificity clause); the 'pseudo-element plus its argument' sentence appears only under §3.2.4 ::slotted(). Specificity counting: https://drafts.csswg.org/selectors-4/#specificity-rules §15.

**Refuted:** pitfalls / claim #5: ":host-context() … Chromium-only; Firefox marked its implementation bug WONTFIX and Safari opposes the feature on principle, so this silently no-ops in two of three engines" (confidence: medium).

- Why wrong: Stale by roughly 18 months and understated. The CSSWG RESOLVED to drop :host-context() (~March 2025, w3c/csswg-drafts#1914); MDN's page — last modified 2026-08-21 — now carries a deprecation banner: "Avoid using this feature in new projects. The CSS Working Group removed :host-context() from the specification, due to opposition from vendors, performance considerations, and interest in alternatives", and points to container style queries as the replacement. The css-shadow-1 ED of 2026-04-28 still defines it, which is editorial lag, not endorsement — a published rule that cites the ED as if the selector were merely under-implemented will read as a green light. The correct verdict is 'do not use; it is being removed', and confidence is high, not medium.
- Correction: "`:host-context()` is deprecated — the CSSWG resolved to remove it (csswg-drafts#1914, 2025) and it never shipped outside Chromium. Never author it. For ancestor-driven theming, set a custom property in the light DOM and read it inside the root; container style queries (`@container style(--theme: dark)`) are MDN's suggested replacement."
- Evidence: https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:host-context (fetched 2026-08-30, page last modified 2026-08-21) ; https://github.com/mdn/content/issues/38960 (":host-context is being dropped", citing the CSSWG resolution and w3c/csswg-drafts#1914) ; https://drafts.csswg.org/css-shadow-1/ §3.2.3 still defines it (ED 2026-04-28).

**Refuted:** emitted_specificity: ":host(.foo) outranks a bare :host {} and, if it ever matched off the host's own tree (it can't), would outrank a plain .foo."

- Why wrong: The parenthetical implies the `:host(.foo)` vs `.foo` comparison never happens. It happens on every themed component. The host element IS in the outer tree, and a light-DOM rule `custom-element { }` (0,0,1) and the shadow rule `:host(.foo) { }` (0,2,0) both target it — from different encapsulation contexts. Cascade 5 §cascade-sort step 2 (Context) is evaluated BEFORE specificity: "for normal rules the declaration from the outer context wins". So the consumer's (0,0,1) type selector beats the component's (0,2,0) `:host()` rule. The specificity table as published invites exactly the wrong conclusion — that `:host(.foo)` is a strong default a consumer must out-specify.
- Correction: "On the host element, every `:host`/`:host()` declaration is the WEAKEST normal declaration: any light-DOM rule that matches the host beats it regardless of specificity (Context step). That is why `:host { --token: … }` defaults are safely overridable, and why `:host` is never the place to lock appearance in."
- Evidence: https://drafts.csswg.org/css-cascade-5/#cascade-sort (Context step, quoted verbatim); https://drafts.csswg.org/css-shadow-1/ §3.2.1 "Declarations inherit the tree context of the selector that was matched to apply them."

**Refuted:** scoping_mechanism / claim #1: custom properties "inherit through the shadow boundary unconditionally (open or closed mode) because inheritance operates on the flat tree".

- Why wrong: 'Unconditionally' is doing work the flat tree does not support. The same flat-tree rule the claim invokes ALSO redirects inheritance for slotted content: css-shadow-1 §4.1 — "some of its light tree children can be 'pulled into' the shadow tree by assigning them to slots. This causes them to be treated as children of the slot for CSS purposes." So a slotted element inherits custom properties from the SLOT's ancestors inside the shadow tree, not from its light-DOM parent — the single most common shadow-DOM token surprise, and it is absent from the pitfall list. Separately, a custom property registered with `@property { inherits: false }` does not inherit at all, boundary or no boundary.
- Correction: Keep the host→shadow direction (correct, and mode-independent), but add: "Slotted light-DOM content inherits through the FLAT tree — from the `<slot>`'s ancestors inside the shadow root, not from its own light-DOM parent. A token you set on the slotted element's light-DOM parent will not reach it; one the component sets around the slot will. `@property … { inherits: false }` opts a property out of inheritance entirely."
- Evidence: https://drafts.csswg.org/css-shadow-1/ §4.1 Flattening the DOM into an Element Tree, quoted verbatim from the fetched ED.

**Refuted:** testability (b): "iterate el.shadowRoot.styleSheets … and for each declaration of an appearance property assert style.getPropertyValue(prop) matches /^var\(--/".

- Why wrong: As specified, the test passes on the code it exists to catch. `CSSStyleSheet.cssRules` is a flat list of top-level rules: any declaration inside `@media`, `@supports`, `@layer`, or a nested rule lives on a CSSGroupingRule child and is never visited, so a hardcoded `background:#1a1a1a` inside `@media (prefers-color-scheme: dark)` — precisely where hardcoded colours accumulate — goes unseen. `shadowRoot.styleSheets` also excludes adopted sheets (Lit's `static styles` path), and `.cssRules` throws SecurityError on a cross-origin `<link>`ed sheet. A green suite that cannot fail is worse than no suite; doctrine point 5 is about a contract that is actually pinned.
- Correction: "Recurse into CSSGroupingRule.cssRules (@media/@supports/@layer/nested), and walk both `shadowRoot.styleSheets` AND `shadowRoot.adoptedStyleSheets`; wrap `.cssRules` access in try/catch for cross-origin sheets. Prove the test fails by adding one hardcoded colour inside a @media block before landing it."
- Evidence: CSSOM: cssRules is per-rule-list and grouping rules nest their own (https://drafts.csswg.org/cssom/#the-cssgroupingrule-interface); adoptedStyleSheets is a separate slot from styleSheets (https://developer.mozilla.org/en-US/docs/Web/API/Document/adoptedStyleSheets).

### Confirmed

- Cascade sort order, verbatim from https://drafts.csswg.org/css-cascade-5/#cascade-sort: 1 Origin and Importance, 2 Context, 3 Element-Attached Styles, 4 Layers, 5 Specificity, 6 Order of Appearance — Context IS above Layers and Specificity. Context step verbatim: "When comparing two declarations that are sourced from different encapsulation contexts, then for normal rules the declaration from the outer context wins, and for important rules the declaration from the inner context wins." The annex's central mechanism is CORRECT: a consumer's `el::part(x)` beats the component's internal rule with no !important and no specificity fight, and component-side !important is the one thing that inverts it.
- "Cascade layers are scoped to their origin and context, so the ordering of layers in the light DOM has no impact on the order of identically-named layers in the shadow DOM (and vice versa)" — verbatim in css-cascade-5. Cross-boundary layering is genuinely a no-op (the over-generalisation drawn from it is refuted above).
- :host = (0,1,0), :host(.foo) = (0,2,0). Verbatim css-shadow-1 §3.2.3: "The specificity of :host is that of a pseudo-class. The specificity of :host() is that of a pseudo-class, plus the specificity of its argument." plus the spec's own Note: "This is different from the specificity of similar pseudo-classes, like :is() or :not(), which only take the specificity of their argument." The researcher's non-forgiving-:host() pitfall is exactly right and well sourced.
- ::slotted(.foo) = (0,1,1). Verbatim: "The specificity of ::slotted() is that of a pseudo-element, plus the specificity of its argument." Grammar in the ED body is `::slotted( <compound-selector> )` — single compound selector, no combinators; MDN agrees ("accepts a compound selector only, not a comma-separated selector list") and adds that it never matches text nodes. Tree-abiding pseudo-elements after it (::slotted()::before) are explicitly allowed.
- :host / :host() / :host-context() match only when evaluated in the context of a shadow tree — "In any other context, it matches nothing" (three times, verbatim). Writing :host in a light-DOM sheet is inert.
- Total non-selectability across the boundary, not a specificity loss. Verbatim css-shadow-1 §3.2.2: "selectors are limited to a single tree"; the host is featureless and "unselectable except through :host and its related functional forms". The divergence-from-core framing (Astro's `[data-astro-cid-*]` inflation has no analogue; the failure mode is non-matching, and the fix is expose-a-part or expose-a-property, not raise specificity) is correct and is the strongest part of the report.
- ::part() cannot be chained to ::part(). Verbatim: "x-panel::part(confirm-button)::part(label) never matches anything. This is because doing so would expose more structural information than is intended."
- exportparts is required per hop; part exposure is not transitive. Confirmed by §5.3 and its worked example whose inner span "will not be red because textspan in the document style cannot match against the part inside the inner custom element if it is not forwarded."
- ::part(tab):hover = (0,1,1) and structural pseudo-classes cannot follow ::part — and the consequence is stronger than stated: Selectors 4 §3.6.3 "This specification allows any pseudo-element to be followed by any combination of the logical combination pseudo-classes and the user action pseudo-classes… Combinations that are not explicitly allowed are invalid selectors." So `::part(x):nth-child(2)` invalidates the whole rule, it does not merely fail to match. Specificity via Selectors 4 §15 (pseudo-elements in C, pseudo-classes in B).
- adoptedStyleSheets phrasing matches MDN exactly: "Baseline Widely available… It's been available across browsers since March 2023" — the researcher's wording mirrors MDN's banner, so the earlier-looking 'widely available since March 2023' is MDN's own phrasing, not an error. MDN also confirms in-place mutation (`push()`), noting "In an earlier version of the specification, the array was not modifiable" — pre-Chrome-99/Safari-16.4 engines need whole-array assignment.
- Citation URL https://drafts.csswg.org/css-shadow-1/ is CORRECT and current, contrary to first impression: css-scoping-1 now redirects there. "This specification was originally titled CSS Scoping Module Level 1. It has since been merged with CSS Shadow Parts Module Level 1 and renamed to CSS Shadow Module Level 1." ED dated 28 April 2026. (Only the shadow-parts-related cascade text moved: 'scoped style rules' went to css-cascade-6; the cascade-sort text the annex relies on is still css-cascade-5, so that cite is right too.)
- "No local repo in this workspace ships a shadow-DOM component" — verified by grep for attachShadow/adoptedStyleSheets/::part/::slotted/:host/exportparts across grimoire-indexer, ocx-catalog, kate-middlechild, grimoire-vscode, grimoire-lore. Zero `attachShadow` in any source tree; the only `:host` hits are /home/mherwig/dev/grimoire-indexer/__probe3.mjs (an Astro-compiler probe feeding `:host { color: red }` through @astrojs/compiler-rs) and vendored/compiled CSS in ocx-catalog and kate-middlechild dist bundles.

### Unverifiable

### On the annex call

Agree annex_worth_it: true — but two of its three stated reasons need rewriting before they justify anything. Reason (1) as written ('an agent would wrap styles in @layer expecting the consumer to win — a structural no-op') is itself wrong: layers are exactly right for the injected-sheet path the same report lists as override channel 3, and an annex that says otherwise deletes a working mechanism. Reason (3) understates :host-context() (deprecated and being removed, not merely Chrome-only). Reason (2) — that the consumer already wins by the Context step and component-side !important is the defect, inverting the core doctrine's assumption about who reaches for !important — is fully confirmed against css-cascade-5 and is by itself enough to earn the file. The strongest justification is one the rationale buries: in shadow DOM an untokenized value with no `part` attribute is not hard to override, it is UNREACHABLE by any selector from outside ('selectors are limited to a single tree'), which makes core doctrine point 1 categorically stronger here than in Astro/Vue, and makes 'raise your specificity' — the reflex the core rule spends its words disarming — not merely weak but meaningless. None of this is discoverable by reading a repo's code. Keep the annex, but it must ship shorter than what came back: cut ::theme() history, cut the Firefox bug forensics, cut anything not framed as a trap.

Not a clean bill of health. The report's spine — non-selectability across the boundary, and the Context step outranking layers and specificity so the consumer wins ::part()/::slotted() overrides for free — is CONFIRMED verbatim against css-cascade-5 and css-shadow-1 (ED 2026-04-28) fetched today. Every specificity tuple it publishes is right: :host (0,1,0), :host(.foo) (0,2,0) with the spec's own non-forgiving note, ::slotted(.foo) (0,1,1), ::part(x) (0,0,1). Seven defects need fixing before publication, ranked by blast radius:

1. ':root inside a shadow root reaches nested shadow trees' — invented behaviour; it matches nothing.
2. '@layer is a structural no-op in shadow DOM' — true across the boundary, false inside it, and false for the report's own adoptedStyleSheets channel, which is the ONLY override path for internals with no exposed part. This one deletes a working mechanism.
3. A fabricated verbatim ::part() specificity quote (it is the ::slotted() sentence) plus a '+ argument specificity' clause that is meaningless for an ident list. Value right, citation wrong — and this rule set is about to teach agents to trust its citations.
4. :host-context() is deprecated and CSSWG-removed (csswg-drafts#1914, 2025; MDN 2026-08-21), not merely Chromium-only.
5. The '(it can't)' parenthetical about :host(.foo) vs .foo hides the fact that the comparison happens constantly and specificity loses to Context — :host declarations are the weakest normal declarations on the host.
6. 'Custom properties inherit unconditionally' omits the flat-tree redirection for slotted content — the most common token surprise in shadow DOM, missing from the pitfall list.
7. The proposed CSSOM grep test cannot fail on hardcoded values inside @media/@supports/nested rules, and misses adopted sheets — a contract that only looks pinned.

Two things the report gets right that are worth preserving verbatim in the annex: the invalid-selector consequence (a structural pseudo-class after ::part() invalidates the whole rule per Selectors 4 §3.6.3, so it fails silently), and the exportparts one-hop worked example straight from §5.3.

Also worth adding: css-shadow-1 now defines :has-slotted (§3.2.5), which the report does not mention.

Provenance caveat for whoever publishes this: no browser and no shadow-DOM component exists on this machine (verified), so unlike the Astro/VitePress annexes nothing here is pinned to compiled output. If the rule ships a testability section telling consumers to prove the contract in a real browser, the rule's own authors should run that test once against a throwaway component before publishing — otherwise doctrine point 5 is being preached and not practised.
