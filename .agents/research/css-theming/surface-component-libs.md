# Surface study — Component-library layer: Lit (adoptedStyleSheets/css/:host), Stencil scoped:true, Shoelace/Web Awesome (::part + custom-property hooks), Radix/shadcn/Base UI (data-slot/data-state conventions)

Commissioned by round 1's critic as a gap: a surface the study never reached.

- **Versions checked:** Lit 3.3.3 / lit-element 4.2.2 / lit-html 3.3.3 / @lit/reactive-element 2.1.2; Playwright 1.5x-series bundled Chromium (installed via `npx playwright install chromium`, 2026-08-30). Stencil 4.44.2 (@stencil/core, scaffolded via `npm init stencil` 2026-08-30). @shoelace-style/shoelace 2.20.1 (legacy line, npm 2026-08-30) and @awesome.me/webawesome 3.12.0 (current successor, per npm view 2026-08-30); shoelace-style/shoelace GitHub repo confirmed archived 2026-08-28, shoelace-style/webawesome active (pushed 2026-08-27). @radix-ui/react-dialog 1.1.23, @radix-ui/react-checkbox 1.3.11, @radix-ui/react-switch (latest resolved), @radix-ui/react-accordion 1.2.20, @radix-ui/react-select 2.3.7, all installed 2026-08-30. @base-ui/react 1.7.0, installed 2026-08-30. shadcn/ui source read live from github.com/shadcn-ui/ui `main` branch, fetched 2026-08-30 (no local install — shadcn ships as copy-in source, not a package to `npm install`).
- **Placement:** `fold-into-existing-annex` — All four findings extend structures round 1 already created rather than needing a new one: Lit's adoptedStyleSheets confirmation and the un-namespaced-hook nuance belong in the existing shadow-dom annex (as a concrete "here's a real library exercising this" example plus a correction to the assumed `--component-*` prefix); Stencil's `scoped: true` needs one new row in the existing diagnosis table (it is a sibling of the attribute-scoped and shadow-DOM rows, not a reason for a new table); and the Shoelace churn evidence plus the shadcn/Radix/Base UI attribute-family findings are direct, dated substantiation for the identity-attribute exception clause and the "finest-grained tier churns" warning that already exist in the design — they upgrade those claims from asserted to evidenced, they don't introduce a new doctrine.

## Mechanism

Four independently-verified mechanisms, each a different shape:
(1) Lit: `static styles = css\`...\`` compiles to a CSSStyleSheet assigned wholesale to `renderRoot.adoptedStyleSheets` (source-confirmed gate in @lit/reactive-element on `supportsAdoptingStyleSheets`, true in all evergreen browsers) — no `<style>` element is ever created on that path. `unsafeCSS()` splices a raw string into the tagged template for cases like a JS-sourced color constant.
(2) Stencil `scoped: true`: NOT shadow DOM. Compiler appends a class to the host (`sc-<tag>-h`) and to every rendered descendant (`sc-<tag>`), compounding it onto the element's authored selector in the emitted CSS (`.name` → `.name.sc-my-component`), and injects that CSS as one real, global `<style>` tag in document `<head>` — the scoping unit is a classList mutation plus compound-selector rewriting, not a tree boundary and not an attribute (contrast Vue/Astro's `[data-v-hash]`).
(3) Shoelace/Web Awesome: `::part()` exposed at fine granularity per component (six parts on `sl-button` alone: base/prefix/label/suffix/caret/spinner) plus a two-tier custom-property system — a namespaced global-token tier (`--sl-color-*`, now `--wa-*`) and a frequently UN-namespaced per-component tier (`--size`, `--track-width`) that relies on Shadow DOM's natural per-tree scoping rather than a naming convention.
(4) Radix/shadcn/Base UI: two independent, complementary attribute families stacked on the same DOM elements — Radix/Base UI's interaction-state family (`data-state`, `data-disabled`, `data-orientation`, `data-highlighted`, `data-placeholder`, each computed by a small `getState()`-style function per component) and shadcn's own structural-identity family (`data-slot="<part-name>"`, plus prop-mirroring attributes `data-variant`/`data-size`) added in shadcn's own wrapper source, which is copied verbatim into the consumer's repo rather than shipped as a versioned package.

## Where it contradicts the core

None of round 1's core doctrine is contradicted by what I reproduced — Lit and Stencil-shadow both confirm the shadow-dom annex's structural claims (adoptedStyleSheets-only, no styleSheets walk, custom-property inheritance crosses the boundary). What breaks is an ABSENCE, not a wrong claim: Stencil's `scoped: true` mode is neither attribute-scoped (core doctrine's dominant case) nor shadow-boundary-isolated (the annex's case) — it is a third mechanism (compiled compound-class selectors in a real global stylesheet) the diagnosis table has no row for, so an agent following the table's binary framing will misdiagnose it as one of the two and give wrong override advice. Separately, round 1's assumed `--component-*` custom-property prefix convention is only partially right: Shoelace/Web Awesome's actual per-component hooks are frequently bare/un-namespaced (`--size`, `--track-width`), relying on Shadow DOM's natural per-tree scoping instead of a naming prefix.

## Traps

- An agent using the round-1 diagnosis table alone will misclassify Stencil `scoped: true` output as either attribute-scoped or shadow-isolated and give wrong override advice both ways — it is neither; it's compound-class inflation in a real global stylesheet.
- Stencil's `sc-<tagname>` scoping class is a plain, guessable, tag-name-derived string (unlike Vue's build hash) — a consumer CAN write `.sc-my-component{...}` directly and it works, but it's an undocumented internal name with no semver contract, so treating it as a stable target is its own footgun even though it happens to be reachable.
- Believing the shadow-dom annex's `--component-*` custom-property prefix is universal: Shoelace's actual per-component hooks (`--size`, `--track-width`) are frequently bare, relying on Shadow DOM's natural per-tree scoping rather than a naming convention — an agent hunting for a `--component-*`-prefixed hook on a real Shoelace/Web Awesome component may not find one that exists under a different, unprefixed name.
- Assuming Shoelace's stable global token tier (`--sl-*`) is the whole hook surface and is itself permanent: the entire prefix rebranded to `--wa-*` across the Web Awesome transition, and even within one library's post-1.0 history individual part names and individual component custom properties get removed/renamed in ordinary minor releases (v3.9.0, v3.12.0) — pinning to any single hook name is a live risk, not a hypothetical one.
- Assuming `data-slot` is a single universal shadcn convention: it's specific to the Radix-backed (and similar) registries; shadcn's own Base-UI-backed registry variant uses a completely different hardcoded-class convention instead, so 'defer to data-slot' is not safe advice for every shadcn output a consumer might encounter.
- Assuming shadcn is a normal publisher/consumer CSS surface at all: because its CLI copies component source directly into the consumer's repo (verified by pulling the exact same raw source shadcn's own installer fetches), there is no separately-versioned package whose stylesheet a consumer overrides from outside — the retheming surface is a git diff on code you now own, not a cascade override, so core doctrine's 'ship tokens as a versioned public API' framing has no target here.

## Reproduced here

- Lit 3.3.3 (lit-element 4.2.2, lit-html 3.3.3, @lit/reactive-element 2.1.2): source-confirmed adoptedStyleSheets-only path in evergreen browsers; live Playwright/Chromium render of a real component shows shadowRoot.styleSheets.length===0, adoptedStyleSheets.length===1 with the actual CSS text, no <style> tag in the shadow root, unsafeCSS() interpolation rendered correctly (border:1px solid red), and a light-DOM `--component-card-bg` override reaching an internal var() fallback chain through :host (computed background rgb(255,105,180)/hotpink) — artifact: `r2/surface-component-libs/lit/{my-card.js,inspect.mjs}` (session scratch)
- Stencil 4.44.2, `scoped: true`: real build (npm init stencil scaffold, `npx stencil build`) shows no shadow root, host gets class `sc-my-component-h`, descendants get `sc-my-component`, compiled CSS `.sc-my-component-h{display:block}.name.sc-my-component{color:blue}` injected as a genuine global <style> in <head>, and a live-rendered consumer override attempt (`.name{color:green}` in a later <style> tag) LOST to the compiled `.name.sc-my-component` rule (computed color stayed blue) despite later source order — specificity (0,2,0) beats (0,1,0) — artifact: /tmp/.../stencil-test/my-stencil-comp/{dist/esm/my-component.entry.js,scoped.html,inspect.mjs}
- @shoelace-style/shoelace 2.20.1 shipped source confirms sl-button exposes six ::part() names (base/prefix/label/suffix/caret/spinner) and sl-avatar/progress-ring consume un-namespaced per-component custom properties (--size, --track-width, --indicator-width) alongside the namespaced --sl-* token tier
- shoelace-style/shoelace GitHub repo is archived (2026-08-28) — 'Shoelace is now Web Awesome'; live successor is @awesome.me/webawesome (currently 3.12.0); its dated release notes show real component-hook churn: v3.9.0 removed `--wa-accordion-divider-color` outright, v3.12.0 deprecated the `label` ::part() name in favor of `form-control-label`
- @radix-ui/react-{dialog,checkbox,switch,accordion,select} (versions 1.1.23/1.3.11/1.2.20/2.3.7, installed 2026-08-30): source-confirmed data-state values (open/closed, checked/unchecked/indeterminate) plus a companion family (data-disabled, data-orientation, data-highlighted, data-placeholder)
- shadcn/ui live main-branch source (fetched 2026-08-30): button.tsx and dialog.tsx confirm data-slot="<part-name>" on every component root/part, plus data-variant/data-size mirroring cva props, stacked on top of Radix's own data-state on the same elements
- @base-ui/react 1.7.0 (installed 2026-08-30) ships the same data-state-family convention as Radix (per-component *DataAttributes.js files), confirming the convention spans the whole Radix/Base UI lineage, not just Radix
- shadcn's own Base-UI-backed registry variant (apps/v4/registry/bases/base/ui/button.tsx) does NOT use data-slot at all — it uses hardcoded class names (cn-button-variant-outline) instead, a real divergence from the default Radix-backed registry's convention
