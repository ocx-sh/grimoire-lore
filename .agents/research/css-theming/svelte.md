These are all specificity/pruning/packaging behaviors specific to Svelte's compiler, not generic CSS knowledge, and each is a wrong-code trap, not architecture.

## Scoping mechanism

Every top-level selector in a component's `&lt;style&gt;` block gets a hash class (`.svelte-xxxxx`, hash of the component's style content) appended to its LAST simple selector on first occurrence; only the FIRST occurrence in a given rule adds the class directly — every subsequent occurrence in the same selector (e.g. combinators) is added wrapped in `:where(.svelte-xxxxx)`, which is zero-specificity, so specificity does not compound across a multi-part selector. `:global(...)` opts a single selector out of scoping entirely; a `:global { ... }` block (or `.scope :global { ... }`) opts a nested group out while the outer scope selector stays scoped. `@keyframes` names are hashed/scoped the same way; `-global-` prefix opts a keyframe out. Verified by compiling with `svelte@5.57.0`: `.version{color:red}` → `.version.svelte-3gz7um{color:red}`; `.foo .bar{color:blue}` → `.foo.svelte-3ge52z .bar:where(.svelte-3ge52z){color:blue}`.

## Emitted specificity

A single-class rule like `.version{...}` compiles to `.version.svelte-3gz7um{...}` — TWO class selectors on one compound selector, specificity **(0,2,0)** — same shape and same number as Astro's `[data-astro-cid-...]` attribute-selector scoping named in the brief. This is NOT wrapped in `:where()` — the scope hook has non-zero specificity, so it is NOT the `:where()`-wrapped-to-zero pattern the core doctrine's override strategy needs. `:where()` in Svelte only suppresses the SECOND+ occurrence of the hash class within one already-scoped selector (descendant/combinator chains), never the base (0,2,0) added to every top-level rule. A bare-element selector `p{...}` compiles to `p.svelte-xxx{...}` at (0,1,1) — still beats a consumer's unlayered `p{...}` at (0,0,1).

## Cascade-layer support

The Svelte 5.57.0 compiler DOES correctly preserve and scope selectors inside author-written `@layer` blocks — verified by compiling `@layer base,special{ @layer special{.item{...}} @layer base{.item{...}} }` and getting `.item.svelte-3d0zst` correctly scoped inside each named layer (the 2022-vintage bug tracked in sveltejs/svelte#7504, which stripped `@layer` contents entirely, is fixed as of this version). HOWEVER there is no automatic per-project mechanism that puts ALL component styles into one named layer — a component author must hand-wrap every `&lt;style&gt;` block's content in `@layer name { ... }`, or apply a custom Svelte `preprocess` `style` hook (`style: ({content}) => ({code: \`@layer svelte { ${content} }\`})`) registered in `svelte.config.js`. Absent either, SvelteKit places compiled component CSS in the anonymous (unlayered) layer, which — per the CSS layers spec — outranks EVERY named layer regardless of source order (this is exactly why `sveltejs/svelte#11345`, "Add CSS @layer support for components, tailwind v4," is still open: Tailwind v4's own `@utilities` layer loses to an unlayered Svelte component rule even though the component author used `:where()` to try to stay low-specificity). Net: layering in Svelte is opt-in and per-repo — an agent must grep `svelte.config.js`'s `preprocess` array for a layer-wrapping hook before assuming the doctrine's "ship every author rule inside one @layer" is already in force.

## Consumer override entry point

Two distinct paths, and an agent must know which repo it's in: (1) **Instance-level custom properties** — Svelte has first-class syntax: `&lt;Slider --track-color="black" /&gt;` passed by ANY consumer (parent component or a downstream app) desugars to a wrapper `&lt;svelte-css-wrapper style="display:contents; --track-color:black"&gt;&lt;Slider/&gt;&lt;/svelte-css-wrapper&gt;` (an `&lt;g&gt;` wrapper for SVG). This wrapper does not affect layout but DOES break any override selector using a direct-child combinator (`>`) targeting what the consumer thinks is the component's outermost element — a real trap. Source: svelte.dev docs `04-styling/03-custom-properties.md`. (2) **Sheet-level override CSS** — only works if the library/app deliberately layers its own component styles (see layer_support); otherwise an unlayered consumer stylesheet loses to the always-(0,2,0)-or-higher scoped selectors regardless of source order, exactly per core doctrine point 2. There is no third path: a plain selector reaching into a child component's scoped class from outside that component's own `&lt;style&gt;` block is not merely outranked, it is DELETED at compile time (see pitfalls) unless wrapped in `:global(...)`.

## Token exposure

Idiomatic: declare tiers as plain CSS custom properties, primitive/semantic tiers on `:root` in a global (non-component) stylesheet or in a `&lt;svelte:head&gt;`/app.css, consumed inside component `&lt;style&gt;` blocks via `var(--semantic-token, fallback)`. `:root{...}` inside a component's own `&lt;style&gt;` block is NOT pruned as "unused" (verified: compiling a block containing bare `:root{--brand-color:blue}` alongside a used `.card` rule leaves `:root` untouched, no `css_unused_selector` warning) — so a component is free to declare its own token defaults at `:root` scope without them vanishing, but doing so also means those declarations are NOT scoped to the component (there is exactly one global `:root`) — a naming collision across components sharing the same custom-property name is a real, silent conflict-prone pattern the doctrine's "primitive tier is private" point should flag for Svelte specifically. Component-instance-level exposure of a hook uses the `--prop-name` attribute syntax above, which IS Svelte's native "component hook" analogue — an agent should reach for it before inventing a `theme` prop object.

## Theme switching

No framework-native theme-switch primitive beyond what plain CSS provides — a theme toggle is conventionally `data-theme` on `&lt;html&gt;`/`&lt;body&gt;` (set via SvelteKit's `app.html` + a tiny script, or `$app/environment` + `$effect`) driving `:root[data-theme="dark"]{--semantic-token: ...}` overrides in a global stylesheet, same mechanism as any other framework — there is no Svelte-specific tier interaction to document beyond: dark-mode overrides declared in a component's own `&lt;style&gt;` block are scoped like anything else, so a `:global(:root[data-theme="dark"])` wrapper (or keeping theme tokens entirely out of component `&lt;style&gt;` blocks, in global CSS) is required for a component-authored dark variant to reach the rest of the app.

## Testability

The load-bearing divergence: **for a published Svelte component library there is usually no compiled CSS artifact to grep in the published package at all.** The documented, idiomatic packaging path (`@sveltejs/package` / `svelte-package`) ships components as UNCOMPILED `.svelte` source — TS/SCSS get preprocessed to JS/CSS, but the Svelte compiler's own scoping/`@layer`/`:where()` transform does NOT run until the CONSUMING app builds, with whatever Svelte version that consumer has installed. So a grep-the-compiled-output contract test (per core doctrine point 5) cannot live inside the library's own repo/CI against its `dist/` — it has no scoped CSS to grep — it must instead run inside a real consumer fixture: build a minimal SvelteKit app that imports the library, run `vite build`, then grep the emitted `.css` chunk for `@layer <name>{` wrapping every library-originated rule and for zero unlayered library selectors. Concretely runnable check: `vite build` the fixture app, then `grep -c '@layer mylib' build/**/*.css` should be non-zero AND `grep -B2 '\.svelte-[a-z0-9]\{6,\}' build/**/*.css | grep -v '@layer'` should be empty (every scoped-class rule must appear only inside the named layer). A second, cheaper unit check: compile a representative component in isolation with `svelte.compile(source, {css:'external'})` and assert the output string starts with `@layer <name>{` — this catches "forgot to wrap this file's style block" (or "forgot the preprocessor hook") without needing a full app build, and is what I ran locally to derive every claim above.

## Where this contradicts the core doctrine

Two real contradictions, one confirmation: (A) Doctrine point 2 cites Astro's scoping example as representative of "component-scoped styles compile to a selector that outranks a consumer's plain class in either source order" — Svelte's scoping (0,2,0) matches that shape exactly, so point 2 holds unmodified. (B) Doctrine point 3 ("the fix is cascade layers: ship every framework-authored style block inside a single @layer") is NOT true out of the box for Svelte/SvelteKit — there is no built-in, automatic mechanism that puts compiled component CSS into a named layer; by default it lands unlayered (highest priority), which is the OPPOSITE of the doctrine's assumed baseline, and doing it right requires a hand-added preprocess hook the core's generic advice would never surface. (C) Doctrine point 5 ("pin the contract with a test that greps the compiled output") assumes a compiled output artifact exists in the repo/package under test — for a published Svelte component library it usually doesn't (ships as uncompiled .svelte source); the grep target has to be a consumer-fixture build, a packaging-model divergence the core doesn't anticipate.

## Traps

- Reaching into a child component's internal class from a parent's &lt;style&gt;, unwrapped: the compiler doesn't just fail to match it, it DELETES the rule (emits `/* (unused) .foo{...} */` plus a `css_unused_selector` warning) — verified locally. The fix is `:global(.child-internal-class){...}` or, for markup injected via `{@html}`, the nested `&lt;selector&gt; :global { ... }` block form (svelte.dev/docs/svelte/global-styles).
- Assuming `:where()` neutralizes Svelte's scoping specificity the way it does in the doctrine's `@layer` strategy — it doesn't: `:where()` only suppresses the SECOND+ occurrence of the *hash* class inside one compound selector; the base rule is still `(0,2,0)`, same order of magnitude as Astro's attribute-hash scoping named in the brief. Writing an unlayered override in a consumer app still loses to any Svelte component's default scoped rule.
- Assuming `@layer` in a `&lt;style&gt;` block 'doesn't work in Svelte' because of the well-known, still-cited 2022 bug (#7504) — that bug is fixed as of svelte@5.57.0; `@layer` now compiles and scopes correctly. The live, UNFIXED problem (#11345, open) is the opposite: nothing puts component CSS into a layer automatically, so it defaults to the always-winning anonymous layer, which silently beats even a consumer's `@layer utilities` block (e.g. Tailwind v4) — an agent must check for a `preprocess` layer-wrapping hook in `svelte.config.js`, not assume either 'layers are broken' or 'layers are default-on'.
- Publishing/consuming a Svelte component library and expecting to grep its `dist` for compiled, scoped CSS to verify a layer or token contract: for the idiomatic `svelte-package` output there is nothing to grep — components ship as uncompiled `.svelte` source and only acquire scoping/layer wrapping when the DOWNSTREAM app builds. A contract test belongs in a consumer-fixture build, not the library's own CI against its own dist.
- Passing `--custom-property="value"` to override a component instance and then writing a `>` (direct-child) override selector against what looks like the component's root in the DOM — Svelte silently inserts a `&lt;svelte-css-wrapper style="display:contents"&gt;` (or `&lt;g&gt;` for SVG) around the component when ANY `--custom-property` prop is passed, which breaks direct-child combinator selectors even though it doesn't affect visual layout.
- Declaring token defaults with a bare `:root{...}` inside a component's own `&lt;style&gt;` block, assuming component scoping protects it — `:root` selectors are NOT scoped (there's only one `:root`) and are NOT pruned as unused, so two components declaring the same custom-property name on `:root` silently collide app-wide; primitive/private tokens belong in one shared global stylesheet, not per-component `:root` blocks.

## Review verdict

**Refuted:** Concretely runnable contract check: `grep -B2 '\.svelte-[a-z0-9]\{6,\}' build/**/*.css | grep -v '@layer'` should be empty (every scoped-class rule must appear only inside the named layer).

- Why wrong: Production CSS is minified to a SINGLE LINE. `grep -B2` returns context lines, but when the whole bundle is one line, the line containing a leaked `.svelte-hash` rule also contains `@layer` somewhere else on that same line, so `grep -v '@layer'` discards it. The check silently returns empty — i.e. PASSES — while a genuinely unlayered library rule is sitting in the bundle. It is a test that cannot fail for the reason it exists. Secondary defects: `grep -c` counts matching LINES not occurrences, so check A returns 1 on any minified bundle regardless of how many layered rules exist; `build/**/*.css` assumes globstar (off by default in bash/sh CI) and assumes an output dir that is adapter-dependent (`dist/` for plain Vite, `.svelte-kit/output/` by default, `build/` only with adapter-node/static). This is the most dangerous error in the findings because doctrine point 5 is the enforcement mechanism for the whole contract.
- Correction: Do not grep. Brace-match the layer body and assert no scoped-class token survives outside it. ### Confirmed

- `.version{color:red}` compiles to `.version.svelte-hash{color:red}` = specificity (0,2,0) — reproduced independently (refute1.mjs, svelte@5.57.0). This matches Astro's `.version[data-astro-cid-3oqgkrws]` at (0,2,0) exactly, verified against /home/mherwig/dev/grimoire-indexer/.claude/rules/quality-css-overrides.md:24. Doctrine point 2 holds unmodified for Svelte.
- `.foo .bar{}` → `.foo.svelte-X .bar:where(.svelte-X){}` = (0,3,0). Reproduced (refute1.mjs/refute6.mjs). The numeric tuple is right even though the prose describing WHERE the hash lands is wrong (see refuted).
- Bare element `p{}` → `p.svelte-X{}` = (0,1,1), which beats a consumer's unlayered `p{}` at (0,0,1). Reproduced (refute1.mjs).
- @layer blocks inside a component `<style>` are preserved AND correctly scoped in svelte@5.57.0; the 2022 stripping bug (sveltejs/svelte#7504) is fixed. Reproduced: `@layer base,special;@layer special{.item{...}}` → `@layer base,special;@layer special{.item.svelte-14o2oe3{...}}`. Notably a live 2026 web search STILL surfaces the stale 'styles inside the layer are stripped' claim, which makes this a genuine, current trap.
- No built-in mechanism puts component CSS into a named layer. The `css` compiler option is only `'injected' | 'external' | (fn)` (node_modules/svelte/types/index.d.ts:1069); no layer option exists anywhere in the type surface. sveltejs/svelte#11345 confirmed still OPEN via GitHub API (created 2024-04-18, updated 2025-09-04, closed_at: null). Component CSS therefore lands unlayered by default, which outranks every named layer — this genuinely inverts doctrine point 3's assumed baseline.
- The prescribed preprocess workaround genuinely works end to end. Reproduced (refute5.mjs): hook `{ style: ({content}) => ({ code: `@layer svelte { ${content} }` }) }` run through `preprocess` then `compile` yields `@layer svelte { .btn.svelte-7wqwd3{color:red} @media(...){.btn.svelte-7wqwd3{...}} }` — scoping applied correctly inside the layer, zero warnings.
- Unmatched selectors are DELETED, not merely outranked: a rule targeting a child component's class compiles to `/* (unused) .child-internal-class{color:red}*/` with warning code `css_unused_selector`. Reproduced (refute2.mjs). This is a stronger and more silent failure than the core doctrine anticipates.
- Pruning also operates INSIDE a layer, and `:global()` inside a layer stays in that layer. Reproduced (refute7.mjs): `@layer mylib{.used{...}.never{...}}` → `@layer mylib{.used.svelte-X{...}/* (unused) .never{...}*/}`; `@layer mylib{:global(.ext){...}}` → `@layer mylib{.ext{...}}`. Useful and not previously stated.
- Passing any `--custom-property` to a component instance wraps it in `<svelte-css-wrapper style="display: contents">`, and `<g>` in SVG context. Both reproduced from actual emitted JS (refute2.mjs, refute3.mjs): `$.from_html('<svelte-css-wrapper style="display: contents"><!></svelte-css-wrapper>')` plus `$.css_props(...)`; SVG case emitted `<g>`. The `>`-combinator breakage is a real consequence.
- `:root{...}` inside a component `<style>` block is neither scoped nor pruned — emitted verbatim as `:root{--brand:blue}` alongside the scoped `.card.svelte-X`. Reproduced (refute1.mjs). The cross-component collision hazard the researcher draws from this is sound.
- @keyframes names are hashed (`spin` → `svelte-1gu34b2-spin`, with the `animation` shorthand rewritten to match) and `-global-` opts out (`-global-glow` → `glow`). Reproduced (refute3.mjs).
- Svelte component libraries ship UNCOMPILED .svelte source via @sveltejs/package — CONFIRMED at HIGH confidence, upgrading the researcher's own 'medium' from a search snippet to primary source. @sveltejs/package@2.5.8 `src/index.js` imports only `preprocess`, never `compile`, and writes the .svelte file through. The scoping/layer transform genuinely runs only at the consuming app's build, with the consumer's svelte version.

### Unverifiable

- That the preprocess layer-wrapping hook is 'the documented community workaround'. It demonstrably WORKS (I reproduced it), but it appears in the sveltejs/svelte#11345 issue thread, not in official Svelte documentation. A published rule should present it as a community pattern, not a documented API — it carries no compatibility guarantee.
- The theme-switching guidance (`$app/environment` + `$effect`, `data-theme` on `<html>` via app.html). Not tested; it is generic CSS practice with a Svelte-flavored wrapper. The researcher's own conclusion that there is 'no Svelte-specific tier interaction to document' is probably right, which also means this field contributes nothing to the annex.
- The exact default `cssHash` implementation body. I proved empirically that filename affects the output hash and read the getter's signature, but did not locate and read the default function itself, so the precise input string it hashes is unconfirmed.
- Whether a real SvelteKit `vite build` preserves an author-written `@layer` through minification into the final bundle. I verified the COMPILER preserves it, but the full app-build path was not executed (npm install for a fixture app was blocked by the sandbox). Given the layer is plain CSS text that lightningcss/esbuild preserve, this is very likely fine — but it is the one link in the chain I did not run, and it is exactly the link the consumer-fixture test exists to cover.

### On the annex call

Agree — annex_worth_it: true is justified, and it is not padding. But two of the three supporting arguments need repair before they are written down.

What genuinely earns the annex, in order of value:

1. **Compile-time DELETION of unmatched selectors.** This is the strongest item and it is unique among the frameworks in this rule set. Nothing in the core doctrine prepares an agent for a rule that vanishes with no visual effect, no DOM-inspector trace, and only a build-log warning. Reproduced: `/* (unused) .child-internal-class{color:red}*/` + `css_unused_selector`.

2. **The unlayered-by-default baseline inverts doctrine point 3.** Svelte is the case where the core's "the fix is cascade layers" is not merely absent but backwards — component CSS defaults into the anonymous layer, which BEATS every named layer, so a consumer's Tailwind v4 `@utilities` loses to a component rule. And the remedy is a hand-added preprocess hook the core would never surface. Verified: no layer option in the compiler type surface, #11345 open.

3. **The packaging model.** Real and Svelte-specific — but the researcher drew the wrong conclusion from it (see refuted #2). The annex-worthy fact is "your dist contains .svelte source, so assert the layer contract against `dist/**/*.svelte` text, not compiled CSS", NOT "you cannot test this in your own repo."

Where the rationale needs repair: argument (3) as written would send an agent to build a consumer fixture for a contract it can check with a one-line assertion over its own dist. And the annex must NOT ship the prescribed grep test or the `startsWith('@layer name{')` assertion — both are broken (refuted #1, #6), and shipping a contract test that cannot fail is strictly worse than shipping none, because it manufactures false confidence in exactly the invariant the whole rule exists to protect.

Two fields should be dropped as annex content: `theme_switching` (the researcher's own text concedes there is no Svelte-specific interaction) and the generic half of `token_exposure`. Both repeat the core. The keeper from `token_exposure` is the `:root`-in-a-component collision hazard, which is Svelte-specific and verified.

Not a clean bill of health. The descriptive core is solid and reproduces; the enforcement machinery does not, and that is the half a published rule actually ships.

Everything I could reproduce, I reproduced independently rather than re-running the researcher's scripts — fresh test files refute1.mjs through refute7.mjs in /tmp/claude-1000/-home-mherwig-dev-grimoire-lore/02df8e5f-0fb1-4b65-a7c7-c9e23829614b/scratchpad/svelte-test/, against the same svelte@5.57.0 install. Every specificity tuple in the findings survived: (0,2,0) single class, (0,3,0) descendant, (0,1,1) bare element. The Astro parity claim that doctrine point 2 rests on is real — I checked it against /home/mherwig/dev/grimoire-indexer/.claude/rules/quality-css-overrides.md:24 and both are (0,2,0). No tuple is inverted. The override contract is not at risk from the numbers.

The damage is concentrated in doctrine point 5, the contract test. The prescribed grep produces a FALSE NEGATIVE on minified CSS — I built a bundle containing a genuinely leaked unlayered rule and the check passed silently. This is the worst possible failure mode for a rule set whose entire premise is "a contract nobody tests is a contract that has already broken": it would ship a test that can never break, and the repo would look protected while being wide open. The tell is that this project already solved this correctly — grimoire-indexer's build.test.ts brace-matches the layer body in JS (lines 855-872) specifically because a regex cannot survive minification. The annex should reuse that shape. Its own rule file even explains why, calling the bundle check "the honest form and the reason the source checks are not enough on their own."

Second substantive correction: the researcher was right that svelte-package ships uncompiled .svelte (I upgraded this from their medium to high by reading the package source — it imports `preprocess` and never `compile`), but wrong about the consequence. Because svelte-package runs the preprocessor, a layer-wrapping hook bakes `@layer name { ... }` into the shipped .svelte files. The library CAN test its own contract in its own CI. Their conclusion sends agents to build a consumer fixture for something a text assertion over dist covers.

Third, and the item the brief specifically warned about: no version boundary. Every specificity claim here is Svelte 5-only. The uniform +0,1,0 `:where()` hybrid scoping landed in PR #10443 for Svelte 5; Svelte 4 scoped non-uniformly with higher bumps. The findings stamp "svelte@5.57.0" as a version *checked* but never say the behavior *changed at 5*, which is the thing that makes a published rule wrong in somebody else's Svelte 4 repo. This is precisely the failure the ground rules called out and it slipped through.

Two smaller errors worth fixing before publication because they'd waste an agent's time rather than mislead the contract: the hash is a function of filename AND style content (proven — same CSS, different filename, different hash), so renaming a file rotates every hash and no literal hash should ever be pinned; and the prescribed `startsWith('@layer name{')` assertion fails on correct code because the emitted CSS preserves the wrapper's whitespace as `@layer name { `.

One gap I could not close: the sandbox blocked `npm i` for a fixture app, so I verified the compiler preserves `@layer` but never ran a full SvelteKit `vite build` end to end. That is the single unexercised link, and it happens to be the exact link a consumer-fixture test would cover — so the recommendation to keep a (correctly written) fixture check stands, just as the narrow second tier rather than the primary contract.

Net: keep the annex, keep every tuple, rewrite the testability section, and stamp the versions.
