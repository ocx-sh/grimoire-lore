## Summary

- Conan 2's `CMakeDeps`/`CMakeToolchain` pair is the default CMake integration; an **experimental** `CMakeConfigDeps` generator (since Conan **2.25**) is the stated future — Conan's own docs say "fixes, support, new features and maintenance is expected mainly in `CMakeConfigDeps`" and it can be switched on globally with `-c tools.cmake.cmakedeps:new=will_break_next` with zero recipe changes.
- `CMakeConfigDeps` never generates `FindXxx.cmake` module files — module-mode generation is explicitly "not planned" — so any codebase whose `find_package(... MODULE)` calls assume Conan-authored Find modules must stay on `CMakeDeps` or add its own modules.
- The cmake-conan dependency-provider bridge (`conan_provider.cmake`, hooked via `CMAKE_PROJECT_TOP_LEVEL_INCLUDES`) is explicitly **unstable**: "This `cmake-conan` project stability is not guaranteed, and it has some known issues and limitations," and Conan's own docs still recommend calling `conan install` explicitly before `cmake` as "the preferred and most recommended flow for most cases."
- The provider bridge only reliably auto-detects settings on the three most common platform/compiler pairs (Windows+MSVC, Linux+gcc, macOS+clang); single-config generators additionally require `CMAKE_BUILD_TYPE` to be set or the bridge cannot pick a Conan build type.
- CMake's own `cmake_language(SET_DEPENDENCY_PROVIDER)` (introduced **CMake 3.24**) is the neutral seam every provider (Conan, vcpkg) plugs into: **only one provider can be active at a time** system-wide, it must be registered from a file named by `CMAKE_PROJECT_TOP_LEVEL_INCLUDES` (itself CMake 3.24, module-name support added 3.29) while the first `project()` call is still executing, and it supports exactly two intercept points — `FIND_PACKAGE` and `FETCHCONTENT_MAKEAVAILABLE_SERIAL`.
- vcpkg's `VCPKG_MANIFEST_MODE` auto-turns on the moment a `vcpkg.json` exists next to the toolchain-driven `CMakeLists.txt`; all vcpkg-affecting CMake variables (triplet, manifest features, overlay ports) **must be set before the first `project()` call**, matching CMake's own toolchain-file timing rule and the same trap that catches Conan's provider.
- vcpkg's binary cache defaults to a `files` provider at `%LOCALAPPDATA%\vcpkg\archives` / `$XDG_CACHE_HOME/vcpkg/archives`; every non-default, non-`nuget` binary/asset-cache backend (`x-azblob`, `x-gcs`, `x-cos`, `x-aws`, `x-az-universal`, `x-azcopy*`) is marked "**Experimental: will change or be removed without warning**" as of the 2025-12-15 revision, and `x-gha` (the GitHub-Actions-cache provider) has been **removed outright**.
- vcpkg's ABI hash — the binary-cache key — folds in every port file, the triplet file, both compiler executables' identity, selected features, the CMake and PowerShell versions, and toolchain-file text; changing any of those silently invalidates the cache with no diagnostic beyond a cache miss.
- Conan lockfiles (`conan.lock`, format version `"0.5"` as documented) pin recipe **and package revisions**, not just versions, and are picked up implicitly by `conan install`/`conan graph info`/`conan create` merely by being present in the working directory — an implicit-pickup trap parallel to CMake's own cache-variable stickiness.
- vcpkg's parallel lock format is the pair `builtin-baseline` (in `vcpkg.json`) plus per-registry `baseline` (in `vcpkg-configuration.json`) plus the `versions/<letter>/<port>.json` files — three files must move together, and `vcpkg x-add-version` is the only sanctioned way to update them; the command is still `x-`-prefixed six-plus years after `vcpkg.json` itself shipped.
- **Hunter's `cpp-pm` fork is not dead**: `cpp-pm/hunter` shipped release **v0.26.11 on 2026-08-27** with a commit as recent as 2026-08-23, and 30 commits landed since 2024-01-01 — the requester's frame should not assume Hunter is abandoned. `ruslo/hunter` (the pre-fork upstream) last committed **2019-12-26**, confirming `cpp-pm` is the maintained line, but Hunter's own newest exemplar templates (`cmake-init`, `cmake_template`, `ModernCppStarter`, `project_options`) contain zero `HunterGate` references — CPM.cmake and vcpkg/Conan have displaced it in current scaffolding even where the tool itself is alive.
- CPM.cmake is also actively maintained: latest release **v0.43.1 (2026-07-06)**, commits as recent as the same date; it is a "thin wrapper around CMake's `FetchContent`" adding version control, a source cache (`CPM_SOURCE_CACHE`), and a single-line shorthand syntax (`gh:user/repo@version#tag`).
- CPM's own docs steer users toward reproducibility: "For maximum security and reproducibility, always prefer specifying immutable git commit hashes instead of tags or branches," directly contradicting the common CPM snippet culture of pinning a floating tag.
- `CPM_USE_LOCAL_PACKAGES` makes `CPMAddPackage` try `find_package()` first and only fetch source on a miss — the exact mechanism the frame flagged as the "does FetchContent silently shadow the system copy" risk, except here it is opt-in and CPM-native rather than silent.
- Conan Center Index's own recipe rules default every new recipe to `shared=False` / `fPIC=True` (or `implements = ["auto_shared_fpic"]`), and instruct authors to strip the `compiler` setting from `package_id()` for header-only packages — both are policy defaults that silently change binary compatibility if skipped.
- vcpkg's maintainer guide runs a stricter, betterdocumented "must" list than Conan Center's: ports must install simultaneously with every other curated port, must be tested on at least one **official** triplet, must not vendor dependencies, must use an `unofficial-<port>` CMake-config namespace for any target vcpkg itself adds, and any two concurrently-usable ports must never install the same file (checked continuously in CI as `FILE_CONFLICTS`).
- Conan's `conan audit` (added **2.14.0**, experimental) and vcpkg have no exact equivalent for the curated registry itself — vcpkg's answer is upstream-maintenance policy ("packaged projects should be stable and actively maintained... may be delisted") rather than a CVE scanner bundled with the tool.
- Conan workspaces (`conanws.yml`/`conanws.py`) are explicitly called an "**incubating feature**" for monorepo/local multi-package development — not yet a documented stable surface, and any rule referencing it must say so.
- Real dual-build-system exemplars (abseil, grpc, protobuf, googletest) all carry `BUILD.bazel` **and** `MODULE.bazel` **and** `CMakeLists.txt` side by side in this corpus's checkouts, confirming the frame's "two build descriptions in sync" scenario is not hypothetical.
- FetchContent appears directly (not via CPM) in `fmt`, `nlohmann/json`, `ninja`, and `protobuf`'s own `CMakeLists.txt` in this corpus, so a rule about `FetchContent`-vs-`find_package` shadowing has real fleet-adjacent precedent even though the fleet itself has no C++ code.
- vcpkg's platform-expression identifiers (`windows`, `linux`, `osx`, `static`, `staticcrt`, `native`, …) and version-field set (`version`, `version-semver`, `version-date`, `version-string`, each mutually exclusive) are exact, quotable schema surfaces a rule's verification step can grep for.
- The comparison set (Meson wrapdb, build2/cppget.org, xmake/xrepo, pixi/conda-forge, Spack, Nix) each solve a different half of the dependency problem — Meson's CMake-subproject bridge requires a hand-written `meson.build` shadow with no `CMakeLists.txt` fallback path; Spack and Nix both work purely through `CMAKE_PREFIX_PATH` injection with no bespoke CMake API; xrepo ships a `xrepo-cmake` wrapper specifically to expose its packages to plain `find_package()`-style CMake consumers.

### 2. CMakeToolchain generator reference

Generates `conan_toolchain.cmake` (translates settings to CMake vars), `conanvcvars.bat`, and `CMakePresets.json` (schema 3, CMake ≥3.21) plus `CMakeUserPresets.json` (schema 4, CMake ≥3.23, skipped if a non-Conan-authored copy already exists). Key attributes: `variables`, `cache_variables`, `preprocessor_definitions`, `presets_build_environment`/`presets_run_environment`, `user_presets_path`, `extra_cxxflags`/`extra_cflags`/`extra_sharedlinkflags`/`extra_exelinkflags`, `absolute_paths`, `presets_prefix` (default `"conan"`), `add_rpath_link`. Uses a block system (19+ named blocks, e.g. `generic_system`, `compilers`, `fpic`, `cppstd`, `find_paths`) selectable via `tools.cmake.cmaketoolchain:enabled_blocks`. Custom-toolchain composition via `tools.cmake.cmaketoolchain:toolchain_file` (replace) or `:user_toolchain` (include, recommended). macOS universal binaries (`arch=armv8|x86_64`) are marked experimental. [docs.conan.io/2/reference/tools/cmake/cmaketoolchain.html](https://docs.conan.io/2/reference/tools/cmake/cmaketoolchain.html)

### 3. CMakeDeps and CMakeConfigDeps generators

`CMakeDeps` emits `XXX-config.cmake` (+ optional `FindXXX.cmake` when `cmake_find_mode` is `module`/`both`), version files honoring `cmake_config_version_compat` (`SameMajorVersion` default; `AnyNewerVersion`/`SameMinorVersion`/`ExactVersion` also valid), and a Conan-1-compat `conandeps_legacy.cmake`. `CMakeConfigDeps` (experimental, since **Conan 2.25**) is the documented successor: real `SHARED`/`STATIC`/`INTERFACE IMPORTED` targets instead of synthetic interface targets, dependency-specific (not consumer) build-type matching, `IMPORTED_LOCATION`/`IMPORTED_IMPLIB`/`LINK_LANGUAGES` set directly, no `build_context_activated`/`build_context_suffix` needed for `tool_requires`, executable-target generation from `cpp_info.exe`; it never emits `FindXxx.cmake` and module support is "not planned." Migrate with `-c tools.cmake.cmakedeps:new=will_break_next`. [cmakedeps.html](https://docs.conan.io/2/reference/tools/cmake/cmakedeps.html) · [cmakeconfigdeps.html](https://docs.conan.io/2/reference/tools/cmake/cmakeconfigdeps.html)

### 4. Conan/CMake integration page and cmake-conan limitations

The Integrations→CMake page names four tools (CMakeDeps, CMakeConfigDeps, CMakeToolchain, the CMake build helper) and the separate `cmake-conan` project, which hooks CMake's dependency-provider mechanism to auto-run `conan install` on the first `find_package()`. Stability quote: "This `cmake-conan` project stability is not guaranteed, and it has some known issues and limitations," with explicit preference stated for calling `conan install` manually before `cmake`. [docs.conan.io/2/integrations/cmake.html](https://docs.conan.io/2/integrations/cmake.html) · README fetched raw from [conan-io/cmake-conan `develop2` branch](https://raw.githubusercontent.com/conan-io/cmake-conan/develop2/README.md): recommends `CMakeConfigDeps` specifically for this flow; auto-detection is reliable only on Windows+MSVC/Linux+gcc/macOS+clang; single-config generators require `CMAKE_BUILD_TYPE`; and `find_program`/`find_library`/`find_path`/`find_file` calls issued before the first `find_package()` "may not work correctly."

### 5. CMAKE_PROJECT_TOP_LEVEL_INCLUDES and SET_DEPENDENCY_PROVIDER (canonical CMake docs)

`CMAKE_PROJECT_TOP_LEVEL_INCLUDES` (CMake **3.24**; module-name form added 3.29) names files included "immediately after the toolchain file has been read... and platform variables have been set, but before any languages have been enabled" — explicitly for "configuring package managers," not toolchain setup (language-specific compiler variables aren't populated yet). `cmake_language(SET_DEPENDENCY_PROVIDER <command> SUPPORTED_METHODS <methods>...)` (also 3.24) accepts `FIND_PACKAGE` and `FETCHCONTENT_MAKEAVAILABLE_SERIAL` as the only two supported methods; **only one provider can be active** at a time; it can only be set while a `CMAKE_PROJECT_TOP_LEVEL_INCLUDES` file is being processed; the named command must already exist; an empty command string clears the provider. Naming convention: `xxx_provide_dependency()`. [Help/variable/CMAKE_PROJECT_TOP_LEVEL_INCLUDES.rst](https://gitlab.kitware.com/cmake/cmake/-/raw/master/Help/variable/CMAKE_PROJECT_TOP_LEVEL_INCLUDES.rst) · [Help/command/cmake_language.rst](https://gitlab.kitware.com/cmake/cmake/-/raw/master/Help/command/cmake_language.rst)

### 6. Conan profiles

Sections: `[settings]` (from `settings.yml`), `[options]` (pattern-scoped, e.g. `mypkg/*:shared=True`), `[tool_requires]`, `[conf]` (overrides `global.conf`), `[buildenv]`/`[runenv]` (support `+=`/`=+` operators), plus experimental `[replace_requires]`/`[replace_tool_requires]` and `[platform_requires]`/`[platform_tool_requires]` for system-provided deps. Profiles are Jinja2-rendered (access to `platform`, `os`, `subprocess`, a `detect_api` helper) and composable via `include()`. Conan's two-profile model separates build (`-pr:b`) from host (`-pr:h`) context; bare `-pr` sets both. [docs.conan.io/2/reference/config_files/profiles.html](https://docs.conan.io/2/reference/config_files/profiles.html)

### 7. Conan lockfiles

`conan.lock` is JSON (`"version": "0.5"` format tag seen), pinning `requires`/`build_requires`/`python_requires` down to `name/version#recipe_revision%timestamp` tuples. Commands: `conan lock create .`, `conan lock add --requires=...`, `conan lock merge --lockfile=A --lockfile=B`; consumed via `conan install . --lockfile=conan.lock`, produced via `--lockfile-out=conan.lock`; `--lockfile-partial` relaxes strictness, `--lockfile-clean` drops unused entries. A `conan.lock` present in the working directory is picked up **implicitly** by `install`/`graph info`/`create`. [docs.conan.io/2/tutorial/versioning/lockfiles.html](https://docs.conan.io/2/tutorial/versioning/lockfiles.html)

### 8. Conan cache, graph, audit, list/pkglist, and workspace commands

`conan cache`: `path` (locate export/source/build/metadata folders), `clean` (drop non-critical folders by pattern), `check-integrity` (verify against `conanmanifest.txt`), `save`/`restore` (archive/import the cache for CI portability, `.tgz`/`.txz`/`.tzst`), `ref` (debug reverse-lookup), `backup-upload`, and experimental `sign`/`verify`. `conan graph`: `info`, `build-order`, `build-order-merge`, `explain` ("showing missing binaries, closest alternatives, and why they do not match"), `outdated`. `conan audit` (introduced **2.14.0**, experimental): `scan` (recipe + transitive deps against a vulnerability provider, default ConanCenter), `list` (direct refs/SBOM/lockfile, no transitive walk), `provider {add,list,auth,remove}`. `conan list`/pkglist: pattern syntax `name/version@user/channel#rrev:pkgid#prev`, `--format=json|html|compact`, `--package-query`, `--graph=<file>` to list from a computed graph, `--lru` for staleness; explicit warning "The text output in the terminal should never be parsed or relied on for automation." Conan workspace (`conanws.yml`/`conanws.py`) is called an "incubating feature" for monorepo super-builds with a super-project `ConanFile` defining shared `layout`/`generators`. [reference/commands/cache.html](https://docs.conan.io/2/reference/commands/cache.html) · [reference/commands/graph.html](https://docs.conan.io/2/reference/commands/graph.html) · [reference/commands/audit.html](https://docs.conan.io/2/reference/commands/audit.html) · [reference/commands/list.html](https://docs.conan.io/2/reference/commands/list.html) · [reference/workspace_files.html](https://docs.conan.io/2/reference/workspace_files.html)

### 12. vcpkg.json schema

Top-level: `builtin-baseline`, `default-features`, `dependencies`, `description`, `documentation`, `features`, `homepage`, `license` (SPDX expression with a documented EBNF grammar), `maintainers`, `name`, `overrides`, `port-version`, `supports` (Platform Expression), the mutually-exclusive version quartet `version`/`version-semver`/`version-date`/`version-string`, and an embeddable `configuration` (a.k.a. `vcpkg-configuration`) block — illegal to combine with a sibling `vcpkg-configuration.json` file. Dependency objects carry `name`, `default-features`, `features`, `host` (cross-compilation: build for the host triplet, required for any tool/codegen dependency), `platform`, and `version>=`. Platform Expression grammar: `!`/`not` negation, `|`/`,` OR, `&`/`and` AND, parens for grouping, identifiers keyed to triplet settings (`x64`, `arm64`, `windows`, `linux`, `osx`, `static`, `staticcrt`, `native`, …). [reference/vcpkg-json](https://learn.microsoft.com/en-us/vcpkg/reference/vcpkg-json)

### 13. vcpkg-configuration.json schema

Top-level: `default-registry`, `overlay-ports`, `overlay-triplets`, `registries`. Registry kinds: `filesystem`, `git`, `builtin`; fields `kind`, `baseline` (40-char git SHA for git/builtin, arbitrary JSON property name for filesystem), `reference` (git ref, default `HEAD`), `repository`, `path`, `packages` (name or `prefix*` glob, added in **tool version 2022-12-14**). Only the top-level project's `vcpkg-configuration.json` is honored — dependencies' copies are ignored. [reference/vcpkg-configuration-json](https://learn.microsoft.com/en-us/vcpkg/reference/vcpkg-configuration-json)

### 14. vcpkg triplet variables

Per-port customization keys off the `PORT` variable inside triplet files. [users/triplets](https://learn.microsoft.com/en-us/vcpkg/users/triplets)

### 15. vcpkg binary caching

Default source: `files` provider at a per-OS default path. `VCPKG_BINARY_SOURCES` grammar: `clear`, `default[,<rw>]`, `files,<path>[,<rw>]`, `nuget,<uri>[,<rw>]`, `nugetconfig,<path>[,<rw>]`, `nugettimeout,<seconds>`, `http,<url_template>[,<rw>[,<header>]]` (template vars `{name}`,`{version}`,`{sha}`,`{triplet}`), and a long experimental tail all marked "**will change or be removed without warning**": `x-azblob`, `x-azcopy`, `x-azcopy-sas`, `x-gcs`, `x-aws`/`x-aws-config`, `x-cos`, `x-az-universal`. **`x-gha` (GitHub Actions cache) has been removed from vcpkg entirely** — the docs mark it "Removed: This feature has been removed from vcpkg." `interactive` enables NuGet interactive credential debugging. The ABI hash — vcpkg's cache key — is documented exhaustively: every port-directory file, triplet file contents+name, both compiler executable identities, selected features, each dependency's ABI hash, referenced helper functions (heuristic), CMake version, PowerShell version, `VCPKG_ENV_PASSTHROUGH` variable contents, and the toolchain file's textual contents. [reference/binarycaching](https://learn.microsoft.com/en-us/vcpkg/reference/binarycaching) · [users/binarycaching](https://learn.microsoft.com/en-us/vcpkg/users/binarycaching)

### 16. vcpkg asset caching

`X_VCPKG_ASSET_SOURCES` grammar: `clear`, `x-azurl,<url>[,<sas>[,<rw>]]` (also accepts `file://` UNC-style endpoints), `x-block-origin` (disable falling back to the real upstream URL on a cache miss), `x-script,<template>` (external fetcher, template vars `{url}`,`{sha512}`,`{dst}`). Purpose: mirror upstream **source** downloads (not built binaries) for disconnected/offline CI. [users/assetcaching](https://learn.microsoft.com/en-us/vcpkg/users/assetcaching)

### 17. vcpkg maintainer guide

Design goals for the curated registry: ports must install simultaneously with every other curated port (no file conflicts, no test-for-presence-of-another-port logic — "path dependent" installs are explicitly forbidden and checked by CI as `FILE_CONFLICTS`), must be tested on at least one **official** triplet, and packaged projects "should be stable and actively maintained" (delisting risk otherwise) and "mature" (≥6 months of releases or public development). PR hygiene: one port per PR, no trivial reformatting, distinctive/disambiguated port names, renames locked for a year. Portfile rules: avoid deprecated helpers (`vcpkg_extract_source_archive_ex`, `vcpkg_apply_patches`, `vcpkg_configure_cmake`, `vcpkg_build_cmake`, `vcpkg_install_cmake`, `vcpkg_fixup_cmake_targets` all superseded), lowercase all hex strings (`SHA512`, `REF`, git-tree hashes), unique-file attribution across ports, `unofficial-<port>` CMake export namespace for any config vcpkg itself invents, `vcpkg_install_copyright()` for license files, minimal version constraints inside ports, `MAYBE_UNUSED_VARIABLES` entries must be commented with the configuration where they apply. Build technique rules: no vendored/embedded dependencies, prefer CMake when multiple buildsystems exist, must choose static-or-shared cleanly via `vcpkg_check_linkage(ONLY_STATIC_LIBRARY)` when a library can't support DLL export, don't rename binaries outside upstream's own naming, don't add `CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS` unless upstream already relies on it. Prebuilt-binary ports are "allowed but strongly discouraged" and rejected outright if they both (a) skip building from source and (b) expose an ABI surface ("published link domain") depending on other curated ports. Versioning: `x-add-version` (or `--all`) is the sanctioned way to regenerate `versions/baseline.json` and per-port version files; `port-version` increments for packaging-only changes, resets to 0 on an upstream bump. [contributing/maintainer-guide](https://learn.microsoft.com/en-us/vcpkg/contributing/maintainer-guide)

### 21. Comparison / provisioning set (briefly, by each project's own docs)

- **Meson wrapdb / CMake subprojects**: WrapDB hosts Meson-native or Meson-ported build definitions consumable as `subproject()`s; `wrap-git` mode has required full Meson build definitions in the target repo since **0.55.0** (patches now apply to any wrap mode, not just wrap-file). Meson's own CMake module can import a CMake project as a subproject, but a *wrap* still needs a `meson.build` — there's no fallback path that reads `CMakeLists.txt` directly for a wrap entry. [mesonbuild.com/Wrap-dependency-system-manual.html](https://mesonbuild.com/Wrap-dependency-system-manual.html), [mesonbuild/wrapdb](https://github.com/mesonbuild/wrapdb).
- **build2 / cppget.org**: a single toolchain bundling build system + package manager + project manager; cppget.org is stratified into stable/testing/beta/alpha/legacy channels, each with its own repository location. [build2.org](https://build2.org/), [cppget.org](https://cppget.org/).
- **xmake / xrepo**: Lua-based build system (xmake) with an independent package manager (xrepo) that can *also* pull from vcpkg/Conan/conda/apt as upstream sources; ships `xrepo-cmake`, a CMake-side wrapper specifically so plain-CMake consumers can `find_package()`-style consume xrepo packages without adopting xmake itself. [xmake-io/xrepo-cmake](https://github.com/xmake-io/xrepo-cmake), [xrepo.xmake.io](https://xrepo.xmake.io/).
- **pixi / conda-forge**: pixi-build's `compilers = ["c","cxx"]` field selects conda-forge's platform-specific, ABI-tagged compiler packages per build/host platform — cross-compilation is a first-class conda-forge concept (`compiler()` Jinja function, `build`/`host` requirement split), not a CMake toolchain-file exercise. [prefix.dev/blog/pixi-build-for-cmake-projects](https://prefix.dev/blog/pixi-build-for-cmake-projects), [conda-forge.org cross-compilation](https://conda-forge.org/docs/how-to/advanced/cross-compilation/).
- **Spack**: integrates with CMake purely by injecting `CMAKE_PREFIX_PATH` for every dependency spec and setting `CMAKE_INSTALL_RPATH`/`CMAKE_INSTALL_RPATH_USE_LINK_PATH=ON` — no Spack-specific CMake API or generated config files, unlike Conan/vcpkg. [spack.readthedocs.io CMake build system](https://spack.readthedocs.io/en/latest/build_systems/cmakepackage.html).
- **Nix (nixpkgs cmake setup hook)**: overrides the configure phase to invoke `cmake` (auto-selecting Ninja if present), appends every dependency to `CMAKE_PREFIX_PATH` automatically, and exposes `cmakeFlags`/`cmakeFlagsArray` for extra arguments — a pure environment-injection model with no lockfile of its own (the Nix store hash *is* the lock). [nixpkgs doc/hooks/cmake.section.md](https://github.com/NixOS/nixpkgs/blob/master/doc/hooks/cmake.section.md).
- **OCX find_ocx** (fleet's own tool, read for contrast only): tool provisioning via a pinned sha256-verified CLI bootstrap; reproducibility tiers are explicit and named — commit an `INDEX` snapshot, pin a package digest (`@sha256:`), or float and read the resolved digest from the configure log; exports `<name>_ROOT` (CMP0074) for a following `find_package`; offline/mirror knobs are `OCX_MIRRORS`, `OCX_INSTALL_MIRROR_URL`, `OCX_OFFLINE`, `OCX_FROZEN`, `OCX_INSECURE_REGISTRIES`. [find_ocx/README.md](/home/mherwig/dev/find_ocx/README.md) (local, read directly per frame instructions).

## Recent shifts seen in this corpus

- **CMake 3.24 (2022) → now (4.4.1, 2026-07-29 per the fleet's own mirror survey)**: `cmake_language(SET_DEPENDENCY_PROVIDER)` and `CMAKE_PROJECT_TOP_LEVEL_INCLUDES` are the entire foundation both Conan's and vcpkg's newer integration stories lean on; any advice written against a pre-3.24 CMake ("just set `CMAKE_TOOLCHAIN_FILE`") is still correct but incomplete for anything claiming provider-based integration.
- **Conan 2.25 (CMakeConfigDeps) and the cmake-conan `develop2` branch's stated preference for it**: text written against `CMakeDeps` as "the" generator, dated before 2.25, is not wrong but is now the legacy-recommended path per Conan's own docs, and any migration guidance older than this needs to check whether `FindXxx.cmake` module consumers exist before switching.
- **Conan 2.14.0 (`conan audit`)**: security-scanning is now a native (if experimental) Conan verb; guidance written before this release recommending only third-party SCA tools for Conan graphs is incomplete, not wrong.
- **vcpkg's removal of `x-gha`** (exact removal date not fetched, but the docs mark it past-tense "has been removed"): any CI recipe or tutorial snippet using `x-gha` for GitHub-Actions-native vcpkg caching is now dead advice — the NuGet-over-GitHub-Packages path is the documented replacement.
- **vcpkg maintainer guide's PR/triplet policy tightening** (`ms.date: 2026-02-18` on the fetched maintainer-guide page): the "official triplet only" and "no non-community triplet requests at this time" language reads as a deliberate 2025–2026 tightening versus vcpkg's earlier, looser triplet-acceptance era.
- **`cpp-pm/hunter` still shipping in August 2026**: this corpus found no evidence Hunter is dead; what changed is community *mindshare* (zero HunterGate references across four current C++ project-template generators checked), not upstream activity — worth stating precisely rather than as "Hunter is abandoned."
- **CPM.cmake 0.43.x (July 2026) supply-chain-security language**: the explicit commit-hash-over-tag recommendation reads as newer, hardened guidance layered onto the original shorthand-syntax convenience feature — any pre-existing snippet using bare `@version` tags predates this framing.

## Contested

- **Whether `CMakeConfigDeps` should be recommended today.** Conan's docs pull two directions at once: they call it experimental and "subject to breaking changes," yet also say new fixes and features land there first and cmake-conan's `develop2` README recommends it specifically for provider-based flows. Trend: toward `CMakeConfigDeps` becoming the default, but not there yet as of the 2.25–2.32 window fetched.
- **Whether the dependency-provider bridge (cmake-conan) or an explicit `conan install` step is the right default flow.** Conan's own integration page states a preference for the explicit flow "for most cases," while simultaneously documenting and improving the provider bridge. No clear resolution in this corpus; treat as an open choice a project must make deliberately, not a default to inherit silently.
- **Hunter's relevance going forward.** The tool is maintained (evidence in section 18), but zero uptake was found in four current C++ project-template generators in this exemplar corpus, all of which reach for CPM.cmake or vcpkg/Conan instead. Trend: usage is moving away from Hunter even though the fork itself has not stalled — a "maintained but not chosen" state distinct from "abandoned."
- **Whether vcpkg's growing `x-`-prefixed binary/asset-cache surface (six-plus experimental providers, one already removed) should be treated as production-ready.** The docs are internally consistent (everything non-default is explicitly marked experimental) but the sheer number of `x-`-prefixed options in active use across the ecosystem (per general community discussion, not fetched as primary source here) suggests de facto reliance outpacing the documented stability guarantee.
- **Bazel interop scope for Conan's `BazelDeps`/`BazelToolchain`.** This corpus's fetch of Conan's own Bazel integration page did not state Bzlmod support explicitly; whether that's a documentation gap or an accurate reflection of `WORKSPACE`-only support needs a BZL-CC cross-check (candidate #29) before either program writes a rule assuming either answer.
