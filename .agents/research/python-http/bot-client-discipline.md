## Summary

- httpx's implicit default timeout is 5s across all four axes (connect/read/write/pool); the bot never relies on it — every call path resolves to an explicit 30.0s deadline, either per-call (`registry_v2.py`) or client-level (`github_api.py`). Zero unbounded calls, zero missing-timeout call sites in `src/`.
- `RegistryV2` holds one `httpx.Client` for its whole process lifetime (dataclass field, correct). `GitHubApi` constructs and tears down a fresh `httpx.Client` on **14** separate call sites — one per public method — so a single CLI invocation touching several GitHub endpoints opens that many TCP+TLS handshakes to `api.github.com` instead of pooling them.
- The bot's own retry loop (`core/backoff.py` + `adapters/registry_v2.py`) implements AWS's "equal jitter" algorithm correctly: `min(30, 1.0 * 2**(attempt-1)) * (0.5 + jitter)`, 5 attempts, `Retry-After` wins outright when positive. This machinery is **not shared** with `github_api.py`, which classifies 401/429/5xx into `TransientError` but never sleeps-and-retries in-process for GitHub calls — an asymmetry worth an explicit decision, not obviously a bug.
- `registry_v2.py`'s pagination (`_parse_next_link`) explicitly rejects a `Link: rel="next"` header whose host differs from the client's own — real SSRF-via-pagination hardening, tested (`test_list_tags_rejects_cross_host_next_link`). `github_api.py`'s `_paginate` follows `response.links["next"]["url"]` on the same authenticated client **with no host check at all** — same pagination-authority pattern, no equivalent test, no equivalent guard.
- `httpx.Client`/`AsyncClient` do **not** follow redirects by default (`follow_redirects=False`); the bot never overrides this, so it inherits the safe default. But it also never handles a bare 3xx response explicitly — `raise_for_status()` only fires on >=400, so an unexpected 3xx from GHCR/GitHub would fall through to `response.json()` and fail as an unhandled `JSONDecodeError`, not a clean `IndexBotError`.
- `verify=` is never touched anywhere in `src/` — TLS verification stays on the httpx default (`True`) everywhere. No exposure found.
- `get_blob()`/`get_manifest()` read the full response body into memory via `response.content` with no size cap and no `.stream()` — the one clear gap against the sibling SDK's bar, which streams downloads through a 256 MiB cap and a 1 MiB chunk size (`ocx_sdk/_dist.py`).
- Of the 56 `cast(` sites, exactly **12** trace back to `response.json()` or `json.loads()` on registry-fetched bytes (the untyped-`Any` HTTP boundary): `registry_v2.py` (1), `core/desc.py` (6), `core/validate_entry.py` (4), `core/observe.py` (1). The other 44 split into 32 argparse-`Namespace` attribute casts (a different, non-HTTP axis), 5 local-file-read narrowing casts, 4 internal dataclass/Protocol narrowing casts, and 3 local-config-JSON casts.
- The codebase already contains the right pattern for a boundary validator — `core/policy.py`'s `load_registry_hosts` does `isinstance` checks and a regex on every field of a local JSON file before a single `cast` — it just isn't applied to the 12 registry-JSON sites, which each do ad hoc, inconsistent shape-checking instead of one reusable validator.
- No test in this repository reaches the real network. `github_api.py`/`registry_v2.py` unit tests run entirely under `@respx.mock` (transport-level interception, no socket ever opens); integration tests run against `ThreadingHTTPServer` fakes bound to `127.0.0.1:0` (a real socket, but loopback-only). Verified by grep: every `def test_` in both adapter test files is either respx-mocked or makes no HTTP call at all.
- httpx's own docs point straight at `tenacity` for anything beyond bare connection-failure retries (`HTTPTransport(retries=...)` only catches `ConnectError`/`ConnectTimeout`); Hynek Schlawack's `stamina` is an opinionated wrapper over `tenacity` built from watching people copy-paste the same jitter/cap boilerplate — the bot's hand-rolled `core/backoff.py` already reimplements that boilerplate correctly, so adding a dependency here would be a lateral move, not a fix.
- GitHub's documented backoff guidance (check `Retry-After`, else `x-ratelimit-reset`, else exponential backoff, never hammer through a 403) is followed for `Retry-After` but the bot never reads `x-ratelimit-remaining`/`x-ratelimit-reset` proactively — it only reacts after a 429/403 already happened.
- Credential-leak-on-cross-host-redirect is a real, historical CVE class in the Python ecosystem (CVE-2018-20060, `urllib3` < 1.23, CVSSv3 9.8) and httpx explicitly strips `Authorization` on a cross-origin redirect — but that protection covers HTTP 3xx only, not the bot's own manual "next link" re-request pattern in `github_api.py`, which is architecturally identical to a redirect and carries the same authenticated-client risk without the same guard.
- A malicious/compromised registry can inject terminal control sequences into a response header (e.g. `Retry-After`) that flows, uninterpolated with `!r`/`repr()`, into a `TransientError` message `main.py:146` prints straight to stderr — CWE-150 territory. One site in `registry_v2.py` (`AnomalyError` for digest mismatch) already guards this correctly via `!r`; `github_api.py`'s rate-limit message does not.
- Every one of the 7 canonical LLM HTTP mistakes the team lead named has a one-line mechanical grep check; all seven were watched going red against a planted violation and green against clean code in this session's scratch directory before being written into this document.

## Findings

### 1. Timeouts

httpx's documented default is exact: *"The default behavior is to raise a `TimeoutException` after 5 seconds of network inactivity"* ([httpx timeouts docs](https://www.python-httpx.org/advanced/timeouts/)), broken into four independent budgets — connect (socket handshake), read (waiting for a chunk of response body), write (waiting to send a chunk of request body), and pool (waiting to acquire a connection from the pool) — each settable individually via `httpx.Timeout(default, connect=..., read=..., write=..., pool=...)`, and settable per-client (`httpx.Client(timeout=...)`) or per-request (`client.get(url, timeout=...)`), with the per-request value overriding the client's. `timeout=None` disables every axis; the docs show the syntax with no warning attached, which is itself a footgun — a bot that disables timeouts has no bound on a stalled connection short of the OS TCP keepalive (often hours).

The bot never takes that path. `registry_v2.py` defines `_DEFAULT_TIMEOUT_SECONDS = 30.0` with a docstring explaining exactly why: *"Raised from 10s after a GHCR manifest GET stalled past it and failed a REQUIRED announce check... a request that has not answered inside 30s is a stall, not a slow transfer"* (`src/indexbot/adapters/registry_v2.py:104-109`), passed explicitly on every `client.request(...)` and `client.get(...)` call (`registry_v2.py:343`, `:393`). `github_api.py` sets `timeout: float = 30.0` as a dataclass field and bakes it into the client at construction (`github_api.py:83`, `:271`), so every one of the 14 `with self._client() as client:` blocks inherits it — a per-client default rather than per-call, which is fine because no call site overrides it downward and every call is short (JSON API, not a download).

Check for an unbounded call: any `httpx.Client(`/`httpx.AsyncClient(` construction line lacking `timeout=`, or any bare `httpx.<verb>(` call (which always inherits the library's silent 5s default rather than a stated one) — see [Rule R2/R1](#normative-guidance-candidates).

### 2. Client lifetime and connection reuse

httpx's own advice: *"if you're doing anything more than experimentation, one-off scripts, or prototypes, then you should use a `Client` instance"* — the top-level `httpx.get()` API *"establish[es] a new connection for every single request"*, where a `Client` gets *"HTTP connection pooling... [and] all of the cookies are stored across requests"* ([httpx clients docs](https://www.python-httpx.org/advanced/clients/)). Pool sizing lives in `httpx.Limits`: `max_connections=100`, `max_keepalive_connections=20`, `keepalive_expiry=5` seconds by default ([resource limits docs](https://www.python-httpx.org/advanced/resource-limits/)) — a client constructed and immediately closed never benefits from any of this, because the keep-alive pool it would have populated dies with it.

Measured in the bot: `RegistryV2` does this correctly — `client: httpx.Client = field(default_factory=httpx.Client)` (`registry_v2.py:239`) constructs exactly one client per `RegistryV2` instance, held for the instance's (i.e. the process's) whole lifetime, reused across `list_tags`/`get_manifest`/`get_desc_tag_digest`/`get_blob`/`_fetch_token`. `GitHubApi` does not: `_client()` (`github_api.py:270-271`) is called fresh inside a `with` block at **14 distinct call sites** (`github_api.py:91,100,111,123,145,153,171,194,203,214,224,240,251,303`), one per public method (`get_file_contents`, `get_ref_sha`, `commit_files`, `open_or_update_pull_request`, `add_labels`, `enable_auto_merge`, `get_pull_request_info`, `set_commit_status`, `request_reviewers`, `create_comment`, `create_or_update_issue`, `_paginate`). Within one method the client *is* threaded through to its own helpers (e.g. `open_or_update_pull_request` passes its one client into `_find_open_pull_request`), so it's not "new client per HTTP call" — it's "new client per public method call." But a single `indexbot` invocation routinely calls several of these methods back to back (commit files, then open/update the PR, then add labels, then enable auto-merge is a realistic sequence in `cli/announce.py`), each paying a fresh TCP+TLS handshake to the same host that a shared client-per-adapter-instance (matching `registry_v2.py`'s own pattern) would have pooled into keep-alive reuse. This is a static count, not a runtime profile — the bot was not executed to confirm socket counts, per this dive's read-only constraint.

`AsyncClient` is event-loop-bound: a client created on one loop cannot be reused on another (unclosed-connections/`RuntimeError` territory), which is why the resource-limits/clients docs don't surface loop-affinity warnings for the *sync* `Client` the bot uses everywhere — moot here, since nothing in `src/indexbot` constructs an `AsyncClient`.

### 3. Retries, backoff and idempotency

httpx is explicit about scope: `httpx.HTTPTransport(retries=N)` *"Requests will be retried the given number of times in case an `httpx.ConnectError` or an `httpx.ConnectTimeout` occurs"* and nothing else — no status-code retries, no read/write-error retries. The docs then point straight at an application-level tool: *"If you need other forms of retry behaviors, such as handling read/write errors or reacting to `503 Service Unavailable`, consider general-purpose tools such as [tenacity](https://github.com/jd/tenacity)"* ([httpx transports docs](https://www.python-httpx.org/advanced/transports/)). This is the load-bearing distinction: transport-level retries repair the TCP handshake; they cannot see an HTTP status code, so a bot that only sets `HTTPTransport(retries=3)` and calls it done has not implemented 429/5xx retry at all.

Idempotency is the reason retrying is a correctness question, not a tuning knob: GET/HEAD/PUT/DELETE are safe to replay because the server-visible effect of N identical calls equals one call; POST is not — a retried POST to `/pulls` or `/issues` can create the resource twice. Every retry loop in the bot's `src/` operates on GET/HEAD only (`registry_v2.py`'s `_send` covers `list_tags`, `get_manifest`, `get_desc_tag_digest`, `get_blob`, all reads); `github_api.py`'s POST/PATCH call sites (`open_or_update_pull_request`, `commit_files`, `add_labels`, etc.) are never wrapped in a retry loop at all — on 401/429/5xx they raise `TransientError` immediately via `_check_transient` and let the exit-75 contract (BD-2, `errors.py:45`) hand "retry later" to an outer rerun, not an in-process resend. That is a defensible design (a mutating call retried at the process level, after the caller sees the failure, is safer than an automatic in-process resend that might double-apply), but it means `core/backoff.py`'s jitter/cap machinery is effectively registry-only — GitHub calls get zero in-process resilience against a transient 5xx blip, where registry calls get five attempts with backoff. Nothing in the code comments this specific asymmetry (only the 401-never-retried case is explained, `github_api.py:279-286`); it reads as an unexamined gap rather than a decision, for the 429/5xx path specifically.

Where the bot does retry, the algorithm is textbook: `delay_seconds()` computes `min(max_delay_seconds, base_delay_seconds * 2**(attempt-1)) * (0.5 + jitter)` with `base_delay_seconds=1.0`, `max_delay_seconds=30.0`, `max_attempts=5` (`core/backoff.py:16-53`) — AWS's "Equal Jitter" variant from the canonical [Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) reference, with a positive `Retry-After` overriding the computation outright, matching the spec's own guidance (finding 4). `random.random()` is explicitly not for security use (`# nosec B311 - retry-jitter, not crypto`, `registry_v2.py:367`), correctly — jitter timing doesn't need a CSPRNG.

On the dependency question: adding `tenacity` (or Hynek Schlawack's `stamina`, an *"opinionated wrapper around the great-but-unopinionated Tenacity package"* built because its author got tired of *"years of copy-pasting the same configuration over and over again"* — [stamina docs](https://stamina.hynek.me/en/stable/)) is not justified here. The bot's own `core/backoff.py` already is that "stop copy-pasting the config" abstraction, purpose-built, 100%-coverable without mocking `random`/`time` per its own docstring, and correctly separates pure delay math (testable without I/O) from the imperative retry loop (`registry_v2.py:330-397`) — which is a *better* separation than either library gives out of the box, since neither `tenacity` nor `stamina` splits "what to wait" from "how to loop" as two independently-testable units. The gap is not "missing a retry library," it's "the existing retry loop isn't reused for the second HTTP adapter."

### 4. Rate limits and the specific APIs this bot uses

**GitHub REST**: unauthenticated requests get 60/hour; authenticated PATs and standard OAuth get 5,000/hour; `GITHUB_TOKEN` inside Actions gets 1,000/hour/repo (15,000 for Enterprise Cloud) ([GitHub REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Response headers `x-ratelimit-remaining`/`x-ratelimit-reset`/`x-ratelimit-used` let a well-behaved client back off *before* hitting 403/429, not just after. Secondary limits add a 100-concurrent-request ceiling and ~900 points/minute regardless of primary headroom, with an explicit warning: *"Continuing to make requests while you are rate limited may result in the banning of your integration."* The documented recovery order is: honor `retry-after` if present; else read `x-ratelimit-reset`; else wait "at least one minute" for a secondary limit with no `retry-after`; else back off exponentially.

The bot's `_check_transient` (`github_api.py:277-296`) implements the first rung only — it reacts to a 429, or a 403 carrying `Retry-After`, by raising `TransientError` with the `Retry-After` value surfaced in the message, and treats a bare 403 (no `Retry-After`) as `raise_for_status()`'s permanent-config-bug path, which is the right call per the docs (secondary-limit 403s carry `Retry-After`; a 403 without one is usually a real permission denial, not a rate limit). What it never does is *proactively* read `x-ratelimit-remaining`; a run that's about to make its 4,999th call in an hour has no way to know it's one call from a 403 until the 403 happens. Given `indexbot`'s call volume (dozens of calls per `announce`/`reconcile` invocation against a 1,000-5,000/hour budget) this is low-severity, but it is the literal gap the docs call out as best practice.

**GHCR / OCI distribution-spec**: pagination is standardized — *"A `Link` header MAY be included in the response when additional tags are available... MUST be set according to RFC 5988 with the Relation Type `rel=\"next\"`"*, and *"When `n` is zero, this endpoint MUST return an empty list, and MUST NOT include a `Link` header"* ([OCI distribution-spec](https://github.com/opencontainers/distribution-spec/blob/main/spec.md)). Rate limiting is only loosely specified: *"A `429 Too Many Requests` response SHOULD include a `Retry-After` header"*, with `TOOMANYREQUESTS` as the defined error code — the spec leaves numeric limits to each registry. GHCR-specific constraints that do have numbers: a 10 GB per-layer size limit and a 10-minute upload timeout ([GitHub Packages container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)) — relevant to `get_blob`'s unbounded read (finding 6): GHCR itself will hand the bot a blob up to 10 GB with no smaller ceiling enforced client-side.

**PyPI**: the JSON API (`GET /pypi/<project>/json`, `GET /pypi/<project>/<version>/json`) documents no rate limit or fair-use policy in its reference page ([PyPI JSON API docs](https://docs.pypi.org/api/json/)) — not currently consumed by this bot (no `pypi.org` reference found in `src/`), noted for completeness since the team-lead brief named it as in-domain.

### 5. Error taxonomy at the boundary

httpx's exception tree, confirmed against the docs page: `HTTPError` is the base for `RequestError` (everything that happens before/during the wire exchange) and `HTTPStatusError` (raised only by `raise_for_status()`, i.e. a *successful* exchange that came back >=400). `RequestError` branches into `TransportError` — `TimeoutException` (`ConnectTimeout`/`ReadTimeout`/`WriteTimeout`/`PoolTimeout`), `NetworkError` (`ConnectError`/`ReadError`/`WriteError`/`CloseError`), `ProtocolError`, `ProxyError`, `UnsupportedProtocol` — plus sibling `DecodingError` and `TooManyRedirects` ([httpx exceptions docs](https://www.python-httpx.org/exceptions/)).

The bot's mapping is disciplined and matches the sibling SDK's own doctrine of mapping every failure class to one outcome: `except httpx.TransportError` in `registry_v2.py:357` catches the whole timeout/network/protocol branch in one net (correct — the bot doesn't discriminate a `ReadTimeout` from a `ConnectError`, both spend the same `BackoffPolicy` budget and both become `TransientError`) and re-raises as `TransientError` after the attempt budget, with the original exception chained (`from exc`). Nothing in `src/` catches bare `Exception` around an HTTP call (verified: zero matches for `except Exception:` within a request-adjacent block — [see Rule R6](#normative-guidance-candidates)). `IndexBotError` subclasses (`TransientError`, `ValidationError`, `AnomalyError`) each carry a fixed exit code (`exit_codes.py`), and `cli/main.py:140-147` is the single place that turns any `IndexBotError` into `print(str(exc), file=sys.stderr)` plus a step-summary write and a process exit — this is the sibling SDK's exception-to-exit-code doctrine, applied consistently: an HTTP failure becomes an `IndexBotError` subclass inside the adapter, never a bare `httpx` exception escaping to `main()`.

`raise_for_status()` vs explicit branching: the bot's pattern is "branch on the status codes that need bot-specific meaning, then let `raise_for_status()` catch everything else" — 404 becomes `[]`/`KeyError`/`None` per method's semantics, 401 triggers the token dance, 403 becomes a permanent `ValidationError`, 429/5xx feed `is_retryable_status`, and *then* `response.raise_for_status()` runs for anything left over (`registry_v2.py:375-397`). This is the right shape: `raise_for_status()` alone (no branching) would conflate "missing" with "server broken" with "rate limited" into one generic `HTTPStatusError`, losing exactly the distinctions the bot's exit-code contract depends on.

The one gap: no branch, anywhere in either adapter, for a bare 3xx. Because `follow_redirects` is never set, httpx returns a 3xx response object as-is rather than raising or following it — and because `raise_for_status()` only triggers at >=400, a stray redirect response falls through every status check and reaches `response.json()`, which will most likely throw `json.JSONDecodeError` on an HTML or empty redirect body — an unhandled exception, not a mapped `IndexBotError`, breaking the exit-code contract for a case the bot has clearly reasoned about for every *other* status family.

### 6. Untrusted response data

This is where the bot's discipline is most uneven, and it's the section with the clearest sibling-SDK comparison point.

**Unbounded reads before deserialization.** `get_manifest()` and `get_blob()` both call `response.content` (`registry_v2.py:278`, `:309`) — httpx buffers the *entire* body into memory for this ([httpx streaming docs](https://www.python-httpx.org/quickstart/#streaming-responses): *"When using `response.content`... HTTPX loads the complete response body into memory at once"*), with no `.stream()`, no pre-check of the `Content-Length` header, and no post-hoc size assertion. GHCR's own layer-size ceiling is 10 GB (finding 4) — a manifest is documented as "a few KiB" in the bot's own comments (`registry_v2.py:104-109`), so in the honest-server case this never bites, but a compromised or misbehaving registry handing back a multi-GB body for what should be a small manifest/readme/logo blob has nothing client-side stopping it. `response.json()` inherits the same exposure — it's built on the same unbounded `.content` read.

Compare the sibling SDK, which cannot lean on httpx's convenience and so was forced to be explicit: `ocx_sdk/_dist.py` defines a 1 MiB chunk size and a 256 MiB byte cap, streams via `urllib.request` with an injectable `OpenerDirector` seam, and (per the prior sibling audit referenced in the brief) extracts archives one named member at a time with symlink and path-traversal checks. The bot has none of the equivalent machinery for its own downloads — this is the one place the bot is measurably behind its zero-dependency sibling rather than ahead of it.

**Decompression bombs.** httpx auto-decompresses `Content-Encoding: gzip/deflate/br/zstd` transparently on `.content`/`.json()` (only `.iter_raw()` skips it, per the streaming docs above). CWE-409 names the general class: *"the product does not handle or incorrectly handles a compressed input with a very high compression ratio that produces a large output"* ([CWE-409](https://cwe.mitre.org/data/definitions/409.html)) — memory exhaustion from a small compressed body. Nothing in the bot caps decompressed size independent of transport size; a size cap on `.content`/`.stream()` reads (the fix for the previous paragraph) would also close this, since httpx decompresses incrementally as bytes are read, not all-at-once from a pre-known total.

**Redirects and credential leakage across a host boundary.** This is a real, historical CVE class in the Python HTTP-client ecosystem: **CVE-2018-20060** — *"urllib3 before version 1.23 does not remove the Authorization HTTP header when following a cross-origin redirect... This can allow for credentials in the Authorization header to be exposed"*, CVSSv3 **9.8 (Critical)** ([NVD CVE-2018-20060](https://nvd.nist.gov/vuln/detail/CVE-2018-20060)). The same class recurs across ecosystems and is still live in 2024-2026: Scrapy's redirect middleware leaked `Authorization` on cross-domain redirects until 2.11.1/1.8.4 ([GHSA-cw9j-q3vf-hrrv](https://github.com/scrapy/scrapy/security/advisories/GHSA-cw9j-q3vf-hrrv)); `follow-redirects` (npm) had the `Proxy-Authorization` variant patched as CVE-2024-28849; Go's `net/http` had a same-origin-but-different-final-host variant fixed under CVE-2024-45336. httpx's own fix for the `Authorization` case is real: it strips the header on a cross-origin redirect by default, matching curl/requests/Go convention (confirmed via multiple corroborating sources including the WHATWG fetch spec's equivalent PR and the maintainers' own issue thread on documenting the behavior, [encode/httpx#3334](https://github.com/encode/httpx/issues/3334)).

But that protection is scoped to actual HTTP 3xx redirects, and the bot's most sensitive follow-the-server-supplied-URL pattern isn't a redirect — it's `github_api.py`'s `_paginate()`, which takes `response.links.get("next", {}).get("url")` from the GitHub API's own `Link` header and issues the next request on the *same, already-Authorization-headered* `client` (`github_api.py:303-312`), with **no host comparison at all**. `registry_v2.py`'s equivalent (`_parse_next_link`, `registry_v2.py:159-189`) explicitly checks the next link's host against the current `base_url` and raises `ValueError` on mismatch — *"a server-supplied `Link` header pointing at a different host is not a condition this adapter has a defined recovery for (SSRF-via-pagination-link)... rejected."* GitHub itself is a trusted, TLS-verified party today, so this isn't presently exploitable without GitHub's own compromise — but it's the same shape of authority-following-authority bug that CVE-2018-20060 and the Scrapy advisory are instances of, applied here at the application layer instead of the transport layer, and the codebase already has the correct fix pattern sitting one file away, untested and unapplied to this second call site.

**SSRF from config-supplied URLs.** Out of scope for this dive's boundary (it's a config-input problem, not an HTTP-client one) but worth noting the bot already has a dedicated defense: `check_repository_allowlisted`/`check_repository_shape` in `core/validate_entry.py` run against every `repository` URI *before* any `RegistryPort` call, and `tests/security/test_threat_classes.py::test_threat_ssrf_allowlist_before_registry` pins it.

**TLS verification.** `verify=` never appears in `src/` — confirmed by grep — so every client uses httpx's default `verify=True` everywhere. No exposure.

**Terminal escape-sequence injection.** CWE-150, *"Improper Neutralization of Escape, Meta, or Control Sequences,"* covers exactly this: untrusted input reaching a terminal can *"manipulate cursor positioning and screen clearing, create fake prompts... potentially enable arbitrary code execution"* ([CWE-150](https://cwe.mitre.org/data/definitions/150.html)), and the entry explicitly flags this as *"particularly relevant, with emerging vectors like Large Language Model (LLM) output in terminal applications"* — directly on-topic for an agent-driven bot. `cli/main.py:146` does `print(str(exc), file=sys.stderr)` on every `IndexBotError`; if a message embeds a raw, attacker-influenceable value (a registry or GitHub response header), that value reaches the terminal exactly as received unless it was `repr()`'d first. One site gets this right: `registry_v2.py`'s digest-mismatch `AnomalyError` interpolates the registry's `Docker-Content-Digest` header via `!r` (`registry_v2.py:298-303` — repr of a Python string escapes control characters as `\xHH`, neutralizing the injection). One site does not: `github_api.py:292-293` builds `suffix = f" (retry after {retry_after}s)"` directly from `response.headers.get("Retry-After")` with no `repr()`/sanitization, and that string becomes the `TransientError` message that flows straight to `main.py`'s unguarded `print()`. GitHub is trusted infrastructure today, so severity is low, but the inconsistency between the two adapters is real and mechanically checkable.

### 7. The 56 casts

`response.json()` returns `Any` — every `dict`/`list` access downstream of it type-checks only because pyright is told to trust it via `cast(...)`. Reading all 56 sites and tracing each back to its origin:

| Category | Count | HTTP-boundary? |
|---|---:|---|
| `argparse.Namespace` attribute access (`args.foo`) | 32 | No — stdlib `argparse` never types `Namespace` attributes |
| Registry-JSON-derived (`response.json()` / `json.loads()` on fetched bytes) | 12 | **Yes** |
| Local-file-read narrowing (`files.read_bytes(...)`) | 5 | No |
| Internal dataclass/Protocol narrowing (already-typed fields) | 4 | No |
| Local config-JSON (`.github/index-policy.json`, already `isinstance`-validated before cast) | 3 | No |
| **Total** | **56** | |

The 12 registry-JSON sites: `registry_v2.py:216` (manifest annotations), `core/desc.py:73,137,139,144,151,153` (title/description/logo extraction from a fetched manifest), `core/validate_entry.py:601,659,666,668` (`json.loads()` on `ManifestFetch.raw`/image-index bytes), `core/observe.py:92` (source annotation). Every one of these operates on `_Manifest = dict[str, object]` (`core/desc.py:32`) — an alias for "whatever JSON the registry sent," re-derived independently at each call site rather than validated once.

The answer to "would a boundary validator remove most of them": no — it would remove **12 of 56 (21%)**, not "most." The other 79% is a different, non-HTTP problem (`argparse.Namespace` typing) that a validator at the HTTP boundary can't touch. Within its actual scope, though, a validator is clearly worth building: the codebase already contains the right shape for one — `core/policy.py`'s `load_registry_hosts` (`policy.py:75-115`) does exactly this against a local JSON file: `json.loads`, `isinstance(parsed, dict)`, per-key presence/shape checks, a regex on each element, and only *then* a `cast` that pyright can trust because the runtime checks already proved it. Applying that same pattern once — a `parse_manifest(raw: bytes) -> Manifest` function (real dataclass, not `dict[str, object]`) called at the single point where `ManifestFetch.parsed` is produced — would let `desc.py`/`observe.py`/`validate_entry.py` consume a real type and drop all 12 casts plus their scattered, inconsistent `isinstance` guards.

Given the fleet's dependency conservatism (the bot's only runtime dependency is `httpx` itself; `respx` is dev-only) and the sibling SDK's *zero* runtime dependencies, the right validator is a **stdlib `TypedDict` + hand-written validator function**, following `core/policy.py`'s own precedent — not `pydantic` or `msgspec`. The shape being validated (an OCI manifest's `annotations`/`layers`, a handful of string/dict/list fields) is small and stable enough that a hand-written check pays for itself in one function; `pydantic`/`msgspec` earn their weight at higher field-count or when validation needs to compose across many independently-evolving schemas, neither of which applies to a single, spec-fixed manifest shape. This rule cannot transfer to the SDK as "use `httpx` + a validator" — the SDK has no `httpx` at all — but "validate untyped JSON once at the boundary, never re-derive `isinstance` per call site" transfers unchanged; the SDK's own `urllib`-based fetch path would benefit from the identical pattern.

### 8. Testing HTTP without the network

Confirmed by reading, not assuming: `respx` mocks *"the HTTPX, and HTTP Core, libraries"* at the transport level — *"By patching HTTPX before tests run, it intercepts all HTTP requests and matches them against defined routes"* ([respx docs](https://lundberg.github.io/respx/)); `respx.mock`'s default `assert_all_mocked=True` means an unmatched request (including one that would otherwise reach a real host) fails the test rather than escaping. `tests/test_github_api.py` (35 `@respx.mock`-decorated tests) and `tests/adapters/test_registry_v2.py` (43) cover both adapters this way. The four `def test_` functions in `test_registry_v2.py` *not* preceded by `@respx.mock` were checked individually: `test_ghcr_registry_conforms_to_registry_port` (bare `isinstance` check, no I/O), `test_routed_registry_conforms_to_registry_port` (same), `test_routed_registry_refuses_a_host_it_has_no_client_for` (raises before any request is attempted), and `test_token_url_defaults_to_base_url_token` (string-equality check on `.realm`, decorated with `@respx.mock` one line above the point my automated scan mis-attributed it to — verified by direct read). None make a real call.

Integration tests (`tests/integration/`) use a different, complementary technique: `FakeGhcrServer`/`FakeForgeServer` are genuine `http.server.ThreadingHTTPServer` instances bound to `("127.0.0.1", 0)` (`tests/integration/harness/fake_ghcr.py:194-196`) — a real TCP socket, but loopback-only and ephemeral-port, so it can never reach the public internet regardless of what the code under test does. This is the socket-level tier the harness's own module docstring names deliberately (`tests/integration/harness/__init__.py:4`).

The one thing genuinely missing is a `pytest-socket` guard (`pytest --disable-socket`, or `disable_socket()` in `conftest.py`) that would make "no test reaches the real network" a property enforced by the test *runner*, not an inference from reading every test file — `pytest-socket` works by blocking Python's socket interface outright and raising `SocketBlockedError` on any attempt, DNS included ([pytest-socket README](https://raw.githubusercontent.com/miketheman/pytest-socket/main/README.md)). Given the loopback-bound fakes already in use, adding it would need an `--allow-hosts 127.0.0.1` carve-out for the integration tier; it would not change any test's behavior today, only convert "verified by reading" into "verified by the suite failing loudly if this regresses."

### 9. What an LLM gets wrong

Team lead's list, each with the smallest mechanical check — see [Normative guidance candidates](#normative-guidance-candidates) rules R1, R2, R3, R5, R6, R7, R8 for the exact commands (all watched red/green in this session).

## Normative guidance candidates

1. **Never call the bare `httpx.<verb>()` top-level API in application code; always go through a `Client`.**
   Rationale: the top-level API opens and closes a connection per call with no pooling, and silently inherits the library's undocumented-at-call-site 5s default instead of a stated one.
   Verify: `grep -rn "httpx\.\(get\|post\|put\|patch\|delete\|head\|request\|stream\)(" <src-path> --include=*.py | grep -v /tests/` — VIOLATION is any matched line; empty output is a pass.

2. **Every `httpx.Client(`/`httpx.AsyncClient(` construction states `timeout=` explicitly, even to restate the library default.**
   Rationale: an implicit 5s (or, worse, a mismatched inherited value from another call site) is not a decision — writing it down makes the deadline a reviewable number instead of a fact you have to know the library to see.
   Verify: `grep -n "httpx\.\(Async\)\?Client(" <file> | grep -v "timeout="` — VIOLATION is any matched construction line; empty output is a pass. (Multi-line constructor calls need the window widened, e.g. `grep -n -A5 "httpx\.\(Async\)\?Client($" <file>`.)

3. **`verify=False` never appears outside a test double.**
   Rationale: disabling TLS verification to silence a cert error is a self-inflicted MITM hole, and it never belongs in code that ships.
   Verify: `grep -rn "verify[[:space:]]*=[[:space:]]*False" <src-path>` — VIOLATION is any match; empty output is a pass.

4. **One shared `Client` per adapter instance, held for the instance's process lifetime — never constructed fresh inside a method that another method in the same adapter also calls.**
   Rationale: a client-per-method-call pattern pays a full TCP+TLS handshake per call to the same host when a single pooled client would reuse the connection across every call in one CLI invocation; `registry_v2.py`'s `field(default_factory=httpx.Client)` is the reference shape.
   Verify: `grep -c "httpx\.Client(" <adapter-file>` — VIOLATION is a count greater than the number of `__init__`/dataclass-field construction points (i.e. greater than 1 for a single-host adapter); a count equal to the number of public methods is the finding, not a pass.

5. **A retry loop's backoff math is pure and separately testable from the loop that sleeps and re-sends.**
   Rationale: mixing "how long to wait" with "did the attempt budget run out, do the I/O, sleep" makes the delay formula untestable without mocking `time.sleep`/`random`; `core/backoff.py`'s split is the reference shape.
   Verify: `grep -rln "time\.sleep" <adapter-path>` then confirm the matched file imports its delay computation from a separate module with no `time`/`random`/`httpx` import — mechanical only as a starting point; the actual separation needs a read, not a grep.

6. **Retry only idempotent methods (GET/HEAD/PUT/DELETE) automatically; a POST/PATCH that fails goes to the caller, never an in-process resend.**
   Rationale: retrying a non-idempotent request risks double-applying it (two PRs, two issues) — that's a correctness bug wearing a performance-tuning costume.
   Verify: `grep -n -B5 "\.post(" <file> | grep -E "^[0-9]+-[[:space:]]*(for|while)[[:space:]]"` — VIOLATION is a `for`/`while` loop header found within 5 lines above a `.post(` call in the same function; empty output is a pass. (Heuristic: a real retry loop for POST may be further than 5 lines away in a large function — widen the window and read on a match-adjacent miss.)

7. **A `Retry-After`/rate-limit header value reaches an exception message only through `repr()`/`!r`, never interpolated raw.**
   Rationale: an attacker-influenceable header value flowing unescaped into a message that later gets `print()`ed to a TTY is CWE-150 — ANSI/control-sequence injection into the operator's terminal.
   Verify: `grep -n "{[^}!]*\.headers\.get([^}]*)}" <file>` — VIOLATION is any f-string that embeds a `.headers.get(...)` call without a trailing `!r` inside the same `{...}`; empty output is a pass. (Catches only the single-line/inline case; a value extracted to a variable first and interpolated later on a different line needs a manual read — see finding 6's `github_api.py:292-293` example, found by reading, not by this grep.)

8. **Every server-supplied "next" URL (redirect *or* `Link: rel="next"` pagination) has its host compared against the current base host before the same authenticated client reuses it.**
   Rationale: this is the shape of CVE-2018-20060/GHSA-cw9j-q3vf-hrrv — an authenticated client blindly following a server-supplied URL to a different host leaks the credential to whoever controls that host; the bug doesn't care whether the "server-supplied URL" arrived via a 3xx `Location` header or an apparently-benign `Link` header — both hand the client a URL it didn't choose.
   Verify: `grep -rl "\.links\.get(\"next\"" <src-path>` then `xargs grep -L "netloc"` on the result — VIOLATION is any file that follows a `Link: rel="next"` header with no `urlsplit(...).netloc` comparison anywhere in the same file; empty final output is a pass. `registry_v2.py` passes this check (`_parse_next_link` contains the `netloc` guard); `github_api.py` fails it.

9. **A streamed or size-unknown-in-advance response body is capped in bytes before being handed to a JSON parser or written to disk.**
   Rationale: `response.content`/`response.json()` buffer the entire body (post-decompression) into memory with no ceiling — a compressed decompression bomb or a merely-larger-than-expected honest response both exhaust memory the same way; the fix is a byte cap enforced while reading, not after.
   Verify: `grep -rl "\.content\b" <src-path>` then `xargs grep -L "Content-Length\|MAX_\|len("` on the result — VIOLATION is any file reading `.content` with no size-bound identifier anywhere in the file; empty final output is a pass. This is a coarse heuristic (a `MAX_`/`len(` match anywhere in the file doesn't prove it gates that specific read) — treat a match as "needs a read," not as proof of compliance.

10. **`response.json()` output is validated once at a single boundary function and converted to a real type; call sites never `cast(...)` a fresh, ad hoc shape out of the same raw dict more than once.**
    Rationale: `Any` propagating from `response.json()` is why 12 of the bot's 56 casts exist; a single `parse_x(raw) -> X` function (stdlib `isinstance` checks, following `core/policy.py`'s own pattern) turns 12 unverified casts into one verified one.
    Verify: `grep -rn "\.json()\[" <src-path>` — VIOLATION is any direct subscript off `.json()` (untyped dict access with no named parse step in between); empty output is a pass.

11. **`except Exception:` never wraps an HTTP call directly.**
    Rationale: `httpx`'s exception tree (`TransportError`, `HTTPStatusError`, `DecodingError`, `TooManyRedirects`, `InvalidURL`) is precise on purpose; catching `Exception` around a request swallows programming errors (a `TypeError` in a header-building helper) in the same breath as a legitimate network failure, hiding real bugs behind "transient, retry later."
    Verify: `grep -n -A3 "client\.\(get\|post\|put\|patch\|delete\|request\)(" <file> | grep "except Exception"` — VIOLATION is `except Exception` appearing within 3 lines after a client call; empty output is a pass.

12. **`import requests`/`from requests import` never appears in a codebase whose HTTP client is `httpx`.**
    Rationale: the single most common LLM substitution — `requests` is what most training data uses by default — silently reintroduces a second client with its own connection pool, its own timeout default (`requests` has *none* by default, unlike httpx's 5s), and no shared test-mocking story with the rest of the suite.
    Verify: `grep -rn "^import requests\|^from requests" <src-path>` — VIOLATION is any match; empty output is a pass.

13. **A bare 3xx response is handled explicitly, not left to fall through to `raise_for_status()` (which ignores it) and then a body parser (which will fail on it unpredictably).**
    Rationale: `follow_redirects=False` is httpx's safe default, but "safe" here only means "doesn't silently leak credentials to a new host" — it does not mean "the rest of the code copes gracefully with getting a redirect response object back." Silence on this path converts a clean, nameable failure into a `JSONDecodeError` with no relation to the real cause.
    Verify: for each `raise_for_status()` call site, confirm a `response.is_redirect` or explicit `3xx` status check exists in the same function before it — no clean single-grep check; this one needs a read per adapter, noted rather than mechanized to avoid a false sense of coverage.

14. **CI/tests never open a socket to a real external host; enforce it at the runner, not by convention.**
    Rationale: `respx`/loopback fakes make it *true today* by construction, but only a runner-level guard (`pytest-socket`) makes a future regression (a test added without the decorator, an accidental real-host string in a fixture) fail loudly instead of silently passing against the internet.
    Verify: `pytest --disable-socket --allow-hosts=127.0.0.1 <test-path>` — VIOLATION is any test failure caused by a blocked socket to a non-allowlisted host (`SocketBlockedError` in the failure output); a clean run (all tests still pass) is the pass condition. Requires adding the `pytest-socket` dev dependency and the `--allow-hosts` carve-out for the loopback integration tier first — not yet true of this bot's `pyproject.toml`.

## Contested / evolving

As of August 2026:

- Whether `httpx.HTTPTransport(retries=...)` should grow status-code-aware retries, versus staying deliberately narrow and pointing users at `tenacity`, is an open design stance in httpx's own docs rather than a settled question — the docs currently take the narrow position, but this has been requested against the project before and could change in a future minor version.
- Whether `respx`'s transport-level interception is sufficient network isolation for CI without an additional `pytest-socket`-style runner guard is a matter of house style, not a settled industry consensus — teams reasonably differ on whether "provably true by construction" (this bot's current state) needs backing by "provably true if it ever regresses" (what `pytest-socket` would add).
- `pydantic` vs. hand-written `TypedDict` validators for small, stable JSON shapes remains genuinely contested across the Python ecosystem at large; this document's recommendation for *this* bot (hand-written, following `core/policy.py`'s own precedent) is scoped to its specific dependency-conservatism and small-shape context, not offered as a universal answer.
