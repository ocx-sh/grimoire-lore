## Summary

- `Package.resolved` is a cache, not a lock, unless `--force-resolved-versions` (aliases `--disable-automatic-resolution`, `--only-use-versions-from-resolved-file`) is passed: a plain `swift build` after a manifest edit re-resolves and rewrites the file with exit 0 (measured, 6.3 and 6.4).
- `--force-resolved-versions` fails (exit 1, "out-of-date resolved file") when a requirement is raised past a pin or a dependency is added, and fails with "a resolved file is required" on a cold scratch dir; on a warm scratch dir with the file deleted it passes (exit 0), so the flag alone is not a sufficient gate.
- The sufficient gate is three checks: tracked file (`git ls-files --error-unmatch Package.resolved`), the flag on a fresh scratch dir, and `git diff --exit-code -- Package.resolved` after a plain build.
- `originHash` is the SHA-256 of the root `Package.swift` bytes plus the root dependency locations; it is consulted only in the default (best-effort) mode, and the file is rewritten only when a pin changes, so a stale hash is normal and harmless. `--force-resolved-versions` ignores it.
- Re-resolution is minimal: with a pin that still satisfies the requirement, relaxing `exact:` to `from:` did not move the pin although a newer tag existed, and raising one requirement did not move unrelated pins (measured).
- Policy per kind (confirms conflict 7): anything that ships a binary, app, container or service tracks `Package.resolved` and gates CI with the flag; library-only repos gitignore it. Two corpus repos enforce the lock, not one: tuist (`--force-resolved-versions`) and containerization (`--disable-automatic-resolution`).
- Requirement style: `from:` (70% of URL dependencies in the corpus) or a half-open range; `exact:` only in a shipped root with a dated reason; `branch:`/`revision:` never in anything consumed by version (resolve fails, exit 1) and only inside swiftlang's co-released repos.
- Never write a closed range `"1.0.0"..."2.0.0"`: it admits 2.0.0 and resolved 2.0.0 in the fixture.
- A swift-syntax major is a Swift release (604 = Swift 6.4), so `from: "604.0.0"` means exactly one major and conflicts with every sibling on another major. A macro or plugin library declares a multi-major half-open range such as `"600.0.0"..<"606.0.0"` and guards version-specific code with `#if canImport(SwiftSyntaxNNN)`, newest first.
- A range does not admit prereleases unless a bound carries a prerelease identifier; an `exact:` prerelease pin therefore conflicts with every range-pinned sibling (all four combinations failed, exit 1). `from: "605.0.0-latest"` is worse: it drags the whole graph onto the newest prerelease. Both are leaf-tool idioms (SwiftLint, swift-testing), never library idioms.
- A swift-syntax range is only as wide as the lowest version CI builds: unguarded `InlineArrayTypeSyntax` compiled at 604.0.0 and failed at `exact: "600.0.1"` (exit 1); the `canImport(SwiftSyntax602)` twin passed both.
- swift-syntax prebuilts are on by default in 6.4 (`Options.swift:220-223`) but are keyed to the host distro; the swift:6.4 image (Ubuntu 26.04 "resolute") is not in SwiftPM's list, so prebuilts silently do nothing there. "Exact prerelease defeats prebuilts" stays an inference.
- Traits (SE-0450, tools 6.1): `traits: ["X"]` on a dependency REPLACES the default traits (measured: `Verbose` default lost); write `[.defaults, "X"]` to keep them. A trait-gated optional dependency is not fetched while the trait is off (an unreachable URL resolved with exit 0), but one ungated reference anywhere in the package defeats that (exit 1).
- A build that passes by default can hide breakage behind a trait: `swift build --enable-all-traits` and `--disable-default-traits` caught a planted error in `#if Zed` (exit 1 vs default exit 0). A mistyped flag (`#if Zedd`) is silently false even with `--enable-all-traits` (exit 0): no compiler gate exists for trait-name typos.
- Underscored products are outside SemVer (swift-crypto README says so in terms): the planted minor bump removed one product (resolve ok, build exit 1) and changed a signature in another (compile error), while the public product kept building. Ban `.product(name: "_...")`; containerization's `_NIOFileSystem` is the corpus counter-example.
- swift-crypto: use `"1.0.0" ..< "6.0.0"` (README at `swift-crypto@1c80d3aff53f`, 5.0.0 shipped 2026-09). The corpus form `"3.0.0"..<"5.0.0"` (containerization) conflicts with any package requiring 5.x (exit 1).
- Agents reach for cargo-style `--locked` / `--frozen` / `--offline` (all "Unknown option", exit 64), `from: "1.0"` (opaque "invalid manifest", exit 1), `.package(name:url:from:)` (deprecated warning, exit 0), `exact:` to silence conflicts, and `swift package update` in CI.

## Findings

### 1. How SwiftPM uses Package.resolved

- SwiftPM's own docs: the file "does not pin dependency versions for packages used as libraries"; when a package is a dependency, "its own `Package.resolved` file is ignored" ([ResolvingPackageVersions.md](https://raw.githubusercontent.com/swiftlang/swift-package-manager/main/Sources/PackageManagerDocs/Documentation.docc/ResolvingPackageVersions.md)). `swift package resolve` "resolves to those versions as long as they are still eligible"; to "explicitly use" the file pass `--force-resolved-versions`.
- Three resolution strategies exist in code: `.lockFile` (when the flag is set), `.update(forceResolution:)` (`swift package update`), `.bestEffort` (default) (`swift-package-manager@5546f44a3b52:Sources/Workspace/Workspace.swift:804`; `Sources/Workspace/Workspace+Dependencies.swift:297,306`).
- `.bestEffort`: no file -> resolve; no `originHash` -> resolve; hash differs from the current hash -> resolve; otherwise try the file (`Workspace+Dependencies.swift:306-330`, debug messages "origin hash is missing" / "does do not match manifest dependencies"). "Resolve" here is `precomputeResolution`, which exits early when every pin still satisfies its requirement (`Workspace+Dependencies.swift:672-700`, case `.notRequired`).
- `.lockFile`: never looks at `originHash`; it only checks that pins exist and satisfy requirements, and otherwise emits an error (`Workspace+Dependencies.swift:297-305, 385-425`).
- File format: `Package.resolved` v3 with `originHash` is written when the root tools version is above 5.9; at or below 5.9 SwiftPM writes v2 without it (`swift-package-manager@5546f44a3b52:Sources/PackageGraph/ResolvedPackagesStore.swift:276`). SwiftLint (tools 5.9) is the only v2 file in the corpus (`SwiftLint@ec4691d9e813:Package.resolved`, [pkg](../swift-audit/exemplar-packaging-and-release.md) Resolution). A v2 root can never reach the "hash matches" fast path.
- v3 and `originHash` came from [SwiftPM PR 6698](https://github.com/swiftlang/swift-package-manager/pull/6698) ("prefer versions in package.resolved file when one exists and matches the original manifest", tomerd, merged 2023-08-08).
- Xcode (unverified: read only): the file lives at `<App>.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` or `<App>.xcworkspace/xcshareddata/swiftpm/Package.resolved` ([Jesse Squires, 2024-05-29](https://www.jessesquires.com/blog/2024/05/29/swiftpm-package-resolved-xcode/)); the xcodebuild analogue of the SwiftPM flag is `-onlyUsePackageVersionsFromResolvedFile`, reported to be needed because Xcode otherwise prefers its source cache ([forum 65031](https://forums.swift.org/t/xcode-ignoring-package-resolved-file/65031), 2023-05). IceCubesApp tracks only the Xcode-managed file; element-x-ios tracks five lockfiles ([pkg](../swift-audit/exemplar-packaging-and-release.md) Resolution).

### 2. --force-resolved-versions, exactly

Source: `Options.swift:399-402` declares one flag with three spellings, `--force-resolved-versions`, `--disable-automatic-resolution`, `--only-use-versions-from-resolved-file`, help "Only use versions from the Package.resolved file and fail resolution if it is out-of-date." (`swift-package-manager@5546f44a3b52:Sources/CoreCommands/Options.swift:399-402`). All three were run (cold scratch, no file: each exit 1 "a resolved file is required when automatic dependency resolution is disabled").

Measured on 6.4 and 6.3 (fixture `a-lockfile/`, exit codes identical on both):

| Step | Command | Exit | Lockfile afterwards |
|---|---|---|---|
| lockfile made with `exact: "1.0.0"`; upstream later tags 1.1.0 | `swift build` (unchanged manifest) | 0 | identical, pin stays 1.0.0 |
| comment-only manifest edit | `swift build --force-resolved-versions` and plain | 0 / 0 | identical (originHash NOT refreshed) |
| `exact: "1.0.0"` relaxed to `from: "1.0.0"` | force / plain | 0 / 0 | identical, pin stays 1.0.0 although 1.1.0 exists |
| requirement raised to `from: "1.1.0"` | `--force-resolved-versions` | **1** | untouched; error "out-of-date resolved file ... Running resolver because requirements have changed" |
| same | plain `swift build` | **0** | rewritten silently: pin 1.0.0 -> 1.1.0, new originHash |
| new dependency added | force / plain | **1** / 0 | plain rewrites and adds the pin |
| file deleted, cold scratch | force | **1** | "a resolved file is required" |
| file deleted, WARM scratch | force | **0** | none created: false green |

So: (a) the flag makes SwiftPM a lockfile consumer for pin/requirement mismatch; (b) it does not require the file to exist when the scratch dir already holds resolved checkouts (`workspace-state.json`), so run it on a fresh checkout or add the tracked-file check; (c) `swift package resolve --force-resolved-versions` is the documented spelling, and `swift build`/`swift test`/`swift run` accept it as well. The pitch to make the file a real lock ([forum 68475](https://forums.swift.org/t/pitch-swiftpm-treating-package-resolved-as-a-lock-file/68475), Franz Busch, 2023-11-15) was not adopted as default behaviour; the flag remains the only lock mode.

### 3. originHash and the re-resolution path

- `computeResolvedFileOriginHash` = SHA-256 of the full byte content of each root `Package.swift` plus the `locationString` of each root dependency (`Workspace+Dependencies.swift:368-381`). Any byte of the manifest, even a comment, changes it.
- It is consulted only in best-effort mode (`Workspace+Dependencies.swift:314,323`). A mismatch routes into `precomputeResolution`, which re-runs the resolver only when a pin no longer satisfies a requirement, a package is added/removed, or constraints changed.
- The store is rewritten only if pins changed: "we want to avoid re-writing the resolved files unless absolutely necessary" (`swift-package-manager@5546f44a3b52:Sources/Workspace/Workspace+ResolvedPackages.swift:49-72`). Measured: after a comment-only edit and a plain build the committed `originHash` was byte-identical. A reviewer must therefore never read a stale hash as "lockfile out of date"; the diff that matters is in `pins`.
- The resolver prefers existing pins: raising `libdep` past its pin moved `libdep` 1.0.0 -> 1.1.0 and left `libdep2` at 1.0.0 although 1.1.0 existed (fixture `a-lockfile/run-a3.sh`). The silent change is therefore small but real: one dependency moves, and nothing fails.
- The topic-map wording "mismatch triggers silent re-resolution" (conflict 7) is correct only in that sense; the corrected statement is: mismatch triggers a re-check, and the file is rewritten silently when the check fails.

### 4. Package.resolved policy per package kind (conflict 7)

Confirmed with one correction to the audit.

| Kind | Track `Package.resolved`? | Gate |
|---|---|---|
| CLI, daemon, app, container image, plugin tool that ships | yes | CI builds with the flag; drift check |
| Service / server application | yes | same |
| Library-only repo, SDK library | no (gitignore) | none; CI floats on purpose to catch upstream breakage |
| Library that commits it for an Xcode workspace | tolerated, not a defect (TCA, swift-dependencies, snapshot-testing) | none: consumers ignore it ([docs](https://raw.githubusercontent.com/swiftlang/swift-package-manager/main/Sources/PackageManagerDocs/Documentation.docc/ResolvingPackageVersions.md)) |

Evidence: 10 repos track, 23 gitignore, 7 have none; the 3 library trackers are Point-Free's ([pkg](../swift-audit/exemplar-packaging-and-release.md) Headline 2). Correction: the audit says only tuist enforces the lock; containerization also does, through the alias: `--disable-automatic-resolution` at `containerization@3e7bc39e66b3:Makefile:28`, `.github/workflows/linux-build.yml:51,60`, `scripts/build-dist-x86_64.sh:160`, with a tracked 30-pin `Package.resolved`. tuist runs `tuist install --force-resolved-versions` and `swift build ... --force-resolved-versions` (`tuist@2f6ac74754bf:.github/workflows/cli.yml:121,158,162,478`). sourcekit-lsp exposes the same switch as an option (`sourcekit-lsp@c6ce93d5f8aa:Sources/SKOptions/SourceKitLSPOptions.swift:75`). The ocx and grimoire Rust analogue is `Cargo.lock` + `--locked`; Swift's `--locked` does not exist (exit 64).

### 5. Requirement style

Corpus (436 `.package(` declarations, [pkg](../swift-audit/exemplar-packaging-and-release.md) Headline 3): `from:` 192 (44% overall, 70% of 275 URL deps), `path:` 99, registry `id:` 62 (tuist only), `branch:` 33 (all swiftlang repos plus two app deps), `exact:` 20, ranges 16, `upToNextMinor` 8, `revision:` 6 (SwiftPM only). Every core and community library uses `from:` or a range; `exact:` clusters in shipped roots: tuist 13, element-x-ios 4, IceCubesApp 3, swiftly 2.

- SwiftPM docs: `from:` = "at least ... up to the next major version" and tags must carry all three components ([AddingDependencies.md](https://raw.githubusercontent.com/swiftlang/swift-package-manager/main/Sources/PackageManagerDocs/Documentation.docc/Dependencies/AddingDependencies.md)).
- A package consumed by version cannot have an unstable dependency: planted `pubBranch` (tag 1.0.0, `branch: "main"` on `base`) consumed with `from: "1.0.0"` -> exit 1, "package 'pubbranch' is required using a stable-version but 'pubbranch' depends on an unstable-version package 'base'" (fixture `e-branch/`, 6.4 and 6.3). The `from:` twin resolves (exit 0). The swiftlang `branch:` idiom (`relatedDependenciesBranch`, `swift-package-manager@5546f44a3b52:Package.swift:1133,1152`) is legal only because those repos are roots or co-released.
- Closed range: `"1.0.0"..."2.0.0"` resolved 2.0.0 when 2.0.0 was tagged; `"1.0.0"..<"2.0.0"` and `from: "1.0.0"` resolved 1.1.0; `branch: "main"` resolved 2.0.0 (fixture `f-agent/`). `from: "1.0"` fails manifest evaluation with the opaque "invalid manifest (evaluation failed)" (exit 1).
- Reasoned exact pins exist in the corpus: vapor pins `exact: "1.6.0"` with the comment "Pin until Async Algorithms releases a fix for the Collections 1.7.0 preview APIs" (`vapor@bf77fc69b142:Package.swift:86-88`) in a published framework: tolerated shape = dated comment naming the removal condition. container pins its sibling containerization in lock-step (`container@f70ecbb926d9:Package.swift:58`); swiftly pins swift-subprocess `exact: "1.0.0", traits: []` (`swiftly@c8cf2e35bfca:Package.swift:34`).
- `.package(name:url:from:)` is deprecated: "use package(url:from:) instead" is a warning, exit 0 (fixture `f-agent/cName`, 6.4).

### 6. swift-syntax: ranges, prereleases, ladder, prebuilts

**Versioning model.** Releases "are aligned with corresponding language and tooling releases, for example the major version 509 ... with Swift 5.9" ([swift-syntax README](https://raw.githubusercontent.com/swiftlang/swift-syntax/main/README.md)); available tags today include 600.0.1, 601.0.1, 602.0.0, 603.0.2, 604.0.0 and 605.0.0-prerelease-2026-06-08/-06-26/-09-15 (`git ls-remote --tags`, 2026-10-10). SwiftPM's `from:` therefore spans exactly one swift-syntax release: measured `from: "603.0.0"` renders as `603.0.0..<604.0.0`.

**Range resolution (fixture `b-macros/`, six macro packages, `swift package resolve`, 6.4 and 6.3 identical).**

| Consumer depends on | Result | Exit |
|---|---|---|
| `MExact` (`exact: "605.0.0-prerelease-2026-09-15"`) alone | 605.0.0-prerelease-2026-09-15 | 0 |
| `MRange` (`"600.0.0"..<"606.0.0"`) alone | 604.0.0 (no prerelease) | 0 |
| MExact + MRange | "'mexact' depends on 'swift-syntax' 605.0.0-prerelease-2026-09-15 and 'mrange' depends on 'swift-syntax' 600.0.0..<606.0.0" | **1** |
| MExact + MPfree (`"509.0.0"..<"605.0.0"`, Point-Free form) | conflict | **1** |
| MExact + MFrom (`from: "604.0.0"`) | conflict | **1** |
| MExact + MFrom603 | conflict | **1** |
| MFrom603 + MFrom (two single-major `from:`) | "603.0.0..<604.0.0 and 604.0.0..<605.0.0" | **1** |
| MRange + MPfree + MFrom (range-only twin) | 604.0.0 | 0 |
| MRange + MFrom | 604.0.0 | 0 |
| MBranch (`branch: "main"`) + MRange | branch main (be549876fe91), range ignored | 0 |
| MLatest (`from: "605.0.0-latest"`) alone | 605.0.0-prerelease-2026-09-15 | 0 |
| MLatest + MRange | 605.0.0-prerelease-2026-09-15 (range now yields a prerelease) | 0 |
| MLatest + MFrom | "'swift-syntax' >= 605.0.0 is required because ... 'mlatest' depends on ... 605.0.0-latest..<606.0.0" | **1** |

Mechanism: a range "supports prereleases" only if a bound has prerelease identifiers (`swift-package-manager@5546f44a3b52:Sources/PackageGraph/VersionSetSpecifier.swift:541-543,558-560`); otherwise prereleases are stripped (`:483-496`). `exact:` on a prerelease is itself a prerelease-bearing constraint, and `"605.0.0-latest"` is a prerelease lower bound that makes the whole intersection prerelease-eligible. swift-testing documents the intent: "the lexicographically highest-sorted tag ... meaning the most recent 'prerelease' tag will always be used" (`swift-testing@c7d68ca20cd7:Package.swift:130-140`). A `branch:` swift-syntax pin in a root overrides sibling ranges (cBranchRange exit 0) and gives no release version.

**Macro-version policy in the corpus** (13 repos, five strategies, [pkg](../swift-audit/exemplar-packaging-and-release.md) Plugins and macros): range plus `canImport` ladder (TCA `"509.0.0"..<"605.0.0"`, `swift-composable-architecture@bc2db5ba8ad3:Package.swift:52`; swift-dependencies `swift-dependencies@b476cc576105:Package.swift:42` plus a narrower `Package@swift-6.0.swift:33`), narrow `from:` (vapor `from: "602.0.0"`, element-x-ios `from: "604.0.0"`), exact prerelease (SwiftLint, `SwiftLint@ec4691d9e813:Package.swift:39`), `branch:` (swiftlang repos), `-latest` (swift-testing). Point-Free's rule since 2023: accept a range of majors, not the template's `from:` ([post 116](https://www.pointfree.co/blog/posts/116-being-a-good-citizen-in-the-land-of-swiftsyntax)); Brandon Williams (mbrandonw) repeats it in 2025-10 ("as permissive as possible", [forum 82587](https://forums.swift.org/t/macros-in-foundational-libraries/82587)).

**The `canImport` ladder.** swift-syntax ships empty marker modules `SwiftSyntax509` ... `SwiftSyntax605`; "All versions of swift-syntax >= 509 will include an empty `SwiftSyntaxVersion509` module" (the doc says `SwiftSyntaxNNN` in the code sample) ([Macro Versioning.md](https://raw.githubusercontent.com/swiftlang/swift-syntax/main/Sources/SwiftSyntax/Documentation.docc/Macro%20Versioning.md); `swift-syntax@be549876fe91:Package.swift:234-235`). Measured (fixture `b2-ladder/`): a library with range `"600.0.0"..<"606.0.0"` and an `#if canImport(SwiftSyntax605) ... #elseif canImport(SwiftSyntax604) ...` ladder printed `604` by default, `600` under a consumer root `exact: "600.0.1"`, `603` under `exact: "603.0.2"` (all exit 0). Real sites: `swift-composable-architecture@bc2db5ba8ad3:Sources/ComposableArchitectureMacros/ObservableStateMacro.swift:18,272`; `swift-dependencies@b476cc576105:Sources/DependenciesMacrosPlugin/DependencyClientMacro.swift:76`.

**The range is only as wide as CI proves** (fixture `b2-ladder/`, `run-b3.sh`): `LadderBad` uses `InlineArrayTypeSyntax` (added after 600.0.1; absent from 600.0.1, present in 604.0.0, found by diffing the public type lists of the two tags) unguarded: default resolve builds (exit 0), consumer root `exact: "600.0.1"` fails `error: cannot find 'InlineArrayTypeSyntax' in scope` (exit 1). `LadderGood` wraps it in `#if canImport(SwiftSyntax602)` and builds at both ends (exit 0, prints `n/a-before-602` at 600.0.1). A declared lower bound that CI never builds is a claim, not a fact.

**Prebuilts.** On by default in 6.4: `usePrebuilts: Bool = true` (`swift-package-manager@5546f44a3b52:Sources/CoreCommands/Options.swift:220-223`), and `swift build --help` prints `--enable-experimental-prebuilts/--disable-experimental-prebuilts ... (default: --enable-experimental-prebuilts)`. Introduced as opt-in in 6.1.1 for 600.0.1 and 601.0.1, "If prebuilts aren't available for that combination, SwiftPM will build from source as it does today", macro targets only ([forum 80202](https://forums.swift.org/t/preview-swift-syntax-prebuilts-for-macros/80202), dschaefer2, 2025-05-29); extended in 6.3 to libraries "only used by macros", disabled when a non-macro target may use them ([SwiftPM 6.3 release notes](https://raw.githubusercontent.com/swiftlang/swift-package-manager/main/Sources/PackageManagerDocs/Documentation.docc/ReleaseNotes/6.3.md)). Selection is by resolved package version (`Workspace+Prebuilts.swift:551-554`) and host platform: Linux hosts are matched on `/etc/os-release` against ubuntu noble/jammy/focal, fedora 39/41, amazonlinux 2, rhel 9, debian 12 only (`swift-package-manager@5546f44a3b52:Sources/PackageModel/PrebuiltLibrary.swift:154-278`); no match -> no prebuilts manager (`Sources/Workspace/Workspace.swift:599-602`). The research image is Ubuntu `VERSION_CODENAME=resolute`, so no prebuilts directory appeared and a build of the range-pinned macro package (604.0.0, 16 s wall) and the exact-prerelease one (19 s) both compiled swift-syntax from source; this measurement cannot distinguish them. "A prerelease pin defeats prebuilts" therefore remains an inference from the version-keyed lookup, flagged unverified. Practical consequence for the fleet: on a CI image whose distro is not in the list (a new Ubuntu LTS, Alpine, the static SDK host) the "swift-syntax is cheap" premise does not hold. Apple platforms use a different mechanism (Xcode default `IDEPackageEnablePrebuilts`), unverified: read only.

**Multiple majors are being built** ([forum 86317](https://forums.swift.org/t/multiple-major-versions-of-a-package-in-swiftpm-opening-the-discussion/86317), bripeticca, 2026-04-28, project board 2026-05-20); until it ships, "SwiftPM cannot hold two majors" (all fixtures above).

### 7. Macros in foundational libraries

[Forum 82587](https://forums.swift.org/t/macros-in-foundational-libraries/82587) (2025-10-08, ktoso opens for swift-distributed-tracing): Honza Dvorsky (Apple): fine "as long as there's a way to opt out ... a separate product ... or using package traits (and it's fine for the trait to be enabled by default ...)"; Johannes Weiss: "I don't think there's a reasonable path to adoption of macros whilst we require a single swift-syntax version for the whole graph"; Franz Busch: the two problems are build time (solved by prebuilts) and a new major per Swift release. The opt-out only helps if SwiftPM does not fetch the macro dependency when the trait is off. Measured: a dependency referenced only under `condition: .when(traits: ["Zed"])` is never fetched while the trait is off (unreachable `https://invalid.invalid/bogusdep.git`, `swift package resolve` exit 0; with the trait on, exit 1); a second, ungated target reference (`Other` target, in the same package) made it fetch anyway (exit 1) (fixture `c-traits/run-c3.sh`, `run-c4.sh`, 6.4 and 6.3). bripeticca's stated criteria match: guarded in every target reference and used nowhere else; `--experimental-prune-unused-dependencies` (default false, `Options.swift:414-420`) is a separate experimental switch. ### 8. Traits

- Status: SE-0450, implemented in Swift 6.1; manifest API needs tools 6.1. A `traits:` manifest under tools 6.0 fails (`'init(name:...traits:...)' is unavailable`, `'when(traits:)' is unavailable`, exit 1; fixture `c-traits/lib60`, run-c5). `swift package show-traits` arrived in 6.3 ([6.3 release notes](https://raw.githubusercontent.com/swiftlang/swift-package-manager/main/Sources/PackageManagerDocs/Documentation.docc/ReleaseNotes/6.3.md)); on 6.4 it printed `Verbose - Extra logging (default)` / `Zed - ...`.
- Syntax (6.4, verified by compile): in the defining package `traits: [.trait(name: "Zed", description: "..."), .default(enabledTraits: ["Verbose"])]`; gated dependency `.product(name: "ZDep", package: "zdep", condition: .when(traits: ["Zed"]))`; in code `#if Zed`. Trait names are Swift identifiers plus `-` and `+`; `default`/`defaults` (any case) are reserved ([PackageTraits.md](https://raw.githubusercontent.com/swiftlang/swift-package-manager/main/Sources/PackageManagerDocs/Documentation.docc/Dependencies/PackageTraits.md)); SE-0450 limits a package to 300 traits.
- Default traits: if none are declared, none are on. Removing a default trait or removing API behind a trait is SemVer-major; adding a trait is not (docs above; SE-0450 "Default traits"). Traits are unified across the whole graph, so they "should be additive" and mutually exclusive traits need `#error` guards (SE-0450 "Trait unification").
- Dependent side (fixture `c-traits/`, consumers of `lib` whose default is `Verbose`): no `traits:` -> `plain true` (defaults only); `traits: []` -> `plain false`; `traits: ["Zed"]` -> `zed-1.0.0 false` (default `Verbose` LOST, pin for `zdep` appears); `traits: [.defaults, "Zed"]` -> `zed-1.0.0 true`. The docs state the same in a tip ("The default traits aren't included automatically").
- CI matrix (fixture `c-traits/run-c2.sh`): in `libBroken`, `#if Zed` references `ZDep.doesNotExist`. `swift build` exit 0 (the error is invisible), `swift build --enable-all-traits` exit 1, `swift build --disable-default-traits --traits Zed` exit 1, `swift build --disable-default-traits` exit 0; the twin `lib` passes all. Flags are SE-0450's `--traits`, `--enable-all-traits`, `--disable-default-traits`.
- Typo hole: `#if Zedd` (undeclared flag) containing a type error built with exit 0 under `--enable-all-traits`, in both toolchains (fixture `run-c5.sh`): there is no compile-time check that a flag is a declared trait (SE-0450 lists "Integrated compiler trait checking" as future direction). Mitigation is a reading heuristic or a test that exercises each trait.
- Corpus (30 `.trait(` declarations in 8 repos, [pkg](../swift-audit/exemplar-packaging-and-release.md)): swift-collections gates unstable API behind empty-default traits `UnstableContainersPreview` / `UnstableSortedCollections` / `UnstableHashedContainers` (`swift-collections@935f696a549a:Package.swift:17-48`), the textbook "experimental API" use; swift-protobuf defaults two traits ON (`BinaryDelimitedStreams`, `FieldMaskUtilities`, `swift-protobuf@6c84c3dedac0:Package.swift:46-53`); swift-log uses seven `MaxLogLevel*` traits to COMPILE OUT API with `.default(enabledTraits: [])` (`swift-log@4038b6a4f74a:Package.swift:11-24`), contradicting the additive guidance on purpose (see Contested); swiftly passes `traits: []` to swift-subprocess to shed its optional dependencies (`swiftly@c8cf2e35bfca:Package.swift:34`). Xcode supports SE-0450 traits from 26.4 (Massicotte, 2026-03-27, as summarised in [prac](../swift-topic-map/practitioner.md); not fetched here; unverified: read only).

## AI-agent angle

What an LLM characteristically gets wrong here, and the smallest mechanical check:

1. **Xcode macro template reflex: `from: "604.0.0"` for swift-syntax** in a package other code depends on. Conflicts with siblings (exit 1). Check: D06 grep.
2. **Silencing a resolver conflict with `exact:`, `branch: "main"` or `revision:`**. Check: D01a grep; consumer `swift package resolve` exit 1 for a versioned library with a branch dependency.
3. **Closed range `"1.0.0"..."2.0.0"`**, believing it excludes 2.0.0. Check: D01b grep.
4. **`from: "1.0"`** (two components). Fails with an opaque manifest error (exit 1). Check: `swift package dump-package` exit code.
5. **`.package(name:url:from:)`** (pre-5.6 form). Deprecated warning only. Check: D12 grep.
6. **Cargo-style flags** `--locked`, `--frozen`, `--offline`, or `swift package update --locked`. "Unknown option" exit 64. Check: run it, or the D17 flag grep; correct spelling `--force-resolved-versions`.
7. **Treating `Package.resolved` as a lock without the flag**, or putting `Package.resolved` in `.gitignore` for a CLI/app (or committing one for a library and assuming consumers honour it). Check: D03 commands, D04 drift gate.
8. **Believing `--force-resolved-versions` needs no tracked file**: it passed on a warm scratch dir with the file deleted. Check: `git ls-files --error-unmatch Package.resolved`.
9. **`swift package update` inside the CI build job** to "fix" a failing build. Check: D05 grep.
10. **Reading `originHash` as a freshness signal** or hand-editing it. Check: review `git diff -- Package.resolved` pins only.
11. **`traits: ["X"]` expecting defaults to stay**, or inventing a trait API (`.package(url:..., traits: .defaults + ["X"])`, `.enable(...)`). Only `traits: [.defaults, "X"]` compiles. Check: D11 grep; `swift package dump-package` exit code.
12. **Trait name typo or a trait used under tools 6.0** (`traits:` unavailable, exit 1). Typos in `#if` are silent. Check: D12 reading heuristic and per-trait CI leg (`--traits <T>`).
13. **Using `_`-prefixed products because they autocomplete** (`_NIOFileSystem`, `_CryptoExtras`, `_Concurrency`-style names). Check: D13 grep.
14. **swift-crypto `from: "3.0.0"` / `"3.0.0"..<"5.0.0"` copied from older docs and blogs**. Check: D14 grep; the README range.
15. **Wide swift-syntax range without a ladder or lower-bound build** (compiles on the resolved latest, breaks on the lowest). Check: V7 pattern, a CI leg with `exact:` lowest.
16. **`#if swift(>=6.2)` instead of `canImport(SwiftSyntax602)`** to gate swift-syntax API; the compiler version is not the library version. Check: `grep -rn -e 'if swift(' --include='*.swift' Sources` in macro targets (reading heuristic).
17. **Prerelease pins copied from SwiftLint/swift-testing into a library** (`from: "605.0.0-latest"`). Check: D06b grep.
18. **Assuming prebuilts make swift-syntax free on every Linux image**. Check: `grep -e '^ID=' -e '^VERSION_CODENAME=' /etc/os-release` against the supported list in section 6 (reading heuristic).

## Contested / evolving

- **Package.resolved for libraries** (stable, as of 2026-10): SwiftPM docs and 23 of 40 repos ignore it; Point-Free commits it for Xcode workspaces. The 2023 pitch to make it a real lock file did not change defaults ([forum 68475](https://forums.swift.org/t/pitch-swiftpm-treating-package-resolved-as-a-lock-file/68475)). Trend: ignore for libraries, track plus flag for shipped roots. Xcode still behaves differently from SwiftPM (unverified: read only).
- **Multiple major versions in one graph** (moving fast): a SwiftPM effort opened 2026-04-28 reuses module aliasing and PubGrub changes, board created 2026-05-20 ([forum 86317](https://forums.swift.org/t/multiple-major-versions-of-a-package-in-swiftpm-opening-the-discussion/86317)); if it lands, the multi-major range plus ladder (D06/D07) may relax. Today it is required. Revisit at the first SwiftPM release that lists "multiple majors".
- **Macros in foundational libraries**: Johannes Weiss says not viable until swift-syntax stops needing one version graph-wide; Honza Dvorsky says fine with an opt-out; ktoso intends an SSWG/ESG recommendation ([forum 82587](https://forums.swift.org/t/macros-in-foundational-libraries/82587), 2025-10). Unresolved as of 2026-10-10; D09 follows the Apple position. Prebuilt coverage depends on the host distro (section 6) and on the published prebuilt set per swift-syntax version; the original 6.1.1 preview covered only 600.0.1/601.0.1.
- **Trait pruning scope**: the SE text says optional dependencies are fetched anyway; 6.3/6.4 prune when every reference is gated (measured). bripeticca calls the criteria incomplete and `--experimental-prune-unused-dependencies` is still experimental and default off. Expect the rules in D09/D10 to loosen once pruning is general.
- **Additive vs subtractive traits**: SE-0450 and the docs say "don't remove or disable public API when you enable a trait"; swift-log's `MaxLogLevel*` traits do exactly that, and documents it in its in-repo proposal `Sources/Logging/Docs.docc/Proposals/SLG-0002.md`. Treat compile-out knobs as the one accepted exception and document them.
- **Underscored products**: graduating (swift-crypto `_CryptoExtras` -> `CryptoExtras`, done in 4.0; swift-nio `_NIOFileSystem` -> `NIOFileSystem`, inferred from `Package.swift:58`) while some Apple repos (containerization) still use the underscored name. Ban stands; re-check the product list of the exact dependency version before accepting a flagged exception.
- **Exact pins in published frameworks**: vapor's dated `exact:` shows the pragmatic exception; the position that `exact:` is never right in a library is the SwiftPM-docs reading (consumers cannot satisfy two exact pins). No core-team statement found either way.
- **swift-crypto 5.0 `@nonexhaustive` enums** (README, September 2026): whether a `"1.0.0"..<"6.0.0"` range needs `@unknown default` handling for code that switches over CryptoKit enums is not verified (read only).
