## Summary

- Configuration cache in Gradle 9.x is the **preferred execution mode with automatic graceful fallback** — an incompatible feature no longer fails the build, it silently falls back to non-cached execution — and the target for making it the *default* moved from Gradle 10.0 to **Gradle 11** ([road-to-cc](https://blog.gradle.org/road-to-configuration-cache)).
- Gradle 9.0.0 closed the old "ignore and still cache" escape hatch: in `--configuration-cache-problems=warn` mode, a task explicitly marked incompatible (`notCompatibleWithConfigurationCache`) now **always causes its cache entry to be discarded**, even though other problems in warn mode still store an entry ([9.0.0 release notes](https://docs.gradle.org/9.0.0/release-notes.html)).
- The plugin/task-author contract lives on one page, [Configuration Cache Requirements](https://docs.gradle.org/current/userguide/configuration_cache_requirements.html) — treat it as the grep-able source of truth, not a summary of it.
- `Task.getProject()` (or any `Project` reference) at execution time is a hard violation; the fix is `@Inject FileSystemOperations`/`ExecOperations` and a `Property<T>` for anything read from `Project` today.
- Live-JVM-state types (`ClassLoader`, `Thread`, `Socket`, `OutputStream`) and concurrency primitives (`Lock`, `Semaphore`, `CountDownLatch`, `CyclicBarrier`, `Phaser`) are banned from task fields/actions outright — the replacement is a **Build Service**, not a workaround.
- `Gradle`, `Settings`, `Project`, `SourceSet`, `Configuration`, `SourceDirectorySet` must never be task inputs — declare the specific `Property`/`FileCollection`/`FileTree`/`Provider<ResolvedComponentResult>` you actually need instead.
- Reading a file, running a process, or enumerating env vars/system properties at configuration time each has one documented replacement: `providers.fileContents(file).asText`, `providers.exec()`/`ValueSource`, and `providers.environmentVariablesPrefixedBy("PREFIX")` (or a named `System.getenv("KEY")`) respectively.
- Registering a `BuildListener` or `TaskExecutionListener` at configuration time is disallowed outright — no fallback flag makes it legal; the replacement is a Build Service registered as `OperationCompletionListener` via `BuildEventsListenerRegistry`.
- **The reviewer's one command**: run the real build with `--configuration-cache` (property already set is fine); Gradle prints an "N problems were found" line and writes `configuration-cache-report.html` only when problems exist — no such line and no report means the build is config-cache clean for that invocation.
- **Verdict (a)**: enabling the configuration cache is a **SHOULD** for an application/library build on Gradle 9.x today (preferred, safe due to automatic fallback, but not yet the default and not yet universally supported by every core/third-party plugin); it is effectively a **MUST** for anyone authoring a Gradle **plugin** — TestKit + `--configuration-cache` compatibility is a day-one gate because your consumers will increasingly run with it on regardless of your own choice.
- **Verdict (c)**: Isolated Projects is **diagnostics-only today**, not a gate — it left "experimental" for "incubating" only in 9.7.0 (2026-08-06, one month before this research), and its own docs list two constraint categories ("cross-build access," "build-to-project access") as **not fully enforced yet**.
- The isolated-projects property is `org.gradle.isolated-projects`; `org.gradle.unsafe.isolated-projects` is the historical name, deprecated as of 9.7.0 and still accepted but slated for removal — 0/32 corpus repos use the dead key, 5/32 use the live one.
- Square's 2022 configuration-cache rollout postmortem holds up as the load-bearing precedent: the blockers that cost the most engineering time were **third-party plugin incompatibility** (forking Wire, patching their own Anvil), not their own application/task code — a rule teaching this topic should lead with "audit your plugins," not "audit your tasks."
- `gradle/gradle#18520` (open) shows the build-listener ban is still an active migration-friction point for real plugin authors three-plus years after the page describing the fix existed.
- `gradle/gradle#24040` documents the Gradle-9-era behavior change for `maven-publish` with explicit repository credentials: instead of a hard failure (older behavior), explicit credentials now **silently disable the configuration cache** for that publish task — a concrete instance of "automatic graceful fallback," and a trap for anyone assuming "no error" means "cached."
- Configuration-cache encryption is on by default (an auto-managed keystore under `GRADLE_USER_HOME`); a reviewer chasing "cache never hits across CI runners" should check for a stable `GRADLE_ENCRYPTION_KEY`, since a rotating key silently defeats reuse without any error.
- `ValueSource` is the escape hatch for anything not covered by a named provider: it is explicitly exempt from Gradle's automatic configuration-cache-input detection, and its `obtain()` re-runs every build to decide cache freshness.

## Findings

### 1. What "preferred with automatic fallback" means operationally

Gradle's own 9.0.0 release notes describe the configuration cache as "the preferred mode of execution," and state Gradle "encourages adoption by prompting users and gradually phasing out incompatible APIs to prepare for a future where it becomes the only supported mode," while explicitly stating "Gradle falls back to non-Configuration Cache mode automatically when encountering unsupported features, instead of failing the build" ([9.0.0 release notes](https://docs.gradle.org/9.0.0/release-notes.html)). This is a behavior change in *tone*, not a new mechanism — configuration cache has been stable since Gradle 8.1 — but it is the sentence that justifies calling it "preferred" rather than merely "available." The Gradle blog's own migration roadmap states the original goal was "enabling it by default in Gradle 10.0"; the topic map's cross-check against [practitioner-and-conferences.md](../jvm-topic-map/practitioner-and-conferences.md) resolves the target as having moved to **Gradle 11** ([road-to-cc](https://blog.gradle.org/road-to-configuration-cache)).

### 2. The Gradle 9 warning-mode change

Prior to Gradle 9, `--configuration-cache-problems=warn` meant "record problems, but still write and reuse a cache entry regardless of severity." Gradle 9.0.0 changed this specifically for tasks marked incompatible (`notCompatibleWithConfigurationCache(reason)` or the plugin equivalent): "Tasks marked as incompatible prevent cache hits in warning mode, ensuring correctness" ([9.0.0 release notes](https://docs.gradle.org/9.0.0/release-notes.html)). Practically: warn mode still tolerates *undeclared* problems (arbitrary configuration-cache violations Gradle detected but the task didn't self-declare), but a task that explicitly opts out of compatibility can no longer ride along in a cached build — its presence discards the entry outright. [gradle-canonical.md](../jvm-topic-map/gradle-canonical.md) independently corroborates this as "the old 'ignore problems and still cache' escape hatch is gone," citing [upgrading_major_version_9.html](https://docs.gradle.org/current/userguide/upgrading_major_version_9.html).

### 3. Disallowed types at execution time, and their replacements

| Disallowed at execution time | Why | Documented replacement |
|---|---|---|
| `ClassLoader`, `Thread`, `Socket`, `OutputStream` (any live-JVM-state type) | "do not represent task inputs or outputs" | Build Service to hold/share the live resource |
| `Lock`, `ReadWriteLock`, `CountDownLatch`, `CyclicBarrier`, `Phaser`, `Semaphore` | cannot "be referenced by task fields or captured in task actions" | Shared Build Service for cross-task coordination |
| `Project`, `Gradle`, `Settings` | pass task inputs implicitly; the "obvious" way to reach a value that should be declared | `Property<T>`/`Provider<T>` for the specific value (e.g. `project.version` → `Property<String>`) |
| `Task.getProject()` (any `Project` access from a running task) | the single most-cited hard violation, and a standalone Gradle Best Practice independent of config-cache | `Task.logger` for `Project.logger`; `@Inject FileSystemOperations` for `project.copy{}`; `@Inject ExecOperations` for `project.exec{}` |
| `SourceSet`, `Configuration`, `SourceDirectorySet` | "contain unnecessary state and are not precise" as inputs | `FileCollection` for resolved `Configuration` files, `FileTree` for `SourceDirectorySet` files, `Provider<ResolvedComponentResult>`/`ArtifactCollection.getResolvedArtifacts()` (returns `Provider<Set<ResolvedArtifactResult>>`) for dependency-graph data |

Source for the whole table: [Configuration Cache Requirements](https://docs.gradle.org/current/userguide/configuration_cache_requirements.html), sections "Certain Types must not be Referenced by Tasks" and "Using the `Project` Object at Execution Time."

Standard streams (`System.in/out/err`) are the one documented exception to the live-JVM-state ban, permitted specifically for `Exec`/`JavaExec` tasks.

### 4. Disallowed configuration-time operations, and their replacements

| Disallowed at configuration time | Why | Documented replacement |
|---|---|---|
| Reading a file directly (`file("x").readText()`, `java.nio.file.Files`, etc.) | undeclared file read becomes an untracked cache input | `providers.fileContents(layout.projectDirectory.file("some.conf")).asText` |
| `ProcessBuilder`, `Runtime.exec()`, `ExecOperations.exec` at configuration time | untracked, unreproducible side effect during configuration | `providers.exec()` / `providers.javaexec()` for simple cases; a custom `ValueSource` with `@Inject ExecOperations` in `obtain()` for anything needing more control |
| Enumerating `System.getenv()` / `System.getProperties()` (`.forEach{}`, `.filterKeys{}`) | "every available property becomes one [cache input]" — turns the whole environment into cache-busting state | `System.getenv("KEY")` / `System.getProperty("key")` (named, singular) or `providers.environmentVariablesPrefixedBy("PREFIX")` for a filtered group; a custom `ValueSource` for arbitrary filter logic |
| Registering a `BuildListener` or `TaskExecutionListener` at configuration time, fired at execution time | no fallback exists — flatly disallowed, not merely discouraged | a Build Service implementing `OperationCompletionListener`, registered through `BuildEventsListenerRegistry` for task-completion notifications; dataflow actions for `buildFinished`-style results |
| Resolving a `Configuration` before task execution (outside a task action) | eager resolution defeats configuration avoidance and can leak into config-cache serialization | defer resolution into the task action via a `FileCollection`/`Provider` input |

Source: [Configuration Cache Requirements](https://docs.gradle.org/current/userguide/configuration_cache_requirements.html), sections "Using External Information Sources," "Running External Processes," "Reading System Properties and Environment Variables," "Using Build Listeners." Dependency-resolution-at-configuration-time is additionally covered by Gradle's own [Best Practices for Tasks](https://docs.gradle.org/current/userguide/best_practices_tasks.html) ("Don't resolve Configurations before Task Execution") — cited independently in [gradle-canonical.md](../jvm-topic-map/gradle-canonical.md) — and remains *legal*, not enforced, because [gradle/gradle#2298](https://github.com/gradle/gradle/issues/2298) ("Forbid dependency resolution at configuration time by default") is still open per [failure-build-and-deps.md](../jvm-topic-map/failure-build-and-deps.md).

`ValueSource` deserves its own note: it is "exempt from the automatic detection of configuration cache inputs," meaning Gradle trusts the author to declare the right parameters; when queried at configuration time its value becomes a tracked build-configuration input and `obtain()` re-runs on every subsequent build purely to decide cache freshness, not to redo the work.

### 5. The CLI and property surface, precisely

- `org.gradle.configuration-cache=true` (gradle.properties) or `--configuration-cache` (CLI) turns the cache on for that build.
- `--no-configuration-cache` overrides an `=true` property for one invocation.
- `--configuration-cache-problems=warn` (or the equivalent `org.gradle.configuration-cache.problems=warn` property) is the flag named in the brief; the documented default is **fail**: "By default, Gradle fails the build if Configuration Cache problems occur" ([configuration_cache_enabling.html](https://docs.gradle.org/current/userguide/configuration_cache_enabling.html)). `warn` stores a cache entry despite problems (see §2 for the incompatible-task exception Gradle 9 added).
- `org.gradle.configuration-cache.max-problems=512` caps how many problems are collected before Gradle gives up trying to enumerate more.
- **The reviewer's single command**: run the actual build/test invocation your CI uses, with `--configuration-cache` appended (or already on via the property) — e.g. `./gradlew build --configuration-cache`. Gradle either completes silently (no "N problems were found" summary line, no `configuration-cache-report.html` written) — **clean** — or prints the problem count and writes the HTML report under `build/reports/configuration-cache/.../configuration-cache-report.html` for triage. Empty/absent output on that line is the pass signal; there is no separate "check" task to run instead of the real build.

### 6. Isolated Projects: status, not yet a gate

[Isolated Projects](https://docs.gradle.org/current/userguide/isolated_projects.html) reached **incubating** status only in **Gradle 9.7.0 (released 2026-08-06)**, promoted from experimental — "APIs and behavior may still change in future Gradle versions while it remains incubating." It is enabled via `org.gradle.isolated-projects=true` (gradle.properties) or `--isolated-projects` (CLI); the historical `org.gradle.unsafe.isolated-projects` property is now explicitly "deprecated but still accepted," per the current docs page, and the [9.7.0 release notes](https://docs.gradle.org/9.7.0/release-notes.html) confirm: "The legacy `org.gradle.unsafe.isolated-projects` property names are now deprecated and will be removed in a future release."

The feature forbids reading or mutating another project's/build's mutable state during configuration — "calling `project(":other").tasks` or `gradle.extensions` is not allowed" — with a landmine the docs call out explicitly: "**Caution:** `group` and `version` are **mutable**!" even though they look like immutable identity fields. `gradle.lifecycle.beforeProject`/`afterProject` callbacks are the recommended, Isolated-Projects-compatible replacement for cross-project configuration logic, but "must be registered from settings, not from a project."

Critically, the same 9.7.0-era docs state two of the four constraint categories are **not fully enforced yet**: "Cross-build access constraints are not fully enforced yet" and "Build-to-project access constraints are not fully enforced yet." Combined with 9.7.0 being barely a month old at research time, and 9.7.0's own violation-reporting model changing in the same release (fail-fast-on-first-violation by default, with a new opt-in Diagnostics mode to collect all violations without failing), this is unambiguously **diagnostics-first territory**: run with `--isolated-projects` in Diagnostics mode to surface violations, don't fail CI on them yet.

### 7. Square's 2022 postmortem: the blockers were dependencies, not tasks

Square's own migration writeup — still the most detailed public account of a real configuration-cache rollout — names exactly two blockers, and both are third-party plugins, not Square's own build logic: Anvil (which Square itself maintains) needed updating, and Wire versions in use were configuration-cache-incompatible, forcing the Foundations team to maintain a fork "until upstream caught up" ([Square: 5,400 hours a year](https://developer.squareup.com/blog/5-400-hours-a-year-saving-developers-time-and-sanity-with-gradles/), 2022; corroborated in [failure-build-and-deps.md](../jvm-topic-map/failure-build-and-deps.md)). The projected payoff (5,400 engineer-hours/year, builds "eventually" 3x faster) was large enough to justify a phased opt-in rollout with case-by-case opt-out before flipping to default-on. **This holds today and generalizes**: for any real build, the first configuration-cache migration step is running `--configuration-cache` and reading which *plugins* (not which tasks you wrote) appear in the problems report — the task-level fixes in §3–4 matter mainly for build-logic you author yourself (convention plugins, custom tasks), which is a much smaller surface than your full plugin graph.

### 8. Live migration-friction evidence from gradle/gradle's own tracker

- [#18520](https://github.com/gradle/gradle/issues/18520) (open) — a real plugin author (`build-time-tracker`) hit the build-listener ban directly: `Gradle.addListener` registration fails under the configuration cache with "registration of listener on 'Gradle.addListener' is unsupported," and the issue is explicitly asking Gradle for a clearer migration path from `BuildListener` to Build Services, because `BuildEventsListenerRegistry` only exposes a task-completion hook, not build-start/build-finish equivalents. This confirms §4's "no fallback exists" framing is a real, currently-unsolved gap for some listener use cases, not a hypothetical.
- [#19793](https://github.com/gradle/gradle/issues/19793) (closed, filed against Gradle 7.4-rc-1/7.3.3) — an included build using kapt failed only when consumed by a parent build under the configuration cache (`ISE: GradleProperties has not been loaded yet`), while working standalone; the reporter's own diagnosis points at a `Task.project` read at execution time inside kapt's Gradle integration. Included builds interacting with the configuration cache remain a documented sharp edge even after the underlying bug's resolution.
- [#24040](https://github.com/gradle/gradle/issues/24040) — originally filed against Gradle 8.0.1 (explicit Maven-repository credentials caused a hard failure asking for implicit gradle.properties-based credentials instead). The issue's own "Update for Gradle 9" comment documents the *behavior change*: "now, when explicit credentials are used, instead of causing a build failure, explicit credentials disable the configuration cache" — a concrete, citable instance of "automatic graceful fallback" from §1, and a trap: a `maven-publish` task with explicit repository credentials will build successfully every time while never actually being cached, with no error to notice.

## Normative guidance candidates

1. **Never reference `Project` (or call `Task.getProject()`) inside a task action.** Rationale: hard configuration-cache violation, independently a standalone Gradle Best Practice. Verify: `grep -rn 'getProject()\|\.project\.' --include='*.gradle.kts' --include='*.kt' --include='*.java'` inside task-action closures/`doLast`/`doFirst` bodies, cross-checked against `./gradlew <task> --configuration-cache` output naming the offending class.
2. **Never enumerate `System.getenv()` or `System.getProperties()` without a filter.** Rationale: turns every environment variable into a cache-invalidating input, "poisoning" the cache-input set (P0 per [caching-and-correctness.md](../jvm-topic-map/gradle-canonical.md)). Verify: `grep -rn 'System\.getenv()\.\(forEach\|filterKeys\|entries\)\|System\.getProperties()\.' --include='*.gradle.kts' --include='*.kt'`; the fix is `providers.environmentVariablesPrefixedBy("PREFIX")` or a named `System.getenv("KEY")`.
3. **Never read a file directly at configuration time; use `providers.fileContents(...).asText`.** Rationale: an undeclared file read is an untracked, cache-busting input. Verify: reading heuristic — any `.readText()`/`Files.readAllLines`/`Files.readString` call outside a task action, at the top level of a `build.gradle(.kts)` file or in a plugin's `apply()` body.
4. **Never shell out (`ProcessBuilder`, `Runtime.exec`, `ExecOperations.exec`) at configuration time.** Rationale: same untracked-side-effect problem, worse because it also slows every configuration phase. Verify: `grep -rn 'ProcessBuilder(\|Runtime\.getRuntime()\.exec\|\.exec {' --include='*.gradle.kts'` outside task-action bodies; the fix is `providers.exec()`/`providers.javaexec()` or a custom `ValueSource`.
5. **Never register a `BuildListener` or `TaskExecutionListener` from a plugin or build script.** Rationale: flatly disallowed under the configuration cache, no fallback exists (confirmed still live friction: [gradle/gradle#18520](https://github.com/gradle/gradle/issues/18520)). Verify: `grep -rn 'addBuildListener\|addListener\|TaskExecutionListener\|BuildListener' --include='*.gradle.kts' --include='*.kt' --include='*.java'`; the fix is a Build Service registered via `BuildEventsListenerRegistry`.
6. **CI must actually run with `--configuration-cache` (or the property set) and triage the report — not blanket-suppress with `warn` mode.** Rationale: Gradle 9 made warn-mode useless as a silent escape hatch for incompatible tasks (§2); `warn` should be a temporary migration aid with an expiry, not a steady state. Verify: check `gradle.properties` first (per [exemplar-publishing-ci-bazel.md](../jvm-audit/exemplar-publishing-ci-bazel.md), the CLI flag appears in only 3/32 CI workflows against 10/32 setting the property — "check gradle.properties first" is the reading heuristic), then confirm no long-lived `--configuration-cache-problems=warn` in CI config without a tracking issue.
7. **When migrating, audit third-party plugins first, not your own tasks.** Rationale: Square's 2022 postmortem — the load-bearing public precedent — names plugin incompatibility (Anvil, Wire), not application code, as the actual blocker. Verify: run `./gradlew help --configuration-cache` (or your real build) once, and read the problems report's plugin/class attribution before touching any of your own task code.
8. **Do not treat Isolated Projects as a hard CI gate yet; run it in diagnostics mode only.** Rationale: incubating only since 9.7.0 (2026-08-06), with two constraint categories the docs themselves call "not fully enforced yet." Verify: `grep gradle.properties` for `org.gradle.isolated-projects=true`; if present in CI as a failing gate (not diagnostics), flag for review — pair with `--isolated-projects` run manually to see the current violation count before deciding.
9. **Reject `org.gradle.unsafe.isolated-projects` in any new or reviewed content; the current key is `org.gradle.isolated-projects`.** Rationale: the historical key is deprecated as of 9.7.0 and slated for removal; 0/32 corpus repos use it, 5/32 use the live key. Verify: `grep -rn 'unsafe.isolated-projects' **/gradle.properties` — any hit is stale.
10. **A Gradle plugin under active development must be tested under `--configuration-cache` via TestKit as a release gate, independent of whether the plugin's own consumers enable it.** Rationale: plugin authors don't control when their consumers turn the cache on, and Gradle's own trajectory (preferred mode, default at 11) makes this a "when," not an "if." Verify: a TestKit test asserting `GradleRunner.withArguments("build", "--configuration-cache").build()` succeeds with zero reported problems, run in plugin CI.
11. **Treat explicit repository credentials on a `maven-publish` repository as a configuration-cache smell, not a safe pattern.** Rationale: Gradle 9 silently disables the cache for that task rather than failing (`gradle/gradle#24040`) — a build can appear to work while quietly never being cached. Verify: grep `publishing { repositories { maven(...) { credentials { ... } } } }` for literal/explicit credential blocks vs. `PasswordCredentials`/env-var-backed provider wiring; prefer the latter.

## Exemplar evidence

- **Satisfies #9 (current key only)**: `android/nowinandroid@12f80da651:gradle.properties`, `gradle/gradle@ea17004a31:gradle.properties`, GradleUp/shadow, junit-framework, okhttp — all set `org.gradle.isolated-projects=true`; zero corpus repos (0/32) set the dead `org.gradle.unsafe.isolated-projects` key ([exemplar-build-shape.md §4](../jvm-audit/exemplar-build-shape.md)).
- **Partial evidence for #6 (CI re-asserting vs. inheriting)**: 11/20 gradle-properties-bearing repos set `org.gradle.configuration-cache=true`; the CLI flag `--configuration-cache` appears in only 3/32 CI workflows against 10/32 setting the property, and `--build-cache` in 7/32 against 17/32 — CI overwhelmingly inherits rather than re-asserts ([exemplar-publishing-ci-bazel.md](../jvm-audit/exemplar-publishing-ci-bazel.md)).
- **Aggressive-adoption exemplar**: `android/nowinandroid@12f80da651:gradle.properties` is the only corpus repo combining `org.gradle.isolated-projects=true` with `ksp.project.isolation.enabled=true` — the two most correctness-forward flags in the corpus, together.
- **No corpus repo directly demonstrates violating #1–#5** in a checked-out build file (these are task/plugin-internals-level violations the audits did not source-grep for beyond `gradlePlugin{}` block presence); treat #1–#5 as grounded in Gradle's own documented contract plus live GitHub-issue evidence (§8 above), not corpus counter-examples — a gap worth naming rather than papering over.
- **Contradicts the frame's own era assumption**: [exemplar-build-shape.md](../jvm-audit/exemplar-build-shape.md) itself states in its "Contradictions" section that "Gradle 9's default is already on regardless of the property" — this is **not supported** by the primary sources fetched here (§1: preferred-with-fallback, default targeted at 11, confirmed by `blog.gradle.org/road-to-configuration-cache` and the 9.0.0 release notes) and should be read as an overstatement in that audit, not as a corrected fact; the topic map's resolution ("Configuration cache is 'preferred with automatic fallback' in Gradle 9, not on by default... the frame is wrong") is the binding one.

## AI-agent angle

- **Trained-era default assumption**: a model is likely to assert "Gradle 9 has the configuration cache on by default" (plausible-sounding, half-true from stale blog framing) — check: `grep gradle.properties` for an explicit `org.gradle.configuration-cache` setting before asserting the property is redundant; absence means the build is running whatever Gradle's actual current default is (still opt-in as of 9.7.x), not silently cached.
- **`org.gradle.unsafe.isolated-projects`**: this is the name that dominated blog posts, Stack Overflow answers, and conference talks for years before the 9.7.0 rename/deprecation — a model trained on that corpus will reach for it by reflex. Check: any generated `gradle.properties` snippet using the `unsafe.` prefix is stale; the current key is `org.gradle.isolated-projects`.
- **`project.copy{}` / `project.exec{}` in generated task code**: these are the idiomatic Groovy-era (and pre-config-cache-aware Kotlin DSL) patterns a model will reach for first when writing a custom task; they are hard configuration-cache violations. Check: any generated task class using `project.` inside a `doLast`/action body should instead show `@get:Inject abstract val fs: FileSystemOperations` (or `ExecOperations`) as a constructor/property injection point.
- **`System.getenv()` used broadly "to be safe"**: a model asked to "make this task read an env var" will often generate a full-environment scan (`System.getenv().forEach { ... }`) rather than a single named lookup, especially when the actual key name is templated/dynamic. Check: any environment-variable access touching more than one named key without `providers.environmentVariablesPrefixedBy(...)` is a smell.
- **Registering a `BuildListener` for "log build start/finish" tasks**: a very common "helper plugin" ask (build-time tracking, notification-on-finish) whose textbook implementation is exactly the pattern [#18520](https://github.com/gradle/gradle/issues/18520) shows is broken under the cache. Check: any generated plugin using `gradle.addBuildListener(...)`/`addListener(...)` needs to be redirected to a Build Service + `BuildEventsListenerRegistry`, and the model should be told this explicitly rather than trusted to know it — the "obvious" API still exists and still compiles.
- **Assuming `warn` mode is a safe permanent CI setting**: pre-Gradle-9 training data would correctly describe warn mode as "logs problems, keeps caching" with no caveat; that is now half-wrong for tasks marked incompatible (§2). Check: any generated CI config setting `--configuration-cache-problems=warn` without a comment/tracking issue linking to a migration plan is citing pre-9.0 behavior as if it still fully applies.
- **Isolated Projects treated as production-ready because it's "in Gradle 9"**: a model reasoning purely from "Gradle 9.x, so all its incubating features are safe defaults" will overstate Isolated Projects' maturity. Check: any generated guidance recommending Isolated Projects as a required CI gate (versus diagnostics-only) needs to name the incubating status and the two unenforced constraint categories, or it is ahead of where the feature actually stands.

## Contested / evolving

- **Configuration-cache-on-by-default timing.** Gradle's own trajectory has already slipped once (10.0 → 11.0 target); treat any specific version number here as provisional and re-check `blog.gradle.org/road-to-configuration-cache` before hardcoding "default at Gradle 11" into a rule with a long shelf life. As of 2026-09-12: still opt-in, preferred, automatic fallback.
- **Isolated Projects' enforcement completeness.** Two of four constraint categories are explicitly unenforced as of 9.7.0 (2026-08-06); this is the kind of gap that closes across a handful of point releases (9.0→9.7 took about a year for experimental→incubating). Re-check the "Recent changes" section of the current `isolated_projects.html` before treating any specific constraint as either enforced or unenforced past this research date.
- **`maven-publish` compatibility with the configuration cache.** A March-2025 Gradle blog post names Maven Publish as a still-incompatible core plugin; `gradle/gradle#24040`'s "Update for Gradle 9" comment shows *credentialed* publish tasks specifically fall back rather than fail. Whether `maven-publish` is now fully compatible without caveats, partially compatible (only the credentials edge case falls back), or still broadly incompatible was **not resolved by the sources fetched for this dive** — a rule citing "maven-publish is/isn't config-cache-safe" should link to the current `configuration_cache_requirements.html`'s own plugin-compatibility notes (if any) rather than repeat the 2025 blog claim verbatim.
- **`dependencyResolution`-at-configuration-time remaining legal.** [gradle/gradle#2298](https://github.com/gradle/gradle/issues/2298) ("Forbid dependency resolution at configuration time by default") has been open long enough to be cited by two different scouts in this research program and is still open — Gradle treats this as a best-practice violation, not a hard gate, and there is no signal in the fetched sources that this will change soon.
