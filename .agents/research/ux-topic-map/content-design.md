# UX content design — landscape scout

Corpus: the words in the product. This scout discovers which decisions an agent makes each time it writes a string, ranks them for the OCX and Grimoire fleet (open-source developer tools: CLIs, Astro and MkDocs sites, one Vite GUI), and says which can be checked mechanically.

## What the corpus agrees on (the stable core)

These show up in nearly every source and are cheap for an agent to apply.

- An error says what happened, then how to fix it. NN/g (https://www.nngroup.com/articles/error-message-guidelines/, 14 May 2023) lists plain language, specific problem, remedy, nonjudgmental tone. GOV.UK (https://design-system.service.gov.uk/components/error-message/) and Adobe Spectrum (https://spectrum.adobe.com/page/writing-for-errors) give the same three-part shape.
- Generic labels fail: "OK", "Yes/No", "Learn more", "Click here", "Get started" (NN/g https://www.nngroup.com/articles/ui-copy/, 3 Mar 2019; https://www.nngroup.com/articles/learn-more-links/, 13 Dec 2015; https://primer.style/foundations/content; https://developers.google.com/style/ui-elements).
- Put the error text where the problem is, never rely on colour alone (NN/g above; WCAG 3.3.1 https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html, page updated 2 Nov 2026).
- Never build sentences from fragments; give translators whole messages (ICU https://unicode-org.github.io/icu/userguide/format_parse/messages/).

## Contested

Each row: the question, the positions, and the sources.

1. **Sentence case or title case for buttons and headings.**
   - Sentence case: GOV.UK button page https://design-system.service.gov.uk/components/button/ ; Primer https://primer.style/foundations/content ("When unsure, don't capitalize").
   - Title case: Apple alert button titles and fragment alert titles (https://developer.apple.com/tutorials/data/design/human-interface-guidelines/alerts.json); Apple writing says choose one style per UI element type (https://developer.apple.com/tutorials/data/design/human-interface-guidelines/writing.json). Polaris and Microsoft: sentence case everywhere (grammar-and-mechanics.mdx in the Polaris clone; https://learn.microsoft.com/en-us/style-guide/global-communications/writing-tips).
   - Evidence quality: Apple's own page is now read (below), replacing the earlier unverified search-result claim. No controlled study was found; the strong claims come from style guides.

2. **Apology and politeness words in errors.**
   - Avoid: GOV.UK bans sorry and please (https://design-system.service.gov.uk/components/error-message/); Atlassian says sorry makes errors seem more severe and please makes required steps sound optional, except for severe irreparable cases (https://atlassian.design/foundations/content/designing-messages/error-messages); Primer drops "Sorry".
   - Allow in serious cases: Adobe Spectrum apologises only for data loss or major actions (https://spectrum.adobe.com/page/writing-for-errors); NN/g suggests pairing an apology with something novel for total system failure (https://www.nngroup.com/articles/error-message-guidelines/).

3. **Humor in errors and empty states.**
   - No: NN/g, "avoid humor" because it goes stale on repeated errors; Primer, "Don't try to be funny"; GOV.UK bans "oops".
   - Conditionally: Mailchimp, humor only when natural, "when unsure, keep a straight face", "forced humor can be worse than none" (https://styleguide.mailchimp.com/voice-and-tone/). NN/g also recommends delight for total failure (guideline 13). The conflict is real; for an automated agent the safe default is no humor in failure states.

4. **Who speaks: "we" in error text.**
   - Atlassian: do not use "we" in place of "you", it can make people feel responsible.
   - Adobe Spectrum: use "we" when the interface owns a failure, "you" for user actions.
   - Apple: avoid "we" entirely, write "Unable to load content" (https://developer.apple.com/tutorials/data/design/human-interface-guidelines/writing.json). Polaris: "we" only when Shopify caused the problem (error-messages.mdx in the Polaris clone).

5. **Where the key information goes in a diagnostic.**
   - Last: clig.dev, "put the most important information at the end of the output" (terminal output where the eye lands last).
   - First: Atlassian, put the most likely cause or simplest fix in the first sentence (graphical interface); Adobe leads with what happened.
   - Rust names the primary span label as standalone-readable. Resolution is probably by medium (CLI vs GUI), which the rule must state explicitly rather than choose one.

6. **When to validate input.**
   - Only on submit: GOV.UK, "Do not validate when the user moves away from a field"; as-you-type only if research shows benefit.
   - Prevent early with inline cues and disabled states: Adobe Spectrum (disable next-step controls). GOV.UK says avoid disabled buttons. NN/g says do not show errors too early but anticipate mistakes and warn beforehand.

7. **Disabled buttons.**
   - Avoid: GOV.UK, poor contrast and confusion.
   - Use to block the next step until requirements are met: Adobe Spectrum.

8. **Ellipsis in labels.**
   - Use for commands that need more input: NN/g https://www.nngroup.com/articles/ui-copy/.
   - Omit trailing ellipses when quoting labels in docs: Google https://developers.google.com/style/ui-elements. These address different contexts (UI vs documentation), so they do not truly conflict, but an agent writing both needs both.

9. **"Click" as a verb.**
   - Avoid, use "select": GOV.UK a-to-z style guide.
   - Allowed: Google lists click among accepted verbs; Primer's own example says "Click **Save**".

10. **Units: spacing and byte prefixes.** GOV.UK writes "3,500kg" and "MB" with no space; the SI convention differs. The fetched sources do not resolve this, and a project rule must declare one convention and apply it everywhere.

11. **Readability formulas as a check.** NN/g gives grade levels and sentence lengths with no cited data (https://www.nngroup.com/articles/plain-language-experts/). Whether such scores are valid for 2-4 word UI strings was not established by any source read; candidate 30 should be treated as an unvalidated proxy.

12. **Is a confirmation dialog the right pattern at all?** NN/g says reserve confirmations and provide undo; frequent prompts train users to click through. The sources read give no threshold for what counts as "serious", so the line is a judgement the rule must make explicit (data loss, money, irreversibility).
