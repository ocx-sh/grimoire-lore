# Pitch surfaces and first-screen copy

The question: which pages are pitch surfaces that marketing copy rules govern, and what must their first screen say beyond what docs-quality already enforces (DOC-TYPE-10..15 for landing pages, DOC-TYPE-32..36 for READMEs)?

## Verdict

1. **Scope is a declaration, never the `doc_type: landing` tag.** Of the 12 fleet pages tagged `landing`, 1 is a pitch, 5 are docs homes and 6 are section hubs ([page-surface-scope.md §3](marketing-first-screen-copy/page-surface-scope.md#3-classification-of-the-12-landing-tagged-fleet-pages)). The second real pitch (grimoire.rs) carries no tag at all. The scoping key is a second declaration key, `doc_surface`, with the values `pitch` and `home`, plus `offer` for a service offer page (Verdict 11). docs-quality owns the key and its enum (owner decision 2026-11-27, CR-1 to CR-4). It is not a new `doc_type` value: a README is `doc_type: readme` and is also a pitch surface, so type and surface are two separate axes. The key is read by `doc_declaration.py` in docs-quality (`DOC-TYPE-01`, page-types depth file), for a source comment and, through `--built DIST`, for the built meta.
2. **There are two product pitch surfaces, plus the service offer page.** (a) A page declared `doc_surface: pitch`, which is the product site root that renders a hero. (b) The first screen of the repository-root README of every repository that publishes a release or a package. The README counts **whether or not a site exists**. This resolves the conflict between the dives: page-surface-scope (PS-09) made the README a pitch only when the product has no site, and page-hero-status (FSC-14) made every product README a pitch. FSC-14 wins. A stranger reaches the repository page from search, from a registry and from links, without passing the site, and GitHub shows the README under the repository name with no other page in front of it ([exemplar-readmes.md](product-audit/exemplar-readmes.md)). uv shows the strongest form: its pitch URL redirects 301 to the repository ([page-surface-scope.md §5](marketing-first-screen-copy/page-surface-scope.md#5-six-exemplars-pitch-versus-docs-home)). (c) A page declared `doc_surface: offer`, which sells a service engagement. It has its own first-screen rules (MKT-PAGE-12, -13; Verdict 11), because it has no version, no README and no product category.
3. **Detection combines both dives.** The rules read the explicit declaration (PS). The implicit test from FSC-14 (the built `/` route renders a hero `<h1>`) becomes the audit that finds an undeclared pitch. It is never the scope itself, because DOC-TYPE-02 forbids reading a page's role from its path.
4. **First-screen checks read the built HTML, not the source.** The ocx pitch keeps its words in `Landing.astro`, and `landing_check.py` returns 0 findings on it while it returns 6 false findings on 5 hubs and docs homes. A source-only check cannot see the one page it was written for. The same holds for the declaration itself: the checks never visit an `.astro` file, and a `//` comment in its frontmatter fence never reaches the build, so a component-rendered pitch declares itself with a built `<meta name="doc-surface">` (Verdict 12, MKT-PAGE-02).
5. **The hero must contain the product's recorded category noun, in the H1 or in the paragraph that follows it (MUST).** This resolves the second severity conflict: PS-04 set it at SHOULD and FSC-1 at MUST. MUST wins on a pitch surface for three reasons. First, 22 of 25 exemplar heroes name a category in the H1 or the subhead. That count is **LLM-rated**: two blind model raters from two vendors (Claude Haiku and Codex) agreed on 23 of 25 H1 labels (kappa 0.88), and no human rated the set ([page-hero-status.md §3](marketing-first-screen-copy/page-hero-status.md#3-what-the-exemplar-corpus-shows-re-measured)). Second, NN/g says the homepage should be "an elevator pitch to prospective customers, quickly and clearly conveying what your organization does". Unless the name already makes the purpose obvious, NN/g also says to carry "a concise tagline" that communicates "who you are and what you do" ([NN/g, 2024-03-15](https://www.nngroup.com/articles/homepage-design-principles/), re-fetched 2026-11-27). NN/g names no H1, no subhead and no category noun. Placing the recorded noun in the H1 or the subhead is this topic's own way of making that guidance checkable. Third, the check is mechanical, because it compares the hero against the noun the positioning record holds. On a `home` page the requirement stays at SHOULD, because only 4 of 6 exemplar docs homes repeat the noun, and that surface belongs to marketing-positioning-record.
6. **The positioning record owns cross-surface agreement.** The canonical sentence, its verbatim reuse in the README tagline, the manifest and the meta description, and the presence of the noun in `<title>` and About all belong to the sibling topic marketing-positioning-record ([positioning-canonical-sentence.md](marketing-positioning-record/positioning-canonical-sentence.md), MKT-POS-07..09). That record lives at `.agents/positioning.toml` (MKT-POS-01). This topic therefore drops PS-05, PS-06 and FSC-6. FSC-6's "at least 3 of 4 surfaces" test is rejected outright: it lets the hero be the surface that drops the noun, and that is exactly the failure at ocx.sh. MKT-PAGE-03 closes that gap for the hero alone. MKT-POS-08 lets `<title>` carry the noun when the H1 is a slogan. MKT-PAGE-03 is stricter on the hero and accepts only the H1 or the subhead. A hero that passes MKT-PAGE-03 also passes MKT-POS-08.
7. **A maturity line on the first screen below 1.0.0 is a SHOULD, not a MUST.** Upstream practice is silence: 0 of 25 landing pages and 1 of 39 READMEs with a release tag state a status ([page-hero-status.md §5](marketing-first-screen-copy/page-hero-status.md#5-maturity-status)). No primary source requires a status line. SemVer §4 says that under 0.y.z "anything MAY change at any time" ([semver.org](https://semver.org/)). That describes the API, and it does not say that a page must announce it. repostatus.org only "very strongly" suggests a badge in the README and sets no position for it ([repostatus.org](https://www.repostatus.org/), re-fetched 2026-11-27). The line is still recommended, because the readers of this copy include coding agents that run README commands with no human present. That reason is argued, not measured, and no conversion data exists for it or against it. A SHOULD warns, and the warning needs a recorded reason to pass.
8. **Dropped, with reasons.** The H1 word band (FSC-2): the corpus maximum of 12 words matches what agents already write, and no source ties a band to an outcome. The audience rule (FSC-13): DOC-TYPE-36 already holds it at CONSIDER, and only 10 of 25 exemplar heroes meet it. The hub-persuasion grep (PS-08): DOC-PLAIN-12 already covers superlatives on docs pages. The banned vague-verb list from the scout: Fletch does not contain one, so it has no source. The checker repairs (PS-07, PS-10, PS-11) are not marketing rules at all; they are change requests CR-1..CR-4 against docs-quality, listed below.
9. **Two rule families never share the first sentence.** docs-quality keeps length, CTAs, placeholders and adoption links. MKT-POS keeps sentence identity. MKT-PAGE keeps what the hero and the README opening must contain: the noun, the differentiator, the maturity status, and the grade-word contradiction.
10. **Documented gap: no differentiator check is mechanical.** The competitor-swap test of MKT-PAGE-04 is the only differentiator test this topic has. It needs a human or a model to judge whether the alternative could print the sentence. So MKT-PAGE-04 is CONSIDER.
11. **A service offer page states the service, the buyer, a price or engagement signal and the next step (SHOULD, MKT-PAGE-12).** Measured on 21 software-service pages fetched 2026-11-27 (11 independent consultancies, 10 vendor professional-services pages; server HTML, one rater plus scripts), the market norm is a service noun and a contact button: 14 to 16 of 21 heroes name the service type, 1 names the buyer, 2 give an engagement signal ("View Packages", "in weeks"), 0 print a price anywhere in the server-rendered page, and 0 say what happens after the click ([followup-q0.md](marketing-first-screen-copy/followup-q0.md) "Answer" and "Scoring"). The rule is therefore normative, not descriptive. It rests on NN/g, which reports business customers rank price as their top information need and leave for competitors when it is absent ([NN/g, 2013-12-01](https://www.nngroup.com/articles/show-price/)), on a vendor survey in which 25% of 451 buyers of software or services rank transparent cost the most important website element ([Clutch, vendor, 2020-02-26](https://clutch.co/press-releases/b2b-buyers-most-concerned-about-transparent-costs-b2b-companies-websites)), and on analyst opinion that complex offerings may keep prices private ([Forrester blog, 2019-12-04](http://www.forrester.com/blogs/prices-public-on-website/)), which is why the price element accepts an engagement model with a time box and "price on request". The only 2020s conversion-shaped data is SaaS, not services, and points both ways: form fills 2.8% with transparent pricing against 4.6% without, pipeline conversion 17.50% against 10.31% ([HockeyStack, vendor data, 2025-12-15](https://hockeystack.com/lab-blog-posts/state-of-pricing-demo-case-study-pages)). All four sources were fetched 2026-11-27 by the follow-up. Unquantified deliverer boasts appear on 5 of 21 heroes, numbers or named partner tiers on 4, so MKT-PAGE-13 is CONSIDER. **Documented gaps:** no conversion or A/B data for any element on service pages (two searches, no 2020s primary study found; paywalled Gartner and Forrester reports and Google Scholar not searched); no productized fixed-price service page in the corpus, which is the population most likely to pass the price element and could move MKT-PAGE-12 to MUST; prices behind JavaScript or on a separate `/pricing` page are invisible to the server-HTML count; no second rater; and three corpus heroes changed between two fetches hours apart, so a service first screen is not stable even within a day.
12. **A pitch declares itself in the built HTML; the `.astro` fence comment is dead (MKT-PAGE-02 changed).** No check reads a `// doc_surface: pitch` line in an `.astro` frontmatter fence, and neither source reader visits an `.astro` file: `doc_declaration.py` walks only `.md .mdx .rst .adoc .asciidoc`, and `strip_prose.py` lists `.md .mdx .markdown`. The built-meta reader in `doc_declaration.py --built` is the fix. Astro drops JavaScript comments from the build ("HTML-style comments will be included in browser DOM, while JS ones will be skipped", [Astro docs, Template syntax](https://docs.astro.build/en/basics/astro-syntax/), page undated, source last committed 2024-12-03, fetched 2026-11-27). A `<meta name="doc-surface" content="pitch">` added through Starlight's per-page `head` field ([Starlight frontmatter reference](https://starlight.astro.build/reference/frontmatter/), "Last updated: May 7, 2026", fetched 2026-11-27) rendered in a real Astro 7.4.13 / Starlight 0.43.1 build of a copy of the grimoire.rs docs, and both the meta and a template HTML comment survive Astro 5.16.0 (both `compressHTML` settings) and 7.4.13 ([followup-q1.md](marketing-first-screen-copy/followup-q1.md) §1-§4). For Markdown and MDX sources the source comment stays valid and is read by `doc_declaration.py`. The follow-up also found a second drift between the two readers: on the ocx website pitch (`ocx-sh/website/site/src/content/docs/index.mdx`, declaration at line 14 after an 11-line front matter) `doc_declaration` read `landing` and `strip_prose` read nothing, because `strip_prose` scanned the raw first 12 lines. `strip_prose.declaration` now skips a leading front matter block the way `doc_declaration` does (CR-3 item d). **Documented gaps:** a build of the ocx website pitch with the meta was not run (same mechanism measured on grimoire.rs); whether a deploy-time minifier strips HTML comments was not measured (the meta does not depend on it).
13. **On github.com the README is below the fold; the 15-line window stays a source-line proxy (documented gap, follow-up answered partly).** One unauthenticated headless Chromium run per case on 2026-11-27 found 0 README lines above the fold on 4 of 4 repositories (uv, ripgrep, serde, esbuild) at 1440x900 and at 390x844: the README starts 993 to 2182 px down on desktop and 1266 to 1348 px on mobile, below the repository name, About text, topics and file list. At 1920x1080, serde showed 2 README lines and ripgrep 0. On crates.io the manifest `description` sits in the header card and the README opening is above the fold (about 16 lines at 1440x900 on ripgrep, 13 at 390x844; one crate measured). npmjs.com answered with HTTP 403 and a Cloudflare challenge, so its fold is unmeasured; `npm view <pkg> readme` returns the packaged Markdown only ([followup-q2.md](marketing-first-screen-copy/followup-q2.md) "Measurements"). No platform documents a fold or a line count: GitHub's README page states only a 500 KiB truncation limit and the display order `.github`, root, `docs` ([GitHub Docs, About READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes), no page date, source last committed 2026-09-03, fetched 2026-11-27); npm and crates.io update the rendered README only on publish ([npm Docs](https://docs.npmjs.com/about-package-readme-files), last edited 2025-11-04; [Cargo manifest reference](https://doc.rust-lang.org/cargo/reference/manifest.html), no page date; both fetched 2026-11-27). Consequences, none of which changes a rule in this revision: on GitHub the above-the-fold pitch text is the About description, which MKT-POS-08 already governs; MKT-PAGE-01's "repository-root README" names the file GitHub shows only when no `.github/README.md` exists (0 fleet repositories have one: `find /home/mherwig/dev/ocx-sh /home/mherwig/dev/grimoire-rs -maxdepth 3 -path '*/.github/README.md' | wc -l` printed `0` on 2026-11-27); and the follow-up's candidate rule that a published registry README must carry the same noun and maturity line was not adopted, because it rests on one crate and no npm page. The numbers are indicative (no fonts installed, one run, unauthenticated layout); the sign of the GitHub result is robust because the file list alone is taller than the viewport.
14. **MKT-PAGE-06's label arm rarely fires on a wrapped line, and a one-condition guard removes the case it does.** Over 165 popular-project READMEs fetched 2026-11-27, the arm fired 0 times in the 15-line windows (0 of 1,670 lines; rule-of-three 95% upper bound about 1.8% of READMEs). Over whole files, outside code fences, it fired twice in 20,910 lines: one wrapped line (`casey/just` line 1,929, "...which is currently" then "unstable.") and one real stage-definition list item (`nodejs/node` line 46). The guard keeps a label hit only when the physical line before it is blank, a heading or the file start; it keeps all 6 fleet status lines and drops the `just` line ([followup-q4.md](marketing-first-screen-copy/followup-q4.md) "Proposed guard and its check"). The follow-up also found that gawk's `IGNORECASE` silently becomes case-sensitive under `mawk` and misses `STATUS: ALPHA.`, so the published guard uses `tolower()`. **Documented gap:** the corpus has almost no status lines, so the false-fire rate in READMEs that do carry a status line near the top is untested; the corpus is a hand-picked convenience sample, English only. The `readme_window` helper itself still uses `IGNORECASE` and stays labelled GNU awk.

### Definition used by every rule: "first screen"

| Surface | First screen, as a check reads it |
|---|---|
| `doc_surface: pitch` page | The hero segment of the **built** HTML. It starts at the first `<section>` whose class contains `hero`, or at `<main>` when no such section exists. It runs from the first `<h1>` after that point to the next `<h2>`. "Subhead" means the first `<p>` of 4 or more words after that `<h1>`. The hero section comes first because a Starlight page puts a site-title `<h1>` inside `<main>`: the built grimoire.rs page (`grimoire-rs/grimoire/docs/dist/index.html`, built 2026-11-24) has 2 `<h1>` elements, and the first one is "Grimoire". |
| Repository-root README | The first 15 non-blank source lines after removing HTML wrapper lines (`<div>`, `</div>`, `<p align>`, `<img>`, `<picture>`, `<source>`, `<br>`) and badge lines (`[![`). The window stops at the first `## ` heading. This is a proxy taken from both dives, not a rendered measurement ([exemplar-readmes.md](product-audit/exemplar-readmes.md) "Definitions"). On github.com no README line is above the fold at 1440x900 or 390x844; on crates.io the README opening is (Verdict 13). |
| `doc_surface: offer` page | The same hero segment of the built HTML as a pitch page. A page from which `hero_text` extracts no `<h1>` (the Python exits non-zero) has a failed first screen, never a pass ([followup-q0.md](marketing-first-screen-copy/followup-q0.md), page p5). |

The two extraction commands that every verification below uses. Both were run on 2026-11-27. `readme_window` printed the same 148 lines over the 17 fleet READMEs as the Python scan the dives used (`diff` was empty).

```sh
# README first-screen window, as path:line:text (GNU awk)
readme_window() { awk 'BEGIN{IGNORECASE=1} /^## /{exit} /^[[:space:]]*$/{next} /^[[:space:]]*(<\/?div|<p[[:space:]]+align|<\/p>|<img|<picture|<\/picture>|<source|<br|\[!\[)/{next} {print FILENAME":"FNR":"$0; if(++k==15) exit}' "$1"; }

# Built hero: line 1 = H1 text, line 2 = subhead, line 3 = whole hero segment as text
hero_text() { python3 -I -c "import re,sys,html;t=open(sys.argv[1],encoding='utf-8').read();m=re.search(r'<section\b[^>]*class=\"[^\"]*hero',t) or re.search(r'<main\b',t);t=t[m.start():] if m else t;s=re.search(r'<h1\b.*?(?=<h2\b|\Z)',t,re.S).group(0);x=lambda h:' '.join(html.unescape(re.sub(r'<[^>]+>',' ',h)).split());print(x(re.search(r'<h1\b.*?</h1>',s,re.S).group(0)));print(next((x(q) for q in re.findall(r'<p\b.*?</p>',s,re.S) if len(x(q).split())>=4),''));print(x(re.sub(r'<(script|style)\b.*?</\1>','',s,flags=re.S)))" "$1"; }
```

### MKT-PAGE-06 and -07: pattern and vocabulary

The product-attached check for MKT-PAGE-06. `$NAME` is the repository name. It has two arms. The label arm (a line that opens with `status` or a stage word, then `:` or `.`) runs on the whole README, so that it sees the physical line before each hit, and keeps a hit only when that line is blank, a heading or the file start. Its output has the same `path:line:text` shape as `readme_window`, so `grep -F -x -f` keeps only the hits inside the window. It uses `tolower()` because gawk's `IGNORECASE` is silently ignored by `mawk` ([followup-q4.md](marketing-first-screen-copy/followup-q4.md) "Portability"). The sentence arm is unchanged from the first version. The hero is one line of text, so on line 3 of `hero_text` only the sentence arm applies; the first version's label arm required a `path:line:` prefix, which hero text does not carry, so in practice only its sentence arm ran there too. Run under bash or zsh (process substitution).

```sh
STAGE='alpha|beta|pre-?1\.0|pre-?release|preview|experimental|unstable|skeleton|concept|work in progress|early (access|development)|under (active )?development|no longer (actively )?maintained|unmaintained|archived|deprecated|stabiliz\w*'
# Label arm, wrap-safe, portable awk. Same STAGE list, with \w written [[:alnum:]_] for POSIX awk.
label_arm() { awk 'BEGIN{S="alpha|beta|pre-?1\\.0|pre-?release|preview|experimental|unstable|skeleton|concept|work in progress|early (access|development)|under (active )?development|no longer (actively )?maintained|unmaintained|archived|deprecated|stabiliz[[:alnum:]_]*"} (tolower($0) ~ "^[>[:space:]*_]*(status|" S ")[*_]*[[:space:]]*[:.]") && (FNR==1 || prev ~ /^[[:space:]>]*$/ || prev ~ /^#/) {print FILENAME":"FNR":"$0} {prev=$0}' "$1"; }
# Sentence arm
SENT="\b(this (project|tool|crate|package|extension|app|library|repository)|it|$NAME) (is|are) (still |currently |now )?(in )?(an? )?($STAGE)"
# README: must print at least 1
{ label_arm README.md | grep -F -x -f <(readme_window README.md); readme_window README.md | grep -i -P "$SENT"; } | grep -c .
# Hero: must print at least 1
hero_text dist/index.html | sed -n 3p | grep -i -c -P "$SENT"
```

Measured 2026-11-27 (bash, GNU awk 5.2.1), in `~/.cache/research-lang/exemplars/product/wave2/mfsc-revise/`: over the 17 fleet READMEs the windowed label arm printed exactly the 5 status lines the first version passed (`grim-gui:9`, `grim-mirror:10`, `grimoire:27`, `indexbot:18`, `website:7`), and the README command printed `0` for `ocx-sh/ocx`, `ocx-sh/catalog` and `grimoire-rs/vscode`, and `1` for `ocx-sh/website` and `grimoire-rs/grimoire`, the same split as before. On the follow-up's synthetic file (`Some prose that is` / `unstable. More text.` / blank / `Status: alpha.`) it kept only line 4.

### Precedence with docs-quality

docs-quality owns `doc_surface` and gates every `doc_type: landing` page with DOC-TYPE-10..15. No MKT-PAGE rule suspends a DOC-TYPE finding. ## AI-agent failure modes

Ranked by how often each bites, grouped by mechanism.

**Scope taken from a label (most frequent).**
1. Treats `doc_type: landing`, or the words "home page", as "write marketing copy here". On today's tags, 11 of every 12 such edits would land on a page that is not a pitch. Caught by MKT-PAGE-01 and MKT-PAGE-11.
2. Hands over a component-rendered pitch with no declaration (grimoire.rs `index.astro`), so no check reads it. Caught by MKT-PAGE-02's built-HTML audit.

**Copying the upstream norm.**
3. Leaves maturity out, because 0 of 25 exemplar heroes state it. Or it moves the status to a footer or a `## Status` section, as 7 of 10 in-scope fleet pre-1.0 READMEs do. Warned by MKT-PAGE-06.
4. Deletes the owner's maturity line to "clean up" the hero. MKT-PAGE-06 warns on the diff, and the ask-first list below forbids it.
5. Reads a feature-level "experimental" as a product status. MKT-PAGE-06's product-attached pattern does not count it.

**Writing each surface fresh.**
6. Writes a new tagline per surface, and the hero is the surface that drops the noun. ocx has 11 distinct one-liners ([messaging-inventory.md smell 1](product-audit/messaging-inventory.md)). Caught by MKT-PAGE-03 here and by MKT-POS for the other surfaces.
7. Writes a slogan-only H1 ("Meet X", "The future of Y") with a subhead that names no category. Caught by MKT-PAGE-03. The name-removal test in MKT-PAGE-04 is advice.
8. Writes a synonym of the recorded noun into the hero. Caught by MKT-PAGE-03's literal match.

**Default promotional vocabulary.**
9. Writes "stable" or "production-ready" for a 0.x tool because the code works. Caught by MKT-PAGE-09.
10. Prepends "AI-powered" or "agentic" to the H1. Warned by MKT-PAGE-05.
11. Writes an outcome that is too broad or too lofty, or stacks three audiences in the subhead. MKT-PAGE-04 advises against it.

**Checking the wrong artefact.**
12. Checks the `.mdx` or `.astro` source and misses words a component renders. Caught by the built-HTML clause in MKT-PAGE-03 and MKT-PAGE-06, and by CR-4.
13. Reads the site-title `<h1>` as the hero H1 on a Starlight page. Caught by the hero-section-first rule in the "first screen" definition.
14. Edits one of the two declaration regexes, so one check sees `doc_surface` and the other does not. Caught by CR-3.
15. Writes the status as an image badge only. Warned by MKT-PAGE-06, which requires text.
16. Puts the declaration as a `//` comment in an `.astro` frontmatter fence, where no check reads it and the build drops it. Caught by MKT-PAGE-02's built-meta check.
17. Changes the built meta and leaves the source comment, or the reverse. Warned by MKT-PAGE-14.
18. Counts a wrapped source line that happens to start with "unstable." as a status label. Prevented by the wrap guard in MKT-PAGE-06's label arm.

**Copying the service-market norm (offer pages).**
19. Writes a service hero with a slogan and a "Let's talk" button, and no buyer, price signal or next step, because 0 of 21 measured service heroes say what happens after the click. Warned by MKT-PAGE-12.
20. Invents a price figure to satisfy element 3. Forbidden by MKT-PAGE-12, which makes the figure an ask-first item and accepts "price on request" with an engagement model.
21. Writes "world-class", "deepest bench" or "decades of experience" about the team. MKT-PAGE-13 advises against it unless a claims row backs a number.

## What an agent must ask a human

- **The category noun and the object noun of each product.** ocx has three live candidates: "package manager", "binary distribution platform" and the job "same tools on every machine". Grimoire has "package manager" or "lockfile". Without a record, MKT-PAGE-03 stops the agent (exit 2).
- **The differentiator to claim**, when the record names none. The agent may propose 2 or 3 drawn from the README and the code. It does not choose.
- **The stage**, when the version field and the maintainer's statement disagree. Also any decision to declare 1.0 or "stable".
- **Removing or softening a maturity line** the owner wrote.
- **AI in the headline**, when AI is not part of the recorded noun.
- **Whether a product gets a pitch page**, or whether a docs home is promoted to one (MKT-PAGE-11). Also which page is the pitch when two candidates exist.
- **Adding `doc_surface` declarations in bulk.** That changes the gate for every open pull request, so it follows docs-quality's rollout rule: changed files first.
- **Which page is an offer page**, and whether the `offer` value is adopted at all.
- **Any price figure, price range or package price on an offer page** (MKT-PAGE-12), and the engagement model and time box the agent may state instead. Also the buyer noun, when the owner has not named it.
- **Any proof number about the team or the clients** on an offer page (MKT-PAGE-13). The agent may propose one from a source it can cite; the owner approves the claims row.
