## Summary

- A docs site's search box must be a visible type-in field on every page, not a link — changing this on one real site raised search usage 91% ([NN/g, 2001](https://www.nngroup.com/articles/search-visible-and-simple/)).
- First-query search success on real sites has measured as low as 51%, dropping to 32% on a retry — most abandon after two failed tries, so query-understanding (typo tolerance, synonym mapping) matters more than result ranking polish ([NN/g, 2001](https://www.nngroup.com/articles/search-visible-and-simple/)).
- Progressive disclosure stops working past two levels: "designs that go beyond 2 disclosure levels typically have low usability" ([NN/g, 2006](https://www.nngroup.com/articles/progressive-disclosure/)) — this directly conflicts with how deep real docs sidebars nest (see Contested section).
- Docusaurus's own docs say most projects should not version their docs at all — versioning "will just increase your build time, and introduce complexity" — and to keep active versions under 10 ([Docusaurus 3.10, versioning](https://docusaurus.io/docs/versioning)).
- GOV.UK's content design gives numeric thresholds most style guides only gesture at: split sentences over 25 words, cap paragraphs at 5 sentences, target a reading age accessible to the least literate reader in the audience ([GOV.UK, clear language](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)).
- GOV.UK content is organized "by task, rather than audience," and every published page must trace to a written user-need statement in the form "As a … I need to … so that …" ([GOV.UK, identify user needs](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs)).
- Top-task links on a homepage should be used "very sparingly" because on mobile — a third of GOV.UK's traffic — top tasks are the only part of the homepage visible before scrolling ([GOV.UK, planning content](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/plan-new-govuk-content/)).
- Nielsen's classic scanning study found 79% of test users scan a new page rather than read it word-by-word, and scannable + plain-language rewrites measured 124% better task performance than promotional copy ([NN/g, 1997](https://www.nngroup.com/articles/how-users-read-on-the-web/)).
- The F-pattern is real but NN/g's own later guidance warns it is "misunderstood": it is not universal, five other scan patterns exist, and "good design can prevent F-shape scanning" — treat it as a diagnostic, not a target ([NN/g, updated 2026](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)).
- Breadcrumbs are recommended for any hierarchy deeper than 1-2 levels and should sit just below global nav, supplementing rather than replacing it — not recommended for flat or linear structures ([NN/g, 2018/2026](https://www.nngroup.com/articles/breadcrumbs/)).
- Nielsen's 10th usability heuristic treats documentation as a last resort: it should be searchable, task-focused, list concrete steps, be delivered in context at the moment of need, and stay concise — an interface that needs no docs is the actual target ([NN/g heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)).
- Information scent — the cues a link or search result gives about what's behind it — degrades when navigation labels use internal jargon instead of the words the reader already searched with ([NN/g, 2020](https://www.nngroup.com/articles/information-scent/)).
- The react.dev rewrite's real lesson is invisible in most retellings: the old docs' failure wasn't tone or layout, it was teaching an abandoned paradigm (class components) to readers who only needed the current one (Hooks) — "learn React twice" ([react.dev blog, 2023](https://react.dev/blog/2023/03/16/introducing-react-dev)). A widely repeated "3x more likely to recommend" statistic could not be verified in the primary blog post itself — treat it as unconfirmed until sourced to React's own data.
- Docusaurus recommends site search response stay in sync with content: Algolia's default crawler only re-indexes weekly, so a docs site with fast-changing content needs a manual-crawl trigger after major changes or search silently serves stale results ([Docusaurus 3.10, search](https://docusaurus.io/docs/search)).
- Google's Technical Writing One teaches that a document should open by declaring scope (including what it does *not* cover) and naming the audience's starting knowledge before any content — e.g. "This document assumes that you understand matrix multiplication..." ([Google TW1, Documents](https://developers.google.com/tech-writing/one/documents)).
- Atlassian's empty-state template is a fixed 3-part shape — title, one-to-two-sentence body naming the reason and the next step, and a 1-2 word imperative CTA — which is a directly reusable template for a docs site's "no results" and "empty section" states ([Atlassian Design System](https://atlassian.design/foundations/content/designing-messages/empty-state)).
- IBM Carbon and Mailchimp both split voice (constant) from tone (context-dependent): error messages get economical, direct wording; onboarding and conceptual prose get fuller, friendlier sentences — the same document should not read identically in both places ([Carbon v10](https://v10.carbondesignsystem.com/guidelines/content/overview/), [Mailchimp](https://styleguide.mailchimp.com/voice-and-tone/)).
- Baymard's ecommerce search-query taxonomy transfers directly to docs search: "non-product" (policy/info-style) queries fail 66% of the time on ecommerce sites, the worst of any query type — the docs analogue is "how do I..." conceptual queries that a keyword index alone won't answer ([Baymard, 2026](https://baymard.com/blog/ecommerce-search-query-types)).
- The big-company corpus is heavier on **UI microcopy** (buttons, error toasts, empty states) than on **docs-site UX** (nav depth, search, landing-page anatomy) — the frame's hypothesis that these design systems "hold most of what matters about docs design" is only partly true; the docs-specific UX guidance came disproportionately from Nielsen Norman Group and GOV.UK, not from Google/Apple/Meta/Atlassian/Salesforce/Adobe design systems, which are mostly product-UI voice guides repurposed for docs by inference.
- None of the fetched corpus — Google, Microsoft, Apple, Meta, Atlassian, Shopify, GOV.UK, Mailchimp, IBM, Adobe, Salesforce, NN/g, Baymard — mentions tested documentation examples, asciicast/asciinema recordings, or acceptance-tested doc scripts anywhere. The ocx `adr_tested_doc_command_mechanism.md` practice has no external validation in this corpus; it should be checked against a docs-testing-tooling-specific scout, not assumed proven here.

## Findings

### 1. Scanning, not reading: the layout consequence

Nielsen's original 1997 study found "79 percent of our test users always scanned any new page they came across; only 16 percent read word-by-word." The prescriptive fallout — highlighted keywords, meaningful (not clever) subheadings, bulleted lists, one idea per paragraph, inverted-pyramid ordering, and roughly half the word count of conventional prose — measured 124% better usability than promotional writing in the same study ([How Users Read on the Web](https://www.nngroup.com/articles/how-users-read-on-the-web/), no revision date noted since 1997, still linked as current NN/g guidance).

The F-pattern eye-tracking work builds on this (first published 2006, most recently reviewed August 2026) but comes with an explicit caveat that most citations drop: the pattern is "misunderstood," it is not universal, five other scan shapes exist (layer-cake, spotted, marking, bypassing, commitment), and "good design can prevent F-shape scanning" — meaning a well-front-loaded page can get users to read past the first two lines, and the F-pattern's persistence is itself evidence of bad layout, not a target to design toward ([F-Shaped Pattern For Reading Web Content](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)).

Nielsen's separate response-time thresholds (0.1s = feels instant, 1s = keeps flow, 10s = attention limit before abandonment) date to 1993 human-factors research and are restated as unchanged as of the article's most recent pass — directly relevant to docs-site search latency and page-load budgets, not just app UI ([Website Response Times](https://www.nngroup.com/articles/website-response-times/)).

### 2. Progressive disclosure has a stated depth limit

"Initially, show users only a few of the most important options. Offer a larger set of specialized options upon request" — but NN/g states a hard-feeling ceiling: "designs that go beyond 2 disclosure levels typically have low usability," based on testing across 46 web applications ([Progressive Disclosure, 2006](https://www.nngroup.com/articles/progressive-disclosure/)). The two failure modes named are (a) putting rarely-needed options up front or hiding frequently-needed ones, and (b) making the escalation path itself unclear — users don't know an "advanced" layer exists or what's in it.

### 3. Search UX for a docs site

NN/g's oldest and most concrete numbers here (2001, still actively linked as current guidance): put a visible type-in box, not a link, at the top of every page; size it to fit a typical query; changing useit.com from a link to a box raised search usage 91%. First-query success measured only 51%, falling to 32% on a second attempt, with most failed first searches abandoned outright rather than refined. Average queries are ~2 words with no Boolean syntax — advanced search belongs on the results page, never the homepage, and any scoped/faceted search must default to "search everything" and show the active scope explicitly, since users routinely miss scope toggles ([Search: Visible and Simple](https://www.nngroup.com/articles/search-visible-and-simple/)).

Baymard's 2026 ecommerce query-type taxonomy (exact / product-type / feature / use-case / abbreviation / compatibility / symptom / non-product) transfers to docs search with the same shape of problem: "non-product" (policy/info) queries fail worst — 66% — because they don't match a keyword-indexed catalog. The docs equivalent is a conceptual "how do I configure X for Y" query that a plain full-text index won't resolve without synonym or intent mapping ([Ecommerce Search UX Best Practices 2026](https://baymard.com/blog/ecommerce-search-query-types)).

Mechanically, Docusaurus's own search docs note that the default (free) Algolia DocSearch crawler indexes weekly — a docs site that changes daily needs a manual re-crawl trigger after major edits, or search quietly serves stale content ([Docusaurus Search](https://docusaurus.io/docs/search)). Docusaurus's "contextual search" (scoping results to the current version/locale) is on by default specifically to stop duplicate cross-version results, which is the versioned-docs analogue of Baymard's zero-result problem.

### 4. Navigation depth and sidebar design

Docusaurus (v3.10.2) auto-generates one sidebar category per folder and one link per file, and offers `autoCollapseCategories` (collapse siblings when one section opens) and a `hideable` sidebar for tablet widths — but states no maximum nesting depth; its own worked example nests four levels deep ([Docusaurus Sidebar](https://docusaurus.io/docs/sidebar)). This sits in tension with NN/g's 2-level progressive-disclosure ceiling (§2) — see Contested section.

Breadcrumbs are recommended specifically for hierarchies deeper than 1-2 levels, especially when visitors land via search and skip the homepage — use ">" as separator, place just below global nav, never as a replacement for the main nav, and on mobile either drop to immediate-parent-only or omit rather than wrap ([Breadcrumbs, 2018, reviewed 2026](https://www.nngroup.com/articles/breadcrumbs/)).

Information scent — whether a nav label or search snippet lets a reader predict what's behind it before clicking — degrades specifically when labels use internal/product jargon instead of the reader's own words; NN/g frames this via information-foraging theory and warns that unmet scent expectations cost trust faster than they cost a single click ([Information Scent, 2020](https://www.nngroup.com/articles/information-scent/)).

### 5. Versioning is opt-in, not default

Docusaurus explicitly discourages defaulting to versioned docs: "Most of the time, you don't need versioning as it will just increase your build time, and introduce complexity," reserving it for "websites with high-traffic and rapid changes to documentation between versions." When versioning is warranted, keep active versions under 10, never cut a version for a patch release, and archive old versions as static external links rather than rebuilding them forever ([Docusaurus Versioning](https://docusaurus.io/docs/versioning)). This is a directly checkable rule for any repo (`ocx-catalog`, `grimoire-indexer`) considering versioned docs.

### 6. Landing pages are organized by task, not by audience

GOV.UK's content model starts from a written user-need statement — "As a [who], I need to [what], so that [why]" — tested against real evidence (analytics, support-call data, research) before content is written at all; vague needs ("understand X") are explicitly rejected unless they enable a concrete action ([Identify user needs](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs)). Content is then "organised and written by task, rather than audience," and guidance "should guide users from when their need arises to when they complete a task" ([Planning content](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/plan-new-govuk-content/)).

Top-task links on a homepage should be used "very sparingly" and only with evidence of relevance, because on mobile — a third of GOV.UK's audience — the top-task block is the *only* part of the homepage visible before any scrolling. This is a concrete, testable landing-page constraint (above-the-fold task list, mobile-first) most style guides state as opinion; GOV.UK ties it to a traffic-share number.

### 7. Plain English has numbers, not just a vibe

GOV.UK's clear-language page gives concrete, quotable thresholds: "Try to split up sentences that are over 25 words long," "Paragraphs should have no more than 5 sentences each," avoid negative contractions ("can't," "don't") because "many users find negative contractions hard to read, or misread them," prefer active voice, and explain specialist terms on first use rather than every use ([Clear language](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)). Related search results (not independently fetched from a primary GOV.UK page, so held to lower confidence) put GOV.UK's reading-age target at roughly age 9, on the logic that content should serve the least literate plausible reader even for specialist audiences.

Google's Technical Writing One converges on the same idea from a different angle: state the document's scope (what's covered and what deliberately isn't), name the audience's assumed prior knowledge explicitly (their example: "This document assumes that you understand matrix multiplication and the fundamentals of backpropagation"), and answer the reader's core question in the opening because many readers won't get past page one ([TW1, Documents](https://developers.google.com/tech-writing/one/documents)).

### 8. Page templates: more types than "landing / guide / reference"

Microsoft's Learn contributor guide splits contribution work into "minor" (typo, single-article edit, broken link) versus "major" (new article, multi-article revision, several days of work) changes, each with its own tooling path (in-browser edit vs. local Git clone) ([How to write: overview](https://learn.microsoft.com/en-us/contribute/content/how-to-write-overview)) — a workflow distinction, not a page-type taxonomy, but it implies Learn's actual page templates (how-to, tutorial, overview, concept, reference, "module" inside a "learning path") are more granular than a 3-way split. Apple's DocC tooling makes the same granularity claim from the API-docs side: articles, step-by-step tutorials, and generated API reference are three structurally distinct artifact types with different authoring syntax, not three tones of the same page (evidence here is secondary — search-derived, not a full primary-page fetch, since `swift.org/documentation/docc/` and the Apple HIG pages are JS-rendered and did not yield fetchable body text).

### 9. The react.dev redesign: what actually changed

When React Hooks shipped in 2018, the old docs still assumed familiarity with class components, forcing new readers to "learn React twice: once with class components and then once again with Hooks." The 2023 rewrite's core move was to teach Hooks-first from page one, split the site into a self-paced "Learn React" course (four chapters: Describing the UI, Adding Interactivity, Managing State, Escape Hatches) and a separate API Reference with a fixed two-part shape per API (formal signature, then "Usage" with canonical copy-paste scenarios), add 600+ inline interactive sandboxes, and end most Learn pages with a challenge-and-solution pair ([Introducing react.dev](https://react.dev/blog/2023/03/16/introducing-react-dev)). No adoption or satisfaction metric appears in the primary post itself — a "3x more likely to recommend" figure circulates in secondary coverage but could not be confirmed against the primary source; treat it as unverified.

### 10. Empty states and tone-by-context

Atlassian's empty-state template is a fixed three-part shape: an informative, scannable title (sentence case, subtle humor allowed); one-to-two-sentence body copy that states the reason for the empty state and where to go next, without repeating the title; and a 1-2 word imperative CTA. Multiple CTAs are discouraged, and a dismiss/cancel option should be present so users don't feel trapped ([Empty state](https://atlassian.design/foundations/content/designing-messages/empty-state)). This template is directly reusable for a docs site's "no search results" and "empty category" states.

IBM Carbon and Mailchimp both separate a constant brand *voice* from a context-dependent *tone*: Carbon states error messages get "economical and direct" wording while onboarding gets "full sentences and friendly explanations" from the same voice ([Carbon v10 overview](https://v10.carbondesignsystem.com/guidelines/content/overview/)); Mailchimp frames its voice as "plainspoken... value clarity above all" while tone "shifts based on reader emotional state," with humor allowed only when it doesn't compromise clarity ([Mailchimp Voice and Tone](https://styleguide.mailchimp.com/voice-and-tone/)). Neither source gives a docs-specific tone rule (e.g., "reference pages are terse, tutorials are warm") — that mapping, if wanted, has to be authored, not borrowed.

### 11. Google's own technical-writing curriculum

Technical Writing One's thirteen units run: Introduction, Just enough grammar (optional), Words, Active voice, Clear sentences, Short sentences, Lists and tables, Paragraphs, Audience, Documents, Punctuation (optional), Markdown (optional), Summary. Technical Writing Two's seven units are: Introduction, Self-editing, Organizing large docs, Illustrating, Creating sample code, Using LLMs in tech writing, Summary ([course overview](https://developers.google.com/tech-writing/overview), [TW1 unit list](https://developers.google.com/tech-writing/one), [TW2 unit list](https://developers.google.com/tech-writing/two)). Notably, TW2 has a unit named "Using LLMs in tech writing" — direct evidence Google has a stated position on AI-assisted doc authoring — but its content could not be fetched (404 on the direct unit URL); this is a real gap worth a follow-up fetch by a later research pass rather than a claim made from title alone.

## AI-agent angle

- **Nesting sidebars infinitely because the framework allows it.** An LLM told to "add navigation" for a large doc set will happily emit 4-5 levels of folders because Docusaurus doesn't error on it. Mechanical check: script a depth count over the generated sidebar config/folder tree; flag anything past 2-3 levels for a human look, per NN/g's 2-level disclosure ceiling.
- **Treating "organize by audience" (For Developers / For Admins) as neutral IA** when GOV.UK's evidence-based practice is to organize by task instead. Mechanical check: grep top-level nav/section titles for role nouns ("developer," "admin," "beginner," "advanced") as a smell — not a hard fail, but a prompt to check whether a task-based split serves readers better.
- **Writing landing-page hero content assuming desktop-first, unlimited above-the-fold space.** Models don't have a mobile viewport to check against. Mechanical check: nothing purely mechanical here short of a screenshot diff at a 375px width against the same page at 1440px — flag if the count of links/CTAs visible above an estimated 600px fold differs wildly.
- **Reusing an old paradigm's explanation because it's in the training data**, e.g. documenting a library's older API pattern alongside the current one "for completeness" the way pre-2023 React docs did with classes-then-Hooks. Mechanical check: grep the doc set for a deprecated-API or "legacy" marker being explained in the same top-level walkthrough as the current approach, rather than moved to a migration-guide page.
- **No numeric ceiling on sentence/paragraph length**, so a model's "short sentences" self-assessment silently drifts long over many edits. Mechanical check: a word-count-per-sentence and sentence-count-per-paragraph grep/lint against the GOV.UK thresholds (25 words, 5 sentences) is trivial to script and catches drift a human skim won't.
- **Fabricating an empty-state or zero-result message that repeats the page title verbatim** instead of naming a reason and next step. Mechanical check: string-similarity between an empty-state's title and its body; near-duplicate strings are the tell.
- **Writing a scope statement that says what a doc covers but never what it deliberately excludes.** Mechanical check: grep the opening paragraph for an explicit negation pattern ("does not cover," "not addressed here," "out of scope") — its absence on a long or complex doc is the tell.

## Contested / evolving

- **Deep sidebar nesting vs. the 2-level disclosure ceiling.** Docusaurus's tooling and worked examples permit and even demonstrate 4+ levels of sidebar nesting ([Docusaurus Sidebar](https://docusaurus.io/docs/sidebar)), while NN/g's usability testing puts the practical ceiling at 2 disclosure levels before usability measurably drops ([NN/g Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)). Real large doc sets (ocx-catalog's 560 files) cannot fit a flat 2-level tree — the live disagreement is whether collapsible/hideable sidebars and strong search compensate for the extra depth, or whether depth should be capped and the excess pushed into search/cross-links instead. Trending: tooling vendors (Docusaurus, Starlight) keep adding UI affordances (auto-collapse, hideable) that treat depth as manageable rather than something to avoid — the UX research hasn't caught up with tooling practice as of 2026.
- **The F-pattern's status.** Treated by many teams as a design target ("put the important stuff top-left") even though NN/g's own most recent pass (reviewed August 2026) calls that reading of it a misunderstanding and says good design should defeat the pattern, not follow it. The direction of travel is toward "F-pattern as a symptom to fix," but plenty of current design-system guidance still cites it uncritically as a layout rule.
- **Reading age / plain-English targets are converging on numbers, but the numbers vary by source.** GOV.UK's ~25 words/sentence figure sits alongside a competing "Content Design London" recommendation of ~15 words/sentence average for limited-English readers (found via secondary source, not independently verified against a primary Content Design London page in this pass) — there is no single agreed threshold across the corpus, only a shared direction (shorter is better, with GOV.UK's number as the most primary-sourced anchor found here).
- **Versioned docs.** Docusaurus's default advice (don't version unless you must, cap at 10) is a maintainer-cost argument, not a reader-UX argument — it says nothing about whether readers on an old version get worse search/nav than readers on latest. This is an open gap: none of the corpus fetched here addresses reader-side UX of a versioned doc set, only build/maintenance cost.
- **"3x more likely to recommend" for react.dev.** This number circulates widely in secondary write-ups about the redesign but does not appear in the primary blog post itself, which explicitly states no metrics. Until traced to a primary source (a React team blog post, conference talk transcript, or survey writeup), treat any citation of this figure as unconfirmed.
