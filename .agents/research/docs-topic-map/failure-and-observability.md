## Summary

- Documentation quality is one of DORA's measured capabilities (8-item score covering clarity, findability, reliability) and it amplifies every other technical practice's payoff, not just its own — teams with above-average docs get a 1525% performance lift from trunk-based development vs. 36% for teams with below-average docs ([dora.dev](https://dora.dev/capabilities/documentation-quality/)).
- The single most common HN/community complaint is not tone or structure, it is **untested examples**: code samples that don't compile, field names with typos, and docs that describe an API that no longer exists ([HN 25422756](https://news.ycombinator.com/item?id=25422756)).
- A close second complaint: **no single source of truth** — multiple slightly-different copies of the same Google Doc, Confluence pages nobody searches, READMEs gated behind a full PR+review process that nobody bothers with for a one-line fix ([HN 39375456](https://news.ycombinator.com/item?id=39375456)).
- Runbooks rot faster than any other doc type because their feedback loop is silent: nobody "gets stuck" on a runbook and dashboard file a bug, the on-call engineer white-knuckles through and moves on ([ekline.io](https://ekline.io/blog/why-your-incident-runbook-lies-to-you-at-3-a-m-and-how-to-tell-before-the-page-fires)).
- "Was this helpful" widgets and support-ticket mining both suffer survivorship bias: the people who file feedback are the ones who almost succeeded, not the ones who bounced silently — the bounced majority never shows up in either channel ([dev.to](https://dev.to/ben/the-developer-feedback-you-are-actually-getting-is-survivorship-bias-4b54)).
- Zero-result search mining is the single highest-leverage docs-analytics practice available to any project with a search box: Algolia's own guide gives concrete remediation levers (`synonyms`, `removeWordsIfNoResults`, `optionalWords`) for turning a logged failed query into a fix ([Algolia](https://www.algolia.com/doc/guides/managing-results/optimize-search-results/empty-or-insufficient-results)).
- 39% of documentation teams track no success metric at all, and among those who do, nearly half don't measure onboarding effectiveness specifically ([State of Docs 2025](https://www.stateofdocs.com/2025/documentation-metrics-and-measurement)).
- Top Tasks (Gerry McGovern) is a repeatable, falsifiable method for finding a project's real top-tier tasks: 200–400 candidate tasks, shortlisted to 50–80, voted on by 100+ (ideally 400+) users choosing their top 5 — results stabilize after as few as 30 votes in a 107,000-voter study ([Smashing Magazine](https://www.smashingmagazine.com/2022/05/top-tasks-focus-what-matters-must-defocus-what-doesnt/)).
- Liverpool City Council deleted over 80% of a 4,000-page site after Top Tasks analysis showed 200 pages generated 85% of traffic — the inverse relationship between importance and content investment is the rule, not the exception ([Smashing Magazine](https://www.smashingmagazine.com/2022/05/top-tasks-focus-what-matters-must-defocus-what-doesnt/)).
- GOV.UK's "user need" template — `As a…, I need to…, so that…` — is falsifiable in a way "who is this page for" personas are not: a bad user need "suggests a specific solution" or "justifies existing content"; a good one names an action verb (apply, appeal, pay, claim) with no implementation baked in ([GOV.UK](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs/)).
- Stripe's "friction log" is the closest thing to a portable, tool-free version of card sorting/tree testing for teams with no research budget: one person plays a persona, narrates a stream-of-consciousness attempt at a real task, the log goes to an all-company mailing list, and it turns into bugs/feature requests before launch ([Stripe friction-logging-toolkit](https://github.com/mikeb-stripe/friction-logging-toolkit/blob/main/how-we-use-friction-logs-at-stripe.md)).
- Time-to-hello-world (TTHW) is the DX field's most agreed-on funnel metric: Ably's own benchmark rates under 30 minutes as 5/5, over 4 hours as 1/5; Twilio's stated target is 5 minutes ([Nordic APIs](https://nordicapis.com/why-time-to-first-call-is-a-vital-api-metric/)).
- Vale is the de facto prose-linting tool for docs-as-code CI in 2026 (Datadog runs it across 14 writers and 35 product areas; Grafana, GitLab, Mozilla, and the Linux Foundation all run it in CI) and it is rule-name addressable (e.g. `Grafana.GooglePassive`), which is what makes a prose rule enforceable rather than aspirational ([Grafana Writers' Toolkit](https://grafana.com/docs/writers-toolkit/review/lint-prose/)).
- llms.txt is the era's cautionary tale on writing for an unverified audience: adoption grew 8.8x in a year (4,088 → 36,120 sites) but an Ahrefs log analysis found 97% of published llms.txt files got zero requests, and of the requests that did arrive only 1.1% were AI bots — the standard is being published far faster than it is read ([mecanik.dev](https://mecanik.dev/en/posts/does-llms-txt-do-anything-yet/)).
- The maintenance problem is now bigger than the creation problem industry-wide: 65% of engineering teams ship weekly or faster, docs release cadence lags, and "keeping docs up to date" is cited as the top challenge by API teams — a direct rot mechanism, not a one-off complaint ([State of Docs 2025](https://www.stateofdocs.com/2025/introduction-basic-stats), via [happysupport.ai roundup](https://www.happysupport.ai/en/blog/state-of-documentation-2026)).
- A stale runbook is worse than no runbook: 3 stale steps in a 30-step runbook is a 10% error rate, and each wrong step costs 8–15 minutes — enough to double or triple recovery time in a 20-minute incident ([ekline.io](https://ekline.io/blog/why-your-incident-runbook-lies-to-you-at-3-a-m-and-how-to-tell-before-the-page-fires)).

## Findings

### 1. Documentation quality is a measured DORA capability, not a vibe {#f1}

DORA has treated documentation quality as a first-class, measured capability since 2021, scored via an eight-metric survey instrument covering clarity, findability, and reliability, aggregated into a standardized 0–1 score per respondent ([Google Cloud, 2022 deep dive](https://cloud.google.com/blog/products/devops-sre/deep-dive-into-2022-state-of-devops-report-on-documentation/)). The finding that repeats every year since: documentation quality does not act as an independent capability, it **amplifies every other technical capability's payoff**. The 2022 report's own numbers, cited on the current capability page:

| Technical capability | Performance lift, above-average docs | Performance lift, below-average docs |
|---|---|---|
| Trunk-based development | 1525% | 36% |
| Continuous integration | 750% | 34% |
| Supply-chain security practices | 451% | 37% |
| Site Reliability Engineering practices | 343% | 79% |

([dora.dev/capabilities/documentation-quality](https://dora.dev/capabilities/documentation-quality/)). The practical implication for a fleet-wide rule: a project cannot fix "documentation" in the abstract, and a rule that only grades prose quality is grading the wrong axis. The axis that predicts organizational payoff is whether a reader can *find* the right doc and *trust* it once found — not whether the sentence is well formed.

The 2024/2025 wave adds an AI-adoption interaction: a 25% increase in AI coding-assistant adoption correlates with a 7.5% improvement in *documentation* quality score specifically (more AI-authored docs get written) but a 7.2% *decrease* in delivery stability and a 1.5% decrease in throughput, because more auto-generated code and docs raises the volume of things a team must understand without raising review capacity ([Swimm summary of 2024 DORA report](https://swimm.io/blog/heres-what-the-2024-dora-report-has-to-say-about-code-documentation)). More docs volume is not the same as more docs quality — a distinction every AI-authoring rule needs to state explicitly, because an LLM defaults to maximizing volume (see AI-agent angle, below).

### 2. The "worst documentation" genre: what HN threads actually complain about {#f2}

Three threads fetched in full, tabulated by complaint type:

| Thread | Complaint types present |
|---|---|
| [HN 25422756](https://news.ycombinator.com/item?id=25422756) — "This is the worst documentation I have ever seen in my life" (Amazon Selling Partner API, 2020) | Untested code examples (a documented fork bomb from a 1990s MS DDE example); typos in field names that silently break integrations (`fuebar`/`foobar`); inconsistent error-reporting shapes across the same API surface ("4 different ways of returning errors"); docs that describe an auto-generated, inconsistent API (Boto3 comparison); no incentive to fix ("AWS has horrible docs because the incentive is to sell premium support"); docs as the only signal that the underlying software is broken, not just the docs |
| [HN 13702628](https://news.ycombinator.com/item?id=13702628) — "Bad documentation" | Docs that "look professional and complete… and lie through their teeth" (trust erosion is worse than obvious incompleteness); support staff reading the same broken docs as the customer; machine-translated docs losing meaning (a datasheet translated from Korean, a manual reading "adjust until the sun shines most brightly upon the screen") |
| [HN 39375456](https://news.ycombinator.com/item?id=39375456) — "worst documentation tool, except all the others" | No single source of truth (multiple divergent copies of one Google Doc); high-friction update paths (a Jira ticket + branch + review to fix a one-line README); wikis nobody searches ("physically impossible for people to use a search bar in a wiki") |

Note on Reddit: the sandbox's network policy blocks `reddit.com` fetches outright (confirmed: a direct request returns an network-policy block page, not a 429). The HN sample above is the verified primary-source coverage; Reddit threads on the same theme were not independently confirmed and are not cited as fact anywhere in this file.

Cross-cutting theme across all three threads: almost none of the complaints are about *tone* or *style*. They are about **whether the documented thing is true right now** — compiles, matches the field name, matches the error shape, is the current file. This is the throughline into documentation debt/rot below, and it argues that a docs-quality rule under-invests if it stops at prose and does not gate on executability/currency.

### 3. Documentation debt and rot: silent, not alarmed {#f3}

"Documentation debt" (missing/inadequate/incomplete docs of any type) and "docs rot" (docs that no longer match the system: contradicted endpoints, broken README steps, comments referencing refactored functions) are both named as *silent* debt: unlike a failing build or a lint error, nothing pages anyone when a doc goes wrong ([OpsIntell](https://opsintell.com/documentation-debt-the-most-undervalued-form-of-technical-debt/)). This is consistent with the HN findings above — the fix that survives contact with the corpus is not "write better prose," it's "make staleness loud." Concretely this means tying doc claims to something that *can* fail visibly: an executable example that fails in CI, a link checker, or a freshness stamp.

### 4. Runbooks decay faster than any other doc type, and nobody notices until 3 a.m. {#f4}

Runbooks are the extreme case of the silent-feedback-loop problem in finding 3. Unlike API docs (corrected by customer complaints/support tickets) or tutorials (abandonment is at least visible in funnel data), a runbook is read by a small number of people, infrequently, under incident pressure where nobody stops to file a doc bug ([ekline.io](https://ekline.io/blog/why-your-incident-runbook-lies-to-you-at-3-a-m-and-how-to-tell-before-the-page-fires)). The same source gives a concrete cost model: a runbook with 30 steps and 3 stale ones is a 10% error rate; each wrong step costs 8–15 minutes; in a 20-minute incident that alone can double or triple recovery time. Three concrete countermeasures given: tie every runbook step to a live dashboard/query so it "breaks visibly" the moment the referenced thing moves; run scheduled game-day exercises that walk the runbook end-to-end outside of a real incident; land runbook updates in the same PR as the system change they describe, so the two cannot drift independently. No general-purpose documentation SLO number is given in this source, or in any source surveyed — see Contested/evolving.

### 5. Observability: what to instrument and its known failure modes {#f5}

Distinct instrumentation channels surveyed, each with a documented bias or blind spot:

- **Zero-result / no-result search mining.** The single highest-leverage, lowest-cost signal for any docs site with a search box: it directly names a content gap. Algolia's own optimization guide gives concrete remediation levers — `synonyms` for vocabulary gaps, `removeStopWords`, `ignorePlurals`, and for multi-word queries specifically `removeWordsIfNoResults` (iteratively drops query terms until something matches) and `optionalWords` (runs a merged dual query) ([Algolia docs](https://www.algolia.com/doc/guides/managing-results/optimize-search-results/empty-or-insufficient-results)). This is a mechanism any Algolia DocSearch or self-hosted Meilisearch/Typesense deployment exposes — the query log is the instrumentation, no separate telemetry needed.
- **"Was this helpful" widgets and support-ticket mining.** Both share survivorship bias: only people who almost succeeded — understood enough to not fear looking foolish, or persisted past the confusing part — leave feedback or file a ticket. The reader who bounced in the first 10 seconds is invisible to both channels ([dev.to, "The Developer Feedback You Are Actually Getting is Survivorship Bias"](https://dev.to/ben/the-developer-feedback-you-are-actually-getting-is-survivorship-bias-4b54)). Neither channel should be read as "no complaints = the page works"; absence of negative feedback is not evidence of success on a low-traffic or high-abandonment page.
- **GitHub issue labels for docs.** A `docs` label pre-categorizes incoming feedback and is one of the highest-value keys an issue template can carry; the smallest useful docs-issue report is "this section is unclear, here's what I expected instead" rather than a rewrite. This is a real feedback loop, but it inherits the same survivorship bias as above — only readers who both hit a problem *and* were GitHub-literate enough to file an issue appear in it.
- **Freshness stamps / "last verified" dates.** Documented pattern in commercial knowledge-base tooling (verification dates aged into tiers, e.g. "verified <90 days" vs. "verified >180 days"); no fleet-relevant open-source implementation was found as a primary source — this is a practice more than a specific tool, see Candidate topics.
- **Link checkers.** Named as necessary CI-pipeline hygiene alongside prose linters, but link-liveness is a narrower signal than content correctness — a link can be alive and still point at content that no longer answers the question.
- **Session recordings.** Named in the corpus's own brief as a channel to survey; no primary source with fleet-relevant specifics was found (this is a UX-research-tooling topic, e.g. Hotjar/FullStory on docs sites, better suited to a UX-track scout with product access to verify).

### 6. Use-case discovery without analytics: Top Tasks, JTBD, friction logs {#f6}

**Top Tasks** (Gerry McGovern) is the most rigorously repeatable of the methods surveyed, with a defined pipeline and stabilization property:

1. Gather 200–400 candidate tasks from existing site structure, top searches, most-visited pages, support tickets, competitor sites (3–4 weeks).
2. A cross-functional group of 3–8 people shortlists to 50–80 tasks over 5–8 ninety-minute sessions (3–4 weeks).
3. A single randomized list is put to 100+ respondents (400+ ideal), each picking their top 5 (2–4 weeks).
4. Rank by vote count.

(All figures: [Smashing Magazine, "Top Tasks: To Focus On What Matters You Must De-Focus On What Doesn't", 2022](https://www.smashingmagazine.com/2022/05/top-tasks-focus-what-matters-must-defocus-what-doesnt/).) The distribution this reveals is consistently skewed and consistently *inverse* to where content investment already sits: Liverpool City Council found its most-critical citizen tasks got the least content investment, and subsequently deleted over 80% of a 4,000-page site once 200 pages were shown to generate 85% of traffic — findings from 2009 that were reportedly still valid in 2022. A European Commission study with 107,000 respondents found the top-3 tasks were identical after just 30 votes, meaning the method is cheap to run even at small scale; it does not require hundreds of respondents to get a directionally correct answer, only to get a *precisely ranked* one.

**Jobs-to-be-done (JTBD)** applied to docs is looser in the literature surveyed — the `When [situation], I want to [action], so I can [outcome]` template is the same shape as GOV.UK's user-need template (finding 7) but JTBD's own corpus is mostly product-marketing, not documentation-specific; no docs-specific primary source with concrete numbers was found, unlike Top Tasks or friction logs. Treat JTBD as the mental model, Top Tasks/friction logs as the executable methods.

**Friction logs** (Stripe) are the lowest-overhead of the three for a project with no research budget or user base to survey: one person adopts a specific persona, attempts a real task end-to-end, and writes a stream-of-consciousness log with three fixed sections — Context (persona + goal), Pros/Cons, and the stream-of-consciousness narrative with screenshots/GIFs. The completed log is mailed company-wide and to the owning team, and becomes bugs/feature requests before wider rollout ([Stripe friction-logging-toolkit, GitHub](https://github.com/mikeb-stripe/friction-logging-toolkit/blob/main/how-we-use-friction-logs-at-stripe.md)). This is directly executable by a single maintainer on an open-source project with zero users yet to survey — it substitutes a deliberately-adopted outside perspective for a research budget.

### 7. Diataxis and GOV.UK: writing the "user need" as a testable sentence {#f7}

Diataxis's own framing places tutorial/how-to/reference/explanation on a 2×2 grid: acquisition (study) vs. application (work) crossed with action vs. cognition, giving Tutorials (acquisition+action), Explanation (acquisition+cognition), How-To (application+action), Reference (application+cognition) ([diataxis.fr/start-here](https://diataxis.fr/start-here/)). This is a *classification* framework — it says what kind of page a piece of content should become, not what content a project needs in the first place. That second question is what GOV.UK's content design guidance answers directly with a falsifiable template:

> `As a… [who], I need to… [what], so that… [why]`

with a stated failure mode for each side: a *good* user need "does not suggest a specific solution" (example given: "As a carer, I need to get financial help, so that I can carry on looking after the person I care for"); a *bad* one "creates a need to justify existing content" (example given: "As a carer, I need to use a benefits calculator, so that I can find out if I can get Carer's Allowance" — this bakes a UI solution into the stated need) ([GOV.UK content design guidance](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs/)). The guidance also insists on a specific persona noun ("carer," "exporter") rather than the generic "a user," and on action verbs (apply, appeal, pay, claim, submit) rather than passive cognition verbs ("understand," "know") unless tied to a concrete task outcome. This is the sharpest tool surveyed for turning "what are our top-tier use cases" from an opinion into something a reviewer can reject on stated grounds — a Diataxis label alone cannot be graded this way.

### 8. Card sorting and tree testing: validate structure before you ship it {#f8}

Card sorting is generative (used early, to learn how users would group content from scratch); tree testing is evaluative (used once a structure exists, to check whether users can actually find things in it) — the two are complementary and commonly sequenced, card sort first to build the structure, tree test after to validate it, per Optimal Workshop's own guidance on the two methods ([Optimal Workshop](https://www.optimalworkshop.com/blog/card-sorting-vs-tree-testing-whats-the-best)). Neither method was found with a docs-specific primary source in this survey — both are general IA research methods adapted to docs navigation, and the tooling (Optimal Workshop) is commercial and unlikely to be adopted by the fleet's smaller repos. The candidate-topic value here is lower for the fleet than Top Tasks or friction logs, which require no paid tooling.

### 9. Time-to-hello-world: the one funnel number everyone in DX agrees on {#f9}

Time-to-hello-world (TTHW) / time-to-first-call (TTFC) — elapsed time from landing on docs to a first successful API response — is the most-cited single funnel metric in the DX literature surveyed, and unusually for this domain it has an agreed benchmark scale, from Ably: under 30 minutes rates 5/5, 30–60 min rates 4/5, 1–2 hours rates 3/5, 2–4 hours rates 2/5, over 4 hours rates 1/5 ([Nordic APIs, "Why Time to First Call Is a Vital API Metric"](https://nordicapis.com/why-time-to-first-call-is-a-vital-api-metric/)). Twilio's own stated target is 5 minutes or less; a widely repeated variant target (unverified against a primary Twilio/Postman source in this survey, treat as directional) is "hello world in 5 minutes, a real task in 30." The mechanism this metric indicts is almost always the same one the HN threads complain about: an example that doesn't run as-copied costs the reader the entire TTHW budget in one failed paste.

### 10. Readability scoring and prose linting: the mechanical half of "plain English" {#f10}

Flesch-Kincaid Grade Level is the standard mechanical readability check: `0.39 × (words/sentences) + 11.8 × (syllables/word) − 15.59`, producing a US school-grade-level score ([Wikipedia, Flesch–Kincaid readability tests](https://en.wikipedia.org/wiki/Flesch%E2%80%93Kincaid_readability_tests)); secondary sources converge on a grade 9–12 target for technical documentation and grade 7–9 for general-audience content, though no single authoritative source ties a specific grade-level number to developer-docs completion or comprehension outcomes in this survey — treat the 9–12 figure as a starting default, not a validated threshold.

Prose *linting* (as opposed to readability scoring) is the enforceable half: Vale is the de facto tool in 2026, addressable by specific rule name (e.g. `Grafana.GooglePassive`, `Grafana.FirstPersonPlural`), importable from published style packs (Google Developer Documentation Style Guide, Microsoft Manual of Style), and wired into CI at Datadog (14 writers, 35 product areas), Grafana, GitLab, Mozilla, and the Linux Foundation ([Grafana Writers' Toolkit](https://grafana.com/docs/writers-toolkit/review/lint-prose/); [Datadog engineering blog](https://www.datadoghq.com/blog/engineering/how-we-use-vale-to-improve-our-documentation-editing-process/)). This is the direct verification mechanism the frame's constraint ("every rule carries a verification... a lint, not a reading opinion") is asking for — a rule that says "avoid passive voice" without naming a Vale rule ID or equivalent grep is exactly the kind of unenforced prose opinion the frame wants avoided.

### 11. Docs for AI agents: llms.txt is published faster than it is read {#f11}

llms.txt (Jeremy Howard's proposal, published 2024-09-03) is a root-level Markdown file meant to tell an LLM which parts of a site to read. As of 2026 it remains a community convention, not an IETF/W3C standard. Adoption data diverges sharply by what is measured:

- **Publishing side**: Originality.ai's tracking of 3M+ sites shows an 8.8x growth in one year (June 2025 → May 2026: 4,088 → ~36,120–38,980 sites).
- **Consumption side**: Ahrefs' server-log analysis across 137,000 domains found 97% of published llms.txt files received zero requests in May 2026; of the requests that did arrive, AI retrieval bots were only 1.1% (GPTBot 4.51% of *those* requests, ClaudeBot 0.80%, DeepseekBot 0.02% — note these are shares of the small non-zero slice, not of all traffic).
- **Who actually reads it**: coding agents pointed at a specific domain by a user (Cursor, Claude Code, Continue, Cline) are named as the one genuinely high-intent consumer; Perplexity states it uses the file to prioritize crawl pages.

(All figures: [mecanik.dev, "Does llms.txt Do Anything Yet — The 2026 Evidence"](https://mecanik.dev/en/posts/does-llms-txt-do-anything-yet/), itself synthesizing Originality.ai and Ahrefs data.) The practical read for this fleet: an llms.txt file is cheap and plausibly useful for the one audience that does demonstrably read it — a coding agent a developer has pointed at the repo — but should not be justified by, or measured against, general AI-crawler adoption, which the primary log data says is negligible.

### 12. Survey landscape 2025–2026: what the industry says about itself {#f12}

Three independent 2025/2026 industry surveys converge on the same shape of problem — creation is solved, maintenance and measurement are not:

- **State of Docs Report 2025** (GitBook, 450+ docs professionals surveyed): 39% of respondents track no documentation success metric at all; over one-third don't measure onboarding effectiveness specifically even though nearly 80% believe troubleshooting docs are "at least somewhat effective"; over 90% of leaders/engineers rate docs "extremely" or "somewhat" important to purchase decisions, but only 35% think their *own* docs move conversion — a stated-importance vs. measured-impact gap ([stateofdocs.com](https://www.stateofdocs.com/2025/documentation-metrics-and-measurement), [gitbook.com blog highlights](https://www.gitbook.com/blog/state-of-docs-report-2025)).
- **Atlassian State of Developer Experience 2024** (2,100+ developers/managers, with DX and Wakefield Research): 69% of developers report losing 8+ hours per week to workflow inefficiencies; documentation gaps are named among the top contributors to that loss, alongside technical debt and slow build processes ([atlassian.com](https://www.atlassian.com/blog/development/developer-experience-report-2024)).
- **Stack Overflow Developer Survey 2025** (49,000+ respondents, 177 countries): GitHub is the most-used documentation/collaboration tool at 81%, ahead of Jira (46%) and GitLab (36%) — a signal that "documentation" for most developers now means "what's in the repo," not a separate wiki or portal.

## AI-agent angle {#ai-angle}

- **Volume over verification.** An LLM asked to "improve the docs" characteristically adds more prose, more examples, more sections — the exact failure mode DORA's 2024 wave measured (+7.5% doc-quality score, −7.2% stability) when AI-authored volume outpaces review capacity. Smallest mechanical check: a diff-size gate or a required "what was removed" line alongside "what was added" in any AI-authored docs PR, so volume growth is visible and must be justified, not free.
- **Confident, untested examples.** An LLM will write a code sample that reads plausibly and was never run. This is precisely the top HN complaint (the fork-bomb example, the `fuebar`/`foobar` typo class of error). Smallest mechanical check: every fenced code block that claims to be runnable is either extracted and executed in CI, or is not claimed as runnable (labeled illustrative) — a grep for fenced code blocks with no corresponding test-runner reference is a one-line check.
- **Invented "who is this for."** An LLM asked to add a persona/audience line for a page will generate a plausible-sounding one ("developers integrating payment systems") without evidence, and it will not name a solution-free need in GOV.UK's falsifiable sense — it will default to describing the page's own content back at the reader. Smallest mechanical check: grep every stated user-need sentence for whether it names the *page's own feature* inside the "I need to…" clause; if it does, it's post-hoc justification, not a real need.
- **Doc drift after code changes.** An LLM implementing a code change will not reliably know which doc pages reference the changed behavior unless told to check, and unlike a human it will not "remember" that a doc exists somewhere without being pointed at it. Smallest mechanical check: a required grep/link-check step from changed source symbols to doc references before a PR claiming to touch documented behavior is considered complete.
- **Readability theater.** An LLM told to "write in plain English" will often perform simplicity signals (short sentences) while keeping structurally complex, hedge-heavy paragraphs, or will over-correct into a childish register that fails the 9–12 grade-level target for technical content in the opposite direction. Smallest mechanical check: run an actual Flesch-Kincaid or Vale readability rule on the file and gate on the number, not on a human's impression of tone.
- **Reflexive llms.txt / AI-optimization additions.** An LLM asked to "make the docs AI-friendly" will readily add an llms.txt file (or an FAQ schema, or agent-oriented metadata) as a low-effort compliance gesture, without any check that the specific consumer claimed (a crawler, a coding agent) actually reads it. Smallest mechanical check: require the PR that adds such a file to name which consumer it targets and how that will be verified (e.g., "Claude Code reads this when a user runs `/init` against this repo" — checkable — vs. "helps AI find our docs" — not checkable).

## Contested / evolving {#contested}

- **Whether documentation SLOs (a stated freshness/accuracy target with a number attached) are standard practice.** No source surveyed gives a validated numeric SLO for documentation freshness generally (only the runbook-specific staleness-rate framing in finding 4). As of September 2026 this looks like an open gap in the field rather than settled practice — a fleet-wide rule that invents a specific number (e.g., "reviewed within 90 days of the code it describes") would be prescribing ahead of the evidence, not reflecting it. Trending direction: freshness stamps are appearing in commercial knowledge-base products (finding 5) faster than in open-source docs-as-code workflows, suggesting the practice migrates from support/KB tooling into engineering docs next, not the reverse.
- **Whether AI adoption net-improves or net-harms documentation quality.** DORA's own 2024 data is two-directional in the same release: AI adoption raises the *documentation-quality score* (+7.5% per +25% AI adoption) while lowering *delivery stability* (−7.2%) — these coexist in the same report, not sequential findings. The field has not converged on whether this nets positive; treat "AI makes docs better" and "AI makes docs worse" as both defensible from the same primary source depending on which axis is weighted, as of the 2024/2025 report cycle.
- **llms.txt: publish now vs. wait for signal.** As of mid-2026 the evidence is unusually one-sided for a "contested" topic — publishers are moving fast (8.8x adoption growth) while the measured consumer side is nearly inert (97% zero-request rate). This is trending toward "publish only for a named, checkable consumer" rather than "publish because it might help," but the community discourse (per the search corpus) has not caught up to the log-level evidence yet — expect continued advocacy for blanket adoption through 2026 despite the data.
- **Whether JTBD adds anything to docs planning beyond what Top Tasks and Diataxis's "user need" already cover.** This survey found no docs-specific JTBD primary source with independent evidence (numbers, a repeatable method) distinct from the GOV.UK-style user-need template. Practitioners in the DX/product space treat JTBD as foundational; the documentation-specific literature surveyed here does not independently validate it as a distinct method. Unresolved as of this survey — likely worth a follow-up pass with product-management-specific sources rather than docs sources, which is out of this scout's corpus.
