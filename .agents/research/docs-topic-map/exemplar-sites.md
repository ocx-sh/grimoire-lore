## Summary

- Landing pages at the top exemplar sites (Stripe, uv) skip hero/marketing copy entirely and open directly on task links or an install command — this directly cuts against the "big-company-style-guide" framing, since the winning pattern here is a content-architecture choice, not a copywriting one.
- Diataxis (tutorial / how-to / reference / explanation) shows up, in substance if not name, in Kubernetes' docs nav, uv's Guides/Concepts/Reference split, and Astro's concept-vs-guide split — but its own advocate-adjacent critics (Tom Johnson) note it has no empirical basis and was arrived at by inspection, not user research.
- A project's "use-case tier" (first steps → everyday → integration → edge) and a page's "content type" (tutorial/how-to/reference/explanation) are two different, orthogonal axes — uv and Astro run both at once without collapsing one into the other, and a docs rule set that treats them as the same idea will misfile pages.
- Every fetched quickstart that stated a step count landed at 5–9 steps to a working result (Twilio 5–7, Supabase 9), matching the "Hello World in ~5 minutes" target from DX literature — this gives the tier model a checkable number instead of an opinion.
- Reference docs split two ways for a reason: Stripe keeps one long page per resource with anchors (fast ctrl-F, easy skim); Rust's std keeps one page per item (clean deep links, smaller diffs, better for machine-generated docs) — pick per how the reference is generated and consumed, not by house preference.
- GitBook's traffic data puts 41% of documentation page requests as coming from AI agents, and Stripe, Cloudflare, Vercel, Anthropic and Deno all now ship an `/llms.txt` file — this is no longer speculative, it is current infrastructure.
- Stripe and Laravel both serve every doc page as raw Markdown at a predictable `.md` URL (`docs.stripe.com/payments.md`) alongside the rendered HTML page — a mechanical, checkable convention distinct from and cheaper than an `/llms.txt` index.
- A controlled test (not a survey) found that an explicit "if you are an agent, do X" instruction does move model compliance (33.3% → 100% when the instruction states a clear preference), but labeling a section "for agents" specifically, versus a plain heading, adds nothing (34.5% vs 34.5%) — the win is clarity, not audience-targeting.
- GitLab enforces Vale (prose linter) in CI, running 82 rules across 2,827 pages in under 20 seconds, and this specifically includes gating AI-generated documentation before human review — a lint is the frame's required "verification," an opinion is not.
- Zero-result and repeated search queries on a docs site are a direct, low-cost, already-collected signal of missing content and vocabulary mismatch; nobody in this survey's exemplars publishes their own zero-result rate, but the practitioner literature treats mining it as baseline practice, not advanced.
- Link-rot checking in docs-as-code is a solved, cheap CI step (a Rust tool like `mlc` run in offline/internal-only mode against source Markdown, non-blocking) — distinct from and cheaper than a full-site build-then-crawl.
- Flesch-Kincaid targets differ by audience in the practitioner literature: grade 6–8 for consumer content, grade 9–11 for professional users, grade 9–13 for technical specialists — "plain English" needs to pick one of these per doc type, not assert a single number for a whole site.
- GitLab's own workflow makes technical-writer review non-blocking for merge (a tracked follow-up issue substitutes), while still requiring developers, not writers, to author the first draft of feature docs — docs-in-the-same-PR is a spectrum, not a binary the frame should assume settled.
- Stripe explicitly rejected semver/URL-versioning for its API in favor of date-stamped versions pinned per account, with docs that detect the logged-in user's pinned version and annotate incompatible fields inline — a concrete alternative worth citing before defaulting to semver for any versioned reference in this fleet.
- Canonical operationalizes "always complete, never finished" as quarterly per-team documentation objectives plus a mandatory onboarding workshop, not as a philosophy alone — the frame's iteration model should borrow the cadence, not just the metaphor.
- AI chat widgets on docs sites report real ticket deflection (20–50%, vendor-reported) but every case study conditions this on the assistant saying "I don't know" rather than guessing — an unqualified assistant is a plausible net-negative, not a free win.
- The general-purpose big-company style guides (Google, Microsoft) reduce, in practice, to word-choice/passive-voice/inclusive-language rules (this is literally what Vale's `Google`/`Microsoft` packages check) — none of this wave's high-value, contested findings (tiering, versioning, AI-agent readability, playground ROI) came from that literature; they came from framework docs, practitioner postmortems, and exemplar-site inspection.
- Mixing two content types on one page, and writing one page for two audiences, are named as two of the most common documentation mistakes in independent practitioner analysis — both are mechanically checkable per page ("does this page contain both a numbered procedure and an unlinked concept-only section?").

## Findings

### 1. Landing pages skip the marketing hero

Stripe's docs index has no hero copy or headline at all — it opens directly with a CLI install line ("install the Stripe CLI... and run `stripe docs`") followed by grouped task links ("Accept online payments," "Set up your development environment") organized by product area, with no scroll-stopping banner in between ([docs.stripe.com](https://docs.stripe.com/)). uv's landing page follows the same shape: one sentence of positioning ("An extremely fast Python package and project manager, written in Rust"), then the install command, then a Guides/Concepts/Reference nav — no separate marketing section ([docs.astral.sh/uv](https://docs.astral.sh/uv/)). Laravel is the outlier: its installation page keeps marketing prose ("Laravel is incredibly scalable... hundreds of millions of requests per month") interleaved with the install steps ([laravel.com/docs/12.x](https://laravel.com/docs/12.x)) — the corpus does not agree on this, but the two sites most often cited as "docs done right" (Stripe, and the Astral tools generally) both cut the hero.

### 2. Page-type separation is real and contested at once

Diataxis names four page types — tutorial, how-to, reference, explanation — split across two axes (theoretical/practical, study/work) and argues that conflating them on one page is the root cause of most bad documentation ([diataxis.fr](https://diataxis.fr/)). Kubernetes' docs home literally uses this shape under different names: "Understand Kubernetes" (concepts/explanation), "Try Kubernetes" (tutorials), "Learn how to use Kubernetes" (tasks/how-to), "Look up Reference Information" (reference) — predating and independently converging on the same split ([kubernetes.io/docs/home](https://kubernetes.io/docs/home/)). uv runs a three-way Guides/Concepts/Reference nav ([docs.astral.sh/uv](https://docs.astral.sh/uv/)); Astro's Islands page is explicitly an explanation page ("why," historical context, no directives) that hands off to separate how-to guides for `client:load`/`client:idle` directives ([docs.astro.build/en/concepts/islands](https://docs.astro.build/en/concepts/islands/)). Canonical adopted Diataxis formally and reports the split "makes existing documentation problems harder to hide" rather than fixing them by itself — it is diagnostic, not curative ([ubuntu.com/blog/diataxis-a-new-foundation](https://ubuntu.com/blog/diataxis-a-new-foundation-for-canonical-documentation)). But Tom Johnson, sympathetic to the framework, states the honest objection directly: "Siloing documentation into tutorials, how-tos, reference, and explanation seemed overly opinionated and arbitrary," and presses Procida on "what research was this information model based on?" — the model was arrived at by pattern-noticing, not a controlled study ([idratherbewriting.com](https://idratherbewriting.com/blog/what-is-diataxis-documentation-framework)). Mintlify's own "common mistakes" post names "mixing content types" (a paragraph of prose inside an API reference, a diagram inside an SDK setup guide) as mistake #1, with "apply Diataxis" as the stated fix ([mintlify.com/blog](https://www.mintlify.com/blog/breaking-down-common-documentation-mistakes)).

### 3. Use-case tiers and content-type axes are different, orthogonal cuts

The frame's hypothesized tier model (first steps → everyday tasks → elaborate integration → edge reference) answers "what should a reader see first," not "what kind of page is this." uv keeps these separate: its Guides section itself is internally staged (installation → scripts → tools → projects → publishing → integrations like Docker/Jupyter/GitHub Actions/AWS Lambda), while Concepts and Reference sit as separate top-level sections serving the content-type axis ([docs.astral.sh/uv](https://docs.astral.sh/uv/)). Astro runs three tiers under three different names at once: a 6-unit guided Tutorial (build-a-blog), a one-command self-directed quickstart (`npm create astro@latest`), and topic Guides for depth — plus a separate Reference tier for API/CLI/runtime syntax ([docs.astro.build/en/getting-started](https://docs.astro.build/en/getting-started/)). A rule set that tells a project to "map tiers to page types" 1:1 will misfile work: a tier is a reading-order decision across many pages of any type; a page type is a per-page structural contract.

### 4. Quickstarts converge on 5–9 steps, not a fixed time

Twilio's SMS quickstart reaches a working, verified result (an actual received SMS) in 5–7 focused steps per language, even though the page as a whole spans ~40+ steps across seven language variants ([twilio.com/docs/messaging/quickstart](https://www.twilio.com/docs/messaging/quickstart)). Supabase's React quickstart runs 9 sequential steps from project creation through querying data locally, explicitly scoped as "getting you to a working app, not for production" ([supabase.com/docs/guides/getting-started/quickstarts/reactjs](https://supabase.com/docs/guides/getting-started/quickstarts/reactjs)). This matches the DX-industry "time to hello world" framing, where Postman is cited as calling it "the most important API metric" and practitioner guidance sets a five-minute target for a first successful call, tracked alongside time-to-200, activation rate, docs search dead-ends, and support tickets per integration as a correlated metric set (search-aggregated from Fern/Moesif/APIscene DX writing; see Sources).

### 5. Reference pages split single-page vs per-item, on purpose

Stripe's API reference is a single logical reference tree organized by resource, generated per-account (it explicitly states "Log in to see docs with your test key and data" and differs "for every account as we release new versions") ([docs.stripe.com/api](https://docs.stripe.com/api)). Rust's std library reference is the opposite: every primitive, module, macro, and type gets its own page (`primitive.char.html`, `collections/index.html`, etc.), with a distinct search-by-name tool at the top of every page rather than in-page ctrl-F ([doc.rust-lang.org/std](https://doc.rust-lang.org/std/index.html)). The tradeoff: single-page favors fast in-page search and a mental map of the whole surface; per-item favors clean permalinks, smaller diffs per change, and machine-generated-doc pipelines (rustdoc generates one file per item automatically; Stripe's per-account single page requires runtime personalization instead).

### 6. Code presentation: tabs, single command, or interactive console

Vite's guide shows five parallel package-manager tabs (npm/yarn/pnpm/bun/deno) for every scaffold command, remembered as a preference across the site ([vite.dev/guide](https://vite.dev/guide/)); Tailwind's installation page does the same with five installation-method tabs (Vite/PostCSS/CLI/Framework Guides/Play CDN) ([tailwindcss.com/docs/installation](https://tailwindcss.com/docs/installation)). Bun's own landing page takes the opposite stance on its front door: exactly one command (`bun run index.tsx`), with platform/manager variants deferred to a separate Installation page — deliberately not tabbed at the point of first contact ([bun.sh/docs](https://bun.sh/docs)). At the high-interactivity end, an independent teardown names Stripe's in-page API playground — pre-filled with the reader's own live test key, so "you fill in parameters in a form, hit send, and see the response inline" — as "the single biggest accelerator for time to first API call" ([writechoice.io](https://writechoice.io/blog/best-api-documentation-stripe-teardown)); Vitest achieves a similar effect more cheaply via a table of StackBlitz-embedded example projects rather than a custom playground ([vitest.dev/guide](https://vitest.dev/guide/)).

### 7. Versioning has three unrelated meanings

Kubernetes runs the last four minor releases as fully separate subdomains (`v1-36.docs.kubernetes.io`, etc.) — versioning the whole site ([kubernetes.io/docs/home](https://kubernetes.io/docs/home/)). Django and Laravel instead keep one domain with a per-page version dropdown reaching back to much older releases (Django: 5.2 down through 1.8; Laravel explicitly banners "You're browsing the documentation for an old version") ([docs.djangoproject.com/en/5.2/intro/tutorial01](https://docs.djangoproject.com/en/5.2/intro/tutorial01/), [laravel.com/docs/12.x](https://laravel.com/docs/12.x)). Next.js's "version switcher" is not a release version at all — it toggles between the App Router and Pages Router content forks, an architecture choice, not a time axis ([nextjs.org/docs](https://nextjs.org/docs)). A rule that says "add a version switcher" without naming which of these three problems it solves is not yet a rule.

### 8. AI agents are now a measured share of doc traffic, with mechanical conventions to serve them

GitBook's own traffic data, as cited by a third party, puts "41% of documentation page requests" as coming from AI agents — "Cursor building features, Claude answering support tickets, custom RAG pipelines" ([gitdoc.ai](https://gitdoc.ai/blog/llms-txt-ai-readable-documentation)). The `llms.txt` spec itself requires exactly one thing (an H1) and optionally a blockquote summary plus H2-grouped markdown link lists, sited at `/llms.txt` or any subpath, with the more-specific file winning when both apply ([llmstxt.org](https://llmstxt.org/)). Deno's docs point AI coding agents at a companion `deno.com/agents.md` and separately reference an `/llms.txt` index ([docs.deno.com/runtime](https://docs.deno.com/runtime/)). Separately and more cheaply, Stripe and Laravel both serve every doc page as raw Markdown at a predictable `.md` sibling URL (`docs.stripe.com/payments.md`, and Laravel's own guidance recommends `.ai/guidelines/*.md` files for project-specific agent context via its Boost tool) ([docs.stripe.com](https://docs.stripe.com/), [laravel.com/docs/12.x](https://laravel.com/docs/12.x)) — this is a static-hosting convention, not a spec, and is checkable by curling the URL.

### 9. Telling an agent "this part is for you" is measured, not assumed

Ferri-Benedetti ran a controlled comparison with Claude Sonnet rather than asserting an opinion: comparing documentation with and without an explicit stated preference, the model followed the recommended procedure 33.3% of the time with no guidance versus 100% of the time when the preference was explicit — instructions do work. But separately testing whether labeling a section "For agents" changes anything relative to a plain heading, both conditions scored identically at 34.5% when the page also contained conflicting information — the agent label itself added nothing ([passo.uno/if-you-are-an-agent-read-this](https://passo.uno/if-you-are-an-agent-read-this/)). His recommendation is to write one clear, unambiguous page for everyone, verify it with evals across models, and push code samples into collapsible sections or a separate LLM-friendly file rather than degrade the page a human reads. A companion piece argues the deeper split is by *purpose*, not audience label: docs should be "the best possible fuel" for agents' factual retrieval while a human still needs "mental models, not a reference," attributed to Drew Breunig — meaning the same reference content can serve both, but a human still needs separate explanatory material an agent does not ([passo.uno/tech-writing-role-split](https://passo.uno/tech-writing-role-split/)).

### 10. Docs quality gates are mechanical, not editorial opinion

Vale is a markup-aware prose linter (Markdown/AsciiDoc/reStructuredText/HTML) distributed as a single Go binary, configured per-project via `.vale.ini`, with importable rule packages named after the Google and Microsoft style guides plus Red Hat and others, run via GitHub Actions, pre-commit, or an LSP-capable editor ([vale.sh](https://vale.sh/)). GitLab's own published workflow states explicitly: run Vale on a doc file before submitting for review, and — as of this era — AI-generated documentation specifically "must pass Vale testing before technical writer review" ([docs.gitlab.com/development/documentation/workflow](https://docs.gitlab.com/development/documentation/workflow/)); the scale claim on Vale's own site is that GitLab runs 82 rules across 2,827 pages in under 20 seconds in CI. This is the concrete shape of "every rule carries a verification" that the frame's constraints already demand — Vale (or a grep-based equivalent) is the mechanism, not a style opinion offered without one.

### 11. Observability of docs means specific logs, not a vibe

Practitioner writing on docs-site search analytics treats zero-result and high-volume-repeated queries as a direct, already-collected signal: "a query like 'bulk export billing data' with zero results, repeated many times in a month, is a clear indicator to write that article," distinguished from a second pattern — the article exists but the query used different vocabulary, a terminology gap rather than a content gap (search-aggregated from Earley/Wizzy/HelpDocs writing; see Sources). None of the twenty exemplar sites surveyed here publish their own zero-result rate publicly, so this practice is inferred from the vendor/practitioner literature about docs-search tooling, not verified against a named site's own numbers — flagged as a gap in this wave's direct evidence, not a settled claim.

### 12. Plain English needs a number, and the number depends on audience

Flesch-Kincaid grade-level guidance in the practitioner literature is audience-specific rather than a single site-wide target: roughly grade 6–8 for consumer-facing content, grade 9–11 for professional users, and grade 9–13 for technical specialists, with an explicit caveat that the metric "penalizes long sentences and multi-syllable words — both common in technical writing," so absolute scores skew high for any reference doc and the metric is better used as a relative gauge between drafts than an absolute pass/fail bar (search-aggregated from Readable and Docsie readability guides; see Sources). This directly operationalizes the frame's "plain English" hypothesis into something a lint can check, but it needs a chosen target per doc type (landing vs reference will differ), not one number for the whole site.

### 13. Docs-as-code process choices are contract questions, not style questions

GitLab's published workflow makes three specific, non-obvious calls: developers, not the writing team, are "the primary authors of documentation for a feature"; documentation review (by a technical writer) is *not allowed to block a merge* — if a feature merges before writer approval, a maintainer must open a tracked post-merge follow-up issue assigned to both the engineer and the writer; and some teams opt in to making docs-in-the-same-MR mandatory as part of their own definition of done, but this is a per-team choice, not the house default ([docs.gitlab.com/development/documentation/workflow](https://docs.gitlab.com/development/documentation/workflow/)). Branch names starting `docs/` or `docs-` also get a faster, docs-only CI pipeline. This is a process/governance question the frame's artifact set does not yet address at all.

### 14. "Always complete, never finished" is a cadence, not a slogan

Procida's Write the Docs talk argues the trap is confusing "finished" (an impossible standard for a living product) with "complete" (usable and non-misleading at every increment) — the practical instruction is to iterate on a small unit (a paragraph, not a master outline) and publish it as soon as it is honestly complete, rather than holding a whole rewrite for a big-bang release (secondary summary, original talk page unreachable: [knowledgeowl.com/blog/posts/always-complete-never-finished](https://www.knowledgeowl.com/blog/posts/always-complete-never-finished)). Canonical, where Procida works, operationalizes this as a recurring practice rather than a one-time philosophy adoption: a mandatory four-hour onboarding workshop for new hires on doc types and placement, plus quarterly per-team objectives around specific areas of documentation, tracked in shared spreadsheets — "most teams don't need to work harder... they just need to do it in the right way" ([getdx.com/blog/making-technical-documentation-easier](https://getdx.com/blog/making-technical-documentation-easier/)).

### 15. AI chat widgets on docs sites deflect tickets, conditionally

Vendor-reported case studies (kapa.ai) claim 20–50% support-ticket deflection when an AI answer widget is layered across the docs widget, support form, and community channels simultaneously, with named examples (Mapbox: 20% fewer monthly tickets; CircleCI: 28% faster Zendesk response times) ([kapa.ai/use-cases/support-ticket-deflector](https://www.kapa.ai/use-cases/support-ticket-deflector)). Every source surveyed here conditions the win on the assistant explicitly saying "I don't know" and routing hard cases to a human rather than guessing — an assistant tuned for coverage over accuracy is described as capable of net-harming trust rather than helping it. No source in this wave measured or reported the failure case directly (i.e., a docs site whose AI widget backfired) — this is a vendor-reported literature, treat the numbers as directional rather than independently audited.

## AI-agent angle

What an LLM writing documentation in this corpus's area characteristically gets wrong, and the smallest mechanical check that catches it:

- **Writes a marketing hero for a docs landing page** because that is the dominant pattern in its training data for "landing page." Check: grep the first 200 words of the docs index page for superlative adjectives ("powerful," "seamless," "effortless") or an unlinked headline sentence with no code and no link — either is a hero, and the exemplar pattern (Stripe, uv) has neither.
- **Mixes content types on one page** — adds a paragraph of "why this matters" explanation into the middle of a numbered how-to procedure, or a reference table into a tutorial — because it is optimizing for "helpful and complete" on a single pass rather than for a reader who came in with one specific need. Check: does the page contain both an unlinked, non-actionable prose block *and* a numbered procedure, or both a parameter table *and* a first-person narrative? Either combination is the mixing Mintlify names as mistake #1.
- **Invents a fixed word count or "should take N minutes" claim for a quickstart** without checking the actual step count against what similar tools ship, because it has no access to a completion-rate metric. Check: count discrete numbered actions (not sentences) to the first working result; flag if a "quickstart" exceeds ~9 or a "getting started" page has no bounded action count at all.
- **Writes an "if you are an agent" callout** as its own idea of a helpful addition, without evidence it changes anything. Check: does the instruction encode a *specific stated preference* between two named alternatives (the only case measured to help), or is it a generic audience label added to already-clear prose (measured to add nothing)? If the latter, delete it and keep the plain heading.
- **Asserts a documentation practice ("teams do X") from its training data without a fetched, dated source**, especially for anything version- or tool-specific (Vale's rule count, a framework's current router split, a CLI's current flag). Check: does every non-obvious claim in the draft carry a link to a page actually fetched this session, not a memory of what that tool "usually" does? A claim with no link is a claim to re-verify, not to ship.
- **Adds a semver-style version number to a reference doc by default**, because that is the most common versioning scheme in its training data, without checking whether the actual tool needs per-account pinning, a content fork, or no version marker at all. Check: does the "version" being switched change a release date, a whole site, or a content fork (App Router vs Pages Router)? Naming the wrong one produces a switcher nobody can use correctly.
- **Writes a glossary/tooltip definition that duplicates the term's real reference page** instead of linking to it, because generating fresh prose is cheaper than checking for an existing anchor. Check: before adding a tooltip or glossary entry, grep the reference tree for an existing heading matching the term; link it instead of re-explaining it inline.

## Contested / evolving

- **Diataxis's evidentiary basis.** Adoption is accelerating through 2024–2026 (Canonical formally, Kubernetes' shape independently, uv/Astro/Mintlify's stated fix-it advice), but its own sympathetic critics ask what research grounds the four-way split, and its inventor's own case study (Canonical) reports it mainly makes existing problems *visible*, not that it measurably improves outcomes on its own. Trending: wider adoption as a default vocabulary, but treated as a diagnostic lens rather than a proven-effective intervention.
- **Whether AI-agent-facing docs should be separate content or the same content, clearer.** The industry is building dedicated tracks fast (llms.txt, Laravel Boost, Stripe's `.md` URLs and skills, Deno's agents.md) — but the one controlled test found in this survey argues the win from any of this is clarity that also helps humans, not audience-specific instruction that only helps agents. Trending: toward serving agents from the same well-structured source (one canonical page, machine-fetchable), away from parallel "for agents" prose forks.
- **Interactive playground investment.** Stripe invests heavily (per-user, key-prefilled, in-page); most sites in this survey (Twilio, Django, Laravel, Bun) invest nothing beyond a copy button. As of this era there is no consensus threshold for when the build cost is worth it — the two data points found (Stripe's teardown claim, Vitest's cheaper StackBlitz-table alternative) suggest "when the API surface is large and TTHW is actually measured" rather than a general default.
- **API versioning scheme.** Semver-in-URL (long the default) is directly and publicly rejected by Stripe in favor of date-pinned-per-account; most tool docs in this survey (Tailwind, Bun, uv) instead show only "current" with an upgrade guide and no persistent version concept at all. Trending: no single winner — the fleet should pick per how often the surface actually breaks compatibility, not by copying whichever scheme is most familiar.
- **AI chat widgets as a docs-UX default.** Genuinely new since ~2024, evolving fast, and every source found here is vendor-reported (kapa.ai) rather than independently audited — the deflection numbers are plausible but unverified by a third party in this wave, and no source measured the failure mode (a widget that erodes trust by guessing). Treat as unresolved, not as settled best practice, until an independent measurement is fetched.
- **Docs-in-the-same-PR as a merge gate.** GitLab's own default explicitly refuses to make this blocking, while naming it as an option some teams choose. This is presented by GitLab as a deliberate, still-open choice per team, not a solved question — the frame should not assume one answer for the whole fleet.
