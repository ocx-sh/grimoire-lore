## Summary

- The single most-reacted open issue in `gradle/gradle` (387 👍, [#15383](https://github.com/gradle/gradle/issues/15383)) is that type-safe version-catalog accessors are invisible from precompiled script plugins — version catalogs are the modern default but have a real seam at the `build-logic`/convention-plugin boundary.
- Configuration cache is now the load-bearing migration of the era: stable since Gradle 8.1, and Gradle 9.0 makes it the "preferred mode of execution" — but the requirements list (no `Project`/`Configuration`/`Thread`/`Lock` at execution time, no ad-hoc file reads, no un-migrated `BuildListener`) is long and mechanically checkable.
- Isolated Projects is still **incubating** even as of Gradle 9.7.0 (promoted from experimental just this cycle) — it is not yet a "must adopt now" gate, but its forbidden patterns (cross-project property access, plugin application on `Gradle` from project scope) are the same patterns configuration-cache migration already flags.
- `buildSrc` is Gradle's own documented anti-pattern for anything beyond trivial: any change inside it invalidates the whole build's configuration phase and forces re-execution, which is exactly why `build-logic`-as-included-build is now the default convention-plugin shape in the newer exemplars (nowinandroid, detekt, ktlint, apollo-kotlin, ktor, spotless all use `build-logic`/`catalog`, not `buildSrc`).
- The `kotlin-dsl` plugin embeds a fixed Kotlin runtime; applying a Kotlin Gradle plugin whose version differs trips "Runtime JAR files in the classpath should have the same version" or "The Kotlin Gradle plugin was loaded multiple times" — root cause is Gradle's classloader isolation per included build, not a user dependency conflict, and the only durable fix is aligning plugin/embedded-Kotlin versions, not classpath surgery.
- `api` vs `implementation` is mechanically enforceable: a type that leaks through a public superclass, method signature, or field but is declared `implementation` produces "package does not exist" **at the consumer**, not at the declaring module — the check has to run from the consumer's compile task, which is why it is easy to skip in solo-module dev loops.
- `compileOnly` misuse is the mirror failure: a dependency needed by generated bytecode or reflection at runtime but only declared `compileOnly` produces `NoClassDefFoundError` in production, never in the unit-test run that shares the compile classpath.
- Guava's `listenablefuture:9999.0-empty-to-avoid-conflict-with-guava` is a real, shipped, versioned workaround (not folklore) for the standalone `listenablefuture:1.0` vs bundled-in-Guava class conflict — Gradle's highest-version-wins picks the fake 9999 release over the real 1.0, which is the entire trick; it silently breaks for build tools that don't do highest-wins or when an old Guava forces a downgrade.
- Fat/shadow jars have a whole taxonomy of *silent* failures because a merge tool defaults to first-wins or last-wins on duplicate paths: `META-INF/services/*` (ServiceLoader providers vanish — JDBC drivers, Jackson modules), `META-INF/spring.factories` / `spring/*.imports`, and `META-INF/org/apache/logging/log4j/core/config/plugins/Log4j2Plugins.dat` all need an explicit merge transformer (Shadow ships `ServiceFileTransformer`/`mergeServiceFiles()` and `Log4j2PluginsCacheFileTransformer`; Maven Shade's `ServicesResourceTransformer` is the analogue) — the default `duplicatesStrategy` silently drops correctness with no build failure.
- Signed dependency jars shaded into a fat jar throw `SecurityException: Invalid signature file digest for Manifest main attributes` at runtime, because the merged classes no longer match the original signature; the fix is to exclude `META-INF/*.SF`, `*.DSA`, `*.RSA` from the shaded artifact, never to try to re-sign the merge.
- Multi-release jars interact badly with shading: Log4j2 (and others) ship a `module-info.class` inside `META-INF/versions/<N>/`, and until Shadow explicitly excluded it (tracked in [GradleUp/shadow#729](https://github.com/GradleUp/shadow/issues/729)) it leaked into fat jars as a dangling, irrelevant module descriptor; split packages across shaded libraries (e.g. `jaxb-impl`/`jaxb-core`) independently break JPMS regardless of the module-info question.
- Spring Boot deliberately does **not** use Shadow/Shade: its `BOOT-INF/classes` + `BOOT-INF/lib/*.jar` nested-jar layout keeps every dependency jar intact (no merge, no class-identity change) at the cost of a small nested-jar classloading startup cost, which it now also lets you erase via `java -Djarmode=tools -jar app.jar extract` before running the extracted layout — i.e. the "don't shade a fat jar, nest it" alternative is a first-class, documented, still-current (2026) strategy, not a historical footnote.
- Central Portal is now the *only* publishing path: OSSRH reached end-of-life 2025-06-30, all namespaces were force-migrated, and any pipeline still pointing at `oss.sonatype.org`/`s01.oss.sonatype.org` fails outright — this is a hard, dated (2025-06-30), zero-ambiguity fact for any release-runbook rule.
- Gradle Module Metadata's variant-aware resolution is invisible to Maven consumers by design: a Maven build only ever sees the legacy POM, so a Gradle-only extra variant (e.g., a `shadowJar` publication or a Kotlin Multiplatform target) simply does not exist for it — the POM carries a marker comment for Gradle, nothing actionable for Maven.
- Maven Enforcer's `dependencyConvergence` / `requireUpperBoundDeps` / `bannedDependencies` / `banDynamicVersions` rules are Maven's answer to the same nearest-wins surprise Gradle solves with dependency locking + `resolutionStrategy` — none of them are on by default; a project without an enforcer binding has no mechanical guard against version drift at all.
- Gradle's own wrapper-jar checksum validation (`gradle/wrapper-validation-action`, folded into `gradle/actions/wrapper-validation` since v3) exists specifically because the wrapper jar is a supply-chain target: a tampered `gradle-wrapper.jar` runs before any dependency resolution or sandboxing kicks in.
- Dependency-verification metadata (`gradle/verification-metadata.xml`) has a documented chicken-and-egg problem: bootstrapping it with `--write-verification-metadata sha256` trusts whatever is currently resolvable, so the file must be diffed and reviewed by a human on every regeneration, not treated as itself a security control.
- JEP 400 (UTF-8 by default, JDK 18+) does not automatically fix Gradle: Gradle historically never set `file.encoding` for its own daemon JVM, so a daemon launched under a non-UTF-8 platform default (classically Windows code pages) still needs an explicit `org.gradle.jvmargs=-Dfile.encoding=UTF-8` even on a modern JDK, because the daemon's own launch predates the build script's toolchain selection.
- `rules_jvm_external`'s `maven_install.json` lock file is the Bazel-Java analogue of a Gradle/Maven lockfile: generated via `REPIN=1 bazel run @maven//:pin`, it pins every resolved artifact's SHA-256 for offline, reproducible fetches, and Bazel fails the build outright if a `maven.install()` change requires repinning that hasn't happened.
- The Jakarta EE `javax.*` → `jakarta.*` rename (forced because Oracle kept the `javax` trademark when Eclipse Foundation took over Java EE) is still an active migration tax in 2026: every third-party library in the dependency graph needs a Jakarta-namespaced artifact before an app can move, and Spring Boot's own dependency management only covers the libraries it manages, not arbitrary transitive ones.
- Square's own configuration-cache rollout (2022, still the most detailed public postmortem) needed to fork Wire and get Anvil patched before their monorepo could adopt the cache — concrete evidence that third-party plugin compatibility, not the application code itself, is usually the long pole in a configuration-cache migration.

## Survey

### 1. Gradle's official troubleshooting guide
[docs.gradle.org/current/userguide/troubleshooting.html](https://docs.gradle.org/current/userguide/troubleshooting.html) — Gradle's own canonical error catalogue is thin relative to its actual failure surface: it covers installation (`JAVA_HOME is set to an invalid directory`, `command not found: gradle`, `chmod +x`), one build-logic scenario ("Task executed when it should have been UP-TO-DATE" → use `--info` / Build Scan Timeline), and one daemon-connection scenario (NAT masquerading breaking daemon reconnection, diagnosable via `$GRADLE_USER_HOME/daemon/<version>/daemon-<PID>.out.log`). Debug flags documented: `-Dorg.gradle.debug=true`, `-Dorg.gradle.debug.port`, `--console=verbose`, `--status`. **Implication for this program**: the official page is not where the real long tail of pain lives — that lives in the issue tracker and forum, surveyed below.

### 2. `gradle/gradle` issues sorted by reactions (`gh api search/issues`, read-only)
Top-reacted overall: [#15383](https://github.com/gradle/gradle/issues/15383) type-safe version-catalog accessors unreachable from precompiled script plugins (387, open, labels `a:feature in:kotlin-dsl in:dependency-version-catalog in:precompiled-script-plugin`); [#847](https://github.com/gradle/gradle/issues/847) same-named subprojects causing "unintended conflict resolution" (137, open, `a:bug in:dependency-resolution in:multi-projects`); [#16345](https://github.com/gradle/gradle/issues/16345) "Remove fixed Kotlin runtime version limitation in Gradle" (163, closed, `in:kotlin-dsl`); [#13020](https://github.com/gradle/gradle/issues/13020) suppress Kotlin compiler version mismatch warning (128, closed); [#19750](https://github.com/gradle/gradle/issues/19750) `org.gradle.jvmargs` can cause "Daemon disappeared" failures (50, open). Filtered by label: `in:configuration-cache` top is [#13510](https://github.com/gradle/gradle/issues/13510) "shareable between machines" (114, open) plus a cluster of migration-friction issues — [#18520](https://github.com/gradle/gradle/issues/18520) build listeners incompatible with the cache, [#19793](https://github.com/gradle/gradle/issues/19793) `ISE: GradleProperties has not been loaded yet` for included builds, [#24040](https://github.com/gradle/gradle/issues/24040) explicit repo credentials breaking under the cache. `in:isolated-projects` top is [#8538](https://github.com/gradle/gradle/issues/8538) parallel configuration phase (25, closed) and several "how do I do X under Isolated Projects" issues ([#28857](https://github.com/gradle/gradle/issues/28857) `findProperty` replacement, [#29037](https://github.com/gradle/gradle/issues/29037) adding dependencies to a project) confirming the feature still lacks parity APIs for common cross-project patterns. `in:dependency-resolution` besides #847: [#2298](https://github.com/gradle/gradle/issues/2298) "Forbid dependency resolution at configuration time by default" (52, open — still open, i.e. still legal to shoot yourself in the foot); [#9160](https://github.com/gradle/gradle/issues/9160) "Support overriding BOM version properties with ext" (47, open); [#5426](https://github.com/gradle/gradle/issues/5426) `AmbiguousVariantSelectionException` (30, closed).

### 3. `gh api` search for the specific classloader/dependency error strings named in the brief
"Cannot change dependencies of dependency configuration" ([#957](https://github.com/gradle/gradle/issues/957), plus [Gradle forum thread](https://discuss.gradle.org/t/weird-error-when-trying-to-add-dependency-cannot-change-configuration-after-it-has-been-resolved/9751)): the error fires on **read access** to an already-resolved `Configuration`, not only on mutation — classic trap is calling `configurations.runtimeClasspath.files` inside a `Jar { manifest {} }` block before the graph is finalized. "Runtime JAR files in the classpath should have the same version" / "Kotlin Gradle plugin was loaded multiple times" ([gradle/kotlin-dsl-samples#1388](https://github.com/gradle/kotlin-dsl-samples/issues/1388), [forum](https://discuss.gradle.org/t/the-kotlin-gradle-plugin-was-loaded-multiple-times-in-different-subprojects/51021), [KT-41142](https://youtrack.jetbrains.com/issue/KT-41142/Kotlin-version-conflict-when-using-Kotlin-Gradle-plugins-in-pre-compiled-script-plugin)): root cause is the `kotlin-dsl` plugin embedding a fixed Kotlin stdlib/compiler version that clashes with an explicitly-applied `org.jetbrains.kotlin.jvm` plugin of a different version; suppressible only cosmetically via `-Xskip-runtime-version-check`, fixable only by aligning versions.

### 4. Configuration cache requirements reference
[docs.gradle.org/current/userguide/configuration_cache_requirements.html](https://docs.gradle.org/current/userguide/configuration_cache_requirements.html) — the exhaustive, mechanically-checkable disallow-list: live JVM types (`ClassLoader`, `Thread`, `Socket`, `Lock`/`Semaphore`/`CountDownLatch`), Gradle model types (`Project`, `Settings`, `SourceSet`, `Configuration` — use `FileCollection`/`Provider<ResolvedComponentResult>` instead), `Task.getProject()` at execution time, `BuildListener`/`TaskExecutionListener` registered at configuration time, `ProcessBuilder`/`Runtime.exec()`/`ExecOperations.exec` at configuration time (use `providers.exec()` or a `ValueSource`), enumerating all `System.getenv()`/`System.getProperties()` (use `providers.environmentVariablesPrefixedBy()`), and direct file reads at configuration time (use `providers.fileContents(...).asText`). Every one of these is a static-analyzable AST pattern.

### 5. Isolated Projects current status
[docs.gradle.org/current/userguide/isolated_projects.html](https://docs.gradle.org/current/userguide/isolated_projects.html) — promoted from experimental to **incubating only at Gradle 9.7.0**; forbids direct cross-project mutable-state access (`description`, `group`, `version`, `tasks`, `configurations` of another project), forbids registering listeners/applying plugins/mutating extensions on the `Gradle` object from project scope, and eliminates implicit parent-project property/method lookup. Recommended migration path: diagnostics mode first (report without failing), then convention plugins over cross-project configuration, then the read-only `IsolatedProject` API for the rare legitimate cross-project read.

### 6. `buildSrc` vs included builds
[docs.gradle.org/current/userguide/sharing_build_logic_between_subprojects.html](https://docs.gradle.org/current/userguide/sharing_build_logic_between_subprojects.html) — states plainly that "changes to code in `buildSrc` will invalidate the configuration phase and require re-execution of all tasks." Cross-checked against the exemplar corpus's own table (`jvm-frame.md`): the newer, more actively-maintained plugin-shaped repos (nowinandroid, detekt, ktlint, apollo-kotlin, ktor, spotless, sqldelight) have all moved to `build-logic`/version-catalog convention plugins; `buildSrc` survives mainly in older or Java-heavy exemplars (dagger, grpc-java, micronaut-core, mockito, testcontainers-java, spring-boot, kotlinx.coroutines, Exposed) — a live, measurable "old shape vs new shape" split in the corpus itself.

### 7. `api` vs `implementation` separation
[docs.gradle.org/current/userguide/java_library_plugin.html](https://docs.gradle.org/current/userguide/java_library_plugin.html#sec:java_library_separation) — `api` dependencies transitively appear on consumers' compile classpath; `implementation` dependencies do not. A dependency belongs in `api` if its types appear in the library's own public superclasses/interfaces, public method parameters/returns, public fields, or public annotations — everything else is `implementation`. Misdeclaring an `api`-shaped dependency as `implementation` produces "package does not exist" **at the consumer's compile task**, which is exactly why it is easy to miss in a single-module dev loop and only surfaces in a downstream consumer or a multi-module CI build.

### 8. Dependency locking
[docs.gradle.org/current/userguide/dependency_locking.html](https://docs.gradle.org/current/userguide/dependency_locking.html) — `./gradlew dependencies --write-locks` (or `--update-locks group:module,...` for a scoped update) writes `gradle.lockfile` per project (`buildscript-gradle.lockfile` for the buildscript classpath); `dependencyLocking { lockAllConfigurations() }` turns it on globally; `LockMode.STRICT` vs `LENIENT` controls whether an unlocked-but-marked configuration fails; explicitly documented incompatibility: "should not be used with changing versions (e.g. `-SNAPSHOT`)" because a changing version's resolved artifact can differ build-to-build even at a pinned version string; a failed build does not persist lock-state changes, preventing a broken build from silently rewriting the lockfile.

### 9. Dependency verification metadata bootstrapping
[docs.gradle.org/current/userguide/dependency_verification.html](https://docs.gradle.org/current/userguide/dependency_verification.html) — `./gradlew --write-verification-metadata sha256[,pgp]` generates `gradle/verification-metadata.xml` by resolving everything across root, subprojects, `buildSrc`, and included builds and hashing what it fetches. The documented chicken-and-egg risk: bootstrapping "trusts whatever is currently in your repositories," so a compromised dependency present at bootstrap time gets a checksum recorded and permanently trusted unless a human reviews the generated diff. Every subsequently-added dependency without a matching entry fails the build with "checksum is missing from verification metadata," naming the exact GAV — mechanically checkable, but only after the fact.

### 10. Wrapper checksum supply-chain validation
[github.com/gradle/wrapper-validation-action](https://github.com/gradle/wrapper-validation-action) — validates checksums of every `gradle-wrapper.jar` in the repo and fails the build on any unrecognized wrapper jar; as of v3 it delegates to `gradle/actions/wrapper-validation`. Exists because the wrapper jar executes before any of Gradle's own dependency-resolution or configuration-cache sandboxing takes effect — a tampered wrapper jar is a pre-toolchain compromise, the same class of risk as a compromised `curl | sh` installer.

### 11. Central Portal publishing and the OSSRH sunset
[central.sonatype.org/publish/publish-portal-guide](https://central.sonatype.org/publish/publish-portal-guide/) plus [central.sonatype.org/news/20250326_ossrh_sunset](https://central.sonatype.org/news/20250326_ossrh_sunset/) and [central.sonatype.org/pages/ossrh-eol](https://central.sonatype.org/pages/ossrh-eol/) — OSSRH reached end-of-life **2025-06-30**; all namespaces were migrated (self-service or automatic, oldest-publishers-first) to the Central Portal; any release pipeline still targeting `oss.sonatype.org`/`s01.oss.sonatype.org` fails outright post-sunset. Central Portal publishing validates against Central's requirements (namespace verification, javadoc/sources jars, GPG signatures, complete POM metadata) before promotion; snapshot publishing requires explicit per-namespace enablement in the Portal, unlike OSSRH's always-on snapshot repo.

### 12. Gradle Module Metadata and Maven-consumer blindness
[docs.gradle.org/current/userguide/publishing_gradle_module_metadata.html](https://docs.gradle.org/current/userguide/publishing_gradle_module_metadata.html) — GMM is a variant-aware sibling to the POM; a pure-Maven consumer has no concept of variants and sees only the legacy POM (with a marker comment pointing Gradle consumers at the `.module` file), so any Gradle-only extra variant — a `shadowJar` publication, a Kotlin Multiplatform target, a feature variant — is invisible to Maven and must be separately mapped as a classified artifact if Maven consumers need it at all.

### 13. Shadow plugin merge transformers
[gradleup.com/shadow/configuration/merging](https://gradleup.com/shadow/configuration/merging/) — `mergeServiceFiles()` (backed by `ServiceFileTransformer`, configurable `path =`, and per-service `exclude(...)`) is the fix for ServiceLoader providers silently vanishing under default first-wins/last-wins duplicate handling; `Log4j2PluginsCacheFileTransformer` merges `META-INF/org/apache/logging/log4j/core/config/plugins/Log4j2Plugins.dat`; other named transformers include `ApacheLicenseResourceTransformer`, `ApacheNoticeResourceTransformer`, `GroovyExtensionModuleTransformer` (`mergeGroovyExtensionModules()`), `AppendingTransformer`, `XmlAppendingTransformer`. Spring's `spring.factories`/`spring/*.imports` merging is a known pain point in the wider ecosystem but not documented on this specific page — Spring Boot's own answer (survey #14) is to avoid the merge entirely.

### 14. Multi-release-jar / module-info interaction with shading
[GradleUp/shadow#729](https://github.com/GradleUp/shadow/issues/729), [johnrengelman/shadow#398](https://github.com/johnrengelman/shadow/issues/398), [Gradle forum](https://discuss.gradle.org/t/shadow-plugin-and-multi-release-jars/27753) — libraries (Log4j2 named specifically) ship `module-info.class` inside `META-INF/versions/<N>/` to carry a JPMS descriptor for JDK 9+ while remaining usable pre-9; Shadow now excludes `module-info.class` in multi-release folders **by default** (a behavior change tracked in that issue, i.e. older Shadow versions leaked a meaningless module descriptor into the fat jar). Independently, split packages across shaded libraries (`jaxb-impl`/`jaxb-core` cited) break JPMS regardless of the module-info question — shading two libraries that share a package is illegal under the module system even with no descriptor present.

### 15. Signed-jar `SecurityException` on shading
[melix/jmh-gradle-plugin#5](https://github.com/melix/jmh-gradle-plugin/issues/5), [spring-attic/gs-maven#7](https://github.com/spring-attic/gs-maven/issues/7) — shading a signed dependency jar produces `java.lang.SecurityException: Invalid signature file digest for Manifest main attributes` at runtime because the merged class bytes no longer match the original `jarsigner` signature block (`.SF`/`.DSA`/`.RSA`/`.EC` files under `META-INF`). The only correct fix is excluding those signature files from the shaded artifact (Maven Shade: a `<filter>` with `<excludes>META-INF/*.SF</excludes>` etc.; Shadow: `exclude 'META-INF/*.DSA'`/`'META-INF/*.RSA'`) — re-signing the merged jar is not a fix because the signed content itself changed.

### 16. Spring Boot's alternative to shading
[docs.spring.io/spring-boot/reference/packaging/efficient.html](https://docs.spring.io/spring-boot/reference/packaging/efficient.html) — Spring Boot's executable jar nests dependency jars intact under `BOOT-INF/lib/`, application classes under `BOOT-INF/classes/`, with a custom `MANIFEST.MF` and its own classloader (`org.springframework.boot.loader`) — explicitly *not* a Shade/Shadow merge, so no ServiceLoader/signature/module-info failure modes apply. Documented cost: a small nested-jar classloading startup penalty, erasable in production via `java -Djarmode=tools -jar app.jar extract` followed by running the extracted, exploded layout — "after startup, you should not expect any differences in execution time between running an executable jar and running an extracted jar." Layered jars and Cloud Native Buildpacks are the documented path to Docker-layer-cache-friendly images without ever shading.

### 17. Maven Enforcer rules
[maven.apache.org/enforcer/enforcer-rules](https://maven.apache.org/enforcer/enforcer-rules/index.html) — the mechanical-check surface Maven offers in place of Gradle's locking/resolutionStrategy: `dependencyConvergence`, `requireUpperBoundDeps` (transitive resolves to its declared version or higher), `requireSameVersions`, `bannedDependencies`, `banDynamicVersions` (blocks version ranges, `RELEASE`/`LATEST`, and SNAPSHOT), `banTransitiveDependencies`, `banDependencyManagementScope`, `banDuplicatePomDependencyVersions`, `requireReleaseDeps`/`requireReleaseVersion` (no SNAPSHOT in a release build). None are enabled by default — a Maven project with no `maven-enforcer-plugin` binding in its `pluginManagement` has zero mechanical protection against any of these.

### 18. Maven 4 migration
[maven.apache.org/guides/mini/guide-migration-to-mvn4.html](https://maven.apache.org/guides/mini/guide-migration-to-mvn4.html) and [maven.apache.org/whatsnewinmaven4.html](https://maven.apache.org/whatsnewinmaven4.html) — Maven 4 introduces POM model version `4.1.0` (backward compatible with `4.0.0`; most existing POMs need no change), ships a built-in migration tool (`mvnup check` / `mvnup apply` since 4.0.0-rc-4), and the official guidance is explicit: migrate to the Maven 4 *tool* first without adopting model-version-4.1.0-only features, then adopt new POM features separately. Third-party plugin compatibility is flagged as the remaining long pole.

### 19. `rules_jvm_external` pinning
[bazel-contrib/rules_jvm_external README](https://github.com/bazel-contrib/rules_jvm_external/blob/master/README.md) — `maven_install.json` pins every resolved artifact's SHA-256 for reproducible, offline-capable builds; workflow is `lock_file = "//:maven_install.json"` in the `maven.install()` call, then `REPIN=1 bazel run @maven//:pin` to (re)generate; Bazel fails the build if a `maven.install()` change requires repinning that hasn't happened yet. `strict_visibility` (default `//visibility:private`) forces explicit declaration of direct Maven deps by hiding transitives from unrelated targets. The README does **not** document `unused_deps` or `strict_java_deps` — those live in `rules_java`/Bazel core, not this ruleset, confirming the brief's premise that Java-under-Bazel pain spans two separate rule surfaces.

### 20. Square's configuration-cache migration postmortem
[developer.squareup.com/blog/5-400-hours-a-year-...](https://developer.squareup.com/blog/5-400-hours-a-year-saving-developers-time-and-sanity-with-gradles/) (2022, still the most detailed public account) — projected 5,400 engineer-hours/year saved, builds "eventually" 3x faster; the two named blockers were third-party plugin incompatibility, not Square's own code: Anvil (which Square itself maintains) needed updating, and newer Wire versions were configuration-cache-incompatible, requiring the Foundations team to maintain a fork until upstream caught up. Rollout was opt-in via internal tooling before the plan to flip to default-on with case-by-case opt-out.

### 21. Gradle's own "road to configuration cache" status post
[blog.gradle.org/road-to-configuration-cache](https://blog.gradle.org/road-to-configuration-cache) — stable since 8.1; of the top 50 plugins (Jan–Nov 2024 sample) "over half" declare compatibility; Android Gradle Plugin, Kotlin Gradle Plugin, and Spring Boot's plugin all support it; `maven-publish` "carries a compatibility warning"; Ant integration will ship with a reduced feature set rather than full compatibility; IDE project-file generation (IDEA/Eclipse plugins) is being deprecated in this mode. Gradle 8.10 cut cache size 4x via deduplication (a cited example: 270MB → 65MB); 8.11's parallel configuration caching cut configuration time ~50% on large builds. **Gradle 9.0 makes the cache the "preferred mode of execution"** with default-on for new projects and gentle nudges for existing ones — not yet mandatory, but the direction is explicit and dated.

### 22. Annotation processor on compile classpath deprecation
[Gradle forum, "annotation processors on compile classpath warning in Gradle 4.6"](https://discuss.gradle.org/t/regarding-the-annotation-processors-on-compile-classpath-warning-in-gradle-4-6/26144), [gradle/gradle#5056](https://github.com/gradle/gradle/issues/5056), [gradle/gradle#2300](https://github.com/gradle/gradle/issues/2300) — the fix is declaring processors via the dedicated `annotationProcessor` configuration (separate from `implementation`/`compileOnly`), not relying on Gradle auto-detecting a processor sitting on the ordinary compile classpath; `-proc:none` is the escape hatch for a processor jar that must be on the classpath but should not run. This is old (Gradle 4.6-era, 2018) but the underlying configuration shape (`compileOnly` + `annotationProcessor` as two separate declarations for one library) is still exactly how modern annotation-processor-using libraries (Dagger, MapStruct, Lombok) are declared in the exemplar corpus today.

### 23. Guava's `listenablefuture` empty-artifact trick
[google/guava#7129](https://github.com/google/guava/issues/7129) and the [pom.xml itself](https://github.com/google/guava/blob/master/futures/listenablefuture9999/pom.xml) — `ListenableFuture` was extracted to a standalone `com.google.guava:listenablefuture:1.0` artifact; to avoid duplicate-class conflicts when both standalone and bundled-in-Guava copies land on one classpath, Guava (27.0+) depends on an intentionally-empty `listenablefuture:9999.0-empty-to-avoid-conflict-with-guava` release, relying on highest-version-wins resolution to make Gradle/Maven pick the empty artifact over the real `1.0` whenever full Guava is also present. Documented limitation: build tools or dependency-management setups that don't do highest-wins (or projects pinned to an old Guava) can still hit the class conflict and must exclude/force the artifact manually.

### 24. Jakarta EE namespace migration
[javacodegeeks.com, "Spring Boot 3 and the Move to Jakarta EE"](https://www.javacodegeeks.com/2024/12/spring-boot-3-and-the-move-to-jakarta-ee-what-developers-need-to-know.html) and related — the `javax.*` → `jakarta.*` rename was forced by Oracle retaining the `javax` trademark when Jakarta EE moved to the Eclipse Foundation; every third-party library touching those namespaces (Hibernate, Tomcat, Jetty, Jackson's Jakarta modules) needed a separately-versioned Jakarta artifact before an application dependency graph could move; Spring Boot's managed dependency BOM only auto-upgrades the libraries *it* manages, leaving unmanaged transitive/direct dependencies as a manual audit. Still an active migration tax for legacy codebases moving to Spring Boot 3.x/Jakarta EE 9+ in 2026, not a solved problem.

### 25. JEP 400 and Gradle daemon encoding
[openjdk.org/jeps/400](https://openjdk.org/jeps/400) plus [gradle/gradle#2270](https://github.com/gradle/gradle/issues/2270) — JEP 400 (JDK 18+) makes `UTF-8` the JVM-wide default charset, replacing the old platform-locale-dependent default (notably Windows code pages like `windows-1252`); as a **supported** system property since JDK 18, `file.encoding` may only be `UTF-8` or `COMPAT` (JDK 17-and-earlier behavior) — anything else is undefined. Gradle historically never set `file.encoding` when launching its own daemon, so a daemon on a non-UTF-8-locale Windows host still needs an explicit `org.gradle.jvmargs=-Dfile.encoding=UTF-8` even under a modern JDK, because the daemon JVM's own launch invocation predates any build-script-selected toolchain.

### 26. Java-under-Bazel migration retrospectives
[Wix Engineering, "Migrating to Bazel from Maven or Gradle" series](https://medium.com/wix-engineering/migrating-to-bazel-from-maven-or-gradle-part-5-how-to-avoid-jar-dependency-hell-with-bazel-57d60d0bc9f1) (5-part series, Natan Silnitsky) — covers build-unit granularity trade-offs, CI/remote-execution server choice, monorepo-vs-manyrepo compatibility, and dedicates a full part specifically to avoiding "jar dependency hell" with Bazel; reports ~5x faster clean builds and >10x faster average builds from remote-execution + aggressive caching post-migration from an 800+ microservice Maven backend. Confirms the brief's premise that "migrating a Gradle/Maven multi-module to Bazel" is a real, documented retrospective genre with recurring granularity and dependency-hell themes, though the specific mechanism detail (jar hell root causes) needs a follow-up fetch of Part 5's full text for a rule-writing pass.

### 27. jlink automatic-module and jpackage signing failures
[YouTrack SUPPORT-A-2700, "jlink fails with the automatic module cannot be used with jlink error"](https://youtrack.jetbrains.com/articles/SUPPORT-A-2700/jlink-fails-with-the-automatic-module-cannot-be-used-with-jlink-error), [moditect/moditect#140](https://github.com/moditect/moditect/issues/140) — `jlink` refuses to include an automatic module (a plain, unnamed-module-descriptor jar placed on the module path) in a custom runtime image; the fix is either finding/building a properly-modularized replacement or explicitly excluding the dependency from the jlink'd image and shipping it on the classpath of the resulting image instead. jpackage per-OS signing (notably macOS notarization/entitlements) is a separately-cited, still-live pain point in Apple's own developer forums, confirming this remains an active packaging-shape trade-off, not a solved corner.

### 28. Dependency verification / classloader-conflict cross-reference in flagship-repo review history

## Recent shifts seen in this corpus

- **OSSRH → Central Portal, 2025-06-30**: hard cutover, not a soft deprecation. Any release-runbook rule or skill written against `oss.sonatype.org` is dead on arrival; must target the Central Portal Publisher API/UI. Source: [OSSRH sunset announcement](https://central.sonatype.org/news/20250326_ossrh_sunset/).
- **Isolated Projects: experimental → incubating at Gradle 9.7.0** (2026): this is very recent within the corpus's own timeframe — a rule set written even a few months earlier would have had to caveat IP as "experimental, do not rely on stability." Source: [Isolated Projects docs](https://docs.gradle.org/current/userguide/isolated_projects.html).
- **Configuration cache: stable (8.1) → "preferred mode" at Gradle 9.0**: the framing shifted from "adopt if you can" to "the default path, non-adopters get nudged" — invalidates any older advice treating CC as strictly opt-in/experimental. Source: [Road to CC](https://blog.gradle.org/road-to-configuration-cache).
- **`buildSrc`-as-default → `build-logic`-included-build-as-default for convention plugins**: visible directly in the exemplar corpus's own build-logic column (newer/actively-maintained repos favor `build-logic`+catalog; older/Java-heavy repos still show `buildSrc`). Any rule written from a `buildSrc`-only mental model is already behind current best practice.
- **Shadow's multi-release `module-info.class` exclusion became the default** (tracked via [GradleUp/shadow#729](https://github.com/GradleUp/shadow/issues/729)): pre-fix guidance telling users to manually exclude `module-info.class` from multi-release folders is now redundant for current Shadow versions, though still correct for anyone pinned to an older Shadow release.
- **JEP 400 (JDK 18, 2022) does not retroactively fix Gradle's own daemon encoding**: this is old (2022) at the JDK level but the Gradle-side gap (`file.encoding` never set for the daemon launch) persists into 2026 and is still worth an explicit `org.gradle.jvmargs` line — a case where the *platform* shifted but the *build tool*'s own behavior around it did not follow automatically.
- **Sonatype's 2025/2026 supply-chain reports add an AI-specific data point (28% hallucinated LLM-assisted dependency upgrades)** that did not exist in earlier editions of this report — directly relevant to how this fleet's own agents should validate any dependency version they propose, not just how humans should.

## Contested

- **Fat/shadow jars as best practice vs anti-pattern**: the brief's hypothesis #2 (shadow/fat jars deserve their own best-practice topic) is only half right per this survey — Spring Boot's own docs actively argue *against* shading in favor of nested, unmerged dependency jars, calling out exactly the failure classes (ServiceLoader, signatures, module-info) that shading causes. The more defensible framing for a rule is "shading is a distribution-shape decision with a specific failure taxonomy, not a default," with Spring's nested-jar and jlink/Jib as co-equal alternatives to weigh, not shading as *the* fat-jar answer.
- **`buildSrc` vs included builds**: Gradle's own docs are unambiguous that `buildSrc` invalidation is a real cost, but the exemplar corpus shows plenty of still-actively-maintained, large repos (dagger, grpc-java, spring-boot, kotlinx.coroutines) that have not moved off `buildSrc` — trending toward `build-logic`, but not yet a "this is deprecated" situation; a rule should recommend the newer shape without flagging `buildSrc` itself as broken.
- **Isolated Projects readiness**: Gradle's framing is optimistic-but-honest ("incubating," "APIs may still change"); the open-issue evidence (missing `findProperty` replacement, no clean way to add cross-project dependencies) suggests real production adoption before common escape-hatch APIs land would be premature for most teams — trending toward "worth understanding and instrumenting for, not yet worth hard-gating on."
- **Dependency-verification-metadata bootstrapping as a security control**: Gradle's own docs concede the bootstrap step "trusts whatever is currently in your repositories," which is in tension with treating the resulting file as itself trustworthy without a human diff review — the corpus doesn't resolve this tension, it just documents it; a rule should treat the bootstrap command as scaffolding, the reviewed diff as the actual control.
- **Whether Maven or Gradle deserves more rule-authoring depth** (brief hypothesis #1): this corpus's issue-tracker/GH evidence skews overwhelmingly toward Gradle (richer public issue tracker, more active migration churn around configuration cache/isolated projects/version catalogs) — but that is partly an artifact of Gradle's issue tracker being public and heavily used for feature requests, versus Maven's more plugin-distributed pain surface (Enforcer, Shade, Surefire each have their own trackers). Not fully resolved by this scout; the Maven-specific survey items here (#17, #18, #28) are real but thinner than the Gradle side purely because fewer Maven-specific primary sources were fetched this pass.
