## Summary

- Kotlin 2.4.0 (with 2.4.10 as the current patch, per the Gradle plugin compatibility table) is the shipping stable release as of this research date; K1 compiler support was **fully removed** in 2.4.0 (`-language-version=1.9` is rejected) — "K2 migration" is now a historical topic, not a live one.
- The library-author "API guidelines" set names five pillars — simplicity, readability, predictability, consistency, debuggability — plus testability and backward compatibility, and explicitly tells authors to use **explicit API mode** for every public library module.
- Kotlin's own coding conventions carry a distinct, short "Coding conventions for libraries" section: always specify visibility, always specify return/property types, KDoc every public member — these are the three highest-yield lint rules a fleet could check mechanically.
- Binary compatibility guidance is unusually concrete: adding a default-valued parameter, narrowing *or* widening a return type, and using a `data class` in a public API are each shown breaking bytecode with the exact `NoSuchMethodError` signature that results.
- The standalone `binary-compatibility-validator` Gradle plugin (`apiDump`/`apiCheck`) is now in **maintenance mode**; new binary-compatibility work is going into an experimental `abiValidation {}` block built into the Kotlin Gradle plugin itself (`@OptIn(ExperimentalAbiValidation::class)`, stable in KGP terms since 2.2.0).
- `@JvmOverloads` is explicitly flagged by JetBrains as **not** preserving binary compatibility for Kotlin callers when a published function's default-valued parameters change; the replacement is the still-Experimental `@IntroducedAt` annotation under `@OptIn(ExperimentalVersionOverloading::class)`.
- `-Xjvm-default` is deprecated in favor of a stable `-jvm-default` flag (and a `jvmDefault` Gradle DSL property), whose **default value flipped to `ENABLE`** in Kotlin 2.2.0 — a compatibility-relevant default change, not just a rename.
- Several `-X` flags a Kotlin-JVM rule set might reference by habit are gone from the current compiler-options page as flags: guard conditions, non-local `break`/`continue`, and multi-dollar interpolation went **Stable in 2.2.0** (no `-Xwhen-guards`/`-Xnon-local-break-continue` needed); **context parameters** went Stable in **2.4.0** (no `-Xcontext-parameters` needed).
- JSpecify (`org.jspecify.annotations`) is the only nullability-annotation flavor whose Kotlin compiler default is `strict` (errors); JSR-305 defaults to `warn`; Kotlin 2.4.x's compatibility guide adds "Enforce Jakarta nullability annotations" as a new check.
- Java interop is asymmetric and each annotation solves one distinct problem: `@JvmStatic` (static dispatch), `@JvmName` (erasure clashes), `@JvmField` (expose a backing field), `@JvmOverloads`/`@IntroducedAt` (default-parameter overloads), `@Throws` (checked-exception declarations Java can catch) — a rule that teaches only one of these as "the Java interop annotation" is incomplete.
- The KGP-to-Gradle/AGP compatibility table is versioned and narrow: KGP 2.4.0–2.4.10 supports Gradle 7.6.3–9.5.0 and AGP 8.5.2–9.1.0; a build pinning an old KGP against a new Gradle (or vice versa) is a real, checkable failure mode.
- `jvmTargetValidationMode` defaults to `ERROR` (not `WARNING`) — a Kotlin/Java target mismatch between `compileKotlin` and `compileJava` now fails the build by default.
- Migrating from kapt to KSP is framed as a Gradle "best practice" for build-time reasons (kapt stubs Kotlin to Java and reruns annotation processors on the stubs); the two can coexist per-module during a staged migration.
- Dokka 2 is a from-scratch Gradle-plugin migration (DGP v1 → v2), not a version bump: multi-module aggregation, output directories, and several config options are restructured, not renamed.
- `kotlinx-coroutines-test`'s `runTest` auto-skips `delay()`, times out after **60 seconds** by default, and propagates uncaught child-coroutine exceptions at the end of the test — properties `runBlocking` does not have.
- `Dispatchers.IO`'s thread ceiling defaults to **64 threads or the CPU core count, whichever is larger** (`kotlinx.coroutines.io.parallelism` system property), and `limitedParallelism(n)` on it produces an elastic view that reuses IO's own threads rather than allocating new ones.
- The coding conventions explicitly forbid a public function/property from being initialized with an inferred **platform type** — the Kotlin type must be declared explicitly — which is the single most common silent-NPE seam at a Java/Kotlin boundary.
- "Avoid using the boolean type as an argument" and "avoid using data classes in your API" are both readability/compatibility rules with a named, mechanically-detectable shape (a `Boolean`-typed public parameter; a `data class` with `public`/no explicit visibility modifier).
- Opt-in requirement propagation is opt-out by mistake: if a library's public signature uses an experimental type, the signature itself must also require opt-in, or its own users unknowingly consume an experimental API through it.
- Kotlin 2.4.0 also aligned Maven builds: "Automatic alignment between Java and JVM target versions" for Maven — a JVM-target-mismatch failure mode that used to be Gradle-only guidance now has a Maven-side fix, too.

## Survey

1. **[Coding conventions](https://kotlinlang.org/docs/coding-conventions.html)** — the full style guide: source-file naming (avoid `Util`-style meaningless names; multiplatform files need a `.jvm.kt`/`.android.kt` suffix to dodge JVM's "Duplicate JVM classes" file-facade clash), class/interface-implementation/overload layout order, naming rules (`SCREAMING_SNAKE_CASE` only for `const val`/no-custom-getter top-level `val`s; backtick-quoted test names), four-space indentation with no tabs, a long list of horizontal-whitespace rules ("never put a space around `.` or `?.`"), guard-condition parenthesization, and — the two sections a JVM ruleset most needs — **"Platform types"** ("A public function/method returning an expression of a platform type must declare its Kotlin type explicitly") and **"Coding conventions for libraries"** ("Always explicitly specify member visibility… Always explicitly specify function return types and property types… Provide KDoc comments for all public members").
2. **[Idioms](https://kotlinlang.org/docs/idioms.html)** — 30+ named idioms (DTOs, read-only list/map, lazy property, inline value classes for type-safe IDs, if-not-null shorthand, single-expression functions, `with`/`apply`, Java 7 try-with-resources equivalent, `TODO()`). A checklist of "does this code use the idiomatic form" rather than a rule table.
3. **[Introduction to library authors' guidelines](https://kotlinlang.org/docs/api-guidelines-introduction.html)** — frames the whole API-guidelines set around minimizing mental complexity, backward compatibility, and informative documentation, and states the library's job is first to define its problem domain and meet non-functional criteria (performance, reliability, security, usability) before any style question matters.
4. **[Minimizing mental complexity](https://kotlinlang.org/docs/api-guidelines-minimizing-mental-complexity.html)** — the five-pillar taxonomy (simplicity, readability, consistency, predictability, debuggability) that the next five pages each expand.
5. **[Simplicity](https://kotlinlang.org/docs/api-guidelines-simplicity.html)** — "We recommend using the explicit API mode… With explicit API mode, you must: Add visibility modifiers… Define the types for all your public functions and properties." Also: reuse existing stdlib types (`kotlin.time.Duration`) rather than inventing new ones, and build derived operations (`filter`, `map`) on top of a small core (`transform`) as Kotlin Flows itself does.
6. **[Readability](https://kotlinlang.org/docs/api-guidelines-readability.html)** — "Classes and interfaces should define the core concept of a type. Additional functionality and information should be written as extension functions." "Avoid using the boolean type as an argument… your code should not use boolean types as arguments." Numeric-type guidance: don't use arithmetic types (`Long`) for non-arithmetic entities like IDs; `Byte`/`Float`/`Short` are memory-layout types only; unsigned types (`UByte`/`UShort`/`UInt`/`ULong`) are for full-positive-range or native-interop use, not just "non-negative."
7. **[Predictability](https://kotlinlang.org/docs/api-guidelines-predictability.html)** — "Your library should anticipate the 'happy path' for each use case, and provide default settings accordingly. Users should not need to supply default values." "Avoid exposing mutable state… your API should, whenever possible, accept and/or return read-only collections… If arrays must be used, make defensive copies." Input validation example uses `require(...) { "message" }` with the message naming the actual bad value.
8. **[Consistency](https://kotlinlang.org/docs/api-guidelines-consistency.html)** — parameter-name/order consistency across overloads ("if one of your existing methods has `offset` and `length` parameters, you should not switch to alternatives like `start`/`size`"); "Avoid using exceptions for normal control flow. Design your API to allow for condition checks before attempting operations." "A Kotlin library should also provide a suite of unit and integration tests covering all documented behaviors… Any untested behavior should be assumed to be (at best) unreliable."
9. **[Debuggability](https://kotlinlang.org/docs/api-guidelines-debuggability.html)** — "For every type that contains state, provide a meaningful `toString` implementation" — and explicitly warns that using a `data class` purely to get a free `toString` is not recommended for backward-compatibility reasons (cross-refs item below). "You must adopt and document a consistent approach to exception handling."
10. **[Backward compatibility guidelines for library authors](https://kotlinlang.org/docs/api-guidelines-backward-compatibility.html)** — the densest page. Defines binary/source/behavioral compatibility as three distinct, independently-breakable guarantees. Walks concrete bytecode breaks: adding a default-valued parameter to `fun fib()` produces `NoSuchMethodError: 'int LibKt.fib()'` at the old call site; narrowing `Number` → `Int` return type produces `NoSuchMethodError: 'java.lang.Number Library.demo()'` even though source compiles fine; a `data class` gaining one property changes both the constructor signature and the generated `copy()` signature. Covers the Binary Compatibility Validator (`apiDump`/`apiCheck` tasks, `.api` file in VCS), the new in-KGP `abiValidation` (since KGP 2.2.0), `@IntroducedAt`/`ExperimentalVersionOverloading` vs `@JvmOverloads`, `@PublishedApi` for inline-function internals, annotation-target changes silently redirecting Java-reflection lookups from `field` to `property`, and a `@Deprecated`(`message`, `replaceWith`, `level`) cycle as the sanctioned way to remove an API.
11. **[Testability](https://kotlinlang.org/docs/api-guidelines-testability.html)** — "Your library should not rely on state in global variables or provide stateful top-level functions… tests need to find ways to control these global values." Worked example: replace a top-level `Clock.now()` with an injectable `Clock.System` instance (as `kotlinx-datetime` does).
12. **[Best practices for library authors to create informative documentation](https://kotlinlang.org/docs/api-guidelines-informative-documentation.html)** — "Your library must provide sufficient documentation to let users adopt it with minimum effort." "Every supported API entry point should be documented using KDoc." Also: document lambda parameters explicitly, keep docs self-contained rather than pointing out to an external spec for basic facts.
13. **[Calling Java from Kotlin](https://kotlinlang.org/docs/java-interop.html)** — platform types and their notation, the nullability-annotation flavor list (JetBrains, **JSpecify**, Android, **JSR-305**, FindBugs, Eclipse, Lombok, RxJava3, Vert.x), `-Xnullability-annotations=@<pkg>:<level>` for arbitrary flavors, the **JSpecify support** subsection (`@Nullable`/`@NonNull`/`@NullMarked`/`@NullUnmarked` in `org.jspecify.annotations`, `-Xjspecify-annotations=<strict|warn|ignore>`, default `strict`), and the **JSR-305 support** subsection (`-Xjsr305={strict|warn|ignore}`, `-Xjsr305=under-migration:{...}`, `-Xjsr305=@<fqn>:{...}` for a single annotation, default behavior equal to `warn`).
14. **[Calling Kotlin from Java](https://kotlinlang.org/docs/java-to-kotlin-interop.html)** — `@JvmField` (static field with the property's own visibility), `lateinit`/`const` as the other two ways a property gets a static backing field; `@JvmStatic` generates a real static method on the enclosing class from a companion object (and works on interface companions too) but *doesn't* generate a duplicate instance method for a named `object`; `@JvmName` fixes type-erasure signature clashes and lets a property/getter pair use different JVM names (`@get:JvmName`, `@set:JvmName`); Overloads generation covers both `@IntroducedAt` (Experimental, version-tagged optional parameters, binary-compat-safe) and `@JvmOverloads` (generates one overload per trailing default parameter, cannot be used on abstract/interface methods, and the two annotations conflict with a compiler warning if combined); `@Throws` is required for a Java caller to `catch` a checked exception a Kotlin function throws, since Kotlin itself has no checked exceptions.
15. **[Opt-in requirements](https://kotlinlang.org/docs/opt-in-requirements.html)** — "you must give explicit consent before you can use it in your code." Opt-in is not propagated by default — "others might unknowingly use experimental APIs" — so a library exposing an experimental type in a public signature "must also require opt-in" on that signature. `@SubclassOptInRequired` for inheritance-only gating, distinct from call-site `@RequiresOptIn`.
16. **[K2 compiler migration guide](https://kotlinlang.org/docs/k2-compiler-migration-guide.html)** — smart-cast scope changes (local variables/further scopes, logical-or type checks, inline functions, exception handling, increment/decrement operators), stricter expected/actual visibility rules for KMP, improved null safety for Java primitive arrays, and a changed resolution order for Kotlin properties vs Java fields sharing a name. Historically framed as "how to migrate to K2"; as of Kotlin 2.4.0 this is retrospective — see Recent shifts.
17. **[Kotlin compiler options](https://kotlinlang.org/docs/compiler-reference.html)** — the authoritative current flag list: `-progressive`, `-Werror`/`-Wextra`/`-Xwarning-level=DIAGNOSTIC:level`, `-Xjdk-release=version` (auto-sets `-jvm-target`), `-Xdump-directory`, `-Xjvm-expose-boxed`, `-Xnullability-annotations`, the contract-related `-Xallow-*` flags, `-Xcollection-literals`, `-Xexplicit-context-arguments`. Several flags the wider Kotlin literature still cites by name (`-Xjvm-default`, `-Xwhen-guards`, `-Xnon-local-break-continue`, `-Xcontext-parameters`, `-Xlambdas`, `-Xsam-conversions`, `-Xstring-concat`, `-Xno-param-assertions`, `-Xemit-jvm-type-annotations`) are **absent from this page** — each either stabilized into a non-`-X` flag, became always-on language behavior, or was quietly dropped; see Recent shifts and Candidate topic 14.
18. **[Compiler options in the Kotlin Gradle plugin](https://kotlinlang.org/docs/gradle-compiler-options.html)** — the `compilerOptions {}` DSL at extension/target/compilation-unit level; "Attributes specific to JVM" table: `jvmTarget` (default `"1.8"`, values up to `"26"`), `jvmTargetValidationMode` (`WARNING`/`ERROR`/`IGNORE`, **default `ERROR`**), `jvmDefault` (`ENABLE`/`NO_COMPATIBILITY`/`DISABLE`, **default `ENABLE`**), `javaParameters`, `noJdk`; "Common attributes": `optIn`, `progressiveMode` (default `false`), `extraWarnings` (default `false`); and a migration table mapping the deprecated `-Xjvm-default=all-compatibility|all|disable` values onto the new `jvmDefault.set(JvmDefaultMode.*)` DSL.
19. **[Configure a Gradle project](https://kotlinlang.org/docs/gradle-configure-project.html)** — the **KGP/Gradle/AGP compatibility table** (KGP 2.4.0–2.4.10 → Gradle 7.6.3–9.5.0 / AGP 8.5.2–9.1.0, down through 1.9.20–1.9.25 → Gradle 6.8.3–8.1.1); Gradle Java toolchains support (sets `-jdk-home` and, unless the user overrides it, `compilerOptions.jvmTarget`, to the toolchain's JDK); JPMS configuration requiring a `--patch-module` `CommandLineArgumentProvider` on `compileJava` for mixed Java/Kotlin module sources; dependency-type and kotlin-test JVM-variant guidance.
20. **[Compilation and caches in the Kotlin Gradle plugin](https://kotlinlang.org/docs/gradle-compilation-and-caches.html)** — incremental compilation, Gradle build-cache and configuration-cache support, the Kotlin daemon and its JVM-argument precedence (`kotlin.daemon.jvm.options` system property → `kotlin.daemon.jvmargs` Gradle property → `kotlin{}` extension → specific task, each level able to override the last), rolling back to a previous compiler version, and **Build reports**: `kotlin.build.report.output=file,single_file,http,build_scan,json` (comma-separated, multiple sinks allowed), `kotlin.build.report.json.directory`, `kotlin.build.report.file.output_dir` (default `build/reports/kotlin-build/`).
21. **[Binary compatibility validation in the Kotlin Gradle plugin](https://kotlinlang.org/docs/gradle-binary-compatibility-validation.html)** — the new in-KGP mechanism: `kotlin { @OptIn(ExperimentalAbiValidation::class) abiValidation() }` generates and compares ABI dumps per module, distinct from (and positioned as the successor to) the standalone BCV plugin.
22. **[Gradle best practices](https://kotlinlang.org/docs/gradle-best-practices.html)** — headings only surveyed in depth elsewhere in this program's Gradle scout, but names: Kotlin DSL, version catalogs, convention plugins, local/remote build cache, configuration cache, "Migrate from kapt to KSP" as an *optimization* heading (not a correctness one), modularization, CI/CD setup.
23. **[Getting started with KSP](https://kotlinlang.org/docs/ksp-quickstart.html)** and **[Migrate from kapt to KSP](https://kotlinlang.org/docs/ksp-kapt-migration.html)** — kapt works by "translating Kotlin source code into Java 'stubs' and then running the annotation processors on those stubs," which "significantly increases build time, and loses some Kotlin-specific features." KSP and kapt "can run alongside each other, so you can migrate your project in stages, one library or module at a time." Example pins `id("com.google.devtools.ksp") version "2.3.10"` — current KSP version tracks the Kotlin version it targets.
24. **[Introduction to Dokka](https://kotlinlang.org/docs/dokka-introduction.html)** and **[Migrate to Dokka Gradle plugin v2](https://kotlinlang.org/docs/dokka-migration.html)** — Dokka understands both KDoc and Javadoc comments in mixed-language projects; output formats include its own HTML, Javadoc HTML, GFM, and Jekyll Markdown; libraries using Dokka include kotlinx.coroutines, Ktor, and OkHttp. The v1→v2 migration restructures top-level DSL configuration, visibility settings, source links, multi-module aggregation (with and without convention plugins), and output-directory behavior — not a drop-in version bump.
25. **[Document Kotlin code: KDoc](https://kotlinlang.org/docs/kotlin-doc.html)** — KDoc block tags: `@return`, `@constructor`, `@receiver`, `@author`, `@since`, `@suppress`, plus inline linking syntax.
26. **[Coroutines guide](https://kotlinlang.org/docs/coroutines-guide.html)** and its sub-pages — table of contents matches the frame's expectation exactly: basics, cancellation and timeouts, flows, channels, [coroutine context and dispatchers](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html) (dispatcher/thread debugging, parental responsibilities, thread-local data in a coroutine context), [coroutine exception handling](https://kotlinlang.org/docs/exception-handling.html) (`CoroutineExceptionHandler`, supervision jobs/scopes), and [shared mutable state and concurrency](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html) ("Volatiles are of no help" for compound operations; thread-confinement fine- vs coarse-grained; mutual exclusion via `Mutex`).
27. **[kotlinx-coroutines-test README](https://github.com/Kotlin/kotlinx.coroutines/blob/master/kotlinx-coroutines-test/README.md)** — `runTest` auto-skips `delay()`, **times out after 60 seconds by default** (overridable via `runTest(timeout = ...)`), and propagates uncaught child-coroutine exceptions at the end of the test; `Dispatchers.setMain`/`resetMain` for main-dispatcher substitution; `StandardTestDispatcher` (linked to a shared `TestCoroutineScheduler`, virtual time) vs `UnconfinedTestDispatcher` (behaves like `Dispatchers.Unconfined`); current published version `1.11.0`.
28. **`Dispatchers.IO`'s own KDoc / the kotlinx.coroutines API docs** — default parallelism ceiling is 64 threads or the CPU core count (whichever is larger), governed by the `kotlinx.coroutines.io.parallelism` system property; `Dispatchers.IO.limitedParallelism(n)` produces an elastic view reusing IO's own thread pool rather than allocating dedicated threads, so several `limitedParallelism` views can coexist without linearly summing thread counts under steady load.
29. **[binary-compatibility-validator README](https://github.com/Kotlin/binary-compatibility-validator/blob/master/README.md)** — states up front: **"This plugin is in maintenance mode… The implementation of new features has been stopped in favor of adding them to the experimental binary compatibility validation in the Kotlin Gradle plugin."** Defines `apiDump` (writes a human-readable `.api` file) and `apiCheck` (compares current compiled classes to the checked-in `.api` file, wired into Gradle's `check` task), plus experimental KLib ABI validation for multiplatform.
30. **[kotlinx.serialization guide](https://github.com/Kotlin/kotlinx.serialization/blob/master/docs/serialization-guide.md)** — surveyed only as far as it reinforces library-API conventions: constructor-property requirement for `@Serializable` classes, "defaults are not encoded by default," and explicit handling of nullable/optional/transient/required properties as first-class annotated states rather than ad hoc nullability.
31. **[Kotlin language specification — chapter list](https://kotlinlang.org/spec/introduction.html)** — Introduction, Syntax and grammar, Type system, Built-in types and their semantics, Declarations, Inheritance, Scopes and identifiers, Statements, Expressions, Operator overloading, Packages and imports, Overload resolution, Control- and data-flow analysis, Kotlin type constraints, Type inference, Runtime type information, Exceptions, Annotations, Asynchronous programming with coroutines, Concurrency. Useful as the ground-truth vocabulary for terms a rule set uses loosely (e.g. "platform type," "smart cast," "flexible type").
32. **Books, surveyed as tables of contents only**: *Effective Kotlin* (Marcin Moskała) — item-numbered, organized under Part 1 "Good code" (Safety, Readability) and Part 2 "Code design" (Reusability, Abstraction design, Object creation, Class design); *Kotlin Coroutines: Deep Dive* (2nd ed.) — four parts (Understanding Coroutines; the coroutines library including Dispatchers, cancellation, exception handling, and "Testing Kotlin Coroutines"; Channel and Flow including "SharedFlow and StateFlow" and "Testing flow"; Coroutines in practice / Best practices); *Kotlin in Action*, 2nd ed. — Part 3 devotes five full chapters to coroutines/flows/structured concurrency/error-handling-and-testing, and Appendix A/B/C cover "Building Kotlin projects," "Documenting Kotlin code," and "The Kotlin ecosystem" respectively.

## Recent shifts seen in this corpus

- **Kotlin 2.4.0 removes K1 entirely** (`-language-version=1.9` rejected) — as of this release, the "K2 compiler migration guide" describes a completed, historical transition, not a live decision. (Kotlin 2.4.0, per [whatsnew24.html](https://kotlinlang.org/docs/whatsnew24.html); K2 itself went Stable in **2.0.0**, released **May 21, 2024**.)
- **Context parameters** went from Experimental preview (`-Xcontext-parameters`, introduced **2.2.0**, released June 23, 2025) to **Stable in 2.4.0** — invalidates any rule text that still tells authors to pass the compiler flag.
- **Guard conditions, non-local `break`/`continue`, and multi-dollar string interpolation** went from preview (`-Xwhen-guards` etc., introduced **2.1.0**, Nov 27 2024) to **Stable in 2.2.0** — same invalidation pattern, one release earlier.
- **`-Xjvm-default` is deprecated**, replaced by a stable `-jvm-default` flag and a `jvmDefault` Gradle DSL property, and **the default value itself flipped to `ENABLE`** in **2.2.0** ("Changes to default method generation for interface functions") — a behavior change, not just a naming change, that predates a specific check for it in any old ruleset.
- **Binary compatibility validation is moving from a standalone plugin into the Kotlin Gradle plugin itself**: the `Kotlin/binary-compatibility-validator` GitHub plugin declared itself "in maintenance mode" with new-feature work redirected to the experimental in-KGP `abiValidation {}` block, available since **KGP 2.2.0**. A rule authored before this split will point at the wrong tool for a greenfield SDK.
- **`@JvmOverloads` was demoted from "the" binary-compat overload mechanism to "does not preserve binary compatibility for Kotlin callers"**, with `@IntroducedAt`/`ExperimentalVersionOverloading` positioned as the replacement — but that replacement is still Experimental as of this corpus, so no non-experimental mechanism fully solves this problem yet.
- **Kotlin/JVM Java-version support tracks LTS releases closely**: Java 25 support landed in Kotlin **2.3.0** (Dec 16, 2025); Java 26 support landed in Kotlin **2.4.0**. A rule pinning "Kotlin supports up through Java N" needs a version-keyed table, not a single number.
- **Maven gained automatic Java/JVM-target alignment in Kotlin 2.4.0** — a target-mismatch failure mode previously requiring manual Gradle-side (`jvmTargetValidationMode`) attention now has a Maven-side automatic fix, narrowing (but not eliminating) the topic's Gradle-only framing.
- **`jvmTargetValidationMode` defaults to `ERROR`**, not `WARNING` — any rule assuming a soft warning on Kotlin/Java target mismatch is describing behavior the current KGP no longer has by default.
- **JSpecify enforcement tightened further in 2.4.x**: the compatibility guide for 2.4.x adds "Enforce Jakarta nullability annotations" as a new check, alongside JSpecify's pre-existing `strict`-by-default posture — nullability-annotation support keeps expanding release over release, so a rule enumerating "the" supported flavor list needs a version caveat.
- **kapt→KSP migration is now framed purely as a build-performance optimization** in the official Gradle best-practices guide, not a correctness fix — a rule justifying the migration on correctness grounds is overstating the official rationale.

## Contested

- **Standalone BCV plugin vs in-KGP `abiValidation`**: the standalone plugin's own README calls itself maintenance-only and points at the KGP feature, but that KGP feature requires an explicit `@OptIn(ExperimentalAbiValidation::class)` as of this corpus — meaning the "recommended" path is still experimental while the "legacy" path is what nearly every existing library (per the exemplar corpus) actually runs today. Trending toward the in-KGP mechanism, but not there yet for a rule that must recommend something stable right now.
- **`@JvmOverloads` vs `@IntroducedAt`**: JetBrains' own guidance flags the older annotation as broken for exactly the case (binary-compat-safe optional parameters) it's most commonly reached for, but its replacement is Experimental. A rule recommending "the" annotation to use has to either accept an experimental opt-in or accept the known compatibility gap — this is unresolved in the corpus itself, not just under-documented.
- **Explicit API mode as a default vs an opt-in**: the API guidelines page recommends it unconditionally for library authors, but it's a project-level Gradle DSL toggle (`explicitApi()`), off by default, and (per the frame's separate audit workstream) likely absent from most of the exemplar corpus in practice — the gap between "recommended" and "actually enabled" is the live tension here, not a documentation disagreement.
- **KSP1 vs KSP2**: the fetched pages assume a single current KSP without stating definitively whether the KSP2 (K2-based) implementation is now the sole supported processing backend or whether a legacy path persists for laggard processors — flagged as partial coverage in the candidate table pending a dedicated fetch of `ksp-overview.html`'s supported-libraries and KSP2 status sections.
- **Context receivers vs context parameters**: `-Xcontext-receivers` (older, still mentioned in the Gradle compiler-options examples as of this corpus) and context parameters (the Stable-since-2.4.0 successor) cannot both be enabled at once per the docs, but the corpus doesn't state a deprecation timeline for context receivers — unclear whether existing `-Xcontext-receivers` usage in the exemplar corpus is now stale advice or still a live, supported choice.
