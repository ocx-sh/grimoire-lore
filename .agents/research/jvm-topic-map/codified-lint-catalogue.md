## Summary

- Error Prone ships 650 bug patterns today (measured from the `bugpattern/*.md` docs generated straight from the `@BugPattern` annotations); the authoritative enabled/disabled split lives in `BuiltInCheckerSuppliers.java`, not in the docs: 187 `ENABLED_ERRORS`, 312 `ENABLED_WARNINGS`, 150 `DISABLED_CHECKS` — a check being "WARNING severity" in the docs does not mean it runs by default, `DISABLED_CHECKS` is a separate opt-in list.
- Worth turning on from `DISABLED_CHECKS`: `DefaultLocale`, `EqualsMissingNullable`, `FieldMissingNullable`, `CatchingUnchecked`, `ConstantPatternCompile`, `UnnecessaryDefaultInEnumSwitch`, `FieldCanBeFinal`/`FieldCanBeStatic` — every one of these fires on code an LLM writes routinely (locale-naive string ops, missing `@Nullable` on equals-adjacent APIs, swallowed-then-rethrown `Exception`).
- NullAway's `AnnotatedPackages` vs `OnlyNullMarked` (0.12.3+) are mutually exclusive entry points, and `JSpecifyMode=true` is still separate from `JSpecifyExperimental=true` (JDK nullness models, wildcard inference, generic-inference warnings) — the wiki says explicitly these will merge into the default "in a future release," meaning any rule authored today should assume this is a moving target through 2026.
- NullAway's `JSpecifyMode` requires JDK 22+ or `-XDaddTypeAnnotationsToSymbol=true` on JDK 17.0.19+/21.0.8+, and fails the build with an `IllegalStateException` otherwise — a Gradle toolchain pinned below those patch versions silently breaks nullness checking, not just misses features.
- Checkstyle ships 230 standard checks across 15 categories (`coding` 67, `javadoc` 34, `naming` 22, `whitespace` 20, `misc` 20, `imports` 11, `sizes`/`design`/`annotation` 10 each, `metrics`/`blocks` 6, `regexp`/`modifier` 5, `header` 3); `google_checks.xml` enables 89 modules and `sun_checks.xml` enables 73, and the sets diverge sharply — `google_checks.xml` turns on `EmptyCatchBlock`, `MissingOverrideOnRecordAccessor`, `SuppressWarningsHolder`; `sun_checks.xml` alone turns on `MagicNumber`, `HiddenField`, `VisibilityModifier`, `DesignForExtension` — picking one as a starting ruleset is not cosmetic.
- PMD's Java ruleset (measured from `category/java/*.xml`, the real rule source since the docs' per-language markdown files no longer exist in the same layout) has 315 non-deprecated rules: `errorprone` 99, `bestpractices` 69, `codestyle` 63, `design` 44, `performance` 25, `multithreading` 12, `security` 2, `documentation` 6; only 18 rules carry PMD's own priority 1 ("Change absolutely required"), 248 sit at priority 3.
- SpotBugs defines 519 distinct `BugPattern` entries and 164 `BugCode` abbreviations (measured from `etc/messages.xml`) grouped into 10 categories: `CORRECTNESS`, `BAD_PRACTICE`, `STYLE`, `PERFORMANCE`, `SECURITY`, `MALICIOUS_CODE`, `MT_CORRECTNESS`, `I18N`, `EXPERIMENTAL`, `NOISE`.
- detekt's shipped `default-detekt-config.yml` defines 231 rules across 10 rule sets, with only 129 active out of the box; `naming` is the largest active set (13/21), `standard-library` and `potential-bugs` sit near 60% active, `comments` ships with 0/10 active. The `formatting`, `libraries` and `ruleauthors` rule sets are not present in the default config at all — they require explicit opt-in dependencies.
- detekt 2.0 (alpha since 2025-09, at alpha.6 as of 2026-08-04, built against Kotlin 2.4.10 / Gradle 9.6.1 / JDK 25) renamed the `:detekt-formatting` module to `:detekt-rules-ktlint-wrapper` (package `dev.detekt.rules.ktlintwrapper`), and that wrapper now targets JVM 17 in preparation for ktlint's own next major requiring JVM 17+ — a rule authored against detekt 1.x formatting config will need updating.
- ktlint's `standard` rule set has 55 documented rules and `experimental` has at least 8 more (`Blank line before file annotation`, `Call expression wrapping`, `KDoc delimiter`, `Lambda return`, etc.); 62 distinct `ktlint_*`/`ij_kotlin_*` `.editorconfig` properties are referenced across the standard docs.
- Kotlin 2.1+ added `-Wextra` / `extraWarnings` (Gradle: `kotlin { compilerOptions { extraWarnings.set(true) } }`), currently Experimental, surfacing checks like `CAN_BE_VAL`, `USELESS_CALL_ON_NOT_NULL`, `UNREACHABLE_CODE`, `ASSIGNED_VALUE_IS_NEVER_READ` that plain compilation does not warn on; `-Xsuppress-warning=NAME` lets a project silence one warning ID globally but explicitly cannot silence an error.
- `javac -Xlint` on JDK 25 has 40 keys (including `none`/`all`); several are version-specific and easy to miss: `this-escape` (constructors leaking `this`), `dangling-doc-comments`, `restricted` (JEP restricted-method calls), `missing-explicit-ctor`, `output-file-clash` — none of these existed in the JDK 8-era `-Xlint` list most LLM training data reflects.
- SonarJava's rule metadata (measured from `sonar-java-plugin/.../rules/java/*.json`, 501 rules read at fetch time) breaks down as 340 `CODE_SMELL`, 107 `BUG`, 42 `VULNERABILITY`, with severities `Blocker` 29, `Critical` 86, `Major` 199, `Minor` 170, `Info` 5; 46 rules are simultaneously (`BUG`|`VULNERABILITY`) and (`Blocker`|`Critical`) — that intersection is the closest thing to "rules that should always gate CI."
- The SEI CERT Oracle Coding Standard for Java has moved off Confluence entirely to `cmu-sei.github.io/secure-coding-standards` (the old wiki URL 301-redirects); it defines 19 rule categories totalling roughly 174 numbered rules, weighted toward `FIO` (16, I/O), `NUM` (14, numeric), `OBJ` (14, object orientation), `MET` (13, methods) and `SER` (12, serialization) — serialization and I/O path handling are where CERT invests the most rule count, which lines up with where OWASP's cheat sheets also concentrate (Deserialization, XXE).
- Gradle's own Best Practices docs (5 pages, all `.adoc` under `userguide/best-practices/`) contain 31 named, quotable Do/Don't items — 9 general, 8 dependency, 4 performance, 5 security, 5 structuring — each with an explicit title ("Don't Explicitly Depend on the Kotlin Standard Library," "Always Declare Attributes on Consumable and Resolvable Configurations," "Do not use `gradle.properties` in subprojects") that maps almost one-to-one onto a checkable rule.
- Gradle's `validation_problems.adoc` — the source for `validatePlugins`/task-validation diagnostics — now lives under a path literally named `unused/` in `gradle/gradle`, a signal the page itself may be superseded by inline Problems-API reporting; it still enumerates 31 distinct problem IDs (`missing_annotation`, `implicit_dependency`, `cannot_write_output`, `unsupported_notation`, etc.) worth treating as a checklist even if the doc's home is in flux.
- Maven Enforcer ships roughly 35 built-in rules as of enforcer-rules 3.6.3 (2026-05-15); the ones that catch supply-chain and reproducibility problems specifically are `banDynamicVersions`, `banDuplicatePomDependencyVersions`, `dependencyConvergence`, `requireUpperBoundDeps`, and `reactorModuleConvergence` — none of these are on by default in a fresh POM, all require explicit `<execution>` wiring.
- `dependency-analysis-gradle-plugin`'s `projectHealth` task reports four categories of dependency-declaration mistakes (unused, used-but-transitive, wrong-configuration `api`/`implementation`/`compileOnly`, unused annotation processors) plus plugin-level advice (Kotlin/Android plugin applied but unused); `fixDependencies --upgrade` is explicitly the "safe" auto-remediation mode that never removes or downgrades a declaration, only adds/upgrades.
- Central Portal publishing (the only path since OSSRH's 2025-06-30 sunset, confirmed against `central.sonatype.org/publish/requirements/`) requires, per artifact: javadoc jar, sources jar, a GPG/PGP signature per file, checksums, and a POM carrying name/description/URL, license, developer, and SCM blocks — none of these are enforced by Gradle or Maven themselves; they are enforced by the Portal's validation gate on upload.
- Reproducible-builds.org's JVM guidance is narrow but concrete: jar entry timestamps are the primary non-determinism source, `Properties.store()` always writes a timestamp comment, and Gradle's fix since v3.4 is `isPreserveFileTimestamps = false` + `isReproducibleFileOrder = true` on every `AbstractArchiveTask`; Maven's is `project.build.outputTimestamp`. Locale/charset (`file.encoding`, `user.language`, `user.country`) must also be pinned for JDK ≤17 (JDK 18+ defaults `file.encoding` to UTF-8).

## Survey

### 1. Error Prone bug patterns — [errorprone.info/bugpatterns](https://errorprone.info/bugpatterns), sourced from [google/error-prone `gh-pages:bugpattern/*.md`](https://github.com/google/error-prone/tree/gh-pages/bugpattern) and [`core/.../scanner/BuiltInCheckerSuppliers.java`](https://github.com/google/error-prone/blob/master/core/src/main/java/com/google/errorprone/scanner/BuiltInCheckerSuppliers.java)

Each bug pattern's page is generated straight from its `@BugPattern` annotation (`title`, `summary`, `severity` ∈ {`ERROR`,`WARNING`,`SUGGESTION`}, `tags`). Parsing all 650 pages: 211 `ERROR`, 389 `WARNING`, 50 `SUGGESTION` by declared severity. But declared severity is not the same as "runs by default" — `BuiltInCheckerSuppliers.java` defines three disjoint sets fed by `getSuppliers(...)`: `ENABLED_ERRORS` (187 checkers), `ENABLED_WARNINGS` (312), `DISABLED_CHECKS` (150, e.g. `AssertFalse`, `BooleanParameter`, `CatchingUnchecked`, `ConstantPatternCompile`, `DefaultLocale`, `EqualsMissingNullable`, `FieldMissingNullable`, `FieldCanBeFinal`, `FieldCanBeStatic`, `UnnecessaryDefaultInEnumSwitch`, `UnnecessaryStaticImport`, `Varifier`). A `DISABLED_CHECKS` member needs `-Xep:CheckName:WARN` or `:ERROR` to activate; it never fires on a stock `-Xep:...` -free invocation. The `BugPattern` annotation itself (`api/latest/.../BugPattern.html`) exposes `disableable`, `altNames`, `tags`, `suppressionAnnotations`, `documentSuppression` as the knobs a custom check or a build can use.

### 2. NullAway configuration and JSpecify mode — [github.com/uber/NullAway/wiki/Configuration](https://github.com/uber/NullAway/wiki/Configuration), [.../wiki/JSpecify-Support](https://github.com/uber/NullAway/wiki/JSpecify-Support)

42 distinct `-XepOpt:NullAway:*` flags exist (`AnnotatedPackages`, `OnlyNullMarked`, `UnannotatedSubPackages`, `UnannotatedClasses`, `ExcludedClassAnnotations`, `CheckOptionalEmptiness`, `HandleTestAssertionLibraries`, `JarInferEnabled`, `JSpecifyMode`, `JSpecifyExperimental`, `JSpecifyJDKModels`, `HandleWildcardGenerics`, `WarnOnGenericInferenceFailure`, `CustomContractAnnotations`, `SerializeFixMetadata`, …). Before 0.12.3 `AnnotatedPackages` was mandatory; 0.12.3+ accepts `OnlyNullMarked=true` instead, and the two are mutually exclusive — passing neither crashes the build immediately with an explicit "DO NOT report an issue to Error Prone for this crash" message. JSpecify support: `JSpecifyMode=true` checks "full JSpecify semantics... including generic types" but is "still under development"; `JSpecifyExperimental=true` (alongside `JSpecifyMode`) additionally turns on JDK nullness models from `jspecify/jdk`, wildcard-generic checking, and generic-inference-failure warnings — the wiki states NullAway intends to flip `JSpecifyExperimental` on by default "in a future release." Guava 33.4.1+ ships `@NullMarked` on most packages, so NullAway checks Guava call sites more strictly regardless of whether the consuming project runs in JSpecify mode. Two newer, off-by-default Error-Prone-style checkers ship inside NullAway itself: `RequireExplicitNullMarking` (flags a top-level class with no `@NullMarked`/`@NullUnmarked` anywhere in class/package/module — SUGGESTION severity by default, meaning silent unless explicitly raised) and `JSpecifyUnrecognizedAnnotationLocation` (flags `@Nullable`/`@NonNull` on a JSpecify-unrecognized location such as a primitive type or a cast's root type, 19 named locations, one config flag `CheckLocalVariableRootType`).

### 3. Checkstyle's check index and shipped rulesets — [checkstyle.org/checks.html](https://checkstyle.org/checks.html) (source: [`src/site/xdoc/checks.xml`](https://github.com/checkstyle/checkstyle/blob/master/src/site/xdoc/checks.xml)), [`google_checks.xml`](https://github.com/checkstyle/checkstyle/blob/master/src/main/resources/google_checks.xml), [`sun_checks.xml`](https://github.com/checkstyle/checkstyle/blob/master/src/main/resources/sun_checks.xml)

230 standard checks, grouped by their doc path into 15 categories: `coding` (67), `javadoc` (34), `naming` (22), `whitespace` (20), `misc` (20), `imports` (11), `sizes` (10), `design` (10), `annotation` (10), `metrics` (6), `blocks` (6), `regexp` (5), `modifier` (5), `header` (3), `modules` (1, `SuppressionCommentFilter`'s parent). `google_checks.xml` enables 89 modules, `sun_checks.xml` enables 73; the sets diverge substantially rather than one being a subset of the other — Google-only: `AbbreviationAsWordInName`, `AnnotationLocation`, `EmptyCatchBlock`, `Indentation`, `JavadocParagraph`, `MissingOverrideOnRecordAccessor`, `OneTopLevelClass`, `SuppressWarningsHolder`, `TextBlockGoogleStyleFormatting`; Sun-only: `AvoidNestedBlocks`, `ConstantName`, `DesignForExtension`, `HiddenField`, `MagicNumber`, `MemberName`, `RedundantModifier`, `VisibilityModifier`. A project starting from `sun_checks.xml` gets stricter design/visibility checks; one starting from `google_checks.xml` gets stricter Javadoc/annotation/indentation checks and modern-syntax awareness (records, text blocks).

### 4. PMD's Java rule catalogue — [pmd.github.io/pmd/pmd_rules_java.html](https://pmd.github.io/pmd/pmd_rules_java.html) (source: [`pmd-java/src/main/resources/category/java/*.xml`](https://github.com/pmd/pmd/tree/main/pmd-java/src/main/resources/category/java), [`.../rulesets/java/quickstart.xml`](https://github.com/pmd/pmd/blob/main/pmd-java/src/main/resources/rulesets/java/quickstart.xml))

PMD 7 moved rule *definitions* to `category/java/*.xml`; the old per-category `docs/pages/pmd/rules/java/*.md` files from PMD 6-era docs no longer exist at that path (a stale copy under `pmd-doc/src/test/resources` is a test fixture, not the live doc). Parsed rule counts by category: `errorprone` 99, `bestpractices` 69, `codestyle` 63, `design` 44, `performance` 25, `multithreading` 12, `documentation` 6, `security` 2 (PMD leaves most Java security coverage to SpotBugs/find-sec-bugs and SonarJava). Priority distribution across all 315 non-deprecated rules: priority 1 ("Change absolutely required, an error will occur otherwise") — 18 rules; priority 2 — 19; priority 3 (default working set) — 248; priority 4 — 21; priority 5 — 1; 16 rules are `deprecated="true"` in-tree. `quickstart.xml` is a curated ruleset reference rather than an inline rule list — it composes named rules from the category files by reference (351 lines of `<rule ref=".../category/java/....xml/RuleName"/>` entries), confirming "quickstart" is PMD's own opinionated subset, not "everything."

### 5. SpotBugs bug patterns — [spotbugs.readthedocs.io/en/latest/bugDescriptions.html](https://spotbugs.readthedocs.io/en/latest/bugDescriptions.html) (source: [`spotbugs/etc/messages.xml`](https://github.com/spotbugs/spotbugs/blob/master/spotbugs/etc/messages.xml))

The published RST doc (`docs/bugDescriptions.rst`) is a stub that `.. include::`s a build-generated file; the real machine-readable source is `messages.xml`, which defines 519 `<BugPattern>` elements, 164 `<BugCode>` short codes, and 10 `<Category>` values: `CORRECTNESS`, `BAD_PRACTICE`, `STYLE`, `MT_CORRECTNESS` (multithreading), `PERFORMANCE`, `SECURITY`, `MALICIOUS_CODE`, `I18N`, `EXPERIMENTAL`, `NOISE`. The `SECURITY` category is deliberately narrow in core SpotBugs — the `find-sec-bugs` plugin exists specifically to extend it with OWASP-Top-10-shaped patterns (SQL/LDAP/XPath injection, weak crypto, path traversal, SSRF) that core SpotBugs does not attempt.

### 6. detekt's rule sets and default activation — [detekt.dev/docs/rules/](https://detekt.dev/docs/rules/) (source: [`detekt-core/src/main/resources/default-detekt-config.yml`](https://github.com/detekt/detekt/blob/main/detekt-core/src/main/resources/default-detekt-config.yml))

The shipped default config is itself the machine-readable index: 10 top-level rule sets — `comments` (10 rules, 0 active), `complexity` (13, 7 active), `coroutines` (9, 4 active), `empty-blocks` (15, 15 active — every empty-block rule is on), `exceptions` (15, 13 active), `naming` (21, 13 active), `performance` (5, 2 active), `potential-bugs` (32, 18 active), `standard-library` (33, 19 active), `style` (78, 38 active) — 231 rules total, 129 active by default. `formatting`, `libraries`, and `ruleauthors` rule sets are absent from this file entirely; they ship as separate modules/dependencies and require explicit `detektPlugins(...)` wiring plus a config block to activate. detekt 2.0 (alpha since 2025-09-04, alpha.6 as of 2026-08-04) renamed the formatting module `:detekt-formatting` → `:detekt-rules-ktlint-wrapper` (package `dev.detekt.rules.ktlintwrapper`, [PR #8474](https://github.com/detekt/detekt/pull/8474)) — an explicit admission that detekt's formatting rule set is a ktlint wrapper, not an independent implementation.

### 7. ktlint's standard and experimental rules — [pinterest.github.io/ktlint/latest/rules/standard/](https://pinterest.github.io/ktlint/latest/rules/standard/) and [.../experimental/](https://pinterest.github.io/ktlint/latest/rules/experimental/) (source: [`documentation/snapshot/docs/rules/standard.md`](https://github.com/pinterest/ktlint/blob/master/documentation/snapshot/docs/rules/standard.md), `experimental.md`)

55 `##`-level rule sections in `standard.md` (annotation formatting, blank-line rules, chain-method wrapping, class signature, enum entry, KDoc, naming, spacing — the doc groups many spacing sub-rules under one `## Spacing` heading with sub-cases, but the rule-ID surface itself is 55 named rules); `experimental.md` documents at least 8 more (blank line before file annotation/imports/package, call-expression wrapping, expression-operand wrapping, KDoc delimiter, lambda return, no-blank-line-at-start-of-file). 62 distinct `.editorconfig` property names are referenced across the standard doc (`ktlint_code_style`, `ktlint_official`, `ktlint_ignore_back_ticked_identifier`, `ktlint_standard_<rule>` per-rule toggles, plus several `ktlint_*_ignore_when_*` and `*_force_multiline_when_*_greater_or_equal_than` tunables) — ktlint's primary configuration surface is `.editorconfig`, not a Kotlin/YAML config file.

### 8. Kotlin compiler warnings, `-Wextra`, `-Xsuppress-warning` — [kotlinlang.org/docs/whatsnew21.html](https://kotlinlang.org/docs/whatsnew21.html)

Kotlin 2.1 introduced `-Wextra` (Gradle: `kotlin { compilerOptions { extraWarnings.set(true) } }`), an Experimental opt-in bundle of additional warnings not raised by default compilation: `REDUNDANT_NULLABLE`, `PLATFORM_CLASS_MAPPED_TO_KOTLIN`, `ARRAY_EQUALITY_OPERATOR_CAN_BE_REPLACED_WITH_EQUALS`, `REDUNDANT_CALL_OF_CONVERSION_METHOD`, `USELESS_CALL_ON_NOT_NULL`, `CAN_BE_VAL`, `ASSIGNED_VALUE_IS_NEVER_READ`, `UNREACHABLE_CODE`. Separately, `-Xsuppress-warning=WARNING_NAME` lets a build silence one named warning globally (via `freeCompilerArgs`); an unknown warning name is itself a compile error, and errors — as opposed to warnings — cannot be suppressed this way.

### 9. `javac -Xlint` categories — [docs.oracle.com javac(1) for JDK 25](https://docs.oracle.com/en/java/javase/25/docs/specs/man/javac.html)

40 keys including `all`/`none`. Post-Java-8 additions relevant to code an LLM is likely to write unaware of: `this-escape` (constructor leaks `this` before subclass init — added Java 21), `dangling-doc-comments` (misplaced Javadoc), `restricted` (JEP restricted native/FFM method calls), `missing-explicit-ctor`, `output-file-clash`, `incubating`, `identity`/`synchronization` (value-based-class misuse, relevant with Integer/Long caching and upcoming value classes), `lossy-conversions` (compound-assignment narrowing). `serial` (missing `serialVersionUID`), `rawtypes`, `unchecked`, `deprecation`, `removal`, `preview`, `exports`/`opens`/`module`/`requires-automatic`/`requires-transitive-automatic` round out the module-system and generics-era warnings.

### 10. SonarJava rule metadata — [rules.sonarsource.com/java/](https://rules.sonarsource.com/java/) (source: [`sonar-java-plugin/src/main/resources/org/sonar/l10n/java/rules/java/*.json`](https://github.com/SonarSource/sonar-java/tree/master/sonar-java-plugin/src/main/resources/org/sonar/l10n/java/rules/java))

The live site is a JS-rendered rule browser; its data comes straight from per-rule JSON metadata in the `sonar-java` repo (`title`, `type` ∈ {`BUG`,`VULNERABILITY`,`CODE_SMELL`}, `defaultSeverity`, `code.impacts`, `tags`). Of 501 rule files retrievable at fetch time: 340 `CODE_SMELL`, 107 `BUG`, 42 `VULNERABILITY`; severities `Blocker` 29, `Critical` 86, `Major` 199, `Minor` 170, `Info` 5. 46 rules are both a `BUG`/`VULNERABILITY` and `Blocker`/`Critical` — including `S2168`/`S2168` double-checked-locking misuse, `S2695` invalid JDBC index, `S4830`/`S5527` unverified SSL/TLS certs and hostnames, `S4544` unsafe Jackson deserialization config, `S5344` plaintext/fast-hashed passwords, `S2053` unsalted password hashing, `S4790` weak hashing, `S2115` insecure DB connection credentials — this list is close to a ready-made "must never ship" set for a JVM security rule.

### 11. SEI CERT Oracle Coding Standard for Java — [cmu-sei.github.io/secure-coding-standards/sei-cert-oracle-coding-standard-for-java/rules/](https://cmu-sei.github.io/secure-coding-standards/sei-cert-oracle-coding-standard-for-java/rules/)

The historical `wiki.sei.cmu.edu/confluence/display/java` URL now 301-redirects here — the standard has moved off Confluence to a static GitHub Pages site under `cmu-sei/secure-coding-standards`. 19 categories: `IDS` (Input Validation and Data Sanitization, 11 rules), `DCL` (Declarations and Initialization, 3), `EXP` (Expressions, 7), `NUM` (Numeric Types and Operations, 14), `STR` (Characters and Strings, 5), `OBJ` (Object Orientation, 14), `MET` (Methods, 13), `ERR` (Exceptional Behavior, 9), `VNA` (Visibility and Atomicity, 5), `LCK` (Locking, 11), `THI` (Thread APIs, 5), `TPS` (Thread Pools, 5), `TSM` (Thread-Safety Miscellaneous, 3), `FIO` (Input Output, 16), `SER` (Serialization, 12), `SEC` (Platform Security, 10), `ENV` (Runtime Environment, 6), `JNI` (Java Native Interface, 4), `MSC` (Miscellaneous, 11) — 174 rules total. Named examples confirmed: `IDS00-J` (SQL injection), `SER12-J` (prevent deserialization of untrusted data), `FIO16-J` (canonicalize paths before validating), `LCK10-J` (correct double-checked-locking form), `SEC05-J` (don't use reflection to widen accessibility), `MET03-J` (security-check methods must be `private`/`final`).

### 12. OWASP Cheat Sheet Series (Java-relevant sheets) — [cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/) (source: raw markdown in [OWASP/CheatSheetSeries](https://github.com/OWASP/CheatSheetSeries))

Fetched: [Deserialization](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html) (386 lines — look-ahead deserialization, allow-listing over deny-listing, `ObjectInputFilter` since JEP 290/Java 9), [XML External Entity Prevention](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html) (816 lines — per-parser-type `setFeature`/`setExpandEntityReferences` disables for `DocumentBuilderFactory`, `SAXParserFactory`, `XMLInputFactory`, `TransformerFactory`, `SchemaFactory`, `Validator`, JAXB, XPath), [Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html), [LDAP Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/LDAP_Injection_Prevention_Cheat_Sheet.html), [Java Security](https://cheatsheetseries.owasp.org/cheatsheets/Java_Security_Cheat_Sheet.html) (1002 lines — the broadest sheet, covering crypto, JNDI/Log4Shell-class lookups, and general hardening), [Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html), [Vulnerable Dependency Management](https://cheatsheetseries.owasp.org/cheatsheets/Vulnerable_Dependency_Management_Cheat_Sheet.html) (317 lines — names OWASP Dependency-Check, Snyk, GitHub Dependabot, and SBOM formats CycloneDX/SPDX as the tool landscape). Note: there is no standalone "Log4Shell" or dedicated "JNDI" cheat sheet in the current series (an older `Injection_Prevention_Cheat_Sheet_in_Java.md` path 404s) — that guidance now lives inside the Java Security sheet's JNDI section.

### 13. Gradle's official Best Practices — [docs.gradle.org userguide best-practices](https://docs.gradle.org/current/userguide/best_practices_general.html) (source: [`platforms/documentation/docs/src/docs/userguide/best-practices/*.adoc`](https://github.com/gradle/gradle/tree/master/platforms/documentation/docs/src/docs/userguide/best-practices))

### 16. dependency-analysis-gradle-plugin — [github.com/autonomousapps/dependency-analysis-gradle-plugin](https://github.com/autonomousapps/dependency-analysis-gradle-plugin) `README.asciidoc`

Reports on 4 dependency-declaration issue types (unused; used-transitive-should-be-direct; wrong configuration `api`/`implementation`/`compileOnly`; unused annotation processors) plus plugin-applied-but-unused advice (`org.jetbrains.kotlin.jvm`, `com.android.library`), classpath duplicate-class warnings, a dominator-tree print for "fat" dependency discovery, and a project graph generator. `./gradlew app:projectHealth` runs the analysis per module; `./gradlew fixDependencies` auto-remediates all findings; `fixDependencies --upgrade` is the conservative mode that only adds/upgrades declarations, never removes or downgrades — explicitly designed for incremental rollout on a large or library-publishing codebase where a removed-but-actually-needed dependency silently breaks consumers. Supported languages: Groovy, Java, Kotlin, Scala on the JVM (plus Android).

### 19. Reproducible builds for the JVM — [reproducible-builds.org/docs/jvm/](https://reproducible-builds.org/docs/jvm/)

Root cause named first: jar/zip entry timestamps, and `java.util.Properties.store()` always writing a generation-timestamp comment line. Gradle fix (available since Gradle 3.4): `isPreserveFileTimestamps = false`, `isReproducibleFileOrder = true`, plus explicit `dirPermissions`/`filePermissions`, applied via `tasks.withType<AbstractArchiveTask>().configureEach { ... }`. A specific footgun called out: `withXml()` on `GenerateMavenPom` (`.asNode().appendNode()`) reintroduces non-deterministic element ordering into an otherwise-reproducible POM. Maven's fix is `Maven - Guide to Configuring for Reproducible Builds` plus pinned `file.encoding`/`user.language`/`user.country` properties; JDK 18+ defaults `file.encoding` to UTF-8, so this only bites JDK ≤17.

### 20. SLSA build levels — [slsa.dev/spec/v1.1/levels](https://slsa.dev/spec/v1.1/levels)

Build track: L0 "no requirements," L1 requires automated provenance generation and distribution to consumers, L2 requires a hosted build platform that itself generates and signs the provenance (consumers must validate authenticity), L3 requires the hosted platform to additionally isolate builds from each other and keep signing material inaccessible to user-defined build steps. No Source track content was surfaced in this fetch. Central-published Maven/Gradle artifacts today are typically at L1-L2 depending on whether CI runs on a hosted, isolated runner and whether provenance is signed by the platform rather than the build script.

### 21. OpenSSF Scorecard checks — [github.com/ossf/scorecard docs/checks.md](https://github.com/ossf/scorecard/blob/main/docs/checks.md)

720-line canonical check list; the ones most directly applicable to a Gradle/Maven repo's CI posture are Pinned-Dependencies (are GitHub Actions and base images pinned by SHA, not tag), Token-Permissions (does every workflow declare least-privilege `permissions:`), Dangerous-Workflow (does a workflow run untrusted PR code with secrets), Branch-Protection, Code-Review, Signed-Releases, and Vulnerabilities (does the repo have open, unfixed OSV-reported CVEs).

## Recent shifts seen in this corpus

- **detekt 2.0** has been in public alpha since 2025-09-04, at `alpha.6` (2026-08-04) as of this research date, targeting Kotlin 2.4.10 / Gradle 9.6.1 / JDK 25. It renames `:detekt-formatting` → `:detekt-rules-ktlint-wrapper` and tightens YAML parsing to reject `active: "true"` (string) — any rule file's example detekt config needs the strict-boolean form and the new module coordinate, or it will look correct against detekt 1.x and break on 2.0.
- **NullAway 0.12.3** (2024) introduced `OnlyNullMarked` as an alternative to the previously-mandatory `AnnotatedPackages`; **NullAway 0.14.0** removed the `LegacyAnnotationLocations` compatibility flag that had eased the 0.12.0 type-use-annotation-placement transition — code written against pre-0.14.0 guidance about annotation placement is now unsupported, not just discouraged.
- **JSpecify 1.0** (2024) is now what Guava (33.4.1+) annotates its public API with; this changes NullAway's behavior for *any* consumer of Guava, whether or not that consumer runs in JSpecify mode — a shift invisible to a project that hasn't touched its own nullability config at all.
- **Kotlin 2.1** (2024/2025 era) added `-Wextra`/`extraWarnings` as an Experimental, opt-in warning bundle — a rule authored before this either doesn't know it exists or must flag it as still-experimental rather than default-on.
- **`javac -Xlint`** has grown categories unknown to pre-2021 (Java 16) documentation: `this-escape` (Java 21), `dangling-doc-comments`, `restricted`, `missing-explicit-ctor`, `output-file-clash`, `incubating` — an LLM's training-data-era mental model of "the `-Xlint` list" is stale by roughly a dozen keys.
- **OSSRH sunset (2025-06-30)** made Central Portal the sole Maven Central publishing path (per jvm-frame.md's era hypothesis, consistent with but not independently re-verified against this scout's Central Portal fetch) — any rule or skill describing "deploy to OSSRH" or `nexus-staging-maven-plugin` is describing a dead path.
- **Gradle's `validation_problems.adoc` living under a path named `unused/`** in the `gradle/gradle` source tree as of this fetch is itself evidence of an in-progress documentation reorganization — the content is still accurate today, but a rule citing this exact doc URL should expect it to move again.

## Contested

- **detekt `formatting` vs ktlint directly**: detekt 2.0's own release notes frame `:detekt-rules-ktlint-wrapper` as exactly what the old name obscured — a wrapper, not an independent implementation. A project already running ktlint standalone gets no additional signal from also enabling detekt's `formatting` rule set; the trend (explicit renaming, JVM-17 target alignment with ktlint's own roadmap) is toward treating detekt-for-logic + ktlint-for-formatting as the two-tool split, not detekt-does-everything.
- **nebula-lint vs dependency-analysis-gradle-plugin**: both claim "unused dependency" and "duplicate classes" detection for Gradle. This survey did not find recent nebula-lint activity comparable to DAGP's (DAGP has `fixDependencies` auto-remediation, `projectHealth`, and active 2026-era documentation); the trend favors DAGP, but this scout did not check nebula-lint's actual release cadence to confirm abandonment — worth a direct verification pass before a rule file picks a side.
- **Error Prone severity vs "on by default"**: the errorprone.info docs page's `severity` field (`ERROR`/`WARNING`/`SUGGESTION`) is easy to mistake for "runs by default at that level," but the real gate is membership in `ENABLED_ERRORS`/`ENABLED_WARNINGS`/`DISABLED_CHECKS` in `BuiltInCheckerSuppliers.java` — these two views of the same tool disagree in scope (docs: 650 patterns by declared severity; source: 649 patterns by enabled/disabled membership, off by one likely due to a check added/removed between the two snapshots fetched). A rule file must cite the source list, not the docs page, when claiming a check is "on by default."
- **Maven Enforcer vs Gradle dependency locking/verification** as the "which build system polices dependency drift better" question: Maven's answer is Enforcer rules bolted on via explicit `<execution>`s (opt-in, rule-by-rule); Gradle's answer is `dependencyLocking` + `verification-metadata.xml` (opt-in, but broader and checksum/signature-based rather than convergence-based). This corpus doesn't adjudicate which is "better" — it surfaces that the two ecosystems solve dependency-drift with structurally different mechanisms, which the frame's "modern Gradle deserves more depth than Maven" hypothesis should account for rather than assume.
