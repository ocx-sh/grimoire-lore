## Summary

- The Gradle community's settled position as of 2025-2026 is: convention plugins belong in an **included build** (`build-logic`), not `buildSrc` — `buildSrc` invalidates the whole build on any change, an included build only invalidates its consumers.
- `afterEvaluate {}` is treated as a smell in Gradle plugin authorship, not a tool: the canon alternative is `plugins.withId()`, lazy `Property`/`Provider` wiring, and explicit opt-in configuration functions instead of implicit defaults applied late.
- Configuration Cache is stable (since Gradle 8.1) but still not the default; Gradle moved the "default execution mode" target from 10.0 to **11.0**, and Maven Publish is a named holdout among core plugins as of the Gradle blog's own March 2025 post.
- Isolated Projects graduated experimental → incubating only in **Gradle 9.7.0**; the Gradle blog itself does not recommend it for production artifacts yet.
- The Shadow (fat-jar) plugin changed ownership and Maven/Plugin-Portal coordinates from `com.github.johnrengelman.shadow` to **`com.gradleup.shadow`**; any build still pinned to the old coordinate is stale.
- OSSRH (the legacy Sonatype publishing endpoint) sunset on **2025-06-30**; every JVM library that still publishes via the old Nexus staging API must move to the Central Portal (`central.sonatype.com`) or its OSSRH-compatibility shim.
- kapt is explicitly framed by Kotlin's own docs as inferior, not merely different: it generates Java stubs (expensive, lossy for Kotlin-only features) while KSP analyzes Kotlin source directly; Kotlin 2.0 does not enable kapt by default, and JetBrains' own guidance is "migrate what supports it," though no hard removal date is published.
- Binary compatibility validation moved **into the Kotlin Gradle plugin itself starting 2.2.0** (`kotlinlang.org/docs/gradle-binary-compatibility-validation.html`), alongside the older standalone `Kotlin/binary-compatibility-validator` tool — two tools now do the same job and a project must pick one, not both.
- JSpecify's 1.0 release (July 2024) followed by Spring Framework 7 / Spring Boot 4 completing migration (Nov 2025) is treated by multiple 2026 sources as "the most consequential change to Java null-safety in a decade" — ending the JSR-305/`@Nullable`-flavor fragmentation. Kotlin's compiler (2.1.0+) treats JSpecify annotations as **errors by default**, not warnings.
- NullAway's JSpecify mode is still described as evolving in early-2026 sources, with a named open issue against lambda-heavy Spring/Reactor APIs (`NullAway#1290`) — adopting it is not yet a solved problem.
- `Optional` guidance from Goetz and Marks is unambiguous and unchanged since its introduction: return-type only, never a field, never a parameter, never a collection element — yet this is still one of the most commonly violated rules in the wild per multiple 2024-2025 retrospective posts.
- Structured concurrency's API is not stable: JEP 505 (5th preview, JDK 25) replaced `StructuredTaskScope`'s public constructors with static factory methods (`open()`, `open(Joiner)`) and introduced the `Joiner` interface; JEP 525 (6th preview) changes it again — any rule that names concrete API shapes here needs a version guard.
- Virtual threads did not obsolete `ReentrantReadWriteLock`: Kabutz documents a hard 65536-concurrent-read-lock ceiling that virtual threads can hit in practice, with `StampedLock.asReadWriteLock()` as the workaround — a genuinely boring-sounding topic that bites at scale.
- Maven 4.0.0 deliberately deferred its more invasive features (mixins, cascading profiles) to a later 4.1.0 to ship a stable core first (Guillaume Nodet, mailing list, 2025); GA was cut in October 2025.
- Maven's reproducible-builds effort (Hervé Boutemy) reached "reproducible by default" as of `4.0.0-beta-5`, backed by minimum versions of `maven-source-plugin`, `maven-jar-plugin`, and `maven-assembly-plugin` (3.2.0+) — a concrete, checkable dependency floor.
- The fakes-vs-mocks-vs-Testcontainers argument has a sharp practitioner claim worth preserving: Testcontainers gives binary up/down failure semantics, a hand-written fake can inject *partial* failure (e.g., one partition failing, others healthy) that neither a mock nor a container can express as naturally.
- The Kotlin testing landscape is genuinely fragmented in 2025: a practitioner survey (Ivan Canet) compares JUnit, kotlin-test, Kotest, Prepared, and TestBalloon side by side — there is no single obvious default the way there is for Java (JUnit 5/6).
- `rules_jvm_external`'s Maven-dependency pinning is a manual, committed-artifact workflow (`REPIN=1 bazel run @maven//:pin`, a tracked `maven_install.json`), structurally different from Gradle's lockfile model — a Bazel-Java rule cannot just describe Gradle's `dependency_verification.html` semantics and call it done.
- A named large-scale Gradle→Bazel migration (Spotify, ~5M LOC Kotlin/Java/C++, BazelCon 2024) is cited by the corpus as real evidence for feasibility at scale, while a separate 2024-2025 case study argues a specific migration's cost exceeded its savings — the "worth it at what size" question is still argued both ways with no clean threshold.
- Baeldung's JUnit-5-vs-Kotest comparison is the kind of generically-correct-but-stale content the frame flagged for scrutiny: it reads as accurate on syntax/assertions but is silent on the 2.2.0+ binary-compatibility-validator convergence and the newer Kotlin-native runners (TestBalloon, Prepared) that a 2025-2026-dated survey (Canet) already treats as live alternatives.

## Survey

### 1. Brian Goetz — Data-Oriented Programming (v1.1 series) and JavaOne 2025

Goetz's [Data-Oriented Programming, Version 1.1 introduction](https://inside.java/2024/05/23/dop-v1-1-introduction/) (Inside.java, 2024-05-23) restates and updates four core principles from the original 2022 essay: model data as data (records), make illegal states unrepresentable (sealed hierarchies + exhaustive pattern matching), keep data immutable, and validate at the boundary. The [why-update](https://inside.java/2024/06/26/dop-v1-1-why-update/) companion post argues the update exists because pattern matching for `switch` and record patterns finalized in Java 21, giving the guidelines a stable feature set to assume. On [Optional](https://blog.indrek.io/articles/misusing-java-optional/) and related roundups, Goetz's stated position (quoted across multiple secondary sources) is that `Optional` is "a limited mechanism for library method return types where there needed to be a clear way to represent 'no result'" — explicitly not a field type, not a parameter type, not a collection element type. On checked exceptions and lambdas, Goetz has been on record calling "sneaky-throw" workarounds irresponsible: "Just because you don't like the rules, doesn't mean it's a good idea to take the law into your own hands... irresponsible... places the convenience of the code writer over the far more important considerations of transparency and maintainability."

### 2. Ron Pressler et al. — [JEP 505: Structured Concurrency (Fifth Preview)](https://openjdk.org/jeps/505)

The JEP's stated rationale: "If a task splits into concurrent subtasks then they all return to the same place, namely the task's code block" — structured concurrency makes the thread hierarchy mirror the lexical/call hierarchy the way sequential code already does, so cancellation, error propagation, and observability all follow scope rules instead of manual bookkeeping. This preview (targeted JDK 25, created 2024-09-18, updated 2025-10-09) replaced `StructuredTaskScope`'s public constructors with static factory methods — `open()` (default: fail if any subtask fails) and `open(Joiner)` for custom policies — and introduced the `Joiner` interface (`onFork`, `onComplete`, `result`) with built-in factories `anySuccessfulResultOrThrow()`, `allSuccessfulOrThrow()`, `awaitAll()`, `allUntil(Predicate)`. [JEP 525](https://openjdk.org/jeps/525) (Sixth Preview) changes the API again, and [SoftwareMill's critique of JEP 505](https://softwaremill.com/critique-of-jep-505-structured-concurrency-fifth-preview/) argues the API is still not settled enough to commit to in production code.

### 3. Local Variable Type Inference — [Style Guidelines](https://openjdk.org/projects/amber/guides/lvti-style-guide) (OpenJDK Amber project, official)

The canonical `var` guidance, still the standard reference in 2026: `var` can only appear for local variables (never fields, parameters, or return types); the primary justification for using it is readability, and "the further away our `var` gets from its definition, the less useful it becomes" — i.e., `var` degrades when the initializer's type can't be inferred by a reader glancing at the line. This is the source every linter's "no-var-when-type-unclear" rule ultimately cites.

### 4. Jendrik Johannes — [onepiece.software](https://onepiece.software/), the `gradlex-org` plugin suite, and the [gradle-project-setup-howto](https://github.com/jjohannes/gradle-project-setup-howto)

Johannes's free "Understanding Gradle" video series and his gradlex-org plugins (`java-module-dependencies`, `extra-java-module-info`, `java-module-testing`, `java-ecosystem-capabilities`) are built around one recurring argument: Gradle's own dependency model should be the single source of truth for module boundaries, and JPMS `module-info.java` should drive Gradle configuration rather than being configured twice. His `README` for the setup-howto repo (raw-fetched) lays out a canonical project shape: base/feature/report/check/component/testing convention plugins organized by concern, driven by GitHub Actions + Renovate for continuous dependency and report freshness — a concrete convention-plugin taxonomy worth citing verbatim in a Gradle rule's support directory.

### 5. Tony Robalik (`autonomousapps`) — [dependency-analysis-gradle-plugin](https://github.com/autonomousapps/dependency-analysis-gradle-plugin)

The plugin's stated purpose: "eliminate unused dependencies and correctly declare all actually-used dependencies... exactly what you need to build your project: nothing more, nothing less." Its main task is `buildHealth`, producing `build/reports/dependency-analysis/advice.json`. The project explicitly targets the `api`-vs-`implementation` leak problem Gradle itself only partially warns about, and is used by Gradle's own build (per the corpus's `gradle/gradle` exemplar) as well as "some of the largest Gradle projects in the world."

### 6. Björn Kautler / Martin Bonnin — the `afterEvaluate` canon

[Bonnin's "My life after afterEvaluate"](https://blog.mbonnin.net/my-life-after-afterevaluate) states the community's now-settled argument precisely: relying on `afterEvaluate {}` in a plugin makes "anyone wanting to use your code" also need `afterEvaluate`, cascading the anti-pattern down every consumer's build. His concrete alternatives: expose a function on the plugin's extension that runs logic immediately rather than deferring it; require explicit opt-in for defaults (a named `greeting()` call) rather than silently applying them late. The one carve-out he grants `afterEvaluate` is validation checks scoped entirely to your own plugin's state. Kautler (Vampire) is cited across Gradle Discourse/Slack as the person who most consistently pushes `plugins.withId()` as the correct replacement for cross-plugin coordination.

### 7. Cédric Champeau — [melix.github.io/blog](https://melix.github.io/blog/2023/gradle-synthetic-projects.html)

Champeau's blog (Gradle team, Micronaut) covers Gradle's dependency-resolution flexibility and toolchain design from the implementer's side; his synthetic-projects post and lifecycle-mythbusting posts are the frequently-cited canon for "Gradle's task graph and configuration phase are not what you think they are."

### 8. Roman Elizarov — [Kotlin and Exceptions](https://elizarov.medium.com/kotlin-and-exceptions-8062f589d07), [Structured Concurrency](https://elizarov.medium.com/structured-concurrency-722d765aa952)

Elizarov's stated design principle for coroutines: "no exception should be lost, all bugs should get reported to developers" — structured concurrency in `kotlinx.coroutines` (introduced 0.26.0) exists specifically so a child coroutine's failure cannot silently vanish the way a bare `Thread` or unstructured `launch` can. This is the design rationale a Kotlin rule should cite when explaining why `GlobalScope.launch` is discouraged.

### 9. Jake Wharton — [jakewharton.com/blog](https://jakewharton.com/blog/)

Wharton's build-focused posts carry sharp, specific verdicts: "[Gradle toolchains are rarely a good idea](https://jakewharton.com/blog/)" (2024-03-21) argues toolchain auto-provisioning trades a simple, explicit JDK requirement for opaque, environment-dependent resolution (the same foojay-resolver fragility later corroborated by IDE bug reports); "Nonsensical Maven is still a Gradle problem" (2024-03-28) argues Gradle's own POM-consumption logic, not Maven's format, is responsible for a specific interop failure; "Kotlin's JDK release compatibility flag" (2024-03-13) is a build-target-vs-toolchain distinctions post. His posts consistently model the "opinionated senior engineer naming a specific flag/task and its failure mode" register a JVM rule should imitate.

### 10. Kotlin official docs — [kapt-to-KSP migration](https://kotlinlang.org/docs/ksp-kapt-migration.html) and [binary compatibility validation](https://kotlinlang.org/docs/gradle-binary-compatibility-validation.html)

Official framing: kapt "translat[es] Kotlin source code into Java 'stubs'... expensive, significantly increases build time, and loses some Kotlin-specific features"; KSP "understands all Kotlin features and analyzes the source code directly." Migration is designed to be incremental — kapt and KSP coexist per-module during a staged migration; the plugin coordinate changes from `kotlin-kapt` to `com.google.devtools.ksp`. Separately, binary compatibility validation is now built into the Kotlin Gradle plugin from **2.2.0**, generating ABI dumps and diffing them against a checked-in baseline — functionally overlapping with the older standalone `Kotlin/binary-compatibility-validator` tool.

### 11. Central Portal / OSSRH sunset — [official announcement](https://central.sonatype.org/news/20250326_ossrh_sunset/)

OSSRH (the legacy Nexus-staging publishing path) sunset **2025-06-30**; all namespaces migrated to the Central Publisher Portal (`central.sonatype.com`). The stated fast-path for projects that can't immediately rewrite their publishing plugin config is the "OSSRH Staging API Service," a compatibility shim translating a subset of Nexus 2 APIs to the new Portal API — meaning a JVM SDK-publishing rule must name both the correct target (Portal) and the fallback (compat shim) with an expiry-risk note.

### 12. Gradle blog — Configuration Cache and Isolated Projects state

[The Road to Configuration Cache](https://blog.gradle.org/road-to-configuration-cache) (Gradle blog, dated ~March 2025) states Configuration Cache has been stable since Gradle 8.1, that over half of the top-50 most-downloaded plugins declare compatibility, and that Maven Publish remains a named incompatible core plugin. It cites concrete numbers from real adopters: one build recovered 26 seconds of configuration time to "negligible," another halved cache size (700MB→400MB) and configuration time (2m04s→55s), and parallel-loading benchmarks show ~2x speedup (3.6s→1.5s). The default-execution-mode target moved from Gradle 10.0 to **Gradle 11**. Separately, [Isolated Projects](https://docs.gradle.org/nightly/userguide/isolated_projects.html) graduated experimental→incubating only in **Gradle 9.7.0**, explicitly "not yet recommended for building production artifacts."

### 13. Shadow plugin ownership change — [GradleUp/shadow](https://github.com/GradleUp/shadow)

The Shadow (fat/uber-jar) plugin transferred from `johnrengelman` to the GradleUp org; the plugin ID changed from `com.github.johnrengelman.shadow` to **`com.gradleup.shadow`**, current major version 9.x. Any build config that still resolves the old coordinate from a stale tutorial is citing dead guidance — a concrete, checkable staleness signal for a Gradle rule.

### 14. JSpecify adoption — [Spring's null-safety post](https://spring.io/blog/2025/03/10/null-safety-in-spring-apps-with-jspecify-and-null-away/) and secondary 2026 coverage

Spring Framework 7 / Spring Boot 4 completed migration to JSpecify by November 2025, described by multiple 2026 retrospectives as ending the JSR-305/annotation-fragmentation era in the Java ecosystem. IntelliJ IDEA 2025.3 aligned its own inspections to prefer JSpecify over JetBrains' proprietary annotations when both are present on the classpath. The Kotlin compiler, from 2.1.0, treats JSpecify nullness violations as **compiler errors by default** when calling Java from Kotlin — a strictness level higher than most JSR-305 setups defaulted to. Countervailing signal: NullAway's own JSpecify mode is still described as evolving in early-2026 sources, with an open, named issue (`NullAway#1290`) against lambda-heavy Spring/Reactor call patterns.

### 15. Fakes vs. mocks vs. Testcontainers — [Pierre Zemb](http://pierrezemb.fr/posts/why-fakes-beat-mocks-and-testcontainers/)

The sharpest formulation in the corpus: "A fake that covers 80% of a dependency's behavior with determinism and fault injection is strictly better than Testcontainers covering 100% with none of those properties." The concrete argument is about failure-mode granularity — Testcontainers gives binary up/down; a hand-rolled fake can return `Ok` for one partition and `Err(PartitionUnavailable)` for another in the same call, modeling partial/production-shaped failure that neither pure mocks nor real containers naturally express.

### 16. Kotlin testing fragmentation — [Ivan Canet, "State of Kotlin Tests"](https://ivan.canet.dev/blog/2025/06/17/state-of-kotlin-tests.html)

A 2025-06-17 practitioner survey directly comparing JUnit 5, kotlin-test, Kotest, Prepared, and TestBalloon — evidence that, unlike Java where JUnit 5/6 is the unchallenged default, Kotlin's testing-framework choice is still genuinely unsettled in 2025-2026, with newer contenders (Prepared, TestBalloon) actively competing against the incumbents. [Baeldung's JUnit-5-vs-Kotest comparison](https://www.baeldung.com/kotlin/kotest-vs-junit-5) is accurate on the surface (syntax, assertion style, parallel execution) but is silent on this newer-contender landscape and on the 2.2.0+ binary-compatibility-validator convergence — the kind of generically-true-but-dated content the research brief asked to flag by name.

### 17. Maven 4 — Guillaume Nodet (mailing list) and the [official "What's new in Maven 4"](https://maven.apache.org/whatsnewinmaven4.html)

Nodet's 2025-05 mailing-list position: ship 4.0.0 with a deliberately limited feature set for stability, deferring mixins and cascading profiles to 4.1.0. GA was cut in October 2025 after fixes accumulated on the 4.0.x branch. The "Mason" extension (Tamás Cservenák + Nodet) adds alternate POM syntaxes — YAML, JSON5, TOML, HOCON — as an opt-in, not a default replacement for XML POMs.

### 18. Hervé Boutemy — Maven reproducible builds

Maven reached **reproducible-by-default** as of `4.0.0-beta-5`, the outcome of a multi-year effort tracked at reproducible-builds.org. The concrete dependency floor: `maven-source-plugin`, `maven-jar-plugin`, and `maven-assembly-plugin` **3.2.0+** are required to get reproducible output "as a direct output from the build system" rather than as an opt-in add-on.

### 19. `rules_jvm_external` — [pinning workflow](https://github.com/bazel-contrib/rules_jvm_external)

Bazel's Maven-dependency pinning is an explicit, committed-artifact workflow, not an implicit lockfile: `REPIN=1 bazel run @maven//:pin` regenerates a tracked `maven_install.json` (or a name-specific `lock_file` when multiple `maven_install` declarations exist), which is meant to be committed to source control and which enables fully offline builds after the first `bazel fetch @maven//...`. This is structurally different from Gradle's `dependency_verification.html` model and from Maven's absence of a lockfile concept entirely — a Bazel-Java depth file cannot just restate Gradle's locking semantics.

### 20. BazelCon 2024 — Spotify's Gradle→Bazel migration

Spotify described migrating the Android Music app (~5M LOC across Kotlin, Java, and C++) from Gradle to Bazel at BazelCon 2024, presented as evidence migration is tractable at large scale. Countervailing practitioner claim found in the corpus (an anonymized 2024-2025 migration retrospective): "The migration cost more than it saved... they could've optimized their Maven builds and saved $180K" — i.e., the "worth it at what size" question has real evidence on both sides, not a clean threshold.

### 21. Gradle version catalogs — [official naming best-practices post](https://blog.gradle.org/best-practices-naming-version-catalog-entries) and [dependency-verification docs](https://docs.gradle.org/current/userguide/dependency_verification.html)

Gradle's own guidance: a single `gradle/libs.versions.toml` should be the norm (not per-module catalogs); plugin coordinates referenced as regular dependencies should be suffixed `-plugin` (e.g., `dependency-check-plugin` for `org.owasp:dependency-check-gradle`) to disambiguate from the `[plugins]` table. Separately, the docs are explicit that a version catalog **only affects declared versions**, not resolved versions — it must be paired with locking or alignment to actually enforce a resolved version across a build, a distinction the corpus shows practitioners frequently blur.

### 22. Structured build organization — [Best Practices for Structuring Builds](https://docs.gradle.org/current/userguide/best_practices_structuring_builds.html) (official) plus community consensus

Official and community sources converge: "the preferred location for build logic is an included build (typically `build-logic`), not `buildSrc`." The mechanism cited for *why*: any change under `buildSrc` invalidates the entire build's configuration, while a subproject inside an included build only invalidates its actual consumers — a real incrementality difference, not just style preference. `buildSrc` remains acceptable only when a build needs to reach into internal, unstable Gradle APIs that an included build's dependency isolation would block.

### 23. Java Specialists Newsletter — Heinz Kabutz on virtual threads and locks

Kabutz's newsletter content on virtual threads names a specific, concrete ceiling: `ReentrantReadWriteLock` supports at most **65,536 concurrent read locks**, a limit that becomes reachable once virtual threads make "one thread per request" cheap again; his documented workaround is `StampedLock.asReadWriteLock()`. This is exactly the "boring topic that bites" the brief asked to surface.

### 24. KotlinConf 2025 — [JetBrains recap](https://blog.jetbrains.com/kotlin/2025/05/kotlinconf-2025-language-features-ai-powered-development-and-kotlin-multiplatform/)

K2 became the default analysis backend in IntelliJ IDEA 2025.1; JetBrains cites an internal 40% build-time drop after their own monorepo switched to K2 mode — a concrete, named number for "why K2 matters" beyond compiler-internals framing. Kotlin 2.2 roadmap items announced: guard conditions in `when`-with-subject, multi-dollar string interpolation, non-local `break`/`continue`, context parameters.

### 25. Gradle Plugin Portal / TestKit — [official docs](https://docs.gradle.org/current/userguide/publishing_gradle_plugins.html), [TestKit](https://docs.gradle.org/current/userguide/test_kit.html)

The `java-gradle-plugin` plugin auto-wires `gradleTestKit()` into `testImplementation`. `com.gradle.plugin-publish` 2.0.0+ requires Gradle 7.4+; its bundled Compatibility Plugin went from incubating (0.1.0) to stable (1.0.0) as recently as March 2026 — a plugin-dev rule pinning a specific `plugin-publish` version needs to name this stability boundary explicitly.

## Recent shifts seen in this corpus

- **OSSRH sunset, 2025-06-30.** Any publishing guidance dated before mid-2025 that references the Nexus staging repository or `oss.sonatype.org` is dead; the target is the Central Portal, with a compatibility shim as the only bridge. [Source](https://central.sonatype.org/news/20250326_ossrh_sunset/)
- **Shadow plugin coordinate change.** `com.github.johnrengelman.shadow` → `com.gradleup.shadow` under new ownership; version 9.x. Pre-2024 tutorials cite the dead coordinate. [Source](https://github.com/GradleUp/shadow)
- **Gradle's Configuration-Cache-default target slipped from 10.0 to 11.0**, and Isolated Projects only left "experimental" for "incubating" in **9.7.0** — both later than the frame's era hypothesis assumed "on by default"; verify against the actually-installed Gradle version before asserting either is default. [Source](https://blog.gradle.org/road-to-configuration-cache)
- **kapt is not Kotlin 2.0's default annotation-processing path**; KSP is the sanctioned direction, though no formal kapt removal date exists as of this survey. Guidance predating Kotlin 2.0 that recommends kapt without qualification is stale. [Source](https://kotlinlang.org/docs/ksp-kapt-migration.html)
- **Binary-compatibility validation moved into the Kotlin Gradle plugin itself at 2.2.0**, duplicating what the standalone `Kotlin/binary-compatibility-validator` tool already did — pre-2.2.0 guidance recommending only the standalone tool is now incomplete, not wrong. [Source](https://kotlinlang.org/docs/gradle-binary-compatibility-validation.html)
- **JSpecify 1.0 (July 2024) plus Spring's completed migration (Nov 2025)** ends the JSR-305/`@Nullable`-flavor fragmentation multiple 2026 sources call out explicitly; pre-2024 nullness-annotation guidance recommending JSR-305 or a vendor-specific annotation set without mentioning JSpecify is now behind the ecosystem consensus. [Source](https://spring.io/blog/2025/03/10/null-safety-in-spring-apps-with-jspecify-and-null-away/)
- **Structured concurrency's public API is still churning inside preview status**: JEP 499 (4th preview) → JEP 505 (5th preview, replaced constructors with `open()`/`Joiner`) → JEP 525 (6th preview, further changes). Any code sample naming a concrete `StructuredTaskScope` constructor call is already stale. [Source](https://openjdk.org/jeps/505)
- **Maven 4.0.0 GA cut in October 2025** with mixins and cascading profiles explicitly deferred to 4.1.0 — treat any "Maven 4 supports X" claim as needing an explicit 4.0 vs 4.1 version check. [Source: Guillaume Nodet mailing-list posts]
- **`buildSrc` vs included-build consensus has fully settled toward included builds** as of the current Gradle docs' own "Best Practices for Structuring Builds" page — older tutorials defaulting new readers to `buildSrc` without qualification are behind current guidance. [Source](https://docs.gradle.org/current/userguide/best_practices_structuring_builds.html)

## Contested

- **Fat/uber jar vs. jlink/jpackage/layered images.** Trend: fat jars remain common for CLI tools and simple deployables, but the corpus's application-shape sources (Jib, Spring Boot layered-jar repackaging) treat a single monolithic fat jar as the naive baseline, not the recommended default, once container-layer caching or a minimal runtime image matters. No source in this survey defends "always fat-jar" as best practice for a library; the disagreement is specifically about applications and only about *which* alternative wins.
- **Maven vs. Gradle for libraries.** Trend: split, not converging. A 2025 JetBrains-cited survey shows a near-even split (52% Maven / 48% Gradle); Gradle's own comparison page claims 2-10x speed advantages, while an independent migration retrospective argues a specific 50-project Gradle migration cost more than it saved. Treat "Gradle is simply better" as an overclaim the corpus does not fully support for libraries specifically, even though Gradle's plugin-development and dependency-configuration story (`api`/`implementation`) is more expressive.
- **kapt vs. KSP.** Not really contested any more — KSP is the sanctioned direction and the corpus found no practitioner defending kapt going forward, only migration-in-progress caveats (processor support gaps). Trend: fully toward KSP.
- **Checked exceptions from lambdas ("sneaky throw").** Genuinely contested: Goetz calls workarounds irresponsible on design-intent grounds; Kabutz documents the mechanics without renouncing them as a pragmatic escape hatch. Trend unclear from this corpus — likely stays contested since it's a language-design disagreement, not a tooling one that a new release resolves.
- **Virtual threads vs. reactive.** Trend strongly toward virtual threads for new blocking-style code since JDK 21 GA, but structured concurrency (the piece that gives virtual threads *correctness*, not just scale) is still in preview through JDK 25/26 — meaning the full recommended pattern is not yet API-stable enough to bake into a rule without a version guard.
- **Mocks vs. fakes vs. Testcontainers.** Trend toward "fakes for unit-level tests, Testcontainers for integration tests," with mocks increasingly cast as the weakest of the three for anything beyond pure interaction verification — but the corpus shows genuine confusion in the wild between "writing a fake" and "using a fakes library," which a rule should disambiguate rather than assume settled.
- **Gradle Kotlin DSL vs. Groovy DSL.** Trend strongly toward Kotlin DSL for new builds (IDE default since IntelliJ 2023.1 / Android Studio Giraffe), but the frame's own exemplar table shows real, current holdouts at scale (`apache/kafka`: groovy=9, kts=0; `spring-boot`: groovy=736, kts=54) — Groovy DSL is legacy-common, not merely historical, in large pre-existing codebases.
- **Bazel for Java/Kotlin — worth it at what size?** No clean threshold established in this corpus: Spotify's ~5M-LOC migration is cited as evidence of feasibility, a separate retrospective argues a named migration's cost exceeded its savings. Trend: adopted at the largest scale (Google-adjacent orgs, very large monorepos), genuinely contested below that.
