## Summary

- Structured concurrency (`StructuredTaskScope`, `Joiner`) is **still a preview API in JDK 26** (its sixth preview, JEP 525) as of 2026-09-05 — any rule that recommends it must also say `--enable-preview` is required and the API shape has changed release to release since JDK 21.
- Scoped Values, by contrast, **finalized in JDK 25** (JEP 506) with one late API change (`ScopedValue.orElse` no longer accepts `null`) — a rule written against a JDK-24-era preview signature is stale.
- Virtual-thread pinning on `synchronized` — the headline virtual-threads footgun for three years — was **fixed at the JVM level in JDK 24** (JEP 491); `jdk.tracePinnedThreads` was simultaneously removed and silently does nothing on JDK 24+. A rule that still says "avoid `synchronized`, use `ReentrantLock`, for virtual threads" is now JDK-version-gated advice, not a universal rule.
- Virtual threads still pin on three residual cases even post-JEP-491: blocking while resolving a class reference, blocking inside a class initializer, and waiting for another thread's class initialization to finish — all native-frame-on-stack cases JEP 491 explicitly deferred as "Future Work."
- Virtual threads are explicitly **not meant to be pooled or cached**, and per-thread caching patterns (ThreadLocal-based object pools, cached parsers/buffers) actively fight the model — see the real `jackson-core` issue filed for exactly this migration hazard.
- JEP 400 (UTF-8 by default, JDK 18) removed the platform-default-charset hazard for *most* APIs, but legacy constructors/methods that still silently defer to the platform charset (`String(byte[])`, `FileReader`, `new PrintStream(OutputStream)`) remain live traps in code written before or ported without updating; Error Prone's `DefaultCharset` check exists precisely because this bites repeatedly.
- JEP 403 (strong encapsulation, JDK 17) made "relax with one flag" go away — code relying on `--illegal-access=permit`-era leniency needs per-module `--add-opens`/`--add-exports`, and reflection-heavy frameworks (ORMs, mocking, serialization) are the recurring victims.
- JDK 21's `SequencedCollection` (JEP 431) retrofitted `getFirst()`/`getLast()`/`reversed()` onto `List`/`Deque`, and this produced *real, filed* method-name and covariant-override collisions — Kotlin's `.first()` colliding with the new `.getFirst()` broke Gradle's own Kotlin DSL build on JDK 21 (`gradle/gradle#27699`), and OpenJDK's own Quality Outreach team published a heads-up specifically warning early adopters.
- The Security Manager is **permanently disabled as of JDK 24** (JEP 486, no flag to bring it back) and `Finalizer` has been deprecated for removal since JDK 18 (JEP 421) — both are one-way JDK exits: code that still gates behavior on `System.getSecurityManager()` or relies on `finalize()` for cleanup is holding dead code, not defensive code.
- `sun.misc.Unsafe`'s memory-access methods now **warn on first use as of JDK 24** (JEP 498), ahead of an eventual removal — this is the same deprecation-then-warn-then-remove shape as Security Manager and finalize, and it is the shape libraries keep getting caught flat-footed by.
- GlobalScope, unstructured `launch`, and `runBlocking` on a shared dispatcher remain the top-cited Kotlin coroutine antipatterns; the official Kotlin exception-handling guide is explicit that `CoroutineExceptionHandler` **must be installed on a root coroutine** (never a child `launch`) and has **no effect at all on `async`**, whose exceptions surface only via `await()`.
- Kotlin's own docs distinguish `SupervisorJob` (a `Job` implementation, manual wiring) from `supervisorScope` (a scoping function whose children behave like independent roots), and warn that installing `CoroutineExceptionHandler` inside a plain (non-supervisor) child changes nothing — only the closest ancestor matters.
- `CancellationException` is deliberately transparent to `CoroutineExceptionHandler` and must never be blanket-caught by `catch (e: Exception)` or `runCatching {}` without a rethrow, or cooperative cancellation silently breaks.
- Kotlin's official binary-compatibility-validator plugin is now **in maintenance mode**; JetBrains is moving ABI-compatibility checking into the Kotlin Gradle Plugin itself as an experimental `abiValidation {}` DSL block with `checkKotlinAbi`/`updateKotlinAbi` tasks — a rule that only names the old standalone plugin is already behind current guidance.
- Mockito's inline mock maker (final classes, final methods, static methods, constructors) became the **default mock maker in Mockito 5.0.0** — code or CI images pinned to the pre-5 assumption that final classes can't be mocked, or that carry an old `org.mockito.plugins.MockMaker` override file, silently get different (or broken) behavior on upgrade.
- Testcontainers' Ryuk cleanup process is **deliberately bypassed** for any container started with `.withReuse(true)`; that reuse flag is meant for local development only (gated behind the per-machine `TESTCONTAINERS_REUSE_ENABLE`/`testcontainers.reuse.enable` property) and is explicitly documented as unsuited to CI, where fresh, isolated containers are the point.
- JUnit's own flagship repository shows the ResourceLock/parallel-execution machinery is still actively evolving in 2026 (merged PRs adding exclusive-resource declarations for child nodes, programmatic resource-lock registration, and Vintage-engine parallel method execution) — "just add `@ResourceLock`" is not a finished, static feature set.
- Deserialization of untrusted data remains the single most consequential Java/Kotlin failure class: Log4Shell (CVE-2021-44228, JNDI lookup substitution in log messages) and Jackson-databind's recurring polymorphic-typing gadget-chain CVEs (most recently CVE-2026-54512/54513, a `PolymorphicTypeValidator` bypass via generic type parameters, fixed in 2.18.8/2.21.4/3.1.4) are the same root cause restated a decade apart: code that lets attacker-controlled input select which class gets instantiated.
- ZipSlip (Snyk, disclosed 2018-06-05) is still the canonical name for "archive-extraction code that writes wherever a `../`-laden entry name tells it to," and it recurs because the JDK ships no high-level, path-traversal-safe archive-extraction API — every extractor has to re-derive the same "resolve, then verify it's still under the target directory" check by hand.
- SonarSource's rule catalogue gives several of these bugs stable, citable rule IDs that double as review-comment shorthand: `S2142` ("InterruptedException" should not be ignored), `S1181` (catching `Throwable`/`Error` is too broad), `S2245` (`java.util.Random`/`RandomStringUtils` is not cryptographically secure), `S1206` (`equals`/`hashCode` must be overridden in pairs), and `S2057` (`Serializable` classes should declare `serialVersionUID`) — each maps directly to a "why did the reviewer flag this" moment.

## Survey

### 1. [Error Prone bug pattern catalogue](https://errorprone.info/bugpatterns)

Google's Error Prone ships one bug-pattern page per check, grouped by category, and each name doubles as the exact `@BugPattern` annotation value used to suppress or configure it (`@SuppressWarnings("CheckName")`). Categories directly relevant to this corpus: **Concurrency & Thread Safety** (`DoubleCheckedLocking`, `ThreadJoinLoop`, `WaitNotInLoop`, `StaticGuardedByInstance`, `GuardedBy`, `SynchronizeOnNonFinalField`, `ThreadLocalUsage`, `LockOnBoxedPrimitive`, `NonAtomicVolatileUpdate`, `ClassInitializationDeadlock`); **Equality & Hashing** (`EqualsHashCode`, `EqualsReference`, `BoxedPrimitiveEquality`, `ReferenceEquality`, `BigDecimalEquals`, `OptionalEquality`); **Java Time & Date** (`JavaUtilDate`, `DateFormatConstant`, `JavaTimeDefaultTimeZone`, `ThreeLetterTimeZoneID`, `InvalidTimeZoneID`, an entire Joda-Time migration family); **Character & String Encoding** (`DefaultCharset`, `StringCaseLocaleUsage` — the Turkish-i check by name); **JDK Obsolescence** (`JdkObsolete`, `ClassNewInstance`); **Miscellaneous High-Risk Patterns**: `BanJNDI` ("Using JNDI may deserialize user input via Serializable API which is extremely dangerous" — a direct, named Log4Shell-shaped check), `BanSerializableRead`, `InsecureCryptoUsage`, `MustBeClosedChecker`/`StreamResourceLeak` (resource-leak detection for `Files.walk`/`list`/`lines`-shaped APIs), `UnusedException` (caught exception swallowed instead of chained), `InterruptedInCatchBlock` ("Did you mean `Thread.currentThread().interrupt()`?" — the exact fix for swallowed `InterruptedException`), and `TryFailThrowable` (catching `Throwable`/`Error` masks `fail()` in tests).

### 2. [SpotBugs bug pattern messages (`messages.xml`)](https://raw.githubusercontent.com/spotbugs/spotbugs/master/spotbugs/etc/messages.xml)

SpotBugs' own source of truth for every bug code and its short description. Verified in this corpus: `DM_DEFAULT_ENCODING` ("Reliance on default encoding"), `ES_COMPARING_STRINGS_WITH_EQ` ("Comparison of String objects using == or !="), `EQ_DOESNT_OVERRIDE_EQUALS`, `SIC_INNER_SHOULD_BE_STATIC`, `DL_SYNCHRONIZATION_ON_BOXED_PRIMITIVE`, `DC_DOUBLECHECK` ("Possible double-check of field"), `RV_RETURN_VALUE_IGNORED`, `OS_OPEN_STREAM` ("Method may fail to close stream"), `SR_NOT_CHECKED` (`InputStream.skip()` return value ignored), `REC_CATCH_EXCEPTION`, `DE_MIGHT_IGNORE`, `RC_REF_COMPARISON`, `SE_BAD_FIELD` (non-transient non-serializable field in a `Serializable` class), `SE_NO_SERIALVERSIONID`, `EI_EXPOSE_REP` (exposing internal mutable state by reference), `IS2_INCONSISTENT_SYNC`, `UL_UNRELEASED_LOCK`, `DMI_RANDOM_USED_ONLY_ONCE`, `NP_LOAD_OF_KNOWN_NULL_VALUE`, `VA_FORMAT_STRING_USES_NEWLINE`, and `PT_RELATIVE_PATH_TRAVERSAL`. The core `findbugs.xml`/`messages.xml` does **not** carry the security-hotspot codes (`XXE_*`, `COMMAND_INJECTION`, `SQL_INJECTION`, `WEAK_MESSAGE_DIGEST`, `PREDICTABLE_RANDOM`, `HARD_CODE_PASSWORD`) — those live in the separate `find-sec-bugs` plugin, a distinction worth stating explicitly since teams often assume core SpotBugs alone covers injection classes.

### 3. [SonarSource rule pages (rules.sonarsource.com/java)](https://rules.sonarsource.com/java/)

Spot-verified rule IDs, each independently confirmed against the SonarSource rules explorer or community forum threads: `S2142` — "InterruptedException" should not be ignored ([RSPEC-2142](https://rules.sonarsource.com/java/type/bug/rspec-2142/)); `S1181` — catching `Throwable`, `Error`, `NoSuchMethodError` etc. is too broad ([discussion](https://community.sonarsource.com/t/s1181-catch-throwable-is-too-broad/1656)); `S2245` — pseudorandom number generators (`java.util.Random`) should not be used in security contexts ([discussion](https://community.sonarsource.com/t/java-s2245-identification-of-commons-lang-randomstringutils-secure-as-safe/125248)); `S1206` — "equals(Object)" and "hashCode()" should be overridden in pairs ([RSPEC-1206](https://rules.sonarsource.com/java/rspec-1206/)); `S2057`/`S4926` — `Serializable` classes should declare (and not declare blindly) `serialVersionUID` ([RSPEC-2057](https://rules.sonarsource.com/java/tag/serialization/rspec-2057/)); `S106` — standard outputs should not be used directly to log; and `S1148`, now **deprecated** in favor of `S4507` ("Delivering code in production with debug features activated is security-sensitive") — i.e. the old direct `printStackTrace()`-is-bad rule was folded into a broader debug-feature rule, a naming/rule-lineage detail worth citing rather than assuming `S1148` is still the live rule ID.

### 4. [JEP 400: UTF-8 by Default](https://openjdk.org/jeps/400)

Delivered in JDK 18. Specifies UTF-8 as the default charset for the *standard Java APIs*, replacing the prior "whatever the OS/locale picked at JVM startup" behavior. The JEP's own motivating example: a `FileWriter` on macOS UTF-8 producing garbled text through a `FileReader` on Windows in an `en-US` or `ja-JP` locale — corruption invisible to either program. Explicitly **not** a goal to deprecate or remove the charset-less overloads that still exist (`String(byte[])`, `FileReader`, `PrintStream`), so those overloads remain a live hazard for anyone who *hasn't* upgraded past JDK 17, or for code that explicitly re-derives the pre-18 default via `Charset.defaultCharset()` assumptions.

### 5. [JEP 403: Strongly Encapsulate JDK Internals](https://openjdk.org/jeps/403)

Delivered in JDK 17, superseding JEP 396's JDK-16-era "default to encapsulated, but let people opt back out with a flag" posture. As of 17, it is **no longer possible** to relax internal-API encapsulation via a single command-line switch (the old `--illegal-access=permit`). `sun.misc.Unsafe` is explicitly named as the one exception left unencapsulated because no standard replacement exists yet. This is the JEP that turns "reflection into a JDK-internal class used to just work with a flag" into "reflection into a JDK-internal class now needs a per-module `--add-opens`/`--add-exports`, chosen deliberately, forever" — the direct cause of the long tail of "worked on JDK 8/11, breaks on JDK 17+" bug reports in ORMs, mocking frameworks, and serialization libraries.

### 6. [JEP 431: Sequenced Collections](https://openjdk.org/jeps/431)

Delivered in JDK 21. Introduces `SequencedCollection`, `SequencedSet`, `SequencedMap` as new supertypes above `List`/`Deque`/`LinkedHashSet`/`LinkedHashMap`, adding uniform `getFirst()`, `getLast()`, `addFirst()`, `addLast()`, `reversed()`. Framed by the JEP itself as closing a real, repeatedly-complained-about gap (no common supertype could express "has a defined encounter order"). The retrofit is exactly the kind of "new default method lands on an interface everyone already implements" change that produces override collisions — see the [Quality Outreach heads-up](#7-quality-outreach-jdk-21-sequenced-collections-incompatibilities-insidejava) below for the concrete fallout.

### 7. [Quality Outreach: JDK 21 Sequenced Collections Incompatibilities](https://inside.java/2023/05/12/quality-heads-up/)

OpenJDK's own Quality Outreach program (not a third party) publishing a pre-release heads-up specifically because `SequencedCollection` was known to break real code before JDK 21 even shipped. Documents three concrete incompatibility shapes: (1) method-naming conflicts, where a type already had a same-named method with a different return type or access modifier than the new interface's; (2) covariant-override conflicts, where a type implementing both `List` and `Deque` now inherits two different `reversed()` return types and the compiler can't pick one; (3) type-inference changes, where the *inferred* type of an existing expression silently changes once the new supertypes exist. In practice this collided with Kotlin's `.first()` on Gradle's own Kotlin-DSL build: [gradle/gradle#27699](https://github.com/gradle/gradle/issues/27699), "Gradle 8.5, Kotlin DSL `.first()` collides with JDK21 `.getFirst()`" — Gradle 8.5 was the first Gradle release with full JDK-21 run-time support, which is exactly when the collision surfaced for real projects.

### 8. [JEP 491: Synchronize Virtual Threads without Pinning](https://openjdk.org/jeps/491)

Delivered in JDK 24. Before this JEP, a virtual thread blocking inside a `synchronized` method or statement — including blocking on `Object.wait()` inside one — could not unmount from its carrier platform thread, defeating the entire scalability premise of virtual threads (JEP 444, JDK 21). JDK 24 changes the JVM's monitor implementation so virtual threads acquire, hold, and release monitors independently of their carriers, eliminating pinning in the `synchronized`/`wait`/`notify` case. Two consequences worth stating precisely: the `jdk.tracePinnedThreads` system property, introduced alongside JEP 444, is **removed** — "setting it on the command line will have no effect" as of JDK 24 — and the JEP explicitly retains the `jdk.VirtualThreadPinned` JFR event for the residual pinning cases it does **not** fix: blocking while resolving a symbolic class reference, blocking inside a class initializer, and waiting on another thread's class initialization — all cases where a native stack frame pins the carrier. The JEP also updates the previous "migrate `synchronized` to `ReentrantLock` for virtual-thread scalability" advice: post-JEP-491, that migration is "no longer necessary," and code already migrated need not be reverted.

### 9. [JEP 499/505/525: Structured Concurrency (4th/5th/6th Preview)](https://openjdk.org/jeps/525)

Structured concurrency's `StructuredTaskScope` API has been *re-previewed, not finalized*, release after release: incubated in JDK 19/20 (JEP 428/437), previewed in JDK 21 (JEP 453, `fork()` changed to return `Subtask` rather than `Future`), re-previewed unchanged through JDK 22/23/24/25/26 (JEP 462/480/499/505/525). JEP 525 (JDK 26, shipped 2026-03-17) adds a `Joiner::onTimeout()` method and changes `Joiner::allSuccessfulOrThrow()` to return a list rather than a stream — meaning the API shape is *still moving*, and per the JEP's own history section, finalization is now targeted for **JDK 28**, with JEP 533 (JDK 27) still only adding a type parameter to `join()`'s thrown-exception type. As of 2026-09-05 this means every current JDK release requires `--enable-preview` to use `StructuredTaskScope` at all, and code samples from a JDK-21-era blog post are very likely calling an API shape that has since changed.

### 10. [JEP 506: Scoped Values](https://openjdk.org/jeps/506)

By contrast, **finalized in JDK 25** after incubating (JEP 429, JDK 20) and previewing four times (JEP 446/464/481/487). The one behavior change on finalization: `ScopedValue.orElse` no longer accepts `null` as its argument. Scoped values are pitched explicitly as the lower-cost, easier-to-reason-about replacement for `ThreadLocal` when combined with virtual threads and structured concurrency — a genuinely stable, non-preview API as of JDK 25/26, in contrast to structured concurrency itself.

### 11. [JEP 421: Deprecate Finalization for Removal](https://openjdk.org/jeps/421) / [JEP 486: Permanently Disable the Security Manager](https://openjdk.org/jeps/486) / [JEP 498: Warn upon Use of Memory-Access Methods in `sun.misc.Unsafe`](https://openjdk.org/jeps/498) / [JEP 472: Prepare to Restrict the Use of JNI](https://openjdk.org/jeps/472)

Four JEPs tracing the same deprecate-then-restrict-then-remove lifecycle for JDK escape hatches: `Object.finalize()` deprecated for removal in **JDK 18** (421); the Security Manager permanently disabled — no flag to re-enable it — as of **JDK 24** (486); `sun.misc.Unsafe`'s memory-access methods (`getInt`, `putLong`, etc.) now emit a warning on first use as of **JDK 24** (498), ahead of an eventual restriction; and JNI itself is being prepared for the same restricted-native-access treatment JEP 472 already applied conceptually (JDK 24), the same track that produced JDK 22's "restricted method" warnings and JDK 24's stricter enforcement of `--enable-native-access`. Each is independently a "code that worked for a decade suddenly needs an explicit opt-in flag, and eventually won't work at all" trap — exactly the shape that a version-gated lint rule should flag by JDK baseline.

### 12. [Kotlin official docs: Coroutine exceptions handling](https://kotlinlang.org/docs/exception-handling.html)

The canonical source for Kotlin's coroutine exception model, and it is unusually explicit about where developers go wrong. Verified guidance: `launch` treats an uncaught exception like `Thread.uncaughtExceptionHandler` (propagates immediately); `async` always captures the exception into the `Deferred` and only surfaces it on `.await()` — a `CoroutineExceptionHandler` installed on an `async` coroutine has **no effect**. `CoroutineExceptionHandler` is only ever consulted on a **root** coroutine (one created directly in a `CoroutineScope`/`supervisorScope`, or a direct child of `SupervisorJob`) — installing it on a nested `launch(handler) { ... }` inside another `launch` silently does nothing, and the doc calls this out with a labeled "wrong" vs "correct" example pair. `supervisorScope` makes each direct child behave like an independent root for exception-handling purposes, distinct from a plain child of `SupervisorJob`, which still needs its own handler wired explicitly. `CancellationException` is transparent to handlers by design and must be rethrown, not swallowed, by any `try/catch` wrapping a cancellable operation. Exception aggregation follows a "first exception wins, later ones attach as `.suppressed`" rule identical in spirit to Java's try-with-resources suppression.

### 13. [Kotlin `binary-compatibility-validator` README](https://raw.githubusercontent.com/Kotlin/binary-compatibility-validator/master/README.md) and [Kotlin Gradle Plugin ABI validation docs](https://kotlinlang.org/docs/gradle-binary-compatibility-validation.html)

The standalone `org.jetbrains.kotlinx.binary-compatibility-validator` Gradle plugin's own README now opens with an "IMPORTANT" callout: **"This plugin is in maintenance mode"** — critical-bug and current-Kotlin-version fixes continue, but new features go instead into "the experimental binary compatibility validation in the Kotlin Gradle plugin." That built-in replacement ships as an opt-in `kotlin { abiValidation { ... } }` DSL block (gated behind `@OptIn(ExperimentalAbiValidation::class)` for the detailed configuration surface), registering `checkKotlinAbi` (wired into `check`) and `updateKotlinAbi` tasks. Any rule recommending "add the binary-compatibility-validator plugin" without naming this migration path is citing the org's own now-secondary tool.

### 14. [Mockito 5 release notes / inline mock maker default](https://www.baeldung.com/mockito-core-vs-mockito-inline) (cross-checked against Mockito's own versioning practice)

Mockito switched its **default** `MockMaker` from the classic subclass-based maker to the inline byte-buddy-based maker in **Mockito 5.0.0**, which is what enables mocking `final` classes, `final` methods, and `static` methods (previously the separate `mockito-inline` artifact, or an explicit `org.mockito.plugins.MockMaker` resource file) without any extra configuration. Live evidence this is still actively evolving rather than a settled corner: [mockito/mockito#3795](https://github.com/mockito/mockito/pull/3795) fixes a **non-deterministic `AssertionError`** specifically when using the newer `MockMakers.SUBCLASS`, and [mockito/mockito#3173](https://github.com/mockito/mockito/pull/3173) fixes interference between spies when spying on Java `record`s — both merged PRs in the flagship repo, exactly the kind of "recurring review objection" the brief asked for.

### 15. [JUnit user guide overview](https://docs.junit.org/current/user-guide/) and merged PRs in [junit-team/junit-framework](https://github.com/junit-team/junit-framework)

The overview page itself confirms the corpus's era assumption: JUnit is versioned **6.1.3** as of this fetch (September-2026-era JUnit is JUnit 6, not 5 — the project having renamed its umbrella repo to `junit-framework`). The parallel-execution/`@ResourceLock`/`@Isolated` feature area is not a finished 2021-era feature: merged PRs in 2026 include [#4151](https://github.com/junit-team/junit-framework/pull/4151) "Allow declaring exclusive resources for child nodes," [#3889](https://github.com/junit-team/junit-framework/pull/3889) "Support programmatic registration of resource locks," [#4242](https://github.com/junit-team/junit-framework/pull/4242) "Implement Parallel Method Execution in JUnit-Vintage engine," and [#2614](https://github.com/junit-team/junit-framework/pull/2614) "Acquire global read lock in presence of other exclusive resources" — all evidence that "shared mutable static state breaks parallel JUnit execution unless you declare a resource lock" is a live, still-being-hardened mechanism, not a solved problem developers can treat as fire-and-forget.

### 16. [Testcontainers reuse documentation](https://newsletter.testcontainers.com/announcements/enable-reusable-containers-with-a-single-click) (cross-checked against community writeups)

Container reuse (`.withReuse(true)`, gated by the `testcontainers.reuse.enable=true` property in `~/.testcontainers.properties` or the `TESTCONTAINERS_REUSE_ENABLE` env var) is explicitly **not suited to CI** — the documentation's own framing is that CI wants every build reproducible and isolated, starting each container fresh. The mechanism deliberately excludes reused containers from Ryuk's automatic cleanup (the entire point of reuse is that the container survives the JVM exiting), which means a reuse flag left on by accident in a CI image, or a Ryuk failure in a Docker-in-Docker CI runner, both produce the same symptom: accumulating zombie containers. The documented mitigation for the latter is `TESTCONTAINERS_RYUK_DISABLED=true` paired with an explicit `docker container prune --filter "label=org.testcontainers=true"` cleanup step.

### 17. [Log4Shell — CVE-2021-44228](https://www.rapid7.com/blog/post/ra-cve-2021-44228-log4shell-analysis/)

Root cause as consistently stated across vendor writeups: Log4j 2's message-lookup substitution feature evaluated `${jndi:...}` patterns found *inside logged strings themselves*, and did not restrict which JNDI providers or hosts a lookup could target. An attacker who could get any string logged — a User-Agent header, a username field, anything — could trigger a remote JNDI lookup and load an attacker-controlled class. Affected versions: 2.0-beta9 through 2.14.1. Fix timeline: 2.15.0 (2021-12-10) disabled message lookups by default and restricted JNDI to specific classes/hosts; 2.16.0 (2021-12-13), three days later, removed message-lookup and JNDI support entirely after the first fix proved incomplete — itself a lesson in "the first patch for a deserialization-shaped CVE is often not the last."

### 18. [Jackson-databind polymorphic deserialization CVE criteria](https://github.com/FasterXML/jackson/wiki/Jackson-Polymorphic-Deserialization-CVE-Criteria) and [CVE-2026-54512/54513](https://github.com/advisories/GHSA-j3rv-43j4-c7qm)

Jackson's own wiki page states project policy directly: as of end of 2021, "Default Typing"-style CVE reports are **no longer accepted** regardless of gadget type used — i.e. the project's official position is that enabling global default typing is a known-dangerous configuration choice, not a bug to keep patching around. The most recent concrete instance of the underlying class still recurring: CVE-2026-54512/54513 (disclosed June 2026), where `PolymorphicTypeValidator`'s allow-list check validated only the raw container class name from a type identifier and never re-validated the *nested* generic type parameters, letting a denied class slip through as a type argument of a permitted container. Affects 2.10.0 through 2.18.7 / 2.21.3 / 3.1.3; fixed in 2.18.8 / 2.21.4 / 3.1.4.

### 19. [ZipSlip vulnerability](https://snyk.io/research/zip-slip-vulnerability) (Snyk, disclosed 2018-06-05)

Root cause: archive-extraction code that concatenates an entry's stored path directly onto the destination directory without verifying the resolved result stays inside that directory. A malicious `../../../.ssh/authorized_keys`-style entry name walks the write back up the tree. Snyk's disclosure specifically calls out that this is "especially prevalent in Java, where there is no central library offering high level processing of archive files" — every project re-implements extraction, and every reimplementation has to re-derive the same directory-containment check by hand, which is exactly why the same bug recurred across dozens of unrelated projects (including ones from HP, Amazon, Apache, Pivotal) simultaneously.

### 20. [Virtual threads and ThreadLocal pooling](https://github.com/FasterXML/jackson-core/issues/919) ("Be ready for Virtual Thread: avoid ThreadLocal pooling")

A live, real-world example of the "don't pool/cache resources per-thread under virtual threads" guidance biting a flagship library: a filed jackson-core issue specifically about auditing `ThreadLocal`-based object pooling (parser/buffer reuse) ahead of virtual-thread adoption, because virtual threads are cheap, plentiful, and short-lived by design — caching per-thread state that assumes "few, long-lived, expensive-to-create threads" defeats the entire model and creates unreclaimed per-thread garbage instead of the intended reuse.

## Recent shifts seen in this corpus

- **JDK 24 (March 2025)** fixed virtual-thread pinning on `synchronized`/`wait`/`notify` (JEP 491) and simultaneously removed `jdk.tracePinnedThreads`; permanently disabled the Security Manager (JEP 486, no re-enable flag); started warning on `sun.misc.Unsafe` memory-access use (JEP 498); and prepared restricted native access enforcement (JEP 472 lineage). Any pre-2025 advice to "migrate off `synchronized` for virtual-thread scalability" is now conditional on the JDK baseline, not a blanket rule.
- **JDK 25 (September 2025)** finalized Scoped Values (JEP 506) with one late signature change (`orElse` no longer accepts `null`) — code samples from JDK 21-24 previews of scoped values may be citing a superseded (though close) signature.
- **JDK 26 (March 2026)** shipped structured concurrency's **sixth** preview (JEP 525) — still not final, still requires `--enable-preview`, and the `Joiner` interface gained `onTimeout()` while `allSuccessfulOrThrow()`'s return type changed from a stream to a list. The JEP's own text now targets JDK 28 for finalization. This directly contradicts a common outside impression that "structured concurrency shipped in Java 21."
- **Mockito 5.0.0** (2023) flipped the *default* mock maker to the inline (final-class-capable) implementation — pre-2023 guidance that "you need `mockito-inline` to mock a final class" is now backwards for anyone on Mockito 5+.
- **JetBrains put the standalone Kotlin `binary-compatibility-validator` plugin into maintenance mode**, moving new ABI-validation feature work into an experimental `abiValidation {}` block inside the Kotlin Gradle Plugin itself — a build-tooling-location shift, not a semantic one, but real enough to make an "install this separate plugin" rule stale.
- **JDK 21 (September 2023)**'s `SequencedCollection` retrofit produced real, dated incompatibilities (OpenJDK's own May-2023 pre-release Quality Outreach heads-up, and Gradle's own JDK-21-adoption-triggered `.first()`/`.getFirst()` collision in November 2023) — a concrete, corpus-verifiable instance of "a JDK feature that adds default methods to a widely-implemented interface breaks real code."
- **Jackson's "Default Typing" CVE-acceptance policy hardened at end-of-2021** — the project now explicitly will not accept new CVEs against that configuration shape — yet the underlying validator-bypass bug class recurred in 2026 (CVE-2026-54512/54513) via a different code path (generic type-parameter nesting), showing the mitigation (`PolymorphicTypeValidator`) itself needs to be kept current, not just present.

## Contested

- **Whether `synchronized` or `ReentrantLock` is now the "right default" under virtual threads** is explicitly resolved by JEP 491 itself in favor of "either, based on the problem" — the JEP text says the earlier consensus to prefer `ReentrantLock` for virtual-thread scalability is "no longer necessary" post-JDK-24, but a great deal of 2023-2024-era blog content (predating JDK 24) still recommends the migration unconditionally. Trending toward: `synchronized` regains first-class status on JDK 24+, with `ReentrantLock` reserved for cases needing its extra flexibility (fairness, tryLock, multiple conditions) rather than pinning avoidance.
- **Whether structured concurrency is "ready to use in production"** is contested precisely because it is *still preview* through JDK 26 — some practitioner blogs (`ankurm.com`, `bazlur.ca`) walk through "JDK 25/26 production patterns" for an API that requires `--enable-preview` and is targeted for JDK 28 finalization; the corpus's own JEP sources make clear this is pre-final API surface that can still change. Trending toward: caution, or an explicit "preview API, pin the JDK/flag combination" caveat in any rule that recommends it.
- **Whether Kotlin's own `Result<T>` should ever be a public return type** is genuinely split in community practice (widely used internally, discouraged publicly by JetBrains) without a single authoritative rule this survey found — kept as P2/contested rather than promoted to a MUST.
- **Whether the standalone Kotlin BCV plugin or the new Kotlin-Gradle-Plugin `abiValidation` block is the "current" tool** is a live transition, not yet settled: the standalone plugin is explicitly still shipping fixes ("maintenance mode" is not "deprecated"), and the built-in replacement is explicitly experimental. A rule written today should probably name both and explain the direction of travel rather than picking one as canonical.
