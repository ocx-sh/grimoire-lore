## Summary

- Gradle 9.0.0 (released 2025-07-31) raised the **minimum JVM to run the Gradle Daemon to 17** (from 8); builds can still *target* lower JVMs via toolchains, but the daemon itself cannot start on JVM 8-16 anymore.
- Gradle's own **Best Practices** guide (new first-party content, not a blog post) now explicitly tells authors to **favor a `build-logic` composite build over `buildSrc`** for shared build logic — the opposite of the older community default.
- The **Java Library plugin's `api`/`implementation` split** is Gradle's own load-bearing rule: "Prefer the `implementation` configuration over `api` when possible" — `api` is for types that leak into method signatures/supertypes/public fields, everything else is `implementation`.
- **Configuration Cache Requirements** is a full contract for plugin/task authors: tasks "must not use any `Project` objects during execution," must not enumerate `System.getenv()`/`System.getProperties()` (only named lookups are safe cache inputs), and must replace `project.copy{}`/`project.exec{}` etc. with `@Inject`ed services (`FileSystemOperations`, `ExecOperations`).
- **Isolated Projects** was promoted from *experimental* to *incubating* status in Gradle 9.7.0 (2026-08-06) — still not stable, but no longer a throwaway preview; it forbids reading or mutating another project's mutable state (`tasks`, `dependencies`, `extensions`, `version`, etc.) during configuration.
- Gradle 9.x embeds **Kotlin 2.2.0 and Groovy 4.0.27**; a direct, version-specific consequence for plugin authors: **plugins written in the Kotlin DSL and built with Gradle 9.x can only run on Gradle ≥ 8.11** (the first release embedding Kotlin 2's metadata format), and Groovy-DSL plugins built with Gradle 9.x require Gradle ≥ 7.0 to run.
- Incremental build correctness for custom tasks is annotation-driven and precise: `@Classpath` vs `@CompileClasspath` (the latter ignores everything but ABI-affecting class changes), `@PathSensitive(PathSensitivity.NAME_ONLY|RELATIVE|NONE|ABSOLUTE)`, `@Nested` for custom input types, `@Internal`/`@Console` for non-inputs — `java-gradle-plugin` fails the `jar` task with a warning if any custom-task property lacks one of these.
- **TestKit's automatic plugin-classpath injection (`GradleRunner.withPluginClasspath()`) is documented as incompatible with plugins that use `compileOnly` on another plugin's API** — the recommended practice for cross-plugin API dependencies actively breaks the recommended testing shortcut, forcing a local-Maven-repo test setup instead.
- Version catalogs (`gradle/libs.versions.toml`), platforms/BOMs (`platform()`, `enforcedPlatform()`), and rich versions (`strictly`/`require`/`prefer`/`reject`, `!!` shorthand) are all first-class, actively documented mechanisms — Gradle's Best Practices page explicitly tells authors to "Use Version Catalogs to Centralize Dependency Versions."
- Dependency verification (`gradle/verification-metadata.xml`) supports SHA-256/SHA-512 checksums and PGP signatures, generated via `./gradlew --write-verification-metadata sha256,pgp`; Gradle's own docs warn that bootstrapping "trusts whatever is currently in your repositories" and must be manually reviewed, not treated as a security guarantee by itself.
- Toolchain auto-provisioning needs an explicit resolver plugin (the Foojay convention plugin, `org.gradle.toolchains.foojay-resolver-convention`) — without one, Gradle can auto-*detect* local JDKs but cannot auto-*download* a missing one.
- The Shadow plugin's Gradle-Java-ID compatibility is a real matrix, not folklore: `com.github.johnrengelman.shadow` is the pre-8.3 ID; `com.gradleup.shadow` is required from Shadow 8.3.0+; **Shadow 9.3.0+ requires Gradle ≥ 9.0 and Java ≥ 17 to build**, and Shadow ships built-in `mergeServiceFiles()`/`relocate()` for the two most common fat-jar failure modes (duplicate `META-INF/services`, package collisions).
- Spring Boot's layered-jar feature (`bootJar { layered { } }`) orders layers `dependencies → spring-boot-loader → snapshot-dependencies → application` specifically to maximize Docker layer-cache reuse — the order is a documented, load-bearing default, not arbitrary.
- Declarative Gradle remains an **explicitly experimental** project (third Early Access Preview as of this research); it is not a near-term migration target for build-logic authored today.
- Gradle's compatibility matrix is precise and load-bearing for toolchain planning: Java 25 support-for-toolchains landed in Gradle 9.1.0, Java 26 in Gradle 9.4.0; Kotlin 2.2.0 requires Gradle ≥ 9.0.0.
- Gradle's own Best Practices catalogue (8 pages: general, structuring, dependencies, tasks, performance, security, testing, index) is itself a ready-made source of MUST/AVOID rules with runnable Kotlin/Groovy DSL examples for both the "don't do this" and "do this instead" case — an unusually direct source for rule-authoring.
- JUnit Platform testing gained **non-class-based test discovery and `useJUnitJupiter()`** in Gradle 9.4.0 (2026-03-04), removing the old "empty `@Suite` class" workaround needed for Cucumber-style `TestEngine`s.
- Gradle's release cadence in this window is roughly every 6-7 weeks: 9.0 (2025-07-31), 9.1 (2025-09-18), 9.2 (2025-10-29), 9.3 (2026-01-16), 9.4 (2026-03-04), 9.5 (2026-04-28), 9.6 (2026-06-18), 9.7 (2026-08-06) — a rule set targeting "current Gradle" has a very short half-life if it hardcodes a specific 9.x point release.
- `jcenter()` was fully removed (not just deprecated) in Gradle 9.0.0, five years after its 7.0 deprecation — a concrete example of Gradle's stated multi-year deprecation timeline actually completing.
- Best Practices for Tasks explicitly tells authors: "Avoid DependsOn" (favor proper input/output wiring), "Don't resolve Configurations before Task Execution," "Don't access a `Project` instance during Task Execution," and "Use `@PathSensitivity.NONE` for file inputs and `@PathSensitivity.RELATIVE` for directories" — each with a worked before/after example.

## Survey

### 1. [Gradle User Manual — Table of Contents](https://docs.gradle.org/current/userguide/userguide.html)

The canonical nav enumerates every userguide page (crawled directly from the rendered TOC HTML, ~180 distinct `.html` targets). Confirms the full page set the brief asked for exists under `docs.gradle.org/current/userguide/`, plus an entirely new **Best Practices** section (`best_practices*.html`, 8 pages) not named in the original brief but directly relevant: it is Gradle's own first-party MUST/AVOID rule catalogue with runnable before/after examples, replacing what used to live only in blog posts and conference talks.

### 2. [Compatibility Matrix](https://docs.gradle.org/current/userguide/compatibility.html)

States: "A JVM version between 17 and 26 is required to execute Gradle. JVM 27 and later versions are not yet supported." The wrapper/Tooling API/TestKit client remain compatible with JVM 8. Table 1 (Java Compatibility) is precise per-Gradle-version: JDK 25 toolchain support lands at Gradle 9.1.0, JDK 26 at Gradle 9.4.0. Kotlin table: Gradle is "tested with Kotlin 2.0.0 through 2.4.20-Beta1"; Kotlin 2.2.0 requires Gradle 9.0.0+ (embedded), Kotlin 2.4.0 pairs with Gradle 9.7.0. "Gradle plugins written in Groovy must use Groovy 4.x for compatibility with Gradle and Groovy DSL build scripts."

### 3. [The Java Library Plugin](https://docs.gradle.org/current/userguide/java_library_plugin.html)

The `api`/`implementation` contract in full: "The `api` configuration should be used to declare dependencies which are exported by the library API, whereas the `implementation` configuration should be used to declare dependencies which are internal to the component." Rule of thumb: "Prefer the `implementation` configuration over `api` when possible." An API dependency is one exposing a type in super classes/interfaces, public method parameters, public fields, or public annotation types; everything used only in method bodies or private members is `implementation`. Callout: "The `compile` and `runtime` configurations have been removed with Gradle 7.0."

### 4. [Configuration Cache Requirements for your Build Logic](https://docs.gradle.org/current/userguide/configuration_cache_requirements.html)

The plugin-author contract for config-cache compatibility, in full detail: "Tasks must not use any `Project` objects during execution. This includes calling `Task.getProject()` while a task is running." Gives the fix pattern — `@get:Inject abstract val fs: FileSystemOperations` replacing `project.copy{}`. A full replacement table maps `project.rootDir`/`project.buildDir`/`project.copy{}`/`project.exec{}`/etc. to their Provider- or service-injection equivalents. On environment reads: "you should avoid reading the value of system properties and environment variables at configuration time"; enumerating patterns like `System.getenv().filterKeys{}` are called out by name as "discouraged" because they turn *every* env var into a cache-invalidating input.

### 5. [Isolated Projects](https://docs.gradle.org/current/userguide/isolated_projects.html)

"Isolated Projects is an **incubating** feature" (promoted from experimental in Gradle 9.7.0, released 2026-08-06 — the "Recent changes" section dates this precisely). Enforces that project-scope build logic cannot "observe or change" mutable state of other projects/builds. Lists forbidden mutable `Project` state (`tasks`, `dependencies`, `configurations`, `extensions`, `ext`, `version`, `buildDir`) vs allowed immutable state (`name`, `path`, `projectDir`). Notable landmine: "Caution: `group` and `version` are **mutable**!" even though they look like basic identity fields. `gradle.lifecycle` callbacks are "the recommended, Isolated Projects-compatible way," but "must be registered from settings, not from a project."

### 6. [Toolchains for JVM projects](https://docs.gradle.org/current/userguide/toolchains.html)

Auto-provisioning requires a **toolchain download repository** — without one configured, Gradle can auto-*detect* but not auto-*download*. The de facto standard is the [Foojay Toolchains convention plugin](https://github.com/gradle/foojay-toolchains): `id("org.gradle.toolchains.foojay-resolver-convention").version("1.0.0")` in `settings.gradle.kts`. "Gradle only downloads JDK versions for GA releases. There is no support for downloading early access versions." Toolchain declaration order in `toolchainManagement{}` matters — first matching repository wins. `./gradlew -q javaToolchains` lists every detected JDK with its detection source.

### 7. [Testing Build Logic with TestKit](https://docs.gradle.org/current/userguide/test_kit.html)

Cross-version testing is a documented, first-class pattern: `GradleRunner.create().withGradleVersion(gradleVersion)...` inside a Spock `where:` block iterating `['5.0', '6.0.1']`. Critical, sharply-worded gotcha: "The automatic classpath injection provided by `GradleRunner.withPluginClasspath()` is **incompatible** with plugins that use `compileOnly` to depend on another plugin's API," symptom "`ClassNotFoundException`," fix: publish to a local Maven repo and pull the plugin from there in the test's `settings.gradle`. TestKit builds run in a **separate process** via the Tooling API — `GradleRunner` daemons are distinct from normal build daemons and auto-shut-down after tests. `org.gradle.testkit.dir` / `withTestKitDir()` control where working directories persist (not deleted by default).

### 8. [Gradle Plugin Development Plugin (`java-gradle-plugin`)](https://docs.gradle.org/current/userguide/java_gradle_plugin.html)

Auto-applies `java-library`, adds `gradleApi()` on the `api` configuration, and "performs validation of plugin metadata during `jar` task execution": checks a plugin descriptor exists, has `implementation-class`, that class resolves in the jar, and "Each property getter or the corresponding field must be annotated with a property annotation like `@InputFile` and `@OutputDirectory`." Failed validations produce warnings at `jar` time, not build failures — a rule could tighten this by running `./gradlew validatePlugins` explicitly.

### 9. [Publishing Plugins to the Gradle Plugin Portal](https://docs.gradle.org/current/userguide/publishing_gradle_plugins.html)

`com.gradle.plugin-publish` (current major "2.0.0") auto-applies `java-gradle-plugin` and `maven-publish` since 1.0.0. Credentials: `gradle.publish.key`/`gradle.publish.secret` Gradle properties or `GRADLE_PUBLISH_KEY`/`GRADLE_PUBLISH_SECRET` env vars for CI. Callout: "The group and artifact must reasonably represent the organization, person, and the plugin." `./gradlew publishPlugins --validate-only` validates without uploading. Applying the `signing` plugin auto-signs artifacts (since 1.0.0); applying `com.gradleup.shadow` auto-fat-jars the plugin (since 1.0.0). Publication goes through a manual Portal "approval process" that "can take a few days."

### 10. [Incremental build](https://docs.gradle.org/current/userguide/incremental_build.html)

The full annotation reference table: `@Nested` (custom types with their own annotated properties), `@Console`/`@Internal` (neither input nor output — but still required so `java-gradle-plugin`'s validator doesn't flag the property), `@SkipWhenEmpty` (implies `@Incremental`, produces a `NO-SOURCE` outcome), `@PathSensitive(PathSensitivity.NAME_ONLY)` (moving files without changing content doesn't invalidate), `@NormalizeLineEndings` (CRLF/LF-insensitive hashing). Classpath-specific: `@Classpath` treats jar/directory order as significant but ignores internal file order/timestamps; `@CompileClasspath` additionally "ignore[s] changes to everything but class files" and uses ABI-level class analysis so implementation-only changes in a dependency don't invalidate compilation of consumers.

### 11. [Declaring Versions and Ranges — rich versions](https://docs.gradle.org/current/userguide/dependency_versions.html)

Full hierarchy from strongest to weakest: `strictly`/`!!` (excludes any non-matching version, can downgrade, fails resolution if no acceptable transitive version exists), `require` (default behavior for a direct dependency — floor, not ceiling), `prefer` (softest, only applies absent a stronger constraint, doesn't support dynamic versions), and `reject` (outside the hierarchy, fails resolution if selected). Shorthand: `"org.slf4j:slf4j-api:[1.7, 1.8[!!1.7.25"`. Explicit warning: "Using `strictly` in a library requires careful consideration, as it affects downstream consumers." Rich version data survives in Gradle Module Metadata but is lossy when converted to Ivy/Maven POM (only the highest-priority term publishes, `reject` is dropped entirely).

### 12. [Verifying Dependencies](https://docs.gradle.org/current/userguide/dependency_verification.html)

Bootstrapping command: `./gradlew --write-verification-metadata sha256` (or `sha256,pgp`) writes `gradle/verification-metadata.xml`. Explicit security caveat, stated plainly: bootstrapping "trusts whatever is currently in your repositories. If a malicious dependency has already been introduced... Gradle will record the compromised artifact's checksum," so "you must **review the generated verification file**." Supports MD5/SHA1/SHA-256/SHA-512 but states only SHA-256/SHA-512 "are considered secure for modern use." Signature verification is PGP-only (ASCII-armored `.asc` files) and only proves "the artifact was signed by a specific key," not that the signatory was legitimate.

### 13. [Best Practices for Structuring Builds](https://docs.gradle.org/current/userguide/best_practices_structuring_builds.html)

"Favor `build-logic` Composite Builds for Build Logic" — the section head is unambiguous: "The preferred location for build logic is an included build (typically named `build-logic`), **not** in `buildSrc`." Reasons given: classloader/dependency-resolution differences, coarser invalidation (any `buildSrc` change invalidates the whole build vs. only affected subprojects for an included build), independent buildability/publishability, and `buildSrc` auto-applying the `java` plugin unconditionally. Caveat: Settings plugins are the one case where `build-logic` needs `pluginManagement{}` inclusion, which "reduces Build Caching capability" — recommends a separate minimal `build-logic-settings` included build for just those.

### 14. [Best Practices for General / Dependencies / Tasks](https://docs.gradle.org/current/userguide/best_practices_general.html) ([dependencies](https://docs.gradle.org/current/userguide/best_practices_dependencies.html), [tasks](https://docs.gradle.org/current/userguide/best_practices_tasks.html))

A dense rule catalogue, each with runnable before/after Kotlin+Groovy DSL examples: "Do Not Use Internal APIs" (any package segment named `internal`, or type suffixed `Internal`/`Impl` — "types have `Internal`... treat these... as subject to unannounced breaking changes... during any new Gradle release, even during minor releases"); "Avoid `afterEvaluate`"; "Use Version Catalogs to Centralize Dependency Versions"; "Don't Explicitly Depend on the Kotlin Standard Library"; "Always Declare Attributes on Consumable and Resolvable Configurations"; "Avoid DependsOn"; "Favor `@CacheableTask` and `@DisableCachingByDefault` over `cacheIf(Spec)`"; "Don't resolve Configurations before Task Execution"; "Use `@PathSensitivity.NONE` for file inputs and `@PathSensitivity.RELATIVE` for directories"; "Don't access a `Project` instance during Task Execution" (this rule appears independently in both the Best Practices pages and Configuration Cache Requirements — Gradle treats it as a standalone correctness rule, not only a config-cache migration concern).

### 15. [Upgrading to Gradle 9.0.0](https://docs.gradle.org/current/userguide/upgrading_major_version_9.html)

Runtime floor: "Gradle 9.0.0 requires a Java Virtual Machine (JVM) version 17 or higher to run the Gradle Daemon." Kotlin/Groovy embed bumps: Kotlin 2.0.21→2.2.0, Groovy 3.0.24→4.0.27 — both are described as carrying real breaking changes for build-logic authors (Kotlin: `this@Build_gradle`-style labels no longer resolve the script instance; Groovy: `DELEGATE_FIRST` closure lookup order changed, `is`-prefixed Boolean getters no longer auto-recognized as properties). Plugin-version floors, stated as hard requirements: **Kotlin-DSL plugins built with Gradle 9.x only run on Gradle ≥ 8.11** (first release embedding Kotlin-metadata-version-2); **Groovy-DSL plugins built with Gradle 9.x require Gradle ≥ 7.0**; minimum supported Kotlin Gradle Plugin is 2.0.0; minimum supported Android Gradle Plugin is 8.4.0. "Project directories must exist and be writeable" is now a hard failure, not a warning. `jcenter()` is fully removed (deprecated since 7.0). Default test-framework versions bumped for JVM Test Suite users: JUnit Jupiter 5.12.2, TestNG 7.11.0, Spock 2.3.

### 16. [Gradle 9.4.0 Release Notes](https://docs.gradle.org/9.4.0/release-notes.html) (released 2026-03-04)

Introduces **non-class-based testing**: JUnit Platform `TestEngine`s can now discover tests defined outside JVM classes (e.g. XML test definitions, Cucumber feature files) via `useJUnitJupiter()` on a `JvmTestSuite`, eliminating the old "empty `@Suite` class" or `@RunWith(Cucumber.class)` workaround. Recommends storing non-class test definitions under the conventional `src/<TEST_TASK_NAME>/definitions`.

### 17. [Gradle 9.7.0 Release Notes](https://docs.gradle.org/9.7.0/release-notes.html) (released 2026-08-06, current stable at research time)

Isolated Projects promoted experimental→incubating in this release; failures now stop at "the first violation by default" (a new Diagnostics mode exists to surface all violations in one run without failing fast). Test-framework-initialization failures (TestNG/JUnit 4/JUnit Platform startup errors) now "surface... in the console by default."

### 18. [Version Catalogs](https://docs.gradle.org/current/userguide/version_catalogs.html)

Standard mechanism (`gradle/libs.versions.toml`) for centralizing dependency coordinates and versions across a multi-project build; supports importing a published catalog, importing from a file, and combining multiple catalogs. Gradle's own Best Practices for Dependencies page names this the top dependency-management recommendation.

### 19. [The Java Platform Plugin](https://docs.gradle.org/current/userguide/java_platform_plugin.html)

Publishes/consumes BOM-style constraint platforms; documents "API and runtime separation" and "Local project constraints." `enforcedPlatform()` overrides even explicit consumer version choices — a mechanism specific enough to warrant its own rule about when it is (rarely, for apps) vs isn't (never, for libraries) appropriate.

### 20. [Shadow Gradle Plugin docs](https://gradleup.com/shadow/) and [GitHub README](https://raw.githubusercontent.com/GradleUp/shadow/main/README.md)

Compatibility table is explicit and versioned: `com.github.johnrengelman.shadow` for Shadow ≤8.0.0 series; **`com.gradleup.shadow` required from Shadow 8.3.0+** (after the maintenance transfer, tracked as [GradleUp/shadow#908](https://github.com/GradleUp/shadow/issues/908)); **Shadow 9.3.0+ requires Gradle ≥ 9.0 and Java ≥ 17** to build the plugin itself. Built-in mitigations for the two classic fat-jar failure modes: `mergeServiceFiles()` for colliding `META-INF/services/*` provider-config files, and `relocate("junit.framework", "shadow.junit")`-style package relocation to avoid classpath collisions between the shaded dependency and the consumer's own copy.

### 21. [Spring Boot Gradle plugin — Packaging](https://docs.spring.io/spring-boot/gradle-plugin/packaging.html)

Layered-jar feature (`bootJar { layered { } }`) exists specifically for Docker layer-cache reuse. Default layer order — "least likely to change... first" — is `dependencies` → `spring-boot-loader` → `snapshot-dependencies` → `application`; this ordering is the documented mechanism, not an implementation detail, and changing it defeats the caching benefit. `includeTools = false` removes the `spring-boot-jarmode-tools` bootstrap dependency that layered jars add by default.

### 22. [Declarative Gradle](https://declarative.gradle.org/)

Self-described as "an **experimental** project, now in its third Early Access Preview," with an explicit feedback-solicitation banner. Not a current-practice target; a rule set should not steer authors toward `.gradle.dcl` syntax as anything but a future-watch item.

## Recent shifts seen in this corpus

- **Gradle 9.0.0 (2025-07-31)**: minimum JVM to run the Daemon raised from 8 to **17**; embedded Kotlin bumped 2.0.21→2.2.0; embedded Groovy bumped 3.0.24→4.0.27 (both carrying real breaking changes for build-logic authors); `jcenter()` fully removed after a 2020 (7.0) deprecation; Kotlin-DSL plugins built on 9.x now require a Gradle ≥8.11 consumer to run; incompatible-task config-cache entries are now always discarded even in warning mode (the old "ignore problems and still cache" escape hatch is gone). Source: [upgrading_major_version_9.html](https://docs.gradle.org/current/userguide/upgrading_major_version_9.html), [Gradle 9.0.0 release notes](https://docs.gradle.org/9.0.0/release-notes.html).
- **Gradle 9.1.0 (2025-09-18)**: Java 25 toolchain support added. Source: [compatibility.html](https://docs.gradle.org/current/userguide/compatibility.html).
- **Gradle 9.4.0 (2026-03-04)**: non-class-based JUnit Platform testing plus `useJUnitJupiter()`, retiring the old empty-`@Suite`-class Cucumber workaround. Source: [Gradle 9.4.0 release notes](https://docs.gradle.org/9.4.0/release-notes.html).
- **Gradle 9.4.0**: Java 26 toolchain support added. Source: [compatibility.html](https://docs.gradle.org/current/userguide/compatibility.html).
- **Gradle 9.7.0 (2026-08-06, current stable)**: Isolated Projects promoted from *experimental* to *incubating*; violations now fail fast on the first one by default (previously ran to completion collecting all violations), with a new opt-in Diagnostics mode for the old collect-all behavior; `Project.getProperties()` treated as an Isolated Projects incompatibility while also being generally deprecated. Source: [isolated_projects.html](https://docs.gradle.org/current/userguide/isolated_projects.html), [Gradle 9.7.0 release notes](https://docs.gradle.org/9.7.0/release-notes.html).
- **Shadow plugin, ongoing since 8.3.0**: plugin ID migrated `com.github.johnrengelman.shadow` → `com.gradleup.shadow` after a maintainer-transfer ([GradleUp/shadow#908](https://github.com/GradleUp/shadow/issues/908)); Shadow 9.3.0+ raised its own floor to Gradle ≥9.0 / Java ≥17. Older exemplar repos still on the `johnrengelman` ID or an 8.x Shadow version are on borrowed time. Source: [gradleup.com/shadow](https://gradleup.com/shadow/).
- **Gradle's own docs, ongoing (Best Practices pages are new first-party content, not dated to one release)**: the `buildSrc` → `build-logic` composite-build recommendation reverses what was, for years, the community-default pattern (and is still what most tutorials and the frame's own exemplar table show as `buildSrc` for several repos). This invalidates "put your convention plugins in buildSrc" as current best advice, though `buildSrc` remains fully supported and is still the pragmatic choice for prototyping or very-large-subproject-count builds per the same page's own caveat.

## Contested

- **`buildSrc` vs. `build-logic` composite build**: Gradle's own Best Practices page now recommends `build-logic` for essentially all convention-plugin use, but simultaneously documents two real caveats where `buildSrc` (or a special-cased minimal included build) is still preferable — Settings plugins, and builds with a very large number of subprojects where per-subproject classpath variation from `build-logic` plugin combinations can break Build Services in hard-to-diagnose ways. The exemplar corpus (per the frame's fetch table) still shows `buildSrc` as the dominant pattern in real, actively-maintained repos (kotlinx.coroutines, mockito, micronaut-core, dagger, grpc-java, testcontainers-java), so the "trending" direction is real but adoption lags the documentation by a wide margin as of this research.
- **Fat/shadow jars — library anti-pattern vs. app necessity**: nothing in this corpus states a library should never be shaded; the framing in this corpus (Shadow's own docs plus Spring Boot's layered jars) treats fat/executable jars purely as an *application-distribution* concern, never mentioning shading a *library* artifact at all. The frame's hypothesis that "fat jars may be an anti-pattern for libraries" is not contradicted here, but also not directly confirmed by Gradle/Shadow's own docs — it would need cross-checking against an SDK-authoring or library-quality-focused scout.
- **Isolated Projects — is it "coming soon" or "not yet real"?** The status jump from experimental to incubating in the very latest release (9.7.0, one month before this research) is a genuine trend toward stabilization, but the same release notes list two constraint categories ("Cross-build access constraints are not fully enforced yet," "Build-to-project access constraints are not fully enforced yet.") as explicitly incomplete — a rule set that treats Isolated Projects as a hard gate today would be ahead of where the feature itself currently stands.
- **Declarative Gradle**: the project's own site brands it experimental (third EAP); it is not contested within this corpus so much as clearly pre-production — but it is worth flagging because the frame names it as one of several "adjacent futures," and nothing in Gradle's canonical docs treats it as a migration target yet.
