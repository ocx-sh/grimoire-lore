## Summary

- Comment density has never been shown to predict quality on its own: the founding large-N study (Arafat & Riehle, 5,229 OSS projects, 2009) reports a **19% mean / 16.7% median**, independent of team and project size, and finds it declining only slightly with project age — density is a *description*, not a target.
- Purpose predicts density far better than language or team size: He (2019, 150 repos, 5 languages) found **application-type projects average 0.06 (Java) to 0.11 (JavaScript)**, reusable-library projects 0.18-0.27, and education-purpose projects 0.27-0.58 — the fleet's 1:4-1:6 hypothesis sits closest to the *application* band, not the corpus-wide average.
- A large minority of what gets counted as "comment" isn't information about the code at all: Pascarella & Bacchelli's 6-category/16-subcategory Java taxonomy (2,000 files, >28,000 comment lines) found **59% of comment lines fall in categories (Under-Development, Style/IDE, Metadata, Discarded) that "do not reflect any aspect of readability or maintainability"** — a flat ratio gate punishes the wrong lines.
- A named-smell taxonomy already exists and maps closely onto the fleet's own ad hoc categories: Jabrayilzade et al. (EMSE 2024, 2,448 comments / 8 OSS projects) define **11 inline comment smells** — misleading, obvious, no-comment-on-non-obvious-code, commented-out-code, irrelevant, task, **too much information**, attribution, beautification, **non-local**, vague — giving a citable vocabulary for "essay," "plan ID," and "narration."
- Content correctness, not comment volume, drives LLM code-generation quality: comments transplanted from a passing solution raise pass@1 by **+17.2%**, comments from a failing solution give no reliable gain, and comments written for a different problem cut pass@1 by **-20.8%** — while how often comments appear "predicts nothing" (arXiv 2609.09242, LiveCodeBench).
- The same content asymmetry holds for bug-fixing, not just generation: comments present at both training and inference time raise automated bug-fix accuracy **up to 3x**, implementation-detail comments are the most effective type, and training with comments never hurts instances that lack them (arXiv 2601.23059).
- Misleading natural-language cues — of which a stale or wrong comment is one instance — reliably override an LLM's own code reasoning: CodeCrash (NeurIPS 2025, 1,279 questions, 17 models) measured a **23.2% average accuracy drop**, still **13.8%** with chain-of-thought, and a distinct "Reasoning Collapse" failure mode in QwQ-32B.
- Comment sensitivity is task-dependent, and the task the cleanup skill performs is the *most* sensitive one measured: deactivating a model's internal "comment concept" swings performance from **-90% (code refinement) to +67% relative gain (code translation)**, with code completion nearly insensitive — a blanket "strip the comments" pass is the wrong grain (arXiv 2512.16790, "Inside Out").
- Agents have a measured, structural bias against deletion that directly threatens a "shrink the essay, leave one line" cleanup rule: on SWE-bench-adjacent tasks, deletion recall tops out at **71.7%** even on solved instances, models localize the right file 92.5-94.4% of the time but remove the exact line only **44.6-51.6%** of the time, and 29% of passing patches show a "Guard-and-Go" pattern that keeps the old logic alive behind a new conditional (arXiv 2607.28887, CanItDelete benchmark).
- Agents mostly do **not** read decision records or classical documentation unprompted: across 557 agentic sessions and 33,097 agentic PRs, self-initiated documentation consultation is common (70.2%) but **60.5%** of what gets consulted is agent-facing instruction files/working notes, only **10.6%** classical docs, and **1.3%** API references — and consulting documentation correlates with *less* immediate testing, not more (arXiv 2608.20195).
- When agents do consult something, they rarely verify against it: "actionability and verifiability lack consistent behavioural support," and no explicit documentation-based validation sequences were observed (arXiv 2608.20195) — an embedded-ADR pointer convention assumes more agent diligence than is measured.
- Path-scoped agent-rule files (AGENTS.md/CLAUDE.md-style) already exist at scale but skew heavily toward what to build, not what not to break: across 2,303 files / 1,925 repos, test procedures (75.9%), implementation details (70.8%), and architecture (68.1%) dominate, while security (14.8%) and performance (14.5%) are rare — and the files "evolve like configuration code" rather than staying static (arXiv 2511.12884).
- LLM-authored comments skew hard toward low-information types: in one measured repository, **97% of LLM-detected comments fell into the Meta and Explanation categories**, and the prevalence of LLM-flagged code is *declining* 2021-2025 in the repositories studied — "AI always over-comments" is a moving target tied to model generation, not a fixed fact (arXiv 2607.01867).
- Each individual AI-written comment is not the problem: expert judges rated AI-generated Javadoc equivalent to (58.8%) or better than (27.7%) the human original on 142 classes/273 methods, and standard IR metrics (BLEU/ROUGE/METEOR) did not reliably track that human judgment (arXiv 2408.14007).
- Link rot is measured, not assumed: **~10% of 9.6 million links in source-code comments are dead**, targets evolve even when the link text doesn't, and license/homepage/spec links are the most common category (Hata et al., ICSE 2019) — this generalizes the fleet's own finding of a gitignored plan path cited from tracked code.
- Comment-code inconsistency correlates with bugs (Wen et al., ICPC 2019, widely reported as ~1.5x more bug-prone for inconsistent changes) but this figure could not be independently re-verified from primary text in this pass — the author's PDF link is dead and the ACM page returns 403; treat as reported, not confirmed.
- Comprehension effects are real but small, variable, and quality-gated, not volume-gated: a 2025 eye-tracking study (20 CS students) found comment effects on performance ranging **from -30% to +34% depending on snippet**, comments guide up to 23% of fixations, and — the more load-bearing finding for a cold-reader eval — participants overwhelmingly used a **"code-first" strategy**, reading code before comments, not the reverse.
- Self-admitted technical debt (SATD) comments are frequently lost by accident, not by design: 20-50% are deleted incidentally alongside the code/method they annotate, and developers acknowledge the removal in a commit message only 8% of the time (Zampetti et al.) — reported via secondary aggregation only in this pass, not independently fetched.
- Automated staleness/inconsistency detectors are useful but not gate-grade: DocChecker reaches 72.3% accuracy on inconsistency detection (beating GPT-3.5/CodeLlama by ~10 points), and Panthaplackel et al.'s best just-in-time model reaches 87.1% F1 on a cleaned, balanced sample but drops to 79.6% F1 on the full, realistically-imbalanced test set.
- Re-verification caught two citation errors worth fixing at the source: (1) the "already covered" claim that arXiv 2605.13280 sampled "5,869 code-generation scenarios" does not match the fetched abstract's **2,735** (1,000 WoC + 1,735 LeetCode); (2) He (2019) is often summarized (including in this program's own prior search) as finding a "30-60% optimal" density band — that phrase and claim do **not** appear anywhere in the fetched paper text, which makes no optimality claim at all.

## Survey

### 1. Arafat & Riehle, "The Comment Density of Open Source Software Code" (ICSE 2009 NIER)

Fetched in full ([PDF](https://dirkriehle.com/wp-content/uploads/2009/02/icse-2009-nier-for-web.pdf)). Measures comment density (comment lines / total lines) across **5,229 active OSS projects** (a 2008 Ohloh snapshot, ~30% of the estimated active-OSS population, analysis cut off at 2007-12-31). Result: **mean = 0.1867, median = 0.1674, stdev = 0.1088**, reported in the text as "about 19%." Comment density correlates with project size at **r = -0.0079** (independent) and with team size at **r = -0.0255** for teams under 20 committers (independent), but with project age at **r = -0.9054** — a statistically significant decline that the authors themselves call "rather small" in absolute terms (19.13% at month 1 down to ~18.08% at month 48). Small commits (1-100 SLoC) run hotter, mean 0.25. Explicitly treats all comment lines as equal regardless of content — a limitation the authors name themselves, and the one this program's classifier (bucketing interface/licence/tool-directive separately) already improves on. Era: pre-dates modern doc-comment tooling (rustdoc, docstring linters) and predates any LLM authorship; treat as a historical floor, not a target.

### 2. Pascarella & Bacchelli, "Classifying Code Comments in Java Open-Source Software Systems" (MSR 2017)

Fetched in full ([PDF](https://sback.it/publications/msr2017a.pdf)). Builds an empirically-grounded taxonomy from **6 Java OSS projects** (Spark, Eclipse CDT, Guava, Hadoop, Guice, Vaadin), inspecting **2,000 files** and manually classifying **>15,000 comment blocks / >28,000 comment lines**, externally validated with 3 professional developers (agreement >92%). The taxonomy has 6 top categories and 16 subcategories: **Purpose** (Summary, Expand, Rationale), **Notice** (Deprecation, Usage, Exception), **Under Development** (TODO, Incomplete, Commented-out code), **Style & IDE** (Directive, Formatter), **Metadata** (License, Ownership, Pointer), **Discarded** (Auto-generated, Noise). Key finding for a ratio-based check: **"59% of lines of comments should not be considered [for a code/comment quality metric]... as they do not reflect any aspect of readability and maintainability"** (categories C-F). SUMMARY is the single most prominent subcategory but only 24% of lines, and averages just **1.4 lines per block** — the cleanest available human-written baseline for a "why"-comment length cap. LICENSE and EXPAND blocks average >11 lines, the longest categories measured. A supervised classifier (naive Bayes / decision trees) reaches line-level precision/recall in the 0.6-1.0 range depending on category (weakest on EXPAND, strongest on LICENSE/DEPRECATION).

### 3. Rani, Blasi, Stulova, Panichella, Gorla & Nierstrasz, "A Decade of Code Comment Quality Assessment: A Systematic Literature Review" (J. Systems and Software 2022 / [arXiv:2209.08165](https://arxiv.org/abs/2209.08165))

Fetched (abstract page). Screens **2,353 papers**, retains **47** as directly relevant. Identifies **21 distinct comment-quality attributes** in the literature but finds actual studies concentrate on **4** of them, with "a clear predominance of checking consistency between comments and the code." Names the field's structural gaps directly relevant to this program: techniques are overwhelmingly **Java-only** (a caution against porting Rust/Python/TS thresholds from Java-derived numbers unmodified), assessment relies on **manual heuristics rather than automated measurement**, tools target narrow comment types (Javadoc, TODO) rather than a general model, and **there is no universally accepted definition of "comment quality"** — an explicit invitation for this program to state its own operational definition rather than assume one exists.

### 4. He, "Understanding Source Code Comments at Large-Scale" (ESEC/FSE 2019)

Fetched in full ([PDF](https://hehao98.github.io/files/2019-comment.pdf)). Samples the 30 most-starred GitHub repos in each of **5 languages** (Python, Java, C++, JavaScript, Go; April 2019), **150 projects** total. Overall: **avg = 0.2124, stdev = 0.1807, max = 1.27, min = 0.003**. Python and Java comment density is significantly higher than C++/JavaScript/Go (Wilcoxon signed-rank, e.g. Python-vs-C++ p = 0.0003), attributed to widely-adopted doc-generation tooling (Javadoc, docstring conventions) rather than an inherent language property. Manually inspects 30 Java + 30 JavaScript projects by declared purpose and finds density tracks purpose far more than language: **Education 0.575 (Java) / 0.265 (JS), Software Reuse 0.274 / 0.176, Application 0.064 / 0.105** — explicitly noting the sample is too small for significance testing and flagged as future work never completed by the author. Finds **no correlation** between team size (contributor count) and density, contradicting the initial H3 hypothesis. **Correction to prior citation**: no "30-60% optimal density" claim exists anywhere in this paper's fetched text; that figure, previously repeated as this paper's finding, does not originate here and should not be attributed to it.

### 5. Jabrayilzade, Yurtoğlu & Tüzün, "Taxonomy of inline code comment smells" (Empirical Software Engineering 2024) and its follow-up, "Towards Automated Detection of Inline Code Comment Smells" ([arXiv:2504.18956](https://arxiv.org/abs/2504.18956))

The detection follow-up fetched in full ([HTML](https://arxiv.org/html/2504.18956v1)), which restates the original taxonomy's scope as background: **2,448 manually labeled inline comments** from **8 OSS projects**, 4 Java (Anki-Android, Jitsi, Moshi, Light-4j) and 4 Python (Requests, Scrapy, Kivy, Scikit-learn), evenly split. The 11 named smells: **misleading, obvious, no-comment-on-non-obvious-code, commented-out-code, irrelevant, task, too-much-information, attribution, beautification, non-local, vague**. Several map directly onto categories this program already treats informally: "too much information" ≈ essay, "non-local" ≈ misplaced/dead pointer, "attribution" ≈ plan-ID/authorship narration, "beautification" ≈ decorative headers. The detection paper trains classical ML (Random Forest 69% accuracy, MCC 0.44) and an LLM classifier (GPT-4, 34%→55% accuracy after training-data augmentation) to flag smells automatically — evidence that automated smell detection is feasible but still well short of gate-grade reliability. The original taxonomy paper's own PDF was not independently fetchable in this pass (paywalled/no open mirror found); its category list here is corroborated by the follow-up paper's own restatement, which counts as an independent primary re-derivation, not a search snippet.

### 6. Classic and modern comprehension experiments: Woodfield, Dunsmore & Shen (ICSE 1981) and Abdelsalam et al., "The Effect of Comments on Program Comprehension: An Eye-tracking Study" (Empirical Software Engineering 2025)

The 1981 paper (Woodfield, Dunsmore & Shen, "The Effect of Modularization and Comments on Program Comprehension," ICSE 1981, pp. 215-223) could **not** be independently fetched in this pass — no open-access text was found; it is cited here only by its lineage and title, and its "comments significantly enhance comprehension" claim should be treated as reported-not-verified until re-read. The 2025 study was fetched in full via its local PDF mirror ([se.cs.uni-saarland.de](https://www.se.cs.uni-saarland.de/publications/docs/APB+25.pdf)) after the Springer-hosted version required authentication. Design: **20 CS students**, mixed quantitative (correctness, response time) and eye-tracking (fixation count/duration, reading linearity, gaze strategy) plus a post-questionnaire. Headline: the effect of comments on comprehension performance **"varies significantly across code snippets, ranging from a 30% decrease to a 34% increase"** — comments are not uniformly helpful. Comments account for **up to 23% of all fixations** and promote more linear reading, but participants predominantly used a **"code-first" strategy**, reading code before consulting comments, not the reverse. Comments were rated subjectively positive for clarity, but "this favorable perception did not consistently translate into improved performance" — perceived helpfulness and measured helpfulness diverge. Thematic analysis specifically flags **misleading or redundant comments** as the criticized failure mode, and notes comment presence can *increase* perceived complexity even when comments are liked. Directly informs the program's reason-recovery eval: a cold reader's default path to a non-obvious line already goes through the code first, so a comment (or its replacement, a pointer) has to survive being consulted second, not first.

### 7. Hata, Treude, Kula & Ishio, "9.6 Million Links in Source Code Comments: Purpose, Evolution, and Decay" (ICSE 2019 / [arXiv:1901.07440](https://arxiv.org/abs/1901.07440))

Fetched (abstract page). Studies **9,654,702 links** embedded in source-code comments across a large GitHub corpus. **~10% are dead** at time of study. Link targets cluster around licenses, project homepages, and specifications. Central asymmetry: **"links are rarely updated, but many link targets evolve"** — the comment's pointer stays frozen while the thing it points to moves or disappears, which is exactly the failure mode the fleet's own prior research found in a gitignored, renamed plan file cited from tracked Rust source. The authors demonstrate the problem is fixable in practice by submitting pull requests to repair broken links, most of which were merged — evidence that a pointer-tracked-file check (does the named file exist in `git ls-files`?) is both diagnostic and actionable, not merely descriptive.

### 8. Comment-code inconsistency and its detection: Wen et al. (ICPC 2019), Panthaplackel et al. (AAAI 2021), DocChecker ([arXiv:2306.06347](https://arxiv.org/abs/2306.06347))

**Wen, Nagy, Bavota & Lanza, "A Large-Scale Empirical Study on Code-Comment Inconsistencies"** (ICPC 2019) is described consistently across independent secondary listings (ACM DL abstract, Semantic Scholar) as the largest study to date of code/comment co-evolution, finding inconsistent changes **~1.5x more likely** to be part of a bug-introducing commit. The author's self-hosted PDF is a dead link and the ACM DL page returns HTTP 403 to automated fetch; **this figure could not be independently re-verified from primary text in this pass** and should be treated as reported, not confirmed, until re-fetched (e.g. via institutional access or the paper's GitHub replication package, which does exist at [USI-INF-Software/ICPC2019-code-comment-inconsistencies](https://github.com/USI-INF-Software/ICPC2019-code-comment-inconsistencies)).

**Panthaplackel, Li, Gligoric & Mooney, "Deep Just-In-Time Inconsistency Detection Between Comments and Source Code"** (AAAI 2021) was fetched in full ([PDF](https://ojs.aaai.org/index.php/AAAI/article/view/16119/15926)). Trains a deep model on **40,688 comment/code-change examples**, evaluated on a curated, class-balanced sample of **300 examples** (50 positive/50 negative per comment type) plus a realistically-imbalanced full test set. Best model (HYBRID with hand-engineered features) reaches **F1 = 87.1% / accuracy = 87.8%** on the cleaned balanced sample but only **F1 = 79.6% / accuracy = 81.5%** on the full test set — the gap between a curated benchmark and deployment-realistic data is itself a finding for anyone building a check on this technique.

**DocChecker** ([arXiv:2306.06347](https://arxiv.org/abs/2306.06347), EACL 2024 demo) was fetched (abstract page). Reaches **72.3% accuracy** on the Inconsistency Code-Comment Detection task, beating StarCoder by ~30 points and GPT-3.5/CodeLlama by ~10 points despite those being pretrained on larger corpora, built on a UniXcoder backbone with joint code-text contrastive, classification, and generation objectives. 72.3% is well above chance but well short of what a hard CI gate would want — supports "detector as a triage signal, not a gate" rather than "detector as the check."

### 9. Self-admitted technical debt (SATD): Potdar & Shihab (ICSME 2014), Maldonado & Shihab (MTD 2015), Zampetti et al. (ICSME 2017/2018)

None of these three were independently fetchable as primary text in this pass (IEEE/ACM paywalls, no open mirror located); reported here via consistent, multiply-corroborated secondary summaries and treated as directional, not confirmed-primary. **Potdar & Shihab** coined "self-admitted technical debt" for comments that consciously flag incomplete, defective, or sub-optimal code, manually analyzing comments from **4 large OSS systems** and finding SATD comments present in **2.4-31% of files** depending on project. **Maldonado & Shihab** manually reviewed **33,093 heuristically-filtered comments across 5 Java projects**, confirming **2,457** as SATD and classifying them into **5 categories**: design, requirement, defect, documentation, and test debt — a pre-existing, citable taxonomy that the fleet's own ad hoc "history narration" bucket should be checked against rather than reinvented. **Zampetti et al.** studied how SATD gets resolved across 5 Java OSS projects and found **20-50% of SATD comments are removed by accident** — the annotated method or class is deleted for unrelated reasons, not because the debt was paid down — and developers acknowledge the removal in a commit message only **8%** of the time. This is a direct, measured counter-argument to "history goes in the commit body": if the comment and its code usually leave together, unremarked, the commit-body destination is unused in practice even when policy asks for it.

### 10. LLM-generated code readability: "The Readability Spectrum" ([arXiv:2605.13280](https://arxiv.org/abs/2605.13280))

Fetched in full (HTML). Sample: **2,735 code-generation scenarios** (1,000 from World of Code, 1,735 from LeetCode) — **not** the 5,869 figure this program's own frame text carried forward from prior research; that number does not match the primary source and should be dropped. Table VI (defect counts, human-written vs. LLM-generated): Excessive Complexity 41/48, **Redundant Comments 3/24**, Inconsistent Style 58/15, Poor Structure 24/16, Poor Naming 22/21, Magic Values 7/8, Code Duplication 6/2, Deficient Comments 60/10, High Coupling 0/0. Redundant Comments is the sharpest human/LLM split in the whole table (3 vs. 24, an 8x swing) and is LLM code's second-most-frequent defect after Excessive Complexity — a strong, now precisely-sourced confirmation of the "AI over-comments" claim, distinct from (and better-grounded than) the density studies above. Human-written code's dominant defects run the other way: Deficient Comments and Inconsistent Style. The paper separately names LLM-only defect categories (Unknown API usage, Redundant Variables, Overblanking) not present in the shared taxonomy table.

### 11. LLM-generated comments in the wild ([arXiv:2607.01867](https://arxiv.org/abs/2607.01867))

Fetched in full (HTML). Studies **8 repositories** (4 company-maintained, 4 community-maintained), 2021-2025, sampling **370 comments per repository** at 95% confidence / 5% margin of error for manual categorization. Comments detected as likely LLM-generated skew overwhelmingly to low-information types: in one repository **97%** of LLM-flagged comments fell in the Meta+Explanation categories combined (vs. Type, Interface, Code-relationship, Past-Future making up "a relatively small proportion"). LLM-flagged comments show high punctuation correctness (~90%) but comparatively low grammatical correctness. Prevalence of LLM-generated code/comments **declined** over 2021-2025 in the studied repos (one company repo from 82.16% to 69.62%, one community repo from 56.6% to 37.67%) — evidence that "AI comments are bad" is a snapshot of specific model generations, not a fixed law. Bug association is weak: only **10.79%** (NVD) and **5.56%** (OSS-Fuzz) of human-labelled bugs in these repos associate with LLM-generated code, undercutting a naive "LLM code/comments cause more bugs" framing.

### 12. AI-generated Javadoc quality ([arXiv:2408.14007](https://arxiv.org/abs/2408.14007))

Confirmed via search-returned abstract text (large, consistent quote overlap across independent listings; not independently re-fetched as full HTML in this pass, treated as reliably reported). Evaluates **142 classes / 273 methods**, all created after the evaluated models' training cutoff (GPT-3.5 Turbo, GPT-4o, DeepSeek-V3), with two experts independently Likert-scoring generated Javadoc against the human original. **58.8%** rated equivalent, **27.7%** rated superior — 86.5% combined at or above the human baseline. IR metrics (BLEU, ROUGE-L, METEOR) did **not** reliably track the human judgments, arguing against using surface-similarity metrics as an automated comment-quality gate.

### 13. CodeCrash: misleading natural-language cues in code reasoning (NeurIPS 2025 / [arXiv:2504.14119](https://arxiv.org/abs/2504.14119))

Fetched (abstract page). **1,279 questions** from CruxEval and LiveCodeBench, **17 LLMs** evaluated under logic-preserving structural perturbations and misleading natural-language context. Average degradation on output-prediction tasks: **23.2%**; still **13.8%** with chain-of-thought reasoning enabled. Names a distinct failure mode, "Reasoning Collapse," observed severely in QwQ-32B, where the model's reasoning process itself degrades under a misleading cue rather than just its final answer. This is the strongest evidence in the corpus that a stale or wrong "why" comment is not merely unhelpful to an LLM reader — it can actively out-compete the model's own correct reading of the code, at a scale (23%) too large to treat as noise.

### 14. What comment content, not comment count, does to code generation ([arXiv:2609.09242](https://arxiv.org/abs/2609.09242))

Fetched (abstract page). "Talking to Itself While Coding" uses controlled interventions on LiveCodeBench: prefilling a weaker "recipient" model with a comment block written by a stronger "source" model, to separate a comment's surface form from the solution content it carries. Comments from a source solution that **passes** its tests raise recipient pass@1 by **+17.2%** on average; comments from a **failing** source solution give no reliable gain; comments written for a **different problem** cut pass@1 by **-20.8%**. Critically, "how often comments appear predicts nothing" — volume is not a proxy for benefit or harm; only correctness of content is. Even when a recipient model is told an external comment might be unreliable, it recovers at most **24%** of the induced gain — models cannot fully discount a misleading comment even when warned.

### 15. Comments and automated bug-fixing ([arXiv:2601.23059](https://arxiv.org/abs/2601.23059))

Confirmed via abstract fetch. Compares two model families across training/inference conditions with and without comments present (using an LLM to backfill comments where a benchmark lacks them, isolating the comment-presence variable). Comments boost bug-fixing accuracy **"by up to threefold"** when present in both training and inference; training with comments causes **no degradation** on instances that lack them at inference; an interpretability pass finds comments describing **implementation details** are the most effective type for helping a model localize and fix a bug correctly. This directly counters a "strip comments before feeding code to a model" preprocessing habit for a task (bug-fixing) that is a large share of real agent work.

### 16. Comment internalization is task-dependent, "Inside Out" ([arXiv:2512.16790](https://arxiv.org/html/2512.16790v1))

Fetched in full (HTML). Tests whether LLMs form a separable internal "comment concept" that can be activated/deactivated, across Qwen2.5-Coder-32B-Instruct, Qwen2.5-32B-Instruct, and QwQ-32B (4-bit quantized), on three tasks: code translation (Java→Python/C/C++/Go, 43 samples), code completion (281 samples from 1,046 commented records), and code refinement (81 samples from 103 filtered records); a separate classifier trained on 69,610 Apache-derived records confirms comments are internalized as a distinct, identifiable concept (96% median classifier accuracy for Javadoc specifically). Effect of deactivating the comment concept is sharply task-dependent: **code refinement degrades up to -90%**, **code completion degrades only up to -19%** (its weakest sensitivity), and **code translation improves up to +67%** when the concept is activated. This is the single most important finding for the program's cleanup skill design: refinement-style tasks (rewriting/shortening existing code, which is exactly what the cleanup skill does) are the most comment-sensitive task type measured — a blanket "strip comments" cleanup pass risks doing the most damage on precisely the operation the program plans to run.

### 17. Deletion avoidance in LLM code editing, "CanItDelete" ([arXiv:2607.28887](https://huggingface.co/papers/2607.28887))

Fetched (paper page summary). Names and measures "deletion avoidance": the systematic tendency of LLM code editors to retain code an edit requires removing, typically by wrapping it in a new conditional rather than deleting it — "Guard-and-Go." Across five frontier models on SWE-bench Verified, deletion recall tops out at **71.7%** even on instances every model solved (28-35% of required deletions survive); models localize the correct **file** for a required deletion 92.5-94.4% of the time but remove the exact **line** only **44.6-51.6%** of the time; **29%** of passing patches exhibit Guard-and-Go. On the purpose-built CanItDelete benchmark (200 tasks, 35 repositories, minimum 3 deletion hunks per task, deterministic occurrence-aware scoring), best models reach 79% success, weaker open-weight models fall to 18%. Retrofitting tasks with deletion-checking tests dropped four frontier models' success from 63.2% to 41.9%. A proof-of-concept fix — post-training a 7B model on 12,821 deletion examples (0.7% of training tokens) — cut incomplete deletion from 80.4% to 66.5% and improved SWE-bench Verified by 5.3 points, suggesting deletion is undertrained rather than fundamentally hard. **This is a load-bearing finding for the cleanup skill and its checks**: an agent asked to "delete the essay, leave a one-line pointer" is fighting a measured, general-purpose bias, not just a bad habit in this codebase, and a cleanup pass needs its own delete-verification step, not just a rule telling agents to delete.

### 18. What coding agents actually read, "From Agent Behaviour to Agent-Friendly Documentation" ([arXiv:2608.20195](https://arxiv.org/abs/2608.20195))

Fetched (abstract page, rich in reported statistics). Analyzes **557 agentic coding sessions** from SWE-chat (94,813 development events, 3,033 documentation interactions) and **33,097 agentic pull requests** from AIDev (690,260 file-level change records), building a single ordered event stream of user/agent messages, tool calls, tool results, and code changes. Documentation-interaction breakdown: **60.5%** agent-facing artifacts (instruction files, working notes), **10.6%** classical technical documentation, **1.3%** API references. Consultation is mostly self-initiated (**70.2%**) rather than failure-driven (**7.5%**). In multi-commit PRs touching both code and docs, **code is modified first 4.7x more often** than docs. Consultation correlates with **reduced** immediate testing (adjusted OR **0.39** [0.25, 0.60]) — reading documentation substitutes for, rather than triggers, verification in the observed behavior. The paper explicitly challenges two assumed properties of agent-friendly documentation — actionability and verifiability — finding "no explicit documentation-based validation sequences were observed" in agent behavior. This is the single most important source for the program's H5 hypothesis ("cold agents seldom read git history or decision records unprompted"): the data says agents *do* read something unprompted most of the time, but overwhelmingly the wrong tier (instruction files, not ADRs/classical docs), and having read it, do not check their work against it.

### 19. Path-scoped agent instruction files at scale, "Agent READMEs" ([arXiv:2511.12884](https://arxiv.org/abs/2511.12884))

Fetched (abstract page). Empirical study of **2,303 agent context files** (AGENTS.md/CLAUDE.md-style) across **1,925 repositories**. Content emphasis: test procedures **75.9%**, implementation details **70.8%**, architecture **68.1%** — vs. security **14.8%** and performance **14.5%**, a roughly 5x gap between "how to build this" and "what not to break." These files are characterized as "complex, difficult-to-read artifacts that evolve like configuration code through frequent, small additions" rather than stable, authored documentation — directly relevant to how the program's own path-scoped `code-docs` rule should expect to be edited and drift over time, and a concrete argument for keeping the guardrail content (the 20% currently under-covered) terse and separable from the build/test content that already dominates these files.

### 20. Lore: commit messages as a structured knowledge protocol for agents ([arXiv:2603.15566](https://arxiv.org/abs/2603.15566))

Fetched in full (abstract page, verbatim). Single-author proposal (Ivan Stetsenko) naming the "Decision Shadow" — the reasoning, rejected alternatives, and forward-looking context a commit diff discards — and proposing that commit messages, restructured via native git trailers into fields for constraints, rejected alternatives, agent directives, and verification metadata, serve as self-contained decision records queryable by any agent that can run shell commands. Explicitly a **protocol proposal**, not an empirical measurement: the abstract states the paper "compares it against five competing approaches, stress-tests it against its strongest objections, and outlines an empirical validation path" — i.e. the validation is future work, not yet done. Should be read as a candidate design, not as evidence that commit-message-as-decision-record works in practice; the SATD-removal finding above (Zampetti: only 8% of SATD removals are acknowledged in a commit message today) is a caution about adoption gap, not about the protocol's soundness.

### 21. Embedded Architecture Decision Records, e-adr convention ([adr.github.io/e-adr](http://adr.github.io/e-adr/))

Fetched. Names the gap this program's decision-record seed has to close: "architectural knowledge... is primarily created and consumed in tools made for software architects. Developers... do not always use such tools," contributing to "architectural erosion and knowledge vaporization." Defines two mechanisms: a full `@MADR` annotation embedding an entire decision record's fields (title, context, alternatives, justification) directly in code, and a lighter `@ADR(n)` reference pointing at a numbered file under a conventional `docs/adr/` location, compatible with either MADR or Nygard's original ADR format. This is exactly the "pointer, not paraphrase" pattern the fleet's own prior research recommended for OCX — but arXiv 2608.20195 above (agents rarely read classical docs unprompted, 1.3% of consultations are API-reference-tier, no verification behavior observed) is direct behavioral evidence that this convention's implicit assumption — an agent that follows `@ADR(n)` to the file and reads it — is not the median measured behavior. The convention is sound engineering; its uptake by an agent cold-reading code is the open, empirically-thin part.

### 22. Anthropic, Claude Code best-practices documentation ([code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices))

If not, cut it") and an explicit instruction to **exclude** "self-evident practices like 'write clean code'" from CLAUDE.md — i.e. Anthropic's own guidance for agent-config files already argues against vacuous, restated-the-obvious content, the same failure mode the fleet's "narration" and "tautological doc" categories target, just applied to config files rather than inline comments. ## Recent shifts seen in this corpus

- **An entirely new empirical genre appeared in the last ~12 months: measuring what agents actually do with documentation, not what they're told to do.** arXiv 2608.20195 (Aug 2026), 2511.12884 (Nov 2025), 2607.28887 (Jul 2026), and 2512.16790 (Dec 2025) are all agent-behavior studies with no precedent in the pre-2025 literature. Older guidance — "write comments for the reader," the Ousterhout test, embedded-ADR conventions — implicitly assumes a reader that reads top-down, consults references when pointed to them, and verifies its understanding. The behavioral data says a cold agent reads code first (eye-tracking, human proxy), consults agent-facing instruction files over classical docs when it does look elsewhere (2608.20195), and does not verify against what it reads (2608.20195) — none of which invalidates older comprehension findings, but all of which changes where a "why" should be placed to actually be found.
- **Deletion avoidance (arXiv 2607.28887, mid-2026) reframes any cleanup rule that says "shrink this, leave a pointer" as fighting a general, measured model bias, not a habit specific to this codebase.** This is new: no pre-2026 source in this corpus measured deletion behavior as its own phenomenon; the closest prior work (Wen et al., SATD-removal studies) measured deletion as a side effect of other changes, not as a directed editing task with its own success rate.
- **Comment sensitivity is now known to be task-dependent, not a single number (arXiv 2512.16790, Dec 2025).** Every pre-2025 ablation in this corpus (and most of the "delete comments and see what happens" folklore it's built from) implicitly treats "comment removal" as one intervention with one effect. The Inside-Out result — -90% for refinement, +67% for translation, -19% for completion — means a single global "comments help/hurt" verdict from an older study should not be trusted to predict the effect on a *different* task, including the cleanup skill's own task.
- **The "AI over-comments" claim is now measured precisely enough to know it's a moving target, not a constant (arXiv 2607.01867, mid-2026).** LLM-flagged comment prevalence *declined* 2021-2025 in the repositories studied, tracking model generations. A rule calibrated once against a 2024-era ratio may already be loose or tight relative to 2026-era model output; the ratchet-not-fixed-gate design (H7) is the right response to a moving baseline, and this is new evidence for it.
- **Content-correctness-over-volume is now a load-bearing, multiply-replicated finding for LLM readers specifically (arXiv 2609.09242, Sept 2026; CodeCrash, 2025; arXiv 2601.23059, Jan 2026), superseding any comment-density-as-quality-proxy framing inherited from the 2009-2019 human-reader literature.** Arafat & Riehle and He both use density as their only lens because, for a human reader in 2009-2019, no cheaper proxy existed. For an LLM reader in 2026, the direct experiments (transplant a correct vs. incorrect comment, measure pass@1) make density irrelevant to the actual mechanism and should be weighted far higher than density studies when the two conflict.

## Contested

- **Does comment volume matter, or only content correctness?** arXiv 2609.09242 states frequency "predicts nothing"; arXiv 2601.23059 finds mere *presence* of comments (especially implementation-detail ones) triples bug-fix accuracy. These are reconcilable — correct-content comments help, and having more of them (if they stay correct) helps more — but a naive read of either alone gives opposite advice ("count doesn't matter" vs. "more comments help"). Trending toward: frequency-of-*correct*-content is what's measured to matter; raw count in isolation is not.
- **Does stripping comments help or hurt an LLM?** A pre-2026 ablation-study snippet found in this survey's own search process claimed "for most LLMs, removing comments improved performance" on some code-understanding benchmarks. Inside Out (2512.16790) shows the effect swings from -90% to +67% by task, and arXiv 2601.23059 shows up to 3x gains from presence on bug-fixing. Trending toward: the blanket "strip comments" claim is an artifact of which task was benchmarked, not a general truth, and is looking dated next to the task-resolved 2025-2026 results.
- **Is density itself an informative signal, or purely a proxy that gets gamed?** Arafat & Riehle and He both treat density as a maintainability/quality proxy worth tracking at scale. Pascarella & Bacchelli's own data (59% of comment lines carry no readability/maintainability information) and this program's own prior critique (a pure ratio target can be gamed by deleting good "why" comments) point the other way. Trending toward: a *categorized* ratio (excluding metadata/style/discarded lines, as this program's classifier already partially does) rather than a raw line-count ratio.
- **Do agents follow embedded decision-record pointers the way the e-adr convention assumes?** The convention (and this program's own H4 hypothesis) presumes a reader that, given `@ADR(n)` or a file-qualified pointer, goes and reads the target. Measured agent behavior (arXiv 2608.20195) shows real but narrow documentation consultation (1.3% API-reference-tier, no verification sequences observed) heavily skewed toward agent-facing instruction files instead. Trending toward: the convention is sound design that predates the behavioral data, and needs the pointer's target to be an agent-facing instruction file or the equivalent, not a separately-maintained ADR directory, if it wants to actually get read.
- **Is a 72% (DocChecker) or ~85% (Panthaplackel, curated) automated inconsistency detector good enough to gate on?** No source in this corpus argues for a hard gate at these accuracy levels; the fleet's own prior research explicitly rejected LLM-judged comment review as too expensive and dedicated detectors as too inaccurate. Not really contested so much as converged: use as triage/ranking signal, not as a merge gate, until accuracy is measured well above 90% on realistic (not curated-balanced) data.
