## Summary

- Every language-official style guide surveyed (C++, Python, Java, Go, TypeScript,
  Shell) converges on the same two-register model: a doc comment is a tool-parsed,
  reader-facing contract; a plain `//` comment is a human-only maintenance note —
  Google's TypeScript guide states this as an explicit rule (`§ JSDoc versus
  comments`), not an implied convention.
- The single most-repeated "don't" across every source is restating what the code
  literally does one line below the comment (Google C++ `Don'ts`, Google Python
  "Never describe the code", Linux kernel "NEVER try to explain HOW"). No source
  disagrees with this.
- Sources disagree sharply on volume. Ousterhout states he would write "5-10x more
  lines of comments" than Martin for the same code; the Google, Linux, and LLVM
  guides all instruct commenting only what is "non-obvious," "tricky," or
  "nonobvious" — closer to Martin's end of that range than Ousterhout's.
- No surveyed source states a numeric length cap on an individual comment or doc
  block. Length is governed only by structural conventions (summary-then-blank-line,
  one Errors/Panics/Safety section each) that bound growth indirectly, not by a
  line count.
- The "first sentence is a summary, extracted and shown elsewhere" rule is nearly
  universal (PEP 257, Google Java's summary fragment, Go's first-sentence rule,
  Kotlin's first-paragraph rule) but the *grammatical form* required is not: Java
  wants a sentence fragment ("Returns the customer ID."), Go and the Google Go
  style guide want a full sentence starting with the name ("A Request represents
  a request to run a command."), Rust's rustdoc book gives no such rule at all.
- Every doc-comment spec defines a closed, small vocabulary of section headers
  (Rust: `# Examples/Errors/Panics/Safety`; Javadoc: `@param/@return/@throws` in a
  fixed order; Google Shell: `Globals/Arguments/Outputs/Returns`) — this is a
  portable, checkable pattern that none of the fleet's overlapping lore rules
  currently enforce outside Rust.
- Rust's ecosystem is the outlier on volume by design: `C-EXAMPLE` in the Rust API
  Guidelines asks for a runnable example on "every" public item, and the rustdoc
  book states "the more documentation you write for your crate the better" — this
  is a docs-as-product stance (docs.rs), not a docs-as-maintenance-aid stance, and
  the two should not be blended into one ratio target.
- Unsafe/unchecked operations get a dedicated, mandatory section in every language
  that has the concept: Rust's `# Safety` (C-FAILURE), and, as of the C# 15 preview
  (2026), a new `<safety>` XML doc tag tied to the "updated memory safety model" —
  this convention is converging across languages independently.
- Google's own two style guides are internally inconsistent on TODO format: the
  C++ guide prefers a bug ID over a name; the Shell guide accepts a bare name with
  no mention of a tracker. A fleet-wide TODO rule cannot cite "Google style" as a
  single source of truth.
- Linux kernel style inverts the usual "why not what" framing: it says comments
  should say **what** the code does (at a level above the code) and **why**, while
  the code itself must make **how** it works obvious — a three-way split (what/how/
  why) that the Google guides collapse into a two-way one (why vs. restating).
- Google's engineering-practices guide for code review treats a reviewer's request
  to explain unclear code as a signal to **rewrite**, not to comment: "that should
  usually result in them rewriting the code more clearly." A comment is only an
  "occasionally... appropriate response," never the default fix for unclear code.
- Self-explanatory-member exemptions (Google Java 7.3.1, Google TypeScript "as
  judged by your reviewer") delegate the hardest classification decision — is this
  non-obvious? — to human judgment at review time. No surveyed source gives a
  mechanical proxy for "obvious," which matters directly for an agent-run check.
- Structured, tool-checked deprecation beats prose deprecation wherever the
  language supports it: Kotlin explicitly refuses a `@deprecated` doc tag in favor
  of the compiler-checked `@Deprecated` annotation; Go's `Deprecated:` paragraph is
  the weaker, prose-only fallback for languages without such an annotation.
- Google Java's 2025-26 style guide now sanctions two parallel Javadoc syntaxes:
  traditional `/** */` blocks and a new Markdown-based `///` form (JEP 467); this
  is the most concrete "recent shift" found in any official style guide surveyed.
- RFC 1574's "link all the things" convention pushes readers toward other doc
  items via markdown reference links; it has no answer for what happens when the
  link target is a decision record outside the crate rather than another rustdoc
  page — that gap is exactly where the fleet's pointer-staleness problem lives.
- The C++, Java, and Shell guides all explicitly document a special class of
  "guard" comments — synchronization assumptions, sentinel-value meanings, side
  effects on constructors/destructors — as always required regardless of any
  general economy-of-comments rule. This is the closest any source comes to
  naming the "guard comment" category the eval program needs to protect.
- None of the surveyed canon sources discuss AI-agent authorship or reading at
  all; every "recent shift" found is a human-tooling change (new syntax, new
  compiler-checked tag) whose relevance to agent-authored code is an inference
  this program has to make, not a claim any source makes itself.

## Survey

1. **[A Philosophy of Software Design vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code)** (Ousterhout & Martin, discussions Sept 2024–Feb 2025, published as a GitHub repo). A structured written debate, not a synthesis — the two authors never fully agree. Martin's *Clean Code* p.54 line "Comments are always failures" is quoted and contested by Ousterhout as stigmatizing comments; Martin replies the chapter also calls a well-placed comment "quite... helpful" and that comments are a "necessary evil." Ousterhout's closing summary (`### Comments Summary`, line 1209) states two measured-feeling claims with no citation behind them: "I would probably write 5-10x more lines of comments for a given piece of code than you would," and "I believe that missing comments are a much greater cause of lost productivity than erroneous or unhelpful comments." Both authors agree on one thing only: "implementation code only needs comments when the code is nonobvious." The debate over `PrimeGenerator` (Martin's *Clean Code* Listing 10-8) turns into a concrete disagreement about whether to encode meaning in "megasyllabic" names (`isLeastRelevantMultipleOfLargerPrimeFactor`, Martin's style) or short names plus a header comment (Ousterhout's proposed `/** Returns true if candidate is a multiple of primes[n]... */`).

2. **[Rust API Guidelines — Documentation](https://rust-lang.github.io/api-guidelines/documentation.html)** ([raw source](https://raw.githubusercontent.com/rust-lang/api-guidelines/master/src/documentation.md), living document, checked 2026-09-27). Defines checkable rule IDs: **C-CRATE-DOC** (crate docs thorough, citing [RFC 1687](https://github.com/rust-lang/rfcs/pull/1687)); **C-EXAMPLE** ("Every public module, trait, struct, enum, function, method, macro, and type definition should have an example that exercises the functionality," with the caveat that the purpose is usually to show *why*, not *how*); **C-QUESTION-MARK** (examples use `?`, never `unwrap`, because "example code is often copied verbatim by users"); **C-FAILURE** (mandatory `# Errors`, `# Panics`, and `# Safety` sections, with the example that `Vec::insert` panics "if `index` is out of bounds" and `std::ptr::read`'s Safety section spells out every invariant the caller must uphold); **C-LINK** (hyperlink everything via reference-style markdown links); **C-HIDDEN** (`#[doc(hidden)]` to keep irrelevant trait impls out of rendered docs). No numeric length limit anywhere in the document.

3. **[PEP 257 — Docstring Conventions](https://peps.python.org/pep-0257/)** (Goodger & van Rossum, created 2001-05-29, status Active). One-line docstrings "should really fit on one line," phrased "as a command ('Do this', 'Return that'), not as a description" — explicitly bans `"""Returns the pathname..."""` in favor of `"""Return the pathname..."""`. Multi-line docstrings require a summary line, then a blank line, then elaboration; "the summary line may be used by automatic indexing tools" — an early statement of the same "extracted first line" mechanism every later spec repeats. Includes the canonical `trim()` algorithm for stripping docstring indentation, given "since code is much more precise than words."

4. **[rustdoc book — How to Write Documentation](https://doc.rust-lang.org/rustdoc/how-to-write-documentation.html)** ([raw source](https://raw.githubusercontent.com/rust-lang/rust/master/src/doc/rustdoc/src/how-to-write-documentation.md)). States "the more documentation you write for your crate the better" and "if an item is public then it should be documented" — an explicit maximalist stance, contrasted below against Google/Linux minimalism. Prescribes item structure: short sentence, detailed explanation, at least one example, advanced explanation. Notes "because the type system does a good job of defining what types a function passes and returns, there is no benefit of explicitly writing it into the documentation" — a Rust-specific argument against redundant type-restating prose.

5. **[RFC 1574 — More API Documentation Conventions](https://rust-lang.github.io/rfcs/1574-more-api-documentation-conventions.html)** ([raw source](https://raw.githubusercontent.com/rust-lang/rfcs/master/text/1574-more-api-documentation-conventions.md), 2016-03-31, extends [RFC 505](https://github.com/rust-lang/rfcs/blob/master/text/0505-api-comment-conventions.md)). Fixes the canonical heading vocabulary: "Examples, Panics, Errors, Safety, Aborts, Undefined Behavior." Introduces "Link all the things": every type mentioned in prose should be a reference-style markdown link resolved at the bottom of the doc comment. States a rule for module-vs-type docs: "module-level documentation should show a high-level summary of everything in the module, and each type should document itself fully... It is okay if there is some small amount of duplication here."

6. **[go.dev/doc/comment — Go Doc Comments](https://go.dev/doc/comment)** (official Go spec, current). Doc comments must be immediately adjacent to the declaration, no blank line. Package comment's first sentence "must begin with 'Package'"; a command's package comment "conventionally begins with the name of the program itself, capitalized." Boolean functions: "use 'reports whether' (not 'returns whether')" — e.g. `HasPrefix reports whether the string s begins with prefix`. Zero-value semantics must be documented "if its meaning isn't obvious." Defines a full micro-syntax: headings (`# Heading`, must be unindented, blank-line-set-off), doc links (`[Name1.Name2]`), notes (`MARKER(uid): body`, MARKER = 2+ uppercase letters, e.g. `TODO(user1): ...`), and `Deprecated:` paragraphs that tools warn on. `gofmt` reformats lists and code blocks automatically and does not support nested lists.

7. **[Google C++ Style Guide — Comments](https://google.github.io/styleguide/cppguide.html#Comments)** ([raw source](https://raw.githubusercontent.com/google/styleguide/gh-pages/cppguide.html), current). "The best code is self-documenting... [but] comments are absolutely vital." Function declaration comments must state, among other things: nullability of pointer arguments, whether reference/pointer arguments are retained past the call, and "performance implications of how a function is used." Class comments must "document the synchronization assumptions the class makes" for any class usable from multiple threads. Data-member comments: "add comments to describe the existence and meaning of sentinel values, such as `nullptr` or `-1`, when they are not obvious" (worked example: `// -1 means that we don't yet know how many entries the table has.`). The `Don'ts` section gives the canonical bad/good pair: `// Find the element in the vector.` (bad, obvious) vs `// Process "element" unless it was already processed.` (good, states why), and notes the ultimate fix is self-describing code (`IsAlreadyProcessed(element)`) needing no comment at all. TODO format: `TODO` in caps plus "bug ID, name, e-mail address, or other identifier," preferred forms `// TODO: bug 12345678 - ...` or `// TODO(bug 12345678): ...`.

8. **[Google Python Style Guide — §3.8 Comments and Docstrings](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings)** (current). Docstring summary line: "one physical line not exceeding 80 characters," terminated by `.`/`?`/`!`, blank line, then body. "Never describe the code. Assume the person reading the code knows Python... better than you do" — explicitly bans `# Now go through the b array and make sure whenever i occurs the next element is i+1`-style narration. Function docstrings need `Args`, `Returns`/`Yields`, `Raises` sections when the function is "part of the public API," has "nontrivial size," or has "non-obvious logic" — i.e., triviality is an explicit exemption, same shape as Java's.

9. **[Google Java Style Guide — §7 Javadoc](https://google.github.io/styleguide/javaguide.html#s7-javadoc)** ([raw source](https://raw.githubusercontent.com/google/styleguide/gh-pages/javaguide.html), current, dated content confirms 2025-26 revision). Sanctions two Javadoc syntaxes side by side: traditional `/** ... */` blocks and a new `///`-per-line "Markdown Javadoc" form (JEP 467) — the clearest dated syntax change in the corpus. §7.2 "Summary fragment": "This is a fragment — a noun phrase or verb phrase, not a complete sentence... does not begin with `A Foo is a...`" and flags the common mistake `/// @return the customer ID.` as wrong, correct form `/// Returns the customer ID.` or the new inline `/// {@return the customer ID}`. §7.3.1 "Exception: self-explanatory members": Javadoc optional for a `getFoo()`-shaped member "if there really and truly is nothing else worthwhile to say," but explicitly warns against citing this to skip documenting something like `canonicalName` whose meaning isn't obvious from the name alone.

10. **[Google TypeScript Style Guide — Comments and documentation](https://google.github.io/styleguide/tsguide.html#comments-and-documentation)** ([raw source](https://raw.githubusercontent.com/google/styleguide/gh-pages/tsguide.html), current). States the two-register rule explicitly under **"JSDoc versus comments"**: "Use `/** JSDoc */` comments for documentation, i.e. comments a user of the code should read. Use `//` line comments for implementation comments... JSDoc comments are understood by tools... while ordinary comments are only for other humans." Bans redundant `@param`/type restating: "JSDoc type annotations are redundant in TypeScript source code" and "avoid comments that just restate the parameter name and type" — `@param`/`@return` "are only required when they add information, and may otherwise be omitted." Defines a call-site convention for unclear positional arguments: `someFunction(obviousParam, /* shouldRender= */ true, /* name= */ 'hello')`, but instructs "before adding these comments, consider refactoring the method to instead accept an interface" — comment as a worse fallback to a signature fix, not a first resort.

11. **[Google Shell Style Guide — Comments](https://google.github.io/styleguide/shellguide.html#comments)** (current). Every function that is "not both obvious and short" needs a header with a fixed section vocabulary: `Globals`, `Arguments`, `Outputs`, `Returns`. Every library function needs one "regardless of length or complexity." TODO rule: "the name, e-mail address, or other identifier of the person with the best context" — no bug-ID preference stated, unlike the C++ guide (§ Contested).

12. **[Google Go Style Decisions](https://google.github.io/styleguide/go/decisions.html)** (current, Google-internal Go conventions layered on top of the official spec). "All top-level exported names must have doc comments, as should unexported type or function declarations with unobvious behavior or meaning." Doc comments "should be full sentences that begin with the name of the object being described" (e.g. `A Request represents a request to run a command.`) — a full-sentence rule, contrasting with Java's fragment rule. "Package comments must appear immediately above the package clause with no blank line... There must be a single package comment per package."

13. **[Linux kernel coding style, ch. 8 — Commenting](https://www.kernel.org/doc/html/latest/process/coding-style.html)** ([raw source](https://raw.githubusercontent.com/torvalds/linux/master/Documentation/process/coding-style.rst), current). Inverts the common "why not what" framing into a three-way split: "NEVER try to explain HOW your code works in a comment: it's much better to write the code so that the working is obvious... Generally, you want your comments to tell WHAT your code does, not HOW... put the comments at the head of the function, telling people what it does, and possibly WHY it does it." Explicitly warns against over-commenting kernel-doc: "Do not add boilerplate kernel-doc which simply reiterates what's obvious from the signature of the function." Preferred multi-line block style is the asterisk-column form (`/* ... * ... */`), a stylistic rule with no equivalent in the other guides surveyed.

14. **[LLVM Coding Standards — Commenting](https://llvm.org/docs/CodingStandards.html#commenting)** (current). Rule of thumb: comments should document "what the code is trying to do and why, not *how* it does it at a micro level" — the same why-not-how framing as Google, opposite emphasis from the Linux kernel's phrasing (§ Contested). File headers: "the first sentence (or a passage beginning with `\brief`) is used as an abstract" (Doxygen). Every "non-trivial class is expected to have a doxygen comment block."

15. **[Chromium C++ style guide](https://chromium.googlesource.com/chromium/src/+/main/styleguide/c++/c++.md)** (current). Inherits the Google C++ guide wholesale for comments; the fetched exceptions list contains zero comment-specific deviations — evidence that a single core comment spec plus per-project exceptions is a viable shape, not an argument for a from-scratch Chromium rule.

16. **[TSDoc](https://tsdoc.org/)** (Microsoft-led community spec, ongoing; [spec repo](https://github.com/microsoft/tsdoc)). Exists to fix tool disagreement, not human readability: "different tools can extract content without getting confused by each other's markup," citing TypeDoc, DocFX, API Extractor, ESLint, and VS Code as parsers that "recognize a syntax loosely based on JSDoc, but each with its own flavor of syntax extensions." States JSDoc itself "is not rigorously specified, but rather inferred from the behavior of a particular implementation" — the closest thing in this corpus to an admission that ungoverned doc-comment convention drifts into incompatible dialects, which is the same failure mode a fleet's ad hoc `ponytail:`/plan-ID markers risk without a grammar.

17. **[Oracle — How to Write Doc Comments for Javadoc](https://docs.oracle.com/en/java/javase/21/docs/specs/javadoc/doc-comment-spec.html)** (official spec, JDK 21 era, current). "The first sentence of the main description should be a summary sentence that contains a concise but complete description of the declared entity" — automatically extracted for indexes. No tag is strictly required, but `@throws` is "now recommended" over the older `@exception`. Explicit don't: doc comments "in method bodies... are ignored." Deprecation rule: "the first sentence of deprecated text should tell the user when the API was deprecated and what to use as a replacement."

18. **[Kotlin — Document Kotlin code: KDoc](https://kotlinlang.org/docs/kotlin-doc.html)** (official docs, current). "By convention, the first paragraph of the documentation text (the block of text until the first blank line) is the summary description... the following text is the detailed description" — same shape as PEP 257 and Javadoc. Notably: "KDoc does not support the `@deprecated` tag. Instead, please use the `@Deprecated` annotation" — a structured-metadata-over-prose choice with no equivalent restriction in Java, Go, or Rust. "Since Kotlin does not have checked exceptions, there is also no expectation that all possible exceptions are documented" (contrast with C-FAILURE's mandatory Errors section for fallible Rust functions).

19. **[Microsoft — Recommended XML documentation tags (C#)](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/recommended-tags)** (official docs, page dated 2026-09-10/14 in its metadata, i.e. refreshed this quarter). Separates `<summary>` (short, IntelliSense-facing) from `<remarks>` ("supplemental information," explicitly "can include more lengthy explanations," recommends `CDATA` for embedded Markdown) — a two-tier length model no other source states this explicitly. New in this revision: **`<safety>`**, "a preview feature in C# 15 and .NET 11," for the "updated memory safety model" — used on a `requires-unsafe` member to state "the conditions the caller must guarantee," directly parallel to Rust's mandatory `# Safety` section, arriving independently in a second language in 2026.

20. **[Google Engineering Practices — Writing Code Review Comments](https://google.github.io/eng-practices/review/reviewer/comments.html)** (current). Reframes the comment-vs-fix tradeoff at the review stage rather than the authoring stage: "if you ask a developer to explain a piece of code that you don't understand, that should usually result in them rewriting the code more clearly," and a code comment is "occasionally... an appropriate response, as long as it's not just explaining overly complex code." Also states "explanations written only in the code review tool are not helpful to future code readers" — an explicit ranking of where an explanation should live (code comment > review-tool comment, for anything future readers need).

21. **Steve McConnell, *Code Complete 2nd ed.*, ch. 32 "Self-Documenting Code"** — full text is paywalled; content triangulated from the [O'Reilly table of contents](https://www.oreilly.com/library/view/code-complete-2nd/0735619670/ch32.html) and a community-maintained [chapter checklist](https://github.com/janosgyerik/software-construction-notes/blob/master/checklists-all/ch32-self-documenting-code.md), not the primary text — **flagged as secondary, do not cite specific rule wording from this entry.** The checklist's headline items ("Do comments explain the code's intent... rather than just repeating the code?", "Has tricky code been rewritten rather than commented?", "Do comments focus on why rather than how?") track the same why-not-what convergence seen in every primary source above, so directionally consistent, but no exact McConnell wording is quoted here because the book itself could not be fetched.

22. **Swift documentation markup (DocC / triple-slash `///`)** — the primary pages ([swift.org/documentation/docc/writing-symbol-documentation-in-your-source-files](https://www.swift.org/documentation/docc/writing-symbol-documentation-in-your-source-files), Apple's archived [Markup Formatting Reference](https://developer.apple.com/library/archive/documentation/Xcode/Reference/xcode_markup_formatting_ref/SymbolDocumentation.html)) render as JS-driven pages that returned no extractable rule text through this session's fetch tools; **content not verified, not cited.** What is confirmed only via search-result snippets (not fetched primary text, so treated as unverified): a `Parameters:`-prefixed Markdown list item and a `Returns:` delimiter are the documented callout mechanism. This source should be re-fetched with a tool that executes the page's JS, or via the swift-docc GitHub source, before any rule cites it.

## Recent shifts seen in this corpus

- **Google Java style guide now sanctions Markdown Javadoc (`///`) alongside traditional `/** */` blocks** (JEP 467, reflected in the [current guide](https://google.github.io/styleguide/javaguide.html#s7.1.1-javadoc-multi-line), 2025-26). The terser per-line form removes the asterisk-column boilerplate that traditional Javadoc requires on every line — a free length reduction the fleet's Java/Kotlin-adjacent surfaces (none currently in this fleet, but worth flagging for any future JVM addition) get without a content-level rule change.
- **C# 15 preview (2026) adds a `<safety>` XML doc tag** for the "updated memory safety model," used on `requires-unsafe` members to state caller obligations ([Microsoft docs](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/recommended-tags), page metadata dated 2026-09-10/14). This is the second language, after Rust's long-standing `# Safety` (C-FAILURE), to make an unsafe-operation contract a first-class, separately-named doc section — evidence that "unsafe needs its own mandatory section" is converging as a cross-language norm, not a Rust idiosyncrasy, and older guidance that treats unsafe/unchecked code like any other function (document if non-obvious) is being superseded for this specific case.
- **The Ousterhout-vs-Martin debate itself is an 18-month-old primary source** (discussions Sept 2024–Feb 2025, published as a GitHub repo, not a book revision) — it is the most current book-adjacent statement of the comments-volume disagreement in this corpus and should be treated as live, not historical, unlike the underlying books (*Clean Code* 2008, APOSD 1st ed. 2018) it argues about.
- **Google's own review-process guidance ("rewrite, don't comment") predates agent-authored code but its cost assumption is newly testable**: the guidance assumes asking a human author to refactor costs more than accepting a comment, which is why comments are tolerated as a cheaper fallback. When both the reviewer and the author can be the same class of fast, tireless agent, that cost asymmetry may no longer hold — this is an inference from the source, not a claim the source makes, and is exactly why it is flagged as P1/P2 in the candidate table rather than adopted outright.
- **Nothing surveyed discusses AI-agent authorship or reading directly.** Every "recent shift" found in this canon is a human-tooling or human-workflow change (new syntax, new compiler-checked tag, a fresh public debate); the agent-era relevance of each is this program's own inference, and should be labeled as such wherever it is cited in a rule, not attributed to the source.

## Contested

- **Comment volume.** Ousterhout: "I would probably write 5-10x more lines of comments... than you would." Martin/*Clean Code*: comments are a "necessary evil," minimized by design. The practitioner-facing Google/Linux/LLVM guides all land close to Martin's end ("non-obvious," "tricky," "as needed") rather than Ousterhout's. Trend: the *style-guide* consensus (as opposed to the *book* debate) is toward minimalism; Ousterhout is the outlier among primary sources surveyed, not the mainstream.
- **What "why not what" actually means.** Google/LLVM: ban restating literal code behavior, keep the "why." Linux kernel: comments should state **what** the code does (at a level of abstraction above the literal statements) and **why**; the code itself must make **how** obvious. These are not the same claim wearing different words — Linux's "what" is Google's banned "what" turned into a required higher-level summary. A rule that says "never say what, only why" without Linux's how/what/why split will misclassify a legitimate Linux-style function-header summary as a violation.
- **Comment volume as a product decision.** Rust's ecosystem (rustdoc book: "the more documentation... the better"; C-EXAMPLE: examples on nearly every public item) treats docs as a product surface for external consumers via docs.rs. Google/Linux/LLVM treat docs as a maintenance aid for people who already have codebase context. Trend: no convergence — these are two different audiences (public-crate consumer vs. internal maintainer) and the fleet's own ocx critique already found this exact confusion (interface docs counted as maintenance comments) costly. The fleet should keep the two counted and ratcheted separately, not converged into one number.
- **TODO attribution format, even within one organization.** Google C++ prefers a bug ID over a bare name; Google Shell accepts a bare name with no tracker mentioned. Not a trend so much as an unresolved inconsistency inside a single style-guide family — the fleet cannot inherit "Google's TODO rule" as if it were singular.
- **Stale/incorrect comments as a real cost.** Ousterhout: "I have not found them to be a significant problem over my career... the cost of missing comments is easily 10-100x the cost of incorrect comments" (his own unweighted personal estimate, no citation). This sits in tension with the already-covered empirical literature (Wen et al. ICPC 2019: comment-inconsistent commits ~1.5x more bug-prone; DocChecker's staleness-detection research existing at all implies the industry treats staleness as worth building tooling for). Trend: the measured literature takes staleness more seriously than Ousterhout's practitioner intuition does; a rule citing Ousterhout's stale-comments-are-fine claim without the counter-evidence would be one-sided.
