## Summary

- An ADR's job per Nygard is narrower than a design doc: title, context (neutral), decision (active voice), status, consequences — "one or two pages," prose not bullets.
- MADR 4.0 (2024-09-17) added a "Confirmation" section asking explicitly for an automated fitness function (e.g. ArchUnit) or review that checks compliance — decisions now point at a check, not just a narrative.
- MADR ships four template variants (full/minimal × annotated/bare) precisely so a team can shrink the mandatory surface without forking the convention — a ratchet-friendly template design.
- Decision status is a closed vocabulary — proposed, rejected, accepted, deprecated, superseded by ADR-NNNN — and supersession never deletes the old record; adr-tools' `-s` flag encodes this in the tool itself.
- e-adr embeds a decision pointer directly in source as a Java `@ADR(1)` annotation resolving to `docs/adr/0001-*.md`; it is the closest existing prior art to "a comment that names a decision record."
- matklad's counter-argument to embedding pointers everywhere: prefer names over links in architecture docs, because links rot and names are re-findable by symbol search — a direct tension with e-adr's approach.
- The Linux kernel's submitting-patches doctrine gives the cleanest split for where "why" lives: in-code comments explain **how** the code works with its neighbors; the commit message explains **why** the change exists, "so should make sense to a competent reader who has long since forgotten the immediate details."
- Git trailers (`git-interpret-trailers`) are a structured, machine-parseable key:value block already sitting at the bottom of every commit — the mechanism the (separately covered) Lore "decision shadow" protocol builds on.
- Conventional Commits v1.0.0 puts rationale in the commit **body**, structured metadata in **footers**; `BREAKING CHANGE:` is the one footer with build-tooling consequences (semver MAJOR).
- Tim Pope's 2008 seven rules (50/72 char wrap, imperative mood, blank line before body) remain the de facto style baseline that Conventional Commits layers structure onto.
- Kent Beck's 2024 "Documentation Tradeoff" ranks four ways to communicate design intent — simplify, socialize, test, document — and puts prose documentation last because "passing tests are guaranteed to be in sync with the code" while docs decay; his ordering assumes a socialization channel (pairing, whiteboarding) that a cold agent reading a file alone does not have.
- Fitness functions (Ford/Parsons/Kua's term, operationalized by ArchUnit, pytest-archon, arch-go) convert a Consequences-section claim ("we will keep layers separate") into a CI-checked assertion; arch-go additionally reports a numeric "compliance level" (e.g. 3/4 rules met = 75%) rather than a binary pass/fail.
- pytest-archon's own pitch is explicitly about discoverability over prose: rules "make new people on the project aware of the structure through a simple set of rules, instead of lore" — i.e., a runnable check replaces a paragraph of explanation.
- BDD per cucumber.io is a three-step cycle — Discovery, Formulation, Automation — and its output (Gherkin scenarios) is offered as "living documentation" because it is both human-readable and executable; DDD's Ubiquitous Language is the vocabulary layer underneath it, shared by code, tests and business conversation.
- DDD's Intention-Revealing Interfaces pattern is explicitly a comment-avoidance technique: "Name classes and operations to describe their effect and purpose, without reference to the means by which they do what they promise" — the naming-over-commenting move that a code-docs rule can cite by name.
- Osherove's 2005 `UnitOfWork_StateUnderTest_ExpectedBehavior` naming convention is the oldest attempt to make a test name carry a requirement; it is now contested by natural-language/Given-When-Then styles precisely because it degrades under refactoring.
- DO-178C and IEC 62304 both mandate bidirectional traceability (requirement → design → code → test, and back) as an audited artifact, not a convention — the heaviest-weight version of "a reader must recover why this line exists," useful as an upper bound on what a lightweight agent-era scheme should approximate cheaply.
- No source in this corpus proposes a length cap on a why-comment before its content must move to a decision record — the gap the frame's H4/eval is meant to fill is real and unaddressed by existing methodology literature.
- Living Documentation's core move (Martraire) is treating existing artifacts — code, comments, commit history — as the documentation, generated/curated rather than separately authored; this is the strongest existing argument against maintaining prose docs as a parallel artifact at all, once tooling can extract them.
- Across every ADR tool surveyed (adr-tools, log4brains, e-adr, MADR), the record itself lives as a file in the repo, versioned with the code — none of the surveyed conventions store decisions in an external wiki or ticket system as the source of truth.

## Survey

### 1. Michael Nygard, "Documenting Architecture Decisions" (2011)

The foundational ADR post. Defines an "architecturally significant" decision as one affecting structure, non-functional characteristics, dependencies, interfaces, or construction techniques, and gives a five-part template: Title, Context (stated neutrally, "not styled in judgmental language"), Decision (active voice, "We will …"), Status (proposed/accepted/deprecated/superseded), Consequences (all effects, "not just the 'positive' ones"). Length guidance is explicit and still frequently violated by later tooling: "The whole document should be one or two pages long, and we will write it as if it were a conversation with a future developer... full sentences, connected to each other... Bullets kill people, even PowerPoint bullets." On supersession: decisions are never deleted; "we will keep the old one around, but mark it as superseded." [Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

### 2. adr.github.io — the ADR umbrella site

Aggregates terminology across the ADR ecosystem: an Architectural Decision (AD) is "a justified design choice addressing a functionally or non-functionally significant requirement," an ADR "captures a single AD," and the collection is a project's "decision log." Points to sibling pages for templates, tooling, and practices rather than defining lifecycle states itself. [Architectural Decision Records (ADRs)](https://adr.github.io/)

### 3. MADR (Markdown Architectural Decision Records) template and changelog

The current default template as of 4.0.0 (2024-09-17). Frontmatter carries `status: "{proposed | rejected | accepted | deprecated | … | superseded by ADR-0123}"`, `date`, `decision-makers`, `consulted`, `informed` — the last two borrowed from RACI. Body sections, in order: **Context and Problem Statement** (guidance: "two to three sentences" or a question), optional **Decision Drivers**, **Considered Options**, **Decision Outcome** (a chosen-option sentence with justification), optional **Consequences** (Good/Bad/Neutral bullets), optional **Confirmation** — added in 4.0 and explicitly framed as executable: "Is there any automated or manual fitness function? … a test with a library such as ArchUnit can help validate this. Note that although we classify this element as optional, it is included in many ADRs." Optional **Pros and Cons of the Options** and **More Information** close the template. Four variants ship — `adr-template.md` (annotated), `-minimal.md` (mandatory sections only, still annotated), `-bare.md` and `-bare-minimal.md` (same two tiers, no explanatory text) — added in the 4.0.0-beta (2024-09-02) specifically per [issue #88](https://github.com/adr/madr/issues/88) so teams can shrink the ceremony without forking the schema. [MADR template](https://github.com/adr/madr/blob/main/template/adr-template.md), [MADR CHANGELOG](https://github.com/adr/madr/blob/main/CHANGELOG.md)

### 4. adr-tools (npryce)

CLI wrapper: `adr init <dir>` (default `doc/adr`) creates the first ADR, which itself documents the decision to use ADRs and links to Nygard's article. `adr new "<title>"` numbers and opens a new record. Supersession is a first-class command: `adr new -s <n> <title>` creates a new ADR and marks ADR *n* superseded, updating its status field automatically — the tool enforces "never delete, always mark" rather than leaving it to author discipline. [adr-tools README](https://github.com/npryce/adr-tools)

### 5. log4brains

Turns a git-tracked ADR folder into a searchable static site: timeline view, full-text search, git-derived metadata, and — notably — "no enforced numbering schema," specifically to avoid merge conflicts when multiple branches add ADRs concurrently (a concurrency problem the agent-fleet case shares). Supports per-package ADRs in a monorepo alongside global ones. Commands: `log4brains init`, `adr new`, `preview` (local hot-reload UI), `build` (static site for CI deploy to Pages/S3). [log4brains](https://github.com/thomvaill/log4brains)

### 6. Joel Parker Henderson's architecture-decision-record repo

A template catalog (11+ variants: Nygard, Tyree/Akerman, EdgeX, arc42, "Alexandrian," MBA-style business-case, MADR, Planguage, Y-statements, ITDs) rather than a single convention. Its explicit non-goal guidance is the most-cited part: write an ADR when a decision has "meaningful scope and risk"; skip it when the decision "is limited in scope and time and risk and cost, or is already covered elsewhere" — a scope filter this program's cleanup rule can reuse verbatim as a decision-record-vs-comment routing test. Naming convention: lowercase, dash-separated, present-tense imperative verb phrase (`choose-database.md`). [architecture-decision-record](https://github.com/joelparkerhenderson/architecture-decision-record)

### 7. e-adr (Embedded Architectural Decision Records)

The one existing convention for pointing from source code directly at a decision record. Two Java annotations: `@ADR(1)` links a class/method to `docs/adr/0001-*.md` by number (format-agnostic — MADR or Nygard both supported); `@MADR(...)` embeds an entire record's fields (`title`, `contextAndProblem`, `alternatives`, `chosenAlternative`, `justification`, `relatedDecisions`) as annotation parameters, i.e., the decision record lives *in* the code rather than being pointed at. Shipped as a Maven/Gradle dependency (`io.github.adr:e-adr`). Example: `@ADR(1)` on `class MADRAnnotationDemoClass`. This is prior art already named in the harness context as "already covered" — the extension here is the concrete mechanism (two annotation shapes, not one) and that it is Java-only with no equivalent surfaced for Rust/Python/TS/Go in this survey. [e-adr](http://adr.github.io/e-adr/)

### 8. ADR template variants page

Characterizes the Y-statement format precisely: "In the context of `<use case/user story>`, facing `<concern>` we decided for `<option>` to achieve `<quality>`, accepting `<downside>`" — a single-sentence ADR, the most compressed format surveyed. Also notes ISO/IEC/IEEE 42010:2011 suggests nine information items for architecture decisions, i.e., a decision-record shape with a standards body behind it, independent of the ADR movement. [ADR Templates](https://adr.github.io/adr-templates/)

### 9. ThoughtWorks Technology Radar — "Lightweight Architecture Decision Records"

First appeared **Trial, November 2016**; moved to **Adopt, May 2018**. Rationale, quoted: "Much documentation can be replaced with highly readable code and tests. In a world of evolutionary architecture, however, it's important to record certain design decisions for the benefit of future team members as well as for external oversight." Explicit storage guidance: keep records "in source control [as markdown files] rather than wikis or collaboration tools," so they stay synchronized with the codebase. This is the clearest industry-adoption signal (Adopt ring, not just Trial) among the sources surveyed. [Lightweight Architecture Decision Records](https://www.thoughtworks.com/en-us/radar/techniques/lightweight-architecture-decision-records)

### 10. arc42, Section 9 — Architecture Decisions

Adopts Nygard's ADR wholesale into a broader arc42 template, crediting it for producing "smaller pieces of documentation" that are "easier to read, create and maintain" than one monolithic decisions section. Explicit anti-redundancy rule: document "only architecturally relevant decisions," and don't duplicate what's already covered in arc42 §4 (Solution Strategy) — a boundary rule directly analogous to the comment-vs-ADR boundary this program needs. [arc42 §9](https://docs.arc42.org/section-9/)

### 11. Gojko Adzic, Specification by Example (2011) — via gojko.net

Adzic's own page frames the book as a distillation of practice from "over 50 [Lean/Agile] projects." The living-documentation claim central to this program's corpus: acceptance-test specifications, written and refined collaboratively, double as documentation because they are executable — "the examples are the only executable part of the test" — so unlike prose they cannot silently drift from what the system does, only fail loudly. [Specification by Example](https://gojko.net/books/specification-by-example/)

### 12. Cucumber.io — BDD documentation

Defines BDD as "a way for software teams to work that closes the gap between business people and technical people," operating as a three-step cycle: **Discovery** (explore examples, find what the system *could* do), **Formulation** (write examples as executable specifications — Gherkin — confirming what it *should* do), **Automation** (examples become tests driving what it *actually does*). Gherkin's stated value is being "a medium that can be read by both humans and computers" — the same dual-reader requirement this program applies to comments, but solved by making the artifact executable rather than by shortening it. [BDD docs](https://cucumber.io/docs/bdd/)

### 13. Eric Evans, Domain-Driven Design — Ubiquitous Language / Intention-Revealing Interfaces / Supple Design (via secondary notes, cross-checked)

Ubiquitous Language: a shared vocabulary spanning domain experts and code, where "changes to the language are changes to the domain model" — i.e., naming is not decoration, it *is* the model, and a name that drifts from the language is a defect independent of any comment. Intention-Revealing Interfaces, quoted: "Name classes and operations to describe their effect and purpose, without reference to the means by which they do what they promise" — an explicit instruction to encode the *what/why* in the signature so a comment restating it becomes redundant by construction. Supple Design, quoted: "To be open to change, a design must be easy to understand, revealing the same underlying model that the client developer is drawing on." These are the book's own terms (1st ed. 2003) and the clearest primary argument in this corpus that naming/typing is a comment-avoidance mechanism, not merely a style preference. [DDD key concepts notes](http://www.withouthaste.com/codeNotes/domainDrivenDesign.php); official one-page reference exists but its PDF could not be text-extracted this session, so no further quotes are drawn from it: [DDD Reference (PDF)](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)

### 14. Building Evolutionary Architectures (Ford, Parsons, Kua) — fitness functions, via ArchUnit/pytest-archon/arch-go as the executable form

The book's term "fitness function" is now instantiated by concrete tools surveyed directly:

- **ArchUnit** (Java): a fluent API — `classes().that().resideInAPackage("..service..").should().onlyBeAccessed().byAnyPackage("..controller..", "..service..")` — that imports compiled classes into an in-memory model and checks package/layer/cycle/naming/annotation rules. JUnit-native: `@AnalyzeClasses` + `@ArchTest` fields, with JUnit 4/5/6 support and cached class imports across runs. [ArchUnit User Guide](https://www.archunit.org/userguide/html/000_Index.html)
- **pytest-archon** (Python): rules are import-boundary tests written with an `archrule(...)` DSL inside pytest, explicitly pitched as a discoverability mechanism, not just a lint: "Explicitly defined architectural boundaries helps you keep your code in shape... New people on the project are made aware of the structure through a simple set of rules, **instead of lore**." Supports custom fitness functions via a callback receiving the matched module and its direct/transitive imports. [pytest-archon README](https://github.com/jwbargsten/pytest-archon)
- **arch-go** (Go): rule categories include allowed/disallowed internal, stdlib and third-party dependencies per package, and package-content shape rules (`shouldNotContainInterfaces`, `shouldNotContainStructs`, `shouldOnlyContainInterfaces`, etc.), configured in `arch-go.yml` and run via `go test`. Reports a numeric **compliance level** — e.g. 3 of 4 rules met = 75% — checked against a configured threshold, rather than a binary pass/fail; this graduated-compliance model is one candidate shape for a per-package comment-density ratchet. [arch-go README](https://github.com/arch-go/arch-go)

### 15. Roy Osherove — unit test naming standard (2005)

Original post, dated 2005-04-03. Pattern: `[UnitOfWork_StateUnderTest_ExpectedBehavior]`, e.g. `Sum_NegativeNumberAs1stParam_ExceptionThrown()`, `Parse_OnEmptyString_ExceptionThrown()`. Four stated principles: test names should express a specific (business or technical) requirement; must communicate both the input/state condition and the expected result; should read as declarative facts, prioritizing readability over brevity; must name the method under test. This is the earliest attempt in the corpus to make a test's *name alone* recoverable as a spec line, twenty years before "agents read test names cold" became the operative constraint. [Naming standards for unit tests](https://osherove.com/blog/2005/4/3/naming-standards-for-unit-tests.html)

### 16. Kent Beck — "The Documentation Tradeoff" (2024-06-12)

Frames documentation as the costliest of four ways to transmit design intent, in ascending-cost order: **Simplify** ("the superior programmer exercises superior design skills to avoid having to exercise superior communication skills"), **Socialize** (pairing, whiteboarding, conversation), **Test** ("Passing tests are guaranteed to be in sync with the code" — his stand-in for "cannot lie"), **Document** (justified only when three conditions hold together: large audience, API stability, low opportunity cost). Names the decay loop explicitly: "More documentation leads to more decay leads to more maintenance leads to more pressure leads to less documentation." Directly relevant tension for this program: Beck's ordering assumes a Socialize channel is available; a cold agent reading a file alone has no pairing/whiteboard option, so its second-best channel collapses straight to Test and Document, raising the stakes on both relative to Beck's human-team calculus. [The Documentation Tradeoff](https://newsletter.kentbeck.com/p/the-documentation-tradeoff)

### 17. matklad — "ARCHITECTURE.md" (2021-02-06)

Argues for one file (a "codemap") answering "where's the thing that does X?" and "what does the thing I'm looking at do?", pitched at the *coarse-grained* module level, explicitly not implementation detail. Concrete maintenance rules: "Keep it short: every recurring contributor will have to read it"; only document things "unlikely to frequently change"; revisit "a couple of times a year," not on every commit. Directly opposes e-adr's per-callsite-annotation approach: "name, don't link" — name important files/modules/types in prose and let the reader use symbol search, because names survive refactors and links don't require maintenance to *stay wrong* silently. Points to rust-analyzer's `docs/dev/architecture.md` as the reference example. [ARCHITECTURE.md](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)

### 18. git-interpret-trailers

The mechanism, not a methodology: a trailer is a `key: value` pair in a blank-line-preceded block at a commit message's end; `git interpret-trailers --trailer key=value --parse` reads and writes them programmatically. This is exactly the substrate the separately-covered Lore "decision shadow" protocol (arXiv 2603.15566, already covered by prior research — see below) proposes structuring: constraints, rejected alternatives and verification metadata as trailers rather than freeform prose, because trailers are `grep`/parse-able where prose paragraphs are not. [git-interpret-trailers](https://git-scm.com/docs/git-interpret-trailers)

### 19. Conventional Commits v1.0.0

Format: `<type>[optional scope]: <description>`, blank line, optional **body** ("providing additional contextual information about the code changes" — i.e., the why), blank line, optional **footer(s)** as `token: value` or `token #value` pairs (this is git trailer syntax). `BREAKING CHANGE:` is the one footer with build-tool consequences (maps to semver MAJOR); it can also be signaled with `!` before the colon. This is the widest-adopted convention that already puts structured, checkable metadata (footers) below freeform rationale (body) in the same artifact — a template this program's "where does X go" table can point at directly. [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)

### 20. Tim Pope — "A Note About Git Commit Messages" (2008-04-19)

Seven style rules still cited as baseline: separate subject from body with a blank line ("critical"); subject ≤ 50 characters, capitalized, no trailing period; imperative mood ("Fix bug" not "Fixed bug"); wrap body at ~72 characters (his stated reason: `git log` piped through `less -S`, and 80-column terminals minus margin, land on 72; also relevant when `git format-patch` turns commits into indented email replies). Predates Conventional Commits by nine years; the newer spec's body/footer split is additive on top of, not a replacement for, these formatting rules. [A Note About Git Commit Messages](https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html)

### 21. Linux kernel — submitting-patches, "Describe your changes"

The clearest explicit division of labor in the whole corpus between in-code comments and the commit message: code comments explain **how** the code works with its neighbors; the commit message explains **why**, because it "will be committed to the permanent source changelog, so should make sense to a competent reader who has long since forgotten the immediate details of the discussion that might have led to this patch." Also requires failure symptoms (log lines, oops messages) in bug-fix commit bodies specifically so future `git log` search finds the patch. This is the oldest and most battle-tested "comment vs. commit-message" routing rule surveyed, predating ADRs, still current in the maintained kernel docs. [Submitting patches](https://docs.kernel.org/process/submitting-patches.html)

### 22. DO-178C traceability (via Parasoft explainer, standard itself is paywalled)

Four traceability objectives quoted: system/high-level requirements allocated to software "were developed into the high-level requirements"; high-level and derived requirements "were developed into the low-level requirements"; low-level requirements "were developed into source code"; and "traceability between requirements and test cases, test procedures, and test results" — required to run **forwards and backwards** across the full chain (system requirement → software requirement → code → test). This is traceability as an audited, bidirectional artifact rather than a best-effort convention — the ceiling this program's lightweight scheme should be measured against, not copied wholesale. [DO-178C traceability](https://www.parasoft.com/learning-center/do-178c/requirements-traceability/)

### 23. IEC 62304 traceability (via Jama Software explainer, standard itself is paywalled)

Requires the Software Development Plan to "explain how system requirements, software requirements, system tests, and risk controls will stay linked" *before* development begins — traceability is planned, not retrofitted. Links run requirements → architecture → detailed design → units → tests, plus a mandatory link from risk controls (from ISO 14971 hazard analysis) to the software elements implementing them. The clause citation available secondhand is coarse ("Clause 5," the eight development activities); no sub-clause numbers confirmed. [IEC 62304 guide](https://www.jamasoftware.com/requirements-management-guide/medical-devices/iec-62304/)

## Recent shifts seen in this corpus

- **2024-09-17 — MADR 4.0** added the Confirmation field, formally tying a decision record to an automated fitness function for the first time in the mainline template lineage (it existed as tool-specific practice before, e.g. via ArchUnit blog posts, but not as a template field). Invalidates the older assumption that a decision record is pure prose with no CI hook.
- **2024-09-02 — MADR 4.0-beta** added minimal/bare template tiers specifically to let teams shrink mandatory ADR content — direct precedent for "shrink the ceremony without abandoning the convention," which is this program's whole premise applied one layer up (decision records, not comments).
- **2024-06-12 — Kent Beck, "The Documentation Tradeoff"** reframes documentation as the last-resort channel behind Simplify/Socialize/Test. This is recent enough, and specific enough about *why* documentation decays (the maintenance-pressure loop), that it should be treated as current guidance, not superseded — but its ordering was built for human teams with a Socialize channel; applying it unmodified to agent-authored/agent-read code overstates how cheap "Test" is relative to "Document" once no human pairing session exists to catch a stale comment early. Treat the ranking as needing an agent-era correction, not adoption verbatim.
- **2026-03 — Lore protocol (arXiv 2603.15566, already covered by prior research)** proposes structuring git trailers as a "decision shadow" specifically because "each commit captures a code diff but discards the reasoning behind it" for agent-authored commits — the first source in either corpus to frame the commit-message-as-why-store problem as agent-specific rather than a general software-engineering hygiene issue. This directly extends the older Linux-kernel and Tim-Pope guidance (both pre-2010, written for human contributors) into the agent-authored-commit case; it has not yet been adopted by any tool surveyed here (git-interpret-trailers, Conventional Commits, adr-tools, log4brains all predate or ignore it).
- **No dated shift found for e-adr, adr-tools, or log4brains' core mechanics** — the surveyed pages give no recent version/date signal indicating these conventions have changed materially in the last 18-24 months; treat them as stable, not stale (the ADR movement itself is 15 years old and still actively maintained per the MADR changelog above).

## Contested

- **Prose vs. structured ADR.** Nygard: "full sentences... Bullets kill people." MADR: a template with 6+ headed sections and bullet-first guidance throughout. Trend: structured is winning in tooling (every surveyed tool — adr-tools, log4brains, e-adr — defaults to MADR, not Nygard's freeform prose), but Nygard's original is still the more-cited *definition* of what an ADR is for. For an agent-authored fleet, structured almost certainly wins further still: bullets are more parseable and more diffable than paragraphs.
- **Embed the pointer in code (e-adr) vs. name it and let search find it (matklad).** No consensus; these are opposite mechanisms solving the same problem (code → decision record), and both are current (e-adr is an active library; matklad's post is 2021 but still the most-cited ARCHITECTURE.md argument as of 2026). Direction: matklad's "names don't rot, links do" argument has spread further outside the Java ecosystem where e-adr lives (see `awesome-architecture-md`'s adoption list found during search), suggesting name-based discovery is trending over link-embedding for polyglot fleets.
- **Test-name granularity.** Osherove's three-part mechanical convention (2005) vs. natural-language/Given-When-Then test names. Search evidence: "developers found that this naming style became difficult to understand during code refactoring, and modern practices tend to favor human-readable naming." No single winning convention has replaced Osherove's; the field is fragmented by ecosystem (xUnit-style codebases skew Osherove-like, BDD-style codebases skew Given-When-Then) rather than converged.
- **Beck's documentation-is-last-resort stance vs. the entire ADR/living-documentation movement.** Beck (2024) treats separate documentation as something to minimize; MADR, arc42, ThoughtWorks radar (Adopt ring since 2018) and Martraire's whole book argue for *more* structured decision capture, not less. These are not strictly contradictory — Beck is talking about ongoing design-rationale prose in general, ADRs are a narrow, bounded, point-in-time artifact — but the tone is opposed, and this program has to pick a side for the "does this decision need a record at all" gate (topic #7 leans toward the Joel Parker Henderson scope filter as the practical resolution).
