# Platform and toolchains

## Verdict

1. **Two numbers, never one.** The toolchain JDK (what runs `javac`) and the bytecode/API floor (`options.release` / `maven.compiler.release` / `jvmTarget`) are independent and both stated explicitly. `sourceCompatibility`/`<source>`/`<target>` alone is the defect, because it sets the class-file version without checking the target platform's API surface ([jdk-floors §1](jvm-platform-and-toolchains/jdk-floors-modules-and-removed-apis.md#1-toolchain-vs---release-two-numbers-two-jobs)).
2. **But the check for that rule reads the owning compile execution, never a grep count.** `google__guava@5fb424c43a:pom.xml:215-216` uses `<source>1.8</source><target>1.8</target>` *correctly* as the base layer of a two-execution MR-JAR. A raw `grep -c sourceCompatibility` flags the repo that gets it right — the same trap wave-2 correction 33 caught on `GRADLE-DEP-05`.
3. **OCX SDK: floor 17, toolchain 25, CI matrix 17/21/25.** Spring Boot 4 and JUnit 6 both hold at 17 as of 2026-09-12 while the LTS is 25; matching the frameworks costs nothing and maximises the addressable consumer base. Toolchain 25 also lands the SDK on the vendor-independent side of NullAway's `jspecifyMode` precondition for free.
4. **SDK and library: a real `module-info.java` with a minimal `exports` list.** It is the `__all__` analogue the config inventory asks for (Axis 3 / M-Y-04): one file states the whole contract, compiler-enforced. `Automatic-Module-Name` is not a lighter `module-info` — it is a name with zero encapsulation, correct only when the floor is below 9 or the module cannot host a descriptor. Application and CLI: CONSIDER.
5. **`jdeps --jdk-internals -R` and `jdeprscan --for-removal` are a gate, not a tip.** 0/32 exemplars run either in CI. This is a new commitment the rules impose, stated as such.
6. **Encoding is two fixes at two layers, and both are MUST.** `options.encoding`/`<project.build.sourceEncoding>` covers `javac`'s source reading; `org.gradle.jvmargs=-Dfile.encoding=UTF-8` covers the Gradle daemon, which launches *before* toolchain selection and which Gradle never sets itself ([gradle/gradle#2270](https://github.com/gradle/gradle/issues/2270), open, milestone 10.0.0-RC1). A JDK-18+ floor fixes neither. 13/32 and 15/32 adopt them, and they are not the same repos.
7. **Timezone pinning stays CONSIDER, against the map's P1.** Priority ranks research value; severity ranks what fails a build. 0/32 corpus support means a MUST here would be invention wearing a measurement's clothes — and `jvm-quality-gates.md` verdict 10 names this exact rule as the thing an agent invents when told to "harden the test gate."
8. **The adversarial-locale CI job drops from the dive's SHOULD to CONSIDER**, for a reason the dive did not state: the call-site lint (`-Xep:StringCaseLocaleUsage:ERROR`, `DefaultLocale`, owned by `JAVA-LINT`) is the MUST that catches the defect. Guava's `hi`/`IN` suite is the residual belt-and-braces, adopted 2/32.
9. **Archive reproducibility is not this family's rule.** `GRADLE-CACHE-17` owns it and `shadowJar` inherits it unmodified (verified by source: `ShadowJar` never overrides `createCopyActionExecuter()`). JAVA-PLAT keeps only the half Gradle's archive defaults cannot reach: `Properties.store()`'s unconditional date comment, Maven's `project.build.outputTimestamp`, and `mergeServiceFiles()`'s classpath-ordered merge.
10. **Kotlin: `jvmToolchain(N)` does not raise the bytecode target.** `jvmTarget` still defaults to `"1.8"` and the toolchain only back-fills it when unset. A Kotlin build compiling on JDK 21 and shipping Java 8 bytecode is the default state, not an accident.
11. **In a mixed Java+Kotlin module, `options.release` and `jvmTarget` are one decision stated twice**, and `jvmTargetValidationMode` (default `ERROR`, not `WARNING`) is what catches them diverging. Neither sub-dive stated the joint rule; it is KT-COMP-04 here.
12. **kapt is not permitted in a new module** unless the specific processor has no KSP implementation and a comment at the `kapt(...)` line names it. In the corpus kapt survives only as a deliberate legacy-path regression fixture (`google__dagger`'s `javatests/artifacts/**`), never as production build logic.
13. **Retired `-X` flags are dead weight, not harmless.** `-Xwhen-guards`, `-Xnon-local-break-continue`, `-Xmulti-dollar-interpolation` (Stable, flag-free, Kotlin 2.2.0), `-Xcontext-parameters` (Stable 2.4.0). `-Xcontext-receivers` is always a defect — that design was withdrawn, not renamed.
14. **The Kotlin floor claim has two halves that are routinely conflated**: `-language-version 1.8/1.9` was dropped in Kotlin **2.3.0**; the K1 compiler itself was removed in **2.4.0**. Frame correction 2 states the second; the dive establishes the first. Both are true and a rule must name which it means.
15. **Dokka's version-and-DSL rule belongs here (KT-COMP), not in `docs-quality`.** It is an edit to a `*.gradle.kts` file. What goes to the sibling set is only the unsolved half: Dokka generates its own site and fits no row in `docs-quality`'s generator table (M-Y-06).

## AI-agent failure modes

Ranked by how often it bites.

1. **Writes `sourceCompatibility`/`<source>`/`<target>` because that is the dominant pre-2020 idiom, and it looks identical in effect on a same-JDK build.** The bug only appears when the compiling JDK is newer than the target. **Check**: grep the old pair, then open the owning execution and confirm a `release` value governs it — do not count hits.
2. **Reaches for `--add-opens=ALL-UNNAMED` broadly, or `--illegal-access=permit`, which has done nothing since JDK 17.** The JDK 9–16 warning-only behaviour is what its training window recorded. **Check**: `--illegal-access` anywhere on a JDK 17+ target is a hard finding; `ALL-UNNAMED` spanning more than one library's actual internal package is a smell. Confirm with `jdeps --jdk-internals -R`.
3. **Sets `jvmToolchain(21)` and believes the bytecode target moved.** It did not — `jvmTarget` defaults to `"1.8"` and the toolchain only back-fills an unset value. **Check**: `grep -A3 'jvmToolchain'` for a sibling `jvmTarget`.
4. **Treats JEP 400 as "encoding is solved since 18" and omits the `Charset` argument.** The default value changed; the API surface did not, and JEP 400 lists not-deprecating those overloads as an explicit non-goal. **Check**: `-Xep:DefaultCharset:ERROR`, faster than reasoning about it.
5. **Emits `-Xjvm-default=all` / `-Xjvm-default=all-compatibility`, the 2023-era shape.** **Check**: `grep -rn 'Xjvm-default' **/*.gradle.kts` — and translate the *intent*, not the flag name, because the implicit default is now `ENABLE`.
6. **Writes kapt scaffolding for a new Dagger/Hilt/Moshi/Room module.** Years of training data show kapt. **Check**: `grep -rln 'kotlin("kapt")\|id("org.jetbrains.kotlin.kapt")'` on newly-added build files; cross-reference the processor against KSP's supported-libraries page.
7. **Adds `-Dfile.encoding` to the test or `JavaExec` task and stops there.** That fixes task JVMs and leaves the daemon — which reads the version catalog and properties at configuration time — on the host default. **Check**: `grep -c 'file.encoding' gradle.properties` must be non-zero independently.
8. **Invents timezone pinning as an obvious hardening step and states it at MUST confidence.** Named in `jvm-quality-gates.md` verdict 10, reproduced here for the sibling family. **Check**: any rule or review comment requiring a timezone pin must cite what broke; citing nothing means it is the invented pattern.
9. **Copies Gradle's pre-9.0 reproducibility snippet onto a wrapper that already pins ≥ 9.0.0**, because it reads as correct boilerplate. It is the exact opposite of correct — kafka ships this live. **Check**: read `gradle/wrapper/gradle-wrapper.properties` *before* accepting any diff touching `reproducibleFileOrder`/`preserveFileTimestamps`/`useFileSystemPermissions()`.
10. **Passes `-Xwhen-guards`/`-Xcontext-parameters` "to be safe"**, or reaches for `-Xcontext-receivers` when asked for context parameters — two sequential, differently-named Kotlin features, one withdrawn. **Check**: grep the flag names against the Kotlin version in `libs.versions.toml`.
11. **Upgrades a build to JDK 21+ without checking for a `getFirst()`/`reversed()` collision**, because the resulting error reads like an unrelated Gradle DSL bug. **Check**: a JDK-21 migration PR touching a codebase with user types implementing `List`/`Deque`/`Map` that never mentions SequencedCollection is under-scoped.
12. **Recommends `Automatic-Module-Name` for a new published library as if it were a lighter `module-info`.** Older tutorials present them as two ways to modularise. **Check**: any such recommendation that does not state "zero encapsulation" is the finding.
13. **States a removal without its JDK number, or attaches a neighbouring one** (JEPs 483/491/493 shipped in **24**, not 25 — the corpus made this exact error once). **Check**: every removal claim carries a number, cross-checked against the [§4 table](jvm-platform-and-toolchains/jdk-floors-modules-and-removed-apis.md#4-the-removed-or-disabled-list-by-jdk-number).
14. **Assumes Kover behaves like JaCoCo (report-only, `check`-independent).** It does not; the default is the opposite. **Check**: never state Kover's binding without citing [kotlinx-kover#523](https://github.com/Kotlin/kotlinx-kover/issues/523); look for `onCheck = false`, `.disable()` or a property gate before calling any `verify { rule {} }` enforced.
15. **Configures Dokka with `tasks.dokkaHtml {}` / `dokkaHtmlMultiModule`** — still the dominant shape in tutorials in 2026. **Check**: any such hit on Dokka ≥ 2.1.0.
16. **Sets `jspecifyMode = true` without reading the JDK vendor.** **Check**: the `setup-java` `distribution:` value against JAVA-PLAT-03's matrix.
17. **Believes `mergeServiceFiles()` sorts.** It preserves classpath-resolution order via a `LinkedHashSet`, so a dependency-graph reorder silently rewrites merged provider files. **Check**: any "byte-identical shadowJar" claim made without locked or fixed dependency versions is unverified.
18. **Hallucinates a `Properties.store()` suppression flag.** None exists in the JDK as of 25 — only `java.properties.date` (Maven) or a custom subclass. **Check**: any cited JDK API to suppress the comment must be shown against `java.util.Properties`'s actual public surface.

## Open questions

**Needs an owner decision**

1. **Does JAVA-PLAT-17 (timezone) stay CONSIDER?** The 0/32 measurement cannot distinguish "nobody needs it because GitHub runners default to UTC" from "a real latent gap nobody has looked for." Deciding it up requires a CI-runner-timezone audit nobody has run; deciding it down requires accepting that a date-sensitive library's suite may be passing for an environmental reason.
2. **Does the SDK ship `module-info.java` only, or also an `Automatic-Module-Name` manifest entry?** The corpus says a library picks one (12/32 vs 10/32, largely disjoint). JAVA-PLAT-04 says one. Confirm nobody wants the belt-and-braces pair.
3. **When does the floor move off 17?** JAVA-PLAT-11 (in the sub-artifact) writes the trigger as "when Spring Boot 4 and JUnit 6 move," deliberately not the LTS calendar. Confirm that trigger rather than a date.
4. **Java-first or Kotlin-first for the SDK** (the frame's own open question) decides whether KT-COMP-03 through -07 bind the SDK at all, or only the Gradle plugin.

**Deserves another research round**

- **Kotlin/Java joint compilation in a mixed module.** KT-COMP-04 asserts `jvmTarget` must equal `options.release`, and `jvmTargetValidationMode` enforces it when both compile tasks exist — but nothing in the corpus or the dives measures what happens to a **Kotlin-only** module published alongside a Java-only module at a different target in the same multi-project build, which the validator never sees. *Question: in a multi-project library, what mechanically enforces a single bytecode floor across modules whose compile tasks never meet?*
- **Dokka's place in `docs-quality`.** M-Y-06 records zero Java/Kotlin rows in the sibling set's `tested-examples-by-language.md` and zero Dokka/Javadoc rows in `wiring-by-generator.md`; Dokka emits its own site and fits no existing wiring column. *Question: does Dokka get a new generator row in the sibling set, or does the JVM set carry a "docs examples are tested by a subprocess harness" rule of its own?* This is a sibling-file edit, not a new artifact.
- **`Properties.store()` on the Gradle side.** Maven has `java.properties.date`; Gradle has nothing, and the only shipped workaround in the corpus is a plugin-internal Kotlin class. *Question: is there a supported Gradle-side mechanism, or does every plugin that writes `.properties` output re-implement `ReproducibleProperties`?*
- **JEP 472's `deny` flip.** JDK 24 ships `warn`; the JEP promises only "a future release." Any rule naming a JDK number would be fabricating one. *Question: has a target release been announced since 2026-09-12?*
