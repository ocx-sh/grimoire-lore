## Summary

- **`crypto/rand.Text()` (Go 1.24+) is the MUST for any token, key, nonce or password salt** — never `math/rand` v1 or v2, regardless of Go version; both are non-cryptographic PRNGs even after the v2 API redesign.
- **Every planted `math/rand`/`math/rand/v2` token fires gosec G404**, and every `crypto/rand`-based twin is silent — verified, exit 1 → exit 0.
- **Corpus reality check (20 sites classified): math/rand v1 in production Go code is used for retry jitter, temp-filename disambiguation and load-shuffling, essentially never for a real secret** — the one borderline case, an upload-session ID minted with `rand.Int63()` in a *local test/dev* OCI registry implementation, is exactly the shape that becomes a vulnerability if copied into production.
- **The "G101 fires only at package scope, never on a local `:=`" claim from wave 2 (go-gates/golangci-config.md §4) is WRONG for gosec's current source and for golangci-lint 2.14.0's bundled build** — re-verified on 10 planted variants; G101 registers on `*ast.AssignStmt` (local `:=`) exactly as it does on `*ast.ValueSpec` (package/file-scope `const`/`var`). The real, narrower gap is entropy and value-shape, not scope: G101 fires on any scope when the value matches one of gosec's ~25 hardcoded vendor-key regexes (AWS `AKIA…`, Stripe `sk_live_…`, GitHub `ghp_…`, etc.) or clears its zxcvbn entropy threshold, but stays silent — at *any* scope — on a low-real-entropy dictionary-shaped secret, on a value built by string concatenation, or on a value assigned through a second local variable.
- **`InsecureSkipVerify: true` outside `_test.go` fires gosec G402**; the compliant twin (no skip, explicit `MinVersion: tls.VersionTLS12`) is silent. crypto/tls's own default minimum as of Go 1.27.1 is already TLS 1.2, with TLS 1.3 as the negotiated ceiling and a post-quantum hybrid key exchange (`X25519MLKEM768`, and `SecP256r1MLKEM768`/`SecP384r1MLKEM1024` since 1.26) added to `CurvePreferences` by default.
- **A struct field named like a secret (e.g. `Password`) that reaches `json.Marshal` fires gosec G117**; tagging it `json:"-"` silences it — verified, exit 1 → exit 0.
- **No gosec rule and no golangci-lint linter catches a secret compared with `==`** — confirmed on a planted fixture (0 issues on both the violation and the fix). `crypto/subtle.ConstantTimeCompare` is the MUST; a grep reading heuristic (function name suggests a secret, body contains `==`, file lacks `subtle.ConstantTimeCompare`) is the only mechanical check, and it is watched red/green in this dive.
- **`html/template` is the MUST for any templated HTTP response body; `text/template` is a MUST-NOT there** — no gosec rule and no golangci-lint linter fires on a planted text/template-into-`http.ResponseWriter` fixture; the check is a two-step grep (files importing `text/template` intersected with files referencing `http.ResponseWriter`), watched red/green.
- **`text/template` reaching an HTTP response is not automatically the same bug as unescaped user data** — Caddy's own `caddyhttp/templates` module deliberately uses `text/template` for response bodies and documents the real risk as server-side template injection (attacker-influenced *template content*, not just data), which `html/template`'s escaping would not fix either; its `fileserver/browse.go` directory listing uses `text/template` with manual, context-correct escaping (`{{html .Name}}` for text nodes, `{{.Name | pathEscape}}` for URL attributes) plus a per-request CSP nonce as defense in depth. The fleet MUST still defaults to `html/template` because that manual discipline is not something to expect from generated code; a documented deviation needs the reasoning Caddy's own doc comment gives, not a copy of the mechanism.
- **`unsafe`, `//go:linkname` and cgo are each forbidden by default and require an ADR to use**, per the map's own default (M-I-08). golangci-lint's bundled gosec (2.14.0) did not fire G103 ("audit the use of unsafe block") on any planted `unsafe.Pointer`, `unsafe.String` or `unsafe.SliceData` call in this toolchain, despite G103's own source registering exactly those identifiers — the policy therefore rests on a grep reading heuristic, not a lint MUST, which matches the map's own row justification.
- **`unsafe.String` over a buffer the caller keeps mutating breaks Go's string-immutability guarantee** — demonstrated with a runnable `go test`, not a lint: the "bad" test fails with the mutated byte observed in the returned string (exit 1), the "good" twin (`string(buf)`, a real copy) passes (exit 0).
- **Go 1.23 tightened `//go:linkname`: the linker now refuses a *new* reference to an unexported stdlib/runtime symbol unless that symbol is itself marked `//go:linkname` on its definition side**; existing corpus usages predating 1.23 keep working, and `-ldflags=-checklinkname=0` disables the check for debugging. `cockroachdb/pebble` links into `runtime.mallocgc`, `runtime.memmove` and `runtime.throw` for its manual memory allocator — the single clearest example in the corpus of the "documented, deliberate, load-bearing" exception the ADR path exists for.
- **Real, non-test cgo in this 35-repo corpus is 2/35 (pebble, tailscale)**; the other 128 corpus-wide `import "C"` hits are 97% build-tooling test fixtures (`bazel-contrib/rules_go`'s own cgo-handling tests), a measurement trap already flagged in `exemplar-code-shape.md`.
- **`json.NewDecoder(r.Body).Decode(...)` with no prior body bound is not caught by any golangci-lint linter or gosec rule**; `r.Body = http.MaxBytesReader(w, r.Body, N)` before the decode is the MUST fix, watched red/green with a grep heuristic (files that use `json.NewDecoder(...).Body` minus files that also mention `MaxBytesReader`/`LimitReader`).
- **gosec G120 fires on every `(*http.Request).ParseMultipartForm` call whose body was not first wrapped in `http.MaxBytesReader`, regardless of the `maxMemory` argument passed** — a smaller `maxMemory` alone does *not* silence it (gosec's own doc comment: `maxMemory` bounds only the in-memory part, never the on-disk temp-file part or the total bytes read off the wire); wrapping the body in `MaxBytesReader` first does silence it. Verified red on `ParseMultipartForm(0)`, still red on `ParseMultipartForm(bounded)` without `MaxBytesReader`, green only once `MaxBytesReader` wraps `r.Body` first.
- **Go's `regexp` package is RE2-syntax and guaranteed linear-time in input size by construction** ("a property not guaranteed by most open source implementations of regular expressions" — the package's own doc); it has no backtracking exception, so ReDoS from a stdlib `regexp.Compile`d pattern is a category error unless the code shells out to a different engine. This closes M-I-09's ReDoS half with a normative citation, not a fixture.
- **`crypto/subtle.WithDataIndependentTiming` (Go 1.24) is a newer, stronger constant-time primitive than `ConstantTimeCompare`** — it enables architecture-level constant-time execution (ARM64 `PSTATE.DIT`) around a whole function, including goroutines and cgo calls it spawns; not yet measured in the corpus and not made a MUST here (too new, no exemplar adoption), but flagged for the next `go-upgrade` pass.

## Findings

### 1. `crypto/rand` is the only acceptable source for a token, key, nonce or salt

`crypto/rand.Text()` (added Go 1.24, [pkg.go.dev/crypto/rand#Text](https://pkg.go.dev/crypto/rand#Text)) "returns a cryptographically random string using the standard RFC 4648 base32 alphabet... at least 128 bits of randomness," which is exactly the shape a token/password/API-key generator needs without hand-rolling an encoding over `rand.Read`. `crypto/rand.Read` itself never returns an error under normal operation and will crash the program if its underlying `io.Reader` does — it draws from `getrandom`/`arc4random`-class OS sources, not a seedable PRNG.

`math/rand` (v1) and `math/rand/v2` (Go 1.22+) are **both** unsuitable regardless of version: v2 changed the *API* (better generators, `n.Int()`, no global lock contention) but not the *security model* — neither package claims unpredictability against an adversary who can observe outputs or timing. OWASP's Go-SCP puts this plainly: "you should carefully read the documentation when it states that... `math/rand`... produce[s] a deterministic sequence of values each time a program is run" ([Pseudo-Random Generators](https://raw.githubusercontent.com/OWASP/Go-SCP/master/src/cryptographic-practices/pseudo-random-generators.md)).

### 2. TLS: MinVersion, InsecureSkipVerify, cipher suites

`crypto/tls`'s own doc as of the Go 1.27.1 toolchain in this environment: "By default, TLS 1.2 is currently used as the minimum" ([pkg.go.dev/crypto/tls](https://pkg.go.dev/crypto/tls)), `VersionTLS13` is the negotiated ceiling, and `CipherSuites` left `nil` uses "a safe default list" that "might change over time" — so a fleet `tls.Config{}` with no fields set is already at the floor the MUST wants; the rule exists for the two ways code actively lowers it. Since Go 1.24, the default `CurvePreferences` also includes the post-quantum hybrid `X25519MLKEM768`; Go 1.26 added `SecP256r1MLKEM768`/`SecP384r1MLKEM1024`, both disable-able only via `GODEBUG=tlsmlkem=0`/`tlssecpmlkem=0` — this is a default a fleet CLI should never need to touch, and touching it is itself a finding.

`InsecureSkipVerify`'s doc is explicit about what it removes: "If InsecureSkipVerify is true, crypto/tls accepts any certificate presented by the server and any host name in that certificate" — a complete MITM bypass, not a partial relaxation. gosec's G402 ("Look for bad TLS connection settings") fires on this and on a custom `MinVersion` below `VersionTLS12`, on a `CipherSuites` list containing a deprecated suite, and (per RULES.md) is one of the four configurable-threshold rules alongside G301/G302/G306/G307.

Corpus measurement ([run] §5, already cited by the map): 14 `InsecureSkipVerify: true` sites, 3 of 4 spot-read carry a `//nolint:gosec`/`#nosec` annotation (e.g. `caddyserver/caddy@54937914234b:caddytest/caddytest.go:360`, a test helper) — i.e. acknowledged, not silent; 21 explicit `MinVersion: tls.*` sites, roughly matching the 14 `InsecureSkipVerify` sites plus additional defensive-TLS code.

**Verified (fixture `insecureskipverify/`):** `bad/bad.go` fires G402 exactly on `InsecureSkipVerify: true`; `good/good.go` (`MinVersion: tls.VersionTLS12`, no skip) is silent. The `_test.go` exemption is GO-GATE-09's own exclusion (`exclusions.rules: path: _test\.go, linters: [gosec]`) — cited, not re-verified here.

### 3. Secret handling: G117, constant-time compare, and the real G101 gap

**G117 (secret exposure via marshaling).** gosec's own RULES.md: G117 is "[p]otential exposure of secrets via JSON/YAML/XML/TOML marshaling," configurable via a field-name `pattern` (default matches `secret|token|password`, case-insensitive). Verified: a struct with an untagged `Password string` field marshalled with `json.Marshal` and logged fires `G117: Marshaled struct field "Password" (JSON key "Password") matches secret pattern`; tagging the field `json:"-"` silences it. This is the mechanical MUST for "secrets never reach a log or marshalled struct" — it catches the shape (a credential-named field reaching `encoding/json`), not the string value.

**Constant-time compare.** `crypto/subtle.ConstantTimeCompare(x, y []byte) int` "[r]eturns 1 if the two slices... have equal contents and 0 otherwise. The time taken is a function of the length of the slices and is independent of the contents" ([pkg.go.dev/crypto/subtle](https://pkg.go.dev/crypto/subtle)) — this is the MUST for comparing any secret against a caller-supplied value. **No gosec rule and no golangci-lint linter fires on a plain `supplied == want` secret comparison** — verified empirically (0 issues on both the fixture's `bad/` and `good/` packages under the full fleet roster). This is a genuine, confirmed detection gap: G401-G408 cover weak hashes, bad TLS settings, short RSA keys, weak `rand`, hardcoded IV/nonce and SSH-callback misuse, but nothing in gosec's G4xx family checks *how* a secret is compared. The mechanical check here is necessarily a reading heuristic: functions whose name suggests a secret (`Key`/`Secret`/`Token`/`Password`) that contain `==` and whose file never mentions `subtle.ConstantTimeCompare` — see [Verification runs](#verification-runs) for the exact grep, watched red/green. `crypto/subtle.WithDataIndependentTiming` (Go 1.24) is a stronger, function-scoped primitive worth a future `go-upgrade` mention, but is not yet adopted anywhere in the corpus and is not made a MUST here.

**The real G101 gap (this dive's principal correction to wave 2).** `go-gates/golangci-config.md` §4 states: "a package-scope `const apiKey = "AKIAIOSFODNN7EXAMPLE..."` fires G101; a functionally identical local `password := "Sup3rS3cr3t!2026Password"` inside a function body does **not**. G101 only inspects package/file-scope `const`/`var` declarations." **This is wrong, both for gosec's current upstream source and for the golangci-lint 2.14.0 build in this toolchain.** Reading gosec's own rule (`securego/gosec@master:rules/hardcoded_credentials.go`, fetched 2026-09-26), `NewHardcodedCredentials`'s `Match` function registers on **four** AST node kinds: `*ast.AssignStmt` (a local `:=`/`=`), `*ast.ValueSpec` (package/file-scope `const`/`var`), `*ast.BinaryExpr` (`==`/`!=` comparisons against a literal!) and `*ast.CompositeLit` (a struct/map literal with a credential-shaped key). `matchAssign` and `matchValueSpec` run the *identical* two-stage check: (a) does the identifier's name match the configurable `pattern` (default `(?i)passwd|pass|password|pwd|secret|token|pw|apiKey|bearer|cred`) **and** is the value high-entropy (zxcvbn-scored, default threshold 80 bits total or 3 bits/char at half that threshold); (b) failing that, does the literal value match one of ~25 hardcoded vendor-key regexes (AWS `AKIA[0-9A-Z]{16}`, Stripe `sk_live_[0-9a-zA-Z]{24}`, GitHub `ghp_[a-zA-Z0-9]{36}`, Slack, Google, Twilio, Heroku, Mailgun, etc.) — and stage (b) has **no scope restriction and no name-match requirement at all**.

Re-verified on 10 planted variants (`fixtures/untrusted-input-and-crypto/local-credential/{tA,tB,tD,tF,tG,tI,tJ,tK,tL}` and `bad/`, `good/`, `miss/`):

| shape | scope | value | fires? |
|---|---|---|---|
| `password := "Sup3rS3cr3t!2026Password"` | local | low real entropy, name matches | **no** |
| `const password = "Sup3rS3cr3t!2026Password"` | package | low real entropy, name matches | **no** (identical to local — scope is not the variable) |
| `secret := "sk_live_51H8x..."` | local | Stripe-shaped | **yes** — `G101: ...: Stripe API Key` |
| `x := "AKIAIOSFODNN7EXAMPLE"` | local, non-credential name | AWS-shaped | **yes** — `G101: ...: AWS API Key` |
| `x := "ghp_16C7e42F..."` | local, non-credential name | GitHub-shaped | **yes** — `G101: ...: GitHub personal access token` |
| `password := "kQ9zR2vN7mT4pW8xY1cB6dF3"` | local | high real entropy, name matches | **yes** — generic `G101: Potential hardcoded credentials` |
| `const password = "kQ9zR2vN7mT4pW8xY1cB6dF3"` | package | high real entropy, name matches | **yes** — identical to the local case |
| `password := "kQ9zR2vN7mT4" + "pW8xY1cB6dF3"` | local | same high-entropy value, split by `+` | **no** |
| `raw := "kQ9zR2vN7mT4pW8xY1cB6dF3"; password := raw` | local | same value via a second identifier | **no** |

**Conclusion: scope was never the variable. The real gaps are (1) a low-real-entropy, dictionary-derived secret (zxcvbn scores "Sup3rS3cr3t!2026Password" below threshold even though a human reads it as a password) and (2) any value gosec's static `GetString` cannot resolve to a literal in one step — a `BinaryExpr` concatenation or an indirection through a second variable, both trivially defeat it at *any* scope.** Both gaps matter more for agent-authored code than the scope claim did: an agent asked to "not hardcode the credential" is far more likely to build it from parts or read it through an intermediate variable than to move it to package scope. The grep reading heuristic in [Normative guidance candidates](#normative-guidance-candidates) closes gap (1) directly (it has no entropy gate) and is a partial mitigation for gap (2) only when the literal is still adjacent to the credential-named identifier on the same line.

### 4. Templates: `html/template` for HTML sinks, and the SSTI risk `text/template` alone does not fix

`html/template`'s own doc: it "should be used instead of text/template whenever the output is HTML" and works by contextual autoescaping — "at parse time each `{{.}}` is overwritten to add escaping functions as necessary," so `<a href="/search?q={{.}}">{{.}}</a>` compiles to `<a href="/search?q={{. | urlescaper | attrescaper}}">{{. | htmlescaper}}</a>` ([pkg.go.dev/html/template](https://pkg.go.dev/html/template)). `text/template` performs **zero** escaping of any kind; the same `{{.}}` in a `text/template` renders `<script>...</script>` verbatim.

**No analyzer catches this.** Verified: a `text/template` parsed once at package init and `Execute`d directly into an `http.ResponseWriter` from an `http.HandlerFunc` (with the query parameter interpolated unescaped) produces **0 issues** under the full fleet golangci-lint roster, including `gosec`. gosec's G203 ("[u]se of unescaped data in HTML templates") targets a different shape — bypassing `html/template`'s own escaping via a `template.HTML(...)` cast — not "used `text/template` at all for HTML." gosec's RULES.md also lists **G708** ("[s]erver-side template injection via `text/template`," Taint) as a distinct rule, but it did not fire on this fixture either under golangci-lint 2.14.0's bundled gosec, so the whole family of `text/template`-into-HTTP risk is currently unenforced by tooling in this toolchain and needs a reading heuristic.

**`caddyserver/caddy@54937914234b` is the load-bearing counter-example, and it sharpens the rule rather than breaking it.** Caddy's `caddyhttp/templates` module deliberately executes response bodies as `text/template` and documents exactly why escaping is not the whole story: "⚠️ Template functions/actions can access the environment, files on disk, and make HTTP requests... you need to make sure templates are only evaluated on content that you trust, control, or at least sanitize properly" (`caddyserver/caddy@54937914234b:modules/caddyhttp/templates/templates.go:36-42`). This is server-side template injection (SSTI) — the risk is attacker-influenceable *template source*, which `html/template`'s output-escaping does not address at all (it escapes *data* inserted into a *trusted* template; it does nothing if the template itself is untrusted). Caddy's `fileserver/browse.go` directory-listing handler is the case that *is* about data escaping, and it gets it right the hard way: it uses `text/template` (not `html/template`) but manually escapes every occurrence of the filesystem-derived `.Name` with the builtin `html` function for text nodes and a `pathEscape` function for URL attributes (`caddyserver/caddy@54937914234b:modules/caddyhttp/fileserver/browse.html:308,929,1068` use `{{html .Name}}`; `:31` uses `{{.Name | pathEscape}}`), and additionally sets a strict per-request `Content-Security-Policy` with a nonce (`browse.html:1-7`) as a compensating control if any escaping slot is ever missed. `staticresp.go` (`caddyserver/caddy@54937914234b:modules/caddyhttp/staticresp.go:69-70`) also uses `text/template`, but only over operator-supplied config values (`{{.N}}`, `{{.Port}}`, `{{.Address}}`) — never request-derived data — so it carries neither risk.

The fleet MUST is still: use `html/template` for any HTML sink. Caddy's manual-escaping discipline is real but expensive to sustain and easy to get subtly wrong at one call site out of many; it is not something to expect an agent to reproduce correctly across a codebase. A deviation needs the same kind of explicit reasoning Caddy's own comment gives (what specifically is trusted, and why), not a bare `//nolint`.

### 5. `unsafe`, `//go:linkname` and cgo: forbidden without an ADR

The map's default (M-I-08) is adopted as-is: **forbidden without an ADR.** The grep it names is the correct mechanism precisely because tooling does not catch this reliably:

```
grep -rn --include='*.go' -e '"unsafe"' -e '//go:linkname' -e 'import "C"' DIR
```

**gosec's G103 ("[a]udit the use of unsafe block") did not fire in this toolchain.** Its own source (`securego/gosec@master:rules/unsafe.go`) registers a `callListRule` against `unsafe.Pointer`, `unsafe.String`, `unsafe.StringData`, `unsafe.Slice` and `unsafe.SliceData` as `*ast.CallExpr` matches — by the rule's own logic it should fire on any of these calls at any severity/confidence threshold (`issue.Low`/`issue.High`, and golangci-lint's default severity/confidence filter is `low`/`low`, which passes everything). Empirically, under golangci-lint 2.14.0's bundled gosec, neither a raw `unsafe.Pointer` conversion nor an `unsafe.String(unsafe.SliceData(b), len(b))` call produced a finding (`g103probe/`, `unsafe-string/bad/`, both 0 issues). This dive could not determine why from outside the vendored build; it is reported as an observed fact, not a root cause, and it is the reason the policy is a grep, not a lint MUST — which matches what the map already specified.

**`//go:linkname` (Go 1.23 tightened this, [go.dev/doc/go1.23](https://go.dev/doc/go1.23)):** "the linker now disallows using a `//go:linkname` directive to refer to internal symbols in the standard library (including the runtime) that are not marked with `//go:linkname` on their definitions," and the same restriction applies to assembly references; existing pre-1.23 usages in the wild "remain supported," but *new* references to unmarked internal symbols are rejected. `-ldflags=-checklinkname=0` disables the check. ### 6. Input bounds beyond HTTP bodies

**`json.NewDecoder(r.Body).Decode(...)` with no prior bound.** No golangci-lint linter and no gosec rule fires on this shape (0 issues on the planted fixture under the full roster). `http.MaxBytesReader(w, r.Body, n)`, applied to `r.Body` *before* the decoder is constructed, is the MUST fix; it is a stdlib primitive (`net/http`), not a third-party dependency. Verified with a grep heuristic (below), red on the violation, green on the fix.

**`ParseMultipartForm` and G120.** gosec's G120 ("[u]nbounded `ParseMultipartForm` in HTTP handlers can cause memory exhaustion," Taint, `securego/gosec@master:analyzers/form_parsing_limits.go`) fires on **every** call to `(*http.Request).ParseMultipartForm`, and — this is the load-bearing detail — the rule's own doc comment explains why a smaller `maxMemory` argument does not silence it: "the caller-supplied `maxMemory` only limits the in-memory portion while the total can be `maxMemory` + 10 MiB. Without `http.MaxBytesReader` the full body is consumed." Verified empirically: `ParseMultipartForm(0)` fires; `ParseMultipartForm(10<<20)` **also fires** (still red — a smaller argument alone is not the fix); wrapping `r.Body = http.MaxBytesReader(w, r.Body, 10<<20)` *before* the call is what silences it. One mechanism (`http.MaxBytesReader` on the body) is therefore the MUST for both the JSON-decoder and the multipart-form case — simpler than two separate rules.

**RE2 and ReDoS.** `regexp`'s own doc: "[t]he syntax of the regular expressions accepted is... the syntax accepted by RE2... except for `\C`" and "[t]he regexp implementation provided by this package is guaranteed to run in time linear in the size of the input. (This is a property not guaranteed by most open source implementations of regular expressions.)" ([pkg.go.dev/regexp](https://pkg.go.dev/regexp)). Because the guarantee is a property of the engine (no backtracking, ever), a ReDoS finding against stdlib `regexp.Compile`/`MustCompile` is a category error — the pattern that would be catastrophic-backtracking in PCRE simply cannot express that failure mode in RE2 syntax (no backreferences, no lookaround). This closes the ReDoS half of M-I-09 with a citation, and no fixture is needed: there is no code shape to plant that demonstrates a linear-time guarantee failing. The residual risk is a package that shells out to a different (non-RE2) regex engine, or hand-rolled backtracking matching — out of this row's scope.

## AI-agent angle

- **Reaching for `math/rand` (or, post-training-cutoff, `math/rand/v2`) for "a random token" is the single most likely mistake here** — both APIs read as the obvious, idiomatic choice, and an agent has no reason to know the security distinction unless told. *Smallest check:* `gosec` G404 (already a MUST under GO-GATE-14's config) catches the direct case; the grep in candidate #1 catches it even without gosec configured.
- **An agent asked to "stop hardcoding the secret" is far more likely to build it from parts (`prefix + "-" + suffix`) or read it through an intermediate variable than to move the literal to package scope** — exactly the two shapes this dive proved defeat gosec's G101 at any scope. *Smallest check:* candidate #5's grep, which has no entropy or static-resolvability requirement.
- **An agent building an HTTP handler that renders dynamic content commonly reaches for `text/template` because it "already imported template package X" in the same file, or copies a CLI/config-generation helper that legitimately uses `text/template` into an HTTP context** — the import alone looks identical whether or not the output later reaches a response writer. *Smallest check:* candidate #6's two-step grep (text/template import ∩ `http.ResponseWriter` reference).
- **An agent "fixing" an unbounded JSON/multipart handler by adding a numeric argument in the wrong place** — passing a smaller `maxMemory` to `ParseMultipartForm` looks like the fix and compiles, but gosec's own G120 (and the underlying reality) says it is not one; the actual fix is a `MaxBytesReader` around `r.Body`, a call most agents will not think to add because nothing about the `ParseMultipartForm` signature hints at it. *Smallest check:* candidate #10 — the `good` twin's shape is short enough to put directly in a code-review comment template.
- **An agent copying an `unsafe.String`/`unsafe.Slice` pattern from one place to another without re-checking whether the source buffer is still mutated afterward** — the call itself is identical in the safe and unsafe case; only the surrounding code differs, and nothing type-checks the difference. *Smallest check:* candidate #9's runnable `go test` shape is the cheapest way to catch this in review — ask "does a test exist that mutates the source buffer after the unsafe call and asserts the string didn't change?"
- **An agent treating `html/template`'s autoescaping as sufficient defense against *any* templating risk**, including a case where the template source itself (not just the interpolated data) is influenceable — Caddy's own doc comment is the citation for why this is a different risk `html/template` does not address. *Smallest check:* candidate #7's reading heuristic — trace where the template *text* comes from, not just what data is interpolated into it.
- **An agent generating a constant-time comparison only when explicitly asked for one, and using `==`/`bytes.Equal` by default for any string/byte-slice equality check including secrets**, because that is the overwhelmingly common correct choice for non-secret comparisons and no compiler or linter distinguishes the two cases. *Smallest check:* candidate #4's grep, run specifically over functions whose name/parameters suggest a credential.

## Contested / evolving

- **Whether `text/template`-into-HTTP is *always* wrong is genuinely contested**, and the answer is trending toward "no, but the bar for doing it safely is high and rarely worth it." Caddy (a widely-deployed, security-conscious production server) does it deliberately in two different places with two different, both-correct answers: forbid it entirely by trust-boundary documentation (`templates` module) or manually escape every occurrence with the matching builtin function (`fileserver/browse.go`). As of 2026-09-26 this dive found no second major exemplar taking the same position, so "Caddy does it correctly" is n=1 evidence for the exception path, not a trend — the fleet default stays `html/template`.
- **gosec's G101 entropy threshold is a moving target.** zxcvbn's scoring (via `ccojocar/zxcvbn-go`) is a heuristic password-strength estimator, not a security-proof; a memorable, human-chosen "strong" password can score below its 80-bit default threshold while a random 24-character string scores above it, which is backwards from a pure information-theoretic view (the random string usually *is* higher-entropy, but the threshold's practical effect is that dictionary-derived secrets — the more common real-world credential shape — are the ones most likely to slip past G101 silently). No public discussion of raising or removing the threshold was found as of this dive's date; flagged for the next `go-upgrade`/gosec-bump pass per GO-GATE-14's own "re-review the excludes and thresholds on every bump" instruction.
- **`crypto/subtle.WithDataIndependentTiming` (Go 1.24) vs `ConstantTimeCompare`** — the newer primitive is architecturally stronger (covers a whole function including spawned goroutines and cgo calls, using ARM64 `PSTATE.DIT` where available) but has zero measured adoption in this 35-repo corpus as of 2026-09-26. Too new for a MUST; worth a SHOULD note in a future revision once real-world usage patterns exist to cite.
- **The vendored-gosec-vs-upstream-source gap (G103, G120's exact silencing condition) is itself evolving** and worth re-checking on every golangci-lint bump, not just the excludes list GO-GATE-14 already tracks — this dive's empirical results (G103 silent, G120's MaxBytesReader-clears-it behavior) may not hold across gosec versions, since they were not fully explained by the upstream source read.
