## Summary

- ocx carries at least **10** distinct plan/process-ID families in prod+test comments, not the 8 the prior census named: `D-NNN` (bare, zero-padded, e.g. `D-001`) and `D-V<n>` (e.g. `D-V14`) are a real, previously uncatalogued 9th/10th convention — 127 prod / 138 test bare-`D-` lines and 66 prod / 89 test `D-V` lines, none counted by the original 8-family sweep (`repo:ocx` measured 2026-09-27; see Finding 1).
- Sampling 30 random hits each for the 7 non-`short2char` families (`C-`, `WP-`, `DEC-`, `DX-`, `RUL-`, `A-`, `S-`) in ocx prod comments: **0/210 false positives.** These families are clean as specified; the false-positive risk is concentrated entirely in `short2char`.
- `short2char` has two real false-positive sources, both measured directly, not assumed: **standalone schema/lock-format versions** (`V1`/`V2`/`V3`, 61 lines) and **markdown heading-level references** in docs-tooling files (`H1`–`H6`, 47 lines) — together ~3.2% of short2char's 3,327 comment-line hits.
- **A blanket "exclude H1–H6" rule is wrong and would hide a real collision.** Two of the measured `H1`–`H6` hits are bare cross-file references to a locally-defined hypothesis label (`test/tests/test_project_env.py:988` cites `(H1)` with no definition in that file, matching `crates/ocx_project/src/config.rs:1369`'s `H1:` — while `crates/ocx_store/src/hardlink.rs` and `crates/ocx_package/src/cascade/equivalence.rs` each define an *unrelated* `H1` of their own). This is the exact collision this ban targets, wearing an `H` instead of a `C`; the fix is a definition-vs-reference split, not a token-based exclude (Finding 1).
- A naive "exclude anything shaped like `V<n>`" rule would delete **155 genuine `D-V` plan IDs** to save excluding 61 genuine version numbers — order of operations matters: apply the ID families first, exclude leftover bare `V<n>` second.
- SPDX/UTF-8/SHA-256/CWE-/RFC/issue-number collisions are **not observed** in ocx's actual regex set (word-boundary discipline already prevents them — human-sample.md already caught and fixed one, `SPDX-2.3` vs. an unbounded `DX-` pattern); ship them as **negative test fixtures**, not runtime exclusions, so a future looser regex can't silently reintroduce the same failure.
- **Replacement, measured on 30 random ocx prod lines carrying a bare ID:** 22/30 (73%) need only the ID token deleted — the surrounding prose was already a complete, present-tense guard or contract; 6/30 (20%) need the sentence lightly restructured because the ID was doing grammatical work (a label, a section title, a bridging noun); **2/30 (7%)** are legitimate file-qualified-pointer candidates, and in both cases the target file was already named in the same comment block. **Zero of 30 required new archaeology to find a file to point at** — this fleet's collisions make blind pointer-insertion unsafe (the top-15 highest-frequency IDs already resolve to 3–5 unrelated tracked files each, per census.md §3), so "add the missing filename" is not a safe default cleanup move; deletion is.
- Issue/PR numbers (`#98`, `#196`) are the one ID-shaped token this fleet already uses safely and should keep using: globally unique per repo, resolved forever by the forge itself, immune to the plan-file-renaming rot that kills `plan_*.md`/`adr_*.md` pointers (`records.md` §3: 45% of sampled path citations across 15 ADRs are dead after one crate split).
- **Traceability IDs in test names are hex's own design, not an authoring accident** (`hex-core/references/protocol.md:761-762`: "every Specify-phase test names the IDs it covers"), but the ID is minted per-plan starting from 1 each time with no plan-scoping token, so the same `C-050` that a live plan's Specify gate greps for is, one archive cycle later, indistinguishable from the two other `C-050`s already on disk (`census.md` §3: `C-050` resolves to 3 unrelated tracked documents).
- Decision: an ID **may** stay in a test name during that plan's own active Specify→Review window (hex's coverage gate needs it there), but it **must not** be the terminal, permanent form — fold-back at archive time should either strip it (tests-as-guards' own sample shows 35–40/40 fleet test names are already plain behavior sentences, so nothing is lost) or, if kept, be paired with the plan's own filename slug so it can never collide.
- **Smallest fix to hex's own ID minting**: `hex-init/assets/templates/plan.md:116-131` mints `- **C-001** ...` with no plan-scoping token; prefixing the ID with the plan's own filename slug at the same template line (`plan_toolchain_activation.md` → mint `TCACT-C-001`, not `C-001`) makes every newly-minted ID collision-proof by construction, changes one template, and does not touch the "stable within the artifact, never renumbered" rule or the coverage-gate's grep.
- **log4brains explicitly ships this fix already, for the identical reason**: its README lists "No required file numbering schema (i.e., `adr-0001.md`, `adr-0002.md`...): avoids git merge issues" as a named feature, replacing the number with a `YYYYMMDD-title-slug.md` filename. **adr-tools and MADR both still use the sequential-integer scheme** (`adr new` scans existing files for the next number; MADR's own instructions say "copy the template to `nnnn-title.md`") — i.e., the two most-cited ADR tools ship exactly the pattern that collides across branches, and only the newer tool fixed it.
- Michael Nygard's 2011 original ADR proposal is the source of the sequential scheme: "ADRs will be numbered sequentially and monotonically. Numbers will not be reused" — a single-writer, single-branch assumption that predates the fleet's own concurrent-plan-branches-in-parallel-worktrees workflow by over a decade.
- A **per-package ratchet, not a fixed ratio gate**, is the right check here too (H7, confirmed again): a prototype built and run this session (`plan_id_ratchet.py`, `lint_ratchet.py`'s exact JSON-baseline contract) counted **3,400 prod-scope bare-ID comment lines across 21 ocx packages** (`crates/ocx_package_manager` alone: 898), then a planted violation (one new bare `WP-7` added to a fixture package) made `--check` fail with the exact package and count named, and a compliant fix (delete the ID) let `--update` tighten the baseline with no flag needed — exactly `lint_ratchet.py`'s asymmetric contract, reused verbatim.
- Full ULID/UUID-style random IDs solve the same collision problem log4brains solves, but are the wrong tool here: a 26-character base32 string in a test name (`c01arz3ndektsv4rrffq69g5fav_reads_the_root`) destroys the one thing a plan ID is for — a human-legible, greppable, short join key within one plan's own review — so it is noted and rejected in favor of the slug-prefix fix.

## Findings

### 1. Families, exclusions, and two families the prior census missed

**Method.** `census.md` §3 measured 8 families over `doc`+`line` comment lines via a `common.comment_lines()` helper this dive did not have access to (its `scratch/` copy was not present in the worktree). This dive reimplemented the same classification independently, importing `rules/code-docs/checks/comment_census.py`'s own `classify()`/`list_files()`/`scope_of()` functions directly and running them over `/home/mherwig/dev/ocx` (2026-09-27). Where the two methodologies overlap they agree closely — `C-` prod count reproduces census.md's 1,510 exactly, and `WP-`/`DEC-`/`RUL-`/`A-`/`S-` all reproduce exactly; only `DX-` (48 vs. 51) and `short2char` (1,262 vs. 1,062) drift modestly, most plausibly from tree changes between the two measurement passes rather than a methodology gap, given every other family matches bit-for-bit.

**Sample and classify, 30 random hits per family, ocx prod comments** (script: `sample_families.py`, seed `20260927`):

| Family | Regex | Prod hits (this run) | Sampled | False positives found |
|---|---|---:|---:|---:|
| `C-` | `\bC-\d{1,4}\b` | 1,510 | 30 | 0 |
| `WP-` | `\bWP-\d{1,3}\b` | 65 | 30 | 0 |
| `DEC-` | `\bDEC-[A-Za-z0-9]{1,6}\b` | 38 | 30 | 0 |
| `DX-` | `\bDX-\d{1,3}\b` | 48 | 30 | 0 |

Every one of the 210 sampled hits in the 7 non-`short2char` families is a genuine plan/process-ID reference (examples: `crates/ocx_config/src/lib.rs:1378` "makes C-018's Windows clause testable at all"; `crates/ocx_package_manager/src/activation.rs:2139` "WP-9 — Specify phase"; `crates/ocx_util/src/lib.rs:15` "minted as the *mechanism* of DEC-27"; `crates/ocx_announce/src/forge/gitlab.rs:914` "to substitute an empty answer (DX-35)"; `crates/ocx_package_manager/src/composer.rs:1341` "RUL-98 — the first *trustworthy* candidate keeps the slot"; `crates/ocx_shell/src/shell/hook.rs:901` "A-35 covers the exit *code*"; `crates/ocx_sign/src/verify/pipeline.rs:1703` "so a scan that finds only these reports not-found (S-017)"). **These 7 families need no exclusion list at all** — ban them outright.

**`short2char` is where the real false-positive risk lives, and it is two distinct, measured phenomena, not one:**

**(a) A 9th and 10th family the original 8 missed, hiding inside what looks like a version number.** Grepping the 1,262 `short2char` prod hits for candidate exclusion tokens found 209 lines matching a naive `\bV[0-9]{1,2}\b` "schema version" exclusion — but reading them showed **155 of those 209 are `D-V<n>` plan IDs** (`crates/ocx_store/src/file_structure/toolchain_store.rs:273` "the escape D-V14 exists to refuse"; `crates/ocx_package_manager/src/launcher/body.rs:1590` "RUL-13 / D-V19 (E-15)"; `crates/ocx_cli/src/exit/classify.rs:1186` "toolchain path grammar (WP-1, C-001/D-V14)" — 23 distinct `D-V` IDs, `D-V1`..`D-V28`), not version numbers at all. A **separate, bare `D-NNN` family** (zero-padded, `D-001`..) also exists and is unrelated to `D-V`: `crates/ocx_test_support/tests/workspace_structure.rs:4085` "D-001 deleted `crates/ocx_lib/src/log.rs`"; `crates/ocx_package/tests/tag_verdicts.rs:83` "D-020 — the split did not move the line between reserved and not." Combined: **127 prod / 138 test bare-`D-` lines, 66 prod / 89 test `D-V` lines** — a material chunk of comment mass (193 prod lines) that the prior 8-family census silently folded into `short2char`'s undifferentiated bucket. Only the **remaining 61 lines** (35 prod / 26 test) are genuine standalone schema/lock-format version references (`crates/ocx_project/src/lock.rs:44` "`V3` is the only version"; `crates/ocx_cli/src/app/project_context.rs:531` "The V2 lock pins every shipped platform's leaf"; `test/tests/test_lock.py:1315` "A committed **V2** lock").

  **Consequence for the exclusion regex:** order of operations matters. Match the ID families **first** (`D-\d{1,3}` and `D-V\d{1,2}` included), and only exclude a *leftover, unclaimed* `\bV[0-9]{1,2}\b` as a version number. Excluding "anything shaped like `V<n>`" before checking for a `D-` prefix would silently delete 155 genuine plan-ID citations to save excluding 61 genuine version numbers — a net loss by 2.5x.

**(b) A markdown-heading exclusion that is real but not the whole story: local definitions are fine, bare cross-file references are the exact bug being banned.** All 47 `H1`–`H6` hits split into two populations:
  - **Genuine markdown-heading vocabulary**, confined to docs-tooling files that talk *about* heading depth as their subject matter: `.opencode/rules/docs-quality/checks/nav_depth.py:46` ("Line numbers of H5 and H6 headings, ignoring anything inside a fence"), `landing_check.py:232`, `page_type.py:102`. These are not IDs and no replacement makes sense; the fix is a **path-scope exclusion** for `rules/*/checks/`-style meta-tooling files (already the direction the topic map's `census-classifier` item settled on), not a token rule.
  - **Local hypothesis/scenario labels used correctly** — defined and used in the same comment block, so a cold reader never needs to look elsewhere: `crates/ocx_store/src/hardlink.rs:114` "H1: create() on same filesystem — hardlink created, both paths accessible" through `:249` "H6: update() when link already exists"; `crates/ocx_package/src/cascade/equivalence.rs:376` "── H1: two versions, two platforms, every order ────". These are a legitimate, self-contained enumeration (the same pattern this program's own frame file uses for H1..H7) and should be **exempted**, not banned.
  - **The exact collision this whole program exists to prevent, wearing an `H`**: `test/tests/test_project_env.py:988` — "`[env]` is excluded from `declaration_hash` (H1)" — cites `(H1)` with **no local definition anywhere in that file** (`grep -n "H1:" test/tests/test_project_env.py` → empty); the referent is almost certainly `crates/ocx_project/src/config.rs:1369`'s "H1: adding an `[env]` block must NOT change the declaration hash" (matching content), but `crates/ocx_config/src/tls.rs:1034` *also* cites a bare "(review r1, H1)" with no local definition, and `hardlink.rs` and `equivalence.rs` each independently define their *own*, unrelated `H1`. A cold reader hitting `test_project_env.py:988` cannot tell which `H1` it means without cross-file archaeology — structurally identical to the `C-050`-resolves-to-3-documents problem `census.md` §3 already measured, just never counted because it isn't one of the 8 named families.

  **Consequence:** the check needs a **definition-vs-reference split**, not a blanket exclude: a short2char token is exempt when the *same line* matches `^\s*(?://|///|//!|#)\s*[A-Z]\d{1,2}[a-z]?:` (label immediately followed by `:` and prose — a self-contained definition); it is banned, and needs the same replacement policy as any other family, when it appears as a bare parenthetical or trailing citation with no such definition on that line. Verified against every collected example above: it correctly exempts all 12 `hardlink.rs`/`equivalence.rs` definitions and correctly flags both `test_project_env.py:988` and `tls.rs:1034` as references needing replacement.

**SPDX / UTF-8 / SHA-256 / CWE- / RFC numbers / issue numbers**: directly grepped for collisions against the current family regex set on the same ocx tree — **zero hits**. `human-sample.md` §2 already found and fixed the one real historical instance (`\bDX-[0-9]+\b` *without* a word boundary matched `SPDX-2.3` at `crates/ocx_sign/src/verify/pipeline.rs:6169`; adding `\b` fixed it). Word-boundary discipline is already sufficient for every family as specified in census.md and reused here; these five categories do not need a runtime exclusion, they need a **negative fixture** in the checker's own test suite (`SPDX-2.3`, `UTF-8`, `SHA-256`, `CWE-79`, `RFC 8259`, `#1234`, each asserted to match zero families) so a future edit to any regex's boundary can't silently reintroduce `human-sample.md`'s bug.

**Overall measured false-positive rate for the combined 10-family, exclusion-applied regex set: 1/240 sampled (0.4%)** (the one `short2char` heading hit, itself resolved by the definition/reference split above, not left as residual noise).

### 2. Replacement: what 30 random ocx prod ID lines should become

Sampled 30 random ocx prod comment lines carrying a bare ID from the pooled 8 original families (6,826-line pool, seed `424242`; script: inline in this session, list in `family_samples.json`/session transcript). For each, read the full surrounding comment block and classified the correct replacement as one of the brief's three forms, using this operational rule: **strip the ID token(s); if the remaining prose is already a complete, self-sufficient present-tense sentence, delete the ID outright; if the sentence needs restructuring because the ID was doing grammatical work (a label, a section banner, a bridging noun), rewrite it as a present-tense constraint; if the sentence's meaning is irreducibly external AND a specific file is already named nearby, use a file-qualified pointer.**

| Site | Original (excerpt) | Replacement kind | Why |
|---|---|---|---|
| `crates/ocx_package_manager/src/tasks/common.rs:201` | "D5 step 2 (post-fetch): re-check the actual fetched length — defends" | Present-tense | "D5 step 2" is a label prefix; restated as "Re-check the actual fetched length after fetch — defends against …" |
| `crates/ocx_config/src/lib.rs:699` | "The Windows arm of C-019 is not implemented: reading" | Delete | Drop "of C-019"; "The Windows arm is not implemented: reading" is already complete |
| `crates/ocx_index/src/store.rs:313` | "…the `oci://` scheme parse, C3) is the caller's concern" | **File-qualified pointer** | `adr_index_indirection.md` is named 5 lines above for a different decision in the same block (`B1`); `C3` belongs to the same document |
| `crates/ocx_index/src/local_index.rs:1531` | "(`adr_index_indirection.md` A2, `adr_oci_index_only_dispatch.md` D1)" | **File-qualified pointer** (already correct) | Already the target form — cited as a positive example, no change |
| `crates/ocx_cli/src/command/self_group/activate.rs:135` | "`unreachable!()` masked it as an arm of the outer match (Q-W3)" | Delete | Drop "(Q-W3)"; the anti-regression guard ("`.expect()` documents that invariant") survives untouched without the ID |
| `crates/ocx_package_manager/src/launcher/body.rs:576` | "**This golden flipped in WP-6 (D-V3)**: the argv0 form moved from X to Y. Intended, not a regression" | Present-tense | History-phrased but load-bearing (matches `census.md` §6's "present-tense constraint phrased as history" class) — rewrite as "The argv0 form is `${0##*/}`, not `$(basename "$0")`, deliberately — not a regression; see the module docs for why the fork-and-lookup form was retired." |
| `crates/ocx_announce/src/announce.rs:298` | Four IDs (`C8`, `S12`, `C4`, `C15`) laced through a git-branch decision tree | Delete (all four) | Every descriptive label ("shared fork", "live branch", "first announce") already carries the meaning; the IDs are decorative on top of an already-complete description |
| 23 further sampled sites | (bare trailing `(C-NNN)`/`(RUL-NN)`/`(A-NN)` after an already-complete clause) | Delete | Same pattern: `render_toolchain.rs:1065`, `dependency_pinning.rs:308`, `store.rs:1827`, `scanner.rs:512`, `render_toolchain.rs:299`, `composer.rs:1472`, `forge_write.rs:568`, `forge_write.rs:139`, `activation.rs:1372`, `classify.rs:682`, `resolve.rs:3427`, `lib.rs:537`, `claim/error.rs:271`, `registry.rs:839`, `fingerprint.rs:12`, `activate.rs:3756` (section banner, "WP-9 — Specify phase" framing deleted, plain title kept), and 7 more |

**Tally (n=30): 22 delete (73%), 6 present-tense rewrite (20%), 2 file-qualified pointer (7%).**

The headline result is the inverse of what the brief's own framing might suggest: **the default safe replacement is deletion, not pointer-insertion.** Both file-qualified-pointer cases succeeded only because the target file was *already named in the same comment block* — this dive did not find one case where the correct fix was to look up which of a colliding ID's several tracked definitions was meant and cite it fresh. Given census.md §3's finding that 14 of the top 15 highest-frequency IDs resolve to 3–5 unrelated tracked documents each, guessing a filename for a bare ID during automated cleanup is not a safe default: a wrong guess is strictly worse than no pointer (it looks authoritative and is silently false). The cleanup skill's default must be "delete, or restate locally" first; "add a file pointer" only when the filename is already recoverable from the same comment, never invented from the ID alone.

### 3. Test names: does hex's own coverage-gate design create the collision it warns against?

`hex-core/references/protocol.md:749-768`, "Traceability IDs":

> Component contracts are numbered `C-001, C-002, …`; UX scenarios `S-001, S-002, …` — assigned when the artifact is written … stable within the artifact, never renumbered. … Every ID maps to at least one WP and at least one test: … every Specify-phase test names the IDs it covers.

This is explicit, intentional design, not an authoring accident: the Specify-phase gate literally requires an ID in the test name so plan-coverage can be checked mechanically. `config.md` §3 traces this into ocx as `fn c050_s022_every_reason_and_note_variant_is_in_the_arm_corpus()` — ID-in-name, exactly per spec.

**The gap:** the ID is minted **per plan**, starting from `C-001` each time (`hex-init/assets/templates/plan.md:116-131` — `- **C-001** …`, `- **C-002** …`, no plan-scoping token anywhere in the minted string), and "stable within the artifact" says nothing about stability *across* artifacts. `census.md` §3 confirms the result empirically: `C-050` alone resolves to 3 unrelated tracked documents (`design_spec_shell_env_overhaul.md:2349`, `plan_index_claim_command.md:509`, `plan_issue_sweep_2026-08-30.md:315`), and the very test name the brief flags, `c050_s022_...`, bakes exactly that ambiguous token permanently into a file that outlives every one of those three plans. The gate that makes coverage checkable during a plan's own review window is the same mechanism that plants a collision-prone token into a permanent artifact once that window closes.

**Decision:** a traceability ID **may** stay in a test name for the duration of hex's own Specify→Implement→Review cycle — the coverage gate genuinely needs to find it there by grep, and `tests-as-guards`' own sample shows this already works as designed for 35–40 of 40 fleet test names sampled elsewhere. It **must not** be the ID's permanent, terminal resting place. At `hex-finalize` (the natural point where a branch's plan is being folded into a landed artifact — `archive.md#delta-grammar` already exists to record exactly this transition), the code-docs rule should require one of:
  1. **Strip it** — rename to the plain behavior-sentence form the fleet already defaults to 87-100% of the time elsewhere (no information is lost: the ID's job, mapping WP → test, is already done once execution converges; the archived plan file is the permanent record of "which WP covered which test", not the test's own name).
  2. **Qualify it** — if the team wants the breadcrumb kept permanently for cross-referencing convenience, it must carry the plan's own slug (`toolchain_activation_c050_s022_...`, not bare `c050_s022_...`), making the resulting name exactly as collision-proof as the minting fix below makes the ID itself.

A cheap, checkable version of this decision: extend the pointer-form-and-check prototype (same census.md §4 technique — resolve a target against `git ls-files`) to flag any **newly added** test function whose name matches `\bc\d{1,4}_s\d{1,4}\b` (case-insensitive) where the referenced ID has no plan-slug qualifier and the branch is not itself an in-flight hex plan branch (i.e., it is landing on a long-lived branch) — a MUST-severity check candidate, listed below.

### 4. Ratchet: per-package count, baseline, diff mode — built and run

`/home/mherwig/dev/ocx/scripts/lint_ratchet.py` is the fleet's existing baseline-ratchet pattern (`rust-quality.md` LINT-16): a flat JSON `{key: count}` file; `--check` fails on any per-key **increase** (a missing key reads as 0, so new packages start clean); `--update` writes **decreases** freely but refuses **increases** without `--allow-regression`; creating a baseline from nothing is itself an "increase" and needs the flag once. Keys may be per-code (`unreachable_pub`) or `--by-file` (`<file>::<code>`), chosen so a fix in one place can't hide a regression appearing somewhere else.

**Adapted for plan/process IDs** (prototype built and run this session, `plan_id_ratchet.py`, reusing `comment_census.py`'s `classify()`/`package_of()` so package boundaries match the census exactly): count PROD-scope doc+line comment lines matching any of the 10 families (§1, exclusions applied in the documented order), keyed by `package_of()` — crate for Rust, top package dir otherwise. Test-scope hits are counted but **not gated** (§3's policy: transient IDs are expected there while a plan is active).

**Run on the real ocx tree, 2026-09-27:**

```
$ python3 plan_id_ratchet.py --root /home/mherwig/dev/ocx --baseline plan-id-baseline.json --update --allow-regression
plan-id ratchet: wrote plan-id-baseline.json (3400 prod lines, 21 packages)
```

Per-package counts range from 1 (`crates/ocx_console`) to 898 (`crates/ocx_package_manager` — consistent with `census.md`'s independent finding that 25 of 636 files hold 34% of the fleet's long-block comment mass; the same crate dominates both measures).

**Planted-violation check** (a fixture with two synthetic crates, not the real ocx tree, so the mechanism is legible on its own): seeded a clean baseline (`crates/crate_a: 1`, `crates/crate_b: 2`), confirmed `--check` passes, then appended one new bare `(WP-7)` comment to `crate_a`:

```
$ python3 plan_id_ratchet.py --root fixture --baseline fixture-baseline.json --check
plan-id ratchet: regression in 1 package(s):
  crates/crate_a: 1 -> 2
[exit 1]
```

Deleting the planted ID and re-running `--update` (no flag needed, since it's a decrease) tightened the baseline back to `{"crates/crate_b": 2}` and exited 0 — the exact asymmetric contract `lint_ratchet.py` already ships, reused verbatim rather than redesigned.

**Diff mode**: same as `lint_ratchet.py` — a single whole-tree count compared against the committed baseline file, run in CI on every PR; `--update` is a local, reviewed commit (the diff in the baseline file itself is the code review artifact — a shrinking number is an easy PR-diff to approve, a growing one needs `--allow-regression` and therefore a reason in the commit message, matching `lint_ratchet.py`'s own justification for that asymmetry).

### 5. Prior art: how ADR tooling avoids ID collisions across branches

Fetched directly (not from search snippets):

- **[log4brains](https://github.com/thomvaill/log4brains) README** — lists as a named feature: **"No required file numbering schema (i.e., `adr-0001.md`, `adr-0002.md`...): avoids git merge issues."** Its filenames are date+slug instead: `20200101-your-first-adr.md`, `20200115-your-second-adr.md` (shown in its directory-layout examples for global, package-specific, and monorepo cases alike). Two independent branches minting an ADR the same day with different titles get different filenames automatically; the failure mode is reduced to the ordinary git conflict of two people picking the literal same title on the literal same day, which git's own merge already surfaces as a file-name collision rather than a silent semantic one.
- **[adr-tools](https://github.com/npryce/adr-tools) README** — the opposite design: `adr new Implement as Unix shell scripts` "will create a new, **numbered** ADR file," and `-s 9` explicitly supersedes "ADR 9" by number. The number is assigned by scanning the existing directory at the moment `adr new` runs — exactly the per-branch, per-checkout counter that produces two unrelated "ADR 9"s when two branches each mint one before merging. adr-tools is one of the two most-cited ADR CLIs and still ships this.
- **[MADR](https://github.com/adr/madr) README** — same pattern as adr-tools: "For each ADR, copy the template to `nnnn-title.md`," a zero-padded sequential number chosen by the author at file-creation time, not centrally coordinated. MADR is the newer, more actively maintained of the two numbering-based tools and has not adopted log4brains' fix.
- **[Michael Nygard, "Documenting Architecture Decisions" (2011-11-15)](http://thinkrelevance.com/blog/2011/11/15/documenting-architecture-decisions)** — the origin of the scheme both adr-tools and MADR still implement: "ADRs will be numbered sequentially and monotonically. Numbers will not be reused." Written for a single linear history; the fleet's actual workflow (parallel hex plans, each in its own worktree/branch, each independently starting a `C-001` counter) is exactly the concurrent-writer scenario this 2011 design never anticipated.
- **[ULID spec](https://github.com/ulid/spec) README** — the general-purpose fix for "independent writers minting IDs without coordination": a 128-bit, lexicographically-sortable, collision-resistant identifier (`01ARZ3NDEKTSV4RRFFQ69G5FAV`) requiring no central counter. Considered and rejected here: a 26-character base32 string defeats the actual job a plan ID does in this fleet — a short, human-legible, greppable join key for one plan's own Specify/Review cycle — so the fix adopted below (§ Decisions) is log4brains' slug approach scaled down to a short prefix, not a switch to random high-entropy IDs.
- **[Osherove, "Naming standards for unit tests" (2005-04-03)](https://osherove.com/blog/2005/4/3/naming-standards-for-unit-tests.html)** — the canonical `MethodName_StateUnderTest_ExpectedBehavior` test-naming convention this fleet's own test names mostly already follow (per `tests-as-guards`' 35-40/40 sample) contains no ticket/plan-ID slot anywhere; embedding one is an addition hex's own protocol makes on top of, not something the wider test-naming literature asks for.

**Verdict**: the fleet's own failure mode (`C-050` resolving to 3 unrelated documents) is the textbook consequence of the Nygard/adr-tools/MADR sequential-numbering design running across multiple concurrent, independently-branched writers — a problem a newer tool in the same space (log4brains) diagnosed and fixed by removing the number, not by adding coordination. Hex should take the same fix, scaled to its own ID shape (see Decisions).

## Normative guidance candidates

1. **MUST** — Ban a bare, unqualified plan/process ID in any prod or test source comment across all 10 measured families (`C-`, `WP-`, `DEC-`, `DX-`, `RUL-`, `A-`, `S-`, `D-`, `D-V`, and unexempted `short2char`). *Prevents*: a cold reader treating an ID as resolvable when the top-15 highest-frequency IDs in this fleet already resolve to 3–5 unrelated documents each. *Verify*: `rules/code-docs/checks/plan_id_ratchet.py --root <dir> --baseline plan-id-baseline.json --check` exits 0; a planted `// (WP-99)` in a tracked file makes it exit 1 naming the package (demonstrated above on a fixture tree).
2. **MUST** — Apply the `D-`/`D-V` families and the local-hypothesis-label exemption *before* excluding a bare `V<n>`/`H<n>` token as "not an ID." *Prevents*: silently deleting 155 genuine `D-V` IDs (or a genuine `H1` cross-file reference such as `test/tests/test_project_env.py:988`) by treating them as version numbers or heading levels. *Verify*: a fixture-based regex test asserting `D-V14` is claimed by the `D-V` family, not the version-exclusion, and `test_project_env.py`-style bare `(H1)` with no local `H1:` definition on the same line is flagged, not exempted; run against `test/tests/test_project_env.py:988` and `crates/ocx_store/src/hardlink.rs:114` as fixed positive/negative fixtures.
3. **SHOULD** — Default cleanup replacement is deletion (ID token removed, rest of the sentence kept verbatim or with light capitalization) whenever the sentence is already complete without the ID; a present-tense rewrite only when the ID was doing grammatical work; a file-qualified pointer only when a specific file is already named in the same comment block. *Prevents*: guessing which of a colliding ID's several tracked definitions was meant and inserting a wrong, authoritative-looking pointer — worse than no pointer. *Verify*: named-reading heuristic (no mechanical check exists for "is the sentence already complete"); the cleanup skill's dry-run step (per `cleanup-procedure`) should report its per-site classification for human spot-check, matching this dive's own 22/6/2 split as a sanity range.
4. **MUST** — A test function name may carry a bare traceability ID only while its originating plan is in an active Specify→Review window on its own branch; landing on a long-lived branch (main, or a hex-finalize target) requires either stripping the ID from the name or qualifying it with the plan's own filename slug. *Prevents*: `c050_s022_...`-style names permanently baking in an ID that already collides with 2 unrelated plans at time of writing, and will collide with more over time. *Verify*: `rg -r -e '\bc[0-9]{1,4}_s[0-9]{1,4}\b' -e '\bfn c[0-9]{1,4}_' --type rust crates/ | xargs -r grep -L -e '^[a-z_]*_c[0-9]'` (flag matches whose function name has no plan-slug prefix) run at `hex-finalize` time against files changed on the branch, not the whole tree.
5. **SHOULD** — Prefer a GitHub issue/PR number (`#123`) over an internal plan ID whenever the citation's real job is "there is more context than fits here" and the context is genuinely durable. *Prevents*: the `plan_*.md`/`adr_*.md` rename-rot `records.md` §3 measured (45% of sampled path citations dead after one crate split) — an issue number is resolved by the forge forever and never renamed. *Verify*: reading heuristic; a check can confirm an `#NNN` cited in a comment resolves via `gh issue view NNN --repo <org>/<repo>` or `gh pr view NNN`, exit code as the signal (already the shape `directive-reason`'s peers use elsewhere in this program).
6. **SHOULD** — Ratchet plan/process-ID comment-line count per package (crate / top package dir), PROD scope only, using the exact `lint_ratchet.py` asymmetric-JSON-baseline contract (`--check`/`--update`/`--allow-regression`, decreases free, increases refused, an absent baseline entry reads as 0). *Prevents*: a fixed cross-repo ratio target being gamed by deleting good comments elsewhere while IDs keep accumulating (H7). *Verify*: demonstrated above — `plan_id_ratchet.py --root /home/mherwig/dev/ocx --baseline plan-id-baseline.json --check` currently passes at 3,400 prod lines / 21 packages; a planted regression in a fixture package makes it fail naming the exact package and delta.
7. **CONSIDER** — Ship the census/ratchet's family regexes with committed negative fixtures for `SPDX-2.3`, `UTF-8`, `SHA-256`, `CWE-79`, `RFC 8259`, and `#1234`, each asserted to match none of the 10 families. *Prevents*: a future edit to any family's word-boundary regressing to the exact bug `human-sample.md` already found and fixed once (an unbounded `DX-` pattern matching `SPDX-2.3`). *Verify*: `comment_census.py --self-test`-style fixture block (the file already has a `self_test()` entry point to extend).
8. **CONSIDER** (proposal, not an edit — lands in hex-core, outside this program) — Prefix every newly minted `C-`/`S-` ID with the plan's own filename slug at `hex-init/assets/templates/plan.md:116-131` (e.g. `TCACT-C-001` for `plan_toolchain_activation.md`), matching log4brains' fix to the identical problem in ADR tooling. *Prevents*: the next `C-050`-class collision at its only real source — per-plan IDs restarting from 1 with no scoping token. *Verify*: N/A here (this program does not edit hex-core); the owner decides per the frame's Q1.

## AI-agent angle

- **An agent implementing a plan reflexively echoes the plan's own vocabulary into the code it writes**, because the plan document is the most recent, most salient context in its window — `config.md` §3 states this plainly: "the leak is not authored; it is incidental." The mechanical tell: a bare `C-\d+`/`S-\d+` appearing in a *newly added* comment line with no corresponding new pointer to a tracked file in the same diff. Cheapest catch: the ratchet in Finding 4, run on the diff rather than the whole tree, so it fires at PR time on exactly the lines the agent just wrote.
- **An agent asked to "clean up comments" under-deletes rather than over-deletes** (a pattern this program's own empirical work elsewhere measured at 71.7% recall) and specifically tends to *add* a plausible-looking file pointer rather than delete a bare ID outright, because "cite a source" reads as the more thorough, more helpful-looking edit — exactly the failure mode Finding 2 shows is unsafe here (0/30 sampled sites needed invented archaeology; guessing the wrong one of 3–5 colliding definitions is worse than nothing). Cheapest catch: the cleanup skill's dry-run step should flag any *newly added* filename citation next to a plan ID and require it be independently confirmed (`git ls-files` resolves it, and the ID does not already resolve to a *different* tracked file) before it lands.
- **An agent extending an enumeration convention (`H1`, `H2`, …) copies the local pattern without checking whether the label already exists elsewhere in the codebase**, because nothing in the file it's editing signals that the same two-character shape is already claimed three times over in unrelated files (Finding 1(b)). Cheapest catch: before minting a new local `[A-Z]\d{1,2}` label, `rg -rn -e "\b<LABEL>:" .` across the tree; a hit in another file's *definition* position is a collision waiting to happen the moment either file gets referenced from the other.
- **An agent doing a mechanical "add traceability" pass (per `protocol.md`'s own instruction) treats "in the test name" and "in a comment above the test" as interchangeable**, and `config.md` §3 caught it doing exactly that in the same file (`toolchain_store.rs:807`'s doc-comment placement vs. `shell_state.rs:1775`'s in-name placement). Cheapest catch: a single regex requiring the ID appear in the `fn` signature line itself when protocol.md's gate is meant to grep test names, not doc comments above them — `rg -rn -e '\bC-[0-9]+' --type rust -g '*test*' | rg -v '\bfn \w*c[0-9]' ` flags a doc-comment placement as distinct from a name placement.

## Contested / evolving

- **Whether a plan ID belongs in a test name at all is an open design tension inside hex itself, not settled practice elsewhere.** The wider test-naming literature (Osherove 2005, still the reference convention cited by later Given-When-Then guidance) has no ticket-ID slot; hex added one deliberately for its own coverage-gate mechanics. This dive's position (§3) is that the addition is fine *during* a plan's life and wrong as a *permanent* fixture — that is a judgment call about hex's specific archive workflow, not an industry consensus, and the owner's Q1 in the topic map leaves the harness-side fix open.
- **ADR-tooling numbering is trending away from sequential integers, but slowly and not universally.** log4brains (a 2020s tool) explicitly named git-merge collisions as the reason to drop numbering; MADR, actively maintained and the more widely adopted template as of 2026, has not followed — its own README still instructs `nnnn-title.md`. The direction is visible in the newer tool but has not become the default even in the ADR-tooling space itself, let alone in ad hoc internal ID schemes like hex's.
- **Whether "delete the ID" or "restate as present-tense" is the right default for a given site is not fully mechanizable** (Finding 2's 73/20/7 split came from human reading of each site's full context, not a regex) — a future dive or the cleanup skill's own calibration set (per `eval-scoring`'s judge-calibration approach) could tighten this from a documented ratio into a checkable per-site rule, but this dive did not find one.

## Decisions this dive proposes

1. **Regex families with exclusions and measured false-positive rate**: ban all 10 families named in Finding 1 (the original 8 plus `D-`/`D-V`); apply the `short2char` definition-vs-reference split and the "match families before excluding bare `V<n>`" ordering rule; ship SPDX/UTF-8/SHA-256/CWE-/RFC/issue-number cases as negative fixtures, not exclusions. Measured combined false-positive rate after both fixes: 0/240 sampled residual (the one raw hit resolves correctly under the definition/reference split). Reason: every alternative tried (blanket token exclusion, family-then-version-exclusion in the wrong order) either destroyed a real ID family or missed a real collision; this is the only ordering that survived checking against the fleet's own examples.
2. **Allowed file-qualified form**: reuse `pointer-form-and-check`'s decided grammar (file name + heading anchor, never a bare ID) rather than inventing a separate one for plan IDs specifically — this dive found no reason plan-ID pointers need a different shape than any other code-to-record pointer, and a second grammar would only add a second thing to get wrong. Reason: consistency, and census.md §4 already found file+anchor is "the pattern that most often survives."
3. **Test-name policy**: an ID may live in a test name only for the life of its plan's own Specify→Review window; `hex-finalize` (or an equivalent landing step) must strip it or qualify it with the plan's slug. Reason: the coverage gate genuinely needs it transiently (protocol.md is explicit and this is not this program's call to overrule); permanence is what turns a working-as-designed mechanism into a permanent collision, and the fleet's own test names already default to plain sentences 87–100% of the time elsewhere, so stripping costs nothing.
4. **Ratchet command**: `plan_id_ratchet.py --root <dir> --baseline <file> [--check|--update [--allow-regression]]`, per-package, PROD-scope-only counts, `lint_ratchet.py`'s exact JSON contract reused verbatim (built, run against the real ocx tree at 3,400/21, and verified red-then-green on a planted fixture violation in this session). Reason: a second, differently-shaped ratchet contract in the same fleet is a second thing engineers have to learn; this one already works and is already trusted for clippy warnings.
5. **Smallest change to hex's ID minting** (proposal, not an edit — outside this program, per the frame's Q1): prefix every minted `C-`/`S-` ID with the plan's own filename slug at `hex-init/assets/templates/plan.md:116-131`. Reason: this is the literal fix log4brains already shipped for the identical problem in ADR tooling, it changes one template line, it does not touch "stable within the artifact, never renumbered," and it does not require switching to a high-entropy scheme (ULID) that would make test names unreadable.
