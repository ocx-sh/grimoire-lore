## Summary

- Of the sweep's 30 verifiable `adopt-as-rule-text` rows in this task's scope, **7 promote to prose+verification, 5 promote to a lint config change (all Biome, all kate-middlechild-only), and 18 drop outright** — dropping is the majority outcome, as the brief expected.
- The sweep's frontmatter claims "34 from typescript-eslint" but the sweep's own table tags exactly **16** rows `adopt-as-rule-text` — the 34 does not reconcile against a direct `grep -c` of the table; treat 16 as ground truth (see [Finding 0](#0-scope-reconciliation-against-the-sweeps-own-table)).
- `no-loop-func` is a **correction to the sweep**: typescript-eslint's own docs mark it deprecated — "the base `eslint/no-loop-func` rule now handles TypeScript syntax… no longer any need to use this extension rule" — the sweep's deprecated-flag cross-check missed it. [typescript-eslint.io/rules/no-loop-func](https://typescript-eslint.io/rules/no-loop-func/). Drop, cite the deprecation, not the noise.
- `detect-object-injection` — the rule the brief specifically asked to measure — is a clean drop: **391 bracket-notation call sites fleet-wide** (grep, 8 repos), sampled two dozen by hand, and every one is a typed lookup table, loop-index, or discriminant switch (e.g. `grimoire-indexer/src/ratings/registry.ts` pattern, `ocx-catalog/src/ci/discover.ts:38`). Zero sites index with an externally-untrusted string.
- `detect-non-literal-fs-filename` is the opposite case: **≥707 non-literal fs-call arguments** across the three file-heavy repos alone (`grimoire-indexer` 186, `grimoire-vscode` 314, `setup-ocx` 187) — a blanket lint would flag nearly every `fs.*` call in three repos whose entire job is file I/O. Prose only, narrowed to destructive ops on externally-sourced paths.
- `detect-child-process` (34 files use `child_process`/`exec`/`spawn`) is redundant with an already-established fleet fact: interpolated-exec shell injection was independently measured at zero occurrences fleet-wide in an earlier wave. Drop — the rule would flag legitimate process-spawning in every CLI whose job is spawning processes, and the one real risk it targets is already clean.
- `detect-possible-timing-attacks` finds nothing to protect: every `password|secret|token|apikey|hash|hmac|signature\s*===` hit fleet-wide is a type-guard (`typeof token === 'string'`) or an `undefined` check, never a real credential comparison. Drop — the code pattern the rule exists for isn't present in nine local dev tools with no server-side auth path.
- `no-non-null-assertion` (the one rule in this set that IS in a preset — typescript-eslint's `strict`) has a real, low, and legitimate fleet footprint: **~18 genuine uses** (not the ~38 my first grep pass reported — most of that was a false match on GraphQL SDL non-null markers, `$path:ID!`, inside template literals in `grimoire-indexer/src/ratings/provider_gitlab.ts`), concentrated in DOM/ref-access sites the rule's own docs call out as the accepted exception (`fma/src/main.tsx:7`, `fma/src/audio/FFTBars.tsx:20`). Prose, not a hard gate.
- `prefer-enum-initializers` targets a construct that is **structurally absent from every hand-authored file in the fleet** — `grep -rl '^\s*(export\s+)?(const\s+)?enum\s'` finds zero hand-written enums in 7 of 8 repos; the only 3 hits are protobuf-codegen files in `creeptd-ng/web/src/gen/`. Drop.
- `no-unsanitized/property` and `/method` both drop: the one `insertAdjacentHTML`-adjacent hit fleet-wide is a comment in `grimoire-vscode/src/webview/sidebar/main.ts:271` explicitly noting the code does *not* use it (lit's `render()` instead), and the shared webview-HTML helper (`grimoire-vscode/src/views/html.ts:9-34`) already documents its trust boundary in a code comment ("Trusted markup — callers pass already-escaped render output") behind a strict nonce-only CSP. The fleet independently converged on the exact discipline the rule would enforce.
- `prefer-readonly-parameter-types`, `naming-convention`, `no-magic-numbers`, `explicit-module-boundary-types` all drop on documentation evidence alone (each rule's own docs carry an explicit noise/performance/config-heaviness warning) — no fleet measurement needed, consistent with the brief's own framing.
- Biome's opt-in picks split 2 promote / 3 drop, and **all five only apply to kate-middlechild** — it is the fleet's sole Biome repo, so `noBarrelFile`/`noAwaitInLoops`/`noSecrets` decisions have zero bearing on the other 8 ESLint repos.
- `noExcessiveCognitiveComplexity` (threshold 15, stable since Biome v1.0.0) and `noExcessiveLinesPerFunction` (threshold 50, stable since v2.0.0) are both single-flag, zero-config, currently-off in `kate-middlechild/biome.json` — cheap enough to just turn on. Promote.
- `noBarrelFile` drops: kate-middlechild's own barrel count is 0 of 1 `index.ts`; the fleet's one real barrel-shaped file (`fma/src/render/index.ts`) is in an ESLint repo the Biome rule can't reach anyway.
- `noSecrets` drops: zero 32-64 char hex/hash-like literals found in kate-middlechild, so there's no measured problem, and per the rule's own docs the entropy heuristic false-positives on exactly that kind of string — adding it asymmetrically to 1 of 9 repos buys little.
- `max-params` and `no-non-null-assertion` are the two clearest genuine "write as prose" cases: real, checkable, low-but-nonzero incidence, with fleet-native accepted exceptions a blanket lint can't express without per-site config.

### 2. typescript-eslint — type-annotation-boundary rules

`explicit-module-boundary-types`, `explicit-function-return-type`, and `explicit-member-accessibility` all fail the same test. `explicit-module-boundary-types`'s own docs say: "If your project is not used by downstream consumers that are sensitive to API types, you can disable this rule" [typescript-eslint.io/rules/explicit-module-boundary-types](https://typescript-eslint.io/rules/explicit-module-boundary-types/). Neither `ocx-catalog` nor `grimoire-indexer` — the fleet's only two npm-published packages — is consumed as a typed library; both ship an `export {}` stub as their package entry point (established fact, not re-derived here). `explicit-function-return-type`'s own "When Not To Use It" section is unconditional: skip it if you don't find explicit return types worthwhile, no library-vs-app distinction at all [typescript-eslint.io/rules/explicit-function-return-type](https://typescript-eslint.io/rules/explicit-function-return-type/) — a strictly noisier superset of the boundary-types rule with even less justification here. `explicit-member-accessibility` just contests TS's own default (members are `public` unless marked otherwise); its docs offer a `no-public` variant for teams that accept the default [typescript-eslint.io/rules/explicit-member-accessibility](https://typescript-eslint.io/rules/explicit-member-accessibility/) — no fleet evidence of accidental over-exposure was found. All three: drop.

`naming-convention` is the single heaviest-to-configure rule in this set: 6 case-format options, 20+ individual selectors, 7+ group selectors, and its own docs call it "feature frozen" because "stylistic rules that enforce naming and/or sorting conventions tend to grow incomprehensibly complex" [typescript-eslint.io/rules/naming-convention](https://typescript-eslint.io/rules/naming-convention/). A representative working config runs 15-50+ lines. camelCase/PascalCase conventions are universal in the fleet's training-data-adjacent JS/TS idiom and were not observed to be violated in any sampled file. Drop.

`no-restricted-types` bans a caller-supplied list of types (classically `{}`, `Object`, `Function` used in *type* position — the "any non-null value" footgun) but ships with **no default list**; the docs describe it purely as a migration tool, "ban a list of specific types… situations like migrating from one type to another" [typescript-eslint.io/rules/no-restricted-types](https://typescript-eslint.io/rules/no-restricted-types/). Grepping the fleet for `: Object`, `: Function`, and bare `: {}` type annotations returned 20 candidate lines in `grimoire-vscode` alone; every one, on inspection, was `{}` used as an empty-object *value* in a spread fallback (`...(cond ? { x } : {})`) — a completely different, idiomatic pattern this rule doesn't even target. Zero real type-position occurrences of the footgun were found anywhere. Drop — no evidence of the anti-pattern, and the rule needs bespoke configuration to do anything at all.

`prefer-readonly-parameter-types` carries the strongest self-documented warning in this whole set: "This rule is very strict on what it considers mutable. Many types that describe themselves as readonly are considered mutable because they have mutable properties such as arrays or tuples," on top of the standard type-aware performance caveat [typescript-eslint.io/rules/prefer-readonly-parameter-types](https://typescript-eslint.io/rules/prefer-readonly-parameter-types/). It also requires type-checked linting, which is wired in exactly 1 of 9 fleet repos (established fact). Drop.

`no-magic-numbers`'s TypeScript-specific surface (`ignoreEnums`, `ignoreNumericLiteralTypes`, `ignoreReadonlyClassProperties`, `ignoreTypeIndexes`, all default `false` [typescript-eslint.io/rules/no-magic-numbers](https://typescript-eslint.io/rules/no-magic-numbers/)) sits on top of the base ESLint rule's own required ignore-list, in a fleet whose repos are full of unnamed numeric constants by nature of the work (page sizes, retry counts, HTTP status checks, array-slice bounds in a catalog/indexer pipeline). This is the textbook "too noisy without heavy tuning" case the sweep already called correctly. Drop.

### 3. typescript-eslint — structural/ordering rules

`class-methods-use-this` adds `ignoreOverrideMethods` and `ignoreClassesThatImplementAnInterface` specifically because interface-shaped classes routinely have methods that don't touch `this` [typescript-eslint.io/rules/class-methods-use-this](https://typescript-eslint.io/rules/class-methods-use-this/) — exactly the shape of `grimoire-vscode`/`vscode-ocx`'s `vscode.TreeDataProvider`/webview-provider classes, which the VS Code extension API requires to be classes regardless of whether every method needs instance state. Tuning the exceptions per class is more config than the payoff justifies. Drop.

`no-shadow` is a real extension rule (TypeScript needs it for `this`-parameter and namespace-augmentation scoping the core rule can't see [typescript-eslint.io/rules/no-shadow](https://typescript-eslint.io/rules/no-shadow/)) but shadowing bugs are overwhelmingly a legacy copy-paste artifact, not something a model authoring fresh variable names introduces; no shadowed-name confusion turned up incidentally while sampling ~100 fleet files for other rules in this sweep. Drop — model already does this reliably.

`no-use-before-define`'s TypeScript extension exists to check `enum`/`type` reference ordering; the docs state plainly that "you must disable the base rule as it can report incorrect errors" when switching to the TS version [typescript-eslint.io/rules/no-use-before-define](https://typescript-eslint.io/rules/no-use-before-define/) — real bugs in this class (using a `const`/`let`/class before its TDZ) are already hard compiler/runtime errors; what's left is a stylistic ordering preference for types and enums. Drop.

`prefer-destructuring` needs type information to distinguish array-like from index-signature objects — the docs mark it 💭 ("requires type information to run, which comes with performance tradeoffs") and its own "when not to use it" section is literally "disable this if type-checked linting is causing performance problems" [typescript-eslint.io/rules/prefer-destructuring](https://typescript-eslint.io/rules/prefer-destructuring/). Type-aware linting is wired in exactly 1 of 9 repos, so this rule is structurally inapplicable to 8 of them. Drop.

`no-unnecessary-qualifier` only fires on redundant references through a TS `namespace`/`enum` scope — and the fleet has zero hand-written TS `namespace` declarations (namespaces are separately gated by `no-namespace`, already `adopt` per the sweep) and, per the enum measurement below, effectively zero hand-written enums either. The construct this rule polices barely exists in agent-authored code here. Drop.

`prefer-enum-initializers` guards against TypeScript's implicit auto-increment silently renumbering values when a numeric enum's members are reordered or inserted — a real footgun, but `grep -rEln '^\s*(export\s+)?(const\s+)?enum\s+[A-Za-z]'` across all 8 repos found enum declarations in exactly one — `creeptd-ng/web` — and all 3 hits (`match_result_pb.ts:269`, `leaderboard_pb.ts:765,817`) are protobuf-codegen output under `src/gen/`, never hand-edited. No agent-authored enum exists anywhere in the fleet to misconfigure. Drop.

`no-loop-func` is **deprecated upstream**: "This rule has been deprecated because the base eslint/no-loop-func rule now handles TypeScript syntax. There is no longer any need to use this extension rule" [typescript-eslint.io/rules/no-loop-func](https://typescript-eslint.io/rules/no-loop-func/). The sweep's table marks it `Dep: No`, which its own deprecated-rule cross-check should have caught and didn't. Drop, on the correct grounds this time.

`max-params` and `no-non-null-assertion` are this section's two prose promotions — see the [triage table](#1-triage-table) for their draft rule text; both have real, low, fleet-native incidence with legitimate exceptions a static threshold can't express (options-object refactors change call sites everywhere; DOM/ref `!` sites are a well-known accepted carve-out even in strict style guides).

### 5. eslint-plugin-no-unsanitized

Both rules (`method`: `insertAdjacentHTML`/`document.write`/`DOMParser#parseFromString`; `property`: `.innerHTML`/`.outerHTML`/iframe `.srcdoc`) target DOM-write sinks with no equivalent in React's/Vue's own escape hatches [github.com/mozilla/eslint-plugin-no-unsanitized](https://github.com/mozilla/eslint-plugin-no-unsanitized) — the sweep's own reasoning for flagging these specifically for the VS Code extension repos was sound in principle. In practice, fleet measurement shows the risk already engineered away: every `innerHTML` hit (`ocx-catalog` 6 files, `grimoire-indexer` 6, `grimoire-vscode` 3) is either a test-fixture reset (`document.body.innerHTML = ""`) or, in `grimoire-vscode`, a code *comment* explicitly describing innerHTML-wipe rendering as something the codebase moved away from ("no free wipe-on-rerender the way the old wholesale innerHTML replace did", `grimoire-vscode/src/webview/sidebar/main.ts:284`; "old innerHTML-wipe restamp is gone", `.../details/main.ts:123`) in favor of `lit`'s auto-escaping `render()`. The one `insertAdjacentHTML`-adjacent grep hit in the whole fleet is itself a comment confirming its absence (`.../sidebar/main.ts:271`: "this is lit's own render(), not insertAdjacentHTML"). The shared webview-shell builder further documents its own trust boundary in-line: `grimoire-vscode/src/views/html.ts:16` takes a `bodyContent` param annotated "Trusted markup — callers pass already-escaped render output," behind a nonce-only CSP (`html.ts:26`) that would block an inline-script injection even if a sink were missed. The fleet converged on the rule's own intended discipline without the rule. Drop both.

### 6. Biome opt-in rules (kate-middlechild only)

All five apply only to `kate-middlechild` — the fleet's sole Biome repo (`biome.json` present; all 8 others run ESLint flat config + typescript-eslint) — so each decision is single-repo, not fleet-wide.

`noBarrelFile` (Biome `performance` group, stable since v1.6.0, opt-in [biomejs.dev/linter/rules/no-barrel-file](https://biomejs.dev/linter/rules/no-barrel-file/)) has nothing to catch: `kate-middlechild` has exactly 1 `index.ts`, and it is not barrel-shaped (0 of 1 by the "≥70% of non-blank lines are `export … from`" heuristic used fleet-wide). The fleet's one genuinely barrel-shaped file, `fma/src/render/index.ts`, lives in an ESLint repo this Biome rule can never reach. Drop.

`noSecrets` (Biome `security` group, stable since v1.9.0, entropy-based, opt-in, default `entropyThreshold: 41` [biomejs.dev/linter/rules/no-secrets](https://biomejs.dev/linter/rules/no-secrets/)) has no measured target either: `grep -rEon '[a-f0-9]{32,64}'` across `kate-middlechild`'s TS/TSX/Astro files returns nothing, so there is neither a real secret to catch nor the hash/checksum-shaped false positives the rule's own docs warn about. Adding entropy scanning to 1 of 9 repos with no matching coverage anywhere else is asymmetric fleet hygiene for a problem that isn't present; secret scanning belongs in a dedicated CI scanner with an allowlist workflow, not a per-edit linter rule live in one repo. Drop.

`noAwaitInLoops` (Biome `performance` group, stable — **not** nursery, contra its listing alongside nursery picks in the brief [biomejs.dev/linter/rules/no-await-in-loops](https://biomejs.dev/linter/rules/no-await-in-loops/)) pushes `Promise.all()` unconditionally, with no doc acknowledgment of legitimate sequential-await use (ordering, rate limiting, shared mutable state across iterations) — this sweep's own await-in-loop grep (a rough for/while→await proximity heuristic, not AST-accurate) found the pattern is common fleet-wide, including ~24 rough hits inside `kate-middlechild` itself. A blanket enable would demand mass per-site suppression comments in a repo that hasn't earned that cost yet. Prose.

`noExcessiveCognitiveComplexity` (Biome `complexity` group, stable since v1.0.0, default threshold 15, opt-in [biomejs.dev/linter/rules/no-excessive-cognitive-complexity](https://biomejs.dev/linter/rules/no-excessive-cognitive-complexity/)) and `noExcessiveLinesPerFunction` (Biome `complexity` group, stable since v2.0.0, default threshold 50, opt-in [biomejs.dev/linter/rules/no-excessive-lines-per-function](https://biomejs.dev/linter/rules/no-excessive-lines-per-function/)) are both single numeric-threshold flags with no other config surface. `kate-middlechild/biome.json` currently sets `linter.rules.preset: "recommended"` plus three unrelated overrides (`noUnusedImports`, `useImportType`, `noNonNullAssertion`) — neither complexity rule is on. Cheap to turn on, catches exactly the maintainability class an agent editing without a human review loop most needs a mechanical backstop for. Promote both.

## Normative guidance candidates

1. **Do not use `x!` (non-null assertion) except immediately on a DOM/ref-API call already known non-null in context** (`document.getElementById(id)!`, `ref.current!` right after a mount guard). Anywhere else, narrow the type or handle the nullable case. *Rationale*: typescript-eslint's own `strict` preset bans `!` outright but documents this exact carve-out as its main false-positive source. *Verify*: `grep -rEon "[A-Za-z0-9_$)\]]!(\.[A-Za-z_$]|[;,)\]}])" --include='*.ts' --include='*.tsx'` (exclude `.test.` files and `!==`/`!=` matches), inspect each hit.
2. **A function taking more than 4 positional parameters takes an options object instead.** *Rationale*: readability and call-site stability under future param additions; matches the fleet's already-low baseline (4 hits total). *Verify*: `grep -rEn '^\s*(export )?(async )?function \w+\(([^()]*,){4,}[^()]*\)'`.
3. **A path segment reaching a destructive `fs` call (`rm`, `rmSync`, `unlink`, `unlinkSync`, `writeFile*` with overwrite semantics) must be resolved and checked to stay inside its intended root before use.** *Rationale*: `detect-non-literal-fs-filename` would flag ~700 legitimate call sites fleet-wide; the actual risk (path traversal from an external string) is narrow and needs a human/model read of the specific call site, not a blanket ban. *Verify*: `grep -rn "fs\.\(rm\|unlink\|writeFile\)"` then trace the path argument's origin by hand.
4. **A `new RegExp(dynamicString)` outside a test file must be wrapped in `try/catch` and built from a bounded, schema-validated source string, never raw external input.** *Rationale*: one such site exists in production (`grimoire-vscode/src/webview/settings/model.ts:311`) and is already correct — codify it as the pattern rather than inventing new guidance. *Verify*: `grep -rn "new RegExp(" --include='*.ts' | grep -v '\.test\.'`, confirm try/catch at each hit.
5. **A `for`/`while` loop with `await` inside its body needs a comment stating why the iterations run sequentially, or a rewrite to `Promise.all()` when they're independent.** *Rationale*: Biome's `noAwaitInLoops` has no way to distinguish the two cases and this fleet's CLI/indexer repos have many legitimate sequential-await loops (ordered downloads, rate-limited API calls). *Verify*: manual review — grep for `for (`/`while (` blocks containing `await`, check for a nearby rationale comment.
6. **`kate-middlechild/biome.json`: set `linter.rules.complexity.noExcessiveCognitiveComplexity` and `noExcessiveLinesPerFunction` to `"error"`.** *Rationale*: zero-config, stable, currently off, and this is the one repo in the fleet where turning it on costs a one-line config change instead of a new toolchain integration. *Verify*: `biome lint` in CI; both are Biome's own zero-suppression-workflow-needed rules (unlike `noSecrets`/`no-unsanitized`, which need an escape-hatch convention the fleet doesn't have).
7. **Do not add `eslint-plugin-security`'s `detect-object-injection`, `detect-non-literal-require`, `detect-child-process`, or `detect-possible-timing-attacks` to any repo's config.** *Rationale*: each targets a risk pattern independently measured at zero (or near-zero and already-covered) occurrences fleet-wide; enabling any of them buys alarm fatigue, not coverage. *Verify*: the fleet-wide greps in [Finding 4](#4-eslint-plugin-security) are reproducible and cheap to re-run periodically as a sanity check rather than gating every edit.
8. **Do not add `eslint-plugin-no-unsanitized` to the VS Code extension repos.** *Rationale*: both extensions already build webview HTML through one shared, CSP-locked, trust-boundary-documented helper (`grimoire-vscode/src/views/html.ts`) and use `lit`'s auto-escaping renderer for dynamic content — the rule would be pure noise against code that already does the right thing by convention. *Verify*: `grep -rn "webview\.html\s*=" --include='*.ts'` should always resolve to a call into `webviewHtml()`/an equivalent shared helper, never inline string concatenation — spot-check this on new webview code instead of linting every file.

## AI-agent angle

- **An agent asked to "harden this CLI" will reflexively reach for `eslint-plugin-security`'s full recommended set** because the plugin advertises itself as `recommended`-by-default — without knowing the plugin's own README admits high false-positive rates needing human triage. The mechanical check: before adding any `eslint-plugin-security` rule, grep the fleet for the pattern it targets (bracket access, dynamic `require`, `child_process` usage) and compare hit count to file count — a hit-rate above roughly 1-in-5 files is a noise signal, not a coverage signal, before a single line of code changes.
- **An agent regenerating a webview or extension entry point tends to inline HTML via template-literal concatenation** rather than reusing an existing shared builder, because that's the shortest local diff. The mechanical check: `grep -rn "\.html\s*=" --include='*.ts'` in a VS Code extension repo should resolve to exactly one call site pattern (the shared helper); a second inline `<html>` template literal appearing anywhere is the actual thing to flag, not the presence of `innerHTML` per se.
- **An agent adding a numeric enum for a new IPC/message-type union will not reliably assign explicit initializers**, because the fleet has zero hand-written precedent to imitate and TypeScript's implicit auto-increment is silently valid. The mechanical check is trivial and worth keeping even though the rule itself is dropped for lack of current incidence: `grep -A1 '^\s*enum '` and confirm every member line contains `=`.
- **An agent copying a config snippet from one repo to another risks enabling a typescript-eslint extension rule (`no-shadow`, `no-use-before-define`, `class-methods-use-this`, etc.) alongside the same-named core ESLint rule** rather than turning the core one off — both then fire, or the later-declared one silently wins depending on config order. This is a real fleet-relevant footgun the sweep already flagged in its "Extension rules" section; it applies regardless of this report's per-rule drop/promote calls, because it's about *how* any rule from this family gets enabled, not whether it should be.

## Contested / evolving

- **`no-non-null-assertion` in a preset at all is contested inside typescript-eslint itself** — it lives only in `strict`, not `recommended`, specifically because the maintainers' own docs concede it "might create many false reports" during incomplete `strictNullChecks` migration. As of 2026-08-29 this fleet's own low, DOM-concentrated usage pattern argues for prose over the preset's blanket ban, but a fleet that finished a `strictNullChecks` migration years ago (this one has — `any`/`@ts-ignore` are already at zero) is exactly the population the preset assumes has earned the stricter posture. Watch for this to flip if non-null-assertion count grows past the DOM/ref carve-out.
- **Biome's rule-group boundaries moved during 2026 itself**: `noAwaitInLoops` sits in `performance`, not `nursery`, contradicting how this task's brief grouped it — worth re-checking group membership at time of read rather than trusting a prior categorization, since Biome promotes/demotes rules between groups across minor versions.
- **`no-loop-func`'s deprecation is a live example of catalogue rot inside the sweep this report is built on** — a same-day sweep (2026-08-29) still mis-tagged a rule's deprecation status, which the sweep's own "Catalogue rot" section calls out as a general risk for exactly this reason (docs pages mis-stating metadata vs. source-of-truth config files). Re-verify deprecation flags against the rendered rule page's own banner, not just a table someone else compiled, even same-day.
- **Whether `detect-object-injection`-class rules are worth *any* lint posture (even opt-in) remains genuinely disputed across the ecosystem** — this report's zero-fleet-incidence finding is fleet-specific evidence, not a general verdict; a repo that actually indexes objects with request-derived keys (a web server processing user input into config lookups, unlike anything in this fleet) would reasonably reach a different conclusion. Could not establish a fleet-independent consensus position as of 2026-08-29.
