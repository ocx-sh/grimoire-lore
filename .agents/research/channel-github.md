# GitHub and package registries as the active channel

GitHub is the only channel the fleet uses with any traffic. The repository card, the Releases tab and the registry listings are where a visitor meets the product, and the GitHub and registry counters are the only usage numbers the fleet has ([distribution-posture.md](product-audit/distribution-posture.md), headline 1 and section 3). This file decides which surfaces every fleet repository sets, to which published limits, and which numbers a team may report.

It does not decide the release-body contract (commit footers, the `cliff.toml` template, the Migration line, the summary sentence, internal-scope filtering, tag-to-Release coverage). The marketing consolidation [marketing-release-announcements.md](marketing-release-announcements.md) (`MKT-REL-*`) owns those, and this file defers to it. README and description wording, keyword choice and site `og:image` tags belong to marketing. Launch-plan structure belongs to channel-launch, which takes its counter list from CH-GH-23.

## Verdict

1. **The repository card is a MUST set for every public repository the owner has not classed as internal.** Every such repository has a description, a homepage when a site exists, and 1 to 20 valid topics (MUST, CH-GH-03), with 3 or more as the catalog norm (SHOULD, CH-GH-30). GitHub's default repository search reads only the name, description and topics ([GitHub Docs, searching for repositories](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories), undated, fetched 2026-11-27). Today 14 of 17 fleet repositories have no topics and 3 have no description ([gh-repo-card.md](channel-github/gh-repo-card.md) section 2.2). Conflict resolved: the registry dive graded the card SHOULD (its rule 15) and the card dive graded it MUST. MUST wins, because a repository with an empty description and no topics is absent from the default search and from every `github.com/topics/<topic>` page, and fixing it costs one `gh` call.
2. **One description budget for every surface: 140 characters, one line, plain text.** The card dive proposed 140 for the GitHub About field (the upstream maximum is 139, the median 47). The registry dive proposed 160 for registry `description` fields. Neither number is a platform limit. Conflict resolved: use one budget, so that the same sentence can serve GitHub, crates.io, npm, PyPI and the Marketplace without a rewrite. Docker Hub's short description has a hard platform cap of 100 characters ([Docker Docs](https://docs.docker.com/docker-hub/repos/manage/information/), undated, fetched 2026-11-27). No GitHub page states a description limit. The 350-character figure on third-party sites is unverified, and no rule may cite it.
3. **A custom social preview is MUST for the two flagships (`ocx-sh/ocx`, `grimoire-rs/grimoire`) now, and SHOULD for other public repositories.** Conflict resolved: the card dive made the flagship MUST conditional on "once a post links to it". That condition already holds, because the READMEs, both sites and the Discord already link these repositories. Spec: PNG, JPG or GIF, under 1 MB, at least 640 x 320, 1280 x 640 for best display ([GitHub Docs, social preview](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview), undated, fetched 2026-11-27). Second conflict: the audit's share-card pattern asks for 1.91:1 at 1200 x 630 for LinkedIn and Meta ([distribution-posture.md](product-audit/distribution-posture.md) pattern 1). Resolved: keep GitHub's 1280 x 640, and keep the product name and subject inside the central 1222 x 640 area, so that a 1.91:1 crop clips nothing. The 1222 is derived (640 x 1.91 = 1222.4) and assumes a centre crop; no source states it. Site `og:image` is marketing territory. The owner supplies the artwork. The agent only checks it.
4. **Each organisation gets a public `.github/profile/README.md`, a description of 160 characters or fewer, and a website.** Both organisations return 404 for the profile README today, and both have an empty description ([distribution-posture.md](product-audit/distribution-posture.md) section 4). The 160 limit is in the [REST orgs reference](https://docs.github.com/en/rest/orgs/orgs) (undated, fetched 2026-11-27).
5. **The release body belongs to MKT-REL. This file owns the GitHub release mechanics: Latest, pre-release, immutability, download URLs, version agreement and notification claims.** Three conflicts resolved against the release dive:
   - GH-REL-3 asked for a separate "Breaking" heading first. MKT-REL verdict 4 forbids that heading, because DOC-TYPE-37 allows only the six Keep a Changelog headings, and the GitHub body and `CHANGELOG.md` come from the same template. MKT-REL wins.
   - GH-REL-11 (tag parity, exempt only by owner instruction) is replaced by MKT-REL-11, which classifies a repository by grepping its consumers and keeps a baseline file. That form is more checkable.
   - GH-REL-9 (`.github/release.yml` for repositories with GitHub-generated notes) is dropped. Every fleet repository that releases now has a `cliff.toml`, so GitHub-generated notes are a MKT-REL-10 violation to remove, not a configuration to tune. The website workflow comment that says otherwise is stale ([marketing-release-announcements.md](marketing-release-announcements.md), MKT-REL-10 row).
6. **The Latest flag is derived by comparing versions, never passed unconditionally.** The release dive's GH-REL-13 had the backport direction backwards. A backport (1.4.1 after 2.0.0) needs `--latest=false`, not `--latest`. GitHub's own pages disagree on how Latest is chosen when nothing is passed: "based on semantic versioning" in [managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), and the most recent non-prerelease by `created_at` in the [REST releases reference](https://docs.github.com/en/rest/releases/releases) (both undated, fetched 2026-11-27). So the workflow decides the flag and checks the result after publishing. Today, ocx passes `--latest` for every stable release and www-setup sets `make_latest=true` for every stable tag. Both would move Latest to a backport.
7. **Immutable releases: the workflow is made draft-first before anyone turns immutability on, and turning it on is the owner's decision.** The feature became generally available on 2025-10-28 ([GitHub changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)). 5 of 12 exemplar CLIs publish every sampled release as immutable, and the fleet publishes none (0 of 34 grimoire releases). A deleted immutable release keeps its tag name locked permanently ([GitHub Docs, immutable releases](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/immutable-releases), undated, fetched 2026-11-27). That cost makes the switch an owner call.
8. **A Discussions thread per release is not recommended.** 0 of 120 exemplar releases link one, and 0 of 34 grimoire releases do. GitHub documents no notification effect. No rule requires one, and no release skill adds `--discussion-category` by default ([gh-release-announcement.md](channel-github/gh-release-announcement.md) finding 8).
9. **Registry listings follow one per-registry field table, and the platform limits in it are MUST because the registry rejects a violation at publish.** README links have to be absolute only where the registry does not rewrite them. Conflict resolved (the registry dive's rule 10 said SHOULD for links in its text and enforced PyPI and npm in its check): images are MUST absolute `https` everywhere. Links are MUST absolute for PyPI, which keeps them relative (measured on typer 0.29.3, and the [PyPA guide](https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/) says they break). Links are SHOULD for npm, whose behaviour is undocumented and could not be measured (403 to every client, retried 2026-11-27); community reports alone do not carry a MUST. Links are SHOULD for crates.io and the Marketplace, which rewrite them to `blob/HEAD`. A link rewritten to `HEAD` still resolves, but to the default branch, not the release.
10. **Homebrew: publish a tap, and never submit to homebrew-core before the thresholds hold.** The bar is 30 forks, 30 watchers or 75 stars, or 90, 90 or 225 for a self-submission, and the repository must be at least 30 days old ([Homebrew Package Acceptance Policy](https://docs.brew.sh/Package-Acceptance-Policy), undated, fetched 2026-11-27). ocx has 20 stars, 2 forks and 0 watchers. grimoire has 17 stars, 2 forks and 2 watchers. Neither qualifies.
11. **A team may report a GitHub or registry number only as a named signal with a window, a read date, the command and a caveat id (a catalog norm, CH-GH-23). A team never reports one as users, adopters or installs.** Stars, Trending, Product Hunt points and Hacker News score are never the goal of a launch. The evidence behind this:
    - Stars include fake stars (3.81 million after postprocessing in [He et al., arXiv:2412.13459 v2](https://arxiv.org/html/2412.13459v2), 2025-09-06).
    - The star model drops removals ([GitHub engineering](https://github.blog/engineering/architecture-optimization/from-2500-requests-to-24-rebuilding-star-history-without-the-stargazers/)).
    - Release-asset `download_count` has no documented definition ([REST release assets](https://docs.github.com/en/rest/releases/assets), undated). On the fleet, the `.sha256` sidecar is fetched at 48% of its tarball's rate, which points to machines.
    - npm counts every HTTP 200 tarball response, including CI and mirrors ([npm blog, 2014-07-22](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html)).
12. **A weekly traffic archive is MUST for the flagships.** The traffic API returns only the past 14 days ([GitHub Docs, viewing traffic](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository), undated, fetched 2026-11-27), and the fleet archives nothing. Conflict resolved: three GitHub pages name three different permission levels for these endpoints (push, write, and Administration read). The agent ships and lints the workflow; the owner creates and tests the token. Cross-catalog finding: DOC-OBS-16 (`skills/docs-quality-reference/observability.md:64`, CONSIDER) asks for a nonzero traffic number "for 30 consecutive days", and for a repository with no site it checks only that `traffic/views` returns 200. A single call returns 14 days, so the 30-day clause cannot be met from that call. CH-GH-25 does not change DOC-OBS-16's text and does not contradict it. For the docs-quality owner: on the `traffic/views` branch, read the 30 days from the CH-GH-25 archive and cite CH-GH-25.
13. **Counts in this file follow the dives, not the audit, where they differ.** The audit's 90 release bodies and 45 ocx BREAKING lines recount to 89 bodies (rules_ocx has 9 releases, not 10) and 44 `**BREAKING**` lines. The audit's denominator of 18 includes `michael-herwig/arcana`, so the fleet base is 17. The audit's wording that `usesCustomOpenGraphImage` false means "GitHub's generated card" contradicts the GraphQL reference ("the owner's avatar"), so no rule encodes either reading. The rule checks the boolean only.

## The ruleset

Placeholders: `R` is `owner/repo`, `o` and `n` are its parts, and `O` is an organisation login. Every command is read-only unless it says otherwise. "Internal" means a repository the owner has classed as not public-facing (see "What an agent must ask a human"). GitHub Docs pages carry no date, so the date given is the fetch date, 2026-11-27. Inside a table cell, `\|` stands for a literal `|`; type `|` when you run the command. When a Verification cell lists several checks, the rule passes only when every check passes; a partial pass is a fail. "Catalog norm" marks a value this catalog chose: it is not a platform fact, and no copy may present it as one.

### Release mechanics (the body contract is MKT-REL)

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CH-GH-07 | After every publish, exactly one release is Latest, and it is the highest stable version. The workflow derives the flag. It never hard-codes either value for all stable releases. | GitHub's pages disagree on the default ([managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository) says semver, [REST releases](https://docs.github.com/en/rest/releases/releases) says most recent by `created_at`; both fetched 2026-11-27). | CH-GH-11 | Keep one version string across the tag, the release title, the changelog heading and the registry version, after stripping a leading `v`. | CH-GH-12 | Never claim that publishing a release notifies anyone beyond watchers who chose Custom > Releases. ## Agent failure modes

Ranked by how often each bites in the measured evidence, grouped by mechanism.

**A. Treating a number as a result (most frequent).**
1. Calls download or install counts "users" or "adopters", or sums release-asset downloads across releases. Every fleet counter is machine-heavy: clones run 7,990 against 180 views on ocx, and the `.sha256` sidecars are fetched at 48% of the tarball rate. Caught by CH-GH-23.
2. Reports 14-day traffic as "monthly" or "all time", or treats `uniques` as people. Caught by CH-GH-23 (window and id) and CH-GH-25 (archive).
3. Sets stars or a Trending spot as the launch goal, or proposes "ask friends to upvote". Caught by CH-GH-24 and CH-GH-27.
4. Quotes OSS Insight or star-history widgets from training data. Caught by CH-GH-28.

**B. Inventing or misremembering a platform limit.**
5. States "GitHub allows 350 characters" as fact. Caught by CH-GH-02.
6. Invents crates.io category slugs (`cli`, `developer-tools`), uses six or more keywords, or lints Marketplace categories against the incomplete doc list. Caught by CH-GH-14 and CH-GH-19.
7. Cites "75 stars" as the only Homebrew bar, or submits to homebrew-core early. Caught by CH-GH-20.
8. Treats 1280 x 640 as the minimum, or `usesCustomOpenGraphImage` as an image-quality check. Caught by CH-GH-05.

**C. Destructive or unapproved writes.**
9. Calls `PUT topics` with only the new names, which wipes the old ones, or tries to set topics through `PATCH /repos`. Caught by CH-GH-04.
10. Runs `gh repo edit` or a `PATCH orgs` without approval. Caught by CH-GH-04.
11. Creates the traffic token or secret itself. Caught by CH-GH-25.
12. Deletes and re-pushes a tag to "fix" a release, which burns the tag name for good once immutability is on. Caught by CH-GH-10.

**D. Release flags and URLs.**
13. Hard-codes `--latest` (as ocx does) or `make_latest: true` (as www-setup does), so that a backport takes Latest. Caught by CH-GH-07.
14. Runs `gh release view --json isLatest`, which fails because the field does not exist, then "confirms" Latest some other way. Caught by CH-GH-07, which uses `gh release list`.
15. Renames an asset and breaks `/releases/latest/download/<asset>`. Caught by CH-GH-08.
16. Uploads assets after publishing on an immutable repository. Caught by CH-GH-10.

**E. Wrong source of truth.**
17. Reads the version from a checked-in manifest that CI bumps at publish time (theme 0.6.0 against 0.7.0). Caught by CH-GH-11.
18. Assumes a README edit updates the registry page. Caught by CH-GH-22.
19. Leaves `./docs/x.md` or `./assets/logo.svg` in a README that PyPI or npm reuses. Caught by CH-GH-18.
20. Scans a third party's `/stargazers` list and reads the 404 as zero stars. Caught by CH-GH-26.
21. Claims a release "notifies followers", or adds a Discussions thread to every release. Caught by CH-GH-12.

## What an agent must ask a human

- Which public repositories are internal and exempt from CH-GH-01, CH-GH-03 and CH-GH-05. The candidates are e2e-index, grimoire-lore, index and conventions.
- The wording of every description, the category topics, and the homepage target for repositories that have no site. These are positioning decisions, so the agent proposes and the owner approves.
- Any topic that names a third-party product or trademark (for example `claude`, `cursor` or `copilot` on grimoire today).
- The social-preview artwork, colours and logo use. The agent checks size and format and never generates or uploads brand imagery.
- The organisation descriptions, the profile README claims and the pinned repositories (pinning is owner-only).
- Turning on immutable releases, at repository or organisation level.
- Marking a release Latest by hand, or as a pre-release, outside the derived rule.
- The crates.io name for the CLI (`grim` and `grimoire` are held by other projects), whether to rename, or whether to publish to crates.io at all.
- Tap or homebrew-core, a Docker Hub namespace next to GHCR, and the timing of a verified Marketplace publisher (which needs 6 months on the Marketplace and a DNS TXT record).
- The traffic-archive token: which account owns it, its permission, and where the archive lives, because it may become public.
- Whether any GitHub or registry number appears in public copy, and the launch counter and target.
- Cutting a patch release only to refresh a registry README.
- Removing a Marketplace extension, which deletes its statistics.

## Open questions

Another round deserves:
- How does npm render relative README links and images today? Every non-browser client got a 403, including a `x-spiferack: 1` JSON request on 2026-11-27. A real-browser fetch of `npmjs.com/package/@grimoire-rs/indexer` would settle whether CH-GH-18's npm links can rise from SHOULD to MUST.
- Does grimoire's cargo-dist step (`gh release create ... artifacts/*` in one call) succeed with immutable releases on? And how does Latest resolve when a backport is published after a higher version with no flag? Both need a scratch repository and owner approval, because they change state.
- What is the minimum token that reads the traffic endpoints: `GITHUB_TOKEN` with `contents: read`, a fine-grained token with Administration read, or push access? The three GitHub pages disagree.
- Does `docker/metadata-action` put `org.opencontainers.image.source` and `.description` on `ghcr.io/ocx-sh/ocx`? A `docker buildx imagetools inspect` would answer CH-GH-21.
- What does a fleet repository's default `opengraph.githubassets.com` card look like when it unfurls on LinkedIn and X? The image could not be downloaded (rate limit). The answer tells how much CH-GH-05 buys on other repositories.
- Is there a real GitHub description cap? One test write on a scratch repository would settle the 350 figure.
- Can an org's pins be read through GraphQL `organization.pinnedItems`? That decides whether pins can become a checkable rule.
- What star-anomaly threshold separates a burst from a campaign on a small repository? The dive's "5 times the 30-day median and at least 10 stars" is unsourced. The owner calibrates, or the rule stays out.

Owner decisions: every item under "What an agent must ask a human". Three of them block adoption: the internal-repository list (it scopes CH-GH-01, -03 and -05), the flagship social-preview artwork (CH-GH-05), and the traffic-archive token and storage (CH-GH-25).
