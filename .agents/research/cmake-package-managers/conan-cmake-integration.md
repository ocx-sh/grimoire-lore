## Summary

- Conan 2.32.0 (2026-08-31, [changelog](https://raw.githubusercontent.com/conan-io/docs/develop2/changelog.rst)) is current; no release since.
- `CMakeDeps` + `CMakeToolchain` is the stable, documented default generator pair; `CMakeConfigDeps` remains **experimental** in its own reference page even though `incubating.rst` calls it "generally available" — the reference page's literal `experimental_warning.inc` include is what a build actually ships, so treat it as experimental (Conan 2.32.0).
- `CMakeConfigDeps` never generates `Find*.cmake` modules and none is planned; a consumer that does `find_package(pkg MODULE)` breaks on migration from `CMakeDeps` (Conan 2.25.0+).
- `CMakeConfigDeps` needs no `build_context_activated`/`build_context_suffix` to expose `tool_requires` targets — `CMakeDeps` does, and without it a build-context dependency's config files are not generated by default (Conan 2.13.0+ / stable `CMakeDeps`).
- Explicit `conan install .` then `cmake --preset conan-<x>` is Conan's own documented "recommended flow for most cases"; the `cmake-conan` dependency-provider (`CMAKE_PROJECT_TOP_LEVEL_INCLUDES`) is for "extraordinary and exceptional scenarios" and its own README says stability "is not guaranteed" (cmake-conan `develop2`, HEAD `b1593849dd`, 2026-06-05, unchanged since 2026-09-05).
- The `cmake-conan` provider only auto-detects the MSVC/gcc/clang trio, needs `CMAKE_BUILD_TYPE` set for single-config generators, only intercepts the *first* `find_package()` (an earlier `find_program`/`find_library` call is missed), and only supports `CMakeConfigDeps` as its generator.
- `build_requires` was deprecated in favour of `tool_requires` in Conan **2.28.0** (2026-04-28, PR #19849); a conanfile still declaring it is a P0 finding, not a style choice.
- Cross builds need both profiles set explicitly (`-pr:b`/`-pr:h`); `[tool_requires]` and `[replace_requires]` now accept negated-OR patterns to break build-context cycles (2.27.0).
- `conan.lock` is picked up **implicitly** from the working directory by `conan install`/`conan create`/`conan graph info` alike — an explicit `--lockfile=conan.lock` is still recommended for CI so the intent is visible.
- Lockfiles are **strict by default**: a dependency not present in the lock fails the resolve (`ERROR: Requirement '...' not in lockfile`); `--lockfile-partial` relaxes it, `--lockfile-out` writes an updated lock, `--lockfile-clean` prunes entries unused by the current configuration.
- A lockfile records `pkgref#revision%timestamp` and can hold several versions of one package; on resolve the **newest listed version/revision in range wins** — it cannot force a version outside the recipe's own version ranges.
- No CMake-side check exists for `compiler.cppstd`/`build_type` vs the project's own `CMAKE_CXX_STANDARD`: **measured** on CMake 4.4.2 — a project `set(CMAKE_CXX_STANDARD 20)` placed after `project()` silently overrides a Conan-toolchain-injected `CMAKE_CXX_STANDARD 17` with **no diagnostic at any `-Werror=author`/`-Werror=dev` level**.
- MSVC runtime detection has the same blind spot for a different reason: `CMAKE_MSVC_RUNTIME_LIBRARY` (CMake ≥3.15) is a generator expression by default, and Conan's CMake integration has had an **open, unresolved issue since 2019** ([cmake-conan#174](https://github.com/conan-io/cmake-conan/issues/174)) about not being able to evaluate it back into a Conan setting.
- `CMakeToolchain` writes `CMakePresets.json` at **schema version 3** and, when the source and build folders differ, a `CMakeUserPresets.json` at **schema version 4**; **measured from source** (`conan/tools/cmake/presets.py@2.32.0`): the skip rule keys on the JSON `vendor.conan` object — if a `CMakeUserPresets.json` already exists and lacks that key, Conan leaves it untouched rather than overwriting a hand-written file.
- Conan-1 residue is not hypothetical: `abseil/abseil-cpp`'s own `conanfile.py` (repo HEAD as of 2026-09-26) still imports `from conans import ConanFile, CMake, tools`, sets `generators = "cmake"`, and patches in `include(conanbuildinfo.cmake)\nconan_basic_setup()` — all Conan-1-only APIs that error under Conan 2.
- Conan Workspaces are GA per the 2.31.0 (2026-07-23) changelog entry "Get Workspace feature out of incubating" — but `incubating.rst` itself still labels them "generally available **as experimental**," a live hedge, not a wave-1 misreading.
- `conan graph explain` diagnoses a missing-binary/mismatch error and proposes the closest alternative; `conan graph info` computes and inspects the full dependency graph (JSON/HTML/dot) without downloading binaries; both honour an implicit `conan.lock` exactly like `install`.

## Findings

### 1. Which generator, and the two-page contradiction

Conan ships two CMake-consumption generators side by side. `CMakeDeps` is the
long-standing generator; its own reference page tells the reader to prefer the
newer one on trouble: "There is a new experimental `CMakeConfigDeps` generator
that implements many improvements and fixes over this `CMakeDeps`
generator... give a try to `CMakeConfigDeps` first"
([`cmakedeps.rst@develop2`](https://raw.githubusercontent.com/conan-io/docs/develop2/reference/tools/cmake/cmakedeps.rst), lines 6–16). `CMakeConfigDeps`'s own
page opens with `.. include:: ../../../common/experimental_warning.inc` and
states "(available as experimental from Conan 2.25)"
([`cmakeconfigdeps.rst@develop2`](https://raw.githubusercontent.com/conan-io/docs/develop2/reference/tools/cmake/cmakeconfigdeps.rst), lines 1–8).

The brief's chase-the-surprise — the changelog resolution — is unambiguous.
`incubating.rst@develop2` (fetched 2026-09-26) says: "This generator is not
incubating anymore, but already generally available." But the changelog entry
that produced today's docs never says "generally available": Conan **2.25.0**
(28-Jan-2026) "Move `CMakeConfigDeps` from incubating to experimental" (PR
#19421); Conan **2.32.0** (31-Aug-2026, current) has no further status change
for the generator (`grep`-checked against `changelog-2.13-2.32.rst`, no hit
for `CMakeConfigDeps` promoted past "experimental"). The two Conan pages
disagree with each other, not with the changelog: the changelog and the
generator's own reference page (which literally renders the experimental
warning box a user sees) agree with each other, and `incubating.rst`'s "GA"
line is the outlier. **The newest changelog entry supports "still
experimental."** This matches the program's opus verifier's independent
resolution of the same conflict ([cps-v row 43](../cmake-dependency-seam/cps-verification.md)).

`CMakeDeps` generates one config file (and matching `Find*.cmake` only when a
dependency's `cmake_find_mode` property requests it) plus a Conan-1-style
`conandeps_legacy.cmake` convenience file (`cmakedeps.rst` lines 73–86).
`CMakeConfigDeps` "is only intended to generate `xxx-config.cmake` config
files, it will not generate `Find*.cmake` find modules, and support for it is
not planned" (`cmakeconfigdeps.rst` line 80) — a hard, permanent limitation,
not a temporary gap. `CMakeConfigDeps` also creates real
`SHARED/STATIC/INTERFACE IMPORTED` targets (no more `CONAN_LIB::` artificial
targets), needs no `build_context_activated`/`build_context_suffix` for
`tool_requires` targets, and matches each dependency's own build type rather
than the consumer's (`cmakeconfigdeps.rst` lines 90–108) — real fixes, still
shipped behind the experimental label.

`CMakeDeps`'s build-context default is the opposite and easy to miss: "When
you have a build-require, by default, the config files (`xxx-config.cmake`)
files are **not generated**" unless `build_context_activated` names it
(`cmakedeps.rst` lines 100–113).

### 2. Explicit `conan install` vs the cmake-conan provider

Conan's own integration page states the flow directly: "`conan install ...`;
`cmake --preset conan-xxxx`... This is the recommended flow for most cases,"
and reserves the provider for "extraordinary and exceptional scenarios,"
naming IDE integrations like CLion as the motivating case
([`integrations/cmake.rst@develop2`](https://raw.githubusercontent.com/conan-io/docs/develop2/integrations/cmake.rst), lines 32–55). The same page: "This
`cmake-conan` project stability is not guaranteed, and it has some known
issues and limitations... calling `conan install` explicitly before calling
`cmake` is still the preferred and most recommended flow for most cases."

`cmake-conan`'s own README (`develop2`, HEAD `b1593849dd`) repeats and sharpens
this under "Known limitations with Conan 2.0":
- Only `CMakeConfigDeps` is recommended for the provider (not `CMakeDeps`).
- Settings normally supplied by `CMakeToolchain` must come from a separate
  `conan install` call — the provider does not replace `CMakeToolchain`.
- The provider triggers `conan install` at the **first** `find_package()`
  call; any `find_program`/`find_library`/`find_path`/`find_file` used
  *before* that first `find_package()` runs against an empty prefix path.
- A single-configuration generator needs a non-empty `CMAKE_BUILD_TYPE`, or
  `CONAN_INSTALL_BUILD_CONFIGURATIONS` must be set.
- Compiler autodetection only covers Windows+MSVC, Linux+gcc, Apple+clang; any
  other toolchain needs an explicit Conan profile via `CONAN_HOST_PROFILE`.

### 3. `tool_requires` vs deprecated `build_requires`, two-profile model

`build_requires` was deprecated in Conan **2.28.0** (2026-04-28): "Deprecate
`build_requires`, use `tool_requires` instead" (PR #19849, confirmed at
`changelog.rst` line 198, inside the `2.28.0` section spanning lines 163–214).
This matches the frame's "~2.28" estimate exactly. The two-profile model
(`-pr:b`/`-pr:h` for host/build) is what makes `tool_requires` meaningful for
cross builds — a `tool_requires` dependency is built for the **build**
machine, a plain `requires` for the **host** machine. `[tool_requires]` and
`[replace_requires]` gained negated-OR pattern support
(`!(<pattern1>|<pattern2>)`) in **2.27.0** specifically to let a profile break
build-context self-dependency cycles (changelog line 223).

The CCI package template's canonical form is `self.tool_requires("cmake/[>=3.16 <4]")`
inside `build_requirements()` — `tool_requires` is the *method* called from
inside that hook, not a competing keyword
([`conan-io/conan-center-index@07389b8fa0:docs/package_templates/cmake_package/all/conanfile.py:76-78`](https://github.com/conan-io/conan-center-index/blob/07389b8fa0/docs/package_templates/cmake_package/all/conanfile.py)).

### 4. `conan.lock` semantics

Fully measured against `tutorial/versioning/lockfiles.rst@develop2` (the
worked example, verbatim commands):

- **Implicit pickup.** `conan install .` is "equivalent to
  `conan install . --lockfile=conan.lock`" whenever `conan.lock` sits in the
  working directory (line 98); the same is true for `conan graph info` and
  `conan create` (lines 113–116). "If using a lockfile is intended, like in
  CI, it is better that the argument `--lockfile=conan.lock` [is] explicit"
  (line 118) — CI should never rely on the silent default.
- **Strict by default.** A range dependency not present in the lock fails
  hard: `ERROR: Requirement 'sound32/[>=1.0 <2.0]' not in lockfile` (line
  135). `--lockfile-partial` downgrades this to "resolve what's not locked
  normally" (lines 139–152).
- **Revisions and ordering.** Each locked entry is
  `pkg/version#revision%timestamp`; a lockfile can carry two revisions of one
  package (one per version range that needs it), and is "sorted... so latest
  versions and revisions are the ones that are prioritized when resolving"
  (lines 176–187). A lockfile can never force a version the recipe's own
  ranges forbid — it can only pick among what a fresh resolve would already
  allow.
- **Evolution commands.** `conan lock add --requires=<ref>` manually inserts
  an unresolved candidate; `conan install ... --lockfile-out=conan.lock`
  re-resolves and writes back revisions; `conan install ...
  --lockfile-out=conan.lock --lockfile-clean` additionally prunes entries the
  current configuration didn't use; `conan lock create ... --lockfile-out=X
  --lockfile-clean` plus `conan lock merge --lockfile=A --lockfile=B
  --lockfile-out=conan.lock` is the documented CI pattern for combining
  per-configuration locks into one shared lock (lines 201–316) — explicitly
  flagged as "not something that developers should do, only CI scripts."

Version ranges without a lock are a live pattern in the corpus:
`conan-io/conan-center-index@07389b8fa0:.../conanfile.py:64`
(`self.requires("openssl/[>=1.1 <4]")`) — CCI's own template teaches an
unlocked range as normal, because CCI recipes are meant to float; a
*consuming* application repeating that pattern without a `conan.lock` is the
finding (M-M-04).

### 5. `compiler.cppstd`/runtime vs the CMake project's own settings

`CMakeToolchain`'s `cppstd` block "defines `CMAKE_CXX_STANDARD`,
`CMAKE_CXX_EXTENSIONS`" from the profile's `compiler.cppstd`
([`cmaketoolchain.rst@develop2`](https://raw.githubusercontent.com/conan-io/docs/develop2/reference/tools/cmake/cmaketoolchain.rst), line 493); `vs_runtime`
"Defines the `CMAKE_MSVC_RUNTIME_LIBRARY` variable, as a generator expression
for multiple configurations" (line 491). Neither is documented as a *cache*
variable — both are plain `set()` calls inside `conan_toolchain.cmake`, which
CMake processes at the start of the first `project()` call.

**Measured** (CMake 4.4.2, `ocx package exec kitware/cmake:4.4`, ninja
1.13.2, `/opt/zig/zig c++` as `CMAKE_CXX_COMPILER` — scratch project at
`.agents/research/cmake-package-managers/scratch/conan-cmake-integration/`):
a `fake_conan_toolchain.cmake` sets `CMAKE_CXX_STANDARD 17` before `project()`
runs (simulating `conan_toolchain.cmake`); `CMakeLists.txt` then calls
`set(CMAKE_CXX_STANDARD 20)` **after** `project()`, exactly as most real
projects that pin a language standard do. Command:

```
cmake -S proj -B build -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=proj/fake_conan_toolchain.cmake \
  -DCMAKE_CXX_COMPILER=.../zig-cxx-wrapper.sh
```

Output:
```
-- conan_toolchain.cmake: setting CMAKE_CXX_STANDARD to 17 (profile compiler.cppstd=17)
-- Effective CMAKE_CXX_STANDARD=20
```

**No diagnostic, no cache-value conflict, no `-Werror=author`-visible
category fires** — the project's later plain `set()` in the same
directory scope simply wins, silently. This answers the Conan half of
M-L-05: **a `compiler.cppstd`/project mismatch is not checkable at configure
time by any built-in mechanism; the only check is a project-side
`if(DEFINED CMAKE_CXX_STANDARD AND NOT CMAKE_CXX_STANDARD STREQUAL "<expected>")` guard, or `target_compile_features()` instead of the global variable (a
different row, M-E-04) so there is no global variable to fight over.**

MSVC runtime has the same shape for a structural reason, not just precedent:
because `CMAKE_MSVC_RUNTIME_LIBRARY`'s default value is itself a generator
expression (`$<$<CONFIG:Debug>:...>...`, since CMake 3.15/CMP0091), no
configure-time Conan or CMake code can evaluate "what will this actually be
per-config" without re-implementing genex evaluation. This is precisely the
seven-year-old open issue
[cmake-conan#174](https://github.com/conan-io/cmake-conan/issues/174)
(opened 2019-09-04, still `state: open`): "Conan obviously cannot handle
per-target variation, or see targets that aren't defined yet at all... the
new mechanism can (and by default, does) use a generator-expression in its
value, so I'm not sure how conan.cmake should evaluate it." CCI's template
sidesteps the whole problem by reading Conan's own settings instead of
CMake's: `tc.cache_variables["USE_MSVC_RUNTIME_LIBRARY_DLL"] = not
is_msvc_static_runtime(self)` — a Conan-side helper (`is_msvc_static_runtime`)
feeding a project-defined cache variable, never reading
`CMAKE_MSVC_RUNTIME_LIBRARY` back
(`conan-io/conan-center-index@07389b8fa0:.../conanfile.py:90-92`).

### 6. Presets `CMakeToolchain` writes

`cmaketoolchain.rst` states the versions directly: "`CMakePresets.json`... It
currently uses version '3' of the JSON schema" (line 77); "the version schema
of the generated `CMakeUserPresets.json` is '4' and requires CMake >= 3.23"
(lines 128–129); repeated as a note: "schema for the `CMakePresets.json` is 3
(compatible with CMake>=3.21)" (lines 141–144). Preset names default to
`conan-<x>`, controlled by `layout()`'s `self.folders.build_folder_vars`
(lines 95–97).

The skip rule for `CMakeUserPresets.json` is stated in prose ("Conan will skip
the generation of the `CMakeUserPresets.json` if it already exists and was
not generated by Conan", line 135–136) and **measured from source** at the
pinned tag:

```python
# conan-io/conan@2.32.0:conan/tools/cmake/presets.py:307-311
if not os.path.exists(user_presets_path):
    data = {"version": 4, "vendor": {"conan": dict()}}
else:
    data = json.loads(load(user_presets_path))
    if "conan" not in data.get("vendor", {}):
        # The file is not ours, we cannot overwrite it
        return
```

The mechanism is a `vendor.conan` object, not a filename convention or a
hash: any pre-existing `CMakeUserPresets.json` that lacks that key — hand
authored, or generated by a different tool — is left completely alone on
every subsequent `conan install`. `CMakePresets.json` itself (schema 3) is
always regenerated; it is `CMakeUserPresets.json` (schema 4) that carries the
one-time skip check.

### 7. Conan-1 residue

Conan 2's own residue checklist (`from conans import ...`, `conan_basic_setup()`,
`generators = "cmake"`, `cpp_info.names`) is not academic. In the exemplar
corpus fetched 2026-09-26, **`abseil/abseil-cpp`'s live `conanfile.py`** —
one of the corpus's flagship dual-build C++ libraries — is unmigrated Conan 1:

```python
# abseil/abseil-cpp@61d073d671:conanfile.py:1-13,29
from conans import ConanFile, CMake, tools
from conans.errors import ConanInvalidConfiguration
from conans.model.version import Version
...
generators = "cmake"
...
    def build(self):
        tools.replace_in_file("CMakeLists.txt", "project(absl LANGUAGES CXX)",
            "project(absl LANGUAGES CXX)\ninclude(conanbuildinfo.cmake)\nconan_basic_setup()")
```

Abseil's own file-header comment says as much: "Note: Conan is supported on a
best-effort basis. Abseil doesn't use Conan internally, so we won't know if
it stops working." `conans` (no leading `conan.`), `conan_basic_setup()`, and
`include(conanbuildinfo.cmake)` are all Conan-1-only surface area that raises
an import error under a Conan 2 install — this recipe cannot run with a
Conan-2 client at all, and nothing in abseil's CI exercises it (frame's fleet
audit and this program's corpus both found zero Conan tooling on the fleet
side, so this is a pure upstream-repository finding).

Contrast with the same corpus's actually-migrated recipe,
`catchorg/Catch2@222e233903:conanfile.py`: `from conan import ConanFile`
(singular, `conan.` not `conans.`), `conan.tools.cmake.cmake_layout`,
`self.cpp_info.set_property("cmake_target_name", ...)` (not the Conan-1
`.names` dict), and `rmdir(self, os.path.join(self.package_folder, "lib",
"cmake"))` so Conan's own generated files are the only CMake package
description a consumer sees.

### 8. Workspaces

Changelog **2.31.0** (23-Jul-2026): "Get Workspace feature out of incubating"
(PR #20202, `changelog.rst` line 64, inside the section spanning lines
61–93). But `incubating.rst@develop2` (fetched 2026-09-26) still reads:
"Workspaces are not incubating anymore, but **generally available as
experimental**." That is a genuinely contradictory-sounding phrase in Conan's
own words, not a misreading — it means "no longer gated behind an opt-in
flag" (GA in the sense of being on by default and documented) while the
feature area itself keeps evolving fast: the same changelog range shows
`conanws.py`'s `get_ref(folder)` (2.31.0), `python_requires` support limited
to `conanws.yml` only (2.30.0), and a lockfile-interaction bugfix for
`workspace install/build --lockfile-partial` (2.30.0) landing in the same
three months. Treat "GA" as "no flag required, syntax may still move," not
"stable API."

### 9. `conan graph explain`/`info` for triage

`conan graph` groups five read-only subcommands
([`reference/commands/graph.rst@develop2`](https://raw.githubusercontent.com/conan-io/docs/develop2/reference/commands/graph.rst)): `info` ("Computes a
dependency graph and displays information about it"), `build-order`,
`build-order-merge`, `explain` ("Explain what is wrong with the dependency
graph, showing missing binaries, closest alternatives, and why they do not
match"), and `outdated`. `graph info` is the general-purpose inspector (JSON,
HTML with cycle highlighting since 2.27.0, dot); `graph explain` is
specifically for the "why did my build fail to find/build a binary" case —
the two are complementary, not alternatives: reach for `explain` when a
`conan install` reports a missing binary, `info` for auditing the resolved
graph shape (duplicate versions, `provides` conflicts, transitive requires).
Both honour an implicit `conan.lock` exactly like `install`
(`lockfiles.rst` line 113).

## Normative guidance candidates

1. **A consumer of a Conan-packaged dependency uses `CMakeDeps` +
   `CMakeToolchain` as the default; adopt `CMakeConfigDeps` only with an
   explicit acknowledgement that it is experimental at 2.32.0.**
   Rationale: `CMakeConfigDeps`'s own reference page still ships the
   experimental warning include; the "GA" claim lives only in
   `incubating.rst`, contradicted by the generator's own doc and by the
   changelog. Verify: `rg -n -e 'generators = .*CMakeConfigDeps' -e 'CMakeConfigDeps\(self\)' -g 'conanfile.*' <dir>` — a hit with no adjacent
   comment citing the experimental status is a finding. Version floor: Conan
   ≥2.25.0 for the generator to exist at all.
2. **Never pair `CMakeConfigDeps` with `find_package(... MODULE)`.**
   Rationale: `CMakeConfigDeps` "will not generate `Find*.cmake` find
   modules, and support for it is not planned" — a hard-coded literal in a
   docs page fetched 2026-09-26. Verify: if a conanfile sets
   `generators = "CMakeConfigDeps"` (or calls it in `generate()`), then
   `rg -n -e 'find_package\([A-Za-z0-9_]+ MODULE' -g CMakeLists.txt -g '*.cmake' <dir>` — any hit for a Conan-provided package name is a finding.
   Empty output = pass. Version floor: Conan ≥2.25.0.
3. **`conan install` explicit, then `cmake --preset <name>`, is the default
   flow; the cmake-conan provider (`CMAKE_PROJECT_TOP_LEVEL_INCLUDES`) is an
   opt-in for IDE-driven or single-command scenarios only, and its five
   documented limits must be re-checked before adopting it.** Rationale:
   both Conan's own integration page and cmake-conan's README say so in
   their own words. Verify (reading heuristic): grep the top-level
   `CMakeLists.txt`/CI for `CMAKE_PROJECT_TOP_LEVEL_INCLUDES.*conan_provider`
   — if present, confirm `CMakeConfigDeps` (not `CMakeDeps`) is the
   generator in use and that `CMAKE_BUILD_TYPE` is always set for
   single-config generators. Version floor: cmake-conan `develop2` (CMake
   ≥3.24 prerequisite per its README).
4. **`build_requires` is a P0 finding wherever it appears in a conanfile
   authored or maintained today; the replacement is `tool_requires`.**
   Rationale: deprecated in Conan 2.28.0 (2026-04-28), a dated fact, not a
   style preference. Verify: `rg -n build_requires -g 'conanfile.*' <dir>` —
   any hit is a finding (empty = pass). Version floor: none — flag it at any
   Conan 2 floor, since the replacement has existed since Conan 2.0.
5. **A version range (`pkg/[>=X <Y]`) in a *consuming* project's
   `requires`/`tool_requires` must be paired with a committed `conan.lock`
   used with an explicit `--lockfile=conan.lock` in CI.** Rationale: ranges
   resolve to "whatever is newest today" without a lock; implicit pickup
   from the working directory is real but Conan's own tutorial recommends
   making it explicit in CI. Verify: `rg -n -e '\[.*[<>=]' -g 'conanfile.*' <dir>` for ranges, then check for a tracked `conan.lock` and a
   `--lockfile=` flag in the CI invocation — range present, either missing =
   finding. Version floor: none.
6. **Never assume a `CMAKE_CXX_STANDARD`/`compiler.cppstd` mismatch will be
   diagnosed; a library that must pin a standard states it via
   `target_compile_features(<t> PUBLIC cxx_std_NN)`, never a bare global
   `set(CMAKE_CXX_STANDARD ...)` after `project()`, if it also expects to be
   consumed through `CMakeToolchain`.** Rationale: measured on CMake 4.4.2 —
   the later plain `set()` silently wins over the toolchain-injected value,
   with zero diagnostic at any warning level. Verify: reading heuristic —
   `rg -n 'set\(CMAKE_CXX_STANDARD' -g CMakeLists.txt <dir>` after
   `project(...)` in the same file, cross-checked against whether the
   project is also built through a Conan profile; a hit in an installable
   library's own `CMakeLists.txt` is a finding (M-E-04 owns the general
   rule; this is its Conan-specific trigger). Version floor: CMake ≥3.25 (the
   floor this rule set assumes); the behaviour is a language-scoping fact,
   not version-gated.
7. **A CI job must never assume `MSVC_RUNTIME_LIBRARY` agreement between a
   Conan profile and the CMake project is checkable; on Windows, this is a
   documented, seven-year-old open gap, not a rule this program can close.**
   Rationale: [cmake-conan#174](https://github.com/conan-io/cmake-conan/issues/174), open since 2019, unresolved because the CMake-side
   default is itself a generator expression. Verify: named reading
   heuristic — a project relying on `is_msvc_static_runtime(self)` (Conan
   side) to drive its own `CMAKE_MSVC_RUNTIME_LIBRARY`/cache variable, as
   CCI's template does, is the working pattern; a project instead trying to
   *read back* `CMAKE_MSVC_RUNTIME_LIBRARY` from CMake into Conan settings is
   the anti-pattern. No command settles this generically. Version floor:
   CMake ≥3.15 (CMP0091) for the variable to exist as a genex at all.
8. **A hand-written `CMakeUserPresets.json` is safe from Conan overwrite only
   if it lacks a `vendor.conan` key it did not itself add; do not manually
   add that key to "adopt" a file Conan should regenerate.** Rationale:
   measured from `conan/tools/cmake/presets.py@2.32.0` — the skip check is
   exactly `"conan" not in data.get("vendor", {})`. Verify: `python3 -c "import json,sys; d=json.load(open('CMakeUserPresets.json')); sys.exit(0 if 'conan' in d.get('vendor', {}) else 1)"` — exit 0 means Conan considers the file
   its own and will keep rewriting it; exit 1 means it is genuinely
   hand-owned. Version floor: current `CMakeToolchain` behaviour, unchanged
   across the 2.13–2.32 range checked.
9. **Recognise Conan-1 residue as a P0, not a lint nit: `from conans import`,
   `conan_basic_setup()`, `include(conanbuildinfo.cmake)`, or a bare
   `generators = "cmake"` string.** Rationale: this is not hypothetical —
   `abseil/abseil-cpp`'s own conanfile is exactly this, and it cannot run
   under a Conan 2 client at all. Verify:
   `rg -n -e 'from conans import' -e 'conan_basic_setup' -e 'conanbuildinfo.cmake' -e '\bcpp_info\.names\b' -g 'conanfile.py' <dir>` — any hit is a finding (empty = pass).
   Version floor: none — this is a Conan-1-vs-2 binary check.
10. **Treat Conan Workspaces (`conanws.yml`/`conanws.py`) as usable without
    an opt-in flag since 2.31.0, but not as a frozen API — read the
    changelog for the exact minor before depending on a specific
    `conanws.py` hook.** Rationale: Conan's own docs call the feature "GA as
    experimental" in the same sentence; three consecutive minors (2.29–2.31)
    changed `conanws.py`'s contract. Verify: reading heuristic — check the
    changelog range between the project's declared minimum Conan version and
    2.32.0 for `workspace`/`conanws` entries before trusting a specific hook
    signature. Version floor: 2.31.0 for "no incubating flag needed."

## AI-agent angle

- **Writes Conan-1 syntax as if it were current.** `from conans import
  ConanFile`, `generators = "cmake"`, `self.copy(...)` in `package()`,
  `conan_basic_setup()`, `cpp_info.names[...]` — all training-data-plausible
  because real, currently-hosted repositories (abseil, this dive found)
  still contain exactly this code. Mechanical check: candidate 9's grep.
- **Assumes `CMakeConfigDeps` is the modern default and reaches for it
  first**, because "newer generator with more features" reads as "the one to
  use." It is still experimental at 2.32.0 and permanently cannot emit
  `Find*.cmake`. Mechanical check: candidate 1 and 2's greps; also check the
  conanfile for a comment acknowledging the experimental status.
- **Recommends the cmake-conan provider as the default integration path**
  because "one CMake invocation, no extra step" sounds like the better
  developer experience an LLM optimizes for. Conan's own docs invert this
  priority. Mechanical check: candidate 3's grep for
  `CMAKE_PROJECT_TOP_LEVEL_INCLUDES.*conan_provider` — presence should
  trigger a review of the five documented limits, not silent approval.
- **Suggests `build_requires` for a tool dependency** because it is the
  older, more training-frequent term. Mechanical check: candidate 4's grep.
- **Treats a Conan profile's `compiler.cppstd` as authoritative and assumes
  CMake will "obviously" respect it**, or conversely assumes CMake's
  `CMAKE_CXX_STANDARD` will "obviously" be validated against the profile.
  Neither happens; this dive measured zero diagnostic either way. Mechanical
  check: candidate 6's reading heuristic — a plain `set(CMAKE_CXX_STANDARD)`
  after `project()` in a library meant to be Conan-consumed is the trap.
- **Assumes a lockfile is either always used or never used**, missing that
  `conan.lock` is picked up *implicitly* by filename in the working
  directory — an LLM asked to "make this build reproducible" may add a
  `conan.lock` file without also adding `--lockfile=conan.lock` to CI, or may
  not realize an *existing* `conan.lock` is silently already constraining
  every `conan install` in that directory. Mechanical check: `ls conan.lock`
  plus grep CI for an explicit `--lockfile=` flag.
- **Hallucinates a `cmake-lint`/schema-validation step for `CMakePresets.json`
  version 3 vs `CMakeUserPresets.json` version 4** as if they must match —
  they are deliberately different schema versions from two different Conan
  code paths (`presets.py` lines 115 vs 306), and this is correct, not a bug
  to "fix."

## Contested / evolving

- **`CMakeConfigDeps`'s status is a live internal contradiction inside
  Conan's own docs, not a settled fact.** `incubating.rst` says GA;
  `cmakeconfigdeps.rst` still ships the experimental banner. Trending: the
  feature keeps gaining real fixes every 1–2 releases (2.25.0 through
  2.32.0, ~15 distinct `CMakeConfigDeps` changelog entries in that range,
  `grep`-counted against `changelog-2.13-2.32.rst`) with no formal
  "stable" changelog line yet as of 2026-09-26. Watch the next Conan minor
  for a changelog entry that actually says "stable" or "no longer
  experimental," not just "GA," before upgrading this rule's default.
- **Conan Workspaces' "GA as experimental" phrasing is Conan choosing to keep
  moving the ground under a feature it also calls done.** Three consecutive
  minors changed the `conanws.py` contract (2.29–2.31). Trending: toward
  stabilization, but not there yet as of 2.32.0.
- **The MSVC-runtime generator-expression gap ([cmake-conan#174](https://github.com/conan-io/cmake-conan/issues/174)) has been open
  for seven years with no active PR.** This is not "evolving" so much as
  "a structural limit both projects have made peace with" — CCI's
  documented workaround (drive the CMake side from Conan settings, never the
  reverse) is the de facto resolution, and no rule should promise a future
  fix.
- **`cmake-conan`'s own stability disclaimer is unchanged across releases**
  ("even if not released as 1.0 yet") — it is not drifting toward GA
  language the way `CMakeConfigDeps` and Workspaces are; treat it as a
  permanently-secondary path, not a beta on its way to primary.
