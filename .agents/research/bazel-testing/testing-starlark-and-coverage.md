## Summary

- `unittest.make()` tests pure Starlark functions; `analysistest.make()` tests a rule's analysis-phase behavior (providers, actions) against a real `target_under_test`. Neither official doc mentions testing a `repository_rule` or `module_extension` implementation directly — [bazel.build/rules/testing](https://bazel.build/rules/testing) is silent on both, and [bazel.build/external/extension](https://bazel.build/external/extension) gives exactly one sentence: run `bazel mod deps` to force real evaluation. Treat that silence as a gap, not permission to skip.
- `analysistest.make(expect_failure=True)` works by setting `//command_line_option:allow_analysis_failures=True` via an `analysis_test_transition` — read straight from [bazel-skylib's `unittest.bzl` source](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L280-L281).
- `asserts.expect_failure`'s vacuous-pass trap is a one-line mechanism, not folklore: it does `actual_errors.find(expected_failure_msg) < 0` against the *concatenated* `AnalysisFailureInfo` cause messages ([source, L541-560](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L541-L560)). A Starlark traceback echoes each frame's source line, so a fragment that also appears at the test's own call site matches the echo and the guard passes even when the code under test never ran the failing branch.
- A `repository_rule`'s `_impl` function is a plain Starlark function — it can be `unittest.make()`-tested directly with a hand-rolled fake `repository_ctx` struct, exactly the same technique already used for pure helpers. `analysistest` cannot reach it: `repository_rule` implementations run in the loading/fetch phase and produce a repository, not an analyzable `Target` with providers, so there is no `target_under_test` to point at.
- `module_extension` orchestration does not transfer as cleanly: its `_impl` body calls repository-rule symbols as its primary side effect, and Bazel's own doc offers no offline-fake technique for that half — only `bazel mod deps`, which evaluates for real.
- `bazel coverage`'s `--instrumentation_filter` default is `-/javatests[/:],-/test/java[/:]` — two hardcoded Java exclusions, nothing vendor-aware ([command-line reference](https://bazel.build/reference/command-line-reference#flag--instrumentation_filter)). Any non-Java repo with vendored/third-party deps gets zero default protection from instrumenting them.
- `--combined_report` flipped its own default from `none` to `lcov` in [commit b6fd304b](https://github.com/bazelbuild/bazel/commit/b6fd304b) ("`RELNOTES[INC]`"), landing in **Bazel 9.0.0** — verified directly against `BazelCoverageReportModule.java` at the `8.8.0` tag (`defaultValue = "none"`) versus `9.2.0` (`defaultValue = "lcov"`). A repo whose CI matrix spans both majors gets a combined LCOV report on the 9.x leg and none on the 8.x leg unless `--combined_report=lcov` is set explicitly.
- `--enable_runfiles` defaults to `"auto"`: off on Windows, on everywhere else ([command-line reference](https://bazel.build/reference/command-line-reference#flag--enable_runfiles)). Any coverage collector that reads sources back through the test's runfiles tree — confirmed for JS by rules_js — reports empty coverage on Windows unless this flag is passed.
- rules_js's own troubleshooting doc names the exact failure: `ERROR: ...: coverage report generator '...' not found; code coverage requires a runfiles tree` — and the test itself still **passes** ([rules_js docs/troubleshooting.md](https://github.com/aspect-build/rules_js/blob/v3.4.1/docs/troubleshooting.md#coverage-requires-a-runfiles-tree)). Coverage failure is silent with respect to test-pass/fail exit status.
- Coverage runs against the test's own `size`/`timeout` budget, not a separate one: rules_js states plainly that generating the lcov report "consumes the target's own `timeout`/`size` budget" and that conversion time is proportional to the number of instrumented files ([same doc](https://github.com/aspect-build/rules_js/blob/v3.4.1/docs/troubleshooting.md#coverage-runs-count-against-the-tests-timeout)). Bazel's own `test-encyclopedia.md` says nothing about this at all — it is silent on coverage entirely.
- rules_rust's own recommended fix for the vendored-dependency instrumentation-filter gap is `coverage --instrumentation_filter=^//` (optionally `,-^//third_party`) in `.bazelrc` — read from [`docs/src/coverage.md` at the pinned `0.74.0` tag](https://github.com/bazelbuild/rules_rust/blob/0.74.0/docs/src/coverage.md).
- `rust_test(crate = ...)` compiles the library into the test binary as one unit, so library coverage shows up without `--instrument_test_targets` (which defaults `false`) — but so does `#[cfg(test)]` code, a documented inconsistency with the general Bazel convention (same rules_rust doc).
- `analysistest`'s failure-testing shape requires the target-under-test be tagged `manual`, or `bazel build //...`/`:all` builds the intentionally-failing target and breaks the build ([bazel.build/rules/testing, "Failure testing"](https://bazel.build/rules/testing#failure-testing)).
- Data-driven test generation is a documented `bazel-skylib` idiom, not a fleet invention: `unittest.suite()` accepts `partial.make(rule, **kwargs)` entries alongside bare rules ([source, L306-338](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L306-L338)) — looping a dict of `{case: expected}` into `partial.make()` calls is the natural extension, and `rules_ocx` does exactly this for 34 of its 76 targets.
- `rules_ocx` measures the gap this dive settles: 76 `analysistest`/`unittest` targets across five files, zero `analysistest.make()` call against any of its 4 `repository_rule` implementations — the two `analysistest.make()` calls that exist target hand-written fixture rules built solely to fail, not the production repository rules (`ocx/tests/launcher_test.bzl:1169,1299`).
- The offline-fake technique generalizes: `rules_ocx`'s three hand-rolled `repository_ctx` fakes (`_fs_ctx`, `_replay_ctx`, `_env_ctx`, `launcher_test.bzl:40-197`) duck-type only the methods each tested function calls — a filesystem-membership predicate, a scripted-exit-code sequencer, and an attribute/getenv/watch recorder. None of them are ocx-specific.
- `rules_testing` (bazelbuild's own newer Starlark test framework, current `v0.9.0`, 2025-08-06) offers Truth-style fluent matchers over the same `AnalysisTestResultInfo`/`analysis_test_transition` machinery — it is a nicer analysistest, not a fix for the repository-rule/module-extension testing gap.
- `rules_bazel_integration_test` (bazel-contrib, active as of `v0.37.1`, 2026-01-31) packages the "spin up a real nested workspace and run a real Bazel subprocess" technique first described by [Tweag in 2022](https://www.tweag.io/blog/2022-10-06-bazel-rules-to-test-bazel-rules/) — this is the modern name for what `rules_ocx`'s live-registry `examples/*` do by hand, and it is the only technique that can exercise a `module_extension`'s actual repository-rule invocations for real.

## Findings

### 1. `unittest` vs `analysistest`: the doc-blessed split

[bazel.build/rules/testing](https://bazel.build/rules/testing) draws the line explicitly: `unittest.bzl`'s `analysistest` checks "the analysis-time behavior of rules, such as their actions and providers"; plain `unittest` is for "utility functions that are neither macros nor rule implementations," and its `unittest.suite()` convenience function removes the boilerplate `analysistest` still needs. A fourth, smaller module, `loadingtest`, exists in the same file for macro/`native.*` loading-phase behavior ([`unittest_doc.md`](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/docs/unittest_doc.md#loadingtestequals)) — out of scope here (macros are `bazel-starlark-and-build`'s territory) but worth knowing it exists so nobody reaches for `analysistest` to test a macro.

The mechanical difference that matters for choosing correctly: `analysistest.make()` always injects a `target_under_test` attribute (`attr.label(aspects=[_action_retrieving_aspect], mandatory=True, ...)`) and marks the generated rule `analysis_test = True` ([source, L282-297](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L282-L297)). `unittest.make()` injects neither — it is `rule(impl, test=True, _skylark_testable=True)` with no target dependency at all ([L188-198](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L188-L198)). If the thing under test has no `Target` to depend on, `analysistest` is the wrong tool by construction — this is the fact that later settles the repository-rule question (Finding 4).

`analysistest` also caps certain features "to verifying targets with a maximum number of transitive dependencies (currently 500)" for performance ([bazel.build/rules/testing](https://bazel.build/rules/testing#testing-rules)) — a concrete number worth knowing before building a large fixture graph under one test.

### 2. The `expect_failure` vacuous-pass trap, from the source

`.claude/rules/starlark.md:34-39` in `rules_ocx` names this trap; wave-2 dive `bazel-starlark-and-build/starlark-dialect-and-determinism-traps` documents the general Starlark-dialect angle — cited here, not re-derived, because the mechanism is testing-specific and worth grounding independently in `unittest.bzl`'s own source:

```python
# bazel-skylib lib/unittest.bzl, _expect_failure (asserts.expect_failure)
def _expect_failure(env, expected_failure_msg = ""):
    dep = _target_under_test(env)
    if AnalysisFailureInfo in dep:
        actual_errors = ""
        for cause in dep[AnalysisFailureInfo].causes.to_list():
            actual_errors += cause.message + "\n"
        if actual_errors.find(expected_failure_msg) < 0:
            _fail(env, "Expected errors to contain '%s' but did not..." % expected_failure_msg)
    else:
        _fail(env, "Expected failure of target_under_test, but found success")
```
([source, L541-560](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L541-L560))

The check is a plain substring search (`.find(...) < 0`) against every `cause.message` concatenated together. A Starlark `fail()` traceback echoes the *source line* of every frame that led to it — so if the expected fragment also appears, verbatim, anywhere in the test's own call-site source (a case label, a variable name, a comment on the same physical statement Bazel echoes), the traceback's own echo satisfies the substring check independent of whether the guarded code path ever ran. `rules_ocx` neutralizes this by holding the fragment in a module-level constant the call site cannot spell:

```python
# ocx/tests/launcher_test.bzl:1153-1154
# Held in a constant the call site cannot spell (.claude/rules/starlark.md).
_DRIFT_HINT = "it pins the ocx version"
...
asserts.expect_failure(env, _DRIFT_HINT)   # launcher_test.bzl:1169
```

and the same for a second guard family (`_CALLSITE_HINT`, `launcher_test.bzl:1173-1176,1299`). Both are the two `analysistest.make()` calls the brief's fleet evidence names — targeting hand-written fixture rules (`_bad_closure_report`, `_guard`) built to fail, never a production repository rule.

### 3. Data-driven test generation: dict literals + `partial.make()`

`unittest.suite()`'s own doc names the mechanism: pass `partial.make(your_test, **kwargs)` instead of a bare test rule when a case needs arguments ([source, L306-338](https://github.com/bazelbuild/bazel-skylib/blob/1.9.0/lib/unittest.bzl#L306-L338)). Looping a dict of cases into that call is the natural extension bazel-skylib's own doc doesn't spell out but does not forbid:

```python
# ocx/tests/launcher_test.bzl:1579-1585 (34+28 cases generated this way)
for case, expected in _GUARD_CASES.items():
    subject = "{}_guard_{}".format(name, case)
    _guard(name = subject, case = case, tags = ["manual"])
    guards.append(partial.make(
        guard_test,
        target_under_test = ":" + subject,
        expected = expected,
    ))
...
unittest.suite(name, ..., *guards)
```

Each fixture target under the loop carries `tags = ["manual"]` (Finding 1's constraint) and a name derived from the dict key, so a new failure case is one dict entry, not one new `.bzl` function + one new BUILD-visible target declared by hand.

### 4. Testing a `repository_rule` or `module_extension`: the documented gap

This is the surprise the brief asks to chase, and it resolves to a structural fact rather than an opinion. `analysistest.make()` requires a `target_under_test` — a `Target` produced by a `rule()` and inspectable for providers/actions during the analysis phase. A `repository_rule`'s `_impl` function runs during the *loading* phase (repository fetch), and its product is a repository — files on disk that later loading/analysis reads — not a `Target` with providers of its own. There is nothing for `analysistest`'s aspect-based `target_under_test` machinery to attach to. [bazel.build/rules/testing](https://bazel.build/rules/testing) confirms this by omission: the word "repository" does not appear on the page at all.

[bazel.build/external/extension](https://bazel.build/external/extension) is equally sparse for `module_extension`, offering one line: "While testing a module extension, `bazel mod deps` can be useful as it unconditionally evaluates all module extensions" — a real-evaluation, network-capable command, not an offline unit-test technique. The same page states the impl function "calls repo rules to generate repos," which is the operative difference from a `repository_rule` impl: invoking a `repository_rule`-produced symbol (e.g. `ocx_download(name=..., version=...)`) is Bazel's own repo-instantiation mechanism, not a plain function call — nothing in the corpus this dive read confirms it can be exercised outside real extension evaluation, so that half of a `module_extension`'s logic is presented here as genuinely unresolved (see Contested/evolving), not as solved by the same technique.

A `repository_rule`'s `_impl` function has no such obstacle. It is an ordinary top-level Starlark function that receives one argument (`ctx`) and calls whatever methods it needs on it (`ctx.download`, `ctx.getenv`, `ctx.watch`, `ctx.file`, `ctx.os`, ...). Starlark has no static ctx type — any struct exposing the same method names works identically, offline, with zero network and zero sandboxing. `rules_ocx`'s own `_ocx_download_impl` (`ocx/private/download.bzl:27-58`) never calls another repository-rule symbol; it only calls `ctx.*` methods plus pure helper functions already proven by unit test (`host_info`, `select_release`, `artifact_url`, `manifest_sha256`, `archive_type`, `min_version_error`). Every one of those `ctx.*` methods is already faked, individually, by the existing `_env_ctx`/`_fs_ctx` fakes for other call sites in the same test file — the technique is present, it is simply not yet pointed at the four `_impl` functions themselves (see Decision 1).

### 5. Hand-rolled ctx fakes: the portable offline-test technique

`rules_ocx` ships three fakes in `ocx/tests/launcher_test.bzl:40-197`, each duck-typing only the surface the tested code calls:

| Fake | Faked surface | What it proves |
|---|---|---|
| `_fs_ctx(files, dirs, listing)` | `ctx.path(p).exists/is_dir/readdir()`, one `ctx.execute()` shape | Filesystem discovery helpers (Windows `readdir` scan and the POSIX `ctx.execute` scan) without touching a real disk |
| `_replay_ctx(codes, calls, sleeps)` | `ctx.execute()` returning a scripted sequence of exit codes, tracking call count | Retry/backoff logic (`run_ocx`'s retry loop) without a real subprocess |
| `_env_ctx(env, attr..., sigstore_trusted_root)` | `ctx.getenv`, `ctx.path`, `ctx.watch` (recording every watched path), `ctx.read`, `ctx.file`, `ctx.attr` | Environment-forwarding and config-staging logic, including the `watch()` contract itself — since Bazel cannot invalidate on a file no rule ever declared reading, the fake's `watched` list is a first-class assertion target |

None import anything ocx-specific; all three are `repository_ctx`-shaped structs built from `struct(...)` and closures. This is the "written portably enough to lift" pattern Decision 2 formalizes.

### 6. Coverage instrumentation: flags, defaults, and the Bazel 8→9 flip

Four flags govern what gets instrumented, read verbatim from the [command-line reference](https://bazel.build/reference/command-line-reference) (fetched 2026-09-05):

| Flag | Default | What it does |
|---|---|---|
| `--collect_code_coverage` | `false` | The underlying switch; "Usually this option should not be specified directly — `bazel coverage` command should be used instead." |
| `--instrumentation_filter` | `"-/javatests[/:],-/test/java[/:]"` | Regex allow/deny list (leading `-` excludes) for which targets get instrumented |
| `--instrument_test_targets` | `false` | Whether *test* rules themselves (not just their deps) are instrumented |
| `--combined_report` | **`lcov` (Bazel 9.0+) / `none` (Bazel 8.x)** | Whether a merged report is produced at `_coverage/_coverage_report.dat` |

The `--combined_report` default change is version-exact and independently verified against source, not inferred from prose:

```
$ curl -sL .../bazel/8.8.0/.../BazelCoverageReportModule.java | grep defaultValue
    defaultValue = "none",
$ curl -sL .../bazel/9.2.0/.../BazelCoverageReportModule.java | grep defaultValue
    defaultValue = "lcov",
```

The commit is [b6fd304b](https://github.com/bazelbuild/bazel/commit/b6fd304b), dated 2025-06-18, with `RELNOTES[INC]: --combined_report now defaults to lcov (was: none)`, closing [bazelbuild/bazel#26328](https://github.com/bazelbuild/bazel/issues/26328). It shipped in the **9.0.0** release (2026-01-20 per the frame), not any 8.x patch — 8.8.0, the current Maintenance-line release, still defaults `none`. rules_rust's own current docs already assume the Bazel-9 behavior ("`--combined_report=lcov`: Produce a combined LCOV report (set by default with `bazel coverage`)" — [`coverage.md`](https://github.com/bazelbuild/rules_rust/blob/0.74.0/docs/src/coverage.md)), which is only true on the majors where it actually is.

`--instrumentation_filter`'s default excludes two hardcoded Java-ecosystem paths and nothing else — there is no generic "vendor" or "third_party" concept baked into Bazel itself. rules_rust's own recommendation for the vendored-dependency case:

```text
# .bazelrc
coverage --instrumentation_filter=^//
coverage --instrumentation_filter=^//,-^//third_party
```

restricting to workspace-rooted labels (`^//`) and optionally excluding a vendor subtree. This is the concrete shape the brief asks for; it generalizes beyond Rust since `--instrumentation_filter` is a core Bazel flag, not ruleset-specific.

### 7. Coverage needs a runfiles tree — and Windows fails silently without one

Bazel's own [`configure/coverage.md`](https://github.com/bazelbuild/bazel/blob/master/site/en/configure/coverage.md) says nothing about runfiles or Windows at all — it covers C++, Java, and points to rules_python's own docs for Python, and is silent on JS/TS and Rust entirely. The runfiles/Windows interaction is documented only at the ruleset level, exactly as the brief anticipated:

> "The reporter maps V8 coverage data back onto sources through the test's runfiles, so a target built without a runfiles tree (`enable_runfiles = False`, which is the default on Windows without `--enable_runfiles`) reports empty coverage and logs
> `ERROR: ...: coverage report generator '...' not found; code coverage requires a runfiles tree`
> The test itself still passes; enable runfiles to collect coverage for it."
> — [rules_js `docs/troubleshooting.md`, "Coverage requires a runfiles tree"](https://github.com/aspect-build/rules_js/blob/v3.4.1/docs/troubleshooting.md#coverage-requires-a-runfiles-tree)

The load-bearing flag is `--enable_runfiles`, default `"auto"` — "off on Windows, on on other platforms" ([command-line reference](https://bazel.build/reference/command-line-reference#flag--enable_runfiles)). The failure is silent with respect to `bazel test`'s own exit status: the test target still reports PASS, only the coverage artifact is empty. rules_rust's own `coverage.md` (fetched in full, §6 above) makes no mention of runfiles or Windows at all — this dive can confirm the JS case directly from the ruleset's own docs and can only flag Rust/Python as unconfirmed (M-E-13 stays open for those two, matching the map's own deferral note).

A second, adjacent silent-empty-coverage signal, general to any language: `WARNING: no coverage report was generated in the test action, reporting empty coverage.` — rules_js's own doc names two causes: nothing was instrumented (check `--instrumentation_filter`/`--instrument_test_targets`), or a custom test rule reused only part of the coverage support. Neither is Windows-specific, but both share the same "test still passes, only the report is empty" shape.

### 8. Coverage counts against the test's own size/timeout budget

Bazel's `test-encyclopedia.md` (fetched in full) contains zero mentions of `coverage` — the general test contract is silent on this interaction; it is documented only per-ruleset. rules_js states it plainly:

> "Because the report is produced by the test itself, generating it consumes the target's own `timeout`/`size` budget. Converting V8 coverage to lcov takes time proportional to the number of instrumented files, so a test that sits near its timeout under `bazel test` may need a larger `size` or `timeout` to pass under `bazel coverage`."
> — [rules_js `docs/troubleshooting.md`](https://github.com/aspect-build/rules_js/blob/v3.4.1/docs/troubleshooting.md#coverage-runs-count-against-the-tests-timeout)

Two Bazel-level flags govern the post-processing shape and both default `true` as of 2026-09-05: `--experimental_split_coverage_postprocessing` ("Bazel will run coverage postprocessing for test in a new spawn") and `--experimental_fetch_all_coverage_outputs` ("Bazel fetches the entire coverage data directory for each test during a coverage run") — both from the [command-line reference](https://bazel.build/reference/command-line-reference). rules_js names the first as "required for remote execution" alongside the second; since both already default `true` locally, the practical exposure is remote-execution-specific, which does not apply to this fleet (RBE is structurally out of reach for `rules_ocx` per the map's Conflict 10).

### 9. Emerging alternatives: `rules_testing` and `rules_bazel_integration_test`

[`bazelbuild/rules_testing`](https://github.com/bazelbuild/rules_testing) (current `v0.9.0`, 2025-08-06 — no newer release as of 2026-09-05) wraps the identical `analysistest`/`AnalysisFailureInfo`/`analysis_test_transition` machinery behind a Truth-style fluent `env.expect` API ([`lib/private/analysis_test.bzl`](https://github.com/bazelbuild/rules_testing/blob/v0.9.0/lib/private/analysis_test.bzl)) — confirmed by reading its source, not asserted. It is declared as a `dev_dependency` in `bazelbuild/bazel`, `bazel-skylib`, `rules_cc`, and `rules_java`'s own `MODULE.bazel` files (measured via GitHub code search, 2026-09-05) — real, growing adoption inside the Bazel org itself — but it does not touch the repository-rule/module-extension gap: it is still analysis-phase only.

[`bazel-contrib/rules_bazel_integration_test`](https://github.com/bazel-contrib/rules_bazel_integration_test) (`v0.37.1`, released 2026-01-31) is the actively-maintained, packaged form of the technique [Tweag described in 2022](https://www.tweag.io/blog/2022-10-06-bazel-rules-to-test-bazel-rules/): spin up a real nested workspace, pin its cache path to avoid rebuilding toolchains per test run, and execute a real Bazel subprocess against it. This is the only technique in this corpus that can exercise a `module_extension`'s actual repository-rule invocations end to end — at real cost: 25-30 seconds per test (Tweag's own measurement), weaker hermeticity (shared cache, real file I/O), and a required `exclusive` tag to avoid concurrent-cache corruption. It is the named, current form of what `rules_ocx`'s own `examples/*` directories already do by hand, uncached, against a live registry.

## Decisions

**Decision 1 — the coverage bar for a ruleset's own public surface is not "give the repository-rule impl an `analysistest`."** That framing is a category error: `analysistest` cannot target a `repository_rule` or `module_extension` implementation at all (Finding 4 — no `Target`, no providers, wrong phase). The bar this dive sets instead: **every `repository_rule` `_impl` function must have a `unittest.make()`-based orchestration test that calls it directly with a hand-rolled ctx fake and asserts on the fake's recorded side effects** (which paths were watched, in what order; which URL/sha256 was downloaded; which files were written) — the same technique already proven for pure helpers, pointed one level up at the entry point itself. Evidence: `bazel.build/rules/testing` and `bazel.build/external/extension` both confirm no first-party alternative exists; `rules_ocx`'s own `_ocx_download_impl` makes zero calls to other repository-rule symbols (`download.bzl:27-58`), so nothing structurally blocks the technique — it is simply unwritten (Smell #1, `starlark-code-shape.md`). **Assumption named**: this holds only when the `_impl` function makes no nested repository-rule/module-extension calls of its own — true for all four of `rules_ocx`'s repository rules today. A `module_extension`'s `_impl` does not clear this bar the same way (Finding 4's second half) — its repo-rule-invocation core stays covered only by `bazel mod deps` and/or a real integration test (Finding 9), and the shipped rule states that asymmetry explicitly rather than papering over it with one "have an analysistest" MUST that cannot be satisfied.

**Decision 2 — the offline-test pattern is portable enough to lift, and here is its shape.** Three fake-ctx primitives cover the `repository_ctx` surface most repository rules touch: (a) a filesystem-membership/listing predicate (`_fs_ctx`), (b) a scripted-return-value sequencer with call-count tracking, for retry/backoff logic (`_replay_ctx`), and (c) an attribute/env/watch/read/file recorder (`_env_ctx`). Layered on top: a private `visibility()` grant naming the test package so the `_impl` symbol is `load()`-able from the test file (Starlark's leading-underscore convention is not a cross-file privacy boundary — only `visibility()` gates which packages may load anything from a `.bzl` file at all), a dict-of-cases-plus-`partial.make()` generator for repetitive guard/error-path tests, and the vacuous-pass-trap discipline (Finding 2) applied to every `expect_failure` case. **Assumption named**: portability holds for `repository_ctx`-shaped fakes; a `module_ctx` fake would need its own surface (`module_ctx.modules`, `.tags`, `.extension_metadata`) and, per Decision 1, does not close the repo-rule-invocation half of module-extension testing regardless of how faithfully it's built.

## Normative guidance candidates

1. **Use `unittest.make()` for pure Starlark functions; use `analysistest.make()` only when a real `Target` with providers exists to depend on.** *Rationale*: `analysistest` always injects a mandatory `target_under_test` label — pointing it at anything else is a type error waiting to surface at build time, not analysis time. *Verify*: for every `analysistest.make(` call, confirm the paired `target_under_test =` label resolves to a `rule()`-produced target, never a `repository_rule`-produced one. Empty output (no `analysistest.make()` calls at all) reads as PASS only if the file also has no rule-analysis behavior to test — otherwise it is a coverage gap, not a pass. **MUST**. Bazel 7/8/9, bazel-skylib ≥1.0 (mechanism unchanged 1.9.0→1.9.2). Settles: M-E-10.

2. **Give every `repository_rule` `_impl` function a `unittest.make()`-based orchestration test with a hand-rolled ctx fake.** *Rationale*: this is the only offline technique that exists for this phase (Finding 4); without it, correctness of the actual `ctx.download`/`ctx.execute`/`ctx.symlink`/`ctx.file` sequencing rests entirely on live-registry integration tests, which are slow, networked, and typically run far less often than `bazel test //...`. *Verify*: `grep -n 'repository_rule(' **/*.bzl` to enumerate `_impl` functions, then confirm each appears as the function under test in some `unittest.make(` call in the same package's test file (a plain `grep -n '<impl_name>(' *_test.bzl` hit that isn't just a `load()` line). Empty output (an `_impl` with no matching test-file hit) is a FINDING. **MUST** for any repository rule with no nested repository-rule calls of its own (Decision 1's assumption). Bazel 7/8/9, bazel-skylib ≥1.0. Settles: M-E-10.

3. **Do not claim `module_extension` orchestration is covered by the same ctx-fake technique.** *Rationale*: the `_impl` body's primary job is invoking repository-rule symbols, which is Bazel's own repo-instantiation mechanism, not a plain function call this dive found evidence can be faked offline (Finding 4). *Verify*: a reading heuristic — if a proposed `module_extension` unit test's fake `module_ctx` is handed to the real `_impl` and that impl calls a real `repository_rule` symbol (e.g. `ocx_download(...)`), confirm by actually running it once whether it errors outside extension evaluation; do not assume it works by analogy with the `repository_rule` case. **CONSIDER** (argued, not measured — this dive did not execute the failing case to confirm the exact error). Bazel 8/9. Settles: M-E-10 (partially; names the residual gap).

4. **Run `bazel mod deps` as the coarse, real-evaluation safety net for module-extension logic, not as a substitute for testing the extension's pure decision functions offline.** *Rationale*: it is the one technique the official doc names, and it "unconditionally evaluates all module extensions" — but it needs network for any actual fetch and gives no assertion surface beyond "did it evaluate without error." *Verify*: `bazel mod deps` exits 0; read its output structurally, it is not machine-checkable against an expectation without additional tooling. **SHOULD**. Bazel 7/8/9 (bzlmod-only). Settles: M-E-10.

5. **Hold every `expect_failure` fragment in a module-level constant the guarded call site cannot spell.** *Rationale*: `asserts.expect_failure` does a substring search against the concatenated traceback, which echoes every frame's source line — a fragment repeated at the call site matches its own echo and passes vacuously regardless of whether the guard ever fired (Finding 2). *Verify*: for each `asserts.expect_failure(env, X)` call, confirm `X` is a named constant (not an inline string literal) and that the constant's value does not appear as a substring anywhere else in the same `.bzl` file outside its own definition and this one call site. Empty output on that grep (the fragment appears exactly twice) is PASS; a third occurrence is a FINDING. **MUST**. All Bazel majors, bazel-skylib all versions. Settles: M-E-11.

6. **Confirm every guard/`expect_failure` test has been seen red at least once.** *Rationale*: a guard test that has never failed when its guard is removed is not evidence the guard does anything — it may be passing vacuously (Finding 2) or asserting on the wrong target. *Verify*: a named reading/procedural heuristic, not a command — temporarily comment out or invert the `fail()`/validation the test claims to guard, re-run `bazel test :that_target`, confirm it goes red, then revert. No static check substitutes for this. **SHOULD** (procedural, cannot be fully mechanized). All Bazel majors. Settles: M-E-11.

7. **Tag every fixture rule instantiated under an `expect_failure` test `manual`.** *Rationale*: without it, `bazel build //...`/`:all` builds the intentionally-failing target and reports a build failure that has nothing to do with the test suite ([bazel.build/rules/testing](https://bazel.build/rules/testing#failure-testing)). *Verify*: for every rule instantiation whose label is later passed as `target_under_test =` to an `analysistest.make(expect_failure=True)`-declared test rule, confirm its call carries `tags = ["manual"]` (or a superset including it). Empty output (no offending instantiation lacks the tag) is PASS. **MUST**. All Bazel majors, bazel-skylib all versions. Settles: M-E-10.

8. **Generate repetitive guard/error-path tests from a dict literal fed through `partial.make()`, not hand-copied per-case boilerplate.** *Rationale*: `unittest.suite()` already accepts `partial.make(rule, **kwargs)` entries by design (Finding 3); hand-copying each case risks silent drift between cases that should share assertion logic. *Verify*: a reading heuristic — for a test file with more than ~5 structurally similar guard cases, confirm they are generated from a `for case, expected in SOME_DICT.items():` loop rather than repeated near-identical function/rule pairs. **SHOULD**. Bazel 7/8/9, bazel-skylib ≥1.0. Settles: M-E-10, M-E-11.

9. **Grant `visibility()` to the test package on every `.bzl` file whose `_impl` functions need direct unit testing.** *Rationale*: Starlark's leading underscore is a naming convention, not an access boundary across files — only `visibility()` controls which packages may `load()` anything from a file at all, and a too-narrow grant silently blocks the offline-fake technique from reaching the function that needs it. *Verify*: `grep -L '^visibility(' **/private/*.bzl` should print nothing if every private file declares one; then confirm the test package is in each declared allowlist. Empty output on the first grep is PASS; a listed file is a FINDING. **MUST**. Bazel 6/7/8/9 (the `visibility()` builtin itself; stable since Bazel 6.0). Settles: M-E-10.

10. **Keep a hand-rolled ctx fake duck-typed to only the methods the code under test actually calls — never a speculative full `repository_ctx`/`module_ctx` reimplementation.** *Rationale*: Bazel gives no compile-time contract between a fake struct and the real ctx type, so an over-built fake silently drifts from the real surface with nothing to catch the mismatch until a real repository rule breaks in production. *Verify*: for each fake, list its exposed struct fields/methods and diff against the `ctx.` call sites of every function it stands in for (`grep -n 'ctx\.' <impl-or-helper-file>`) — a fake method never referenced anywhere is dead surface; a `ctx.` call in the real code with no matching fake method will itself throw at test time (loud, not silent), but should not exist at all in a well-maintained fake. **SHOULD**. All Bazel majors. Settles: M-E-11.

11. **Set `--instrumentation_filter` explicitly in `.bazelrc`'s `coverage:` section for any repository with vendored or third-party dependencies.** *Rationale*: the built-in default excludes only two hardcoded Java paths — every other language and every vendor tree gets instrumented by default, inflating both coverage noise and collection time. *Verify*: read the `coverage --instrumentation_filter=...` line in `.bazelrc`; confirm it is anchored (`^//`) rather than the untouched Java-only default. Empty output (no `coverage --instrumentation_filter` line at all) reads as a FINDING for any repo with vendored deps. **MUST** for a repo with vendored/third-party deps; **SHOULD** otherwise. Bazel 7/8/9 (flag stable). Settles: (contextual; feeds the coverage half of the brief, no single M-E-nn is dedicated to it).

12. **Do not assume `--combined_report` needs `=lcov` passed explicitly — check the pinned Bazel major first.** *Rationale*: the default flipped from `none` to `lcov` exactly at Bazel 9.0.0 (Finding 6); a rule or `.bazelrc` comment written against pre-9 behavior is stale on 9.x, and a CI matrix spanning both majors needs the explicit flag only on its 8.x leg. *Verify*: `bazel --version`, then read `BazelCoverageReportModule.java`'s `defaultValue` at that exact tag if in doubt, or simply pass `--combined_report=lcov` explicitly everywhere and treat the default as an implementation detail not worth relying on. **SHOULD**. Bazel 8 (`none`) vs Bazel 9 (`lcov`) — version-exact. Settles: (feeds the coverage half of the brief).

13. **Pass `--enable_runfiles` explicitly on any Windows CI leg that also runs `bazel coverage`.** *Rationale*: the flag defaults off on Windows only, and at least one language (JS, confirmed) reports empty coverage with a specific ERROR-level log line while the test itself still passes silently — a false sense of "coverage is fine" on every other platform. *Verify*: in the CI workflow, confirm any `windows-*` runner leg that invokes `bazel coverage` also passes `--enable_runfiles` (via `.bazelrc` or the invocation). Empty output on `grep -n 'enable_runfiles' .bazelrc <ci-workflow>` for a repo with a Windows coverage leg is a FINDING. **MUST** for a repo with a Windows coverage CI leg; not applicable otherwise. Bazel 7/8/9 (flag stable, default unchanged across these majors per the sources read). Settles: M-E-13.

14. **Budget test `size`/`timeout` for the coverage run, not just the plain test run.** *Rationale*: at least one ruleset (JS, confirmed) documents that coverage post-processing consumes the same `size`/`timeout` budget as the test itself and scales with instrumented-file count — a test passing comfortably under `bazel test` can time out under `bazel coverage` with no code change. *Verify*: a reading/procedural heuristic — after enabling coverage on a target, run `bazel coverage //target` once and confirm it completes well under the target's declared `timeout`, not just that it eventually passes. **SHOULD**. All Bazel majors; confirmed for rules_js 3.4.1, unconfirmed for rules_rust 0.74.0/rules_python 2.3.3 (M-E-13's deferred half). Settles: M-E-13 (JS only; Rust/Python explicitly left open).

15. **Treat a `WARNING: no coverage report was generated ... reporting empty coverage` line as silent with respect to test pass/fail — never rely on `bazel coverage`'s own exit code to detect an instrumentation gap.** *Rationale*: the test target reports PASS regardless; only the `.dat` file's emptiness signals the problem, and nothing in the standard `bazel coverage` invocation surfaces that automatically as a build/test failure. *Verify*: if coverage completeness is a CI gate, add an explicit check on the produced `_coverage_report.dat` (non-empty, or a minimum line count) as a separate step — do not trust `bazel coverage`'s own exit code alone. **SHOULD**. All Bazel majors. Settles: (feeds the coverage half of the brief).

16. **For a repository with a "no network" test target/suite, verify the claim by running from a cold repository cache — never trust the label.** *Rationale*: a target's declared `deps`/`data` are the ground truth for whether a first `bazel test //...` needs network; a taskfile or CI-step description asserting "no network" can drift from the actual BUILD graph (measured: `rules_ocx`'s own `taskfile.yml:43` calls its `test` task "no network" while `ocx/tests/BUILD.bazel:23-42` groups two `sh_test`s consuming externally-fetched `@ocx_tool`/`@dev_tools` into that same `//...` expansion). *Verify*: `rm -rf ~/.cache/bazel` (or an equivalent clean repository-cache state), then run the claimed-offline test target with network disabled (e.g. a firewalled sandbox or `--repository_cache=` pointed at an empty dir) and confirm it still passes. Empty output (no failure) is PASS; any fetch attempt is a FINDING against the "no network" label. **MUST** wherever a target or task is explicitly labeled network-free. Bazel 7/8/9. Settles: M-E-12.

17. **Do not point buildifier, stardoc, or a BUILD-graph grep at BUILD content generated as a raw string inside a `repository_rule`/`module_extension` — none of them can see inside the string.** *Rationale*: a typo in a generated `package(default_visibility=...)` string, or any other structural error in generated BUILD content, passes every static check in the authoring repo and surfaces only when a generated target is actually built (`starlark-code-shape.md` Smell #3). *Verify*: confirm at least one integration/example test actually builds a target defined inside the generated repo, for every repository rule that emits BUILD content via string templates — a `grep -c` over the template string is not a substitute. Empty output (no such integration test exists for a template-emitting repo rule) is a FINDING. **MUST**. Bazel 7/8/9. Settles: M-E-10 (names why the offline unit test in candidate 2 does not replace the live-registry integration test — the two check different things).

18. **When testing rule behavior under different build flags (`-c opt` vs `-c dbg`, or any other), use `analysistest.make(config_settings={...})`, never rely on invoking `bazel test` twice with different flags on the same suite.** *Rationale*: both flag variants cannot coexist in a single build/test invocation — `config_settings` applies an `analysis_test_transition` scoped to just that test rule's target-under-test, letting both variants exist side by side in one `bazel test //...` ([bazel.build/rules/testing, "Verifying rule behavior under different flags"](https://bazel.build/rules/testing#verifying-rule-behavior-under-different-flags)). *Verify*: `grep -n 'config_settings' *_test.bzl` for any test asserting flag-dependent behavior; absence alongside a comment/TODO about flag-dependent behavior is a FINDING. **SHOULD**. Bazel 7/8/9, bazel-skylib ≥1.0. Settles: (general analysistest hygiene, not a dedicated M-ID).

19. **Prefer `rules_testing`'s fluent matchers over hand-rolled `asserts.equals` chains for a new analysis test, but do not expect it to close the repository-rule/module-extension gap.** *Rationale*: it wraps the identical `AnalysisFailureInfo`/`analysis_test_transition` machinery with better failure messages (Finding 9) — a readability upgrade, not a capability upgrade. *Verify*: reading heuristic only; if adopted, confirm the `MODULE.bazel` dev-dependency pins an exact `rules_testing` version (`0.9.0` as of 2026-09-05). **CONSIDER**. Bazel 7/8/9 (rules_testing has no stated Bazel-version floor found in this dive's sources). Settles: none directly (background alternative).

20. **For a `module_extension`'s repository-rule-invocation logic specifically (as opposed to its pure tag-processing helpers), rely on a real integration test — `rules_bazel_integration_test` or an equivalent nested-workspace technique — not an offline fake.** *Rationale*: this dive found no confirmed offline technique for that half of module-extension logic (Finding 4, Decision 1); the packaged, actively-maintained alternative to a hand-rolled nested-workspace harness exists and is current. *Verify*: confirm at least one test target depends on `rules_bazel_integration_test` (or runs an equivalent real-`bazel`-subprocess harness) covering the extension's actual repository creation, tagged `exclusive` per the library's own hermeticity constraint. **SHOULD**. Bazel 7/8/9 (the library's own `bazel_compatibility` was not read in this dive — verify before pinning). Settles: M-E-10 (module_extension half).

## Fleet evidence

- **76 `analysistest`/`unittest` targets across five files** (`ocx/tests/{launcher,manifest,package,platforms,policy}_test.bzl`), confirmed by direct count: `grep -c "analysistest.make\|unittest.make"` returns 28 (launcher), 7 (policy), 5 (manifest), 2 (package), 2 (platforms).
- **Zero `analysistest.make()` calls target a production rule.** The two that exist (`closure_packages_guard_test`, `guard_test`, `ocx/tests/launcher_test.bzl:1169,1299`) both target hand-written fixture rules (`_bad_closure_report`, `_guard`, `launcher_test.bzl:1145,1290`) built solely to exercise `fail()` paths — never one of the four production `repository_rule`s. Settles M-E-10's "count `analysistest.make(` calls that target a production rule" check at exactly zero.
- **Three hand-rolled `repository_ctx` fakes, `launcher_test.bzl:40-197`** (`_fs_ctx`, `_replay_ctx`, `_env_ctx`) — the concrete, portable pattern behind Decision 2 and candidate 10.
- **34 of the 76 targets are generated data-driven from two dict literals**: `_MALFORMED_CLOSURE_REPORTS`/`_MALFORMED_CLOSURE_CONTAINERS` (9 cases, `launcher_test.bzl:1058-1139`) and `_GUARD_CASES` (25 cases, `launcher_test.bzl:1184-1227`), both fed through `partial.make()` in `launcher_test_suite` (`launcher_test.bzl:1567-1584`) — the exemplar for candidate 8.
- **The four `repository_rule` `_impl` functions** (`_ocx_download_impl` `download.bzl:27`, `_ocx_project_repo_impl` `project.bzl:232`-adjacent, `_ocx_package_repo_impl`/`_ocx_package_hub_impl` `package.bzl:299,408`-adjacent) **are proven only by live-registry example tests** (`examples/cross_platform`, `examples/project`, `examples/package`, run by the CI `examples` job matrixed across OS/Bazel version, `.github/workflows/ci.yml:64-90`) plus two dogfood `sh_test`s (`ocx/tests/BUILD.bazel:21-42`) that themselves consume network-fetched external repos (`@ocx_tool`, `@dev_tools`) — confirming M-E-12's finding that the taskfile's "no network" label (`taskfile.yml:43`) does not hold for the `//...` expansion it describes.
- **Coverage is entirely unexercised fleet-wide**: `grep -rn "coverage\|combined_report\|instrumentation_filter"` across every `.github/workflows/*.yml` and `.bazelrc*` in `rules_ocx` returns zero matches. Empty output here reads as "coverage is not configured," not "coverage is silently broken" — there is no coverage CI leg to be broken. This means Decision-level guidance on `--combined_report`'s Bazel 8→9 default flip (Finding 6) and the `--enable_runfiles`/Windows interaction (Finding 7) apply to `rules_ocx`'s *users* (shape F, per the map), not to `rules_ocx` itself today.
- **`bazel_skylib` is pinned at `1.9.0`** (`MODULE.bazel:13`), one patch behind the current `1.9.2` (2026-07-17). Diffed `lib/unittest.bzl` byte-for-byte across `1.9.0`, `1.9.2`, and `main`: identical. No API drift risk from moving the pin, for this file at least.
- **`repo_utils.bzl` (1,602 lines) spans 7 concerns** and every private module depends on it (`starlark-code-shape.md` Smell #2) — orthogonal to this dive's scope but the reason the three ctx fakes in `launcher_test.bzl` end up testing helpers from several different concerns through one shared fake set rather than one fake per concern.
- **Generated BUILD content is raw string concatenation in 4 places** (`download.bzl:17-26`, `project.bzl:124-127,228-230`, `package.bzl:284-295,367-406`, plus `repo_utils.bzl`'s `render_launchers_build`/`render_env_bzl`), invisible to buildifier — the concrete grounding for candidate 17.

## AI-agent angle

- **Assuming `analysistest.make()` can wrap a `repository_rule` or `module_extension` directly.** It cannot — there is no `Target`/providers to attach to (Finding 4). *Check*: for any newly-written `analysistest.make(` call, confirm the rule type behind its `target_under_test` label is a `rule()`, not a `repository_rule()` or an extension-generated repo's synthetic target meant to stand in for the extension itself.
- **Hand-writing `native.test_suite(name=..., tests=[...])` boilerplate alongside `unittest.make()` calls instead of using `unittest.suite()`.** This is WORKSPACE-era muscle memory carried forward; `unittest.suite()` already does this (Finding 3). *Check*: `grep -n 'native.test_suite' **/*.bzl` next to any file that also calls `unittest.make(`/`analysistest.make(` — a hand-rolled `test_suite` in the same file is redundant scaffolding.
- **Writing an `expect_failure` fragment as an inline string literal instead of a named constant.** This is the single highest-value mechanical mistake to catch, since it produces a test that looks correct and green forever (Finding 2, candidate 5). *Check*: `grep -n 'asserts.expect_failure(env, "'` — any hit with a quoted literal (rather than a bare identifier) as the second argument is the finding.
- **Forgetting `tags = ["manual"]` on the fixture rule under a failure test.** An LLM copying the "Minimal example" from `bazel.build/rules/testing` sometimes drops the tag when adapting it, since the doc's failure-testing section is a separate example from the minimal one. *Check*: candidate 7's grep.
- **Assuming `--combined_report=lcov` must be passed explicitly, because that is what most existing tutorials and blog posts (pre-2025) show.** Harmless on Bazel 9+ (redundant with the new default) but the inverse mistake — assuming a Bazel-8 CI leg also produces a combined report by default — silently drops the merged `.dat` file on that leg only (Finding 6). *Check*: read the pinned `.bazelversion`/CI matrix major before writing `--combined_report` guidance into a rule or `.bazelrc` comment.
- **Assuming Bazel 9's general Windows improvements (venvs, downloader defaults) also fixed coverage's runfiles requirement on Windows.** They are unrelated subsystems — `--enable_runfiles`'s Windows-off default is a Bazel-core flag, not a ruleset behavior, and nothing in this dive's sources shows it changing across Bazel 8/9. *Check*: for any Windows CI leg running `bazel coverage`, grep for `enable_runfiles` explicitly rather than assuming a Bazel-9 upgrade alone fixes it.
- **Over-building a hand-rolled ctx fake into a full `repository_ctx`/`module_ctx` reimplementation "to be safe."** This produces a fake that drifts silently from the real ctx surface, since Starlark gives no compile-time check that the fake matches reality (candidate 10). *Check*: diff the fake's method list against the actual `ctx.` call sites of the function(s) it stands in for; any fake method with zero matching real call site is speculative surface to delete.
- **Assuming `analysistest` scales to an arbitrarily large fixture graph.** The doc's own 500-transitive-dependency cap (Finding 1) is easy to hit by accident when a test's fixture rule pulls in a large dependency closure. *Check*: no mechanical grep; a reading heuristic — if a fixture target's transitive dependency count is unclear, run `bazel query 'deps(//path:fixture)' | wc -l` before trusting an `analysistest` result that silently degrades or errors near that boundary.
- **Treating a repository or module extension's live-registry/integration test as redundant once an offline `unittest.make()` orchestration test exists for its `_impl`.** The two check different failure classes (candidate 17): the offline test proves the `_impl`'s decision logic and ctx-call sequencing; the integration test is the only thing that can catch a malformed generated-BUILD string or an actual live-registry incompatibility. *Check*: confirm both exist side by side for any repository rule that emits BUILD content via string templates — removing either lowers coverage, it does not deduplicate it.

## Contested / evolving

- **Whether `module_extension` orchestration can ever be offline-fake-tested is unresolved in the corpus this dive read.** The official doc offers no technique beyond `bazel mod deps` (a real-evaluation command); this dive could not confirm or rule out whether a repository-rule symbol invoked from a bare Starlark function call (outside real extension evaluation) succeeds or errors, and did not find a primary source settling it either way. Trending: `rules_bazel_integration_test`'s continued 2026 release cadence (`v0.37.1`, 2026-01-31) suggests the ecosystem is converging on "test it for real, cheaply, via a packaged nested-workspace harness" rather than waiting for an offline technique to be invented.
- **`rules_testing` versus `bazel-skylib`'s `unittest.bzl` is not a settled replacement, only a growing parallel option.** Both wrap the identical underlying `AnalysisFailureInfo`/`analysis_test_transition` mechanism (Finding 9); `rules_testing` v0.9.0 is a year-plus old as of this writing with adoption inside `bazelbuild/bazel` itself, `bazel-skylib`, `rules_cc`, and `rules_java` (measured), but bazel-skylib's `unittest.bzl` remains the doc-cited default on `bazel.build/rules/testing` itself. Neither is deprecated as of 2026-09-05.
- **The `--combined_report` default flip is recent enough (landed 9.0.0, 2026-01-20) that most existing tutorials, StackOverflow answers, and pre-2026 blog posts predate it** and will show `--combined_report=lcov` as a required flag rather than the current default on Active LTS. This will keep being a source of stale-seeming-but-still-correct guidance for as long as Bazel 8 (Maintenance until December 2027 per the frame) remains in any CI matrix.
- **Whether `--instrumentation_filter`'s Java-only default should ever change is not under active discussion in any source this dive read** — it appears to be treated as a stable, if narrow, default that every non-Java ecosystem is expected to override locally (rules_rust's own docs model this as expected, not as a bug to file upstream).
