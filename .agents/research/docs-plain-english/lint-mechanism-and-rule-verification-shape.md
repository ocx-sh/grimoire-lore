## Summary

- Ship the mandatory prose gate as **grep + markdownlint**, with zero new runtime dependency required to pass CI; Vale is an **opt-in escalation layer**, never a requirement, because the fleet has zero prose tooling today and forcing a Go binary onto 12+ heterogeneous repos is a real adoption cost, not a preference (`config-inventory.md` axis 5).
- Vale's own vocabulary is eleven rule types — existence, substitution, occurrence, repetition, consistency, conditional, capitalization, metric, spelling, sequence, script — each configured with a `level:` of `suggestion`, `warning` (the default), or `error` ([docs.vale.sh/topics/styles](https://docs.vale.sh/topics/styles/)).
- markdownlint (`DavidAnson/markdownlint`) ships a stable, zero-config rule catalogue from MD001 to MD060 (with several IDs retired) covering Markdown *syntax*, never prose *content* — this is the free half of the mechanism ([Rules.md](https://github.com/DavidAnson/markdownlint/blob/main/doc/Rules.md)).
- **Any new prose rule launches at `warning` severity, scoped to lines a PR actually adds or touches — never `error` against the whole tree on day one.** GitLab's own rule states it in one sentence: "If you add an error-level Vale rule, you must fix the existing occurrences of the issue in the documentation before you can add the rule" ([docs.gitlab.com/development/documentation/testing/vale](https://docs.gitlab.com/development/documentation/testing/vale/)).
- A January-2026 rollout guide names the exact mechanism for that scoping: `MinAlertLevel = warning` plus `filter_mode: added`, so only lines a PR adds or modifies are gated, tightened to `error` once noise subsides ([buildwithfern.com/post/docs-linting-guide](https://buildwithfern.com/post/docs-linting-guide), corroborated by direct fetch of `docs.gitlab.com` and by `recent-shifts-and-tooling.md` §13).
- Real production configs start even softer than the guide recommends: Grafana's own `.vale.ini` sets `MinAlertLevel = suggestion`, one rung below "warning," and its Git-hook path shows errors only while the CI/MR-diff path shows the fuller warning+suggestion signal ([grafana.com/docs/writers-toolkit/review/lint-prose](https://grafana.com/docs/writers-toolkit/review/lint-prose/), [docs.gitlab.com/development/documentation/testing/vale](https://docs.gitlab.com/development/documentation/testing/vale/)).
- **The conflict this topic owns — explain-a-term-once vs. hyperlink-every-occurrence — is resolved as explain/link once, at first meaningful mention per page.** GOV.UK's guidance is explicit: "You just need to explain what they mean the first time you use them" ([guidance.publishing.service.gov.uk/…/clear-language](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)); GitLab's independent ~15-links-per-page soft cap is the tiebreaker no every-occurrence rule can pass on a page of any real length ([docs.gitlab.com/…/styleguide](https://docs.gitlab.com/development/documentation/styleguide/)).
- ocx's own rule already fails its own hyperlink-every-occurrence mandate at scale: `docs-shape.md` §5 counts 2,337 internal plus 611 external links across only 44 pages, and the site's reference-style-only mandate (`docs-style.md:104-124`) coexists with 555 measured inline-style links in the very same repo — the rule the fleet states is not the rule the fleet writes.
- **Link syntax (reference-style vs. inline) is a separate axis from link frequency, and is decided the opposite way from ocx's current rule: require inline `[text](url)`, ban reference-style.** GitLab's own shipped Vale rule, `ReferenceLinks.yml`, independently enforces exactly this — inline links, not reference-style — for the same maintainability reason ([confirmed via GitLab forum discussion of the rule](https://forum.gitlab.com/t/cant-make-a-reference-style-link-thats-part-of-a-bulleted-list-render-in-a-markdown-file-on-gitlab-com/37484), cross-checked against `docs.gitlab.com/…/styleguide`).
- **markdownlint and Vale/GitLab can silently fight over the same construct.** Link style is already double-owned: markdownlint's `MD054` (`link-image-style`) natively supports a `style: "inline"` config option, the exact same check GitLab ships as a Vale rule. Assign it to markdownlint alone in the no-Vale baseline; disable the Vale-side rule if Vale is later adopted.
- GitLab's own documented thresholds are the fleet's best-available, fully-cited numeric anchor set: heading depth capped at H5, links-per-page soft cap ~15, line wrap ~100 characters, alt text ≤155 characters, screenshots ≤1000×500px and ≤100KB, glossary tooltips 5–10 max per page — every one mechanically checkable ([docs.gitlab.com/…/styleguide](https://docs.gitlab.com/development/documentation/styleguide/)).
- The fleet's single most rigorously verified documentation rule set is `grimoire-lore/rules/rust-quality/docs-and-tracing.md` (propagated to `ocx`), 11 of 12 rustdoc rules carrying an exact `rg`/`grep`/CI-flag command inline in the same table row — this is the row shape to copy for the docs-site prose family, which currently sits at 2 mechanical checks out of ~92 rules (`config-inventory.md` axis 5).
- **A rule with no runnable check must say so, visibly.** The shipped shape for an unverifiable rule states `Unverified — reading heuristic: <what a reviewer looks for>` in the Verification cell and caps its severity at SHOULD/CONSIDER, never MUST — an empty or prose-only cell is indistinguishable from an omission and is itself a finding.
- Harper (`Automattic/harper`), a Rust, offline grammar checker exposed via `harper-ls` (LSP), is not a substitute for Vale's custom-style capability — it checks grammar, not organization-specific wordlists, tone, or readability metrics — and Vale itself ships a "Harper" wrapper *package* (547 rules) that pulls Harper's grammar checks into Vale's own severity system, meaning the two tools are complementary, not competing, if Vale is ever adopted ([github.com/Automattic/harper](https://github.com/Automattic/harper), [vale.sh/hub](https://vale.sh/hub/)).
- Vale's package hub shows a real naming trap: at least two separately-authored packages both distributed as "vale-ai-tells" exist (`krishnasunkam/vale-ai-tells`, 17 rules, 6 error/11 suggestion; `tbhb/vale-ai-tells`, ~111 rule files, all defaulting to error) — pin the exact GitHub org/repo in `Packages =`, never a bare display name.
- Vale itself shows a currency flag worth a human decision before locking it in as the "escalation layer": its GitHub org was renamed from `errata-ai` to `vale-cli`, and the latest tagged release fetched was `v3.20.0`; treat the exact release cadence as worth re-confirming rather than assumed current, though the rule-type vocabulary and severity model above are stable regardless of release cadence.
- markdownlint (core library) is actively maintained: `0.41.1` published 2026-07-13 on npm; its CLI wrapper `markdownlint-cli2` is at `0.23.2` (2026-07-27) — both current as of this research.
- This topic's recommendation directly answers the topic map's own open item ("Is Vale acceptable as a new dependency in every adopting repo?"): **no, not required — opt-in only**, with the mandatory gate fully specified without it; the map still lists this as needing the owner's confirmation, and that confirmation is what remains open, not the mechanism.

## Findings

### 1. Vale's rule-type vocabulary and severity model

Vale describes itself as "a linter for prose" — a single, dependency-free Go binary that parses (not merely pattern-matches) twelve markup formats and checks them against a configurable rule set called a *style* ([vale.sh](https://vale.sh/)). A style is a directory of individual `.yml` rule files, each an instance of one of eleven extension points, confirmed identically across two independent fetches of Vale's own documentation ([vale.sh](https://vale.sh/), [docs.vale.sh/topics/styles](https://docs.vale.sh/topics/styles/)):

| Rule type | What it checks |
|---|---|
| `existence` | presence of a banned regex/term |
| `substitution` | suggests replacing one term with another |
| `occurrence` | a pattern's frequency against a numeric bound |
| `repetition` | a pattern repeated too many times in sequence |
| `consistency` | a pattern used inconsistently within one file |
| `conditional` | pattern A requires pattern B nearby |
| `capitalization` | enforces a capitalization convention |
| `metric` | a custom formula over the text (readability scores, word counts) |
| `spelling` | Hunspell-compatible dictionary spellcheck |
| `sequence` | part-of-speech-tagged grammar patterns |
| `script` | a Tengo script for arbitrary custom logic |

Every rule sets its own `level:` — `suggestion`, `warning`, or `error`, with `warning` as the documented default when a rule omits the field ([docs.vale.sh/topics/styles](https://docs.vale.sh/topics/styles/)). This three-tier severity, configurable per rule rather than per tool, is the single capability grep alone cannot replicate without a bespoke wrapper script, and it is what makes Vale the natural home for a **metric** rule (a readability formula) and for any rule whose severity needs to change over a rollout without touching the rule's regex.

Vale's package hub lists ready-made styles with their rule counts, several directly relevant to this program: Google (36 rules), Microsoft (47), write-good (8), alex (11, inclusive language), proselint (34), Joblint (17, already ruled inapplicable to software docs — `codified-practice.md`), Readability (7 rules, requires Vale ≥ 2.13.0), and an "AiTells" package (17 rules) ([vale.sh/hub](https://vale.sh/hub/)) — the tell taxonomy and readability formula themselves are the sibling topics' job; this topic's job is only that Vale's `metric` and `existence`/`substitution` types are the mechanism those sibling rules would run on, if Vale is adopted.

### 2. markdownlint's syntax catalogue — what comes free

`DavidAnson/markdownlint`'s rule reference spans MD001 through MD060, with several IDs retired (MD002, MD006, MD008 do not appear in the current catalogue) ([Rules.md](https://github.com/DavidAnson/markdownlint/blob/main/doc/Rules.md)). Every rule fires on Markdown *syntax*, never prose wording — this is the structural half of the mechanism and needs no styles directory, no package sync, and (via `npx markdownlint-cli2`, current release `0.23.2`, 2026-07-27, confirmed via the npm registry) no persistent install. The rules most relevant to this program, all zero-config:

| ID | Name | Catches |
|---|---|---|
| MD001 | heading-increment | a heading level skip (H2 straight to H4) |
| MD003 | heading-style | inconsistent heading syntax (ATX vs. setext) — **not** casing |
| MD022 | blanks-around-headings | a heading with no surrounding blank line |
| MD025 | single-h1 | more than one top-level heading in a document |
| MD026 | no-trailing-punctuation | a heading ending in punctuation |
| MD029 | ol-prefix | inconsistent ordered-list numbering |
| MD034 | no-bare-urls | a bare URL with no angle brackets or link syntax |
| MD036 | no-emphasis-as-heading | a bold/italic line standing in for a real heading |
| MD040 | fenced-code-language | a fenced code block with no language tag |
| MD045 | no-alt-text | an image with no alt text |
| MD051 | link-fragments | a `#anchor` link whose target heading doesn't exist |
| MD054 | link-image-style | inconsistent link/image style (autolink, inline, reference, shortcut, collapsed) — **configurable to a single required style** |
| MD059 | descriptive-link-text | generic link text ("click here") |

Note the correction already on record for this fleet's own upstream research: MD003 does **not** check letter-casing (`codified-practice.md:194` cites MD001+MD003 for "Title Case headings," which is imprecise — the casing check, if wanted, is a Vale `Capitalization` rule or Google's own `Google.Headings` package rule, not markdownlint at all; see `ai-tell-set-and-honest-label.md` §6 for the full worked example).

### 3. Harper and the case against a second grammar tool

`Automattic/harper` is a Rust, offline, privacy-first grammar checker exposed via `harper-ls` (Language Server Protocol), with editor support named for VS Code, Neovim, Helix, Emacs, and Zed, and a stated speed advantage — its own comparison places typical suggestion latency at ~10ms against LanguageTool's ~650ms and Grammarly's ~4000ms, with memory use "less than 1/50th of LanguageTool's" ([github.com/Automattic/harper](https://github.com/Automattic/harper)). It is real, current, and a legitimate choice for grammar (subject-verb agreement, tense, article use) — but it is not a substitute for the custom organizational rules this program needs (a marketing-tone wordlist, a timeless-language blocklist, a readability metric): Harper has no equivalent to Vale's `existence`/`substitution`/`metric` rule types, and its own comparison table only measures itself against other *grammar* checkers (LanguageTool, Hunspell, Grammarly), never against Vale. Notably, Vale's own hub lists a "Harper" *package* (547 rules) that pulls Harper's grammar checking into Vale's severity/config system — the two tools are layered, not competing, in any future state where Vale is adopted ([vale.sh/hub](https://vale.sh/hub/)). For the mandatory, no-new-dependency baseline this program ships, Harper is out of scope entirely: it solves a problem (grammar) this program's rule set does not currently name as a gap.

### 4. Three real adopters' rollout patterns

Three independently fetched sources converge on the same shape, with real variation in exactly how soft the starting point is:

- **The documented guide.** A January 2026 rollout guide states the sequence directly: start at `MinAlertLevel = warning` (errors block the build, warnings let a team see and adapt), wire `filter_mode: added` so a CI gate fails only on lines a given PR adds or modifies — pre-existing prose debt does not block — then tighten to `error` once noise subsides ([buildwithfern.com/post/docs-linting-guide](https://buildwithfern.com/post/docs-linting-guide); the guide's page proved too long for direct automated re-fetch after the first pass, so this exact wording is corroborated independently below).
- **A real, currently-running config.** Grafana's actual `.vale.ini`, fetched directly, sets `MinAlertLevel = suggestion` — one rung softer than the guide's own recommendation — layers `BasedOnStyles = Grafana` (three named custom rules: `Grafana.FirstPersonPlural`, `Grafana.GoogleEllipses`, `Grafana.GooglePassive`) on top, requires `vale sync` after each pull, and lets a PR skip linting entirely via an HTML comment, `<!-- vale = NO -->` ([grafana.com/docs/writers-toolkit/review/lint-prose](https://grafana.com/docs/writers-toolkit/review/lint-prose/)).
- **A production severity contract, quoted directly.** GitLab's Vale-testing documentation states its three tiers in prose, not just config: **error** is for "branding guidelines, trademark guidelines, and anything that causes content on the documentation site to render incorrectly"; **warning** is for "general style guide rules, tenets, and best practices" and surfaces in the MR diff without blocking; **suggestion** is for "technical writing style preferences that may require refactoring... or updates to an exceptions list" and is local-editor-only, never shown in the MR (`ReadingLevel.yml` and `Uppercase.yml` are named as the suggestion-tier examples). The rollout rule is explicit: *"If you add an error-level Vale rule, you must fix the existing occurrences of the issue in the documentation before you can add the rule."* And local friction stays low deliberately: *"Vale only reports errors in the Git hook (the same configuration as the CI/CD pipelines)"* — suggestions and warnings never block a local commit, only the fuller CI/MR-diff view surfaces them ([docs.gitlab.com/development/documentation/testing/vale](https://docs.gitlab.com/development/documentation/testing/vale/)).

Read together: the "warning first" guide is the floor, not the ceiling — real adopters go softer (`suggestion`) for anything not yet proven low-noise, reserve `error` for rules that are either brand-new-content-only (nothing to retrofit) or already fully fixed fleet-wide, and keep the local pre-commit path stricter-signal-only so a developer isn't blocked by noise a CI reviewer will see anyway.

### 5. The fleet's own verification ratio and the shape to copy

`config-inventory.md` axis 5 counted every distinct normative statement across the fleet's docs-authoring rule families and found the docs-site-prose family (ocx's four files plus grimoire's fork) sits at **2 mechanical checks out of ~92 rules** — both coarse (a whole-site build gate, and one specific table-parity test), neither a per-rule lint. The one rule family that does this well governs code, not docs-site prose: `grimoire-lore/rules/rust-quality/docs-and-tracing.md` (propagated verbatim to `ocx`) carries **11 of 12 rules with an exact `rg`/`grep`/CI-flag command inlined in the same table row as the rule** — read directly, the shape is:

```
| ID | Rule | Verification | Severity |
|---|---|---|---|
| DOC-02 | Every `pub fn` returning `Result` carries a `# Errors` section... | Two totals, read off the `N matches` line each prints:
  `rg -q --stats --type rust --glob '!external/**' '# Errors' .`;
  `rg -q --stats --type rust --glob '!external/**' 'pub fn .*-> .*Result' .`
  — the first must be ≥ the second | MUST |
```

This is the template a docs-site prose rule should copy verbatim: the Verification cell *is* the check, not a pointer to one, and it names exactly what a passing vs. failing count looks like. The one rule in that same file with no mechanical check (`DOC-03`, panics documentation) is still labelled honestly — "Review: a new `pub fn` with a panicking operation and no `# Panics` is a finding" — a human-review instruction stated in the same cell shape as every mechanical one, not omitted.

### 6. The link rule, resolved

The brief names one conflict for this topic to resolve: explain-a-term-once vs. hyperlink-every-occurrence, against a links-per-page cap that collides with the latter. Three sources, independently fetched, converge on a resolution:

- **GOV.UK, quoted directly:** on specialist terms, "You just need to explain what they mean the first time you use them," with a worked example ("Explain the term in plain English when you first use it") ([guidance.publishing.service.gov.uk/…/clear-language](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)).
- **GitLab's soft cap:** "~15 links per page" ([docs.gitlab.com/…/styleguide](https://docs.gitlab.com/development/documentation/styleguide/)) — a page that hyperlinks *every* occurrence of *every* named external tool blows past 15 the moment it names four or five tools a couple of times each, which is the ordinary shape of a comparison-heavy page (exactly ocx's `user-guide.md`, at 13,789 words).
- **ocx's own rule and its own measured failure:** `docs-style.md:44-50` mandates "Every external tool mentioned must hyperlink — every occurrence, not just first"; `docs-shape.md` §5 counts 2,337 internal and 611 external links across only 44 pages in that same repo, and separately measures the site's reference-style-only link mandate (`docs-style.md:104-124`) coexisting with 555 inline-style links violating it. The rule the fleet states and the rule the fleet writes are two different rules.

**Resolution, decided here:** hyperlink or explain a term/tool once, at its first meaningful mention per page; every later mention in the same page stays plain text. This directly satisfies GOV.UK's guidance, is structurally compatible with a ~15-link soft cap, and does not require inventing a maintained entity list of "every external tool" the way a hyperlink-everywhere rule does (`config-inventory.md` axis 2 already flags that entity list as the missing piece making the current rule unverifiable even in principle). Verification: a script that extracts every markdown link per page, groups by (normalized anchor text, target URL), and flags any group appearing twice or more in one file as an over-linking violation, plus a separate total-non-footer-link-count check against 15. This governs *external and first-mention internal-term* linking density only — internal fragment liveness (a link resolving to real, non-stub content) is already covered and gated elsewhere (`ux-observability-posture.md` §3) and is out of this topic's scope.

A second, genuinely separate axis hides inside the same ocx rule and needs its own decision: link **syntax**. ocx mandates reference-style-only (`[text][ref]`, definitions collected at file bottom); GitLab's own shipped Vale rule, `ReferenceLinks.yml`, does the opposite — it requires **inline** links (`[text](url)`), flagging reference-style as the violation (confirmed via a GitLab community forum thread discussing a false positive against this exact rule, cross-checked against the GitLab styleguide page listing `ReferenceLinks.yml` by name). Given ocx's own measured 555-instance drift away from its stated reference-style mandate — writers default to inline links even when told not to — and given GitLab ships the opposite rule as a *maintainability* choice, not a stylistic one, this topic decides link syntax the way GitLab did: **require inline links, ban reference-style.** This is directly enforceable by markdownlint's own `MD054` rule configured to `{"style": "inline"}` — no new tool needed (see §7).

### 7. The markdownlint/Vale ownership boundary

The brief calls out headings as the place both tools touch; the sharper, previously-unnoted collision found in this research is link style. markdownlint's `MD054` (`link-image-style`) already supports a `style` option (e.g. forcing `inline` and rejecting `reference`, `shortcut`, `collapsed`, or `autolink` forms) — the exact same construct GitLab ships as a Vale existence-style rule (`ReferenceLinks.yml`). If both tools run with their own defaults active, they can demand opposite things on the same file, and a contributor fixing one tool's complaint breaks the other's. The resolution generalizes past this one example:

**Every construct gets exactly one owning tool, named explicitly in the rule's row; the other tool's equivalent check is disabled, not merely left unconfigured.**

For this program specifically: markdownlint owns Markdown *syntax and structure* — heading increment/skip (MD001), single top-level heading (MD025), blank lines around structural elements (MD022, MD031, MD032), fenced-code language (MD040), alt text presence (MD045), link/image style (MD054), link-fragment validity (MD051). Vale (where adopted) owns prose *content* — wording, tone, banned terms, readability metrics, and any capitalization or existence rule that needs a maintained wordlist markdownlint has no mechanism to express. Where a heading-adjacent check could plausibly live in either (e.g. a banned literal heading word, or heading capitalization style), it goes to Vale's `existence`/`capitalization` rule types, never re-implemented as a markdownlint custom rule, because Vale's regex engine is the one built for organization-specific wordlists and markdownlint's is not (see `ai-tell-set-and-honest-label.md` §6 for the worked heading-casing example, which independently arrives at the same boundary from the AI-tell side).

### 8. A found-in-the-wild adoption trap: two packages, one name

Vale's package hub and a targeted GitHub search both surface the same collision: at least two separately-authored packages are distributed under the name `vale-ai-tells`. `krishnasunkam/vale-ai-tells` is the disciplined one — 17 rules, six gating at `error` (unambiguous regardless of context: raw file paths, `ALL_CAPS_UNDERSCORE` tokens in prose, status brackets) and eleven at `suggestion` (judgment calls: epigrams, clichés, abstract-noun triads) — this is the package `ai-tell-set-and-honest-label.md` §5 documents in full. `tbhb/vale-ai-tells` is a separate, independently-authored package (confirmed via its `CITATION.cff`) with ~111 rule files, all defaulting to `error` — a far more aggressive design with no suggestion tier at all. Its GitHub repository description is itself an almost perfect specimen of the tells it exists to catch: *"...vale-ai-tells is a comprehensive, cutting-edge Vale style package that empowers writers to seamlessly delve into the rich tapestry of AI tells. It's not just a rule set; it's a game-changer that supercharges your prose, unlocks new possibilities, and really lands. Ship cleaner prose. Full stop."* — very likely deliberate self-aware irony from its author rather than an accident, but it stands as a genuinely useful worked bad-example regardless of intent, paired against its own README's much plainer, straight-written body text. The adoption lesson: Vale's `Packages =` directive resolves by whatever string is configured, and two same-named packages behave very differently at the severity level — pin the exact GitHub org/repo in configuration, never a bare display name, and read the severity distribution (how many rules default to `error`) before wiring any third-party package into a CI gate.

## Normative guidance candidates

1. **Ship the mandatory prose gate as grep plus markdownlint; require no new runtime dependency to pass CI.** Rationale: the fleet has zero prose tooling in any of 12 repos today, and the one rule set that already hits 11/12 mechanical verification (`docs-and-tracing.md`) does it with bare `rg`, proving a Go/Node toolchain is not a prerequisite for a rigorously verified rule. Verify: the mandatory rule file's Verification column contains only `grep`/`rg` invocations and markdownlint rule IDs, nothing requiring `vale sync` or a styles directory. Evidence: **measured** (`config-inventory.md` axis 5) + **argued** (recommendation).

2. **Treat Vale as an opt-in escalation layer, wired only when a repo's owner accepts the binary; ship a working `.vale.ini` so opting in is one `vale sync` away.** Rationale: Vale is the only found tool that natively expresses a readability `metric` rule and the AiTells taxonomy without a bespoke script, but requiring it fleet-wide contradicts the fleet's own zero-tooling baseline and the map's own flagged human decision on this exact question. Verify: presence of `.vale.ini` in a repo signals opt-in; its absence must not fail the mandatory gate. Evidence: **argued**, resolving a decision the topic map explicitly deferred to the owner.

3. **A new prose rule launches at `warning` severity, scoped to lines a PR adds or modifies, never `error` against the whole tree.** Rationale: the fleet's median page already fails em-dash, semicolon, and Flesch thresholds (`docs-shape.md` §3); an error-at-whole-file gate blocks effectively every PR on day one, and GitLab's own rule states existing occurrences must be fixed before a rule may go to error. Verify: the CI config for a newly-added rule shows either a `filter_mode`-equivalent diff scope or an explicit note that the rule has zero current fleet violations; a rule added at `error`/whole-file with neither is a finding. Evidence: **codified** (GitLab, Fern) + **measured** (fleet numbers).

4. **Keep the local pre-commit/Git-hook path stricter-signal-only; reserve the full warning+suggestion view for CI and the PR diff.** Rationale: GitLab's own production config does exactly this so a developer isn't blocked by noise a reviewer will see anyway. Verify: the pre-commit hook's alert-level flag is set stricter than (or equal to) the CI job's, never looser. Evidence: **codified** (GitLab, quoted directly).

5. **Assign every checkable construct to exactly one owning tool; where two tools can check the same thing, name the owner in the rule row and disable the other tool's equivalent rule.** Rationale: markdownlint's `MD054` and a Vale/GitLab-style `ReferenceLinks` rule can already demand opposite link styles with both tools' defaults active — an unowned overlap produces contradictory fix suggestions. Verify: grep the shipped rule file for every construct name; each must appear as an active check in exactly one tool's config, never two. Evidence: **measured** (the real MD054/ReferenceLinks.yml collision found in this research) + **normative**.

6. **Own link syntax with markdownlint's `MD054` set to `{"style": "inline"}`; ban reference-style link definitions.** Rationale: ocx's own reference-style-only mandate already drifted to 555 measured inline-style links in the same repo, and GitLab's independently-shipped Vale rule enforces inline for the same maintainability reason this program should adopt. Verify: `markdownlint --config '{"MD054":{"style":"inline"}}' <file>`, or the raw check `grep -n '\]\[[A-Za-z0-9_.-]*\]' <file>` for a reference-style usage outside a code fence. Evidence: **normative** (GitLab's shipped choice) + **measured** (ocx's own drift), resolving a conflict this topic owns.

7. **Own link frequency with a per-page script: hyperlink or explain an external tool or specialist term once, at first meaningful mention; later mentions stay plain text; cap non-footer links per page near 15.** Rationale: GOV.UK's explain-once guidance and GitLab's ~15-link soft cap together make hyperlink-every-occurrence structurally impossible to satisfy on any page of real length, exactly the failure ocx's own metrics show. Verify: a script groups each page's links by (normalized anchor text, target) and flags any pair used twice or more in one file, plus flags a non-footer link count above ~15. Evidence: **normative** (GOV.UK, GitLab), resolving the conflict this topic owns.

8. **Every checkable rule's row states the exact verifying command in the same cell as the rule — never a cross-reference to a separate check document.** Rationale: the fleet's one 11/12-verified rule set achieves that ratio because the check lives in the row; the docs-site family's ~30 statements separate rule from check (or omit it) and land at ~1/34. Verify: read the rule table; every Verification cell for a MUST/SHOULD rule contains a backtick-fenced command or rule ID, never a prose description alone. Evidence: **measured** (`config-inventory.md` axis 5) + codified pattern to copy.

9. **A rule with no runnable check states `Unverified — reading heuristic: <what a reviewer looks for>` in its Verification cell, and its severity is capped at SHOULD or CONSIDER, never MUST.** Rationale: ~90 of the fleet's ~92 prose rules are silently unverifiable today and visually indistinguishable from a checked rule at a glance — this is the exact ambiguity the frame's own constraint (every rule carries a verification) exists to close. Verify: grep the shipped rule file's Verification column for cells matching neither a backtick-fenced command nor the literal string "Unverified — reading heuristic"; any such cell is a finding. Evidence: **normative** (directly requested by the frame's constraint).

10. **Reuse one shared text-preprocessing function (strip frontmatter, code fences, ATX headings, table rows, inline code) as the input to any prose `metric` rule, regardless of which tool computes the number.** Rationale: `docs-shape.md` had to build exactly this preprocessing before any Flesch number meant anything on prose full of identifiers; reinventing it per-tool is how a naive metric rule manufactures a nonsense score on a reference page. Verify: the metric script (or Vale style) imports or duplicates the same strip function, checkable by a shared module path. Evidence: **measured** (`docs-shape.md` §3) — mechanism only, not the threshold, which is the sibling topic's decision.

11. **If Vale is adopted, pin every third-party package by its exact GitHub org/repo in `Packages =`, never a bare display name, and read the rule-severity distribution before wiring it into a CI gate.** Rationale: at least two separately-authored Vale packages both distribute as "vale-ai-tells" with wildly different severity defaults (17 rules, tiered, vs. ~111 rules, all-error) — a name-only reference can silently pull the aggressive one. Verify: the `.vale.ini`'s `Packages` line names a specific org/repo or a pinned archive URL, not a bare package name resolved by Vale's own hub search. Evidence: **measured** (the real package collision found in this research).

12. **markdownlint rules are binary (a rule is on and blocking, or off) with no native staged-severity rollout; give a newly-enabled markdownlint rule its own diff-scoped introduction (lint only files a PR touches) before widening it to the full tree, mirroring Vale's `filter_mode: added` by hand.** Rationale: unlike Vale, markdownlint has no `level:`/`MinAlertLevel` mechanism, so the same rollout risk (blocking every existing PR on day one) needs a manual equivalent. Verify: the rule's introduction PR lints only `git diff --name-only` against the target branch, not the whole tree, until a follow-up PR widens scope. Evidence: **argued** (tool-capability reasoning, generalizing the Vale-only pattern found in adopters).

## AI-agent angle

- **Writing a lint rule as prose and calling it done, with no wired check.** An agent asked to "add a rule" will often add a bulleted sentence to a rule file and stop, reproducing the fleet's own ~2/92 problem instead of fixing it. Smallest check: grep the new rule's row for a backtick-fenced command; a row with none, and no "Unverified — reading heuristic" literal either, is unfinished.
- **Introducing a new lint tool at `error` severity, fleet-wide, on the first commit.** "Strict" reads as safer to an agent than "staged," but against a corpus that already fails the new rule at scale it instantly blocks every open PR. Smallest check: run the new tool/config against the current tree before merging its introduction; a red result on existing, unrelated files means the severity or scope is wrong.
- **Satisfying two source rules that already collide, without checking whether they collide.** Told to enforce both "hyperlink every occurrence" and "cap links at 15 per page," an agent will often write pages that violate one or the other rather than noticing the two cannot both hold past a handful of named tools. Smallest check: run the per-page link-count and duplicate-link-group script on any page an agent just finished, before it is presented as done.
- **Citing a tool or flag that sounds real but isn't, to make a Verification cell look filled.** A fabricated command (`vale --strict-headings`, a nonexistent markdownlint rule ID) reads identically to a real one until someone runs it. Smallest check: execute every Verification-cell command once against a scratch file before publishing the rule; an "unknown flag" or "unknown rule" error means the row was invented, not tested.
- **Picking a third-party lint package by display name alone.** Handed "add the ai-tells Vale package," an agent will resolve whichever repo a search turns up first — exactly the `krishnasunkam` vs. `tbhb` collision found in this research — without comparing severity defaults. Smallest check: before wiring any `Packages =` entry, print the resolved package's rule count and its error/warning/suggestion split; an unexpected "all rules at error" result is the tell of the wrong package.
- **Re-implementing a construct in a second tool because the first tool's config felt awkward, rather than checking who already owns it.** An agent frustrated by markdownlint's `MD054` syntax will sometimes add an equivalent Vale existence rule instead of fixing the config, quietly producing the exact two-tools-disagree failure mode this topic names. Smallest check: before adding any new Vale/grep rule, grep the markdownlint config for the same construct name; a hit in both means one must be removed, not both kept.

## Contested / evolving

- **Is Vale acceptable as a new dependency in every adopting repo? Named as needing the owner's decision in the topic map; this topic's recommendation is no, opt-in only, with the mandatory gate fully specified without it.** The mandatory grep+markdownlint baseline covers every rule this and the sibling topics need to gate at MUST/SHOULD severity; Vale is recommended only as the mechanism for two things grep genuinely cannot express well — a readability `metric` and the wider AiTells taxonomy — and only where a repo's owner accepts the binary. This is not "it depends" left open: it depends on whether the owner values the metric/AiTells capability enough to accept a Go binary and a styles directory per opted-in repo, and the default recommended here, absent that decision, is not to.
- **markdownlint/Vale ownership boundaries are not a written industry convention — most real adopters (GitLab, Grafana, Red Hat) run both tools side by side with no stated boundary.** This topic's explicit owner-per-construct rule (§7) appears to be the first place in this research program that states one; it is a genuine design decision, not a summary of existing consensus, and should be revisited if a future Vale/markdownlint release adds overlapping functionality (e.g. if markdownlint ever ships a wordlist-style rule type).
- **Vale's own release cadence is a currency flag, not yet fully resolved.** The project's GitHub org was renamed from `errata-ai` to `vale-cli`, and the latest tagged release fetched during this research was `v3.20.0`; the rule-type vocabulary and severity model this topic relies on are stable regardless (they are documented on the project's current, actively-served docs site), but before locking Vale in as the recommended opt-in escalation layer, re-confirm its release cadence is still active rather than assuming continuity from this research's snapshot.
- **The em-dash/semicolon punctuation ban's labelling (detector vs. house style) is a named conflict but is owned and resolved by the sibling topic `ai-tell-set-and-honest-label`, not here.** This topic only establishes the mechanism (rollout severity, diff-scoping) that any punctuation ban — however labelled — should be delivered through; it takes no position on the labelling question itself.
