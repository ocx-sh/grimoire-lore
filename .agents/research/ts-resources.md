## Verdict

1. **Explicit resource management is adopted with a narrow scope, not preferred as a style.** The rule is *"never hand-roll `try/finally` where the resource already implements `Symbol.dispose`/`Symbol.asyncDispose`"* — not *"prefer `using` for anything disposable-shaped."* The broad form drags in the fma/creeptd WebGL-dispose-on-unmount and the VS Code extension-session patterns, whose lifetimes are not the enclosing block (`explicit-resource-management.md` §8).
2. **The gate on `using` is the runtime floor, not the compiler.** Every fleet repo except `setup-ocx` (Bun) sits below the native line (Node ≥24, Chrome ≥134, FF ≥141; Safari never). A `Symbol.dispose` polyfill as the entry point's first statement is therefore mandatory before the first `using` in a repo, and `target: "esnext"` — which emits `using` completely unlowered — is a load-time `SyntaxError` on those runtimes, not a graceful degrade.
3. **`vscode.Disposable` and `Symbol.dispose` stay two protocols, bridged by exactly one adapter per extension.** `vscode.d.ts` has zero `Symbol.dispose` references; the lifetimes genuinely differ (block vs. extension session). Merging them regresses a `context.subscriptions` discipline the audits measured at zero leaks.
4. **A child-process invocation without an explicit `timeout` and `maxBuffer` is a defect, full stop — and on a command that can fork, that shape is necessary but not sufficient.** Node's defaults are `timeout: 0` and 1 MiB — permissive, not safe. `grimoire-vscode/src/grim.ts:596-633` is the exemplar; every divergence from it is judged against that shape. But `timeout`'s internal kill is `child.kill()`, which reaches the **direct child PID only** — Node's docs say verbatim that "child processes of child processes will not be terminated." A `timeout` closes *hangs forever*; it does not close *descendant survives the kill* (TS-RES-15).
5. **`@actions/exec` stays.** Its lack of a timeout is a verified API fact, not a fleet defect — `ExecOptions` has no `timeout`/`signal` and `ToolRunner` never kills. If one call ever needs a hard bound, that one call moves to `execFile`; the rest keep the log-grouping and `io.which` resolution a raw rewrite would have to reimplement.
6. **The timer rule is about shape, not counts.** Awaited-as-sleep needs nothing; debounce/rearm must clear before reassigning; fire-and-forget needs either a reachable `clear*` on a teardown path or a realm-teardown guarantee that is *independently true*. The raw "7 setTimeout / 0 clearTimeout" figures are not evidence of a leak.
7. **Process-group termination: hand-roll in one file, do not adopt `execa`.** Measured across 9 first-party child-process sites, exactly one both spawns something that forks its own descendants *and* runs unattended: `ocx-catalog/src/sources/git.ts`'s `runGit` (`git` against a config-supplied remote that can be `ssh://`, which spawns `ssh`/`GIT_ASKPASS`). Every other spawn-capable site is a human- or CI-supervised `npm` call; every other unattended site spawns a first-party Rust binary (`grim`, `ocx`) directly. `execa@10.0.1` costs ~11 transitive dependencies, is ESM-only, and floors at Node `>=22` — against `ocx-catalog`'s own `>=20.19` and against a VS Code extension host's bundled Node, which `engines` cannot move. ~15 dependency-free lines in the one wrapper does the same job (TS-RES-15, -18).
8. **Documented gap, not an open question: Node core has no tree-kill and no owner for one.** [nodejs/node#64406](https://github.com/nodejs/node/issues/64406) (`subprocess.killTree()`, filed 2026-07-10) is open with a volunteer twice offering a PR and zero maintainer response; its 2021 predecessor [#40438](https://github.com/nodejs/node/issues/40438) was bot-closed on staleness after a collaborator laid out the real difficulty — not enough subtrees own a process group for a generic answer. Two consequences the ruleset absorbs rather than resolves: (a) process-group signalling (execa, TS-RES-15) is defeated by any descendant that calls `setsid()`, while the tree-walk strategy that catches those (`tree-kill`, `pgrep -P`) is unmaintained since 2019 — the ecosystem converged on process groups as *good enough*, not as correct; (b) on Windows the robust primitive is a Job Object, which no pure-JS path reaches, so `taskkill /T`'s dependence on parent-PID bookkeeping is an accepted industry-wide limitation. Every TS-RES rule here is best-effort by construction. Do not write "Node will ship `killTree`."

**Conflicts resolved**

- **Argv-array / `shell: true`.** `process-and-timer-lifecycle.md` rule 2 proposes a don't-regress rule; Wave 1 established shell injection as already clean (0 interpolated exec, every site argv-array) and out of scope. **Dropped** — it changes no agent behaviour and duplicates `TS-SEC`.
- **"`kate-middlechild` is the one repo on `target: ESNext`"** (`explicit-resource-management.md` summary + rule 8) vs. `config-inventory.md:53-55`, which shows `creeptd-ng/web` and its e2e config on `target: ESNext` too. **Resolved against the sub-artifact**: the rule is per *emit path*, not per repo — `creeptd-ng` lowers at Vite's build target and `kate-middlechild/packages/core` runs on Bun (native since 1.0.23), so the exposure narrows to emit paths with no lowering step. The repo-specific carve-out is dropped in favour of TS-RES-04.
- **The divergence catalog is incomplete.** `process-and-timer-lifecycle.md` §4 omits `grimoire-indexer/src/enrich/index.ts:64-70` (`spawnGrim`), which `runtime-posture.md:193` records and which sets `timeout` + `maxBuffer` but conflates ENOENT with a real exit failure. **Resolved for the audit**: it is a partial-conformance row, listed below.
- **"`setup-ocx` is the fleet's Bun repo."** Carried in from the frame and used to reason about native `using` and `Bun.spawn`. **Corrected against the repo's own files**: `action.yml:61-63` declares `runs: {using: node24}`, and the shipped action spawns exclusively through `@actions/exec`. Bun is `setup-ocx`'s dev/build/test runtime only (`bun scripts/build.ts`, `bun test`, `bunfig.toml`). This strengthens TS-RES-10 rather than changing it, and it removes `Bun.spawn` from this topic entirely — whose `timeout`/`killSignal` mirror Node core's single-PID limit anyway, with no `detached` and no group concept documented.
- **`grimoire-indexer` timer counts: "7 / 0"** (`code-shape.md:399`) vs. "10 total, 1 `clearTimeout`" (`process-and-timer-lifecycle.md` §6). **Resolved for the sub-artifact**: the one `clearTimeout` lives at `Base.astro:323`, and `code-shape.md`'s ripgrep globs were TS-file-typed (its scope block lists no `.astro`). The 0 is a file-extension artifact — which is exactly why the rule is phrased on shape, not on a count.

## The ruleset

**Family: `TS-RES`** (this topic owns it outright — `using`/`await using`, disposal protocols, child processes, timers, file handles).

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| **TS-RES-01** | Set an explicit `timeout` **and** `maxBuffer` on every `exec`/`execFile`/`execFileAsync`/`spawn` call that runs a real external command; size `maxBuffer` to the payload or state in a comment why the output is provably small. | Node defaults are `timeout: 0` and 1 MiB; the latter silently truncates and kills the child rather than throwing something diagnostic. **Scope of the bound:** `timeout` fires `child.kill()`, which reaches the direct child PID only — sufficient for a command that does not fork, and necessary-but-not-sufficient for one that does (TS-RES-15). | For each hit of `grep -rn "execFile(\|execFileAsync(\|exec(\|spawn(" src/`, confirm the options object contains both keys. | MUST |
| **TS-RES-02** | Branch on `(error as NodeJS.ErrnoException).code === 'ENOENT'` before reporting a generic failure from a child-process call. | A spawn failure and a non-zero exit are structurally different events; collapsing them turns "the tool isn't installed" into "the tool errored". | Any `catch`/callback around a child-process call with no ENOENT branch (or equivalent `isNotFound` helper) is the finding. | MUST |
| **TS-RES-03** | Attach `child.stdin.on('error', () => {})` **before** the first write to a child's stdin. | [nodejs/node#40085](https://github.com/nodejs/node/issues/40085) is closed as *not planned* — the EPIPE race is permanent, and an unguarded write becomes an uncaught exception. | `grep -n "\.stdin\.end(\|\.stdin\.write(" src/**/*.ts`; each hit needs the listener on the same object above it. | MUST |
| **TS-RES-04** | Never emit `using`/`await using` at `target: "esnext"` (tsc) or an `esnext` bundler target for code that reaches a runtime below the native floor — Node ≥24.0.0, Chrome/Edge ≥134, Firefox ≥141, Bun ≥1.0.23, Deno ≥2.2.10; Safari never. | At `esnext` both tsc and esbuild emit the syntax completely unlowered; a pre-native engine cannot parse it — a load-time `SyntaxError`, invisible to `tsc --noEmit`. | In any repo containing `using `, grep tsconfig + bundler config for `"target": "esnext"` (any case). On Vite 8/Rolldown/Oxc, additionally run the repro in [oxc#25155](https://github.com/oxc-project/oxc/issues/25155) against the project's real browserslist. | MUST |
| **TS-RES-05** | Run `Symbol.dispose ??= Symbol('Symbol.dispose'); Symbol.asyncDispose ??= Symbol('Symbol.asyncDispose');` as the first executable statement of every entry point before adopting `using` anywhere in that repo. | Computed class keys resolve at class-definition time, so the polyfill must precede *any* transitively imported module's `[Symbol.dispose]` member — not merely the `using` statement. Both tsc and esbuild throw a `TypeError` at first execution otherwise. | Read each entry point (`src/extension.ts`, `src/cli/*.ts`, `bin/*`): the assignment is the first executable line. Plus one smoke test that actually executes a `using` block, run on the runtime named in `engines.node`. | MUST |
| **TS-RES-06** | Use `using`/`await using` only where the resource's lifetime *is* the enclosing block — never for a value that is returned, stored on `this`/a ref, or pushed to `context.subscriptions`. | Disposal fires before a `return` completes, so a returned `using` binding hands the caller an already-disposed object; extension- and component-lifetime resources are the wrong shape entirely. | `grep -n "return \w\+;"` where that identifier was declared with `using` earlier in the same function — always wrong. Same for a `using` binding later pushed/assigned outward. | MUST |
| **TS-RES-07** | Never bind a `vscode.*` factory result directly with `using`; go through one shared `toDisposable` adapter per extension, and never write an inline `{ [Symbol.dispose]: … }` literal elsewhere. | `vscode.Disposable` has zero `Symbol.dispose` members, so this fails the type checker — and the fleet's habitual fix (`as unknown as T`, 164 occurrences) papers over the check and silently defeats disposal. | `grep -n "using .* = vscode\."` must only match `toDisposable(...)` wrappers; `grep -n "using .*as unknown as"` and `grep -n "\[Symbol\.dispose\]:"` outside the adapter's own file are findings. | MUST |
| **TS-RES-08** | Clear the previous handle before reassigning a debounce/rearm timer to the same variable. | The stale callback stays scheduled and races the new state — the toast-fade bug `Base.astro:323` exists to prevent. | For every `let`/`var` timer handle reassigned more than once in a file, a `clear*` on that variable must precede each reassignment after the first. | MUST |
| **TS-RES-09** | A `setInterval` or fire-and-forget `setTimeout` must either pair with a `clear*` reachable from its owner's teardown path, or carry a comment naming an *independently checkable* realm-teardown guarantee. | `main.ts:900-906`'s uncleared interval is correct only because the webview's script realm is destroyed atomically; the same reasoning is false in the extension host, which outlives any panel. Awaited `new Promise(r => setTimeout(r, ms))` sleeps are exempt — nothing owns the handle. | For each `setInterval(`/bare `setTimeout(` hit: either a reachable `clear*`, or the file is webview-side (imported only by `webview/**`, never from `activate()`) *and* no `retainContextWhenHidden: true` appears in its panel/view registration. | MUST |
| **TS-RES-10** | Never wrap an `@actions/exec` `exec`/`getExecOutput` call in `Promise.race`/`Promise.any` to fake a timeout; if a hard bound is genuinely needed, move that one call to `execFile`/`execa` and leave the rest. | `exec()` returns only `Promise<number>` — no `ChildProcess` is ever exposed, so racing stops the caller waiting while the process keeps running orphaned. | `grep -n "Promise.race\|Promise.any" src/` in `setup-ocx`; any hit touching an `@actions/exec` call is the finding, unconditionally. | MUST |
| **TS-RES-11** | Replace a `try/finally` whose `finally` only calls `.close()`/`.dispose()` with `await using` when the resource already implements the protocol — `fs/promises` `FileHandle` first. | `FileHandle` implements `Symbol.asyncDispose` natively and Node's own docs call GC-based auto-close unreliable; this is the narrow adoption target, and the only one where the conversion is mechanical. | `grep -n "finally {" -A2 src/` for bodies that only `close()`/`dispose()`; and `fsPromises.open(` sites not bound with `await using`. Preconditions TS-RES-04 and TS-RES-05 must already hold. | SHOULD |
| **TS-RES-12** | Register a `DisposableStack`/`AsyncDisposableStack` member in the same statement as its acquisition — `disposer.use(acquire())`, never on a following line. | Anything inserted between acquisition and `.use()` is a leak window if it throws (MDN's own guidance). | `grep -n "\.use("` — the argument must itself be a call or `new` expression on that line. | SHOULD |
| **TS-RES-13** | Prefer a bare `timeout:` over `signal: AbortSignal.timeout(ms)` on a child process unless a real cancel trigger (a `CancellationToken`, a superseding invocation) exists to compose with. | Both bound a duration identically; a `signal` with nothing that ever calls `.abort()` is dead code that reads as a feature. | `grep -rn "AbortController\|AbortSignal" src/` cross-checked against `grep -rn "CancellationToken" src/` — a `signal:` with no trigger in the same call chain. | CONSIDER |
| **TS-RES-14** | In repos where `tsc` itself emits JS (`ocx-catalog`, `grimoire-indexer`), set `"importHelpers": true` with a `tslib` dependency before adopting `using` broadly. | Otherwise every emitted file carries its own ~2 KB copy of `__addDisposableResource`/`__disposeResources`. | `grep -c "__addDisposableResource" dist/**/*.js` — more than one definition across files is the finding. | CONSIDER |
| **TS-RES-15** | A child-process call that runs **unattended** and spawns `git`, a package manager (`npm`/`pnpm`/`yarn`/`bun`), or anything under `shell: true` must pair its `timeout` with a group kill — `detached` at spawn, and your own timer calling `process.kill(-pid, …)` / `taskkill` — never the built-in `timeout` option alone. | The built-in `timeout` kills one PID. `git` over `ssh://` spawns `ssh`, which spawns `GIT_ASKPASS`; `npm` spawns lifecycle scripts. Node documents the survival verbatim and has shipped no fix ([#64406](https://github.com/nodejs/node/issues/64406) open). `Bun.spawn` has the identical limit — not an escape hatch. | For each such site: the options object sets `detached`, and the timeout handler calls a platform-branching kill helper, not `child.kill()`. **Exempt:** dev/CI-only spawns (build scripts, prepublish smoke tests, an interactive `init` scaffold's `npm install`) — a supervising human or CI job already owns tree cleanup, and hardening them is scope creep. "Unattended" means reachable from a runtime path an agent or scheduled job invokes. | MUST |
| **TS-RES-16** | Write `detached: process.platform !== "win32"`, never a bare `detached: true`; do not pair `detached` with `.unref()` on a child the caller still awaits; and make the Windows branch of the kill helper `taskkill /pid <pid> /t /f`. | On Windows `detached` means "own console window, outlives the parent" — an unrelated behaviour that pops a visible window on every run, and there is no process group Node can address by PID sign. `.unref()` is orthogonal to `detached` and silently changes whether the parent waits at all. | `grep -n "detached"` — every hit is a platform expression, not `true`. `grep -n "process.kill(-"` — every hit sits inside a non-`win32` branch. Each Windows branch contains `taskkill` with **both** `/t` and `/f`. | MUST |
| **TS-RES-17** | Never pass `killDescendants`, `forceKillAfterDelay`, `cancelSignal`, or `gracefulCancel` to a bare `child_process` `exec`/`execFile`/`spawn`. | These are `execa`-only option names. Node ignores unknown keys and TypeScript strips the excess property — no error, no warning, and the bound the author believes they added does not exist. Same class as TS-RES-10: the code reads as hardened and is not. | `grep -n "killDescendants\|forceKillAfterDelay\|cancelSignal\|gracefulCancel"` in any file that does not import from `execa`. Zero hits fleet-wide today; the first one is the finding. | MUST |
| **TS-RES-18** | Do not add `execa` or `tree-kill` for fewer than three call sites that actually meet TS-RES-15's bar; if adding it anyway, first diff the package's floor against the target's `engines.node` **and** against the runtime that is not `npm install`-selectable. | `execa@10.0.1` is ESM-only, `engines.node: ">=22"`, ~11 transitive deps — against `ocx-catalog`'s declared `>=20.19`, and against a VS Code extension host's bundled Node, which no `engines` field can move. `tree-kill` is the only tool that walks the real process tree (reaching a descendant that called `setsid()`), but its last publish is 2019-12-11 — technically interesting, not a live option. | Count TS-RES-15 sites in the target repo *before* any `package.json` edit. A PR adding `execa` for one call site, or one that bumps `engines.node` to satisfy it, is the finding. | MUST |

## AI-agent failure modes

Ranked by how often it bites.

1. **`Promise.race` around `@actions/exec` to "add a timeout."** Compiles, type-checks, appears to work in a manual test — and leaves the process running orphaned, because no handle is ever exposed. The single highest-value unconditional check in this topic (TS-RES-10).
2. **Adding a `timeout` and reporting the hang fixed.** Asked to "stop this from hanging," an agent adds `timeout` to a `git`/`npm`/`shell: true` call and stops — correctly, as far as the option's own doc paragraph goes. Node buries the caveat in the `kill()` section, so the descendant that outlives the kill is invisible from where the model was reading (TS-RES-15).
3. **One `catch` for both a spawn failure and a non-zero exit.** `try { await execFileAsync(...) } catch (e) { report(errorMessage(e)) }` looks complete and destroys the distinction the exemplar exists to preserve (TS-RES-02).
4. **Assuming `using` "just works" once `lib` is set.** The lib entry satisfies the type checker; the missing polyfill throws at the *first execution* on every fleet runtime below the native floor — invisible to `tsc --noEmit` and to any test that doesn't hit that exact branch (TS-RES-05).
5. **Copying `main.ts:900-906`'s "never cleared" comment into extension-host code.** The precedent is real and realm-specific; pattern-matching on the comment text without checking which side of the webview boundary the code runs on introduces a genuine leak while citing correct-looking authority (TS-RES-09).
6. **Casting past the `vscode.Disposable`/`using` type error.** The compiler catches the direct bind; the model's habitual fix is `as unknown as T` — the fleet's own most common escape hatch — which silently produces a resource that never disposes (TS-RES-07).
7. **Returning a `using`-bound value from the same function**, unaware disposal fires *before* the return completes. Mechanical conversion of a `try/finally` that returned the resource produces this every time (TS-RES-06).
8. **Claiming `DisposableStack`/`Symbol.dispose` availability for browser code from training data.** Availability changed repeatedly across 2023-2026; whether the project's *current* Vite/Oxc pin lowers for its *actual* browserslist is a live fact, not an inferable one — and oxc#25155 currently ships `using` unlowered to Safari with no build warning (TS-RES-04).
9. **Hallucinating `execa` options onto bare `child_process`** — `killDescendants`, `forceKillAfterDelay`, `cancelSignal`, `gracefulCancel` on an `execFile` options bag. TypeScript strips the excess property, Node ignores it at runtime, and the bound the agent thinks it added does not exist. Most likely right after the model has read execa's docs in the same session (TS-RES-17).
10. **Assuming a promisified callback's rejection carries `stdout`/`stderr` generically.** It does for `execFile` only because `execFile` ships its own `promisify.custom`; porting the pattern to another Node API loses both silently.
11. **Reaching for `execa` the moment descendant-kill comes up**, because it is the best-documented answer to "how do I kill a process tree in Node" — without counting qualifying call sites in the target repo or diffing its Node floor. The result compiles and works, and quietly moves `ocx-catalog`'s published `engines.node` for one function (TS-RES-18).
12. **Pasting `process.kill(-pid, sig)` onto a cross-platform path.** The negative-PID idiom is everywhere in POSIX-only codebases and reads as portable. On Windows it either throws or resolves to nothing — and two of this fleet's repos are VS Code extensions that run there (TS-RES-16).
13. **Pairing `detached: true` with a reflexive `.unref()`,** because "detached" pattern-matches to "background process." They are independent: the intent here is a killable process group while the caller still awaits normally, and `.unref()` silently removes the wait (TS-RES-16).

## Open questions

- **Human decision — does `using` get adopted at all, or is the FileHandle migration (TS-RES-11) deferred?** Every precondition (polyfill, target, `lib`, `importHelpers`) is real work in five repos to remove `try/finally` blocks that currently function correctly. The rules are written so that the *first* adoption is safe; whether to spend that budget now is not a technical call.
- **Human decision — `runGit`'s timeout value.** TS-RES-15's shape is settled and the patch is ~18 lines, but the duration is a judgment call: a cold `git clone` of a large catalog remote over a slow link is legitimately slow, and `30_000` in the sketch is a placeholder nobody has measured. Same class as the `installer.ts` question below.
- **Human decision — `installer.ts:242-251` bounds.** Adding a `timeout` to `tar` extraction is mechanical, but the right value depends on the largest supported grim release archive on the slowest supported `storageDir`. Nobody has that number.
- **Watch, don't decide yet: [oxc#25155](https://github.com/oxc-project/oxc/issues/25155).** Open and unresolved as of 2026-08-29, filed less than a month prior. TS-RES-04's Vite-8 clause is a workaround for a live bug; if it lands fixed, that clause simplifies to a version floor.
- **Unresolved fact, flagged not papered over:** `typescript@7.0.2` ships no `lib/lib.*.d.ts` files of any kind, and where the Go rewrite's type-library data lives could not be established. Any TS-RES rule depending on `lib: ["ESNext.Disposable"]` is verified against 5.9/6.0 only.
