## Summary

- `cargo_build_script`'s runner parses `cargo:KEY=VALUE` and `cargo::KEY=VALUE` lines from a build script's stdout into a fixed set of directives; `rerun-if-changed` and `rerun-if-env-changed` are parsed and then **explicitly discarded** — "Ignored because Bazel will re-run if those change all the time" ([cargo_build_script_runner/lib.rs:76-80](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/cargo_build_script_runner/lib.rs)).
- `rustc-cdylib-link-arg`, `rustc-link-arg-bin`, and `rustc-link-arg-bins` are recognized but **unsupported** — the runner prints a warning and drops them; a build.rs relying on per-binary link-arg scoping loses that scoping silently under Bazel ([lib.rs:101-109](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/cargo_build_script_runner/lib.rs)).
- A build script's action environment inherits `ctx.configuration.default_shell_env` by default (`use_default_shell_env` build-setting default `True`) "so crates like `cmake` can probe $PATH to find tools" — this is documented, intentional host-tool visibility, not an oversight ([cargo/settings/settings.bzl:38-44](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/settings/settings.bzl)). Whether that inherited env is the full client environment or only `--action_env`-listed variables is exactly the Bazel-8-vs-9 split BZL-HERM-01 already settles — cited, not restated.
- `use_cc_toolchain` (a `cargo_build_script`-only setting, `scope = "universal"`) defaults `True` ruleset-wide: **every** crate with a build.rs pulls in the resolved `cc_toolchain`'s `CC`/`CXX`/`AR`/`CFLAGS`/`CXXFLAGS`/`LDFLAGS`/`INCLUDE` by default, whether or not that build.rs touches C/C++ ([settings.bzl:46-67](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/settings/settings.bzl)).
- When `use_cc_toolchain` is disabled (or no `cc_toolchain` resolves), the runner substitutes `no_ar`/`no_cc`/`no_cxx` stub binaries that fail at **execution** time with `No binary provided for {program}` — a build script that never actually invokes `cc` never notices; one that does gets a late, cryptic failure ([cargo/private/BUILD.bazel](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/BUILD.bazel), [no_binary.rs](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/no_binary.rs)).
- `crate.annotation()` at 0.74.0 has 40 keyword parameters; the build-script-specific ones (`build_script_env`, `build_script_env_files`, `build_script_data`/`_glob`, `build_script_tools`, `build_script_deps`, `build_script_toolchains`, `build_script_use_cc_toolchain`, `build_script_use_default_shell_env`, `build_script_rundir`) are how a third-party crate's build.rs is patched from the outside without forking it ([crate_universe/private/crate.bzl:88-201](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/crate_universe/private/crate.bzl)).
- `override_targets` (keys `proc-macro`, `custom-build`, `lib`, `bin`) lets a parent repo substitute its own hand-written target for anything `crate_universe` would otherwise generate for that crate — the general-purpose escape hatch when annotation-level patching is not enough ([crate.bzl:193-194](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/crate_universe/private/crate.bzl)).
- `crate_universe` genuinely ignores intra-workspace path dependencies: `cargo-bazel`'s own metadata pass filters every workspace-member node out of the "generate an external crate" set before rendering BUILD content ([metadata_annotation.rs:191-213](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/crate_universe/src/metadata/metadata_annotation.rs)) — confirmed still true at 0.74.0, not just in the 2023 Tweag account that first named it.
- Nothing in `crate_universe` re-syncs a hand-written internal `deps = [...]` list against `Cargo.toml`'s path dependencies as either side changes. The one tool that can — `Calsign/gazelle_rust`, third-party and 0.1.0 — resolves `some_lib::Foobar`-style imports against a single project-wide namespace spanning both first-party crates and crate_universe crates ([gazelle_rust README §Assigning dependencies](https://raw.githubusercontent.com/Calsign/gazelle_rust/main/README.md)); its maturity and the correct verification form (`gazelle_test`, not a bare `gazelle -mode=diff`) are already `BZL-ARCH-11`/`BZL-ARCH-12` — cited, not restated.
- The 2019 proc-macro-builds-for-target bug (`rules_rust#205`) is **fixed** — closed as resolved by a cross-compilation transition (PRs #240/#272) with no unresolved thread since 2019-11-22.
- The **architecture** problem underneath it is not fixed: a single `rust_toolchain` rule still bundles `rustc`, `rustc_lib`, `cargo`, `clippy_driver`, `rustfmt`, and `rust_std` as one `ToolchainInfo` at 0.74.0 ([rust/private/toolchain.bzl:684-856](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/private/toolchain.bzl)) — exactly the shape `discussions#815` (2021) proposed splitting and never shipped (last comment 2022-01-27: "still possible through macro magic... without changing the toolchain interface itself").
- `extra_exec_rustc_flags_triples` (a `string_list_dict`, key = exec triple) is real, ships today, and is a **flag-level** knob only — it lets exec-configuration `rustc` invocations (host builds of proc-macros and build scripts) take different flags per host triple, but it does not give Bazel an independently resolvable host toolchain ([rust/extensions.bzl:262-267](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/extensions.bzl)).
- As of 0.74.0, every core rule (`rust_library`, `rust_binary`, `rust_test`, `rust_proc_macro`, `rust_static_library`, …) declares `@bazel_tools//tools/cpp:toolchain_type` with `mandatory = False` ([rust/private/rust.bzl](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/private/rust.bzl), every `toolchains = [...]` block) — the fix tracked by `rules_rust#1601` ("Support building pure-Rust targets without a C++ toolchain") landed at the rule level; that issue closed 2022-10-21 as "completed", though its own comment thread shows continued outside interest as late as 2025-05-02.
- That fix does not reach `cargo_build_script` in practice: its `use_cc_toolchain` build setting still defaults `True`, so any crate with a build.rs — nearly every non-trivial `crate_universe` closure — still triggers the C++ toolchain autodetection Bazel runs at module-extension setup, unless a repo both disables the setting and sets `BAZEL_DO_NOT_DETECT_CPP_TOOLCHAIN=1` (BZL-HERM-07, cited not restated).
- `rustc_env_files` (on `rust_library`/`rust_binary`/`rust_test`) and `rust_binary`'s `stamp` attribute (default `-1`, defer to `--stamp`) are the Bazel-native mechanism for baking git/CI provenance into a binary: a checked-in `NAME={STABLE_GIT_SHA}`-style file has its bracketed placeholders resolved from `ctx.info_file`/`ctx.version_file` at action-execution time, fed by a `--workspace_status_command` script that runs **outside** the sandbox ([rust/private/rust.bzl:853-871](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/private/rust.bzl); [rust/private/rustc.bzl:838-839,1112-1113](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/private/rustc.bzl)).
- The fleet's real `ocx_cli/build.rs` (`vergen-gix`) already ships the correct fallback for a `.git`-less tarball build ([build.rs:14-21](/home/mherwig/dev/ocx/crates/ocx_cli/build.rs)); under `cargo_build_script` that fallback fires **unconditionally**, on every Bazel build including a full clean checkout in CI — the sandboxed action's manifest-dir replica is built from `runfiles`, never includes `.git/`, and nothing declares `.git` as an input.

## Findings

### 1. What cargo_build_script does with cargo:* directives, and what it drops

`cargo_build_script`'s runner (a small first-party Rust binary, `cargo/private/cargo_build_script_runner`) reads the build script's stdout line by line and classifies each `cargo:KEY=VALUE` / `cargo::KEY=VALUE` line by `KEY`:

| Directive | Runner behaviour |
|---|---|
| `rustc-link-lib`, `rustc-link-search`, `rustc-cfg`, `rustc-flags`, `rustc-link-arg`, `rustc-env` | Captured and fed into the consuming crate's compile action (flags/env/link-search files declared as `BuildInfo` outputs) |
| `rerun-if-changed`, `rerun-if-env-changed` | **Parsed then discarded** — "Ignored because Bazel will re-run if those change all the time" |
| `warning` | Printed to stderr only when `emit_warnings` (per-target attribute or the `emit_build_script_warnings` flag) says to |
| `metadata` (the post-Cargo-1.77 `cargo::metadata=KEY=VALUE` spelling) and any other unrecognized `cargo::KEY=VALUE` | Forwarded as `DEP_<LINKS>_<KEY>=<VALUE>` to dependents, matching Cargo's own `links`-script convention |
| `rustc-cdylib-link-arg`, `rustc-link-arg-bin`, `rustc-link-arg-bins` | Recognized, **unsupported**: a warning is printed and the directive is dropped |

Source: [`cargo_build_script_runner/lib.rs:50-120`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/cargo_build_script_runner/lib.rs). The `rerun-if-*` behaviour is the one an LLM porting a build.rs is most likely to mis-model: Bazel already re-executes a `cargo_build_script` action whenever any of its declared inputs (source files, `data`, `build_script_env` values, the toolchain) change, so the whole "tell the build system when to invalidate me" half of Cargo's build-script contract has no Bazel equivalent to preserve — there is nothing to port, and a build.rs comment written for Cargo's benefit (like the fleet's own `println!("cargo:rerun-if-env-changed=CI")`, see [Fleet evidence](#fleet-evidence)) is inert but harmless under Bazel.

### 2. The default build-script action environment

`cargo_build_script`'s implementation builds an `env` dict from several sources, in this order ([`cargo_build_script.bzl` (private):399-581](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/cargo_build_script.bzl)):

1. `ctx.configuration.default_shell_env`, only if `use_default_shell_env` resolves `True` (build-setting default `True`, `cargo/settings/settings.bzl:38-44`) — this is the "crates like `cmake` can probe `$PATH`" line quoted in the Summary, and it is a deliberate design choice, not an accidental leak.
2. The fixed Cargo-compatible set: `CARGO`, `CARGO_CRATE_NAME`, `CARGO_MANIFEST_DIR`, `CARGO_PKG_*`, `HOST`, `TARGET`, `NUM_JOBS` (hardcoded to `"1"`), `OPT_LEVEL`, `DEBUG`/`PROFILE` (derived from `COMPILATION_MODE`), `RUSTC`, `RUSTDOC`.
3. Linker/CC environment (`CC`, `CXX`, `AR`, `LD`, `CFLAGS`, `CXXFLAGS`, `LDFLAGS`, `INCLUDE`) if `use_cc_toolchain` resolves a real `cc_toolchain` — see [§3](#3-use_cc_toolchain-on-by-default-with-a-loud-fallback-when-off).
4. `CARGO_ENCODED_RUSTFLAGS`, always including `--remap-path-prefix=${pwd}=.` — "Keep build scripts from baking the exec root into their output" (the code comment, `cargo_build_script.bzl:566-571`), i.e. the ruleset already defends against one classic non-determinism source (a baked-in absolute sandbox path) for anything that reads this variable, though a build script invoking `rustc`/`cc` directly rather than through the provided wrapper env does not get this for free.
5. `build_script_env` (per-target dict, or `crate.annotation(build_script_env=...)` for a third-party crate) merged last, with Make-variable location expansion against `data`/`tools`.

What is structurally absent, independent of any flag: **`.git`**. `CARGO_MANIFEST_DIR` is a synthesized path under a `runfiles`-backed directory that `_create_runfiles_dir` builds from the target's own `data`/`data_runfiles` ([`cargo_build_script.bzl:352-373`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/cargo_build_script.bzl)) — never the real repository root, and never anything that would contain a `.git/` directory unless a repo explicitly and unusually declared it as `data` (which would defeat action caching, since `.git`'s content changes on every commit). Network reachability and the sandbox's environment-inheritance policy (client `PATH`/`LD_LIBRARY_PATH` on Bazel 8.x vs. not on 9.0+) are exactly `BZL-HERM-02` and `BZL-HERM-01` — cited here, not re-derived.

### 3. use_cc_toolchain: on by default, with a loud fallback when off

`use_cc_toolchain` is a `cargo_build_script`-only bool flag (`@rules_rust//cargo/settings:use_cc_toolchain`), `scope = "universal"`, `build_setting_default = True` ([`settings.bzl:46-67`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/settings/settings.bzl)). Per-target, `cargo_build_script(use_cc_toolchain = ...)` is a tri-state int (`-1` defer / `0` force-off / `1` force-on, default `-1`), and `crate.annotation(build_script_use_cc_toolchain=...)` sets the same thing for a `crate_universe`-generated target.

```python
# Force-disable per third-party crate whose build.rs never touches C/C++,
# to shrink the action's input tree (particularly valuable with a hermetic sysroot):
crate.annotation(
    crate = "serde_derive",
    build_script_use_cc_toolchain = 0,
)
```

When the resolved value is `0` (or a `cc_toolchain` fails to resolve at all — the toolchain type is `mandatory = False`, see [§7](#7-does-rules_rust-still-require-a-c-toolchain-for-a-pure-rust-build)), the implementation substitutes stub tools for `AR`/`CC`/`CXX`:

```
CC=${pwd}/external/rules_rust/cargo/private/no_cc.exe
```

`no_cc.exe`/`no_ar.exe`/`no_cxx.exe` are all `copy_file` aliases of the same tiny `rust_binary`, `no_binary.rs` — "A cross platform implementation of `/bin/false`" — which prints `No binary provided for {program_name}` and exits 1 ([`cargo/private/BUILD.bazel`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/BUILD.bazel), [`no_binary.rs`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/cargo/private/no_binary.rs)). A build script that genuinely doesn't shell to a C compiler never notices; one that does — `cc`/`cmake`-rs crates being the common case — fails at **build-script execution time**, not analysis time, with that exact string in the log.

### 4. crate.annotation(): the escape hatch, attribute by attribute

`_annotation()` (public name `crate.annotation`) takes 40 keyword parameters and JSON-encodes them into the `crates_repository`/`crates.spec` graph ([`crate_universe/private/crate.bzl:88-252`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/crate_universe/private/crate.bzl)). The build-script-relevant subset, with the exact attribute each maps onto the generated `cargo_build_script` target:

| `crate.annotation()` param | Maps to `cargo_build_script`'s | Purpose |
|---|---|---|
| `build_script_env` (dict) | `build_script_env` | Env vars the build script sees — the Tweag `PCRE2_SYS_STATIC=1`-style pkg-config workaround (below) |
| `build_script_env_files` (labels) | `build_script_env_files` | `.env`-format files, bracket-stampable |
| `build_script_data` / `_glob` | `data` | Extra files/dirs the script may read |
| `build_script_tools` | `tools` | Extra executables the script may invoke |
| `build_script_deps`, `build_script_proc_macro_deps`, `build_script_link_deps` | `deps`, `proc_macro_deps`, `link_deps` | Extra Rust build-dependencies |
| `build_script_toolchains` | `toolchains` | Extra Bazel toolchains the action can see |
| `build_script_use_cc_toolchain` | `use_cc_toolchain` | See §3 |
| `build_script_use_default_shell_env` | `use_default_shell_env` | See §2 |
| `build_script_rundir` | `rundir` | Override the working directory the script runs in |
| `gen_build_script` (bool) | — | Authoritative override: force-generate or force-suppress the `cargo_build_script` target entirely |
| `additive_build_file_content` / `additive_build_file` | — | Raw extra Starlark appended to the generated `BUILD.bazel` for that crate |
| `override_targets` (dict, keys `proc-macro`/`custom-build`/`lib`/`bin`) | — | Replace what `crate_universe` would generate for that crate/target-kind with a hand-written label |

The Tweag account's worked example — a crate whose build.rs shells to `pkg-config` to locate a system PCRE2 install, breaking hermeticity — is fixed the same way today: `crate.annotation(build_script_env = {"PCRE2_SYS_STATIC": "1"})` forces the `*-sys` crate's build.rs down its static-link code path instead of probing the host ([tweag.io/blog/2023-07-27](https://www.tweag.io/blog/2023-07-27-building-rust-workspace-with-bazel/)). The mechanism (`build_script_env` → `cargo_build_script.build_script_env`) is unchanged at 0.74.0 — confirmed against the current attribute, not assumed from the 2023 post.

`override_targets` is the coarser tool: when a crate's whole build.rs (or its `lib`/`bin`/`proc-macro` output) needs to be something other than what `crate_universe` would render — for example a git-submodule fork that already carries a hand-written `BUILD.bazel` — `override_targets = {"lib": "@//third_party/mycrate:lib"}` substitutes that label everywhere the generated graph would otherwise point at the crate_universe-rendered one, with zero forking of the crate's own source.

### 5. crate_universe ignores workspace-member path dependencies

`cargo-bazel`'s metadata pass computes `workspace_members` from `cargo metadata`'s own `workspace_members` list, then explicitly excludes every workspace-member node before turning the dependency graph into "crates to render a BUILD target for":

```rust
// crate_universe/src/metadata/metadata_annotation.rs:191-213 (0.74.0)
let workspace_members: HashSet<&PackageId> = metadata.workspace_members.iter().collect();
let is_workspace_member = |id: &PackageId| -> bool { workspace_members.contains(id) };
// ...
.filter(|node| !is_workspace_member(&node.id))
```

A separate `SourceAnnotation::Path` case exists in the same file, but it is for a **non-workspace** local path source (Cargo's `path+file://…` lockfile encoding for something like a test fixture crate outside the workspace) — it is not the mechanism that resolves `ocx_cli`'s dependency on `ocx_lib` in the fleet's own workspace. Internal workspace edges never enter `crate_universe`'s generated output at all; they must be hand-written as ordinary `deps = ["//crates/ocx_lib"]` entries on the first-party `rust_library`/`rust_binary` BUILD targets, exactly as the 2023 Tweag account describes and as `blog.fahhem.com` independently confirms for a from-scratch setup ("we need to manually specify internal dependencies inside the workspace").

Nothing in `crate_universe` itself re-derives or checks that hand-written list against `Cargo.toml`'s `path = "../foo"` entries as either side drifts. The one tool positioned to close that gap is `Calsign/gazelle_rust`: its default (non-`generate_from_cargo`) mode parses every `.rs` file for import-shaped paths (`some_lib::Foobar`) and resolves each to whichever crate provides that name — first-party project crate or `crate_universe` crate — inside **one project-wide namespace** ([gazelle_rust README §Assigning dependencies](https://raw.githubusercontent.com/Calsign/gazelle_rust/main/README.md)). Run as a generator/checker (`bazel run //:gazelle`, gated in CI the correct way per `BZL-ARCH-12`'s `gazelle_test` form, not a bare `gazelle -mode=diff` shell step), this regenerates the internal `deps` list on every run rather than leaving it to drift; `gazelle_rust`'s own maturity (third-party, `0.1.0`, `rules_rust >= 0.40.0` compatible — cleared against the fleet's 0.74.0 pin) is `BZL-ARCH-11`'s finding, cited not restated. Without it, the hand-written list has no built-in sync mechanism at all.

### 6. Proc-macro host builds: a fixed bug and an unfixed architecture problem

Two distinct claims hide under "proc-macro crates must build for the host":

**The runtime-correctness bug is fixed.** [`bazelbuild/rules_rust#205`](https://github.com/bazelbuild/rules_rust/issues/205) (filed 2019-03-13): proc-macro crates were compiled for the *target* platform instead of the *host*, breaking them outright whenever the target lacked a standard library (the case for a proc-macro run at host compile time, always). The thread resolves via a Starlark configuration transition (PRs `#240`/`#272`, referenced by `m3rcuriel` on 2019-11-20) and closes with no further correctness complaint. An LLM citing this issue as still-open is citing 2019-era history, not current behaviour.

**The architecture problem it exposed is not fixed.** [`discussions#815`](https://github.com/bazelbuild/rules_rust/discussions/815) ("Splitting `rust_toolchain` into multiple toolchains", opened 2021-06-30) names the root cause directly: `rust_toolchain` is monolithic — one `rule()` bundling `rustc`, `rustc_lib`, `cargo`, `clippy_driver`, `rustfmt`, and `rust_std` — so Bazel's toolchain resolution cannot pick a host-appropriate `rustc` independently of a target-appropriate `rust_std`, forcing every exec/target pairing to carry a full, near-duplicate toolchain repository. A draft PR (`#800`) and several design rounds followed; the discussion's last comment (`UebelAndre`, 2022-01-27) concludes the split is "still possible through macro magic and repository rules" without changing the toolchain interface — i.e., abandoned as a public-API change. Confirmed unchanged at 0.74.0: `rust_toolchain`'s `attrs` still declare `cargo`, `cargo_clippy`, `clippy_driver`, `rust_doc`, `rust_std`, `rustc`, `rustc_lib`, `rustfmt` on one rule ([`rust/private/toolchain.bzl:684-856`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/private/toolchain.bzl)).

The shipped mitigation is `extra_exec_rustc_flags_triples` (module-extension tag, `attr.string_list_dict`, key = exec triple, value = flags), which is real and current: it fails loudly if combined with `extra_exec_rustc_flags` on the same toolchain tag ([`rust/extensions.bzl:116-146,262-267`](https://raw.githubusercontent.com/bazelbuild/rules_rust/0.74.0/rust/extensions.bzl)). It is correctly described as "partial": it lets host-side (exec-configuration) `rustc` invocations diverge from target-side ones *by flag*, without needing to resolve or maintain a second toolchain — but it does not give Bazel a mechanism to select, say, a different `rustc` version or a leaner host-only component set for exec builds. The underlying bundling `discussions#815` objected to is still there.

### 7. Does rules_rust still require a C++ toolchain for a pure-Rust build?

As of `blog.fahhem.com` (Sept 2024, rules_rust 0.51.0, Rust 1.81.0): "at this moment, `rules_rust` has a dependency on a C++ toolchain, even though for pure-Rust projects you don't need it," worked around with `apt install g++`, and tracked at [`rules_rust#1601`](https://github.com/bazelbuild/rules_rust/issues/1601) ("Support building pure-Rust targets without a C++ toolchain").

That issue closed **2022-10-21** with `state_reason: completed`, and the mechanism it proposed — marking the C++ toolchain type optional per [Bazel's own optional-toolchains feature](https://bazel.build/extending/toolchains#optional-toolchains) (shipped Bazel 6) — is present in the current source: every core rule (`rust_library`, `rust_binary`, `rust_test`, `rust_proc_macro`, `rust_static_library`, `rust_cdylib_library`, and the `_without_process_wrapper` variants) declares:

```python
fragments = ["cpp"],
toolchains = [
    str(Label("//rust:toolchain_type")),
    config_common.toolchain_type("@bazel_tools//tools/cpp:toolchain_type", mandatory = False),
],
```

(`rust/private/rust.bzl`, every rule definition, 0.74.0.) So at the level of `rust_library`/`rust_binary` themselves, the C++ toolchain is formally optional and a pure-Rust target with no `cc_library` deps and no build script does not require one to resolve.

The practical answer is narrower than "fixed," for two independent reasons, neither of them rules_rust's own rule attrs:

1. Bazel's own C++ autoconfiguration repository rule runs at `MODULE.bazel`/module-extension evaluation time regardless of whether any `cc_*` target exists anywhere in the graph — a fact this program's hermeticity dive already establishes and gives the off-switch for (`BAZEL_DO_NOT_DETECT_CPP_TOOLCHAIN=1`, `BZL-HERM-07`, cited not restated).
2. `cargo_build_script`'s `use_cc_toolchain` setting defaults `True` ruleset-wide ([§3](#3-use_cc_toolchain-on-by-default-with-a-loud-fallback-when-off)), so any crate carrying a build.rs — which is most of a non-trivial `crate_universe` closure (`libc`, `proc-macro2`, and dozens of common `*-sys` crates all ship one) — pulls the resolved `cc_toolchain` in by default even when that build.rs never touches C/C++.

So: the rule-level requirement the 2024 blog reported is gone; the practical, still-live requirement moved one layer up, to `crate_universe`'s own default build-script settings and to Bazel's unconditional autoconfiguration probe. `BZL-HERM-24` (rules_cc/rules_python defaults are non-hermetic until an explicit hermetic toolchain is registered) is the more general form of this same fact — cited, not restated.

### 8. Workspace-status stamping: the Bazel-native replacement for vergen-gix

`rust_library`/`rust_binary`/`rust_test` all take `rustc_env_files` (`attr.label_list`, files of `NAME=value` lines) and `rust_binary`'s own `stamp` attribute (tri-state int, `rust_binary` default **`-1`** — defer to the global `--stamp` flag; `rust_library`'s default is `0` — never stamp). The `rustc_env_files` doc states the mechanism directly:

> "the variables here are subject to [workspace status] stamping should the `stamp` attribute be enabled. Stamp variables should be wrapped in brackets in order to be resolved. E.g. `NAME={WORKSPACE_STATUS_VARIABLE}`."

(`rust/private/rust.bzl:853-871`, 0.74.0.) The plumbing is real, not aspirational: `rustc.bzl` only passes `ctx.version_file`/`ctx.info_file` to the compile action's process wrapper when `is_stamping_enabled(ctx, attr)` is true, as `--volatile-status-file`/`--stable-status-file` flags:

```
# rust/private/rustc.bzl:838-839, 1112-1113 (0.74.0)
stamp_info = [ctx.version_file, ctx.info_file] if stamp else []
...
process_wrapper_flags.add("--volatile-status-file", ctx.version_file)
process_wrapper_flags.add("--stable-status-file", ctx.info_file)
```

`ctx.info_file` (Bazel's stable-status.txt) and `ctx.version_file` (volatile-status.txt) are populated by a `--workspace_status_command` script that Bazel runs **once per build, outside every action sandbox** — with full, real access to `.git`, unlike a `cargo_build_script` action. `ctx.info_file`-sourced (`STABLE_`-prefixed) keys trigger a rebuild of every stamped target when they change; `ctx.version_file`-sourced keys do not — precisely the "value that must force a rebuild vs. one that may go stale" distinction `BZL-HERM-17` already states, and the `--stamp`-vs-target-default risk `BZL-HERM-18` already names (cited, not restated).

## Decisions

**Decision: `ocx_cli/build.rs`'s existing "no `.git/`" fallback path is the wrong thing to lean on under Bazel; a `--workspace_status_command` plus `rustc_env_files` stamping is the fix, and it is a real migration, not a drop-in.**

Evidence: `vergen-gix`'s git-derived instructions come from `GixBuilder`, which the build.rs already wraps in a caught-`Err` branch specifically for ".git/?"-less tarball builds ([build.rs:59-77](/home/mherwig/dev/ocx/crates/ocx_cli/build.rs)). Under `cargo_build_script`, `CARGO_MANIFEST_DIR` is a synthesized runfiles-backed path ([§2](#2-the-default-build-script-action-environment)) that never contains `.git/`, and no `.git` path is declared as a `data`/input anywhere in the toolchain — so `GixBuilder::default().build()` hits that same `Err` branch on **every** Bazel build, including a full, clean checkout in CI, not only genuine tarball builds. The consuming code, `commit_info()` in [`build_info.rs:116-128`](/home/mherwig/dev/ocx/crates/ocx_cli/src/app/build_info.rs), short-circuits its entire `CommitInfo` struct on `option_env!("VERGEN_GIT_SHA")?` — so `ocx version --format json`'s `commit` field would be unconditionally absent from any Bazel-built `ocx`, while a `cargo build` of the identical commit in the same CI job would include it. This is a **silent** behavioural divergence between the two build paths with no error and no warning surfaced to a consumer of the binary — only a `cargo:warning=vergen-gix metadata unavailable` line buried in the build-script action's log.

The other two `vergen`-sourced groups in the same file are **not** structurally broken by the sandbox — only by ordinary env-var plumbing, an already-solved BZL-HERM-04/06-class problem: `build_info()` (`VERGEN_BUILD_TIMESTAMP`/`VERGEN_CARGO_TARGET_TRIPLE`/`VERGEN_RUSTC_SEMVER`, `build_info.rs:130-144`) comes from `CargoBuilder`/`RustcBuilder`, neither of which touches git, and both `TARGET` and `RUSTC` are already populated in the `cargo_build_script` action's own env ([§2](#2-the-default-build-script-action-environment)); `ci_info()` (`GITHUB_*`, `build_info.rs:146-158`) only needs those variables threaded through `build_script_env`/`--action_env` in the CI leg's `.bazelrc`. So the fix is scoped narrowly to the git-provenance third: replace `GixBuilder` with a `tools/workspace_status.sh` that runs `git describe --always --dirty`/`git rev-parse HEAD` (outside the sandbox, with real `.git` access) and emits `STABLE_GIT_SHA`/`STABLE_GIT_DESCRIBE`/`STABLE_GIT_DIRTY` lines; set `build --workspace_status_command=tools/workspace_status.sh` in `.bazelrc`; give `ocx_cli`'s `rust_binary` a checked-in `rustc_env_files` target with `VERGEN_GIT_SHA={STABLE_GIT_SHA}`-style lines (keeping the existing env-var *names* means `build_info.rs` needs no changes at all); and set `stamp = -1` (the `rust_binary` default already matches this) so `--stamp` — not the target definition — controls whether a given invocation pays the rebuild cost.

Assumption named: this treats "identical `option_env!()` names, real values instead of a permanent `None`" as strictly better than "an honest, permanent `None` under Bazel with the code path unchanged." That is the right call for a CLI whose own JSON contract already documents every provenance field as optional (`build.rs:9-10,22-24`) — nothing downstream breaks either way — but it is a real piece of migration work (a new shell script, a new `.bazelrc` line, a new checked-in env-file target, and CI wiring for `GITHUB_*` forwarding), not something `crate_universe` or `cargo_build_script` does automatically. If the adopting team instead prefers "no git provenance under Bazel, ever, and say so," the existing fallback already delivers that for free with zero changes — the wrong assumption to make silently is that Bazel and Cargo produce the same `ocx version` output today; they do not.

## Normative guidance candidates

1. **Never rely on `cargo:rerun-if-changed`/`cargo:rerun-if-env-changed` for correctness inside a build.rs that must also work under Cargo and Bazel.** Rationale: rules_rust's runner parses and discards both directives outright; any invalidation logic that assumes they do something under Bazel is dead code there. Verify: named reading heuristic — a build.rs comment or design note that treats these directives as load-bearing for *Bazel* correctness (not just Cargo's own incremental cache) is a finding; the directives themselves are harmless to leave in for Cargo's benefit. Empty grep for the directive is not meaningful (their presence is fine, their assumed *effect* under Bazel is the finding). Severity: SHOULD. Bazel 7-9; rules_rust 0.74.0 (unchanged, no version floor). Settles: M-I-05.

Severity: MUST wherever a genuine git-provenance requirement exists; N/A otherwise. Bazel 7-9; rules_rust 0.74.0. Settles: M-I-05. Depends on: BZL-HERM-17, BZL-HERM-18.

Verify: named reading heuristic against `crates.bzl`/annotation definitions — a crate known to need a substituted target (forked source, vendored patch) using `additive_build_file_content` alone rather than `override_targets` is a finding on inspection, not a grep target (both are valid Starlark either way). 15. **Never write a build.rs review comment or migration note claiming "Bazel and this crate's `cargo build` behave identically" without checking whether the build.rs reads `.git`, the network, or a host tool via `PATH`.** Rationale: `use_default_shell_env`'s own doc frames host-`PATH`-probing as intentional (Rule not a bug), but that only covers tools reachable via the inherited shell env — it says nothing about network access (governed separately by `BZL-HERM-02`) or `.git` (never available at all, Rule 3). Bazel 7-9; rules_rust 0.74.0. Settles: M-I-05. Depends on: BZL-HERM-02.
16. **When a `rust_binary`/`rust_library` needs stamped values, set `stamp` explicitly at the target rather than relying on its rule default, and document which default applies.** Rationale: `rust_binary`'s `stamp` defaults `-1` (defer to `--stamp`) while `rust_library`'s defaults `0` (never) — a library and a binary in the same crate family behave differently by default with no warning, matching the general `*_binary`-vs-`*_test`/library divergence `BZL-HERM-18` already names at the whole-of-Bazel level. Verify: `bazel query 'attr(stamp, -1, kind(rust_binary, //...))'` to enumerate every binary deferring to the flag; confirm CI documents whether `--stamp` is set for the builds that matter. Severity: SHOULD. Bazel 7-9; rules_rust 0.74.0. Depends on: BZL-HERM-18.
17. **Grep for `no_ar.exe`/`no_cc.exe`/`no_cxx.exe`/`No binary provided for` in a failing `cargo_build_script` action's log before investigating the crate's own build.rs logic.** Rationale: this exact string, not a compiler error, is what a disabled or unresolved C++ toolchain produces — a cheap, decisive first check that avoids hours spent debugging build.rs logic that never runs. Verify: named reading heuristic (log-grep) applied at diagnosis time, not a static repo check. Severity: CONSIDER (diagnosis procedure — candidate for `bazel-diagnose`, not a standing repo check). ## Fleet evidence

- **`ocx/crates/ocx_cli/build.rs:1-118`** is the fleet's one real instance of everything this dive covers: `vergen-gix` bakes `VERGEN_*` (git/build/rustc/cargo), `__OCX_BUILD_*`, and `GITHUB_*` into `cargo:rustc-env` instructions, consumed via `option_env!()` in [`ocx_cli/src/app/build_info.rs`](/home/mherwig/dev/ocx/crates/ocx_cli/src/app/build_info.rs), all best-effort per the doc comment ([`build.rs:9-10,22-24`](/home/mherwig/dev/ocx/crates/ocx_cli/build.rs)). See [Decisions](#decisions) for the full analysis — the git-provenance third breaks unconditionally under `cargo_build_script`; the build/CI-provenance thirds do not.
- **`creeptd-ng/crates/creeptd-proto/build.rs`** is real codegen (`tonic-build`/`prost-build` against a vendored `protoc`) and, per its own docstring, "the single Rust protoc source for the whole workspace" ([fleet-bazel-readiness.md:120,281](../bazel-audit/fleet-bazel-readiness.md)) — this maps cleanly to a `rust_prost_library`/equivalent codegen target and needs none of this dive's cross-compilation/build-script-hermeticity findings, since it never reads `.git`, network, or a host tool.
- **`creeptd-ng/services/leaderboard/build.rs`, `services/profile/build.rs`** are `println!("cargo:rerun-if-changed=...")`-only, tracking an `.sqlx/` offline-query cache that does not exist in the repo — Rule 1 above (rerun-if-changed is a no-op under Bazel) applies to these directly, but they are otherwise inert; the live problem for these two crates is the `sqlx::query!` macro's own compile-time live-database dependency, which belongs to `BZL-HERM`'s general non-hermetic-build-dependency treatment, not to `cargo_build_script` mechanics specifically ([fleet-bazel-readiness.md:270](../bazel-audit/fleet-bazel-readiness.md)).
- **`grimoire/src/command/build.rs`** is not a Cargo build script at all (confirmed: no `build =` key in `grimoire/Cargo.toml`) — a false positive a naive `find -name build.rs` produces, already corrected by the wave-1 fleet audit ([fleet-bazel-readiness.md:122,288](../bazel-audit/fleet-bazel-readiness.md)); nothing in this dive applies to it.
- **Zero proc-macro crates exist anywhere in the fleet** ([bazel-topic-map.md M-I-07 row](../bazel-topic-map.md)) — Findings 6/9's host-build mechanics are grounded entirely on upstream sources for this fleet, not exercised by any repo, matching the map's own "uncovered" coverage marking for the row.
- **`ocx-mirror/crates/ocx_python/Cargo.toml:29-32`** carries 4 pinned-rev git dependencies on `astral-sh/uv` internals — a `crate_universe`-adjacent shape this dive does not cover (git-dependency handling, not path-dependency or build-script handling; that is `M-I-13`, assigned to no wave-3b dive listed in this brief) — named here only so it is not silently conflated with the path-dependency finding above.
- **No fleet Rust repo uses `crate_universe`, `crates_repository`, or `crates_vendor` today** — every finding above is grounded on the ruleset's own source and documentation (shape F), not on a fleet pass/violation, per the map's own coverage convention for this family.

## AI-agent angle

- **Treating `cargo:rerun-if-changed`/`cargo:rerun-if-env-changed` as something that needs a Bazel-side equivalent when porting a build.rs.** It has none, and none is needed — Bazel's own input-based invalidation already supersedes it. Smallest check: if a migration PR adds a genrule/aspect specifically to "watch" a file a build.rs already names in `rerun-if-changed`, that work is redundant; delete it.
- **Citing `rules_rust#205` (proc-macro-built-for-target) as a live risk.** It closed in 2019. Smallest check: any guidance draft citing `#205` should read its close date before citing it as current; redirect to `discussions#815` for the actually-open architecture question.
- **Citing "rules_rust requires a C++ toolchain for pure-Rust builds" as an unconditional, current fact from a 2023-2024-era blog.** The rule-level requirement is gone (`mandatory = False` since the fix tracked by `#1601`); the practical default-on behaviour survives only in `cargo_build_script`'s `use_cc_toolchain` setting. Smallest check: does the guidance name `use_cc_toolchain`/`cargo_build_script` specifically, or does it make the claim about `rust_library`/`rust_binary` generally? The latter is now wrong.
- **Assuming a build.rs that reads `.git` (via `vergen`, `git2`, or a raw `Command::new("git")`) "just works" under Bazel the way it does under a local `cargo build`.** It cannot — there is no code path by which `.git` reaches a `cargo_build_script` sandbox. Smallest check: `grep -rln 'vergen\|git2\|Command::new("git")' **/build.rs`; any hit needs an explicit stamping plan (Finding 8), not an assumption that the crate's own tarball-build fallback quietly covers Bazel too (it does, but silently and probably not on purpose — see Decisions).
- **Inventing a `stamp` attribute on `cargo_build_script` itself, or expecting `build_script_env_files`' bracket-stamping syntax to apply there.** `cargo_build_script` has no `stamp` attribute at all in its `attrs` dict at 0.74.0 — stamping is a `rust_library`/`rust_binary`/`rust_test` mechanism (`rustc_env_files`), not a build-script one, even though `build_script_env_files`' own doc comment mentions workspace-status stamping in passing. Smallest check: `grep -n '"stamp"' cargo/private/cargo_build_script.bzl` on whatever `rules_rust` version is pinned — absence confirms the attribute genuinely does not exist there.
- **Reaching for a second `rust_toolchain` registration to "give proc-macros their own toolchain" instead of `extra_exec_rustc_flags_triples`.** Nothing in the public API supports independently swapping components of the bundled `ToolchainInfo`; a second full `rust_toolchain` repository duplicates the entire asset bundle (`discussions#815`'s exact complaint) for a problem `extra_exec_rustc_flags_triples` already solves at the flag level for the common case (host-triple-specific `rustc` flags). Smallest check: does the proposed fix touch `MODULE.bazel`'s `rust.toolchain()` tag's `extra_exec_rustc_flags_triples`, or does it register an entirely new toolchain set? The latter is very likely solving the wrong layer.
- **Assuming `crate.annotation(override_targets=...)` and `additive_build_file_content` are interchangeable "extra BUILD content" knobs.** They are not: one substitutes a generated target wholesale, the other only appends. Smallest check: does the intended change *replace* what `crate_universe` would generate (needs `override_targets`) or merely *add* something alongside it (needs `additive_build_file_content`)? Picking the appending form for a replacement need leaves the original, wrong target still generated and potentially still referenced elsewhere in the graph.

## Contested / evolving

- **Whether "`rules_rust` requires a C++ toolchain" is settled.** Genuinely improved since the 2024 blog account (rule-level `mandatory = False` landed via `#1601`), but the practical default (`cargo_build_script`'s `use_cc_toolchain=True`) means most real workspaces with third-party crates still trigger it today. Trending toward the optional model in principle; not yet in the common-case default. As of 2026-09-05, state both halves — never just one.
- **Whether the monolithic-`ToolchainInfo` architecture will ever be split.** `discussions#815` (2021) proposed it, drew maintainer pushback on ergonomics grounds (`hlopko`'s comments), and the last update (2022-01-27) treats the split as achievable only "through macro magic" without a public-API change. No open PR, no roadmap item found in this dive's sources. Trending: toward permanent flag-level mitigation (`extra_exec_rustc_flags_triples`) rather than a toolchain-shape change — treat the bundling as a durable property of the ruleset, not a temporary gap.
- **`gazelle_rust`'s fitness as the sync mechanism for internal dependencies.** It is the only tool that closes the gap `crate_universe` structurally cannot, but it is third-party and `0.1.0` — `BZL-ARCH-11`'s maturity finding applies at full force here. A repo betting its internal-dependency hygiene on a pre-1.0 plugin is a real, live trade-off, not a settled recommendation; this dive states the mechanism and leaves the adoption call to the reader, per `BZL-ARCH-11`.
- **`root_path` on `cargo_build_script`'s public macro.** Landed via [`#4243`](https://github.com/bazelbuild/rules_rust/pull/4243), merged 2026-08-27, one day before the 0.74.0 tag — present at `cargo/private/cargo_build_script_wrapper.bzl:35` but easy to miss if reading only the older `cargo_build_script.md` doc index, since the attribute lives on the public macro wrapper, not the private rule this dive otherwise quotes throughout. Named here as a live instance of this program's own conflict-8 pattern (a doc/release surface can be *behind* the tagged source, not just ahead of it) — worth re-verifying against whichever minor is pinned when this guidance is next refreshed.
