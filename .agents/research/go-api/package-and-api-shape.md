## Summary

- Never add a new `pkg/` directory; a single-binary CLI keeps `main` at the module root; `cmd/<name>/` appears only with a second binary or an importable library sharing the repo; the SDK's non-API code lives under `internal/` — [go.dev/doc/modules/layout](https://go.dev/doc/modules/layout), measured 11/34 `pkg/` with a stated rationale in only 1 ([shape](../go-audit/exemplar-code-shape.md) §1).
- Interfaces are ~55% producer-side / ~45% consumer-side in the corpus at n=20 — "accept interfaces, return structs" holds for constructors (80% concrete) but producer-side interfaces are legitimate for a real subsystem abstraction with several implementations; the defect a reviewer names is an exported interface with exactly one implementation and no external implementer.
- The options decision is a procedure, not a single pattern: positional parameters for required inputs, a config struct with a useful zero value for a small/closed optional set, functional options (func-typed, returning `error` when options can conflict) for a growing public constructor — and a second, interface-typed options flavor (`grpc-go`'s `DialOption`) is equally legitimate and invisible to a naive `func(` grep.
- `gochecknoglobals` already exempts identifiers that look like error sentinels by name (`Err*`), so it is safe to enable as a MUST-backing linter with no extra allowlist for GO-ERR-17-compliant code — verified by fixture, not assumed.
- Doc-comment enforcement is staticcheck's `ST1000`/`ST1020`/`ST1021`/`ST1022` (all **non-default**, must be turned on explicitly) plus revive's `exported`; both were run against a planted violation and fired exactly as documented.
- `//go:fix inline` (Go 1.26+) is the self-deprecation mechanism: mark the old declaration, `go fix -diff` reports the pending rewrite (exit 1) until callers are migrated, then exits 0 — verified end-to-end on a real fixture.
- `apidiff` never fails a build by itself — it always exits 0 and is a report-only diff tool; the CI-blocking mechanism is `gorelease`, and its exit code is major-version-dependent by design: a v0 module's incompatible change exits 0 (tolerated), the identical change in a v1+ module exits 1 (blocking) — both confirmed by running the real tool against a planted removed method.
- The fleet's major-version strategy split in the wild: `grpc/grpc-go` stays unsuffixed at v1 forever; `google/go-github` is at `/v92` — the map folds this into this brief: state which strategy fleet libraries take, not which is universally correct.
- `go vet`'s `composites` check catches an unkeyed literal of another module's exported struct type; it does not fire on same-package literals, and it does not catch an `IsLocal`-guarded `filepath.Join` (a different check, gosec G305, GO-IO-02).
- No linter separates "copies a returned slice" from "leaks the internal slice" (M-D-07) — the verification is a behavioral test proving the mutation reaches (or does not reach) the source's internal state, matching the pattern already used for GO-ERR-18's `errors.Join` row.
- Embedding a type into a public struct is a documented Uber anti-pattern (method-set leakage, breaking-change surface on the embedded type's own evolution) with no linter; it is a reading heuristic: does an exported struct embed an unexported field whose methods are now promoted onto the public API?
- `exhaustive` (nishanths/exhaustive, bundled in golangci-lint) is the compile-time-adjacent substitute for Go's lack of closed sum types on a typed enum switch; confirmed to fire on a missing case and pass once every case is covered, even with a `default:` present.
- Doc-comment syntax is formal since Go 1.19: package comments begin `Package x …`; `Deprecated:` (capital D, colon, one space) is the exact tooling-recognized prefix; `[Name]`/`[pkg.Name]` are doc links, not Markdown links — [go.dev/doc/comment](https://go.dev/doc/comment).
- `context.Context` struct fields, unkeyed literals of your own package's types, and loop-variable copies are documented anti-patterns that flagship Go-team-adjacent repos (etcd, terraform, grpc-go) still carry — style guidance and practice have diverged; a rule set that flags every instance without a "real subsystem abstraction" or "documented invariant" escape hatch will out-argue its own exemplars.
- `google.github.io/styleguide/go/decisions` states the consumer-side interface rule and "functions should take interfaces as arguments but return concrete types" in nearly identical language to the wiki's Code Review Comments — both normative sources agree; measurement (§ Findings 2–3) is what supplies the "not absolute" nuance.
- A rule that only teaches `type Option func(*T)` will misjudge `grpc/grpc-go`'s 100% interface-typed options surface; any options guidance must show both shapes side by side.
- Constructors returning an interface (`ireturn`) is measured 4/20 = 20%; `ireturn` linter is available via golangci-lint and was watched red on a planted violation and green on a concrete-return twin.
- The receiver-naming/var-naming family (ST1003, ST1016, revive `var-naming`/`receiver-naming`) is all **non-default** — the same enablement gap as the doc-comment family, and the two should be turned on together, not separately, since both live in the same `staticcheck.checks`/`revive.rules` config blocks.

## Findings

### 1. Package layout: never a new `pkg/`

[go.dev/doc/modules/layout](https://go.dev/doc/modules/layout) walks seven shapes (basic package, basic command, package-or-command-with-supporting-packages, multiple packages, multiple commands, packages-and-commands-in-the-same-repo, server project). Fetched in full: **`pkg/` is never mentioned anywhere in the document** — it is not a rejected pattern, it is simply absent from Go's own canonical answer. `internal/` appears from shape 3 onward with exact wording: *"it's recommended placing such packages into a directory named `internal`; this prevents other modules from depending on packages we don't necessarily want to expose and support for external uses."* `cmd/` first appears at shape 5 as an explicit convention, not a requirement, for a repository of multiple commands: *"A common convention is placing all commands in a repository into a `cmd` directory; while this isn't strictly necessary in a repository that consists only of commands, it's very useful in a mixed repository."* Shape 7 (server project) is the strongest recommendation for both: *"it's recommended to keep the Go packages implementing the server's logic in the `internal` directory… it's a good idea to keep all Go commands together in a `cmd` directory."*

Measured: `cmd/` in 21/34 repos, `internal/` in 26/34, `pkg/` in 11/34 with a stated rationale in a top-level doc in only 1 of the 11 (`containerd`) ([shape](../go-audit/exemplar-code-shape.md) §1). `pkg/` usage in the other 10 is carried-over ecosystem convention, not a documented per-repo decision. `api/` in 3/34, all three protobuf/gRPC-surface directories, not incidental.

Laurent Demailly's argued position sharpens the "never new `pkg/`" default further: *"99% of people do not need `internal/`"* and `pkg/` is *"a very outdated convention from before `internal/`"* with no advantage over root-level packages ([practitioner.md](../go-topic-map/practitioner.md) §14). The map's resolution (conflict 6) accepts Demailly's claim for single-binary CLIs and rejects it for the SDK: the SDK's non-API code lives under `internal/` — the compiler-enforced analogue of ocx-sdk-python's underscore-prefixed modules ([config-inventory](../go-audit/config-inventory.md) §3).

The directory-count proxy for `go list ./...` **overcounts by 1–66x** on any repo with more than one `go.mod` or an underscore-prefixed directory (`charmbracelet/bubbletea`: 66 directories by `find`, 1 real package by `go list ./...`, because `examples/`, `tutorials/` are nested modules) ([shape](../go-audit/exemplar-code-shape.md) § go list vs. directory-count proxy). A layout check that shells out to `find` instead of `go list ./...` is unreliable on exactly the multi-module repos (10/34 here) where it matters most.

### 2. Interface placement: consumer-side default, producer-side for real subsystems

Normative: [go.dev/wiki/CodeReviewComments §Interfaces](https://go.dev/wiki/CodeReviewComments#interfaces) — *"Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values."* Google's own decisions doc: *"The consumer of the interface should define it (not the package implementing the interface)"* and *"Avoid creating interfaces until a real need exists."* Both sources point the same direction.

Measured (sample of 20, 5 repos: `google/go-containerregistry`, `kubernetes-sigs/controller-runtime`, `restic/restic`, `oras-project/oras-go`, `cli/cli`): unexported interface names (`temporary`, `withManifests`, `haver`, `discardReader`, `runner`) were **100% consumer-side** — small (1–3 methods), declared where used, classic duck typing. Exported names leaned **producer-side 8/12** (`Cache`, `EventRecorder`, `Migration`, `ConfigFile`, `Invoker` — one true abstraction, multiple real implementations) vs. 4/12 consumer-side utility interfaces. Overall split ~55% producer-side / ~45% consumer-side at n=20 ([shape](../go-audit/exemplar-code-shape.md) §6) — not the "interfaces are always consumer-defined" purism some style guides teach in isolation.

**Resolved (map conflict 5, imported as settled):** the measured producer-side interfaces are subsystem abstractions with several real implementations, which the normative text does not forbid. The finding a reviewer names is narrower than "any producer-side interface": an exported interface with exactly one implementation and no external implementer, or a constructor returning an interface with no documented reason. `ireturn` (golangci-lint-bundled) catches the constructor half mechanically; the "one implementation" half is a reading heuristic — grep the interface's method set, then `grep -rn` for `var _ IfaceName =` assertions or literal `IfaceName` type usage across the module to count implementers.

Arundel's Tao of Go sharpens the framing further: *"don't make users implement our interfaces; we aim to implement theirs"* — a consumer-side framing distinct from, and slightly sharper than, the generic "accept interfaces" proverb ([practitioner.md](../go-topic-map/practitioner.md) §18).

`context.Context` stored in a struct field is a related, separate anti-pattern: 219 hits across 15/34 repos, and golangci-lint's own `containedctx` linter exists specifically to flag it — yet etcd, terraform, tailscale and grpc-go all do it anyway, spot-read 6/6 genuine uses at `etcd-io/etcd@7583cc6e7e27:client/v3/concurrency/session.go:120` ([shape](../go-audit/exemplar-code-shape.md) §6). Style guidance and practice have diverged in the wild; a rule that treats this as an absolute MUST NOT will contradict its own flagship exemplars — SHOULD, with a documented reason, is the honest severity.

### 3. Constructors return concrete types, accept narrow interfaces

Measured (sample of 20, 4 repos): 16/20 (80%) return a concrete pointer or value type; 4/20 (20%) return an interface (`client.WithWatch`, `Registry`, `location.Factory`, `io.ReadSeekCloser`) — verified exceptions at `kubernetes-sigs/controller-runtime@d0127f7f66de:pkg/webhook/conversion/conversion_registry.go:40` (`func NewRegistry() Registry`) and `restic/restic@5127c4abf921:internal/backend/location/registry.go:32` (`type Factory interface`). This **confirms "accept interfaces, return structs" empirically**, not just as folklore ([shape](../go-audit/exemplar-code-shape.md) §6, "Patterns worth encoding").

The Google style guide states the accepting half directly: *"functions should take interfaces as arguments but return concrete types."* The wiki's version: *"Implementations should return concrete types to enable future expansion without refactoring."*

**Verification:** `ireturn` (golangci-lint v2.14.0's bundled linter). Watched red and green against a planted fixture (§ Verification runs). One caveat from the exemplar exceptions above: `ireturn` will also flag the 20% of legitimate cases (a `Factory`/`Registry`-shaped subsystem constructor), so its finding needs the same "real subsystem abstraction, several implementations" escape hatch as row 2 — it is a strong SHOULD with a documented-reason override, not an unconditional MUST.

### 4. Options: a decision procedure, not a winner

The map's conflict 4 frames this as unresolved between two normative-adjacent sources and settles it as a decision procedure. [google.github.io/styleguide/go/best-practices](https://google.github.io/styleguide/go/best-practices) names two named patterns with explicit "when to use" criteria, fetched verbatim:

- **Option structure** — *"a struct type that collects some or all of the arguments of a function or method, that is then passed as the last argument."* Use when *"all callers need to specify one or more of the options,"* *"a large number of callers need to provide many options,"* or *"the options are shared between multiple functions that the user will call."*
- **Variadic options** — *"exported functions… return closures that can be passed to the variadic (`...`) parameter."* Use when *"most callers will not need to specify any options," "most options are used infrequently," "there are a large number of options," "options require arguments."* Explicit ordering rule: *"options should be processed in order. If there is a conflict or if a non-cumulative option is passed multiple times, the last argument should win."*

Rob Pike's original post frames self-referential functional options as solving the "package with dozens of settings" scaling problem that option structs and variant constructors leave *"unsatisfactory."* Dave Cheney's canonical write-up (fetched) frames the config-struct alternative's specific costs: a caller must pass a value even when using defaults, a zero value becomes ambiguous ("default" vs. "explicitly set to zero"), and a caller can retain a mutable reference to the configuration. Both are the load-bearing "why functional options at all" citations the corpus repeatedly points at.

**The counter-argument, not a rejection:** rednafi's dysfunctional-options-pattern post (argued, dated March 2024) measures a builder/chaining alternative as allocation-cheaper and *explicitly concedes* functional options *"solves a valid problem and definitely has its place"* — this is a qualified critique of overuse, not a rejection of the pattern ([practitioner.md](../go-topic-map/practitioner.md) §11).

**Measured, and the reason a naive grep misses half the picture:** the func-typed flavor (`type FooOption func(*fooConfig)`) undercounts on a literal `type Option func(` grep (46 hits) because most repos name it `<Thing>Option(s)`; broadening to `type \w*Options?\w* func\(` finds **107** corpus-wide (`aquasecurity/trivy@ae561f8cca36` 29, `google/go-containerregistry@0c8bedb78437` 16, `etcd-io/etcd@7583cc6e7e27` 15). **A second, interface-typed flavor is invisible to any func-typed grep**: `grpc/grpc-go@acccf8cd101a:dialoptions.go:102` declares `type DialOption interface { apply(*dialOptions) }`, plus `ServerOption`, `PluginOption` — grpc-go's options are 100% interface-based, 0% func-based ([shape](../go-audit/exemplar-code-shape.md) §3).

**Error-returning options, when they can conflict:** `google/go-containerregistry`'s `type Option func(*options) error` documents `WithAuth` and `WithAuthFromKeychain` as mutually exclusive — *"It is an error to use both… in the same Option set"* ([domain.md](../go-topic-map/domain.md) §9). This is the concrete precedent for "func-typed, returning `error` when options can conflict."

**Resolved (imported from the map):** required inputs are positional parameters; a small or closed optional set is a config struct whose zero value is the default; an exported constructor of a published SDK whose options will grow across minor versions uses functional options — func-typed and returning `error` when options can conflict, interface-typed only when options must be opaque or comparable. Both flavors are recognized in review; a linter or grep that recognizes only one will silently pass the other half of the ecosystem's APIs.

### 5. Zero value useful

Rob Pike's proverb: *"Make the zero value useful."* Uber's guide sharpens it to a specific, common over-engineering smell: *"Zero-value Mutexes are Valid"* — *"no explicit init needed, a common source of over-engineered constructors"* ([codified.md](../go-topic-map/codified.md) §9). No linter in the roster checks this directly; it is a reading heuristic — does an exported type require a constructor purely to zero-initialize a `sync.Mutex` or a `map`/`slice` field that would otherwise be usable nil (a nil map reads as empty; a nil slice ranges as empty)? If the only reason `NewX()` exists is to satisfy this, the type's zero value should be redefined to be useful instead.

### 6. Copy slices and maps at boundaries

Uber's guide, fetched: *"Copy Slices and Maps at Boundaries"* — an aliasing/mutation-leak rule for public APIs, framed as method-set leakage risk in the embedding section and as a data-race and unintended-mutation risk here specifically. [shape](../go-audit/exemplar-code-shape.md)'s failure-mode framing: slices are the largest race category in the corpus's concurrency findings (cited from `[fail]` §3 by the map).

**No linter checks this** — confirmed during this dive: no analyzer in the golangci-lint v2.14.0 roster, staticcheck, revive, or gocritic flags "a method returns a struct's own slice/map field without copying it." The verification is a **behavioral proof**, the same pattern established for GO-ERR-18's `errors.Join` row: a violation fixture where mutating the returned slice provably corrupts the source's internal state, and a twin fixture where it provably does not (§ Verification runs). Both tests *pass* — the difference is which behavior each one asserts, not a red/green analyzer signal.

### 7. Global state and `init()`

Google's litmus test, fetched verbatim: does removing a piece of package-level state *"ever require changing every caller's test setup? then it shouldn't be global."* Uber's parallel rule: *"Avoid Mutable Globals"* — recommends injecting a dependency (a struct field) rather than mutating a package var, illustrated with a `_timeNow` function-pointer example rewritten into a struct with a `now` field.

Measured: `init()` 1,040 corpus-wide; mutable package vars (heuristic: `^var [A-Za-z]…` minus `Err*=`, `errors.New(`, `fmt.Errorf(`, blank-identifier assertions) 4,875; panics outside `main` 4,236; `os.Exit`/`log.Fatal*` outside `main` 285/359 ([shape](../go-audit/exemplar-code-shape.md) §4). Spot-read of 6 `tailscale/tailscale` hits: 0/6 false positives, though the heuristic does not separate "genuinely mutable" from "effectively immutable, declared `var` because Go has no way to express a compile-time constant" (an OLE GUID constant is one such case) — the heuristic over-includes both under one count, which a reviewer must read past.

**Verification:** `gochecknoglobals` (golangci-lint-bundled, opt-in). **Measured directly in this dive, not assumed:** the linter already exempts identifiers whose name matches the `Err*` sentinel-error convention — `ErrTimeout` (exported) was **not** flagged while `defaultTimeout` (unexported int), `timeoutFailure` (unexported `error`-typed, non-`Err`-named) and `DefaultTimeout` (exported, non-`Err`-named int) **were all flagged** (§ Verification runs). This means `gochecknoglobals` is safe to enable as a MUST-backing linter for GO-ERR-17-compliant code (sentinels named `Err*`) with no additional allowlist config — a fact worth stating explicitly since the map left "config gap" as an open question for several linters in this family.

`init()` gets no dedicated linter in this roster beyond `gochecknoinits` (not independently re-verified in this dive; cited from the map's row).

### 8. Doc-comment MUSTs and the checks that enforce them

[go.dev/doc/comment](https://go.dev/doc/comment), fetched in full. Exact, checkable conventions:

- **Package comment:** first sentence begins `Package x …` immediately before the `package` clause. Example fetched: `// Package path implements utility routines…`
- **Command package:** first sentence conventionally begins with the program's name, capitalized (`Gofmt formats Go programs.`).
- **Function/method:** explain what it returns, or for a side-effect function, what it does; named parameters/results may be referenced directly by name.
- **Type:** start with a complete sentence naming the type (`// A Reader serves content from a ZIP archive.`).
- **Deprecation notice — exact format:** a paragraph beginning **`Deprecated: `** (capital D, colon, one space) — this is the literal prefix `go vet`, IDEs and pkg.go.dev key off; anything else (`// deprecated:`, `// DEPRECATED`, `// Deprecated -`) is not recognized.
- **Doc links:** `[Name]`, `[Name1.Name2]`, `[pkg]`, `[pkg.Name1]`, `[*bytes.Buffer]` — rendered as pkg.go.dev hyperlinks, distinct from Markdown `[text](url)` links. `pkg` is only resolved as a full import path if it contains a dot or is a stdlib package name; otherwise it is resolved against the file's own imports.
- **Headings:** `# Heading text` — must be unindented, a single line, and blank-line-separated from surrounding paragraph text; `#Text` (no space) and multi-line headings are not recognized.
- **Common mistakes**, all fetched with before/after examples: unindented numbered/bulleted lists render as unintended code blocks; unindented multi-line shell commands or JSON blocks likewise; continuation lines of an ordinary paragraph must **not** be indented, while continuation lines of a list or code block **must** be.

**Enforcement — the doc-comment half of M-M-09:** staticcheck's `ST1000` ("at least one file in a package should have a package comment"), `ST1020`/`ST1021`/`ST1022` (comment on an exported func/type/const should start with its name) are **all flagged non-default** in staticcheck 2026.2.1's own check registry — 7 checks total carry the `NonDefault` badge, and these are 4 of the 7 ([codified.md](../go-topic-map/codified.md) §5, `dominikh/go-tools@6cb65e58a558`). `ST1003` (identifier naming) and `ST1016` (receiver-name consistency) are the other three non-default checks in this same family (§13 below). None of the seven fire under a bare `staticcheck ./...` or a bare golangci-lint `staticcheck` enable — they require an explicit `checks` list.

revive's `exported` rule (golangci-lint-bundled, opt-in via `revive.rules`) independently catches missing doc comments on exported functions, methods, and (with `check-public-interface`) interface methods; it is a different tool from staticcheck's `ST102x` family and checks a superset (doc-comment *presence*, not the `ST1020`-style first-word format).

**Both watched red and green on planted fixtures**, two independent ways: (a) `staticcheck -checks="ST1000,ST1020,ST1021,ST1022"` directly, and (b) `golangci-lint` with `settings.staticcheck.checks: [all]` — both fired identically on the same violation (§ Verification runs). revive's `exported` fired independently on a separate fixture missing only the function comment.

Code Review Comments' framing is the shortest normative statement of the MUST itself: *"All top-level, exported names should have doc comments, as should non-trivial unexported type or function declarations,"* and *"Comments documenting declarations must be complete sentences beginning with the entity name and ending with a period."*

### 9. Self-deprecation: `Deprecated:` plus `//go:fix inline`

[go.dev/blog/inliner](https://go.dev/blog/inliner), fetched. `//go:fix inline` is a directive comment placed directly above a func, type-alias, or const declaration. On a func, `go fix` inlines every call site into a copy of the declaration's body with arguments substituted; the canonical example fetched from the post is `ioutil.ReadFile` rewritten in place to `os.ReadFile` at every caller. It also applies to type aliases (`//go:fix inline` above `type Rational = newmath.Rational`) and constants (`//go:fix inline` above `const Pi = newmath.Pi`), rewriting every reference to the new target throughout the codebase. This is the Go 1.26 "self-service" migration mechanism named in the map (M3) — a package author drives its own callers' migration without a hand-written codemod.

**Verified end-to-end on a real fixture, not read-only:** a package declares `GreetOld` with `// Deprecated: use [Greet] instead.` and `//go:fix inline` above it, calling through to `Greet`. A caller still invoking `GreetOld` is the violation: `go fix -diff ./...` prints the exact rewrite and **exits 1**. Applying `go fix ./...` rewrites the call site to call `Greet` directly; running `go fix -diff ./...` again on the now-fixed code **exits 0**, identical to a twin fixture whose caller already calls `Greet` directly (§ Verification runs). This is the concrete mechanism behind "the go-upgrade skill's `go fix -diff` step is a real CI gate, not advisory" already established in GO-GATE-01/GO-GATE-03.

The combination — a `Deprecated: ` paragraph (human-readable, tooling-recognized per row 8) plus `//go:fix inline` (machine-rewritable) — is the two-part self-deprecation contract: the doc comment tells a human reader what to use instead and why; the directive lets `go fix` do the mechanical migration for every caller in the module, and (once released) for every downstream module that runs its own `go fix` against the new version.

### 10. The API-break gate and major-version strategy

[golang/exp `apidiff`/`gorelease`](https://raw.githubusercontent.com/golang/exp/master/cmd/gorelease/gorelease.go), fetched (source, since neither ships prebuilt binaries — `go install golang.org/x/exp/cmd/apidiff@latest` and `.../gorelease@latest`, both installed and run in this dive).

`apidiff`'s own usage text: *"reports two kinds of changes: incompatible ones, which require incrementing the major part of the semantic version, and compatible ones, which require a minor version increment."* **Verified directly: `apidiff` always exits 0**, on an incompatible change, a compatible change, or no change at all (§ Verification runs) — it is a pure diff-reporting tool. The CI-blocking mechanism must grep its output (`grep -q "^Incompatible changes:"`, empty match = pass) or, better, use `gorelease` instead.

`gorelease`'s doc comment, fetched from source: *"compares a base version (set with `-base`) with the currently checked out revision"* and, given a proposed `-version`, *"reports whether the changes are consistent with semantic versioning."* The exact, load-bearing sentence: *"If there are incompatible API differences for a proposed version with major version 1 or higher, gorelease will exit with a non-zero status… For a proposed version with major version 0, which allows incompatible changes"* — no non-zero exit ([domain.md](../go-topic-map/domain.md) §19, confirmed against the tool's actual source rather than a description of it).

**Verified directly against a real removed method, in both major-version worlds** (a local file-based module proxy stood in for the module's normal VCS/proxy resolution so `gorelease -base=vX.0.0` could fetch a real "before" version):

- `example.com/v0demo` (module declares no version suffix, i.e. v0): base has `(*Client).Close`, new removes it. `gorelease -base=v0.1.0` reports the incompatible removal and **exits 0** — *"Suggested version: v0.2.0."*
- `example.com/v1demo`, same removal: `gorelease -base=v1.0.0` reports the identical incompatible removal and **exits 1** — *"Cannot suggest a release version. Incompatible changes were detected."*
- The v1 twin (no change at all against the same base) **exits 0** — *"Suggested version: v1.0.1."*

This is the exact mechanism the map's conflict resolution and M-D-11's coverage cell point at, now run rather than read: **the API-break gate is `gorelease` in CI, not `apidiff`**, and its severity is conditional on the module's own declared major version — a v0 SDK cannot use `gorelease`'s exit code as its breaking-change gate at all; it needs the human-read report or a separate policy (e.g., "no removal without a `retract` and a changelog entry") layered on top.

**Major-version strategy — measured, not decided in the abstract:** `grpc/grpc-go@acccf8cd101a` has stayed unsuffixed at v1 across its entire lifetime (never a `/v2` import path); `google/go-github@48d0a668cde8` sits at `/v92` — both are real, maintained, widely-imported libraries taking opposite strategies to the same problem (adding functionality and fixing mistakes without ever making a source-incompatible change vs. accepting periodic `/vN` bumps as the normal cost of an evolving REST-API wrapper). **This is folded into the API-shape brief rather than left as a modules-release question** because it is a *design* decision each fleet library makes once, not a release-mechanics detail: a library that avoids ever adding a required parameter, ever removing an exported name, or ever changing a signature can credibly commit to staying unsuffixed; a library that mirrors an actively-evolving upstream API (the OCX CLI, the ocx REST surface) should expect and plan for `/vN` bumps rather than distorting its API to avoid them. `gorelease` is what enforces "no accidental break" either way; the choice of "avoid vN forever" vs. "accept vN periodically" is a project-level policy the SDK's own author states once and `gorelease`'s exit code then holds it to.

### 11. Unkeyed composite literals of a foreign struct

[go.dev/wiki/CodeReviewComments](https://go.dev/wiki/CodeReviewComments) does not carry this rule by name; it is a `go vet` analyzer (`composites`), on by default under `go vet`, cited by the map from [codified.md](../go-topic-map/codified.md) §1. It fires when a struct literal from **another package** uses positional (unkeyed) field values — `libpkg.Point{1, 2}` instead of `libpkg.Point{X: 1, Y: 2}` — because a future field addition to that struct silently shifts every positional literal's meaning, or breaks compilation only if the added field's type mismatches, and *not at all* if it happens to match.

**Verified directly:** a two-module fixture (`example.com/libpkg` defines `Point{X, Y int}`; a caller module imports it via `replace`) — the unkeyed literal `libpkg.Point{1, 2}` makes `go vet ./...` **exit 1** with `main.go:10:7: example.com/libpkg.Point struct literal uses unkeyed fields`; the keyed twin `libpkg.Point{X: 1, Y: 2}` makes `go vet ./...` **exit 0** (§ Verification runs).

**Scope, confirmed from the audit rather than assumed:** the check applies across module/package boundaries, not within the same package — `go-cmp`'s own 7 vet hits in its own test suite are deliberately-constructed same-package fixtures for the check itself, not organic violations ([gates](../go-audit/exemplar-quality-gates.md) §5, cited by the map). A rule enforcing this should scope its finding to imported types, matching what `go vet` itself already does — flagging every unkeyed same-package literal as an equal-severity defect would over-report relative to the real risk.

### 12. Embedding leaks into a public struct's method set

Uber's guide, fetched: *"Avoid Embedding Types in Public Structs"* — embedded types *"leak implementation details, inhibit type evolution, and obscure documentation."* The concrete evolution cost, fetched verbatim: *"Adding methods to an embedded interface is a breaking change. Removing methods from an embedded struct is a breaking change."* The guide's recommended fix is hand-written delegate methods instead of relying on embedding to satisfy an interface or expose behavior.

**No linter checks this** — confirmed by this dive's tool inventory (golangci-lint v2.14.0's default and commonly-enabled linters, staticcheck, revive, gocritic: none has an "embedded type in an exported struct" rule). It is a reading heuristic: does an exported struct embed a field (named or anonymous) whose methods are now promoted onto the struct's own public API, where the embedded type is not itself part of the package's documented contract? The finding is sharper than "any embedding": embedding a stdlib interface like `io.Reader` to satisfy an interface requirement is idiomatic and expected; embedding a helper type purely to inherit its methods without documenting that inheritance as part of the contract is the anti-pattern.

### 13. Naming conventions

Merges the map's receiver-type row into one naming section, per the row's own instruction. Sources, all fetched:

- **Package names.** Wiki: *"All references to names in your package will be done using the package name, so you can omit that name from the identifiers"* — avoid `util`, `common`, `misc`. Google: *"Package names must be concise and use only lowercase letters and numbers… Go package names should not have underscores."* Cheney's Practical Go, independently: avoid package names like `base`, `util`, `common`.
- **Receiver names.** Wiki: *"briefly reflect their type's identity, often using one or two letter abbreviations… Don't use generic names such as 'me', 'this' or 'self'."* Google, near-identical: *"Short… Abbreviations for the type itself… Applied consistently to every receiver for that type."*
- **Receiver type (pointer vs. value).** Wiki: *"Don't mix receiver types. Choose either pointers or struct types for all available methods."* Google: *"When in doubt, use a pointer receiver."* Maps, funcs, and channels never use pointer receivers (wiki). This is the same "one receiver kind" constraint GO-ERR-17 already settled for error types specifically (imported here as settled); this row generalizes it to every exported type.
- **`Get` prefix.** Google, fetched: *"Function and method names should not use a Get or get prefix, unless the underlying concept uses the word 'get.'… Prefer starting the name with the noun directly, for example use `Counts` over `GetCounts`."*
- **Variable names.** Wiki: *"short rather than long… especially true for local variables with limited scope… The further from its declaration that a name is used, the more descriptive the name must be."* Google, near-identical framing with a formula: *"The length of a name should be proportional to the size of its scope and inversely proportional to the number of times that it is used within that scope."*

**Enforcement, all non-default:** `ST1003` (identifier naming, staticcheck), `ST1016` (consistent receiver names, staticcheck) — both carry the `NonDefault` badge alongside the doc-comment family in row 8, so they should be enabled in the same `checks` list, not as a separate config pass. revive's `var-naming` (initialism casing, e.g. rejecting `Url`/`Id` in favor of `URL`/`ID`) and `receiver-naming` (consistency across a type's methods, with a `max-length` option) are the golangci-lint-bundled equivalents, both opt-in.

### 14. Concurrency-safety doc comments

Google's Best Practices states the obligation directly (cited from [practitioner.md](../go-topic-map/practitioner.md) §8, the map's own citation for this row): the author of an exported type that is not obviously safe for concurrent use **must say so** in its doc comment — silence is not a safe default to assume either way. No linter checks this; it is a reading heuristic paired with the memory-model's own framing (fetched, [canonical.md](../go-topic-map/canonical.md) §9): *"programs that explicitly signal synchronization… are correct; the rest… is for people implementing synchronization primitives."* A type whose doc comment is silent on concurrency and whose implementation contains unsynchronized mutable state is the defect; a type documented as "safe for concurrent use" backed by a `sync.Mutex` or immutable-after-construction fields is compliant regardless of whether the sentence uses the word "goroutine."

### 15. Typed enums starting at one

Uber's guide, fetched: *"Since variables have a 0 default value, you should usually start your enums on a non-zero value"* — example `const (Add Operation = iota + 1; Subtract; Multiply)`, so the zero value reads as "unset" rather than colliding with the first real value (`Add`).

**Verified directly:** a typed `Color int` enum (`Red = iota + 1`, `Green`, `Blue`) with a `Name(c Color) string` switch missing the `Blue` case is the violation — golangci-lint with `exhaustive` enabled reports `missing cases in switch of type colors.Color: colors.Blue` and **exits 1**; the twin, covering all three cases (even alongside a `default:` clause), **exits 0** (§ Verification runs). `exhaustive` (`nishanths/exhaustive`) is the golangci-lint-bundled substitute for the compile-time-enforced sum-type exhaustiveness Go's type system does not provide — the exact language-capability gap `config-inventory.md` §4 (EXIT-07) already flagged for the CLI exit-code taxonomy; this row is the general form of the same gap applied to any typed enum.

A `String()` method generated by `stringer` (not independently re-verified in this dive; cited from the map's row) completes the pattern: a typed, `iota+1`-based enum with a generated `String()` and an `exhaustive`-checked switch everywhere the type is consumed.

### 16. `io.Reader`/`io.Writer`/`fs.FS` vs. paths and whole `[]byte`

Cheney's Practical Go, fetched via the scout digest: *"don't force allocations on the callers of your API"* — an API that accepts a whole `[]byte` or reads an entire file by path forces every caller to have the whole payload in memory (or on a real filesystem) up front, even when streaming or an in-memory `fstest.MapFS`-backed test double would do. Accepting `io.Reader`/`io.Writer` (for streams) or `fs.FS` (for a rooted, swappable file tree) instead lets a caller supply a network stream, a `bytes.Buffer`, or a test fixture without the library caring which.

**This interacts directly with GO-IO-02 (imported as settled), not merely alongside it.** GO-IO-02's rule: *"Open every file name the program did not choose through `os.Root`/`os.OpenInRoot"* — archive entries, and tag-, digest-, ref-, or URL-derived names. The two rows resolve to one coherent guideline for the SDK's method signatures: when an API parameter is a **name the caller does not control the trust boundary of** (an archive entry name, a registry tag, a digest-derived path) it is never a bare path string passed to `os.Open`; it is either wrapped through `os.Root`/`os.OpenInRoot` internally (GO-IO-02's mechanism) or the API is redesigned to accept the already-opened `fs.FS`/`io.Reader` so the caller — who is closer to the trust decision — supplies a value the library never has to path-join at all. When the parameter is simply "the caller's own file" with no untrusted-name component, a plain path parameter is fine and forcing an `fs.FS`/`io.Reader` onto every caller is the over-engineering rung above what the problem needs.

## AI-agent angle

- **`interface{}` instead of a concrete return type, or reaching for an interface "for testability" before a second implementation exists.** An LLM trained on pre-2018 Go idiom over-produces mock-friendly interfaces for every dependency. Mechanical check: `ireturn` (rule 4/5's fixture) plus a reading pass for "does this interface have more than one real implementation in this module?" — if not, the interface is very likely AI-generated scaffolding, not a measured need.
- **`type Option func(*Config)` without the `error` return, applied to options that are documented (elsewhere) as mutually exclusive.** A model recalling the Pike/Cheney pattern from training data reproduces the simplest form even when the actual options can conflict, silently accepting the last-applied one with no error. Mechanical check: grep every func-typed `Option` definition; if any two options in the same set are described as mutually exclusive in a doc comment, the option func's signature must return `error` (reading heuristic — no linter distinguishes "conflicting options" from "independent options" by signature alone).
- **A package-level `var config = defaultConfig()` or similar "convenience" global, introduced to avoid threading a dependency through a call chain.** This is exactly the shape Google's litmus test and Uber's "Avoid Mutable Globals" name, and it is a common LLM shortcut under time pressure (it "just works" in a single test run). Mechanical check: `gochecknoglobals` (rule 7's fixture) — already exempts `Err*` sentinels, so no extra tuning is needed before treating every other hit as a genuine finding.
- **Writing a `Deprecated:` comment with no `//go:fix inline`, or vice versa, when a mechanical migration is possible.** A model that knows the `Deprecated:` convention from older training data but has not seen Go 1.26's inliner will produce a doc-comment-only deprecation that leaves every caller to migrate by hand. Mechanical check: `go fix -diff ./...` reports nothing to inline for a `Deprecated:`-only declaration even though callers exist — a human (or a later pass) has to notice the missing directive; there is no automated "you forgot `//go:fix inline`" check, only the absence of an expected diff.
- **Bumping a module to `/v2` for a change that is actually backward-compatible, or skipping the bump for one that is not.** An LLM asked to "release a new version" after making a change has no innate sense of SemVer compatibility and will guess based on the size of the diff rather than its actual API-shape effect. Mechanical check: `gorelease -base=<previous tag>` (rule 12's fixture) run before any version-bump decision — its exit code (for v1+) or its human-read report (for v0) is the actual answer, not the diff's line count.
- **`libpkg.Point{1, 2}` — an unkeyed literal of an imported struct, copy-pasted from that struct's own test file or an example in its README**, which is frequently written with positional fields for brevity. Mechanical check: `go vet ./...` (rule 15's fixture) — already on by default under `go vet`, so this is one of the cheapest AI-mistake catches in the entire rule family, and its absence from a CI pipeline (relying only on `go test`'s narrower vet subset) is itself a finding GO-GATE-02/GO-GATE-07 already name.
- **A getter method returning `r.internalSlice` directly, described in its doc comment as "returns the X" with no mention of aliasing**, because this compiles cleanly and passes every naive test that does not specifically try to mutate the result. Mechanical check: none exists as a static analyzer (finding 6); the only mechanical catch is the behavioral test pattern in rule 16 — an agent generating a getter for a slice/map field should default to `slices.Clone`/`maps.Clone` unless a comment states why not, since no lint will ever flag the unsafe version.
- **Embedding a concrete struct into another exported struct to "get its methods for free," with no comment stating the embedding is intentional public surface.** A model optimizing for the shortest diff that satisfies an interface will reach for embedding over hand-written delegation every time. Mechanical check: none exists (finding 12); a reviewer must read every exported struct's field list for an unqualified (embedded) type and ask whether its promoted methods were meant to be part of the contract.

## Contested / evolving

- **Functional options vs. builder/chaining.** rednafi's 2024 critique (measured allocation cost, argued readability win) is a real, recent, and explicitly qualified disagreement with the Pike/Cheney canon — not yet reflected in any normative source, and not adopted by any exemplar in this corpus at the time of the code-shape audit. Trending: watched, not yet resolved; the map's decision procedure (rule 6) accommodates both without picking a side, which is the correct posture until more of the ecosystem actually adopts the builder alternative in a public API rather than an internal one.
- **`context.Context` as a struct field.** Documented anti-pattern (`containedctx` exists specifically to catch it) vs. observed practice at etcd, terraform, tailscale, grpc-go (15/34 repos, spot-read genuine). As of 2026-09-26 this is a case where style guidance and flagship practice have simply diverged and show no sign of converging — the honest rule severity is SHOULD-with-documented-reason, not MUST NOT, and a future revision of this brief should re-check whether the gap narrows.
- **Major-version strategy (stay-at-v1-forever vs. periodic `/vN`).** Not contested in the sense of disagreement — both `grpc/grpc-go` and `google/go-github` are stable, successful choices — but genuinely unresolved as a *fleet policy* until `api/sdk-surface` (a sibling wave-3 dive) pins the OCX SDK's own choice. This brief supplies the mechanism (`gorelease`) and the framing (a one-time, documented project decision); it does not pick a side for the fleet.
- **`go.uber.org/atomic` vs. stdlib typed atomics.** Not a row of this brief directly, but adjacent to the naming/API-shape family: Uber's own guide (fetched, still current text as of this read) recommends its own wrapper package, while the map's conflict 24 (imported context) already resolved this in favor of stdlib for the fleet, since the 1.27 `atomictypes` modernizer actively rewrites toward stdlib and measured adoption is already 69% typed-stdlib. Flagged here only to note the guide text itself has not caught up to the ecosystem or tooling direction as of 2026-09-26.
- **Whether `pkg/` is dead or merely unfashionable.** `golang-standards/project-layout`'s own maintainers disclaim official status ([github.com/golang-standards/project-layout/issues/117](https://github.com/golang-standards/project-layout/issues/117)), Demailly argues it should be abandoned outright, yet 11/34 real repositories still use it and none has been observed migrating away in this corpus's snapshot. Trending: the *new*-repository guidance (never add it) is not contested; the *existing*-repository guidance (don't churn it) reflects that migration cost, not conviction, is what's actually holding `pkg/` in place in the repos that have it.
