# Recent packaging shifts (delta update)

Scope: packaging, distribution and supply-chain changes between 2026-08-23 and 2026-11-27 that the python-packaging pair does not mention. This is a delta against the existing corpus, not a re-creation. Every fact below comes from a page fetched on 2026-11-27. Where a fetched page was truncated or silent, the item is marked "could not determine".

## Verdict

No shift in the window justifies raising the severity of an existing PY-PKG rule. One shift (PyPI archive-format rejections) justifies a new low-priority rule. One more (the pip and uv lock-format work) strengthens the case for a rule the corpus deliberately left out, but does not yet demand one. Everything else on the candidate list either did not happen in the window or is informational.

## Shifts that happened

### 1. PyPI rejects non-conforming sdists and wheels (touches: new)

- Date: 2026-11-18. The post says PyPI added the checks "over the past few months" and began rejecting uploads "over the last few weeks"; it gives no exact enforcement date.
- Citation: https://blog.pypi.org/posts/2026-11-18-stricter-checks-for-uploaded-sdists/
- Fact: PyPI now rejects sdists packed as legacy V7-style tar archives and wheels carrying archive-level ZIP comments that could be misread as ZIP control structures. Hand-packed sdists must be POSIX pax tar (GNU tar needs `--format=pax`), with no sparse members and no pax vendor extensions, and member filenames must be UTF-8. Backend-built distributions generally conform. PyPI is still evaluating rejecting GNU-style tar entirely (warehouse issue 21012) and all ZIP comments (warehouse issue 20934); neither is in effect.
- Proposed rule sketch (new, PY-PKG-11, section What Ships):

| ID | Rule | Verification | Severity |
|---|---|---|---|
| PY-PKG-11 | Distributions are produced by the declared build backend, never packed by hand with `tar` or `zip` — PyPI now rejects non-conforming archives at upload, so a hand-packed release fails at the last step of the pipeline. | Read the release workflow and Taskfile for `tar `, `zip ` or `zipfile` invocations that write into `dist/`. Any hit that builds a release artifact is the violation; `uv build` or `python -m build` alone is the pass. | SHOULD |

- Note: only a SHOULD. Most projects already use a backend, so the rule is cheap and rarely fires.

### 2. pip 26.3 installs pylock.toml with extras and groups; uv 0.13.2 honours PEP 751 environment restrictions (touches: lockfile check, PY-PKG-05; the corpus left pylock out)

- Dates: pip 26.3 on 2026-11-02; uv 0.13.2 on 2026-10-19.
- Citations: https://pip.pypa.io/en/stable/news/ ; https://github.com/astral-sh/uv/releases
- Fact: pip 26.3 lets extras be selected in `pylock.toml`, lets `--group` select non-default groups such as `pylock.toml:docs`, and makes `--no-binary` work with `-r pylock.toml`. uv 0.13.2 honours PEP 751 environment restrictions on install and includes them on export. PEP 751 is Final per https://peps.python.org/topic/packaging/ (no status change date in the window was visible there).
- Effect on the pair: PY-PKG-05 (`uv lock --check`) stays correct. `uv.lock` remains uv's native lock and `uv lock --check` remains its verifier. pylock.toml is an export and interchange format, not a replacement, so no severity change.
- Proposed rule sketch: none now. Revisit only if a consumer of these harnesses installs from pylock.toml; a future rule would be "a committed `pylock.toml` is regenerated by `uv export --format pylock.toml` and diffed in CI", severity MAY. Not recommended yet.

### 3. uv 0.13.10 strengthens `--locked` validation (touches: PY-PKG-05)

- Date: 2026-11-24.
- Citation: https://github.com/astral-sh/uv/releases (0.13.10 entry).
- Fact: 0.13.10 validates that `uv.lock` dependency requirements match locked versions and explains why `--locked` rejects a lockfile. 0.13.9 (2026-11-17) shrinks lockfiles by factoring repeated marker conditions. The uv versioning policy page (https://docs.astral.sh/uv/reference/policies/versioning/) says the `uv.lock` schema version is public API and changes only in minor releases. No new schema revision is named in the fetched release text.
- Effect: PY-PKG-05 is unchanged and now catches slightly more drift. No change needed. The 0.13.9 lockfile shrink may produce a one-time diff when contributors upgrade uv; that is a note for the reference skill, not a rule.
- Proposed rule sketch: none.

### 4. PEP 794 Import-Name metadata accepted, core metadata 2.5 (touches: new, informational)

- Date: PEP resolved Accepted on 2025-09-05, which is before the window. The window delta is the PEP-index status only; no in-window implementation evidence was found.
- Citation: https://peps.python.org/pep-0794/
- Fact: adds `Import-Name` and `Import-Namespace` to core metadata 2.5 and `import-names` and `import-namespaces` under `[project]`. Projects SHOULD list them; backends MAY compute them; PyPI and backends are not required to support it.
- Effect: not enforceable by PyPI today as far as fetched sources show. No rule.

### 5. PEP 808 accepted (touches: new, informational)

- Date: Accepted 2026-05-19, which is before the window. Listed here only because it is new to the corpus.
- Citation: https://peps.python.org/pep-0808/
- Fact: allows static entries in `[project]` fields that are also listed in `dynamic`, with backends only able to add. Raises sdist metadata to 2.6. It touches PY-PKG-04 and version single-sourcing only indirectly.
- Effect: no rule; mention in the reference skill only if backend support is confirmed, which was not determined.

### 6. CPython 3.15 and `importlib.metadata.MetadataNotFound` (touches: PY-PKG-04, could not determine)

- Date: Python 3.15 released 2026-10-09.
- Citation: https://docs.python.org/3.15/whatsnew/3.15.html
- Fact: `importlib.metadata.metadata()` and `Distribution.metadata` now raise `MetadataNotFound` when a distribution's metadata file is missing, instead of returning an empty object. The fetched text did not say whether `importlib.metadata.version()` still raises `PackageNotFoundError` for an absent distribution; the pair's PY-PKG-04 text names only `PackageNotFoundError`.
- Effect: PY-PKG-04 likely unchanged for `version()`, but a package that reads `metadata(...)` for its version could now leak `MetadataNotFound` on 3.15. Could not determine from the truncated page.
- Proposed rule sketch: widen the PY-PKG-04 verification wording from "a bare `PackageNotFoundError`" to "a bare `PackageNotFoundError` or `MetadataNotFound`", same SHOULD severity. Confirm against the `importlib.metadata` docs before editing the rule.

## Candidates that did not happen (dropped)

- PyPI or backends enforcing PEP 639 (rejecting `License ::` classifiers or the legacy license table): not found. The 2026-09-21 discuss.python.org thread (https://discuss.python.org/t/packages-without-a-specified-license-on-pypi/109152) is a proposal about requiring a license; participants opposed hard rejection. The PEP 639 text itself defers PyPI validation. Nothing enforced in the window.
- PEP 770 SBOM support in PyPI or backends: PEP 770 is Final (resolved 2025-04-11, https://peps.python.org/pep-0770/); the PEP and the pip 26.3 notes show no PyPI or backend enforcement. uv 0.13.2 sped up CycloneDX export (2026-10-19), which is an export feature, not wheel-embedded SBOMs. pip 26.2 (2026-07-29) is before the window. No rule.
- uv 1.0: not found. The fetched uv release page covers 0.13.1 through 0.13.10 only; the versioning policy page names no 1.0. The release page was truncated at 100000 characters, so releases between 2026-08-23 and 0.13.1 (2026-10-14) were not read; treat the "no 1.0" finding as covering 0.13.x only.
- Wheel variants (PEP 825 Provisional, PEP 817 Draft, per the topic index): not Final. uv 0.13.8 (2026-11-12) expanded wheel-variant detection in preview only.
- PyPI token deprecation, typosquat or malware controls, organisation accounts: not found in the blog list for the window. Only organisation-project size limits rose (2026-10-26), which is not a rule matter. The 128-character version limit (2026-10-23, https://blog.pypi.org/posts/2026-10-23-version-length-limit/) is real but no sane project hits it; no rule.
- Core metadata version bump required by PyPI: not found. PEP 794 sets 2.5 and PEP 808 sets sdist 2.6 in the PEPs, but no PyPI requirement was fetched.
- PEP 833 (frozen HTML simple index), 2026-08-11, is before the window and affects installers, not project manifests.
