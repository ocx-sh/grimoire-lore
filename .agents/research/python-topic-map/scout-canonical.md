## What this corpus is

The authoritative, citable Python curriculum: the language's own reference
(the data model — the special-method surface every class silently opts
into), the typing specification and the PEPs that built the modern type
system in layers (484 → 526 → 585/604 → 612/646/655/673/692 → 695/696/698/702/727/728/742),
the stdlib documentation for the modules this project's four codebase shapes
actually import, and the book curricula that turned "idiomatic Python" into
an enumerable list (Fluent Python's chapter architecture, Effective Python's
125 numbered, independently-titled rules, Architecture Patterns with
Python's service-layer/repository pattern set, Robust Python's type-system
argument, High Performance Python's profiling-first discipline) — plus the
two guides that own the edges this project lives at: packaging.python.org
(how a `pyproject.toml`-defined package actually ships) and the pytest docs
(how the acceptance-harness shape of this project is supposed to be built).

Two things distinguish this corpus from "read the docs": first, nearly
every stdlib page under survey turns out to have a *documented footgun
section* — subprocess's deadlock note, tempfile's Windows-reopen caveat,
json's `ensure_ascii`/`NaN` defaults, enum's aliasing behavior — these are
not folklore, they are called out in the primary source, which is exactly
what "verification: a grep, a lint name, a reading heuristic" needs. Second,
Effective Python's 125 items are the single richest *topic list* in the
survey: each item title is already phrased as a testable claim ("Prefer X
over Y"), which is close to rule-shape already.

## Sections nobody would think to ask about

- **The data model's copy/pickle protocol** (`__getstate__`/`__setstate__`/`__reduce__`) — nobody drafting a Python style guide lists pickling, but shape 3's automation and any cross-process work in shape 2 that touches `multiprocessing`/`concurrent.futures.ProcessPoolExecutor` silently depends on it, and a class with unpicklable state (an open file handle, a lock) fails only at the call site that pickles it.
- **`warnings` module semantics, not just `DeprecationWarning` text** — the fact that `DeprecationWarning` is *invisible by default outside `__main__`* means a library (shape 2) can ship a deprecation that its own test suite never sees fire, unless tests explicitly `catch_warnings(record=True)`.
- **The import system's `sys.modules` caching** — module-level code runs exactly once and circular imports fail via a *partially initialized* module object, not a clean ImportError; this is invisible until someone reorders imports and shape 3's 93-file automation tree is exactly the size where that starts happening by accident.
- **pexpect's PTY line-ending behavior** (`\r\n`, not `\n`) — this is the kind of thing that produces a flaky test that "sometimes" matches, and it's specific to shape 1's harness in a way none of the other three shapes would ever surface it.
- **`functools.cached_property`'s incompatibility with bare `__slots__`** — a memory-conscious rewrite of a dataclass to `slots=True` silently breaks any `cached_property` on it, and the failure mode is a `TypeError` at first access, not at class-definition time.
- **PEP 728's `closed=True`/`extra_items=`** — landed Final for 3.15 (mid-2025), so it's genuinely new; anyone whose mental model of `TypedDict` predates this will not know it exists, and it directly replaces a hand-rolled "reject unknown keys" validator that shape 4's catalog validation may already have.
- **`argparse`'s `type=bool` anti-pattern** — `bool('False')` is `True`; this is the kind of one-line landmine that a code reviewer skims past because it "looks fine," and it's exactly the shape of bug an unattended agent would introduce and not notice.
- **The packaging guide's "Distribution package vs. import package" distinction** — the fact that a single distributable can expose multiple importable top-level packages (or vice versa) is invisible until a rename or a namespace-package migration goes wrong, and it directly governs how shape 4's "must have zero third-party imports" constraint should even be phrased/verified.
