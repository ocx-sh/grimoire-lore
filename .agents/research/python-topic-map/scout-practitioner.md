## Where practitioners contradict the docs

- **Timeout composition**: asyncio's own docs teach `asyncio.wait_for(coro, timeout)` / `asyncio.timeout()` as the standard cancellation primitive; Nathaniel J. Smith argues edge-triggered per-call timeouts can't compose across layers and leave cleanup exposed mid-cancel ([#2](#argued-positions), [#18](#candidate-topics)) — a consolidator must decide whether the SDK's async layer needs cancel-scope-style discipline or whether `wait_for` suffices for the SDK's actual call patterns.
- **Style vs quality**: linter/formatter docs (and most CI configs) treat "ruff passes" as the quality bar; Hettinger's "Beyond PEP 8" argues lint-clean code can still be non-Pythonic ([#21](#argued-positions), [#25](#candidate-topics)) — conflict for the consolidator: is "ruff passes" sufficient verification for a no-human-loop agent, or does the project need idiom-level reading heuristics no linter checks?
- **Docker base images**: widely-repeated Docker-for-Python tutorials (and Docker Hub's own popularity signal) push Alpine for small images; Turner-Trauring argues Alpine's musl libc causes wheel/build problems that outweigh the size win ([#15](#argued-positions), [#6](#candidate-topics)) — conflict for shape (1)'s Docker-driving harness.
- **Dataclasses as the default**: the stdlib docs (and the general "no dependencies" instinct this project's own zero-dependency-tools shape embodies) present `dataclasses` as the obvious default; Hynek argues it's a strict, MRO-buggy subset of `attrs` ([#5](#argued-positions), [#13](#candidate-topics)) — conflict: for the typed SDK (which *can* take a dependency), is attrs still worth recommending in 2026?
- **Asyncio as the I/O default**: most modern Python I/O guidance (including this project's own SDK, which is asyncio-based) treats asyncio as the correct default for I/O-bound work; Ronacher argues real threads beat async/await, especially with free-threading now available ([#8](#argued-positions), [#20](#candidate-topics)) — conflict: does the async-heavy SDK need a rule nudging new I/O paths toward threads, or is that premature given the SDK already commits to asyncio?
- **Typing richness as unqualified good**: typing PEPs and mypy/pyright feature announcements generally frame new type-system features as pure progress; Eric Traut, speaking for the Typing Council, argues untested features without cross-checker support "do not help the community" ([#19](#argued-positions), [#30](#candidate-topics)) — conflict: should the project's typing rules gate on confirmed multi-checker support before recommending new syntax?
- **Coverage as a proxy for quality**: this project's own `fail_under=100` gate (and most CI folklore) implies more coverage is strictly better; coverage.py's own maintainer, Ned Batchelder, has long cautioned that coverage measures execution, not correctness ([#15](#argued-positions), [#15](#candidate-topics)) — conflict: does the 100% gate need a companion rule against assert-free "coverage theater," or does the number alone already do the job?
- **Python as an agent-safe default**: this project's entire premise treats Python as a language worth investing agent-quality rules in; Ronacher argues he switched to TypeScript specifically because agents perform worse in Python, citing implicit typing and poor greppability ([#9](#argued-positions), [#31](#candidate-topics)) — conflict for the consolidator: is wave two's job partly to write *compensating* rules (mandatory explicit types, avoid heavy inference) rather than general quality rules, and is that in scope at all?
