## 1. The claim, precisely

The headline claim, from [A Language For Agents](https://lucumr.pocoo.org/2026/2/9/a-language-for-agents/) (Feb 2026):

> "I'm now routinely reaching for JavaScript in places where I would have used Python. Not because I love it or the ecosystem is better, but because the agent does much better with TypeScript."

That sentence is the headline; the post's substance is six narrower, checkable mechanism claims, each quoted verbatim below with its surrounding context. **All six are stated as personal coding-agent experience. The post cites no benchmark, no measurement, no third party.**

1. **Type inference requiring a tool call.** "The downside is that you now need an LSP or the resulting compiler error messages to figure out what the type of an expression is." — languages that infer types silently force the agent to run a tool (LSP query) to learn something a signature could have stated for free.
2. **Whitespace-significant syntax and diff/patch mechanics.** "Quite often they will intentionally disregard whitespace, add markers to enable or disable code and then rely on a code formatter to clean up indentation later." — the claim is specifically about editing existing code via diffs/patches, not about writing fresh code.
3. **Greppability / symbol scoping.** "What's really nice about Go is that you mostly cannot import symbols from another package into scope without every use being prefixed with the package name." — the mechanism is namespace-qualified call sites, held up against Python's unqualified `from x import y`.
4. **Local reasoning without extra context.** "agents really like local reasoning. They want it to work in parts because they often work with just a few loaded files in context and don't have much spatial awareness of the codebase."
5. **Exceptions vs. typed results.** "Agents struggle with exceptions, they are afraid of them... agents will try to catch everything they can, log it, and do a pretty poor recovery." He explicitly does not claim this is solved: composability of typed-result chains is left as an open problem in the same post.
6. **The Python→TypeScript switch itself** — quoted above, framed as anecdote, not measurement.

**A direct, important complication from the same author, seven months earlier**, in [In Support Of Shitty Types](https://lucumr.pocoo.org/2025/8/4/shitty-types/) (Aug 2025) — this is not a third party rebuttal, it is Ronacher qualifying Ronacher, and it cuts directly against treating claim (1) above as "more/stricter typing is better for agents":

- "The LSP protocol slows things down and pollutes the context significantly" — giving an agent live type information via LSP tool calls (the exact mechanism claim (1) says agents are forced into) measured **no gain** in his own trials.
- Running a strict type checker inside the agent's edit loop makes things *worse*, not better: the agent writes code, the checker flags errors only after the fact, and the agent burns context re-debugging — "wastes a ton of context."
- **Python specifically** is named as a worse case than TypeScript here for a *different* reason than claim (1): checker fragmentation — "different type checkers cannot even agree" (mypy vs. Pyright vs. the newer `ty` diverge on real code).
- His stated conclusion is the opposite of "maximally strict typing helps": **"best-effort type systems or type hints like JSDoc" serve agents better than rigorous, enforced typing**, because the agent needs a rough type signal, not a proof obligation.

I searched Hacker News, lobste.rs, and discuss.python.org for a third-party response to the Feb 2026 post specifically and found none — no HN submission, no lobste.rs thread, no Python-typing-community rebuttal surfaced. The one adjacent piece I found, Gergely Orosz's [Pragmatic Engineer interview with Ronacher](https://newsletter.pragmaticengineer.com/p/python-go-rust-typescript-and-ai), covers language choice for startups and Sentry's error-handling patterns but does not engage the Python-vs-TypeScript-for-agents claim at all — cited for completeness, not as a counter-source. **Honest gap: no independent practitioner has published a response to this specific claim; the only complicating voice found is the author's own earlier post.**

## 2. The evidence, in either direction

None of the benchmark literature measures Ronacher's actual mechanisms (whitespace-diff application, greppability, exception-vs-typed-result friction) in isolation — that measurement does not exist. What exists is **aggregate per-language issue-resolution accuracy**, which is a different, adjacent question ("can an agent fix a bug in an existing large repo") and it points the opposite direction from the headline claim:

| Benchmark | Model | Python | TypeScript/JS | Go | Rust | Java | C/C++ |
|---|---|---|---|---|---|---|---|
| [Multi-SWE-bench](https://agentmarketcap.ai/blog/2026/04/06/aider-polyglot-leaderboard-2026-swe-bench-python-bias) (via OpenHands) | Claude 3.7 Sonnet | **52.2%** | 5.1% | 7.5% | 15.9% | 21.9% | 14.7% |
| [SWE-bench Verified](https://www.swebench.com/multilingual.html) (Python-only, cited for comparison) vs. [SWE-bench Multilingual](https://www.swebench.com/multilingual.html) (9 other languages) | Claude 3.7 Sonnet | **63%** (Verified) | 34.9% (JS/TS, in Multilingual table) | 31.0% | 58.1% (Multilingual's best non-Python language) | 53.5% | 28.6% |

Multi-SWE-bench's own authors' conclusion, as reported: **"Python performance was 3x to 23x higher than any other language."** SWE-PolyBench (Amazon, April 2025) is cited in the same source as showing Python leading file-retrieval recall by 9.3 points and precision by 12.5 points over the other languages tested.

Caveats that matter for how much weight this carries:
- This is **issue-resolution in existing, mature open-source repos** — Django alone is ~45-50% of SWE-bench Verified's instances — which measures training-data familiarity and repo-scale navigation, not the write/edit-loop friction Ronacher is describing. A model doing well here could still be doing worse at the specific whitespace-diff-application or greppability mechanisms; the benchmark can't distinguish "Python is easier to navigate" from "the model has just seen more Python."
- [Aider's polyglot leaderboard](https://aider.chat/docs/leaderboards/) — the benchmark closest in spirit to "agent edits code via diffs," which is exactly Ronacher's domain — publishes only aggregate scores across all six languages. **No public per-language breakdown was found**, despite two separate searches and a direct fetch of the leaderboard page. The page's own caveat: it measures "edit format correctness" (did the diff apply cleanly, not the resulting code's quality) — directly relevant to mechanism (2), but the specific number does not exist publicly.
- [Type-Constrained Code Generation with Language Models](https://arxiv.org/abs/2504.09246) reports that when LLMs generate TypeScript, ~94% of resulting compilation errors are type-check failures (vs. ~6% syntax errors). This is a **TypeScript-only** result — the paper does not run the same measurement on Python — so it cannot be read as "Python beats/loses to TypeScript." It's evidence for a narrower, orthogonal point: even in a language with mandatory static types, LLM-generated code still struggles predominantly with types, which complicates any simple "static types fix agent code" story.

**Verdict on this section: the per-language issue-resolution gap is measured, and it runs opposite to Ronacher's claim (Python highest, not lowest). The specific mechanisms Ronacher names (greppability, whitespace-diff friction, exception avoidance) are not measured anywhere found — they remain asserted, from his own agent-use experience, not benchmarked.**

## 3. Mechanisms: inherent vs. conventional, and their neutralisers

Only the "conventional" (property-of-how-the-code-is-written) mechanisms translate into a rule an agent can follow when editing *this* codebase — you cannot write a project rule that changes CPython's grammar.

| # | Mechanism | Inherent to Python, or a property of how a codebase is written? | Concrete convention that neutralises it |
|---|---|---|---|
| 1 | Implicit/absent types at call sites (need an LSP to learn a type) | **Conventional.** Python allows omitting annotations; nothing forces it. | Mandate full parameter + return annotations on every public callable, so the signature alone answers the question. |
| 2 | `getattr`/`setattr` with computed names, monkeypatching, `from x import *` | **Conventional.** All three are opt-in language features, not required by anything. | Forbid computed dynamic attribute access and star-imports in shipped code; confine monkeypatching to test fixtures. |
| 3 | Whitespace-significant syntax breaking diff/patch application | **Inherent** — Python's grammar is whitespace-significant; no project convention removes that. | Cannot neutralise the cause. Can neutralise the *symptom* Ronacher names ("rely on a formatter to clean up indentation later"): require the formatter to be the last step of every edit and diff the formatted output against itself as a no-op check, so a malformed intermediate never ships. |
| 4 | Import indirection / re-export chains hiding a symbol's true definition | **Conventional.** Nothing forces a project to have more than one public path to a symbol. | One canonical import path per public symbol; an explicit `__all__` that is the only public surface; no silent re-export under a second path. (`ocx-sdk-python`'s own `__init__.py` already does exactly this — see §6.) |
| 5 | Runtime-only behaviour no static tool can confirm (metaclasses, `__getattr__` hooks, pytest fixture injection by parameter name, decorator-altered signatures) | **Mixed.** Metaclass/`__getattr__` magic is avoidable by convention; pytest's name-based fixture injection is the ecosystem's own idiom, not something a single project can opt out of without losing pytest's ergonomics. | For the avoidable half: prefer an explicit registration object over metaclass/`__getattr__` magic. For pytest fixtures specifically: this is an accepted ecosystem cost, not a fixable one — flag it CONSIDER, not MUST (see rule 13 below). |
| 6 | Many idiomatically-equivalent ways to write the same thing (four string-formatting styles, `is None` vs falsy checks, comprehension vs loop) | **Conventional**, and largely already Python-community-recognised, not a novel finding. | `ruff`'s `UP`/pyupgrade-family rules already collapse most of this to one canonical form; the residual gap is project-specific idiom choices ruff doesn't have an opinion on. |
| 7 | Exceptions vs. typed results for error-path visibility | **Conventional but contested** — exceptions are the idiomatic Python error mechanism; a Result-type convention fights the grain of the language and its own libraries. Ronacher himself calls composability here unsolved. | No clean neutraliser found. Weakest available compromise: require public functions to document their raised-exception set (a discipline, not a language feature — Python has no checked exceptions) — CONSIDER only, not a confident MUST. |

## 4. Candidate rules

Verification commands use `rg`/`grep` with an explicit path operand; **empty output is a PASS unless stated otherwise** — each row says which.

| # | Rule (imperative) | Mechanism neutralised | Verification | Evidence level | Shape |
|---|---|---|---|---|---|
| 1 | Every public function/method signature carries full parameter and return annotations — no bare `def foo(x, y):` on anything importable without a leading underscore. | #1 | `rg -n --pcre2 '^\s*(async )?def [a-zA-Z][a-zA-Z0-9_]*\([^)]*\)\s*:' <path>` then manually filter to non-`_`-prefixed defs missing `->`; empty (after filtering) is a pass. Or, faster: `pyright --outputjson <path> \| jq '.generalDiagnostics[] \| select(.rule=="reportMissingParameterType" or .rule=="reportMissingReturnType")'` — any output is the finding. | codified elsewhere (pyright strict already enforces this in shape 2; ruff `ANN` rules do it syntactically for all shapes) | (2) MUST, (1)(3)(4) CONSIDER |
| 2 | Do not gate an agent's live edit loop on a strict type-checker pass; run the type checker as a separate, later CI step, not inline in the same turn as the edit. | #1, and directly Ronacher's Aug-2025 complication of #1 | No grep — this is a workflow/CI-ordering rule, not a code-shape rule. Verification is a reading of the CI config: does the type-check step block the same commit that made the edit, or a separate review gate? | argued (Ronacher, single post, no measurement) | (2) CONSIDER — directly contradicts a naive reading of rule 1; keep both, scoped differently |
| 3 | Pin the project to exactly one type checker as the source of truth (state it by name in the repo), rather than expecting mypy/pyright/`ty` to agree. | #1's Python-specific aggravation named in the Aug-2025 post (checker fragmentation) | `rg -l 'mypy\|pyright\|^ty ' pyproject.toml <path>` — more than one checker configured as a *blocking* gate (not just available) is the finding. | argued (Ronacher, asserted from experience) | (2) SHOULD, (1)(3)(4) CONSIDER |
| 4 | No computed `getattr(obj, name)`/`setattr(obj, name, val)` where `name` is not a string literal, in shipped (non-test) code. | #2 | `rg -n --pcre2 '\b(get|set)attr\([^,]+,\s*(?!["\x27])' <path>` — a match where the second argument doesn't start with a quote is the finding. | asserted (no benchmark; standard static-analysis folklore) | (2)(3)(4) SHOULD, (1) CONSIDER (test harnesses sometimes legitimately need dynamic dispatch) |
| 5 | No `from module import *` anywhere in shipped code. | #2 | `rg -n 'from [\w.]+ import \*' <path>` — any match is the finding. | codified elsewhere (ruff `F403`/`F405` already flag this by default) | all four, MUST — already covered, low incremental cost to restate |
| 6 | `unittest.mock.patch`/manual monkeypatching appears only inside `test_*.py`/`conftest.py`, never in a module under `src/`. | #2, #5 (structured-concurrency-adjacent: no hidden runtime rewiring in production code) | `rg -l 'monkeypatch\|mock\.patch\|setattr(' <path>/src --glob '!*test*'` — any file listed is the finding. | asserted | all four |
| 7 | Every edit that touches a formatted file ends with the formatter run, and the formatter's output is idempotent (running it twice produces no further diff). | #3 (symptom, not cause) | `ruff format --check <path>` — nonzero exit / any file listed is the finding (this is the rare case where the tool's own "would reformat" output *is* the violation list). | codified elsewhere (this is exactly what `ruff format --check` is for; the rule is naming *when* to run it — after every edit, not only in CI) | all four, MUST |
| 8 | A public symbol has exactly one import path; a package's `__init__.py` re-exports it once, and no second module re-exports the same name under a different path. | #4 | `rg -n '^from \.[\w.]+ import' <path>/__init__.py` to enumerate the declared re-export set, then `rg -rn "import <symbol>" <path>` across the package for a second, different source path — a second distinct source module for the same symbol name is the finding. | codified elsewhere as a pattern, but not lint-enforced anywhere found — this is a reading-heuristic rule, no existing tool catches it | (2) MUST (it's a shipped library's API contract), (1)(3)(4) SHOULD |
| 9 | Every package declares `__all__` explicitly; nothing importable-by-default is left to "whatever isn't underscore-prefixed." | #4 | `rg -L '__all__' <path> --glob '**/__init__.py'` — files *without* a match are the finding (this is a files-without-match check, not a per-line grep). | codified elsewhere (ruff has no default rule for this specifically, but it's PEP 8-adjacent and static-analysis-tool-recognised) | (2) MUST, (1)(3)(4) SHOULD |
| 10 | Public error/result types name their raised-exception set in a docstring `Raises:` section (or equivalent structured field), even though Python has no compiler-checked exception contract. | #7 | `rg -n --pcre2 -B2 'def [a-zA-Z][\w]*\([^)]*\)\s*->' <path> \| rg -v 'Raises:'` (approximate — a full check needs a docstring parser, this greps for the common miss) — any function whose surrounding docstring lacks a `Raises:` block, that the reviewer confirms actually raises, is the finding. | CONSIDER-tier only — the neutraliser is weak per §3 row 7 | (2) CONSIDER |
| 11 | A background `asyncio.create_task`/bare `threading.Thread` spawn is not left to outlive its enclosing function; prefer a structured-concurrency construct (`asyncio.TaskGroup`, or an explicit join/gather before return). | not one of Ronacher's six, but it's the concrete, checkable form of the "local reasoning" mechanism (#4 above, "agents work with just a few loaded files") — an unstructured background task is exactly the kind of thing invisible from local inspection | `rg -n 'asyncio\.create_task\(' <path>` then check, per hit, whether the returned task is awaited/joined before the enclosing function returns — an un-joined task is the finding. | argued (Nathaniel J. Smith, cross-referenced from the practitioner-writing scout, not agent-specific but directly supports the same mechanism) | (2) SHOULD |
| 12 | Prefer a plain top-level `def` over a closure when the closure's only purpose is to capture one or two values a partial/dataclass could carry — closures hide a call site behind a name that greps to nowhere. | mechanism adjacent to #3/#4: a closure defined inside another function is invisible to a top-level symbol search | `rg -n '    def [a-z_]+\(' <path>` restricted to functions nested inside another `def` (indentation > 4 and not a method — i.e., the enclosing block is a `def`, not a `class`) — each hit is a candidate for the reviewer to judge, not an automatic finding. | asserted | all four, CONSIDER (reading heuristic, not a hard rule — closures are sometimes the right, idiomatic tool) |
| 13 | Accept pytest's name-based fixture injection as-is; do not attempt to route around it with explicit dependency objects. | #5 (the unavoidable half) | No verification — this is a deliberate non-rule, recorded so a future pass doesn't propose "ban fixtures" as a greppability fix. | argued (this scout's own judgment call, stated as such) | (1) explicitly exempted |
| 14 | CLI/subprocess boundary functions (the actual mechanism-neutral topics already surfaced by the practitioner-writing scout, cross-referenced here because they compound with agent-legibility): explicit `timeout=`/`check=True` and structured cancellation are *also* local-reasoning wins — a hang is the ultimate "invisible from local inspection" failure. | #4 | See `scout-practitioner.md` candidate topics 1, 2, 8, 17-19 — not re-derived here to avoid duplicating that file. | see practitioner scout | (1)(2) |
| 15 | Do not introduce a second, differently-named private helper whose name is a substring of a public function's name (e.g. `push_blob` / `_push_blob` in the harness, found in §6) without a word-boundary-safe naming scheme — a plain grep for the public name will false-positive-match the private twin. | novel mechanism found during the local experiment, not named by Ronacher at all | `rg -n '\bdef _?(\w+)\(' <path> \| sort` then diff for any name that is a substring of another — the pair is the finding. | measured (this project's own local experiment, §6) | (1) SHOULD — found concretely in `ocx/test/src/registry.py` |

## 5. Where this is wrong or overstated

- **Rule 1 (mandatory annotations) and rule 2/3 (don't gate the loop on strict checking, distrust multi-checker agreement) pull against each other**, and that tension is real, not a drafting mistake: the same practitioner argues both "explicit is better than an LSP round-trip" and "a strict checker in the loop wastes context." A consolidator has to pick a lane rather than average them — my read: keep annotations mandatory (it's a static-authoring-time cost, paid once) but do not make the type checker a blocking step inside the same edit/verify cycle the agent runs turn-by-turn; make it a separate, later gate. That's an editorial judgment call, not something either source settles cleanly.
- **[Hettinger's "Beyond PEP 8"](https://www.youtube.com/watch?v=wf-BqAjZb8M)** (carried over from the practitioner scout) cuts directly against rules 4, 6, 9, and 12: mechanising Python toward maximum machine-legibility — banning closures, mandating `__all__` everywhere, forbidding dynamic attribute access outright — is exactly the kind of rule that makes code pass every check while reading less like idiomatic Python to the humans who eventually maintain it. Rules 4 and 12 are marked SHOULD/CONSIDER rather than MUST specifically because of this cost; rule 6 (star-imports) and rule 9 (`__all__`) are kept at MUST/SHOULD because they cost nothing idiomatically — no one considers `from x import *` more Pythonic than an explicit import list.
- **The whole "greppability" framing (mechanism #3, rules 7 and 15) risks solving a problem this project doesn't clearly have.** The local experiment in §6 found the SDK already greppable with plain-substring, single-pattern searches and zero false positives — not because of any rule, but because of ordinary PascalCase-class / no-name-collision hygiene. If that generalises, the "make Python more greppable" agenda may be largely already-satisfied by conventions these codebases already follow, and the marginal rule (15) is narrow and specific rather than a broad new axis.
- **Genuinely undecided, not resolved here**: whether the per-language issue-resolution gap in §2 (Python winning by 3-23x on Multi-SWE-bench) transfers to the write/edit-loop workflow Ronacher describes. I could not find a benchmark that isolates his specific mechanisms, and I would not claim the issue-resolution numbers refute him — they refute the aggregate "Python is bad for agents" framing, but not the mechanism-level claims, which remain untested. Reporting this as settled either way would be the "fake resolution" the brief asked me not to produce.

## 6. The cheap experiment

Picked three real names from `/home/mherwig/dev/ocx/test/src/` (harness — fully type-annotated, contrary to an assumed "unannotated" baseline; both codebases here are typed, so this measures naming/dispatch hygiene, not annotation presence) and one from `/home/mherwig/dev/ocx-sdk-python/src/ocx_sdk/` (typed SDK), using `grep -r` with an explicit path and counting distinct patterns needed for full-recall, zero-false-positive call-site discovery.

| Symbol | Repo | Grep patterns needed for full recall | False positives with the naive pattern | Finding |
|---|---|---|---|---|
| `_compose(` (private helper, `helpers.py`) | ocx/test | 1 (`_compose\(`) | none found | Clean — 6 call sites across 3 files, one pattern. |
| `push_blob(` (public registry function) | ocx/test | 1 to find real calls, but **the naive substring pattern also matches `_push_blob(`**, a different, unrelated function | Yes — `push_blob(` as plain substring matches both `push_blob(...)` and `_push_blob(...)` text; a word-boundary pattern (`\bpush_blob\(`) is required to exclude the twin | Concrete instance of rule 15: a private helper's name being a *suffix* of the public function's name defeats plain substring grep. |
| `.provision(` (Protocol method, dispatched through a `dict[str, StateProvider]` registry keyed by string) | ocx/test | 1 pattern finds every call site (all 20+ call sites use the literal `.provision(` regardless of which concrete adapter class runs) | none for *finding calls* | Structural typing here does **not** hurt call-site recall — every caller writes the same method name. It hurts a *different* question: which concrete class runs at a given call site is not visible from the call site itself, only from tracing `STATE_PROVIDERS[key]` — a distinct, narrower cost than "can't find call sites." |
| `Ocx(` (SDK's main constructor) | ocx-sdk-python | 1 (`Ocx\(`) | Checked explicitly: plain substring `Ocx(` and word-boundary `\bOcx\(` both return exactly 47 matches — zero false positives (no `OcxConfig(`, `OcxError(`, etc. collide, because none of them have `(` immediately after `Ocx`) | Clean, and the reason is ordinary naming hygiene (PascalCase, no truncating prefix collision), not type annotation. |

**Verdict on the greppability claim specifically: not supported as an annotated-vs-unannotated contrast in this sample** — both codebases are typed, and both were 1-pattern-greppable for their chosen symbols. The one real defect found (`push_blob`/`_push_blob`) is a naming-collision hazard present in the *harness*, independent of typing, and it generalises to a genuinely new, narrow rule (15) that the corpus itself never named.
