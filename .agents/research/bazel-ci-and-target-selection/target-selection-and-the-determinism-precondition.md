## Summary

- 31.23% of Bazel projects with a CI service configured never invoke Bazel inside it, and 27.76% of the ones that do need extra tooling to make it work ([Zheng, Adams & Hassan 2024](https://arxiv.org/abs/2405.00796)) — a hand-off checklist's first line item is "does CI invoke `bazel`/`bazelisk` at all", before target selection is even a topic.
- rules_ocx already runs whole-repo green today (`bazelisk test //...`, `.github/workflows/ci.yml:62`) with zero `bazel-diff`/`target-determinator` anywhere in the repo — the fleet default this dive recommends is what the one Bazel repo already does, not a change.
- `bazel-diff` and `target-determinator` diff the build graph by two structurally different mechanisms: `bazel-diff` (default mode) hashes the pre-analysis `bazel query` graph plus source-file content, per target, treating each external repository as one opaque blob; `target-determinator` runs `bazel cquery` before and after and diffs the resulting `ConfiguredTarget` objects directly.
- `bazel-diff`'s own maintainer closed [issue #134](https://github.com/Tinder/bazel-diff/issues/134) as "expected behavior": a transitive dependency introduced only by *executing* a repository rule (e.g. a `pip`/`whl_library`-resolved package) is invisible to the default hash, because the tool queries the rule's *definition*, not the fetched repository's generated `BUILD` content.
- `target-determinator`'s README states its own results-cache key "excludes home- and system- bazelrc files, environment variables, and host hardware/OS" — a cached "before" `cquery` result computed under a different rc file, env, or machine can silently diverge from a fresh one, producing spurious differences its own doc walks through.
- The phrase "bazel-diff is incorrect and will sometimes miss affected targets" is Aspect's own 2022 blog characterization (citing bazel-diff issue #134), not text in `bazel-diff`'s README — attributing it to the tool's own docs is a citation error worth not repeating.
- `bazel-diff` has grown a `--useCquery` flag (Bazel ≥6.2.0) that trades speed for the same configuration-aware precision `target-determinator` has by default, plus `--fineGrainedHashExternalRepos`/`--seed-filepaths`/`--alwaysAffectedTags` — all opt-in patches for named miss classes documented in its own `README.md`, current as of release `v46.1.0` (2026-08-28).
- Tinder's reported "93 percent CI time reduction" is a **combined** number: 93% P100 savings comes from `bazel-diff` *plus* Buildkite's dynamic pipelines together, a 54% improvement over `bazel-diff` alone — quoting "93 percent, from bazel-diff" drops the half that came from a different mechanism entirely.
- Canva's sequencing is the load-bearing fact, not their tooling choice: they converted non-hermetic backend integration tests off shared containers (via TestContainers) and cut accessibility-suite jobs from 67,145 per commit to 1 *before* their custom `bazel-diff`-hash-precompute layer went live (2024-01-31) — the input-hashing layer is Canva's third path, and it only became trustworthy after that prep.
- Aspect's own current commercial product (`aspect.build/docs/workflows/features/delivery/`) ships a **"Selective Delivery"** feature that compares the content hash of each *build output* after a full build, not `bazel-diff`'s pre-build graph hash — it sidesteps the entire target-selection correctness debate by deciding what to *publish*, never what to *test*.
- Google's TAP runs "more than 50,000 unique changes and… more than four billion individual test cases" a day and, at that scale, stopped running every test on every change — it batches related changes and accepts that batching "can obscure which change… caused a test to break" ([Software Engineering at Google, ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)).
- Meta's Predictive Test Selection is a third model neither `bazel-diff` nor `target-determinator` implements: an ML-scored, probabilistic skip that explicitly accepts a quantified miss rate — "over 95% of individual test failures" and ">99.9% of faulty changes" still surface — rather than promising a deterministic, zero-miss graph diff ([Machalica et al. 2018/2019](https://arxiv.org/abs/1810.05286)).
- Bazel core has no native target-diffing feature; the tracked request ([bazelbuild/bazel#7962](https://github.com/bazelbuild/bazel/issues/7962)) has been open since 2019-04-05 and was still open as of 2024-02-28 — every tool discussed here is, and will remain, third-party.
- The fleet default is **whole-repo green** for every repo that exists today: `creeptd-ng`, the fleet's largest, has 13 `Cargo.toml`, 3 `package.json`, 3 build scripts — roughly an order of magnitude below the scale (~300 Bazel targets, 40–60 min whole-repo CI) at which Tinder found whole-repo green no longer tenable.
- The determinism precondition is not this dive's to invent: it is BZL-HERM's environment-tier and non-determinism rows plus BZL-CACHE's action-key rows, run in order, before either tool's own miss-class becomes the dominant risk rather than a secondary one.
- `bazel-diff`'s default mode is a `bazel query`-based over-approximation of `select()`: it "runs over the results of Bazel's loading phase, before options are evaluated" and so conservatively includes every branch, while `cquery` (opt-in via `--useCquery`) "runs over the results of Bazel's analysis phase" and resolves `select()` exactly ([bazel.build/query/cquery](https://bazel.build/query/cquery)) — the same query/cquery split that defines `target-determinator`'s whole design.

## Findings

### 1. The surprise: adoption that never reaches CI

[Zheng, Adams & Hassan (2024)](https://arxiv.org/abs/2405.00796), an empirical study of 383 Bazel projects, reports two adjacent numbers that the map's Conflict 2 already uses to settle *whether* to adopt Bazel; this dive uses the same numbers to settle the *hand-off checklist* for target selection specifically: **31.23% of Bazel projects that configure a CI service never invoke Bazel inside that CI**, and **27.76% of the ones that do need extra tooling to make it work**. Neither `bazel-diff` nor `target-determinator` has any opinion to offer a project in either bucket — a selection tool only has something to select from once Bazel is the thing CI actually runs. The practical consequence for a hand-off checklist (`bazel-adopt`'s territory, cited here because it is this dive's evidence): the first line item is never "which selection tool", it is `grep -rn 'bazel\|bazelisk' <ci-config>` returning a hit inside an actual build/test step, not just an install step. Zero fleet exhibit today — `rules_ocx`'s CI runs `bazelisk test //...` and `bazelisk build //...` directly (`ci.yml:62,91,124`) — but the checklist item is for the adopting repo, not this one.

### 2. What each tool actually diffs

`bazel-diff`'s own "How it works" section: run `generate-hashes` on the before revision, run it again on the after revision, diff the two JSON hash maps. Each target's hash is "the summation of the rule implementation hash, the SHA256 value for every attribute of the rule and then the summation of the SHA256 value for all `rule_inputs`… For source_file inputs the content of the file are converted into a SHA256 value" ([README.md, "What does the SHA256 value… represent?"](https://github.com/Tinder/bazel-diff/blob/master/README.md)). By default this traversal uses `bazel query`, not `cquery` — an opt-in `--useCquery` flag exists ("If true, use cquery instead of query when generating dependency graphs. Using cquery would yield more accurate build graph at the cost of slower query execution… only works with Bazel 6.2.0 or above").

`target-determinator` never computes a content hash at all. Its `WalkAffectedTargets` API checks out both revisions with `git`, runs `bazel cquery` on each, and diffs the resulting `analysis.ConfiguredTarget` objects directly (`WalkCallback func(label.Label, []Difference, *analysis.ConfiguredTarget)`, [README.md](https://github.com/bazel-contrib/target-determinator/blob/main/README.md)). This is the structural difference the brief asks to pin down: **content hash of the whole graph** (bazel-diff, default) versus **cquery-based configured-target comparison** (target-determinator, always). Bazel's own reference states the mechanism each rides: `query` "runs over the results of Bazel's loading phase, before options are evaluated", while `cquery` "runs over the results of Bazel's analysis phase" and therefore resolves `select()` and platform constraints exactly ([bazel.build/query/cquery](https://bazel.build/query/cquery)). `bazel-diff`'s optional `--useCquery` mode is the point where the two tools' mechanisms converge — at the cost target-determinator pays by default: slower, per-revision `cquery` execution.

### 3. bazel-diff's documented miss class

The brief's required admission — "bazel-diff is incorrect and will sometimes miss affected targets" — traces to a specific, reproducible class, not a vague hedge. [Issue #134](https://github.com/Tinder/bazel-diff/issues/134) (opened 2022-05-19, closed 2023-03-01) reports that a `whl_library` (rules_python's pip-resolution repository rule) gaining a new transitive dependency does not change `bazel-diff`'s output hash for the dependent target. Maintainer [alexeagle](https://github.com/Tinder/bazel-diff/issues/134#issuecomment-1131359885) diagnosed the mechanism precisely: `bazel-diff` queries `//external:my_deps_testcontainers`, the repository rule's **definition**, which "doesn't express any dependency on `wrapt`"; the dependency only appears in `@my_deps_testcontainers//:pkg`, the **generated** `BUILD` content produced by *executing* the rule. Tinder's own reply closed the issue: "This is expected behavior. If you want to include these transitive targets I would look into the `-s=<seedFilepaths>` option" (`tinder-maxwellelliott`). `target-determinator`'s own maintainer, in the same thread, states this class of bug was one of their project's founding motivations: "we put in quite a bit of care to follow deps through repository rules to all affecting files" (`illicitonion`).

The current README documents three mitigations layered on top of the 2022/2023 state, none of them the default:

```
-s, --seed-filepaths=<seedFilepaths>
    A text file containing a newline separated list of filepaths. Each file in
    this list will be read and its content will be used as a SHA256 seed when
    determining affected targets in the build graph. Invalidating any of these
    files will effectively mark all targets as affected.

--fineGrainedHashExternalRepos=<fineGrainedHashExternalRepos>
    Comma separate list of external repos in which fine-grained hashes are
    computed for the targets. By default, external repos are treated as an
    opaque blob… For example, one wants to specify `maven` here if they use
    rules_jvm_external so that individual third party dependency change won't
    invalidate all targets in the mono repo.

--alwaysAffectedTags=<alwaysAffectedTags>
    …Any target whose `tags` attribute contains one of these values is always
    reported as impacted… Use this for non-hermetic targets that read
    undeclared workspace state at execution time (e.g. repo-scanning linters
    such as buildifier/gofmt/eslint tests) which would otherwise hash as
    unchanged and be wrongly skipped.
```

`seed-filepaths` is the coarsest fix (marks *everything* affected on any change to the named files); `--fineGrainedHashExternalRepos` is the surgical one, but it is an allow-list a maintainer must keep exhaustive as new module extensions/repo rules are added — a second, quieter miss class. A related, current (not 2022-era) trap: `//external:*` labels are synthetic, exist only so `generate-hashes` can express the dependency, and "are not buildable in bzlmod-only mode… and will fail downstream `bazel build`" ([issue #326](https://github.com/Tinder/bazel-diff/issues/326), cited in the current README); `--excludeExternalTargets` defaults to on when Bzlmod is auto-detected via `bazel mod graph`, but a repo that runs with `--enable_workspace=false` in an unusual configuration must set it explicitly.

### 4. target-determinator's documented miss class

The exact quoted admission, verbatim from the current README's `-cache-dir` flag help text: "home- and system- bazelrc files, environment variables, and host hardware/OS are not included in the results cache key. Use `--nocache_results` if necessary." The README's own "Caching" section names the concrete failure: a cached "before" `cquery` result "may have been computed in an earlier pipeline run, under the environment variables that were in effect *at that time*. If an environment variable affected Bazel's query output… the cached result reflects the old environment, while the 'after' result reflects the new one. The two results are then compared under different conditions, which may produce spurious differences." The worked example given is release/stamping variables (`MY_PKG_VERSION`)-style env vars that vary run to run. The tool's own fix is explicit: `--nocache_results` forces both computations into the same, current environment — at the cost of losing the cache's speed entirely for that run. A second, separately named exclusion: "The host machine (hardware, OS). Cache entries produced on one machine are not guaranteed to be valid on another (e.g. a different CPU architecture can change which platform-constrained targets are selected). Do not share the cache directory across machines" — a direct trap for any CI matrix that shares a cache volume across OS/arch legs. `-filter-incompatible-targets` also defaults `true`, silently dropping platform-incompatible targets from the affected set before a caller ever sees them — correct for "should CI build this", wrong for "does this exist" style audits.

### 5. The provenance of "bazel-diff is incorrect" — who actually said it

The map's Conflict 1 attributes the quote "is incorrect and will sometimes miss affected targets" to "`bazel-diff`'s README" concedes it. A full-text fetch of the current README, and a GitHub code search across the whole repository for that exact phrase, both return zero matches. The phrase is [Aspect's own characterization](https://aspect.build/blog/monorepo-shared-green), in Alex Eagle's 2022-08-08 blog post: "tinder/bazel-diff is very incorrect" (linking to issue #134) and, separately, "target-determinator is very slow" (linking to target-determinator's own issue #3). The distinction matters for anyone re-deriving this claim later: `bazel-diff`'s README documents specific, named mitigations for a specific, named miss class (Finding 3); it does not carry a blanket self-admission of incorrectness. Both readings point at the same underlying fact (issue #134 is real and was closed as "expected behavior"), but citing the wrong source as "the tool's own admission" is exactly the kind of provenance error this program's house standard exists to prevent.

### 6. Aspect's shared-green counter-position, and where its own product has moved since

Aspect's 2022 post argues for one unified pipeline: "If anything is red, nothing can release," with in-flight collisions handled by either reverting or a merge queue, and notes shared-green scales for organizations "100 to 1000 times smaller than 2015 Google" (2 billion SLOC) — i.e. up to roughly 2–20 million lines, a scale no fleet repo is within three orders of magnitude of. That is Aspect's 2022 argued position, and the map's Conflict 1 already resolves the "which tool" fork on it.

What is new here: Aspect's **current** commercial product, Aspect Workflows, ships a feature named **Selective Delivery** (`aspect.build/docs/workflows/features/delivery/`) that does not resemble either tool. It compares "the content hash of each build output, not the git SHA or a timestamp" — "If Bazel produces the same output digest for a target, that target is not pushed, even if unrelated files changed in the same commit." This runs *after* a full, already-green build and test (so it inherits none of `bazel-diff`'s or `target-determinator`'s pre-build correctness risk) and decides only what to *publish*: "works from hashes alone and never downloads an artifact, so determining what to deliver costs almost nothing." This is a third model, distinct from both tools this brief was scoped to and from Canva's input-hashing layer (Finding 8): decouple "what must be tested" (needs the full determinism gate, Finding 10) from "what must be published" (needs only Bazel's own already-computed output digests, post-build).

### 7. Tinder's 93 percent, unpacked

The number the brief names — "Tinder's reported 93 percent CI time reduction" — is real but composite. Per the [Buildkite webinar](https://buildkite.com/resources/webinars/how-tinder-built-and-open-sourced-bazel-diff-to-transform-their-ci-cd-at-scale/) featuring `bazel-diff` maintainers Maxwell Elliott and Connor Wybranowski, and the BazelCon 2025 talk "[Precision CI at Scale: Target-Aware Workflows with Bazel Diff](https://www.youtube.com/watch?v=rCFc3tFcVVE)": **93% P100 CI time savings comes from `bazel-diff` combined with Buildkite's dynamic pipelines**, and is explicitly framed as "a 54% improvement over Bazel-diff alone" — meaning roughly half of the 93% figure is attributable to a pipeline-orchestration mechanism (Buildkite dynamic pipelines), not to `bazel-diff`'s target diffing by itself. The accompanying scale context: a 1.5-million-line codebase, 300+ Bazel build targets, a 5-engineer platform team serving 40+ affected engineers, and 40–60 minute CI builds before adoption; the reported savings are 17 years of annual compute at P100, 4+ years at P90. The webinar also states the tool provides "100% accurate target diffing" via "Merkle tree cryptographic summation" — a claim in tension with the tool's own issue tracker (Finding 3); see AI-agent angle §1.

### 8. Canva's third path, and the step that had to come first

[Canva's account](https://www.canva.dev/blog/engineering/faster-ci-builds-at-canva/) (Marco Lacava & Arpit Sharma, 2024-07-30) describes building a dedicated system that precomputes `bazel-diff`-style input hashes per commit and uploads them to S3, moving the expensive computation off the pipeline-generation critical path (10+ minutes down to 2–3 minutes) and into a background job with an explicit fallback: "if the process failed, we left Bazel to do its usual thing." This is the "custom input-hashing layer over BwoB" the brief names — a decoupling optimization on top of the same content-hash idea `bazel-diff` uses, not a different correctness model.

The sequencing is the finding the brief asks to lead with: before this layer went live (2024-01-31), Canva had to make three separate hermeticity fixes, in this order:
1. Backend integration tests were "non-hermetic (and therefore not cacheable)" — converted to TestContainers so each test brings its own isolated dependency rather than sharing a long-lived container across runs.
2. Frontend integration tests were similarly converted to run under Bazel, enabling caching and parallelism.
3. Accessibility (a11y) tests ran unbounded, one job per page — Bazelifying this collapsed **67,145 jobs down to 1 per commit**.

Only after all three did the CI Experience working group (formed mid-2022) trust a selective-execution layer on top of the result: April 2023's pipeline v2 (49→35 min), September 2023's Bazel-integrated FE/a11y suite, and January–March 2024's static-pipeline-generation-plus-selective-delivery work took the whole pipeline from roughly 80 minutes (April 2022) to under 30 minutes (2024), a reported 62.5% reduction. The 67,145-to-1 collapse is the single most concrete illustration in this corpus of "carve out the non-hermetic and unbounded steps before any selection strategy can be trusted" — it happened *before* the input-hashing layer, not alongside it.

### 9. What Google's TAP and Meta's Predictive Test Selection do instead

Neither of Google's or Meta's approaches is a drop-in alternative to `bazel-diff`/`target-determinator` at fleet scale, but both name the ceiling and floor of the design space these two tools occupy. Google's TAP, per *Software Engineering at Google* ch. 23, runs "more than 50,000 unique changes and… more than four billion individual test cases" a day; at that volume "it can no longer run every test on every change. Instead, it falls back to batching related changes together" — accepting that batching "can obscure which change in the batch caused a test to break," mitigated by automated batch-splitting and developer-facing binary-search tooling ([abseil.io/resources/swe-book/html/ch23.html](https://abseil.io/resources/swe-book/html/ch23.html)). This is neither `bazel-diff`'s nor `target-determinator`'s model — it is throughput-driven batching over a dependency graph, not per-commit graph diffing, and it only becomes necessary at a scale no fleet repo is within several orders of magnitude of.

Meta's [Predictive Test Selection](https://arxiv.org/abs/1810.05286) (Machalica, Samylkin, Porth & Chandra; submitted 2018-10-11, revised 2019-05-29) is the third model: an ML classifier trained on historical test-outcome data decides, per change, which tests to run — a probabilistic skip that "accounts for the non-determinism of test outcomes, also known as test flakiness," and reports an infrastructure-cost reduction "by a factor of two" while still catching "over 95% of individual test failures" and reporting "over 99.9% of faulty changes… back to developers." The structural difference from both `bazel-diff` and `target-determinator`: this model accepts and publishes a quantified miss rate as a design parameter, rather than presenting a graph diff as deterministically complete. Neither tool in this dive's scope offers that framing — see Contested/evolving.

### 10. The determinism precondition as an ordered gate

Per the REVISION ADDENDUM, this gate cites wave-2 conclusions; it asserts none of its own. In order, each step is a stop condition for the next:

1. **Environment tiers are pinned per Bazel major.** [BZL-HERM-01](../bazel-hermeticity-determinism.md) (`--incompatible_strict_action_env` defaults `false` on all of Bazel 8.x, `true` only from 9.0.0) and [BZL-HERM-04/05](../bazel-hermeticity-determinism.md) (`--repo_env` vs `--action_env`, and `--incompatible_repo_env_ignores_action_env`'s own 8→9 flip) must be satisfied — otherwise two revisions built under different Bazel majors in the same CI matrix are not comparable in the first place, independent of any selection tool.
2. **No undeclared non-determinism in the actions a selection tool would otherwise trust as "unchanged".** [BZL-HERM-10/11](../bazel-hermeticity-determinism.md) (no embedded timestamps, PIDs, absolute paths; sorted serialization) and [BZL-HERM-19](../bazel-hermeticity-determinism.md) (a `glob()`'s match set is not readable from its pattern and can shrink silently) — a target selection tool computing "this target's inputs didn't change" is only as trustworthy as the input enumeration itself.
3. **Isolate every non-hermetic CI step**, per Canva's own sequencing (Finding 8): a shared external service (a database, a container, a live registry) or an unbounded per-item suite must be converted to a self-contained, Bazel-visible test *before* any tool's "unchanged" verdict on it means anything.
4. **Cache-eviction and lost-input handling must not be misread as "nothing to select".** [BZL-CACHE-12](../bazel-caching-rbe.md) (exit code 39 is retryable, reachable on a cache-only build) — a build that silently retries past an evicted blob, or worse treats the retry's absence of output as "target unaffected", produces a false negative indistinguishable from the selection tool's own miss class unless the two are diagnosed separately.
5. **Only then is a selection tool's own documented miss class (Findings 3–4) the dominant remaining risk**, and it is diagnosed with [BZL-CACHE-16](../bazel-caching-rbe.md)'s execution-log diff method when a specific "why wasn't this rebuilt" question arises, not by re-reading Starlark.

This gate is a precondition, not a checklist item that can be skipped for a small repo: a repo below the scale threshold (Decisions §1) does not need a selection tool, but every repo — selecting or not — benefits from steps 1–2 being true, because they are the same facts BZL-CACHE-16's "diagnose an unexplained rebuild" procedure depends on.

## Decisions

**1. Fleet default: whole-repo green, with a named scale threshold for switching.**
Decision: every fleet repo, and any Bazel-adopting repo below the threshold, runs `bazel test //...`/`bazel build //...` on every CI trigger; a repo crosses into "consider target selection" territory at roughly **300 Bazel targets or a whole-repo CI wall-clock time consistently above ~40 minutes, whichever comes first**.
Evidence: Tinder's own reported pre-adoption state — "300+ build targets", a 1.5M-line codebase, 40–60 minute CI builds — is the only concretely evidenced point in this corpus where a real team found whole-repo green no longer tenable and adopted a selection tool ([Buildkite webinar](https://buildkite.com/resources/webinars/how-tinder-built-and-open-sourced-bazel-diff-to-transform-their-ci-cd-at-scale/)). Aspect's argued upper bound (shared-green viable up to roughly 2–20M SLOC) is consistent with, not contradicting, a much lower switch point for a team without a dedicated build-platform group — Canva and Tinder both stood up dedicated platform effort (a working group, a 5-person platform team) specifically to cross this line.
Assumption named: the threshold assumes no dedicated Bazel build-infrastructure team is doing the crossing-work for free; a team the size of Canva's (with hermeticity prep already amortized org-wide) can push the practical switch point far higher. Test against real fleet numbers per the brief: `creeptd-ng` (13 `Cargo.toml`, 3 `package.json`, 3 build scripts) is roughly an order of magnitude below 300 targets even under a generous 2–3-targets-per-crate estimate — **no repo in this fleet is within reach of the threshold today**, matching frame decision-table Q3 and map Conflict 16.

**2. The determinism precondition is an ordered gate, cited not asserted.**
Decision: the five-step gate in Finding 10 is mandatory before trusting *any* target-selection tool, and its steps are cited from BZL-HERM/BZL-CACHE by rule ID, per the REVISION ADDENDUM's binding instruction.
Evidence: Canva's own documented sequencing (Finding 8) — hermeticity fixes shipped before the input-hashing layer, not alongside it — is the only primary source in this corpus that names an explicit *order*, and it matches the wave-2 rule dependencies exactly (environment tiers → non-determinism causes → non-hermetic isolation → eviction handling).
Assumption named: "trustworthy" here means "a false-negative rate the team has actually reasoned about", not "zero false negatives" — no tool in scope claims the latter honestly (Finding 9's contrast with Predictive Test Selection is the sharpest illustration of why not).

**3. Per-tool miss class, stated so a reviewer need not re-read the README.**
Decision: `bazel-diff` (default mode) misses a transitive dependency that appears only in a repository rule's *generated* content (pip/npm/Maven-style resolution, module-extension-created repos) unless `--fineGrainedHashExternalRepos` names that repo or `--seed-filepaths` marks the coarser boundary; `target-determinator` misses (or worse, produces a spurious *false positive*) a change whose effect flows only through a home/system `.bazelrc`, an environment variable, or the host machine's hardware/OS, because none of those enter its results-cache key.
Evidence: `bazel-diff` issue #134 (maintainer-confirmed, closed as expected behavior) and the current README's own flag documentation; `target-determinator`'s README, verbatim, in its `-cache-dir` help text and "Environment variables and caching" section.
Assumption named: both descriptions are of the tools' **current** releases (`bazel-diff` v46.1.0, 2026-08-28; `target-determinator` v0.34.0, 2026-06-19) — the 2022-era Aspect critique predates most of the mitigation flags named here (Contested/evolving).

**4. The 31.23%/27.76% surprise becomes the hand-off checklist's opening gate, not a footnote.**
Decision: `bazel-adopt`'s go/no-go gate (frame Conflict 2, M-F-04) is upstream of this dive's entire subject — a hand-off checklist item reading "choose bazel-diff or target-determinator" is malformed until "CI actually invokes Bazel in a build/test step" is independently confirmed.
Evidence: [Zheng, Adams & Hassan (2024)](https://arxiv.org/abs/2405.00796)'s own two numbers, unconditional on scale or tool choice.
Assumption named: none — this is the one item in this section resting on measured, not argued, evidence.

## AI-agent angle

1. **Quoting "93 percent CI time reduction" as `bazel-diff`'s number alone.** The actual figure is `bazel-diff` *plus* Buildkite's dynamic pipelines, with the vendor's own materials stating a "54% improvement over Bazel-diff alone." Check: does the sentence citing 93% also name the second mechanism? If not, it is dropping half the causal story.
2. **Attributing "is incorrect and will sometimes miss affected targets" to `bazel-diff`'s own README.** A full-text search of the current README (and a GitHub code search across the whole repository) returns zero matches; the phrase is Aspect's 2022 blog characterization. Check: before quoting a tool's "own admission," grep the actual fetched document for the exact string.
3. **Assuming `bazel-diff`'s default mode is `cquery`-based and resolves `select()` exactly**, because `target-determinator` (its most commonly co-mentioned peer) works that way. `bazel-diff` defaults to plain `bazel query`; `cquery` mode is opt-in via `--useCquery` and needs Bazel ≥6.2.0 plus an explicit target platform. Check: does the invocation being described pass `--useCquery`? If not, describe it as an over-approximation of configuration effects, not an exact one.
4. **Recommending a BwoB/`--remote_download_*` flag as the fix for a slow or incorrect target-selection setup.** That family (`BZL-CACHE`) governs how much of a build's outputs are materialized locally; it has no bearing on which targets a selection tool decides to build in the first place. Check: is the flag being proposed one that changes what gets *selected*, or one that changes what gets *downloaded* after selection already ran?
5. **Treating a tool's "empty diff" or "zero impacted targets" result as proof nothing changed**, rather than as a claim scoped by that tool's own documented exclusions (BZL-CI-15). Check: before accepting an empty result as a skip-everything signal, name which of the tool's own miss classes (Findings 3–4) could produce that exact output for a real change.
6. **Proposing a Bazel-native "affected targets" flag** because one "feels like it should exist" for a build system this mature. It does not: [bazelbuild/bazel#7962](https://github.com/bazelbuild/bazel/issues/7962), Bazel core's own tracked request for a rule-key/target-diffing primitive, has been open since 2019-04-05 and remained open through 2024-02-28. Check: `bazel help query 2>&1 | grep -i affected` — no such built-in exists; any guidance implying one is fabricated.
7. **Carrying forward a 2022-era description of either tool's flag surface** (BZL-CI-16). `bazel-diff` has added a persistent `serve` mode, an S3-backed shared cache, Firecracker-snapshot integration (`warmup`/`fingerprint` subcommands), and four flags that did not exist when the Aspect critique was written. Check: `bazel-diff --help` (or a fresh README fetch) against any flag name before citing it.

## Contested / evolving

- **`bazel-diff` is mid-rewrite from Kotlin to Rust, and shipping infrastructure features, not just a CLI.** The live repository carries both a legacy Kotlin/JVM toolchain (`Prerequisites: Java 8 JDK or higher`) and Rust build files (`Cargo.toml`, `build.rs`, `cargo-bazel-lock.json`, a `rust/` directory) plus comparison docs (`docs/kotlin-rust-perf-gate.md`, `docs/kotlin-vs-rust-benchmark.md`, `docs/kotlin-rust-test-parity.md`). As of the current release (v46.1.0, 2026-08-28) the tool has grown a long-running HTTP `serve` mode with a shared S3 cache tier and Firecracker-snapshot warmup/fingerprint commands — trending toward becoming CI infrastructure in its own right, not a point-in-time CLI invoked twice per pipeline run. Any guidance more than a year old likely undersells its current feature surface.
- **Aspect's own position has bifurcated since 2022.** The 2022 blog argues against target selection entirely, in favor of shared-green. The current commercial product (`aspect.build/docs/workflows/features/delivery/`) ships a selective mechanism of its own — just scoped to *delivery* (post-build output-digest comparison) rather than *test selection* (pre-build graph diffing). This is not a reversal of the 2022 argument so much as a narrower, lower-risk problem the same organization decided was worth automating once the higher-risk one was set aside.
- **Deterministic graph-diffing versus probabilistic, quantified-miss-rate selection are still two separate communities.** `bazel-diff` and `target-determinator` both frame correctness as a property to approach asymptotically (more flags, finer-grained external-repo handling); Meta's Predictive Test Selection frames it as a number to publish and manage (">99.9% of faulty changes still reported," "over 95% of individual test failures" caught). As of 2026-09-05 no widely-used open-source Bazel tool in this space has adopted the probabilistic framing — it remains a large-single-org (Meta, and by extension Google's TAP-scale batching) pattern, not yet a packaged tool a mid-scale Bazel adopter could install.
- **Bazel core still has no native answer, five-plus years into the tracked request.** [bazelbuild/bazel#7962](https://github.com/bazelbuild/bazel/issues/7962) (opened 2019-04-05, last updated 2024-02-28, still open) means every tool discussed in this dive remains third-party by necessity, not by current oversight — worth stating plainly so nobody waits for an upstream fix that has no committed timeline.
