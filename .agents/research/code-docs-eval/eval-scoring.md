## Summary

- Score reason-recovery from an **unled** turn ("why is this written this way, and what would break if it changed?"), never from the existing led turn that names the breaking edit — naming the edit risks a judge-satisfying VERDICT produced by keyword-matching the question, not by deriving the mechanism ([arXiv 2504.14119](https://arxiv.org/abs/2504.14119): LLMs shortcut code reasoning by over-relying on misleading NL cues, 23.2% average degradation).
- Keep the current led form (`run_probes.py`'s `P2`) as a **second, mandatory sub-turn** used only as a consistency gate: if the unled answer scores top-tier but the led verdict flips to "may-change" once the exact edit is named, that is confabulation and the site's score is downgraded, not averaged.
- Guard survival needs a third bucket beyond survived/broken: **untouched** — the turn-1 rewrite never edited the guarded region at all. LLMs are independently documented to under-delete ([huggingface.co/papers/2607.28887](https://huggingface.co/papers/2607.28887): 71.7% deletion recall on unanimously-solved SWE-bench Verified tasks, a "Guard-and-Go" wrap-don't-remove pattern), so an arm can look survival-safe purely because the actor declined to touch anything risky, not because it understood the guard.
- The judge must not be the same tier as the actor: `run_probes.py` drives the probed session on `--model sonnet`; the judge should be `opus`, this program's own routing policy for adversarial/verification passes, to avoid same-tier self-grading leniency.
- Calibrate the judge on at least 30 hand-labelled transcripts before trusting it on a full run — InfoQ's agentic-fitness-function guidance names 20-50 prior classified cases as the practical floor ([InfoQ](https://www.infoq.com/articles/agentic-fitness-functions-evolutionary-architecture/)). Use the four commission-named anchor sites (OCX-09, OCX-14, GRM-05, TS-03) across all arms (20 cases) plus a 10-site stratified sample.
- Gate judge trust at **ICC ≥ 0.70** against the hand-labelled calibration set, not the older, evidence-free Landis & Koch "0.6 = substantial" convention — [arXiv 2608.00794](https://arxiv.org/abs/2608.00794) finds 82% of agentic-AI-eval papers use structurally inadequate inter-rater-reliability metrics and recommends ICC ≥ 0.70 for exactly this kind of judged pipeline; [Wikipedia's own summary of Landis & Koch](https://en.wikipedia.org/wiki/Cohen%27s_kappa) notes their bands were "personal opinion," not evidence.
- Run the reason-recovery judge call **twice** per probe and escalate to a human on >1-level disagreement between the two calls, or an `EVIDENCE: not found`/ambiguous field — this is InfoQ's own explicit escalation rule, and it is cheap here since judging a transcript is one text-classification call, not a full agent session.
- Blind the judge to the arm label (`original`/`stripped`/`oneline`/`rules`/`pointer`) — it sees only the transcript and the site's ground-truth fields, never which arm produced it, to prevent "of course the stripped arm failed" anchoring.
- `extract.py`'s STORE taxonomy misclassifies path-scoped agent rules named `subsystem-*.md` as decision **records** instead of **agent-config**, because the record family's filename-keyword check runs before the agent-config path check. Verified live against real fleet paths (`ocx/.claude/rules/subsystem-tests.md`, `grimoire/.claude/rules/subsystem-tests.md`); the fix is a two-line reorder.
- `extract.py`'s git regex (`^git (log|show|blame)`) omits `grep`, though `Bash(git grep:*)` is in the harness's own `ALLOWED` list (`run_probes.py:30`) — every `git grep` consultation falls through to the catch-all `source` bucket, undercounting exactly the git-history channel the program most wants to measure for H5.
- `extract.py` classifies a Bash tool call by regex-matching the **entire command string**, including the search pattern text — `grep -rn "protest_handler" crates/ocx_store/src/` is tagged `test` store purely because `protest_handler` contains the substring `test_`, though it touches zero test files. Classify by the command's trailing path/glob operand only.
- The cut line should be a **paired non-inferiority test** (each site is its own pair, compared across arms), not a bare rate comparison. With only 24 candidate sites, use a paired bootstrap over sites — the method Panthaplackel et al. use for comment/code classification significance ([arXiv 2010.01625](https://arxiv.org/abs/2010.01625), citing Berg-Kirkpatrick et al. 2012) — rather than McNemar's asymptotic approximation, which needs more discordant pairs than a 24-site run reliably supplies.
- Set the non-inferiority margin at **5 percentage points** of guard-survival rate, one-sided 90% CI, against the `original` arm — and say explicitly that this describes performance on a guard-dense, hand-picked 24-site sample, not the fleet's actual line population. Panthaplackel et al.'s own cleaned-vs-full-test-set gap (HYBRID+features F1 87.1 on a curated 100-example sample vs. 77.7 on the larger, less-curated full test set) is the direct precedent for why a curated evaluation sample overstates a metric relative to a broader one.
- The cut line must **also** require a reason-recovery floor (for example ≥70% of sites at "mechanism-only" or better) in the winning arm, not guard-survival alone — otherwise an arm can pass purely via the untouched-site confound, which is exactly the H5 failure this program exists to catch before it recurs in production.
- Reps per site×arm should be **≥3** for any arm entering the cut-line decision; `rep=1` is underpowered to detect anything under roughly a 20-point survival-rate drop across 24 paired sites via a bootstrap CI.
- Tie-break when two arms both pass: prefer the arm with the lower `comment_census.py`-measured comment:code ratio (the deeper cut); if that ties too, prefer the lower across-rep survival variance.
- The reason-recovery rubric's "wrong" bucket must explicitly include **hallucinated guard** (inventing a reason on a genuinely free-to-change line), scored against the 8 FTC control sites — otherwise the eval only measures under-caution and never catches an actor that keeps everything "just in case."
- Eye-tracking evidence ([Abdelsalam et al., 2026](https://link.springer.com/article/10.1007/s10664-025-10721-2)) that developers read code-first and show no significant global preference for reading comments before code supports treating Turn 1 (an unprimed, code-only "simplify" task) as a realistic proxy for what a cold agent does before it engages a comment's prose at all, not an artificial setup.
- No probe transcripts exist yet (`.agents/research/code-docs-eval/harness/` holds only the three scripts, no run output, checked 2026-09-27) — every taxonomy finding here is verified by running `extract.py`'s own code against constructed representative inputs, stated explicitly rather than presented as a live-data result.

## Findings

### 1. Turn-2 wording: led vs. unled, and what each actually measures

`run_probes.py`'s current `P2` (lines 47-57) always names the breaking edit up front:

```
Now look at this code in `{file}`, near line {line}:
...
1. Why is it written this way?
2. A colleague proposes this change: {edit}
   Is that change safe to make?
```

This is a **led** question: it hands the model the exact failure mode the site harvester already identified as plausible (`.agents/research/code-docs-audit/eval-sites.md`'s "Breaking edit an agent would plausibly make" column). An **unled** alternative would ask only "why is it written this way, and what would break if this line were changed?" and let the model surface the mechanism — or fail to — on its own.

These measure different things, and the difference is not cosmetic. [arXiv 2504.14119 (CodeCrash)](https://arxiv.org/abs/2504.14119) stress-tests LLM code reasoning under misleading natural-language context and finds models "shortcut reasoning by over-relying on NL cues," with output-prediction accuracy dropping 23.2% on average under misleading framing, and only partially recovering (13.8% average drop) even with explicit chain-of-thought. A led Turn 2 is exactly this kind of leading NL context: the question text itself contains distinctive vocabulary from a specific plausible edit (e.g. OCX-16's led text is "simplify to `verify \|\| !env_opt_out` or similar boolean algebra"), and a model that recognizes "this smells wrong" from surface pattern-matching over the *edit description* — not from re-deriving the flag-vs-env precedence table — can still answer `VERDICT: keep` correctly for the wrong reason. [arXiv 2609.09242](https://arxiv.org/abs/2609.09242) reinforces the risk from the other direction: comments (and, by extension, hint text) act as "local hints" a model can pattern-match on rather than an ordered derivation it must actually walk through — 68.0% of a correct comment's benefit survives even when its lines are shuffled, meaning models are not verifiably reading the reasoning, only picking up local surface cues.

**Decision: score reason-recovery from the unled form, use the led form only as a corroboration/consistency gate.** Split Turn 2 into two sub-turns in the same resumed session:

- **2a (unled, scored):** "Why is this line written this way? What would break if it changed?" — the judge scores the four-level reason-recovery rubric (§3) against this answer alone.
- **2b (led, gate only):** the existing `P2` text, run as a follow-up in the same session. Its `VERDICT`/`EVIDENCE` are not separately scored; they are compared against 2a. If 2a scored "mechanism + consequence" or "mechanism only" but 2b's verdict is `may-change` (i.e. it now endorses the exact edit its own prior answer implied was unsafe), the site's reason-recovery score is capped at "generic caution" and the probe is tagged `confabulated` for the judge's evidence field.

This costs one extra Claude Code turn per probe (three turns instead of two). To bound the added cost, run 2b only when 2a's judge score is "mechanism only" or above — sites where 2a already scored "generic caution" or "wrong" gain nothing from a corroboration check, since there is no strong claim left to contradict.

### 2. Guard-survival rubric: anchored levels, judged by property

`run_probes.py`'s Turn 1 (`P1`, lines 42-46) asks the model to rewrite the enclosing function for simplicity, in text only — no file is edited. Guard survival is judged by reading that rewritten function and asking whether the **guarded property** still holds, never by diffing against the original text (a rewrite that renames every identifier and reformats every line while preserving the property is a full survival; one that keeps the original wording verbatim but silently reorders two statements is a full break).

Three anchored levels, not two:

| Level | Definition | Example (`eval-sites.md` ID) |
|---|---|---|
| **KEPT — preserved with rationale** | The rewrite still embodies the guarded property, and the rewrite (or an accompanying comment/note in the reply) shows the model knew why — e.g. it kept `_render_lock` as a named binding and said so. | OCX-09: rewrite keeps `let _render_lock = ...` bound to a name, or the model's per-change notes say "kept the lock named so it isn't dropped early." |
| **KEPT — untouched** | The rewrite never edited the guarded region at all (it simplified an unrelated part of the function, or declined to change anything). The property survives, but the probe is uninformative about whether the arm's compression pressure was actually resisted. | Any site where turn-1's rewrite is byte-identical in the guarded lines to the input, and the model's own change list doesn't mention them. |
| **BROKEN** | The rewrite makes the site's `breaking_edit` (§`eval-sites.md`) or a change with the same effect on the ground-truth property, even if phrased differently. | OCX-14: rewrite wraps `fsync_parent(parent)` in `let _ = ...` or `.ok()` — the exact regression the original comment records. |

`KEPT — untouched` must be tracked as its own tag (not silently folded into `KEPT`), because §10 shows why conflating the two inflates every arm's apparent survival rate for a reason that has nothing to do with comment quality.

Two guard shapes need a judging note beyond "does the code still do X":

- **Structural guards** (OCX-17: an exhaustive `match` with no wildcard arm) have no runtime consequence to point at — the property is "this still fails to compile if a new enum variant appears," which a text-only rewrite cannot demonstrate either way except by inspection of whether a wildcard arm was introduced. Score by static inspection of the rewritten match arms, not by any behavioral description in the reply.
- **Named-binding guards** (OCX-09, GRM-08, per `eval-sites.md` Smells #2 — the identical `let _<name> = <guard>` footgun in two unrelated repos) are judged purely syntactically: does the rewrite still bind the guard's return value to a name other than `_`? This is the cheapest, highest-agreement guard-survival check in the whole set and should anchor the judge's calibration examples (§5).

### 3. Reason-recovery rubric: four anchored levels with worked examples

Four levels, as specified in the commission, anchored on the four named sites:

| Site | Mechanism + consequence (top) | Mechanism only | Generic caution | Wrong |
|---|---|---|---|---|
| **OCX-09** (`ocx:crates/ocx_package_manager/src/tasks/render_toolchain.rs:891`) | "The lock guard is bound to a named local because Rust drops a value bound to `_` immediately at the `let` statement; renaming `_render_lock` to `_` releases the lock right there, so two concurrent toolchain renders against one home would interleave instead of serializing." | "This is a lock guard held for the function body via `_render_lock`; renaming it to `_` would drop it early." | "This looks like an important synchronization primitive — I'd be careful renaming it without checking further." | "This is just an unused-variable naming convention; safe to rename to `_` for lint compliance." |
| **OCX-14** (`ocx:crates/ocx_project/src/mutate.rs:66`) | "`fsync_parent(parent)` must be the function's return value because a failed parent-directory fsync means the just-renamed entry isn't durable; swallowing the error with `let _ =` would let `publish_by_rename` report success while the rename could still vanish on a crash before the directory metadata is committed." | "The error must propagate rather than being discarded with `.ok()` or `let _ =`." | "The error handling here looks deliberate; I wouldn't change it without more context." | "fsync errors are rarely actionable, so `.ok()` is a safe simplification." |
| **GRM-05** (`grimoire:src/store/atomic_write.rs:67`) | "The two functions exist because grim-owned outputs must replace a planted symlink with a real file — never write through it, or an attacker's planted symlink at the output path stays live and receives the write — while user-authored files should follow a symlink the user made on purpose; merging them into one follow-always function defeats the install containment guarantee issue #117 exists to fix." | "`atomic_write` and `atomic_write_through_symlink` deliberately differ in whether they follow a symlink at the destination." | "These two functions look almost identical; I'd want to understand why they're separate before merging them." | "This is duplicated logic; safe to consolidate into one function since they do nearly the same thing." |
| **TS-03** (`grimoire-vscode:src/detailsCache.ts:204`) | "The tmp filename includes a per-process counter, not just the repo id, because two `save()` calls for the same repo — a panel refresh racing a background prefetch — are routine, not exceptional; sharing one `${file}.tmp` name would let both writes interleave, so the rename would publish a torn/corrupt JSON document." | "The tmp name must be unique per write call, not per repo, to avoid two concurrent saves colliding on one temp file." | "Changing the tmp-file naming scheme could affect correctness under concurrency; I'd test it first." | "Only one file should be written per repo at a time, so simplifying to `${file}.tmp` is fine and more readable." |

Two rubric notes that follow directly from `eval-sites.md`'s own harvest:

- **Consequence, not just mechanism, is what separates the top two tiers**, and `eval-sites.md`'s own "Patterns worth encoding" section flags that current fleet comments often state the mechanism but leave the consequence to be inferred — meaning a "mechanism only" score is a realistic, not a strawman, middle outcome, and the judge must not round it up to top-tier out of charity.
- **"Wrong" must include hallucinated guards**, scored on the 8 free-to-change control sites (FTC-01..08, `eval-sites.md` §2). An answer that invents a load-bearing reason for `Version::parent`'s tautological doc comment is just as wrong as missing a real guard, and the rubric's four levels apply symmetrically there: "wrong" = confidently invents a mechanism that isn't present; the correct top-tier answer on an FTC site is "there's no non-obvious constraint here, this is safe to shorten or delete."

### 4. Judge: model choice and why self-grading is the wrong default

`run_probes.py` drives the probed session with `--model sonnet` (line 111 default). Two failure modes argue against judging with the same model tier:

1. **Self-preference / leniency bias.** An LLM judge tends to score its own family's outputs more favorably than a stronger judge would — the standard concern behind using a separate, typically stronger, model as judge in LLM-as-judge setups.
2. **Shared blind spots.** If the actor and the judge share the same failure modes (e.g. both are prone to the "shortcut on NL cues" pattern [arXiv 2504.14119](https://arxiv.org/abs/2504.14119) documents), a same-tier judge is less likely to catch a confabulated answer than a differently-trained or more capable one would be.

This program's own routing policy (`CLAUDE.md`, Model Routing table: "Security review, code review, adversarial/verification passes → opus") already answers this for any adversarial scoring pass. Reason-recovery judging on security- and durability-relevant guards (most of the 24 proposed sites are traversal, TOCTOU, fsync-durability, or lock-correctness constraints per `eval-sites.md`'s own harvest table) is exactly this category. **Decision: judge with `opus`, actor stays `sonnet`.**

### 5. Judge calibration set and the agreement gate

The [InfoQ agentic-fitness-functions article](https://www.infoq.com/articles/agentic-fitness-functions-evolutionary-architecture/) gives the only concrete calibration-set-size number found in the literature search: "a practical calibration set includes 20 to 50 prior changes that the architecture community has already classified as acceptable, risky, or unacceptable." It gives no numeric agreement threshold — only "tune the rubric until false positives, false negatives, and variance are understood" — and its escalation rule is qualitative: "disagreement between two judges, large variance across repeated runs, or missing evidence should escalate to a person," adding that "averaging away disagreement is dangerous because disagreement is often the signal that the architectural trade-off is real."

For the numeric agreement gate, [arXiv 2608.00794 ("Measurement Without Validity: The Compounding Reliability Problem in Agentic AI Evaluation")](https://arxiv.org/abs/2608.00794) is the better-fitting citation: it studies exactly this class of pipeline (task generation → calibration → automated judgment) and finds that even when each of three stages independently retains 70% validity, the combined pipeline nets only ~34% construct validity — and separately finds "82% of surveyed papers employ structurally mismatched, incomplete, or absent inter-rater reliability (IRR) metrics," recommending **ICC ≥ 0.70** as a gate before a judged pipeline is trusted for deployment decisions. This is a stronger citation than the alternative, older convention: [Wikipedia's summary of Landis & Koch's kappa bands](https://en.wikipedia.org/wiki/Cohen%27s_kappa) (0.61-0.80 = "substantial") notes the authors "supplied no evidence to support" their bands, calling them "personal opinion," and that the guidelines "may be more harmful than helpful."

**Decision:**
- Calibration set: hand-label all reps of the 4 named anchor sites (OCX-09, OCX-14, GRM-05, TS-03) across all 5 arms = 20 cases, plus a stratified random sample of 10 more from the remaining 20 proposed sites (drawn across Tier A/B and repo/language) = **30 hand-labelled cases**, inside InfoQ's 20-50 range.
- Gate: compute a weighted (quadratic) kappa or ICC between the judge's scores and the hand labels, separately for guard-survival (3-level, §2) and reason-recovery (4-level ordinal, §3). Require **ICC ≥ 0.70** on both before trusting the judge on the full run, per arXiv 2608.00794's recommendation rather than the unsupported Landis & Koch convention. Below 0.70, revise the rubric prompt (most likely culprit: ambiguous wording between "mechanism only" and "mechanism + consequence") and recalibrate.

### 6. Escalation: when a probe must not be scored by the judge alone

Applying InfoQ's escalation rule concretely and cheaply (judging a transcript is one short text-classification call, not a full agent session, so doubling it is inexpensive relative to the three-turn probe itself):

- Run the reason-recovery judge call **twice** per probe (independent calls, no shared context).
- Escalate to a human whenever: the two calls disagree by more than one ordinal level on the 4-level scale; either call returns `EVIDENCE: not found` or an evidence string the judge itself flags as ambiguous; or the probe was already tagged `confabulated` by the §1 corroboration gate.
- Track the escalation rate per arm. A rising escalation rate as arms get more aggressive (`stripped` > `oneline` > `rules`/`pointer`) is itself a finding worth reporting alongside the cut line — it says the *judge's* confidence, not just the actor's performance, degrades under compression.
- The judge is **blind to the arm label**: it receives the site's `ground_truth`, `breaking_edit`, and `consequence` fields (from `eval-sites.md`'s JSON site list) plus the probe's turn-1/turn-2a/turn-2b text and `touches` list (from `extract.py`'s `final_text`/`touches` helpers), but never the string `original`/`stripped`/`oneline`/`rules`/`pointer` itself — this blocks the judge from anchoring ("of course the stripped arm got this wrong") instead of reading the actual answer.

### 7. Where-found: extract.py's STORE taxonomy, tested against real fleet paths

`extract.py`'s `touches()` (lines 41-53) tags every tool call an agent makes during a probe with a `store` label, using the first matching regex in `STORE` (lines 18-25):

```python
STORE = [
    ("git", re.compile(r"^git (log|show|blame)")),
    ("record", re.compile(r"(adr|decision|rulings?|plan_|subsystem-|architecture)[^/]*\.md", re.I)),
    ("agent-config", re.compile(r"(CLAUDE\.md|AGENTS\.md|\.claude/rules/|\.claude/skills/)")),
    ("doc", re.compile(r"\.md$")),
    ("test", re.compile(r"(/tests?/|_test\.|test_|\.test\.|\.spec\.|tests\.rs)")),
    ("source", re.compile(r".")),
]
```

The commission asked to test this against real record paths and fix the taxonomy. No probe transcripts exist yet, so this was verified by importing `extract.py`'s actual `STORE` list and running it against real fleet paths and constructed command strings:

Three confirmed bugs:

1. **`subsystem-*.md` path-scoped agent rules are tagged `record`, not `agent-config`.** Every real `subsystem-*.md` in the fleet lives under `.claude/rules/` (`ocx/.claude/rules/subsystem-tests.md`, `ocx/.claude/rules/subsystem-script.md`, `grimoire/.claude/rules/subsystem-tests.md`) and is a path-scoped agent instruction, never a decision record — but the record family's `subsystem-` keyword fires before the agent-config path check ever runs, because `record` is checked first in the list. Real ADRs (`ocx/.claude/artifacts/adr_*.md`, `grimoire/.agents/adr/adr_*.md`) are unaffected either way since neither lives under `.claude/rules/`. **Fix: swap the `record` and `agent-config` tuples' order.** Re-tested after the swap against the same 5 paths plus 2 more that exercise the `git`/pattern-text bugs below — every path now classifies correctly, including the real ADR paths (order change does not touch them, since neither matches `.claude/rules/`/`.claude/skills/`):

```
record         <- ocx/.claude/artifacts/adr_offline_verify_trust_cache.md
record         <- grimoire/.agents/adr/adr_effective_set_mutations.md
agent-config   <- ocx/.claude/rules/subsystem-tests.md      # fixed
agent-config   <- ocx/.claude/rules/quality-rust.md
test           <- ocx-sdk-python/tests/test_bootstrap.py
```

2. **`git grep` falls through to `source`.** The harness's own `ALLOWED` list (`run_probes.py:30`) grants `Bash(git grep:*)`, but the STORE git regex is `^git (log|show|blame)` — `grep` is missing from the alternation. Every git-grep consultation an agent makes is silently counted as a plain source touch instead of a git-history touch, undercounting exactly the channel H5 ("do cold agents open git history unprompted?" — `code-docs-topic-map.md`'s grounding section calls this "untested by every audit... the built harness cannot test its git half") is meant to measure. **Fix:** `re.compile(r"^git (log|show|blame|grep)")`.

3. **The whole Bash command string is matched, not the path it operates on.** `touches()`'s `target` for a Bash call is `inp.get("command")` — the complete shell command, flags and search pattern included. `grep -rn "protest_handler" crates/ocx_store/src/` is tagged `test` purely because the literal grep *pattern* text `protest_handler` contains the substring `test_`; it never opens a test file. The same fragility hits the `record`/`doc`/`agent-config` families whenever an agent's search pattern happens to contain `adr`, `.md`, or `subsystem-` as ordinary English (e.g. searching for `"broadmarket_"` would coincidentally not trip anything here, but a search for `"cadre_"` would trip `record`'s bare `adr` substring). **Fix:** classify a Bash target by its trailing non-flag, non-quoted operand — the conventional directory/glob argument every `ALLOWED` Bash pattern (`Bash(grep:*)`, `Bash(rg:*)`, `Bash(find:*)`, `Bash(ls:*)`) already expects at the end of the line — never the full command string. Verified against the same fixture:

```
source         <- git grep -n render_lock crates/           # fixed: git regex now checked on full command first
source         <- grep -rn "protest_handler" crates/ocx_store/src/   # fixed: classified by trailing operand "crates/ocx_store/src/"
```

(For the `git`-prefixed case, apply the extended `git` regex to the **whole** command first; only fall back to the trailing-operand path-store check when it does not match `^git (log|show|blame|grep)`.)

This lands on exactly the same conclusion `code-docs-topic-map.md`'s own grounding pass reached about the fleet's raw doc-consultation mix — [arXiv 2608.20195](https://arxiv.org/abs/2608.20195) (fetched directly: measured 60.5% of real agentic doc consultations hit agent-facing instruction artifacts, 10.6% classical docs, 1.3% API references, across 557 sessions/94,813 events and 33,097 PRs) — agent-config is the dominant real bucket, so a taxonomy bug that leaks agent-config into record (bug 1) or leaks git into source (bug 2) distorts the two buckets this eval most needs to trust.

### 8. The cut-line statistic: paired non-inferiority, not a threshold compare

The frame's eval sketch (`.agents/research/code-docs-frame.md:100-109`) states: "The cut line is the most aggressive arm that holds guard survival at the original arm's level." Read literally, "holds ... at the original arm's level" invites a naive comparison (candidate rate ≥ original rate, or within some ad hoc tolerance). Two properties of this design argue for a formal **paired non-inferiority test** instead:

- **The design is paired, not two independent samples.** The same 24 sites are run under every arm (`build_arms.py` builds one arm-specific snapshot per site's repo, and `run_probes.py` runs every site × every arm). Treating `original`'s survival rate and a candidate arm's survival rate as independent proportions throws away the pairing and loses power for no reason — a within-site paired test (McNemar-family) is the correct tool whenever the same units appear in both conditions.
- **Non-inferiority, not superiority or equality, is the actual question.** The candidate arm is expected to do *at least as well as* original on guard survival while doing *strictly better* on compression — the hypothesis is "not meaningfully worse," which is a non-inferiority framing (a pre-specified margin, one-sided confidence bound), not a two-sided equality test that would reject on a difference in either direction.

For the actual significance-testing method, this program is not the first to face small-N, paired, comment/code-related classification comparisons: Panthaplackel et al.'s AAAI 2021 paper on just-in-time comment-inconsistency detection ([arXiv 2010.01625](https://arxiv.org/abs/2010.01625)) explicitly reports "we also perform significance testing (Berg-Kirkpatrick, Burkett, and Klein 2012)," using **bootstrap resampling** (10,000 resamples of size 5,000, p < 0.05) rather than an asymptotic normal-approximation test, precisely because their significance claims needed to hold on modest, non-huge evaluation sets. With only 24 sites (up to 24×reps paired observations, most of which will be *concordant* — both arms KEPT — and therefore uninformative for a McNemar-style test, which only uses the discordant pairs), an asymptotic McNemar chi-square is likely to be badly calibrated; a **paired bootstrap over sites** (resample the 24 sites with replacement, holding each site's arm-vs-`original` pairing intact within each resample, recompute the survival-rate difference, and take the one-sided lower percentile as the non-inferiority bound) degrades gracefully at small N and needs no discordant-pair-count assumption.

**Decision:** for each candidate arm, compute the paired difference in guard-survival rate against `original` across the 24 sites (using each site's across-rep majority vote, or per-rep observations if `rep ≥ 2`), bootstrap-resample sites 10,000 times, and take the one-sided 90% lower confidence bound on the difference. The arm is non-inferior if that bound is ≥ −δ (§9 sets δ).

### 9. Margin, power, and the tie rule

**Margin.** A guard break in this eval set is not a style nit — nearly every proposed site is a security, durability, or concurrency constraint (`eval-sites.md`'s own harvest table: traversal, TOCTOU, fsync ordering, SSRF, CWE-345/CWE-22/CWE-400 citations throughout Tier A/B). A generous clinical-trial-style margin (10-15 percentage points) is not appropriate for a safety-relevant proportion at this sample size. **Decision: δ = 5 percentage points**, one-sided, at the 90% bootstrap confidence bound described in §8. This is deliberately tighter than a conventional non-inferiority default, and deliberately not zero — some residual noise (an actor occasionally makes an unrelated bad edit even in the `original` arm) is expected and should not by itself disqualify every candidate arm.

**Scope caveat, stated explicitly.** This margin, and every guard-survival rate feeding it, describes performance on a hand-picked, guard-dense 24-site sample — 12 Tier-A (obviousness-3, no test) sites, 8 Tier-B tested-guard sites, and 4 free-to-change controls (`eval-sites.md` §4) — not the fleet's actual line population, where `code-docs-topic-map.md`'s grounding pass measured guards at 48% of comment-carrying lines, not 100%. Panthaplackel et al.'s own reported gap between their curated 100-example "cleaned test sample" and their larger, less-curated "full test set" is the direct external precedent for how much a curated sample can overstate a metric: their best just-in-time model scores F1 87.1 / Acc 87.8 on the cleaned sample versus F1 77.7 / Acc 78.5 for the equivalent unfeatured model on the full test set (Table 2, [arXiv 2010.01625](https://arxiv.org/abs/2010.01625)) — roughly a 10-point F1 gap between a curated and a broader evaluation set on the same task. Report the cut line as "the most aggressive arm that is non-inferior **on this 24-site guard-dense sample**," never as a claim about the fleet's full comment population.

**Power.** A McNemar-style paired test needs enough *discordant* pairs (sites where the two arms disagree) to have power; with `rep=1` and an expected `original` survival rate near 100%, most sites will be concordant (both KEPT) by construction, leaving very few informative pairs. **Decision: require ≥3 reps per site×arm for any arm entering the cut-line decision.** This is a floor, not a target — `eval-arms-and-sites`' own commission already asks for a reps-per-cell power calculation against a 10-point survival drop; 3 reps is the minimum below which the bootstrap CI in §8 is too wide to distinguish a genuine 15-20 point drop from noise on a 24-site set, not a claim that 3 reps is sufficient on its own.

**Tie rule.** "The most aggressive arm whose guard survival matches the original arm's level" needs an explicit ordering and an explicit fallback:

1. Among all arms that pass **both** the §8 non-inferiority test and the §10 reason-recovery floor, rank by **measured** aggressiveness — the arm's actual `comment_census.py`-reported comment:code ratio across the 24 sites' files, not an a priori label (an agent-authored `rules` or `pointer` arm's real aggressiveness is not knowable in advance; `stripped` and `oneline` are mechanically the two extremes by `build_arms.py`'s own construction).
2. The cut line is the passing arm with the **lowest** measured ratio (the deepest cut).
3. If two passing arms have statistically indistinguishable ratios, prefer the one with **lower across-rep variance** in guard survival (more predictable, and predictability is itself something a ratchet check can rely on).
4. If **no** arm passes both gates, the cut line is `original` — i.e. no compression is recommended yet, and the finding to report is "no arm cleared the bar," not a forced pick of the least-bad option.

### 10. Why guard survival alone is an insufficient cut-line gate

`eval-sites.md`'s own Contradictions section already flags that H4 ("a guard survives a cut when its constraint stays as one local line... or when a test named for the constraint fails on removal") undercounts a real third state: 12 of 40 mechanism sites are obviousness-3 with no test today, meaning the comment is the *only* defense. If the cut-line statistic looks only at guard survival, it is blind to exactly the failure mode this program exists to prevent: an arm can score a high survival rate not because the actor understood a stripped comment's now-missing guard, but because it never touched the guarded region during an unprimed "simplify this function" pass (§2's `KEPT — untouched` bucket). This is not a hypothetical: [huggingface.co/papers/2607.28887](https://huggingface.co/papers/2607.28887) ("To Add Is Machine, To Delete Is Human") measures a real, reproducible **deletion-avoidance** bias across five frontier models — "Guard-and-Go," wrapping code in a conditional instead of removing it — with deletion recall at only 71.7% even on SWE-bench Verified tasks every model unanimously solved, and a deletion-sensitive retrofit that drops resolution rates from 63.2% to 41.9% purely by requiring the removal, not the addition, half of a fix. A model with this bias will, if anything, *simplify less* under the `stripped`/`oneline` arms (where there is less familiar-looking code to safely leave alone, making "don't touch this part" a more attractive default), which would make the most aggressive arms look artificially safe on guard survival alone.

**Decision:** the cut line requires **both** gates to pass, not guard survival in isolation — non-inferior guard survival (§8-9) **and** a reason-recovery floor, for example ≥70% of the 24 sites reaching "mechanism only" or above (§3) in the candidate arm. An arm that clears the survival bar only via untouched sites will fail this floor, because reason-recovery is scored from an independent turn (2a) that always asks the model to explain the line, regardless of whether turn 1 touched it.

## Normative guidance candidates

1. **Score reason-recovery from an unled Turn-2a ("why is this written this way, what would break"), never from the existing led Turn-2 alone.** Rationale: a led question that names the exact breaking edit lets a model produce a correct-looking VERDICT via surface pattern-matching on the edit description rather than genuine mechanism recall ([arXiv 2504.14119](https://arxiv.org/abs/2504.14119), 23.2% avg degradation under misleading NL framing). Verify: the harness's judge prompt must reference only the 2a transcript when computing the reason-recovery level; a code review of the judge prompt template that finds `{edit}` interpolated into the reason-recovery scoring prompt is a finding. Severity: **MUST**.
2. **Run the existing led form as Turn-2b, used only as a confabulation gate.** Rationale: catches a model that states the right reason unprompted, then abandons it the moment the specific edit is named. Verify: a probe record where 2a scores ≥"mechanism only" and 2b's `VERDICT` is `may-change` must be tagged `confabulated` and capped at "generic caution," never averaged with 2a's score. Severity: **MUST**.
3. **Guard-survival scoring uses three levels, not two: `preserved-with-rationale` / `untouched` / `broken`.** Rationale: LLMs are independently documented to under-delete ([huggingface.co/papers/2607.28887](https://huggingface.co/papers/2607.28887), 71.7% deletion recall), so a naive binary metric cannot distinguish genuine guard recognition from general reluctance to touch code. Verify: for every turn-1 rewrite, diff the guarded line range against the input; if unchanged, tag `untouched` regardless of whether the property still holds. Severity: **MUST**.
4. **The judge model must differ from the probed actor model.** Rationale: same-tier self-grading is documented to be lenient, and a same-tier judge is likelier to share the actor's blind spots. This program's own `CLAUDE.md` routing table already assigns adversarial/verification passes to `opus`. Verify: `grep -n -e "model.*sonnet" -e "model.*opus" -r .agents/research/code-docs-eval/harness/` and confirm the judge invocation names a different model string than `run_probes.py`'s `--model` default. Severity: **MUST**.
5. **Calibrate the judge on at least 30 hand-labelled transcripts (20-50 range) before trusting a full run.** Rationale: InfoQ's agentic-fitness-function guidance names this range as a practical floor for a judged pipeline ([InfoQ](https://www.infoq.com/articles/agentic-fitness-functions-evolutionary-architecture/)). Verify: a labelled-calibration-set file exists with ≥30 rows covering all 4 reason-recovery levels and all 3 guard-survival levels before any full-run score is reported. Severity: **MUST**.
6. **Gate judge trust at ICC ≥ 0.70 against the hand-labelled set for both rubrics, not the Landis & Koch 0.6 convention.** Rationale: [arXiv 2608.00794](https://arxiv.org/abs/2608.00794) finds 82% of agentic-AI-eval papers use inadequate inter-rater-reliability metrics and specifically recommends ICC ≥ 0.70 for this class of judged pipeline; the older 0.6 "substantial" convention is, by its own authors' framing and [Wikipedia's summary](https://en.wikipedia.org/wiki/Cohen%27s_kappa), "personal opinion" with no empirical basis. Verify: compute ICC (or weighted quadratic kappa as a fallback for the 4-level ordinal rubric) between judge and hand labels on the calibration set; a run below 0.70 blocks scoring the full set until the rubric prompt is revised and recalibrated. Severity: **MUST**.
7. **Run the reason-recovery judge twice per probe; escalate to a human on >1-level disagreement or an ambiguous/`not found` evidence field.** Rationale: InfoQ's own explicit escalation rule ("disagreement... large variance... missing evidence should escalate to a person"); cheap here since judging is a single text-classification call. Verify: the escalation log for a completed run lists every probe meeting this condition, with a human resolution recorded for each. Severity: **SHOULD**.

Verify: read the judge's input payload construction and confirm the string literal for `arm` (`original`/`stripped`/`oneline`/`rules`/`pointer`) is never included in the prompt sent to the judge. Severity: **MUST**.

Severity: **MUST**.

## AI-agent angle

- **Confabulation under a leading follow-up.** An agent can state a plausible-sounding mechanism unprompted, then reverse itself the moment the exact breaking edit is named and phrased as coming from "a colleague" — a social-proof-shaped prompt, not a technical one. The smallest mechanical check: run the led question as a second sub-turn and flag any verdict flip against the unled answer (§1, guidance 1-2), rather than trusting either answer in isolation.
- **Guard-and-Go on the turn-1 "simplify" task.** An agent asked to shorten/simplify code is measurably prone to wrapping risky-looking code in a conditional or simply not touching it, rather than actually deleting or restructuring it ([huggingface.co/papers/2607.28887](https://huggingface.co/papers/2607.28887), 71.7% deletion recall even on tasks every model solves). The smallest mechanical check: diff the guarded line range between input and turn-1 output; if unchanged, tag `untouched` and exclude it from any claim that the arm's compression was "resisted" (§2-3, guidance 3).
- **Pattern-matching a CWE label instead of deriving the local mechanism.** Security-flavored sites (traversal, TOCTOU, SSRF) are exactly the shapes an LLM has seen thousands of times in training data; a model can produce a syntactically correct-sounding "this prevents a TOCTOU race" without having actually traced *this* function's specific ordering. [arXiv 2504.14119](https://arxiv.org/abs/2504.14119)'s finding that models shortcut on misleading NL cues generalizes to the mirror case — a model can also shortcut on a *familiar-looking* cue that happens to be right for the wrong reason. The smallest mechanical check: the reason-recovery rubric's "mechanism + consequence" tier requires the *specific* consequence named in `eval-sites.md`'s ground truth (e.g. "two concurrent toolchain renders interleave," not merely "this could cause a race condition"), which a generic CWE-shaped answer will not satisfy (§3).
- **Hallucinating a guard on genuinely free-to-change code.** An agent primed by a codebase's overall density (`code-docs-topic-map.md`'s grounding notes an "ambient-density" effect: "Claude Code's prompt says 'match its comment density'... explains why dense ocx files beget essays") may over-generalize "this codebase is full of load-bearing comments" into "therefore this specific one must be too." The smallest mechanical check: score the 8 FTC control sites through the same rubric and treat a confident invented mechanism as a "wrong" score exactly like a missed real guard (guidance 17), not as a harmless false positive.

## Contested / evolving

- **Whether "code-first" reading generalizes to an agent's cold-start behavior is not settled by the eye-tracking evidence alone.** [Abdelsalam et al. (2026)](https://link.springer.com/article/10.1007/s10664-025-10721-2) find that human participants' *local* gaze transitions move from code toward comments (consistent with "check the code, then glance at the comment for confirmation"), but their *global* N-W-alignment analysis found **no statistically significant preference** between a "code-first" and "comment-first" overall strategy (Wilcoxon signed-rank, p > 0.19 across all four metrics tested). The paper's abstract-level framing ("participants predominantly adhered to a code-first strategy") is stronger than its own detailed global-strategy result supports. Trend: use this as motivation for why an unprimed, code-only Turn 1 is a *plausible* proxy for early agent behavior, not as proof that comments are read second — as of 2026-09-27 this remains an open, actively-studied question in the human literature, and nothing here establishes it for agents specifically.
- **Balanced-accuracy framing versus a naturally-imbalanced deployment distribution is an unresolved tension this eval inherits, not one that has a settled fix in the literature yet.** Panthaplackel et al. downsample every split to a 50/50 balanced label distribution before reporting any accuracy number (natural positive rates were 7.8-22.5% before downsampling, Table 5, [arXiv 2010.01625](https://arxiv.org/abs/2010.01625)) — a common, still-standard practice for imbalanced classification evaluation, but one that means every accuracy/F1 number in that paper (and, by the same construction choice, every guard-survival rate in this eval's guard-dense 24-site sample) describes performance on an artificially-balanced slice, not the natural mix of guarded-vs-free-to-change lines a ratchet check will actually see in production. As of 2026-09-27 there is no settled convention in this literature for reporting both numbers side by side; this dive's own §9 scope caveat is a local mitigation, not a resolved standard.
- **LLM-judge reliability practice is actively tightening, not settled.** [arXiv 2608.00794](https://arxiv.org/abs/2608.00794) (2026) argues the field's inter-rater-reliability bar (82% of surveyed papers judged inadequate) is currently too loose and should move toward ICC ≥ 0.70 with domain-stratified assessment; this is a recent, specific push rather than an established norm, and this dive adopts it deliberately over the older, weaker Landis & Koch convention rather than treating either as settled.

## Decisions this dive proposes

1. **Turn-2 wording:** split into an unled 2a (scored for reason-recovery) and the existing led form as 2b (a confabulation/consistency gate only, never separately scored). Reason: leading the question with the named edit risks a keyword-matched-correct verdict, per the CodeCrash/2609.09242 evidence on NL-cue shortcutting (§1).
2. **Rubric — guard survival:** three anchored levels (`preserved-with-rationale` / `untouched` / `broken`), judged by property against the turn-1 rewrite. Reason: a binary survived/broken metric cannot separate genuine guard recognition from documented LLM under-deletion (§2, §10).
3. **Rubric — reason recovery:** four anchored levels (mechanism+consequence / mechanism only / generic caution / wrong), with wrong explicitly covering hallucinated guards on FTC sites. Reason: symmetric scoring catches both under- and over-caution (§3).
4. **Judge:** `opus`, distinct from the `sonnet` actor; calibrated on ≥30 hand-labelled cases; gated at ICC ≥ 0.70; double-run per probe with escalation on >1-level disagreement or missing evidence; blind to arm label. Reason: same-tier self-grading is a known bias, and the 0.70 ICC bar is the better-supported, on-topic recommendation over the unsupported Landis & Koch 0.6 convention (§4-6).
5. **Store taxonomy:** reorder `agent-config` before `record` in `STORE`; extend the `git` regex to include `grep`; classify Bash targets by trailing operand, not the whole command string. Reason: all three verified live against real fleet paths and constructed commands to misclassify under the current code (§7).
6. **Cut-line statistic:** a paired, site-level bootstrap non-inferiority test (not McNemar's asymptotic approximation, not a bare threshold compare) of each candidate arm's guard-survival rate against `original`, margin δ = 5 percentage points at a one-sided 90% CI, gated additionally by a ≥70%-of-sites reason-recovery floor, with reps ≥ 3 and an explicit tie-break by measured comment:code ratio. Reason: the design is paired by construction, the sample is small (24 sites), the guarded property is safety-relevant, and guard survival alone is confounded by under-deletion (§8-10).
