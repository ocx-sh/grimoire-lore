## Summary

- The two harnesses are not the same suite at different scale — `ocx/test`'s conftest brings up docker-compose registries plus a Sigstore stack, `grimoire/test`'s spins a stdlib-socket registry; a rule written against one conftest does not transfer mechanically to the other ([existing-rules-ledger.md:96](#sources)).
- The adopted `ocx-sdk-python/.claude/rules/quality-tests.md` bans raw `os.environ` mutation and `time.sleep` **inside its own declared scope** (`tests/**`, `**/conftest.py`, `**/test_*.py` — ordinary test functions and fixtures in a library suite). Read verbatim at [ocx-sdk-python/.claude/rules/quality-tests.md:211-218](#sources), it is correct there. It is wrong only when copy-pasted onto an acceptance harness unmodified — see §2.
- **Ruling on `os.environ`**: direct mutation is correct exactly once — in a `pytest_configure`/`pytest_sessionstart`-time hook, before any fixture exists to inject with, setting process-wide state that xdist workers inherit at fork. `grimoire/test/conftest.py`'s 9 sites are all this case ([grimoire/test/conftest.py:198-222](#sources)). Everywhere else (a function/class/module-scoped fixture, an ordinary test body), `monkeypatch.setenv`/`delenv` is correct and the library rule's ban holds.
- **Ruling on `time.sleep`**: the categorical ban is wrong as stated. Three real categories exist in this codebase, only one of which is a bug: (a) the inner step of an already-bounded poll loop — fine; (b) a wait on filesystem/clock resolution (mtime granularity) — irreducible, no poll shortens it; (c) a fixed "give the process a moment" guess with no observed proxy — the actual anti-pattern, convertible to poll-with-deadline. Replace the ban with "every `time.sleep` names, in a comment, what it waits past" — which is already this harness's own convention, not a new one ([existing-rules-ledger.md:207](#sources)).
- `--strict-markers` is absent from both harnesses' `addopts` ([ocx/test/pyproject.toml:1-17](#sources), [grimoire/test/pyproject.toml:1-9](#sources)) but present in `ocx-sdk-python` ([ocx-sdk-python/pyproject.toml:93](#sources)). Watched red in §6/Sources: without it, a mistyped marker silently stays in the suite it should have been excluded from and the run still exits 0; with it, collection hard-fails with `'<marker>' not found in markers configuration option`.
- The 14 `time.sleep` sites the sibling audit counted are real; reading all of them confirms every one already carries an explanatory comment or lives inside a bounded loop — the harness already does the thing a correct rule should ask for.
- `push_blob`/`_push_blob` in `ocx/test/src/registry.py` is a genuine plain-substring-grep collision (found independently in the companion agent-legibility scout) — worth carrying into this file's ordering/hidden-state section because the same private-twin-function pattern is a place a renamed helper silently stops shadowing the one it was meant to.
- Of the session/module-scoped fixtures inventoried, **none inspected here are silently xdist-unsafe**: the registry/mirror/target/legacy fixtures resolve addresses to infrastructure started once in `pytest_sessionstart` *before* xdist workers fork ([ocx/test/conftest.py:52-60](#sources)); `sigstore_stack` uses fixed ports deliberately (one shared stack) and is protected by a host-wide `FileLock`-equivalent (`_COMPOSE_LOCK`) plus an idempotent already-running check; `auth_registry` in grimoire uses a dynamic port folded into its own container name; the one fixture with genuinely unpartitionable shared state (`test_patches.py`'s global descriptor-slot reset) is already forced into `xdist_group("patch_global_slot")` affinity by its own authors.
- `index/bot` already configures `mutmut` (`[tool.mutmut]` in `pyproject.toml`) but has never run it — no `.mutmut-cache`, no result artifact anywhere in the repo. It is adopted in name only.
- `index/bot/tests/golden/` is already a working whole-blob/golden-fixture pattern, with a documented provenance rule ("never hand-typed, produced by the real serializer and committed") that pre-empts the "blessing a snapshot nobody reads" failure mode syrupy/inline-snapshot are named for — a stronger existing answer than adopting either library from scratch.
- No repo defines `pytest_assertrepr_compare` (confirmed by a direct grep across all four; the sibling audit found the same for the two harnesses).
- A sibling audit ([version-floor.md:119,133,227-236](#sources)) already ran both library suites under free-threaded 3.14t and found them clean (`954 passed` / `762 passed`, no failures) — this file does not re-run that; §3 treats it as settled and names `pytest-run-parallel` as the tool to reach for only if that status changes.
- Collection timing (measured here, `--collect-only`, no docker/network): `ocx/test` 2328 tests in 0.42s; `grimoire/test` 1060 in 0.18s; `ocx-sdk-python` 1037 in 0.26s; `index/bot` 849 in 0.74s (the last also fires a spurious `fail_under` coverage failure under `--collect-only`, because its `addopts` bakes in `--cov`, which still evaluates on zero executed lines — a real, minor operational gotcha, not a bug in the suite).
- Coverage's own maintainer, Ned Batchelder, has said in writing since 2007 that "100% test coverage doesn't really mean much" beyond "statement coverage" ([nedbatchelder.com/blog/200710](#sources)) and, in 2019, tried mutation testing on his own project and endorsed it only as "an occasional (but expensive) way to assess your test suite" — not a regular gate ([nedbatchelder.com/blog/201903/mutmut](#sources)).

## Findings

### 1. Fixture architecture at 2000+ tests

**Scope discipline observed.** All four suites already use the standard pytest scope ladder correctly in the cases inspected — `function` (default, no `scope=` needed) for anything mutating state, `module`/`session` reserved for read-only or externally-idempotent setup. pytest evaluates scopes in a fixed hierarchy — session, package, module, class, function — and instantiates the broader scope first within a given test's fixture graph; a session-scoped fixture cannot meaningfully depend on a module-scoped one, only the reverse ([docs.pytest.org/reference/fixtures.html](#sources)).

**Conftest layering, measured.** `ocx/test` has 4 conftest files: root (`386` ln, shared registry/sigstore infra), `tests/conftest.py` (`48` ln, `unique_repo` + package-building fixtures — test-tier-specific), `recordings/conftest.py` (`335` ln, a second tier with its own state-provider machinery), `bench/conftest.py` (`140` ln, smoke-only, explicitly documents it is *not* the real benchmark driver). `grimoire/test` has 2: root (`365` ln) and `tests/conftest.py` (`64` ln). `ocx-sdk-python` has 3, one per test tier: root `conftest.py`, `tests/conftest.py`, `tests/contract/conftest.py`, `tests/acceptance/conftest.py` — a layering that maps directly onto its own test-tier directory split (unit / contract / acceptance), which is the textbook use of pytest's directory-scoped conftest discovery: "each directory can have its own `conftest.py` with its own fixtures, adding on to the ones provided by parent directories," and a test can search upward for a fixture but never down into a sibling directory ([docs.pytest.org/en/6.2.x/explanation/fixtures.html](#sources)). `index/bot` mirrors this at smaller scale: `tests/conftest.py` (25 ln) plus `tests/integration/conftest.py` (46 ln) for the one tier that needs heavier setup.

**The right layering rule, stated generally**: put a fixture at the shallowest conftest that can see every consumer, no shallower. A fixture used by exactly one test tier belongs in that tier's own `conftest.py` (`ocx-sdk-python`'s three-tier split is the clean example); a fixture every tier needs (a binary path, a registry address) belongs at the root. `ocx/test`'s 386-line root file stays a plain fixture/hook file, not a "god object," because it is deliberately restricted to two things: session-hook orchestration (`pytest_sessionstart`) and the handful of session-scoped infrastructure fixtures every test tier shares — tier-specific fixtures (`unique_repo`, package builders) already live one level down in `tests/conftest.py`.

**Factory fixtures vs. fixtures returning data.** pytest's own guidance: "Instead of returning data directly, the fixture instead returns a function which generates the data. This function can then be called multiple times in the test" ([docs.pytest.org/how-to/fixtures.html](#sources)). `unique_repo` (`ocx/test/tests/conftest.py:22`) is the data-returning shape (one value, one use per test) and is correct as such — a factory would be overkill for a value computed once per test id. `tmp_path_factory.mktemp(...)`, used throughout for session-scoped temp directories, is the standard library example of the factory shape done right — called once per distinct sub-resource, never memoized across tests.

**Yield-fixture teardown order** is strictly LIFO relative to setup: "pytest will go back down the list of fixtures... in the reverse order, taking each one that yielded, and running the code inside it that was after the `yield` statement" ([docs.pytest.org/how-to/fixtures.html](#sources)). This matters concretely for `sigstore_stack` → `identity_token` (`ocx/test/tests/fixtures/sigstore_stack.py:95,113`): `identity_token` depends on `sigstore_stack`, so its teardown (implicit — it returns a bare path, no yield) runs before `sigstore_stack`'s, which is correct since the token file only makes sense while the stack it names is still up.

### 2. Isolation and the two live contradictions

**(a) `os.environ` mutation — resolved, not surveyed.** The three legitimate tools, in order of preference: `monkeypatch.setenv`/`delenv` (auto-reverting, function/class-scoped, the default answer); a context manager wrapping a `with monkeypatch.context():` block for a narrower blast radius inside one test; direct `os.environ[...] =` mutation. Direct mutation is legitimate in exactly one situation, and this codebase's every real instance is that situation: **inside a collection-time or session-start pytest hook (`pytest_configure`, `pytest_sessionstart`), which runs before any fixture — including `monkeypatch` — exists to be requested.** `grimoire/test/conftest.py`'s 9 `os.environ[...] =` sites are all inside `_resolve_registry_host()`, called from `pytest_configure`-adjacent code, precisely because `src.registry`'s module-level `REGISTRY_HOST = os.environ.get(...)` must see the correct value the instant that module is first imported by a test module during collection — a fixture-scoped `monkeypatch.setenv` runs too late for that ([grimoire/test/conftest.py:143-156](#sources), docstring is explicit about the ordering constraint). The variable also has to survive into forked xdist worker processes, which inherit the parent's environment at fork time but never receive a `monkeypatch` teardown from the controller — another reason a fixture-scoped tool cannot substitute here. `ocx-sdk-python`'s own quality-tests.md ban is correct for its stated scope (ordinary unit tests with full dependency-injection control) and was never written to cover this hook-time case; if the SDK ever needed process-wide env bootstrap before its own fixtures exist, the identical exception would apply to it too. The fix is not "the rule is wrong," it is "the rule's scope note needs one carve-out clause naming pytest hook functions," which is a one-line addition, not a reversal.

**(b) `time.sleep` — resolved, not surveyed.** Reading all 14 sites (12 in `ocx/test`, 2 in `grimoire/test`) sorts cleanly into three categories:

| Category | Example | Verdict |
|---|---|---|
| Already a bounded poll (sleep is the inner step of a retry loop) | `ocx/test/src/helpers.py:85-90` — `for _ in range(30): if reachable(): return; time.sleep(0.5)`; `ocx/test/src/static_index.py:322-329` — `time.monotonic()`-deadline loop | Not a bug. Prefer the `time.monotonic()` deadline form over a fixed iteration count where the *timeout value itself* matters to the test, but a fixed-count retry loop is not the anti-pattern the rule is trying to catch. |
| Filesystem/clock-resolution wait — the condition being waited for is bounded by wall-clock granularity itself, not by an external process | `ocx/test/tests/test_project_pull.py:1467` — `# Sleep to ensure a distinct mtime on coarse (1-second) filesystems.`; `ocx/test/tests/test_update_check_throttle.py:244` — same reason | **Irreducible.** A poll loop checking `stat().st_mtime` in a spin would not converge any faster — the mtime literally cannot advance until real time has advanced by the filesystem's granularity. Converting this to a poll changes nothing but the code shape. |
| "Give the process a moment" — waiting for an external process to reach an internal state with no directly observed proxy | `ocx/test/tests/test_project_crash_recovery.py:142` — `# Give the process time to write ocx.lock and reach the pause.`; `ocx/test/tests/test_project_concurrency.py:276` — `# Give flock(1) a moment to acquire.` | **The real anti-pattern**, but only sometimes fixable. `test_project_crash_recovery.py` could poll for `ocx.lock`'s existence with a deadline instead of guessing 2.0s. `test_project_concurrency.py`'s flock-acquisition wait is harder — polling for another process's advisory-lock state needs `fcntl`/`/proc/locks` inspection, not a trivial swap; a generous, commented sleep is a defensible compromise there specifically. |

One case looks like category (c) but is actually convertible with a net improvement: `ocx/test/tests/test_announce.py:1173`'s `time.sleep(7)  # past the immediate probe + the first 2s backoff sleep` waits out a *known* backoff schedule under test. It could poll `fake_forge.request_count("GET", ...) >= 2` with a deadline instead — faster on a fast machine, more robust on a loaded CI runner, same assertion. Flagged as a candidate improvement, not a current bug.

**Verdict**: the blanket "`time.sleep` in a test is a bug" line in `quality-tests.md` is wrong as a universal statement — it is right for library unit tests (category (b)/(c) essentially never arise there, because a well-written unit test never touches a real filesystem's mtime or waits on a real subprocess) and wrong as written for an acceptance harness, where both irreducible and legitimate-but-improvable sleeps exist. Replace with: *"A `time.sleep` with no comment naming what it waits past is a bug. A `time.sleep` waiting on an observable proxy (file existence, process exit, log line, port open) must poll that proxy with a deadline instead. A `time.sleep` waiting on wall-clock/filesystem resolution, or on an external process's unobservable internal state, is acceptable with a comment naming the wait — sleep is the correct tool there, not a fallback."*

### 3. Parallelism

**The idiom for a session fixture that must run exactly once**, verbatim from pytest-xdist's own docs:

```python
import json
import pytest
from filelock import FileLock


@pytest.fixture(scope="session")
def session_data(tmp_path_factory, worker_id):
    if worker_id == "master":
        return produce_expensive_data()

    root_tmp_dir = tmp_path_factory.getbasetemp().parent
    fn = root_tmp_dir / "data.json"
    with FileLock(str(fn) + ".lock"):
        if fn.is_file():
            data = json.loads(fn.read_text())
        else:
            data = produce_expensive_data()
            fn.write_text(json.dumps(data))
    return data
```
([pytest-xdist.readthedocs.io/en/stable/how-to.html](#sources)) — `worker_id` is `"master"` when xdist is not active (`-n0`/no `-n` flag at all); helper functions `xdist.is_xdist_worker()`, `xdist.is_xdist_controller()`, `xdist.get_xdist_worker_id()` exist since xdist 2.0 as the programmatic alternative to reading `PYTEST_XDIST_WORKER` directly ([pytest-xdist.readthedocs.io/en/latest/how-to.html](#sources)).

**This codebase already implements the equivalent pattern by hand, at a coarser grain**: `ocx/test/conftest.py`'s `pytest_sessionstart` brings up the shared registries once, *before* xdist workers fork, so no worker-side race or `FileLock` is even needed — every worker inherits an already-running, already-resolved address. `grimoire/test` does the same via `pytest_configure` plus `os.environ` inheritance at fork (§2a). `sigstore_stack` additionally carries a genuine cross-*process-tree* lock (`_COMPOSE_LOCK`, a host-wide file lock, not xdist-specific — its own docstring names two worktrees running concurrently as the case it exists for, which also covers concurrent xdist workers) plus an idempotent "already running" check before calling `docker compose up`. This is the `tmp_path_factory.getbasetemp().parent`-file-lock idiom's spirit, implemented against `docker compose`'s own idempotency instead of a hand-rolled JSON cache file — a reasonable variant given the resource being shared is a docker-compose stack, not computed data.

**Distribution modes** (`--dist`): `load` (default) — sends pending tests to any available worker, no ordering guarantee; `loadscope` — groups by module (functions) or class (methods), keeping each group in one worker, for expensive module/class fixtures; `loadfile` — groups by containing file; `loadgroup` — groups by the `@pytest.mark.xdist_group(name=...)` marker, merging multiple group names lexically when a test carries more than one; `worksteal` — starts even, then reassigns from a worker whose queue drops below two tests, handling variable test duration better than `load`; `no` — sequential, no distribution ([pytest-xdist.readthedocs.io/en/stable/distribution.html](#sources)). Neither harness's `pyproject.toml`/taskfile pins a `--dist` mode in `addopts`, so both currently take the default `load`.

**Fixture-inventory audit (the "11 + 3" from the sibling count).** Read the bodies of every session-scoped fixture in `ocx/test`'s root conftest (5), `sigstore_stack.py` (2), `bench/conftest.py` (2, pure), `test_cosign_interop.py` (1), plus grimoire's 2 session fixtures and the one autouse module fixture in `test_patches.py`, and the one module fixture in `grimoire/test/tests/test_login.py`:

| Fixture | File:line | Shared resource | Why it is / is not xdist-safe |
|---|---|---|---|
| `registry`, `mirror_registry`, `target_registry`, `legacy_registry`, `ocx_binary` | `ocx/test/conftest.py:119-230` | fixed-port docker registries, resolved not started | **Safe.** `pytest_sessionstart` starts the infrastructure once, before workers fork (`conftest.py:52`); these fixtures only resolve an address and optionally skip. Test-level data isolation comes from `unique_repo` (`tests/conftest.py:22`, `uuid4().hex[:8]`), not from the fixture. |
| `sigstore_stack`, `identity_token` | `tests/fixtures/sigstore_stack.py:95,113` | fixed ports (`5555`/`3000`/`6962`), one shared stack | **Safe by design.** Fixed ports are intentional — one Sigstore stack for the whole run, not one per worker. `_COMPOSE_LOCK` (host-wide file lock) plus `_stack_is_already_running()`'s idempotent check (`src/helpers.py:98-123`) serialize bring-up across concurrent workers/worktrees. |
| `bench_scenarios`, `bench_compare_fn` | `bench/conftest.py:30,38` | none — pure, read-only module data | **Safe**, trivially: no I/O, no mutation, scope is irrelevant. |
| `cosign_image` | `test_cosign_interop.py:31` | `docker pull` of a pinned image | **Safe.** `docker pull` of the same reference from concurrent processes is an idempotent operation Docker itself serializes internally; worst case is duplicated download effort, not corruption. |
| `_empty_global_descriptor_slot_afterwards` (autouse, module) | `test_patches.py:55` | a registry-wide "global descriptor slot" with **no** per-test/per-worker scoping — explicitly documented as outliving the session | **Genuinely unsafe if run concurrently with itself — and the suite already knows it.** The module carries `pytestmark = pytest.mark.xdist_group("patch_global_slot")` (`test_patches.py:3`), forcing every test in it into one worker. | `grim_binary`, `registry` (grimoire) | `grimoire/test/conftest.py:299,312` | binary path; registry address | **Safe**, same reasoning as ocx's: resolved via `pytest_load_initial_conftests`/`pytest_configure` before worker fork, documented explicitly as `xdist-safe` in the fixture's own docstring. |
| `auth_registry` | `grimoire/test/tests/test_login.py:149` | a dedicated `registry:2` container | **Safe.** Dynamic port (`_free_port()`) folded directly into the container name (`grim-login-verify-{port}`) — the standard collision-avoidance idiom, done correctly. |

**Verdict on the "11 + 3" count**: the raw count of session/module-scoped fixtures is not itself informative. Every one inspected here is either (i) infrastructure started once before xdist forks, (ii) protected by dynamic-port-derived naming, (iii) a pure data fixture, or (iv) the one case of genuinely unpartitionable shared state — already correctly handled with `xdist_group`. **Zero silently-unsafe fixtures found in this sample.** The right normative rule is not "avoid session/module scope" but "name which of these four safety arguments applies, in the fixture's docstring" — several already do this explicitly (`sigstore_stack`, `registry` in both repos); a few (`cosign_image`, `bench_*`) don't bother to state it because the safety is self-evident from the body.

**Free-threading.** A sibling audit already installed `3.14t` and ran both library suites against it: `ocx-sdk-python` — `954 passed` (of 1037 collected — the delta is skips, e.g. platform-gated `# pragma: no cover` paths, not failures), `index/bot` — `762 passed` (of 849 collected), identical to their 3.12/3.13/3.14 results, with the explicit conclusion "no free-threading rule is needed yet" ([version-floor.md:119,133,227-236](#sources)). This file treats that as settled and does not re-run it (no network/build tooling available in this pass). The tool to reach for *if* that status changes is `pytest-run-parallel` (formerly discussed as a Quansight-Labs project): it re-runs an existing suite's tests concurrently across threads within one process to surface shared-mutable-state bugs, which `pytest-xdist`'s multi-*process* model cannot do (xdist parallelizes across OS processes, each with its own GIL-or-not interpreter state — it says nothing about whether two threads inside one process corrupt shared state). The official free-threading guide is explicit about the limit: these plugins "are useful for discovering issues related to use of global state, but cannot discover issues from multithreaded use of data structures defined by your library" — deliberately constructed concurrent tests are still needed for real multithreaded workflows ([py-free-threading.github.io/testing/](#sources)). `ocx_sdk/_envmodel.py`'s `threading.Lock` is the one place `version-floor.md` itself flags as worth re-checking once free-threaded traffic is real, not synthetic.

### 4. Ordering and hidden state

**Mechanical way to find order dependence in an existing suite**, without hand-auditing 2000+ tests: run the suite twice under `pytest-randomly` with two different explicit seeds and diff the pass/fail sets.

```
pytest --randomly-seed=1 -q > /tmp/run-seed1.txt
pytest --randomly-seed=2 -q > /tmp/run-seed2.txt
diff /tmp/run-seed1.txt /tmp/run-seed2.txt
```

`pytest-randomly` shuffles at module level, then class level, then function level ([pytest-randomly, github.com/pytest-dev/pytest-randomly](#sources)), and prints the base seed at the start of every run so a failure is reproducible with `--randomly-seed=<value>` (or `--randomly-seed=last`). It is explicitly a **detector**, not a fix — its own docs point to the separate `pytest-order` plugin for pinning an intentional order, and its purpose is finding hidden inter-test dependencies through randomization, not resolving them. Neither harness currently declares `pytest-randomly` in its dev dependency group, so this check does not run today.

**Module-level mutable state / class-attribute mutation / surviving caches** — the specific things to grep for, each with an explicit path and stated pass/fail meaning:

- `lru_cache`/module-level dict or list literals used as caches: `rg -n --glob '*.py' '@(functools\.)?lru_cache' <path>` — every hit is a candidate whose cache lifetime spans the whole test session (or worker process, under xdist) unless something clears it; not automatically a finding, but each one needs a `.cache_clear()` in a fixture teardown or an explicit note why it's safe to leave warm.
- Class-level (not instance-level) mutable attributes: `rg -n --glob '*.py' -P '^class \w+.*:\n(\s+#.*\n)*\s+\w+\s*=\s*(\[|\{)' <path>` — a class body assigning a list/dict literal directly (not inside `__init__`) is shared by every instance; a match is the finding.
- `importlib` caches surviving across tests that reimport a module with different monkeypatched state: `rg -n 'importlib\.reload\(' <path>` — any hit needs a paired `sys.modules.pop(...)` or fixture-scoped isolation; absence of any hit is a pass by construction (nothing reloads).

None of the four suites showed any hits for the first two greps run against `ocx/test/src`, `grimoire/test/src` and both SDKs' `src/` trees during this pass (spot-checked, not exhaustively re-run for every path — the commands above are the reusable form).

**The `push_blob`/`_push_blob` naming-collision hazard** (found in the companion agent-legibility scout, restated here because it is squarely an ordering/hidden-state risk too): `ocx/test/src/registry.py` defines both a public `push_blob(...)` and a private `_push_blob(...)` with different signatures. A plain substring grep for `push_blob(` matches both — meaning a reviewer or an agent auditing "every call site of the public function" over-collects, silently including the unrelated private helper's call sites. `\bpush_blob\(` (word-boundary) is required for a clean result. This is a real, present defect in the harness, not a hypothetical.

### 5. Markers and selection

**Why `--strict-markers`'s absence is a silent failure, demonstrated.** Without it, an unregistered/mistyped marker only emits `PytestUnknownMarkWarning`; the run still exits 0. Planted in a scratch project (`/tmp/.../pytest-demo/`, watched red — full transcript in Sources):

```
$ pytest -m "not requires_docker" -q          # marker on test_two is "requires_dokcer", a typo
.                                                                        [100%]
test_demo.py:9
  PytestUnknownMarkWarning: Unknown pytest.mark.requires_dokcer - is this a typo?
1 passed, 1 deselected, 1 warning in 0.01s
exit code: 0
```

`test_two` (meant to be excluded from the fast subset) silently ran in the wrong bucket — the marker-based routing broke, and CI is green. Adding `--strict-markers` to the same invocation (no test-file change):

```
$ pytest -m "not requires_docker" -q --strict-markers
ERROR test_demo.py - Failed: 'requires_dokcer' not found in `markers` configuration option
1 error in 0.07s
exit code: 2
```

**Registration syntax** (TOML): `markers = ["slow: marks tests as slow (deselect with '-m \"not slow\"')", "serial"]` plus `addopts = ["--strict-markers"]` in the same `[tool.pytest.ini_options]` table ([docs.pytest.org/how-to/mark.html](#sources)) — this is exactly `ocx-sdk-python/pyproject.toml:93`'s shape, and exactly what `ocx/test`'s `markers = [...]` (one entry, `requires_tty`) is missing the `addopts` half of.

**A marker taxonomy for tiers**, proposed for the harnesses (neither currently has more than one marker declared):

```toml
markers = [
  "requires_tty: needs a real TTY on stderr (skipped under output capture)",
  "requires_docker: needs a live docker daemon and the compose stack",
  "requires_network: needs outbound network access",
  "slow: takes materially longer than the median test; excluded from the fast loop",
]
```

CI runs the full set; a developer's fast loop runs `pytest -m "not requires_docker and not slow"`. The check that every marker *used* in the tree is *declared* in config: `rg -oh --glob '*.py' -P '@pytest\.mark\.(?!parametrize|skip|skipif|xfail|usefixtures|filterwarnings)\w+' <path> | sort -u` against the declared `markers = [...]` list in `pyproject.toml` — any name in the first set absent from the second is the finding; this is exactly what `--strict-markers` already automates at collection time, so the grep is a pre-commit-hook-speed substitute, not a replacement.

### 6. Assertion style and output stability

**Substring vs. whole-blob, decided.** Measured by a sibling audit and independently spot-checked here: substring checks (`in result.stdout` / `in result.stderr`) dominate — `ocx/test` 369 sites, `grimoire/test` 201; whole-blob equality is rare — 10 and 9 sites respectively ([harness-shape.md:149](#sources)). **This is the right default for CLI-output assertions in an acceptance harness**, and the reasoning is not merely "resilient to incidental drift" — the harness tests a CLI binary it does not control the exact byte-for-byte output format of across Rust toolchain/dependency bumps (color codes, trailing whitespace, a reordered-but-equivalent JSON key). A substring assertion states the actual claim under test ("this diagnostic mentions the missing field") without also asserting a formatting decision nobody meant to pin. Whole-blob equality is reserved, correctly, for the 10-19 sites where the full output genuinely *is* the contract (frozen JSON/manifest bytes, a schema-generation golden file).

**Where this reasoning does *not* transfer**: `index/bot/tests/golden/` — a library-shape suite testing a serializer whose exact byte output (field order, escaping, indentation) *is* the product. There, whole-blob comparison is not a lesser choice made resilient by narrowing to substrings; it is the correct claim, stated fully: `assert serialize_package_root(parsed) == raw` against a committed fixture ([index/bot/tests/core/test_serializer_golden.py:44-46](#sources)). The two shapes need opposite defaults, and a single project-wide "prefer substring" rule would be wrong for the SDK/bot shape.

**`syrupy`/`inline-snapshot` vs. what `index/bot` already does.** `syrupy` stores expected values in separate `__snapshots__` files and *fails the suite outright if a snapshot file is missing* — not merely on a diff — specifically to stop a snapshot library from being used to silently rubber-stamp new output ([syrupy-project.github.io/syrupy](#sources)); `inline-snapshot` keeps the expected value inline in the test body instead of a separate file, trading "jump between files" for "the assertion and its expectation are the same diff hunk" ([pydantic.dev/articles/inline-snapshot](#sources)). Both still share the review-burden problem the brief names: a `--snapshot-update` run regenerates *every* snapshot in one pass, and a reviewer sees a fixture-file diff with no inherent signal about which changes are intended. `index/bot`'s golden pattern sidesteps this by splitting into two directories with two different, explicitly documented provenance claims: `serializer/root/*.json` is "never hand-typed" — it must be produced by calling the real serializer, so any diff to it in a PR is by construction a behavior change worth reviewing, not a maintainer blessing a black box; `dispatch/sha256/<hex>.json` carries its own filename-is-a-hash invariant, independently checkable (`sha256(file bytes) == <hex>`), so a corrupted or hand-edited fixture is self-evidently wrong regardless of what the test asserts ([index/bot/tests/core/test_serializer_golden.py:1-21](#sources)). **Verdict: for a project already willing to hand-write this provenance discipline, it beats adopting `syrupy`/`inline-snapshot` from scratch** — those libraries solve the ergonomics of snapshot storage, not the review-burden problem the brief actually raises; this codebase already solved the harder problem by hand.

**`pytest_assertrepr_compare`.** Confirmed zero uses in any of the four suites (`rg -n 'pytest_assertrepr_compare' <path>` on each, empty in all four). The hook's signature is `pytest_assertrepr_compare(config, op, left, right)`, returning `None` for no custom explanation or a list of strings joined by newlines, the first line acting as a summary ([docs.pytest.org/how-to/assert.html](#sources)). Candidate use: the SDK's `TestResult`/`CommandResult` types would get a materially better failure diff than the default `attrs`/dataclass repr diff for an `==` comparison mismatch on a multi-field result object — currently unclaimed ground in all four suites. One real limitation worth citing: pytest only rewrites assertions in modules it collects directly as tests — assertion helpers living in a non-test support module need `pytest.register_assert_rewrite("modulename")` called before that module is first imported (typically in the root `conftest.py`) to get the same introspective failure messages; none of the four suites currently call it, and `ocx/test`'s shared `assertions.py`/`helpers.py` support modules are candidates if their own internal asserts ever need rich diffs.

### 7. Coverage that means something

**Ned Batchelder, coverage.py's maintainer, on 100%:** "100% test coverage doesn't really mean much. There are dozens of ways your code or your tests could still [be] broken" — because "the measurement coverage.py provides is more accurately called statement coverage… it tells you which statements were executed," not whether the range of *data* that flows through those statements was exercised, or whether the test that executed a line actually asserted anything about its result ([nedbatchelder.com/blog/200710/flaws_in_coverage_measurement.html](#sources)). His own summary line: "Coverage tools are only helpful if they're used to enhance thought, not replace it." Separately, on setting coverage *goals*, he built tooling (`goals.py`) specifically because a single project-wide percentage is too coarse — teams legitimately want "100% coverage in tests and 85% in product code, or whatever," i.e., goals should be per-directory/per-purpose, not one number ([nedbatchelder.com/blog/202111/coverage_goals.html](#sources)).

**`# pragma: no cover` as an escape hatch, and how the codebases keep it honest.** Every instance found across `ocx-sdk-python` (11 sites) and `index/bot` (1 site) — the harness has exactly one, on a `TYPE_CHECKING` block — carries an inline reason after the pragma (`# pragma: no cover - macOS-only sysctl probe`, `# pragma: no cover - Windows: no new process group...`), not a bare pragma. That is the discipline that keeps the escape hatch from silently swallowing real gaps: a bare `# pragma: no cover` on a line that could plausibly execute is a review smell; one with a platform/typing reason attached that a reviewer can independently verify ("is this actually unreachable on this platform?") is legitimate. `index/bot`'s coverage config additionally excludes `if TYPE_CHECKING:`, `if __name__ == "__main__":`, and bare `...` structurally via `exclude_also` rather than a pragma at every site — the right default for those three specific, unambiguous cases.

**Why line coverage says nothing about whether an error path was *asserted*.** A test that calls a function expected to raise, wrapped in a bare `try/except: pass`, executes every line of the raising branch — 100% statement coverage on that branch — while asserting nothing about *which* exception, its message, or that it was the expected failure mode rather than an unrelated `TypeError` masking a real bug. `quality-tests.md`'s own §10 forbids exactly the milder version of this ("bare `pytest.raises(Exc)` without `match=`") for the same underlying reason.

**Mutation testing: the actual answer, and its cost.** `mutmut` (and `cosmic-ray`) systematically rewrite one operator/statement at a time (`a + b` → `a - b`, `x > 0` → `x >= 0`, `x += 1` → `x = 1`, etc.), rerun the suite against each mutant, and report which mutants *survived* — i.e., which single-line behavior changes no test caught, regardless of whether the line was "covered." Batchelder ran it on his own project (`templite`, a small codebase) and found real value — 4 of 8 surviving mutants pointed at genuine test gaps — but flagged it as expensive (43 minutes for 513 mutants on a 10-second suite) and prone enough to false positives (the other 4 survivors were not real bugs, with no clean way to silence them without also suppressing real catches) that his own conclusion was: "as an occasional (but expensive) way to assess your test suite, mutmut works well," not "I don't know how I would use this regularly" as a standing gate ([nedbatchelder.com/blog/201903/mutmut](#sources)).

**Affordability here**: `index/bot`'s own test suite is 849 tests collecting in 0.74s — fast enough that even a multi-hour mutation run against `src/indexbot/` (a much smaller surface than the full test tree) is plausible as a periodic, not per-PR, job. It is already configured (`[tool.mutmut]`, `paths_to_mutate = "src/indexbot/"`, `runner = "python -m pytest -x -q"`) but has never been run — no cache, no result artifact anywhere in the repo. **Recommended gate for the two library suites**: `mutmut` as a scheduled (weekly, or pre-release) job, not a per-commit gate — matching Batchelder's own "occasional" framing — reporting a mutation-score *floor* that only ratchets up, the same shape as the existing `fail_under` line/branch gate. **For the harness, which measures nothing today**: neither `ocx/test` nor `grimoire/test` runs coverage at all (`test/pyproject.toml` has no `[tool.coverage]` table in either repo, confirmed by direct read); a harness whose job is to catch regressions in a compiled Rust binary rather than to prove Python-side statement coverage is a materially different animal — the right gate there is not statement coverage on `src/`, but a durations-and-skip audit (§8) plus the ordering check in §4, since the harness's actual risk is a test that silently stops exercising the behavior it claims to (a skip nobody notices), not an unexecuted Python line.

**Fixture reuse vs. isolation, the central trade-off, stated concretely for this fleet**: every session-scoped infrastructure fixture *reused* across a worker's whole test run is exactly the isolation this suite gives up to buy speed — and it recovers correctness for that trade by pushing isolation down to the data layer (`unique_repo`'s per-test UUID prefix) rather than the infrastructure layer. That is the correct trade for this suite shape: infrastructure bring-up (docker compose, a Sigstore stack) is the expensive, safely-shareable part; repo/tag names are the cheap, must-not-collide part.

| Sleeps instead of polling an observable proxy (rule 3, category (c)) | `rg -n -B1 'time\.sleep\(' <path>` per rule 3's verification — a hit with no adjacent comment naming what it waits past. |
| A test passes because a marker typo silently excluded it from the tier the developer meant to run (§5) | Rule 1's verification, run once: `--strict-markers` added to a local invocation turns this into a hard collection error instead of a silent pass. |
| Adds `# pragma: no cover` to reach a `fail_under` gate, on a line that is actually reachable | Rule 12's verification (bare pragma with no reason) catches the laziest form; the harder form (a *reasoned* pragma whose reason is false) needs a human to check the stated reason against the actual platform/typing claim — no grep proves a reason is true, only that one was written. |
