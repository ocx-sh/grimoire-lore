## Summary

- **Retracted, on evidence:** "610+ call sites with no `timeout=`" is not a defect unique to this fleet. A sibling survey read `pip`'s functional-test source, pytest's own `Pytester.run()`, and uv's `TestContext`, and found **zero of three ship a per-call subprocess timeout by default** — pytest's is opt-in and `None` by default. A per-call timeout is not the industry norm; adding one would put this fleet *ahead* of the reference implementations, not catch it up. See [`scout-cli-acceptance.md`](/home/mherwig/dev/grimoire-lore/.agents/research/python-topic-map/scout-cli-acceptance.md).
- **Verdict: adopt `pytest-timeout` as a session-level config line, plus a bounded CI `timeout-minutes`, plus restoring `-v` and forcing unbuffered stdout in CI — not a per-call runner `timeout=`.** The reason isn't "timeouts are good in the abstract" — it's that the *actual* backstop this fleet relies on today (the CI job's own wall-clock limit) is measurably worse than in the surveyed peers, for reasons specific to this fleet's own CI config, detailed in §1.
- What a hung test produces in this fleet's CI **today**, measured directly from the workflow files: no `timeout-minutes` is set on either `acceptance-tests` job, so GitHub's 360-minute (6-hour) default/hard-max applies; the `task test -- --junit-xml=...` invocation silently drops the `-v` flag (Task's `{{.CLI_ARGS | default "-v"}}` templating only applies the default when no args are passed, and CI always passes `--junit-xml=...`), so pytest runs in default dot-per-test mode with **no test name printed before it runs**; and the `Upload Test Results` step is gated `if: ${{ !cancelled() }}`, so a job killed by the 360-minute timeout uploads **no JUnit artifact at all**. The practical result: an operator gets a red job, up to 6 hours later, with no reliable attribution of which test hung.
- `subprocess.run(timeout=)` kills only the **direct child**, never its descendants — reproduced live: a grandchild process survived a timed-out parent and had to be manually SIGKILLed. This fact is unchanged by the premise correction above — it just now answers a narrower question (does a timeout orphan children, if one exists) rather than "should a timeout exist."
- Both harness runners (`ocx/test/src/runner.py`, `grimoire/test/src/runner.py`) call bare `subprocess.run(cmd, capture_output=True, text=True, env=..., input=stdin)` with no `timeout=` parameter in the method signature — this is now read as "matches pip/pytest/uv's own default," not as an obvious bug.
- AST count of `.run(` call sites with no `timeout=`, kept as a measurement, not a verdict: ocx/test has 313 raw `subprocess.run(` calls (301 missing timeout) plus ~300 calls that route through `ocx.run(...)`; grimoire/test has only 31 raw `subprocess.run(` calls but **804** calls to `runner.run(...)`.
- One codebase already has the correct process-group-kill pattern for the rare case a timeout *is* wanted: `ocx/test/tests/test_lazy_loading.py:213` uses `start_new_session=True` + `communicate(timeout=)` + `os.killpg(os.getpgid(pid), SIGKILL)` on `TimeoutExpired`. Nobody else surveyed — not even pytest's own `Pytester.run()`, which calls bare `popen.kill()` on the direct child only — does this. Pioneering it here would be a genuine advance, not table stakes.
- Found one genuine, unmitigated pipe-deadlock pattern: `grimoire/test/tests/test_fix_locking.py:102` spawns N concurrent `Popen(..., stdout=PIPE, stderr=PIPE)` and reaps them with bare `p.wait()` — nothing ever drains the pipes. Measured the trigger threshold live: Linux's default pipe capacity is 65536 bytes (`fcntl.F_GETPIPE_SZ`); once either stream crosses that, the child blocks in `write()` and `.wait()` never returns.
- Five more direct `Popen(...PIPE...)` sites were read individually; two are safe (`communicate()`), three call `.wait()`/`.poll()` without draining and are structurally fragile even though current output volume is low.
- Neither runner passes `encoding=`/`errors=` — `text=True` alone falls back to `locale.getpreferredencoding(False)`, which is UTF-8 on a normal Linux/macOS runner but can silently become ASCII on a misconfigured `LANG=C`/`LC_ALL=POSIX` CI box, turning any non-ASCII CLI output into an intermittent, environment-dependent `UnicodeDecodeError`.
- `Windows` is not a hypothetical concern for this fleet: both repos run pytest under `windows-latest` in CI (`ocx/.github/workflows/build-windows-shims.yml:262`, `ocx/.github/workflows/shell-activation-deep.yml:85`) — `os.killpg`/`start_new_session` are POSIX-only and need a Windows branch.
- Zero `shell=True` in either repo — argv-list discipline is already followed everywhere; this is not a gap to fix, just a discipline to keep.
- PEP 787 ("safer subprocess usage using t-strings") is **Deferred**, targeting 3.15 at the earliest, as of August 2026. PEP 750 t-strings (landed in 3.14) are a *building block*, not a shipped subprocess-safety feature — the "does 3.14 change shell-command construction" framing is overstated for anyone on 3.14 today.
- `pexpect.expect()` reads one character at a time, so `$` matches after *every* character, not end-of-line — you must match the literal `\r\n` a PTY actually emits, not `\n`. Confirmed via pexpect's own docs, not blog paraphrase.
- pexpect's `.+`/`.*`-ending patterns are **non-greedy** against a live stream (there's nothing to look ahead into), the opposite of `re` module behavior — a pattern like `expect('.+')` matches one character.
- `TIMEOUT` and `EOF` are meant to be explicit entries in the `expect([...])` pattern list (matched by index), not exceptions to swallow generically — treating them as generic exceptions throws away exactly the diagnostic context (`before`/`after`/`buffer`) needed to say what the child actually sent.
- `capture_output=True` combined with explicit `stdout=`/`stderr=` is not a style nit — it raises `ValueError` immediately, confirmed live. No lint rule is needed for that one; the interpreter already refuses it.
- `check=False` appears 57 times in each repo — a legitimate opt-out when the test wants to assert on a specific non-zero returncode itself, but nothing statically confirms the caller actually reads `.returncode` afterward.
- The runner's stderr-attached `AssertionError` on failure (`f"ocx {' '.join(args)} failed (rc={result.returncode})\nstderr: {result.stderr.strip()}"`) is a **good** default for a black-box harness — it is evaluated explicitly below rather than assumed.

## Findings

### 1. Timeout design: the corpus, the CI backstop's real cost, and the verdict

**The premise this section originally argued from was wrong, and the correction matters more than the mechanics below.** A sibling survey read `pip`'s `tests/lib/__init__.py` → `scripttest`'s `TestFileEnvironment.run()` (no `timeout=` in the call chain, confirmed from source), pytest's own `Pytester.run()`/`popen()` helper (`timeout: float | None = None`, opt-in, off by default), and uv's `TestContext` (`with_http_timeout()` configures the *binary's* HTTP client, not the harness's wall-clock). Zero of three ship a default per-call subprocess timeout. So "610+46+1141 call sites with no `timeout=`" is not, by itself, evidence of a defect — it is this fleet doing exactly what pip, pytest, and uv do. Retracting the original framing plainly, per instructions: **the finding was overstated as "an obvious gap"; it is at most "an industry-wide open question this fleet could get ahead of."**

**What is not retracted, because it's a fact about this fleet's own CI, not an opinion about timeout design in general:** the thing every one of those projects relies on *instead* of a per-call timeout — the CI job's own wall-clock limit — costs measurably more here than the abstract "eventually the job dies" framing suggests. Read directly from `ocx/.github/workflows/verify-deep.yml` and `grimoire/.github/workflows/verify-deep.yml`:

- **No `timeout-minutes` is set on either `acceptance-tests` job.** GitHub's default for a job with no explicit value is **360 minutes**, and for GitHub-hosted runners that default is also the hard ceiling — "The maximum number of minutes to let a job run before GitHub automatically cancels it. Default: 360" [[GitHub Actions timeout discussion, quoting the official reference]](https://github.com/orgs/community/discussions/25700). A hang burns up to 6 hours of runner time before anything happens.
- **The actual CI invocation loses its verbosity flag.** `test/taskfile.yml`'s `default` task runs `uv run pytest {{.CLI_ARGS | default "-v"}}` — Task's `default` filter only substitutes when the variable is *empty*; the CI step runs `task test -- --junit-xml=results/junit.xml`, which sets `CLI_ARGS` to `--junit-xml=results/junit.xml`, so `-v` is silently dropped for every real CI run (confirmed in both `ocx/test/taskfile.yml:46` and `grimoire/test/taskfile.yml:26`, and `ocx/test/pyproject.toml`'s `[tool.pytest.ini_options]` sets no `addopts` to compensate). Default pytest output without `-v` is one character per test **after** it finishes (`.`/`F`/`E`) — nothing is printed when a test *starts*, so a hang produces no name to blame.
- **Stdout is very likely block-buffered, not line-buffered, in that log.** Python's own docs: "'Interactive' text files (files for which `isatty()` returns `True`) use line buffering. Other text files use the [128 KiB block] policy" [[Python `open()` docs]](https://docs.python.org/3/library/functions.html#open). GitHub Actions captures a job's stdout via a pipe, which is not a TTY, so `isatty()` is `False` and CPython defaults to block buffering — meaning the dots for tests that already finished may sit unflushed in an up-to-128 KiB buffer and never reach the visible log at all if the process is later hard-killed rather than exiting cleanly.
- **No JUnit artifact survives a timeout-killed job.** `Upload Test Results` is gated `if: ${{ !cancelled() }}` in both workflows; a job GitHub cancels for exceeding `timeout-minutes` reports as cancelled, so the step — and with it, any record of which tests passed before the hang — never runs. (`Stop Registry`, by contrast, is `if: ${{ always() }}`, so Docker cleanup does happen even on a cancelled job — only the test-attribution artifact is lost.)

Put together: on this fleet's *actual* CI config, a hung test costs up to 6 hours of runner time and produces a red job with no test name, a log that may not even show the last several dozen tests that legitimately passed, and no JUnit XML to inspect afterward. That is a worse outcome than the "CI eventually kills it" backstop the corpus shows other projects tolerating — not because the *concept* of relying on the backstop is wrong, but because *this fleet's specific implementation of that backstop* is unusually silent.

**The middle option the corpus flagged but didn't itself adopt: `pytest-timeout`.** Read directly from its own PyPI/README description: `--timeout=N` bounds every test (opt-in via one config line, not a per-call parameter). Two methods, auto-selected per platform: **signal** (POSIX default) "schedules an alarm when the test item starts... If the alarm expires... the signal handler will dump the stack of any other threads running to stderr and use `pytest.fail()` to interrupt the test. The pytest process is not terminated and the test run can complete normally" [[PyPI `pytest-timeout`]](https://pypi.org/project/pytest-timeout/) — i.e. one hung test fails with a stack dump and *every other test still runs and still gets recorded in the JUnit XML*. **Thread** (fallback where signal isn't available, i.e. Windows) "starts a timer thread which will terminate the whole process after the specified timeout... Test runs are not completed... JUnit XML output... will not function normally" [[same]](https://pypi.org/project/pytest-timeout/) — worse than signal method, but still strictly better than today: it dumps every thread's stack before exiting, so the operator learns which test and where, in minutes instead of hours. Neither method is documented anywhere in pytest-timeout's own description as killing the timed-out test's **child processes** — the absence of any such claim in its own docs, combined with the corpus's confirmation that nobody surveyed does process-group cleanup either, means adopting `pytest-timeout` fixes attribution and wall-clock cost but leaves orphaning exactly as open as §2 describes.

A stdlib-only alternative worth naming because it requires zero new dependency: `faulthandler.dump_traceback_later(timeout, repeat=False, file=sys.stderr, exit=False)` — "Dump the tracebacks of all threads, after a timeout of `timeout` seconds... If `exit` is `True`, call `_exit()` with status=1 after dumping the tracebacks" [[faulthandler docs]](https://docs.python.org/3/library/faulthandler.html#faulthandler.dump_traceback_later). This is strictly narrower than `pytest-timeout` (no per-test scoping, no pytest-native reporting, has to be wired up by hand in a session fixture) — it is the right tool if the goal is purely "never lose the stack trace," not if the goal is "bound each test and keep the suite moving." Not recommended over `pytest-timeout` for this fleet, but worth knowing it exists as the zero-dependency fallback if a new dev-dependency is ever blocked.

**Verdict:** adopt `pytest-timeout` (a `[dependency-groups] dev` addition plus one `addopts = "--timeout=<N>"` line in each `test/pyproject.toml`, letting it auto-select signal-on-Linux / thread-on-Windows), keep a bounded `timeout-minutes` on both CI jobs as defense-in-depth for hangs outside a test body (collection, session-scoped fixture bring-up, which a per-test timer doesn't cover), and separately restore `-v`/force `PYTHONUNBUFFERED=1` in the CI invocation regardless of the timeout mechanism — that last change alone, independent of everything else in this section, is what actually makes "what happened before the hang" visible in the log. This is a config-line-and-one-workflow-edit fix, not a 1,141-call-site edit. A per-call runner `timeout=` is not recommended: it would require tuning a value that has to cover a cold binary start, a Docker pull, and a registry round-trip in the same number, and a value picked wrong converts a slow-but-passing test into a newly-flaky one — exactly the failure mode `scout-cli-acceptance.md` warned this program to weigh against the (real, but now correctly-scoped) cost of the status quo.

The mechanics below (what `timeout=` actually kills, process-group orphaning) remain accurate and relevant to the rare call site that legitimately does want a hard per-call bound — `ocx/test/tests/test_lazy_loading.py:213` is exactly such a case, and its pattern is still the right one to copy for that narrower use, just not as a blanket runner default.

`subprocess.run(timeout=)` **auto-kills** the direct child and re-raises `TimeoutExpired` after it's reaped: "If the timeout expires, the child process will be killed and waited for." [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.run) By contrast, the lower-level `Popen.communicate(timeout=)` pattern documented right below it does **not** auto-kill — the docs show the caller must do it manually:

```python
proc = subprocess.Popen(...)
try:
    outs, errs = proc.communicate(timeout=15)
except TimeoutExpired:
    proc.kill()
    outs, errs = proc.communicate()
```

Neither path documents killing descendants, and the docs don't spell out the tree behavior at all — I proved it instead of trusting silence. Reproduction (`/tmp/.../subproc/parent_default.py`, deleted after use): a `child.py` spawns a grandchild via `Popen` and then sleeps; the top-level call is `subprocess.run([sys.executable, "child.py"], timeout=2)`.

```
child pid=1022989 spawned grandchild pid=1022992
subprocess.run: TimeoutExpired raised (as expected)
grandchild pid=1022992 still alive after parent timeout: True
```

The grandchild was still alive after the timeout fired and had to be SIGKILLed manually in the repro script. This matters enormously for this harness: `ocx package test` and similar commands legitimately spawn a script runner, which can spawn `docker`, which can spawn a registry client — a timeout on the top-level `ocx` process leaves that whole tail alive, still holding registry connections, still writing to the shared test registry, after the test that spawned it has already failed and moved on.

The fix is a process-group kill, reproduced against the same scenario:

```python
proc = subprocess.Popen([...], start_new_session=True)
try:
    proc.wait(timeout=2)
except subprocess.TimeoutExpired:
    os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
    proc.wait()
```

```
Popen.wait: TimeoutExpired raised (as expected)
grandchild pid=1023707 still alive after killpg: False
```

This is not a hypothetical fix — it is the exact pattern already committed in `ocx/test/tests/test_lazy_loading.py:213-221`, including the second `communicate()`/`wait()` call after the kill to reap the zombie and drain any buffered output. **For the specific tests that legitimately need a hard per-call bound (a background/concurrent process a test deliberately hangs and then kills), this pattern is the one to copy — it is not, per the verdict above, being proposed as a blanket runner default.**

Retry-vs-fail: a timeout in a black-box CLI test should be a hard failure, not a silent retry. A registry operation that didn't finish in the allotted time is either a real product bug or a flaky-infra symptom that retrying silently would mask; the harness already has a separate, explicit retry layer for known-flaky network conditions (`fake_forge` polling/backoff in `test_announce.py`) — timeout and retry are different concerns and conflating them in one primitive hides both. This still applies to `pytest-timeout` too: it should never grow a retry-on-timeout option in this fleet's config for the same reason.

### 2. Process groups and orphans — a separate, still-open question

- `start_new_session=True` calls `setsid()` in the child before exec — it becomes a **session leader** with a fresh process group whose PGID equals its own PID, and it detaches from the controlling terminal. [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.Popen) Because PGID == PID here, `os.killpg(os.getpgid(proc.pid), sig)` reaches the whole tree the child spawns (any descendant that doesn't itself call `setsid()`/`setpgid()` inherits the group).
- `process_group=` (added in **3.11**) is the narrower primitive: `setpgid(0, value)` — it puts the child in a new process group without making it a session leader or detaching the controlling terminal. [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.Popen) For a test harness that never needs the controlling-terminal detachment, `process_group=0` is the more precise choice; `start_new_session=True` is the older, more common idiom and is what's already in the codebase, so there's no need to migrate the one existing correct example.
- `preexec_fn` (the old way to call `os.setsid()`/`os.setpgid()` manually) carries an explicit safety warning: "The `preexec_fn` parameter is NOT SAFE to use in the presence of threads in your application. The child process could deadlock before exec is called." [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.Popen) `start_new_session=`/`process_group=` exist specifically "to take the place of code using `preexec_fn`" for this purpose — never write a new `preexec_fn` for this.
- **This is now explicitly a separate question from "should a timeout exist," and orphaning does not become harmless just because nobody surveyed kills a process group.** `scout-cli-acceptance.md` confirms zero of seven real-subprocess projects read (pip, pytest, uv, ruff, ripgrep, gh CLI, and this fleet) kill a process group on timeout or failure — "it is not an omission specific to shape 1, it is an unsolved problem industry-wide." Unsolved-everywhere is not the same as harmless-everywhere; it means the fact is unmeasured elsewhere, not that it's absent. This report keeps the empirical check the team lead asked to preserve regardless of the premise change: **does the harness currently orphan processes? Yes, measured, not assumed.** `runner.run()` has no timeout and no process-group isolation today, so a hang there hangs the whole pytest worker and any descendant it spawned is invisible to whatever eventually reaps the top-level process. For the handful of direct `Popen(...)` call sites, `test_project_crash_recovery.py:144` and `test_project_concurrency.py:289-290` call `.terminate()`+`.wait(timeout=...)` on the direct child only — no `killpg` — so **any grandchild those specific commands spawn today would already be orphaned on a timeout in those two tests**, by the exact mechanism proven live in §1's reproduction (a `subprocess.run(timeout=)`-style kill leaves a `Popen`-spawned grandchild alive; confirmed by PID check, not inferred).
- **Windows**: this fleet is not exempt. `os.killpg`/`os.getpgid`/`start_new_session` are POSIX-only; the docs note `process_group` is POSIX-only too. Both harnesses run under `runs-on: windows-latest` in CI — confirmed directly: `ocx/.github/workflows/build-windows-shims.yml:262` runs `uv run pytest tests/test_windows_shim.py -v` on `windows-latest`, and `ocx/.github/workflows/shell-activation-deep.yml:85` also targets `windows-latest`. A cross-platform runner needs a `creationflags=subprocess.CREATE_NEW_PROCESS_GROUP` + `proc.send_signal(signal.CTRL_BREAK_EVENT)` branch on Windows (`os.killpg` simply doesn't exist there — `AttributeError`, not a silent no-op).

### 3. Deadlock: which sites are actually at risk

The documented rule is unambiguous: "This will deadlock when using `stdout=PIPE` or `stderr=PIPE` and the child process generates enough output to a pipe such that it blocks waiting for the OS pipe buffer to accept more data. Use `Popen.communicate()` when using pipes to avoid that." [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.wait) I measured the actual trigger size rather than citing "the pipe fills up" abstractly: `fcntl.fcntl(w, fcntl.F_GETPIPE_SZ)` on this machine reports **65536 bytes** per pipe (Linux default; stdout and stderr are separate pipes, so either one alone crossing ~64 KiB is enough). Reproduction: a child that writes 200,000 bytes to stdout with nothing reading it never reaches `sys.stdout.flush()`'s return; `Popen.wait(timeout=8)` in the parent timed out every run:

```
default Linux pipe buffer size (bytes): 65536
DEADLOCK REPRODUCED: still not exited after 8.0s (child blocked on full pipe)
```

Read all seven direct `Popen(...)` call sites in both harnesses (excluding calls that go through the runner, which uses `subprocess.run(capture_output=True)` — safe by construction, since `capture_output=True` is implemented as `communicate()` under the hood):

| Site | Drains PIPE? | Risk assessment |
|---|---|---|
| `grimoire/test/tests/test_fix_locking.py:102` | **No** — `codes = [p.wait() for p in procs]`, N concurrent processes, pipes never read | **Real.** `grim add --global --no-install` output is currently small, but this is N *concurrent* unread pipes reaped by `.wait()` in a batch — the exact textbook pattern, one verbose-logging change away from a real CI hang |
| `ocx/test/tests/test_package_test_script.py:663` | No — `proc.wait(timeout=20)` then `.kill()` | Low today (child only runs `touch`+`sleep`, minimal output) but structurally fragile |
| `ocx/test/tests/test_announce.py:1151` | No — `process.terminate(); process.wait(timeout=5)` in a `finally`, after 7s of polling/retry logging | Moderate — depends on how much the retry-logging path emits during the 7s wait; not provably safe |
| `ocx/test/tests/test_project_concurrency.py:289-290` | No — `holder.terminate(); holder.wait(timeout=5)` | Low-moderate — a lock-holder process, mostly idle, but not provably safe |
| `ocx/test/tests/test_project_crash_recovery.py:144` | No — `proc.wait(timeout=10)` | Low — process is killed quickly, unlikely to accumulate 64 KiB first |
| `grimoire/test/tests/test_broken_pipe.py:53` | **Yes** — `proc.communicate(timeout=10)` | Safe (deliberately tests `EPIPE` via a raw `os.pipe()` fd, not the deadlock path) |
| `ocx/test/tests/test_index_selfcontained.py:719-723` | **Yes** — both processes use `communicate(timeout=30)` | Safe |

The interesting question the team lead flagged — what to do when you need to stream output *and* bound it, not just "always use `communicate()`" — is exactly what `test_lazy_loading.py:213` already answers for the timeout axis: read everything via `communicate(timeout=N)` in one shot rather than incrementally, and treat "took too long to finish" and "produced too much output" as the same failure mode a black-box test doesn't need to distinguish. True incremental streaming-with-a-cap needs a reader thread (`threading.Thread` draining `proc.stdout` into a bounded buffer) or `selectors`/`select.select()` on both fds — neither harness needs this today since every current caller wants the complete output at the end, not a live tail.

### 4. Capture, decoding, encoding

Both runners pass `text=True` with no `encoding=`/`errors=`. Per the docs, `text=True` alone means "the class uses the encoding `locale.getpreferredencoding(False)`" [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.Popen) — not a fixed UTF-8. On a normal interactive Linux/macOS shell this resolves to UTF-8; on a minimal container image or a CI runner with `LANG=C`/`LC_ALL=POSIX` it can resolve to ASCII, and any byte above 0x7F in the CLI's stdout/stderr raises `UnicodeDecodeError` from *inside* `subprocess.run()` — a failure that reproduces on one CI image and not another, indistinguishable from a flaky test until someone reads the traceback closely.

`errors="replace"` is the right default for a black-box test harness specifically because the harness's job is to assert on the CLI's *behavior*, not to be a faithful byte-for-byte proxy for its output — a mis-decoded character in an assertion string is nearly always tolerable (the test just needs the surrounding text to compare), whereas the same choice inside a published library (`ocx-sdk-python`) would silently corrupt data the caller might parse or re-emit, which is why `errors="strict"` (the default) is correct there and wrong here — the two are different failure domains, not different tastes.

### 5. Exit codes and failure reporting

`CalledProcessError` (raised by `check_call`/`check_output`/`run(check=True)`) carries `returncode`, `cmd`, `output`/`stdout`, and `stderr`. [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.CalledProcessError) A **negative** `returncode` means the process was killed by a signal — "If the process exited due to a signal, this will be the negative signal number" [[subprocess docs]](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.returncode) — so `-15` is `SIGTERM`, `-9` is `SIGKILL`. This distinction matters for this harness specifically: `test_package_test_script.py` and `test_announce.py` both `.terminate()`/`.kill()` a process and then assert on its exit — a test that treats `returncode != 0` as one undifferentiated "failure" bucket cannot tell "the CLI legitimately errored" apart from "we killed it," which is exactly the ambiguity `TimeoutExpired` is supposed to resolve if the runner raised it as a distinct exception instead of `subprocess.run()` silently returning a negative-returncode `CompletedProcess`.

The runner's current failure message —

```python
raise AssertionError(
    f"ocx {' '.join(args)} failed (rc={result.returncode})\nstderr: {result.stderr.strip()}"
)
```

— is evaluated against the alternatives, not assumed correct:

- **vs. `subprocess.run(check=True)`'s own `CalledProcessError`**: the stdlib exception's default `str()` does *not* include stderr, so a bare `CalledProcessError` in a pytest failure traceback shows only the returncode — a strictly worse debugging experience for a black-box harness where the whole point of failure is "read what the CLI actually said." The runner's custom message is a genuine improvement here, not incidental.
- **vs. `pytest.fail(...)`**: `AssertionError` is what `assert` itself raises, so it composes correctly with pytest's assertion-rewriting and shows the same traceback style as every other test failure in the suite — no functional difference from `pytest.fail`, but no reason to introduce a second failure idiom either.
- **The gap**: the message conflates "non-zero exit" and "timed out" into the same code path (there is no timeout today), and conflates "exited with an error" and "was killed by a signal" (no negative-returncode branch). Once a timeout is added to the runner, the failure message needs a third branch: `TimeoutExpired` should raise its own distinct exception/message (`"ocx {args} timed out after {N}s"`) rather than falling through to the same `rc={result.returncode}` string, and a negative returncode is worth calling out explicitly (`"killed by signal {-rc}"`) rather than printed as a bare negative integer a reader has to know to interpret.

### 6. `shell=True` and argument construction

The docs are direct: "If the shell is invoked explicitly, via `shell=True`, it is the application's responsibility to ensure that all whitespace and metacharacters are quoted appropriately to avoid shell injection vulnerabilities. On some platforms, it is possible to use `shlex.quote()` for this escaping." [[subprocess docs — security considerations]](https://docs.python.org/3/library/subprocess.html#security-considerations) The library "will not implicitly choose to call a system shell" by default — the argv-list form is what makes "all characters, including shell metacharacters, can safely be passed to child processes" [[same]](https://docs.python.org/3/library/subprocess.html#security-considerations) true. Both harnesses already follow this with zero exceptions (`rg -c 'shell=True'` returns 0 in both repos) — there is nothing to fix here, only a discipline to defend against regression.

Narrow legitimate uses of `shell=True` are for shell *features* Python doesn't otherwise expose cheaply (pipelines, globbing at the shell level, `&&`/`||` chaining) — and the docs point out that most of what people reach for `shell=True` to get, Python already has natively: `glob`, `fnmatch`, `os.walk()`, `os.path.expandvars()`, `os.path.expanduser()`, `shutil` [[same]](https://docs.python.org/3/library/subprocess.html#security-considerations). This harness has no such need — it drives one compiled binary with a fixed flag grammar.

**Does 3.14 change this?** No, not yet, and the "PEP 750 changes shell-command construction" framing is overstated for anyone running 3.14 today. PEP 750 (t-strings, `string.templatelib.Template`) landed in 3.14 as a general lazy-interpolation mechanism [[PEP 750]](https://peps.python.org/pep-0750/) — it does not itself touch `subprocess` or `shlex`. The proposal that *would* — **PEP 787, "Safer subprocess usage using t-strings"**, adding a `shlex.sh()` renderer that auto-escapes interpolated values and t-string support to `subprocess.run`/`Popen` — is explicitly **`Status: Deferred`** [[PEP 787]](https://peps.python.org/pep-0787/), targeting 3.15 at the earliest, with the authors planning "to develop an experimental library through Python 3.14's beta period before revising the proposal for Python 3.15." Both project floors (3.10, 3.12) and the current ceiling (3.14) predate this; the argv-list-only rule holds unchanged for the foreseeable future and should not be softened in anticipation of a deferred PEP.

### 7. pexpect and PTYs — read from the source, not summaries

pexpect is used for interactive login flows (`ocx/test/tests/test_login.py`, `test_lazy_loading.py`, plus the cast-recorder tooling). Read the official overview and API docs directly rather than blog paraphrase:

- **`$` does not mean end-of-line.** "Pexpect reads from the child one character at a time, so each character looks like the end of a line." [[pexpect overview — end of line]](https://pexpect.readthedocs.io/en/stable/overview.html) A PTY emits `\r\n`, not bare `\n`, for line endings — "to match ends of lines you have to expect the CR/LF combination: `child.expect('\r\n')`" [[same]](https://pexpect.readthedocs.io/en/stable/overview.html). Every `expect()` pattern in this harness that assumes `\n` line-ending semantics from `re` is silently matching something other than what it thinks.
- **Greedy quantifiers at the end of a pattern are *not* greedy.** "Patterns requiring lookahead will always get a minimal match (non greedy). For example, the following will always return just one character: `child.expect('.+')`" [[same]](https://pexpect.readthedocs.io/en/stable/overview.html). This inverts the `re`-module intuition every Python developer already has — a pattern copy-pasted from a `re.match` call and dropped into `expect()` behaves differently with no error, no warning.
- **`TIMEOUT` and `EOF` are meant to be list entries, not caught exceptions.** The documented idiom is `child.expect([pattern, pexpect.TIMEOUT, pexpect.EOF])` and reading `child.expect()`'s return index to know which branch matched, or explicitly passing `timeout=None` to disable timeout entirely when EOF alone should terminate the wait: `child.expect(pexpect.EOF, timeout=None)` [[pexpect overview]](https://pexpect.readthedocs.io/en/stable/overview.html). Wrapping the whole `expect()` call in `try: ... except pexpect.TIMEOUT: ...` works, but throws away the chance to distinguish "the child hung" from "the child exited unexpectedly" in one code path, and both should produce a different assertion message.
- **Report what was actually seen, not a bare timeout.** `before` holds everything read up to the match, `after` holds the matched text itself, `match` is the `re` match object [[pexpect overview — finding the end of line]](https://pexpect.readthedocs.io/en/stable/overview.html). On any `expect()` failure, the diagnostically useful message is `child.before` (and, for a raw `EOF`/`TIMEOUT`, `child.buffer`) — a caught-and-reraised `pexpect.TIMEOUT` with no `before` attached tells a future debugger only "it hung," never "it hung after printing X."
- **`setwinsize(rows, cols)`** sets the child TTY's window size and "will cause a SIGWINCH signal to be sent to the child" [[pexpect API docs]](https://pexpect.readthedocs.io/en/stable/api/pexpect.html) — relevant if the CLI under test reflows output based on terminal width (a login/interactive flow reasonably might), since a default/unset window size can make output wrap unpredictably and break line-anchored `expect()` patterns.
- **`delaybeforesend`** defaults to 50ms specifically because "many users were experiencing" unreliable echo-back timing around password prompts [[pexpect API docs]](https://pexpect.readthedocs.io/en/stable/api/pexpect.html) — worth knowing this is a documented, deliberate default and not a magic number to "optimize away" if a login test feels slow.
- **`searchwindowsize`**: `None` (default) searches the *entire* accumulated buffer on every new byte received; setting a bound trades correctness (a pattern spanning more than the window won't match) for throughput [[pexpect API docs]](https://pexpect.readthedocs.io/en/stable/api/pexpect.html) — not something to set casually in a test harness where correctness matters far more than the microseconds saved.
- **ANSI escapes / buffer stripping**: neither the overview nor the API reference document any ANSI-stripping behavior — pexpect does not strip escape codes from its buffer by default. Any `expect()` pattern matching against colorized CLI output must either account for embedded escape sequences explicitly or force the child to run with color disabled (see §8) — this was not documented anywhere I could find, consistent with the team lead's note that this area is thinly documented; the honest answer is "verified absent from the docs," not "confirmed absent from the source" (I did not read the pexpect source for this dive; flagged as a gap below).

### 8. TTY-versus-pipe divergence

Two independent, overlapping conventions govern this:

- **`NO_COLOR`**: "Command-line software which adds ANSI color to its output by default should check for a `NO_COLOR` environment variable that, when present and not an empty string (regardless of its value), prevents the addition of ANSI color." [[no-color.org]](https://no-color.org/) Precedence: "User-level configuration files and per-instance command-line arguments should override the `NO_COLOR` environment variable" [[same]](https://no-color.org/) — i.e. an explicit `--color=always` flag should still win over an inherited `NO_COLOR=1`. The standard is scoped narrowly to *color*, not to bold/underline/italic or other styling.
- **`FORCE_COLOR`** is the inverse convention (force color on even when output isn't a TTY) — widely adopted alongside `NO_COLOR` by tools including ruff, pip, pytest, and rich, but it is not part of the `NO_COLOR` spec itself; it is a separate, complementary de facto standard.
- **`CI=true`**: GitHub Actions sets this by default for every workflow run — "The GitHub Actions runner now sets the `CI=true` environment variable by default" [[GitHub Changelog]](https://github.blog/changelog/2020-04-15-github-actions-sets-the-ci-environment-variable-to-true/) — and it is overwhelmingly the convention across CI systems generally, which is why many CLI tools treat a bare `CI` env var as an implicit "don't assume a human is watching a terminal" signal even independent of `isatty()`.
- **`TERM=dumb`** is a terminfo-database convention (the `dumb` terminal type declares no capabilities — no cursor movement, no color) rather than a formally standardized environment-variable spec the way `NO_COLOR` is; I could not find a single authoritative "spec" document for it the way I could for `NO_COLOR`, so this is flagged rather than over-cited — the honest statement is "widely observed convention, not a formal RFC-style standard."
- **`isatty()`** (`sys.stdout.isatty()`) is the actual mechanism by which a CLI distinguishes a terminal from a pipe/file at runtime — this is what changes the CLI's own default behavior (color, progress bars, interactive prompts) between a developer's terminal and a test harness's captured pipe, and it is the reason the harness needs a `requires_tty` marker at all: `subprocess.run(capture_output=True)` always presents a pipe to the child, so any test that needs the child's *TTY-mode* behavior cannot get it through the plain runner — it needs a real PTY, which is exactly what `pexpect.spawn()` provides and `subprocess.Popen` does not.

**Evaluating the harness's `requires_tty` marker**: `ocx/test/tests/test_update_check_throttle.py` documents it directly — tests not marked `requires_tty` assume no controlling terminal (the normal `subprocess.run` pipe path); tests marked `requires_tty` need `pexpect` because the behavior under test only fires when `isatty()` is true. This is the right design: it makes the TTY-vs-pipe choice an explicit, named property of each test rather than an implicit side effect of which helper happened to get called, and it correctly routes only the tests that need the divergence through the heavier `pexpect` path rather than defaulting everything to a PTY "to be safe." The one gap: nothing in the harness appears to force `NO_COLOR=1`/`TERM=dumb` on the *non*-`requires_tty` path explicitly in the runner's env dict (both runners set an explicit, minimal env, but neither sets these) — today this works because the pipe path naturally makes most CLIs suppress color via their own `isatty()` check, but that makes the harness's pipe-mode output correctness an accidental consequence of the CLI's own good behavior rather than a guarantee the harness itself asserts.

## Normative guidance candidates

1. **Adopt `pytest-timeout` as a session-level `--timeout=<N>` default in both `test/pyproject.toml`s, not a per-call runner `timeout=`.** *Rationale*: pip, pytest's own `Pytester`, and uv all ship zero per-call timeout — a per-call default would be ahead of the corpus, not catching up to it, and would introduce a value that has to be tuned across cold binary start + Docker pull + registry round-trip in one number, a known flaky-test-creation risk. `pytest-timeout` bounds the same hang at the suite level with one config line, auto-selects signal method on Linux (run continues, JUnit XML stays valid for every other test) and thread method on Windows (process exits, but with a full thread-stack dump — still strictly better than today's silent 360-minute wait). *Verify*: `rg -c 'pytest-timeout' -g 'pyproject.toml' test` returns 1 in each repo; a deliberately-hung test in CI now fails within `<N>` seconds with a named test and a stack dump in the log, instead of a 6-hour silent hang.
2. **Set a bounded `timeout-minutes` on both `acceptance-tests` CI jobs.** *Rationale*: today neither job sets one, so GitHub's 360-minute default/hard-max applies — confirmed by reading both workflow files directly. This is defense-in-depth for hangs `pytest-timeout`'s per-test timer doesn't cover (test collection, session-scoped fixture bring-up like the registry/sigstore stack). *Verify*: `rg -n 'timeout-minutes' ocx/.github/workflows/verify-deep.yml grimoire/.github/workflows/verify-deep.yml` shows a value on the `acceptance-tests` job in both files (currently: no match at all).
3. **Restore `-v` (or an equivalent explicit verbosity flag) and force unbuffered stdout in the CI invocation, independent of the timeout mechanism chosen.** *Rationale*: measured directly — `task test -- --junit-xml=...` silently drops the taskfile's own `-v` default via Task's `default` templating, so CI runs with no per-test name printed as it starts; and GitHub Actions' log pipe is not a TTY, so CPython block-buffers stdout by default, meaning even the dots that *did* print may not reach the visible log before a hard kill. Both compound into "the log shows nothing useful right before a hang," independent of whatever kills the hung process. *Verify*: `rg -n 'CLI_ARGS' test/taskfile.yml` in the CI step should show an explicit `-v` (or `-ra`) surviving into the actual invocation; the "Run Acceptance Tests" step's `env:` should set `PYTHONUNBUFFERED: "1"`.
4. **Never call `.wait()`/`.poll()` on a `Popen` with `stdout=PIPE`/`stderr=PIPE` without draining via `.communicate()`.** *Rationale*: the deadlock is real and quantified (64 KiB per stream); `test_fix_locking.py:102` is a live instance. *Verify*: `checks/check_popen_deadlock.py <path>` — empty output = pass; a `Popen(` + `PIPE` + no `communicate` anywhere in the same file is the finding.
5. **Every direct `Popen(...)` call outside the runner must pass `start_new_session=True` and drain via `communicate(timeout=)`, mirroring `test_lazy_loading.py`.** *Rationale*: five of seven direct `Popen` sites in this audit lack process-group isolation; two already got this right independently, which means the pattern is known but not enforced. *Verify*: manual review of each `Popen(` call site (no crisp static check — a Popen call with `start_new_session=True` two lines earlier vs. two functions earlier is not distinguishable by grep alone).
6. **Pass `encoding="utf-8", errors="replace"` explicitly instead of relying on `text=True` + locale default.** *Rationale*: `text=True` alone resolves to `locale.getpreferredencoding(False)`, which is not guaranteed UTF-8 on every CI image; a black-box harness should tolerate malformed bytes in captured output rather than crash on them. *Verify*: `rg -c 'text=True' -g '*.py' src/runner.py` should be 0 once migrated; `rg -c 'encoding="utf-8"' -g '*.py' src/runner.py` should be 2 (one per runner).
7. **Keep the argv-list-only discipline; do not introduce `shell=True`.** *Rationale*: both harnesses are already at zero `shell=True` sites — this is a "don't regress" rule, not a new fix. *Verify*: `rg -c 'shell=True' -g '*.py' <path>` — nonzero output is the finding.
8. **Windows needs its own kill-the-tree branch — `os.killpg` is POSIX-only and raises `AttributeError` on Windows, it does not silently no-op.** *Rationale*: both harnesses run under `windows-latest` in CI today; a `killpg`-based fix that isn't platform-guarded breaks Windows CI outright rather than just failing to clean up. *Verify*: the runner's timeout-kill path branches on `sys.platform == "win32"` and uses `creationflags=subprocess.CREATE_NEW_PROCESS_GROUP` at spawn plus `proc.send_signal(signal.CTRL_BREAK_EVENT)` (or `proc.kill()` as a same-process fallback) on that branch.
9. **`pexpect.expect()` patterns must match `\r\n`, never bare `\n`, and must not rely on `$` for end-of-line.** *Rationale*: pexpect reads one character at a time, so `$` matches after every character, and a PTY emits CR/LF — documented directly, not inferred. *Verify*: `rg -n "expect\(.*\\\\n['\"]" -g '*.py' <path>` flags any `expect()` pattern ending in a bare `\n` with no preceding `\r`.
10. **Every `pexpect.spawn(...).expect([...])` call in an interactive-flow test must list `pexpect.TIMEOUT` and `pexpect.EOF` as explicit pattern-list entries, not rely on a caught exception around the whole call.** *Rationale*: the indexed-branch form is what the library is designed around, and it's the only form that lets a failure message report `child.before` distinctly for "hung" vs. "exited early." *Verify*: manual review — `rg -n 'expect\(\[' -g '*.py' <path>` finds the good pattern, `rg -n 'except pexpect\.(TIMEOUT|EOF)' -g '*.py' <path>` finds the pattern to migrate away from.
11. **A `pexpect` failure message must include `child.before` (and `child.buffer` for a bare `TIMEOUT`/`EOF`), never a bare "expect failed."** *Rationale*: this is the only way a CI failure log tells you what the child actually printed before it stopped answering. *Verify*: grep for `except pexpect` blocks and confirm each one references `.before` in its `pytest.fail(...)`/raised-exception message.
12. **`check=False` call sites must assert on `.returncode` explicitly in the same test.** *Rationale*: an opt-out from the runner's default `check=True` is only safe if the caller actually inspects the result; otherwise a regression that changes the CLI's exit code from 1 to 0 (or vice versa) passes silently. *Verify*: no automated check exists (flagged in §9) — this is a code-review heuristic: for every `check=False`, confirm `.returncode` appears within the same test function.
13. **Do not add a timeout-triggered retry anywhere in the timeout/pytest-timeout path.** *Rationale*: retry and timeout are different concerns; the harness already has a purpose-built backoff/retry layer for known-flaky network conditions (`fake_forge`), and folding retry into the timeout primitive would silently mask both real product hangs and genuine infra flakiness under the same "it eventually passed" signal. *Verify*: no retry loop wraps `pytest-timeout`'s failure or any per-call `communicate(timeout=)` handler; retries stay confined to the network-facing fixtures that already have them.
14. **For the narrow set of tests that legitimately need a hard per-call kill (a deliberately-hung background process a test spawns and then kills, e.g. `test_lazy_loading.py`, `test_package_test_script.py`, `test_announce.py`), the kill must take the whole process group, not just the direct child.** *Rationale*: proven live in §1 — `subprocess.run(timeout=)`/`Popen.kill()` leaves a `Popen`-spawned grandchild alive; `scout-cli-acceptance.md` confirms nobody surveyed (pip, pytest, uv, ruff, ripgrep, gh CLI) does this either, so doing it here is a genuine improvement, not catch-up, and should stay scoped to these specific call sites rather than generalized into every `pytest-timeout`-covered test. *Verify*: `test_lazy_loading.py:213-221`'s pattern (`start_new_session=True` + `os.killpg(os.getpgid(pid), SIGKILL)` on `TimeoutExpired`) is present at every site in rule-4's violation list (below) that spawns a process it may need to kill early.
15. **A test that explicitly `.terminate()`s or `.kill()`s a child (as opposed to one that times out) should assert on the resulting negative `returncode` explicitly, not just `returncode != 0`.** *Rationale*: `-15`/`-9` (SIGTERM/SIGKILL) and a genuine CLI error currently collapse into the same "non-zero" bucket in every test that checks exit status this way; distinguishing them is what tells a future reader whether the test proved "the CLI errored correctly" or merely "we killed it and it died." *Verify*: `test_package_test_script.py` and `test_announce.py`'s kill-and-assert blocks compare against the specific expected negative value, not a bare truthiness check on non-zero.

## AI-agent angle

See the table in [§9](#9-what-an-llm-gets-wrong) for the full mistake/check pairing. Condensed to actionable form for an agent editing this codebase:

- Writing `subprocess.run(...)` or adding a call through `ocx.run()`/`grim.run()`? Do **not** add a per-call `timeout=` "to be safe" — the suite-level `pytest-timeout` bound (rule 1) already covers it, and pip/pytest/uv's own reference harnesses ship none at the call level either; a per-call value an agent guesses is more likely to be a new source of flakiness than a fix.
- Writing a new direct `Popen(...)` (bypassing the runner, e.g. for a background/concurrent process test that deliberately hangs and kills a child)? Copy `test_lazy_loading.py:213-221`'s pattern verbatim — `start_new_session=True` at spawn, `communicate(timeout=)`, `killpg`+`SIGKILL`+drain on `TimeoutExpired` — this is the one place a per-call timeout and an explicit process-group kill are both correct.
- Never reap a `Popen` with `PIPE` streams via `.wait()`/`.poll()` alone — always `.communicate()`.
- Never write `shell=True` in this codebase — it is a zero-occurrence pattern today and any new instance is itself the violation.
- `check=False` requires a `result.returncode ==`/`!=` assertion in the same test — an agent adding `check=False` "to see what happens" without reading the code afterward is adding dead permissiveness.

## Contested / evolving

As of 2026-08-23:

- **The premise correction itself, stated plainly per instructions:** the original framing of "610+ call sites missing `timeout=`" as an obvious defect was overstated — retracted, not merely caveated, once a sibling survey confirmed pip, pytest's own `Pytester`, and uv all ship zero default per-call subprocess timeouts. The part that survived scrutiny and hardened rather than weakened is the CI-backstop cost analysis in §1, which is specific to this fleet's actual (unset `timeout-minutes`, verbosity-dropping, non-`PYTHONUNBUFFERED`) CI config, not a property of subprocess timeouts in the abstract.
- **`pytest-timeout`'s signal-vs-thread method choice** is settled by platform, not by preference — signal on POSIX (keeps the run going), thread as the documented fallback "on systems not supporting the signal method" (implying, not explicitly stating, that this covers Windows; I did not find a sentence naming Windows directly in the fetched description). Treat this as a reasonable inference from the auto-selection behavior, not a directly-quoted fact — flagged rather than asserted with false confidence.
- **PEP 787** (t-string-based safe subprocess construction) is Deferred, not Rejected — its eventual landing (targeted 3.15) could change the recommended idiom for building shell-invoked commands from interpolated values, but does not change anything about argv-list `Popen`/`run()` calls, timeouts, or process groups, which are the overwhelming majority of what this harness does.
- **`process_group=` vs `start_new_session=`** for new code: both are correct and both are POSIX-only; there is no consensus in the docs or in this codebase favoring one over the other when session-leader/controlling-terminal detachment isn't otherwise needed. This report defers to the codebase's existing precedent (`start_new_session=True`) rather than asserting `process_group=0` is objectively better — it is only more precise, not more correct.
- **pexpect and ANSI escape stripping**: I found no documentation, in either the overview or the API reference, describing whether pexpect strips ANSI escape sequences from its internal buffer. This is a genuine gap in this research — it was checked against pexpect's *documentation* only, not its *source code*, and the team lead's brief specifically asked for source-level reading here. Flagged rather than guessed at.
- **`TERM=dumb`** has no single canonical specification the way `NO_COLOR` does (a terminfo convention, not an RFC-style standard) — cited as a widely-observed convention, not as a spec with a single authoritative URL.
