## Summary

- **`GradleRunner.withPluginClasspath()` does reach settings scope** — the injected classpath is wired as a `PluginResolver` at Gradle's `Scope.Build` service layer and consulted by `DefaultPluginRequestApplicator.applyPlugins(...)` regardless of whether the `PluginManagerInternal target` is a project or a `Settings` — the method signature never branches on target type ([gradle/gradle@ea17004a31:platforms/extensibility/plugin-use/src/main/java/org/gradle/plugin/use/internal/DefaultPluginRequestApplicator.java:88](#sources)).
- **Gradle's own configuration-cache TestKit suite documents this generalization in a code comment**, naming both routes explicitly: `INJECTED_CLASSPATH` through `DefaultInjectedClasspathPluginResolver` (`withPluginClasspath()`) and `MAVEN_REPO` through `DefaultScriptClassPathResolver` (publish-locally + `pluginManagement { repositories {} }`) ([gradle/gradle@ea17004a31:platforms/core-configuration/configuration-cache/src/integTest/groovy/org/gradle/internal/cc/impl/ConfigurationCacheTestKitIntegrationTest.groovy:36-48](#sources)).
- **Nobody exercises this combination.** Zero of the 32 exemplars, and zero of gradle/gradle's own ~30 TestKit integration-test files, apply a plugin from a *generated settings.gradle(.kts)*'s `plugins {}` block in a functional test — every `settings.gradle` write in `GradleRunnerPluginClasspathInjectionIntegrationTest.groovy` is a bare `include '...'`, never a plugin application. The mechanism is real; the exemplar is not.
- **The `pluginManagement { repositories { maven(...) } }` route is the one with a citable canonical shape**: `pluginManagement { repositories { maven(url = file("./maven-repo")); gradlePluginPortal() } }`, documented to be the first block in the settings file ([Gradle: Working with Plugins](https://docs.gradle.org/current/userguide/plugins_intermediate.html)).
- **The `compileOnly` × `withPluginClasspath()` incompatibility is identical at settings scope, not merely analogous** — the injected classpath is one `ClassPath` object read once from `plugin-under-test-metadata.properties`'s `implementation-classpath` key ([gradle/gradle@ea17004a31:platforms/extensibility/test-kit/src/main/java/org/gradle/testkit/runner/internal/PluginUnderTestMetadataReading.java:31-32](#sources)); it is consumed by the same `DefaultInjectedClasspathPluginResolver` no matter which script's `plugins{}` block is being resolved, so a `compileOnly` dependency missing from that classpath produces the same `ClassNotFoundException` naming the *other* plugin's class regardless of whether the plugin under test is `Plugin<Project>` or `Plugin<Settings>`.
- **No API or build-scan value reports how many times a shared `BuildService` was instantiated.** `BuildServiceRegistry` exposes only `registerIfAbsent(...)` and `getRegistrations()`; neither returns an instantiation count, and the "exactly once" guarantee is a construction-time property of `registerIfAbsent` itself, not something introspectable after the fact ([BuildServiceRegistry javadoc](https://docs.gradle.org/current/javadoc/org/gradle/api/services/BuildServiceRegistry.html)).
- **The only sanctioned assertion is a file the service writes** — per the already-shipped GRADLE-PLUG-15 rule, a TestKit build runs in a separate process via the Tooling API, so no in-process static counter is legal evidence; the service's own execution-time code must append a marker (a UUID, a PID, a monotonic line) to a file on first use, and the test reads that file after `build()` and asserts exactly one line even though ≥2 subprojects consumed the service.
- **`withDebug(true)` technically breaks process isolation and would make an in-process static readable**, but this is a debugging aid for IDE breakpoints, not a sanctioned assertion path — it changes daemon/classloading behavior and is documented incompatible with `withEnvironment(...)`, so a test suite that relies on it for assertions is coupling correctness to a debug-only code path.
- **`--configuration-cache` passed to `withArguments(...)` is a build-invocation-level flag with no project/settings distinction in the instrumentation layer** — `InjectedClasspathInstrumentationStrategy` operates on the `ClassPath`, not on `PluginManagerInternal` target type, so a functional-test leg that runs `--configuration-cache` against a build that applies the settings plugin under test *is* GRADLE-PLUG-23's verification, and GRADLE-PLUG-10's existing "dedicated functional-test leg" language covers it without new machinery — the one caveat is that the leg's test project must be the one whose *settings file* applies the plugin, since that is unavoidable for a Settings plugin (there is no other file to apply it from).
- **Isolated Projects diagnostics reuses the configuration-cache problem-reporting pipeline** — gradle/gradle's own fixture routes `IsolatedProjectsMode.DIAGNOSTICS` through `assertStateStoredAndDiscarded`, meaning diagnostics mode always stores then discards the cache entry and reports through the same channel as `--configuration-cache` problems ([gradle/gradle@ea17004a31:platforms/core-configuration/configuration-cache/src/integTest/groovy/org/gradle/internal/cc/impl/isolated/IsolatedProjectsFixture.groovy:124-132](#sources)) — which means `BuildResult.getOutput()` **is** a legal TestKit assertion surface for it (GRADLE-PLUG-15's own sanctioned categories), not merely a human-read report.
- **The exact diagnostics console string is not pinned by any source read** — Isolated Projects is incubating only since 9.7.0 and its wording is one of the program's already-catalogued "dated re-checks nothing can close today" (jvm-topic-map.md convergence, item 2). GRADLE-PLUG-27's cell is written to assert on the *presence/absence of a violation report*, not on frozen wording.
- **Six of the seven rules (GRADLE-PLUG-23/24/25/27, partially -22 and -28) gain a genuinely runnable TestKit assertion that did not exist in the shipped cells**, most of them negative tests (tamper with the input, assert the build *fails* at the right place) rather than positive greps — this is the wave's real yield, not just "yes, TestKit reaches settings scope."
- **Two rules keep a reading heuristic, named as such, because no dynamic assertion adds signal**: GRADLE-PLUG-26 (parameter-mutation shape is a code-structure fact, not a runtime symptom on its own) and the process half of GRADLE-PLUG-28 (a diff-review policy gate). Both cells say "reading heuristic" explicitly rather than presenting a grep as if it were a functional test.

## Findings

### 1. Does withPluginClasspath() reach settings scope at all

The TestKit user guide itself is silent on settings scope: it documents `withPluginClasspath()` purely in terms of the `plugins {}` DSL in a "test build," and its worked example applies the plugin from `build.gradle` ([Testing Gradle plugins](https://docs.gradle.org/current/userguide/test_kit.html)). Nothing in the guide says the mechanism is build-script-only, but nothing says it reaches settings scope either — the brief's premise (wave 2/3 established nothing here) is confirmed by the primary doc's silence, not just by absence of an exemplar.

Reading the source resolves it. `GradleRunner.withPluginClasspath()` populates a `ClassPath` that TestKit wires into the build as an injected-classpath plugin resolver. The wiring point is `PluginResolverFactory`, a `@ServiceScope(Scope.Build.class)` service whose `addDefaultResolvers(...)` method appends `DefaultInjectedClasspathPluginResolver` to the resolver chain unconditionally — the chain is the same list of resolvers (`NoopPluginResolver`, `CorePluginResolver`, the injected-classpath resolver, contributed resolvers, the plugin-repositories resolver) for *any* caller ([gradle/gradle@ea17004a31:platforms/extensibility/plugin-use/src/main/java/org/gradle/plugin/use/internal/PluginResolverFactory.java:56-86](#sources)). The caller is `DefaultPluginRequestApplicator.applyPlugins(PluginRequests requests, ScriptHandlerInternal scriptHandler, PluginManagerInternal target, ClassLoaderScope classLoaderScope)` — `target` is typed to the generic `PluginManagerInternal`, and the method body never inspects what kind of target it is before resolving plugins against it ([gradle/gradle@ea17004a31:platforms/extensibility/plugin-use/src/main/java/org/gradle/plugin/use/internal/DefaultPluginRequestApplicator.java:82-131](#sources)).

Confirming that a `Settings`'s `PluginManagerInternal` genuinely is one of these targets: `SettingsScopeServices.createPluginManager(...)` builds it the same way core does for a project, via `ImperativeOnlyPluginTarget<>(PluginTargetType.SETTINGS, settings, problems)` wrapped in the same `DefaultPluginManager` class used everywhere else ([gradle/gradle@ea17004a31:subprojects/core/src/main/java/org/gradle/internal/service/scopes/SettingsScopeServices.java:98-117](#sources)). There is a distinct `PluginTargetType.SETTINGS` enum value, but it exists to route *plugin application* (calling `apply()` and validating the plugin implements the right marker interface), not plugin *resolution* — resolution is target-agnostic by construction.

Gradle's own configuration-cache TestKit test states this generalization outright, in a doc comment on the test class itself, naming both application routes a functional test can use and which internal class each one exercises:

> "How the plugin under test reaches the inner build: INJECTED_CLASSPATH goes through `DefaultInjectedClasspathPluginResolver`, exercised by TestKit's `withPluginClasspath()`. MAVEN_REPO goes through `DefaultScriptClassPathResolver`, exercised by publishing the plugin to a local Maven repository and applying it via the `plugins {}` block." ([gradle/gradle@ea17004a31:platforms/core-configuration/configuration-cache/src/integTest/groovy/org/gradle/internal/cc/impl/ConfigurationCacheTestKitIntegrationTest.groovy:36-48](#sources))

That comment is written about a *build*-script plugin in that specific test, but nothing in the two classes it names (`DefaultInjectedClasspathPluginResolver`, `DefaultScriptClassPathResolver`) branches on target type either — both are consulted from `DefaultPluginRequestApplicator.applyPlugins`, which is exactly as reachable from a settings script's `plugins {}` block as from a project's.

**What is genuinely missing is an exemplar.** `GradleRunnerPluginClasspathInjectionIntegrationTest.groovy` and its sibling `GradleRunnerManualPluginClasspathInjectionIntegrationTest.groovy` — gradle/gradle's own tests of this exact feature — write `settings.gradle` files only to `include` subprojects, never to apply a plugin from them. Across the 32-repo corpus, `ktorio/ktor`'s `build-settings-logic` (the cleanest `*.settings.gradle.kts` split in the corpus, GRADLE-STRUCT-02's copy target) and `junit-team/junit-framework`'s `gradle/base/settings-conventions` ship **zero** test source directories (`git ls-tree` on both returns no `src/test`, `src/functionalTest`, or `src/integTest` path under either module). Nobody in the corpus tests a Settings plugin under TestKit at all — the brief's framing ("nothing established how GradleRunner applies a Plugin<Settings> at all") is not a research gap this dive closes by finding a hidden exemplar; it is a fact about the ecosystem the dive confirms by reading gradle/gradle's own test suite and two real Settings-plugin-shipping repos and finding none of them do it.

**Answer, concretely runnable:** a functional test for a `Plugin<Settings>` generates a test-project `settings.gradle.kts` whose first block is
```kotlin
pluginManagement {
    repositories {
        maven(url = file("./maven-repo"))
        gradlePluginPortal()
    }
}
plugins {
    id("com.example.ocx-settings") version "1.0"
}
```
(canonical `pluginManagement` shape per [Working with Plugins](https://docs.gradle.org/current/userguide/plugins_intermediate.html), which states the block "must be the first block in the file") and either (a) publishes the plugin under test to `./maven-repo` first (`maven-publish` to a `file://` repo, the `MAVEN_REPO` route), or (b) skips the `pluginManagement` block's `maven(...)` entry, calls `GradleRunner.create().withPluginClasspath().withProjectDir(testProjectDir).withArguments("help")`, and lets the injected classpath resolve the `plugins { id(...) }` line directly (the `INJECTED_CLASSPATH` route). Both are real, both are runnable, and the choice between them is exactly GRADLE-PLUG-14's compileOnly decision (§2).

### 2. The compileOnly × withPluginClasspath trap at settings scope

The trap is not "similar" at settings scope, it is **the same defect object reached from a different call site**. `PluginUnderTestMetadataReading.readImplementationClasspath(...)` reads one property, `implementation-classpath`, out of one generated file, `plugin-under-test-metadata.properties` ([gradle/gradle@ea17004a31:platforms/extensibility/test-kit/src/main/java/org/gradle/testkit/runner/internal/PluginUnderTestMetadataReading.java:31-32](#sources)). That classpath is computed once, by the `PluginUnderTestMetadata` task, from the plugin module's `main` source set's runtime classpath — which by construction excludes anything declared `compileOnly`, because that is what `compileOnly` means. `GradleRunner.withPluginClasspath()` hands this single `ClassPath` to `DefaultInjectedClasspathPluginResolver`, and — per Finding 1 — that resolver is consulted for *every* `plugins {}` block resolution in the build, settings or project. There is no second, settings-aware copy of the classpath computation to fix independently; fixing the trap for `Plugin<Project>` (GRADLE-PLUG-14, already shipped) and fixing it for `Plugin<Settings>` are the same fix, applied at the same call site, for the same reason.

The documented symptom is unchanged too: "your tests will fail with a `ClassNotFoundException` because the required base plugin classes are not included in the isolated test classpath" — a stack trace pointing at the *other* plugin's class, not at a "missing classpath" diagnostic ([Testing Gradle plugins](https://docs.gradle.org/current/userguide/test_kit.html); corroborated in [jvm-gradle-plugin-dev/testkit-matrix-and-portal.md:200](../jvm-gradle-plugin-dev/testkit-matrix-and-portal.md)). Nothing about *which* scope's `plugins{}` block triggered the resolution changes which class the `ClassNotFoundException` names — it names whatever `compileOnly` dependency's class the plugin under test's own code references but didn't get packaged.

**Runnable check, unchanged in shape from GRADLE-PLUG-14, applied to a Settings plugin module:**
```bash
grep -rn 'compileOnly(' <settings-plugin-module>/build.gradle.kts
grep -rln 'withPluginClasspath' <settings-plugin-module>/src/*[Ff]unctional*/
```
Co-occurrence is the violation, exactly as for a project plugin — the only new clause is that the functional test's `settings.gradle.kts` (not `build.gradle.kts`) is where the `pluginManagement { repositories {} }` workaround has to live, because for a Settings plugin that *is* the only file with a `plugins {}` block to put it in.

### 3. Asserting a shared BuildService was created exactly once

Neither the Build Services user guide chapter nor the `BuildServiceRegistry` javadoc documents an instance-creation counter, a build-scan surface for it, or any introspection API beyond `getRegistrations()` (which returns the set of *registrations*, i.e. names and types, not instantiation history) ([Shared build services](https://docs.gradle.org/current/userguide/build_services.html); [BuildServiceRegistry javadoc](https://docs.gradle.org/current/javadoc/org/gradle/api/services/BuildServiceRegistry.html)). The "exactly once" guarantee documented for `registerIfAbsent(...)` is that "only the first registration succeeds, and any later registrations return the previously registered instance" ([Isolated Projects](https://docs.gradle.org/current/userguide/isolated_projects.html)) — a guarantee about the *registration*, i.e. that Gradle will not construct two different `Provider`s for the same service name, not a runtime-observable "constructed N times" value a test can read back.

Combined with the already-shipped GRADLE-PLUG-15 rule (a TestKit build runs in "a separate process via the Tooling API with its own classpath, classloaders and dedicated daemons," so "an in-process assertion tests the test JVM, not the plugin" — [jvm-gradle-plugin-dev.md:80](../jvm-gradle-plugin-dev.md)), a static counter incremented in the service's constructor is not legal evidence even if the test author is tempted to read it back via a static field, because the test JVM and the build JVM are different processes by default.

There is one loophole worth naming and rejecting: `GradleRunner.withDebug(true)` runs the build in the *same* JVM as the test, specifically so an IDE debugger can attach — which would make an in-process static genuinely readable. This is not a sanctioned substitute for a real assertion: it is documented as incompatible with `withEnvironment(...)`, it changes daemon and classloading behavior relative to what a real consumer experiences (the entire point of TestKit's process isolation), and a test suite whose pass/fail depends on `withDebug(true)` staying enabled has coupled its correctness signal to a debugging feature. **Rejected, not adopted.**

**What is left, and what it actually reads:** a file the service writes. The `BuildService`'s execution-time code (its constructor, or the first call into its own methods — whichever the plugin's implementation treats as "first use") appends a marker — a random UUID, a PID, or simply a line — to a fixed path (e.g. under the test project's build directory, or a path the test controls via `BuildServiceParameters`). The TestKit test configures a multi-project build where at least two subprojects each cause the service to be requested (via `registerIfAbsent(...)` returning the same `Provider`, consumed by a task in each project), runs `build()` once, and asserts the marker file contains **exactly one** entry. This is not a build-scan value and not a Gradle-provided assertion API — it is the reading heuristic GRADLE-PLUG-15 already sanctions (files on disk), applied to this specific question. **No first-class mechanism exists; this is the constructed check, and the rewritten cell says so rather than implying a built-in assertion.**

### 4. Does --configuration-cache in withArguments exercise a settings plugin

`--configuration-cache` is a start-parameter flag processed once per build invocation; nothing in the configuration-cache instrumentation layer conditions on which kind of plugin manager requested a class. `InjectedClasspathInstrumentationStrategy.getTransform()` — the exact hook the `ConfigurationCacheTestKitIntegrationTest` class comment calls out as the trigger for TestKit + config-cache interaction ("that is what triggers `DefaultInjectedClasspathPluginResolver` construction and, by side effect, `InjectedClasspathInstrumentationStrategy.getTransform()`") — operates on the injected `ClassPath`, a scope-agnostic object ([gradle/gradle@ea17004a31:platforms/core-configuration/configuration-cache/src/integTest/groovy/org/gradle/internal/cc/impl/ConfigurationCacheTestKitIntegrationTest.groovy:36-48](#sources)). The test class itself parametrizes every one of its config-cache-compatibility cases over both `INJECTED_CLASSPATH` and `MAVEN_REPO` (`where: mode << PluginResolutionMode.values()`), i.e. Gradle's own suite already treats "which route resolved the plugin" as an axis orthogonal to "does configuration-cache work," which is exactly the orthogonality GRADLE-PLUG-10's rationale already asserts for `Plugin<Project>` (M-F-04, cited in jvm-gradle-plugin-dev.md verdict 5).

So: **yes, and the "separate leg" language in GRADLE-PLUG-10 already covers GRADLE-PLUG-23's verification, with one structural fact worth stating rather than assuming.** For a `Plugin<Project>`, the functional-test leg's `--configuration-cache` run and the leg that actually applies the plugin under test can, in principle, be different projects. For a `Plugin<Settings>`, they cannot be — the settings file is the only place the plugin is ever applied, so *any* `--configuration-cache` invocation against that generated test project necessarily also exercises the settings plugin's configuration-cache compatibility. There is no failure mode where a settings-plugin functional-test suite runs `--configuration-cache` against "the wrong build" — running it at all is running it against the settings plugin.

**Runnable check (identical in shape to the existing GRADLE-PLUG-23 cell, confirmed rather than assumed):**
```kotlin
val first = GradleRunner.create()
    .withProjectDir(testProjectDir)
    .withArguments("help", "--configuration-cache")
    .build()
val second = GradleRunner.create()
    .withProjectDir(testProjectDir)
    .withArguments("help", "--configuration-cache")
    .build()
assert(second.output.contains("Reusing configuration cache."))
```
(literal string, per frame correction 36 / [gradle/gradle#24040](https://github.com/gradle/gradle/issues/24040) — a green build alone does not prove the cache was reused, only this exact line does, because some failure modes silently disable the cache rather than erroring).

### 5. Isolated Projects diagnostics output and TestKit

`-Dorg.gradle.isolated-projects.diagnostics=true` is the primary-doc-confirmed flag; Isolated Projects itself was "promoted from experimental to incubating" in Gradle 9.7.0 ([Isolated Projects](https://docs.gradle.org/current/userguide/isolated_projects.html)). The user guide describes diagnostics mode's *behavior* ("runs configuration of projects sequentially," "all violations… are detected") but not its exact console output, and no primary doc read for this dive pins the literal string. Reading gradle/gradle's own integration-test fixture for this feature answers the mechanism question, if not the exact wording: `IsolatedProjectsFixture`'s handling of `IsolatedProjectsMode.DIAGNOSTICS` "forwards to `assertStateStoredAndDiscarded`" — i.e. diagnostics mode stores a configuration-cache-shaped entry and then always discards it, routing violation reporting through the **same problem-reporting pipeline `--configuration-cache` uses for its own problems** ([gradle/gradle@ea17004a31:platforms/core-configuration/configuration-cache/src/integTest/groovy/org/gradle/internal/cc/impl/isolated/IsolatedProjectsFixture.groovy:124-132](#sources)).

That routing matters for testability: `--configuration-cache` problems are known to surface as console text a TestKit test can grep (the existing `ConfigurationCacheTestKitIntegrationTest` asserts `!output.contains("Configuration cache problems found")` as a matter of course). If IP diagnostics reuses that pipeline, `BuildResult.getOutput()` is exactly the surface GRADLE-PLUG-15 already sanctions for a TestKit assertion (a `BuildResult`, not in-process state) — so **yes, a TestKit test can assert on it**, with the caveat that the precise phrase to grep for is one of the program's already-catalogued "dated re-checks nothing can close today" (jvm-topic-map.md convergence, item 2: IP's console wording is not pinned by any source this program has read, and IP is young enough — 9.7.0, 2026-08-06 — that it is a reasonable thing to re-verify on the next Gradle minor).

**Runnable check, stated without a frozen string:**
```bash
./gradlew help -Dorg.gradle.isolated-projects.diagnostics=true 2>&1 | tee out.log
# pass: exit 0 AND no "problems were found" / "Isolated Projects" violation summary in out.log
# re-check the exact phrase against the pinned Gradle version before trusting a grep on it
```
via TestKit: `GradleRunner.create().withArguments("help", "-Dorg.gradle.isolated-projects.diagnostics=true").build()` then assert `result.output` contains none of the violation-summary vocabulary current for the pinned Gradle version — a reading heuristic on the *exact phrase*, a runnable command on the *presence/absence check*. The CI-required-job half of the rule (never wire `org.gradle.isolated-projects=true` into a required job) is a separate, static `grep -rn 'isolated-projects' .github/workflows/` over the *consumer's* CI config, not something TestKit can see at all — TestKit only runs the plugin's own functional-test build, never the CI YAML that invokes it.

## Normative guidance candidates

1. **A Settings-plugin functional test applies the plugin under test from the generated `settings.gradle.kts`'s own `plugins {}` block — never from a project `build.gradle.kts`, and never assume `withPluginClasspath()` is build-script-only.** Rationale: the injected-classpath resolver is wired at `Scope.Build` and consulted by `DefaultPluginRequestApplicator` for any `PluginManagerInternal` target; nothing in Gradle restricts it to project scope. Verify: reading heuristic — confirm the functional test's generated settings file, not its build file, carries the `plugins { id(...) }` line applying the plugin under test.
2. **Choose the `MAVEN_REPO` route (`pluginManagement { repositories { maven(...) } }`) over `withPluginClasspath()` for any Settings plugin that declares `compileOnly` on another plugin's API — the trap is identical at settings scope, not merely analogous (GRADLE-PLUG-14 extended).** Verify: `grep -rn 'compileOnly(' <module>/build.gradle.kts` co-occurring with `grep -rln 'withPluginClasspath' <module>/src/*[Ff]unctional*/` is the violation, same as GRADLE-PLUG-14.
3. **Prove a shared `BuildService`'s "created once" guarantee with a file the service writes on first use, never with a static field or `withDebug(true)`.** Rationale: no Gradle API or build-scan surface reports instantiation count; TestKit's default process isolation makes in-process state untestable by construction (GRADLE-PLUG-15), and `withDebug(true)` defeats that isolation as a side effect rather than a sanctioned exception. Verify: run a ≥2-subproject functional test, assert the marker file has exactly one entry after `build()`.
4. **Treat a dedicated `--configuration-cache` functional-test leg as sufficient evidence for a Settings plugin's configuration-cache compatibility — do not write a second, settings-specific leg believing the existing GRADLE-PLUG-10 leg does not reach it.** Rationale: for a Settings plugin, the settings file is the only place it is applied, so any invocation against that generated project necessarily exercises it; the instrumentation layer is scope-agnostic by source. Verify: run `help --configuration-cache` twice via `GradleRunner`; the second `BuildResult.output` must contain the literal `Reusing configuration cache.`.
5. **Prove sha256 enforcement (GRADLE-PLUG-24) with a negative TestKit test, not only a grep.** Rationale: a grep proves where the `MessageDigest`/`Sha256` call lives but not that a mismatch actually stops the build — a check computed but never consumed by anything (a common laziness bug with Gradle `Provider`s) passes every grep while doing nothing. Verify: tamper with the expected sha256 in the functional test's configuration, run `buildAndFail()`, and assert the failure occurs at (or before) the point the binary is first placed on a classpath/`PATH` — run the same tampered case once more with `--configuration-cache` to confirm the failure still occurs on a cached run.
6. **Prove the cache-directory and hash-based skip rule (GRADLE-PLUG-25) with two TestKit legs, not a source read alone**: (a) run the build, `./gradlew clean`, run again, and assert the second run's output contains no re-download marker (proves the cache path survives `clean`, i.e. is not under `build/`); (b) pre-place a file at the expected cache path with the *right name and wrong content*, run the build, and assert it is rejected/re-fetched rather than silently trusted (proves the skip condition compares a hash, not `exists()`).
7. **GRADLE-PLUG-26 keeps its reading heuristic, named as one — TestKit adds no independent signal.** Rationale: "parameters set once, read only via `findByName`" is a structural fact about where code executes, not a runtime symptom that manifests observably on its own; its dynamic corroboration is candidate 8 (IP diagnostics), not a dedicated functional test. Verify: `grep -rn 'sharedServices' <plugin>/src` — every hit is either the single registration or a `findByName` call; any `.parameters` assignment elsewhere is the violation.
8. **Run Isolated Projects diagnostics as a TestKit-assertable functional-test leg (GRADLE-PLUG-27), asserting on `BuildResult.output`, and separately grep CI workflow files for the "never required" half — the two checks live in different files and neither substitutes for the other.** Verify: `GradleRunner.create().withArguments("help", "-Dorg.gradle.isolated-projects.diagnostics=true").build()`, assert no violation-summary text (re-confirm the exact phrase against the pinned Gradle version first — dated re-check); separately, `grep -rn 'isolated-projects' .github/workflows/` must return nothing in a job with `pull_request:`/`push:` triggers.
9. **GRADLE-PLUG-28's process gate (major version + changelog on a JSR-305→JSpecify swap) gains a genuine functional-test corroboration, not just a diff review**: a consumer-shaped fixture project applies the plugin (old annotation set) with a call site that is a real nullness mismatch against the plugin's public API, asserts `build()` succeeds with a warning in the output (`-Xjsr305=warn` default); the same fixture against the new (JSpecify) annotation set asserts `buildAndFail()` (`-Xjspecify-annotations=strict` default since Kotlin 2.1). Verify: run both fixtures under TestKit as a compatibility-matrix leg, plus the existing `git diff --stat` changelog/major-version gate for the process half.
10. **Never treat a green functional-test suite for a Settings plugin as proof it works under `--configuration-cache` or Isolated Projects unless the specific leg for each ran** — a suite that only runs `./gradlew help` without either flag has tested neither, and both are separate MUST/SHOULD rows (GRADLE-PLUG-10/23 and -27) precisely because they are orthogonal failure modes, not implied by a plain green build.

## AI-agent angle

- **An agent asked to write a functional test for a Settings plugin defaults to writing it as if it were a project plugin** (applying it from a generated `build.gradle.kts` instead of `settings.gradle.kts`), because every TestKit example an LLM was trained on — including Gradle's own user-guide walkthrough — is a project-plugin example. Mechanical check: the functional test's generated project must contain a `settings.gradle(.kts)` with a `plugins { id(...) }` block naming the plugin under test; a functional test whose only `plugins {}` block is in a `build.gradle(.kts)` while testing a class that implements `Plugin<Settings>` is testing the wrong scope entirely, and will typically pass for the wrong reason (the plugin id resolves against Gradle core or an unrelated cached artifact) or fail with a misleading "plugin not found."
- **An agent "fixes" GRADLE-PLUG-14's compileOnly trap only in the build-script-plugin test suite** and leaves the settings-plugin suite using `withPluginClasspath()`, because it treats the rule as being about `Plugin<Project>` specifically (its only documented context) rather than about the shared classpath-computation mechanism. Mechanical check: `grep -rln 'withPluginClasspath'` across **every** `src/*[Ff]unctional*/` directory in the repo, project-scope and settings-scope alike, cross-checked against every module with a `compileOnly(` on a plugin artifact.
- **An agent asked to "verify the BuildService is created once" reaches for a static counter and `withDebug(true)`**, because it is the shortest code path to an assertion that reads naturally in a unit test. This is exactly the trap named in Finding 3: it works today, breaks the isolation guarantee TestKit exists to provide, and silently stops testing what a real Gradle daemon does. Mechanical check: `grep -rn 'withDebug' <plugin>/src/*[Ff]unctional*/` — any hit paired with a static-field assertion in the same test file is the smell; the fix is the file-marker pattern in candidate 3.
- **An agent asked to prove sha256 enforcement writes only a grep for `MessageDigest`**, satisfying the letter of GRADLE-PLUG-24 while never proving the check actually runs — a common failure mode is a `Provider<String>` computed from a `ValueSource` that nothing ever calls `.get()` on, which passes the grep and does nothing at runtime. Mechanical check: candidate 5's negative test — tamper with the pin, assert `buildAndFail()`.
- **An agent hallucinates a Gradle build-scan API or a `BuildServiceRegistration` field for instantiation count** when asked "how do I prove this service is a singleton" — no such surface exists as of the Gradle release this dive read against (`BuildServiceRegistry` javadoc, current). Mechanical check: any code review or generated test referencing a build-scan value, a `.instantiationCount`, or similar for a `BuildService` is citing an API that does not exist; the file-marker pattern is the only real option.
- **An agent assumes IP diagnostics prints a stable, quotable string it can hardcode into a rule or a test**, when Isolated Projects is incubating only since 9.7.0 (2026-08-06) and the primary doc gives behavior, not wording. Mechanical check: any rule or test hardcoding a specific IP-violation phrase should carry a dated re-check comment naming the Gradle version it was last confirmed against, per this program's own convention for dated facts.

## Contested / evolving

- **Isolated Projects diagnostics' console wording is unverifiable as of this dive** (2026-09-12) — the mechanism (routes through the configuration-cache problem pipeline) is source-confirmed, the exact string is not, because IP has been incubating for barely five weeks (since 9.7.0, 2026-08-06). Trending: expect the wording to stabilize alongside IP's promotion out of incubating, at which point GRADLE-PLUG-27's cell should be re-confirmed and a literal string added, the same way GRADLE-PLUG-23's cell already carries one for configuration-cache reuse.
- **Whether `withPluginClasspath()` or the `MAVEN_REPO` route should be the *default* recommendation for Settings-plugin testing, independent of the `compileOnly` trap, is unsettled by any source read for this dive.** `withPluginClasspath()` is less setup (no local publish step) but couples the test to the exact `main` source-set classpath the `PluginUnderTestMetadata` task computes; the `MAVEN_REPO` route is closer to what a real consumer experiences (resolution through `pluginManagement { repositories {} }`, the actual mechanism a Settings plugin ships through) at the cost of a `maven-publish` step in the test fixture. No corpus exemplar and no gradle/gradle test settles this for settings scope specifically, because none exists (Finding 1). Recommend `MAVEN_REPO` as the higher-fidelity default and `withPluginClasspath()` only where the `compileOnly` trap is provably absent — consistent with, not contradicting, GRADLE-PLUG-14's existing carve-out.
- **The "created once across projects" assertion pattern (candidate 3) is this dive's own construction, not a documented Gradle idiom** — no primary source recommends the file-marker pattern by name. It follows directly from combining two already-shipped facts (no instantiation-count API; TestKit's process isolation), but an adopter should not expect to find this pattern named in Gradle's own docs or samples.
