## Summary

- **Lighthouse's a11y score is a weighted average of ~70 binary pass/fail audits (weights 3–10), each derived from axe-core** (`lighthouse@13.4.1`'s own `package.json` pins `axe-core@^4.12.1`) — it is not a separate accessibility engine, it is axe wearing a scoring rubric ([Chrome for Developers scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring), [npm registry lighthouse](https://registry.npmjs.org/lighthouse)).
- **Every Lighthouse a11y audit is a single-DOM-snapshot, single-viewport check** — there is no audit in the list that simulates a keyboard Tab sequence, a click, a route change, or any post-interaction state; the audit list itself (alt text, labels, ARIA validity, contrast, landmark presence, tabindex *values* not tabindex *behavior*) is the evidence, not an explicit disclaimer on the page ([Chrome for Developers a11y audits](https://developer.chrome.com/docs/lighthouse/accessibility/)).
- **Deque's own claim for axe-core: "you can find on average 57% of WCAG issues automatically"** ([dequelabs/axe-core README](https://github.com/dequelabs/axe-core)) — and W3C's own guidance is blunter: **"no tool alone can determine if a site meets accessibility standards. Knowledgeable human evaluation is required"** ([W3C WAI Test and Evaluate](https://www.w3.org/WAI/test-evaluate/)). Lighthouse, running the same engine once against one route, cannot exceed that ceiling — it is a floor check, not a compliance check.
- **`eslint-plugin-jsx-a11y` is stale: latest `6.10.2`, published 2024-10-26 — 22 months old as of 2026-08-29**, with 113 open issues and no v7 in sight ([npm registry](https://registry.npmjs.org/eslint-plugin-jsx-a11y), [GitHub](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y)). It is purely AST-based (static JSX-element analysis) — it needs no `parserOptions.project`, no type-aware wiring, and works unmodified with `fma`'s existing flat-config ESLint 9 setup.
- **`eslint-plugin-vuejs-accessibility` is the opposite: latest `2.6.0`, published 2026-08-10 — 19 days before this research**, actively maintained, depending only on `vue-eslint-parser@^9||^10` and `aria-query` ([npm registry](https://registry.npmjs.org/eslint-plugin-vuejs-accessibility)).
- **`creeptd-ng/web` cannot adopt it today without standing up ESLint from scratch: `eslint` is not a dependency anywhere in the monorepo** — the root `package.json`'s `devDependencies` is a literal `{}`, and `web/package.json` has no `eslint` entry either, despite a `"lint": "eslint src --ext .ts,.vue"` script. Running `npm run lint` here fails with "command not found," not a lint error — confirmed by reading both `package.json` files directly.
- **`kate-middlechild/packages/web` already has static a11y coverage and needs no new tool**: its committed `biome.json` sets `linter.rules.preset: "recommended"` with an explicit (non-disabling) `a11y: {}` override, and Biome's `a11y` rule group ships 37 rule files covering JSX ([GitHub `biome_js_analyze/src/lint/a11y`](https://github.com/biomejs/biome/tree/main/crates/biome_js_analyze/src/lint/a11y)) — the same 36-rule group the fleet's own `lint-catalogue-sweep.md` already mapped 1:1 against `jsx-a11y` rule IDs.
- **Biome v2.4 (2026-02-10) extended that further: 15 new HTML-embedded a11y rules that "work seamlessly with Vue, Svelte, and Astro files"** ([Biome v2.4 blog](https://biomejs.dev/blog/biome-v2-4/)) — meaning `kate-middlechild`'s `.astro` templates (8 files) get native markup-level a11y linting today, on Biome `2.5.11` (published 2026-08-27, two days before this research — [npm registry](https://registry.npmjs.org/@biomejs/biome)), a materially more current tool than either ESLint a11y plugin.
- **The correction that pairs with the above: `kate-middlechild` is not "no typescript dep at all" as the project brief states** — its root `package.json` declares `"typescript": "^5.8.0"` and `packages/{core,web}/package.json` both pull it via `catalog:`. This does not change the Biome-vs-typescript-eslint decision (Biome is still the sole linter; `typescript`/`vue-tsc`-style checking here is `astro check`, not a lint tool), but the "no TS at all" framing is factually off and worth flagging so downstream config doesn't assume zero `tsconfig.json` surface in this repo.
- **`@axe-core/playwright` is current and cheap for the two repos already running Playwright: `4.13.0`, published 2026-08-11, depending on `axe-core@~4.13.0` (published 2026-08-05) and peering on `playwright-core >= 1.0.0`** ([npm registry](https://registry.npmjs.org/@axe-core/playwright)) — both `kate-middlechild` (`@playwright/test@^1.52.0`) and `creeptd-ng/web` (`@playwright/test@^1.60.0`) already satisfy that peer range; the marginal cost really is one spec file, confirmed by reading both `playwright.config.ts` files directly.
- **Axe's own results shape is the tolerance mechanism — do not bolt on a numeric ratio.** `AxeBuilder.analyze()` returns `violations` (definite, rule-level pass/fail) separately from `incomplete` (axe's own "needs review" bucket — the `color-contrast` rule is explicitly tagged both `failure` and `needs review` in axe-core's own rule descriptions) ([axe-core rule-descriptions.md](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md)). Gate hard on `violations`, never on `incomplete`; use `disableRules()`/`exclude()` for known false positives ([Playwright accessibility-testing guide](https://playwright.dev/docs/accessibility-testing), [`@axe-core/playwright` README](https://github.com/dequelabs/axe-core-npm/blob/develop/packages/playwright/README.md)). This is categorically different from `kate-middlechild`'s existing `maxDiffPixelRatio: 0.01` pixel-diff tolerance (a continuous drift measure) and should not copy that pattern.
- **Vitest's `toMatchAriaSnapshot()`/`toMatchAriaInlineSnapshot()` asserts against the accessible-name/role/state tree, needs zero new dependency beyond `@vitest/browser` (which `kate-middlechild` already has as `@vitest/browser-playwright`), and is a genuinely different check from axe** — a regression snapshot of computed accessible names and ARIA roles, not a WCAG rule engine ([Vitest ARIA snapshots](https://vitest.dev/guide/browser/aria-snapshots)). It catches "this button lost its accessible name" the moment a component test runs; axe catches "this page violates WCAG."
- **VS Code gives webview authors exactly two CSS hooks and nothing else — no accessibility contract, no automated reach.** The webview guide's entire Accessibility section, quoted in full: *"The class `vscode-using-screen-reader` will be added to your webview's main body in contexts where the user is operating VS Code with a screen reader... the class `vscode-reduce-motion` will be added... By observing these classes and adjusting your rendering accordingly, your webview content can better reflect the user's preferences."* ([VS Code webview guide](https://code.visualstudio.com/api/extension-guides/webview)) — no ARIA passthrough, no built-in check, no mention of automated testing anywhere on that page or the extension UX guidelines page.
- **`grimoire-vscode`'s webview is not JSX or Vue at all — it's `lit-html` templates rendered with `unsafe-html`/`ifDefined`/`repeat` directives plus `@vscode-elements/elements` custom elements** (confirmed by reading `src/webview/render.ts` directly) — `jsx-a11y` and `vuejs-accessibility` are structurally inapplicable here. The one tool shaped for this surface, `eslint-plugin-lit-a11y`, is itself stale: latest `5.1.1`, published 2025-07-21, 13+ months old ([npm registry](https://registry.npmjs.org/eslint-plugin-lit-a11y)).
- **The decision: static linting binds everywhere an ESLint/Biome AST already runs (mechanical, always-on, zero runtime cost); dynamic `@axe-core/playwright` binds only where Playwright already runs (`kate-middlechild`, `creeptd-ng/web` after it gets ESLint); LHCI stays where decision (d) already put it; the VS Code webviews get a static-only, best-effort rule because nothing automated reaches inside the extension host.**
- **On block-vs-warn: static a11y lint errors should block CI the same way any other lint rule blocks — an agent editing a component sees it before commit, no new gate class needed. Dynamic axe `violations` should block CI too, but only on `violations`, never on `incomplete` — warning-only on `incomplete` avoids the flaky-gate failure mode `kate-middlechild` already guards against with its pixel-diff tolerance, without inventing a parallel numeric-tolerance mechanism axe doesn't need.**

## Findings

### 1. What Lighthouse's a11y category actually is

Lighthouse's accessibility category score is **a weighted average of all accessibility audits**, weighting derived from axe's own user-impact assessments, per the scoring-methodology page ([Chrome for Developers, `/docs/lighthouse/accessibility/scoring`](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)). Every audit is **binary, not partial-credit**: the page's own example — *"if some buttons on a page have accessible names, but others don't, the page gets a 0"* for that audit — makes clear a single unlabeled button anywhere on the page zeroes that audit's contribution, not just the affected element.

The audit list itself (`/docs/lighthouse/accessibility/`, [Chrome for Developers](https://developer.chrome.com/docs/lighthouse/accessibility/)) runs to roughly 70 audits at weights 3–10: the weight-10 tier is ARIA attribute validity/matching, `aria-hidden` misuse, required-ARIA-attributes, valid roles, button/input/select/form-label names, image alt text, `<meta>` viewport scaling, table headers, video captions; weight-7 covers `accesskey` uniqueness, dialog/tooltip/treeitem names, focus-related `aria-hidden` conflicts, contrast, document `lang`, link names/distinguishability, list structure; weight-3 covers heading order, landmark presence, skip-link focusability, `xml:lang` matching.

That entire list is powered by axe-core under the hood: `lighthouse@13.4.1`'s `package.json` (npm registry, `dependencies`) pins `"axe-core": "^4.12.1"` directly. Lighthouse is not an independent a11y engine — it is axe-core, run once, against one static rendered snapshot per collected run, scored as a weighted pass/fail rubric. `numberOfRuns` (3 in `ocx-catalog`'s config) exists to smooth *render* jitter across repeated loads of the same page, not to explore different application states.

### 2. What it structurally cannot reach

No entry in the Lighthouse a11y audit list simulates: a keyboard `Tab` traversal (the `tabindex` audit checks the presence of a *positive* tabindex value, not whether focus actually lands in a sane visual order), a click/keypress interaction and its resulting DOM mutation, a modal open/close cycle, a route change in an SPA, or any state that only exists after a user acts. This is not because the page says so explicitly (it doesn't carry a limitations disclaimer) — it's because the audit catalogue itself contains no audit whose description involves a second frame of interaction. A single static-HTML capture is the only input axe-core (and therefore Lighthouse) ever receives.

That boundary is independently confirmed by the tool's own maintainer and by the standards body: Deque's `axe-core` README states plainly, **"With axe-core, you can find on average 57% of WCAG issues automatically"** ([dequelabs/axe-core](https://github.com/dequelabs/axe-core)) — under half of WCAG issues, by the rule engine author's own accounting, are not reachable by any automated run of axe, regardless of how many pages you point it at. W3C's own testing guidance is more categorical still: **"no tool alone can determine if a site meets accessibility standards. Knowledgeable human evaluation is required to determine if a site is accessible"** ([W3C WAI, Test and Evaluate](https://www.w3.org/WAI/test-evaluate/)).

Concretely, for this fleet: keyboard traps in `fma`'s `@xyflow/react` canvas interactions, focus order through `creeptd-ng/web`'s Bevy/WASM canvas + HUD overlay, and any accessibility state that only exists after opening `grimoire-vscode`'s marketplace details panel or a `@vscode-elements` dropdown are all outside what a Lighthouse run or a bare axe scan of the landing state will ever see. This is the argument for a second tier (dynamic scanning against real interaction states) being necessary rather than optional — but it is *also* the argument that even a second tier only closes part of the gap, because Playwright specs still have to be *written* to reach those states; axe does not discover them on its own.

### 3. Static tier: eslint-plugin-jsx-a11y for fma

`eslint-plugin-jsx-a11y` latest is **`6.10.2`, published 2024-10-26T04:45:18Z** — 22 months stale as of 2026-08-29, with **113 open issues** on the repo and no v7 branch visible ([npm registry](https://registry.npmjs.org/eslint-plugin-jsx-a11y), [GitHub jsx-eslint/eslint-plugin-jsx-a11y](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y)). Its own dependency list pins `axe-core: ^4.10.0` — a floor, not a pin, so npm resolves it against the current `axe-core@4.13.0` fine; the plugin's staleness is about rule/PR velocity, not a broken dependency.

It needs no type-aware wiring: the GitHub description states it is a **"Static AST checker for accessibility rules on JSX elements"** — pure syntax-tree analysis over JSX attribute/element shape, no `parserOptions.project`, no `typescript-eslint` type-checked config required. This means it drops into `fma`'s existing ESLint 9 flat-config setup (`eslint.config.js`, confirmed present) alongside `typescript-eslint@^8.18.1` with zero additional TS-project wiring — the only integration cost is `npm install -D eslint-plugin-jsx-a11y` and adding its recommended config to the flat-config array.

Its rule surface overlaps almost entirely with the Biome `a11y` group the fleet's own `lint-catalogue-sweep.md` already enumerated (Biome's 36 recommended a11y rules table, each row mapped to a `jsx-a11y/*` equivalent — `noAccessKey`→`jsx-a11y/no-access-key`, `useAltText`→`jsx-a11y/alt-text`, and so on through all 36). That table is not re-derived here; the point that matters for `fma` is narrower: `fma` is an ESLint repo, not a Biome repo, so the practical choice isn't "jsx-a11y vs. Biome's a11y group" in the abstract — it's "adopt the ESLint-native plugin that already has that ruleset mapped, because switching `fma`'s linter to Biome is a separate, much larger decision this brief does not open."

### 4. Static tier: eslint-plugin-vuejs-accessibility for creeptd-ng/web

`eslint-plugin-vuejs-accessibility` latest is **`2.6.0`, published 2026-08-10T02:12:32Z — 19 days before this research**, actively maintained (three releases in the last 6 months per the registry's version history: `2.4.2`→`2.5.0`→`2.6.0`), depending on `vue-eslint-parser: ^9.0.0 || ^10.0.0` and `aria-query: ^5.3.0`, peering on `eslint: ^5..^10` ([npm registry](https://registry.npmjs.org/eslint-plugin-vuejs-accessibility)). Like `jsx-a11y`, it is template-AST-based (`vue-eslint-parser` parses `.vue` SFC templates into an AST the plugin walks), not type-aware — no `vue-tsc` project wiring needed.

But `creeptd-ng/web` cannot use it as-is: **`eslint` is not installed anywhere in this monorepo.** The workspace root's `package.json` declares `"devDependencies": {}` literally, and `web/package.json`'s own `devDependencies` list — read directly — has no `eslint` entry despite carrying a `"lint": "eslint src --ext .ts,.vue"` script. There is also no `eslint.config.*`/`.eslintrc*` file anywhere under `creeptd-ng/web`. Running `pnpm --filter web lint` today fails at "eslint: command not found," not at a missing-config error — a materially worse starting point than `fma`, where the only gap is one missing plugin in an already-working setup. Adopting `vuejs-accessibility` here is therefore a two-step lift: stand up ESLint 9 + `vue-eslint-parser` + a flat config for `.vue`/`.ts` first, then add the a11y plugin — not a one-line addition.

### 5. Static tier already present: Biome's a11y group in kate-middlechild

`kate-middlechild`'s committed `biome.json` already carries:

```json
"linter": {
  "enabled": true,
  "rules": {
    "preset": "recommended",
    "a11y": {},
    ...
  }
}
```

`linter.rules.preset` is Biome's current (non-deprecated) config key — the docs describe `"recommended"` as *"enables Biome's recommended rules (default)"*, distinct from the older deprecated boolean `linter.rules.recommended` ([Biome configuration reference](https://biomejs.dev/reference/configuration/)). The `a11y: {}` entry is an explicit key with no rule turned `"off"` inside it — it does not disable the group, it is present only as a placeholder for future per-rule overrides, so the `a11y` group's recommended-tagged rules apply exactly as the `"recommended"` preset would apply them with no `a11y` key at all.

That group is substantial: Biome's own source tree lists **37 rule files** under `crates/biome_js_analyze/src/lint/a11y` ([GitHub](https://github.com/biomejs/biome/tree/main/crates/biome_js_analyze/src/lint/a11y)) — `no_access_key`, `no_autofocus`, `no_positive_tabindex`, `use_alt_text`, `use_valid_aria_role`, `use_semantic_elements`, and so on — the same 36-rule set (35 recommended) the fleet's `lint-catalogue-sweep.md` already tabulated with 1:1 `jsx-a11y` rule-ID mappings. `kate-middlechild/packages/web` has 30 `.tsx` files (React islands via `@astrojs/react`) that this group already lints on every `biome check` run.

**As of Biome v2.4 (2026-02-10) this extends past JSX**: the release introduced **"15 comprehensive accessibility-focused lint rules for HTML,"** and the release post states explicitly these rules **"work seamlessly with Vue, Svelte, and Astro files"** ([Biome v2.4 blog](https://biomejs.dev/blog/biome-v2-4/)). `kate-middlechild/packages/web` has 8 `.astro` files whose markup now gets native a11y linting through the same tool already gating every commit, on `@biomejs/biome@2.5.11` (published 2026-08-27 — [npm registry](https://registry.npmjs.org/@biomejs/biome)), a release two days old at research time. This is a materially more current a11y story, on both axes (rule breadth into non-JSX templates, and tool freshness), than either ESLint plugin covers for their respective ecosystems.

One correction to the project brief's framing: `kate-middlechild` is described there as having **"no typescript dep at all."** Reading the actual files: root `package.json` declares `"typescript": "^5.8.0"`, and `packages/core/package.json` / `packages/web/package.json` both pull `typescript` via a pnpm `catalog:` reference. TypeScript is present as a *type-checking* dependency (`astro check`, `@astrojs/check`) — the accurate claim is "no `typescript-eslint`, no type-aware linting" (Biome is the sole linter, and Biome does not consume TypeScript's type-checker), not "no TypeScript dependency."

### 6. Dynamic tier: @axe-core/playwright

`@axe-core/playwright` latest is **`4.13.0`, published 2026-08-11T17:07:40Z**, depending on `axe-core: ~4.13.0` (axe-core's own latest, published 2026-08-05T16:53:07Z) and peering on `playwright-core: >= 1.0.0` ([npm registry](https://registry.npmjs.org/@axe-core/playwright), [npm registry axe-core](https://registry.npmjs.org/axe-core)). Both repos this tier targets already clear that peer range: `kate-middlechild` runs `@playwright/test@^1.52.0`, `creeptd-ng/web` runs `@playwright/test@^1.60.0` (both read directly from their `package.json`).

Canonical usage, verbatim from the Playwright docs and the package's own README:

```js
const { AxeBuilder } = require('@axe-core/playwright');
// ...
const accessibilityScanResults = await new AxeBuilder({ page }).analyze();
expect(accessibilityScanResults.violations).toEqual([]);
```

([Playwright accessibility-testing guide](https://playwright.dev/docs/accessibility-testing), [`@axe-core/playwright` README](https://github.com/dequelabs/axe-core-npm/blob/develop/packages/playwright/README.md)). Suppression is built into the builder API: `.exclude(selector)` drops an element **and all its descendants** from the scan (an explicit caveat in the Playwright docs), and `.disableRules(ruleIds)` "skips verification of the rules provided" for known, accepted issues.

For `kate-middlechild`, the marginal cost really is what the brief frames it as: the `playwright.config.ts` already boots the built `dist/` via `preview` on `localhost:4321` across two color-scheme projects — an axe spec is one new `.e2e.ts` file reusing that same `webServer`/`baseURL` wiring, no new runner. Same shape for `creeptd-ng/web`: its `e2e/` Playwright suite already drives the Vite dev server with software-GL flags for the WASM canvas — an axe spec adds one file to an existing `testDir`. Neither `fma` nor `grimoire-vscode`/`vscode-ocx` have this cost profile: `fma` has no Playwright at all (only `vitest`+`jsdom`), so adding `@axe-core/playwright` there means standing up a second test runner, not appending a file to one that already runs — a materially different, larger ask that this research does not recommend taking on as part of closing this gap.

### 7. Is axe deterministic enough to gate, or does it need tolerance?

Axe-core is a rule engine over the computed DOM/accessibility tree, not a pixel comparator — there is no anti-aliasing or sub-pixel jitter class of noise inherent to its output the way there is for `kate-middlechild`'s screenshot diffs (`toHaveScreenshot: { maxDiffPixelRatio: 0.01 }`, read directly from `playwright.config.ts`). Given the same rendered DOM state, the same axe-core version produces the same violations.

The tool's own result shape is *already* the right tolerance mechanism, and it's categorical rather than numeric: `AxeBuilder#analyze()` returns `violations` (rules with definite failing instances) separately from `incomplete` (axe's own "needs review" bucket for anything it cannot resolve with certainty). `color-contrast` — the rule most likely to produce environment-dependent results (font loading timing, headless rendering differences) — is tagged in axe-core's own rule descriptions as **both `"failure"` and `"needs review"`** ([axe-core `rule-descriptions.md`](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md)), meaning axe itself already routes its least-certain contrast findings into the non-blocking bucket rather than asserting them as hard failures.

The correct gate, therefore, is: assert `violations` is empty (or an explicit, named allowlist via `disableRules`/`exclude` for accepted issues, mirroring how the Playwright docs describe "a more granular set of known issues"); never assert on `incomplete` — surface it as a report artifact instead. This is a different mechanism from `kate-middlechild`'s pixel-ratio tolerance, not the same pattern re-applied: pixel diffing needs a *continuous* threshold because rendering drift is continuous; axe's own output is already binned into "definite" vs. "needs a human," so importing a numeric tolerance on top would be solving a problem axe already solved differently.

### 8. A zero-cost complement: Vitest ARIA snapshots

Vitest's browser-mode `toMatchAriaSnapshot()` / `toMatchAriaInlineSnapshot()` assert against the **accessibility tree** — accessible names (computed from text/labels/`aria-label`), ARIA roles, and states/properties (checked, disabled, expanded, level, pressed, selected) — described directly as testing *"the accessibility structure of your pages"* ([Vitest ARIA snapshots guide](https://vitest.dev/guide/browser/aria-snapshots)). Example from the docs:

```ts
await expect.element(page.getByRole('form')).toMatchAriaInlineSnapshot(`
  - form "Log In":
    - textbox "Email"
    - textbox "Password"
    - button "Submit"
`)
```

This needs no dependency beyond `@vitest/browser`, which `kate-middlechild/packages/web` already has (`@vitest/browser-playwright@^4.1.0`, `vitest-browser-react@^2.2.0`, both read from its `package.json`). It is not a WCAG rule engine and does not replace axe — it is a regression check: "this component's accessible-name tree changed," caught at component-test granularity the moment a PR breaks it, before any axe scan or Lighthouse run gets a chance to see the built app. Worth noting as a candidate rather than folding into the tier decision below, since it is a different kind of check (regression detection, not a compliance rule set) and `creeptd-ng/web`'s `@vue/test-utils`+`jsdom` setup does not currently run Vitest in browser mode at all, so the zero-marginal-cost framing applies to `kate-middlechild` specifically, not the fleet generally.

### 9. The VS Code webview case

VS Code's official webview guide has a section titled "Accessibility," quoted here in full: **"The class `vscode-using-screen-reader` will be added to your webview's main body in contexts where the user is operating VS Code with a screen reader. Additionally, the class `vscode-reduce-motion` will be added to the document's main body element in cases where the user has expressed a preference to reduce the amount of motion in the window. By observing these classes and adjusting your rendering accordingly, your webview content can better reflect the user's preferences."** ([VS Code webview guide, Accessibility section](https://code.visualstudio.com/api/extension-guides/webview))

That is the entirety of the host's accessibility contract: two CSS class hooks the extension can *choose* to read. There is no ARIA passthrough guarantee, no host-side automated check, and no mention of accessibility testing anywhere on that page or on the parallel extension UX-guidelines reference page ([VS Code extension-guidelines](https://code.visualstudio.com/api/references/extension-guidelines)) — that second page covers Command Palette, Quick Picks, Notifications, Webviews, Context Menus, Walkthroughs, and Settings UX conventions with zero accessibility subsection. A VS Code webview is, in the brief's framing, exactly "a Chromium document the host gives no accessibility contract" — confirmed by the absence of one in the host's own documentation, not inferred from silence elsewhere.

Nothing in this fleet's tooling reaches inside the extension-host webview automatically today, and nothing in VS Code's published extension-testing surface (`@vscode/test-cli`/`@vscode/test-electron`) is documented as exposing webview DOM content for inspection by an external scanner like axe — the webview guide makes no such claim, and this research found no VS Code doc asserting one. The honest answer, stated plainly per the brief's instruction: **nothing automated reaches inside the extension host webview as of 2026-08-29; the only gate available for `grimoire-vscode`'s marketplace panel and `vscode-ocx`'s webviews (it has none, confirmed — no `webview` entry in its `package.json`, no `webview` directory under `src/`) is static linting of the source that generates the HTML, and manual/screen-reader spot-checks — there is no mechanical, run-in-CI dynamic check for this surface.**

### 10. grimoire-vscode's actual stack is lit-html, not JSX

`grimoire-vscode/src/webview/render.ts` opens with its own docblock: *"lit-html renderers for both webviews... Interactive primitives are `@vscode-elements/elements` custom elements (vscode-button, vscode-textfield, vscode-single-select, vscode-badge, vscode-progress-bar); kind badges, chips, cards and menus are hand-styled per the design mockups."* The file imports `html`, `nothing`, `ifDefined`, `repeat`, and `unsafeHTML` from `lit-html` — this is template-literal-tagged HTML generation, not JSX and not a Vue SFC. `eslint-plugin-jsx-a11y` cannot attach here (no JSX syntax to analyze) and `eslint-plugin-vuejs-accessibility` is equally inapplicable.

The one tool actually shaped for this surface is `eslint-plugin-lit-a11y`, and it is itself aging: latest **`5.1.1`, published 2025-07-21T13:37:42Z** — over 13 months stale as of 2026-08-29 ([npm registry](https://registry.npmjs.org/eslint-plugin-lit-a11y)), depending on `eslint-plugin-lit@^2.0.0`, `axe-core@^4.3.3`, and `aria-query@^5.1.3`, peering on `eslint: >= 5`. It is the correct category of tool (AST-walks `html\`...\`` tagged templates the same way `jsx-a11y` walks JSX), but its own staleness means it should be evaluated, not assumed current, before being pointed at `grimoire-vscode`'s ESLint config (`eslint.config.mjs`, confirmed present, confirmed to carry no `a11y`/`jsx` rule references today).

## Normative guidance candidates

1. **Every ESLint-linted `.tsx`/`.jsx` file in a repo without Biome must have `eslint-plugin-jsx-a11y`'s recommended config in the active flat config.** *Rationale*: it is the only static a11y check available to React-shaped repos, costs no new runner, and needs no type-aware wiring. *Verify*: `grep -q "jsx-a11y" fma/eslint.config.js` (or the repo's config file) resolves, and `npx eslint . --rule-id-only 2>&1 | grep jsx-a11y` shows at least one active rule ID in a `--print-config` dump.

2. **A repo whose `lint` script invokes a binary not present in its own dependency tree is a broken gate, not a missing rule — fix the dependency before adding the plugin.** *Rationale*: `creeptd-ng/web`'s `"lint": "eslint src --ext .ts,.vue"` fails at "command not found" today; adding `vuejs-accessibility` to a config that never runs is theater. *Verify*: `pnpm --filter web exec eslint --version` (or the repo's package manager equivalent) must succeed before any a11y-plugin PR lands.

3. **Never add a new a11y ESLint plugin to a Biome-linted repo without first checking whether Biome's `a11y` group already covers the file type.** *Rationale*: `kate-middlechild` already gets 37 rules across JSX and (v2.4+) Astro/Vue/Svelte-embedded HTML from the linter it already runs on every commit. *Verify*: read the repo's `biome.json` for `linter.rules.preset` / `linter.rules.a11y`, and confirm the Biome version (`biome --version`) is `>=2.4.0` before assuming JSX-only coverage.

4. **A repo with an existing Playwright suite gates axe on `violations`, never on `incomplete`.** *Rationale*: `incomplete` is axe's own "needs a human" bucket (e.g. some `color-contrast` findings); asserting on it turns a legitimate ambiguity into a flaky red build. *Verify*: the spec must call `expect(results.violations).toEqual([])` (or equivalent), and must not assert emptiness on `results.incomplete`.

5. **Do not add `@axe-core/playwright` to a repo with no existing Playwright suite as part of closing this gap.** *Rationale*: for `fma`, that is a second test runner, not one new spec file — a materially larger decision than "add an a11y check," and out of scope for what this gap analysis can price honestly. *Verify*: `grep -q "@playwright/test" package.json` before proposing an axe spec; if absent, the static tier (jsx-a11y) is the whole ask for that repo.

6. **A VS Code webview gets a static-lint-only a11y gate; do not promise or attempt a dynamic/CI a11y check for extension-host content.** *Rationale*: the host provides no accessibility contract beyond two CSS hooks and no documented way for an external scanner to reach webview DOM content in CI. *Verify*: confirm no `@axe-core/*` or Lighthouse invocation targets a `vscode-webview://` URL anywhere in CI config — if one exists, it is not testing what it claims to.

7. **Match the a11y-lint tool to the actual template syntax, not the file extension.** *Rationale*: `grimoire-vscode`'s `.ts` webview files render `lit-html` tagged templates, not JSX — `jsx-a11y` has nothing to walk there. *Verify*: `grep -rl "from 'lit-html'" src/` (or the repo's webview source directory) before recommending `jsx-a11y`/`vuejs-accessibility` on any given file set; a lit-html hit routes to `eslint-plugin-lit-a11y` instead, after re-checking its staleness has not worsened.

## AI-agent angle

- **An agent asked to "add accessibility testing" defaults to Lighthouse/LHCI everywhere, including SPAs and webviews that structurally cannot run it the way `ocx-catalog` does.** LHCI needs a static-buildable, crawlable dist directory; `fma` and `creeptd-ng/web` are client-routed SPAs with dynamic canvas/WASM state, and a VS Code webview has no URL LHCI can even navigate to. **Mechanical check**: before an agent proposes an `.lighthouserc.cjs` in a new repo, `grep -q "staticDistDir\|url:" ` against the target repo's build output — if the repo has no static, crawlable HTML output (an SPA's `index.html` shell doesn't count), LHCI is the wrong tool and the PR should be rejected on sight.
- **An agent bolts `eslint-plugin-jsx-a11y` onto a file set that's actually lit-html or Vue templates because the file extension is `.ts`/`.tsx`-adjacent.** jsx-a11y silently does nothing on non-JSX syntax — no error, just zero rules ever firing, which looks like a clean pass instead of a non-check. **Mechanical check**: `grep -rl "from 'lit-html'\|<template>" src/` on the target files before trusting a jsx-a11y config addition; if either hits, the PR added a linter that will never fire.
- **An agent gates CI on `axe.incomplete` being empty, not just `axe.violations`.** This looks like the stricter, more thorough choice, but axe's own docs tag rules like `color-contrast` as `needs review` precisely because they are not reliably automatable — gating on `incomplete` manufactures flaky reds the tool's own author chose not to assert on. **Mechanical check**: `grep -n "incomplete" *.spec.ts` in any new axe-core Playwright spec — if `incomplete` appears in an `expect(...).toEqual([])`/`.toHaveLength(0)` assertion, reject it; it belongs in a report step, not a gate.
- **An agent recommends `eslint-plugin-jsx-a11y` v6's `strict` config wholesale on a first pass**, which is more aggressive than `recommended` and can red an otherwise-shipping component tree on day one, discouraging the team from keeping the check at all. **Mechanical check**: confirm the PR wires the `recommended` config specifically (`jsxA11y.flatConfigs.recommended`, not `.strict`) unless the repo has already cleared `recommended` cleanly — read the plugin's own config export name, don't assume "strict" is the safe default because it sounds more thorough.
- **An agent treats `@axe-core/playwright`'s peer requirement (`playwright-core >= 1.0.0`) as satisfied by any Playwright-adjacent dependency**, including `@playwright/test` alone, without checking that `playwright-core` itself resolves in the lockfile (it does transitively via `@playwright/test`, but an agent reasoning from `package.json` alone rather than the lockfile can get this wrong in a workspace with hoisting quirks). **Mechanical check**: `npm ls playwright-core` (or the package manager equivalent) actually resolves before assuming the peer dep is satisfied, rather than pattern-matching on `@playwright/test` being present.

## Contested / evolving

- **Whether Biome's `a11y` group should be treated as a full substitute for `jsx-a11y`/`vuejs-accessibility` or only a partial one is still moving, because Biome's HTML-embedded a11y rules are 6 months old (v2.4, 2026-02-10) as of this research** ([Biome v2.4 blog](https://biomejs.dev/blog/biome-v2-4/)). The direction is toward Biome closing the gap (more file-type coverage added, not less), but this research found no independent audit comparing Biome's 37-rule group's actual detection rate against `jsx-a11y`'s on the same corpus — the 1:1 rule-ID mapping the fleet's `lint-catalogue-sweep.md` already built is a naming-level correspondence, not a proven behavioral-equivalence claim.
- **Whether axe violations should hard-block CI or warn is genuinely unsettled in the wider ecosystem, not just this fleet** — Playwright's own accessibility-testing guide shows the blocking pattern (`expect(violations).toEqual([])`) as the canonical example but does not argue for it over a report-only mode; the guide's own suppression tooling (`disableRules`, `exclude`, violation-fingerprint snapshots) exists specifically because teams that start with a hard block frequently need an escape hatch once real violations accumulate on a codebase that predates the check. This research's position (block on `violations`, warn on `incomplete`) is the reasoned middle, not a documented industry consensus.
- **VS Code's webview accessibility story could change**: the product is actively developed, and a future release could add an accessibility-tree bridge or CI-testable hook for webview content that does not exist today. As of 2026-08-29, no such capability is documented in the webview guide or the extension-guidelines reference; this is a "nothing found," not a "confirmed absent forever" — worth re-checking on the next VS Code extension-API research pass rather than treated as permanently settled.
