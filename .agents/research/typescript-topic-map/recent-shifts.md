## Summary

- **Node 20 is EOL** (the fleet's stated floor). It went EOL 2026-03-24/2026-04-30 depending on source; the "Node ≥20" floor in the brief is already stale as of this research.
- **TypeScript went native.** TS 7.0 shipped stable 2026-07-08 as a Go port (`tsgo`), ~10x faster than 6.0. TS 6.0 (2026-03-23) was the *last* JS-based compiler release and quietly changed nine tsconfig defaults at once.
- **TS 7.0 has no stable programmatic API** — typescript-eslint, ts-morph, ts-jest and any tool that imports the TS compiler API cannot run on it yet (targeted for 7.1). An agent recommending "just upgrade to TS 7" for a typescript-eslint-heavy monorepo is wrong today.
- **Node runs TypeScript natively, no build step, on by default** — type stripping went default-on in Node 23.6/22.18, stable in 24.12/25.2, and the enabling flag was *removed entirely* in Node 26.0. Enums, non-type-only namespaces, parameter properties, and `import =` aliases still error unless `--experimental-transform-types` semantics are invoked (though that flag itself no longer exists in the 26.x doc tree the same way).
- **`erasableSyntaxOnly` (TS 5.8) is the TS-side complement** — it makes those Node-incompatible constructs compile errors so an agent doesn't emit code that works in `tsc` but crashes under `node file.ts`.
- **Corepack is gone from Node 25+.** The TSC voted 2025-03-19 to stop distributing it; Node 25.0.0 shipped without it. `npm install -g corepack` is now required. Any rule telling an agent "corepack is bundled with Node" is stale for the fleet's ≥24-and-up runtimes.
- **npm 12 flips the security defaults that made supply-chain worms possible**: `allowScripts` off by default, `--allow-git`/`--allow-remote` default to none. This directly addresses the class of attack (Shai-Hulud) that defined 2025.
- **Minimum release age / cooldown is now a standard defense**, not a niche idea: npm 11.10 (2026-02-18), pnpm 11.0 (2026-04-28, defaults to 1-day cooldown), Yarn 4.10, and Bun 1.3 all shipped it within a 12-month window, directly in response to the Shai-Hulud npm worm (Sept–Dec 2025).
- **Vite 8 replaced both Rollup and esbuild with Rolldown** (2026-03-12) — a single Rust bundler, not two. Advice to reach for esbuild-plugin patterns around Vite's dev server is stale.
- **tsdown (Rolldown-based) is displacing tsup** for library bundling; tsup remains larger by download count but is no longer the forward recommendation from the Vite/Rolldown team.
- **oxlint crossed from "fast subset" to "can replace ESLint for most projects"** with its JS-plugins alpha (2026-03-11): 650+ rules, runs existing ESLint plugins, ~80% of ESLint users reportedly can switch and have it "just work."
- **Biome's type-aware linting doesn't need `tsc`** and has grown past 500 rules (v2.5, 2026), closing much of the historical parity gap with typescript-eslint.
- **React 19 removed `forwardRef`'s necessity** (`ref` is now an ordinary prop) and tightened ref-callback typing so an implicit non-cleanup return is now a type error — an agent still writing `forwardRef` wrappers or implicit-return ref callbacks is emitting deprecated/broken patterns.
- **Stage-3 decorators are TS's default recommendation for new code**, but framework reality lags: NestJS and DI-heavy frameworks still require `experimentalDecorators` because Stage-3 decorators dropped parameter decorators outright.
- **ES2026 (including `using`/`await using`, Temporal, iterator helpers, `Promise.try`) reached final TC39 ratification 2026-06-30**, but most of these features had already been shipping in Node 22+ and evergreen browsers for months — the ratification date is not the "it works now" date.
- **Temporal is not yet universal**: shipped unflagged in Node 26 (2026-05-05) and in Chrome/Edge 144+/Firefox 139+, but Safari has not shipped it even in Technology Preview as of this research.
- **ESM-only is now the default recommendation for new libraries**, not dual-publishing — enabled by Node 22+'s stable `require(esm)`, meaning CJS consumers can still consume an ESM-only package.
- **`publint` and `@arethetypeswrong/cli --pack` are now considered baseline CI**, not optional extras, for anything published to npm.
- **AI-agent-specific measurement is thin and mostly secondary-sourced** — the strongest concrete claim found ("94% of LLM compile errors are type-related") traces to a Medium post citing unnamed academic work, not a paper this research could verify directly; treat it as directionally suggestive, not a citable statistic.

## Shifts by area

### 1. TypeScript releases

- **TS 5.5** (2024-06, per handbook) — inferred type predicates for boolean-returning functions whose runtime checks align with narrowing, letting many hand-written `is`-guards be deleted; `isolatedDeclarations` matured, requiring `declaration`/`composite` and enabling parallel `.d.ts` emission without cross-package analysis. [Announcing TypeScript 5.5](https://devblogs.microsoft.com/typescript/announcing-typescript-5-5/)
- **TS 5.8** (2025-02-28) — introduced `--erasableSyntaxOnly`, which errors on TS-only-runtime constructs (enums, namespaces with runtime code, parameter properties, `import =`), specifically to pair with Node 23.6's new `--experimental-strip-types`. Also added stable `--module node18` (disallows `require()` of ESM, unlike `nodenext`; permits deprecated `assert` import syntax) and support for `require()` of ESM files under `nodenext`, mirroring Node 22. [Announcing TypeScript 5.8](https://devblogs.microsoft.com/typescript/announcing-typescript-5-8/)
- **TS 5.9** (2025-08-01) — `import defer * as` for deferred module evaluation; expandable hovers in editors; `tsc --init` redesigned to emit a minimal config (`"module": "nodenext"`, `"target": "esnext"`, stricter defaults) instead of a verbose commented template; stable `--module node20` (models Node 20 behavior, implies `--target es2023`); `ArrayBuffer` is no longer a supertype of `TypedArray`s (a real breaking type change). [Announcing TypeScript 5.9](https://devblogs.microsoft.com/typescript/announcing-typescript-5-9/)
- **TS 6.0** (2026-03-23) — the **last JS-based compiler release**; changed nine tsconfig defaults simultaneously: `strict: true`, `module: esnext`, `target: es2025`, `noUncheckedSideEffectImports: true`, `libReplacement: false`, `rootDir` now `.` (tsconfig dir, not inferred), `types: []` (no auto `@types` enumeration). Deprecated/removed: `target: es5`, `--downlevelIteration`, `moduleResolution: node`(10) (deprecated) and `classic` (removed), `amd`/`umd`/`systemjs`/`none` module values (removed), `--baseUrl` as a resolution root (deprecated), `--outFile` (removed), legacy module-namespace syntax (now an error), `assert`-keyword import attributes (deprecated in favor of `with`). Shipped `--ts6-migration`, a syntax/config-only static-analysis pass (not a type-checker run) that reports what 6.0 broke, and `--stableTypeOrdering` to align diagnostics ordering with 7.0's deterministic algorithm (up to 25% perf cost; diagnostic-only, not for long-term use). [Announcing TypeScript 6.0](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/)
- **TS 7.0 beta** (2026-04-21) → **RC** (2026-06-18) → **stable 7.0.2** (2026-07-08) — the Go-native port (`typescript-go`/`tsgo`), ~10x faster than TS 6.0 (VS Code's own full type-check: 125.7s on TS 6 → 10.6s on TS 7, ~11.9x). Distributed as `@typescript/native-preview` during preview (latest nightly `7.0.0-dev.20260707.2` at time of research) and as the standard `typescript` package post-stable; the `tsgo` binary name now refers only to the bleeding-edge nightly channel. **No stable programmatic API** — typescript-eslint, ts-jest, ts-morph and template-type-checkers cannot run on it; that's targeted for 7.1. `rootDir` defaults to `./`, `types` defaults to `[]` (carrying 6.0's defaults forward). A `@typescript/typescript6` compatibility package lets 6.x tooling run alongside. [Announcing TypeScript 7.0 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0-beta/), [TypeScript 7.0 RC coverage](https://visualstudiomagazine.com/articles/2026/06/22/typescript-7-0-rc-moves-microsofts-go-rewrite-into-the-mainline-compiler.aspx)
- **`satisfies`** — mature and stable (introduced TS 4.9), combined with `as const` for self-documenting config objects that preserve literal types while enforcing shape. No further churn found in-window.
- **`const` type parameters** — no dedicated primary-source coverage surfaced in this pass beyond the 5.0 introduction already known; could not establish any 2024-09→2026-08 change beyond steady-state usage.

### 2. Node.js releases

- **Type stripping** (running `.ts` files without a build step): default-**on** since Node 22.18.0 / 23.6.0; reached **Stable** (stability 2) in Node 24.12.0 / 25.2.0; Node 26.0.0 removed the `--experimental-transform-types` flag entirely — it's now baseline behavior, disable with `--no-strip-types`. Erasable-syntax-only files run directly; enums, namespaces with runtime code, parameter properties, import aliases, and (Stage-3, un-polyfilled) decorators still error. [nodejs.org/api/typescript.html](https://nodejs.org/api/typescript.html)
- **`node:test` runner**: mature — assertions, mocks, coverage, watch mode, parallel execution built in; coverage support needs ≥18.15.0/≥20.1.0; JUnit reporter needs ≥21.0.0.
- **`require(esm)`**: stable in Node 22, ending much of the historical CJS/ESM interop pain.
- **Permission model**: Stable (stability 2) since Node 22.13.0 / 23.5.0. Note: `--env-file` and `--openssl-config` read files *before* environment/permission initialization, so they bypass the permission model's file-read restriction even when `--permission` is active — a real, easy-to-miss gap. [Node.js Permissions docs](https://nodejs.org/docs/latest-v22.x/api/permissions.html)
- **Corepack removed from Node 25+**: TSC vote 2025-03-19; remained (experimental) through Node 24; gone from Node 25.0.0 onward. Install via `npm install -g corepack` if needed. [Socket: Node.js TSC votes to stop distributing Corepack](https://socket.dev/blog/node-js-tsc-votes-to-stop-distributing-corepack)
- **LTS state as of 2026-08-29**: Node 20 — **EOL** (nodejs.org/en/about/eol lists it EOL, last-updated 2026-03-24; other sources cite 2026-04-30 as the hard EOL date — treat both as "already gone" for the fleet's stated ≥20 floor). Node 21/23/25 — EOL (odd releases never reach LTS; Node 25 went EOL ~2026-03/06, roughly six months after its October 2025 Current debut). Node 22 — **Maintenance LTS**, EOL 2027-04-30. Node 24 — **Active LTS**, EOL 2028-04-30. Node 26 — **Current** (released 2026-05-05), the eventual LTS line, EOL 2029-04-30 once promoted. [nodejs.org/en/about/eol](https://nodejs.org/en/about/eol)
- **Temporal**: unflagged/default in Node 26.0.0 (2026-05-05); required `--harmony-temporal` on Node 24. [Node.js 26 ships unflagged Temporal](https://lilting.ch/en/articles/nodejs-26-current-temporal-undici)

### 3. The ESM-only migration

- ESM-only is now the **recommended default for new libraries** in 2026, a reversal from the "always dual-publish" guidance that dominated 2022–2024 — enabled by Node 22+'s stable `require(esm)`, so CJS-only consumers can still pull in an ESM-only package.
- `publint` and `@arethetypeswrong/cli --pack` are treated as baseline CI steps (`npm pack` → `publint` → `attw --pack`) for any published package, catching `exports`-map and type-resolution mistakes npm's own `npm publish` doesn't catch.
- `publint` flags invalid dual-publish types resolution specifically: `.d.mts`/`.d.ts` under a `"type": "module"` package are read as ESM types; `.d.cjs`/`.d.ts` under a non-module package are read as CJS types — a common dual-publish authoring mistake.

### 4. Tooling churn

- **Biome**: v2.0 "Biotype" (2025-03) shipped the first type-aware linter that doesn't spawn `tsc` — it infers types itself, catching floating promises, misused `await`, unsafe member access. By v2.5 (2026), the rule count passed 500, with utility-type support (`Partial`/`Required`/`Readonly`/`Pick`/`Omit`) and a `--watch` mode across lint/format/check. [Biome v2.5](https://biomejs.dev/blog/biome-v2-5/), [Biome v2 "Biotype"](https://biomejs.dev/blog/biome-v2/)
- **oxlint/oxc**: rule count passed 650 by 2026-03; the JS-plugins alpha (2026-03-11) lets oxlint run **unmodified existing ESLint plugins**, closing the biggest adoption blocker. Benchmarked 4.8x faster than ESLint on Node.js's own repo (21s vs 1m43s), reportedly up to 16x on large TS/import-plugin-heavy codebases. Production users cited: Midjourney, Preact, PostHog, Outline, Actual. [Oxlint JS Plugins Alpha](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha.html)
- **Rolldown / Vite**: Vite 8.0 (2026-03-12) made Rolldown the **single, unified** bundler, replacing both Rollup (production) and esbuild (dev-server transforms) — not just "an option" as in Vite 6/7's `rolldown-vite` opt-in package. Reported gains: 10–30x on the Vite team's own 19,000-module benchmark (Rollup 40.10s → Rolldown 1.61s, ~25x); real adopters cited include Linear (46s→6s), Ramp (-57%), Mercedes-Benz.io (-38%), Beehiiv (-64%), GitLab (2.5min→40s, -100x memory), Excalidraw (22.9s→1.4s). Install size grew ~15MB (lightningcss + Rolldown). [Vite 8.0 announcement](https://vite.dev/blog/announcing-vite8)
- **Rspack**: 1.0 shipped 2024-08 as a near-drop-in webpack replacement; grew from 100K to 5M weekly downloads between 1.0 and 2.0, intentionally aligning APIs/defaults with webpack 5 for low-friction migration.
- **esbuild**: still pre-1.0 (0.28.1 as of this research), with no 1.0 planned — its dev-server role inside Vite is now superseded by Rolldown, though esbuild itself remains widely used standalone.
- **tsdown**: positioned by the Rolldown/Vite team as tsup's spiritual successor — Rolldown-powered, broader plugin support (Rolldown/Rollup/unplugin), built-in CSS/executable-bundling/workspace-mode/package-validation, with a dedicated tsup-migration tool. tsup still leads by raw download count (~6M/week vs tsdown's ~500K/week) but is no longer the forward recommendation. [tsdown FAQ](https://tsdown.dev/guide/faq)
- **Vitest**: 4.0 (2025-10-22) — Browser Mode graduated out of experimental; Browser Mode providers split into separate packages (`@vitest/browser-playwright`, `-webdriverio`, `-preview`); context import moved from `@vitest/browser/context` to `vitest/browser`; `basic` reporter removed. 4.1 (2026-03-12) added Vite 8 support. Vitest 5 is in active development (regular `vitest@5.0` prereleases as of this research) with no strict timeline, generally tracking Vite majors. [Vitest 4.0](https://vitest.dev/blog/vitest-4), [Vitest 4.1](https://vitest.dev/blog/vitest-4-1.html)

### 5. Runtime competition

- **Bun** (fleet-relevant: the GitHub Action runs on Bun): ~98% Node-API-surface compatibility measured against the top 1,000 npm packages as of 2026. The durable gap is architectural, not incremental: Bun uses JavaScriptCore, not V8, so native (compiled) addons are binary-incompatible; subtler gaps exist in `process.binding`/internal-module/cluster semantics affecting tools like PM2. `bun test` is Jest-syntax-compatible for the common API subset (one team: 200 tests, 1.2s under `bun test` vs 8s under Jest) but diverges on uncommon matchers/custom serializers/Jest-internals-dependent lifecycle hooks. `bun build` is described as production-viable for greenfield work in 2026; a "Bun for builds, Node for runtime" hybrid remains the lower-risk posture for teams with an on-call rotation and legacy compatibility needs.
- **Deno**: Deno 2 (late 2024) brought full Node/npm compatibility as the headline shift. Deno 3 pushed compatibility to 97% of the top-1000 npm packages (up from ~85% in Deno 2), added workspaces (monorepo support), full `node_modules` compatibility including native `.node` addons, and 30–40% faster cold starts via a V8-snapshot overhaul. State of JS 2025 puts backend runtime usage at ~90% Node, ~21% Bun, ~11% Deno — Deno remains a minority runtime despite the compatibility gains.

### 6. Package management & supply chain

- **The defining 2025–2026 supply-chain event is the Shai-Hulud npm worm.** V1 surfaced mid-September 2025 (patient zero: `rxnt-authentication@0.0.3`, published 2025-09-14), self-propagating via compromised maintainer credentials and postinstall hooks, stealing cloud tokens and re-publishing itself into every package the compromised maintainer owned. V2 ("The Second Coming") followed in November 2025, escalating to the **preinstall** hook (so even a failed install still executes the payload) and compromising 700+ packages plus 27,000+ malicious GitHub repos; reported contained by early December 2025, with variants continuing into 2026. This is the direct cause of the minimum-release-age wave below. [ReversingLabs: Shai-Hulud npm worm](https://www.reversinglabs.com/blog/shai-hulud-worm-npm), [Zscaler: Shai-Hulud V2](https://www.zscaler.com/blogs/security-research/shai-hulud-v2-poses-risk-npm-supply-chain)
- **Minimum release age / cooldown became a standard, near-simultaneous defense** across the ecosystem: npm CLI 11.10.0 (2026-02-18, `minimumReleaseAge`/`min-release-age` + bulk OIDC trusted-publishing config via `npm trust`); pnpm 11.0 (2026-04-28, `minimumReleaseAge` **defaults to 1440 minutes / 1 day**, plus `blockExoticSubdeps: true`, `strictDepBuilds: true`, `optimisticRepeatInstall: true`, `verifyDepsBeforeRun: install` — all opt-out, not opt-in); Yarn 4.10 (~2025-09, `npmMinimalAgeGate`); Bun 1.3 (2025-10, `minimumReleaseAge` in seconds). [Socket: npm minimumReleaseAge](https://socket.dev/blog/npm-introduces-minimumreleaseage-and-bulk-oidc-configuration), [pnpm 11.0](https://pnpm.io/blog/releases/11.0)
- **npm 12 (2026-07-29, v12.0.2)** flips install-time trust defaults: `allowScripts` off by default (no more automatic preinstall/install/postinstall execution), `--allow-git` defaults to none, `--allow-remote` defaults to none. These changes were exposed behind warnings starting npm 11.16 to give migration lead time. This is a direct, structural response to the postinstall/preinstall-hook attack vector Shai-Hulud exploited. [GitHub Changelog: npm v12 breaking changes](https://github.blog/changelog/2026-06-09-upcoming-breaking-changes-for-npm-v12/)
- **Provenance/attestation**: when publishing via trusted publishing (GitHub Actions/GitLab CI OIDC), npm now generates and publishes provenance attestations automatically — no `--provenance` flag needed.
- **Corepack**: see §2 — removed from Node 25+, install separately.

### 7. Frontend

- **React 19** (stable 2024-12-05): `ref` is now an ordinary prop on function components — `forwardRef` is no longer required and is slated for deprecation/removal; a codemod exists. The `use()` API reads promises (suspending until resolved) and reads context conditionally, including after early returns, but only accepts promises created/cached outside render. Ref-callback typing tightened: returning anything other than a cleanup function from a ref callback is now a **type error** (a real breaking change for existing code); a `no-implicit-ref-callback-return` codemod exists. As of this research, React sits at 19.2 (patch 19.2.7, ~2026-06) with **no React 20 announced**; React Compiler reached 1.0/stable separately (search-sourced, not independently primary-verified in this pass — flagged as lower confidence).
- **Vue**: Vue 3.6 beta reports Vapor Mode as feature-complete; Vue Language Tools 3.3.8 (2026-07) added Vapor-directive support. No further vue-tsc-specific breaking changes were found in-window beyond ongoing Options-API/external-module type-resolution bug reports (not a deliberate design change).

### 8. Standards landing in the language

- **`using` / `await using` (explicit resource management)**: TS support since 5.2; Node 22+ supports it natively; bundlers (Vite, webpack, esbuild) transpile for older targets. Reached **Stage 4** as part of the broader ES2026 batch, with final TC39 ratification of ECMAScript 2026 on **2026-06-30**. The ratification date lags actual runtime availability by roughly 18+ months — an important nuance for "is this safe to use" advice. [V8: JavaScript's New Superpower](https://v8.dev/features/explicit-resource-management)
- **Temporal**: Stage 4 as of **2026-03-11**. Browser support: Chrome/Edge 144+, Firefox 139+ (as of ~May 2026) — **Safari has not shipped it, not even in Technology Preview**, as of this research. Node: unflagged/default in Node 26.0.0 (2026-05-05); required `--harmony-temporal` on Node 24. [TC39 advances Temporal to Stage 4](https://socket.dev/blog/tc39-advances-temporal-to-stage-4), [Node.js 26 ships unflagged Temporal](https://lilting.ch/en/articles/nodejs-26-current-temporal-undici)
- **Decorators**: TS's default/recommended path is now the TC39 Stage-3 decorator design (`experimentalDecorators` off, absent from tsconfig). This is a genuinely incompatible design from legacy `experimentalDecorators`: different decorator arguments, different constructor-modification semantics, reversed execution order in some cases, and — significant for DI frameworks — **no parameter decorators** in the Stage-3 design. NestJS and similar DI-heavy frameworks still require `experimentalDecorators`/`emitDecoratorMetadata` until they migrate; this is a live compatibility fork, not a fully-resolved transition.
- **Iterator helpers, `Promise.try`, `Float16Array`, `Error.isError`**: bundled into the same ES2026 ratification; iterator helpers and `Promise.try` had already been shipping in Node 22+ and evergreen browsers for months prior to the June 2026 ratification. Could not independently verify `Error.isError`'s runtime-availability timeline beyond its inclusion in the ES2026 batch in this pass.
- **`satisfies`**: no material 2024-09→2026-08 change found; steady-state mature usage (introduced TS 4.9).

### 9. AI-agent-specific findings

- The strongest quantitative claim surfaced — "94% of LLM compilation errors are type-related" — traces to a Medium post attributing it to unnamed "ETH Zurich and UC Berkeley" research; this research pass could not independently verify a primary paper making that exact claim, so **treat it as directionally suggestive marketing-adjacent framing, not a citable statistic**.
- A Stack Overflow blog analysis (2026-01-28) reports AI-generated code shows roughly 2x the concurrency/dependency-ordering error rate and ~2.7x the readability/formatting/naming-consistency issues of human-written code — a more concretely sourced, if still secondary, data point.
- An arXiv survey, "A Survey of Vibe Coding with Large Language Models" (arXiv:2510.12399, 2025-10), exists as a broader academic touchpoint on LLM-driven coding failure modes; this pass did not deep-read it for TypeScript-specific findings — flagged as a candidate for a follow-up research pass, not consumed here.
- No primary-sourced, TypeScript-specific "coding agent configuration" study (e.g., a benchmark of agents against a fixed TS ruleset) was found in this window. **Could not establish** a rigorous, TS-specific measurement of what agents get wrong beyond the general type-error and readability findings above.

## Still true

- `satisfies` for config-shaped literals combined with `as const` — unchanged, still the correct pattern.
- `nodenext` module resolution as the correct choice for anything running on Node (as opposed to `bundler` for bundler-consumed code) — reinforced, not contradicted, by TS 5.9's `tsc --init` defaults and TS 6.0's tightened resolution modes.
- `isolatedDeclarations` as the right lever for fast, parallel, cross-package-analysis-free `.d.ts` emission in a monorepo — unchanged since TS 5.5, still current guidance.
- Node's built-in `node:test` runner as a legitimate, low-dependency choice for unit tests — unchanged; still lacks some ergonomics teams get from Vitest, but the core runner/mocks/coverage/watch story is stable and mature.
- `@arethetypeswrong/cli` + `publint` as the correct pre-publish validation pair — unchanged in role, only grown in how load-bearing/"baseline" they're treated as.
- Bun's fundamental architectural gap (JavaScriptCore vs. V8 → native addon incompatibility) — a 2023-era observation that remains true in 2026; not something incremental compatibility work has closed or will close.
- React's Server Components / Actions model from React 19 — no reversal found; 19.x continues to build on it through 19.2.
