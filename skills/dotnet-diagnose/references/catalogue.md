## How to read a row

Find the row by its code, then match the first line, which is abridged with
`...` and carries no machine paths. Apply the fix, capture again and read the
verification count. A fix is proved by a zero count of its code (CS-CORE-03).
An exit status alone proves nothing (DN-RULE-07).

The captures every Verification cell reads. Each is the DN-RULE-01 form: a
wall-clock bound, all output in a file, the exit status printed. The knobs are
`--tl:off --interactive false -nologo` on `restore`, `build`, `publish`, `pack`
and `clean` only, plus `--disable-build-servers` on `restore`, `build` and `publish`
(DN-RULE-10), and never any of them on `dotnet test` (DN-RULE-02, CS-BUILD-30; an MTP project turns each into exit 5, a VSTest project rejects `--interactive false` with MSB1001).

```sh
timeout 900 dotnet restore "$SLN" --force --tl:off --interactive false --disable-build-servers -nologo -v:q > restore.log 2>&1; echo $?
timeout 900 dotnet build "$SLN" --no-incremental --tl:off --interactive false --disable-build-servers -nologo -v:q > build.log 2>&1; echo $?
timeout 900 dotnet build "$SLN" -c Release --tl:off --interactive false --disable-build-servers -nologo -v:q > build.log 2>&1; echo $?    # pack --no-build needs a Release build
timeout 900 dotnet pack "${PKG:?MISSING PKG}" -c Release --no-build --tl:off --interactive false -nologo -v:q > pack.log 2>&1; echo $?    # PKG is the packable project file, never the .slnx (CS-BUILD-29)
timeout 900 dotnet publish "$APP" -c Release -f "$TFM" --tl:off --interactive false --disable-build-servers -nologo -v:q > publish.log 2>&1; echo $?
timeout 900 dotnet test "$SLN" --no-build > test.log 2>&1; echo $?    # build first, in the same job
```

`SLN` is the one solution or project file the repository builds, `R` the repository root and
`APP` and `TFM` the application and framework to publish (stage 6 only, a library has none,
DN-DIAG-76). All are set in `SKILL.md` (Capture), which also prints `MISSING SLN` when neither the
repository's name nor a `global.json` neighbour names one file and runs every capture from the folder of the nearest `global.json`.
Pass `SLN` on every capture: a bare command stops at MSB1003 or MSB1011 (DN-DIAG-33, DN-DIAG-73).
The empty-packages capture, used by every restore fix (DN-RULE-05), puts the folder on the
working disk and removes it after the capture, because an empty-folder restore writes 0.5 to
2 GB on the four round trees (`du -sh "$P"` prints it per tree). `--no-http-cache` is part of the
capture: the HTTP cache keeps a dead feed's index and its packages, so an empty `--packages` folder
restored green with the network down (0 NU1301) and gave NU1301 only with the flag:

```sh
P=$(mktemp -d "$(dirname "$R")/.pkgs.XXXXXX")
timeout 900 dotnet restore "$SLN" --force --no-http-cache --packages "$P" --tl:off --interactive false --disable-build-servers -nologo -v:q > restore.log 2>&1; echo $?
```

Read `restore.log` (the Verification cell) while the folder exists, then run `rm -rf "$P"` and
a plain `timeout 900 dotnet restore "$SLN" --tl:off --interactive false --disable-build-servers -nologo -v:q > again.log 2>&1; echo $?`,
which must print `0`. Without that last restore `obj` points at the removed folder:
`dotnet build --no-restore` exits 1 with NETSDK1064 and `dotnet test --no-build` exits 0 and runs
no test (measured).

The stage captures build in Debug. `pack` and `publish` run in Release, and the
gate is Release (CS-BUILD-16), so a Debug build before `pack --no-build` fails
with NU5026 and reads `0` for NU5104 whatever the tree holds. The commands
assume Linux or macOS with GNU `timeout`, `ps -eo etimes`, `pgrep` and
`mktemp -d`; on Windows run them in WSL or Git Bash.

- **Count form.** `grep -c -e CODE restore.log` prints the number of lines
  that carry the code. `grep` exits 1 when that count is `0`, so read the
  printed number, not the exit status. It counts lines, and SDK 10.0.401 prints
  most diagnostics twice, so compare zero against non-zero, never an exact number.
- **A code-less row** (Code `none`, first line `error :`) is counted by its message:
  `grep -c -e 'invalid digest' build.log`. The `error :` shape has a space before the
  colon, so a count of `error CODE:` lines reads 0 while the build is red.
- **A restore fix** is proved with a packages folder that starts empty, so a warm
  cache cannot mask a dead source (DN-RULE-05).
- **The number in parentheses after a code** is the count of tracker issues for
  it over the 12 months to 2026-10-11. It ranks the codes, nothing else.
- **Era tags.** `all` means the same on SDK 8.0.425 and 10.0.401. `net10` is
  new or changed in .NET 10 or SDK 10. `net8-SDK` appears only when SDK 8
  drives the build. `ns2.0` appears only on netstandard2.0. `net11-RC1` was
  measured on 11.0.100-rc.1.26425.128; re-measure at GA in November 2026.
- **Not rows.** CS8602, CS9035, CS4014 and NETSDK1083 are ordinary compiler
  and RID errors that need no catalogue entry.
- **Retired.** DN-DIAG-20, DN-DIAG-21, DN-DIAG-28, DN-DIAG-32 and DN-DIAG-65 are retired, not reused: the NU1302, NU1504, NETSDK1004 and NETSDK1100 messages name their own fix, and the ANSI row repeated the Capture paragraph.
- **Held-out additions.** DN-DIAG-67 to DN-DIAG-79 came from failures of the host or the
  checkout on unplanted trees (three rounds, 2026-10-11), not from planted breakage.
