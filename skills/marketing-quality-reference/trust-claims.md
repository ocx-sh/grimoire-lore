# Trust Claims, Licence, Security and Endorsements

Owns the rules for claims that borrow trust: "open source" and "free", security and compliance wording, who may sign off a sensitive class, and everything that quotes, names or counts other people (testimonials, logos, badges, ratings, reviews, adopters, stars, analyst placements). The evidence record, its schema, the lint and the rows for figures, rewrites, prices, comparisons and AI capability are in `claims.md`. This file uses that file's record and its lint checks A to E.

The rules apply to a copy surface as `claims.md` defines it. Docs body pages keep DOC-TYPE-15 (adoption-claim links) from `docs-quality`. Platform-specific review-site terms (one site's incentive cap and AI-drafting rule from 2026-11-04, another's caps) belong to the channel skills. This file only requires that a badge or rating have a record.

## Licence and Openness

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| MKT-CLAIM-11 | Write "open source" about a component only when every option of its SPDX expression has `isOsiApproved: true` in the SPDX `licenses.json` fetched on this run. Otherwise write "source-available under ID", or "fair source" with the conversion date for a delayed-open licence. For a mixed expression, name each option's class. For open core, name which components carry which licence. For a model, write "open weights under ID" unless all three OSAID 1.0 items are released (data information, complete code, parameters). "OSI Approved", the OSI logo and "Open Source Initiative" need the owner's approval. | The OSI board's position is in the table above. BUSL-1.1, SSPL-1.0 and Elastic-2.0 are not OSI-approved, and the SPDX id `Fair` is OSI-approved and is not "fair source". A licence described from pre-relicensing memory is wrong: three well-known products changed licence between 2021 and 2025. | Fetch the JSON with `curl -sL https://spdx.org/licenses/licenses.json`. A script reads the manifest expression (Cargo `[package]` and `[workspace.package]`) and fails when copy matching `open[- ]source` sits in a repository where any option is not approved. | MUST |
| MKT-CLAIM-12 | Keep the licence identical everywhere it is stated: the LICENSE file, every manifest field (`license` in Cargo including `[workspace.package]`, `package.json`, `pyproject.toml` `project.license`, the OCI annotation `org.opencontainers.image.licenses`), the README licence line, and the `license:` frontmatter of published artifacts. Use a current, non-deprecated SPDX id. A repository that names a licence anywhere has a LICENSE file. | The SPDX id is the one machine-checkable licence claim. Cargo and npm deprecate the `/` separator and object-style licences ([Cargo manifest](https://doc.rust-lang.org/cargo/reference/manifest.html#the-license-and-license-file-fields), [npm package.json](https://docs.npmjs.com/cli/v10/configuring-npm/package-json#license)). A checker that reads only Cargo's `[package]` reports "no licence" for a workspace. | See block MKT-CLAIM-12. A LICENSE file exists whenever the first command prints anything. All extracted ids are equal. `isDeprecatedLicenseId` is false for each id in the fetched list. Measured on 14 repositories: 14 LICENSE files, 0 disagreements with the manifests. A repository that publishes 75 artifacts with `license: Apache-2.0` and has no LICENSE file is the violation this rule catches. | MUST |
| MKT-CLAIM-13 | Write "free" only with its meaning in the same sentence: "free of charge" plus its scope, a named plan limit, or a licence id. Never put "free" or "open source" next to a feature that is gated, trial-limited or only in a paid edition. A bare "free" in a headline is allowed only when the limit or the paid boundary is on the same screen. | The FTC "Free" guide requires terms "clearly and conspicuously at the outset", and an asterisked footnote is not enough. Applying it to free tiers is an inference. | See block MKT-CLAIM-13. Every `free` hit on a copy surface ("dependency-free" is skipped) is covered in the same sentence by one of three things: a `claim:ID` marker that resolves to a live `price-or-limit` row; an SPDX id from the fetched `licenses.json`; or a named limit, meaning a number with a unit (`[0-9]+[- ]?(day\|month\|year)s?`, or a number, optionally followed by "free", before `GB`, `MB`, `TB`, `requests`, `seats`, `users`, `projects`, `builds`, `minutes`, `hours`, `events` or `members`). The words "plan", "tier" and "trial" alone do not cover it, so "Free plan" with no limit fails. A headline hit also needs the covering row's `claim` inside the same `<section>` of the built HTML. For each feature named next to "free", the row's edition is not a paid one. Measured on 26 exemplar pages: 54 hits, 4 covered ("100 free projects", "30-day free trial", "2 months free", "Vite is MIT Licensed and will always be free") and 50 not; 6 of the 50 are not the price sense (a calendar sentence) and take an `[[allow]]` entry that check E accepts after its sense test. A sentence split across extracted lines undercounts coverage. | MUST |

```sh
# MKT-CLAIM-12: a licence is named somewhere. Any output means LICENSE* must exist.
git ls-files -z --cached --others --exclude-standard -- 'README.md' 'Cargo.toml' 'package.json' 'pyproject.toml' ':(glob)**/*.md' \
  | xargs -0 -r grep -l -E -e '^license:' -e '"license"' -e '^license *=' --
# MKT-CLAIM-12: the LICENSE file exists on disk. Empty output is the finding. A tracked file deleted from the tree is not listed, and LICENSE-THIRD-PARTY* never counts.
git ls-files -z --cached --others --exclude-standard -- 'LICENSE*' 'COPYING*' \
  | xargs -0 -r ls -d -- 2>/dev/null | grep -v -i -E -e 'third[-_]?party'
```

```sh
# MKT-CLAIM-13: every free hit on a copy surface. Read each line against the three covers in the rule. "dependency-free" never matches.
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.md' ':(glob)**/*.mdx' ':(glob)**/*.astro' ':(glob)**/*.html' \
  | xargs -0 -r grep -H -n -i -E -e '(^|[^A-Za-z0-9-])free([^A-Za-z0-9-]|$)' --
```

For a SOC report, state the type, the period, the examiner and the access route. An agent never writes `source`, `window`, `observed` or `value` on these rows. Whether two products "meet the same needs", and whether a party is a competitor at all, are legal judgements that need the real market (Directive 2006/114/EC Art. 4(b), 2(c)). | `CODEOWNERS` lists `/claims.toml`, and branch protection requires a code-owner review. ## Endorsements and Proof

An agent never creates an endorsement. Every quote, logo, badge, rating and adopter name resolves to a record that holds the person or organisation, the exact words, the capture date, the permission and the connection status. For an individual's testimonial, 16 CFR 465.2(a) names writing or creating a fake one an unfair or deceptive act. An organisation's quote, logo or adopter name is outside the Part 465 testimonial sections and falls under Section 5 and the Endorsement Guides. The EU (UCPD Annex I points 23b and 23c) and the UK (DMCC Act 2024 Schedule 20 paragraph 13, CAP Code 3.44 to 3.52) list the same fabrication as unfair in all circumstances.

An `endorsement` row adds these fields to the common ones: `kind`, `who`, `said_where`, `captured`, `original_ref`, `edits`, `permission`, `permission_ref`, `contact_ref`, `connection`, `disclosure_text`, `typical_result`, and `verification_method` where the page says reviews are checked. `permission_ref` points to where the owner keeps the evidence, and the message itself never enters a public repository. `approved_by` is required. A `licence` row adds `spdx_expression` and `spdx_list_version` and never stores an `osi_approved` value, because the check derives it from the list on every run. A `security-attestation` row adds `examiner` and `access_route`. An `accolade` row's `source_type` is `third-party-study` or `platform-doc`.

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| MKT-CLAIM-20 | Never write a quote, a name with a role, a rating, a review, a testimonial, a customer logo, a review-site badge or an adopter name unless an `endorsement` record backs it. Never generate one, never write a composite, and never draft review text for a customer to sign. A blank list of questions is allowed. A persona appears only under a heading labelled "Persona", without quotation marks. An adopter name needs a self-added pull request or a written permission. Dependency graphs, lockfiles and download counts are evidence of use, not consent. If the page states or implies that reviews come from people who used or bought the product ("verified", "real customers", "from users"), the same page states whether and how that is checked, and the row holds `verification_method`. Never write that reviews come from real customers without one. A badge row (`kind = "badge"`) holds `permission_ref` as `PARTY: POINTER`, where the pointer is a URL or a repository path that exists. | 465.2(a) bars writing or creating a consumer testimonial that misrepresents the individual's existence or experience. It reaches quotes from individuals, and by inference individuals who use the product at work. An organisation's endorsement is under Section 5 and 255.4(a), which requires it to reflect "the collective judgment of the organization". "AI-generated reviews are covered by the final rule" (Federal Register 2024-08-22, fn. 35). "The name or seal of an organization can be endorsements" (255.0(b)). EU Annex I point 23b makes it unfair in all circumstances to state that reviews come from consumers who used or bought the product "without taking reasonable and proportionate steps to check"; point 23c bars submitting or commissioning false reviews and "misrepresenting consumer reviews or social endorsements" (B2C only, Art. 3(1)). UK DMCC Schedule 20 paragraph 13 bars a review that "purports to be, but is not, based on a person's genuine experience", and CAP 3.52 bars a "trust mark, quality mark or equivalent without the necessary authorisation". | See block MKT-CLAIM-20. Every hit carries `data-proof="ID"` or a `claim:` marker that resolves to an `endorsement` row whose `permission.type` is `written` or `public-statement`. So does every line that is only an `@handle` or ends `@handle on X`, the author line of a social-post testimonial: on 26 exemplar pages that pattern found 21 author lines where the `<blockquote>` pattern found 1, and on the 17 measured repositories 0. Every hit of the review-checking words resolves to an `endorsement` row with a non-empty `verification_method`, and the same page carries a sentence matching `checked`, `verified by` or `we confirm`. Measured: 0 repository lines and 1 false exemplar line. Badge rows pass check A. | MUST |
| MKT-CLAIM-21 | Use quotation marks only for the endorser's exact words. List every cut in `edits`, and show it on the page as an ellipsis. Of 8 exemplar landing pages with quotes, 0 dated any of them, which is the base rate an agent copies. It cannot tell whether a pointer resolves in the owner's store. | MUST |
| MKT-CLAIM-22 | When any `connection` field is true (paid, free product or discount, employee, contractor or agent, family, investor, partner or referral fee, early access or prize), state the connection in the same element as the endorsement. It must be visible without a click or hover and be in the endorsement's language. Use the wording "Paid testimonial", "NAME works for COMPANY", "NAME is an investor in COMPANY", "NAME received PRODUCT free of charge" or "NAME had early access to PRODUCT". A footer, a tooltip, a `<details>` element or a link to a disclosure page does not count. | On the internet a disclosure "must be unavoidable" and is "not clear and conspicuous if a consumer must take any action, such as clicking" (465.1(c)). 255.5(a) requires that the disclosure "clearly communicate the nature of the connection". The UK bars a review that "conceals the fact it has been incentivised" (Schedule 20 paragraph 13(1)(b)), and CAP 3.45 requires making clear where reviews were incentivised. | The page check finds `disclosure_text` inside the element with `data-proof`, and the disclosure is not inside `hidden`, `details`, a `title=` value or an `aria-describedby` target alone. The wording matches the list. | MUST |
| MKT-CLAIM-23 | Label a page "case study", "results" or "proof" only when its record holds a baseline, an outcome, a period, a method, a unit and a denominator. Every other page is a "customer story". Every result figure has a sentence beside it stating the generally expected result, unless `typical_result = true` is substantiated. | A result figure implies it is typical (255.2(b)). Of 15 exemplar case studies, 2 give both a before and an after value and 0 give a method (vendor data, measured 2026-11-27). | See block MKT-CLAIM-23: each page listed resolves to a record with all six fields, and each numeric result has a sibling "Typical result" sentence or a record link. | MUST |
| MKT-CLAIM-24 | Show a third-party popularity count (stars, downloads, dependents, followers) only as the number, a link to its source and the retrieval date. Never present it as a customer or adopter list. Never buy one, and never trade one ("star for star"). | 465.8(b) makes it unlawful to "purchase or procure fake indicators of social media influence", and 465.1(h) defines fake indicators to include those that "otherwise do not reflect a real individual's or entity's activities, opinions, findings, or experiences". Buying is in the text. Reading a traded star as one that does not reflect an opinion is an inference. Plainly asking readers for a star is not reached by Part 465, and whether a platform allows it is a platform term for the channel skills. 465.8(b) speaks of influence misrepresented "for a commercial purpose", and 255.0 Example 13 names "potential clients, purchasers, investors, partners", so the bar reaches a count shown to business buyers. EU recital 49 of Directive 2019/2161 names fake social "likes", and a star average or a review count is "consumer review information" under DMCC Schedule 20 paragraph 13(5). Platform counts change daily, so the retrieval date is shown. | Each count hit sits within one element of an `<a href>` to the platform API or page and a `<time>`. Block MKT-CLAIM-24 prints nothing over every copy surface plus `CONTRIBUTING.md` and `.github/`, and its canary prints a line when the file list is empty, so the check cannot pass on no input. | MUST |
| MKT-CLAIM-25 | Send a review or testimonial request to every member of a defined set (all customers in a period, all users of a version), never filtered by score, NPS or sentiment. | The conservative reading of an unsettled point. The consumer reviews preamble says requests "made only to customers whom the business believes to be happy customers would not be 'generalized solicitations'". The FTC Q&A says the practice does not violate a specific Part 465 prohibition but "could still violate the FTC Act". Both point the same way, and neither makes it a clear breach. | The request automation has no condition on `score`, `nps`, `rating` or `sentiment` (reading check). Unverified: reading heuristic. | SHOULD |
| MKT-CLAIM-26 | Tie no incentive for a review to its rating or sentiment, in words or by implication. The EU and UK agree: recital 49 names "publishing only positive reviews and deleting the negative ones", CAP 3.46 names it as misleading, and the CMA says not to offer "inducements (money or gifts) to customers to write positive reviews". | The incentive text contains none of `rating`, `stars`, `positive`, `5-star`, `five-star` or `good review`. ## Documented Gaps

- **Part 465 and business-to-business testimonials.** Settled: an endorsement by an entity is outside every Part 465 testimonial section, and 465.6 is the only section that reaches entities. 465.8(b) reaches fake influence indicators used "for a commercial purpose", so it reaches business buyers. Inferred only: a named individual's quote about a product used at work is a consumer testimonial under 465.1(f). No FTC statement, Q&A entry or case says so. The rule text, the 400,590-byte preamble, the Q&A page and two web searches have no B2B passage, and no legal database was searched. MKT-CLAIM-20 stays MUST for both kinds of speaker, because Section 5 and 16 CFR 255.1 and 255.4 reach an organisation's endorsement.
- **UK reach.** Not determined: whether DMCC Part 3 reaches an overseas trader, whether "turnover" in s.182 is global, whether the CAP Code covers B2B developer-tool claims, whether DMCC names AI-generated reviews expressly, and what the CMA means by "reasonable and proportionate steps". Settled: a paragraph 13 breach is not a s.237 criminal offence (s.237(8)(b)).
- **Review-site terms.** The channel skills own them.
- **Accolades.** Whether a placement may be quoted at all, or only with a licensed reprint, is not decided.
- **Sign-off identity.** Only a review from a second account separates the owner from an agent that acts as the owner. The check in MKT-CLAIM-16 cannot pass until the owner supplies one.

What an agent must ask a human, from this file: whether the organisation holds a SOC report or an ISO certificate, and its period, examiner, scope and access route; any statement that a product is compliant with a law, and the AI Act Art. 50 position for an AI feature or for agent-written public text; any response-time, SLA, uptime, support or bounty promise; choosing, changing or adding a licence, including adding a missing LICENSE file; using the OSI logo or the "OSI Approved" mark; every endorsement (asking for permission, accepting a quote from an employee, founder, investor or relative, deciding whether a connection is "reasonably expected", displaying a logo or badge whose licence terms the agent could not read, offering a review incentive, naming an adopter found only in public data); whether to cite an analyst placement at all; whether to call a product "stable", "production-ready" or "1.0", which is a release decision; and whether a law row the agent re-fetched still applies.

## What Agents Get Wrong Here

1. **Inventing proof.** A testimonial, a persona with a name and role, a "Trusted by teams at ..." line from memory or from a dependency graph, "verified reviews from real customers" over quotes nobody checked (MKT-CLAIM-20, 24). An analyst placement from memory (MKT-CLAIM-31).
2. **Copying compliance vocabulary.** "SOC 2 certified" or "GDPR compliant" in the style of well-known vendors (MKT-CLAIM-14). "Compliant" for one component, read as the whole service. A legal obligation sold as a feature.
3. **Licence from memory.** "Open source" for an open-core or source-available product, the SPDX id `Fair` read as "fair source", a deprecated id such as `GPL-3.0` or `MIT/Apache-2.0` copied into a manifest, a checker that reads only Cargo's `[package]` (MKT-CLAIM-11, 12).
4. **"Free" in the hero with the paid tier below the fold** (MKT-CLAIM-13).
5. **Paraphrasing inside quotation marks.** A customer's words reworded and still quoted, with no capture date (MKT-CLAIM-21). A disclosure moved into a tooltip, a `<details>` element or a footer (MKT-CLAIM-22).
6. **Backing a number with a quote**, and a "case study" with a percentage and no base (MKT-CLAIM-23, 28).
7. **Gaming sign-off.** Typing `approved_by`, relying on a commit signature, or labelling a commercial party `open-source` to skip review (MKT-CLAIM-16).
8. **Deleting the honest negative.** "No third-party audit" and "reviews are not checked" read badly, so they get cut. That rule is MKT-CLAIM-10 in `claims.md`.
