# Interface Text, Errors, Labels and Strings

Owns every string a running product shows a person: CLI prose, VS Code notifications, command titles and setting descriptions, web and webview labels, status messages and alt text. Documentation prose is out (the docs quality set owns it). UX-TEXT-05, 07, 12 and 23 are the terminal-output rows and live in the `ux-cli` skill, with the `error:`, `note:` and `help:` shape that UX-TEXT-02, 08, 09 and 31 below rely on. Where the error appears on the page, and whether input is kept, are UX-STATE-23 to 25 (`forms.md`). Did-you-mean presence and candidate count are `ux-cli`'s. The announcement mechanism for a status string is UX-A11Y-22 to 24, and the words are UX-TEXT-30. Machine-readable errors are `ux-agent-interfaces`'.

## Source Lists and the Scanner

"UI string paths" means the files whose literals reach a user: CLI `Display` text and print calls, VS Code `show*Message` calls and `package.json` `contributes`, web and webview text nodes and `alt`, `title`, `aria-label` and `placeholder` attributes. Tests, panics and comments are out. No extractor separates them perfectly: Rust `format!` calls have no known destination without data-flow analysis (43% of one CLI's string positions and 62% of another's), so every pattern below lists candidates and a reader decides. A grep over an empty list prints nothing and reads as a pass, so run the canary first. `$CHECKS` is `.claude/skills/ux-quality-reference/checks` (`$CLAUDE_CONFIG_DIR/skills/ux-quality-reference/checks` when installed globally). `$SNAP` is the directory of the bad-invocation snapshot corpus that UX-TEXT-05 requires: one rendered diagnostic per `.txt` file. `$CLI` is the built binary and `$NAME` its name.

`text_scan.py` has one arm per pattern. `--arm all` runs every arm. It prints `path:line: [arm] text` and exits 1 on a hit. `python3 -I "$CHECKS"/text_scan.py --self-test` proves each arm still hits its planted violation and stays silent on the clean twin. A hit is a candidate: read it, then fix it or name why it is harmless (a comment, a test, a quoted example).

```sh
# canary: any output means the UI string list is empty
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.tsx' ':(glob)**/*.jsx' ':(glob)**/*.vue' ':(glob)**/*.svelte' ':(glob)**/*.astro' ':(glob)**/*.html' ':(glob)**/*.rs' ':(glob)**/*.go' ':(glob)**/*.py' ':(exclude,glob)**/*test*' ':(exclude,glob)**/*spec*' \
  | tr '\0' '\n' | awk 'END { if (NR == 0) print "canary: nothing listed" }'
```

## Errors and Warnings

```sh
# UX-TEXT-03, 17 (MUST), 20, 25, 28, 30: the MUST arms. Any hit is read, then fixed or explained
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.tsx' ':(glob)**/*.jsx' ':(glob)**/*.vue' ':(glob)**/*.svelte' ':(glob)**/*.astro' ':(glob)**/*.html' ':(glob)**/*.rs' ':(glob)**/*.go' ':(glob)**/*.py' ':(exclude,glob)**/*test*' ':(exclude,glob)**/*spec*' \
  | xargs -0 -r python3 -I "$CHECKS"/text_scan.py --arm generic --arm emoji --arm interjection --arm img-alt --arm plural-s --arm bytes --arm status --
# UX-TEXT-20 in Markdown and MDX: empty alt and HTML img tags in READMEs and docs
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.md' ':(glob)**/*.mdx' \
  | xargs -0 -r python3 -I "$CHECKS"/text_scan.py --arm img-alt --
# UX-TEXT-03: a raw exception message relayed as the toast
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.tsx' ':(exclude,glob)**/*test*' \
  | xargs -0 -r grep -H -n -E -e 'show(Error|Warning)Message\([^)]*(^|[^[:alnum:]_])(e|err|error)[.]message' --
# UX-TEXT-02: snapshots whose last non-blank line is not a help: line; each must carry a note: line that says what the product did
git ls-files -z -- "$SNAP" | xargs -0 -r awk 'FNR == 1 && NR > 1 && last !~ /^help: / { print name } FNR == 1 { name = FILENAME; last = "" } NF { last = $0 } END { if (NR > 0 && last !~ /^help: /) print name }'
# UX-TEXT-02: GUI failure sites. Every message call, then the wrappers that pass their first parameter into one; read each site
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.tsx' ':(exclude,glob)**/*test*' \
  | xargs -0 -r grep -H -n -E -e 'show(Error|Warning)Message\(' --
# UX-TEXT-04: commands written as run `...`; each MISSING line is a suggestion the CLI's own parser rejects
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.rs' ':(glob)**/*.go' ':(glob)**/*.py' ':(glob)**/*.ts' ':(exclude,glob)**/*test*' \
  | xargs -0 -r grep -h -o -E -e 'run `[^`]+`' -- \
  | sed -e 's/^run `//' -e 's/`$//' -e 's/[ ]*[{<].*$//' -e "s/^$NAME //" | sort -u \
  | while read -r c; do "$CLI" $c --help >/dev/null 2>&1 || echo "MISSING: $c"; done
# UX-TEXT-06: a question where a statement belongs; each hit is followed in code by a prompt call
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.rs' ':(glob)**/*.go' ':(glob)**/*.py' ':(exclude,glob)**/*test*' \
  | xargs -0 -r python3 -I "$CHECKS"/text_scan.py --arm did-you-mean --
# UX-TEXT-08: candidates only. A line repeated in one snapshot, or a path printed twice in one line
git ls-files -z -- "$SNAP" | xargs -0 -r awk 'FNR == 1 { delete line } { t = $0; sub(/^[A-Za-z]+:? */, "", t) } length(t) >= 30 && line[t]++ == 1 { print FILENAME ": repeated line: " t } { n = split($0, w, "[^[:alnum:]/._-]+"); delete seen; for (i = 1; i <= n; i++) if (index(w[i], "/") && length(w[i]) >= 5 && seen[w[i]]++ == 1) { print FILENAME ": path twice in one line: " w[i]; break } }'
# UX-TEXT-08: TypeScript gate, listing. Message calls with no button argument; each needs a log call in its function, or is the declared sink
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(exclude,glob)**/*test*' \
  | xargs -0 -r grep -H -n -E -e 'show(Error|Warning)Message\([^,]*\)' --
# UX-TEXT-09: a success-shaped line before the first error: line of a failing-path snapshot
git ls-files -z -- "$SNAP" | xargs -0 -r awk 'FNR == 1 { done = 0 } /^error: / { done = 1 } !done && /(Created|Removed|Removing|Installed|Installing|Added|Adding)/ { print FILENAME ": " $0 }'
# UX-TEXT-10: warnings, deprecations and info lines that may reach stderr; read each
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.rs' ':(glob)**/*.go' ':(glob)**/*.py' ':(glob)**/*.ts' ':(exclude,glob)**/*test*' \
  | xargs -0 -r grep -H -n -i -E -e 'deprecat' -e 'is renamed' -e 'log::info!' -e 'info!\(' -e 'warning:' -e 'showWarningMessage' --
# UX-TEXT-13: message sites with more than two sentences on the line; read the literal
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.tsx' ':(exclude,glob)**/*test*' \
  | xargs -0 -r grep -H -n -E -e 'show(Error|Warning|Information)Message\(' -- | awk '{ if (gsub(/[.!?]([ ]|$)/, "&") > 2) print }'
# UX-TEXT-31: of the snapshots with no help: last line, those that state no ground
git ls-files -z -- "$SNAP" | xargs -0 -r awk 'FNR == 1 && NR > 1 && last !~ /^help: / && !grounded { print name } FNR == 1 { name = FILENAME; last = ""; grounded = 0 } NF { last = $0 } /because|must |cannot |can only|requires|is not allowed/ { grounded = 1 } END { if (NR > 0 && last !~ /^help: / && !grounded) print name }'
```

| UX-TEXT-01 | Every error message states what failed, in terms of the user's action, and quotes the offending input (path, name, value, flag) whenever one exists. | What plus the input is the minimum that lets the user find the problem. 75 of 84 applicable exemplar samples and 17 of 20 measured product errors do it. The misses (`No target files found.`, `network operation attempted in offline mode`) are the ones a user cannot act on. | Per error path, a test passes an invalid input X and asserts that the rendered stderr, dialog or toast contains X. unverified: reading heuristic: could someone who saw only this message name the file or flag at fault? | MUST |
| UX-TEXT-02 | Every error carries a next step that is an action available in the product: a command, a flag, a setting, an environment variable or a button. When no action exists, the message says so and says what the product did. "Contact support" with no contact, and "try again" when nothing will change, do not count. | The next step is absent in 49% of 120 exemplar errors and 9 of 20 measured product errors. Spectrum and Atlassian require it, and [WCAG 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html) (AA) requires known corrections. | CLI: block UX-TEXT-02 lists snapshots whose last line is not `help: `. Each listed one needs a `note:` line stating that no action exists and what the product did. Never gate on action tokens in Rust `#[error]` strings: 83% to 84% lack one, against 45% of rendered errors that lack a next step. GUI: list the sites with the wrapper-aware search, meaning every message call plus every function that passes its own first parameter into one, repeated to a fixed point. One extension had 41 failure sites, not the 14 a direct grep finds. A reviewer confirms that a button, the text or a registered command title names a command, flag, setting, environment variable or button, or states that none exists. Token matching only orders the list: it passed 13 sites and flagged 28, and the 28 held 4 real misses, 6 next steps written as prose and 18 sites that relay a CLI's text and cannot be decided from source. Use no verb list: it fails `create`, `add`, `check` and `rename`. | MUST |
| UX-TEXT-03 | State a cause only when the code checked it. When one signal admits several causes, name every cause it admits. When the cause is unknown, name the operation that did not complete and give one recovery action. Never ship `Something went wrong`, `An error occurred`, `Unknown error`, a bare `Error` or `Failed`, or raw exception text as the message. | Atlassian says never invent a cause. NN/g and Apple HIG name the generic message as the failure pattern. A measured defect: a 401 for a repository that does not exist was reported as "registry authentication failed", which sent the user to log in instead of to the mistyped name. | See the first and second block UX-TEXT-03: the `generic` arm returns nothing (0 hits across 4,510 measured strings, so precision is undefined and the cost is zero), and a raw `.message` relayed into a toast is a finding unless the message is composed around it. For each `because`, `due to` or `caused by` in an error literal, point at the condition in code that established it. | MUST |
| UX-TEXT-04 | Every command, subcommand, flag, setting key or file that a message suggests must exist. Test it with the product's own parser. | A copy-pasted fix that fails is worse than no fix. One measured CLI suggested a command that is not a command, and its own unit test asserted the wrong text, so an agent told "keep tests green" preserves the defect. | See block UX-TEXT-04, which covers only commands written as run-backticks. It does not cover `use` or `pass` phrasing, flags, setting keys, environment variables or files. For those the error's own unit test asserts the suggested name: a flag appears in `$CLI SUBCOMMAND --help`, a setting key exists in the config schema or `package.json` `contributes.configuration`, a file path is created or documented by the product. Grep the tests for the same backticked command: a test asserting a nonexistent command is a finding, not a constraint. | MUST |
| UX-TEXT-06 | State a suggestion as a statement (``help: run `x` ``, clap's `tip: a similar subcommand exists: 'add'`). Write "Did you mean ...?" only when a prompt follows and will act on the answer. | The rustc dev guide says not to phrase suggestions as questions. A question with no prompt asks the user to answer a program that is no longer listening. | Block UX-TEXT-06 (arm `did-you-mean`): each hit is followed in code by a prompt call. 0 hits in two measured CLIs. | SHOULD |
| UX-TEXT-08 | One event, one message. Never print the same cause twice in one run. Never print a warning that the same run then repeats as an error. Raise one toast per failure, and none on a user-cancelled action. | The rustc guide says to avoid multiple messages for the same error. Measured: deno prints the same "Module not found" text as a warning and as an error, and one CLI printed a path twice in one line. | The gate is a snapshot assertion per failing-path fixture: the snapshot records the exact rendered output, and the reviewer who accepts it confirms each cause appears once. The two awk candidates in block UX-TEXT-08 are lists, not pass or fail, because a repeated `note:` or `help:` line or a shared heading can be right. Two narrow idioms are gates. Rust: no `Display` impl writes `self.a` and `self.b` where an `#[error]` string of `b`'s enum also interpolates `{a}` (precision 1 of 1, recall unknown: the `#[error("{path}: {source}")]` shape with a `#[source]` field needs type resolution). | UX-TEXT-09 | Do not print a success-shaped progress line (`Removing x from dependencies`, `Created config.json`) before an operation whose validation then fails. | UX-TEXT-10 | Emit a warning only when a condition may cause a later problem and the user can act on it or silence it. A warning names the action or the opt-out (flag, config key, lint level). A security-relevant notice is a labelled `warning:`, never an unlabelled info line. | Atlassian's definition of a warning and the rustc guide's "warning fatigue". Measured: `gh config set nosuch x` warns with no action, and one CLI prints an unlabelled info line about skipped signature verification on every unsigned install, which trains users to ignore the one security-relevant line. | Block UX-TEXT-10. | UX-TEXT-11 | Validate flags, arguments and syntax before contacting the network or a cluster, so a user's mistake is reported instead of the environment error that would mask it. | clig.dev says to validate input early. | UX-TEXT-13 | In a GUI notification or dialog, the title or first clause names the situation (never "Error" alone), the body is at most two sentences, and longer detail goes behind `Show Output`, `Show details` or a docs link. ## Strings That Survive

A fragment-built sentence is a translation hazard and, in English, harder to grep and test. Rows 24 and 26 are MUST once the owner adopts translation.

```sh
# UX-TEXT-26, 27, 29: noun-swap plurals, hand-rolled formatting, a hard-coded locale. Arms: ternary-plural, format, locale
git ls-files -z --cached --others --exclude-standard -- ':(glob)**/*.ts' ':(glob)**/*.tsx' ':(glob)**/*.jsx' ':(glob)**/*.vue' ':(glob)**/*.svelte' ':(glob)**/*.astro' ':(glob)**/*.rs' ':(exclude,glob)**/*test*' ':(exclude,glob)**/*spec*' \
```

## Ask the Owner

- Voice: any `please`, apology, humour, first person ("may I install here?") or "we", and a product-name prefix in notifications. Default to none until the owner decides.
- Whether strings will be translated, into which languages and with which catalogue (Fluent, ICU MessageFormat, MessageFormat 2). The answer sets UX-TEXT-24 and 26 to MUST.
- Renaming a shipped command or setting breaks keybindings and docs. Fix the quoting text first (UX-TEXT-21), and ask before renaming.
- Minting a public error code, changing a code's meaning or an exit code is a public contract change.
- How much a login, token or permission failure reveals (the WCAG 3.3.3 security exception). Keep a reviewed list of deliberately generic messages.
- Legal, consent, privacy and regulated wording: preserve it verbatim, never reword it.
- The byte-size convention when a surface has none, the time zone and form of an instant that is evidence, whether to auto-run a guessed command, the intent of an ambiguous image, and a support contact or bug-report URL in a message.

## What Agents Get Wrong Here

Ranked by how often each bites. Group 2 is plausible and unmeasured: the measured codebases carry agent configuration and have 0 hits.

1. **Shortest-path strings:** `showErrorMessage(e.message)` or `` `Failed to ${verb}: ${err}` `` relaying a raw cause (UX-TEXT-03). `` `${n} item${n === 1 ? '' : 's'}` `` or `item(s)` (UX-TEXT-25, 26). `(size / 1024).toFixed(1) + ' KB'` (UX-TEXT-27, 28).
2. **A sentence assembled from three template fragments to reuse a noun** (UX-TEXT-24).
3. **A suggested command or flag that does not exist, by analogy with another CLI**, pinned by a test that asserts the wrong text (UX-TEXT-04).
4. **An error with no next step**, and a "next step" that is "contact support" or "try again" (UX-TEXT-02).
5. **An invented cause**, `Network error` for any thrown value, or one cause named where the signal admits two (UX-TEXT-03).
6. **A logger line shown as the user's notice**, with a timestamp and level, and a warning followed by the same error (UX-TEXT-08, and UX-TEXT-07 in `ux-cli`).
7. **Stock copy:** "Oops! Something went wrong. Please try again.", "Click here", "Learn more", a success toast ending in `!` with an emoji, `OK`/`Cancel` as a decision (UX-TEXT-03, 14, 16, 17).
8. **A bare `Done` or `Copied <name>` that does not say what was copied** (UX-TEXT-30).
9. **A label quoted from memory in the README or a manifest** (UX-TEXT-21).
10. **Title Case web buttons, sentence-case VS Code command titles** (UX-TEXT-15).
11. **An invented API (`Intl.MessageFormat`) or an invented limit** such as a reading grade or a character budget (UX-TEXT-27).
